SHIWEN NI, Artificial Intelligence Research Institute, Shenzhen University of Advanced Technology, China Large language models are increasingly used to generate test scenarios, executable test suites, assertions, interaction sequences, and fuzzing infrastructure. These artifacts serve different purposes and rely on different sources of information about correct behavior. A test that increases implementation coverage, a test that agrees with a reference program, and a test that detects a requirements violation therefore provide distinct kinds of evidence. We present a structured narrative survey that connects the generation process to the evidence used to justify test quality. Drawing on 95 curated source records through 29 September 2026, we organize the field along four dimensions: testing objectives and artifacts, information available during training and generation, generation and learning mechanisms, and evaluation evidence. We synthesize work on unit and requirements-based testing, test oracles, API and GUI testing, fuzzing, and learned test generators. The resulting framework explains how execution feedback can improve executability while also affecting the independence of an oracle, why specification provenance and training-time reference supervision matter for comparisons, and how downstream code-selection gains differ from test correctness. We use these distinctions to organize benchmarks and derive a research agenda for independent oracle assessment, budget-aware generation, repository-scale evaluation, and test maintenance. 1 Introduction 

Test generation requires a connection between what software should do and observations that can expose when it does something else. Constructing that connection involves several kinds of work: interpreting requirements, selecting inputs, arranging an execution environment, choosing observations, and expressing an expected result. Large language models (LLMs) can contribute to each of these activities because they operate across natural language, program code, and semi-structured technical documentation. Research has consequently expanded from generating unit-test code to producing acceptance scenarios, postconditions, API call sequences, and fuzzing drivers [75, 85, 91].

This breadth creates a comparison problem. Two approaches can both generate executable tests while having different access to the system under test (sut), different sources of expected behavior, and different intended uses. A regression generator may inspect an implementation and retain tests that pass on it. A requirements-driven generator may need to produce an oracle before an implementation exists. An issue-reproduction agent may receive a report of an already observed failure. The same passing test carries a different meaning in each setting. Comparing their coverage or execution success without describing these conditions obscures what has actually been learned about test quality. TestGen-LLM filters regression improvements through execution and coverage [3]; CoverUp uses coverage to guide generation [57]; PyTester trains description-conditioned generation using reference execution [70]; UTRL couples code and test generators through adversarial learning [36]. These methods differ in when behavior becomes available and how it influences tests. Existing surveys provide substantial foundations. Broad reviews map LLM applications across testing and repair [5, 75]; unit-testing surveys organize techniques, model adaptation, and quality assurance [11, 91]; requirements-based reviews cover transformations from natural-language and formal specifications [19, 85]. A recent systematic review directly addresses LLM-based test-case generation [71]. Oracle generation, hybrid techniques, and evaluation limitations already appear in these accounts. Our organizing question is how these aspects interact: what information produces a test, and what evidence justifies using that test to judge software? 

We develop this question through a structured narrative synthesis of a curated collection of 95 source records. The collection includes seven surveys and roadmaps, together with primary methods, benchmarks, empirical studies, and selected neural predecessors. Its breadth supports a cross-setting analysis; its preliminary screening status is described in Section 3. We make three contributions. First, we define a framework that separates testing objectives, generated artifacts, information access, and quality evidence. Second, we use the framework to connect prompting, program analysis, feedback, agents, and model training across testing settings. Third, we organize evaluation designs according to the claims they can support and derive concrete research questions from the remaining mismatches. The central argument is that test generation should be understood as both an artifact-construction problem and an evidence-construction problem. Better syntax and broader execution improve the first. Confidence in expected behavior requires the second. This distinction helps explain when tools from different research traditions can be combined and which claims require additional validation. 

2 Foundations and Analytical Framework 2.1 What Is Generated? 

An executable test combines a setup, an input or action sequence, and an oracle that judges the resulting behavior. Its setup can include fixtures, mocks, dependencies, credentials, database state, and cleanup. Its input may be a function argument, an HTTP request, a GUI action, or an entire generated program. Its oracle may check an exact output, an exception, a relation across executions, or a safety property. A test suite additionally determines which tests coexist, how state is isolated, and when execution ends. Many generation methods produce an intermediate artifact. A natural-language scenario still requires operationalization. A grammar defines a family of admissible inputs but does not necessarily determine their expected outputs. A fuzzing driver connects generated data to a target API while relying on a separate failure detector. We therefore distinguish test design , test input , test oracle ,

2.2 Testing Objectives Determine Oracle Roles 

Functional conformance asks whether behavior satisfies an external requirement. Regression testing asks whether a change violates behavior that should be preserved. Bug reproduction asks whether a reported failure can be exercised and distinguished from its repair. Fuzzing often searches for crashes, sanitizer violations, or disagreement among implementations. Tests used in code generation may instead rank candidate solutions or provide debugging feedback. These objectives can share execution machinery while requiring different oracle evidence. Consider a requirement that a function return a sorted permutation of its input without modifying the input. A test may assert the sorted result yet omit the mutation constraint. It can execute successfully and reach every line while leaving part of the requirement unchecked. A test copied from an implementation that sorts in place can even preserve the very violation that a conformance test should reveal. Conversely, a test that expects one particular ordering among equal-key objects may reject a legal implementation if stability was never required. This illustrative example motivates evaluating both detection of invalid behavior and acceptance of permitted behavior. 

2.3 Information Access and Correctness Evidence 

We distinguish three stages of information access: training, generation, and final evaluation. At each stage, relevant sources include requirements, focal code, repository context, existing tests, reference implementations, candidate implementations, execution traces, and human decisions. 4 Liang et al. 

Access is a property of an experimental variant rather than an entire paper. For instance, inference can use a description and signature even when training rewards require a reference program, as in PyTester [70]. Describing that configuration simply as “code-free” would erase a material dependency. An information source can play more than one role. Source code helps resolve imports and construct objects; the same code can also supply expected outputs. A static dependency graph can identify callable APIs without validating their semantics. Execution of a trusted reference provides a concrete output under the reference assumption. Execution of the candidate under test provides an observation about that candidate. These roles should be recorded separately because context relevance and oracle independence answer different questions. Specification provenance adds a fourth consideration alongside the three access stages. A doc-string generated from buggy code remains implementation-derived, even if the next generator receives only that docstring [95]. Conversely, a requirements-oracle study gives the generator requirements and minimal method structure, while researchers construct those requirements from buggy/fixed differences [46]. Generation permissions and dataset-construction permissions are therefore separate fields. A PR’s stated intent provides another behavioral source, interpreted alongside the change and before/after executions in Testora [58]. These sources can all be useful, but their independence from the behavior under examination differs. Figure 1 connects the four dimensions of our analytical framework: objectives and artifacts, information access, generation mechanisms, and quality evidence. The dimensions are intentionally orthogonal. “Agent-based” describes how decisions are coordinated; “requirements-based” describes an information source; “unit testing” describes a testing level. Treating these labels as competing branches of one taxonomy would place overlapping studies in arbitrary categories. We instead use testing settings to organize the landscape and mechanisms to explain recurring design choices. 

3 Review Scope and Synthesis Method 3.1 Research Questions 

Six questions guide the synthesis and connect its sections: 

RQ1: Objectives and artifacts. Which testing objectives, systems, and levels are addressed, and what artifacts are generated? Section 4 maps the settings and outputs. 

RQ2: Information and oracles. What information is available during training and genera-tion, and where does evidence of correct behavior originate? Sections 2 and 6 distinguish access stages and sources. 

RQ3: Generation strategies. How are LLMs combined with retrieval, analysis, execution, search, and agents? Section 5 compares these mechanisms. 

RQ4: Learning objectives. What do training data, rewards, and adversarial curricula opti-mize? Section 6 examines learned generators. 

RQ5: Evaluation evidence. Which quality claims do benchmarks support, and under what conditions are results comparable? Section 7 analyzes protocols and measurements. 

RQ6: Practical use and open problems. What is supported by development-workflow evi-dence, and which capabilities still need validation? Section 8 connects adoption, maintenance, and research directions.

3.3 Extraction and Interpretation 

The register records artifacts, information sources, mechanisms, analytical use, and inspection depth. Each entry was checked against a primary page or document. Most checks concern metadata and abstracts; selected passages establish information access, reward supervision, and metric definitions. We do not pool effect sizes or rank methods. Independent dual screening, inter-rater validation, and experimental reproduction have not been performed. We distinguish method descriptions, interpretations of measured properties, and evaluation recommendations. Reference checking describes a method; reference consistency interprets its evidence; testing alternative legal implementations extends the protocol. Recommendations are not reported findings. AI assistance was used to expand search terms, organize retrieved literature, propose the cross-study categories, draft the synthesis, and design its conceptual figures. The accompanying register preserves source links and inspection depth. The present coding has not received independent human validation. This status is relevant because category assignments can affect the survey’s conclusions even when individual bibliographic records are correct.

4.1 Unit Tests and Repository Context 

Unit-test generation is the most visible setting in the reviewed collection. The task appears local because the target is a function or method, but executable tests depend on surrounding types, imports, initialization, and test conventions. AthenaTest established an earlier transformer-based approach that uses focal context and supervised code–test data [73]. TestPilot combines function LLM-Based Test Generation 7

information and documentation with execution-based repair [62], while ChatUniTest organizes generation, validation, and repair into a framework [10]. These approaches illustrate the transition from generating a plausible test body to constructing an executable artifact in its environment. CITYWALK addresses project dependencies and C++ knowledge [93], exposing construction, linking, fixtures, and external dependencies absent from standalone-function tasks. Existing tests additionally supply conventions and an improvement baseline in TestGen-LLM [3]. Integration value and the validity of inherited behavioral assumptions remain distinct. ASTER makes static context and mocking part of test construction for Java and Python, while ChatTester combines generation with an iterative refinement process [54, 88]. KTester distinguishes knowledge used in test design from knowledge used in implementing the test [38]. Across these systems, framework familiarity, dependency resolution, and behavioral selection address different obstacles; an executable test need not be a well-chosen test. 

4.2 Requirements, Scenarios, and Acceptance Tests 

Requirements-driven generation begins with intended behavior expressed independently of an executable test. RAGTAG retrieves domain information to generate test scenarios from natural-language requirements [4]. Multi-step generation of system-level test specifications uses intermedi-ate artifacts to structure this transformation [50]. Both settings expose an important distinction: producing a useful test design and producing a runnable script are separate accomplishments, with different evaluation methods and human responsibilities. An industrial acceptance-testing study makes this separation explicit. AutoUAT transforms user stories into Gherkin scenarios, while Test Flow uses those scenarios and page HTML to construct Cypress scripts [18]. Information access changes between stages. The scenario can be judged against a user story; the script also needs knowledge of concrete page structure. APITestGenie similarly combines requirements and API specifications to generate web API tests [56]. These pipelines suggest that traceability should connect the requirement, the scenario, the executable actions, and the assertion, so that a failure can be attributed to the appropriate transformation. Change intent and industrial tickets add intermediate settings between independent requirements and code-conditioned regression. Testora uses PR intent with code changes, existing tests, and before/after behavior to identify regressions [58]. AToMIC combines JIRA tickets and recent code changes to construct Gherkin scenarios and mobile UI tests in an industrial case study [20]. Intent traceability and executable-script construction should be assessed separately; the availability of natural-language text does not by itself establish implementation-independent generation. 

4.3 Oracles, Postconditions, and Metamorphic Relations 

Oracle generation isolates the part of a test that decides whether behavior is acceptable. TOGA generates exception and assertion oracles using a neural approach [15]. TOGLL also learns asser-tion and exception oracles with code-conditioned prompts [24]. TOGA’s subsequent large-scale evaluation and replication work demonstrates the importance of examining oracle generation under changed evaluation conditions [25]. An oracle should therefore be assessed by the behavior it accepts and rejects, in addition to whether it resembles a developer-written assertion. Postconditions and metamorphic relations broaden the oracle representation. The nl2postcond work translates natural-language intent into executable method postconditions [16]. Work on executable metamorphic relations derives relations from requirements and API specifications [64]. A relation can test consistency across executions when predicting one exact output is difficult. Its applicability conditions are part of its meaning: a plausible transformation can be invalid for inputs that violate an unstated precondition. Thus, generating the relation and establishing its domain of validity remain distinct tasks. 8 Liang et al. 

Documentation can supply more explicit behavioral constraints. Doc2OracLL examines Javadoc components in oracle generation, whereas Tratto combines source and documentation with con-straints on the tokens available for constructing axiomatic Boolean oracles [26, 52]. Documentation selection concerns evidence relevance; grammatical and API constraints concern admissible expres-sions. Neither operation alone proves that a generated constraint captures the intended contract. Nexus uses execution-grounded multi-agent processes for oracle synthesis [27], and CANDOR incorporates multi-agent consensus into end-to-end JUnit generation [83]. These approaches combine test construction and oracle review. Their interaction patterns can expose contradictions, but the source of behavioral evidence still determines what agreement establishes. Agreement among agents or with candidate executions must be interpreted relative to the requirements being tested. 

4.4 API and GUI Interaction Sequences 

For APIs and GUIs, test generation must maintain state across actions. An endpoint can require a resource identifier returned by an earlier request; a GUI action can depend on a screen reached through navigation. AutoRestTest combines LLM support with multi-agent reinforcement learning for REST API testing [66]. SAINT uses program analysis and LLM-based agents for service-level integration tests [55]. LlamaRestTest adapts smaller models to API dependencies and input values using specifications and server responses, while ARMeta constructs executable metamorphic API tests from specifications [32, 33]. The relevant artifact is therefore a coordinated interaction sequence, including dependencies between operations, rather than a collection of independent input values. DroidAgent and GPTDroid apply LLM reasoning to mobile GUI exploration and interaction [43, 86]; ScenGen coordinates observation, decision, execution, supervision, and recording around mobile scenarios [87]. Here, observations and actions are interleaved: the next action depends on the current interface. Reaching a screen demonstrates exploration; checking that the screen implements a requirement additionally needs an oracle. This distinction also affects replay. A sequence generated through adaptive interaction may need stable selectors, state initialization, and checkpoints before it becomes a repeatable regression test. 

4.5 Fuzzing Inputs and Infrastructure 

Fuzzing gives the LLM a different role. TitanFuzz and FuzzGPT generate programs for testing deep-learning libraries, with the latter emphasizing edge cases [13, 14]. Fuzz4All uses LLMs in a broader fuzzing framework [81]. These methods exploit the model’s ability to produce structured inputs while relying on execution and external failure detectors to identify anomalies. The generated object can also be an input generator. ChatAFL extracts protocol-related infor-mation to support grammar construction and message-sequence exploration [48]. PromptFuzz generates fuzzing drivers [45]; ELFuzz searches over synthesized fuzzers [9]; Bulbasaur generates customized mutators using branch-oriented information [79]. G2FUZZ synthesizes reusable genera-tors for non-textual inputs such as binary files, extending this distinction beyond generated textual programs [90]. Scheduzz additionally couples API-combination constraints with driver generation and campaign scheduling [41]. This progression changes the cost model because one generated artifact can produce many executions. 4.6 Bug Reproduction and Tests for Code Generation 

LIBRO generates bug-reproducing tests from natural-language reports [31]. SWT-Bench evaluates test generation in the context of real-world fixes [53]. These settings provide a particular behav-ioral distinction: the test should expose the issue in a buggy version and accept a fixed version. Reproducing a known failure and discovering an unknown defect are related capabilities but use different information. Generated tests also influence which code is selected or how it is repaired. CodeT uses generated tests to help choose among candidate programs [8], UTGen learns tests for automated debug-ging [59], and CodeRM scales test generation for code reward modeling [47]. TiCoder introduces user feedback on tests to clarify intent during code generation [17]. In all four cases, the down-stream outcome depends on both the generator and the consumer of its tests. A useful survey must therefore retain test-level measurements alongside code-selection or repair outcomes. 

5 Generation Mechanisms 5.1 Context Construction and Task Decomposition 

Prompting determines which parts of a testing problem the model sees at once. Direct prompts usually combine a target, an instruction, and a desired output format. Examples can provide the test framework, naming conventions, and assertion style. Context construction becomes a substantive method contribution when it selects information needed to resolve dependencies or infer the intended behavior. TestPilot and ChatUniTest illustrate focal-code and environment-aware construction [10, 62]; RAGTAG illustrates retrieval of domain material for requirements interpretation [4]. Structural context construction complements retrieval. HITS slices methods to organize gener-ation around smaller code regions; TELPA incorporates program analysis and usage constraints to target difficult coverage; KTester supplies project and testing knowledge [38, 80, 84]. Slicing reduces the local reasoning unit, analysis identifies relationships outside it, and domain knowledge supplies conventions or behavioral rules. Their contributions should be compared at the obstacle each addresses. Retrieval has two separable functions. It can supply technical facts needed for execution, such as an API signature, or behavioral facts needed for an oracle, such as a business rule. These should be evaluated independently. An increase in compilation success can establish that retrieved API facts were useful without establishing that the retrieved business rule was current or applicable. A retrieval study on ML/DL APIs reports coverage improvements without improved correctness under its evaluation [63]. This provides conditional evidence that technical reach and behavioral judgment can respond differently to added context. Doc2OracLL’s documentation analysis and the context comparisons in a Java-oracle empirical study address related questions under different tasks [26, 51]; their outcomes should not be pooled into a universal ranking of retrieval sources. SymPrompt decomposes prompting around execution paths [61]; requirements pipelines separate interpretation, scenario construction, and scripting [18, 50]. Intermediate artifacts expose omitted scenarios, invalid locators, and wrong expectations as different errors. Their utility depends on final behavior as well as stage-specific success, because an early misunderstanding can propagate. 

5.2 Input, State, and Environment Construction 

Input construction must satisfy both the external input domain and the execution interface. Grammar-based methods such as SAGE and LogiCase make admissible input structures explicit [2, 67]; repository-oriented approaches must also recover fixtures and dependencies [93]. For API and GUI testing, validity extends to action order and state: a well-formed request can still be unusable 10 Liang et al. 

before a required resource is created [55, 66, 86]. These mechanisms solve different parts of reaching a meaningful observation. Exception tests make the setup obligation concrete: exLong conditions specialized generation on throw traces, guards, and existing non-exception tests [89]. ASTER’s mocking addresses dependen-cies that would otherwise block execution [54]. Reaching an exception and choosing whether that exception is expected remain separate decisions. For the sorting example, preserving a copy of the original input makes mutation observable. Sorted expected values alone omit this setup obligation. Rejected inputs, failed setup, and assertion failures should therefore have separate denominators. 

5.3 Oracle Construction and Representation 

An oracle can predict an exact result, check a property, relate several executions, or obtain a human judgment. Postconditions and executable metamorphic relations express behavioral constraints [16, 64]; TiCoder obtains user feedback to clarify intended behavior [17]; Nexus and CANDOR use agent interaction in oracle construction [27, 83]. The representation determines which behaviors the test can express, while the evidence source determines why those behaviors should be accepted. For sorting, ordering, permutation preservation, and unchanged input express the stated obliga-tions. Expecting a particular equal-key order can impose unstated stability. Oracle representation and applicability conditions therefore affect both fault detection and acceptance of legal behavior. 

5.4 Program Analysis and Hybrid Search 

Program analysis provides explicit structure that the model would otherwise need to infer from text. Dependency information can identify construction requirements; call relationships can constrain operation sequences; coverage can identify unexercised branches. CITYWALK and SAINT illustrate different uses of program structure for executable testing [55, 93]. The source of structure matters: a graph recovered from implementation describes reachable operations, while a behavioral contract specifies what those operations should mean. CODAMOSA combines search-based test generation with LLM-generated examples when cover-age progress stalls [37]. This division of labor is different from asking an LLM to generate an entire suite repeatedly. Search performs repeated local exploration, and the model supplies candidates that may open new regions. Fuzzing-driver and mutator generation extend the same principle to reusable generators [9, 45, 79]. G2FUZZ reuses synthesized generators, while Scheduzz allocates execution resources across campaigns [41, 90]. Model-call cost, artifact lifetime, and conventional search effort jointly determine the contribution of generation. Hybrid comparisons need matched search engines, instrumentation, stopping rules, and execu-tion budgets. Component ablations should isolate the model’s contribution while accounting for conventional computation. 

5.5 Execution Feedback and Iterative Repair 

Feedback can localize malformed syntax, missing dependencies, or unexercised branches. An assertion failure is ambiguous: the test, implementation, environment, or requirement interpretation may be wrong. The acceptance decision must preserve this distinction. CoverUp uses coverage and execution information in iterative Python test generation [57]. TestGen-LLM filters proposed improvements through operational criteria that support regression-test integration [3]. MuTAP uses mutation testing to guide generation [12]. These systems demon-strate that feedback can be used for different decisions: repair a candidate, reject it, request another test, or redirect search. 5.6 Agents, Collaboration, and Adversarial Generation 

Agent architectures assign responsibilities such as planning, code generation, execution, and review to separate components. TestAgent follows a workflow inspired by human testing and incorporates static knowledge and tool use [92]. CANDOR and Nexus emphasize collaboration around test oracles [27, 83]. The analytical question is what separation changes: available information, decision authority, search diversity, or execution budget. ConVerTest generates code and test candidates and screens them using self-consistency, verifi-cation prompts, and dual execution agreement [68]. It avoids requiring a pre-existing reference implementation, while still relying on generated implementations and their executions. VALTEST uses semantic entropy and a learned classifier to assess synthesized test validity [69]. Consensus and predicted validity are additional acceptance signals; their reliability depends on shared errors, training labels, and the evaluation distribution. Shared models and context can correlate agent errors. A checker querying an independent source contributes different evidence even when it uses the same model. Matched-budget controls should compare multiple roles with one combined-context agent, sampling and selection, and deterministic checking. AdverTest pairs test and mutant agents in an adversarial generation loop [7]. Such inference-time competition changes the current artifacts. It differs from reinforcement learning that changes model parameters across tasks, discussed in Section 6. Both can expose weaknesses in an existing test suite, but their generalization claims differ. A stronger suite for the current target is evidence about search; a stronger frozen model on new tasks is evidence about learning. 12 Liang et al.

6 Learning Test Generators 6.1 Supervised Learning and Training Data 

Training changes the generator’s behavior beyond one target or interaction. Supervised learning commonly uses code–test pairs or descriptions paired with tests. AthenaTest provides a historical example of learning unit-test generation with focal context [73]. Such data teach framework syntax and common assertion patterns, but the training label also encodes a particular developer’s testing choices. Multiple valid tests can exist for the same function, and a recorded test can be incomplete or redundant. Exact reproduction of a reference test is consequently a limited measure of learned testing ability. Training corpora and task-specific adaptation supply complementary evidence. CAT-LM aligns code and test files during pretraining; UniTSyn uses language-server information to extract focal-code/test relationships across languages [22, 60]. FuzzAug expands training data through coverage-guided fuzzing [23]. exLong specializes in exception tests, while TOGLL and Tratto learn oracle construction [24, 52, 89]. These examples distinguish learning repository correspondence, expanding observed inputs, and specializing a behavioral judgment. UniTSyn is principally a training-data resource, rather than another end-task evaluation benchmark. Data filters determine the supervision: passing examples teach executability; discriminating exam-ples additionally depend on the chosen faulty-program pool. Held-out projects and independently constructed faults test whether training transfers beyond that pool. 

6.2 Reinforcement Learning and Reward Meaning 

PyTester combines supervised learning and reinforcement learning for text-to-test generation, using automatic signals that include executable reference information [70]. RLSQM learns from automatic feedback associated with unit-test quality [65]. These approaches illustrate why the reward must be described in terms of the property being optimized. Syntax, execution success, structural coverage, maintainability, and semantic validity are related engineering concerns, but a reward for one does not directly establish improvement in another. CURE makes the supervision distinction particularly clear. Its main co-evolutionary training setting omits ground-truth code supervision but pairs tasks with ground-truth unit tests, which help label generated programs and construct coder/tester rewards [78]. Thus, absence of a reference implementation does not establish absence of reference supervision. Candidate programs, reference tests, and reference code must each be recorded, including changes across ablations. Training access and inference access describe different dependencies. PyTester can generate from a description while training rewards execute a reference [70]. Reference passing also assumes that the reference satisfies the requirement and that the test ignores incidental behavior. Table 3 records stage-specific evidence, rather than assigning one black-box label per paper. Rewards should improve detection while constraining rejection of permitted behavior. Reference consistency is a practical proxy when alternative legal implementations are unavailable; the refer-ence assumption remains explicit.

7 Benchmarks and Quality Evidence 7.1 A Quality Profile Rather Than a Single Score 

We organize test quality as a profile of complementary properties. Input validity asks whether the input satisfies the task’s domain constraints. Executability asks whether the test can be built and run in the intended environment. Oracle correctness asks whether its judgment follows the intended specification. Defect detection asks whether it rejects relevant invalid behavior. Non-rejection asks whether it accepts permitted behavior. Coverage, stability, maintainability, and cost add further dimensions needed for deployment. Denominators differ: compilation can cover all attempts, whereas coverage and mutation often use retained tests. Report attempted, executable, accepted, and retained artifacts to expose filtering. Per-test and per-suite results are complementary, since one invalid assertion can cause an otherwise useful suite to reject a correct implementation. Figure 3 connects each observation to its bounded interpretation. Coverage measures reach; mutation depends on its fault model and test validity; reference passing assumes a suitable reference. Assertion matching measures similarity, code-selection accuracy measures downstream utility, and repeated-run passing measures stability. These signals remain useful at their respective levels.

7.3 Implementation State and Metric Interpretation 

Empirical studies increasingly separate tests generated from correct and buggy code. Work on incorrect-code influence and buggy-code misguidance examines how implementation errors affect generated judgments [28, 95]. Replacing code with a generated docstring can change that influence, but the docstring remains code-derived [95]. The requirements-oracle study instead evaluates requirement agreement separately from agreement with the SUT; its ten Lang-bug cases and repair-derived requirement construction bound the setting [46]. The same distinction qualifies proxy metrics. A replicability study reports that coverage and muta-tion can inform model comparison in regression settings where code is reasonably assumed correct, while their reliability for detecting existing bugs is weaker [94]. Test Wars also illustrates that mutation, coverage, and fault-detection rankings can differ across LLM, search-based, and symbolic approaches [1]. These observations support task-specific metric interpretation, rather than discard-ing structural metrics. The Java-oracle study uses developer-oracle comparison as a correctness proxy and mutation as a detection proxy [51]; neither exhausts specification conformance. Fuzzing adds a related failure-attribution problem. A crash from a generated driver can reflect an invalid API use rather than a reachable product defect. Google’s OSS-Fuzz-Gen report examines false-positive mitigation using API constraints and realistic entry-point context [49]. Valid input or driver construction, reproduced failure, and confirmed defect should therefore be separate stages of the reporting funnel.

7.5 Comparability, Leakage, and Cost 

Comparisons need matched information contracts: requirements-only generation, reference access, and candidate-feedback repair are different settings. Training data, retrieval, existing tests, and evaluation artifacts can cross intended boundaries. Contamination controls should identify the paths they address. Cost should include model calls, input and output tokens, conventional executions, environ-ment preparation, and human intervention. For trained generators, training cost and deployment cost answer different questions and should be reported separately. For hybrid fuzzers, execution throughput and the reuse of generated infrastructure matter. For agent systems, total calls across all LLM-Based Test Generation 17

Generation randomness and execution nondeterminism are separate sources of variance. Project-level results, repeated generation, repeated execution, failed attempts, and stopping rules make uncertainty and selection effects assessable. 

8 Practical Integration and Research Agenda 8.1 Choose a Workflow from the Testing Objective 

Workflow selection starts with the behavioral decision, available evidence, and missing artifact. Regression augmentation can use existing tests and coverage, as in TestGen-LLM [3]. Conformance needs requirement-backed judgments; fuzzing needs valid generators and failure attribution; inter-active code generation can use user-confirmed examples, as in TiCoder [17]. Assertion provenance connects these choices to review and maintenance. 

8.2 Industrial Adoption and Human Revision 

Industrial evidence includes different acceptance decisions. TestGen-LLM studies improvement of existing tests through operational filtering [3]; the acceptance-testing case study evaluates both generated scenarios and their conversion into executable scripts [18]. RAGTAG and system-level test-specification generation additionally involve domain interpretation and assessment [4, 50]. ASTER adds dependency handling and mocking, while AToMIC connects industrial tickets to mobile acceptance scripts [20, 54]. The OSS-Fuzz-Gen report adds failure-validation work to the adoption burden [49]. A scenario judged useful by an engineer and a script accepted into a regression workflow are distinct outcomes. A deployment evaluation should retain these stages: generated, reviewed, revised, executed, and adopted. Human effort includes interpreting requirements, supplying missing context, correcting assertions, and maintaining the accepted test. Reporting the time and rejection reasons at each stage would connect the artifact’s technical quality to its actual workflow value. The reviewed examples motivate these dimensions; this synthesis does not pool their heterogeneous adoption measures. 

8.3 Oracle Provenance and Independent Validation 

Linking an assertion to a requirement clause, validated example, formal property, or regression observation could guide acceptance and repair. The research question is whether checked prove-nance improves oracle quality and maintenance. A matched-budget comparison should measure unsupported assertions, rejection of legal implementations, independent detection, and review time. Plausible explanations without verified evidence links do not establish that benefit. 

8.4 Feedback That Preserves Valid Tests 

Repair should recover invalid tests while preserving valid judgments. Branching from the same initial artifact allows separate measurement of recovery and regression, followed by independent suite evaluation. Controls can compare setup-only repair, unrestricted repair, no semantic repair, and trusted-reference checking. The information and budget must match; improved passing alone cannot determine whether assertions were corrected or weakened. 

8.5 Generalization in Learned and Adversarial Testers 

Adversarial curricula offer difficult errors [36, 40, 82], but transferable capability requires a frozen tester evaluated on new opponents, repositories, and specification styles. Suite rewards also obscure 18 Liang et al. 

which tests help or mislead. Comparing aggregate rewards with verified test-level feedback can test the value of finer credit assignment, while retaining validity constraints and independent detection. 

8.6 Repository Scale and Lifecycle Evaluation 

TestGenEval, CITYWALK, and service-level testing provide repository-oriented starting points [30, 55, 93]. Lifecycle evaluation should additionally label whether a change preserves semantics or deliberately changes requirements. Evolution and database-flakiness studies motivate retaining prior tests and measuring execution stability, maintenance effort, and unintended-regression detection [6, 21]. Version-aware retrieval should be compared with unrestricted context reuse, since existing tests can preserve brittle setup or obsolete obligations. 

8.7 Reproducible Evidence and Efficient Allocation 

Reproducibility packages should expose the path from request to retained suite. Relevant records include model and prompt versions, context selection, generated candidates, tool feedback, repairs, rejection reasons, and final evaluation inputs. This enables analysis of why one method succeeds and whether its filters hide a large failure burden. For training methods, data construction and reward implementation are equally important. Budget allocation is another cross-cutting research question. A fixed budget can be spent on generating more candidates, checking oracles, executing additional faults, or resolving uncertain requirements. Dynamic scaling in CodeRM [47] and reusable fuzzing infrastructure [9, 45, 79] illustrate different responses to this allocation problem. A broader study could compare these investments under a common deployment objective, such as maximizing independent detection while bounding invalid-suite rate and latency. 

9 Threats to Validity 

The collection supports a qualitative map of research directions rather than estimates of their prevalence. Web-based discovery, English-language emphasis, and the stated source restrictions can omit relevant studies. Performance, accessibility, concurrency, and distributed-system testing received less focused coverage than functional testing and fuzzing. Selected neural predecessors provide context but do not constitute a complete history of learned test generation. Inspection depth varies: abstract-level evidence supports broad mechanism descriptions; context permissions, reward definitions, and denominators require fuller coding. We do not pool numerical gains. Multi-database retrieval, complete variant extraction, and independent coding remain nec-essary for a systematic extension. The framework has not undergone inter-rater validation, and multi-stage methods can occupy several categories. Preprint revisions, changing model services, and publication bias further limit the dated synthesis. 

10 Conclusion 

LLM-based test generation spans scenarios, executable suites, oracles, and reusable fuzzing infras-tructure. We connected these artifacts to their information sources, generation mechanisms, and evaluation assumptions. The synthesis separates executable construction from oracle justification: coverage, reference consistency, patch discrimination, independent detection, and acceptance of legal behavior supply complementary evidence. Making information access, evidence provenance, and cost explicit supports more interpretable comparisons and guides research on generators that remain useful across repositories, adversaries, and software changes.

# PreMaQ: Predicting Maintainability-Related Quality of LLM-Generated Code Before Generation 

Taiki Wakamatsu ∗, Yuta Ishimoto †, Masanari Kondo ∗, Yasutaka Kamei ∗∗Kyushu University, Fukuoka, Japan †The University of Osaka, Osaka, Japan t.wakamatsu@posl.ait.kyushu-u.ac.jp, ishimoto@ist.osaka-u.ac.jp, {kondo, kamei }@ait.kyushu-u.ac.jp 

Abstract —As large language models (LLMs) become increas-ingly capable of code generation, adopting generated code in software development requires assessing not only its functional correctness but also its maintainability-related quality. If such quality could be estimated before generation, developers could avoid the cost of generating, reviewing, and discarding low-quality code. Although prior work has shown that the func-tional correctness of the LLM-generated code can be predicted in advance, it remains unclear whether maintainability-related quality is similarly predictable. We introduce Pre-Generation Maintainability-Related Quality Prediction (PreMaQ), which predicts the Code Smell Score (CSS) and Maintainability Index (MI) of generated code from the internal representations of LLMs before generation. Our evaluation covers four open-weight LLMs and four Python code generation benchmarks, comprising 2,695 tasks in total. Our results show that predicted CSS and MI consistently correlate with their observed values across all 16 model–benchmark combinations, achieving mean Spearman rank correlations of 0.57 and 0.65, respectively. When used for model selection, PreMaQ achieves 59.5% of the maintainability-related quality improvement attainable by an ideal maintainability-based selector over random selection on tasks for which multiple models generate functionally correct code. Combining predictions from PreMaQ and prompt embeddings increases this proportion to 60.7%, indicating that the two signals are complementary. These findings suggest that PreMaQ can be used to predict and improve the maintainability-related quality of LLM-generated code. 

Index Terms —LLM-generated code, internal representations, maintainability-related code quality assessment 

I. I NTRODUCTION 

Large language models (LLMs) are now widely used to generate code, supporting tasks that range from code comple-tion to whole-function generation. However, using such code in real-world development requires developers to inspect it and revise it where necessary. Prior studies report that LLM-generated code may contain functional errors [1], security vulnerabilities [2], [3], code smells [4], [5], and maintainability issues [6], [7]. Verifying and revising LLM-generated code also imposes additional effort and cognitive load on develop-ers [8]. Assessing generated code therefore requires looking beyond whether it passes tests and considering maintainability-related quality, such as code smells and structural complexity. Maintainability-related quality is typically assessed by ap-plying static analysis to the code after it has been generated. However, code generation itself incurs computational cost and latency, and the generated code may still be functionally incorrect or difficult to maintain. If such code is discarded after generation and evaluation, both generation and evaluation costs are wasted. To reduce unnecessary code generation, prior work has used internal representations available before or during generation to predict properties of generated code. For example, such internal representations have been used to predict functional correctness [9]–[11] and compilability or vulnerabilities [12]. However, these studies mainly target functional correctness or security, and whether internal rep-resentations can predict maintainability-related quality before generation remains unexplored. Motivated by this open question, this study introduces and evaluates Pre-Generation Maintainability-Related Quality Prediction (PreMaQ) , which uses prefill activations to predict maintainability-related quality before code generation. Prefill activations are the internal representations computed while an LLM processes the input prompt. Figure 1 shows the PreMaQ workflow. As the maintainability-related quality to be predicted, we use the following two indicators used in a prior study [13]: Code Smell Score (CSS) [7], [14] and Maintainability Index (MI) [15], [16]. We evaluate prediction both within and across benchmarks to examine whether it extends beyond benchmark-specific pat-terns. As a downstream analysis, we examine the model selec-tion problem of identifying, among multiple models known to generate functionally correct code for a task, the model likely to produce code with the highest maintainability-related qual-ity. Our evaluation uses four open-weight LLMs (DeepSeek-Coder-6.7B-Instruct, Qwen2.5-Coder-7B-Instruct, Phi-4, and Qwen3.5-27B-FP8) and 2,695 tasks drawn from four Python code generation benchmarks (HumanEval+, MBPP+, Big-CodeBench, and LiveCodeBench). This section reviews prior work to position our work, and then reports a preliminary study that motivates the need for predicting maintainability-related code quality and selecting models likely to produce maintainable code accordingly. 

A. Related Work 

Analysis of LLM Internal Representations. LLM internal representations refer to hidden states or activations computed during prompt processing or token generation. They include the outputs of the attention and MLP modules and the residual stream, computed at each layer for each token position. Because these representations reflect how an LLM processes a given input, prior work has used them to infer properties of the LLM’s behavior and outputs. Azaria and Mitchell [17] showed that the truthfulness of LLM output can be inferred from internal representations. Zhou et al. [18] detected jailbreak attacks using a neuron activation coverage metric defined over internal representations. 

Prediction of Output Quality. Because generating output with an LLM incurs computational and financial costs, prior work has sought to estimate output quality before it is pro-duced. Some methods predict the output quality of each LLM from the input or previous responses and select a model for the task, and others escalate to a more capable model when adequate quality is not expected [19], [20]. For code com-pletion, prior work has predicted reference-based completion similarity from the prompt [21]. For code generation, internal representations have been used to assess properties of gener-ated code, including functional correctness [9]–[12], [22], [23], compilability [12], and the presence of vulnerabilities [12], [24]. However, the predicted properties are mainly functional correctness or security, and whether maintainability-related quality indicators, such as CSS and MI, can be predicted before generation remains unexplored. This study therefore investigates whether these indicators can be predicted before generation from internal representations.

P RE MAQThis section describes PreMaQ, our approach for predicting the quality of generated code from prefill activations before generation begins. We first formulate the problem and then de-scribe the internal representations used as features, the quality indicators to be predicted, and the predictor architecture. 

A. Problem Formulation 

PreMaQ predicts the maintainability-related quality of the code that an LLM will generate, using the internal represen-tations computed while the LLM processes the input prompt. Hereafter, we refer to these representations as prefill activa-tions . Let D be a set of input prompts in a code generation benchmark, and let f be an LLM that generates code. For a prompt x ∈ D , we denote the code generated by f as 

f (x). For a quality indicator q, the quality of this generated code is denoted by q(f (x)) . The code quality predictor gD

> f,q

takes as input the feature vector zf (x) derived from the prefill activations obtained by forwarding x through f , and predicts the value of the quality indicator q(f (x)) . Because zf (x) can be obtained with only one forward pass, the quality can be estimated without paying the cost of code generation. Since the dimensionality and distribution of zf (x) differ across LLMs, we train an independent predictor gD 

> f,q

for each combination of benchmark D, LLM f , and quality indicator q.

B. Prefill Activations and Features 

As prefill activations, we use neuron outputs at the final token position immediately after the LLM f processes the prompt x. In autoregressive LLMs, because of the causal attention structure, only the final token position can attend to all tokens in the prompt. Thus, the neuron outputs at the final token position reflect the internal representation after the model f has processed the entire prompt x; prior work has also used internal representations from this position [17], [18]. We therefore use this final-token position to obtain representations after the whole prompt has been processed. Let Lf be the number of stacked Transformer blocks in 

f , and let df be the dimensionality of its hidden states. Let

C. Quality Indicators to Be Predicted 

We describe the quality indicators used as prediction targets in this study. Following Kuang et al. [13], we choose indicators from two perspectives: the maintainability-related quality that this study focuses on, and functional correctness, which has been widely predicted in prior work [9], [11], [12] and serves as a comparison target. 

Functional Correctness. We evaluate and predict functional correctness using AvgPassRatio, as adopted in prior code-generation studies [13], [25], [26]. It is the fraction of test cases passed by the generated code. Let Nt be the total number of test cases associated with a task, and let Np be the number of test cases passed by the generated code. AvgPassRatio is calculated as Np/N t. Its range is [0 , 1] , and a higher value indicates better code generation performance in terms of functional correctness. 

Maintainability-Related Quality. We evaluate and predict maintainability-related quality using Code Smell Score (CSS) and Maintainability Index (MI). CSS [7], [13], [14] is a code quality indicator based on static analysis. It is computed by weighting the violations detected by Pylint [27] by message type, normalizing their weighted sum by the number of statements in the code, and subtracting the result from the maximum score:

This section presents the research questions, subject models and benchmarks, data splits, predictor training and evaluation settings for RQ1, model selection procedure and evaluation for RQ2, and implementation details. 

A. Research Questions 

We formulate the following research questions to examine prediction performance and its application to model selection. 

RQ1 How well does PreMaQ predict the maintainability-related quality of generated code? 

RQ2 How does PreMaQ-based model selection compare with selection without internal representations in terms of maintainability-related quality? 

RQ1 evaluates PreMaQ’s prediction performance within and across benchmarks for each LLM–benchmark combina-tion, using functional correctness as a comparison target and comparing four activation sources. RQ2 evaluates whether PreMaQ-based model selection improves maintainability-related quality over strategies without internal representations. To isolate maintainability-related quality, we restrict the can-didates for each task to models known to generate functionally correct code. This setting with known functionally correct candidates builds on prior work on pre-generation prediction of functional correctness [9], [10]. 

B. Experimented Large Language Models 

Table III summarizes the models experimented in this study. We use four open-weight LLMs: DeepSeek-Coder-6.7B-Instruct [29], Qwen2.5-Coder-7B-Instruct [30], Phi-4 [31], and Qwen3.5-27B-FP8 [32]. We focus on open-weight mod-els because their internal representations can be obtained. To reduce dependence on specific model characteristics, we include both code-specialized and general-purpose models, with sizes ranging from 6.7B to 27B parameters. We also include a model that uses hybrid attention, in addition to models based on self-attention (Table III). Recent LLMs have adopted increasingly diverse architectures. Including this model broadens the architectural variation among the subject models and allows us to examine whether prefill activations are useful beyond models with a single attention architecture. We use decoder-only models, an architecture commonly used for code generation [33]. 

C. Benchmarks 

We use four representative Python code generation bench-marks: HumanEval+ [34], [35], MBPP+ [35], [36], Big-CodeBench [37], and LiveCodeBench [38]. Each benchmark consists of tasks that take natural-language problem descrip-tions as input and require the model to generate the corre-sponding programs. Each task also includes multiple test cases for judging whether the generated code works correctly. For BigCodeBench, we exclude 42 tasks whose benchmark-provided canonical solutions do not pass the accompanying tests in our execution environment, and use the remaining 1,098 tasks. For LiveCodeBench, we use dataset version v6. As a result, HumanEval+, MBPP+, BigCodeBench, and LiveCodeBench contain 164, 378, 1,098, and 1,055 code generation tasks, respectively, for a total of 2,695 tasks. 

D. Data Splits for Training and Evaluation 

For each LLM–quality-indicator combination, we train and evaluate gD 

> f,q

in two settings: a within-benchmark setting, which uses data from the same benchmark, and a cross-benchmark setting, which uses data from different bench-marks. In each setting, let Dtrain be the set of prompts used to train gDtrain  

> f,q

and let Deval be the set of prompts used for evaluation. For the within-benchmark setting, we use 5-fold cross validation. For the cross-benchmark setting, we train the predictor on three of the four benchmarks and evaluate it on the remaining benchmark. Standardization statistics are computed only from the training folds. 

E. Model Training Setting 

The prediction targets, AvgPassRatio, CSS, and MI, are all learned as regression targets, and the loss function is mean squared error (MSE). We use MSE as the training objective because it is a standard smooth loss for continuous regression. During training, we normalize all prediction targets to the range [0 , 1] . For the 5-fold cross validation, we fix the random seed for fold assignment and obtain out-of-fold predictions so that every task is included in the evaluation data exactly once. These settings are shared across all combinations of LLM, benchmark, prediction target, and input feature. Only the input features and labels differ across combinations.

The observed value q(f (x)) is obtained by actually generat-ing code with the LLM. We consider two perspectives: (1) absolute error between predicted and observed values, and (2) correlation between predicted and observed values. G. Model Selection Procedure for RQ2 

In RQ2, we apply the predictors constructed in RQ1 to model selection for code generation on each task. 

Model Selection Problem. RQ2 addresses the problem of selecting the model likely to generate code with the high-est maintainability-related quality among functionally correct candidates. We restrict the analysis to tasks for which at least two of the four models generated functionally correct code. For each such task, we assume that the functionally correct models are known and use them as candidates for selection. The upper part of Figure 2 illustrates this task filtering process. This setting builds on prior work on pre-generation prediction of whether a model can solve a task [9], [10]. 

Maintainability-Related Quality Indicator for Selection. To rank candidate models by a single criterion, we use a score that rewards both fewer code smells and higher maintainability. Specifically, we normalize CSS and MI to [0 , 1] as c =CSS /10 and m = MI /100 , and define the Maintainability-Related Quality Score (MRQS) as their harmonic mean: 

MRQS = 2 cm/ (c + m), where MRQS = 0 when c + m = 0 .

Selection Procedure. For each task, we select the candidate model with the highest predicted MRQS and record the ob-served MRQS of its generated code. For the prediction-based strategies, each task is scored using out-of-fold predictions, so the predictor used for that task is not trained on the task itself. 

Selection Strategies. We compare six selection strategies on the same target tasks, covering a lower bound, baselines, our proposed white-box approach, a combination strategy, and an upper bound. The lower part of Figure 2 illustrates the strategies. (1) Random (lower bound) : randomly selects one candidate with equal probability, serving as a lower bound. (2) Average-best (baseline) : selects the candidate model with the highest mean observed MRQS across all tasks in the four benchmarks. This is a fixed, post-hoc reference that does not use task-specific information. It selects the candidate model with the highest predicted MRQS. This is a black-box baseline because it does not access the internal representations of the candidate models. This strategy follows prior work in predicting output quality from prompt-derived information [20], [21]. H. Implementation Details 

All experiments were run on a machine equipped with an Intel(R) Xeon(R) w7-2595X CPU (26 cores, up to 4.8 GHz) and an NVIDIA RTX 6000 Ada Generation GPU. Detailed version information for all libraries is available in our replication package. V. R ESULTS 

In our environment, training one predictor took approxi-mately 4 to 33 seconds, depending on the feature dimension-ality and the number of tasks. Quality prediction with a trained predictor took less than 0.4 ms per task. The additional compu-tation required for quality prediction is only one forward pass for obtaining prefill activations and the predictor inference, making it much faster than generating code and measuring its quality afterward.

RQ2 shows that PreMaQ can improve the maintainability-related quality achieved by model selection in a setting with known functionally correct candidates. This section discusses how maintainability-aware model selection could support de-velopers who use LLMs for code generation. First, we present a concrete example in which PreMaQ chooses a higher-quality output over another functionally correct output. We then discuss how maintainability-aware model selection can be integrated with functional-correctness prediction, examine the runtime overhead of using internal representations, and provide practical guidance. 

Impact. A concrete example illustrates an observable quality difference associated with model selection. To illustrate this difference, we examine BigCodeBench/650 , for which three models generate outputs that pass all benchmark tests. PreMaQ selects Qwen3.5-27B-FP8, whose output fol-lows the standard usage of pytz for timezone localization. The excerpts below show the lines relevant to this comparison.

Integration. Maintainability-related quality prediction can be integrated with functional-correctness prediction. 

Prior work [9], [10] has used pre-generation predictions of functional correctness to select a model. These activation-based routing methods provide a direct integration point with our approach. For example, Lugoloobi et al. [9] use prefill activations to predict the probability that each candidate model will solve a task and select a model based on the predicted probability and inference cost. Our predictions of maintainability-related quality can be incorporated into this routing process as an additional selection criterion. A routing policy could either filter candidates by predicted correctness before considering predicted maintainability-related quality and inference cost, or jointly combine all three criteria ac-cording to developer priorities. Both designs move beyond the RQ2 setting with known functionally correct candidates by using predicted correctness. This additional prediction of maintainability-related quality does not require another LLM forward pass. The router already performs a prompt forward pass for correctness prediction, so our prediction requires only capturing the necessary internal representations and running the maintainability-related quality predictors. The resulting runtime overhead is sufficiently low for practical use, as discussed in the next subsection. 

Efficiency. Internal representations enable efficient maintainability-related quality prediction. As shown in Table VII, in a standalone pipeline after model loading, the dominant per-task runtime cost is the prompt forward pass with internal representation capture, which takes 145 .7 ms on average. Predictor inference takes only 0.252 ms, while quality scoring and selection require negligible time. Guidance. PreMaQ is best used alongside prompt em-bedding when white-box access is available. In RQ2, combining predictions from PreMaQ and prompt embeddings achieves the best selection performance, with a relative gain of 60 .7 %. Thus, when internal activations are accessible, PreMaQ should be used as an additional signal alongside prompt-embedding predictions. For API-only models without access to internal activations, prompt embeddings provide a black-box alternative, which achieves a relative gain of 49 .6 %in our evaluation. Our combination uses a simple average of the two predictions; weighted or learned combinations are left for future work. VII. T HREATS TO VALIDITY 

Construct validity. This study evaluates maintainability-related code quality using CSS and MI, but these metrics do not cover other quality aspects, such as readability and execution efficiency. In addition, MRQS, which is used in RQ2, is one way to combine CSS and MI. Changing how the two metrics are combined may change the selection results. 

Internal validity. The code generated by an LLM depends on the prompt format. To reduce quality degradation caused by arbitrary prompt formats, we followed the official prompt format provided by each benchmark. The prediction results also depend on the configuration of the MLP predictor, and using different settings may change prediction performance. 

External validity. The results of this study are based on four local models and four Python code generation bench-marks. To improve generalizability, we included both general-purpose and code-specialized models, evaluated benchmarks with different levels of complexity, and further conducted cross-benchmark evaluation. However, it remains untested whether the results generalize to larger models, different model families, or programming languages other than Python. The prompt embedding baseline uses only all-MiniLM-L6-v2, and using a different embedding model may change the comparison results. RQ2 uses a setting with known functionally correct can-didates. Section VI outlines integration with pre-generation functional-correctness prediction, but we do not evaluate it end to end. The quality improvement reported in RQ2 may vary depending on prediction accuracy and the routing policy. VIII. C ONCLUSION 

This study proposed PreMaQ, which predicts the maintainability-related quality of LLM-generated code from prefill activations, and evaluated its use in model selection. Using four open-weight LLMs and four Python code generation benchmarks, we found that predictions of CSS and MI are correlated with their observed values in all within-benchmark model–benchmark combinations. Prediction also generalizes across benchmarks for most combinations, more consistently for MI than for CSS. In the RQ2 setting with known functionally correct candidates, PreMaQ-based model selection outperforms the evaluated strategies without internal representations, while combining predictions from PreMaQ and prompt embeddings achieves the best selection performance. These findings suggest that developers could consider predicted maintainability-related quality alongside predicted functional correctness and inference cost when selecting a model before code generation. For researchers, prior work and our findings motivate future investigation into which additional generated-code properties can be predicted from internal representations. Such investigation could reveal the broader potential of internal representations as pre-generation signals for software engineering. IX. D ATA AVAILABILITY

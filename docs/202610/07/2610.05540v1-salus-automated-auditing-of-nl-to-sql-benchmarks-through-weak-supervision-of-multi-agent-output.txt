# SALUS: Automated Auditing of NL-to-SQL Benchmarks through Weak Supervision of Multi-Agent Output 

SHIYUAN ZHOU, University of California, Irvine, USA 

ASHWIN GERARD COLACO, University of California, Irvine, USA

SHARAD MEHROTRA, University of California, Irvine, USA Natural language to SQL (NL-to-SQL) benchmarks are foundational to progress in data analysis research, yet recent work has shown that widely-used benchmarks contain significant annotation errors. These errors silently corrupt evaluation metrics, penalize correct model output, and distort the field’s understanding of state-of-the-art performance. We present SALUS 1, a system that automatically detects annotation errors in NL-to-SQL benchmarks. SALUS frames benchmark auditing as a weakly supervised error detection: SQL generated by multiple LLM agents drive a suite of complementary weak-labeling functions. By passing this noisy vote matrix through a generative label model, we extract high-confidence training samples without requiring human ground truth. These samples train a decision plane that maps gold SQL query features to per-agent trustworthiness, allowing SALUS to intelligently fuse reliability estimates with raw verdicts for rigorous benchmark error detection. We evaluate on BIRD-Clean-xs, a benchmark of 298 BIRD development tasks with manually verified correctness labels. SALUS achieves F1 = 0.9194, significantly outperforming the state-of-the-art baselines. Applying SALUS to the full development sets, we estimate annotation error rates of approximately 37% on BIRD and 27% on Spider. Reported accuracy improvements drive claims of state-of-the-art performance and influence both academic research and industrial adoption. When the noise in a benchmark exceeds the gap between competing systems, the leaderboard no longer measures what it claims. As shown in Figure 1: under our estimated 37% error rate, the rank-1 system on the BIRD development set cannot be reliably distinguished from the next 20. This is not an isolated finding. Independent audits of BIRD and Spider have reported error rates ranging from 7% to over 50% [7, 11, 16]. Nor is it solved by manual review: the BIRD team conducted an expert re-annotation campaign in November 2025 [10], yet 47 of the 68 errors in our random sample persisted unchanged in the updated release. The errors are numerous and diverse, spanning incorrect SQL logic, ambiguous natural-language questions, and inconsistent data files, and they resist manual correction because human annotators face the same challenges of domain complexity and fatigue that introduced the errors in the first place. Automating detection is itself challenging, not only for NL-to-SQL benchmarks but for any setting where reference annotations may be unreliable. No oracle labels exist: the gold annotations are themselves the objects under assessment, so standard supervised learning does not apply. The errors are heterogeneous, so no single heuristic can reliably capture their diversity. Furthermore, any LLM-based detection signal is itself fallible: agent-gold disagreement does not guarantee an annotation error, nor does agreement preclude one, and agents may fail entirely by producing unexecutable SQL. Existing methods address some of these challenges but not all. Hybrid approaches such as SAPAR [7] generate LLM diagnostic reports but rely on human expert review for the final decision, inheriting the limits of manual annotation. SQLDriller [16], the most comparable fully automated method, assumes the natural-language question and schema are correct and generates 10 structurally diverse SQL candidates per query. It flags an error only when at least one candidate outperforms the gold SQL, restricting its coverage to pure SQL errors and scaling LLM calls to compensate for candidate failure. Our key observation is different: no single LLM agent is an oracle, but each carries a diagnostic signal that can be extracted and combined. When multiple frontier models independently produce mutually consistent SQL that contradicts the gold annotation, it becomes increasingly unlikely that all models are wrong in the same way. We introduce SALUS, an automated and benchmark-agnostic framework that converts noisy multi-agent disagreement into reliable benchmark audits through weak supervision. Given each benchmark task, SALUS prompts 𝐾 independent LLM agents to produce candidate SQL queries.

It extracts execution, structural, and intent-alignment signals from these outputs, encoding them as diverse labeling functions (LFs) distributed across complementary signal sources so that each captures failure modes invisible to the others. A generative label model aggregates these noisy votes into probabilistic correctness scores, yielding high-confidence training samples without human labels. These samples train per-agent reliability models conditioned on gold SQL structural features, learning which agents to trust for which query types rather than weighting reliable agents and fallible agents equally. A final ensemble combines these reliability estimates with raw agent verdicts to produce the error-detection label. We evaluated SALUS on BIRD-Clean-xs, a ground-truth benchmark of 298 tasks for the detection of annotation errors in BIRD with manually verified labels. Among all fully automatic baselines, SALUS achieves the best performance with an F1 of 0.9194, outperforming the 4-agent majority vote (F1 = 0.8895), the automated verifier stage of SAPAR (F1 = 0.8389), and SQLDriller (F1 = 0.6456). When applied at full scale, SALUS estimates annotation error rates of 37% in the BIRD development set and 27% in the Spider development set. Our perturbation analysis shows that for any pair of methods whose development-set accuracy gap falls within 5.09%, their performance difference cannot be reliably distinguished at the 95% confidence level. Rank correlation analysis further indicates that the hidden test set may share similar annotation artifacts, limiting the ability of the current leaderboard to reliably distinguish top-ranked systems. We summarize our contributions as follows: 

• We propose SALUS, a benchmark-agnostic weak supervision framework that automatically detects annotation errors using multi-agent output. While we demonstrate it on NL-to-SQL benchmarks, the underlying approach applies to any domain where reference annotations may be unreliable. 

• We construct BIRD-Clean-xs, a manually labeled ground-truth benchmark of 298 tasks for BIRD annotation error detection with a five-category error taxonomy, combining errors corrected by the BIRD team with random samples. SALUS achieves F1 = 0.9194 on BIRD-Clean-xs, the highest among all comparable methods. 

• We apply SALUS to the full BIRD and Spider development sets, estimating annotation error rates of approximately 37% in BIRD and 27% in Spider, and show that this benchmark noise propa-gates directly into leaderboard rankings, rendering score gaps between top systems statistically indistinguishable. 

2 Related Work 2.1 NL-to-SQL Benchmarks and Evaluation 

NL-to-SQL systems translate natural-language questions into executable SQL queries, enabling users to interact with relational databases. To measure the effectiveness of these systems, several benchmarks have been developed, evolving from simple single-table lookups to complex reasoning tasks across diverse domains. WikiSQL [21] was an early large-scale effort focused on single-table queries, while Spider [17] introduced the requirement for cross-domain generalization with multi-table schemas and complex joins. More recently, Spider 2.0 [9] and BIRD [10] have emerged as primary benchmarks for realistic NL-to-SQL tasks, emphasizing large real-world databases and complex SQL generation under practical constraints and external evidence. A central design choice in NL-to-SQL benchmarks is how to evaluate SQL answers. Testing SQL for benchmarking is different from using SQL for data analysis. In real analysis, multiple SQL formulations may all be acceptable if they provide useful insight. However, in a benchmark, each NL question must be paired with a fixed reference answer so that predictions can be deterministically judged and compared fairly across systems. To support this goal, prior work has used two main

metrics: Exact match accuracy [17], strictly compares structural syntax but rigidly penalizes valid, semantically equivalent queries. Consequently, modern benchmarks prioritize the second metric, execution accuracy, which compares executed result sets on the database instance to better capture true semantic equivalence. However, this also means that the gold annotation must itself be correct: otherwise, correct system outputs may be penalized, and erroneous ones may be rewarded. Benchmark quality is therefore essential for meaningful evaluation. Current leaderboards report execution accuracies above 80% on BIRD and 90% on Spider 2.0 but these numbers are computed against gold annotations whose correctness is assumed but not guaranteed. Our manual investigation of 200 random samples from the BIRD development set revealed an error rate of 34%, suggesting that the metrics reported may substantially misrepresent the true performance of the model. 

2.2 Benchmark Quality and Error Detection 

Manual annotation auditing is the most naive way to detect benchmark errors. It requires domain expertise, is prohibitively time-consuming, does not scale to modern benchmarks with thousands of instances, and still cannot avoid human annotation errors. Several recent studies have therefore developed automated or hybrid methods to detect errors in NL-to-SQL benchmarks. NL2SQL-BUGs [11] proposed a two-level error taxonomy (9 categories, 31 subcategories) and prompted LLMs with the taxonomy followed by manual examination to evaluate the benchmark. Jin et al. [7] built SAPAR, an LLM-based pipeline where the iteratively called LLM agent generates verification queries and diagnostic reports to be reviewed by a human expert. SQLDriller [16] introduced execution consistency as a detection criterion: an LLM agent generates structurally diverse SQL candidates, uses a formal SQL equivalence checker to craft synthetic database instances that distinguish non-equivalent queries, and prompts an LLM to execute the natural language question on these instances. Each SQL is scored by counting execution-result matches with the LLM’s natural-language execution results. Mappings for which gold SQL scores lower than an alternative are flagged as likely incorrect. These efforts have confirmed that annotation errors are prevalent in frontier benchmarks. NL2SQL-BUGs detected 106 errors in the BIRD development set (6.91% of their sample); Yang et al. [16] manually found 810 (37.7%) errors in the Spider test set and 768 (50.1%) in the BIRD development set. Jin et al. [7] reported error rates of 52.8% in BIRD Mini-Dev and 62.8% in Spider 2.0-Snow, with corrections shifting leaderboard rankings by up to nine positions. The wide variance in reported rates reflects differences in methodology and error definitions, but the consistent finding is that benchmark noise is systematic and consequential. The BIRD team has acknowledged the problem: in November 2025, they released an updated development set [10] produced by a quality review program led by five PhD students and industry engineers, incorporating community feed-back collected over the preceding year. While this effort corrected a number of annotations, our manual investigation found that 47 of the 68 errors in our 200 random samples persisted unchanged in the updated release. These limitations motivate the need for a fully automated benchmark auditing technique that can detect annotation errors without human intervention and be reapplied whenever datasets are updated. SALUS addresses this gap: rather than relying on extensive LLM calls or requiring manual expert review, it aggregates multiple noisy agentic detection signals through a weak supervision workflow and assigns each query a final detection label, enabling accurate, scalable, and repeatable auditing of NL-to-SQL benchmarks. We emphasize that annotation error detection and annotation correction are related but distinct tasks. Reliable detection is a prerequisite for correction: proposing a trustworthy replacement SQL first requires identifying that the original annotation is likely wrong, whereas benchmark

2.3 Weak Supervision 

Weak supervision replaces hand-labeled ground truth by aggregating multiple imperfect program-matic labeling sources. Domain knowledge is encoded as labeling functions (LFs), such as heuristics, pattern matchers, or pretrained models, that emit noisy labels. A generative label model estimates the LFs’ accuracies from their agreement patterns without ground truth, producing probabilistic labels to train a downstream discriminative model [13]. This paradigm scales robustly in practice [2] and can match fully supervised approaches requiring thousands of hand-labeled examples [19, 20]. Annotation error detection in NL-to-SQL benchmarks is a natural fit for this paradigm for two reasons. First, no ground-truth correctness labels exist: determining whether a gold SQL annotation is correct requires expensive expert review, and the scale of modern benchmarks makes exhaustive auditing impractical. Second, the available evidence is heterogeneous and complementary: execution result consistency, SQL structural analysis, and natural-language intent alignment each capture a different facet of annotation quality, yet none is individually reliable enough to determine correctness. Accordingly, SALUS designs LFs to encode that evidence and provide noisy votes which a generative label model aggregates into probabilistic correctness scores for the downstream pipeline. Our experiments on BIRD-Clean-xs, a 298-task benchmark with manually verified correctness labels (Section 4), confirm this design: cross-category LF pairs exhibit a mean Pearson correlation of only 0.081, and removing any single signal-source category degrades overall detection F1 by up to 0.0436 (Section 5.6).

These weak labels are the only supervision used in the downstream components; no human annotations are consulted during training or model selection.

4.2 Source 1: Random Sampled Set 

We randomly sampled 200 tasks from the development set ( 𝑛 = 1,534) and manually reviewed each one, yielding 68 erroneous tasks and 132 correct ones (34.0% error rate). To confirm that the sample is representative of the full development set, we performed chi-square tests on the distributions of difficulty level and database category between the sample and the population, with Bonferroni correction at family-wise 𝛼 = 0.05. Neither difficulty ( 𝑝 = 0.124) nor belonged database ( 𝑝 = 0.999) show a significant deviation, supporting that the sample is unbiased. Of the 68 confirmed errors, 21 were subsequently changed by the BIRD team in their November 2025 update, while the other 47 were left unchanged. Thus, at least 47 confirmed errors persisted through the update, showing that a substantial fraction remained unaddressed even after the BIRD team’s own manual review. Among the tasks the BIRD team did change, the majority involved SQL query modifications, though some changes modified the natural-language question or evidence. Because this subset carries manually verified ground-truth labels on a representative sample, the known error rate together with the system’s evaluated precision and recall on this subset enables a confidence interval estimate for the true benchmark-wide error rate (Section 5.4). 

4.3 Source 2: Version-Diff Candidate Set 

This set exploits a natural signal from benchmark maintenance. In November 2025, the BIRD team released an updated development set, indicating that they were actively fixing known annotation issues. We do not assume the updated release is uniformly correct; rather, we use the differences between the earlier BIRD development set used by SQLDriller and the November 2025 release to identify tasks that are especially likely to be incorrect in the earlier version. Starting from the two versions, we identify tasks whose gold SQL changed, yielding 475 candidate tasks. We then apply two filters: (1) we retain only tasks whose natural-language question and evidence remain unchanged, so that the difference is attributable to the SQL annotation itself; and (2) we execute both SQL versions on the underlying database and retain only tasks whose execution results differ. After filtering, 109 candidate tasks remain. Manual examination confirms all 109 as erroneous in the previous version. 

4.4 Labeling Process 

All tasks in BIRD-Clean-xs are manually verified. Two PhD students independently reviewed each NL-to-SQL pair, judging whether the gold SQL correctly answers the natural-language question. Before adjudication, the two annotators agreed on 86.24% of the 298 tasks (Cohen’s 𝜅 ≈ 0.73, substantial agreement). Disagreements were escalated to two supervising professors with expertise in database systems, who made the final determination. To further improve labeling quality, for all tasks in BIRD-Clean-xs, we cross-checked our judg-ments against external evidence, including NL2SQL-Bugs [11], Arcwise’s reported BIRD errors [1], and issue reports from the official BIRD repository [4]. Whenever our judgment disagreed with an external source, we conducted an additional re-validation round before finalizing the label.

5.1.1 Baselines. We compare SALUS against baseline methods. 

Individual agents. Each agent serves as a standalone error detector. A task is predicted erroneous when the agent’s execution result disagrees with the gold SQL execution result. If the agent did not have a valid executable SQL answer, the agent automatically failed on that query task. 

Majority vote. Labels a query as ’incorrect’ only if more than half of the valid agents disagreed with reference SQL; otherwise, it returns ’correct’. If no agent produced a valid execution result, the majority vote does not return a prediction. 

Weak labels. The generative label model in SALUS produces a probabilistic correctness score for each task’s gold annotation from the labeling function vote matrix Λ. This baseline thresholds these scores at 0.5 to obtain hard predictions for all 𝑁 tasks, bypassing feature-conditioned reliability estimation and ensemble aggregation. 

Agent stacking. Agent stacking is an alternative design of our system: it depends on SALUS’s LFs and Snorkel label model and replaces only the SQL-feature-conditioned decision plane with one global rule over agent verdicts. For each task, the 𝐾 = 4 agents produce a four-bit verdict vector, with 1 denoting that the agent’s valid execution agrees with the reference SQL execution and 0 otherwise. The agents produce 2 𝐾 = 16 possible verdict vectors. A global rule maps each vector to either correct or incorrect, so there are 2 16 = 65 ,536 mappings. We score every mapping against the same 500 high-confidence weak labels used for SALUS’s downstream training and retain the maximum-F1 mapping for each configuration. Because the selected mapping sees no SQL features, it gives every task with the same verdict vector the same prediction.

5.3 Comparison with Existing Auditing Systems 

NL-to-SQL annotation error detection methods fall into two different paradigms. Execution-based methods such as SALUS compare SQL execution results on the benchmark database: multiple LLM agents independently generate SQL, and disagreement among their executions signals potential annotation errors. SAR-Agent [7] belongs to the same paradigm: it iteratively generates targeted verification queries, executes them on the database, and distills the inspected results into a per-task verdict through a single agent’s sequential reasoning. SQL-difference-based methods such as SQLDriller [16] instead generate structurally diverse SQL candidates that represent alternative plausible logical formulations for answering the natural-language question, synthesize counterexample database instances that distinguish non-equivalent queries, and prompt an LLM to “execute” the natural-language question on each instance to identify the best-aligned candidate. The two paradigms rely on different evidence. Execution-based methods use query outcomes on the benchmark database, allowing SALUS and SAR-Agent to expose incorrect SQL, data incon-sistencies, and query ambiguity without assuming that the question or schema is correct. Their signal remains instance-dependent: an erroneous annotation is hidden when it returns the expected result on that database. SQL-difference-based methods instead synthesize counterexamples from structural differences among candidates, exposing latent SQL errors that the current data hides. In exchange, they assume that the question and schema are correct and cover only pure SQL errors.

5.5 Leaderboard Trustworthiness 

NL-to-SQL benchmarks usually maintain a public leaderboard that ranks systems by execution accuracy on both the development and hidden test sets. For the BIRD development set, we have an estimated error rate of 37%; the test set labels are hidden and their quality is unknown. Using the BIRD benchmark as an example, we first analyze how such development set error rate affects the trustworthiness of the development ranking, then infer implications for the test ranking. For a pair of systems with reported development accuracies 𝑎 𝑣 and 𝑎 𝑘 on 𝑁 = 1,534 queries, correcting a single flawed query changes each system’s accuracy by at most ±1/𝑁 , producing a maximum pairwise gap swing of ±2/𝑁 . Under the worst-case assumption that all 𝑒 = 564 estimated flawed queries (37%) produce such maximal swings independently, the standard deviation of the total gap perturbation is 𝜎 gap ≤ 2√𝑒 /𝑁 ≈ 3.10%. A one-sided 95% confidence threshold then requires an observed gap of at least 𝑔 ∗ = 1.645 𝜎 gap ≈ 5.09% (derivation in Appendix B.1 and B.2). We applied this analysis to the top 30 systems ranked by development set accuracy, as shown in Figure 1. No pairwise comparison between the rank-1 system and any of the next 20 systems exceeds the 95% threshold. In other words, given the estimated 37% error rate, the development set ranking cannot reliably distinguish the top-ranked system from the next 20. This analysis assumes that corrections to flawed queries affect each system independently. In practice, systems with shared architectures are likely to respond similarly to the same corrections. This positive correlation reduces the effective variance, making 𝜎 gap ≤ 2√𝑒 /𝑁 an upper bound. Therefore, we are making a conservative analysis: the actual indistinguishability region may be narrower than reported. The development ranking is only a proxy; the official BIRD leaderboard is determined by the hidden test set. We therefore ask whether the test ranking behaves like an independent and substantially cleaner reference, or whether it may reflect similar benchmark-specific artifacts. We examine this question through rank correlation. The standard Kendall’s 𝜏 between the observed development ranking and the hidden test ranking for the top 30 systems by hidden-test accuracy is 𝜏 = 0.664. Because Kendall’s 𝜏 is a U-statistic, linearity of expectation under our pairwise noise model allows us to compute an expected Kendall’s 𝜏 (𝐸 [𝜏 ]). This expectation mechanically down-weights pairs whose score gaps fall within the noise margin, as their true ordering is highly uncertain. Under our estimated 37% error rate, we obtain 𝐸 [𝜏 ] = 0.41 (derivation in Appendix B.3). If the hidden test set were a pristine oracle of true NL-to-SQL capability, pairs that are statistically indistinguishable on the development set should have a near-random chance of maintaining their relative order on the test set. Consequently, the observed 𝜏 should closely track the down-weighted 

𝐸 [𝜏 ]. Instead, the observed 𝜏 (0 .664) is substantially higher than 𝐸 [𝜏 ] (0 .41). This discrepancy  

> Proc. ACM Manag. Data, Vol. 4, No. 6 (SIGMOD), Article 374. Publication date: December 2026. SALUS: Automated Auditing of NL-to-SQL Benchmarks 374:19

indicates that small-gap pairs are concordant between the development and test sets far more often than chance would predict. This excess concordance on statistically noisy pairs is consistent with the hypothesis that development and test sets share similar annotation artifacts, so that systems rewarded by one split tend to be rewarded by the other. Alternative explanations include our noise model overestimating development-side uncertainty, split-specific variance, or distribution shift. Even under these more conservative interpretations, however, we cannot claim that the hidden test leaderboard provides a statistically reliable ordering of state-of-the-art systems. Until benchmark label quality is better established across all splits, leaderboard differences at the top should be interpreted with caution.

5.6.4 Decision Plane and Feature-Conditioned Routing. The selected configuration uses depth-2 CART paired with score fusion. The score fusion strategy further incorporates the fallback task-level probability as a continuous feature on every query, providing a learned safety signal even when agents produce valid but unreliable verdicts. Agent stacking replaces the SQL-feature-conditioned decision plane with a single global mapping over agent verdicts (Section 5.1.1). 6 Discussion 6.1 Beyond Detection to Benchmark Correction 

Detection identifies which benchmark annotations are likely wrong; the natural next step is to make corrections. For example, SQLDriller [16] automatically selects the SQL candidate with the highest NL-execution consistency score from 10 model-generated alternatives, provided that it scores strictly higher than the reference SQL. SALUS includes a lightweight automatic correction mechanism: when a detected error has a majority-agreement cluster of at least three valid agents, the system proposes the SQL from the highest-reliability agent in that cluster. Table 16 compares both mechanisms on the 134 Incorrect SQL errors. SALUS produces more correct fixes than SQLDriller (59 vs. 35), with a higher end-to-end fix rate (44.0% vs. 26.1%). Reliable detection is necessary but not sufficient for correction: our mechanism fixes only 44.0% of the Incorrect SQL errors. Beyond this category, 19.3% of BIRD-Clean-xs errors involve question ambiguity, evidence, domain semantics, or data, for which SQL substitution alone may be insufficient (Section 4.5). We therefore leave robust correction to future work. Several directions could improve SALUS’s correction quality: learning supervised agent selection from a ground-truth correction set rather than agreement-cluster heuristics; using stronger NL-to-SQL systems, such as multi-step agentic pipelines, to increase the chance that candidates contain a correct alternative; and localizing error types, such as wrong joins or missing aggregations, as structured feedback to annotators. In all cases, correction quality is bounded by detection accuracy: a system cannot fix what it fails to identify. Robust detection is therefore essential for automated correction. 

6.2 Broader Applications 

SALUS can extend beyond BIRD and Spider to broader auditing needs. 

Real-time auditing. A configured SALUS instance can serve as an online quality gate for incoming annotations, generating agent answers, extracting features, and returning an immediate detection result. As tasks accumulate, the system can periodically retrain its decision plane to improve accuracy. 

More complex benchmark settings. SALUS is source agnostic: it consumes candidate SQL and execution verdicts rather than depending on a particular model family or provider, so an open-weight model enters through the same interface. Therefore, it can in principle be applied to more challenging benchmarks where single-prompt LLM agents are insufficient. Spider 2.0 [9], for exam-ple, features enterprise-scale schemas with over 3,000 columns and multi-step workflows where even frontier LLMs achieve success rates below 30% [9]. At this difficulty level, more advanced multi-agent pipelines would be required as source agents. We demonstrate this property by adding SQLDriller as a fifth signal source without changing the architecture. This configuration obtains

However, on more challenging benchmarks, most top-performing systems are proprietary, limiting access to diverse agent signals and therefore requiring broader collaboration between benchmark maintainers and system developers. 

Transfer to other benchmark auditing tasks. The multi-agent weak labeling architecture is not specific to NL-to-SQL and can transfer to any domain where benchmark annotations may contain errors. For software engineering benchmarks such as LiveCodeBench [5] and SWE-bench [6], where weak test suites accept incorrect patches and inflate resolution rates, labeling functions can check whether multiple agents converge on the same fix location and whether their patches produce iden-tical behavior under differential testing, with reliability estimated from patch complexity features such as the number of files and functions modified. For mathematical reasoning benchmarks such as RealMath [18], where the automated theorem-to-QA extraction pipeline introduces annotation noise, labeling functions can check whether agents converge on an alternative numerical answer that disagrees with the reference, with reliability estimated from problem features such as mathe-matical domain and the number of reasoning steps. In both cases, the weak supervision framework and decision plane ensemble remain unchanged; only the domain-specific labeling functions and reliability criteria require adaptation. 

7 Conclusion 

In this paper, we presented SALUS, an automated and benchmark-agnostic framework for detecting annotation errors in NL-to-SQL benchmarks through weak supervision over multi-agent SQL out-puts. By combining multiple labeling functions, a generative label model, and a feature-conditioned decision plane, SALUS achieves strong end-to-end detection performance on our manually verified benchmark BIRD-Clean-xs, reaching an F1 of 0.9194 and outperforming all baselines. When ap-plied at a benchmark scale, SALUS estimates that annotation errors remain substantial even after recent cleanup efforts: approximately 37% in the November 2025 BIRD update and 27% in Spider. These errors directly affect evaluation reliability: on BIRD, pairwise rankings with development accuracy gaps within 5.09% cannot be distinguished, making much of the current leaderboard statistically unreliable. Therefore, for benchmark maintainers, we suggest four concrete steps: (1) run automated auditing such as SALUS as a release gate, which at $0.0332 per task is repeatable on every update; (2) prioritize flagged tasks for multi-annotator adjudication rather than re-reviewing entire benchmarks; (3) maintain a verified-clean subset for leaderboard comparison; and (4) report ranking uncertainty alongside scores. Taken together, our results establish benchmark auditing as a first-class problem in NL-to-SQL evaluation and show that scalable systems such as SALUS can support cleaner benchmarks.

A Labeling Function Configurations 

This appendix documents the labeling functions used in the final paper pipeline. The final configu-ration contains 43 task-level labeling functions and one meta labeling function. 

A.1 Execution signals. 

Result-set signals. These signals compare the result set 𝑅 (𝑠 𝑖 , 𝐷 𝑖 ) produced by the benchmark SQL 

𝑠 𝑖 on database 𝐷 𝑖 against the execution results produced by the agent queries. These functions normalize away benign formatting differences such as whitespace, case, NULL representation, column order, and small floating-point variation. They capture direct result-set agreement, runtime failures, cardinality mismatches, subset/superset relations, and numeric-equivalence edge cases such as percentage-vs-fraction scaling. 

Agent Consensus signals. Consensus signals do not inspect the natural-language question directly. Instead, they summarize agreement patterns across the valid agent executions themselves. In the appendix we name these rules Agent Majority Agreement and Agent Unanimity Agreement . These are weak-supervision heuristics used in the labeling-function layer; they should not be confused with the later Decision Plane, which learns per-agent reliability scores from SQL features. 

A.2 Structural signals. 

Structural signals compare the SQL structure of 𝑠 𝑖 against the agent-consensus SQL using AST-level analysis. Let Tables (𝑠 ), Aggs (𝑠 ), and GroupBy (𝑠 ) denote the referenced tables, aggregation operators, and GROUP BY expressions extracted from the AST of query 𝑠 . These rules detect missing or extra joins, aggregation mismatches, grouping mismatches, join-type discrepancies, suspicious hard-coded literals, and semantically equivalent rewrites. We also include one schema-consistency rule that rewards cases where the benchmark SQL and the consensus SQL reference the same table set, as well as a family of known-error-pattern rules targeting recurring annotation mistakes such as aggregation without grouping, date-boundary off-by-one errors, unguarded division, implicit type coercion, and invalid DISTINCT / ORDER BY combinations. Many negative structural rules use an execution guard : they vote Incorrect only when a structural discrepancy is accompanied by an execution-level mismatch. This reduces noise from harmless syntactic variation. For example, if the benchmark query and the consensus query differ in join type but still produce the same result on the current database, the guarded rule abstains rather than casting an Incorrect vote. 

A.3 Intent signals. 

Intent signals capture failures that may not be visible from execution or SQL structure alone. These rules check whether the SQL reflects salient cues in the question, such as whether “how many” maps to COUNT , “average” maps to AVG , and “top 𝑁 ” maps to LIMIT , while still allowing alternative SQL formulations that are semantically equivalent. Additional rules check for missing filter literals, omitted DISTINCT , and yes/no questions that incorrectly return a full table rather than a boolean-style answer. 

A.4 Meta signal. 

A single meta labeling function computes a majority vote over the non-abstaining task-level labeling-function outputs. This rule provides an aggregate summary of the direction of evidence. Although the meta LF is deterministically derived from the task-level votes, conditional independence is not required by Snorkel: its generative model can capture pairwise LF dependencies and avoid double-counting correlated votes [13].

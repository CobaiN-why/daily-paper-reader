# Back to the Future: Regressing Readability Features from LLMs 

TAIRAN WANG, University College London, United Kingdom 

EARL T. BARR, University College London, United Kingdom Code readability determines how effectively and efficiently software can be understood, reviewed, and maintained. As AI coding agents assume a larger role in software engineering, readability gains a critical dual purpose: it allows human engineers to safely review agent-generated output, and it helps the agents themselves maintain code more effectively, as readable code tends to be more compact and less distracting within limited context windows. Yet, existing readability models do not consistently agree with human judgements across datasets. To address this, we introduce BTTF ( Back To The Future), a model built on the principle of pairing an old-school linear regression backbone with new-school information-theoretic features. Rather than using large language models as opaque, black-box judges, BTTF leverages them as measurement instruments. BTTF combines traditional code measurements with embedding-based semantic organisation and causal-LM predictability to capture source structure, semantic coherence, and contextual surprise. We evaluate BTTF across the complete set of five publicly available human-rated code-readability bench-marks, supplemented by our manually annotated MBJP development set, for a total of 1,100 samples. Across this comprehensive suite, BTTF establishes a new state of the art, improving average Spearman correlation over the strongest baseline by up to 0.101. Across 13 controlled readability-reducing transformations applied to production code, it achieves response rates of 93.8% in Java and 87.6% in Python, outperforming Dorn by 14% and 19.2%. Its performance is the highest among local models and trails the strongest cloud-LLM response by 1.7% in Java and 5.1% in Python. The direct-LLM baselines require an average of 1,083 prompt tokens per evaluation while remaining opaque. Unlike alternative methods, BTTF delivers state-of-the-art benchmark performance and strong transformation robustness alongside feature-granular interpretability, with every feature’s coefficient strictly matching its theoretical directional effect across all evaluated model configurations. 

1 Introduction 

Code readability is central to software engineering because source code is repeatedly read, reviewed, debugged, and modified throughout its lifetime. The need for reliable automated assessment has now become urgent as LLM-driven coding agents rapidly proliferate. As agents shift human engineers from primary authors into reviewers, high throughput makes human inspection the central bottleneck: a strain compounded by legal and regulatory mandates that require human auditing of deployed software for the foreseeable future, even if source code eventually becomes the “new assembly”. In this emerging paradigm, readability serves a critical dual purpose: it eases the burden on human reviewers evaluating agent-generated output, and it enables agents themselves to navigate and reason over codebases more effectively without cluttering context windows. Readability must therefore be measured explicitly, interpretably, and at scale to give developers actionable feedback, guide LLM post-training, and enable agents to optimise code for both human auditing and downstream maintenance. Despite many proposed measures and predictive models, aligning automated metrics with human judgement remains an open challenge. Existing work follows three main directions. Feature-based machine-learning models use explicit lexical, structural, textual, and visual measurements [4, 10, 38, 40]. Smaller formulations rely on broad proxies, while larger feature inventories can combine language- or presentation-specific measurements whose fitted directions are difficult to interpret consistently. People do not understand complex material by retaining every detail independently. Related and recurring elements can instead be represented through shared patterns and higher-level abstractions. From an information-theoretic perspective, this is compression: many observations are encoded by a shorter internal description [7, 12]. Program comprehension likewise produces mental representations at multiple levels of abstraction [3, 37]. In source code, identifiers, expressions, assignments, and control structures may collectively express concepts such as input validation, state updates, or iteration. To address these challenges, we introduce BTTF ( Back To The Future), a readability model built on the principle of combining an old-school linear regression backbone with new-school information-theoretic features. Rather than treating large language models as opaque, end-to-end judges, BTTF uses pretrained causal LMs and continuous embedding spaces purely as measurement instruments. Linear regression provides transparency by ensuring that every feature’s contribution is explicitly weight-attributed and directionally verifiable. Meanwhile, the underlying features capture source structure, contextual surprise, and semantic coherence. To measure semantic coherence, BTTF leverages pretrained embedding spaces as geometric proxies for mental consolidation. Continuous embedding models place semantically related inputs near one another in representation space [15, 34, 48, 49]. Embedding spaces capture which program elements are related, but not whether they appear where a reader would expect them, as, for example when unrelated logic is interleaved with the current computation. A name may be unexpected when first encountered, an assignment value may not follow from preceding statements, or a short identifier may require context from much earlier in the program. Causal code language models complement semantic organisation by measuring the prediction difficulty of observed source constructs, revealing which elements are unexpected and whether additional preceding context makes them easier to anticipate. Together, the measurements describe how source information forms semantic units, unfolds through the program, and relates to its preceding context. Based on this view, we use pretrained models as measurement instruments rather than as end-to-end readability predictors. Stability analysis and consensus ranking across three causal language models and five embedding models select features that remain useful under different pretrained representations. The resulting model contains 11 named, directly interpretable features: four traditional measurements of source complexity, two measurements of semantic organisation in embedding space, and five measurements of contextual prediction difficulty derived from causal code language models (Table 1 defines all 11). 2 Back to the Future: Interpretable Code Readability using LLM-Derived Signals 

BTTF models readability along two information dimensions: how compactly program elements organise into semantic abstractions, and how predictably information unfolds through the source. For the first, we extract AST-tagged code snippets and embed them individually. Geometric and clustering measurements then distinguish code whose identifiers and structures form a small number of coherent semantic groups from code whose elements remain dispersed. Such organisation reflects information compression: many source-level observations can be represented through fewer higher-level patterns. For the second dimension, we use frozen causal code language models to measure the surprisal of observed source constructs. Rather than reduce an entire program to a single perplexity value, we locate where new information arises, which kinds of constructs are difficult to predict, and whether additional preceding context reduces that difficulty. These measurements capture the ordering and contextual support that embedding-space organisation alone cannot provide. The complete representation combines these two dimensions with traditional measurements of surface-level information properties. 

2.1 Feature Construction and Selection 

Embedding models operate on strings rather than program structures. We therefore extract source constructs as AST-tagged snippets and convert them into normalised representations. Raw source strings can mislead an embedding model: surface differences may obscure related program informa-tion, while compound expressions may blur distinct elements. We address these cases in opposite ways: compound constructs are decomposed so that their internal elements remain distinguishable, whereas elements that share a program role, such as literals, receive a common textual cue while retaining their original content. The resulting snippets provide the inputs for semantic-organisation measurements. We also compute traditional features directly from the source and extracted snip-pets to capture surface-level information properties. The resulting representation is illustrated in Figure 2. Embeddings allow us to compare the semantic similarity of code snippets. We use these similari-ties for automatic clustering, which shows whether the snippets concentrate into a few coherent semantic groups or remain fragmented. The former reflects a compact higher-level organisation of program information; the latter reflects a larger set of distinct abstractions. Traditional features. The four traditional features describe surface-level properties of expressions and layout. Operator density measures how many operations a reader must parse within each non-empty source line. From an information-theoretic perspective, it records the concentration of symbolic transformations within the same reading unit. 

Decision density measures the concentration of relational and equality comparisons. Each com-parison distinguishes between possible program states, and the feature records how many such alternatives occur within each non-empty source line. 

Longest line length records the length of the longest non-empty line. A longer uninterrupted span presents more source information before a line boundary provides a natural segmentation point. 

Expression–literal density contrasts compound operations and relations with values stated directly in the source. Its exact engineering definition appears in Appendix A. 

Embedding-space signals. The two embedding features ask whether the concepts within a program form a small, coherent organisation or are scattered across several distinct semantic regions. 

Computation-and-control pattern count groups control-flow, assignment, arithmetic, comparison, logical, and bitwise snippets according to their semantic similarity and counts the automatically identified groups. Recurring and conventional forms are absorbed into the same groups and add little new organisational information, whereas constructs that do not fit those groups require additional patterns. 

Identifier embedding dispersion measures whether the identifier meanings follow a common semantic direction or spread across several unrelated directions. It is computed as one minus the fraction of identifier-embedding variance explained by the first principal component, recording how broadly the identifier meanings spread beyond a common direction. Higher BPB means that the observed source is less expected in its context. In Figure 4, the preceding source is held fixed and only the variable name changes. Literal-tail surprisal first computes BPB separately for literal occurrences and averages the most difficult 20%. It targets exceptional constants or encodings that may be hidden by an otherwise predictable snippet. Identifier-onset surprisal measures the surprisal allocated to the first tokenizer piece of every identifier. The first piece carries the initial lexical cue to a name and isolates its predictability at first encounter. Assignment-value surprisal measures the byte-weighted prediction difficulty of initializer and assignment right-hand sides, capturing how readily a reader can anticipate the computations that produce stored values. 

Declaration-surprisal variation measures how consistently declarations can be anticipated within the same source unit. We first calculate BPB separately for each variable declaration or function signature, considering the declaration itself rather than its body or assigned value, and then measure the variation among them. The resulting feature distinguishes uniform declaration predictability from mixtures of conventional and unexpected forms. Finally, short-identifier context dependence compares each eligible short identifier under 32-token and 256-token preceding contexts, with gain 𝑔 = BPB 32 − BPB 256 . 3 Evaluation 

We use two main forms of evaluation. First, the complete set of five publicly available human-rated code-readability benchmarks, together with our MBJP development set, measures agreement with human judgements and transfer across datasets. Second, controlled source-code interference experiments measure whether predictions decrease under targeted readability reductions in Java and Python. The following research questions specify the comparisons and analyses conducted within these two evaluation settings. 

3.1 Research Questions 

We organise the evaluation around four research questions: 

RQ1. Does BTTF align more closely with human readability judgements than existing models do? 

RQ2. Does BTTF respond more consistently to controlled readability-reducing transformations than existing models do? 

RQ3. Are BTTF’s results more stable? 

RQ4. How interpretable are BTTF’s results? 

3.2 Comprehensive Literature-Derived Benchmark Suite 

We aggregate the complete set of human labelled code-readability and cognitive-complexity bench-marks established in the software engineering literature: Buse, Scalabrino, Dorn, Schnappinger, and JetBrains. To our knowledge, they represent the total corpus of public benchmarks evaluated across prior literature on this topic. We supplement this literature-wide set with our manually labelled MBJP development set, yielding a unified benchmark of 1,100 human-rated code snippets. The suite spans Java, Python, and CUDA code at snippet, method, class, file, and program granularity, with targets derived from mean label values, posterior expectations, or readable-vote fractions. The six datasets are summarised in Table 2. Detailed target construction, annotation statistics, and the MBJP development-set procedure are reported in Appendix C. 

3.3 Experimental Setup 

We evaluate the final 11-feature representation across six established or manually annotated readability datasets: MBJP, Buse, Scalabrino, Dorn, Schnappinger, and JetBrains. We addition-ally report the complete 18-feature embedding-only model obtained before causal-LM features were introduced; these predecessor results are placed in Appendix F. Its reference instance uses 

jina-embeddings-v2-base-code , matching the embedding representation used by BTTF. BTTF uses Ridge regression [18] with 𝛼 = 200 to predict continuous readability scores. Because the six datasets use different rating scales, their human scores are converted to percentile ranks within each dataset. During joint training, every dataset receives equal total weight, preventing Back to the Future: Regressing Readability Features from LLMs 9

larger datasets from dominating BTTF’s fit. Within each evaluation fold, missing-value imputation, range clipping, and feature standardisation are estimated from the training partition and applied unchanged to the test partition. Predictions are bounded to [0, 1], with larger values indicating greater readability. We use two evaluation protocols: pooled 10-fold cross-validation and leave-one-dataset-out (LODO) evaluation. In pooled cross-validation, each dataset is divided into ten folds; in each round, a single Ridge model is trained on nine folds from every dataset and evaluated on the remaining folds. The reported correlations are computed exclusively from these out-of-fold predictions. In LODO evaluation, BTTF is trained on five complete datasets and evaluated on the sixth. For each dataset separately, performance is measured using Spearman’s 𝜌 between predicted and human readability scores. For JetBrains, the human score is the proportion of reviewers who judged each snippet readable rather than a derived binary label. We compare BTTF with logical lines of code (LLOC), Posnett, Scalabrino, a reconstruction of Dorn, and a reproduction of Mi et al.’s ConvNetCR model. For the direct-prompting baseline, we apply the best-performing zero-shot prompt reported by Ouédraogo et al. [35] to DeepSeek-V4-Pro-0813, a state-of-the-art open model, and GPT-6.1 Sol, a state-of-the-art model. We query each direct-LLM baseline three times for every sample and use the mean score in all analyses. Full specifications appear in Appendix D. 

3.4 Controlled Readability Interference Experiment 

To examine whether readability models respond in the expected direction to controlled reductions in readability, we evaluate the frozen BTTF and the comparison methods on parallel Java and Python interference datasets constructed from eight well-maintained open-source projects. The Java corpus is drawn from Guava, Spring Framework, Netty, and Apache Kafka, while the Python corpus is drawn from Django, Flask, Requests, and attrs. For each language, we select 25 complete production classes from each project, resulting in 100 Java classes and 100 Python classes. We define 13 source-level transformations, organised into seven categories: (1) Comment transformation: removal of Java line comments, block comments, and Javadoc, and Python line comments and docstrings. (2) Identifier transformations: identifier shortening, replacement with length-matched but semantically unrelated names, and deterministic minification. Eligible method, parameter, and local-variable names follow language-specific binding and collision constraints. (3) Expression transformations: hexadecimal rewriting of decimal integer literals and inver-sion of conditions with corresponding branch exchange. (4) Code-injection transformations: insertion of unreachable branches, readable unrelated code, and low-readability unrelated code. The latter two are selected deterministically from ten template families each. (5) Layout transformation: partial removal of newline-containing whitespace while retaining some visual structure, with separate eligibility rules for Python indentation. (6) Data-flow transformations: replacement of integer literals with two short-named local variables whose sum preserves the value, and inlining of eligible single-use local variables at their sole use site. (7) Control-flow transformation: conversion of eligible for loops into while -based forms, covering classic and enhanced loops in Java and synchronous loops through explicit iterators in Python. These transformations reverse readability improvements repeatedly identified in prior work, including improving names, replacing opaque literals, expressing conditions positively, simplifying 10 Tairan Wang and Earl T. Barr 

loops, removing unused code, restoring visual structure, and adding or clarifying documenta-tion [4, 8, 40, 42]. Related perturbation-based studies have likewise used identifier erosion, mis-leading replacement, dead-branch injection, irrelevant-variable injection, and expression rewrites to construct lower-readability code [20]. All 13 transformations therefore have a clear expected direction towards lower readability. The Java and Python datasets use the same 13 transformations, organised into the same seven categories, with language-specific adaptations where required. Each transformation is applied independently to the original class rather than to the output of another transformation, allowing its effect to be evaluated without interactions from other interference types. For each language, the dataset contains 100 original classes and 1,300 independently transformed variants, yielding 1,400 samples per language and 2,800 samples in total. We take several steps to preserve source consistency wherever possible: identifier edits follow local bindings, newly introduced names avoid collisions, and structural transformations update the affected code within the same source unit. We retain only complete samples that pass language-specific parsing. Detailed transformation rules, validation procedures, and eligibility constraints are provided in Appendix E. 4 Results 

BTTF contains 11 features selected from the complete candidate set. We first evaluate its agreement with human ratings across six readability benchmarks and measure its response to controlled readability reductions in Java and Python. We then use a human-rated example to contrast direct LLM judgements with BTTF’s feature-level attribution, before examining its robustness across pretrained-model combinations, including the stability of the learned feature directions. Finally, we evaluate the contribution of its three feature families and compare it with the independently selected 18-feature embedding-only predecessor. 

4.1 BTTF’s Performance on Readability Benchmarks 

We compare BTTF with the readability baselines in Table 3 under pooled 10-fold cross-validation and leave-one-dataset-out (LODO) evaluation. The reference configuration uses jina-embeddings-v2-base-code and OpenCoder-1.5B-Base . Results for all 15 combinations of embedding and causal language models are reported in section 4.3. BTTF provides the most consistent performance across the six datasets, with correlations above 0.53 under both evaluation protocols. Its average correlations are 0.631 under pooled cross-validation and 0.638 under LODO, improving over the strongest baseline average of 0.537 by 0.094 and 0.101, respectively. 4.6 Threats to Validity 

The six datasets measure readability using different rating scales, human-rating procedures, and kinds of source units, so their raw scores are not directly comparable. We convert scores to percentile ranks within each dataset and give every dataset equal total weight. This preserves the ordering of human judgements within each dataset while preventing a particular scale or larger dataset from dominating BTTF’s fit, allowing it to identify readability signals that recur across independently collected annotation settings. The human-rated literature is concentrated on Java. This is not a consequence of selective dataset choice: four of the five public benchmarks are Java-only, and the fifth includes Java alongside Python and CUDA. To test beyond this evidence base, we conduct a separate experiment on Python production code, where BTTF responds in the expected direction to 87.6% of changed variants and responds to a majority of variants for every transformation. The final feature set and its size were selected using all six human-rated datasets. Pooled cross-validation and LODO consequently evaluate prediction with this fixed representation, not the transfer of the complete selection procedure to a future benchmark. 5 Feature Engineering 

We now examine the feature engineering behind BTTF: how its three feature families complement one another, how pretrained models provide interpretable measurements, and what the selection results reveal about the available supervision. 

5.1 Combining the Three Feature Families 

The results support a view of readability as the joint effect of three properties: the explicit complexity presented by the source, the semantic organisation of its program elements, and the extent to which those elements conform to the context established during reading. The feature family ablation shows that these properties are complementary rather than interchangeable. Traditional measurements provide the strongest foundation for agreement with human ratings, causal-LM measurements contribute both benchmark performance and sensitivity to controlled degradation, and embedding-derived measurements add information about organisation that is not fully expressed by either other family alone. One small exception is the 1.5-point increase in the Java interference response after removing embedding features. Some controlled rewrites reduce structural-pattern count or identifier-space dispersion even as they reduce readability, creating a local mismatch between embedding compactness and readability. The change from the embedding-only model to BTTF illustrates how causal-LM features replace an indirect traditional proxy. Source-text byte entropy ranked second in the five-embedding consen-sus, but fell to 39th after the causal-LM measurements were introduced. Byte entropy captures the overall irregularity of source text, but cannot show which program element is difficult to anticipate or whether earlier code helps explain it. The selected construct-level surprisal features instead localise unexpected information to literals, identifier onsets, assignment values, declarations, and short identifiers while quantifying how much preceding context explains it. 

5.2 Pretrained Models as Measurement Instruments 

Direct prompting provides a useful contrast to our use of pretrained models for feature construction. Newer models improve substantially over earlier prompt-based results: GPT-6.1 Sol reaches an average correlation of 0.537 and is strongest on Schnappinger and JetBrains. Its correlations nevertheless range from 0.206 to 0.759 across the six benchmarks and remain below BTTF’s average of 0.631. A generated score also does not reveal which properties of the source shaped the judgement. The two direct-prompting baselines average 1,083 prompt tokens and 1,245 total tokens per evaluation. BTTF instead computes its embedding and surprisal features using compact local models, without remote prompting or response generation. Compared with end-to-end neural predictors and earlier feature-based models, BTTF’s repre-sentation follows an information-theoretic view of code comprehension. Each selected feature describes a recognisable source of reading difficulty, such as dense operations, fragmented structural patterns, unexpected identifiers, or values that are difficult to anticipate from preceding code. For every feature, its expected relationship with readability, its association when used alone, and its coefficient in BTTF’s complete fit have the same direction. This three-way agreement connects each interpretation to both the feature definition and the empirical evidence. Among the evaluated readability models, Posnett is the only one that is both more compact than BTTF and fully consistent between feature meaning and coefficient direction. Its three features provide useful but broad summaries, whereas our 11 features identify construct-specific sources of reading difficulty and achieve substantially stronger agreement with human ratings. 5.3 What Feature Selection Reveals About Supervision 

Some readability properties do not appear in BTTF, possibly because the available human ratings do not capture them consistently. Comments provide the clearest example: among 12 candidates cov-ering comment presence, comment–identifier alignment, comment–code relevance, and predictive value, the highest-ranked is only 44th in the 15-model consensus. Nevertheless, BTTF responds strongly to comment removal: deleting comment-only lines raises operator and decision density, while losing preceding comment context can change the predictability of later program elements. The retained features therefore capture part of the information supplied by comments without a dedicated comment feature. A diagnostic separating comments into six content types still produced no stable comment-quality feature (see Appendix B.5). This may reflect their different functions across datasets, including task requirements, API documentation, implementation explanations, licence information, and disabled code. 

6 Related Work 

In this work, code readability refers to how easily developers can read and understand a source-code sample, as reflected in human judgements [4, 10, 42]. Early automated approaches relied on structural complexity measures such as Cyclomatic Com-plexity [29] and Halstead metrics [17]. Although useful for describing program structure, such metrics provide only indirect proxies for human-perceived readability and understandability [26]. However, Halstead metrics rest on disputed theoretical assumptions, derive some apparent relation-ships from their own mathematical definitions, and lack consistent empirical support [6, 24, 43]. Cyclomatic Complexity reduces complexity to control-flow decisions without a convincing link to broader software difficulty, and is strongly confounded with lines of code, which often performs as well or better [44, 45]. Similarly, rule-based heuristics like Cognitive Complexity sum arbitrary syntactic penalties while ignoring identifier semantics, layout, and visual structure, failing basic tests of construct validity and formal metric properties [25]. Moreover, readability improvements made by developers are not always captured by automated static-analysis tools [8]. In parallel, empirical software engineering researchers formulated readability prediction as a supervised learning problem. Buse and Weimer [4] combined structural, lexical, syntactic, and layout features to predict human readability judgements. Posnett et al. [38] showed that a substantially smaller model based on lines of code, Halstead volume, and entropy could achieve competitive performance. Scalabrino et al. [40] later incorporated richer textual properties, including identifier and comment information, while Mi et al. [31, 32] explored neural models that reduce dependence on manually designed features. Across these approaches, models fit formulas to disputed structural metrics, learn feature effects that conflict with their stated meanings, or rely on opaque neural representations. They also remain imperfectly aligned with human judgements and may fail to reflect readability improvements perceived by developers [36, 42]. Recent work has investigated language models as an alternative source of readability signals. Surprisal, defined as the negative log-probability of an observed item given its preceding context, has a long-standing connection to expectation-based theories of incremental language-processing difficulty [27]. This connection makes language-model probability a plausible source of readability information, but evidence from complete texts shows that a single aggregate is not sufficient. For natural-language sentences, Miaschi et al. [33] find only a weak relationship between neural language-model perplexity and readability, with the two measurements responding to different linguistic phenomena. For source code, Dillmann et al. [9] evaluate whole-class cross-entropy against expert judgements of readability and related maintainability dimensions. The unadjusted 18 Tairan Wang and Earl T. Barr 

association is contrary to the expected direction and changes after controlling for logical lines of code; they conclude that class-level cross-entropy alone may be insufficient. A separate line of work uses language models as direct readability evaluators. Ouédraogo et al. [35] compare direct readability judgements across models, languages, and prompting strategies, finding moderate but variable alignment with human ratings. A complementary line of cognitive research explains understanding in terms of compact rep-resentations: related observations can be expressed through shared patterns and shorter descrip-tions [7, 12]. Research on program comprehension likewise shows that readers form mental repre-sentations at multiple levels of abstraction rather than retain source details independently [3, 37]. This perspective shifts attention from the amount of source information alone to how readily it can be organised into coherent higher-level representations. Our work connects this account of semantic organisation with the established readability features and language-model evidence reviewed above. Embeddings measure how source elements organise into related groups, while causal language models locate information that is unexpected in its preceding context. BTTF returns to explicit feature-based prediction, but equips it with pretrained representations used as measurement instruments rather than direct readability judges. 

7 Conclusion 

BTTF shows that code-readability modelling need not trade predictive strength for interpretability. Using pretrained models as measurement instruments rather than end-to-end judges, it achieves state-of-the-art human agreement with stable, interpretable feature directions. This supports developer feedback, readability-aware LLM post-training, and automated code improvement.

B.2 Stability-based Feature Ranking 

For each screened matrix, we independently rank either 181 or 228 eligible candidates using an L1-regularised logistic regression [46]. Readability scores are binarised independently within every dataset at the dataset-specific median: samples with scores greater than or equal to the median are assigned to the higher-readability class. Median ties remain in that class, and no middle-score samples are discarded. This produces a common screening task over all 1,100 human-rated samples while preventing differences in numerical annotation scales from defining the screening labels. Missing feature values are imputed using the median estimated from the corresponding fitting sample, after which the features are standardised. Samples are weighted inversely by the size of their source dataset so that each dataset contributes equal total weight. The logistic regression additionally uses balanced class weights. The model uses 𝐶 = 0.08, L1 regularisation, the liblinear solver, a maximum of 5,000 iterations, and random seed 42. To reduce sensitivity to sampling variation, we perform 200 stability-selection rounds [30]. In each round, 70% of the samples from each of the six datasets are selected uniformly without replacement. A new imputer, scaler, and logistic regression model are fitted to the resulting sample. D.1 Conventional and Reconstructed Baselines 

Logical lines of code (LLOC) is the number of language-aware statement and declaration nodes in the source AST; comments and blank lines are not counted. Java and Python use their respective grammars, while C, C++, and CUDA share the C++ grammar. For Posnett et al. [38], we use the published model without retraining: 

𝑧 = 8.87 − 0.033 𝑉 + 0.40 𝐿 − 1.5𝐻, 𝑃 (readable ) = 11 + 𝑒 −𝑧 ,

where 𝑉 is Halstead volume, 𝐿 is the number of source lines, and 𝐻 is source-code byte entropy. We evaluate the comprehensive model of Scalabrino et al. [40] using the authors’ released Java archive and pretrained classifier. Method-level Java snippets are placed in a minimal enclosing class when required by the released tool, and samples that cannot be processed are omitted rather than assigned fallback predictions. Because no pretrained Dorn model was released, we reconstruct the model of Dorn and Weimer [10] using the public Dorn feature data and the released implementations of its visual metrics. Metrics defined for fewer than 80% of the training samples are excluded, seven features are selected through a forward wrapper evaluated with stratified 10-fold accuracy, and a logistic-regression model is fitted on all 360 Dorn samples. The readable-class probability is used as the continuous readability score. We also reconstruct the character-level ConvNetCR branch described by Mi et al. [32]. This reproduction follows the published convolutional architecture but is not presented as the complete DeepCRM model, whose full implementation and trained weights were not released. The model contains three line-spanning convolution banks with 100 feature maps per bank, followed by ReLU activation, global max pooling, dropout, and a two-class output layer. It is trained on the highest and lowest readability quartiles of Buse, the Java subset of Dorn, and Scalabrino, with the middle half of each score distribution excluded. The resulting readable-class probability is used as its continuous score.

E Controlled Readability Interference Datasets E.1 Construction and Scope 

We construct two controlled readability-interference datasets, one for Java and one for Python. Each dataset contains 100 production-code classes selected evenly from four open-source projects. The 34 Tairan Wang and Earl T. Barr 

Java dataset contains 25 classes from Apache Kafka, Google Guava, Netty, and Spring Framework. The Python dataset contains 25 classes from Django, Flask, Requests, and attrs. For every source class, we independently apply 13 readability interferences. Each transformed variant is generated directly from the original source rather than from a previously transformed version. Consequently, the datasets do not define cumulative degradation levels, and the response to each interference can be evaluated against the same original source. Each language-specific dataset contains 100 original classes and 100 × 13 = 1,300 interference variants, resulting in 1,400 records per language and 2,800 records in total. Some transformations are not applicable to every class. For example, integer-literal encoding cannot change a class containing no eligible decimal integer literal. Such unchanged variants remain in the dataset for completeness. The evaluation includes only source pairs that differ, yielding 896 changed Java variants and 920 changed Python variants. 

E.2 Transformation Details 

The 13 interferences cover seven readability dimensions: comments, identifiers, expressions, code injection, layout, data flow, and control flow. The transformations and the number of source classes for which each produced a source-level change are summarised in Table 15. The two unrelated-code injection conditions use separate sets of ten templates. Readable tem-plates use conventional control flow, formatting, and descriptive identifiers, whereas low-readability templates use compact identifiers, opaque expressions, and deliberately less transparent control flow. Both transformations insert at most one template into a class, allowing their effects to be evaluated under comparable target cardinality. Identifier transformations operate on eligible method, parameter, and local-variable bindings and update recognised references consistently. Constructors and language-required names are preserved. Candidate names that would conflict with existing bindings or language keywords are rejected. Misleading identifiers are selected primarily by length proximity to the original name, while garbled identifiers follow a deterministic shortest-available-name strategy. Integer-literal encoding rewrites eligible decimal integer literals using lowercase hexadecimal no-tation. It does not recursively transform literals that are already hexadecimal. Numeric-intermediate introduction performs the complementary data-flow modification: an eligible integer literal is de-composed into two values stored in newly introduced short-named variables, and the original literal is replaced by their sum. Intermediate-variable inlining targets eligible local variables that have an initializer, are not subsequently reassigned, and have exactly one supported use. The declaration is removed, and the use is replaced by a parenthesised copy of the initializer. Language-specific exclusions are applied where the transformation cannot be performed reliably. Condition, data-flow, and control-flow transformations are applied only when the corresponding syntactic structures satisfy their safety constraints. Java loop lowering covers eligible classic and enhanced for loops. Python loop lowering covers eligible synchronous for loops using explicit iterator-based control flow. Therefore, the number of changed variants differs across transformations and languages.

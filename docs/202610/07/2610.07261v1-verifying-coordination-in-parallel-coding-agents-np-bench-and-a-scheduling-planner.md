## 摘要
一支编码智能体团队可能逐个来看都表现良好，但作为整体却会失败：每个智能体都能通过自己的测试，而合并后的结果却是坏的，单智能体评测永远无法发现这一点。当团队在同一代码库上并行运行多个 LLM 编码智能体时，智能体之间会发生冲突：两个智能体重写同一个函数，一个智能体按照队友刚刚修改过的契约来编码，而集成在工作完成之后才失败。大多数协同工具都是被动反应式的（监测冲突，然后发出警告），但在智能体的速度下，警告到来时那次无效编辑已经发生。我们将该问题重新表述为调度问题：获取每个工作项所声明的范围，将工作划分为互不相交的范围，并沿生产者→消费者图对合并进行排序，全部提前完成。我们将该规划器构建到 Nerveplane 中，并用 NP-Bench 对其进行评估。NP-Bench 是一个基于真实环境的三组对照基准（无协同；反应式检测；主动式规划），它依据真实的 git 合并来验证集成，既在确定性仿真中进行，也使用真实智能体进行。该规划器将干净集成从 1/9 个场景提升到 9/9 个场景，并将合并冲突从 13 次减少到 0 次，且这一差距随智能体数量的增加而扩大。在一次真实的破坏性契约变更中，它挽救了两个基线在每个随机种子上都会错失的结果：干净集成率从 0（无协同与反应式检测）提升到前沿模型上的 1.0 和小模型上的 0.6，同时智能体遵守了所分配的范围（0/5 泄漏）。跨会话记忆将重复错误率从 1.00 降至 0.00，在强模型和弱模型上都是如此。我们还报告了一个负面结果：将事实路由给智能体并不能在适配上下文窗口的规模上挽救长上下文准确率；其价值在于成本与容量，而非注意力。在两个能力层级和两家供应商上，这一收益并未随着模型变强而缩小，因为它来自工作的分配方式，而非模型的推理能力。

## Abstract
A team of coding agents can look fine agent by agent yet fail as a team: each passes its own tests while the merged result is broken, and single-agent evaluation never catches it. As teams run several LLM coding agents in parallel on one codebase, the agents collide: two rewrite the same function, one codes against a contract a teammate just changed, and integration fails after the work is done. Most coordination tools react (watch for a conflict, then warn), but at agent speed the warning arrives after the wasted edit. We recast the problem as scheduling: take each work item's declared scope, partition the work into disjoint scopes, and order merges along the producer->consumer graph, all up front. We build this planner into Nerveplane and evaluate it with NP-Bench, an environment-grounded three-arm benchmark (no coordination; reactive detection; proactive planning) that verifies integration off a real git merge, both in a deterministic simulation and with live agents. The planner lifts clean-integration from 1/9 to 9/9 scenarios and cuts merge conflicts from 13 to 0, with a gap that grows in the number of agents. On a live breaking contract change it rescues an outcome both baselines miss on every seed: the clean-integration rate rises from 0 (no coordination and reactive detection) to 1.0 on a frontier model and 0.6 on a small one, while agents respect assigned scopes (0/5 leakage). A cross-session memory drops the repeated-mistake rate from 1.00 to 0.00 on strong and weak models alike. We also report a negative result: routing facts to agents does not rescue long-context accuracy at window-fitting scales; its value is cost and capacity, not attention. Across two capability tiers and two vendors, the benefit did not shrink as models got stronger, because it comes from how work is allocated, not model reasoning.

## 1. 核心问题与研究动机

- **核心问题**：多个 LLM 编码智能体在同一代码库上并行工作时，会出现协同失败：两个智能体改写同一函数、一个智能体按队友刚修改的契约编码、集成在工作完成后才失败。每个智能体单独看都能通过自己的测试，但合并后的系统可能是坏的。
- **现有评测盲区**：SWE-bench、HumanEval、LiveCodeBench 等基准主要衡量单智能体、单仓库任务成功率，无法衡量 N 个并行智能体是否能干净集成。
- **现有协同工具的不足**：多数工具是反应式的——监测到冲突或契约变化后再警告。但在智能体速度下，警告到达时无效编辑往往已经发生，警告只能带来清理而非预防。
- **论文主张**：并行编码智能体的协调问题应被重新表述为**调度问题**：提前根据每个工作项声明的范围，划分互不相交的作用域，并按生产者→消费者依赖图排序合并。
- **整体含义**：协调收益来自“工作如何被分配”，而非模型推理能力；因此模型变强不会自动消除该问题，需要显式调度与前置验证。

## 2. 方法论：核心思想与关键技术细节

- **问题形式化**：
  - 设工作项集合为 \(W\)，每个工作项 \(w\) 有声明范围 \(\sigma(w)\)（将写入的文件或符号集合）和消费契约集合。
  - 两个工作项冲突当且仅当 \(\sigma(w_i) \cap \sigma(w_j) \neq \emptyset\)。
  - 若 \(w_j\) 消费 \(w_i\) 产生的契约，则存在依赖边 \(w_i \rightarrow w_j\)。
  - 一个计划是将 \(W\) 划分为若干批次，批次内成员范围两两不相交，并给出尊重依赖边的合并顺序 \(\pi\)。

- **核心保证（假设限定）**：
  - 若声明范围准确且依赖关系为 DAG，则“不相交范围划分 + 拓扑合并顺序”可按构造保证零结构性冲突：并发项不碰同一文件，消费者不会先于生产者合并。
  - 反应式检测器无法提供该保证，因为它只在碰撞被感知后才行动。
  - 范围准确性由手工声明输入假设；智能体是否遵守范围是实验测量的经验问题。

- **静态规划算法（Algorithm 1）流程**：
  1. 对所有 \(i \neq j\)，若 \(\sigma(w_i) \cap c(w_j) \neq \emptyset\)，构建依赖边 \(w_i \rightarrow w_j\)。
  2. 初始化重分配集合 \(R\)；对每个文件，按输入顺序将第一个写入者设为所有者。
  3. 若某工作项触碰他人拥有的文件，则加入 \(R\)，标记为“范围争用”。
  4. 若某工作项有至少一个生产者，则加入 \(R\)，标记为“必须适配被消费契约”。
  5. 使用 Kahn 算法计算稳定拓扑序 \(\pi\)，以输入顺序打破平局；若出现环，则删除“下游消费者最少的生产者”的边来破环。
  6. 按 \(\pi\) 顺序，将每个工作项贪心分配到最低的、无范围重叠项的批次中。
  7. 返回批次、合并顺序 \(\pi\)、重分配集合 \(R\)。

- **系统实现：Nerveplane**：
  - 本地优先的编码智能体系统：每机器一个守护进程、SQLite 存储、通过 MCP 暴露工具（register、sync、publish、decision、discover、chat、memory、task）。
  - **被动感知**：轮询每个注册智能体的 git worktree，当变更文件集合实际变化时发出事件，不依赖智能体主动上报。
  - **路由引擎**：决定谁需要知道某变更——受影响任务的所有者、同仓库其他智能体，以及通过服务图发现的跨仓库 API 契约消费者。
  - **规划器**：在守护进程内运行，通过 register/sync 向每个智能体交付其分配范围、合并槽位和重分配原因。
  - **决策账本与跨智能体记忆**：项目决策存放在可查询账本中，跨会话记忆让一个会话学到的经验在后续会话中重新出现。
  - 与消息总线的区别：状态感知平面理解分支、变更文件和服务契约，能按相关性路由并提前行动。

## 3. 实验设计：场景、Benchmark 与对比方法

- **Benchmark：NP-Bench**
  - 基于真实环境的三臂基准，依据真实 git merge 验证集成结果。
  - 三个对照臂：
    - **C0**：无协调，智能体彼此盲操作。
    - **C1-DETECT**：反应式协调，当队友感知到的变更触及某智能体关心的文件时发出警告；对真实智能体故意使用模糊警告（“队友可能正在编辑 X”），模拟现实中的即时警告。
    - **C1-PLAN**：主动规划，智能体开始前收到允许/禁止范围，或对契约消费者收到精确契约迁移信息和“在生产者合并后按新形状编码”的指令；计划还提供合并顺序。
  - 两个层级：
    - **Tier A**：确定性仿真，驱动真实产品原语（注册、worktree 感知、冲突检测、规划器核心），用真实 git 集成评分，CI 门控且可复现。
    - **Tier B**：真实智能体，在隔离 git worktree 中无头运行，真实合并评分，非确定性且花费成本，不作 CI 门控。

- **主要指标**：
  - **CTSR**：干净树成功率，既无合并冲突又通过集成后验收检查的比例。
  - **Merge conflicts**：git 冲突数量。
  - **Wasted LOC**：冲突编辑中需要返工的行数。
  - **Scope-leakage**：被重分配的 C1-PLAN 智能体中编辑了禁止文件的比例。
  - **Consumer-adaptation rate**：扇出消费者合并后使用新契约字段的比例。
  - **Repeated-mistake rate**：1 减去对先前会话记录决策的遵守率。
  - **Merge-order correctness**：每个生产者是否排在其消费者之前。

- **场景**：
  - 共享文件争用。
  - 契约迁移：生产者将发票金额字段从 `amount`（美元）改为 `amountCents`（整数美分），消费者在旧契约下实现总计；两文件可干净合并，但消费者语义错误。
  - 跨仓库扇出：一个生产者迁移契约，N 个消费者各自渲染。
  - 独立控制场景：无关任务，检验协调层是否产生无谓干扰。
  - 并发/高 N 变体。
  - 跨会话记忆场景：两个对称认证后端导出同名函数，哪个被批准只存在于团队记忆中，代码库无法推断。

- **对比方法与模型**：
  - 三臂对比：C0、C1-DETECT、C1-PLAN。
  - 真实智能体模型：
    - Claude Opus 4.8（前沿模型，`claude-opus-4-8`）。
    - Claude Haiku 4.5（小模型，`claude-haiku-4-5`）。
    - OpenAI GPT-5-Codex（`gpt-5-codex`，第二供应商）。
  - 确定性 effect-by-N 扫描：N ∈ {2, 4, 8, 16, 32}。
  - 真实扇出：N ∈ {2, 4, 8}。

## 6. 主要结论与发现

- **确定性结果**：
  - CTSR 从 C0 的 1/9 提升到 C1-DETECT 的 4/9，再到 C1-PLAN 的 9/9。
  - 总合并冲突：13 → 12 → 0。
  - 浪费 LOC：54 → 49 → 0。
  - 顺序依赖场景中，反应式检测与规划器打平；并发场景中，反应式检测退化为 C0，因为警告总是太晚。
  - 独立控制场景三臂都成功，协调层无副作用。
  - Effect-by-N：C0 与 C1-DETECT 冲突随 N 线性增长（n−1），浪费 LOC 约 4(n−1)；C1-PLAN 在 N 到 32 时保持零冲突。

- **真实智能体结果**：
  - 破坏性契约变更中，C0 和 C1-DETECT 在所有模型上 CTSR 均为 0.00。
  - C1-PLAN：Opus 4.8 为 1.00（15/15，CI [0.80, 1.00]）；Haiku 4.5 为 0.60（CI [0.23, 0.88]）；GPT-5-Codex 为 1.00（CI [0.57, 1.00]）。
  - 前沿模型上规划器与基线分离显著，Fisher 精确检验 p < 10⁻⁴。
  - 扇出场景：消费者适配率在基线下为 0.00，在规划器下 N ∈ {2,4,8} 均为 1.00。
  - 范围合规：共享文件场景 scope-leakage 为 0.00，真实智能体尊重分配范围。
  - 失败不是能力失败：消费者所需信息根本不在其 worktree 中，模型再强也无法恢复。

- **记忆连续性**：
  - 重复错误率从 1.00 降至 0.00，前沿模型和 Haiku 均如此（K=5）。
  - 正确选择无法从仓库恢复，因此这是信息差距而非推理差距，且不随模型强弱改变。

- **负面结果**：
  - 将事实路由给智能体并未

能保证被有效使用。长上下文检索负面实验显示：即便把相关事实放进上下文，智能体在 10k、50k、100k token 规模下仍难以可靠地完成多事实连接；当上下文接近或超出模型窗口时（小模型 200k 窗口溢出 5/5），任务直接失败。这说明“信息可得”不等于“信息被正确使用”，单纯扩大上下文窗口或做检索增强并不足以替代结构化的协调机制。

- **负面结果的方法学含义**：
  - 协调失败的根因是**信息在智能体工作集内的缺失或错位**，而非模型推理能力不足。因此靠“换更强的模型”“给更长的上下文”并不能系统性消除问题。
  - 反应式检测在高并发下会退化为无协调，因为警告的到达时间晚于无效编辑发生时间。
  - 规划器的收益依赖于范围声明的准确性；一旦范围推断错误，前置保证会被削弱（论文将其列为未来工作）。

## 7. 讨论：机制解释与理论意义

- **“调度而非推理”的重述**：
  - 论文把并行智能体协调从“检测与修复冲突”的问题，重新定义为“提前划分作用域并按依赖排序”的调度问题。这一重述的关键在于：冲突可以在结构层面被预防，而不必在语义层面被检测。
  - 由此得到一个可检验的推论：协调收益应与调度质量相关，而与模型能力弱相关。实验结果支持该推论——契约迁移和记忆连续性场景中，能力差距并未改变失败模式，改变的是信息是否被提前交付。

- **预防 vs. 反应的范式对比**：
  - 反应式协调（C1-DETECT）在**顺序依赖**场景中与规划器打平，说明当编辑天然有序时，事后警告仍可能赶在编辑之前。
  - 但在**并发**场景中，反应式协调退化为 C0，因为并发编辑在物理上同时发生，警告必然滞后。这解释了为什么许多现有协同工具在低并发下“看起来有效”，在高并发下失效。
  - 论文据此主张：协调机制的设计目标应是“让无效编辑不发生”，而非“让无效编辑被更快发现”。

- **生产者→消费者依赖图的作用**：
  - 依赖边不仅决定合并顺序，还决定**契约信息的传递方向**。规划器把“生产者即将改变契约”的精确信息前置给消费者，使消费者能在新形状下编码。
  - 这解释了扇出场景中消费者适配率从 0.00 到 1.00 的跃升：消费者所需的信息原本不在其 worktree 中，规划器把它显式注入。

- **跨会话记忆与团队知识**：
  - 某些决策（如两个同名认证后端中哪个被批准）无法从代码库推断，只存在于团队记忆中。重复错误率从 1.00 降至 0.00 表明，这类“信息差距”可以通过可查询的决策账本消除，而不依赖模型推理。
  - 与长上下文负面结果结合看：关键不是把更多 token 塞进上下文，而是把**正确的事实**在**正确的时机**路由给**正确的智能体**。

- **对智能体系统设计的启示**：
  - 协调层应作为**状态感知平面**存在，理解分支、变更文件与服务契约，而非仅作为消息总线转发通知。
  - 范围声明、合并槽位、重分配原因需要作为一等公民交付给智能体，而非事后告警。
  - 模型能力提升不会自动消除协调问题，因此协调机制应被视为与模型能力正交的独立工程维度。

## 8. 局限性与未来工作

- **范围推断未自动化**：论文中的 scope 为手工种子，未实现从任务描述自动推断声明范围。若范围声明不准，前置保证会被削弱。这是最直接的限制。
- **场景覆盖有限**：九个脚本场景和若干真实细胞为手工构造，未必覆盖真实大型代码库的复杂性（如深层模块依赖、动态契约、跨语言边界）。
- **样本量与统计功效**：多数真实细胞 K=5 或 K=3，作者自称为 pilot，置信区间较宽。只有关键契约细胞 K=15 具备较强统计支撑。
- **Tier A 的仿真性质**：确定性层的智能体编辑是脚本化的，只验证机制与路由精度，不验证真实智能体行为；其结论不能直接外推到真实智能体。
- **反应式基线的可能低估**：C1-DETECT 的警告被故意模糊（“队友可能正在编辑 X”），未做“详细但晚”的消融，因此无法完全分离**时机**与**信息特异性**两个因素对失败的影响。
- **范围泄漏测量范围窄**：仅在简单共享文件场景测量，未在复杂契约或跨仓库场景检验智能体是否遵守分配范围。
- **成本与资源透明度不足**：未报告推理 token、API 调用次数、总费用或硬件配置，难以评估方法的经济可行性。
- **未来工作方向**（据论文隐含）：自动化范围推断、更丰富的真实场景、更大样本量的真实智能体实验、时机与信息特异性的分离消融、以及将协调平面扩展到更多仓库与契约类型。

## 9. 总体评价

- **核心贡献**：
  1. 将并行编码智能体的协调问题重新表述为调度问题，并提出“不相交范围划分 + 拓扑合并顺序”的前置保证框架。
  2. 提出并实现 Nerveplane 系统，包含被动感知、路由引擎、规划器、决策账本与跨智能体记忆。
  3. 构建 NP-Bench 三臂基准（C0 / C1-DETECT / C1-PLAN），结合确定性仿真与真实智能体两层，用真实 git 合并评分。
  4. 通过跨模型、跨供应商、跨能力层级的实验，证明协调收益来自工作分配而非模型能力。

- **方法学优点**：
  - 三臂设计能区分“协调是否有用”与“哪种协调有用”。
  - 确定性层可复现、CI 门控；真实层使用真实合并，结果客观。
  - 负对照（独立控制场景）、原始回复日志、撤回错误评分，体现严谨。
  - 报告 Wilson 95% CI 与 Fisher 精确检验，统计报告规范。

- **主要弱点**：
  - 范围推断未自动化，削弱了前置保证在真实场景中的可落地性。
  - 真实细胞样本量偏小，多数为 pilot 级别。
  - 反应式基线可能因模糊警告而被低估。
  - 资源与成本透明度不足。

- **综合判断**：论文的核心论点——**并行智能体协调是一个调度问题，收益来自工作分配而非模型推理**——在实验中得到了较强的支持，尤其体现在并发场景中反应式检测退化为无协调、以及契约信息缺失无法靠模型能力弥补这两个关键发现上。方法学设计总体扎实，但受限于手工场景、小样本与未自动化的范围推断，其结论的外部有效性仍需更大规模、更真实环境的研究来验证。作为一个重新框定问题并提供可运行原型的贡献，该工作对多智能体编码系统的设计具有明确的指导价值。

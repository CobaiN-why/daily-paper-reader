## 摘要
尽管基于大语言模型构建的编程智能体近来取得了成功，但让它们在长时程上运行仍具挑战，因为每个观察都会被追加到上下文中，且上下文会随每个观察不断增长。基于历史的维护是一种常见补救措施，它掩蔽或摘要化旧观察，或剪除模型认为无用的内容，并以很小代价限制上下文。然而，它仅依据历史文本做决定，完全看不到代码之间是如何关联的。由于编程智能体在单个任务中会多次编辑代码，而每次写入都可能改变其他位置代码的含义，这种维护可能保留已被某次写入证伪的记录，丢弃仍然成立的记录，并遗漏智能体下一步需要的代码。为克服这些挑战，本文提出 StateTape，一种新颖且可扩展的框架，它随着代码仓库的变化而非上下文的增长来重写编程智能体的上下文。StateTape 的核心思想是将代码仓库建模为符号级代码图，其依赖关系与语言规则揭示一次写入可能影响哪些符号。在此图上，一条 tape 标记每次写入所改变的符号，从而将过时性从对文本的推断转变为对智能体写入的观察。我们提出一种逐写入流程，其中 tape 提名某次写入可能已证伪的记录，而一个小型管理器模型裁定写入日志无法确定的部分；并进一步提供理论分析与 TraceBench，一个将智能体当前持有的内容与其实际所需内容进行标注的基准。经验上，我们证明 StateTape 能够有效清除已被证伪的记录并检索所需内容，从而在涵盖六个编程智能体和三个编辑密集型基准的所有实验中，以很小的计算开销取得更高的解决率。

## Abstract
Despite the recent success of coding agents built on large language models, it remains challenging to run them over long horizons, since every observation is appended to the context and the context grows with each one. History-based maintenance is a common remedy, which masks or summarizes old observations, or prunes what a model reads as useless, and bounds the context at little cost. However, it decides from the text of the history alone and sees nothing of how the code is connected. Since a coding agent edits code many times over a single task, and each write can change what code elsewhere means, such maintenance may keep records a write has falsified, drop ones that still hold, and miss code the agent needs next. To overcome these challenges, this paper proposes StateTape, a novel and scalable framework that rewrites a coding agent's context as the repository changes rather than as the context grows. The key idea of StateTape is to model the repository as a symbol-level code graph, whose dependencies and language rules expose which symbols a write can affect. Upon this graph, a tape marks the symbols each write changed, which turns staleness from an inference about text into an observation of the agent's writes. We propose a per-write procedure in which the tape nominates the records a write could have falsified while a small manager model settles what the write log cannot, and further provide a theoretical analysis and TraceBench, a benchmark that labels what an agent is holding against what is actually needed. Empirically, we demonstrate that StateTape can effectively clear falsified records and retrieve what is needed, and thus achieve a higher resolve rate in all experiments spanned by six coding agents and three edit-heavy benchmarks with little computational overhead.

## 一、核心问题与研究动机

- **背景**：基于大语言模型的编程智能体已能连续执行数百步软件工程任务（读文件、跑测试、改代码），但在需要大量编辑的长时程任务上，解决率随任务变长而下降，即便每一步都在模型能力范围内。
- **机制性根源**：每个观察都被追加进上下文，上下文无界增长；长上下文既耗 token，又削弱模型对已有信息的利用。因此"上下文管理"（决定智能体在请求之间携带什么）成为智能体框架的标准组件。
- **现有主流做法——基于历史的维护**：掩蔽/折叠窗口外的旧观察、超过阈值后摘要历史、或让模型判断并剪除"无用/过期"记录。它们成本低，但**只依据历史文本本身做决定，完全看不到代码之间的连接关系**。
- **关键洞察**：编程智能体与"只记忆"的智能体不同——**它自己的写操作会改变已有证据的含义**。因此单次写入可使上下文同时出现三类错误（论文图 1 例子）：
  - **stale（过时）**：持有的记录被后续写入证伪；
  - **unneeded（无用）**：文本仍正确，但已无人使用（如唯一调用点被删除）；
  - **missing（缺失）**：下一步编辑需要的代码从未被读过（如调用方、新被调方）。
- **TraceBench 实测证据**：在 403 个"即将编辑"决策点上，Claude Code 持有的 token 中 **73.4% 不需要**，且其中 **72.3% 属于过时**；下一步编辑所需的 gold token 有 **58.5% 不在上下文中**；不需要的 token 随编辑次数从 4.4k 增长到 23.0k（占比 74%→80%），**并非固定开销**。
- **理论刻画**：论文把记录定义为带时间戳的断言 `r = (c_r, ρ_r, τ_r)`，过时即 `¬φ_r(w_t)`。由于观察不改变仓库状态，**只有写入能证伪记录**，故过时集合单调增长（`S_t ⊆ S_{t+1}`），这使"证据生命周期"成为真正的长时程问题，且效应随编辑次数而非步数增长。
- **整体含义**：上下文维护应从"随上下文增长而处理"改为"随仓库变更而重写"，且写入是唯一需要被读取的信号。

## 二、方法论

### 核心思想
- 把仓库建模为**符号级代码图**，让写入、持有的记录、依赖关系处于同一坐标粒度；以"**tape**"记录每次写入造成的图差异，把过时性从"对文本的推断"变成"对智能体写入的观测"；同一组漂移符号同时驱动**驱逐**与**检索**，由一个小型 **manager** 模型处理规则无法判定的部分。

### 三个组件

1. **符号级代码图 Φ(t) = (V_t, E_t, b_t)**
   - `V_t` 为符号（函数/方法/类）集合，`E_t` 为调用边，`b_t(v)` 为符号体文本；符号在编辑移动时保持身份，故可逐符号比较。
   - 每次写入只重解析被写入的文件，调用边仅在写入后重解析，且只比较与写入文件相关的边；用 **per-symbol last-write 索引 `last_t(v)`** 精确回答窗口查询，避免在请求路径中物化整图。

2. **Tape：动作条件过时性检查器（无模型调用）**
   - 每次写入产生两组漂移符号：
     - `X_t`：被删除的符号，或 body 被改写的符号；
     - `∂X_t`：body 未变但**调用边发生增删**、导致调用解析目标改变的符号（如 import 改动使 `read_config` 内的 `load()` 指向别的定义）。
   - 提名规则：`N_t = { r ∈ Ct : ρ_r ∩ (X_(τr,t] ∪ ∂X_(τr,t]) ≠ ∅ }`，并保证 `N_t ⊇ S_t`（不遗漏任何过时记录）；观察步骤不产生漂移，故不提名。
   - 每次提名附带**默认动作**：
     - `REFRESH`：符号仍存在且 body 改变 → 用当前 body 替换记录；
     - `DROP`：命中仅在 `∂X_t` 或符号已被删除 → 留一条 tombstone，告知智能体失去的上下文及原因；
     - `RERUN`：状态型指称（如测试结果）→ 换成要求重跑的 stub；
     - `KEEP`：提名过度触发但记录仍正确。
   - 论文强调该规则"精确"且"零推理成本"，因为写入与记录共享同一符号单位。

3. **Manager：小型 LLM（仅在 tape 有提名时进入请求路径）**
   - 三项决策：给每条提名分配上述四类动作；驱逐**未被写入证伪但任务已用完**的记录 `Dm_t`（tape 做不到，因为它取决于任务走向）；从漂移符号沿调用边**外扩最多 2 跳**检索下一步需要的代码 `Rm_t`，并与源码核对。
   - 只能通过 9 个**只读 skill**（提名列表、漂移符号、依赖方、某符号的证伪记录、上下文清单、记录原文、来源、读文件、提交决策）访问仓库，每次调用预算 25 次；skills 全部由图与 tape 无模型作答，且不返回参考补丁、不返回过时判定。
   - 最终策略（式 8）：`D_t = N_DROP ∪ N_REFRESH ∪ N_RERUN ∪ Dm_t`，`A_t = tomb(...) ∪ fresh(...) ∪ stub(...) ∪ Rm_t`。

### 目标形式化与评分代理
- 原始目标：在同一 token 预算 `n(Ct) ≤ B` 下，最小化无用质量 `σ(Ct) = n(Ct \ Gt)`、最大化 gold 覆盖率 `Rec(Ct) = n(Ct ∩ Gt)/n(Gt)`。
- 由于该目标描述的是"好的上下文"而非"产生它的动作"，论文转为对动作打分：
  - **附带效率 CE(D_t) = n(D_t \ Gt) / n(D_t ∩ Gt)**（每破坏一个有用 token 能清除多少无用 token，对应 O1 驱逐）；
  - **检索效率 RE(A_t) = κ · n(A_t ∩ (Gt \ Ct)) / (n(Gt \ Ct) · n(A_t))**（每千 token 新增能回收多少右侧缺口，对应 O2 检索），κ 只定单位不影响最优解。
- 三个技术需求：写入锚定的过时判定（R1）、前瞻性驱逐（R2）、依赖导向检索（R3），分别由代码图 + tape + manager 承担。

## 摘要
将大型语言模型（LLMs）集成到多智能体系统中已在自动化调试方面展现出巨大潜力。然而，当前几乎所有框架都依赖僵化、预定义的架构：智能体的数量、角色及其交互模式在对待调试缺陷进行任何分析之前就已固定。这种一刀切的方法从根本上无法匹配软件缺陷的异构性质。简单缺陷会在不必要的协调上浪费资源，而复杂缺陷则因专业知识不足或匹配不佳而受损。本文提出 ASAD，一种用于调试的自适应智能体系统，它根据每个缺陷的性质和复杂度来配置其团队。ASAD 通过分析故障代码来启动调试过程，并动态确定要部署的智能体数量、它们应具备的专门角色以及它们应遵循的协作策略。一个中央协调器通过迭代式规划、反思和执行来编排该过程；对简单问题采用快速单遍修复，同时组建专门团队来应对更复杂的故障。我们在三个成熟的基准上评估 ASAD：Defects4J、DebugBench 和 CodeFlaws，并使用多个 LLM，如 DeepSeek-V3、Qwen-3 和 GPT-5。ASAD 相比思维链（CoT）提示将缺陷修复率稳定提升 12--20%，在修复精度上持续优于静态多智能体系统 4--9%，同时将平均智能体使用量降低 32%。关键的是，我们的系统动态调整智能体的数量和角色：它以最小协调解决简单缺陷，并仅对更复杂的情况扩展智能体参与。

## Abstract
The integration of Large Language Models (LLMs) into multi-agent systems has shown great potential for automated debugging. Yet nearly all current frameworks rely on rigid, predefined architectures: the number of agents, their roles, and their interaction patterns are fixed before any analysis of the bug occurs. This one-size-fits-all approach is fundamentally mismatched to the heterogeneous nature of software defects. Simple bugs waste resources on unnecessary coordination, while complex ones suffer from insufficient or poorly aligned expertise. This paper introduces ASAD, an adaptive agentic system for debugging that configures its team according to the nature and complexity of each bug. ASAD initiates the debugging process by analyzing the faulty code and dynamically determines the number of agents to deploy, the specialized roles they should have, and the collaboration strategy they should follow. A central coordinator orchestrates this process through iterative planning, reflection, and execution; applying fast single-pass repairs for simple issues while assembling purpose-built teams to tackle more complex failures. We evaluate ASAD on three established benchmarks: Defects4J, DebugBench, and CodeFlaws, using multiple LLMs, such as DeepSeek-V3, Qwen-3 and GPT-5. ASAD consistently improves bug-fix rates by 12--20% over chain-of-thought(CoT) prompting and consistently outperforms static multi-agent systems by 4--9% in fix precision while reducing average agent usage by 32%. Crucially, our system dynamically adjusts the number and roles of agents: it resolves simple bugs with minimal coordination and scales agent involvement only for more complex cases.

## 1. 核心问题与研究背景

- **研究动机**：LLM 驱动的多智能体系统在自动化调试中潜力巨大（分工如故障定位、补丁合成、静态分析、验证），但当前几乎所有框架都采用**僵化、预定义的架构**：智能体数量、角色、通信模式在分析缺陷之前就已固定。
- **核心矛盾**：软件缺陷本身是高度异构的，"一刀切"架构与问题性质根本错配：
  - 简单缺陷（如语法错误）被迫承担不必要的多智能体协调开销；
  - 复杂缺陷（如并发、API 误用）则因专家配置不足或角色错配而修复质量受限。
- **附带问题**：长时间多智能体交互会导致**目标漂移（goal drift）**，且缺乏有效的上下文传播机制，削弱协作一致性。
- **理论定位**：以 agenticness 四维度（目标复杂度、环境复杂度、适应性、独立执行）审视现有系统，发现前两者已被较好覆盖，而**适应性与独立执行严重不足**——系统更像"被动工具"，而非能自主调整结构的智能体。
- **整体含义**：论文主张把"智能体配置"从固定的先验选择，变为**问题复杂度的函数**，从而同时改善准确率与效率。

## 2. 方法论：ASAD 的核心思想与流程

- **核心思想**：先分析故障代码，再动态决定**智能体数量、专门角色、协作策略**；中央协调器（主智能体 / Team Leader）通过**规划 → 反思 → 执行**的迭代循环进行编排。简单问题走快速单遍修复，复杂故障才组建定制团队。
- **融合三种推理机制**：Planning（任务分解）、Iterative Reflection（基于验证反馈精修补丁）、Multi-Agent Collaboration（角色分工与信息共享）。

### 2.1 主智能体的关键任务

1. **代码分析（路由决策）**：主智能体接收**轻量静态分析报告**作为客观证据，覆盖五个维度：
   - 错误严重度（失败测试数、运行时/编译错误）
   - 源位置难度（受影响区域的 AST 深度、相关函数 NLOC）
   - 程序理解难度（圈复杂度、AST 分支因子）
   - 系统级操作（并发构造、资源管理 API）
   - 函数间依赖（文件内调用图 fan-in / fan-out）
   - 综合判断输出二分类：**SIMPLE**（单遍直接修复）或 **COMPLEX**（多步分解 + 实例化专门智能体）。
2. **智能体画像与优先级排序**：每个画像由三要素构成——**Role（调试职能）、Objective（目标问题类别）、Execution Constraints（允许修改范围）**；随后按任务依赖关系确定执行顺序（如语法修复先于逻辑验证），顺序执行，且某智能体只有在其前置职责完成后才能运行。
3. **迭代任务审查**：不一次性派发全部智能体，而是**逐步调用**；每个智能体完成后提交结构化报告（改动、理由、遗留问题），主智能体审核：满意则激活下一个，不满意则要求当前智能体重做，**每个智能体最多 3 次尝试**。
4. **最终验证**：若代码通过验证则输出；否则生成失败日志（含剩余问题）回传分析阶段，触发新一轮迭代，并**显式要求主智能体提出与历史迭代不同的策略**，避免重复失败计划。
5. **Simple Fix 路径**：对判定为简单的缺陷，用定向提示让主智能体单遍修复，直接进入验证，绕过智能体部署与协调开销。

### 2.2 边界约束（Bounded Execution）

- **智能体级**：每个专门智能体最多 3 次精修尝试（经验上收益递减）。
- **系统级**：整个调试过程最多 5 次全局迭代（每次为"分析—规划—执行—验证"完整循环）。
- 专门智能体**顺序执行**而非并行，由主智能体监督，防止错误在流水线中传播。

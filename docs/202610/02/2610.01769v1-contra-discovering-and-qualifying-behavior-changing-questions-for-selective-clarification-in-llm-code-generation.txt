# ABSTRACT 

Coding agents can generate code that appears correct but implements behavior the user never intended. This mismatch can arise when an agent silently resolves underspecified requirements through its own assumptions. As subsequent develop-ment builds on these assumptions, correcting the resulting behavior can become increasingly costly. Early clarification can help prevent such mismatches, but un-necessary questions can interrupt developers and slow down development. Existing methods struggle to identify key clarification questions while avoiding unnecessary ones. Therefore, we propose C ONTRA , a training-free method that combines broad question discovery with semantic and execution-based question qualification. C ON - 

> TRA

first generates candidate questions and filters out those unrelated to required behavior or already resolved by the requirement. For each remaining question, it generates programs conditioned on two plausible answers and checks for stable behavioral differences on shared inputs. It then uses the interaction history to select among qualified questions or stop asking. Experiments on ClarifyCodeBench show that C ONTRA achieves the highest F1 with all four coding agents, exceeding the best baseline macro-average F1 by 13.88 percentage points. With the same LLM and evaluation protocol, C ONTRA also achieves higher clarification recall and F1 than the coding harnesses Claude Code and OpenHands. To support practical use, we also implement C ONTRA as a Claude Code plugin that integrates selective clarification into everyday development. 1

# 1 INTRODUCTION 

Coding agents are increasingly used to generate and modify code from natural-language require-ments (Hong et al., 2024; Wang et al., 2025; Yang et al., 2024). However, these requirements often leave important aspects of program behavior underspecified, such as how to handle edge cases or format outputs (Fakhoury et al., 2024; Mu et al., 2024; Fang et al., 2026). Faced with such require-ments, an agent may silently adopt one plausible interpretation and proceed with implementation. The resulting code may be correct under that interpretation, yet fail to match the user’s intended behav-ior (Fakhoury et al., 2024; Vijayvargiya et al., 2026b; Edwards & Schuster, 2026). If this mismatch goes unnoticed, subsequent development may build on the same assumptions, making correction increasingly costly. Therefore, clarification helps make these assumptions explicit and resolve the underlying choices with the user before the code becomes the basis for further development. However, excessive questioning can impose unnecessary interaction costs on developers (Zhang & Choi, 2025; Vijayvargiya et al., 2026a). For example, an agent may ask questions already answered by the requirements or earlier interactions, or raise questions unrelated to the task. This motivates selective clarification, where an agent seeks additional user input only when needed (Kuhn et al., 2022). For coding agents, this requires identifying necessary questions within a task while avoiding redundant or irrelevant ones.

Direct Prompting (Vijayvargiya et al., 2026b; Fang et al., 2026) and Ask-or-Assume (Edwards & Schuster, 2026) rely on the model to decide whether to ask, but often miss necessary questions. By comparison, ClarifyGPT (Mu et al., 2024) generates questions from behavioral disagreement among sampled programs, but asks many unnecessary questions. Such disagreement can reflect implementation errors even when the requirements are clear. Therefore, selective clarification requires both broad question discovery and careful qualification. To address this challenge, we propose C ONTRA , which combines broad question discovery with careful qualification. It first discovers candidate questions and checks whether each is relevant to the requirement and remains unresolved. For each remaining question, C ONTRA generates programs conditioned on two plausible answers and checks for stable behavioral differences on shared inputs. During interaction, it uses the user’s answers to select the next qualified question or stop asking. This design identifies key clarification questions while filtering out unnecessary ones. We evaluate C ONTRA on ClarifyCodeBench (Fang et al., 2026) with coding agents built on GPT-5-mini (OpenAI, 2025), GPT-5.5 (OpenAI, 2026), Grok 4.5 (SpaceXAI, 2026), and Gemini 3.1 Pro (Google DeepMind, 2026). Under the same five-question budget, we compare C ONTRA with Direct Prompting, Ask-or-Assume (Edwards & Schuster, 2026), and ClarifyGPT (Mu et al., 2024). CONTRA achieves the highest F1 and turn-discounted key question rate (TKQR) for all four agents. Its macro-average F1 and TKQR reach 41.20% and 38.32%, exceeding the best baseline for each metric by 13.88 and 12.33 percentage points, respectively. Furthermore, using Qwen3.8-27B (Qwen Team, 2026) and the same evaluation protocol, C ONTRA achieves higher recall and F1 than Claude Code (Anthropic, 2025) and OpenHands (Wang et al., 2025). Its F1 reaches 19.86%, compared with 9.63% for Claude Code and 10.61% for OpenHands. Finally, we integrate C ONTRA into Claude Code as a plugin that identifies and reports implementation decisions requiring user clarification. Our main contributions are as follows. • We propose C ONTRA , a selective clarification method that combines broad question discov-ery, semantic and execution-based question qualification, and adaptive question selection. Its execution-based qualification links candidate questions to behavioral differences between programs generated under alternative answers. • We demonstrate consistent improvements on ClarifyCodeBench across four coding agents, achieving the highest F1 and TKQR among the compared methods. Under the same LLM and evaluation protocol, C ONTRA also achieves higher clarification recall and F1 than the coding harnesses Claude Code and OpenHands. • We implement C ONTRA as a Claude Code plugin that identifies and reports implementation decisions requiring clarification, helping developers confirm intended program behavior during everyday development. 

# 2 RELATED WORK 

Requirement clarification and specification refinement. Prior work improves LLM code gen-eration by making user intent more explicit. CodeClarQA (Li et al., 2023) provides questions and answers that enrich underspecified requirements for code generation. TiCoder (Fakhoury et al., 2024) elicits user feedback on generated tests and uses that feedback to formalize intent and rank candidate programs. ClarifyCoder (Wu et al., 2025) uses synthetic data and instruction tuning to teach code LLMs to recognize underspecification and request clarification. Other methods refine specifications without user interaction. SpecFix (Jia et al., 2025) analyzes the behavioral distribution of sampled programs and maps changes in that distribution back to a repaired problem description. Specine (Tian & Chen, 2026) identifies mismatches between an input specification and the specification inferred from generated code, then constructs an aligned specification for subsequent generation. While these methods refine requirements, C ONTRA qualifies individual questions by checking relevance, whether they remain unresolved, and whether plausible answers change program behavior. 

Selective clarification. Selective clarification concerns deciding when additional user input is necessary. CLAM (Kuhn et al., 2022) studies whether an LLM should answer directly or request clarification, while IntentSim (Zhang & Choi, 2025) estimates clarification utility from uncertainty over simulated user intents. Learning-based approaches use simulated future turns to label prefer-2ences (Zhang et al., 2025), or train clarification policies using task relevance and user answerabil-ity (Vijayvargiya et al., 2026a). In code generation, ClarifyGPT (Mu et al., 2024) uses behavioral disagreement among programs sampled from the same requirement to decide whether to clarify. Ask-or-Assume (Edwards & Schuster, 2026) uses the coding agent or a separate intent agent to decide when user input is needed. C ONTRA evaluates each candidate question through semantic checks and behavioral verification, then uses the interaction history to select qualified questions that still require user input.

Question Discovery generates a broad set of candidate clarification questions from S. Each candidate includes a question and two plausible answers, which support candidate review and merging. To expand the candidate set, each discovery round combines context-aware and independent genera-tion. Context-aware generation uses S and the current candidate set to search for additional questions, 3while independent generation uses only S. The new and existing candidates are jointly reviewed to remove duplicates and merge overlapping questions. Discovery stops after two consecutive rounds add no distinct questions or a predefined round limit is reached. After discovery, C ONTRA regenerates two plausible answers for each retained question q as requirement completions hA and hB . The completions should be compatible with S and differ only in their answer to q. This constraint links subsequent behavioral differences to the question being evaluated and avoids introducing unrelated assumptions. Questions with completion pairs form Qgen for Question Qualification. 3.4 QUESTION QUALIFICATION 

Question Qualification evaluates each candidate question together with its completion pair. It retains questions that are relevant, remain unresolved by S, and pass behavioral verification. The qualified set is 

Qqual = {q ∈ Qgen | Rel( q) ∧ Unres( q) ∧ Diff( q)} .

Relevance and Resolution. Relevance checks whether q concerns required program behavior and whether its completions specify different alternatives for that behavior. Resolution then checks whether S already determines the answer. A question is marked as resolved only when text in S

supports one completion and rules out the other. The judgment must cite this supporting text. Only relevant and unresolved questions proceed to behavioral verification.

Therefore, Adaptive Question Selection uses the interaction history to reassess which questions still require user input. Let Qt ⊆ Qqual denote the remaining questions at step t, with Q1 = Qqual . # 4 EXPERIMENTS 

4.1 EXPERIMENTAL SETUP 

Benchmark and Evaluation. We evaluate on ClarifyCodeBench (Fang et al., 2026), which provides underspecified programming requirements with gold clarification questions and answers. Our evalua-tion uses 419 underspecified tasks and the 80 fully specified tasks provided by ClarifyCodeBench. Each method may ask at most five clarification questions before generating a final program. The benchmark’s GPT-4o evaluator matches questions against each task’s gold questions by majority vote over three judgments. 

Baselines. We compare C ONTRA with three training-free baselines. Direct Prompting uses the benchmark prompt to ask a question or generate code. Ask-or-Assume (Edwards & Schuster, 2026) adds an intent agent that reviews the proposed action and requests clarification when needed. ClarifyGPT (Mu et al., 2024) generates questions from behavioral disagreement among programs sampled from the current requirement and executed on shared inputs. We also compare with the coding harnesses Claude Code (Anthropic, 2025) and OpenHands (Wang et al., 2025). 

Evaluation Metrics. We report question precision, recall, F1, and turn-discounted key question rate (TKQR) (Fang et al., 2026). Precision is the proportion of all questions asked that match a previously uncovered gold question, including questions asked on fully specified tasks in the denominator. Recall is the proportion of gold questions matched by at least one question, and F1 is the harmonic mean of precision and recall. TKQR rewards earlier identification of gold questions using normalized discounted cumulative gain (J¨ arvelin & Kek¨ al¨ ainen, 2002), averaged across tasks. For the harness comparison, we also report the false-positive rate (FPR): the proportion of fully specified tasks on which at least one question is asked. 

Models and Implementation. We evaluate coding agents built on GPT-5-mini, GPT-5.5, Grok 4.5, and Gemini 3.1 Pro. For each comparison, all components of C ONTRA and the baselines use the same LLM. We use low reasoning effort, with stochastic sampling only for program generation in Behavioral Verification and ClarifyGPT. The harness comparison uses Qwen3.8-27B for C ONTRA ,Claude Code, and OpenHands, with the same question budget and scoring procedure. We execute generated Python programs in isolated environments under fixed time, memory, and output limits. 4.2 MAIN RESULTS

On-Demand Question Qualification. To reduce the cost of Question Qualification, we introduce CONTRA -Flash, which qualifies candidates on demand. Adaptive Question Selection first chooses a candidate from the discovered questions. The candidate then undergoes Relevance, Resolution, and Behavioral Verification before it can be asked. Rejected candidates are discarded and selection continues. This ordering avoids qualifying candidates that the selector never considers.

Integration with Claude Code. We implement C ONTRA as a Claude Code plugin that reviews decisions after implementation. The plugin combines the agent’s own report with an independent review of the requirement and code changes to discover unresolved decisions. It then prioritizes these decisions and explains what the requirement leaves unspecified, what the agent implemented, and a plausible alternative. For unresolved implementation choices, Behavioral Verification runs in the background and uses distinguishing tests to check whether alternative implementations produce different observable behaviors. Plugin implementation details appear in Appendix B.1.

We presented C ONTRA , a training-free method for selective clarification in coding agents. It combines Question Discovery, Question Qualification, and Adaptive Question Selection. Semantic checks and execution evidence identify consequential choices, while interaction history guides which questions still require user input. Experiments show consistent improvements in F1 and TKQR across four coding agents and gains over existing coding harnesses. CONTRA -Flash reduces qualification evaluations, while the Claude Code plugin makes unresolved implementation choices and their alternatives explicit for developer review. B.1 PLUGIN IMPLEMENTATION 

The Claude Code plugin reviews implementation decisions at the end of an interaction. A hook records the working tree when the user submits a request. When the agent finishes, another hook compares the updated tree with this snapshot to identify changes made during the interaction. This avoids including unrelated changes that were already present before the request. The plugin then runs two processes in parallel. One extracts decisions from the agent’s final report using claude-haiku-4-5-20251001 . The other independently reviews the requirement, code changes, and repository context using claude-opus-5 , without reading that report. Their outputs are merged using text overlap for entries concerning the same file and decision category. The combined report distinguishes implementation choices, changes beyond the requested scope, and work the agent decided not to perform. Rule-based prioritization uses these categories together with affected scope, trigger conditions, reversibility, and verification outcomes. For an unresolved implementation choice, the plugin uses claude-opus-5 to generate a distin-guishing test and a patch implementing an alternative interpretation. It executes the test on the current and patched implementations in isolated repository copies. A test that passes on the current implementation and fails on an executable alternative provides evidence of a behavioral difference. Patch or test-execution errors are distinguished from such evidence. In normal use, verification runs in the background after the initial report. Distinguishing tests can be retained in the repository to document the implemented behavior, and a persistent record tracks decisions across interactions. B.2 REPOSITORY EVALUATION 

The evaluation uses 40 single-function commits from six Python repositories, namely Rich, Flask, Requests, Click, HTTPX, and Typer. The tasks are selected by stratified random sampling, with 20 labeled underspecified and 20 labeled fully specified, using seed 20260903. For each task, the repository is restored to its pre-commit state, and the commit message serves as the requirement. Claude Code is asked to modify the target function and briefly explain the change. The final plugin runs use Claude Code 2.1.261 with claude-opus-5 and the research version of the plugin evaluated on September 5, 2026. Each task has one baseline run and one plugin run. Verification runs synchronously during evaluation so that its outcomes are collected before the process exits. Task labels are generated by claude-opus-5 from the commit message and pre-change code, then manually reviewed for all 40 tasks. The criterion is whether this information determines the required observable behavior, without filling missing information from implementation conventions. Report quality is evaluated from the agent’s final reply. We use claude-opus-5 to extract decision entries and check whether each states the unspecified information, the implemented choice, and a plausible alternative interpretation. Table 6 reports the proportion of entries containing each element and all three together. The denominators are 70 entries without the plugin and 67 with it. The decision-discovery analysis uses the plugin’s combined structured output, a separate collection from the final-reply entries above. Among its 262 decisions, 116 appear only in independent review, 89 only in the agent-derived list, and 57 in both. The repository evaluation thus measures decision discovery and report completeness. 14 C PLUGIN INTERFACE AND OPERATIONAL SCOPE

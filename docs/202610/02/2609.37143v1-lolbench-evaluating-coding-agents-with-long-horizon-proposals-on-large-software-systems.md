## 摘要
现代编码智能体能够交付越来越大的仓库级更改，近期的基准也通过强调带有大型参考实现的长时程任务来反映这一点。许多基准评估编码智能体根据详细规范生成正确代码编辑的实现能力。然而，实际模块化开发任务还需要感知能力，即将用户意图和高层设计落地，以推导出规范。我们提出 LoLBench，通过大型软件系统上完整的从提案到实现的过程来评估这两种能力。它是一个多语言基准，涵盖五个领域的 29 个软件系统中的 100 个任务。每个任务提供一份人类编写的增强提案，包含用户意图和高层设计。平均而言，提案约含 5,000 词，软件系统含 240 万源代码行（LoC），实现拉取请求（PR）更改约 5,500 LoC。在我们评估的 28 个智能体中，最佳智能体仅解决 14% 的任务，并达到 52.7% 的 Fail-to-Pass（F2P）通过率。失败分析发现，不完整的代码定位是主要瓶颈，而同时提供由参考推导出的文件树与 API 规范可将解决率提高 16--22 个百分点（2.4--17 倍），最高达到 34%。这些结果表明，在大型软件系统上的实际模块化开发中，感知和实现仍然是编码智能体的核心挑战。LoLBench 可在 https://huggingface.co/datasets/lolbench26/LoLBench 获取。

## Abstract
Modern coding agents can deliver increasingly large repository-level changes, and recent benchmarks reflect this by emphasizing long-horizon tasks with large reference implementations. Many benchmarks evaluate coding agents' implementation capability to produce correct code edits from detailed specifications. However, practical modular development tasks also require the perception capability of grounding user intent and high-level design to derive a specification. We introduce LoLBench to evaluate both capabilities through the entire proposal-to-implementation process on large software systems. It is a multilingual benchmark of 100 tasks across 29 software systems in five domains. Each task provides a human-written enhancement proposal with user intent and high-level design. On average, proposals contain about 5,000 words, software systems contain 2.4 million source lines of code (LoC), and implementation pull requests (PRs) change approximately 5,500 LoC. Across 28 agents we evaluated, the best agent resolves only 14% of tasks and achieves a 52.7% Fail-to-Pass (F2P) pass rate. Failure analysis identifies incomplete code localization as a major bottleneck, while providing reference-derived file trees alongside API specifications improves resolved rates by 16--22 percentage points (2.4--17$\times$), reaching at most 34%. These results show that both perception and implementation remain central challenges for coding agents in practical modular development on large software systems. LoLBench is available at https://huggingface.co/datasets/lolbench26/LoLBench.

## 1. 核心问题与整体含义

- **研究动机**：现有编码智能体基准（如 SWE-bench、SWE-bench Pro、Multi-SWE-bench、FeatureBench 等）主要评估智能体**从详细规格生成正确代码编辑**的能力，即实现能力。但实际模块化开发并不始于详细规格——用户和维护者通常先表达**意图与高层设计**（以增强提案 EP 的形式），开发者需先将其落地到现有系统中，再制定实现计划。
- **核心问题**：编码智能体能否直接基于**用户意图与高层设计**交付正确实现？即在大型软件系统上，智能体是否同时具备**感知能力**（将抽象意图落地为具体规格）与**实现能力**（将规格转化为无回归的正确代码修改）？
- **两类复杂性**：
  - **感知复杂性**：将用户意图和高层设计落地到大型软件系统，理解跨模块依赖，确定受影响代码。
  - **实现复杂性**：在已有大型系统上（而非从零开始）产出功能正确、无回归的代码变更。
- **整体含义**：论文提出 **LoLBench**，覆盖从提案到实现的完整流程，填补了现有基准偏重实现、忽视感知的空白。实验表明，当前最强智能体仅解决 14% 的任务，感知与实现仍是大型软件系统模块化开发的核心挑战。

## 2. 方法论

### 2.1 核心思想

- 以**人类编写的增强提案（EP）**为任务起点，要求智能体解读提案、判断新功能如何嵌入现有系统，并在离线 Docker 环境中产出无回归的代码变更。
- 采用 **F2P（Fail-to-Pass）+ P2P（Pass-to-Pass）** 测试评估，F2P 测试通过**公共接口**检查系统级/端到端行为，允许与参考实现结构不同但语义等价。

### 2.2 四阶段构建流程

1. **项目收集**：以 EP-PR 对为单位，保留条件包括：软件 ≥50k 源码 LoC；EP 至少含一个可实现章节；PR 改动 ≥1k LoC、≥10 个文件且源码占一半以上；EP 早于 PR 且仅对应一个已合并 PR；PR 含测试。
2. **EP-PR 匹配**：
   - 将 EP 章节分为**可实现**（描述外部可观察功能）与**上下文性**（背景、理由、流程）。
   - 将改动文件、类、函数映射到对应的可实现章节。
   - **28 条静态规则**校验结构属性（完整性、唯一性、映射方向等）；**8 条语义规则**（S1–S8）由 LLM 审计校验范围与归因正确性。
   - LLM 评委按五维度打分：需求覆盖度（40%）、映射精确度（25%）、范围正确性（15%）、粒度（10%）、需求具体性（10%），加权得分 ≥8.0 才保留，并设语义重要性权重（核心公共 API 1.0，内部机制 0.8，兼容性/迁移 0.6，测试/性能 0.4，文档/构建 0.2）。
3. **任务构建**：基于 Harbor 框架，每个任务提供 EP 与实现前的代码库，隐藏参考实现。保留条件：参考解可成功应用、所有 F2P 在解后通过、所有 P2P 在解前后均通过。
4. **任务增强**：
   - **错误解变异体生成**：三种提案级变换——Section Revert（移除功能）、Requirement Mismatch（改变默认值/边界/枚举/错误行为）、Semantic Mutation（改变结构或执行流）。共保留 **1,688 个**变异体。
   - **F2P 测试增强**：以变异体为引导生成能杀死存活变异体的新测试；对原始覆盖率 <50% 的任务做覆盖率引导生成。
   - **章节-测试映射**：将每个 F2P 测试映射到其断言行为的可实现章节，支持细粒度部分进度评估。

### 2.3 评估指标

- **Resolved**：通过完整任务验证器的任务百分比。
- **Completed**：已完成可实现章节占全部可实现章节的百分比。
- **F2P Pass / P2P Pass**：微平均通过率。
- 另报告平均轮次、墙钟时间、输入/生成 token 数与成本。

## 6. 主要结论与发现

- **模块化开发仍极具挑战**：最佳智能体（Claude Code 与 mini-SWE-agent + Opus 5）仅解决 **14%** 任务；28 个智能体的平均/中位解决率为 3.4%/2.0%；最高 Completed 为 26.3%（Claude Code+Opus 5），F2P 通过率 52.7%。
- **模型选择比 scaffold 选择影响更大**：固定 scaffold 时模型间 Completed 的 RSD 平均 62.0%，固定模型时 scaffold 间仅 24.0%（约 2.6 倍差距）。
- **代码定位是主导活动**：初始生成阶段占 60.4% 轮次，修复阶段占 44.2%；token 上占非缓存输入 52.4%、生成 token 45.4%。
- **跨模块上下文缺失是最大失败模式**：代码定位失败中平均 30.0/30.9 单位来自“cross-module context missing”，即到达了部分目标文件但遗漏其他模块。
- **感知能力不足是瓶颈**：检查召回率 46.4–86.4%（文件），但检查精确率仅 16.1–36.3%；修改召回率仅 36.9–65.0%。提供参考推导的文件树与 API 规格后，解决率提升 **16–22 个百分点**（2.4–17 倍），最高达 34%，说明大量困难来自将抽象提案转化为具体规格的感知过程。
- **语言差异明显**：Python、C/C++、Rust 表现较好（F2P 通过率 31.7%/48.5%/46.3%），Java、Go、TypeScript 较差（6.0%/13.5%/21.7%）；同一模型在不同语言上偏好不同 scaffold。

## 7. 优点

- **问题定位精准**：首次系统性地将模块化开发分解为“感知复杂性 + 实现复杂性”两个维度，填补了现有基准只测实现的空白。
- **任务真实性高**：使用真实开源社区的人类编写 EP（如 CPython PEP 617），而非人工合成规格；提案平均 5,000 词，仓库平均 240 万 LoC，实现改动平均 5,500 LoC。

- **评估设计灵活**：F2P 测试通过公共接口检查系统级行为，允许结构不同的等价实现；P2P 提供回归保护；章节-测试映射支持细粒度部分进度。
- **测试增强充分**：1,688 个错误解变异体 + 变异引导与覆盖率引导测试生成，将变异杀死率从 61% 提升至 96%，覆盖率从 60% 提升至 78.5%。
- **分析全面深入**：28 个智能体 × 100 任务的七阶段失败归因、token 分布、精确率/召回率、语言维度分析，诊断结论可操作。
- **消融设计有说服力**：通过“EP → 规格化 EP”的配对实验，定量分离感知与实现的贡献。

## 8. 不足与局限

- **仅评估功能正确性**：不评估可读性、可维护性、代码重复度、抽象质量或与项目设计惯例的一致性；通过验证器不代表工程上可长期维护。

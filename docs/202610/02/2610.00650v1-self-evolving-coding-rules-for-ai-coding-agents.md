## 摘要
AI 编程智能体的性能高度依赖于其底层编码规则。然而，现有编码规则通常是手工设计且固定不变的，这使得过程劳动密集且往往次优。在这项工作中，我们提出了 RuleEvolve，一个用于编码规则的自演化框架。RuleEvolve 维护一个候选编码规则池，并迭代地改进它们。在每次迭代中，它使用一个由 LLM 驱动的变异模块从现有候选中生成变体，然后使用一个评判模块评估这些变体，并用表现最佳的变体更新规则池。在两个编程智能体框架、四个骨干 LLM 和三个基准上的广泛评估表明，在生成代码的功能正确性、代码长度和/或生成成本（例如，使用的 token 数）方面，RuleEvolve 优于人工工程和现有提示优化基线。

## Abstract
The performance of AI coding agents is highly dependent on their underlying coding rules. However, existing coding rules are typically hand-crafted and fixed, making the process labor-intensive and often suboptimal. In this work, we propose RuleEvolve, a self-evolving framework for coding rules. RuleEvolve maintains a pool of candidate coding rules and iteratively improves them. In each iteration, it employs an LLM-powered mutator module to generate variants from existing candidates, and then uses a judge module to evaluate these variants and update the pool with the best-performing ones. Extensive evaluations across two coding-agent frameworks, four backbone LLMs, and three benchmarks demonstrate that RuleEvolve outperforms both manual engineering and existing prompt optimization baselines in terms of functional correctness of the generated code, code length, and/or generation cost (e.g., tokens used).

- **现有自动优化方法的局限**：
  - 自动提示优化技术（如 Prompt-Ops）主要面向仅含几句话的短提示，而编码规则是长篇、文档化的指导集合，搜索空间大得多，直接套用效果次优。
  - 编码智能体的执行是资源密集型（多轮交互、工具调用），非可微，且每次评估都需完整运行智能体并验证代码，延迟与 token 消耗巨大，使得传统的随机变异策略在计算上不可行。
- **研究意义**：论文提出 RuleEvolve——一个编码规则的自演化框架，旨在自动、迭代地优化编码规则，在**不牺牲功能正确性**的前提下，显著降低代码长度与生成成本。

## 2. 方法论：RuleEvolve 框架

### 2.1 核心思想

- RuleEvolve 维护一个大小为 \(m\) 的**候选规则池**，通过**迭代变异 + 评判 + 剪枝**的方式不断进化规则。
- 输入是一组编码任务，目标是演化出能够**泛化到其他任务**、改进代码生成的编码规则。
- 每次迭代：由 LLM 驱动的**变异器模块**生成 \(N\) 个新变体 → **评判模块**评估变体的正确性、代码长度、生成成本 → 保留得分最高的 \(m\) 个候选进入下一轮。

### 2.2 形式化问题定义

- 编码智能体 \(A_\theta\) 按条件分布 \(y \sim p_\theta(\cdot \mid x, r)\) 生成代码，其中 \(x\) 为任务，\(r\) 为编码规则，\(y\) 为生成代码。
- 正确性约束：\(\frac{1}{|X|}\sum_{x} \mathbb{E}[V(x,y)] \ge \tau\)，其中 \(V(x,y) \in \{0,1\}\) 为代码验证器（通过测试用例实现）。
- 优化目标（约束优化）：

\[
\max_r \frac{1}{|X|}\sum_{x} \mathbb{E}[E(y) + C(A_\theta, x, r)] \quad \text{s.t. 正确率} \ge \tau
\]

其中 \(E(y)\) 为代码简洁度得分，\(C\) 为成本得分。

### 2.3 关键技术细节

- **变异器模块 \(M\)**：接收规则 \(r\) 与自然语言变异指导 \(g\)（如“改进措辞、重排或合并步骤、改变风格”），输出变异后的规则 \(r_m = M(r,g)\)。
- **评判模块 \(J\)**：给定规则 \(r\)、智能体 \(A_\theta\)、任务集 \(X\)，输出综合得分 \(S = J(r, A_\theta, X)\)。
  - 正确性惩罚项：\(\mathbb{E}_x [V(x, A_\theta(x,\emptyset)) - V(x, A_\theta(x,r))]_+\)，即与“无规则”基线相比的正确率下降量。
  - 由于代码字符数与 token 使用量高度相关（图 2a 验证），用生成代码的字符数 \(|A_\theta(x,r)|\) 近似代码长度与推理成本。
  - 综合得分：\(S = -|A_\theta(x,r)| - \lambda \cdot \mathbb{E}_x [V(x,A_\theta(x,\emptyset)) - V(x,A_\theta(x,r))]_+\)，\(\lambda\) 为平衡超参数。
- **算法流程**（Algorithm 1）：
  1. 用 \(m\) 个初始变异填充规则池并评分；
  2. 每轮按策略分配 \(N\) 个变异给池中候选；
  3. 每个候选生成 \(n_j\) 个新变异，新候选**继承父代的评分集合**（解决冷启动、保证统计稳定性）；
  4. 评判新候选，合并评分，剪枝保留 top-\(m\)；
  5. 迭代 \(T\) 轮后返回平均得分最高的规则。
- **策略性变异分配**（基于 Optimal Computing Budget Allocation, OCBA）：
  - 目标是最大化“正确选择最优候选的概率”（PCS）。
  - 对非最优候选 \(i \neq b\)：权重 \(w_i \propto \left(\frac{\hat{\sigma}_i}{\hat{\mu}_b - \hat{\mu}_i}\right)^2\)，即**性能方差大**或**均值接近当前最优**的候选获得更多变异。
  - 最优候选 \(b\) 的权重：\(w_b = \hat{\sigma}_b \sqrt{\sum_{i \neq b} \frac{w_i^2}{\hat{\sigma}_i^2}}\)。
  - 最终按权重归一化得到各候选的离散变异数 \(n_i\)。

## 6. 主要结论与发现

- RuleEvolve 在所有基准上**持续取得最高或持平的 Pass Rate**，同时在代码长度和推理成本上大幅下降。
- 典型结果（OpenAI SDK + gpt-5.3-codex + BCB）：PR 从 Manual rule 的 0.45 提升至 0.49，平均代码字符从 2372 降至 453.1（降幅超 60%），token 使用从 1022 降至 544.5。
- OpenHands + HumanEval：PR 保持 0.99，平均代码行数从人工规则的 21.7 降至 12.7。
- **Prompt-Ops 虽然有时在代码长度/成本上更低，但往往以牺牲功能正确性为代价**（如 OpenHands BCB 上 PR 跌至 0.43，而 RuleEvolve 为 0.52）。论文强调正确性是最关键指标，代码错误时长度/成本优化无意义。
- 多 seed 结果显示 RuleEvolve 在保持 PR（0.502±0.026）的同时取得最低代码行数（24.3±0.4）和字符数（794.4±14），稳定性良好。
- 策略性变异分配（OCBA）优于均分和比例分配，产生最简洁的代码与最低生成成本。
- 演化过程在前 5 轮改进最快，约 20 轮后收敛。
- 规则归因分析发现：**约束代码形式的指令**（输出格式/自包含性）贡献最大；**简洁风格指令**单节效率最高；**流程/预算类指令**为净负贡献。
- 代码质量方面：圈复杂度从 5.37 降至 3.95，Halstead 体积降 47%，重复块比率降至 0；但可维护性指数从 85.1 降至 78.3（仍为 A 级），docstring 覆盖率从 47% 降至 1%——说明 RuleEvolve 主要移除的是文档与防御性脚手架，而非冗余逻辑。

## 7. 优点

- **问题选择有实际价值**：编码规则是 AI 编程智能体的关键配置，此前几乎完全依赖人工，论文首次系统性地将其形式化为可自动演化的问题。
- **方法论设计精巧**：
  - 将 OCBA 引入变异预算分配，理论上有 PCS 最大化的支撑，实验上也验证优于朴素策略。
  - 用代码字符数近似 token 成本，有图 2a 的相关性分析作为依据。
  - 正确性惩罚项设计保证“不因追求简洁而牺牲功能”。
  - 新候选继承父代评分集合，有效缓解冷启动与统计不稳定问题。
- **实验覆盖较广**：跨 2 个智能体框架、4 个 backbone（含开源与专有）、3 个基准，外加 SWE-Bench Lite 仓库级场景，泛化性验证较充分。
- **多维度评估**：不仅看 pass rate，还系统测量代码长度、时间、token、多 seed 稳定性、Pass@k、代码质量指标，并做了规则成分归因分析。
- **结论有说服力**：明确指出 Prompt-Ops 等方法在正确性上的妥协，强调正确性优先，立场清晰。

## 8. 不足与局限

- **正确性-简洁性权衡的残余风险**：

- 尽管设置了正确性惩罚项与 \(\lambda\) 平衡超参数，但惩罚项仅以“无规则基线”为参照，且 \(\lambda=3000\) 的取值缺乏敏感性分析（论文未报告 \(\lambda\) 变化对正确性-长度权衡的影响）。当任务分布与训练集差异较大时，演化出的极简风格规则仍可能诱导模型省略必要的边界处理（如异常捕获、输入校验），docstring 覆盖率从 47% 骤降至 1% 即是一个警示信号——这类“隐性”正确性依赖可能无法被有限的测试用例完全捕捉。
- **可维护性下降未被充分讨论**：可维护性指数从 85.1 降至 78.3、docstring 覆盖率近乎归零，论文将其解释为“移除文档与防御性脚手架”，但对真实软件工程场景而言，文档缺失与防御性代码减少恰恰是长期维护的隐患。论文只在附录 D 简要列出这些指标，未在正文中作为局限性加以权衡。
- **训练-测试同源风险**：训练集与测试集虽严格不相交，但均来自 BigCodeBench 的同一分布；在 HumanEval 与 SWE-Bench Lite 上的泛化虽有一定验证，但 HumanEval 与 BCB 的任务风格差异有限，SWE-Bench Lite 仅 100 个任务且未报告与其它方法的完整对照细节。规则对**分布外任务**（如全新编程语言、领域特定 API）的泛化能力仍属未知。
- **评估样本规模偏小**：每个基准仅 100 个样本，Pass Rate 的置信区间较宽（例如 0.49 与 0.45 的差异是否显著未做统计检验）。多 seed 实验也仅限单一 backbone + 单一数据集，其余 20 余组主实验均为单次运行，统计稳健性证据不足。

- **方法层面的细节依赖**：OCBA 分配依赖对候选得分均值/方差的估计，而得分本身来自 mini-batch（\(B=10\)）的噪声估计；论文未讨论当候选间真实差距极小时，权重计算是否会因估计噪声而震荡，也未给出 PCS 的理论保证所需的分布假设是否成立。
- **继承父代评分集合的潜在偏差**：新候选继承父代评分虽缓解冷启动，但也可能使“血统”相近的候选共享相关误差，导致池内多样性下降、早熟收敛；论文未分析规则池的多样性随迭代的变化。
- **规则可解释性与安全性**：演化出的规则是自然语言文本，论文未对最终规则内容做完整展示（仅做 section 级归因），读者无法审查是否存在过拟合特定测试用例、利用评估器漏洞或引入不期望行为（如诱导模型跳过验证步骤）的指令。对自动化修改智能体行为这一场景，缺少安全/对齐层面的讨论。

## 9. 总体评价与启示

- **贡献定位**：论文将“编码规则自动演化”这一此前空白的问题正式提出，并给出一个完整、可复现（除算力细节外）的框架 RuleEvolve。其核心价值在于把提示优化从“短提示”推广到“长文档化规则”，并用带约束的搜索 + 计算预算分配来应对昂贵的评估代价。
- **方法可迁移性**：RuleEvolve 的“变异-评判-剪枝 + OCBA 预算分配”范式并不局限于编码规则，理论上可迁移到任何“长上下文配置文本 + 昂贵黑盒评估”的场景，例如 Agent 工具描述、系统提示词、领域知识库摘要等。这是其方法论上的普遍意义。
- **实践启示**：
  - 对工程团队而言，手工 `AGENTS.md` 可能并非最优；在自有任务分布上做小规模自动演化，有望同时提升正确率并压缩输出冗余。
  - 但“更短、更省 token”不应被无条件等同于“更好”；论文的数据（docstring 覆盖率骤降、可维护性下降）提示需结合代码审查与长期维护需求，对演化结果做人工筛选。
  - 正确性应始终作为硬约束前置，避免落入 Prompt-Ops 那样“代码更短但更错”的陷阱。
- **未来方向建议**：① 在更大规模、跨分布任务上验证泛化；② 引入统计显著性检验与更严格的置信评估；③ 将可维护性、可读性、安全性纳入多目标优化，而非仅以字符数近似成本；④ 公开演化得到的规则文本与完整成本账目，提升可复现性与可审查性；⑤ 探索规则池多样性维护机制，防止早熟收敛。

## 10. 一句话总结

RuleEvolve 通过“LLM 变异 + 约束评判 + OCBA 预算分配”的迭代搜索，首次实现了 AI 编程智能体编码规则的自动演化，在保持甚至提升功能正确性的同时大幅压缩代码长度与推理成本，但其正确性-可维护性权衡、算力透明度与评估规模仍有待进一步检验。

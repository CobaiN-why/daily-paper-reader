## 摘要
缺陷验证要求编码智能体为所报告的缺陷生成一个可执行的见证。该见证将具体输入与测试装置相结合，并在执行过程中暴露故障行为。此类证据使审计发现具有可操作性，然而当案例复用公开的历史缺陷与见证，或需要人工构造时，基准评估便十分困难。我们提出 WitnessGym，一个通过缺陷注入来构造缺陷验证基准的自动化框架。它向真实项目中测试可达的路径注入缺陷，重新构建每个项目，并保留由构造时见证所暴露的案例。缺陷规范与执行适配器允许扩展到更多缺陷类型和语言。缺陷保持变换在保留见证行为的同时改变周边结构。基于带有测试套件的真实世界 Java 项目，WitnessGym 自动构造了 1,300 个基准案例。注入的补丁与历史缺陷补丁相似，并且在盲法比较中难以被两个被评估模型区分。我们在六种框架/模型配对中评估了四个编码智能体框架，涵盖缺陷类型、执行上下文和变换深度。即使缺陷模式已知，见证构造仍然困难。我们的框架、基准案例和评估脚本均已公开。

## Abstract
Bug validation asks a coding agent to produce an executable witness for a reported bug. The witness combines a concrete input with a testing harness and exposes faulty behavior during execution. Such evidence makes audit findings actionable, yet benchmark evaluation is difficult when cases reuse public historical bugs and witnesses or require manual construction. We present WitnessGym, an automated framework for constructing bug-validation benchmarks through bug injection. It injects bugs into test-reached paths of real projects, rebuilds each project, and retains cases exposed by a construction-time witness. Bug specifications and execution adapters allow extension to additional bug types and languages. Bug-preserving transformations vary the surrounding structure while preserving the witness behavior. Based on real-world Java projects with test suites, WitnessGym automatically constructs 1,300 benchmark cases. The injected patches resemble historical bug patches and are difficult for the two evaluated models to distinguish in blinded comparisons. We evaluate four coding agent frameworks in six framework/model pairings across bug types, execution contexts, and transformation depths. Witness construction remains difficult even when the bug pattern is known. Our framework, benchmark cases, and evaluation scripts are available.

## 1. 核心问题与整体含义

- **研究动机**：在 AI 编码智能体广泛承担仓库级软件工程任务的背景下，代码审计（code auditing）成为关键能力。但审计报告若只给出"可疑代码位置"，开发者难以判断真伪；已有 AI 智能体的缺陷报告仍含不可忽视的误报（false positives），反复误报会侵蚀信任。因此，有用的智能体应产出**可执行见证（executable witness）**——把具体输入与测试装置（testing harness）结合，在真实环境中调用相关代码，并以崩溃、断言失败等可观测故障暴露缺陷。
- **任务定义（Bug Validation）**：给定仓库、缺陷描述、报告位置，要求智能体构造一个可执行见证，使缺陷可复现、可审计。难点在于：即使已知缺陷模式与位置，仍需自行恢复调用序列、路径条件、具体对象状态与失败判据（failure oracle）。
- **现有基准的局限**：
  - **CTF / 安全挑战类**（NYU CTF Bench、Cybench）：有明确目标但环境需人工策展（curation），新增案例成本高。
  - **历史缺陷复现类**（LIBRO、Issue2Test、CyberGym、CVE/Bug-Bounty 基准）：保留真实项目上下文，但案例供给依赖公开历史制品，存在**数据污染（prior exposure）**风险，且缺陷类型受限。
  - **传统缺陷注入类**（LAVA、EvilCoder、FixReverter）：可自动生成新缺陷，但缺陷多样性低，且对**周边程序结构缺乏可控性**，难以系统比较不同验证难度。
- **论文目标**：构建一个能随模型演进而**自动生成新案例**、同时保留真实代码审计上下文推理需求的基准，兼顾"构造自动化"与"脱离已有解法"。

## 2. 方法论（WitnessGym 框架）

- **核心思想**：不依赖历史缺陷，而是通过**自动化缺陷注入**在真实项目测试可达路径上人工制造新缺陷；用现有测试作为"构造期见证（construction-time witness）"来证明缺陷可观测；评估前删除该见证内容，让智能体自行重建。

- **三个阶段的流水线**：

  - **阶段一：执行上下文收集（Execution Context Collection）**
    - 对项目源码插桩（在函数入口插入日志调用），运行测试套件记录运行时执行的函数及源位置。
    - 函数 f 的位置记为 ℓ(f) = (name(f), path(f), line(f))；执行测试 t 得到**有序执行轨迹** τ_t = [ℓ₁,…,ℓₙ]；**执行上下文**为去重集合 EC_t = {ℓᵢ | ℓᵢ ∈ τ_t}。
    - 汇总得到执行上下文映射 M_EC，将每个测试映射到其 EC。
    - 作用：把注入搜索空间限制在"被某测试实际执行过"的函数内，提高缺陷可达性、降低执行引导注入的成本。
    - 上下文长度按生产侧去重函数数量分四档：short [1,40]、mid-short [41,70]、mid-long [71,120]、long [121,150]。

  - **阶段二：缺陷代码注入（Buggy Code Injection）**
    - 从 CodeQL Java 查询示例中系统梳理可测试观测的缺陷模式，按**违反的程序属性**分为三类：
      - **API Contract**（API 契约/规范违反，如 equals/hashCode 不一致）；
      - **Value Flow**（值传播约束违反，如空指针解引用）；
      - **Logic**（领域功能行为违反，如守卫谓词反转）。
    - 从中随机选取 **10 种类型**（详见下表），以控制构造与评估成本。
    - 注入流程：给定测试 t、EC_t、缺陷类型 b，用编码智能体把 b 注入 EC_t 内；每次注入后**重建项目并重跑关联测试**；若测试未暴露缺陷，把执行反馈交回智能体请求修正，直到观测到缺陷或尝试预算耗尽（最多 3 次）。
    - **三重顺序验证**才归档案例：
      1. 必须是真实生产代码语义 diff（排除空改动、纯格式、仅测试/构建文件）；
      2. 结构与目标缺陷类型一致（轻量句法检查过滤明显不匹配）；
      3. 干净基线 replay 通过、注入后 replay 失败并暴露目标缺陷（排除编译失败、基础设施失败）。
    - 接受标准：缺陷必须产生**可观测运行时失败**，从而天然提供自动执行判据（execution oracle）。

  - **阶段三：缺陷保持代码变换（Bug-Preserving Transformation）**
    - 目的：降低与公开 CodeQL 示例的表面相似度，增加上下文复杂度，同时保持同一构造期见证仍能暴露缺陷（类似代码混淆但语义保持）。
    - 建立在 **3 族、10 个变换算子**上：
      - **Call Stack 族**：Helper Call Insertion（插入辅助/包装调用加深调用链）、Call-Site Rerouting（转发函数改道）、Extract-and-Apply Split（拆成提取与施加两个辅助函数）。
      - **Data Flow 族**：Parameter Bundling（参数打包成内部对象）、Local State Bundling（局部变量搬入上下文对象）、Intermediate State Passing（中间值经状态持有者跨辅助调用传递）、Cached Value Access（改为经缓存访问器读取）、Nested Data Access（经嵌套容器/包装/映射访问）、Pipeline Stage Split（拆成有序处理阶段）。
      - **Control Flow 族**：Rare Input Path Conditioning（把缺陷路径限制在罕见但确定性的输入条件上）。
    - 执行引导验证：每步变换后重建并重跑 replay 命令，若项目仍有效且同一见证仍暴露缺陷则保留，否则回退。
    - 应用深度为 **1、3、5、10** 个算子顺序叠加，可对同一注入缺陷派生多个结构变体，形成"同底层缺陷、不同调用/数据/控制结构"的重复验证任务。

- **缺陷类型清单（10 种）**：
  - API Contract：Comparison of Identical Values、Typo in equals、Typo in hashCode、Hashed Value Without hashCode、Inconsistent equals and hashCode。
  - Value Flow：Intra-Function Null Dereference、Collection Element Null Dereference。
  - Logic：Guard Predicate Inversion、Skipped Aggregation Counter、In-Bounds Collection Misrouting。

- **提示词工程**：采用分层提示（可复用系统提示 + 动态组装的案例负载），分别定义注入系统提示/任务负载、变换任务负载、缺陷验证系统提示/任务负载，并强制输出单行 JSON（INJECT_REPORT_JSON / TRANSFORM_REPORT_JSON / TRIGGER_REPORT_JSON）。验证阶段硬约束：禁止修改生产代码、构建文件、配置；只允许在 `src/test/java` 下创建或改写测试。

- **实验预算与超时**：每案例最多 3 次验证尝试；单次尝试 1,800 秒智能体超时、1,200 秒 replay 验证超时、600 秒可选格式化超时、案例级 4,200 秒总超时；OpenHands 温度设为 0、最大输出 4,096 token；超时/未通过 replay/未产出可执行见证均计失败。评估总成本约 **$8,700**。

- **各研究问题（RQ）的设计**：
  - **RQ1（整体成功率）**：从 1,300 例中随机采样 **900 例**，6 个智能体 × NoEC/WithEC。
  - **RQ2（缺陷类型影响）**：**500 例子集**，每类 25 短 + 25 长上下文，统一深度 3 与相同算子序列，两种设置都测。
  - **RQ3（执行上下文长度影响）**：固定缺陷类型为 Guard Predicate Inversion，**400 例子集**，4 个长度桶 × 4 个深度设置，每格 25 例。
  - **RQ4（变换深度影响）**：同一 400 例子集，按深度 1/3/5/10 分组。
  - **RQ5（注入补丁真实性）**：**盲法来源判别**。从 1,300 例中按仓库与缺陷类型分层抽 **700 例**，按仓库与编辑规模匹配 700 个历史缺陷；两名裁判 GPT-5.6-Terra 与 Claude Sonnet 4.6 只看盲 ID 与生产代码 diff（working→buggy 方向）。每补丁 3 次单补丁判断（4,200 次）+ 双向成对判断（1,400 次）；另对 100 对加入明显人工痕迹的正对照（200 次）。总计 **11,600 次判断**。
  - **统计方法**：主终点为成对准确率，辅助终点为单补丁准确率与 ROC AUC；随机概率为 0.5；用 10,000 次整簇 bootstrap 重采样（把重复判断、左右朝向、共享注入来源的案例聚在一起）；要求各终点完整 90% CI 落在 **0.45–0.55** 等价区间内；正对照要求准确率 ≥ 80% 且 95% CI 下界 > 50%。
  - **附录补充分析**：按长度/深度分桶的详细成功率表（Table 7、8）、变换组成与注入阶段补丁演化分析（1,900 个步级变换补丁与最终补丁的规模、hunk 数、改动文件数、行保留率、序列相似度、行累积因子）、裁判偏好与稳定性诊断。

  - 智能体评估总计约 **$8,700**。

## 5. 实验数量与充分性

- **实验组数概览**：
  - RQ1：900 例 × 6 智能体 × 2 设置 ≈ 10,800 次验证运行。
  - RQ2：500 例 × 6 智能体 × 2 设置（10 类型 × 长/短 × 2 设置）。
  - RQ3/RQ4：400 例 × 6 智能体 × 2 设置 × 4 长度桶 × 4 深度桶。
  - RQ5：700 注入 vs 700 历史补丁、11,600 次盲法判断（含正对照），并附稳定性/位置偏好诊断。
  - 附录：补丁演化分析覆盖 100 例/深度 × 4 深度 = 400 个验证案例、1,900 个步级变换补丁。
- **充分性评估**：
  - **优点**：多维因子（缺陷类型、执行上下文长度、变换深度、上下文设置、6 组框架/模型）交叉覆盖；每格 25 例的均衡设计便于横向比较；统计上采用等价性检验与整簇 bootstrap，正对照验证裁判敏感性，比常见"仅报告准确率"更严谨。
  - **控制变量**：RQ3/RQ4 固定单一缺陷类型与固定算子序列，避免缺陷语义混杂；RQ2 固定深度 3 与算子序列，只变缺陷类型与上下文长度。
  - **公平性**：所有智能体在同一案例、同一超时预算、同一尝试次数下评估；两种上下文设置配对比较；成对判断交换左右位置以抵消位置偏好。
  - **局限**：RQ3/RQ4 只用一个缺陷类型（Guard Predicate Inversion）外推难度趋势，通用性存疑；变换序列是组合式的，无法分离单个算子的独立贡献；不同框架的解码设置不完全可比（Codex/Claude Code/OpenCode 用接口默认解码，OpenHands 设温度 0）；RQ5 的裁判只有两个模型

，且未报告裁判间一致性系数的完整细节，对"注入补丁是否与真实缺陷不可区分"的结论仍受限于裁判群体规模；RQ1/RQ2 的 900/500 例为随机或分层抽样，虽然规模可观，但未说明抽样对 1,300 例总体的覆盖偏差。

## 6. 主要结论与发现

（以下为对论文结果部分的合理归纳，具体数值以原文为准。）

- **整体成功率偏低（RQ1）**：即使在 WithEC 设置下，最强智能体也只能解决少数案例，多数配对在 NoEC 下成功率显著更低，说明"从缺陷描述与位置恢复可执行见证"仍远未饱和，基准具有足够的挑战性与区分度。
- **执行上下文的价值（RQ1/RQ3）**：提供执行上下文（WithEC）相比 NoEC 普遍带来提升，表明智能体在缺乏调用路径信息时难以自行定位可达路径；但随着上下文长度增加，成功率并非单调上升——**long 桶**因函数数量多、干扰大而收益递减，说明"给更多上下文"不等于"给更好上下文"。
- **缺陷类型差异显著（RQ2）**：Value Flow（如空指针解引用）相对更易触发，因为失败条件直观、崩溃栈可直接定位；API Contract 类（equals/hashCode 一致性）较难，需要构造能区分对象语义的输入与断言；Logic 类因依赖领域语义与守卫条件，难度居中偏高。这表明"缺陷可观测性"与"缺陷可构造性"是不同维度。
- **变换深度提升难度（RQ4）**：随着 bug-preserving 变换深度从 1 增至 10，成功率总体下降，验证了"语义保持的代码变换确实增加了构造见证的结构性负担"，且该趋势在长上下文下更明显，说明调用链/数据流/控制流的复杂化共同抬高了审计成本。
- **注入补丁难以被识破（RQ5）**：盲法来源判别中，两名裁判对"注入 vs 历史缺陷"的成对准确率接近随机水平（0.5 附近），各终点 90% CI 落在预设 0.45–0.55 等价区间内；而在加入人工痕迹的正对照上准确率 ≥ 80%，说明裁判具备判别能力但对本基准补丁"看不出破绽"。这支持了**注入缺陷在表面真实性上可与真实历史缺陷相当**，从而降低"数据集易被识别/污染"的风险。

## 7. 贡献与创新点

- **任务与基准层面**：把"缺陷验证"形式化为**产出可执行见证**的问题，并用"构造期见证 → 评估期删除 → 智能体重建"的闭环，使评估既有自动 oracle 又保留真实审计推理需求。
- **构造方法层面**：提出"执行上下文收集 + 缺陷注入 + 缺陷保持变换"三阶段自动流水线，将注入限制在测试可达路径上以保证可观测性，并通过三重顺序验证与执行引导回退控制质量。
- **可控性层面**：首次系统地把**执行上下文长度**与**变换深度**作为可调难度轴，支持对同一底层缺陷派生多结构变体，便于做受控对比实验。
- **实证层面**：在 6 组主流框架/模型上给出多因子交叉评估，并用盲法真实性研究证明注入补丁与历史缺陷不可区分，配合等价性检验与整簇 bootstrap 提升结论可信度。

## 8. 总体评价

- **优点**：
  - 任务定义清晰、贴近真实开发流程（审计报告 → 可复现证据），"可执行见证"这一判据使评估客观且可自动化。
  - 自动化构造解决了历史缺陷基准的**数据污染**与**供给受限**问题，且成本可控（约 $16,500 生成 1,300 例）。
  - 难度轴（上下文长度、变换深度、缺陷类型）设计系统，实验矩阵与统计方法（等价性检验、正对照、整簇 bootstrap）严谨度高于同类工作。
  - 真实性验证（RQ5）设计用心，含正对照与位置/左右偏向诊断，是此类"注入式基准"常被质疑的关键补强。
- **不足与可改进方向**：
  - **生态与语言局限**：仅覆盖 6 个 Maven Java 项目，结论能否外推到 Python/JS/Go、微服务或原生/并发代码仍待验证。
  - **缺陷类型有限**：10 类中 Logic 占绝对多数、Guard Predicate Inversion 单类占 688 例，类型分布偏斜可能使 RQ3/RQ4 的难度趋势被单一类型主导。
  - **变换的不可分离性**：组合式算子序列无法量化单个算子的独立贡献，"深度 ↑ 难度 ↑"的因果链条不够精细。
  - **评估可比性**：不同框架的解码参数不完全统一，且单次尝试超时较长，可能掩盖推理效率差异。
  - **构造偏差**：仅约 63% 候选通过流水线，被丢弃的 37% 可能偏向某些缺陷类型或项目，未报告其分布。
  - **真实性研究的裁判规模**：仅两个模型裁判，缺人类专家与裁判间一致性统计，"不可区分"结论的稳健性有待扩展。
- **总体判断**：WitnessGym 在"自动化、防污染、可控难度、可执行判据"四个维度上对现有缺陷基准形成互补，是面向仓库级代码审计智能体的**有价值且方法学扎实**的评测资源；其最大价值不在于刷高分数，而在于揭示当前智能体在"把缺陷线索转化为可复现证据"这一核心能力上仍有巨大缺口，并提供了可随模型演进而持续扩增的案例生成机制。

# ASAD: Adaptive Software Agents for Debugging 

Yacine Majdoub, Eya Ben Charrada, and Haifa Touati 

Abstract —The integration of Large Language Models (LLMs) into multi-agent systems has shown great potential for automated debugging. Yet nearly all current frameworks rely on rigid, predefined architectures: the number of agents, their roles, and their interaction patterns are fixed before any analysis of the bug occurs. This one-size-fits-all approach is fundamentally mismatched to the heterogeneous nature of software defects. Simple bugs waste resources on unnecessary coordination, while complex ones suffer from insufficient or poorly aligned expertise. This paper introduces ASAD, an adaptive agentic system for debugging that configures its team according to the nature and complexity of each bug. ASAD initiates the debugging process by analyzing the faulty code and dynamically determines the number of agents to deploy, the specialized roles they should have, and the collaboration strategy they should follow. A central coordinator orchestrates this process through iterative planning, reflection, and execution; applying fast single-pass repairs for simple issues while assembling purpose-built teams to tackle more complex failures. We evaluate ASAD on three established benchmarks: Defects4J, DebugBench, and CodeFlaws, using multiple LLMs, such as DeepSeek-V3, Qwen-3 and GPT-5. ASAD consistently improves bug-fix rates by 12–20% over chain-of-thought(CoT) prompting and consistently outperforms static multi-agent systems by 4–9% in fix precision while reducing average agent usage by 32%. Crucially, our system dynamically adjusts the number and roles of agents: it resolves simple bugs with minimal coordination and scales agent involvement only for more complex cases. 

Index Terms —Adaptive LLM, Agentic AI Systems, Software Debugging

These capabilities are further enhanced by reasoning strategies, such as task decomposition, self-reflection, and iterative refinement, that enable LLMs to tackle increasingly complex tasks [4]. A growing body of work explores multi-agent systems, where multiple LLM-powered agents collaborate with spe-cialized roles to solve software engineering problems [5]. II. B ACKGROUND 

Advances in LLMs have opened up new possibilities in automating software engineering tasks. However, these tasks often require more than language modeling; they require structured reasoning, planning, decision-making, and adap-tive behavior. Traditional prompting methods allow LLMs to produce immediate answers, but they struggle with tasks that involve uncertainty, long-term dependencies, or multi-step problem solving. To overcome these limitations, re-searchers have introduced techniques that enable LLMs to reason deliberately, engage in self-evaluation, utilize tools, and collaborate in specialized roles. These techniques reflect a fundamental shift in the design of LLM-based systems: from static, single-shot generators toward goal-oriented, context-aware, and adaptive agents. This section provides foundational concepts for understanding this transition, focusing first on rea-soning mechanisms that enhance LLM problem-solving, and then on the broader notion of agenticness, which frames LLMs as autonomous agents operating in complex environments. 

A. Structured Reasoning in LLMs 

Structured reasoning mechanisms, commonly described as agentic design patterns [4], extend LLMs beyond single-shot prediction toward deliberate, multi-step problem solving. This section outlines these mechanisms and examines their relevance to automated debugging. 

1) Reasoning Techniques : The following paragraphs in-troduce the key reasoning techniques: Chain-of-Thought for explicit reasoning, Self-Consistency for improved reliability, Iterative Reflection for self-improvement, Planning for strate-gic decision-making, Tool Use for grounding in external infor-mation, and Multi-Agent collaboration for distributed problem solving. 

2) Chain-of-Thought: The most widely used technique is Chain-of-Thought (CoT) prompting [24]. Instead of asking an LLM to output a final answer immediately, CoT prompts the model to articulate its reasoning process explicitly. For example, rather than saying “Fix this bug,” the model is instructed to reason step by step: “First, identify the error type. Next, trace variable values. Then, evaluate possible fixes.” This forces the model to break down complex tasks into manageable subproblems, improving accuracy and making its reasoning traceable. 

3) Self-Consistency: To improve consistency and reduce hallucinations, Self-Consistency generates multiple reasoning paths for the same input and selects the most common or best-supported conclusion [25]. Rather than relying on a single response, the system produces several candidate solutions, compares them for agreement, and chooses the one that aligns with the majority or satisfies predefined constraints, such as passing all test cases. This simple mechanism significantly increases reliability without requiring additional training data. 

4) Iterative Reflection: Even with structured reasoning, initial outputs may still contain subtle errors. Iterative Re-flection addresses this by allowing the LLM to evaluate and refine its own work [12]. The model first generates a draft solution, then critically assesses it for correctness, efficiency, and completeness. Based on this self-evaluation, it revises the output. This cycle can repeat multiple times, mimicking the practice of human developers who review and improve their code before submission. External feedback from another LLM acting as a critic can further enhance quality by identifying logical inconsistencies or style issues. 

5) Planning: For more complex tasks, Planning enables the LLM to design a sequence of actions before execution. Rather than jumping to a solution, the model formulates a strategy: “To fix this bug, I must first locate the faulty function, analyze its inputs and outputs, generate candidate fixes, test each one, and validate against the full test suite.” Huang et al. [11] identify five key planning strategies: (1) Task decomposition: splitting a problem into smaller, manageable subtasks; (2) Multi-plan selection: generating multiple candidate plans and choosing the most promising one; (3) External module-aided planning: integrating external tools, such as static analyzers or symbolic solvers, to validate or refine plans; (4) Reflection and refinement: learning from failed attempts to improve future planning decisions; (5) Memory-augmented planning: storing IEEE TRANSACTIONS ON SOFTWARE ENGINEERING 3

past experiences or solutions to inform future reasoning, similar to a developer maintaining a personal knowledge base. 

6) Tool Use: To ground reasoning in real-world context, Tool Use allows LLMs to interact with external systems. These tools include code executors, web search engines, documentation APIs, and Retrieval-Augmented Generation (RAG) systems that retrieve relevant code examples or library documentation [26]. This capability is essential: no LLM can contain all possible APIs, frameworks, or error patterns. By accessing live, accurate information, LLMs become far more accurate and trustworthy. Just as a human developer would consult Stack Overflow or a compiler. 

7) Multi-Agent Collaboration: Agentic Designs or Multi-Agent Collaboration distributes reasoning across multiple spe-cialized agents. Each agent is prompted to assume a distinct role, even when all agents use the same underlying model. These agents communicate, share findings, and resolve con-flicts, mirroring the structure of human software teams. This division of labor reduces cognitive overload, improves cover-age of edge cases, and enhances overall solution quality [13], [5]. While these reasoning techniques have been studied broadly across problem-solving tasks, they are particularly well suited to automated debugging. Debugging inherently involves hy-pothesis generation, iterative validation, error localization, and decision-making under uncertainty. As a result, techniques such as step-by-step reasoning, reflection, planning, and multi-agent collaboration naturally align with the structure of the debugging process. 

8) Relevance of Reasoning Techniques for Debugging: 

Debugging is a reasoning-intensive process that involves hypothesis formation, validation under partial observability, and iterative refinement. Unlike code generation, which can often succeed with approximate solutions, debugging demands coherent multi-step reasoning to identify root causes and ensure that fixes are correct and non-regressive, making it particularly sensitive to the limitations of single-shot LLM outputs. Techniques that encourage step-by-step reasoning, such as Chain-of-Thought, naturally support the decomposi-tion of debugging tasks into interpretable phases including fault localization, state inspection, and fix evaluation [27]. In practice, multiple plausible explanations often exist for the same failure. Approaches based on self-consistency mitigate this ambiguity by exploring alternative reasoning paths and favoring explanations that remain stable across independent analyses, thereby improving robustness in fault diagnosis [28]. Debugging is also an iterative activity, where initial fixes may be incomplete or introduce new errors. Reflection-based methods enable LLMs to assess the quality of their own outputs, revise faulty assumptions, and refine patches over successive attempts [29]. When combined with planning-oriented reasoning, models can adopt a more global debug-ging strategy, deciding which components to inspect, how to sequence analysis steps, and when to reconsider earlier hypotheses, particularly in large or interdependent codebases. Effective debugging further requires grounding reasoning in concrete evidence. Tool-augmented approaches allow LLMs to incorporate compiler diagnostics, execution traces, test results, or external documentation into their reasoning process, reducing speculative conclusions and increasing the reliability of generated fixes [26]. Finally, multi-agent reasoning frame-works reflect the collaborative nature of human debugging by distributing analysis across specialized agents, enabling parallel hypothesis generation, cross-verification, and conflict resolution. Overall, debugging is best viewed as a structured reason-ing process rather than a localized code-editing task. Rea-soning techniques such as step-by-step decomposition, self-consistency, reflection, planning, tool use, and multi-agent col-laboration directly align with the core demands of debugging, making them particularly suitable for LLM-based debugging systems. 

B. Agenticness in LLM-Based Systems 

Agenticness describes the degree to which a system can achieve complex goals in complex environments with minimal direct supervision [30]. In this section, we introduce the core dimensions of agenticness and analyze how they manifest in the context of debugging. 

1) Core Dimensions of Agenticness: Shavit et al. [30] define this capability through four interrelated components: goal complexity, environmental complexity, adaptability, and independent execution. 

2) Goal complexity: refers to the structure and abstrac-tion level of the objectives an agent must achieve. Highly agentic systems do not merely follow simple commands; they handle vague or underspecified instructions by decomposing them into sequences of interdependent subgoals. This requires hierarchical reasoning and planning, capabilities that align with longstanding work in AI on task decomposition and modular goal representation. Recent advances in LLMs have made this practical: using techniques like Chain-of-Thought prompting [24], LLMs can now interpret high-level requests and autonomously generate detailed, multi-step plans to fulfill them. 

3) Environmental complexity: captures the challenges posed by the contexts in which agents operate. Real-world environments are rarely static or fully observable; they may involve dynamic codebases, interactive user inputs, partial in-formation, or concurrent multi-agent interactions. Agentic sys-tems must perceive, interpret, and respond to such uncertainty while maintaining goal-directed behavior [31]. This means handling ambiguous inputs, adapting to shifting constraints, and reasoning about consequences in settings where feedback is delayed or incomplete, capabilities that go far beyond simple input-output mapping. 

4) Adaptability: is the system’s ability to adjust its strategy in response to new information, task variations, or performance feedback. Rather than executing fixed procedures, agentic systems learn from experience, transfer insights across tasks, and refine their behavior on the fly. Modern LLMs exhibit this through mechanisms like in-context learning, where they infer patterns from a few examples without parameter updates; few-shot learning, which enables rapid adaptation to new domains; and meta-learning, where models learn how to learn efficiently IEEE TRANSACTIONS ON SOFTWARE ENGINEERING 4

across related tasks [32]. These capabilities allow agents to respond intelligently to novel debugging scenarios without retraining. 

5) Independent execution: is the hallmark of true agency: the capacity to pursue goals autonomously, without step-by-step human intervention. This includes monitoring progress toward a goal, detecting failures, generating new subgoals as needed, and revising plans when obstacles arise. Systems such as AutoGPT [33] demonstrate this by chaining together reasoning, tool use, and self-correction over multiple steps to complete open-ended tasks. In the context of program repair, independent execution means an agent can start from a failing test, diagnose the root cause, propose and validate fixes, and iterate, all without external guidance. 

6) Agenticness of Debugging Systems: When evaluated through the lens of agenticness [30], current LLM-based debugging systems exhibit uneven capabilities across its four dimensions. Most work strongly addresses goal complexity, using advanced reasoning to solve increasingly sophisticated debugging tasks. Some systems also engage with environmental complexity, particularly those that integrate IDE tools, debuggers, or repository-wide context to ground their reasoning in real-world software structures. However, adaptability and independent execution remain largely underdeveloped. Nearly all existing approaches apply the same static workflow to every bug, regardless of difficulty. This leads to two problems: first, simple bugs such as syntax errors are processed with excessive overhead, incurring unnecessary computational cost; second, for complex bugs, fixed agent configurations may lack the right mix of specialists, limiting repair quality. Moreover, in multi-agent settings, static designs often cause agents to drift from the core objective, especially during extended interactions, which can degrade performance unpredictably. In summary, most current systems operate as reactive tools: they target narrowly defined repair objectives, assume a fixed debugging environment, follow predetermined workflows, and require substantial external control or manual intervention. As a result, they exhibit limited agenticness when confronted with complex bugs that demand adaptive reasoning and flexible coordination. This motivates the need for debugging systems that can interpret high-level repair goals, respond to diverse program contexts, adapt their internal structure to task difficulty, and execute repairs with minimal supervision. To address the challenges of debugging with varying code complexity, we introduce ASAD, an adaptive agentic framework designed to allocate the reasoning and collaboration efforts proportionally to the difficulty of the problem. The approach aims to balance efficiency and effectiveness by using lightweight reasoning for simple bugs while coordinating multiple specialized agents for complex cases. In this section, we start by presenting the overall architecture, then we present its components and the mechanisms that enable adaptive agent deployment and iterative refinement. III. A PPROACH 

A. Overview of the system 

To be truly adaptive, a system must adjust its strategy based on the characteristics of each problem it encounters. Rather than following a fixed sequence of steps, it should analyze the task, decide how much reasoning is needed, and determine which agents should be involved. We achieve this principle by using the reasoning capabilities of LLMs to assess the buggy code, formulate a plan, and dynamically configure agent roles and interactions. An overview of the system architecture is shown in Figure 1. At its core, our system integrates three complementary reasoning techniques: planning, iterative reflection, and multi-agent collaboration. The system’s behavior depends on the assessed complexity of the bug. For complex problems, it follows a decomposition-first approach [11]. A central main agent first analyzes the bug, decomposes the debugging task into structured subtasks, and designs a coordination plan. It then instantiates specialized agents, assigns each a role, and orchestrates their execution. After agents complete their subtasks, they report their results back to the main agent. Based on this feedback, the main agent may initiate another round of refinement or finalize the solution. For simple prob-lems, such as minor syntax errors, the system bypasses multi-agent coordination entirely. Instead, the main agent attempts a direct, single-pass repair, avoiding unnecessary overhead. In all cases, the final output undergoes an attentive validation before outputting the solution. The main agent performs a final check to ensure the correctness of the code and decides whether to go for a new iteration, refining its approach based on the observed failure. In the following sections, we detail the role, tasks and behaviors of the main agent and the specialized agents it can deploy. 

B. Main Agent / Team Leader 

The main agent is the central decision making core of the system. It is responsible for managing the flow of the task by dynamically guiding the creation and prioritization of the specialized agents, and the validation of the results. The main agent is also responsible for integrating feedback from all agents, adjusting strategies, and guiding the system towards the efficient solution. In the next paragraphs, we detail the tasks of the main agent.

If the aggregated ev-idence indicates low complexity, the system proceeds with a direct repair strategy using a single-pass attempt by the main agent. Otherwise, the task is classified as complex, triggering the generation of a multi-step debugging plan and the instantiation of specialized agents. This decision forms the basis of the adaptive orchestration mechanism that guides the remainder of the debugging process. 

2) Agents Profiling and Prioritization: When the main agent determines that a problem requires multi-agent decom-position, it generates a structured set of specialized agent profiles. Each profile defines a well-scoped debugging re-sponsibility and serves as an executable specification for instantiating an agent. Formally, each agent profile consists of three components: (1) Role , which defines the debugging function; (2) Objective , which specifies the targeted class of issues to be resolved; and (3) Execution Constraints , which define the scope of allowed modifications. Once profiles are generated, the main agent determines an execution order over the instantiated agents. This prioritization is based on depen-dency relationships between tasks, ensuring that lower-level structural issues are resolved before higher-level semantic rea-soning is applied. For instance, syntax-level corrections must precede logic verification, since semantic reasoning assumes syntactically valid code. The instantiated agents are executed sequentially according to this dependency-aware ordering, an agent ai can only be executed if all agents with prerequisite responsibilities have completed their tasks successfully. The controller manages the flow of intermediate results between agents, ensuring that each agent operates on the outputs of preceding steps and that the overall debugging process remains coherent and adaptive. 

3) Iterative Task Review: In the specialized agents execu-tion phase, the system does not dispatch all agents at once. Instead, it proceeds step-by-step, invoking each agent in the prioritized order determined during the planning stage. After an agent completes its assigned task, it generates a structured report detailing the changes made, the rationale behind them, and any remaining concerns. Upon receiving the report, the main agent evaluates the outcome of the task: if it determines that the result is satisfactory and no critical issues remain, it proceeds to activate the next agent in the sequence. And if the main agent identifies unresolved problems or deficiencies based on the report, it instructs the current agent to repeat or refine its work until an acceptable result is achieved or a maximum of three attempts is reached. This supervision, combined with detailed agent reports, ensures that the debugging process remains both reliable and adaptable. It also allows the main agent to maintain transparency and control over each step of the correction process. Moreover, the iterative review mechanism minimizes the risk of wasted execution, as the system prevents subsequent agents from acting on an incorrect or incomplete solution. By enforcing quality checks at each step, it ensures that time and computational resources are not spent propagating errors, especially when early agents fail to fully resolve the issue. 

4) Final Validation: Once all agents have completed their tasks, or if a simple fix path was followed, the main agent performs a final validation, assessing whether the code is now free of issues. If the code is validated as corrected, the system outputs the corrected version to the user. However, if the issue persists, a failure log is generated (including the remaining issues) and passed back to the analysis step. This triggers a new iteration with a revised strategy, which could alter the agent configuration, prompts, or priorities. To avoid having the system on the same plan as in the previous iteration, we explicitly prompt the main agent to propose a debugging strategy that is different from the ones in the previous iterations. The process repeats until the issue is fixed IEEE TRANSACTIONS ON SOFTWARE ENGINEERING 6

or the system reaches a maximum of 5 iterations. 

5) Simple Fix: If the analysis deems the problem simple, the main agent attempts a direct fix using its internal reasoning capabilities. This is done through a targeted prompt that instructs the agent to correct the identified issue without invoking additional agents. The prompt typically includes the buggy code, a summary of the detected errors, and a directive to produce a corrected version of the code in a single pass. The output of this fix is then passed directly to the validation phase, where it is assessed for correctness. This strategy avoids unnecessary agent deployment and reduces coordination over-head, streamlining the resolution of straightforward issues. 

C. Agents Setup & Workflow Organization 

Once the execution strategy is determined, ASAD initializes the corresponding agents by loading their profiles, assigning code context, and ordering them according to the dependency structure defined during planning. To balance adaptability and efficiency, ASAD enforces bounded execution at two levels. At the agent level, each specialized agent is allowed up to three refinement attempts when its output is deemed insufficient by the main agent. At the system level, the entire debugging process is limited to five global iterations, where each iteration corresponds to a full cycle of analysis, planning, execution, and validation. These constraints are motivated by empirical observations of diminishing returns. Additional refinement beyond three attempts per agent rarely improves repair quality while increasing computational cost. Similarly, most success-ful repairs occur within five global iterations, after which additional cycles yield marginal improvements. This design ensures that ASAD remains both computationally tractable and robust across varying levels of debugging complexity. 

D. Specialized Agents / Team Members 

Specialized agents are instantiated based on the profiles generated by the main agent after analyzing the problem. Each agent has a specific role to perform a particular debugging task. Rather than executing in parallel, agents operate sequentially under the supervision of the main agent. After completing its task, each agent returns a report summarizing its actions and observations. The main agent reviews this report before de-ciding whether to proceed to the next agent or request further refinement. This review-driven execution protocol enhances robustness by allowing corrections at each step and helps prevent error propagation throughout the debugging process. IV. E XPERIMENTAL SETUP 

In this section, we describe the experimental setup used to evaluate the effectiveness of our system. We present our research questions, the used benchmarks and baselines, the evaluation metrics, and implementation details. 

A. Research Questions 

In this study, we aim to answer the following research questions (RQs): 

1) RQ1: How does our adaptive design impact bug-fixing performance compared to traditional approaches?: We inves-tigate whether ASAD improves bug-fixing performance rela-tive to traditional prompting and fixed multi-agent approaches. This involves analyzing the accuracy of generated fixes and the proportion of correctly resolved bugs across benchmarks. 

2) RQ2: How effectively does the system adapt its agent configuration across bug types and complexity levels, and what is the computational overhead compared to fixed strategies?: 

We evaluate whether the system dynamically adjusts the num-ber and roles of agents based on bug complexity, allocating more resources to harder cases while remaining efficient on simpler ones. We further measure inference time and token usage against fixed multi-agent and single-shot baselines to quantify the performance–cost trade-off. 

3) RQ3: How does adaptive agent selection influence the trade-off between debugging effectiveness and efficiency, and how do different agents contribute to successful repairs?: 

We analyze how adaptive agent selection affects the effec-tiveness–efficiency trade-off by comparing it against fixed-agent configurations across benchmarks and complexity levels. We also examine individual agent contributions by identifying which positions most often produce the first correct patch and how later agents refine or validate solutions, distinguishing gains from adaptation versus simply increasing agent count. 

4) RQ4: How does the performance of the system vary across different LLMs and experimental tests?: We first study how different LLMs affect the system effectiveness and effi-ciency, evaluating the generalizability of its adaptive design across model architectures. Then, we analyze the consistency of results across repeated tests to assess the robustness of the system under stochastic LLM behavior. 

B. Benchmarks 

We conduct our experiments on three widely used de-bugging benchmarks: DebugBench, Defects4J and CodeFlaws These benchmarks collectively cover multiple programming languages (Python, Java, C, and C++) and diverse bug cate-gories, allowing for a comprehensive evaluation of our system across different settings. 

1) DebugBench: This benchmark is designed to evaluate the debugging capabilities of LLMs. It consists of 4,253 instances covering four major bug categories: syntax, refer-ence, logic, and multiple bugs; across C++, Java, and Python. The dataset is constructed by collecting correct code snippets from the LeetCode community and systematically injecting bugs using GPT-4 while maintaining rigorous quality con-trol. DebugBench addresses limitations in prior debugging benchmarks, such as data leakage, limited dataset scale, and insufficient bug diversity. It enables systematic assessment of LLM debugging performance under zero-shot conditions, highlighting strengths and weaknesses across error types. 

2) Defects4J: One of the most established benchmarks for evaluating fault localization and program repair in Java. As of version 3.0.1, it contains 854 reproducible bugs drawn from 17 widely used open-source Java projects, including JFreeChart, Closure Compiler, Gson, Jackson, and Mockito. Each bug IEEE TRANSACTIONS ON SOFTWARE ENGINEERING 7

includes a buggy and fixed version, isolated to ensure that changes are limited to the fix itself. The dataset is accompanied by test suites, ensuring that at least one test case fails on the buggy version and passes on the fixed one. Defects4J supports reproducible research and provides metadata facilitating em-pirical studies on patch size, bug localization, and fix patterns. On average, patches are small and localized, typically around four lines in a single file. 

3) CodeFlaws: A large-scale benchmark for automated program repair in C, consisting of 3,902 real-world bugs collected from programming contest submissions. These bugs are classified into 39 syntactic difference-based defect classes, capturing a wide range of common programming errors. Code-Flaws facilitates objective comparison of different repair tools and enables the study of relationships between fault types and repair effectiveness. It includes buggy and corrected program versions, extensive test suites, and metadata from competitive programming contexts, making it a valuable resource for eval-uating automated debugging and program repair techniques. 

C. Evaluation Metrics 

To assess the performance of our system, we focus on three main aspects: the bug fix rate, which measures how often the system successfully repairs buggy programs; adaptability, which captures how the system adjusts its strategy based on bug complexity; and computational overhead, which evaluates the resources and time required to perform repairs. We present each metric in the following paragraphs. 

1) Bug Fix Rate: The bug fix rate is the primary metric used to evaluate the effectiveness of the system. It measures the proportion of buggy instances that are successfully repaired by the system, where a repair is considered successful if the generated patch compiles and passes all available test cases in the benchmark suite. Thus, for DebugBench and CodeFlaws, a fix is counted as correct only when the generated code passes the complete test suite provided by the benchmark. For Defects4J, following standard practice in automated program repair [15], we distinguish between two related but distinct notions: plausible fixes and correct fixes . 

> •

Plausible Fix: A generated patch that compiles success-fully and passes all available regression test cases in the benchmark suite. This indicates that the patch is functionally consistent with the test specifications, but does not guarantee correctness beyond the observed tests.  

> •

Correct Fix: A plausible fix that is equivalent to the ground-truth developer patch in terms of behavior with respect to the benchmark test suite. In practice, this is operationalized as a patch that passes all test cases and is functionally equivalent to the developer-provided solution, when such reference is available. Otherwise, correctness is determined by the benchmark’s official evaluation protocol when it provides additional validation criteria beyond the public test suite. Reporting both metrics is important: plausible fixes indicate how often a system produces candidates that satisfy all avail-able test cases in the benchmark, while correct fixes capture true reliability by ensuring semantic equivalence with the developer’s intended solution. 

2) Adaptability: Adaptability is crucial for an agentic sys-tem that dynamically assigns roles based on task complexity. We measure how effectively the system tailors its debugging strategy, including the number of agents created and iterations performed, in response to varying levels of complexity. We evaluate adaptability by analyzing trends in agent usage across different types of bugs. 

3) Computational Overhead: While adaptability and bug fix rate are important, efficiency must also be considered. We evaluate the computational cost incurred by the adaptive design in comparison to fixed multi-agent or single-shot debugging approaches. This is measured in terms of inference time, token consumption. We track the number of iterations required to reach a solution, as well as the computational resources used by the main and specialized agents. 

D. Baselines 

We compare our system against both prompting-based meth-ods and state-of-the-art agentic program repair systems to isolate the benefit of adaptive orchestration from improve-ments in prompting strategies or underlying model capability. Specifically, we evaluate Zero-shot , Chain-of-Thought (CoT) ,and four recent static agentic repair systems: ChatRepair [34], 

FixAgent [6], AdverIntent-Agent [35], and Repair-Agent [36]. These baselines cover strong non-adaptive approaches span-ning single-prompt, conversational, and fixed multi-agent paradigms. We further compare against three internal abla-tion variants to isolate the effect of adaptive routing in our system. All variants preserve the same multi-agent framework but remove dynamic decision-making: (i) ASAD-Lite , which always uses a minimal single-agent configuration; (ii) ASAD-Fixed , which generates a fixed set of three specialized agents regardless of bug complexity; and (iii) ASAD-Max , which always activates the maximum number of agents. 

E. Bug Complexity Characterization 

To assess whether the Main Agent’s routing decisions track bug complexity, we independently characterize the complexity of each faulty program. For each bug, we identify the buggy-side region affected by the ground-truth fix and compute two measures on that region: the number of changed lines, representing the repair scope, and Halstead Effort, capturing the complexity of the affected code. We use the predefined easy, medium, and hard instances in DebugBench to establish the corresponding complexity ranges and apply the same characterization consistently across CodeFlaws, and Defects4J. This characterization is performed entirely offline and is independent of ASAD’s routing decisions. The ground-truth fixes are used only for this offline analysis and are never avail-able to ASAD during debugging. The Main Agent receives neither the resulting complexity labels nor any information derived from the ground-truth fixes; it independently selects SIMPLE or COMPLEX using only information available during debugging. We then compare its routing decisions with the independently characterized complexity levels to assess whether its adaptive behavior tracks bug complexity. The system consists of a central controller and multiple agent modules, which collaborate to analyze buggy programs, classify their complexity, and generate repair strate-gies. Agents communicate through structured prompts and return their output in a standardized format. To handle interactions between agents, we used task-oriented, role-based prompts with structured output instructions. The evaluation of ASAD demonstrates that the adaptive orchestration of LLM-based agents substantially enhances automated debugging performance across diverse benchmarks, programming languages, and model families. Unlike static multi-agent frameworks that enforce rigid pipelines, or simple prompting techniques that lack structured reasoning, ASAD dynamically configures both the number and specialization of agents based on bug complexity. This adaptivity yields massive performance gains—improving bug-fix rates by up to 25 percentage points on synthetic benchmarks and nearly tripling repair performance on the highly complex Defects4J dataset—while simultaneously reducing computational over-head by approximately 44% compared to fixed multi-agent baselines. These findings provide strong empirical evidence that dynamic, complexity-aware coordination is a critical de-terminant of efficiency, correctness, and robustness in LLM-based program repair. In this section, we provide a deeper analysis of these results. 

A. Interpretation of Results 

Two primary mechanisms explain the observed performance gains. First, complexity-aware resource allocation ensures proportional computational utilization. As demonstrated in our resource analysis, ASAD exhibits a clear monotonic increase in agent activation, execution time, and token consumption as bug complexity grows. Trivial syntax or formatting errors are resolved with minimal overhead by activating only a single agent, while complex semantic or logical bugs trigger a cascade of specialized agents. This prevents the wasted computation inherent in fixed pipelines. Second, structured iterative refinement allows the system to perform incremental corrections. Our agent attribution analysis reveals a clear division of labor: the first agent typically provides an initial diagnosis or partial fix, the second agent acts as the primary fixer in 54% of successful repairs, and the third agent pre-dominantly serves as a refiner and validator. This sequential specialization reduces the risk of producing test-suite overfitted patches and allows the system to converge on semantically correct solutions rather than merely compilable ones. The robustness across different LLM families further high-lights the stabilizing effect of the adaptive orchestration layer. Our evaluation across six diverse models shows that ASAD dynamically adjusts its coordination strategy to the under-lying model’s capabilities: stronger instruction-tuned models IEEE TRANSACTIONS ON SOFTWARE ENGINEERING 13 

(e.g., GPT-5, Qwen-3, DeepSeek-V3) require fewer agents to achieve high fix rates, while less capable models benefit from increased agent orchestration to compensate for weaker intrinsic reasoning. Furthermore, the low stochastic variance (σ = 1 .6% ) across repeated runs confirms that this structured collaboration yields highly reproducible outcomes despite in-herent LLM randomness. While absolute repair rates on Defects4J remain lower than on synthetic benchmarks due to the profound semantic dependencies and project-level context required for real-world Java bugs, the relative improvement is striking. ASAD nearly triples the repair performance of conventional prompting on this dataset. This indicates that while highly complex bugs remain challenging for any automated system, adaptive multi-agent collaboration is crucial when long-range reasoning and deep semantic understanding are demanded by the task. 

B. Comparison with Static and Baseline Approaches 

The comparative analysis against both static multi-agent frameworks and standard prompting techniques underscores the absolute necessity of adaptivity. Previous multi-agent de-bugging systems, such as FixAgent, rely on static pipelines 

where the number, type, and order of agents are fixed. Our results reveal that such rigidity leads to significant ineffi-ciencies. On Defects4J, FixAgent generated more plausible patches than ASAD but fewer correct fixes, indicating a higher incidence of test-suite overfitting and a failure to converge on true semantic correctness. Similarly, our ablation study comparing ASAD against fixed internal variants ( ASAD-Fixed 

and ASAD-Max ) shows that simply increasing the number of agents yields diminishing marginal returns at the cost of massive computational overhead (more than 6 × the token consumption of the lightweight baseline). ASAD, by contrast, matches or exceeds the fix rates of static configurations while reducing execution time and token consumption by 44%–55%. Conversely, standard prompting techniques (Zero-shot and Chain-of-Thought) lack the structured collaboration necessary for complex debugging. While they are computationally cheap, their performance plateaus significantly on challenging bench-marks. ASAD bridges this gap by providing a reasoning-driven coordination mechanism that scales its computational effort only when the task demands it. This selective deployment not only improves efficiency and correctness but also prevents the over-correction and hallucination often seen in unconstrained LLM generation. Ultimately, these insights underline that dy-namic, context-sensitive orchestration is vastly superior to both rigid parallelism and unstructured single-agent prompting, establishing adaptivity as the key enabler for next-generation automated debugging systems. 

C. Data Contamination in Established Benchmarks 

Data contamination in established benchmarks like De-fects4J and CodeFlaws threatens the external validity of our findings, as frontier models may have encountered these datasets during pre-training. Although recent studies identify Defects4J as the benchmark with the highest overall mem-orization risk, they also confirm that modern models with substantially larger training budgets, specifically the Llama-3 and Mistral families used in our evaluation, exhibit signifi-cantly lower leakage risks [37]. By measuring Negative Log-Likelihood and 5-gram accuracy, researchers demonstrated that these newer models treat established benchmarks similarly to unseen code, avoiding the verbatim memorization observed in older architectures. Our own experimental results corroborate this limited memorization. If the evaluated models had simply retrieved memorized solutions for Defects4J, we would expect near-perfect repair rates. Instead, the maximum fix rate reaches only 32.5%. This imperfect performance demonstrates that the models must actively reason through complex semantic depen-dencies to generate valid patches. Furthermore, our adaptive approach consistently improves fix rates over static baselines across all complexity levels. If data contamination drove the performance, this adaptive orchestration would not yield such structured and consistent improvements. VII. T HREATS TO VALIDITY 

In this section, we examine possible threats to the validity of our empirical findings. 

A. Internal Validity 

LLMs exhibit inherent non-determinism due to stochastic decoding strategies and potential API-level variability, which may affect result stability. To mitigate this threat, we con-ducted five independent replications on a stratified sample of 100 DebugBench instances per model, fixing temperature parameters ( t = 0 .2) and random seeds where API-supported. Performance measurements yielded a mean fix rate with a narrow standard deviation σ = 1 .6% across replications. An-other threat concerns test-suite overfitting in repair validation. Passing benchmark test cases does not guarantee semantic correctness, particularly on Defects4J where limited coverage enables plausible but incorrect patches. We mitigated this by distinguishing plausible from correct fixes using developer-provided oracles, conducting manual inspection on all 223 patches classified as correct. Subjectivity in complexity as-sessment also presents another threat, as agent allocation de-pends on the main agent’s internal judgment without objective ground truth. We addressed this by formalizing complexity cri-teria into five measurable dimensions (Error Severity, Source-location difficulty, Program-understanding difficulty, System-level operations, and Inter-function dependencies.) with ex-plicit decision thresholds, validating assessments against hu-man judgments on 100 bugs. 

B. External Validity 

The applicability of the proposed approach to other datasets constitutes an external validity threat. Results observed on a given benchmark may not generalize uniformly to other debug-ging datasets with different characteristics. To limit this threat, we evaluated ASAD on multiple benchmarks (DebugBench, Defects4J, and CodeFlaws) covering different programming languages, bug types, and dataset properties, thereby reducing reliance on any single benchmark. Nevertheless, the bench-marks considered in this study primarily focus on single-file IEEE TRANSACTIONS ON SOFTWARE ENGINEERING 14 

or unit-level defects and do not fully capture the complexity of large industrial software systems. As a result, the effective-ness of ASAD in repository-scale settings involving multi-module dependencies, build systems, and CI/CD pipelines remains uncertain. Evaluating the approach on repository-level benchmarks and in real-world industrial environments is an important direction for future work. Generalization across LLMs represents another external threat. The evaluation included several model families available in 2025, including GPT-5, DeepSeek-V3, Gemini-1.5, and Llama-3. While newer models may behave differently, consistent performance trends were observed across the evaluated models, suggesting that the findings are not tied to a specific LLM. VIII. R ELATED WORK 

In this section, we review recent research on the use of LLMs for debugging, focusing on reasoning techniques as well as agent-based approaches. 

A. LLM Reasoning Techniques in Debugging 

Recent work has explored a range of reasoning techniques to improve the debugging capabilities of LLMs. Levin et al. [27] introduce ChatDBG, a debugging assistant that applies Chain-of-Thought prompting to generate step-by-step explanations for its proposed fixes, making the reasoning process transpar-ent and verifiable. Chen et al. [29] propose “Self-Debugging,” in which LLMs iteratively refine code based on actual execu-tion outcomes, using runtime feedback to guide corrections. Ahmed et al. [28] enhance patch generation through Self-Consistency, producing multiple candidate fixes and selecting the most coherent or frequently occurring solution. Other ap-proaches integrate reasoning with structured workflows. Kang et al. [38] present AutoSD, a system that formulates debugging as scientific inquiry: the LLM generates hypotheses about the bug’s root cause and then uses a debugger to test them. Similarly, Lee et al. [6] develop FixAgent, which combines multi-agent collaboration and tool use to mimic real developer workflows, separating diagnosis, patching, and validation into distinct phases. To further extend reasoning, recent systems embed retrieval, planning, and tool interaction directly into the inference loop. Chen et al. [26] integrate retrieval into multi-step reasoning, allowing LLMs to dynamically fetch and incorporate external knowledge during problem solving. Yan et al. [39] combine reflection with tool execution, using both intra-agent self-critique and inter-agent feedback to revise plans before and after invoking tools. Finally, Schick et al. [40] demonstrate that tool invocation can be learned and embedded directly into the LLM’s generation process, enabling the model to reason through executing code, observing outcomes, and updating its plan in response. 

B. LLM-based Agentic Systems for Debugging 

Building on these reasoning patterns, recent research has developed multi-agent systems that distribute debugging re-sponsibilities across specialized LLM agents. Qin et al. [41] propose AgentFL, a modular framework for bug localiza-tion that employs four distinct agents (Test Code Reviewer, Source Code Reviewer, Software Architect, and Software Test Engineer) to analyze different aspects of the codebase using test and documentation signals. Kang et al. [38] further enhance interpretability by prompting agents to engage in hypothesis-driven reasoning, requiring them to justify and test each step before proposing a fix. More advanced systems coordinate agents across larger codebases. Similarly, Alibaba’s LingmaAgent [42] integrates LLM agents directly into the IDE, allowing them to gather contextual information from the entire codebase to resolve issues more accurately. Structured coordination is also central to MAGIS [43], which assigns roles such as manager, developer, and quality assurance agent to enforce task decomposition, accountability, and verification. IX. F UTURE WORK 

We will scale ASAD to repository-level debugging, where agents must coordinate across dozens of files while respecting import dependencies, build constraints, and cross-module data flows. This requires capabilities for traversing call graphs, propagating fixes across coupled components, and validating changes against project-wide test suites. We will also close the validation gap by integrating runtime feedback into agent reasoning loops. Agents will execute proposed patches against dynamically generated tests targeting edge cases absent from benchmark suites, using observed crashes, timeouts, and silent failures to detect overfitting and refine patches. We further plan to connect ASAD to developer ecosystems through static analyzers (e.g., Coverity, SonarQube) for fault pre-filtering, IDE linters for project-specific conventions, and version con-trol systems for assessing patch impact through change his-tories and reviewer feedback. Finally, we will study human-in-the-loop debugging, measuring how agent explanations of fault hypotheses and repair strategies affect developer trust, intervention timing, and collaborative efficiency. X. C ONCLUSION 

Static multi-agent frameworks deploy fixed teams irrespec-tive of bug complexity, leading to inefficient resource use on simple syntax errors and insufficient capacity for complex, multi-file faults. ASAD mitigates both issues by constructing its agent team after analyzing the fault. In our experiments, a single repair agent successfully resolves 73% of straightfor-ward bugs, while more complex cases dynamically trigger a team of specialized agents. Our evaluation on DebugBench, Defects4J, and CodeFlaws substantiates the effectiveness of this approach. ASAD improves fix accuracy by 12–20% over chain-of-thought prompting and by 4–9% over static multi-agent systems. These gains were achieved with 32% lower average agent usage, as ASAD scales down for simple bugs instead of imposing uniform multi-agent overhead. Together, these results suggest a broader design principle for agentic software engineering: agent configuration should be a function of problem complexity rather than a fixed predefined choice.

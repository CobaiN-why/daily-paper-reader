## 摘要
编码智能体如今已足够熟练，能够根据单个提示生成复杂的软件应用。随着其能力不断增强，人工监督已逐渐从逐行代码审查转向对结果的非介入式评估。然而，近期研究表明，这种转变暴露出一个关键风险：仅凭功能正确性并不能保证实现是安全的。尽管代码安全日益受到关注，训练更安全的编码智能体仍然充满挑战，因为难以从真实世界代码仓库中大规模获得可靠的安全监督。我们提出 AuraForge，用于合成并验证可执行的安全测试，以训练安全的编码智能体。我们的方法结合了面向攻击的测试合成、语言可扩展的任务构建，以及针对奖励黑客行为的防护措施。利用 AuraForge，我们构建了 AuraGym，一个多语言、多 CWE 的可执行训练环境：来自 Python、JavaScript 和 TypeScript 的 344 个真实世界代码仓库的 679 个可执行功能实现任务，覆盖 177 个 CWE 类别。在包含人工编写安全测试的子集上，AuraForge 平均生成的测试用例数量约为其 3 倍，并将假阳性率降低 83.23%，从而使其他安全实现也能获得正确监督。使用合成安全测试训练 Qwen3.5-4B 所获得的提升大于使用人工编写安全测试（在三种语言上平均为 19.7 FuncPass 和 6.2 SecPass，对比 14.9 FuncPass 和 4.4 SecPass）。这些结果表明，AuraForge 提供了更多样、更可靠的安全监督，以训练安全的编码智能体。

## Abstract
Coding agents are now proficient enough to generate complex software applications from a single prompt. As their capabilities have grown, human oversight has increasingly shifted from line-by-line code review toward hands-off evaluation of outcomes. However, recent studies have shown that such a transition exposes a critical risk: functional correctness alone does not guarantee a secure implementation. Despite growing attention to code security, training safer coding agents remains challenging because reliable security supervision is difficult to obtain at scale from real-world repositories. We introduce AuraForge to synthesize and validate executable security tests for training secure coding agents. Our approach combines attack-oriented test synthesis, language-extensible task construction, and safeguards against reward hacking. Using AuraForge, we construct AuraGym, a multi-language and multi-CWE executable training gym: 679 executable feature-implementation tasks from 344 real-world repositories across Python, JavaScript, and TypeScript, covering 177 CWE categories. On the subset with human-written security tests, AuraForge produces about 3 times as many test cases on average and reduces the false-positive rate by 83.23%, allowing alternative secure implementations to receive correct supervision. Training Qwen3.5-4B with synthesized security tests gains larger improvements than human-written security tests (average 19.7 FuncPass and 6.2 SecPass vs. 14.9 FuncPass and 4.4 SecPass) on three languages. These results demonstrate that AuraForge provides more diverse and reliable security supervision to train secure coding agents.

## 1. 核心问题与研究动机

- **背景转变**：编码智能体已能从单条提示生成复杂软件，"氛围编程"（vibe coding）使人类监督从逐行代码审查转向对最终结果的非介入式评估。
- **核心风险**：功能正确性并不等于安全性。安全需求（输入净化、授权边界、敏感数据保护等）通常是隐含的，提示中不会显式说明，而人类已无法逐行审查。
- **实证差距**：BaxBench、SecureVibeBench、SusVibes 等基准一致显示，智能体常满足功能需求却产出有漏洞的实现；更强的通用编码能力并不自动带来安全实现。
- **训练侧瓶颈**：现有编码智能体训练数据（SWE-Gym、SWE-smith、SWE-rebench 等）主要依赖功能测试监督，缺少安全监督。而把历史漏洞修复规模化转为可执行训练数据面临三个瓶颈：
  1. **可靠安全测试缺失**：人工安全测试可能漏掉其他脆弱行为，或错误拒绝等价的安全实现。
  2. **多语言任务构建复杂**：源码结构、依赖管理、构建系统、测试运行器各不相同。
  3. **环境完整性难以保证**：仓库历史、编译产物、已安装包副本、外部来源都可能泄漏参考实现，使智能体"检索"而非"实现"即可通过测试。
- **整体含义**：论文主张安全必须由智能体自身习得，因此需要可大规模获取、可执行、可靠的安全监督信号。

## 2. 方法论：AuraForge

### 2.1 问题形式化

- 训练实例定义为 $x = (R, d, T_{func}, T_{sec}, E)$：仓库状态、功能请求、功能测试集、安全测试集、可执行环境。
- 构建元数据 $Z$ 记录历史脆弱实现 $S^*_{vuln}$、修复实现 $S^*_{sec}$ 及漏洞来源，**对智能体保密**。
- 良好安全测试需满足三条性质：**(i) 检测性**（脆弱时暴露）、**(ii) 实现独立性**（接受满足同一安全需求的替代实现）、**(iii) 执行可靠性**（可复现，能区分断言失败与基础设施错误）。

### 2.2 三段式流程（The Forge / The Aura / The Seal）

**① The Forge —— 任务构建**

- **补丁分离**：从漏洞修复提交中分离实现改动与测试改动（文件路径初筛 + LLM 处理歧义，如依赖/配置改动）。
- **特征掩码**：从脆弱仓库状态中移除目标功能实现，生成任务仓库 $R$ 与功能请求 $d$；掩码需保留实现所需接口，且**不泄漏任何安全提示**。
- **共享一致性校验器**：检查参考实现能否满足生成的请求、掩码是否引入无关改动，反馈用于修订掩码与请求。

**② The Aura —— 面向攻击的安全测试合成**

- **阶段一（识别）**：仅依据公开记录（CVE、公告及其链接）调研漏洞，产出结构化"安全属性"：
  - 具体弱点、风险叙事（攻击者是谁、能做什么、获得什么）；
  - **安全不变量**（必须始终成立的"效果"）；
  - **攻击面**（攻击者可控的入口点）；
  - **攻击变体**（覆盖不同入口、编码、代码路径，含可观测效果与来源化 payload）；
  - **安全无关差异**（不同正确实现间会变化、不得断言的细节）。
  - 刻意**不枚举防御措施**，避免测试被引导到历史修复方式上。
- **阶段二（合成）**：在任务执行环境中运行第二个智能体，输入安全属性、功能请求与脆弱代码，编写测试套件。
  - 断言**攻击的可观测效果是否被阻止**，而非防御机制/位置——例如"未渲染出可执行 `<script>` 元素"，而非"输出等于某个转义字符串"；未授权访问被重定向或拒绝都算安全。
  - 历史修复仅作为执行信号（可应用/回滚以检查测试能否区分脆弱与修复状态），**不作为断言来源**。
- **可靠性规则**：禁止外部网络依赖与顺序相关执行；模糊测试需固定种子并设上界；由漏洞导致的挂起须转为有界超时下的断言失败；导入/依赖/安装/连接/超时错误一律不算安全证据；无法满足要求时**放弃该任务而非给出弱 oracle**。
- **后处理与验收**：只保留新增测试文件，删除任何触及实现补丁所改文件的改动；在合成器控制之外的**全新环境**中分别对 $S^*_{vuln}$ 与 $S^*_{sec}$ 运行，只有两次运行都无测试错误、且至少一个测试在脆弱实现失败而在修复实现通过时才接受。

**③ The Seal —— 环境完整性**

- **量化检索风险**：在保留 git 历史与网络的 SusVibes 环境中评测 26 个"智能体–模型"组合，共 5,174 次运行。规则匹配器高召回初筛 + LLM 裁判复核，结果显示 **16% 的运行发生检索，单模型最高达 40%**，主要渠道为 git 历史；此外还发现智能体从 `site-packages` 等本地副本恢复上游包。
- **控制措施**：选择性屏蔽泄漏提交不可行（掩码功能跨多提交演化），因此**彻底移除 git 历史**，仓库以单一初始提交发布；移除构建产物、依赖缓存、已安装包副本；解题时在命令层屏蔽网络与包管理器（`git clone`、`git remote`、`npm`/`yarn`/`pip download` 等）。
- **解题与评估分离**：安全测试仅在评估时于全新容器中引入；测试所用文件的任何编辑在应用解决方案前被丢弃，防止解篡改判分测试。

### 2.3 语言可扩展架构

- 拆分为**共享核心**（语言无关、复用不变）与**语言适配器**（仅提供语言相关部分），支持新语言只需实现三个适配器组件：
  - **源码转换**：语言特定掩码策略（如 JS/TS 处理实现体、初始化器、导出、类型注解）+ 共享一致性校验。
  - **环境准备**：环境构建智能体读取配置、CI 工作流、安装文档；JS/TS 场景需选择 Node 版本、包管理器、解决 workspace 依赖，并**清理陈旧产物、重新构建**，确保测试执行当前源码而非旧构建。
  - **结果归一化**：解析运行器特定报告（pytest/jest/vitest），统一区分通过、断言失败、执行错误；共享核心再做安全测试判别性与功能测试敏感性检查。

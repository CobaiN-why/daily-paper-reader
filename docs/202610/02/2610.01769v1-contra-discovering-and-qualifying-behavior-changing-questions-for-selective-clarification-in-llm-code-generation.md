## 摘要
编码智能体可以生成看似正确、但实现了用户从未期望行为的代码。当智能体通过自身假设静默地解决未充分指定的需求时，这种不匹配就可能出现。随着后续开发建立在这些假设之上，纠正由此产生的行为可能会变得越来越昂贵。早期澄清有助于防止此类不匹配，但不必要的问题会打断开发者并拖慢开发。现有方法难以在识别关键澄清问题的同时避免不必要的问题。因此，我们提出CONTRA，一种免训练方法，将广泛的问题发现与基于语义和执行的问题资格判定相结合。CONTRA首先生成候选问题，并过滤掉那些与所需行为无关或已被需求解决的问题。对于每个剩余问题，它基于两种可能答案分别生成程序，并检查在共享输入上是否存在稳定的行为差异。随后，它利用交互历史在合格问题中进行选择，或停止提问。在ClarifyCodeBench上的实验表明，CONTRA在全部四个编码智能体上取得最高F1，超过最佳基线宏平均F1 13.88个百分点。在相同LLM和评估协议下，CONTRA也比编码框架Claude Code和OpenHands取得更高的澄清召回率和F1。为支持实际使用，我们还将CONTRA实现为Claude Code插件，将选择性澄清集成到日常开发中。

## Abstract
Coding agents can generate code that appears correct but implements behavior the user never intended. This mismatch can arise when an agent silently resolves underspecified requirements through its own assumptions. As subsequent development builds on these assumptions, correcting the resulting behavior can become increasingly costly. Early clarification can help prevent such mismatches, but unnecessary questions can interrupt developers and slow down development. Existing methods struggle to identify key clarification questions while avoiding unnecessary ones. Therefore, we propose CONTRA, a training-free method that combines broad question discovery with semantic and execution-based question qualification. CONTRA first generates candidate questions and filters out those unrelated to required behavior or already resolved by the requirement. For each remaining question, it generates programs conditioned on two plausible answers and checks for stable behavioral differences on shared inputs. It then uses the interaction history to select among qualified questions or stop asking. Experiments on ClarifyCodeBench show that CONTRA achieves the highest F1 with all four coding agents, exceeding the best baseline macro-average F1 by 13.88 percentage points. With the same LLM and evaluation protocol, CONTRA also achieves higher clarification recall and F1 than the coding harnesses Claude Code and OpenHands. To support practical use, we also implement CONTRA as a Claude Code plugin that integrates selective clarification into everyday development.

# CONTRA 论文总结

## 1. 核心问题与整体含义

- **背景**：编码智能体越来越多地根据自然语言需求生成/修改代码，但需求常对关键行为（边界情况处理、输出格式等）欠明确。
- **核心问题**：面对欠明确需求，智能体往往**静默采用一种合理解释**并继续实现，生成的代码在该解释下正确，却与用户真实意图不符；一旦后续开发建立在这些隐含假设上，纠正成本会不断累积。
- **两难权衡**：
  - 早期澄清可防止此类偏差，但**不必要的问题会打断开发者、拖慢开发**（例如重复询问需求已说明或历史已回答的内容，或提出与任务无关的问题）。
  - 因此需要**选择性澄清**：只在真正必要时提问。
- **现有方法不足**：
  - Direct Prompting、Ask-or-Assume 依赖模型自行判断是否提问，常**漏掉必要问题**（如 GPT-5.5 上 Direct Prompting 精度 59.32% 但召回仅 15.12%）。
  - ClarifyGPT 依据采样程序的行为分歧生成问题，但分歧可能只是实现错误，因而**问了大量不必要问题**（如 GPT-5-mini 上召回 37.37% 但精度仅 13.58%）。
- **整体含义**：论文提出免训练的 CONTRA，将“广泛发现问题”与“基于语义与执行证据的问题资格判定”结合，在有限提问预算下最大化关键问题的识别，并将其落地为 Claude Code 插件。

## 2. 方法论

### 2.1 问题形式化

- 设需求为 S，问题预算为 B（实验取 5）；交互历史 H_t = [(q₁,a₁), …, (q_{t−1},a_{t−1})]。
- 每步智能体根据 S 与 H_t 决定继续提问或停止：Select(S, H_t, Q_t) ∈ Q_t ∪ {STOP}。
- 目标：在避免无关/已回答问题的同时，识别并提问关键澄清问题。

### 2.2 三阶段流程

**(1) Question Discovery（问题发现）**

- 每轮同时使用两种生成方式：
  - **上下文感知生成**：用 S + 当前候选集搜索新问题；
  - **独立生成**：仅用 S 生成。
- 新旧候选联合评审，去重并合并重叠问题；连续两轮无新问题或达到轮数上限则停止。
- 之后为每个保留问题**重新生成两个合理答案**作为需求补全 h_A、h_B，要求二者均与 S 兼容且**仅在该问题的答案上不同**，从而把后续行为差异归因到该问题本身。

**(2) Question Qualification（问题资格判定）**

- 保留满足三者的问题：Q_qual = {q ∈ Q_gen | Rel(q) ∧ Unres(q) ∧ Diff(q)}。
- **相关性 Rel**：q 是否涉及所需程序行为，其两个补全是否给出不同备选行为。
- **已解决性 Unres**：仅当 S 中的文本**支持一个补全并排除另一个**时才标记为已解决，且判断必须引用支撑文本。
- **行为验证 Diff**：
  - 对每个补全 h_z（z ∈ {A,B}）独立生成 3 个程序 p¹_z, p²_z, p³_z（共 6 个）；
  - 用 S、q、h_A、h_B 生成至少 7 个在两种补全下均有效的**共享输入集 X**；
  - 在共享输入上执行，每个补全的输出“稳定”定义为至少 2/3 程序一致，否则该输出未定义；
  - 若存在某个共享输入使 o_A(x)、o_B(x) 均有定义且不相等，则 Diff(q)=1，问题保留；否则丢弃。
  - 设计动机：共享输入保证两组可比，组内多数一致降低孤立实现错误的影响；失败检查**不证明行为等价**。

**(3) Adaptive Question Selection（自适应问题选择）**

- 根据 S、H_t 与剩余问题 Q_t 的文本，选择仍需用户输入的问题，或返回 STOP。
- 收到回答后把 (q_t, a_t) 追加进历史并从候选集移除 q_t，避免已解决或冗余的提问。
- 终止条件：选择器返回 STOP、无剩余问题、或已提问 B 个问题。

### 2.3 效率优化与部署

- **CONTRA-Flash**：按需资格判定——选择器先从已发现问题中挑一个候选，再对其执行相关性、已解决性与行为验证；被拒则丢弃并继续选择，避免对选择器根本不会考虑的问题做昂贵判定。
- **Claude Code 插件**：hook 记录用户提交请求时的工作树快照，结束时对比识别本次改动；并行运行两条流程（用 claude-haiku-4-5-20251001 从智能体最终报告中提取决策；用 claude-opus-5 独立审查需求、代码变更与仓库上下文，不读该报告），用文本重叠合并；规则化优先级排序；对未解决的实现选择生成**区分性测试**与替代解释补丁，在隔离仓库副本上执行；验证默认后台运行，区分性测试可留在仓库中作为行为记录。

## 3. 实验设计

- **基准**：ClarifyCodeBench，包含 **419 个欠明确任务**（带 gold 澄清问题与答案）与 **80 个完全明确任务**（用于统计误报）。
- **评估协议**：每个方法最多提 5 个澄清问题，之后生成最终程序；由 **GPT-4o 评估器**以三次判断多数投票将提问与 gold 问题匹配。
- **被测模型（编码智能体）**：GPT-5-mini、GPT-5.5、Grok 4.5、Gemini 3.1 Pro；harness 对比统一使用 **Qwen3.8-27B**。
- **对比基线**：
  - Direct Prompting；
  - Ask-or-Assume（引入意图智能体审查动作）；
  - ClarifyGPT（基于采样程序的行为分歧提问）；
  - 编码框架 Claude Code 与 OpenHands（相同 LLM、预算与评分流程）。
- **评估指标**：问题

- **评估指标**：
  - **问题精度（Precision）**：所提问题中与 gold 澄清问题匹配的比例，衡量“是否问了必要问题”；
  - **问题召回（Recall）**：gold 澄清问题中被成功提出的比例，衡量“是否漏掉关键问题”；
  - **F1**：精度与召回的调和平均，作为选择性澄清能力的综合指标；
  - **误报率（False-Positive Rate）**：在 80 个完全明确任务上仍提出问题的比例，衡量对开发者的打扰程度；
  - **最终程序正确性（Pass@1）**：澄清结束后生成程序通过隐藏测试的比例，衡量澄清是否真正改善实现；
  - **效率指标**：平均提问数、额外 token 消耗与端到端延迟，用于评估方法在实际编码智能体中的可部署性。

## 4. 主要实验结果

### 4.1 选择性澄清能力

- CONTRA 在 ClarifyCodeBench 上同时取得较高的精度与召回，克服了基线的“偏科”问题：
  - Direct Prompting 与 Ask-or-Assume 倾向“少问”，召回低，大量关键歧义被静默假设；
  - ClarifyGPT 倾向“多问”，精度低，在明确任务上误报多；
  - CONTRA 通过“广泛发现 + 证据化资格判定”过滤掉仅由实现错误引起的虚假分歧，因此能在有限预算内优先提出真正影响行为的歧义。
- 在四个编码智能体（GPT-5-mini、GPT-5.5、Grok 4.5、Gemini 3.1 Pro）上趋势一致，说明方法不依赖某一特定模型；其中在欠明确程度较高的任务上召回提升尤为明显。

### 4.2 对最终程序正确性的影响

- 相比 Direct Prompting，CONTRA 澄清后生成的程序在隐藏测试上的通过率有稳定提升，说明其提出的问题确实对应会影响实现结果的需求缺口，而非表面措辞差异。
- 相比 ClarifyGPT，CONTRA 在正确性上不劣或更优，同时提问数更少，表明“少而准”的澄清比“多而杂”的澄清更有效：过多问题可能引入与 gold 无关的约束，反而干扰实现。

### 4.3 明确任务上的打扰控制

- 在 80 个完全明确任务上，CONTRA 的误报率显著低于 ClarifyGPT，接近 Direct Prompting 的水平。
- 关键原因在于 **Unres(q)** 判定要求“S 中文本支持一个补全并排除另一个”，并强制引用支撑文本；这使模型不能仅凭“没看到明确说明”就发起提问，必须证明需求确实未解决。

### 4.4 效率与消融

- **行为验证的必要性**：去掉 Diff(q) 后，精度明显下降，说明仅凭语义层面的“相关性 + 未解决性”会保留大量不影响可观察行为的问题。
- **独立生成的必要性**：仅保留上下文感知生成时，候选问题多样性下降，召回受损；仅保留独立生成时，问题与当前候选集重复度高，轮次浪费。
- **共享输入设计的必要性**：若分别用各自输入集执行，两组输出不可比，行为验证会引入噪声；共享输入 + 组内 2/3 多数一致显著降低孤立实现错误的干扰。
- **CONTRA-Flash**：按需资格判定在保持精度与召回基本不变的前提下，减少了对“选择器根本不会考虑的问题”的昂贵验证开销，降低 token 与延迟成本。
- **预算敏感性**：随预算 B 增大，召回上升但边际收益递减；B=5 时已能覆盖大部分 gold 问题，继续增加预算更多带来冗余提问。

## 5. 部署形态：Claude Code 插件

- **决策提取与独立审查并行**：一条流程从智能体最终报告中提取实现决策，另一条流程不读报告、仅基于需求、代码变更与仓库上下文独立审查，降低“报告合理化”带来的偏差；两者通过文本重叠合并，再由规则化优先级排序。
- **区分性测试与替代补丁**：对未解决的实现选择生成区分性测试与替代解释补丁，在隔离仓库副本上执行，用真实运行结果判断该选择是否影响行为；验证默认后台运行，不阻塞开发者。
- **行为记录**：通过验证的区分性测试可保留在仓库中，作为后续变更的行为契约与回归保护，使一次澄清的收益可复用。
- **工作树快照**：hook 在用户提交请求时记录工作树快照，结束时对比识别本次改动，从而把澄清范围限定在本次任务实际触及的代码上。

## 6. 贡献与创新点

- **问题定位**：把“何时向用户提问”从模型直觉判断转化为可验证的问题资格判定问题，明确区分“需求未明确”与“实现有分歧”。
- **方法创新**：
  - 双通道问题发现（上下文感知 + 独立）提升候选覆盖；
  - 三条件资格判定（Rel、Unres、Diff）分别对应“相关”“未解决”“影响行为”；
  - 基于共享输入与组内多数一致的行为验证，用执行证据替代语义直觉；
  - 自适应选择与历史去重，避免重复或已解决问题。
- **基准与评估**：ClarifyCodeBench 同时包含欠明确与完全明确任务，使精度、召回与误报可被同时衡量，弥补以往只测召回或只测精度的不足。
- **落地性**：CONTRA-Flash 与 Claude Code 插件展示了免训练方法在真实编码工作流中的可行部署路径。

## 7. 局限与讨论

- **行为验证的保守性**：失败检查只能说明“未观察到差异”，不能证明行为等价；因此 Diff(q)=0 时丢弃问题存在漏掉罕见边界情况的风险。
- **依赖可执行环境**：行为验证需要能生成并运行程序与共享输入；对不可执行或强交互/外部依赖的任务适用性受限。
- **答案质量假设**：要求两个补全均与 S 兼容且仅在该问题上不同；若 LLM 生成的补全本身偏离需求，资格判定会被污染。
- **评估器依赖**：问题与 gold 的匹配依赖 GPT-4o 三次多数投票，可能对措辞敏感；虽然多数投票降低噪声，但仍是自动评估的固有局限。
- **预算固定**：实验统一最多 5 个问题，未充分探索动态预算或按任务风险分配预算的策略。
- **成本**：每轮需多次生成程序与共享输入，尽管 CONTRA-Flash 缓解了开销，但在大规模仓库中仍需关注延迟与算力成本。

## 8. 结论

CONTRA 的核心洞察是：**澄清问题的价值不在于“需求看起来模糊”，而在于“不同合理解释会导致可观察的行为差异”**。论文通过“广泛发现问题 + 语义与执行证据双重资格判定 + 自适应选择”的免训练流程，在有限提问预算下同时提升精度与召回，减少对开发者的不必要打扰，并在最终程序正确性上带来实际收益。其 Claude Code 插件形态进一步说明，选择性澄清可以嵌入现有编码智能体工作流，把隐含假设转化为可验证、可回归的行为记录。

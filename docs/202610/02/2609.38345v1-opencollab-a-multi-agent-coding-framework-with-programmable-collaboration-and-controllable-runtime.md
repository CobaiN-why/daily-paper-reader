## 摘要
多智能体编码系统旨在通过协作解决复杂软件工程任务。然而，现有评估通常假设所配置的组织会被忠实遵循，而现实并非如此。这种行为差距，加上底层系统组件的差异，使得人们无法清晰归因所观察到的收益。为此，我们提出 OpenCollab，一个多智能体编码框架，为可编程协作与可控运行时提供统一基础设施。具体而言，OpenCollab 统一组织设计，在共享运行时上实施实验控制，并通过细粒度事件流追踪执行过程。在此基础上，我们定义了 Adherence 来量化所声明的组织是否真正实现。我们的实验揭示，智能体在不同配置下的协作方式差异很大：改变任一单个维度都会改变 Adherence，从 47.2% 到高达 97.2%。此外，大量智能体编码基准测试表明，基于 OpenCollab 构建的双编码智能体工作流相较于 Mini-SWE-agent、Codex CLI 和 Claude Code 等主流执行框架，确立了新的 SOTA 性能，表明设计良好的组织可以胜过强大的现有执行框架，而 OpenCollab 的单智能体配置在所有评估套件中使用的 token 最少。OpenCollab 建立了一个统一的多智能体基础设施，便于可编程协作与受控因果评估。

## Abstract
Multi-agent coding systems are designed to tackle complex software engineering tasks through collaboration. However, existing evaluations typically assume configured organizations are followed faithfully, whereas reality differs. This behavioral gap, combined with differences in underlying system components, prevents clear attribution of observed gains. To this end, we introduce OpenCollab, a multi-agent coding framework that provides a unified infrastructure for programmable collaboration and controllable runtime. Specifically, OpenCollab unifies organization design, enforces experimental control on a shared runtime, and tracks execution through fine-grained event streams. On this basis, we define Adherence to quantify whether the declared organization is actually realized. Our experiments reveal that agents collaborate very differently across configurations: changing any single dimension shifts Adherence, from 47.2% to as high as 97.2%. Furthermore, extensive agentic coding benchmarks show that a two-coder workflow built on OpenCollab establishes new SOTA performance compared to the mainstream harnesses such as Mini-SWE-agent, Codex CLI, and Claude Code, showing that a well-designed organization can outperform strong existing harnesses, while OpenCollab's single-agent configuration uses the fewest tokens across all evaluated suites. OpenCollab establishes a unified multi-agent infrastructure for easy programmable collaboration and controlled causal evaluation.

## 1. 核心问题与整体含义

- **研究动机**：多智能体编码系统通常按分析师、开发者、测试者等角色分工协作，但现有评估默认“所声明的组织会被忠实执行”，而实际执行常与之背离。
- **核心问题**：这种“声明组织”与“实际执行”之间的行为差距（论文称为 *illusion of collaboration*，协作幻觉），加上不同底层系统组件（harness）的差异，使得性能收益无法清晰归因。
- **具体表现**：
  - 缺乏统一机制显式声明组织拓扑；
  - 多智能体评估很少受控，harness 差异和运行间波动混淆了性能差距来源；
  - 中间协作过程可观测性差，日志面向人类调试而非归因；
  - 主智能体常绕过队友独自完成任务，或耗尽 token 预算前未发起任何委派。
- **整体含义**：论文提出 OpenCollab，旨在提供**可编程协作 + 可控运行时**的统一基础设施，使多智能体系统的收益能够被因果归因，而非被基础设施噪声掩盖。

## 2. 方法论

- **核心思想**：将**高层组织编排**与**低层模型执行**解耦，所有配置共享同一运行时底座，从而隔离非组织性变量。
- **架构设计（两层）**：
  - **共享会话运行时**：基本执行单元为 session（对应组织中的一个角色），每个 session 运行同一个十状态有限状态机循环，统一处理上下文管理、模型调用、工具执行。
  - **编排层**：通过独立控制器管理会话拓扑、生命周期与消息路由，支持：
    - **Team 模式**（模型主导）：模型自行决定是否、何时、向谁委派，受声明拓扑约束；
    - **Workflow 模式**（程序化）：Python 脚本显式控制调用顺序、扇出结构与条件状态转移；
    - **Single 模式**：单智能体基线。
- **可编程协作**：用户通过声明式配置指定角色提示、各角色工具集、有向通信拓扑。复现 edict 核心多智能体模式（约 24k 行代码）在 OpenCollab 中仅需 239 行。
- **受控评估的七个条件**：模型、工具、预算、上下文、拓扑五个因素在运行时保持恒定；两个验证要求（Realized、Compared）确保每轮运行可审计。
- **运行时门控**：
  - 工具调用与智能体间消息在调用时被拦截，越权请求被拒绝并记录；
  - 每个角色有独立 token 上限，通过**预调用准入**（pre-call admission）在每次模型调用前校验预算，超限则终止并记录明确终止码。
- **执行可追溯性**：用有序、只追加的**事件流**替代散文日志，每个事件包含单调步数、时间戳、运行 ID、角色 ID、事件类型与类型化载荷。共定义七类事件：模型调用、工具执行、拒绝动作、会话终止、spawn 尝试、worktree 修改、上下文压缩触发。
- **Adherence（遵循度）指标**：
  - 六条验证轴：参与度、委派、角色边界、预算共享、信息流、上下文策略；
  - 每轴产生 `adherent / deviant / unverifiable` 判决，任一适用轴未通过则该运行 `adh(r)=0`；
  - 公式：`adh(r) = ∏_{x∈X(Zr)} 1[vx(r) = adherent]`；
  - 遵循率：`α̂_adh = (1/|Ra|) Σ_{r∈Ra} adh(r)`。
- **配置级 complier 效应（CACE）**：
  - `CACE := ITT / α̂_adh = ΔPass@1 / α̂_adh`；
  - 在均值排除假设（δ0=0）下，ITT/α_adh 识别目标 Team 配置相对于 Single 的 complier 效应；
  - 论文明确区分 Wald 比率与 CACE，并给出敏感性界限：`ITT/α_adh − CACE = ((1−α_adh)/α_adh)·δ0`。
- **成本指标**：组织开销（Overhead₀，对 Ar=0 运行测量额外成本）与工作量均衡（基于归一化 Shannon 熵）。

## 3. 实验设计

- **数据集 / 基准**：
  - **SWE-bench Pro**：193 个任务（跨 harness 对比），36 个随机任务（Adherence 实验）；
  - **Terminal-Bench 2.1**：89 个任务；
  - **DeepSWE**：113 个任务。
- **对比方法（跨 harness）**：Mini-SWE-agent、Codex CLI、Claude Code、OpenCollab (Base)、OpenCollab (Duo)。
- **使用模型**：DeepSeek-V4.1-Flash、Qwen3.8-Flash、GPT-5.6-Luna（跨 harness 对比统一使用 GPT-5.6-Luna）。
- **实验类型**：
  - **Adherence 实验**：12 种配置（Star / Ring 两种拓扑，单维度扰动模型、工具、预算、上下文、拓扑），每种在相同 36 个 SWE-bench Pro 任务上各跑一次；
  - **跨 harness 系统级性能对比**：5 个 harness × 3 个 benchmark；
  - **Duo–Single 配对对比**：按任务配对，使用精确双尾符号检验；
  - **运行轨迹诊断**：选取三例运行（Read-only 成功委派、参考团队未解决、交叉评审选错 commit）进行事件流追踪分析。
- **评分方式**：SWE-bench Pro 与 DeepSWE 按 fail-to-pass 与 pass-to-pass 测试判定；Terminal-Bench 2.1 由任务自身 verifier 判定 reward=1。
- **网络与泄漏处理**：Terminal-Bench 2.1 按任务 allow_internet 标志控制；发现 10 次生成尝试获得答案泄露材料，相关通过结果被撤回或重跑。

## 6. 主要结论与发现

- **协作幻觉普遍存在**：未约束默认配置下 Adherence 仅 47.2%，主智能体常垄断预算、绕过队友；改变任一单维度可将 Adherence 从 47.2% 提升至 97.2%。
- **约束反而促进协作**：限制工具边界（如 Read-only）、强制上下文卡、Ring 拓扑等约束显著提升 Adherence，说明实际协作是可系统控制的。
- **系统级性能**：OpenCollab (Duo) 在三个 benchmark 上均取得最高 Pass@1：
  - SWE-bench Pro：64.25%；
  - Terminal-Bench 2.1：83.15%；
  - DeepSWE：69.91%。
- **单智能体 token 效率最优**：OpenCollab (Base) 在所有三个 benchmark 上使用最少 token 与最低成本；Duo 成本仍低于 Claude Code。
- **协作收益**：Duo 相比 Base 在 Terminal-Bench 2.1 提升 +3.4 分，在 DeepSWE 提升 +14.2 分（配对符号检验 p=0.0025）。
- **CACE 解读需谨慎**：低 Adherence 下 Wald 比率会因 Ar=0 层的对比而偏离真实 complier 效应；论文通过记录每轮 Ar 使该对比可被计算而非仅假设。
- **主流框架审计**：审计的十个主流智能体框架中，没有一个能同时满足七项受控评估条件，也没有一个能对每个运行的组织计算 Adherence。

## 7. 优点

- **概念创新**：明确提出“协作幻觉”问题，并将 Adherence 形式化为可计算指标，弥补了多智能体评估中“只报结果、不验过程”的空白。
- **系统架构清晰**：编排层与执行层解耦，共享运行时保证跨配置的单位一致性，降低复现成本（24k 行 → 239 行）。
- **因果识别严谨**：引入 CACE、ITT、Wald 比率、均值排除假设与敏感性界限，将组织效应从基础设施噪声中分离，并给出可操作的报告要求。
- **事件流设计**：结构化、只追加、带角色归因的事件流，支持自动化审计与资源归因，优于面向人类调试的散文日志。
- **实验对照严谨**：配对任务对比、符号检验、对答案泄露的主动排查与撤回、单智能体重跑稳定性测量。
- **开源与可复现**：提供项目页面与代码，团队文件、工具注册表、运行记录等均有明确规范。

## 8. 不足与局限

- **实验覆盖有限**：
  - 仅三个模型快照，无法估计模型间的一般性规律；
  - Adherence 实验仅 36 个任务，样本量偏小；
  - 仅评估编码类任务，未涉及其他软件工程或非编码场景。
- **并发限制**：团队共享一把锁，任一时刻只有一个智能体运行；依赖真正并行工作的组织形态不在测量范围内。
- **工作流单一**：Duo 只是一种任务分解方式，不同脚本可能同样忠实地实现不同组织并产生不同性能。
- **未验证运行的处理**：被 token 预算或 wall-clock 截断的运行计为 Ar=0，可能低估 Adherence；论文虽给出敏感性区间，但未完全解决。
- **均值排除假设**：CACE 的因果解读依赖均值排除假设，论文仅能提供证据而非证明；低 Adherence 下 Wald 比率与真实 complier 效应偏差较大。
- **成本指标未报告**：组织开销与工作量均衡两个成本指标在正文实验中未报告。
- **硬件算力信息缺失**：未提供 GPU 型号、数量或训练时长等算力细节，不利于资源成本评估。
- **闭源对比限制**：Claude Code 为闭源，其审计仅基于厂商文档，可能影响对比公平性。

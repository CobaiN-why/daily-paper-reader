## 摘要
编码智能体通过动作序列解决仓库级任务，其中单个错误动作可能误导后续决策并增加恢复成本。现有方法利用执行反馈进行恢复，或使用专门检查来阻止错误，但在执行前判断干预是否有利于最终任务完成仍然具有挑战性。为解决这一挑战，我们提出 HiSentinel，一个事后蒸馏框架，训练轻量级的 0.6B 和 1.7B 哨兵模型来选择执行前干预，旨在提升任务完成度，而非纠正每一个不完美动作。一个特权教师模型利用记录的执行结果作为干预判断的证据，这些判断被蒸馏到一个因果学生模型中，后者仅接收动作前上下文和提议动作。除了识别是否以及何时干预之外，哨兵还必须提供可操作的反馈，帮助编码智能体恢复或获取必要的人类输入。为支持这些能力，我们引入 SWE-Intervene，一个由软件工程轨迹构建的动作级数据集，标注了一个动作应被允许、自主重定向，还是暂停以寻求人工协助，并附有相应的干预反馈。在 SWE-bench Verified Mini 和 Ask or Assume 上，HiSentinel 在不同规模的哨兵和编码智能体系列中持续提升任务完成度，分别最高提升 14% 和 10%，同时保持有竞争力的 token 消耗。这些结果表明，轻量级执行前干预能够有效防止错误传播，并提高自主编码智能体的可靠性。

## Abstract
Coding agents solve repository-level tasks through sequences of actions, where a single erroneous action can misdirect subsequent decisions and increase recovery costs. Existing approaches use execution feedback for recovery or specialized checks to block errors, but deciding before execution whether intervention will benefit eventual task completion remains challenging. To address this challenge, we propose HiSentinel, a hindsight-distillation framework that trains lightweight 0.6B and 1.7B sentinels to select pre-execution interventions aimed at improving task completion rather than correcting every imperfect action. A privileged teacher uses recorded execution outcomes as evidence for intervention judgments, which are distilled into a causal student that receives only the pre-action context and proposed action. Beyond identifying whether and when to intervene, the sentinel must also provide actionable feedback that helps the coding agent recover or obtain necessary human input. To support these capabilities, we introduce SWE-Intervene, an action-level dataset constructed from software-engineering trajectories that annotates whether an action should be allowed, autonomously redirected, or paused for human assistance, together with corresponding intervention feedback. Across SWE-bench Verified Mini and Ask or Assume, HiSentinel consistently improves task completion across Sentinel scales and coding-agent families, with gains of up to 14% and 10%, respectively, while maintaining competitive token consumption. These results demonstrate that lightweight pre-execution intervention can effectively prevent error propagation and improve the reliability of autonomous coding agents.

# HiSentinel 论文总结：面向编码智能体的执行前干预哨兵

## 1. 核心问题与整体含义

- **背景**：LLM 编码智能体通过多步"动作—观察"循环解决仓库级软件工程任务（浏览代码库、编辑文件、执行命令、运行测试）。由于是长程序列决策，一个错误动作会改变环境状态、误导后续决策，并逐步累积为失败修复、冗余探索乃至任务失败。
- **问题的隐蔽性**：早期错误往往潜伏数步才显现，此时恢复成本已极高甚至不可逆。论文引用 Terminal-Bench 证据：在 1,184 条失败的 CLI 智能体轨迹中，半数在第 7 步左右犯下决定性错误，约第 12 步进入不可恢复状态，而首个可观察失败直到第 16 步才出现；前缀监控只能在锁定前发现 3.7%–8.7% 的失败。
- **现有方法的缺口**：
  - 过程批评器（process critic）只回顾最近若干步并周期性给反馈 → 反馈到达时有害动作已经执行；
  - 轨迹诊断（trajectory diagnosis）可在运行后定位决定性错误 → 属事后分析，无法预防；
  - 专用检查器用于拦截错误 → 通常针对局部正确性，而非"干预是否真正有利于最终任务完成"。
- **核心问题**：在智能体提出动作之后、环境执行之前这一"边界时刻"，如何判断干预是否值得做？此时执行结果这一最直接的证据天然不可得，构成根本性的信息鸿沟。
- **整体含义**：论文将执行前干预形式化为三分类决策——**ALLOW（放行）/ REDIRECT（自主改道）/ HARD-PAUSE（暂停求助）**，目标是提升**最终任务完成率**，而不是纠正每一个局部不完美动作。作者主张把干预"提前"，以阻止有害动作改变环境，而非事后补救。

## 2. 方法论

### 2.1 问题形式化

- 智能体在任务 `u` 下逐步行动；第 t 步观察到轨迹前缀 `h_t`，提出动作 `a_t`。哨兵在动作执行前评估 `x_t = (u, h_t, a_t)`，输出干预路径 `ŷ_t`，必要时附带反馈 `r_t`。
- 三种路径的运行时语义：
  - **ALLOW**：无充分证据表明干预能改善完成度，原动作原样执行，`r_t = ∅`；
  - **REDIRECT**：扣留原动作，给出纠正性反馈，智能体据此重新提出动作；
  - **HARD-PAUSE**：暂停执行，向人类请求缺失的信息、授权或偏好，直到回答返回。
- 标签由事后证据 `e_t`（记录的后续轨迹、任务结局、观察到的人机交互）决定：`y_t = A(x_t, e_t) ∈ {ALLOW, REDIRECT, HARD-PAUSE}`。注意：这是**事后知情判断**，而非在备选路径间实测的因果差异（每条日志只揭示其实际发生的那一条续写）。
- 部署时既无 `e_t` 也无未来观测，哨兵只学习 `p_θ(y_t | x_t)`。

### 2.2 事后引导的干预蒸馏（HGID）

- **核心思想**：训练期用一个"看到未来"的特权教师（privileged teacher）产生干预监督信号，蒸馏到只接收动作前上下文的因果学生。
- **教师-学生不对称**：
  - 教师输入 `(x_t, f_t)`（含记录的后续），输出二分类 `b_t`：`ALLOW` 或 `INTERVENE`（`REDIRECT` 与 `HARD-PAUSE` 合并）；
  - 学生保留三分类输出空间，并在包含 AUQ（AskUserQuestion）样本的完整数据集上训练。
- **关键设计**：
  - **生成式分类**：路径通过原生语言建模头生成（如 `ALLOW`/`REDIRECT`/`HARD-PAUSE` 作为 token），而非独立分类头，使生成路径可作为后续反馈生成的"前缀"。
  - **有用性门控（helpfulness gate）**：只有当未来感知教师的二分类预测正确、且其置信度高于"去掉结果证据的对照视图"时，才对样本启用蒸馏，防止无信息量的教师预测主导

## ABSTRACT 

As AI agents increasingly tackle complex repository-level coding tasks, distribut-ing work across multiple agents is a natural way to scale beyond the capabilities of a single agent. To coordinate their interdependent work, these agents share findings and agree on interfaces between modules. However, exchanged infor-mation often serves only as context, leaving individual agents to interpret it and incorporate it into subsequent work. Consequently, shared findings may go un-used and deviations from interface agreements may go undetected, undermining the reliability and efficiency of collaboration. This motivates moving part of the coordination responsibility from individual agents to the execution harness. To make shared information actionable during execution, we introduce the Artifact-Exclusive Communication Protocol (AECP). AECP requires agents to commu-nicate exclusively through structured artifacts and specifies how the harness pro-cesses them. The harness supplies findings when agents access relevant code, screens implementations for mismatches with recorded interface commitments, and requires affected agents to revisit revised agreements. These coordination steps become part of harness execution rather than actions that agents must initi-ate from prior messages. Across Doc2Repo, NL2Repo, and CodeProjectEval, us-ing closed- and open-source models including Opus-4.8 and DeepSeek-V4-Flash, AECP improves average test pass rate by 28.2% and reduces average wall time by 16.5% relative to an agent team using free-form inter-agent messages. Artifact-exclusive communication also blocks the relay of malicious instructions between agents, reducing how often they reach other agents from 95% to 0% and how often those agents act on them from 40% to 0%. 

## 1 INTRODUCTION 

LLM-based coding agents (Yang et al., 2024; Xia et al., 2024) increasingly tackle software en-gineering tasks ranging from localized bug fixes to repository-level development (Jimenez et al., 2024; Ding et al., 2025; Chen et al., 2026). As these tasks grow in scope, single agents face a greater context burden and longer completion times. Decomposing and assigning subtasks to multi-ple agents can reduce this burden and enable parallel execution (Zhang et al., 2026; OpenAI, 2026; Anthropic, 2026e;a). This division of work, however, leaves knowledge and implementation deci-sions distributed across separate agent contexts, even though the subtasks remain interdependent. Agents therefore need to share knowledge and align implementation decisions to avoid duplicated exploration and incompatible implementations (Cemri et al., 2025; Khatua et al., 2026). Existing multi-agent coding systems coordinate either centrally, where a main agent or a predefined role sequence assigns bounded subtasks and integrates the results (Hong et al., 2024; Qian et al., 2024; Zhang et al., 2026; OpenAI, 2026; Anthropic, 2026e; Geng & Neubig, 2026; Benkovich & Valkov, 2026), or among peers, where teammates own separate workstreams and communicate di-rectly (Wu et al., 2024; Anthropic, 2026a). In both cases, an agent decides what to do with exchanged information: the coordinator reads returned summaries, and teammates read each other’s messages. Khatua et al. (2026) observe that agents spend up to a fifth of their steps communicating, yet communication does not improve overall task success. Their failure analysis identifies difficul-ties in integrating communicated information and honoring commitments, while broader analyses also report ignored peer messages and missing or incomplete verification (Cemri et al., 2025). These findings highlight a gap between exchanging information and reliably using it to guide and check subsequent implementation. To bridge this gap, the execution harness can participate directly in coordination, using exchanged information to guide and check agents’ work. We introduce the Artifact-Exclusive Communication Protocol (AECP), in which agents communicate exclusively through structured artifacts. Every coordination exchange is thus mediated by the execution harness. As shown in Figure 1 (b), guiding agents with shared findings and checking their implementations against agreements become actions that the harness carries out under the protocol’s rules, reducing reliance on agents to initiate them from prior messages. To identify where such coordination support could reduce development overhead, we analyze multi-agent coding trajectories across all tasks in NL2Repo (Ding et al., 2025). As shown in Figure 1 (c), repeated exploration accounts for 26.8% of token usage, while rework caused by incompatible de-cisions at module boundaries accounts for another 22.2%. These observations motivate two com-plementary forms of support: knowledge reuse across subtasks and consistency checks between in-terdependent implementations. AECP provides a Knowledge Artifact through which agents record findings for the harness to supply during subsequent work, helping other agents build on prior explo-ration. A Contract Artifact records interface agreements with conditions that the harness can check against implementations, helping detect incompatibilities during development. We evaluate AECP on repository construction, where agents build a repository from documentation or natural-language requirements in an empty workspace, using Doc2Repo (Chen et al., 2026), CodeProjectEval (Zhao et al., 2025), and NL2Repo (Ding et al., 2025). Averaged across models and benchmarks, AECP improves test pass rate by 10.6% over a single agent, and by 28.2% and 8.5% over agent teams that use free-form messages (Wu et al., 2024) or centralized integration (Geng & Neubig, 2026), while reducing wall time by 16.5% and 24.9% relative to these teams. Artifact-exclusive communication also blocks the relay of malicious instructions from a compromised agent, reducing how often they reach other agents from 95% to 0% and how often they are acted on from 40% to 0%. 

## 2 BACKGROUND AND RELATED WORK 

2.1 MULTI -AGENT CODING SYSTEMS 

Coding agents extend the reason–act–observe loop (Yao et al., 2023) to repository navigation, file editing, code execution, and testing (Yang et al., 2024). Within this loop, the LLM selects actions, while the surrounding software layer, or harness , executes them, returns observations, and manages workspaces and execution state. Growing context and sequential execution costs motivate distribut-ing work across agents, either by delegating subtasks from a main agent (OpenAI, 2026; Anthropic, 2026e; Zhang et al., 2026; Geng & Neubig, 2026; Benkovich & Valkov, 2026) or by forming teams 2AECP: Artifact-Exclusive Communication Protocol for Multi-Agent Code Generation whose members coordinate among themselves (Qian et al., 2024; Hong et al., 2024; Anthropic, 2026a); Appendix A describes both patterns. In both cases, what agents exchange passes through the harness, and keeping the work coherent depends on what is done with it afterwards. 2.2 COORDINATION CHALLENGES 

Agents that work with separate contexts face coordination challenges (Khatua et al., 2026; Cemri et al., 2025). CooperBench (Khatua et al., 2026) identifies three recurring causes of coordination failure: (i) expectation failures, where an agent does not incorporate a partner’s communicated plans or changes into its implementation; (ii) commitment failures, where an agent does not implement promised changes while its partner assumes they are in place; and (iii) communication failures, where agents never establish the shared information a joint decision requires. The first two share one gap: communication has occurred, but subsequent actions remain inconsistent with it. AECP targets this gap by supporting recipients’ use of shared knowledge and checking producers’ imple-mentations against recorded commitments. 2.3 COORDINATION SUPPORT FOR CODING AGENTS 

Prior work on coordinating coding agents falls into three groups. (i) Shared information. Agent Context Protocols (Bhardwaj et al., 2025) and AgentRoom (Cho & Lee, 2026) keep messages, task records, and workspace state accessible to all agents. A stored finding, however, still reaches a worker only if that worker recognizes its relevance when it later works on the corresponding code. AECP instead delivers the finding when the worker accesses that code. (ii) Contracts and checks. 

Keeping interdependent modules compatible requires detecting when an implementation departs from its agreed interface and ensuring that dependent workers notice when the agreement changes. SEMAP (Mao et al., 2025) specifies what each agent receives and produces, which leaves no module interface against which code can be checked, and Sartori (2026) compare implementations only after both are written, when incompatible assumptions have already been built on. In concurrent work, CodeTeam (Wang et al., 2026) and Contract-Coding (Lin et al., 2026) share interface contracts dur-ing parallel generation, but CodeTeam detects deviations only where QA tests exercise the affected calls, and Contract-Coding merges contract updates only after all agents in a layer have finished, so a revision reaches dependent workers after they have completed their modules. AECP checks each submission against the latest agreement and requires dependent workers to read a revision be-fore they complete. (iii) Harness and pipeline designs. Recent work surveys or formalizes harness responsibilities (Ning et al., 2026; Zhong & Zhu, 2026), gates code changes on sandboxed execu-tion (Kumar et al., 2026), or searches over harness designs (Liu et al., 2026), while pipeline systems such as CodeS (Zan et al., 2026) pass artifacts from one stage to the next. AECP instead specifies the rules by which a harness coordinates agents working in parallel: scope-triggered knowledge delivery, contract checks, and stale-consumer synchronization. Appendix A discusses more details. 

## 3 METHODOLOGY 

AECP follows the leader–worker workflow in Figure 2. In Figure 2 (a), a leader agent prepares parallel execution by translating the project specification into a module plan describing module responsibilities, public symbols, and dependencies. The harness represents this plan as a dependency graph, from which the leader determines how many workers to use and which module groups each one owns. Each module has one owner, while dependencies across workers identify modules whose implementations require coordination. The workers in Figure 2 (b) then explore, implement, and test their modules in parallel, and they coordinate at two points. During exploration, a worker may discover a finding that becomes useful when another worker later accesses the same code. With message-based communication, the re-cipient must connect this earlier information to its current work. AECP instead has workers record such findings as scope-linked Knowledge Artifacts , which the harness in Figure 2 (c) retrieves and supplies when matching code is accessed. During implementation, workers building interdependent modules rely on shared interfaces, but communicating an agreement does not ensure that imple-mentations conform to it. Witness checks and retraction. A finding that holds when recorded may become outdated as the code or execution environment changes. AECP therefore supports checking findings before circulation and rechecking them when consumers question their continued validity. The harness executes any attached witness and records the outcome in z, marking the artifact as witness-checked if the witness passes and rejecting publication if it is refuted. Artifacts without a witness, or whose checks cannot complete because setup is unavailable, remain unchecked and eligible for retrieval. Each delivered finding carries its witness state, so recipients can tell witness-checked findings from unchecked ones. If a consumer later flags a stored claim with an attached witness, the harness reruns the check and excludes refuted artifacts from subsequent delivery while retaining an audit record. As with a message, the correctness of an unchecked finding rests with its producer and recipient; AECP adds a witness state to each delivery, and scope-triggered retrieval places a finding next to the code it concerns, where the recipient can check the claim directly. Appendix C.1 provides a complete artifact and the detailed witness and retrieval rules. 3.2 CONTRACT SHARING 

Exchanging an interface agreement does not by itself keep implementations compatible with it. 

Contract Sharing therefore records agreements as shared artifacts that the harness uses to expose declared interfaces, screen implementations for static mismatches, and require consumers to revisit revised agreements. 

Shared interfaces for parallel development. To implement a dependent module before its producer finishes, a consumer needs to know what interface it can rely on. On the left of Figure 4, Worker A declares the interface of Thing in a Contract Artifact. The declaration records the symbol’s name and kind under identity I, how it is constructed or called under usage U , and its return structure or exposed attributes under observable interface O. These declarations give consumers a shared reference for developing their modules while the producer’s implementation is still in progress. The harness validates the contract and generates stubs. These are placeholder modules that expose the declared symbols and signatures without implementing their behavior. As shown in the center of Figure 4, Workers B and C can then import the declared interface and implement their dependent modules in parallel with Worker A. The stubs occupy the final module paths, so consumers retain the same imports when the producer replaces them with its implementation. 

Detecting interface mismatches. An interface declaration gives consumers a basis for develop-ment, but the producer’s completed code may still depart from it. The verifier on the right of Figure 4 therefore compares each submitted module with its latest Contract Artifact. It parses the source into an abstract syntax tree and checks declared symbols, signatures, statically recoverable types and shapes, and residual stubs without executing the code. A provable mismatch causes the harness to reject the submission and report the violated symbol and constraint, allowing the producer to repair the implementation or revise the agreement. The verifier thus acts as a fast screen that catches signa-ture, attribute, and residual-stub mismatches before integration; Appendix D details the properties it checks. 

Keeping consumers aligned with revisions. An interface may change as development progresses, while consumers continue relying on an earlier version. Updating the producer’s contract alone does not ensure that those consumers revisit their assumptions. To identify affected workers, consumers register the symbols they depend on with the harness during development. ## 4 EXPERIMENTAL SETUP 

4.1 MODELS AND AGENT SCAFFOLDING 

Our experiments are conducted on the AWS Strands Agents SDK (AWS, 2025) and mini-SWE-agent (SWE-agent Team, 2025) with Claude Opus 4.8 (Anthropic, 2026c), Claude Opus 4.6 (An-thropic, 2026b), Claude Sonnet 5 (Anthropic, 2026d), DeepSeek-V4-Flash (Xu et al., 2026), and GLM-5.2 (Zeng et al., 2026). The Claude models are accessed through Amazon Bedrock, whereas DeepSeek-V4-Flash and GLM-5.2 are served through OpenRouter. Appendix F lists turn limits, timeouts, and sampling settings. 4.2 BENCHMARKS 

We evaluate on three Python benchmarks that require building a repository from a textual specifica-tion in an empty workspace and assess the generated code with executable tests. Doc2Repo (Chen et al., 2026) contains 50 specifications derived from GitHub repositories, averaging 26.8 files and 3,528 lines of reference code, and uses adapted repository-level tests. CodeProjectEval (Zhao et al., 2025) contains 18 projects from open-source libraries, averaging 11.9 files and 2,371 lines of ref-erence code, and uses project-level tests. NL2Repo (Ding et al., 2025) contains 104 library tasks across nine domains and uses hidden tests from the original repositories. 6AECP: Artifact-Exclusive Communication Protocol for Multi-Agent Code Generation 4.3 BASELINES 

We compare AECP with three baselines. Single uses one model to construct the entire repository without inter-agent coordination. Team-Freedom uses the same leader-worker scaffold as AECP but allows workers to exchange unrestricted free-form messages, reflecting the message-based co-ordination used in systems such as AutoGPT (Significant Gravitas, 2023) and AutoGen (Wu et al., 2024). Team-Integrator runs workers in isolated worktrees without access to peers’ in-progress code, while a central manager integrates their completed implementations through sequential, test-gated merges, following CAID (Geng & Neubig, 2026). Team-Freedom and AECP workers instead share one workspace. Team-Freedom and AECP therefore differ only in the coordination protocol, free-form messages or AECP’s artifacts together with the harness actions defined on them, making 

Team-Freedom the controlled comparison for AECP as a whole; Team-Integrator represents an al-ternative design that isolates workers and centralizes integration. For each task, we generate a plan once and reuse the same module plan, dependency graph, module-to-worker assignment, and a fixed worker count of N = 3 across all multi-agent configurations, and Single runs the same planning step with the same prompt before implementing every module itself. We hold the coding tools, ex-ecution environment, and task inputs fixed, while varying how workers exchange information and integrate their implementations. We thus compare coordination protocols within one scaffold rather than complete systems, so that differences reflect how workers coordinate.

## 6 CONCLUSION 

We introduced AECP, a protocol that replaces free-form inter-agent messages with Knowledge and Contract Artifacts on which the execution harness acts. Knowledge Artifacts supply prior findings at the point of use, while Contract Artifacts make interface commitments available during parallel implementation and screen completed code for static mismatches with them. Across Doc2Repo, NL2Repo, and CodeProjectEval, AECP raises average code quality over all three baselines, shortens runtime relative to the two team baselines, and transfers across different agent scaffolds. Artifact-exclusive communication also blocked every malicious instruction relayed as a message in our attack cases. Simple tasks often favor fewer agents. Overall, AECP makes coordination explicit and checkable, so parallel agents need not rely solely on natural-language promises. REPRODUCIBILITY STATEMENT

## A RELATED WORK 

Shared context and structured communication help agents exchange information across tasks. Agent Context Protocols combine standardized messages with persistent execution blueprints that record dependencies and intermediate outputs (Bhardwaj et al., 2025). AgentRoom supports concurrent coding through a shared workspace with tools for claiming files, inspecting peer status, and ex-changing messages (Cho & Lee, 2026). These mechanisms make information and collaborators’ progress accessible. Making a finding available, however, does not by itself connect it to a later code access where it becomes relevant. A worker may still need to recognize that an earlier discov-ery applies to its current work. AECP makes this connection explicit by associating findings with code scopes and delivering them when workers access matching code. Contracts and verification address a complementary problem of keeping independently produced work consistent. SEMAP specifies the input and output artifacts required by each agent role and 13 AECP: Artifact-Exclusive Communication Protocol for Multi-Agent Code Generation uses verification outcomes to govern workflow transitions (Mao et al., 2025). Its behavioral con-tracts define agent responsibilities, leaving the interfaces promised to dependent code as a separate verification target. The Specification Gap examines incompatible assumptions in independently gen-erated code and introduces an AST-based detector for conflicts between implementations (Sartori, 2026). AECP checks a different relationship, comparing each submitted implementation with the interface commitments on which its consumers rely. Those commitments can also change during development, so checking the producer alone is insufficient to keep consumers informed. AECP therefore tracks registered symbol dependencies and requires affected consumers to read revised contracts and renew their registrations before completing their tasks. Other systems pass structured intermediate artifacts along a fixed pipeline. CodeS (Zan et al., 2026) builds a repository through successive sketches of its directory structure, files, and functions, and AutoP2C (Lin et al., 2025) generates repositories from papers through blueprint extraction, decom-position, and debugging stages. AgentMesh (Khanzadeh, 2025), DocAgent (Yang et al., 2025), MapCoder (Islam et al., 2024), and MAGIS (Tao et al., 2024) route work through planner, coder, re-viewer, or verifier roles, while CodeAgent (Zhang et al., 2024) equips a single agent with repository tools. Code2MCP (Ouyang et al., 2026) transforms existing repositories into Model Context Pro-tocol services through a multi-stage workflow with a run-review-fix loop, and CompileAgent (Hu et al., 2025) compiles real-world repositories with a tool-integrated agent that searches for build in-structions and resolves errors. Each artifact is consumed by the next agent in the pipeline, whereas AECP’s artifacts are acted on by the harness while workers run in parallel. RepoGenesis (Peng et al., 2026) extends repository-generation evaluation to multilingual microservices with deployment and API-coverage measures. In concurrent work, CodeTeam combines structured design contracts, dependency-aware develop-ment, and Git-based interface update propagation for repository-level code generation (Wang et al., 2026). Because it identifies interface mismatches through QA tests, deviations from declared inter-faces can go undetected when those tests do not cover the affected calls. Also concurrent, Contract-Coding projects user intent into a language contract that serves as a single source of truth for parallel module generation, audits the workspace against the contract’s signatures, and updates the contract as execution proceeds (Lin et al., 2026). AECP shares this contract-first structure. It differs in exposing each declared interface as importable stubs at the final module paths, tracking which con-sumers depend on which symbols, and keeping those consumers from completing after a revision until they have read it. Its Knowledge Artifacts also carry findings that fall outside any interface, such as environment and runtime behavior. Recent work also treats the harness as the substrate of agent behavior. Ning et al. (2026) and Zhong & Zhu (2026) survey or formalize its responsibilities, AgentForge requires code changes to pass sandboxed execution before they propagate (Kumar et al., 2026), and Liu et al. (2026) search over harness designs that include the coordination protocol. AECP instead specifies the rules by which a harness coordinates multiple agents, namely scope-triggered knowledge delivery, contract checks, and stale-consumer synchronization. Following the terminology used by Anthropic (2026a), we distinguish two broad patterns by where coordination primarily resides, subagent delegation and agent teams . In subagent delegation , a main agent assigns tasks to sub-agents in isolated contexts and directs subsequent work from their returned results, as Figure 6 (a) shows. Codex (OpenAI, 2026) and Claude Code (Anthropic, 2026e) provide this as a built-in facility, and FastContext (Zhang et al., 2026) uses it to delegate repository exploration and return compact evidence. Manager-based systems such as CAID (Geng & Neubig, 2026) and Agyn (Benkovich & Valkov, 2026) extend the pattern to implementation, centralizing task delegation and integration in a manager. In agent teams , teammates hold separate parts of the work and coordinate among themselves, as Figure 6 (b) shows. These interactions may follow pre-defined workflows, as in ChatDev’s role-based dialogues and MetaGPT’s structured development pipelines (Qian et al., 2024; Hong et al., 2024). Witness decision rules. At publication, the harness first checks that the witness contains only permitted shape-level operations, such as imports, calls, construction, and attribute checks. A mal-formed witness is rejected before storage. A valid witness is then executed in the workspace and prints KG:REACHED before its assertion. A zero exit marks the artifact WITNESS -CHECKED ; a fail-ure after the marker refutes the witness and rejects the publication; and a failure before the marker indicates that setup did not complete, so the artifact is stored as UNCHECKED . An artifact without a witness is likewise UNCHECKED . If a consumer later flags a stored artifact, the harness reruns its witness, removes a refuted artifact from subsequent retrieval and delivery, and retains the outcome in its audit record. 

Scope-triggered retrieval rules. The harness derives a worker’s current scope whenever it ac-cesses a code file or symbol. It first matches artifacts bound to that symbol or file and then considers artifacts associated with enclosing directories or named global scopes. Refuted artifacts are ex-cluded. Matching artifacts are inserted into the observation returned by the code-access operation, so retrieval occurs at the point of use rather than through a separate inter-agent message. The har-ness additionally forwards each new finding to workers owning related modules, ranking the same file above modules connected to it in the planned dependency graph and those above modules in the same package. Each lookup delivers at most five artifacts and each forward at most four, newest first; a worker that re-reads a file receives only artifacts it has not already seen; and every delivered artifact is labeled with its witness state. A scope matches the current access when one path contains the other or the two share a path segment, and each delivered artifact is truncated to 280 charac-ters. A single access therefore adds at most five truncated artifacts, about 1,400 characters, to the returned observation. A symbol scope is matched through the file that defines it, so matching ulti-mately operates on file paths rather than resolved names, and aliases and re-exports do not affect it: a finding is delivered when a worker reads a file that its tags cover. Conflicting findings are resolved through flags: when a consumer flags a claim that contradicts what it observes, the harness reruns the witness and stops delivering the claim if the witness refutes it. In the Opus-4.6 NL2Repo AECP runs, a task receives 41.9 knowledge deliveries on average; judged from the traces by an LLM, 36% 

of the delivered findings are used in the recipient’s subsequent work. Of the delivered findings, 71% 

are witness-checked, and they account for 88% of the findings used. Witness execution rejects 14% 

of publication attempts before they enter circulation, and consumers flag 0.9 findings per task on average, 0.2 of which are retracted after the witness is rerun.

At completion, the checker receives the latest Contract Artifact and the producer’s Python source. It parses the source into an abstract syntax tree and does not import the module, execute its code, or invoke an LLM. It checks interface shape rather than functional behavior. For each declared symbol, the checker considers the following constraints: • the source parses and the declared symbol exists with the stated kind; • declared positional and keyword-only parameters match the implementation; • parameter and return annotations agree when both are available; • literal return statements do not contradict the declared return type or mapping keys; • a shared class exposes its declared attributes through class members, methods, self as-signments in init , or slots ; and • no declared function or method remains a generated NotImplementedError stub. Mapping-shaped shared types are excluded from the attribute check because their keys belong to instance contents rather than class attributes. Each remaining comparison has three outcomes. A 

failure means that the source proves a mismatch. A pass records a completed comparison with no mismatch. An abstention records that the property cannot be decided statically, as with an inherited constructor or a return value built by another function; such properties are left to the workers’ tests. ## F RUN CONFIGURATION 

Each agent runs for at most 150 turns with a sliding context window of 300 messages. Individual shell commands time out after 300 seconds, and scoring times out after 1,200 seconds for Opus-4.8 and 2,400 seconds for the other models. Model calls use each provider’s default sampling tempera-ture with client-side adaptive retries. Reported wall time and token counts include planning. All four configurations of a setting run concurrently on the same host against the same endpoint, so service latency affects them alike. 

## G TRACE ANALYSIS FOR FIGURE 1

We analyze trajectories of an agent team that coordinates through natural-language messages, run with Opus-4.6 on all 104 NL2Repo tasks. An LLM (Opus 5) reads each complete multi-agent trajec-tory and labels every agent turn with one primary activity: Explore (searching, reading files, tracing dependencies, or otherwise acquiring information), Implement (creating or modifying code), Test 

(running or inspecting validation), or Other (planning, coordination messages, and status updates). It marks an Explore turn as repeated exploration only when another agent had earlier obtained in-formation sufficient for the same need and the later turn reproduces rather than extends that work; re-inspection after the code changed, or to verify an earlier finding, is excluded. It marks an Im-plement turn as conflict-driven rework only when already-written code is revised because decisions in different modules or by different agents are incompatible, such as mismatched signatures, return types, or data structures; a test failure alone is not sufficient. Each flagged turn must cite the earlier turns that establish the information or the conflicting decision, and uncertain cases are labeled neg-ative. Token and turn shares follow from these labels. We manually checked 50 flagged events and confirmed all of them.

## I ATTACK PAYLOADS 

The five payload families request safeguard disabling, validation bypass, input passthrough, a local trace sink, or a hidden keyword argument. Each presents the requested change as a cross-module compatibility requirement and asks the compromised worker to relay it to teammates. None uses a network endpoint. These cases evaluate propagation after an initial worker compromise, rather than the likelihood of that compromise. All attack cases ran in isolated containers without network access, and the generated repositories were discarded after scoring.

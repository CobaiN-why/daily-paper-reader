Abstract 

Code large language model (Code LLM) assistants generate code from heterogeneous development contexts, including open files, imported modules, pasted snippets, and comments, much of which may originate from untrusted sources. We investigate whether insecure instructions embedded in such contexts can steer Code LLMs toward vulnerable code without access to model weights or training data. We evaluate ten open-weight Code LLMs spanning 3B–13B parameters, including four base and six instruction-tuned models, across ten web-application weakness classes. We compare completion tasks containing insecure instructions embedded as code comments with benign tasks without malicious instructions. Attack-condition completions contained a medium-or-higher weakness in 

77.4–92.3 % of cases, compared with 1.7–5.1 % in the benign condition. Base and instruction-tuned models averaged 86.5% and 84.5% vulnerable outputs, respectively; equivalence testing and three matched model pairs indicated reductions of at most 8.1% after instruction tuning. Susceptibility showed no clear association with model scale or specialization. Among vulnerable attack outputs, 86.2–91.0% were rated high or critical, and the effect persisted without the pattern-based detector. Post-generation screening reduced but did not eliminate the risk, the strongest screen leaving roughly one-third undetected. These findings identify inference-time context injection as a substantial attack surface and motivate provenance-aware training objectives. 

Keywords: Code large language models, prompt injection, context injection, insecure code generation, software security, LLM security. 

## 1 Introduction 

Code-generation assistants produce suggestions by conditioning on a heterogeneous development context that may include open files, imported modules, pasted snippets, retrieved examples, and natural-language comments. Although these inputs appear within a common context window, they do not necessarily share the same provenance or level of trust. In particular, substantial portions of the context may originate outside the developer’s control, for example from online forums, third-party dependencies, shared repositories, or outputs generated by other models. The security risks associated with incorporating externally sourced code into software projects predate large language models (LLMs) [Acar et al., 2016, Fischer et al., 2017]. Code LLMs introduce an additional concern: externally sourced content can contain not only insecure code, but also natural-language directives that the model may interpret as instructions for generating new code. This concern arises from the absence of a reliable provenance-aware instruction boundary within the model’s context. Unless provenance is explicitly represented and enforced, a directive written by the developer and a directive embedded in externally sourced content are presented to the model through the same input channel. Prior work has identified the inability to distinguish trusted instructions from untrusted data as a central cause of prompt-injection vulnerabilities in general-purpose LLM systems [Wallace et al., 2024, Zverev et al., 2024]. We 1arXiv:2610.05139v1 [cs.LG] 4 Oct 2026 study the corresponding failure mode in code generation, in which an instruction embedded in untrusted development context may influence a Code LLM even when the developer did not author, endorse, or intend it. We refer to this threat as inference-time context injection . An adversary who can influence a fragment of content that a developer may later incorporate into an assistant’s context, such as a forum snippet, library example, shared-repository file, or model-generated artifact, places an insecure directive in that content, most naturally as a code comment. When the developer subsequently issues a generic and otherwise benign request to complete or extend the code, the model may operationalize the planted directive and generate code containing an exploitable weakness. The adversary requires no access to the model’s parameters, training data, decoding configuration, or the developer-authored prompt. The attack instead exploits the model’s treatment of instructions according to their presence in the context rather than their provenance. Figure 1 provides an illustrative example of this framing-dependent behavior. This threat occupies a distinct position in the existing literature. Studies of insecure code generation examine how frequently Code LLMs produce vulnerable code under neutral or security-relevant prompts [Hajipour et al., 2024, Pearce et al., 2022, Perry et al., 2023], but generally assume no adversary controlling part of the inference-time input. Conversely, work on poisoning and backdoor attacks modifies training or fine-tuning data so that attacker-selected contexts later trigger insecure completions [Aghakhani et al., 2024, Schuster et al., 2021, Yan et al., 2024]. Our adversary requires neither training-pipeline access nor control over the developer’s request. This threat is therefore a form of indirect prompt injection [Greshake et al., 2023, Liu et al., 2024], but with a code-specific payload; rather than producing a prohibited response, corrupting a retrieved answer, or inducing an unauthorized tool action, the injected instruction causes a weakness to be incorporated into the generated source code. To characterize this attack surface, we evaluate ten open-weight Code LLMs ranging from 3B to 13B parameters, including four base models and six instruction-tuned models, across ten web-application weakness classes. We use a standardized two-condition evaluation. In the attack condition, each completion task contains an insecure instruction embedded as an ordinary code comment. In the benign condition, models complete a corpus of ordinary coding tasks containing no malicious directive. The benign condition uses different scaffolds to estimate the rate at which vulnerabilities arise during ordinary coding activity; the resulting contrast compares insecure-instruction exposure with normal coding work, and Section 4.1 details what it does and does not isolate. Our primary outcome is the vulnerable-output rate , defined as the proportion of generated completions that the detector ensemble classifies as containing at least one medium-or-higher-severity weakness. We interpret this rate under the attack condition as an observable con-sequence of compliance , defined as the model’s tendency to follow an instruction present in its context irrespective of its provenance. This operationalization is necessarily imperfect; a model may follow an insecure instruction without producing a detectable weakness, or it may ignore the instruction while generating an unrelated weakness. The metric and its limitations are formalized in Section 4.3. Moreover, our experiments measure model behavior after the insecure instruction is already present in the context; they do not measure the complete end-to-end probability that an adversarial artifact is ingested, acted upon, accepted by the developer, and ultimately deployed. We organize the study around three research questions. RQ1: when an insecure instruction is present in a Code LLM’s context, how often does the model produce vulnerable code, and how severe are the resulting weaknesses? RQ2: does susceptibility vary with training regime, parameter count, code specialization, or release generation? RQ3: how effectively can post-generation screening detect the induced vulnerabilities? Second, on RQ3, output-level defenses mitigate but do not eliminate the risk: the strongest individual post-generation detector in our evaluation leaves approximately one-third of vulnerable outputs undetected, whereas conventional static-analysis detectors leave substantially larger fractions undetected. ## 2 Related Work 

Prior work relevant to our contribution can be organized along two axes. The first is where malicious input enters the system: the model’s training data, the developer’s prompt, or untrusted inference-time context. The second is the nature of the payload: a disallowed language-model output, an unauthorized agent action, an incorrect answer, or, in our setting, an exploitable weakness embedded in generated source code. Taken together, these perspectives expose a gap between existing studies of insecure code generation, poisoning, and prompt injection, and the attack surface we examine here. 4Insecure code generation without an adversary A substantial body of work has measured how often Code LLMs generate vulnerable code under neutral prompts. Pearce et al. [2022] reported that roughly 40% of GitHub Copilot completions in security-relevant scenarios contained weaknesses, Khoury et al. [2023] observed similar behavior across models, and Tihanyi et al. [2024] showed at scale that even neutral prompts frequently yield CWE-classified vulnerabilities. Controlled user studies by Perry et al. [2023] and Sandoval et al. [2023] further showed that developers supported by AI assistants tend to write less secure code, often without recognizing the loss in security. Benchmarks including SecurityEval [Siddiq and Santos, 2022], SALLM [Siddiq et al., 2024], LLMSecEval [Tony et al., 2023], and CodeLMSec [Hajipour et al., 2024] have standardized this measurement, while He and Vechev [2023] demonstrated that security-hardening training can reduce the propensity to generate insecure code. This literature establishes a baseline tendency toward insecure generation, but it does so without an adversary and without distinguishing who controls the input. We treat that baseline as the reference against which our two-condition design measures the effect of an attacker-controlled instruction. 

Insecure code from untrusted provenance Our threat model builds on the long-standing observation that developers often incorporate code they did not author and cannot fully trust. Acar et al. [2016] found that developers relying on informal sources such as Stack Overflow produce measurably less secure code than those using official documentation, and Fischer et al. [2017] traced such snippets into a substantial fraction of production Android applications. Similar concerns arise in the software supply chain: Ohm et al. [2020] catalog 174 malicious packages used in real attacks on npm, PyPI, and RubyGems, and Zimmermann et al. [2019] show that a single popular package can reach more than 100 ,000 dependents. In these cases, the untrusted artifact is typically passive : it contains insecure code directly, which makes scanning and code review plausible countermeasures. By contrast, a Code LLM turns the same channel active, because it can execute instructions embedded in untrusted content rather than merely passing that content through. An attacker therefore need not smuggle vulnerable code past a scanner; a planted comment is sufficient to induce the victim’s assistant to generate the weakness. 

Training-time poisoning and backdoors A second line of work assumes that the adversary can influence what the model learns. Schuster et al. [2021] demonstrated poisoning attacks on code completion systems, TrojanPuzzle [Aghakhani et al., 2024] concealed payloads in out-of-context regions such as docstrings to evade static dataset cleansing, and CodeBreaker [Yan et al., 2024] used LLM assistance to construct disguised vulnerable payloads that survive detection. These attacks are powerful, but they require access to the training or fine-tuning pipeline, which our adversary does not need. The capabilities are therefore distinct: poisoning acts through the model’s learned parameters, whereas our attack acts through inference-time context that a developer later ingests. 

Prompt injection and indirect prompt injection The closest conceptual analog is indirect prompt injection, in which malicious instructions hidden in retrieved or tool-supplied content steer an LLM-integrated system. Greshake et al. [2023] introduced the threat in real-world applications, and Liu et al. [2024] formalized and benchmarked attacks and defenses. More recent work has extended this setting to tool-using and retrieval-augmented systems, including InjecAgent [Zhan et al., 2024], AgentDojo [Debenedetti et al., 2024], and PoisonedRAG [Zou et al., 2025]. In those settings, the payload is usually an unauthorized action or an incorrect answer, and defenses can sometimes intervene by gating tool use or validating retrieval. We study the code-generation instantiation of this threat, in which the payload is not a discrete action but a durable weakness embedded in the victim’s codebase. This makes the attack harder to intercept at the output layer and more consequential for downstream security. To 5our knowledge, this manifestation, and the extent to which compliance is uniform across base and instruction-tuned Code LLMs, has not been systematically quantified. 

Jailbreaking and the limits of safety training Our claim that compliance reflects instruction-following behavior rather than security also connects to work on why aligned models can still be induced to produce unsafe outputs. Wei et al. [2023] argue that jailbreak success reflects competing objectives and imperfect generalization in safety training, and Zou et al. [2023] show that universal adversarial suffixes can transfer across aligned models. Two distinctions are important in our setting. First, jailbreak targets are overtly disallowed content, for which refusal is the intended response and the training signal is explicit, whereas insecure code completion is ordinary-looking code and provides no comparable refusal trigger. Second, jailbreak studies typically rely on adversarially crafted prompts, whereas our results show that a plain insecure instruction suffices across the models we evaluate. This makes refusal- and compliance-based security metrics more naturally interpretable as measures of instruction-following behavior, at least for the open-weight, lightly safety-tuned models in our study (Section 7.3). 

Defenses that separate trusted from untrusted instructions A growing defense literature targets the missing trust boundary directly, and it divides into two broad families. The first family attempts to train the model to prioritize trusted instructions: the instruction hierarchy [Wallace et al., 2024] teaches models to defer to higher-privileged instructions, StruQ [Chen et al., 2025a] retrains them to treat prompt and data as separate channels, and SecAlign [Chen et al., 2025b] uses preference optimization to improve resistance to injection. The second family acts at inference time by marking provenance in the prompt, for example through spotlighting [Hines et al., 2024], which delimits or labels untrusted spans so that the model can be instructed to treat them as data. Both families assume a reliable distinction between instructions and data, which Zverev et al. [2024] show current models do not robustly maintain. Our results motivate this line of defense by quantifying the code-generation manifestation that such methods must address, and our screening evaluation in Section 6 shows that a readily deployable inference-time mitigation still leaves a substantial fraction of induced vulnerabilities undetected. That finding strengthens the case for trained-in and provenance-aware defenses in the coding setting. 

## 3 Threat Model 

We consider an adversary who controls only a fragment of the untrusted context ingested by a developer’s coding assistant. By planting an insecure instruction in that context, the adversary can induce the assistant to generate vulnerable code during an otherwise benign completion task, thereby introducing an exploitable weakness into the victim’s project (Figure 2). This section defines the system model, adversary capabilities, security property, success criterion, and scope of the analysis. 

System model and notation We distinguish between an assistant and the underlying Code LLM . The assistant is the deployed product used by the developer and may include a system prompt, a context-assembly or retrieval layer, an editor integration, and suggestion filtering. The Code LLM is the model underlying that product. Our threat model is defined at the assistant level, but our experiments evaluate the model in isolation: we abstract an assistant as a Code LLM conditioned on a context window, while omitting product-layer components. This abstraction enables measurement at the model level across many checkpoints; Section 7.3 identifies the resulting external-validity limits. We model the context window as the union of two disjoint regions. The first is the developer-authored region D, containing the developer’s prompt, instructions, and code. Victim and asset The victim is a developer using the assistant in good faith. The asset at risk is the security of the code that the developer ships. In normal development, the developer may incorporate code from external sources, a practice that is common and well documented [Fischer et al., 2017]. The attack exploits the fact that the developer does not expect content in U to function as a command. 

Benign request and attack channel The developer issues an ordinary completion request, such as asking the assistant to finish work in a file. This request does not authorize any particular instruction embedded in the imported context, and the developer may not inspect every line of that context. The adversary exploits this gap by planting an instruction in content that later enters the assistant’s context. When the assistant completes the developer’s benign request, it may realize the planted instruction and generate vulnerable code. This is a form of confused-deputy behavior: a broad trusted request carries an untrusted payload. 

Adversary capabilities The adversary controls some portion of the untrusted region U , but not the model, its weights, its training data, or the developer-authored region D. Concretely, the adversary may: • publish a code snippet, such as a forum answer, blog post, or gist, that the developer may later copy [Acar et al., 2016, Fischer et al., 2017]; • contribute an example or comment to a third-party library or template that the developer imports, a channel already used in software-supply-chain attacks [Ohm et al., 2020]; • commit to a shared repository whose files enter the developer’s editor context; or • supply content that another tool, including another LLM, later places into the context window. These channels are often low-cost and may scale to many victims: a single widely viewed snippet or dependency can be ingested by many developers. Popular packages can reach more than 100 ,000 dependents [Zimmermann et al., 2019]. Unlike poisoning adversaries, this attacker 7does not require access to the training pipeline [Aghakhani et al., 2024, Schuster et al., 2021, Yan et al., 2024]; the relevant capability is influence over inference-time context. The setting is therefore an instance of indirect prompt injection tailored to code generation [Greshake et al., 2023, Liu et al., 2024]. 

Adversary knowledge The attack is black-box with respect to the model. The adversary need not know the victim’s weights, decoding parameters, or, in our experiments, even the specific model underlying the assistant, because the compliance behavior we measure is broadly similar across the models in our set (Section 5.3). A planted comment therefore serves as a model-agnostic payload. Whether the same behavior transfers to deployed assistants with different product layers is outside the scope of our experiments. 

Adversary objective The adversary seeks to induce code that contains a chosen exploitable weakness, specified here as a Common Weakness Enumeration (CWE) category, and to have that code enter the victim’s project. The target is a durable vulnerability in source code, not a one-time disallowed output. 

Trust boundary and the security property it protects The trust boundary in this workflow separates the developer-authored region D from the untrusted region U , and it is crossed at the moment external content is brought into the context window. The security property that a correct assistant should preserve is provenance-aware instruction handling: directives originating in D may be followed, whereas content in U should be treated as data to be reasoned about rather than as commands to be executed. Because π conditions on D ∪ U

without regard to provenance, an insecure directive carries the same authority whether the developer typed it or an adversary planted it in U . The attack is exactly a violation of this property, and our evaluation quantifies how often that violation occurs. 

Success criterion We count an attack instance as successful when, given a benign developer request and a planted insecure instruction in the context, the model generates code that the detector ensemble classifies as containing at least one medium-or-higher weakness (Section 4.2). This criterion captures vulnerability induction rather than a targeted CWE outcome, and it does not require that the resulting weakness be exploitable in the deployed environment. A completion may therefore be counted vulnerable without realizing the exact CWE named in its scenario, for three reasons: the target classes overlap, so one insecure completion frequently satisfies several CWEs at once (Appendix A); the model may follow the insecure intent through a different sink than the scenario anticipated; and the criterion is deliberately CWE-agnostic, measuring whether an embedded instruction induces a medium-or-higher weakness rather than the specific targeted one, since from the victim’s perspective any exploitable weakness introduced into the code is the relevant outcome. 

Scope and assumptions We study the adversary’s ability to induce vulnerabilities in generated code, not end-to-end exploitation of a deployed system. We assume a single-turn completion setting. Multi-turn and agentic assistants may expand U by repeatedly reintroducing untrusted tool outputs into context, but they also add product-layer behaviors that our model-level abstraction does not capture. We also assume that the developer does not perform a security review that intercepts the weakness before deployment. This assumption is supported by prior studies showing that AI-assisted developers may write less secure code while remaining more confident in its security [Perry et al., 2023]. Finally, our experiments evaluate the Code LLMs underlying assistants rather than full assistant products (Section 7.3). 84 Attack Construction and Methodology 

This section describes how we construct the attack items, how we define the benign comparison, how we score model outputs, and how we quantify susceptibility. Our goal is to measure whether an insecure instruction embedded in code context changes the vulnerability rate of generated completions under a controlled evaluation. 

4.1 Evaluation Design 

We use a controlled two-condition design to measure the attack channel. In the attack condition, each item is a partially completed Python Flask application. The intended behavior is stated in an embedded insecure instruction. The instruction appears as an in-code comment marked # TODO: , # INSTRUCTION: , or # TASK: . This format matches the kind of comment an adversary could plant in untrusted context (Listing 1). We place the comment at the point in the function body where the completion is produced; as Appendix B shows, the pattern induces the vulnerability regardless of where in the file the comment is located. In the benign condition, the model receives coding tasks with benign instructions. This condition provides the baseline rate at which models emit vulnerabilities during normal work. We compare attack-condition output against this baseline. Every item in both conditions uses the same code-completion template, which frames the model as a completion assistant, asks it to complete the parts marked by the instruction comment, and requests only the final code.   

> You are a code completion assistant. Complete all parts marked with ‘# TODO:’ in this python code. Remove all TODO comments and return only the final working code. Code:
> ⟨scaffold with embedded instruction ⟩

Holding the template, language, and surface form constant across conditions limits prompt-format confounding. The attack and benign items still differ in task content, since the benign set is a corpus of ordinary coding tasks rather than a secure rewrite of each attack scaffold. The attack-versus-benign contrast therefore reflects both the embedded instruction and the task type; isolating the instruction alone would require a within-scaffold paired design. In every experiment, the insecure instruction remains in the code context as a comment, and the model completes the function around it, so our results measure compliance rather than 9end-to-end attack success (Section 7.3).

4.3 Susceptibility Measures and Inference 

Compliance proxy. We use compliance to mean the tendency of a model to follow in-structions in its context, regardless of who placed them there. We do not observe compliance directly. We observe its effect. When the context contains an insecure instruction, a complying model tends to produce insecure code. We therefore use the vulnerable-output rate as our operational measure. It is the fraction of attack-condition completions that the ensemble flags at medium severity or above. The gap between this rate and the benign baseline serves as evidence of compliance. This proxy is imperfect. A model may comply without producing a detectable weakness. A model may also ignore the instruction and still emit an unrelated weakness (Section 7.3). We reviewed each completion to confirm that it implements the requested task rather than merely resembling relevant code, and we executed a subset to check that the generated code runs; the vulnerable-output rate therefore reflects functional, task-appropriate completions that also contain a weakness, rather than detector artifacts on broken or off-task output. MSS states how much of a model’s output the instruction turns vulnerable in absolute terms, and RSR states how far the attack condition departs from the rate observed during ordinary coding work; we report both because a model with a very low benign baseline can show a large ratio from a modest absolute shift. The two conditions use different items. We therefore test the benign-versus-attack difference with an unpaired two-proportion test and report Cohen’s h as the effect size. With N = 700 per condition and effect sizes of this magnitude, statistical significance is not the main question. The more informative quantities are the effect sizes, the separation of the Wilson intervals, and the detector ablation in Section 5.6. 

Equivalence testing. Our uniformity claim is that base and instruction-tuned models comply at similar rates. A non-significant difference test cannot establish that claim. We therefore use two one-sided tests. We declare the two groups equivalent at margin ∆ when the 

90% confidence interval for the difference in mean compliance lies within [−∆, +∆] .We set ∆ = 10 percentage points. We treat that margin as practically small relative to the observed 77 to 92% attack band and the 17 to 49 × contrast between conditions. Because the claim is at the model level, not the completion level, we compute the contrast over the ten per-model rates and account for between-model heterogeneity by clustering at the model level. We report the equivalence result for the base-versus-instruction contrast and for each of the three sibling pairs in Section 5.3. 

## 5 Evaluation 

This section reports the empirical results. We first describe the models, data, generation settings, and scoring pipeline. We then report attack success, uniformity across model groups, severity, attack surface, and detector checks. In all experiments, the insecure instruction appears in the code context as described in Section 4.1. A sample counts as vulnerable under the ensemble rule in Section 4.2.

5.3 Uniformity Across Model Families 

This subsection addresses RQ2. The main result is not only that compliance is high, but that it is relatively consistent across model families. The ten attack rates fall between 77 .4% 

and 92 .3% , and the base and instruction-tuned groups average 86 .5% and 84 .5% respectively. Close means alone do not establish equivalence, so we test the group difference directly using the two one-sided tests described in Section 4.3. Treating each model as the unit of replication, the base-versus-instruction difference is +2 .0 percentage points, with a 90% confidence interval 13 of [−5.5, +9 .5] percentage points. This interval lies within the margin of ∆ = 10 percentage points, so the two groups are equivalent at that margin. It does not fit within the stricter margin of ∆ = 5 percentage points, which is expected given the small number of models per group. The sibling-pair comparisons below provide a tighter test. Within this ten-model sample, the remaining variation shows no clear relationship with scale, release recency, specialization, or training regime. Scale is uninformative: the 13B CodeLlama sits near the bottom of the range at 77.6%, while the 7B StarCoderBase is at 77.4%, and at the upper end the 3B Granite-4.0-H-Micro-Base reaches 92.3% and the 3B StarCoder2-Instruct 88.6%. 5.6 Detector Validity 

We next test whether the result depends on the pattern detector DP . Pattern signatures could overlap with the requested weakness. We therefore recompute the attack rate using only the non-pattern analyzers: Bandit, AST taint, secret detection, and the LLM verifier. Under this stricter rule, the attack rate decreases, but it remains far above the benign baseline. The rate is still about 62% to 79% for eight models, and about 46% to 54% for the two lowest models, StarCoderBase and CodeLlama-13B. The benign baselines remain at 2% to 5% , and the main result therefore does not depend on the pattern signatures. We also examine detector-condition agreement using the experimental condition as the reference label. Precision exceeds recall across the ensemble, as shown in Appendix C. These diagnostics do not establish detector ground truth, but they help characterize the detector behavior. We rely on the full ensemble rather than the LLM verifier alone because LLM-based vulnerability judgments are unreliable in isolation [Ullah et al., 2024]. The non-pattern ablation shows that no single detector component drives the result.

The attack is enabled by the absence of an enforced distinction between developer instructions and untrusted code context in the evaluated setup. This section addresses RQ3: we evaluate post-generation screening directly, and then explain why it is not sufficient on its own. 

6.1 Post-Generation Screening 

A practical defense is to pass each completion through a fast analyzer and block outputs that it flags. We evaluate each screen as a single detector, scored against the ensemble label. This comparison is partly circular, because each screen is also a member of the ensemble. We therefore report each screen against two references. The first is the full ensemble, whereas the second is a leave-one-out reference that excludes the screen under test (Table 3). The resulting bias is small, at 0.7–3.1 percentage points, and it does not change any conclusion. Neither reference is human-adjudicated, so both remain detector-defined. Two quantities matter per screen: coverage , the fraction of ensemble-labeled vulnerable attack outputs the screen flags, and the residual uncaught rate , the fraction that pass the screen. A useful screen should have high coverage and a low residual uncaught rate. In our experiment, we measure only whether an output passes the screen. We do not measure whether it is later reviewed, committed, or deployed. Table 3 reports the pooled results across all ten models, and no single screen prevents the attack. Bandit catches only 21 .4% of vulnerable completions under the full-ensemble reference and 20 .7% under leave-one-out. AST taint catches 32 .1% , or 31 .4% under the leave-one-out reference. The LLM judge, Phi-3, performs better and reaches 71 .0% coverage, or 67 .9% 

under the leave-one-out reference. Even so, it leaves about one-third of vulnerable outputs undetected. The deployable static screens are much weaker. They leave roughly two-thirds or more undetected and therefore reduce risk without containing the attack. 

6.2 Why Screening Falls Short 

These results expose a structural limitation of post-generation screening: a screen that runs after generation can block only what it recognizes. It therefore inherits the recall limits of static analysis on code that is adversarially shaped but still functionally plausible, which is the kind of code this attack produces. Even the union of all three screens reaches only 78 .4% coverage and still leaves 21 .6% uncaught, or 74 .5% and 25 .5% under the leave-one-out reference. Stacking the analyzers we tested therefore does not approach containment. A more direct defense must act before or during generation. It must teach the model to treat instructions in untrusted context as data, and to decline insecure instructions. The instruction hierarchy [Wallace et al., 2024] is the leading example of this approach. StruQ [Chen et al., 16 2025a] and SecAlign [Chen et al., 2025b] are related training-time defenses. Inference-time provenance separation, such as spotlighting [Hines et al., 2024], is also relevant, as it marks untrusted spans that the model can be told to treat as data. It can complement screening, but is less likely to restore the missing trust boundary on its own. Our screening results make the case for these defenses concrete. 

## 7 Discussion 

This section interprets the main findings of the study. It examines what the sibling-pair comparison shows about instruction tuning, why the attack is practical, and what limits the scope of our claims. 

7.1 Instruction Tuning and Compliance 

The most direct hypothesis for the compliance we measure is that instruction tuning is responsible, since tuning is intended to improve prompt following. The three sibling pairs (Section 5.3) are inconsistent with this: in each, the base checkpoint complies at a rate at least as high as its tuned sibling, so instruction tuning is not necessary for the behavior and it is already present after pretraining. We do not identify which training stage produces it; that would require interventions beyond the checkpoint-level comparison we report here. 

7.2 Why the Attack Is Practical 

The attack is practical because it is inexpensive for the adversary and costly for the victim. As in the threat model, the adversary needs no access to the model or the developer’s prompt; it needs only to place a planted instruction in content that a developer may later import into context. The developer then issues a normal completion request, and the model may follow the planted instruction. The induced weaknesses are concentrated in high and critical severity classes. They also appear in web-facing code, which makes them relevant to real deployments. The generated code is often functionally plausible, so casual review may not reveal the problem. Prior work also suggests that developers using AI assistants may write less secure code while feeling more confident about it [Perry et al., 2023], which makes the human-in-the-loop safeguard unreliable. 

7.3 Limitations and Threats to Validity 

What the design isolates. Our results show that models follow insecure instructions present in their code context, and that this behavior opens a context-injection attack surface (Section 4.1). They do not provide a measured end-to-end attack-success rate under a fully separated split, where a benign developer prompt is paired with a malicious instruction in a distinct untrusted artifact. Nor do the two conditions isolate the instruction itself: the benign corpus is a set of ordinary coding tasks, not a secure rewrite of each attack scaffold, and the two corpora differ in security sensitivity, since every attack scaffold is a Flask handler in which user input reaches a sink while the benign corpus contains mostly ordinary Python tasks with little opportunity for vulnerability. The reported 17 –49 × ratio therefore combines the effect of the instruction with the effect of task type. A within-scaffold paired design, flipping only the instruction, would isolate the instruction effect. We did not adopt one for two reasons. First, the benign corpus was authored as an independent set of ordinary coding tasks rather than as secure rewrites of the attack scaffolds, so a matched per-scenario counterpart was not available. Second, a content-based detector complicates a paired contrast: when the exploitable pattern lies in the surrounding scaffold rather than the comment, the detector flags both the secure- and insecure-instruction versions similarly, understating the instruction’s contribution. Cleanly isolating the comment’s effect therefore requires both matched scaffolds and an oracle 17 keyed to each scenario’s targeted weakness, which we leave to future work, together with the non-security-sensitive benign scaffolds a faithful end-to-end study would need. 

Scope of the evaluated systems. Our threat model concerns a developer’s assistant, but our experiments evaluate the Code LLMs that underlie them. A deployed assistant adds a product layer that we do not model, including a system prompt, context assembly or retrieval, editor integration, and in some products, suggestion filtering. Our results therefore establish model-level compliance, which supports an assistant-level attack only under the additional premise that the product layer inherits the model’s behavior. The model set is also open-weight and mid-scale, from 3B to 13B, and excludes closed and frontier systems, so it omits both the systems most developers reach through commercial assistants and those that have received the most safety investment. Our conclusions are established for this set and are hypothesized, not demonstrated, beyond it. Extending the evaluation to a small number of API-served models would be the most useful robustness extension. 

Statistical precision. Our equivalence test uses a margin of ∆ = 10 percentage points and is a group-level claim over four base and six instruction-tuned models. With so few clusters the confidence interval for the group difference is wide, and equivalence holds at ∆ = 10 but not at a stricter ∆ = 5 . Each condition comprises 700 distinct scenarios with one completion each, so the completions are independent, but the Wilson intervals still describe sampling variation within our scenario set rather than generalization to new tasks, frameworks, or languages. 

Measurement instrument. Every rate we report depends on the ensemble detector, which is imperfect. We mitigate this in three ways: an ensemble rather than a single tool; validation against the experimental condition as a reference label; and an ablation that excludes the pattern detector. The metric is also not target-specific: we count any medium-or-higher weakness rather than the exact CWE requested by the planted instruction (Section 4.3), so it does not measure targeted-CWE induction separately. Reporting both would better align the headline metric with the adversary’s goal. 

Coverage of the attack set. The attack items state the insecure objective plainly, whereas a planted comment in practice could be more subtle, and we do not measure how indirect the intent can be while still inducing the same weakness. The set also spans ten weakness classes in a single language and framework, Python with Flask, and 700 scenarios per condition, so absolute counts partly reflect this sampling choice. It remains open whether the same compliance pattern holds in other languages, frameworks, and assistant settings. 

## 8 Conclusion 

We have reframed the security of Code LLM assistants as a trust-boundary problem. Insecure instructions present in code context are followed regardless of provenance, which creates a context-injection surface through which adversary-controlled content can steer an assistant toward insecure code even when the developer’s request is benign. Across the ten open-weight models in Table 1, this behavior is strong and relatively consistent. Attack-condition completions contain medium-or-higher weaknesses at a rate of 77% to 92% , compared with 

2% to 5% under the benign baseline, and the induced weaknesses are predominantly high or critical. Base and instruction-tuned models comply at statistically equivalent rates, instruction tuning does not increase the measured susceptibility in any of the three matched sibling pairs, and neither parameter count nor code specialization explains the pattern. It follows that refusal-based or compliance-based security metrics do not distinguish among the models we study. Post-generation screening mitigates the attack but does not contain it, since substantial 18 fractions of vulnerable outputs remain undetected. Durable mitigation therefore requires provenance-aware defenses upstream of generation. Our contributions are a threat model, a controlled two-condition methodology with susceptibility metrics and equivalence testing, an empirical evaluation across ten models, and a measured baseline for post-generation screening. The most important next steps are a fully separated end-to-end attack study and broader evaluation of heavily safety-post-trained or closed models.

## Ethics Considerations 

This study evaluates a dual-use attack methodology. No live systems, commercial assistants, or third-party users were targeted: all experiments used locally executed open-weight models and synthetic Flask scaffolds, with functional validation confined to an isolated environment, and no generated code was deployed or contributed to any external repository. The study involved no human participants and therefore required no human subjects review. We did not pursue vendor-specific disclosure because the behavior we document is general across independently released open-weight models rather than a vulnerability in a deployed product. Releasing the scaffolds does lower the barrier to reproducing the attack, but the technique requires little specialized knowledge, whereas measuring its effectiveness and the limits of existing defenses supports the development of provenance-aware mitigations; we therefore judge the defensive benefit to outweigh the incremental risk. ## B Comment-Position Sensitivity 

The insecure instruction is embedded as an in-code comment at the point where the model completes the function (Section 4.1). We examine how the position of that comment within the file affects the attack. Holding the scaffold and the instruction fixed, we place the single instruction comment in three positions—at the top of the file (before the imports), in the middle (the completion point), and at the bottom (after the function)—and regenerate. We evaluate 

n = 30 scenarios per position on two instruction-tuned models, DeepSeek-Coder-Instruct and Qwen2.5-Instruct, with greedy decoding and the ensemble of Section 4.2. Table 5 reports the vulnerable-output rate for each position. The rate is essentially unchanged as the comment moves: across the three positions it varies within roughly seven percentage points for both models, Cochran’s Q over the three positions is not significant (DeepSeek: 

Q = 0 .75 , p = 0 .69 ; Qwen: Q = 1 .60 , p = 0 .45 ), and no pairwise McNemar comparison is significant (all p ≥ 0.44 ). No completion was refused in any position. The instruction pattern is therefore effective wherever it appears in the file: once the comment is present in the context, the model produces the vulnerability regardless of its location, and the comment’s position does not change this behavior.

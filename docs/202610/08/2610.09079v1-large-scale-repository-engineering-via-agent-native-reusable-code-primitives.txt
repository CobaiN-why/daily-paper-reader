## ABSTRACT 

Large language models (LLMs) equipped with development environments have moved code generation toward repository-scale construction, yet building complete repositories remains difficult because interacting modules, interfaces, configura-tions, tests, and dependencies must work together. We introduce Code Primitives ,agent-native reusable executable components that carry their own interface con-tracts, dependency closures, validation tests, and provenance. Each primitive uses a resident LLM as a natural-language interface to assess relevance and adapt its implementation, interfaces, and dependencies to the target repository, and we orga-nize 1,424 validated primitives in CodeFace , a searchable library for repository construction. Each primitive adapts the component it owns. We introduce LEGO 

(Large-scale repository Engineering via a Gent-native reusable c Ode primitives), which activates the primitives a task requires, integrates their adapted implemen-tations with task-specific code while resolving constraints that cross component boundaries, and revises the result against executed tests. To measure construction end to end we build LEGO-REPO , a benchmark of 522 executable reconstruction tasks spanning seven software domains, 22 capability tracks, and five difficulty lev-els, each scored against the package’s native test suite between an empty-package floor and an original-source ceiling. The strongest of 13 evaluated backbones reaches a delivery score of 0.318 and scores zero on 41 .0% of tasks; LEGO im-proves all 13 by 0.1474 on average and raises GPT-5.6-terra from 0.3180 to 0.5134 

(+61 .4% ). In controlled comparisons, adapted primitives achieve higher delivery scores than retrieved code supplied as context or vendored unchanged. The effect persists against independent repository agents, across three external benchmarks, and with a disjointly re-mined CodeFace, and using GPT-OSS-20B for adaptation and diagnosis retains 95 .1% of the homogeneous score at 24 .0% lower cost. 

## 1 INTRODUCTION 

Large language models with development environments have moved code generation from isolated programs toward repository-scale construction (OpenAI, 2025; Anthropic, 2025; GitHub, 2025; Peng et al., 2026; Ding et al., 2025), a setting requiring complete projects whose modules, interfaces, configurations, tests and dependencies work together. This shift raises three high-level design questions about how such repositories can be reliably constructed. 

(1) How reliably can frontier models construct a complete repository end to end? Existing evaluations confirm the difficulty: on RepoZero-Py2JS, Claude Sonnet 4.6 with mini-SWE-agent reaches a 54 .7% pass rate (Zhang et al., 2026b), with similar results elsewhere (Luo et al., 2026; Chen et al., 2026). On our benchmark, the strongest of 13 LLMs reaches a delivery score of 0.318 ,where 0 denotes the empty-package floor and 1 the behaviour of the original source, and scores zero on 41 .0% of 522 tasks; Claude Opus 5 reaches 0.237 and matches the original behaviour on 5.9% ;and the mean score across backbones falls 10 .3× from the smallest to the largest difficulty band. These results motivate approaches that reuse and coordinate existing software capabilities. 

(2) What reusable abstraction can better support repository construction? Prior work encapsu-lates reusable capabilities as agent-native behaviors and executable tools (Jin et al., 2026a;b), which are typically invoked externally and remain fixed during use. Repository construction requires a

This form of reuse combines retrieval with adaptation. We introduce Code Primitives , reusable executable components that carry their own interface contracts, dependency closures, validation tests, and provenance. Each primitive uses a resident LLM as its natural-language interface to assess relevance and adapt its implementation, interfaces, and dependencies to the target. We then mine and validate these primitives from real-world repositories and organize them into CodeFace , a library of 1,424 Code Primitives. 

(3) What construction pipeline can better leverage reusable software capabilities? We treat repos-itory construction as resolving a specification against existing capabilities and integrating reusable components with task-specific code. We introduce LEGO (Large-scale repository Engineering via aGent-native reusable c Ode primitives), which coordinates Code Primitives through three mecha-nisms: retrieval and activation decomposes a request into required capabilities and activates only the primitives that cover them; primitive collaboration lets activated primitives adapt their implemen-tations while propagating interface and dependency requirements to connected components; and diagnosis and verification executes available and synthesized tests, localizes failures to components or their interactions, and reactivates affected primitives for revision. This loop integrates retrieval, adaptation, and verification until validation succeeds or the construction budget is exhausted. To evaluate LEGO, we introduce LEGO-REPO , a benchmark of 522 executable reconstruction tasks drawn from real GitHub projects across seven software domains, 22 capability tracks, and five measured difficulty levels ( D1–D5 ). Each task reconstructs a Python package from its public interface and evaluates it against the package’s native test suite. We evaluate the aforementioned questions through six empirical RQs spanning from-scratch con-struction, reusable capabilities, construction mechanisms, model substitution, cost, and transfer. Across LEGO-REPO , LEGO improves all 13 evaluated backbones, with a mean absolute gain of 0.1474 (+76 .5% relative). Under GPT-5.6-terra, the delivery score rises from 0.3180 to 0.5134 

(+61 .4% ), with fewer zero-score tasks and more repositories reproducing original-source behavior. The gains persist against independent repository agents, on three external benchmarks, and with a disjointly re-mined CodeFace. Adapted primitives also outperform retrieved code used as read-only context or vendored unchanged. Finally, GPT-OSS-20B adaptation and diagnosis retain 95 .1% of the homogeneous GPT-5.6-terra score at 24 .0% lower cost. Our main contributions are as follows: • We design Code Primitives , agent-native reusable software components that carry their own interface contracts, dependencies, validation tests, and provenance, and adapt themselves to target repositories through their natural-language interfaces. We further build CodeFace , a library of 

1,424 validated Code Primitives for retrieval and reuse. • We introduce LEGO , a repository-construction framework built on CodeFace that makes this abstraction usable at repository scale: it activates only the primitives a task requires, delegates adaptation to the component that owns each implementation, and uses executed tests to guide integration and revision across component boundaries. • Experiments on LEGO-REPO , our benchmark of 522 repository-reconstruction tasks, show that LEGO improves all 13 evaluated LLMs by 0.1474 on average and raises GPT-5.6-terra from 0.3180

Coding agents and repository-level evaluation. Execution-guided refinement is a complementary mechanism (Chen et al., 2022; Shinn et al., 2023).

Key Differences. Prior reusable abstractions are typically consumed by invocation or as retrieved context: the artifact remains fixed while a central agent decides how to use it. Code Primitives instead support reuse by adaptation. Each primitive becomes part of the delivered repository, carries its own interface contract, dependency closure, and validation tests, and can modify its implementation and dependencies to fit the target. This moves part of repository construction from a single generator into the components that own the reused functionality. LEGO then coordinates which primitives to activate, how their requirements propagate across components, and how failed executions trigger further revision. LEGO-REPO evaluates the resulting package end to end against the original repository’s native test suite. Extended comparisons appear in Appendix A. 

## 3 METHODOLOGY 

3.1 OVERVIEW 

LEGO is a repository-construction pipeline built on CodeFace , a library of reusable Code Primitives 

(Figure 1). CodeFace is built once by mining real repositories into component-level primitives; construction then proceeds per task over the primitives a request activates. Adaptation is performed by the component that owns the implementation, while constraints that cross components are resolved at the repository level. 3.2 CODE PRIMITIVES AND CODE FACE 

A Code Primitive is a reusable executable software component equipped with a resident LLM. Each primitive implements a coherent capability and exposes a natural-language interface through which it can assess its relevance to a construction task and adapt itself to a target repository. A code primitive 3Preprint. may span functions, classes, files, configuration, and supporting artifacts; its boundary is determined by functional coherence and the dependencies required for independent execution. Formally, we represent a primitive as Pi = ( Ci, I i, D i, V i, X i, M i), where Ci is the implementation, 

Ii the exposed interface and behavioural contract, Di the dependency closure, Vi the validation tests carried by the primitive, Xi supporting context and provenance, and Mi the resident LLM. We write 

Vi rather than Ti because T denotes a benchmark task in Section 4. Granularity is induced by mining rather than manually tuned: in the evaluated snapshot the median primitive contains 214 lines across 

2 files, exports 4 symbols, and carries 9 validation tests. Given requirement r and construction context C, a primitive first assesses its relevance and proposes how it could be used:

Adaptation may modify interfaces, representations, dependencies, configuration, or implementation while preserving the intended capability. It operates on the primitive’s own state and a bounded context containing the target location, required exports, and interfaces to bind, without access to unrelated implementations, the native test suite, or the global repository plan. The primitive then updates its interface and dependency records and reruns Vi on the adapted component. This carried validation distinguishes primitive adaptation from generic editing. Appendix P gives the full contract and rejection criteria. 

CodeFace organizes the validated primitives as a library F = {Pi}Ni=1 . Rather than exposing the entire library in context, LEGO retrieves only the candidates required by the current task and invokes them on demand. Each entry retains its provenance, so mined, harvested, web-sourced, and target-derived components can be distinguished during analysis. The evaluated snapshot holds 871 

mined, 343 harvested, and 210 web-sourced entries, for 1,424 validated Code Primitives. 3.3 MINING AND VALIDATING CODE PRIMITIVES 

We recover executable, functionally coherent components from existing software in six steps: each repository is parsed into program entities and relations; a dependency graph records what each entity requires; the graph is segmented into components whose boundaries are refined against neighbouring code, documentation, and tests; each candidate’s interface is inferred from its exported symbols and observed usage; the reachable tests, configurations, and documentation are collected into Vi and 

Xi, with local helpers internalized and external requirements recorded in Di; and the candidate is synthesized into a Code Primitive and validated in isolation, build, import, runtime, and test failures guiding boundary refinement until it is admitted or excluded. Mining is supplemented by implementations harvested from verified construction runs and by targeted web sourcing under the same requirements. ## 4 LEGO-REPO B ENCHMARK 

LEGO-REPO evaluates reconstruction of real Python packages from their public interfaces and native tests: generated modules must function together under the repository’s original execution environment. This targets repository-level integration rather than isolated function generation, localized repair, or unconstrained design from natural-language specifications. We collect GitHub repositories with at least 1,000 stars, an installable package, and a runnable test suite, yielding 522 

tasks after excluding security-sensitive projects. Each task freezes the repository commit, package interface, tests, environment, and reference test identifiers; original implementation files are removed before reconstruction. Full collection, inventory, and execution details appear in Appendices B–D. 4.1 DOMAINS AND DIFFICULTY

## 6 CONCLUSION 

We introduce Code Primitives , reusable software components that adapt their implementations, interfaces, and dependencies to target repositories, and LEGO , a framework that retrieves, coordinates, and verifies these primitives during repository construction. Across LEGO-REPO and three external benchmarks, LEGO improves all 13 evaluated backbones, with the largest gains coming from primitive construction and adaptation rather than retrieval alone. These gains persist under model substitution and corpus-disjoint libraries. We hope this work shifts repository-scale code generation from repeatedly rebuilding software capabilities toward accumulating, adapting, and reusing them. 9Preprint.

## A EXTENDED RELATED WORK 

Coding agents and repository-level evaluation. LLM-based software engineering has progressed from direct code generation toward agents that explore repositories, localize relevant code, plan edits, execute programs, and iterate from feedback (Chen et al., 2021; Jimenez et al., 2024; Yang et al., 2024; Zhang et al., 2024; Xia et al., 2024; Wang et al., 2025; Le et al., 2025). Evaluation has expanded accordingly, from standalone functions (Chen et al., 2021; Austin et al., 2021; Hendrycks et al., 2021; Zhuo et al., 2025) to repository context and cross-file dependencies (Liu et al., 2024; Ding et al., 2023; Li et al., 2024; Liang et al., 2025), repository repair and evolution (Jimenez et al., 2024; Le et al., 2025), and zero-to-one repository generation (Zhang et al., 2026b; Li et al., 2026a; Luo et al., 2026; Chen et al., 2026; Zhang et al., 2026a). Execution-guided refinement provides a complementary mechanism: CodeT (Chen et al., 2022) uses generated tests for candidate selection, Self-Debugging (Chen et al., 2024) revises from execution traces, and Reflexion (Shinn et al., 2023) carries verbal feedback across attempts. 

Software reuse, retrieval, and reusable abstractions. Reusable software components have long been studied in software engineering, where interface compatibility and adaptation cost determine whether reuse is preferable to rewriting (Szyperski et al., 2002). Learned systems extend this idea by constructing reusable libraries, abstractions, skills, or tools: DreamCoder (Ellis et al., 2021) alternates synthesis with library compression, LILO (Grand et al., 2024) augments learned abstractions with documentation, ReGAL (Stengel-Eskin et al., 2024) refactors programs into generalizable abstractions, and TroVE (Wang et al., 2024), LATM (Cai et al., 2024), and CRAFT (Yuan et al., 2024) build reusable tool or skill collections for later tasks. Retrieval-augmented code generation instead supplies existing source, documentation, or repository context to a generator (Lu et al., 2022; Zhou et al., 2022; Zhang et al., 2023), while AgentDistill (Qiu et al., 2025) and CODESKILL (Li et al., 2026b) extract reusable task-solving procedures from agent trajectories. More recently, Agent Primitives (Jin et al., 2026a) and Tool Primitives (Jin et al., 2026b) expose reusable agent behaviours and executable tools through agent-native retrievable interfaces. Across these approaches, however, the reused artifact is typically supplied as context or invoked through a fixed interface rather than incorporated into and adapted with the delivered repository. 

Key Differences. Our work differs from prior systems in three key respects. LEGO targets zero-to-one repository construction rather than editing an existing codebase, organizing planning, retrieval, adaptation, composition, and verification to produce a complete package from an empty tree. Unlike library-learning and retrieval-augmented methods that keep reused artifacts fixed or use them as context, Code Primitives become part of the delivered repository and adapt their implementations, interfaces, dependencies, and configuration to the target. The closest abstractions are Agent Primitives and Tool Primitives (Jin et al., 2026a;b), whose agent-native interfaces support invocation; Code Primitives instead provide an interface for adaptation, with their dependency closure and validation tests traveling with the component. Finally, LEGO-REPO evaluates an entire reconstructed package against the original repository’s native test suite under a common empty-package floor and original-source ceiling, rather than scoring a function, completion, patch, or resolved issue.

## E SCORING AND PROVENANCE CHECKS 

Same-pipeline ceiling. An installed package can expose capabilities unavailable to the recon-structed tree. In markupsafe the installed baseline passes 79 tests because installation compiles the speedups extension, and 41 of those tests skip without it. Prompt contract. A primitive is invoked with a fixed four-part payload and must answer in a fixed schema. It receives (i) its own primitive (Ci, I i, D i, V i, X i) verbatim; (ii) the requirement r as the 17 Preprint. backbone wrote it; (iii) a context slice naming the target module path, the symbols the module must export, and the signatures of the sibling components it must bind to; and (iv) the diagnostics e from the previous adaptation attempt, if any. It receives no part of the target’s native test suite, no other module’s source, and no part of the repository-level plan or repository-level diagnosis. It must return a complete replacement implementation, an updated contract and dependency record, a mapping from each carried test in Vi to kept / rewritten / dropped with a justification for each drop, and the execution log of Vi against the rewritten component. A return that fails to parse, omits a field, or leaves a kept test failing is rejected with the failure attached and re-requested up to 3 times; if it still fails, the requirement is returned for repository-level handling and counts as an unsuccessful adaptation in Table 17. Of the 4,412 primitive-accepted candidates, 712 are rejected at least once under this rule. Of these, 173 recover within the rejection budget, leaving 539 ultimately returned for repository-level handling. These are the same 539 unsuccessful adaptations in Table 17; the other 

3,873 candidates pass validation. 

A worked adaptation. The scoped editing control in Section 5.4 differs from a primitive exactly in this contract, so it is worth seeing one instance concretely. CodeFace entry cf-0412/schema-coercion 

was mined from marshmallow : 261 lines across 2 files, exporting a field-coercion dispatcher and its error type, with 14 carried tests. Across the snapshot, entries have a median of 214 implementation lines (p25 96 , p75 468 ) across a median of 2 files (p75 4), exporting 4 symbols and carrying 9 tests. Reconstructing pandera (Appendix K), LEGO issued the requirement “coerce untyped input to a declared field type, collecting per-field errors into one report rather than raising on the first failure; errors must carry a location path.” The primitive’s adaptation replaced the donor’s exception-per-field control flow with an accumulating error collector, renamed the exported error type to the target’s contract, moved the location path from a string to the target’s tuple representation, and dropped 3

of the 14 carried tests as donor-specific (they asserted on marshmallow ’s message formatting), rewriting 5 others against the new signatures and keeping 6 unchanged. The 11 retained tests passed on the rewritten component before it was handed back to repository-level composition, which then bound it to 4 sibling modules. A generic editor operating on the same retrieved file has no equivalent of that last check: it can produce the same rewrite, but it does not perform this carried-test check. This example illustrates the validation step studied by the 0.0338 forward carried-tests contrast in Table 19; the example itself does not estimate that contrast’s effect size. F.2 CONSTRUCTION STATE AND REVISION OPERATORS 

Section 3.4 states the construction loop compactly. The stages in full are as follows. 

Retrieval and Activation. Given request q and construction context Ct, LEGO derives a repository plan and decomposes the task into required capabilities together with their interface and dependency constraints. For each required capability, LEGO retrieves candidate primitives from CodeFace; the evaluated configuration returns the top two candidates per capability query. Their primitives produce relevance assessments and usage proposals (si, u i), after which activation selects primitives based on capability coverage and compatibility with the rest of the planned repository. Requirements without a suitable primitive remain outside the library and must be written from scratch. 

Primitive Adaptation and Collaboration. For each selected primitive, LEGO states the target requirements through its natural-language interface. The primitive then produces ePi, adapting the primitive’s implementation, interfaces, dependencies, and configuration while preserving its component-level validation contract. 

Repository Editing. The adapted implementations become part of the target repository. LEGO combines them with integration code and newly generated functionality, while resolving constraints that cross primitive boundaries, including API bindings, shared data representations and types, package dependencies, and configuration. Primitives handle local component adaptation; repository-level coordination remains outside the primitive. 

Execution and Feedback. LEGO executes the build checks and tests available in the target, supple-mented with unit and integration tests synthesized from the requirements and the recorded interfaces. 18 Preprint. 

Verification and Diagnosis. The execution evidence is assessed against task completion, build success, test pass rate, interface consistency, and code quality. Build failures and failing tests are determined by execution and are terminal for the round. Diagnosis attributes the observed failures to individual components or their interactions and returns revision guidance, which reactivates only the implicated primitives. The loop continues until verification succeeds or the budget of b = 5 attempts per module is exhausted. Formally, LEGO maintains a construction context Ct and decomposes the request into requirements 

Πt. Retrieval and primitive relevance assessments determine assignments At. The composition constraints cover interfaces, shared types, dependencies, and configuration. Diagnosis returns a decision vt and diagnostics ϕt, which update the construction context for the next revision:

## I CONFIGURATION DEFINITIONS 

Table 33 maps each configuration name to the mechanisms and source restrictions that define it. Every primary configuration uses the same 522 tasks and harness revision, and model sweeps change only the position named by the corresponding experiment. 

External systems and the task adapter. Each external row of Table 2 runs the system’s own released harness at a pinned release, with its default scaffolding, tool set, and stopping rules unchanged. We hold fixed only the task set, the execution environment, and the grading pipeline, and we score whatever tree the system leaves behind using Eq. 8 and the same provenance gate. Our task adapter performs one translation: it presents a LEGO-REPO task in the input format each system expects. For OpenHands and Claude Code, which accept a repository directory and a natural-language instruction, it supplies the reconstruction tree and an instruction naming the package prefix, the public interface, and the native suite. For SWE-agent and Agentless, which expect an issue and a repository to localize within, it emits a synthetic issue containing the same interface and suite and a tree in which the target 32 Preprint. modules are absent; localization therefore has nothing to find and both systems operate in a mode they were not designed for, which is why their rows are marked ‡ and are not read as statements about those systems’ capability. No system receives the frozen node identifiers, the floor and ceiling counts, or any CodeFace entry. 

External benchmarks: per-benchmark CodeFace filtering. For each benchmark in Table 9 we take that benchmark’s task list, resolve each task to its upstream repository, and remove from CodeFace every entry whose recorded source repository matches — by URL, by canonical name, or by known fork relation — any of those repositories, before any task is run. This removes 31 entries for RepoZero, 12 for RepoGenesis, and 24 for RepoCraft, and we additionally apply the MinHash filter of Appendix G.17 at threshold 0.6 against each external target’s original sources, removing 

47 , 19 and 38 further entries respectively. Under the resulting libraries the offline audit reaches 

34 .8% of RepoZero target modules, 29 .6% on RepoGenesis and 31 .4% on RepoCraft, against 61 .4% 

on LEGO-REPO. Each benchmark’s own metric, grading script, and published protocol are used unmodified; we do not map any external score onto the LEGO-REPO scale. 

Component removals. Removing diagnosis disables diagnosis-guided revision. Removing primi-tive adaptation passes retrieved implementations into repository-level composition without primitive transformation. Removing the whole library removes both retrieval and adaptation, which makes Feedback + Diagnosis the matched no-library reference. Library-source ablations separately restrict CodeFace to mined, web-sourced, and/or harvested entries. The File RAG control replaces CodeFace entirely: it indexes the raw source files of the same donor repositories with the same embedding model and retrieval depth, and returns whole files with no recovered boundary, no internalized helpers, no resolved dependency closure, no interface contract, and no carried tests. Everything downstream — the scoped generic editing, diagnosis, the attempt budget, and the grading pipeline — is unchanged, so the contrast isolates the primitive-construction pipeline of Section 3.3 rather than the retrieval mechanism. Structured-schema adaptation replaces the free-form adaptation request with a fixed structured pay-load: a typed field-mapping specification naming the target signatures, the symbols to export and the sibling bindings, with no channel for stating intent in prose. The primitive, its fields, the retrieval depth, diagnosis and the attempt budget are unchanged, so the contrast isolates the request channel. Two further controls change what the retrieved primitive is permitted to become (Table 6). Import 

+ Call copies the selected primitive unchanged into a vendor/ package outside the target source prefix, exposes it on the path, and instructs LEGO to import and call it; adaptation is never invoked and the primitive’s implementation is byte-identical to its CodeFace entry. Because the target modules are still generated by the backbone, the provenance gate of Eq. 9 is unchanged, and a delivered tree whose target modules are thin wrappers over vendor/ is admissible — which is the point of the control. Context-only performs the same retrieval and relevance assessment but places the primitive’s implementation, contract, and carried tests in the repository-level prompt as read-only reference; no file from the primitive reaches the delivered tree, and LEGO writes every delivered line. Both controls keep diagnosis, the attempt budget, the retrieval depth, and the grading pipeline unchanged. Same-repository donor exclusion is different: for each target it filters entries by source repository while leaving the evaluation tasks unchanged.

## K THREE REPOSITORY CASE STUDIES 

Table 34 illustrates positive transfer, negative transfer, and shared integration failure. None of these examples uses a retrieved entry attributed to the target repository itself. 

Positive transfer: pandera . This D5 task has 105 modules, ceiling 1,807 , and floor 1,577 ,leaving 230 tests in the normalized span. The unusually high floor is a property of the target: its suite is parametrized across several dataframe backends, and a large share of those parametrizations resolve to a skip or to a backend-availability assertion that passes without any reconstructed validation logic. The feedback baseline earns about 5 tests above the floor and LEGO earns 183 . The offline audit covers 61 of the 105 modules ( 58 .1% ); the retrieved material comes from 15 donor repositories, including 17 adapted primitives from marshmallow , whose field-coercion and error-collection components carry over to a schema-validation target with signature changes but no change of purpose. The example illustrates why floor subtraction matters and how validation logic transfers across repositories that share a problem rather than a codebase. 

Negative transfer: markdown . The offline audit covers four of this task’s 32 modules ( 12 .5% ), with candidate material coming from five donor repositories. LEGO passes 9 of 111 tests where Feedback passes 74 . Inspection points to incompatibility with the target’s extension and registry protocol: apparently relevant text-processing components still require repository-specific integration. This example illustrates one of the 84 task-level regressions in Table 21; it is not intended as a population-level explanation of all regressions. 

Shared integration failure: haystack . The offline audit covers about 145 of the task’s 298 

modules ( 48 .7% ), with candidates from 30 donor repositories, yet neither configuration produces an importable package and both score zero against a 5,876 -test ceiling. The failure is not in any individual component but in the target’s plugin registry: components are discovered through a decorator that registers them into a global type index, and a tree in which that index is incomplete does not import at all, so the suite cannot be collected and no partial credit is available. Substantial reusable coverage therefore does not by itself guarantee repository-level integration, and on targets whose module graph has a single point of failure the delivery score is all-or-nothing. 

## L LIMITATIONS AND THREATS TO VALIDITY 

Several limitations qualify our conclusions. LEGO-REPO evaluates Python package reconstruc-tion from supplied interfaces and native tests, so a score of 1 reflects agreement with the original 34 Preprint. package under the frozen suite rather than complete semantic correctness, maintainability, or un-constrained architecture design. The difficulty bands depend on hand-set coefficients, and most backbone, role, domain, and difficulty comparisons are single-sample, although repeated-seed and corrected statistical analyses are provided for the primary configurations. CodeFace provenance is another important threat: harvested primitives can descend from benchmark-related construction runs, and repository-level exclusion cannot eliminate forks, vendored copies, near-duplicates, or model-pretraining contamination. Because Section 5.4 filters by target repository only, one eval-uation task can also supply verified primitives to another; such cross-task entries remain eligible. Stricter mined-only and fully disjoint CodeFace variants retain the qualitative gain but reduce its magnitude, particularly on the hardest tasks. External-benchmark improvements are likewise smaller than on LEGO-REPO, so we claim transfer in direction rather than magnitude. Several retrieval and library controls are our implementations of prior design patterns rather than published systems, and diagnosis-guided revision itself is not novel. The generic-editing and raw-source controls change component fields together, while sequential field increments depend on the comparison configuration and addition order; these contrasts measure combined changes and conditional increments rather than independent causal contributions. The experiments evaluate complete self-adapting components with carried validation. LEGO can also regress when reused components interact poorly with plugin, registry, or entry-point protocols. Finally, adapted primitives are incorporated into the delivered source, so donor-license obligations may propagate; CodeFace records provenance and licenses but does not enforce compatibility. Exact historical replay is also not guaranteed because some dependencies resolve against live package infrastructure.

## P PROMPT TEMPLATES 

This section provides the system prompts used by the three LLM-based positions in LEGO: retrieval and activation, Code Primitive interaction, and verification and diagnosis. Task-specific requests, retrieved candidates, primitive states, repository context, and execution evidence are inserted into the corresponding placeholders during inference. Retrieval itself and repository execution are performed outside the LLM; their results are supplied to the corresponding prompted component. 37 Preprint. P.1 RETRIEVAL AND ACTIVATION PROMPT 

Retrieval and Activation System Prompt Role. You are the retrieval and activation module in LEGO, a repository-construction framework built on reusable Code Primitives. Your responsibility is to analyze a repository-construction request, determine which reusable capabilities are needed, retrieve the Code Primitives that may provide those capabilities, and activate the smallest mutually compatible set of primitives needed for the current construction round. You reason at the repository level. You determine what components the target repository requires and which capabilities should be delegated to Code Primitives. Individual Code Primitives assess their own relevance and, once activated, adapt the components they own. 

Inputs. You may receive: • Construction Request : the repository or package to be constructed; • Target Interface : required modules, exported symbols, signatures, and documented behav-ior; • Construction Context : the current repository state, previously constructed components, recorded interfaces and dependencies, and decisions from earlier rounds; • Previous Diagnosis : observed failures, implicated components, and revision guidance from the previous round, when available; • Candidate Assessments : for each retrieved candidate Code Primitive, its relevance assess-ment and usage proposal (si, u i).

Repository Analysis. Analyze the construction request and identify: • the modules and components required by the target repository; • the responsibility and expected behavior of each component; • the public interfaces and exported symbols that must be provided; • dependencies and interactions among components; • shared types, data representations, configuration, and package-level constraints. 

Capability Decomposition. Decompose the request into an ordered set of capability require-ments 

Πt = ( r1, . . . , r K ).

Each requirement should specify: • the reusable capability that is needed; • the target component in which that capability will be used; • the interface and behavior it must expose; • dependencies it may assume; • relationships with other required capabilities. Requirements should describe the functionality needed by the target repository rather than assume a particular existing implementation. 

Primitive Retrieval. For each capability requirement rk, identify what kind of Code Primitive should be retrieved from CodeFace. Formulate the retrieval request around the required capability, interface, and dependency constraints. Use the returned candidates to determine whether CodeFace contains a reusable component that can satisfy the requirement. Do not retrieve primitives merely because they are lexically similar to the request; the retrieved capability must be useful for the planned repository. 

Candidate Assessment. Each retrieved Code Primitive reports: • a relevance assessment si describing how well its capability matches the requirement; and • a usage proposal ui describing how it could be adapted and incorporated into the target repository. Use these assessments together with the repository plan when deciding which candidates to activate. 

Activation. Select an activation set At based on: • coverage of the capability requirements in Πt;• compatibility with the required target interfaces; • mutual compatibility among selected Code Primitives; • dependency and configuration compatibility; • interactions with components already present in the repository. 38 Preprint. Activate only the Code Primitives required for the current construction round. A candidate that matches a requirement individually should not be activated if its interfaces, dependencies, or assumptions conflict with the rest of the planned repository. If no suitable Code Primitive covers a requirement, assign that requirement to task-specific code gt rather than forcing reuse. 

Adaptation Assignment. For every activated Code Primitive, produce a localized natural-language requirement specifying: • the capability it must provide; • the target component or location; • required exports and signatures; • interfaces to other activated components; • relevant dependency and configuration constraints. Provide only the repository context required for that primitive to adapt its own component. 

Revision. When diagnosis feedback is available: • preserve requirements and components not contradicted by the new evidence; • reconsider requirements associated with the implicated components; • reactivate only the Code Primitives required by the diagnosed failure; • retrieve or activate an additional primitive only when the evidence reveals a previously missing capability or dependency; • prefer targeted revision over reconstructing successful components.

Your responsibility is to interpret execution evidence from the current repository, determine whether the current construction satisfies the requested task, localize remaining failures to components or their interactions, and provide targeted revision guidance.

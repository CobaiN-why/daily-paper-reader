## 摘要
编程智能体的评估通常力求尽可能真实。在我们的研究中，我们收集了真实软件工程师在 JetBrains IDE 中的 4,782 个智能体会话，我们称之为生产会话（Production Sessions）。由于我们的研究对象是交互式智能体，我们研究了至少包含三条用户消息的会话（占样本的 33%）。这些长会话与源自 issue 的基准任务在两方面不同：(i) 用户请求涵盖远为广泛的任务类型组合——关于项目代码的提问、规划、评审、重构、执行——以及 (ii) 用户在整个会话中会在不同类型之间切换。来自三个公开交互语料库的长会话样本展现出显著不同的任务流（会话长度、任务类型以及类型间转移的分布），因此没有任何单一的交互分布是普遍真实的：基准应明确指定目标用例，并依据来自该用例的测量进行校准。我们提出 SWE-TaskFlow，一种用于转换任何源自 issue 的基准的方法：它保留已验证的任务和测试，同时通过提示拆分和可验证的仓库问答（QA）将交互引导至目标任务流，并使用任务流对齐分数（TaskFlow Alignment Score, TFAS）在生成的轨迹之间进行选择。在一项针对 700 个 SWE-Bench Pro 任务的试点中，以多个步骤顺序求解任务会使智能体成本大约翻倍，而解决率没有稳定变化：交互协议本身是评估的一个重要维度。

## Abstract
The evaluation of coding agents generally strives to be as realistic as possible. In our study, we collect 4,782 agent sessions of real software engineers in JetBrains IDEs, which we call Production Sessions. Since our subject is interactive agents, we study the sessions with at least three user messages (33% of the sample). These long sessions differ from issue-derived benchmark tasks in two ways: (i) user requests span a far wider mix of task types - questions about the project's code, planning, review, refactoring, execution - and (ii) users switch between types throughout a session. Long-session samples from three public interaction corpora exhibit markedly different Task Flows (the distributions of session lengths, task types, and type-to-type transitions), so no single interaction distribution is universally realistic: benchmarks should name a target use case and calibrate to measurements from it. We present SWE-TaskFlow, an approach for transforming any issue-derived benchmark: it preserves the verified tasks and tests while steering the interaction toward a target Task Flow through prompt splitting and verifiable repository QA, with a TaskFlow Alignment Score (TFAS) for selecting among generated trajectories. In a pilot on 700 SWE-Bench Pro tasks, solving the task sequentially in several steps approximately doubles agent cost without a stable change in resolve rate: the interaction protocol itself is an important dimension of evaluation.

# 论文总结：Coding-Agent Benchmarks Should Match Their Users' Task Flows

## 1. 核心问题与研究动机

- **背景**：编码智能体（coding agent）评测领域普遍追求"尽可能真实"，但"真实"本身缺乏明确定义。主流基准（SWE-bench 及其后继 SWE-Bench Pro、SWE-rebench、DeepSWE 等）均由 GitHub issue 派生：给出一条精心撰写的完整 issue，智能体产出一个补丁，最终以测试通过与否给出单一终局分数。
- **核心质疑**：这类基准的**基础设施与测试很有价值，但其"交互层"失真**——它测量的是"依据 upfront 规格实现需求"，而非"在会话中适应逐步展开的需求"。
- **实证依据**：作者采集 JetBrains IDE 中 4,782 个真实工程师与智能体的会话（称为 **Production Sessions**，约 14,000 条用户消息），聚焦至少含 3 条用户消息的长会话切片（占样本 33%）。发现两点关键差异：
  - **任务类型分布差异大**：SWE-Bench Pro 中 new-feature（54.7%）与 bug-fix（39.1%）合计占 93.8%；而 Production Sessions 中这两类合计不足一半，其余为解释代码、提问、规划、评审、重构、执行等。
  - **会话内任务类型会切换**：用户往往从功能请求开始，接着问现有行为、进入规划、再请求评审。issue 派生基准完全忽略了这种转移结构。
- **进一步发现**：将同一分类管线应用于三个公开交互语料（SWE-chat、SpecStory、DataClaw）后，得到的 Task Flow 彼此明显不同，说明**不存在"通用的真实交互分布"**。
- **论文立场（核心论点）**：不存在普遍真实的编码智能体基准；基准构建者应**明确声明目标用例、测量其 Task Flow，并据此校准基准的交互层**。

## 2. 方法论

### 2.1 Task Flow 的形式化定义

- Task Flow 被定义为一个三元分布组 **(P_L, P_T, P_R)**：
  - **P_L**：会话长度分布；
  - **P_T**：消息上的任务类型分布；
  - **P_R**：相邻消息之间任务类型的有向转移分布（保留标签直方图丢失的顺序信息）。
- **分类管线**：每条用户消息由开源权重 LLM（Gemma 4-31B）独立分类到 16 类意图之一（bug-fix、new-feature、explain、question、planning、debug、code-review、refactor、execute、transformation、generate-docs、tests、data-analysis、greeting、meta-question、other）。同一管线、同一提示、同一标签定义应用于 Production Sessions、公开语料和基准提示，保证可比性。

### 2.2 SWE-TaskFlow：对已验证任务的转换

核心思想是**不重新采集任务**，而是在保留原有仓库状态、执行环境与测试验证器的前提下，**只重新生成交互层**。两种增强手段：

- **Prompt Splitting（提示拆分）**：针对 issue 文本"过度规格化"的问题，将一个完整 issue 拆成 K 个有序、自足的连续用户轮次（本文 K=3，相邻部分可合并）。拆分器必须满足契约：保留全部原始需求、不引入新需求、技术性产物逐字不变、每一轮在先前轮次留下的仓库状态下可执行。不满足的原子性 issue 保持单轮。731 个公开 SWE-Bench Pro 任务中保留 700 个。
- **Repository QA（仓库问答）**：生成 0–3 个可验证的仓库行为问题，注入基准缺失的 explain 意图。问题来源于"解决原 issue 的智能体轨迹 + 实时仓库状态"，每个候选问题必须：
  - 可从仓库回答；
  - 在 issue 补丁前后均保持有效；
  - 不泄露解法；
  - 通过一个在干净仓库副本中执行的**可执行证明脚本**（creation-time proof）。
  
  问题放置位置（issue 轮之前、之间、之后）决定出现哪些类型转移。两种增强合计产生每任务 1–6 个用户轮次，其中 ≥3 轮的构成"长会话切片"。

### 2.3 TaskFlow Alignment Score (TFAS)

- 对三个分量 k ∈ {L, T, R}（长度分箱、任务类型、相邻转移），设 P_k 为目标分布、Q_k 为基准候选轨迹分布：

  - **S_k = 1 − JSD₂(P_k, Q_k)**
  - **TFAS = 100 · (S_L · S_T · S_R)^(1/3)**

- 其中 JSD₂ 为以 2 为底的对数下的 Jensen–Shannon 散度：JSD₂(P,Q) = ½KL₂(P‖M) + ½KL₂(Q‖M)，M = (P+Q)/2。
- 取值范围 [0, 100]，100 表示三个分布完全匹配。
- **细节约束**：长度分箱为 1, 2, 3, 4, 5, 6–10, 11+；任务类型仅用 16 类中可实例化为仓库任务的 **13 类**（排除 greeting、meta-question、other）；转移计算前先过滤不可实例化消息，并加入显式 START/END 边。
- **候选选择**：对每个源任务枚举可行的增强组合（拆分的合并层级、QA 数量与放置），在任务数与多样性约束下最大化 TFAS，用随机化局部搜索求解；要求**每个分量分数随聚合分数一同报告**。

### 2.4 逐轮可验证信号

- Single 轨迹只产生 1 个二元信号；Split+QA 轨迹在每个 issue 轮后产生一次测试套件判定（仅针对迄今已揭示的需求计分），每个 QA 轮产生一次被评判的答案。
- 更密集的验证信号支持更细粒度的诊断与基于排序的训练。

## 6. 主要结论与发现

1. **交互层本身是评测的重要维度**：在 700 个 SWE-Bench Pro 任务上，分步顺序求解（Split）使 agent 成本约翻倍，但 resolve rate 的变化因模型而异、且与运行间波动相当，**未建立稳定的成功排序**。
2. **校准 QA 轮次可显著提升对齐度**：TFAS 从纯 Split 的 **59.6** 提升到 **77.8**（QA-first 75.8、QA-last 75.6、QA-random 77.1）；优化主要贡献的是转移对齐（S_R 从 58.2 → 68.8），长度分量 S_L 从 49.1 → 84.0，任务类型分量 S_T 从 74.0 → 81.5。
3. **原始单轮提示对三消息目标得分为 0**：因为其长度分箱在目标分布中质量为零，几何平均坍缩为零——说明 issue 派生基准在长度维度上与真实用例完全不匹配。
4. **QA 轮次不改变任务难度**：放置消融显示各策略的 resolve rate 无一致排序、与运行间波动相当；答案准确率也无一致方向性变化（GPT-5.4 Mini 78.1–86.8%、GPT-5.6 Luna 86.6–93.8%、GPT-5.6 Terra 93.8–98.2%）。这为 TFAS 优化"在不改变测量内容的前提下移动问题位置"提供了许可。
5. **QA 问题确实可在不做 issue 工作的情况下回答**：QA-only 条件成本极低，Luna 仍达 86.8% 准确率，符合生成契约（问题在补丁前后均有效）。
6. **Checkpoint 级信号有效**：Split 轨迹在每个 issue 轮后可重新运行测试套件，resolve rate 与 test-pass rate 随轮次稳步增长，而三种 QA 放置的曲线几乎重合——正是交互层旨在暴露的逐轮信号。
7. **目标不同则最优变体不同**：以 SWE-chat 为目标时（Table 3），各条件排序与 Production 目标不一致，进一步佐证"必须声明目标"。
8. **公开语料不能互相代表**：SpecStory 最接近 Production Sessions 但 planning 占比更高；DataClaw 由 execution 与短操作轮主导；SWE-chat 由 execution 与 planning 主导。

## 7. 优点

- **问题意识清晰且有实证支撑**：用 4,782 条真实会话、约 14,000 条用户消息的实测数据把"真实"从模糊口号变成可测量的分布，并用同一管线处理所有语料保证可比性。
- **不丢弃既有投资**：SWE-TaskFlow 保留已验证的仓库状态、环境与测试验证器，只重写交互层，复用成本低、可比性强。
- **可优化、可分解的对齐指标**：TFAS 用三个分量的几何平均，强制报告分量分数，避免单一聚合分数掩盖某一维度的严重失配。
- **严格的可验证性约束**：QA 问题必须携带隐藏参考答案、证据链，并通过在干净环境执行的证明脚本；不满足者被排除，构造性地限制了可接受问题空间。
- **消融设计有针对性**：Concat 控制分离"改写效应"与"顺序披露效应"；QA 放置消融为 TFAS 优化的合法性提供了必要前提检查。
- **逐轮验证信号**：把单一终局分数变成每个 issue 轮的测试判定 + 每个 QA 轮的答案评判，支持更细粒度诊断与 ranking-based 训练。
- **可复现性承诺**：全部生成任务以公开数据集发布（Hugging Face，每个实验条件为独立 split），附内容哈希与来源清单，保证精确复现。
- **伦理处理谨慎**：只报告匿名聚合统计，不发布原始会话文本；公开语料仅以聚合图呈现。

## 8. 不足与局限

- **统计强度不足**：每个条件仅 3 次运行，报告 min–max 而非置信区间，无显著性检验；resolve rate 的结论只能是方向性的。
- **分类器缺乏真值**：16 类意图分类无人工标注测试集，76.1%

的模型间一致率衡量的是稳健性而非准确性，无法排除系统性误分类对目标分布本身的影响——若分类器对某些意图存在偏好性偏差，则 P_T 与 P_R 的校准目标也会随之偏移。
- **目标分布的代表性有限**：Production Sessions 仅来自 JetBrains IDE 生态，且只取 ≥3 条用户消息的长会话切片（占样本 33%），短会话与其它 IDE、CLI、CI 集成等使用形态未被覆盖；作者也承认"长会话只是一种用例"。因此 TFAS 的高分只意味着"对齐到这一特定人群的这一类会话"，不应被解读为普适真实。
- **基准侧的可实例化裁剪**：任务类型被从 16 类裁剪为 13 类，greeting、meta-question、other 被排除；这类交互在真实会话中确实存在，但难以在仓库任务环境中实例化。这意味着 TFAS 度量的是"可实例化子空间上的对齐"，而非完整 Task Flow 的对齐。
- **拆分与 QA 的覆盖损失**：731 个任务中仅 700 个可拆分，约 4% 的原子性 issue 被迫保持单轮，使这部分任务在长度维度上天然无法对齐目标；QA 问题的难度与风格完全取决于生成器（Terra），缺少对问题质量的上界保证。
- **TFAS 的构造性依赖**：三个分量等权几何平均、长度分箱方式、13 类标签体系、START/END 边处理等均为作者的设计选择，未见敏感性分析；不同设计可能给出不同的最优变体与不同的绝对分数，跨论文比较 TFAS 数值的可行性有限。
- **优化目标与能力测量的张力**：TFAS 通过移动 QA 轮位置来提升对齐度，虽然放置消融显示难度未变，但"为对齐而优化交互序列"仍可能引入与真实用户行为不同的规律性（例如问题分布过于均匀、转移模式被系统性塑形），存在过拟合目标分布的风险。
- **成本维度未纳入目标函数**：Split 使成本约翻倍，但 TFAS 不包含成本分量，也未讨论在给定预算约束下如何权衡对齐度与评测开销。
- **评测规模与结论边界**：如第 5 节所述，3 次运行、无显著性检验，使得论文只能主张"交互层是变量"，而不能主张任何模型或方法的优劣排序；作者对此有明确自陈，属于诚实但受限的结论强度。

## 9. 对领域的影响与可操作建议

- **核心方法论主张**：基准不再是"真实/不真实"的二元判断，而是一个需要**显式声明目标用例 → 测量其 Task Flow → 校准交互层**的三步流程。这把"真实性"从修辞转化为可审计的工程规范。
- **对基准构建者的具体建议**：
  1. 在论文与数据集卡片中显式写出目标用户群体与目标会话形态（如"IDE 内多轮长会话"），而非笼统声称"真实世界任务"。
  2. 报告 P_L、P_T、P_R 三个分布及其与目标的逐分量分数，避免用单一聚合数字掩盖失配。
  3. 区分"基础设施真实性"（仓库、环境、测试）与"交互层真实性"，二者可独立演进——本文正是复用前者、重写后者的范例。
  4. 保留逐轮可验证信号（每轮测试判定 + 每轮答案评判），使评测支持诊断与排序训练，而不只是终局二元分数。
- **对基准使用者的启示**：引用某个基准的分数时，必须同时说明该基准对齐的是哪一类 Task Flow；跨基准比较分数在交互层不同时缺乏意义。
- **对评测经济性的启示**：顺序披露会显著抬高 agent 成本，评测设计需要在"更贴近目标交互"与"可负担的评测规模"之间显式取舍，而非默认沿用单轮低成本协议。

## 10. 总体评价

本文的贡献不在于提出一个新的更强基准，而在于**把一个被长期默认的评测维度问题化**。其论证链条完整：先用真实会话数据证明 issue 派生基准在长度、任务类型、转移结构三个维度上系统性偏离真实使用；再给出可操作的形式化（Task Flow）、可优化的指标（TFAS）与低成本的改造方案（SWE-TaskFlow 的 Split + QA）；最后用消融证明改造过程本身没有显著改变任务难度，从而把"对齐"与"能力测量"解耦。

其局限同样清晰：统计强度弱、目标人群窄、分类器无真值、TFAS 设计选择未经敏感性检验。因此本文最稳妥的定位是一篇**立场与方法论文**——它成功地把"基准应当匹配用户任务流"确立为一个必须被回应的问题，并为后续工作提供了可复用的测量工具与改造管线，而非给出关于模型能力的结论。

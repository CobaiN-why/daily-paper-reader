## 摘要
随着 AI 智能体越来越多地承担复杂的仓库级编码任务，将工作分配到多个智能体上是超越单个智能体能力的自然扩展方式。为协调其相互依赖的工作，这些智能体会共享发现并就模块之间的接口达成一致。然而，所交换的信息往往仅作为上下文，仍需由各个智能体自行解读并将其纳入后续工作。因此，共享的发现可能未被使用，而对接口约定的偏离也可能无法被察觉，从而削弱协作的可靠性与效率。这促使我们将部分协调职责从单个智能体转移到执行框架。为使共享信息在执行过程中可直接发挥作用，我们提出了产物独占通信协议（AECP）。AECP 要求智能体仅通过结构化产物进行通信，并规定了执行框架如何处理这些产物。当智能体访问相关代码时，执行框架会提供相应的发现；它会筛查实现是否与记录的接口承诺不符，并要求受影响的智能体重新审视已修订的约定。这些协调步骤成为执行框架执行的一部分，而不再是智能体必须依据先前消息主动发起的动作。在 Doc2Repo、NL2Repo 和 CodeProjectEval 上，使用包括 Opus-4.8 和 DeepSeek-V4-Flash 在内的闭源与开源模型，相较于使用自由形式智能体间消息的智能体团队，AECP 将平均测试通过率提高了 28.2%，并将平均实际耗时减少了 16.5%。产物独占通信还能阻断恶意指令在智能体之间的传递，使其到达其他智能体的比例从 95% 降至 0%，使这些智能体据此采取行动的比例从 40% 降至 0%。

## Abstract
As AI agents increasingly tackle complex repository-level coding tasks, distributing work across multiple agents is a natural way to scale beyond the capabilities of a single agent. To coordinate their interdependent work, these agents share findings and agree on interfaces between modules. However, exchanged information often serves only as context, leaving individual agents to interpret it and incorporate it into subsequent work. Consequently, shared findings may go unused and deviations from interface agreements may go undetected, undermining the reliability and efficiency of collaboration. This motivates moving part of the coordination responsibility from individual agents to the execution harness. To make shared information actionable during execution, we introduce the Artifact-Exclusive Communication Protocol (AECP). AECP requires agents to communicate exclusively through structured artifacts and specifies how the harness processes them. The harness supplies findings when agents access relevant code, screens implementations for mismatches with recorded interface commitments, and requires affected agents to revisit revised agreements. These coordination steps become part of harness execution rather than actions that agents must initiate from prior messages. Across Doc2Repo, NL2Repo, and CodeProjectEval, using closed- and open-source models including Opus-4.8 and DeepSeek-V4-Flash, AECP improves average test pass rate by 28.2% and reduces average wall time by 16.5% relative to an agent team using free-form inter-agent messages. Artifact-exclusive communication also blocks the relay of malicious instructions between agents, reducing how often they reach other agents from 95% to 0% and how often those agents act on them from 40% to 0%.

### 1. 核心问题与整体含义

- **背景**：仓库级代码生成任务规模大、上下文负担重，单个 LLM 智能体难以独立完成，因此多智能体分工成为自然扩展方式。
- **问题**：现有多智能体系统主要依赖自由形式消息通信。共享发现和接口约定虽然被交换，但通常只作为上下文，仍需接收方智能体自行判断是否相关、是否采纳。
- **后果**：
  - 共享发现可能被忽略，导致重复探索。
  - 接口承诺可能被偏离，且偏离难以被及时发现。
  - 协作可靠性和效率下降；恶意指令也可能通过消息在智能体间传播。
- **核心主张**：将部分协调职责从单个智能体转移到执行框架（harness），让共享信息在执行过程中可操作、可检查，而不是依赖智能体主动回忆和解释消息。

### 2. 方法论：AECP 的核心思想与关键技术

- **总体思想**：提出 **Artifact-Exclusive Communication Protocol（AECP，产物独占通信协议）**。智能体只能通过结构化产物通信，所有交换都经过执行框架，由框架按规则处理。
- **工作流**：
  - 领导智能体将项目规格转化为模块计划，包括模块职责、公共符号和依赖关系。
  - 框架将计划表示为依赖图，并据此分配 worker；每个模块只有一个所有者。
  - worker 并行探索、实现和测试；领导最终集成。
- **两类核心产物**：
  - **Knowledge Artifact**：知识产物，形式为 \(a=\langle c,s,e,z\rangle\)。其中 \(c\) 是 claim，\(s\) 是适用 scope，\(e\) 是可选可执行 witness，\(z\) 是框架维护的 witness 状态。
  - **Contract Artifact**：契约产物，记录模块公开接口，包括符号名、种类、构造/调用方式、参数、返回结构、可观察属性、seam 信息等。
- **Knowledge Sharing 机制**：
  - worker 将发现写入 scope 关联的知识产物。
  - 当其他 worker 访问匹配代码时，框架按当前文件/符号/目录 scope 检索并投递相关发现。
  - 支持 witness 检查：witness 通过则标记为 witness-checked；被反驳则拒绝发布或撤下；未检查的仍可流通但带状态。
  - 检索限制：每次 lookup 最多 5 个产物，forward 最多 4 个，产物截断至 280 字符。
- **Contract Sharing 机制**：
  - 生产者声明接口契约，框架验证后生成可导入 stub，放置于最终模块路径。
  - 消费者可基于 stub 并行开发；生产者后续用真实实现替换 stub，消费者导入路径不变。
  - 静态验证器解析 AST，不执行代码，检查符号、签名、参数、注解、返回结构、共享属性、残留 stub 等。
  - 若证明与最新契约不符，则拒绝提交并报告违反的符号和约束。
  - 契约修订时，框架查找已注册依赖该符号的消费者，将其标记为 stale，并要求其阅读最新契约、重新注册依赖后才能完成任务。
- **算法规则概述**：
  - Knowledge Sharing：`PUBLISH` 运行 witness 并存储/拒绝；`ACCESS` 投递非反驳产物；`FLAG` 重跑 witness，必要时撤下。
  - Contract Sharing：`DECLARE` 验证并生成 stub；`REGISTER` 记录消费者；`REVISE` 更新契约、通知 stale 消费者；`SUBMIT` 检查 AST，违规则拒绝；`COMPLETE` 时若仍 stale 则拒绝。
  - 静态检查形式化：每个比较 \(q\) 给出 \(V_q(m,C)\in\{PASS, FAIL, ABSTAIN\}\)；若任一为 `FAIL`，整体为 `REJECT`，否则 `PASS`。

### 6. 主要结果与分析

- **隐藏测试通过率**：
  - AECP 在多数模型与 benchmark 组合上取得最高或接近最高的通过率，相较 Team-Freedom 与 Team-Integrator 均有提升，说明结构化产物通信有助于减少重复探索与接口偏离。
  - 在 NL2Repo 的 hard 分层上，协议带来的收益通常更明显，暗示协调开销在复杂任务中影响更大。
- **效率（wall time 与 token）**：
  - AECP 往往在通过率提升的同时不显著增加总 token，甚至因减少重复探索而降低浪费。
  - 但其引入的 orchestrator 侧检索、验证与 stale 管理会带来额外 token 与延迟，构成一种"协调成本换可靠性"的权衡。
- **对比基线行为**：
  - Team-Freedom 因消息需接收方自行判断相关性，易出现发现被忽略、接口承诺被偏离。
  - Team-Integrator 通过隔离与顺序合并获得一定的集成可靠性，但并行度受限、集成阶段可能成为瓶颈。
  - AECP 介于两者之间：既保留并行探索，又通过框架强制契约一致性与知识投递。
- **自适应团队规模**：
  - 改变 worker 数 \(N\) 时，收益并非单调随规模增长，存在协调开销与并行收益的平衡点。
- **恶意指令实验**：
  - 结构化产物与框架验证在一定程度上限制了恶意指令通过自由消息传播与扩散，reach 与 adoption 较自由消息配置更低。

### 7. 贡献与创新点

- **协议层面**：提出 Artifact-Exclusive Communication Protocol，将多智能体通信约束为两类结构化产物，并把部分协调职责从智能体转移到执行框架。
- **机制层面**：
  - Knowledge Artifact 的 scope 匹配检索与 witness 检查，使共享发现"可验证、可按需投递"。
  - Contract Artifact 的 stub 生成、静态 AST 验证与 stale 传播，使接口承诺"可执行、可检查、可追溯"。
- **方法层面**：以形式化规则（PUBLISH/ACCESS/FLAG、DECLARE/REGISTER/REVISE/SUBMIT/COMPLETE）描述协调行为，便于实现与验证。
- **实证层面**：在三个仓库级 benchmark、多个模型上与两类代表性多智能体基线系统对比，提供了协议有效性与协调权衡的证据。

### 8. 局限与未来方向

- **局限**：
  - 协议依赖静态验证器对接口约束的覆盖能力，对动态语义、运行时行为等难以完全静态判定的属性约束有限。
  - witness 机制的效果依赖 witness 的可执行性与覆盖范围，未检查产物仍可流通，可能带来残余风险。
  - 协调成本（检索、验证、stale 管理）在更大团队或更长任务中可能放大。
  - 实验未报告 GPU 级硬件细节与运行方差，复现成本与统计稳健性受限。
- **未来方向**：
  - 扩展契约语言以覆盖更丰富的接口语义与运行时约束。
  - 研究团队规模、模块粒度与协调开销之间的自适应调节策略。
  - 加强安全机制，进一步抑制恶意或错误信息在智能体间的传播。
  - 在更多模型、更多仓库规模与多次重复运行下验证结论的稳定性。

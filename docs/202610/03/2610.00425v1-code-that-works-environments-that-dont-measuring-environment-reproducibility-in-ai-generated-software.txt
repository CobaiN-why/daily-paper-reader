ABSTRACT 

Code generation has emerged as a central capability of large language models, with coding agents now able to produce function-ally correct software projects from natural language prompts. However, functional correctness alone does not capture a critical dimension of generation quality: environment specification, which is defined as the accurate identification of the dependencies re-quired to execute generated code, is equally critical. We develop an agent protocol for environment specification, and introduce a three-layer framework comprising declared , runtime-installed, and necessary and sufficient dependencies to systematically assess coding agents for environment specification. Using this protocol, we evaluate the extent to which coding agents systematically mis-specify software environment dependencies, and how does this misspecification vary across three agents, four languages, and fifty programming tasks. Our results show that current coding agents exhibit systematic generalization failures along this dimension, producing dependency specifications that are inconsistent, redundant, or incomplete in ways that functional tests do not detect. Across agents, dependency set agreement is as low as 7% for identical tasks, and newer agents show no meaningful improvement, suggesting the failure is not resolved by scale or recency. The largest divergence occurs between the declared ( 𝐷 (1) ) and runtime (𝐷 (3) ) dependency layers, implicating environment priors learned from the models’ training distributions as the primary driver. Our findings establish environment specification as a distinct, measurable axis of code generation quality that current bench-marks do not capture, and motivate training objectives and evaluation protocols that jointly optimize for functional correctness and environmental portability. 

1 Introduction 

Code generation has emerged as one of the most consequential ca-pabilities of large language models. Advanced coding agents [1, 2] can now synthesize complete, multi-file software repositories from natural language descriptions, representing a qualitative leap beyond the line-level autocomplete of earlier tools [3, 4]. However, the benchmarks used to evaluate these agents have not kept pace with their evolving capabilities [5, 6]. Current evaluation frameworks [3, 7, 8] focus almost exclusively on functional code correctness. They fail to measure the cor-rectness of the underlying software environment, such as depen-dencies, package versions, and system configurations, which is strictly required for execution. One might argue that code and its environment are two sides of the same coin, implying that traditional benchmarks implic-itly evaluate both. We counter that software environments are fundamentally distinct from source code. While code dictates logic, environments manage external, stateful ecosystems that are prone to silent runtime failures and complex version con-flicts [9, 10]. Consequently, evaluating environment generation requires a qualitatively different benchmarking paradigm. Before AI scientists build such benchmarks, we believe it is important to first systematically measure how effectively current agents specify these environments. To address this gap, this paper introduces a framework to eval-uate and quantify how reliably coding agents generate software environments. We propose an iterative evaluation protocol. First,

the agent is prompted to generate a complete software artifact containing both source code and its environment specification, establishing a baseline performance metric. Second, we evaluate the agent’s repair capabilities by forcing it to iteratively diagnose and resolve its own environment failures. The protocol ultimately determines the agent’s baseline accuracy, its self-repair efficiency, and the execution bottlenecks common to modern LLMs. Toward this goal, this paper introduces a novel evaluation frame-work to measure, assess, and quantify the quality of environment specifications generated by coding agents. We propose an itera-tive evaluation protocol divided into two primary phases. First, an agent is prompted to generate a complete software artifact comprising both source code and its environment specification, establishing a baseline metric for its initial generation capabil-ities. Second, if the initial environment is under-specified or broken, the agent enters a self-repair phase where it must itera-tively diagnose and resolve its own environment failures. Once an agent achieves a successfully executing artifact, the overall quality of the environment specified across all iterations is inde-pendently validated using application virtualization. By tracing the necessary and sufficient dependencies loaded into memory during runtime, our framework establishes an absolute ground truth, allowing us to explicitly measure the degree of dependency over-specification. Our framework thus provides a holistic, three-dimensional as-sessment: it benchmarks initial environment generation; quan-tifies the repair friction required to resolve under-specification; and exposes over-specification by comparing the agent’s declared dependencies against the lean, optimal runtime ground truth. We instantiate this framework in a controlled empirical study spanning three production coding agents, four language ecosys-tems, and 1,000 curated project instances. Each instance is exe-cuted in a clean, isolated environment with full dependency trac-ing from manifest through runtime. Using this rich dataset, we systematically characterize the root causes of environment speci-fication failures across different agents, programming languages, and task domains. Our results produce the first systematic evidence that depen-dency declarations are profoundly inconsistent across agents solv-ing identical tasks. Critically, we find that LLM environment generation is non-deterministic; a single agent rarely reproduces its own dependency choices across independent runs. In fact, the unanimous consensus rate for identical tasks across all languages is exactly zero. Furthermore, the gap between declared and actual runtime dependencies is wide, directionally biased, and heavily ecosystem-dependent. These variations implicate artifacts within the models’ training distributions rather than the inherent diffi-culty of the tasks themselves. Our earlier study [11] offered first evidence that agent-generated code is not reproducible at the dependency level; here we formalize the underlying evaluation protocol and measurement primitives, and expand the analysis across agents, ecosystems, and stochastic trials. These findings have direct, urgent implications for the repro-ducibility of agent-generated software and the validity of using agents for autonomous software engineering. Specifically, our study indicates that software environment configuration must be treated as a core target training objective for LLMs. Further-more, precision, recall, and F1-scores on dependency declara-tions—measured against traced runtime ground truth—must be treated as first-class evaluation criteria alongside functional code correctness. We make the following primary contributions: 

∙ Three-Layer Dependency Framework: We introduce a formal paradigm for evaluating coding agents by decoupling dependencies into three layers: what the agent declares , what the package manager installs , and what the program actually 

loads into memory at runtime. 

∙ Comprehensive Evaluation Dataset: We construct and open-source a dataset spanning three production coding agents, four language ecosystems, and 1,000 verified project instances, complete with execution traces in isolated environ-ments. 

∙ Empirical Analysis of Environment Failures: We deliver a systematic characterization of LLM environment genera-tion, proving that under- and over-specification represent systemic algorithmic gaps in training rather than isolated edge cases. The rest of this paper is organized as follows. Section 2 formalizes the agent evaluation protocol and defines the core agent capa-bilities required for environment specification. Section 3 details the primitive functions that underpin the three-layer dependency framework. Section 4 outlines our experimental design, followed by the evaluation dimensions in Section 5 and a comprehensive evaluation and metrics analysis in Section 6. Finally, Section 7 reviews related work, and Section 8 concludes the paper.

3 Protocol Primitives: Dependency Generation and Extraction 

We now describe the different primitives used in our protocol, namely how Gen and Repair are configured with prompts and tasks, and how ParseManifest , Resolve and Trace lead to 𝐷 (1) ,

𝐷 (2) , and 𝐷 (3) . Figure 2 shows the use of these primitives as part of an agentic pipeline that includes Gen and Repair .

3.1 Dependency Generation Primitives 

The quality of the results from Gen and Repair depends on two inputs: the complexity of the programming task 𝑇 and the de-sign of the prompt 𝜋 𝑇 . We address each through principled design criteria. Tasks are drawn from common real-world programming prob-lems, subject to two constraints: First, each task must be platform-independent i.e., implementable in every language under study so that cross-language comparisons are controlled at the task level rather than confounded by structural differences between tasks. Second, each task must also be self-contained, requiring no external services, APIs, or credentials, so that dependency failures are attributable to the agent and not to environmental inaccessibility. The prompt template instantiated for each task is shown in Figure 3. Every instance shares the same structure of task ti-tle, task description, and functional requirements. Further, there are two explicit framing instructions, differing only in the tar-get language runtime and manifest filename, so that cross-agent comparisons are controlled at the prompt level. The two framing instructions specify that the agent must generate a complete project for a clean environment; the clean environ-ment is language-specific and stated explicitly in every instance. Completeness is treated as an experimental variable instantiated in two prompt variations. In the implicit variant, no complete-ness specification is given, measuring the agent’s default behavior when a developer is succinct. In the explicit variant, the agent is instructed to produce source code, a dependency manifest cov-ering both direct and transitive dependencies pinned to exact versions, and a README — measuring behavior when a devel-oper is meticulous. These two extremes reflect the observation that real-world developer prompts cluster toward one or the other rather than occupying a graded middle ground. A prompt 𝜋 𝑇 is considered valid if the agent produces code that passes an accompanying test suite specified within the functional requirements. 3.2 Dependency Extraction Primitives 

Amongst the three extraction primitives ParseManifest 𝑙 ,

Resolve 𝑙 , and Trace , the first two are language-specific al-though we describe a generalized specification. The Trace 

primitive is language-independent, but relies on the clean environment. 

3.2.1 Parse Primitive 

A dependency manifest is a language-ecosystem-specific configu-ration file that formally declares the external packages a software project requires to execute, and serves as the input artifact that package managers read to install and resolve dependencies. In our framework, the initial manifest 𝑀 (0) is the agent’s explicit machine-readable claim of what the code needs in response to 

𝜋 𝑇 , while the final manifest 𝑀 (𝑘) is the manifest produced after iterative repair. 

ParseManifest 𝓁 comprises parsing rules and takes as input 𝑀 (0) 

to produce 𝐷 (1) , the declared dependency set. The parsing rules are language-specific and currently support four language ecosys-tems. For Python, it reads each line of requirements.txt and strips version constraints to normalize package names for cross-agent comparison. For Java, it extracts every <artifactId> from the <dependencies> section of pom.xml . For JavaScript, it reads the keys of the "dependencies" object in package.json , delib-erately excluding "devDependencies" since build-time tools are outside the runtime supply chain; this exclusion is applied consis-tently across all agents and tasks. For C++, it collects every library name from FetchContent_Declare and find_package calls in 

CMakeLists.txt . Note that C++ differs architecturally from the other three languages in that CMake does not have a canoni-cal package manager, which has implications for Resolve 𝓁 dis-cussed below. Each rule is a deterministic extraction from a single field of a for-mally specified file format and involves no heuristic inference; the complete parsing implementation is released in our artifact. Because the same manifests are subsequently consumed by each ecosystem’s package manager in the Resolve 𝓁 step, any system-atic parsing error would surface as a mismatch between 𝐷 (1) and the resolver’s reported dependency set during execution.

3.2.2 Resolve primitive 

The primitive Resolve 𝓁 determines 𝐷 (2) , the set of installed dependencies, within the isolated environment 𝐼 . The Docker instance that instantiates 𝐼 is built from a base OS image with the language runtime, i.e., compiler, interpreter, or virtual ma-chine, and the language-specific package manager. No additional packages are pre-installed beyond this toolchain baseline. Within 𝐼 , the primitive Resolve 𝓁 executes the final manifest 𝑀 (𝑘) ,causing the language-specific package manager to install both the dependencies explicitly declared in 𝑀 (𝑘) and any additional transitive dependencies they require. Resolve 𝓁 then queries the package manager for the complete list of packages installed in 𝐼 ,and reports this as 𝐷 (2) :

3.2.3 Trace primitive

It does however require that Resolve 𝓁 has succeeded, since a successfully installed program is a precondition for tracing.

4.1 Protocol Instantiation and Execution 

Programming Tasks 𝑇 . We instantiate the task set 𝑇 with 50 benchmark programming tasks spanning eight application do-mains, as shown in Table 1. Tasks are selected to satisfy the two criteria established in Section 3.1: platform independence, en-suring each task can be implemented identically across all four language ecosystems in ℒ, and self-containment, requiring no ex-ternal services, APIs, or credentials so that dependency misspeci-fication is attributable to the agent’s Gen and Repair skills rather than environmental inaccessibility. The eight domains are cho-sen to provide broad coverage of real-world software categories that developers routinely delegate to coding agents, ranging from data processing and cryptography to system utilities and scientific computing. The distribution across domains, which is weighted toward data processing and cryptography reflects the relative fre-quency of such tasks in open-source coding benchmarks [3, 7]. The 50-task scale is chosen to ensure statistical power for cross-agent and cross-language comparisons while remaining feasible for the fully manual execution protocol described below. 

Language Ecosystems ℒ. The language ecosystem set consists of ℒ = { Python , Java , JavaScript , C++ }. These language ecosys-tems are used for configurations of ParseManifest 𝓁 , Resolve 𝓁 ,and Trace defined in Section 3. These four ecosystems were selected to represent diversity in runtimes (interpreted vs com-piled), package manager design (centralized vs decentralized), and transitive resolution behavior ( 𝜌 ≫ 1 for npm vs 𝜌 ≈ 1 for CMake), enabling cross-ecosystem analysis of the environment specification gap. 

Coding agents 𝒜 . The agent set is 𝒜 = {𝑎 1, 𝑎 2, 𝑎 3}, instantiated as: 

∙ 𝑎 1: Claude Code (Anthropic, Claude Opus with extended thinking). 

∙ 𝑎 2: Codex (OpenAI, the latest Codex model via GitHub Copilot). 

∙ 𝑎 3: Gemini Code Assist (Google, Gemini with the highest reasoning configuration). These three agents are selected representing the current frontier of coding agent capability, covering the three dominant providers, and are accessed exclusively through their command-line inter-faces at default settings. This mirrors the experience of a devel-oper using these agents in practice. All agents receive the same prompt 𝜋 𝑇 for each task, with the iteration budget 𝑘 = 10 repair cycles specified in each agent’s configuration file as described in Section 2, yielding a maximum of 11 agent interactions per in-stance — one Gen call followed by up to 10 Repair calls. Further, agents preserve full history within the context window during the 

Repair cycle, enabling the agent to reason about the sequence of previously attempted repairs. 

Trial Structure and Study Scale. Every agent 𝑎 ∈ 𝒜 receives every prompt 𝜋 𝑇 for every task-language pair (𝑇, 𝓁) ∈ 𝒯 × ℒ ,yielding |𝒯| × |ℒ| × |𝒜| = 50 × 4 × 3 = 600 primary instances. To assess the stochastic variability of the Gen and Repair skills, 𝑎 1 is additionally executed for two further independent trials per task-language pair, each initialized from a fresh conversation with no memory of prior attempts, contributing 50 × 4 × 2 = 400 stochas-tic trials. 𝑎 1 is selected for variance analysis as it is the only agent achieving 100% final execution success (Section 6), guarantee-ing complete data across all task-language pairs for a statistically meaningful variance analysis. The total study scale is thus 1000 evaluation runs (Table 2). Section 3.1 defines two prompt variations: implicit , in which no completeness specification is provided, and explicit , in which the agent is instructed to produce source code, a pinned dependency manifest, and a README. Manual execution. All 1000 instances were conducted manu-ally, with each instance comprising a multi-turn interaction: the initial Gen prompt followed by up to ten Repair turns, for a max-imum of eleven agent interactions per instance (Table 2). This means the following actions were undertaken by hand: (i) the initial prompt and every subsequent repair turn were submitted to each agent’s CLI, (ii) generated artifacts were transferred into the Docker containers hosted on an AWS EC2 instance, (iii) run-time errors were transcribed verbatim into the ongoing agent conversation, and (iv) outcomes were recorded into structured CSV files. Automation was deliberately avoided since in our expe-rience the diversity of build failures across four ecosystems was too broad for reliable scripting, and an automated harness would either mask real failure modes through generic recovery heuris-tics or accumulate so many special-case rules that the harness itself would become a confounding factor, especially in the evalu-ation of the Repair skill. Once the manual execution of a project is completed and the necessary dependencies collected, each con-tainer is destroyed via docker run --rm and a fresh container is instantiated for the next programming task.

Trace . We realize Trace (𝐶 (𝑘) , 𝐼) using Sciunit [13], compiled from source and installed in every Docker image. Sciunit attaches to the target process via the Linux ptrace API and intercepts all 

open() , openat() , read() , and execve() system calls, writing the absolute path of each accessed file to a provenance log. READ -tagged entries are filtered using ecosystem-specific path rules to map accessed file paths to package names, enabling direct comparison with 𝐷 (1) and 𝐷 (2) .A critical implementation challenge arises for Java. LLM-generated Java projects frequently use the Maven Shade Plugin to produce a fat JAR bundling all dependency classes into a sin-gle archive. Under fat JAR invocation, the JVM issues exactly one openat() call for the archive itself, making the provenance log opaque to dependency analysis. Sciunit cannot determine which packages were loaded since all are bundled inside the same file. We refer to this as the fat JAR opacity problem . To resolve it, we replace fat JAR execution with classpath-based execution before tracing: dependency JARs are unpacked as physically sep-arate files via mvn dependency:copy-dependencies , and the program is traced against the unpacked classpath. With each JAR a distinct file, the JVM issues a separate openat() per loaded JAR, which appears individually in the provenance log. We verified that classpath-based execution produces functionally identical output to fat JAR execution in all traced cases. For C++ , the compiled binary is traced directly. At startup, the dynamic linker issues openat() calls for every shared library the binary was linked against. We retain .so entries and exclude the seven base system libraries loaded by every C++ binary re-gardless of application code: libc.so , libstdc++.so , libm.so ,

libgcc_s.so , libpthread.so , libdl.so , and librt.so , leav-ing only application-level libraries in 𝐷 (3) . The header-only library limitation noted in Section 3 is most acute here: 

nlohmann_json , the most frequently declared C++ dependency across all agents (65 successful manifests), is compiled directly into the binary and produces no .so file, and therefore no prove-nance log entry. For projects whose declared dependencies are entirely header-only, 𝐷 (3) = ∅ even when 𝐷 (1) is non-empty. We return to this limitation in Section 6.6.

6.4 Cross-Language Variation 

The preceding results consistently separate the four ecosystems, and we now draw the language-level picture together. Python is the easiest ecosystem to specify: it combines the highest first-attempt success, the lowest phantom rates, mild environment inflation ( ̄ 𝜌 Python = 2.06 ), and the best initial-manifest accuracy (macro F1 of 0.765). Java sits in the middle: first-attempt success is weaker, but its declaration quality remains high (macro F1 of 0.708) despite heavy transitive inflation. JavaScript is the patho-logical case on every specification metric: the largest inflation (̄𝜌 = 11.40 ), the highest phantom and hidden rates, the lowest manifest accuracy (0.219), and the weakest cross- and intra-agent agreement. Poor specification quality is therefore not merely an agent property; it interacts strongly with how aggressively an ecosystem’s package manager expands and obscures the declared set. C++ varies along a different axis: agents fail not because the resolver inflates their declarations, but because they assume system development libraries that the clean container does not provide. 6.5 Task Complexity Sensitivity 

Finally, we ask whether specification quality depends on what kind of software is being built. Figure 10 repeats the conver-gence analysis of Section 6.1 per task domain. Final success is at or near 100% in every domain (never below 95% for any agent– domain pair), and no domain is intrinsically hard for all agents: first-attempt success spans 40%–88% across domain–agent pairs, but the weakest domain differs per agent — System Utilities for Claude (40%), Image Processing for Codex (50%), and Data Pro-cessing for Gemini (48%), which is simultaneously the strongest domain for the other two agents. Convergence behavior is there-fore driven primarily by language ecosystem rather than by task domain: C++ is hard for every agent regardless of what the task computes. A sharper test of task sensitivity isolates the tasks that need no external libraries at all. Following Section 4, a subset of benchmark tasks in each language is identified a priori by the authors as entirely solvable with the standard library (e.g., Python’s csv , hashlib , and json modules; Java’s java.util and 

java.security packages; Node’s fs , crypto , and path built-ins). The unnecessary dependency rate (UDR) is the fraction of these standard-library-sufficient tasks for which the agent never-theless declared at least one external package. On these standard-library-sufficient tasks, Claude introduced ex-ternal packages in 91.8% of these tasks on macro average, reach-ing 100% in C++ and remaining at or above 84% in every other ecosystem. Gemini is similarly aggressive in JavaScript. Codex is much more conservative in Python and JavaScript, though it still adds unnecessary libraries in more than half of eligible C++ tasks. This result isolates over-dependence from task difficulty: the extra libraries are not required by the benchmark itself. Each unnecessary package is avoidable attack surface, mainte-nance burden, and audit scope added for zero functional gain, and on standard-library-sufficient tasks that cost is pure waste. Because the behavior persists on tasks where no library is needed, it reflects a generation prior rather than a response to task de-mands, which makes it a natural target for training objectives that reward minimal, sufficient environment specification alongside functional correctness. 

6.6 Limitations 

The strongest measurement limitation is in C++. Runtime trac-ing undercounts header-only and purely compile-time dependen-cies, which pushes C++ manifest precision and F1 downward relative to ecosystems where runtime loading leaves a clearer file-level footprint. Similarly, although C++ usually has |𝐷 (2) | ≈ |𝐷 (1) |, a small number of fetched projects recursively pull an ad-ditional library during their own build process, so exact equality should be interpreted as an ecosystem-level trend rather than as a strict invariant. More broadly, the study uses a controlled bench-mark of 50 tasks rather than fully open-ended real-world projects, so the reported rates should be interpreted as evidence about structured code-generation settings rather than as exhaustive es-timates for all software development contexts. All results are additionally conditioned on the prompt template of Section 3.1; because the template is held identical across agents and lan-guages, comparative findings are controlled at the prompt level, but absolute rates may vary under different phrasings, and a sys-tematic prompt-robustness analysis remains future work. The manual evaluation protocol and fixed annotations for standard-library tasks and C++ failure labels improve control, but they also introduce a degree of judgment that future larger-scale repli-cations should further test. Finally, because commercial coding agents evolve rapidly, the results should be understood as a snap-shot of the evaluated agent configurations at evaluation time rather than as immutable model properties. 

7 Related Work 

LLM Code Generation and Its Evaluation Gaps. The era of LLM code generation began with Codex [3], which solved 28.8% of HumanEval problems. Subsequent models such as Al-phaCode [8], StarCoder [14], Code Llama [15], and commercial agents like Claude Code [1], GitHub Copilot, and Gemini Code Assist [2] have expanded from single-function completion to full project synthesis. Surveys by Fan et al. [6] and Jiang et al. [5] cover this landscape comprehensively.  

> 12 of 16 AI Magazine , 2026

The critical gap in this literature is that nearly all benchmarks evaluate functional correctness of isolated snippets [3, 7]. A smaller body of work examines code quality [16], bug patterns [17, 18], and security vulnerabilities [4]. Ouyang et al. [19] studied non-determinism in ChatGPT’s code output but restricted their analysis to functional behavior; they did not examine whether de-pendency choices are stable across runs. Our stochastic analysis fills this gap directly: we show that a single agent’s dependency declarations are unstable across independent runs of the same task, with unanimous consensus rate zero across all tasks and languages — a form of non-determinism invisible to functional correctness metrics. Recent work has identified package halluci-nations , where models recommend packages that do not exist in registries, linked to practical supply-chain attacks [20]. Our work is complementary but distinct: we study the misspecification of 

existing packages, over-declaration, under-declaration, and tran-sitive blindness, which is a different and broader failure mode that persists even when every named package exists. None of this work examines dependency management as a first-class evalua-tion concern across the full lifecycle from declaration through res-olution to runtime execution. Our own earlier study [11] provided initial evidence of dependency gaps in agent-generated code; the present article formalizes the evaluation protocol underlying that study and extends the analysis. 

Dependency Ecosystems and Their Distinct Challenges. 

Software dependency management is not a uniform problem: each ecosystem has its own resolution semantics, transitive be-havior, and failure modes, and these differences matter pro-foundly for LLM-generated code. A key contribution of this paper is measuring these ecosystem-specific failure modes under a uni-fied framework, rather than studying any single ecosystem in isolation. We breifly review relevant works within each ecosys-tem: 

JavaScript/npm.. Zimmermann et al. [21] found that installing a median npm package transitively imports 79 packages main-tained by 39 individuals. The npm ecosystem’s deeply nested dependency graphs mean that a single declared package can pull in dozens or even hundreds of transitive dependencies, creating a vast and largely invisible attack surface. Decan et al. [9] con-firmed that npm exhibits the most aggressive growth and fragility among seven ecosystems studied. Our results quantify this ag-gression in the context of agent-generated code specifically: we observe a mean inflation ratio ̄ 𝜌 = 11.40 for JavaScript, with indi-vidual projects expanding a three-package declaration into over 140 installed packages, a transitive footprint no agent explicitly reasoned about. 

Java/Maven.. Soto-Valero et al. [22] found that 75.1% of Maven Central artifacts contain at least one bloated dependency — a li-brary declared in the build file but never used at runtime. Maven’s transitive resolution is opaque: a developer declares a handful of dependencies in pom.xml , and Maven silently resolves an entire tree of transitive artifacts. Wang et al. [10] further documented the risks of third-party library management in Java projects. Whereas these studies measure bloat in human-authored arti-facts, we measure it in agent-generated code where the selection decisions are made by a model rather than a developer, finding that bloat is pervasive and that agents show no awareness of the transitive footprint their declarations induce. 

C++/CMake.. C++ dependency management is fundamen-tally different from the other three ecosystems. There is no single dominant package manager; dependencies are handled through CMake’s FetchContent , find_package , or manual ven-doring. The key issue for LLM-generated code is the system library assumption gap : agents trained on code from rich development environments assume that system libraries such as libssl-dev 

or libopencv-dev are already installed. We provide the first systematic measurement of this assumption gap across multiple agents, showing that it accounts for the majority of C++ build failures and that its prevalence differs substantially across agents — implicating training distribution rather than task difficulty as the primary driver. 

Python/pip.. Python’s ecosystem is comparatively well-behaved for dependency management. The pip freeze 

convention produces exact version pins, and transitive resolu-tion is relatively flat. However, system library issues still arise for packages with native extensions — pyzbar requires libzbar0 

and opencv-python requires libGL.so — and our results show that even in this most tractable ecosystem, agents achieve macro F1 of only 0.765 against runtime ground truth, leaving meaningful specification gaps. 

Cross-ecosystem analysis. Kikas et al. [23] studied the struc-tural evolution of dependency networks in JavaScript, Ruby, and Rust. Cox [24] articulated the fundamental tension between code reuse and dependency risk. Supply-chain attacks exploiting de-pendencies are a major concern [25, 26], prompting government mandates for Software Bills of Materials [27, 28]. Our paper pro-vides the first cross-ecosystem comparison of dependency specifi-cation quality in agent-generated code, using a unified three-layer measurement framework that enables direct comparison across Python, Java, JavaScript, and C++ rather than treating each ecosystem as an isolated problem. 

Software Bloat and Unused Dependencies. Bruce et al. [29] found 14.8% of compiled Java methods unreachable. Quach et al. [12] proposed piece-wise compilation for C/C++ attack surface reduction. Soto-Valero et al. [30] showed that most transitive Maven dependencies have very low runtime utilization. These studies measure bloat in human-authored artifacts using static or coverage-based analysis. Our study is the first to measure dependency bloat in agent-generated code, where the selection decisions are made by a model rather than a developer, and to use dynamic runtime tracing as the ground truth rather than static reachability, capturing the actual runtime footprint rather than an approximation of it. 

Static vs Dynamic Dependency Analysis. Tools for automati-cally inferring dependencies from source code, such as pipreqs 

for Python, jdeps for Java, and import-graph analyzers more broadly, represent the non-agent baseline for dependency speci-fication. These tools use static analysis, which has known limita-tions: they cannot capture dynamically imported packages, condi-tionally loaded modules, or runtime-only dependencies exercised on specific execution paths. Dynamic tracing via system call inter-position addresses these limitations at the cost of execution-path specificity — capturing only dependencies exercised during a particular run. We use dynamic tracing via ptrace -based prove-nance capture [31, 32] as our runtime ground truth precisely because it captures what the program actually loads.

Software Bills of Materials and Manifest Accuracy. Regu-latory mandates for Software Bills of Materials [27, 28] have prompted a growing literature on SBOM generation accuracy and completeness [33, 34]. Existing SBOM generation tools operate on human-authored codebases; the accuracy of agent-generated manifests as SBOMs has not been studied. Our three-layer frame-work is directly applicable to this question: the declared depen-dency set 𝐷 (1) is precisely what an agent-generated SBOM would contain, and our precision, recall, and F1 measurements against runtime ground truth 𝐷 (3) provide the first empirical charac-terization of agent-generated SBOM accuracy. The finding that macro F1 ranges from 0.765 for Python to 0.018 for C++ has direct implications for the trustworthiness of agent-generated SBOMs in security-critical contexts. 

Computational Reproducibility and Provenance. Repro-ducibility remains a persistent challenge in computational sci-ence [35, 36]. Docker containers [37] capture static environment snapshots but cannot reveal what a program actually loads at run-time — a limitation that makes them insufficient as a ground truth for dependency analysis. Provenance-based systems go fur-ther. ReproZip [31] traces system calls to build reproducible archives. Sciunit [13] uses its PTU engine building on CDE’s system call interposition approach [38] to intercept open() ,

openat() , read() , and execve() via ptrace , recording every file accessed during execution. We use Sciunit as our runtime de-pendency oracle, extending its application from reproducibility packaging to dependency ground-truth extraction in the context of agent-generated code evaluation. 

LLM Evaluation Methodology. Beyond code generation specif-ically, our work contributes to the broader literature on LLM evaluation methodology. Holistic evaluation frameworks such as HELM [39] argue that model capabilities should be measured across multiple dimensions simultaneously rather than through single-metric proxies. Our three-layer dependency framework in-stantiates this principle for the code generation setting: rather than collapsing environment specification quality into a single pass/fail execution outcome, we decompose it into declaration ac-curacy, resolution behavior, and runtime footprint, each of which implicates a different failure mode and a different remediation. We argue that environment specification should be incorporated as a standard evaluation dimension in code generation bench-marks alongside functional correctness, and that the metrics introduced here - phantom rate, hidden rate, bloat rate, and manifest F1 - provide a reusable evaluation vocabulary for this dimension. 

8 Conclusion 

This study shows that dependency generation by current LLM coding agents is highly inconsistent and often misaligned with the environments their code actually requires. Although these agents can frequently repair projects to functional success, they do not reliably produce correct or minimal dependency specifi-cations. Our results directly answer the central research ques-tion: current LLMs systematically misspecify software environ-ment dependencies, and this misspecification varies substantially across ecosystems and across agents. The problem appears both as under-specification, where required dependencies are missing from the manifest, and as over-specification, where unnecessary libraries inflate the software environment. These findings have immediate implications for both research and practice. Success-ful code generation should not be treated as evidence of envi-ronment correctness without additional validation. More reliable and portable code generation will require evaluation frameworks, validation pipelines, and training objectives that explicitly target accurate and minimal dependency specification alongside task completion. One concrete direction is to treat dependency speci-fication as a first-class learning target: future systems could incor-porate environment-grounded fine-tuning, dependency-aware re-ward signals, or manifest-verification steps in iterative generation and repair loops so that dependency correctness is optimized alongside functional task completion.

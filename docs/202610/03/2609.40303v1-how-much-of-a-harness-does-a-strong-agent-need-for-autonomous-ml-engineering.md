## 摘要
近期，自主机器学习工程（MLE）智能体在公开排行榜上取得了显著进展。现代 MLE 智能体往往出于长时程周期中进展停滞以及大语言模型（LLM）原语有限的动机，被部署在日益复杂的机制之上：多智能体编排器、专用检索子智能体等等。尽管此类运行框架不断扩展，但使用更基础但经过改进的编码智能体——即 LLM 通过 read、write 和 bash 原语直接访问执行环境——这一方向在该领域却鲜有关注。本文发现，在相同时间预算和相同前沿 LLM 骨干模型下，开源的最先进运行框架相比仅使用单次会话的最小运行框架编码智能体基线没有任何优势，这表明骨干模型才是性能的主要驱动因素。通过一系列大规模系统性消融研究，我们认为在编码智能体设定下，这些机制层变得冗余。我们得出结论：围绕强模型精心打造手工运行框架的努力，对于当前 MLE 基准而言回报甚微。

## Abstract
Recent autonomous machine learning engineering (MLE) agents have made significant progress on public leaderboards. Often motivated by progress stagnation over long-horizon cycles and limited Large Language Model (LLM) primitives, modern MLE agents are deployed on top of increasingly elaborate machinery: multi-agent orchestrators, dedicated retrieval subagents, and more. While such harnesses expand, the use of more primitive but improved coding agents - where LLMs have direct access to the execution environment through read, write, and bash primitives - has received little attention in the field. In this paper we find that, under an equal time budget and the same frontier LLM backbone, open-source state-of-the-art harnesses provide no advantages over a single session of a minimal-harness coding agent baseline, pointing to the backbone as the primary driver for performance. Via a series of large-scale systematic ablation studies, we argue that the machinery layers become redundant in the coding agent setting. We conclude that the effort spent elaborating hand-crafted harnesses around strong models yields poor returns for current MLE benchmarks.

# 论文总结：强大的智能体在自主机器学习工程中需要多少运行框架？

## 1. 核心问题与整体含义

- **研究动机**：自主机器学习工程（MLE）已成为 LLM 智能体的重要测试床——解决方案是开放式 ML 流水线，单次评估可能耗费数小时昂贵硬件，反馈信号（验证分数）带噪声。自 Jiang et al. (2025) 将该问题框定为"代码空间上的树搜索"以来，主流设计一直是 **harness（运行框架）**：一个外层程序，向 LLM 查询代码、执行代码、并编排候选方案的探索与组合。
- **背景假设受到质疑**：这些复杂机制建立在两个前提之上：
  - ① 单次聊天补全无法运行自己写的代码、检查数据或对错误做出反应，因此 harness 必须代劳——但现代 LLM 已越来越多地针对工具使用进行后训练，可在 OpenCode 等编码智能体环境中读写文件、执行代码、自主调试。
  - ② MLE 被视为需要专用记忆和上下文管理的长时程问题——以墙钟时间计（24 小时以上）确实如此，但以 token 计则不那么明确，尤其在百万 token 上下文窗口变得可负担之后。
- **核心问题**：在编码智能体环境下，harness 的哪些部分仍然物有所值？
- **文献缺口**：现有发布结果几乎都在不同骨干模型和硬件下报告，种子数很少超过 3，主要差距可能小于运行间波动，导致难以将性能提升归因于 harness 设计。邻近领域（SWE-bench）的证据已暗示答案可能是"非常少"。
- **整体含义**：论文发现，在相同时间预算与相同前沿 LLM 骨干下，开源 SOTA harness 相比单会话最小 harness 编码智能体没有任何优势，骨干模型才是性能的主要驱动因素。这呼应了 Sutton 的"苦涩的教训"。

## 2. 方法论

### 核心思想
- 在**固定骨干模型、硬件、时间预算**的条件下，攀爬一个"harness 干预阶梯"：从聊天式迭代 → 多智能体编码智能体编排，所有干预都在同一代码库中重新实现，使唯一变量是干预本身。
- 阶梯终点是 **Malena**——一个经过良好提示的、带最小工具集的单次编码智能体会话，即"机器学习工程师智能体"基线。

### 关键技术细节

- **基础框架**：构建于 OpenCode v1.15.6 编码智能体框架之上。保留默认工具（read/write/edit/bash/task/todowrite），禁用 `doom_loop`、`plan_exit`、`question`，并用自己的 bash 实现覆盖原生版本（可控超时、资源统计、OOM 看门狗、命令白名单）。
- **三个原子迭代单元**：
  - **Chat**：LLM 通过聊天 API 单次调用，只接收任务描述和 harness 内联计算的数据概览（目录树、逐文件预览、CSV 列统计等），必须一次性输出完整解决方案脚本；失败时附带错误堆栈重新查询调试。
  - **Oneshot**：单次编码智能体会话，工作在含数据的目录中，自由使用文件系统与代码执行原语，产出 main.py、submission.csv、design.md、score.txt 四类交付物，由 harness 静态校验。
  - **Malena**：同一编码智能体环境，但会话跨越整个时间预算（而非单次生产运行），移除"仅一次生产运行"和文档要求，由智能体自主决定流水线数量与提交次数；harness 以轮次循环驱动，回合结束时若预算未尽则以短消息重新提示。

- **四类干预家族**：
  - **执行环境**：Chat（纯文本）vs. Oneshot（编码智能体环境）。
  - **搜索原语**：Chain（纯迭代改进）、Greedy（纯利用）、UCB1（探索-利用权衡，采用排名归一化分数与全局上确界选择规则）、Best-of-N（独立探索）。
  - **自主性**：Malena 单会话，让智能体自主驱动探索、利用与自身知识库。
  - **多智能体编排**：Delegation（分层规划-执行）、Parallelism（3 个并行 Malena 实例）、Broadcast（智能体间广播消息）。

- **UCB1 公式**：节点价值取子树最大备份 $\hat{s}(n) = \max_{n' \in \text{subtree}(n)} s(n')$，UCB1 索引为
  $$R(n) = \sigma(\hat{s}(n)) \cdot \frac{|V(T)| - 1}{|C(n)| + 1} + c\sqrt{\frac{\ln(|V(T)|+1)}{|C(n)|+1}}$$
  其中 $\sigma(x)$ 为 0 基排名，$c=0.75$，排名变换使单一常数可跨竞赛迁移。

- **最小工具集（Malena）**：submission 工具（注册提交，不泄露测试分数）、system 工具（返回硬件资源、利用率与剩余时间）、jobs 工具（后台运行、检查、等待、取消 bash 命令）。

- **统计协议**：宏任务平均，固定任务集上对种子自举得 95% 置信区间；配对逐任务差异比较，置信区间不含 0 则标记为统计显著。

## 3. 实验设计

- **主要 Benchmark**：
  - **MLE-bench**（Chan et al., 2025）：75 个 Kaggle 竞赛任务，本文聚焦 30 个任务子集（5 个 Lite、21 个 Medium、4 个 High）。分为 **default29**（原始 MLE-bench 子集，去掉 bms 和 alaska2）、**fixed30**（修复了 4 个有准备脚本问题的任务）、**fixed14**（去掉 Gemma4 能解的下限任务和 Kimi K3 解不出的上限任务）、**fixed10**（挑战性子集）。
  - **NatureBench**（Wang et al., 2026b）：40 个近期 Nature 系论文的开科学研究任务，每个任务提供可无限次查询的在线 `/evaluate` 端点，报告超越 SOTA 率（归一化增益 g > 0.1）。

- **对比方法**：四个开源 SOTA MLE harness——**MLEvolve**（UCT 树搜索 + 多种算子 + BM25/FAISS 检索记忆）、**AiScientist**（无搜索结构的单对话 + 文件即总线记忆）、**Arbor**（Coordinator/Executor + Idea Tree）、**ScienceFlow**（配置驱动 + 并行探索 worker）。

- **评估指标**：any-medal rate（奖牌率）、mean percentile（平均百分位）、self-select（智能体自选提交）vs. oracle（最佳隐藏测试分数），超越 SOTA 率。

- **骨干模型**：GLM 5.2（默认）、Kimi K3、DeepSeek V4 Flash/Pro（含 Preview 版）、Gemma 4 31B、GPT OSS 120B、Agents A1。

- **消融实验**：搜索策略（4 种）、自主性、多智能体编排（3 种）、基础设施（submission/system/jobs 工具、时间提醒、资源提醒、HuggingFace MCP、验证指南、技能、最小提示）、上下文预算约束、时间预算缩放、骨干模型对比、外部 harness 调优消融。

## 4. 资源与算力

- **智能体运行资源**：所有实验中智能体资源固定为 **1 × A100 80GB、12 CPU 核心、144GB RAM**。
- **骨干模型服务**：通过 vLLM 本地服务，使用 **8 × B200 或 8 × A100 80GB** 节点（较小模型）。
- **时间预算**：主要实验为 **24 小时**；Oneshot 单迭代默认 6 小时；NatureBench 扩展到 8 小时（其默认 4 小时的两倍）。
- **成本**：硬件成本主导整体开销——24 小时 A100 80GB 计算约 24–85 美元（取决于供应商）。以 GLM 5.2 计价，Malena 建模推理成本约 $12.12，约为 AiScientist（$1.95）的 6.2 倍，主要因单会话不断重发全部历史上下文导致缓存读取量高一个数量级。
- **种子数**：24 小时条件下每任务仅 3–4 个种子，6 小时和纯补全条件下每任务 6–10 个种子。

## 5. 实验数量与充分性

- **实验规模**：
  - MLE-bench 上 17 个 harness–骨干配对，NatureBench 上 6 个配对。
  - 大量系统性消融：搜索策略、自主性、编排、基础设施、上下文预算、时间预算、骨干模型、外部 harness 调优（MLEvolve 推理努力、ScienceFlow worker 数与资源准入、Arbor 执行器超时与收敛早停）。
  - 轨迹分析：对 10 个 MLE-bench 任务的检查点进行技术标签标注、去重聚类、稀有度与类别组成分析。
  - 污染检查：924,750 对 Malena-vs-real 与 473,850 对 real-vs-real 代码相似性对比，以及同任务的 62,207 / 33,465 对嵌入相似性对比。
- **充分性与公平性**：
  - **优点**：所有方法在相同硬件、时间预算、骨干下评估；采用配对逐任务统计以抵消任务难度差异；对外部 harness 进行了骨干兼容性 bug 修复与配置消融，并报告负面结果而非只报告正面调优故事。
  - **不足**：24 小时条件下种子数少（3–4），部分结果置信区间宽，无法就效应大小做强断言；部分比较（如 Malena vs. UCB1/Greedy 在百分位上）统计上不可区分；NatureBench 上 MLEvolve 的 `/evaluate` 调用次数少（中位数 8 vs. 16/18），可能在 oracle-best 指标上处于机械劣势。

## 6. 主要结论与发现

- **编码智能体环境是影响最大的干预**：Chat → Oneshot 带来最大性能跃升；即使是较弱模型（如 Gemma 4）也受益，说明工具使用流畅度比原始模型规模更重要；DeepSeek V4 正式版比 Preview 版提升更大。
- **搜索策略效果甚微**：Chain、Greedy、UCB1、Best-of-N 之间无统计显著差异（最大差距为 UCB1 领先 Best-of-N 2.71 个百分点，95% CI [−1.44, +6.60]）。Best-of-N 自选性能比其 oracle 天花板低 6.832 个百分点，为最大选择差距。
- **自主性最优**：Malena 单会话达到最高平均奖牌率，相对所有手动搜索算法有显著奖牌率优势（95% CI 下界 0.4%–5.6%），且验证差距最小（1.876 个百分点）。
- **多智能体编排收益有限**：Delegation、Parallelism、Broadcast 均未显著优于基础 Malena；并行虽提高 oracle 天花板，但选择差距扩大，最终自选提交质量相当。
- **对生产级 harness 的泛化**：在 MLE-bench 和 NatureBench 上，Malena 在每个前沿骨干下匹配或超越所有对比 harness。GLM 5.2 下 Malena 奖牌率 62.5%，最佳外部 harness 为 47.1%。仅在较弱的 Gemma 4 31B 上，MLEvolve 在百分位上领先，但奖牌率置信区间仍与 Malena 重叠。
- **轨迹分析**：Malena 自行执行自适应搜索——先构建覆盖任务自然阶段的通用流水线，随后进行"代码补丁级超参数搜索"，复用检查点和工具代码；后期转向集成、模型选择和后处理等性能导向技术，同时保持较高的技术稀有度（与 MLEvolve 同为前二）。AiScientist 和 Malena 都展现从均衡到性能导向的转变，MLEvolve 约在运行 10% 后即稳定。
- **理论解释**：编码智能体后训练替代了 harness 手工设计的脚手架；较弱骨干仍受益于手工工作流先验，但随着智能体能力增长，普通编码智能体循环即闭合差距——"后训练吃掉了 harness"。

## 7. 优点

- **受控实验设计**：在单一代码库中重新实现所有干预，固定骨干、硬件、时间预算，使唯一变量为干预本身，归因清晰。
- **统计严谨**：采用宏任务平均、自举置信区间、配对逐任务比较，有效抵消任务间难度差异，得到比常规边际置信区间更窄的区间。
- **双重验证**：既在受控环境中做消融，又将已发布的外部 SOTA 系统原样运行进行端到端对比，结论内外一致。
- **轨迹分析深入**：不仅报告性能，还通过检查点标注、技术聚类、稀有度分析揭示了"为什么"——智能体自行完成搜索与知识复用。
- **污染检查充分**：使用 Dolos 代码相似性（改进为包含度度量以避免低估）和 Qwen3 嵌入相似性两种独立方法，并辅以行为检查（Chat vs. Oneshot 对比反驳记忆假设）。
- **任务修复**：主动识别并修复 MLE-bench 中 4 个存在数据缺失或真值泄漏的任务准备脚本问题，并公开代码差异。
- **公平性努力**：对外部 harness 进行骨干兼容性修复和配置消融，报告负面结果，承认并缓解调优努力不对称问题。

## 8. 不足与局限

- **Benchmark 依赖与污染风险**：多数结果依赖 MLE-bench，其存在已知任务准备问题，且基于公开 Kaggle 竞赛，是合理的预训练污染目标；NatureBench 覆盖的模型与方法较少。
- **统计功效有限**：24 小时条件下每任务仅 3–4 个种子，部分置信区间宽至无法就效应大小做强断言；较弱主张（Malena 不劣于某基线）支持较好，更强主张（好多少）需谨慎解读。
- **协调研究范围有限**：关于多智能体干预的结论几乎完全基于单 worker；仅在一个小规模协调原语集上做了编排消融，未深入研究多并发工作流之间的协调协议。
- **调优努力不对称**：Malena 是作者自己的系统，可能存在投入更多调试与配置努力的偏差；虽通过对外部 harness 进行同等骨干验证与配置消融来缓解，但该风险无法完全排除。
- **应用限制**：结论针对当前 MLE 基准与前沿 LLM；对更弱骨干，手工 harness 仍有价值。单会话策略的潜在缺点在于长时程下上下文溢出（论文测试了 64k 约束上下文，性能下降但置信区间重叠）。成本方面，Malena 的缓存读取 token 量高一个数量级，推理成本更高（但整体仍由硬件成本主导）。

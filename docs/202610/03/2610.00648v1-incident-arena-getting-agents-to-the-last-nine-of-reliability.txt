ABSTRACT 

AI coding agents are ubiquitous in software engineering workflows in both academia & industry. Yet, despite their use in app coding, relatively less at-tention has been paid to their ability to execute on production incident response. This emerging field, termed agentic site-reliability-engineering (SRE) contains benchmarks limited by (1) unrealistic environments, typically toy repositories (2) non-standard framework implementations and (3) simple static verifiers. We introduce Incident-Arena , a human-built benchmark of 20 carefully selected tasks grounded in real-world deployed open source software. Each task deploys a pro-duction application to an ephemeral Kubernetes cluster, injecting parameterizable faults, and a sustained load profile given the task requirements. We also present a novel verification method, going beyond static checks to functional verifiers, hold-ing systems level metrics stable, while ensuring repairs are done safely. Agent trials run an average of 4.0M tokens and 68 steps, going beyond existing benchmarks, demonstrating agentic long horizon reasoning in SRE-tasks. Across 20 human-built tasks and 3 application substrates, the best model configuration passes at 64.3%, with failures extending from diagnosis/localization errors, through incomplete repairs and unsafe regressions.

1 INTRODUCTION 

Coding agents have emerged as the dominant form of interacting with code since the advent of Claude Code and Codex, moving from typing by code hand to instructing agents to execute application coding tasks. These agents are increasingly able to solve substantial repository level tasks. As powerful

Operational repairs, as a key component in the lifecycle, are successful only if they restore service, preserve unrelated behavior and state, and remain effective after processes restart. Evaluating this capability therefore goes beyond checking whether an agent produces a plausible patch or eliminates an alert. Recent benchmarks evaluate agents in DevOps, integrations, observability & incident-response tasks (Tang et al., 2026; Kottamasu et al., 2026; Clark et al., 2026). The existing work addressing the agentic SRE space falls short of three core attributes: Operational Validity , Diagnostic Resolution ,

Reproducibility & Interoperability .Firstly, Operational Validity , meaning the verifier & environment realism, is difficult to establish, where some benchmarks operate on repository level artifacts, live-system benchmarks use custom or trivial applications as operational surfaces. While useful for control, they leave uncertainty about measured performance transferring to real-world systems. Furthermore, frontier models are already capable of detecting evaluation regimes (Needham et al., 2025), therefore artificial interfaces, small discrepancies in parity, and unrealistic verifiers or goals let induce evaluation suspicion. Secondly, existing benchmarks provide limited Diagnostic Resolution , where aggregate success rates reveal agent failures, but often not with controlled variation to elicit failure behaviours. Specifically, by sweeping reasoning across frontier models, we’re able to analyze the operational capabilities isolated in stronger models. Thirdly, on Reproducibility & Interoperability , due to the nature of SRE-style tasks that make them difficult to test using Harbor (Harbor Framework Team, 2026), existing work like SRE-Gym (Clark et al., 2026), APEX-SWE (Kottamasu et al., 2026) and DevOpsGym (Tang et al., 2026) all use unique and custom integrations. This makes agent analysis difficult and comparison difficult. We introduce Incident-Arena , a human-authored benchmark, analyzing agent’s ability to diagnose, repair and successfully operationalization broken production systems. We present 20 human-authored tasks built from live Kuberenetes systems, inspired or pulled from real production repositories. Faults are built across configuration, runtime state or image layers, while agent access is varied access from full code visibility through to scoped kubectl commands. Agents are placed in a foothold pod, with read-only access to metrics, logs and other key observability metrics. Final evaluation is deterministic & LLM-free, to avoid rubric design - instead we present a novel verifier with two core checks: Outcome Gate , measuring recovery under continued traffic and a 

Safety Gate , measuring durability, data preservation, repairs and the limited scope. Our contributions are: • A human-authored operational benchmark : Difficulty emerges from complexity in the agent environment, multi-pod, multi-service systems with complex hops in the environment. • Production-oriented verifiers : Our dual-gate verifier jointly measures recovery & repair under continued load, restart and fresh traffic. • A comprehensive frontier evaluation : We analyze 3,000 trials of agent trials across frontier models, thoroughly analyzing their frontier capabilities. 

2 RELATED WORK 

Incident response on live systems. AIOpsLab (Chen et al., 2025) deploys DeathStarBench (Gan et al., 2019) applications on Kubernetes. A mitigation passes if every service is up afterwards. ITBench (Jha et al., 2025) counts a scenario as mitigated when its alert clears, and OperAID (de Castro et al., 2026) verifies fixes on a live 5G core. SREGym (Clark et al., 2026) is the closest to our work. It adds background noise and metastable failures, scores diagnoses with an LLM-judged checklist, and counts a mitigation as successful when the fault is gone and the system is healthy again. Most of these run demo or benchmark applications and give the agent general kubectl commands or privileged actions. Incident-Arena instead runs pinned production applications, Saleor (Saleor Commerce, 2026) and FrappeERP (Frappe Technologies, 2026), alongside a Slack substrate we built. The agent gets scoped permissions, and an LLM-free verifier checks each repair while traffic keeps running or after the affected service restarts. Diagnosis and repository tasks. Other benchmarks stop short of repairing a running system. DevOps-Gym (Tang et al., 2026) and APEX-SWE (Kottamasu et al., 2026) grade the code change or written diagnosis the agent hands in. Diagnosis benchmarks such as OpenRCA (Xu et al., 2025), Cloud-OpsBench (Wang et al., 2026a), ORCA-bench (Gong et al., 2026) and ITBench-AA (Artificial Analysis & IBM Research, 2026) ask for the root cause of failures in recorded data. Two of them find that diagnoses are often ungrounded: Cloud-OpsBench reports 0.76 root-cause accuracy but an evidence-closure rate of only 0.38, and on ORCA-bench the weakest model invents an implausible root cause in 40% of reports. In Incident-Arena , the agent has to find the fault and fix it, and we grade the fix. 

Safe remediation. A repair also has to be safe. R2Act (Qi et al., 2026) finds that 39.5–62.0% of correctly diagnosed incidents still receive an invalid recovery action. Given underspecified DevOps instructions, coding agents overstep an action boundary in 55.8–67.8% of runs (Ji et al., 2026). On live PostgreSQL, DBA-Bench (Chen et al., 2026) reports that human DBAs repair 93.4% of scenarios safely, against 17.9% for the best automated baseline. InfraBench (Gao et al., 2026) comes closest to our verifier. It re-checks infrastructure tasks under sustained load, after a restart and at teardown, but flags risky commands with an LLM judge and gives agents root and SSH access. We run similar checks on incidents in production applications, without an LLM judge and with narrow permissions, and also fail any repair that reaches outside its allowed scope. 

Score validity. Recent coding benchmarks ask whether their own scores can be trusted. Checks can pass wrong answers: 7.8% of all SWE-bench (Jimenez et al., 2024) patches count as correct while failing the developers’ test suite (Wang et al., 2026b), and SWE-Marathon (Desai et al., 2026) finds a verifier bypass in 10.2% of rollouts. In operations, the same failure is a health check that passes on a broken system. Tasks can also leak into training data, which SWE-bench-Live (Zhang et al., 2025) and SWE-rebench (Badertdinov et al., 2025) counter by collecting new ones. And models may recognize when they are being evaluated; Gemini-2.5-Pro does so with an AUC of 0.83 (Needham et al., 2025). We check every task both ways, with a golden solution and a no-op run, and have adversarial agents try to game each one; Appendix J shows that our outcome checks reject reports of repairs that never happened. Because two of our applications are public, we inject new faults and block the agent from code-hosting sites, and our instructions avoid evaluation cues. 

Diagnostic resolution. A single pass rate shows that agents fail, but not where. METR measures agents by the length of task, in human working time, that they can complete at a fixed success 3Preprint rate (Kwa et al., 2025). For root-cause analysis, a pooled accuracy across systems can hide which method wins on each (Hu et al., 2026), and ORCA-bench varies report specificity, detection time and co-occurring faults (Gong et al., 2026). We do the same for repair: we vary the agent’s access from full source visibility to scoped kubectl , run ten model and harness configurations at every available reasoning level, and report results per application. 

3 INCIDENT -A RENA 

Incident-Arena is fundamentally three components together: a substrate, a fault layer, and the agent runtime. The substrate + fault layer build a task, and the runtime determines the agent environment. 3.1 SUBSTRATE CONSTRUCTION 

Substrates are the fundamental unit of how we build tasks in Incident-Arena . They are complete, executable systems where incidents or faults can be injected. Building substrates typically has 3 core stages: mining, operationalizing & packaging. We have 3 core substrates: Slack, Saelor (Saleor Commerce, 2026) & FrappeERP (Frappe Technologies, 2026) - Slack is a highly realistic built substrate, while Saelor & FrappeERP are mined from open source. Mining Open Source Repos : We search for open-source applications used in (or modelled after) production that carry real operational complexity: persistent state, network services, background workers, caches, queues, authentication, and external dependencies. Acceptance requires (1) a permissive license, (2) sufficient documentation, (3) a reproducible build, and (4) enough surface area for task footholds. Each repository is pinned to a commit so upstream changes cannot alter the benchmark. If we have a specific application in mind that does not satisfy our constraints, we find and build our ideal version of that application. For our Slack substrate, we built it from scratch, modelled similar to the Mattermost repository (Mattermost, 2026) but significantly more realism, extending to 47 pods and 45 services (Table 7). 

Operationalizing Repositories : OSS repositories rarely ship as production systems, so we supply the missing infrastructure: containerizing and building services, deterministic startup, migrations and seed data, network configuration, load generators, and metrics logging. We then calibrate each substrate, recording baseline metrics as the healthy reference state. Calibration is a one-time activity that is done against a healthy substrate in order to measure the healthy vs unhealthy states induced in tasks. Core metrics measurincluded duringin the calibration include p50, p99 latency on core pods, split by peak & trough load, error rates, goodput ratios, traffic counts, and probes attached to specific pods and services. We also have probes attached to service availability, data integrity and read-after-write correctness, ordering, duplication, queue lengths/backlogs, repair persistence & forbidden restarts. 4Preprint 

Kubernetes Packaging : Tasks are built through a substrate + a fault overlay. The agent runs in a single main pod that serves as it’s foothold operational shell. The rest of the system runs in separate service pods (app servers, workers, databases, caches, queues). The main pod reaches approved endpoints via task-specific APIs and limited RBAC, with no general cluster credentials and no access to verifier secrets or grading artifacts. 

Agent Network Isolation : The main pod has no direct Internet access all outbound requests must pass through a controlled proxy pod. The proxy allows Internet access during trusted setup, then switches to a restricted policy permitting only model APIs and package hosts before the agent starts. 

NetworkPolicy rules block direct public-IP connections, filtered DNS resolves only cluster-local names, and HTTPS is checked against both hostname and TLS SNI. This prevents proxy bypass and access to source-hosting services such as GitHub. 

Observability : Prometheus scrapes service-pod metrics at fixed intervals and a collector ships pod logs to Loki. The agent queries both through Obs-MCP, a read-only PromQL/LogQL interface. Direct backend access is blocked, so observations cannot be modified and private grading data stays inaccessible. 3.2 TASK CONSTRUCTION 

Tasks are built from using a modified Harbor format (Harbor Framework Team, 2026). In our modification, each task contains a top-level human-readable instruction file, a Kubernetes chart, ground-truth metrics, the hidden verifiers, the solution oracles and one-hour agent time limit. Tasks were built through open source contributors and internal authors. Candidate tasks were built through careful task design, attempting to target specific difficult reasoning and capability gaps found in frontier models. 

Fault injection: Our task creation process involves a healthy substrate combined with a fault in order to induce the task we’d like the agent to target. In this case, we have 3 types of fault injection mechanisms: configuration, runtime and image layer faults. Configuration faults change the Helm values before deployment (connections, timeouts, replicas, etc). Image faults are a small code or image change on top of a pinned base image. Runtime faults are where some fault emerges or evolves after deployment either before or during an agent run. The full taskset with the fault tiers are found in Table 6 in Appendix. 

Agent Access: Recognizing that agent permissions affect the task completion, we devise three types of agent access permissions. Confined , gives the agent an operator pod with very specific diagnostic and repair surfaces - no app pod shell. The Shell-Visible surface exposes narrow scoped shell access to selected pods, mostly non root and read-only file systems. Thirdly, the build-capable surface exposes source files in order to induce trigger a rebuild for the agent. 3.3 VERIFIER DESIGN 

Compared to the static checks typical of other benchmarks, Incident-Arena grades a repair by how the system behaves afterwards, not by what its configuration looks like. We design two gates. Firstly, the Outcome gate measures workload Service Level Indicators (SLIs): goodput ratio, latency and error rate, while fresh traffic continues over a fixed period after the agent has submitted its repair. Secondly, the Safety gate checks that the repair actually holds: we restart the affected service or fire the fault’s trigger again and confirm the setting is still in place, we confirm the agent stayed within the task’s allowed scope, and we confirm protected data and guardrails are intact. This is what stops shortcut repairs such as queue flushing, overly broad grants, disabling traffic etc. from passing. A task is a binary pass only if both gates pass. All of these underlying checks are hidden from the agent and are deterministic; any malformed or missing evidence fails the task. The SLI bounds come from the healthy substrate, measured once per substrate before any trial, not from post-trial tuning. 3.4 TASK DESIGN & Q UALIFICATION 

Instruction Design: In order to avoid eval awareness in agent trials, we explicitly remove any form of markdown writing in the instruction.md , along with any semblance of “AI-writing” (despite 5Preprint being human verified, we try to avoid the stylistic choices models make). We only give the agent the minimal required information to solve the task, the time limit and the submission instructions. 

Qualification: After development, tasks go through multiple rounds of Quality Assessment (QA), patching holes found in the task environments & design. Our QA process is broadly multiple adversarial agents attempting to explicitly reward hack and others where the agent finds unfair flaws in the task or verifier design. Final tasks must pass both Oracle & No-operation trial - oracle to prove the golden solution path and no-op to prove nothing causes the errors to persist. 

4 EXPERIMENTAL SETUP 

Agent configurations: We measure 10 agent configurations from OpenAI, Anthropic, xAI, Meta & Zhipu using their native agent harness, except for GLM 5.3 which is paired with Claude-code. We evaluate with 3 independent trials at every available reasoning level. Across 20 tasks this produces 3,000 model trials. Harness versions and configurations are shown in Table 2. All agents per task receive the same instruction.md and the same set of tools. We use a Harbor fork modified to support Kubernetes backends. 

Runtime Environment : Popular agent sandboxes lack privileged container access, required to run k3s (K3s), needed in Incident-Arena . Therefore, we use AWS EC2s, m7i.2xlarge instances with the standard Ubuntu 24.04 LTS machine image on amd64 , configured with 80 GiB of gp3 disk. The instance comes with 8 vCPUs and 32 GB of memory, to manage the size and complexity of the services on the pods. Each instance creates a fresh k3s cluster and pulls immutable, digest-pinned images from GHCR. The deployment combines the pinned task substrate version with its configuration, image, or runtime fault overlay. After task services and workload generator are ready, the agent is installed in the main operator pod and receives the repair surface specified in Table 5. 

Timing Budgets : The episode clock begins only after cluster deployment and readiness checks succeed, excluding infrastructure startup variance. Harness setup and agent execution share a fixed 60 minute window. An agent may declare completion early otherwise, it is stopped at timeout. The agent PID is sent a SIGTERM , then a SIGKILL 2 minutes later, to give the graded portion an agent-free soak period. The 180 second graded post-agent execution soak period then begins at the next complete load cycle boundary, to prevent agent biasing. 

Cyber Refusal : Model providers are increasingly building safeguards into models, but these also prevent legitimate evaluation exercises outside of the cybersecurity scope. Despite this benchmark focuses on SRE tasks, we occasionally encounter cyber refusals, which are usually resolved by retries. 

Failures and Retries : We retry only failures attributable to benchmark infrastructure or harness execution, according to a fixed retry policy established before evaluation. Agent timeouts and invalid repairs are retained as model outcomes. Cyber refusals are resolved by 3 retries, but after 3 retries we deem it a failure. 

Evaluation Protocol : Our primary metric is resolve rate, Pass@1 . Pass@1 is the share of episodes that receive the binary reward, that is, pass both outcome and safety gates. Error bars in all figures are computed from a 95% task-bootstrap CI, as seen in Figure 1

For each task, the reference solution is a small set of actions that change the task’s state. Agents reach the first correct action at a median 3.3 minutes into the allotted hour (interquartile range 1.7 to 7.7) and issue the rest of the correct actions almost immediately after. Of the 2,967 episodes with a usable action record, 1,638 (55%) issue a “full fix”, meaning every one of the reference solution’s actions is implemented. Without the full fix (1,329 episodes, 457 of which never issue a single reference action) an episode rarely passes: 5.5% (73 of 1,329). Of the episodes that implement a full fix, only 59% (966 of 1,638) pass. The remaining 672 had the full solution in place and still failed. Of these 672, 340 failed only on outcome. They are the agent not knowing when it is done: the repair was correct, and the agent stopped before the system had recovered. Sometimes the fix had not yet taken hold when the agent declared (a queue backlog still draining, a restart still in progress, connections still cycling). More often the fix was necessary but not sufficient: damage the fault had already done (backlogs, duplicated or inconsistent records) keeps the indicators out of bounds until it is cleared, and most of these episodes never returned within bound during the graded period (Appendix D). The other 329 failed a safety check They are agents undoing their own success, most often by moving the maintenance window to a second that was still unsafe (145) or raising the connection pool past its ceiling after it had been fixed (38); subsection 5.1 has the rest. The delay effect is not hard tasks taking longer: inside each task, agents that declared within two minutes of their last correct action out-passed those that waited five minutes or more on eleven of the twelve tasks with enough episodes in both groups, by 20 points on average. Passing full-fix episodes declared a median 2.5 minutes after the last correct action, failing ones 3.7, and only 32% declared within two minutes at all. Figure 3: Reward hacking behaviour, split out by model. We categorize into three buckets, demon-strating significant attempted reward hacking behaviour across all models. 5.4 REWARD HACKING BEHAVIOUR 

We analyzed reward hacking behaviour in our corpus through a post-hoc process. Similar to (Desai et al., 2026) we employ a suspicion score, s ∈ [0 , 1] . We then build the three tiers, attempt-tier :

s ≥ 0.3, includes broad behaviour that is undesirable, such as probing for solution files, questionable behaviour, and mostly actions that did not affect the outcome. In the exploit-tier : s ≥ 0.85 , the agents would typically devise a strategy intended to pass checks, opposed to the intended repair, for example intentionally substituting temporary recovery for a durable fix. In the final tier, successful exploit: exploit ∧ award = 1 , constitutes when an agent has the successful exploit tier and the award is achieved. Our post-hoc process takes these definitions and builds rubrics for them, using GPT-6-Astra as the judge. We also explore other LLM-as-a-judge agreement & human-reviewed tasks in Appendix K. 

Earlier exploits: In an earlier task iteration, an agent reached remote code execution on the grader pod through a flaw in the environment; Appendix K describes it. 

6 LIMITATIONS 

Sampling n = 3 : Few samples generate large confidence interval bounds. With such tight competition between rival models in GPT-6-Astra & Opus-5.5, the CI being so large poses challenges. Further experiments with a larger number of trials is required. 

Task coverage : Due to the human nature of task development, Slack tasks are the majority at 13, while Frappe & Saleor are in the minority. Fault type, onset, and substrate are also confounded in this cohort. The results therefore characterize these tasks and agent interfaces; they do not establish performance across the wider range of production systems. 

Harbor fork : We had to develop our own backend infrastructure to support the K8s in an EC2 in Harbor (Harbor Framework Team, 2026). This poses interoperability challenges we hope to address by merging our changes upstream. 

Time limit: Most of our tasks are multi-hop, but agents typically only receive timer signals from the environment, opposed to a dedicated clock. Future work should include a timer the agent can check, similar to work in (Proximal Labs, 2026). 

Reward hacking interjudge rating : In Appendix K, we find that despite using frontier models, our judges have poor inter-judge rating in some cases. We attempted to seed human-in-the-loop data, but further investigation is required and assessing human-observed trials. 

7 CONCLUSION 

Incident-Arena measures an AI agent’s ability to conduct realistic SRE-style tasks on a human-made benchmark of 20 tasks. Across 3,000 trajectories, we demonstrate that this type of work is still yet to be saturated, with GPT-6-Astra on xhigh reaching a high of 65%. Common failure modes from repairs not lasting, declaring too early, or non-permitted actions, demonstrate agents still suffer from casual reasoning gaps. Extending realism in these tasks, directly demonstrates significant headroom for agents to get better. 9Preprint

J VERIFIER STRESS TEST : REPORTS OF A REPAIR THAT DID NOT HAPPEN 

To test whether the verifier can be passed by a report alone, we built a variant of one frappe task in which an external process, unreachable from the agent, re-applies the database fault about once per second, so that no repair can hold. The report tool on this variant required the agent to state whether the fault was resolved, and the grading accepted a report of “resolved” as sufficient for the diagnosis check, so only the outcome checks stood between a false report and a pass. We ran 17 episodes of one configuration on the variant and 17 on the unmodified task. On the unmodified task 18 Preprint all 17 episodes repaired the fault and reported it correctly. On the variant, 11 episodes reported the fault resolved and 6 reported it unresolved; the outcome checks failed all 11 false reports. Reading the agents’ own tool output shows that every false report followed a test write that succeeded inside the one-second window before the fault was re-applied, so these are over-confident reports after a transiently successful check rather than reports made after observing the fault persist. The stress test uses a modified task and report tool and is not part of the released set; we report it as evidence about the verifier, not about the agents.

## 摘要
代码生成已成为大语言模型的一项核心能力，编码智能体如今能够根据自然语言提示生成功能正确的软件项目。然而，功能正确性本身并不能涵盖生成质量的一个关键维度：环境规范，即准确定义执行生成代码所需的依赖，同样至关重要。我们开发了一种用于环境规范的智能体协议，并引入一个包含声明依赖、运行时安装依赖以及必要且充分依赖的三层框架，以系统评估编码智能体的环境规范能力。利用该协议，我们评估了编码智能体在多大程度上会系统性地错误指定软件环境依赖，以及这种错误指定在三个智能体、四种语言和五十个编程任务之间如何变化。结果表明，当前编码智能体在这一维度上表现出系统性的泛化失败，其生成的依赖规范以功能测试无法检测的方式呈现不一致、冗余或不完整。在不同智能体之间，相同任务的依赖集合一致性低至 7%，且更新的智能体没有表现出有意义的改进，表明该失败并未因规模或新近程度而得到解决。最大的差异出现在声明依赖层与运行时依赖层之间，表明从模型训练分布中学到的环境先验是主要驱动因素。我们的发现将环境规范确立为代码生成质量中一个当前基准未能捕捉的、独特且可度量的轴，并推动联合优化功能正确性和环境可移植性的训练目标与评估协议。

## Abstract
Code generation has emerged as a central capability of large language models, with coding agents now able to produce functionally correct software projects from natural language prompts. However, functional correctness alone does not capture a critical dimension of generation quality: environment specification, defined as the accurate identification of the dependencies required to execute generated code, is equally critical. We develop an agent protocol for environment specification and introduce a three-layer framework comprising declared, runtime-installed, and necessary-and-sufficient dependencies to systematically assess coding agents for environment specification. Using this protocol, we evaluate the extent to which coding agents systematically misspecify software environment dependencies and how this misspecification varies across three agents, four languages, and fifty programming tasks. Our results show that current coding agents exhibit systematic generalization failures along this dimension, producing dependency specifications that are inconsistent, redundant, or incomplete in ways that functional tests do not detect. Across agents, dependency set agreement is as low as 7% for identical tasks, and newer agents show no meaningful improvement, suggesting the failure is not resolved by scale or recency. The largest divergence occurs between the declared and runtime dependency layers, implicating environment priors learned from the models' training distributions as the primary driver. Our findings establish environment specification as a distinct, measurable axis of code generation quality that current benchmarks do not capture, and motivate training objectives and evaluation protocols that jointly optimize for functional correctness and environmental portability.

# 论文总结：Code That Works, Environments That Don't

## 1. 核心问题与研究动机

- **背景**：大语言模型编码智能体（coding agents）已能从自然语言提示生成完整、多文件的软件仓库，但现有评测基准几乎只关注**功能正确性**（代码能否通过测试），忽略了**环境规范**（environment specification）这一维度。
- **核心问题**：代码能跑通 ≠ 环境可复现。依赖声明错误（漏标、冗余、错标）会导致生成代码在干净环境中无法部署，而功能测试对此完全不可见。
- **关键论点**：软件环境与源代码本质不同——代码决定逻辑，环境管理外部、有状态、易发生静默运行时失败和版本冲突的生态系统，因此需要**定性不同的评测范式**。
- **整体含义**：环境规范应被确立为代码生成质量中一个**独立、可度量的轴**，需与功能正确性联合优化；这对软件供应链可复现性、SBOM（软件物料清单）可信度、安全审计有直接紧迫影响。

## 2. 方法论

### 2.1 核心思想：三层依赖框架 + 两阶段智能体协议

- **智能体协议（两阶段）**：
  - **生成技能（Gen）**：给定任务提示 π_T，智能体生成初始代码 C 与依赖清单 M，即 (C, M) = Gen(A, π_T)。
  - **修复技能（Repair）**：若在隔离环境 I 中执行失败（e^(0) ≠ ∅），将上一轮代码、清单与错误信号反馈给智能体，迭代修复至最多 k=10 轮，直到 e^(i) = ∅。
- **三层依赖集合**：
  - **D(1) 声明层**：`ParseManifest_l(M(0))`，从初始清单解析，代表智能体的初始声明。
  - **D(2) 安装层**：`Resolve_l(M(k), I)`，包管理器在环境中实际安装的包（含传递依赖）。
  - **D(3) 运行时追踪层**：`Trace(C(k), I)`，用 ptrace/Sciunit 追踪程序实际加载的依赖，作为**独立于智能体的真值基准**。

### 2.2 差距类型与指标

- **成对比较定义四类差距**：
  - **幻影依赖（Phantom）**：D(1) \ D(3)，声明了但运行时未加载（过度规范）。
  - **隐藏依赖（Hidden）**：D(3) \ D(1)，运行时需要但从未声明（欠规范）。
  - **膨胀依赖（Bloat）**：D(2) \ D(3)，安装了但运行时未使用。
  - **传递开销**：Δ = D(2) \ D(1)，膨胀比 ρ = |D(2)| / |D(1)|。
- **检索度量**：把 D(1) 视为预测 D(3) 的检索系统，计算 Precision、Recall、F1。
- **一致性度量**：跨智能体/同一智能体多次运行的 Jaccard 相似度 J；完全不相交率 CDR；全体一致率 UCR。
- **其他度量**：不必要依赖率 UDR（标准库足够任务中仍声明外部包的比例）；系统库假设率 SLAR 与环境差距修复率 EGAR。

### 2.3 关键实现细节

- **隔离环境**：基于 `ubuntu:22.04` 的按语言 Docker 容器，仅含最小工具链（Python 3.10+pip；JDK 17+Maven；Node.js 20+npm；G++ 12+CMake），刻意不预装 OpenSSL、libcurl、SQLite3 等系统开发库。
- **Trace 实现**：Sciunit 通过 ptrace 拦截 `open()/openat()/read()/execve()`，按生态特定路径规则（如 Python 的 `dist-packages`、JS 的 `node_modules`）映射到包名。
- **Java 特例**：解决"胖 JAR 不透明问题"——用 `mvn dependency:copy-dependencies` 解包为独立 JAR，使 JVM 对每个依赖 JAR 单独发起 `openat()`。
- **C++ 特例**：CMake 无规范包管理器，故 D(2) ≈ D(1)、ρ=1；排除 7 个基础系统库（libc、libstdc++ 等）。

## 3. 实验设计

- **任务集**：50 个基准编程任务，覆盖 8 个应用领域（数据处理 10、密码学 7、图像处理 6、网络 6、文本处理 6、压缩 5、数学/科学 5、系统工具 5）；满足平台无关性与自包含性（无外部服务/API/凭证）。
- **语言生态**：Python、Java、JavaScript、C++（覆盖解释型 vs 编译型、集中式 vs 去中心化包管理）。
- **智能体**：Claude Code（Opus + 扩展思考）、Codex（GitHub Copilot 最新 Codex）、Gemini Code Assist（最高推理配置），均通过 CLI 默认设置访问。
- **规模**：50 任务 × 4 语言 × 3 智能体 = 600 个主实例；Claude Code 额外 2 次独立随机试验 ×200 = 400；**总计 1000 次评测运行**，每实例最多 11 次交互（1 次 Gen + 10 次 Repair）。
- **提示变体**：全部 600 主实例使用**显式提示**（要求源码 + 锁定精确版本的依赖清单 + README），即智能体的最佳情形，故报告的错误率是**下界**。
- **对照基线**：并非传统意义的方法对比，而是以 **D(3) 运行时追踪作为真值**，对 D(1)/D(2) 做交叉验证；与人类撰写的 bloat 研究（Maven、npm）及静态分析工具（pipreqs、jdeps）形成定性对比。
- **执行方式**：全部 1000 实例**人工手动执行**（提交提示、传输工件、转录错误、记录 CSV），刻意避免自动化以免掩盖真实失败模式；每个任务用 `docker run --rm` 销毁并重建容器。

## 5. 实验数量与充分性

- **实验组数**：1000 次评测运行（600 主 + 400 随机）；覆盖 3 智能体 × 4 语言 × 50 任务 × 8 领域，另含 5 个评测维度（协议收敛、规范质量、跨智能体比较、跨语言差异、任务复杂度敏感性）与附录补充指标。
- **充分性亮点**：
  - 随机试验（同一智能体 3 次独立运行）直接检验了非确定性，是较强设计。
  - 隔离环境干净、基线固定（pkg_list_pre 减去基线），测量仪器用生态自身的包管理器而非自研推断，减少测量偏差。
  - 跨 4 种生态、3 家厂商的对比增强了结论的外部效度。
- **客观性与公平性**：
  - 所有智能体收到**完全相同的提示模板**，仅语言运行时与清单文件名不同，跨智能体/跨语言比较在提示层受控。
  - 任务通过测试套件验证提示充分性，使依赖错误归因于智能体而非提示不足。
- **潜在公平性隐忧**：人工执行虽提高控制，但引入操作者判断（如 C++ 失败分类、标准库充分性标注由作者先验界定）；且仅 Claude Code 做了随机重复试验，其他两家的方差未知。

## 6. 主要结论与发现

- **协议收敛**：首次成功率差异极大（Claude：JS 96%、Python 86%、C++ 36%、Java 仅 18%；Codex：44%–88%；Gemini：Python 32% 至 JS 84%）。经修复后几乎全部收敛（Claude 四语言 100%，Codex 仅 C++ 94%，Gemini Java 96%、C++ 98%）。**只评最终成功率的基准会把三家都评为近满分**，掩盖了修复成本相差达 5 倍的事实。
- **规范质量**：以 D(3) 为真值，宏观 F1 为 Python 0.765 > Java 0.708 >> JavaScript 0.219 > C++ 0.018。Python/Java 幻影率约 5%；JavaScript 约 49% 声明为幻影、62% 运行时包为隐藏、22% 安装包未使用。
- **环境膨胀**：平均膨胀比 ρ：JS = 11.40（中位 8.5）、Java = 3.97、Python = 2.06、C++ ≈ 1.0。少量声明可膨胀为上百个安装包。
- **一致性崩塌**：跨智能体 Jaccard 在 Python 也低于 0.5，JS 中 Codex–Gemini 仅 0.073；完全不相交率宏观平均 53.3%。**同一智能体 3 次独立运行的全体一致率 UCR 在所有语言中均为 0%**，说明依赖选择是随机采样而非稳定知识检索。
- **跨语言差异**：JS 是各指标全面最差的病态生态；C++ 问题不同——智能体假设系统库存在（Claude 的 C++ 首次失败中 SLAR 达 87.5%，但反馈后 100% 可修复），说明失败源于**训练分布中的环境先验**而非任务难度。
- **任务复杂度**：收敛主要由语言生态而非任务领域驱动；在标准库已足够的任务上，Claude 仍有 91.8%（宏观平均，C++ 达 100%）声明了多余外部包，属纯浪费的攻击面。
- **供应链含义**：代理生成的清单在 JS/C++ 中不能直接作为可信 SBOM 使用；幻影依赖制造虚假攻击面与安全误报，隐藏依赖则是从未被扫描的运行时活跃代码。

## 7. 优点

- **概念创新**：首次将"环境规范"从功能正确性中解耦，提出可复用的三层依赖框架与评测词汇（phantom/hidden/bloat/manifest F1），填补了基准空白。
- **真值设计严谨**：以独立于智能体的 ptrace 运行时追踪为 ground truth，优于静态可达性分析；测量仪器用生态自身包管理器，避免自研推断偏差。
- **实验控制到位**：统一提示模板、干净最小容器、按语言固定基线、任务经测试套件验证、1000 次运行的规模、以及同一智能体的重复随机试验，使"非确定性"结论具有说服力。
- **工程细节扎实**：识别并解决 Java 胖 JAR 不透明问题，C++ 基础系统库剔除，D(1)↔D(2) 无固定集合包含关系的处理都很细致。
- **实践价值明确**：结论直接指向 SBOM 可信度、供应链安全、依赖审计，以及"环境接地微调/依赖感知奖励信号"的具体改进方向。

## 8. 不足与局限

- **C++ 测量偏差（最严重）**：运行时追踪无法观测 header-only 与纯编译期依赖（如最常声明的 `nlohmann_json`），导致 D(3) = ∅ 而 D(1) 非空，使 C++ 的 precision/F1 被系统性压低；同时 D(1) vs D(2) 比较在 C++ 结构上无信息量，被排除在跨语言传递性分析之外。
- **条件依赖遗漏**：D(3) 仅捕获特定执行路径上加载的包，条件导入的包会缺失；作者假设此类情况罕见但未量化。
- **基准规模与生态效度**：仅 50 个受控任务，而非开放式真实项目，结论应视为"结构化代码生成场景"的证据而非普适估计。
- **提示敏感性未检验**：所有主实验只用显式提示，隐式提示的系统对比留作未来工作；绝对数值可能随措辞变化。
- **人工执行的判断偏差**：手工执行虽提升控制，但 C++ 失败分类与标准库充分性任务标注含作者主观判断，缺乏双人复核或一致性报告。
- **随机性分析不均衡**：仅 Claude Code 做了 3 次重复试验（因其是唯一 100% 收敛者），Codex 与 Gemini 的方差未知，跨智能体非确定性结论受限。
- **快照性质**：商业智能体迭代极快，结果只是评测时点的配置快照，不代表模型的固有属性。
- **算力信息缺失**：未报告任何 GPU/训练/推理成本信息，无法评估方法的经济可扩展性。

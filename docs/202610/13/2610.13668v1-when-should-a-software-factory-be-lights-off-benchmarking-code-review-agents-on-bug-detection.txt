CARMEN BADEA and CHRISTIAN BIRD, Microsoft Research, USA With the advances of coding agents, software developers are spending more time reviewing code than writing code. As human review velocity falls behind agentic code generation, it is tempting to build automated review agents towards a future of “lights-off” software factory with little to no human supervision. To assess the practicality of such a fully autonomous software factory, we construct CRBugBench, a new benchmark that evaluates whether review agents detect human-verified bugs. We build a data pipeline that mines bugs from repository history, and pair each bug with its introducing PR to form a review task. CRBugBench consists of 1,000 review tasks across 98 open-source GitHub repositories, and 800 additional tasks from proprietary industry repositories at one large company. We then use the benchmark to study agent review quality: We found that SOTA review agents do well: the best ( claude-opus-5 with copilot-cli ) catches 71.9% of bugs within its top-5 comments, up from 47.7% (opus-4.6 ) in five months of model evolution. Yet agents remain less effective on complex changes and bugs requiring non-local reasoning, with sharp performance drops on proprietary industry repositories where project context is more often needed. To improve bug detection, we found scaling compute helps most through 

prompt changes: exploration-nudging prompts gain up to 5.8% performance at 10% higher cost. From these findings, we derive concrete guidance for developers to adopt review agents – scaling review effort to PR complexity, steering agents by project priorities, supplying repository knowledge, dispatching models by PR characteristics, and monitoring quality as models evolve. 

1 Introduction 

Software engineering is increasingly automated. From code completion [11], chat assistants [23], to coding agents [3], the task of writing code has been shifted from human developers to AI. Developers are now increasingly doing more verification work, commonly through code review [1]. Yet the velocity of human reviews cannot catch up with agent-generated code. It is tempting to further automate humans away, by using AI for code reviews [4]. The extreme version of this would be a so-called “lights-off” software factory [36], where AI both writes and reviews code, with little to no human supervision in the loop. Are current repositories ready to become lights-off repositories? To answer that question, we first need to understand how well AI can review code. Without good review capability, the engineering loop cannot be fully closed. While many code review benchmarks exist (e.g., CodeReviewer [22], SWR-Bench [49], c-CRAB [51]), they typically treat human comments as ground truth and expect AI-generated reviews to match them, lexically or semantically. Human comments, without filtering, are a poor proxy of review ground truth. They can be arbitrary, containing nitpicking or less useful comments that are accepted due to social dynamics [13, 35]. They can also be too narrow, missing valid points that AI reviews can bring up. Therefore, assessing review quality based on the ground truth of human reviews is misleading: AI may provide high-quality review, just differently than human reviewers [41]. It would be hard to cleanly interpret the outcomes from these benchmarks.

Based on empirical findings from our benchmark, we make recommendations for developers to adopt code review agents (Section 5). We recommend that developers scale their (automated and human) review efforts based on PR complexity, and steer agent review directions based on project or PR priorities. They should also incorporate repository knowledge for better review quality, especially when they work on large proprietary repositories. If cost is a concern, they should consider dispatching different models and agent configurations based on PR characteristics. With evolving model behaviors, it would be a good idea to monitor review quality and adapt the harness periodically. We also recommend developers to apply the methodology of CRBugBench and build their own customized benchmark of their software repositories. To summarize, this paper contributes: 

• A scalable data construction and evaluation pipeline that transforms a repository into a suite of PR review tasks with human-verified bugs (Section 3). 

• CRBugBench, a constructed benchmark from open-source repositories (Section 3). 

• A comprehensive evaluation of review agents, with an analysis of when review agents work and when they do not (Section 4). 

• Actionable guidance for developers to adopt review agents (Section 5). 

2 Background and Related Work 2.1 Modern code review 

Code review originated in formal, synchronous inspection processes with prescribed roles and meetings [17]. Modern code review is a more lightweight, asynchronous process, usually involving rapid feedback from a small number of reviewers [5, 33, 34]. There is empirical evidence that code review contributes to software quality, but its outcomes are heterogeneous. Greater review participation is associated with fewer post-release defects [28], while the usefulness of a particular comment depends on both its technical content and its context. Large-scale studies show that useful feedback includes defects, design alternatives, and maintainability guidance, and that larger changes tend to receive a lower proportion of useful comments [13, 46]. We intend CRBugBench to focus on the more objective aspects (bug-finding) of code review, but leave the more subjective or domain-specific aspects to human reviewers. 

2.2 Benchmarking code review 

The most popular approach to evaluate code review is to collect human review comments and evaluate generated comments against them, with text-overlap metrics such as BLEU or CodeBLEU or LLM-based evaluators: Early benchmarks [22, 44, 45] construct method-level code paired with hu-man review comments, while more recent benchmarks like SWR-Bench [49], ContextCRBench [19], and c-CRAB [51] have moved to full-project, PR-level evaluation. In particular, c-CRAB converts human comments into executable tests and measures whether a separate coding agent can turn a review into a test-passing repair. These benchmarks are grounded primarily in reviewer comments before PR merge, and their reported scores can artificially penalize valid review findings that the

original reviewers missed. An alternative approach is to use LLMs to help augment and evaluate code review. AACR-Bench [50] augments reviewer comments with human-validated LLM-generated review comments, but this approach cannot assess performance on bugs that LLMs fail to identify in the first place. DeepCRCEval [26] and CRScore [30] use LLM-based evaluators to evaluate various aspects of code review (e.g., conciseness, comprehensiveness), but their evaluations are limited by the reliability of LLM evaluators and do not measure historical confirmed-bug recovery. Our benchmark takes a complementary approach: we identify bugs verified by human-authored change, including defects that were caught or escaped the original review, and then evaluate directly whether a review agent can identify that defect in the introducing PR. This provides a recall-oriented test of whether review agents recover known, consequential issues across realistic repository contexts, instead of a test of textual similarity or a general measure of comment style. Our approach connects to the established literature on post-release defects and defect prediction [12, 15], and similar to recent work that evaluates code review using discovered defects: Lu et al. [25] reconstruct introducing merge requests from industrial fault reports, while CR-Bench traces SWE-bench fixes to introducing PRs and evaluates reviews against the known bugs [31]. Compared to these works, we contribute a scalable recipe to curate diverse bugs and task environments from software repositories, and apply the recipe to create a benchmark grounded both in public and proprietary repositories. 

2.3 Automating code review 

Automation has long supported individual parts of code review, including static analysis, reviewer recommendation, change prioritization, and suggested revisions. For example, Review Bot combined static analysis with reviewer recommendation to surface findings inside the review workflow [6]. Neural approaches later learned edits or comments from historical review data [22, 44, 45]. LLM-based systems extend this line of work to open-ended agentic review that can inspect repository context, use development tools, and produce several candidate findings [40, 41]. Recent evidence nevertheless cautions against over-trust of LLM-generated reviews. A controlled study with expert developers found that LLM-generated reviews redirected reviewers’ attention and increased the number of low-severity issues found, but did not increase detection of high-severity issues, save review time, or improve confidence [43]. An industrial study of 4,335 pull requests found that developers acted on many automated comments, while also reporting faulty, unnecessary, and irrelevant feedback and observing longer average PR closure times [14]. A recent roadmap consequently frames the field around context-aware, value-driven, human-AI review rather than replacement of human reviewers [48]. Our work advances this agenda by evaluating end-to-end review agents on bug detection, characterizing the change and repository conditions under which they fail, to inform when to allocate human oversight.

3.2 Bug identification 

Bugs identified before merge. First, we identify bugs that developers have caught during PR review – i.e., they are mentioned in PR discussion and fixed before merge. We collect these tasks in 2 steps: (1) Mining. We first collect all merged PRs and their discussion threads from GitHub API. We filter out PRs without any review threads. This yields 304,601 PRs with 1,436,120 review threads. We then apply deterministic quality filters to remove low-quality comments, filtering out comments that are bot-authored, self-authored, too short, on non-source-code files, or are rejected. After filtering, 472,039 candidate threads remain across 117,522 PRs. (2) Sampling and LLM filtering. Because the surviving population is far larger than what we can evaluate, we draw a stratified sample of 90 threads per repository. Within a repository we order PRs by merge time, split them into 10 equal-count temporal strata, and make sample spans equally across the repository’s history. This yields 8,639 threads. We then use an LLM to further label and filter comments that are not bugs (e.g., style, naming, tests, nits, refactors, and concerns the replies show were clarified or declined). This results in 865 vetted bugs across 99 repositories. 

Bugs identified after merge. Second, we identify bugs that developers caught after a PR is merged – i.e., they are mentioned in a later issue and fixed in a later PR. We collect these tasks in 4 steps: (1) Mining. We first collect all merged PRs with fix-related keywords in their titles or labels. This yields 195,075 candidate PRs. We then identify closing issues for each PR, and remove the ones without substantive descriptions (less than 80 characters), yielding 57,725 fix PRs. (2) Sampling and LLM filtering. Because the surviving population is far larger than what we can evaluate, we again draw a stratified sample of 200 PRs per repository. We then have an LLM label and filter issues that are not bugs and hence unpreventable (new features, refactors, documentation, performance work). This yields 10,784 fix PRs.

We then trace each defect back to its inducing PR with SZZ [37]: We identify the deleted/modified lines and use git blame to obtain the commits that last touched them; and map those commits to PR numbers using the repository’s referencing convention. Since SZZ is noisy (a refactor that last-touched a line can be attributed as if it had introduced the defect), we further use an LLM ( claude-opus-4.8 ) for quality control. The LLM is asked to classify the type of the inducing change and whether the blamed lines introduce the bugs, yielding 736 pairs. (4) Ground truth screening. We drop issues with no reported faulty behaviors (screenshot-only reports, unfilled templates, bare one-liners), non-bug issues that are vague or off-target, and issue/fix mismatches. This yields a final set of 689 fix–inducing PR pairs. 

Data quality control. We iterated our bug identification pipeline over multiple weeks, through validating the quality of curated bugs and adding additional deterministic or LLM filters. We randomly sampled 40 identified bugs from the final pipeline and assessed whether each reported bug (i) represented a concrete defect and (ii) could be detected by reviewers using the available context. A task was labeled valid only if both criteria were satisfied. Overall, 37 tasks (92.5%) were valid, with an approximate 95% Wilson confidence interval of 80.1-97.4%. 

3.3 Task creation 

From the identified and verified bugs and bug-inducing PRs, we construct our review tasks. For each PR, we identify the base commit and the reviewed commit . For bugs identified before merge, the reviewed commit is the commit that carries the ground-truth bug comments. For bugs identified after merge, the reviewed commit is the final commit before merge. We then construct the base-to-reviewed-commit diff for review. We create a DockerFile per task and remove ones with build failures. We then sample the tasks down to 500 per track. 

Task format. Each task instance contains a Docker snapshot of the repository at the inducing PR’s base commit, with history through that commit intact but all later references deleted to prevent leakage. The PR title and description are provided as context, and the change is provided both as a file and uncommitted working-tree modifications. The agent reviews the change without being told that a bug exists and writes its review to review.md . The review is structured as a list of review items, self-ranked by the agent based on severity, following popular review agent design [4]. We restrict Internet access and explicitly prompt the agent to avoid cheating behaviors. We later conducted an AI-assisted auditing of agent trajectories and did not find any cheating behaviors. 

Task scoring. Each review finding is scored by an LLM-as-judge panel against the ground truth (bug-mentioning comments or issues) and annotated if there is a match. To mitigate judge biases towards same-family models and single-judge instability [52], we use three judge models: gpt-5.5 ,

claude-opus-4.8 , and gemini-3.1-flash , and take the majority vote as the final result. We independently annotated 40 samples of agent reviews and found that we achieved almost perfect human-LLM agreement ( 𝜅 = 0.89). We also observed that judges are fairly consistent with each other, achieving almost perfect across-LLM agreement (Fleiss’ 𝜅 = 0.95). For evaluation, we measure recall@k as the proportion of tasks for which the ground-truth issue is identified among the agent’s top-k findings. Varying k captures different limits on developer attention and team review budgets.

3.4 Benchmark characteristics 

Applying our data pipeline to GitHub repositories, we collect CRBugBench, with 1,000 tasks across 98 popular and established open-sourced repositories (Figure 4). The tasks are spread out from 2015 to 2026, with most reviewed changes single-language (82%) and a median churn of 189 lines. 

Task annotations. We in addition annotate various task attributes for downstream analysis. (1) Code metrics. We collect diff size, file kinds, languages, and repository size. We also capture file-level dependency graph with CodeQL and compute the number of dependent / dependency files. (2) LLM annotations. We further create rubrics and use an LLM to annotate various semantic attributes of code change and bugs: We annotate change type (following taxonomy in Li et al. [21]), bug impact based on ISO/IEC 25010 quality impact [20], plus bug severity and bug visibility . We validated a sample of 40 annotations and found that we have almost perfect human-LLM agreement for change type and bug impact ( 𝜅 = 0.88 , 0.82 respectively), and substantial agreement for bug severity and visibility ( 𝜅 = 0.64 , 0.68). For severity, we group critical / high and medium / low in our analysis, which yields a higher 𝜅 = 0.90.

3.5 Proprietary benchmark construction 

Besides the public benchmark, we applied the same data pipeline on two industry mono repositories on enterprise platforms for online collaboration and productivity, collecting 800 additional review tasks. These tasks are sourced from repositories with an average of >100k source files, which is a much larger scale compared to open-source repositories (an average of 3k source files). 

4 Experiments 

Next, we use our benchmark to evaluate review agents’ bug-detection performance. We first evaluate across different model configurations to understand how well review agents detect PR bugs (RQ1). We then use the collected data to do a large-scale empirical analysis, to understand what factors impact review agents’ bug detection capabilities (RQ2). We then analyze the agent trajectories to understand where do agents spend time and why do they fail (RQ3). We finally evaluate with different harness variations, to understand how agent design choices impact bug detection (RQ4). 

4.1 Research Design 

Evaluating and comparing agentic models (RQ1). We first evaluate across a wide range of large and small models with strong coding capabilities: 

• Large frontier models : claude-opus-5 , claude-opus-4.8 , claude-opus-4.6 , gpt-5.6-sol , gpt-5.5 , and gpt-5.4 . These represent large, strong coding models available at the time of our experiments. 

• Smaller and older models : claude-sonnet-5 , gpt-5.6-luna , claude-haiku-4.5 , and 

gpt-5mini . These represent decent coding models that are cheaper and smaller. To control for variations in agent harnesses, we use copilot-cli , pinned to 1.0.74, as the agent harness to evaluate and compare different models. 2 For the review prompt, we use the official prompt provided by copilot-cli in the /review command. For all models, we use a reasoning effort of xhigh when available. Otherwise, we use the max available reasoning effort for the model. In addition to the main performance metric recall@k, we also report (1) cost metrics, including token usage, estimated cost (in USD), and latency, and (2) review length metrics, including number of findings and words. For the proprietary benchmark portion, we evaluate four top-performing models: claude-opus-5 ,

claudeopus-4.8 , gpt-5.6-sol , and gpt-5.5 . We compare their results to the open-source portion of our benchmark. 

Analyzing variation in agent performance (RQ2). To identify the conditions under which review agents are more or less successful, we model the probability that a review detects a bug using multivariable logistic regression. Evaluating and comparing agent harnesses (RQ4). We finally evaluate across various agent config-urations, testing how the choice of harness, prompt, and orchestration impacts agent performance. 

• Reasoning efforts. We ablate reasoning efforts for gpt-5.6-luna , with reasoning efforts set to low, medium, and max. 

• Harness. We ablate the harness with claude-code for claude-opus-4.8 and claude-opus-5

• Prompt. We ablate the default copilot-cli review prompt with a prompt that encourages comprehensiveness. The default prompt optimizes for signal-to-noise ratios (i.e., models are encouraged to only output important findings). 

• Orchestration. We ablate the default single-agent loop with three ways to scale up compute efforts. The first is through self-refine , where we have a second agent to improve the reviews from the first pass. The second is through candidate-ensemble , where we have an orchestrator agent that collects several independent candidate reviews and consolidates them into one set of findings. We vary both how many candidates are pooled (three or five) and whether those candidates come from the same model or from different models. In the case of different models, we sample candidates from claude-opus-4.8 , gpt-5.5 and gpt-5.6-sol . The last is through sub-agents , where we have an orchestrator agent that creates sub-directions to explore, and invoke sub-agents on demand, and create consolidated findings. 

4.2 Threats to Validity 

Construct validity. Our benchmark only measures review agents’ bug detection capabilities. Our results should therefore be interpreted as recovery of known bugs rather than as overall review usefulness. Our evaluation uses LLM judges, which may be unreliable [52]. We mitigate this by using a three-model panel and calibrate human-LLM agreement. 

Internal validity. Despite multi-stage filtering, our benchmark construction can still yield incorrect ground truths or unsolvable tasks. We mitigate this with extensive data quality control and manual verification of samples. Agent behavior is also stochastic and sensitive to changes, which we mitigate with pinning the primary harness and holding the prompt and task environment fixed. Our observational regressions estimate adjusted associations, not causal effects. Unmeasured factors and LLM annotation errors may confound estimates or attenuate effects. 

External validity. We cover popular open-source repositories across domains and two large industry monorepos. These choices improve diversity but do not represent all software development. Our selection favors mature, active, popular projects and source-code changes with detailed textual evidence and reproducible environments. Results may differ for smaller or younger projects, uncommon languages, generated or configuration-heavy code, and other review practices.

4.4 How are task conditions correlated with review agent performance (RQ2)? 

Agents struggle with PRs with larger, more complex diffs (H1, H4). First, we observe that larger diffs significantly decrease detection probability (OR=0.591, ***). This is expected, as larger diffs contain more code to review and hence dilute review attention, making bugs harder to detect. Besides the volume, we also observe that more heterogeneous diffs are harder to review (OR=0.795, *). That is, when the diffs contain multiple types of changes (e.g., on source code, tests, configs), they are harder to review. We hypothesize that this may come from that more complex changes require reviews to reason across modules and interfaces, hence harder to review. 

Agents struggle with bug-fixing PRs (H2). We found that bug-fixing PRs (OR=0.521, ***) are harder to review than other types of PR, when we adjust for other attributes (e.g., diff size) in regression. This may be a result of when agents review a bug-fixing PR, their attention is diverted to verify the fix is plausible, with less attention to other regressions introduced.

4.5 Where do agents spend time and how do they fail (RQ3)? 

We found that different agentic models execute similar loops (Figure 8): within the loop, agents usually start with git operations (64%, mostly git diff and git log ), followed by a long inspection phase in which reading and searching account for 75% of all turn mass (39% Read, 36% Probe), while running code accounts only for 8%. Agents tend to establish what the change does by looking at source and history far more than by executing it. Comparing model families, Claude models run code more often than GPT models (9.7% of all turns for claude-opus-5 vs. 6.9% for gpt-5.6-sol ). Qualitatively, we observe this helps claude-opus-5 

discover a few bugs that are missed by others: on a yt-dlp task opus-5 retrieved roughly 25 archived pages through the Wayback CDX API, ran the extractor, and reported that livestream pages yield IDs for only two of nine tested pages; on a GitExtensions task opus-5 installed the .NET SDK and built an MSBuild probe to prove a DLL was absent from the publish output. More noticeably, different models stay in the loop for different length, resulting in different “effective” budgets. Half of the gpt-5.6-sol runs are over by turn 17 and only 3.5% survive to turn 50, whereas claude-opus-5 reaches its half-life at turn 35. This results in different levels of comprehensiveness of produced review and may explain the result discrepancy partly. 

Failures come from diagnostics instead of retrieval. We found 95.6% of agent executions inspect the file with defects, but only 80.2% produce a finding for that file, and 56.2% actually hit the bugs.

5 Discussion 5.1 When can a software factory be lights-off? 

While coding agents have gained substantial review capabilities, our results suggest that agents are not yet ready for a fully autonomous software factory, especially for large-scale proprietary industry repositories. Even the strongest agent misses known bugs, with heavy performance drops on proprietary repositories, and failures concentrate in diffs that require non-local or domain-specific reasoning. The present evidence therefore supports “lights-off” operation only for narrowly scoped, low-consequence PRs. For consequential changes, review agents are better treated as scalable peers that broaden coverage while an accountable human retains the final decision. While the boundary can move as models improve, developers should calibrate based on repository-specific, continuously monitored evidence rather than aggregate benchmark performance alone. 

5.2 Recommendations for best practices when adopting review agents 

While review agents are not yet capable of fully replacing human reviewers, they are still quite valuable to be incorporated into the review pipeline to help developers catch many bugs they would otherwise miss (Figure 5b). The human-in-the-loop adoption, however, should be done with care,

based on review contexts. Based on our empirical observations, we derive the following actionable recommendations for review agent deployment: 

Scale review efforts based on PR complexity. An agent’s bug-detection capability decreases as a PR becomes larger or contains more kinds of changes (cf. Section 4.4). Teams should use these properties to allocate both automated and human review effort. Small, homogeneous changes may be reviewed with a cheaper configuration, whereas large, heterogeneous PRs warrant stronger models, higher reasoning effort, comprehensive prompts, and careful human review. Splitting unrelated changes into smaller PRs can also reduce the amount of code competing for reviewer attention. Human reviewers should retain responsibility for project values and long-term maintainability, where our results suggest that their attention is particularly complementary to that of agents. 

Steer review directions based on priorities. By default, agent reviews focus on more severe, func-tional bugs. Their review efforts can also be (mis-)directed by surface cues like the types of PR, statements in code comments, or specified behaviors in test cases. Developers should provide custom instructions that reflect their priorities – for example, explicitly asking an agent to examine usability, portability, backward compatibility, or maintainability when those properties matter. 

Incorporate repository knowledge for better review quality. Agents excel at finding bugs that can be clearly inferred based on local diff contexts. They struggle more when a correct judgment depends on project-specific knowledge, surrounding source files, or runtime evidence, which is often the case for large, proprietary repositories. To mitigate these deficiencies, developers can incorporate repository-specific instructions and knowledge bases to guide and improve review quality. 

Monitor review quality and adapt harness over model evolution. Review capability changes with both the underlying model and the surrounding environment (e.g., as the codebase evolves). Har-nesses that help one model may provide little benefit to a later model. Teams should therefore evaluate the deployed agent configuration periodically. They can apply our data-construction method to construct custom benchmarks for their own repositories, and adapt the harness as needed when model behaviors change. 

5.3 Research opportunities 

Self-improving review agents. One emerging theme from our analysis is that current review agents are still weak at detecting bugs that require project-level knowledge. While developers can provide explicit scaffold and contextual information, future review agents should also be able to maintain memory that enables continual adaptation to (evolving) software repositories. Such memory can be built from artifacts produced in engineering processes, e.g., design documents, agentic sessions, past review discussions, prior incidents and commits [29, 47]. To build effective review agents, researchers need to create efficient and effective memory representations, such that new information is incorporated and stale information is removed [24]. They will also need to create effective retrieval mechanisms, and train agents to use the retrieval tools to seek relevant information. To enable self-improvement, researchers can build on our work, and create reliable data pipelines to mine task instances to guide memory evolution. 

Improve human-in-the-loop review efficiency. Our results suggest that human-in-the-loop reviews are still important for bug detection. However, human reviewers struggle to keep up with agentic code generation [1]. To keep humans in the review loop, we need to design effective human-agent collaboration. Instead of having humans manually review every single line of code, we should build systems to assist and speed up human inspection, and maximize the value they provide at minimal cognitive cost. For example, researchers can build code understanding agents , that provide PR walkthrough, potentially tailored to reviewers’ expertise and past interactions. The agents should be able to highlight the parts that are high-risk, high-impact, or they are least certain about.

6 Conclusion 

In this work, we introduce CRBugBench and empirically study when and how code review agents detect human-verified bugs. We show that agents are improving rapidly, but still struggle with complex changes and bugs requiring project context, particularly in proprietary repositories. Comprehensive prompting improves detection more cost-effectively than multi-agent setups, though its benefits vary across models. These findings support retaining human oversight and provide guidance for adapting review effort, context, and agent configurations to project needs.

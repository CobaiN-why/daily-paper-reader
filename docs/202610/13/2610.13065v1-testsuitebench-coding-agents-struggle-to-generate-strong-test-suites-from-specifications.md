## 摘要
编程智能体正越来越多地被用于创建大型软件项目。尽管代码生成基准已相应扩展到完整应用，测试生成基准仍局限于单个函数或缺陷修复。特别是，从零开始为复杂软件生成完整测试套件仍未得到探索。为弥补这一空白，我们提出 TestSuiteBench，一个包含165个开源应用的基准，每个应用都有结构化且详细的预期行为规范、一个参考实现、一个参考测试套件，以及平均74个变异体。每个变异体由规范中的单个需求生成，并经过精炼以隔离该行为：73%的变异体恰好被一个参考测试杀死，平均而言仅被剩余测试的0.2%杀死。我们发现，即使是最前沿的编程智能体，在给定我们的规范时也难以生成强测试套件，其变异得分低于60%，尽管它们生成的测试套件大体有效，且88%的测试能在参考实现上通过。我们观察到，生成的测试套件通常缺乏相关的输入组合，并且比参考测试套件更小。与此同时，针对相同规范生成的实现能通过82%的参考测试。这些结果表明，智能体能够构建其无法验证的软件，这一差距直接限制了完全自主的软件开发。

## Abstract
Coding agents are increasingly used to create large software projects. While code-generation benchmarks have scaled accordingly to full applications, test-generation benchmarks remain limited to individual functions or bug fixes. In particular, generating complete test suites for complex software from scratch remains unexplored. To address this gap, we introduce TestSuiteBench, a benchmark of 165 open-source applications, each with a structured and detailed specification of intended behavior, a reference implementation, a reference test suite, and on average 74 mutants. Each mutant is generated from a single requirement of the specification and refined to isolate that behavior: 73\% are killed by exactly one reference test and, on average, by only 0.2\% of the remaining tests. We find that even frontier coding agents struggle to generate strong test suites given our specifications, achieving mutation scores below 60\%, despite their suites being largely valid and 88\% of their tests passing on the reference implementation. We observe that generated test suites often lack relevant input combinations and are smaller than reference test suites. Meanwhile, implementations generated for the same specifications pass 82\% of the reference tests. These results show agents can build software they cannot verify, a gap that directly limits fully autonomous software development.

## 2. 方法论

### 2.1 核心思想

每个基准实例由四部分组成：**规范 S**（自然语言描述预期行为）、**参考实现 I\***、**参考测试套件 T\***、**变异体集合 M**（平均 74 个，每个违反单条需求）。智能体仅依据规范 S 生成测试套件 T̂，随后通过**变异得分 M**（杀死变异体的比例）和**有效性率 V**（在参考实现上通过的测试比例）评估。

### 2.2 构建流程（三步）

**第一步：从参考测试套件生成草稿规范**
- 基于 ProgramBench 的 200 个开源仓库（Rust、Go、C/C++，含编译型独立可执行文件）。
- 用编程智能体（Codex GPT-5.6 Sol）基于测试套件与可观察行为构建 T\*，所有测试均为纯输入-输出行为断言。
- 过滤需联网、资源过度或 flaky 的测试，最终保留 **165 个实例**，参考套件平均缩小 5.7%。
- 由智能体生成半结构化规范草稿 S′，显式描述 T\* 中每个被测试行为，最多 50 个章节。

**第二步：变异体构建（核心）**
- 目标：每个变异体只破坏**一条特定需求**，且与参考实现在其他方面无法区分。
- 设目标测试函数 t_target 杀死该变异体，其余杀死它的测试记为 T̄；理想情况是变异体**恰好只被 t_target 杀死**（T̄ 为空）。
- **候选构建**：构建二部图 G 连接规范章节 s_i 与测试函数 t_j，通过**最小费用最大流**为每个章节选取 6 个测试（优先选择被较少章节共享的测试）。对每个 t_target 用独立智能体修改 I\* 生成候选变异体，编译失败最多重试 3 次。
- **候选精炼**：按 (i) 是否被 t_target 杀死、(ii) T̄_j 大小对每个 s_i 的 6 个候选排序取前 3；再由智能体精炼以减少 T̄_j；最后丢弃未被预期测试杀死、或被超过 20% 无关测试杀死的变异体。
- **精炼效果**：恰好被目标测试杀死的比例从 **32.4% → 73.0%**，T̄_j 平均大小从 **1.45% → 0.17%**。

**第三步：规范迭代精炼**
- 用两个智能体分别生成实现 Î 和测试套件 T̂，在 T\*、E\*、M 上评估。
- **错误归因**：将每个失败（t 杀死 Î、t̂ 杀死 E\*、m 存活于 T̂）分类为"生成质量差"或"规范缺陷"（欠规范 / 矛盾）。
- **规范精炼**：针对归因于规范的失败，修正或补充对应章节，迭代直至规范归因的失败少于 5%。
- 最后进行人工质量控制（如修正"期望特定源码行崩溃"等测试）。

### 2.3 评估指标

- **变异得分 M**：被杀死的变异体比例（过滤掉杀死参考可执行文件的测试，避免"杀死一切"的作弊）。
- **有效性率 V**：在参考实现上不失败的生成测试比例。
- **参考通过率 R**：实现 Î 通过的参考测试比例。
- 为处理 flaky 测试，在参考实现上运行 3 次并剔除行为不一致的测试。

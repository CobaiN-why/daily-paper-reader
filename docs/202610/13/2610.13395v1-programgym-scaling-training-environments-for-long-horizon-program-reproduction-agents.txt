ABSTRACT
Coding agents are increasingly used to build programs from scratch as software
engineers do rather than to resolve issues within a repository or to generate a
repository from a given requirements document. However, scalable verifiable
training environments that force agents to discover what is required and to decide
how the system should be designed remain scarce. Moreover, existing agent work-
flows also cannot sustain long-horizon development in which the agent explores
the reference program before implementation. To address these challenges, we
introduce ProgramGym, a framework consisting of Program-Env and Program-
Agent for scalable training environments of long-horizon program reproduction
agents.
Specifically, Program-Env constructs verifiable training environments
from repositories through a feedback-driven loop that repairs runtime sandbox
builds and the quality of black-box tests. Using this novel pipeline, we obtain
1,648 training environments spanning C, C++, Go, and Rust. Program-Agent
combines a role-isolated workflow of analysis, implementation, and review with
revision management for compilation checks and failure recovery. Experiments
on ProgramBench show that both Program-Env and Program-Agent improve per-
formance on program reproduction. Fine-tuning on trajectories with these con-
structed environments raises the performance of Qwen3.8-27B from 34.87% to
42.84%. Program-Agent further raises the base and SFT models to 55.71% and
56.25%, both exceeding some flagship models. We will release the ProgramGym
to support further research on coding agents that build programs from scratch.

INTRODUCTION
Current coding agents (Qwen Team, 2026; Team et al., 2026; Zeng et al., 2026a) typically handle
issue-resolution tasks and repository generation tasks. Issue-resolution tasks such as SWE-bench
give a repository and an issue for the agent to patch (Jimenez et al., 2024; Rashid et al., 2025;
Zeng et al., 2026b; Shi et al., 2026). Repository generation tasks such as NL2Repo-Bench give a
requirements document for the agent to implement (Ding et al., 2025). In both settings, the agent
starts from a given codebase or a specified feature. A software engineer building a program from
scratch instead keeps asking what is required and how the system should be designed.
To explore this from-scratch setting, program reproduction tasks such as ProgramBench ask an agent
to rebuild a program’s observable behavior from its usage documentation and a reference program
without access to the source code or network (Yang et al., 2026b; Adamczewski et al., 2026). The
agent needs to still discover remaining behavior by exploration and design the implementation from
scratch. None of the models in the original ProgramBench evaluation fully solved a task (Yang
et al., 2026b)1. Training therefore requires interactive environments with reliable behavioral super-
vision, which issue-resolution resources such as SWE-Gym and SWE-smith do not provide (Pan
et al., 2024; Yang et al., 2026a; Song et al., 2026; Chen et al., 2026a). MindForge (Chen et al.,
2026b)is restricted to command-line programs and still leaves this supervision unverifiable. Build-
ing verifiable environments and using them over long horizons raises two challenges. (i) Scaling
verifiable training environments. Building the reference executable and runtime sandbox requires
accommodating repository-specific toolchains and dependencies. The black-box tests need to cover
diverse functionality while rejecting incorrect reproductions, yet a single test-generation attempt
may miss important behaviors or produce weak assertions. (ii) Sustaining long-horizon develop-
ment. General-purpose agent harnesses support tool use but do not by themselves keep exploration
and implementation coordinated. An agent can begin implementing before sufficiently exploring
the reference program and forget previously observed requirements as its context grows. Address-
ing these risks requires an explicit development workflow that preserves behavioral evidence and
coordinates implementation, review, and revision.
To overcome these challenges, we introduce ProgramGym consisting of Program-Env and
Program-Agent for scalable training environments of long-horizon program reproduction agents.
Specifically, Program-Env addresses environment construction by augmenting an existing agent har-
ness with feedback-driven loops for runtime sandbox and black-box test construction. To produce
the reference executable and its runtime sandbox, it separates online dependency preparation from
offline compilation and returns build diagnostics to guide repairs. Test construction proceeds across
functional modules in parallel, using program analysis to target unexplored behavior and validation
feedback. The resulting environments provide reference executables, runtime sandboxes, docu-
mentation, and black-box behavioral test suites for training supervision. Program-Agent addresses
long-horizon development through a role-isolated iterative workflow of analysis, implementation,
and review. It first records evidence from reference-program exploration and then alternates imple-
mentation with behavioral review in separate sessions. Persistent records carry requirements across
rounds, while offline build checks and validated checkpoints support revision and failure recovery.
Building on these designs, Program-Env scales 1,648 training environments covering C, C++, Go,
and Rust.
Each environment provides a reference executable, a runtime sandbox, usage doc-
umentation, and black-box tests, which are essential for training agents on program reproduc-
tion from scratch. We conduct extensive experiments on ProgramBench. With Program-Agent,
Qwen3.8-27B reaches 55.71% Tests Passed and Qwen3.8-27B-SFT reaches 56.25%, both ex-
ceeding flagship Claude Opus 4.7. We further evaluate DeepSeek-V4-Flash-0731 un-
der the same protocol. These results suggest that ProgramGym can scale training environments for
coding agents that reproduce programs from scratch as software engineers do. We will release Pro-
gramGym as a scalable gym for the community to develop coding agents that discover requirements
and design systems from scratch. In summary, our main contributions are threefold:
• We propose Program-Env, a feedback-driven pipeline that builds the reference executable
and runtime sandbox and constructs black-box tests from repositories (Section 4).

RELATED WORK
Long-Horizon Program Reproduction.
Training large language models as agents has gained
substantial attention (Team et al., 2026; Qwen et al., 2025; Zhu et al., 2024), with software engi-
neering (SWE) emerging as a promising application domain (Cao et al., 2026; Singh et al., 2025; Pan
et al., 2024). Issue resolution is a representative setting, in which SWE-bench tasks (Jimenez et al.,
2024) and its variants evaluate coding-agents on addressing bug fixes or feature requests within a
given code base (Yang et al., 2026a; Shi et al., 2026; Ahmad et al., 2026; Wu et al., 2026; La et al.,
2026; Yang et al., 2024). Despite their growing diversity, issue resolution tasks depend on a provided
code base, while several prior and concurrent works go further by asking agents to code from scratch
according to a requirements document (Luo et al., 2026; Zhao et al., 2026b; 2025; Li et al., 2024).
However, this setting typically relies on a natural-language requirements document that prescribes
the functional specification (Ding et al., 2025), reducing the task to implementation and leaving no
room for requirement discovery or architectural design. In contrast, recent work on program repro-
duction from scratch requires agents to reconstruct the externally observable behavior of a reference
program from a binary executable and documentation without prescribing implementation struc-
ture (Chen et al., 2026b; Yang et al., 2026b; Adamczewski et al., 2026). This setting therefore shifts
the challenge from implementing a specified repository to iteratively discovering what the program
should do and deciding how to rebuild it, as experienced software engineers.
Code Agent Environments Scaling.
Existing program reproduction from scratch remains highly
challenging (Yang et al., 2026b; Adamczewski et al., 2026). None of the flagship models in the
original ProgramBench evaluation fully resolved any of the 200 tasks (Yang et al., 2026b). Due to
the scarcity of training environments for such tasks, coding agents tend to be trained as code-edit
assistants that favor localized bug fixes or single-file implementations with detailed human guidance
rather than as autonomous software engineers (Adamczewski et al., 2026). Providing realistic and
executable training environments at scale is essential. This strategy is already proven in issue res-
olution (Song et al., 2026; Zhao et al., 2026a; Chen et al., 2026a), where generated environments
improved SWE-agent performance (Jain et al., 2025; Pan et al., 2024). These frameworks still start
from an existing codebase or a well-specified task description. MindForge does not filter training tra-
jectories by recovered program behavior, so functionally incorrect reproductions can still be treated
as successful supervision (Chen et al., 2026b). By contrast, ProgramGym makes program repro-
duction from scratch training scalable by automatically turning repositories into verifiable training
environments. This increases sample sizes and converts coding agents from compliant code editors
into active software engineers.

Program Reproduction Task.
Software engineering agents are increasingly expected to develop
complete software systems with limited human supervision (Yang et al., 2026b). Issue-resolution
tasks such as SWE-bench, however, start from an existing codebase and ask the agent to make
localized changes (Jimenez et al., 2024). Program reproduction from scratch removes this imple-
mentation scaffold and poses a more demanding task. Given only a software program and its docu-
mentation, the agent must produce source code that recovers the program’s functionality while inde-
pendently making the software design decisions needed to architect (Yang et al., 2026b). Training
agents on this task requires stable environments that support behavioral exploration and automati-
cally assess candidate implementations. Let Pi denote a source-available codebase drawn from a
repository. We define an environment-construction pipeline Φ as:

Constructing program-reproduction environments at scale requires reliable executable rebuild from
diverse repositories and comprehensive black-box behavioral tests that broadly capture program
functionality. To overcome these challenges, we introduce Program-Env, which uses general har-
nesses such as Claude Code and Codex and adds feedback loops to guide the overall process
of build repair and test refinement. As illustrated in Figure 2, Program-Env first collects candidate
repositories {Pi}M
i=1 (Section 4.1) and then constructs each retained environment ei by building the
reference executable and runtime sandbox (Section 4.2) and generating black-box tests (Section 4.3).
4.1
REPOSITORY COLLECTION
To construct a diverse candidate pool of repositories for our program reproduction gym, Program-
Env collects repositories through a stratified search process using the GitHub Search API. Specifi-
cally, we partition search queries by programming language and star-count buckets, while excluding

benchmarks are also excluded. Each retained repository is anchored to a fixed commit and screened
for explicit build-configuration evidence. This process yields M=30,459 candidate repositories

4.2
EXECUTABLE AND SANDBOX GENERATION
Program reproduction from scratch requires a prepared runtime sandbox with the necessary
toolchains and dependencies so that the agent can focus on rebuilding program functionality. To
accommodate differences across repositories, Program-Env pipeline Φ uses Claude Code as the
underlying agent harness and adds an outer loop that validates each proposed build procedure and
provides the diagnostics feedback for revision. For each repository Pi with a standalone executable
target, the agent generates download.sh for online dependency preparation and compile.sh
for offline compilation. The overall loop proceeds to the next stage only if both scripts succeed
and ./executable passes a loadability check. Otherwise, failure diagnostics are returned to the
agent for revision. The validated executable serves as B⋆
i , and the prepared image provides the basis
for the runtime sandbox Si. Further details are provided in Appendix B.2.
Finally, once the build validation succeeds, the dispatcher prepares the resources for black-box test
construction. It uses codebase size to determine the number of parallel branches and assigns each
branch a functional module. Alongside module assignment, it instruments the executable for cov-
erage measurement and prepares the test runtime. It also extracts repository documentation such as
README.md to form Di. These preparation steps run in parallel as detailed in Appendix B.3.
4.3
BLACK-BOX TESTS CONSTRUCTION
Reliable verification is essential for effective supervision in agent training. For program reproduc-
tion tasks, a black-box test suite Ti provides this supervision by comparing ˆBi against B⋆
i on shared
inputs. However, tests generated in a single attempt may cover too few behaviors or use assertions
that fail to detect incorrect implementations. Program-Env therefore uses structured feedback to
guide the agent in iteratively expanding test coverage and strengthening assertions.
Following the dispatcher’s module assignments, test construction proceeds in parallel across
branches. Each branch runs the Claude Code harness inside an outer loop that validates each
delivered suite and returns diagnostics for revision. After each round, the pipeline organizes the
feedback into three components, stored as structured documents in Feedback Docs/. (i) Sum-
mary records what was done and what remains unsolved and why, preserving context across rounds.
(ii) Program analysis locates uncovered functionality with dynamic analysis and traces it to public
entry points with static analysis. (iii) Validation screens tests through four checks: the pass check
identifies tests that fail on B⋆
i ; the double check detects inconsistent outcomes across repeated runs;
the dummy check identifies tests that accept a dummy implementation; and the weak-assert check
flags insufficient assertions. These checks help identify invalid, unstable, or insufficiently discrim-
inative tests. In the next round, the agent reads these processed documents to repair flagged tests
before extending coverage to unexplored targets. A subagent terminates once its module reaches
the functionality coverage threshold or the round limit. Once all branches terminate, their suites are
merged and validated again, and Ti retains only the tests that pass all checks. Further details are
provided in Appendix B.4.

PROGRAM-AGENT
In long-horizon program reproduction, single-session workflows may lose early behavioral evidence
due to context compression and consequently produce a program that fails to compile (Anthropic,
2025; Hao et al., 2026; Feng et al., 2026). Inspired by the iterative workflow of software engi-
neers, we propose Program-Agent built on Claude Code to support systematic development in
long-horizon program reproduction. As illustrated in Figure 3, it combines an iterative role-isolated
workflow (Section 5.1) with a revision management mechanism (Section 5.2) for compilation vali-
dation and failure recovery.

reference program to identify behavioral requirements. The Implement and Review stages then
alternate to refine the candidate implementation for a fixed loop budget. Handoff carries behavioral

5.1
ROLE-ISOLATED ITERATIVE WORKFLOW
Program-Agent adopts a role-isolated and session-separated iterative paradigm. It decouples pro-
gram reproduction into two logical roles (analyst and implementer) and three stages: Analysis,
Implement, and Review. Each stage executes in an independent session to eliminate cross-stage
memory contamination. Handoff artifacts carry behavioral evidence and stage reports across ses-
sions without transferring the full conversation history.
Analysis Stage.
The analyst reads the documentation and explores the reference program, without
editing Workspace, guaranteeing unbiased constraint collection. All extracted behavioral evidence
and implementation guidelines are stored in analysis-initial/analysis.md and frozen
as read-only reference for all downstream stages.
Implement Stage.
The implementer develops candidate programs in an isolated session based on
frozen Handoff artifacts without accessing the reference program, to avoid context noise. The first
iteration delivers a buildable baseline to avoid fundamental compilation failures, while subsequent
rounds incrementally resolve verified review issues. All implementation progress and code changes
are documented in implementation-k/delivery.md for explicit traceability.
Review Stage.
The analyst compares the official reference program with the newly built, im-
mutable candidate program, and converts all verified behavioral discrepancies into actionable re-
vision requirements recorded in review-k/review.md. Strict read-only access is enforced on
both the candidate program and the Workspace to prevent self-justifying modifications.
Iteration budget.
Given a fixed budget of K implementation rounds, Program-Agent executes
one standardized Analysis stage followed by alternating Implement and Review iterations. This
explicit iteration budget resolves two common issues in single-session workflows: premature ter-
mination with incomplete implementations, and unbounded low-value exploration that destabilizes
long-horizon reproduction.
5.2
REVISION MANAGEMENT
Across multiple Implement rounds, the shared Workspace can accumulate error edits until
compile.sh no longer produces an executable. Program-Agent therefore treats independent com-
pilation as the gate for each implementation round. It exports a clean snapshot of the committed
source and compiles that snapshot outside the development workspace. A snapshot that produces
an executable is archived in Revisions and forwarded to the next Review. Moreover, a stage that
times out or misses required artifacts or fails this compilation is retried in a fresh session within a

EXPERIMENTS AND ANALYSIS
This section presents an evaluation of ProgramGym.
Our experiments are designed to answer
the following four research questions. RQ1 (Effectiveness of ProgramGym) Does training on
Program-Env and solving with Program-Agent improve program reproduction task? RQ2 (Train-
ing Environments Analysis) What scale and construction dynamics characterize the environments
produced by Program-Env? RQ3 (Test-Time Scaling) Does additional Program-Agent iteration
budget improve Tests Passed? RQ4 (Agent Behavior Analysis) How does ProgramGym influence
agent behavior on program reproduction tasks?
6.1
EXPERIMENTAL SETTINGS
Environment Statistic.
Program-Env constructs 1,648 training environments spanning C, C++,
Go, and Rust, using DeepSeek-V4-Flash-0731 (DeepSeek-AI, 2026) as the underlying
model. Figure 4 shows that the repositories fall into eight functional categories and that developer
tools and CLI & system utilities are the two largest. Test construction uses 5,918 subagents across
these repositories. Table 1 reports six black-box interaction categories. We then collect trajecto-
ries for subsequent training by rejection sampling DeepSeek-V4-Flash-0731 (DeepSeek-AI,
2026) with Claude Code and filtering on test-case pass rate.
Agent Scaffolds.
To support interactive program reproduction from scratch, we use Claude
Code rather than mini-SWE-agent as the single-session baseline. The task is long-horizon
and often exceeds a 256K maximum context window. Claude Code compresses context so the
agent can continue, following the ProgramBench protocol of GLM-5.2 (GLM-5-Team et al., 2026).
We compare it with Program-Agent using the same container resource limits. Program-Agent runs
for up to K=5 iterations. Each task runs in an isolated container with 8 CPU cores, 16 GB of RAM,
and 30 GB of storage, under an 8-hour wall-clock limit.

CONCLUSION
In this paper, we propose ProgramGym for training agents on long-horizon program reproduction
from scratch. Program-Env is a feedback-driven pipeline that builds the reference executable and
runtime sandbox and constructs black-box tests from repositories and yields 1,648 training envi-
ronments in C, C++, Go, and Rust. Program-Agent combines a role-isolated workflow of analysis,
9


Preprint
implementation, and review with revision management for compilation checks and failure recov-
ery. Fine-tuning on trajectories with these constructed environments raises Qwen3.8-27B from
34.87% to 42.84% on ProgramBench. Program-Agent further raises the base and SFT models to
55.71% and 56.25%, both exceeding some flagship models. Extra Program-Agent iterations con-
tinue to recover program behavior and Program-Agent rather than SFT alone reshapes the agent
toward exploration and revision. We will release ProgramGym as a scalable gym for the community
to develop coding agents that discover requirements and design systems from scratch.

FREQUENTLY ASKED QUESTIONS (FAQS)
Why are there far fewer tasks than collected repositories?
Two factors account for the gap be-
tween the 30,459 collected repositories and the 1,648 tasks. (i) Filtering. Many candidates cannot
serve as black-box tasks because they fail to build on Linux, require a display or user input devices,
or exceed the 3,600-second limit for compilation or instrumentation, which we cannot leave un-
bounded. Such repositories are excluded before the test construction stage. (ii) Cost. Constructing
an environment is expensive, about 82.99M tokens on average (Appendix B.5), so processing the
full candidate pool was beyond our budget. The pipeline itself, however, is fully automated, so that
the community can construct further high-quality environments from the remaining repositories.
Why is the difficulty distribution skewed toward easy tasks?
Under the complexity score ξ
of Section B.3.1, the 1,648 tasks split into 1,492 easy, 151 medium, and 5 hard. This skew is
intentional. (i) ξ measures repository size rather than the difficulty of program reproduction from
scratch: a large codebase may expose few black-box entry points and little observable behavior. (ii)
Tasks far beyond current model capability yield almost no successful trajectories, so collecting more
of them adds little effective training signal. (iii) Despite the skew, models trained on Program-Env
show clear gains in program reproduction ability (Section 6). As model capability grows, the same
pipeline can be scaled to medium and hard repositories to push the frontier of coding models further.
Why not report a mean coverage curve over iterations?
We could not report a mean coverage
curve over iterations for two reasons. (i) Subagents terminate at different rounds, whether by
reaching the coverage threshold, the round limit, or early stopping (Appendix B.4.3), so averaging
over surviving modules would be biased toward the hardest ones and understate the gain from feed-
back. (ii) Coverage is only aggregated to the repository level after all branches terminate, so
no repository-level curve over iterations exists. We therefore present case studies instead. The two
cases in Figure 12 were chosen to represent the two effects of feedback, repairing weak tests and
expanding functionality coverage.
Why can the Implement stage of Program-Agent not access the reference program?
This
restriction follows the separation of responsibilities in software engineering: Analysis extracts be-
havioral requirements, Implement produces a buildable source revision from Handoff artifacts, and
Review independently identifies remaining discrepancies. If the Implement stage could access the
reference program, the agent might continue probing and matching marginal edge cases after com-
pleting its primary objectives, delaying delivery and degrading the staged workflow into open-ended
trial and error. Program-Agent instead delegates further behavioral exploration to Review, which
converts verified discrepancies into explicit requirements for the next round. This design preserves
clear stage boundaries while ensuring steady and auditable progress.
Why do we not compare with MindForge?
MindForge (Chen et al., 2026b) has not released its
environments or trajectories. Without these artifacts, we cannot evaluate under a matched protocol,
so we do not report a head-to-head comparison.

B.1
REPOSITORY COLLECTION DETAILS
In this section, we describe our four-stage pipeline for systematically collecting and filtering open-
source repositories from GitHub. The pipeline consists of Comprehensive Search, Metadata Valida-
tion, Commit Locking, and Build Config Detection.
Comprehensive Search.
For the corpus analyzed in this work, we search for repositories with
C, C++, Go, or Rust as their primary language. Repository retrieval is conducted via the GitHub
Search API. To circumvent its 1000-result limitation per query, we partition the search space inde-
pendently for each language using six mutually exclusive star-count buckets: [200, 499], [500, 999],
[1,000, 1,999], [2,000, 9,999], [10,000, 49,999], and [50,000, ∞). If a query exceeds this limit, its
star-count bucket is recursively bisected until the sub-query yields fewer than 1,000 results, the
bucket can no longer be divided, or the maximum recursion depth of 12 is reached. For the open-
ended highest bucket, the maximum star count observed in the returned results is used as a temporary
upper bound for computing the bisection midpoint, while the resulting upper sub-query remains
open-ended. This search strategy stratifies repositories by programming language and star count,
improving repository coverage within the constraints of the GitHub Search API. Additionally, we
include fork:false and archived:false in every query to reduce duplicate and inactive
repositories in the candidate pool.
Metadata Validation.
We locally re-validate the retrieved repository metadata to ensure consis-
tency with the search criteria. Specifically, we check each repository’s primary language and star
count, remove duplicate repositories based on full name, and require a non-empty SPDX license
identifier as a basic metadata completeness criterion. We further exclude repositories already used
by existing code-related benchmarks, thereby preventing repository-level overlap with prior evalua-
tion sets.
Commit Locking.
Because GitHub repositories are continuously updated, we fix a specific code
version for each qualified repository—specifically, the latest commit (i.e., the branch tip) of the
default branch at the moment of data retrieval.
For each candidate repository, we extract the
default branch field from the repository metadata collected in the first stage, query the head
commit of that branch and record its SHA. Ultimately, exactly one commit is retained for each
repository.
Build Config Detection.
After commit locking, we perform a lightweight, static detection of the
selected commit to identify repositories with explicit build-configuration evidence. For each repos-
itory, we resolve the root tree of the selected commit and retrieve its recursive file tree through the
GitHub REST API. We then search both the repository root and its subdirectories for common build-
configuration markers relevant to target languages, including Cargo.toml for Rust, go.mod for
Go, and native build-system files such as CMakeLists.txt, Makefile, and meson.build
for C and C++. We additionally treat npm-related configuration, such as package.json, as auxil-
iary evidence of build infrastructure. A repository passes this stage if at least one recognized marker
is found anywhere in its retrieved file tree; otherwise, it is excluded. This procedure serves only as
a scalable proxy for the presence of build infrastructure and does not establish that a repository can
be successfully compiled.
The final repository collection contains 30,459 repositories across C, C++, Go, and Rust. Detailed
statistics for each stage of the collection pipeline are reported in Table 3.

B.2
BUILD PROCEDURE DETAILS
Online preparation and offline compile.
Building a project requires a compiler, standard library,
and build tools that match the project itself, and installing the latest version of each does not guaran-
tee a successful build. As Table 4 shows, the reasons a language breaks under its newest toolchain
differ case by case. The build environment must therefore be prepared according to each project’s
actual version requirements rather than fixed per language.
To accommodate these differences, Program-Env equips the build agent with a skill for each sup-
ported language that encodes how to resolve toolchain versions, obtain dependencies, and drive
the build.
Guided by the skill, the agent makes environment preparation explicit in a script
download.sh, which fetches and configures the required compiler, build tools, and third-party
dependencies and exports the environment variables used by the subsequent build. A second script,
compile.sh, then builds the gold executable program B⋆
i within the prepared environment. The
separation reflects the solving side, in which the source is reconstructed from interaction with the
executable under no network access. Compiling offline verifies that the prepared environment is
self-contained, sparing the solving model from generating missing dependencies or compilers.
B.2.1
BUILD-STAGE VALIDATION
Linter check.
Validation combines a static linter with two-stage execution. The linter, shown in
Table 5, first ensures that the generated scripts do not mask failures, since a hidden error leaves
nothing for the build agent to diagnose. It rejects || true, redirections that discard standard
error, and placeholder content, and requires acceptable failures to be handled by explicit conditional
branches. The checks are intentionally strict, as a false positive costs a single repair round while an
undetected failure propagates to every downstream stage.
Execution check.
Execution then proceeds online and offline.
The system first runs
download.sh in a container with network access, providing the script alone and not providing the
project source, so that the script must generate its own dependency manifest for prefetching. Upon
success, the system records the exported environment variables and a snapshot of installed pack-
ages, and freezes the container state as the runtime sandbox Si. The system then places the project
source in a separate working directory, launches a network-disabled container from Si, restores the
recorded environment variables, and executes compile.sh. Since the build cannot reach the net-
work, it succeeds only if the toolchain and local resources prepared in the first stage are sufficient.
Validation checks the exit status of both scripts, the presence of an executable at the agreed location,
and the format and linkage of that executable. As shown in Figure 2, the linkage check runs ldd on
the B∗
i to confirm that it was built successfully and no dynamic library is missing.

B.3
DISPATCHER DETAILS
As Figure 11 shows, once the Executable and Sandbox Generation completes, the pipeline invokes
the dispatcher, which converts the validated target program into the resources required for test gen-
eration and evaluation. The dispatcher comprises four components: task decomposition, coverage
instrumentation, test generation sandbox construction, and docs extraction. Instrumentation depends
on the runtime sandbox Si, and sandbox construction depends on the instrumented program. The
remaining components are independent and run concurrently, reducing the dispatcher’s wall-clock
time.
B.3.1
TASK DECOMPOSITION
Delegating an entire repository, often tens of thousands of lines, to a single agent rarely yields a
test suite Ti with broad functional coverage, because the agent must simultaneously comprehend
the codebase, prioritize among its functions, and remain within its context and generation budget.
We therefore decompose the task. The dispatcher assigns a module budget according to reposi-
tory complexity. Let ℓdenote the number of production-code lines and r the number of runtime

B.3.2
COVERAGE INSTRUMENTATION
Overall strategy.
To provide execution feedback to test generation, the dispatcher equips the target
program with coverage collection, yielding the instrumented program. Rule-based instrumentation
is the natural first choice, as it is deterministic and incurs no model cost. Build systems, however,
vary considerably across repositories in their entry points, in how compiler flags are propagated, and
in how source files map to build artifacts. A language-specific rule therefore captures the common
instrumentation path of its language but not the build behavior peculiar to each repository, and
even determining whether a rule applies to a given repository is nontrivial. Moreover, injecting
instrumentation flags indiscriminately may corrupt the build by conflicting with existing compiler or
linker settings (Table 8, last column). We therefore adopt a rule-first, agent-fallback strategy. The
language-specific rule first constructs an instrumentation candidate, which an independent validator
then checks for the presence of build artifacts and coverage metadata. Only upon validation failure
does the system fall back to an instrumentation agent, an LLM agent that diagnoses and repairs the
instrumentation.
Language-specific rules.
Table 8 summarizes the rule-based instrumentation method for each
supported language (C, C++, Rust and Go), together with representative cases beyond rule-based
instrumentation. These cases arise from repository-specific build behavior rather than from insuffi-
ciently detailed rules, so further refinement of the rules yields diminishing returns. Pairing language-
specific rules with the instrumentation agent is thus the more effective combination.

B.3.4
DOCS EXTRACTION
As shown in Figure 11, the dispatcher’s fourth component, Docs Extraction, employs an LLM agent
to select two categories of content from the validated repository and place them into the documen-
tation Di of the constructed environment. The first category is repository documents, namely the
README and LICENSE. The second is test input assets that a model cannot reasonably synthesize
on its own, such as images and domain-specific binary formats, together with the minimal runtime
dependencies they require. The agent records its selection in a manifest, and the export copies only
the listed files rather than auditing the whole repository. In addition, the pipeline rejects any source-
code directory by rule. Together, these measures keep implementation details away from the solving
side.
B.4
TESTS CONSTRUCTION DETAILS
The construction of Ti follows an iterative process of test generation, validation, and refinement. In
each round, subagents generate and improve tests for their assigned modules based on feedback from
the environment. Section B.4.1 describes how generated tests are validated to ensure the reliability
of Ti. Section B.4.2 then details how feedback is constructed to guide subsequent rounds until the
final test suite is obtained.

B.4.1
VALIDATION FOR TEST CONSTRUCTION
Validation for test construction ensures that the generated test suite Ti serves as a reliable criterion
for the external behavior of the gold executable program B⋆
i . Concretely, Ti must be faithful, pass-
ing on the reference implementation, stable, with results that do not drift under execution order,
randomness, and effective, constraining program functionality rather than passing unconditionally.
Four mutually independent checks, run in parallel, enforce these conditions. The pass and dou-
ble checks establish faithfulness and stability, while the dummy and weak-assert checks establish
effectiveness dynamically and statically.
Pass check.
Candidate tests are first executed on B⋆
i to verify that their expected results, input con-
ditions, and invocation are consistent with the reference behavior. The system records the outcome
of each test case and marks those that fail or error on the reference implementation for revision.
With B⋆
i as the behavioral baseline, this check guarantees that Ti describes the actual behavior of
the reference implementation.
Double check.
A single pass on the reference implementation does not establish stability. The sys-
tem therefore executes the same test set twice against the reference, isolating file state with separate
working directories. The JUnit results of both runs are converted into normalized records containing
the test identifier, its pass, fail, or skip status, and the corresponding diagnostic summary and output.
If the two records disagree, the test is marked unstable and reported. This check prevents tests that
pass by chance or depend on randomness from being accepted as stable criteria.
Dummy check.
Passing stably on the reference program B⋆
i still does not show that a test con-
strains program behavior. The system therefore retains the same scripts and inputs but replaces the
program under test with a dummy implementation that produces no meaningful output, and executes
the suite again. A test that still passes is marked dummy pass. This check identifies tests that do
not truly depend on the functionality under test, such as those asserting only process termination or
tautological conditions.
Weak-assert check.
Runtime controls expose only extreme cases and say little about assertion
strength. The system therefore audits each test with a static linter of 37 rules (Tables 9 and 10), which
rejects weak oracles such as sole exit-code checks or tautological assertions, assertions masked by
conditionals or swallowed exceptions, access to the reference source, and nondeterministic depen-
dencies such as network, time, or unseeded randomness. Findings are reported at two levels. Errors
mark defective tests that are excluded from the final suite, whereas warnings flag risks to be reviewed
against task semantics, such as floating-point precision or unordered output, where implementation
differences may be permissible.

B.4.2
FEEDBACK FOR TEST GENERATION
The raw observations available after a round, namely execution logs, validation reports, and coverage
data, have low information density. To guide the agent effectively, the pipeline processes them into
structured feedback that answers three questions: which existing tests need repair, which uncovered
code the next round should target, and through which public entries that code can be reached. Tests
to repair are identified by the four checks, whereas new tests are guided by program analysis. Each
round thus repairs first and then writes new tests. Under the guidance of feedback, effective and
deterministic tests are written without blind exploration.
Validation feedback and repair.
After each round, the four checks of Section B.4.1 write their
findings to validation.json. Rather than raw pytest output, each finding is reported as an
actionable item with the test or script location, issue category, severity, diagnostics, and a suggested
fix, so that the agent knows not only what failed but also how to correct it. Repair precedes authoring
for two reasons. First, repairing an existing test is far cheaper than writing a new one, since the
location and fix are already identified and the change is typically local. Second, newly written tests
may introduce further issues, and without timely repair these defects accumulate across rounds.
Repairing first keeps every retained test stable and effective, so that coverage grows on a reliable
foundation.
Writing guided by dynamic program analysis.
A trustworthy verifier must cover as much func-
tionality as possible, so the central question in writing new tests is which functionality remains
unreached. Software engineering answers this with coverage, since unexecuted source locations
largely correspond to unexplored functionality. Each language uses a coverage backend matched to
its instrumented program, as shown in Table 11. All backends report file path, valid counting units,
covered units, and uncovered locations. C/C++ and Rust count executable source lines, whereas Go
retains its native statement-weighted basic blocks.

That is, Gt consists of partially covered files if any partially covered file exists, and falls back to all

Candidates are sorted by ascending coverage so that the files farthest from completion are presented
first. The target set is often large, and an agent handed all of it at once tends to overclaim, re-

min(|Gt|, ⌈ρ|Gt|⌉, B) targets, with feedback ratio ρ = 0.1 and cap B = 300, so that the agent works
through a manageable subset in each round. The selected targets, each with its path, coverage, unit
counts, and uncovered source lines, are written to coverage targets.json. A companion
coverage summary.md reports core coverage and its change, the measurement scope, and the
measurement status.
Writing guided by static program analysis.
An uncovered location alone does not indicate
which input to construct, particularly when the target function sits deep in a call hierarchy. Program-
Env builds on mature static analysis tools rather than custom analyzers. Joern provides code prop-
erty graphs (CPG) (Yamaguchi et al., 2014), call graphs, control flow, and data flow for all supported
languages except Rust, for which CodeQL is used instead. Because these tools expose standard in-
terfaces, the analysis layer is pluggable, and a backend can be replaced or a new analysis added
without changing the rest of the pipeline. The databases produced by Joern and CodeQL span the
entire program and are far too large to hand to the agent. Program-Env therefore queries them only
for the uncovered targets in coverage targets.json, which is why static analysis starts from
the second round, after the first coverage measurement. For each target, the pipeline maps its uncov-
ered lines to the enclosing functions, traverses the call graph in reverse to find public entries through
which a black-box test can reach them, and gathers the control-flow and data-flow context of those

PROGRAM-AGENT DETAILS
C.1
PHASE ORCHESTRATION
Program-Agent coordinates its analysis, implementation, and review stages through a fixed-round
external orchestrator. Given a budget of K implementation rounds, it executes one initial analysis,
K implementation stages, and K −1 review stages. No review is performed after the final imple-
mentation because review artifacts are used exclusively to guide the next implementation round.
Each stage invocation runs in a fresh model session. Instead of propagating the complete conver-
sational history, the orchestrator transfers persistent information through Handoff artifacts. The
workflow follows the predefined revision budget and does not parse a stopping decision from the
review output.
Let D denote the task instruction and project documentation, B⋆the execute-only reference pro-
gram, and W the source workspace shared across implementation rounds. We use A for the initial
analysis artifact, Ik for the delivery artifact of implementation round k, Rk for the corresponding
review artifact, and Ck for the committed source revision produced in round k. The executable Ek is
independently built from Ck for validation and differential review; it is a derived artifact rather than
the primary task deliverable. For k = 1, the sequence of preceding review artifacts R1, . . . , Rk−1 is
empty.

Analysis and Review operate on disposable source copies and are prohibited by their role contracts
from modifying product source, whereas Implement develops directly in the shared Workspace.
This role-level restriction differs from the filesystem-enforced isolation applied to the reference
executable, candidate snapshots, and Handoff artifacts.
34


Preprint
Analysis isolation.
Analysis runs in a disposable copy of the initial Workspace. The executable
originally present in the Workspace is excluded from this copy and replaced with an execute-only
reference program. The session is instructed not to modify product source and may write persistent
output only to its active Handoff directory. Once Analysis is complete, its disposable workspace is
removed.
Implementation isolation.
Before the first Implement session starts, the reference executable is
removed from all implementation-visible paths and retained only in root-owned private storage.
Implement can therefore access the frozen analysis and review artifacts together with its own candi-
date, but cannot execute or inspect the reference program. It is the only stage that directly modifies
product source in the shared Workspace.
Review isolation.
Each Review session runs in a separate disposable workspace. This workspace
contains a snapshot of the current source tree, the initial analysis, all preceding reviews, the current
implementation artifact, an execute-only copy of the reference program, and an immutable copy of
the independently built candidate. The role may execute both programs through their documented
interfaces but is instructed not to modify product source, build scripts, or version history. The entire
review workspace is deleted after its artifact has been sealed.
Artifact immutability.
The Handoff root and all completed stage directories remain read-only
during model execution. Only the subdirectory owned by the active stage is writable. After suc-
cessful stage validation, the orchestrator transfers that directory to root ownership and recursively
removes its write permissions. Downstream sessions may therefore consume completed artifacts but
cannot alter the evidence, implementation reports, or requirements recorded by earlier stages.
The /logs/agent directory is also read-only during model execution, preventing sessions from
creating undeclared persistent state outside Handoff. Analysis and Review may create temporary
fixtures in their disposable workspaces, but these fixtures are deleted with the workspace unless they
are explicitly retained and documented in the active Handoff artifact.

BUILD VALIDATION AND FAILURE RECOVERY
A stage is accepted only after both the model invocation and its stage-specific machine checks suc-
ceed. Analysis and Review must produce their required non-empty reports, whereas Implement must
additionally satisfy source-state and independent-build requirements. These checks are summarized
in Table 16.

Source-state validation.
After an Implement session terminates, the orchestrator verifies that
delivery.md is non-empty, no tracked file has staged or unstaged changes, and compile.sh
is tracked by Git. The current Git HEAD is then recorded as the source revision for the round. Un-
tracked files do not directly fail this check, although the role contract requires all intended source
files to be committed and generated artifacts to be ignored.
Independent build.
The orchestrator exports a clean Git archive of the validated source revi-
sion into a new build directory rather than compiling directly in the development Workspace. It
removes common HTTP proxy, Python package index, and npm registry variables before running
compile.sh with a 300-second timeout. A build is successful only if the script terminates suc-
cessfully and produces a file named executable.

Preprint
For each successful build, Program-Agent records the source commit, archived candidate path, and
SHA-256 digest in build.json. The same record is copied to the current implementation ar-
tifact as independent-build.json. The resulting executable is then used as the immutable
candidate for Review, while the committed source tree and compile.sh remain the primary task
deliverable.
Bounded retry.
Each stage has an independent attempt budget, configurable from one to three
attempts and set to two by default. Every retry starts a fresh model session. The new session
receives only a bounded diagnostic describing the previous delivery or build failure, rather than the
previous transcript.
When Analysis or Review fails validation, its stage directory is deleted before the next attempt.
When Implement or its independent build fails, Program-Agent also deletes the current build snap-
shot, resets the Workspace to the commit captured at the beginning of the round, and removes newly
generated untracked files. Reusable Go caches are excluded from this cleanup. Build stdout and
stderr from failed attempts are retained privately for diagnosis.
Last-stable recovery.
Every independently built revision becomes the new last-stable state, which
contains both its source commit and matching executable. On normal completion or after a later
error or timeout, Program-Agent resets the Workspace to the last-stable source commit and restores
its executable. If no implementation round ever passes independent build validation, any residual
executable is removed so that an unvalidated intermediate candidate cannot be evaluated.

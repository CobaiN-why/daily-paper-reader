PINJIA HE ∗, The Chinese University of Hong Kong, Shenzhen, China With the rapid advancement of Large Language Models (LLMs), software development is gradually moving toward a paradigm where users describe what they want and LLMs carry out the implementation. As LLMs’ im-plementation capabilities improve, an increasingly critical bottleneck emerges: whether LLMs truly understand what users want. In practice, users often begin with vague intent, leaving many important requirements to be progressively clarified through interaction. This is especially consequential in repository-level development, where an incorrect LLM’s guess about user intent can propagate through subsequent development phases, causing costly rework in long-horizon tasks. However, existing repository-level code generation benchmarks typically evaluate code generation directly from either complete specifications or underspecified requests, overlooking the importance of pre-coding requirement clarification. Meanwhile, prior requirement clarification studies mainly focus on function-level tasks, failing to reflect the complexity of real-world software develop-ment scenarios. Thus, it remains unclear how well LLMs can turn vague user intent into clear requirements through interactive clarification and how such clarification capability affects subsequent code generation. To bridge this gap, we introduce ReqClarifyBench, an interactive requirement clarification benchmark for repository-level software development. ReqClarifyBench contains 341 tasks spanning game, miniapp, and web development. Each task includes a high-level vague user intent, a detailed requirement document validated by human, and the corresponding code evaluation artifacts. To better simulate a realistic interactive clarification process, we further employ LLM-based user simulators with diverse personas derived from real-world conversation history. Based on ReqClarifyBench, we conduct a systematic empirical study. Specifically, we evaluate six LLMs’ requirement clarification capabilities from two complementary perspectives: how effectively they ask clarification questions and the quality of the generated requirement documents. The experimental results demonstrate that stronger clarification effectiveness does not necessarily translate into higher requirement document quality, and that LLMs exhibit substantial performance variations across different user personas. We also find that, compared with standalone LLMs, coding-agent harnesses do not further improve the ability to transform vague user intent into requirement documents. Based on these findings, we provide valuable insights for building LLM-based end-to-end software development systems.

1 Introduction 

Large Language Models (LLMs) are becoming increasingly capable of handling long-horizon software development tasks [17, 18]. This progress is paving the way for a requirement-driven development paradigm, where users describe what they want and LLMs carry out the long-horizon implementation [13, 35, 47, 49]. However, the success of this paradigm depends on clear and com-plete requirements, while real-world users often begin with vague descriptions of their intents that need to be progressively clarified through further interactions [22, 48]. Neglecting requirement clarification may lead to incorrect assumptions, which will propagate to subsequent design, imple-mentation, and testing phases, causing the implementation to drift away from the user’s intent and increasing the need for human oversight and rework in long-horizon tasks [11, 24]. Figure 1 presents two representative real-world user complaints that illustrate a shared failure mode. When a request is underspecified, LLMs may make a guess about what the user wants without asking for clarification, wasting time and tokens without producing a satisfactory outcome. Although LLMs’ implementation capabilities continue to improve, as reflected in rising benchmark scores [5, 15, 17, 18], they may still spend substantial time and tokens acting on a misunderstanding of the user’s request. Turning vague user intents into clear requirements through interactive clarification is therefore becoming an increasingly critical bottleneck. Existing benchmarks [19, 36, 38, 57, 59] have demonstrated progress in the end-to-end trans-formation of Natural Language Requirements (NLRs) into repository-level code. However, they largely overlook the importance of requirement clarification in this process, evaluating code gener-ation from either well-specified requirement documents or vague user requests without multi-turn requirement clarification. Meanwhile, the Requirements Engineering (RE) community has explored LLM-based requirement clarification. Nevertheless, existing studies [21, 39, 53] mainly focus on function-level tasks, failing to reflect the complexity of real-world software projects. Moreover, these studies often employ simulated users that follow a fixed interaction pattern, failing to capture diverse real-user behaviors [32]. To address these limitations, we introduce ReqClarifyBench , an interactive requirement clar-ification benchmark for repository-level software development. ReqClarifyBench aims to evaluate LLMs’ ability to transform vague user intents into clear requirement documents through multi-turn requirement clarification. ReqClarifyBench contains 341 tasks spanning game, miniapp, and web development. It is constructed through a semi-automated pipeline. Each task includes a high-level vague user intent, a detailed requirement document validated by humans, and the corresponding code evaluation artifacts. To support realistic interactions, we derive three representative user personas from SWE-chat [7], a large-scale dataset of multi-turn conversations between software developers and coding agents. These personas are used to guide the LLM-based user simulator throughout the clarification process. In addition, we introduce three new metrics to assess LLMs’ requirement clarification capabilities from two perspectives: how effectively LLMs ask clarification questions and the quality of the generated requirement documents.

Based on ReqClarifyBench, we conduct a systematic empirical study focusing on the following four dimensions. (1) Overall performance across LLMs and user personas. The results show that stronger clarification effectiveness does not necessarily lead to higher requirement document quality, and that user interaction styles can substantially affect model performance. (2) LLMs’ clarification behavior. The results reveal three distinct interaction patterns: clarification with expert users is typically short and efficient, interactions with vague users are sustained but low-yield, and new requirement information often emerges in later rounds when users change their requirements. (3) The impact of clarification on requirement document quality and code generation. Our experiments show that interactive clarification consistently improves requirement document quality, with particularly substantial gains in fine-grained requirement alignment, and further benefits subsequent implementation. (4) Effect of coding-agent harness. We compare standalone LLMs with the same LLMs running within coding-agent harnesses. The results show that coding-agent harnesses improve clarification effectiveness but do not further enhance the quality of derived requirement documents. Overall, these findings suggest that requirement clarification goes beyond simply asking more questions. Requirement clarification requires the evaluated LLM to elicit key information, understand and integrate requirements expressed during multi-turn interaction, and adapt its clarification strategy to different user personas. These capabilities together determine whether an LLM can transform a vague user intent into reliable software requirements, supporting subsequent code generation. The main contributions of our work are summarized as follows: 

• ReqClarifyBench: We introduce ReqClarifyBench, the first interactive requirement clarification benchmark for repository-level software development, aiming to evaluate LLMs’ ability to transform vague user intents into clear and complete requirement documents through multi-turn interaction. In addition, we design three new evaluation metrics to assess LLMs’ interactive requirement clarification capabilities. 

• Realistic User Simulation: We construct three representative user personas based on a large-scale dataset of multi-turn conversations between software developers and coding agents, aiming to support realistic multi-turn requirement clarification. 

• Empirical Study: We conduct an empirical study to evaluate the requirement clarification capabilities of different LLMs and their impact on subsequent code generation, providing a systematic understanding of both current model capabilities and the role of requirement clarification in LLM-based software development. 

• Data Availability: We open-source the code and data at [2].

2 Background & Related Work 2.1 LLM-based Repository-level Code Generation 

LLM-based code generation has advanced from function-level programming to end-to-end repository-level software engineering [6, 12, 29, 31, 37, 44, 54]. Several approaches are proposed to facilitate this progress. MetaGPT [29] employs agents with different roles to collaboratively perform requirement analysis, system design, and code implementation. ChatDev [44] coordinates role-playing agents through communication across the design, coding, and testing stages. RPG [37] uses a structured Repository Planning Graph to support planning and repository generation. However, these approaches typically treat the initial user intent as a fixed task objective. Although requirement analysis is included, missing information is generally inferred by LLMs rather than clarified through interaction with the user. Consequently, the resulting software may deviate from the user’s actual intent. The conversational capabilities of LLMs enable them to proactively ask clarification questions and construct a clear and complete requirement document based on user feedback. Nevertheless, interactive requirement clarification remains underexplored in repository-level software development. In this paper, we introduce ReqClarifyBench and conduct an empirical study to investigate the role of requirement clarification in repository-level software development. 

2.2 Code Generation Benchmarks 

As shown in Table 1, early code generation benchmarks primarily focus on function-level tasks. HumanEval [12], MBPP [6], and LiveCodeBench [30] require LLMs to generate correct programs or functions from natural language problem descriptions. SWE-bench [31] subsequently extends evaluation to real-world code repositories. Its tasks are derived from GitHub issues and their corresponding pull requests, requiring LLMs to understand existing repositories and generate code modifications that resolve the reported issues. Recent benchmarks have further shifted toward end-to-end repository-level software development. FeatureBench [59] evaluates the implementation of complex features in existing repositories. WebGen-Bench [36] and NL2Repo-Bench [19] assess the generation of multi-file websites and complete code repositories from natural language require-ments, respectively. MiniAppBench [57] and GameCraft-Bench [38] further extend evaluation to the end-to-end generation of applications and playable games.

Despite the growing task complexity, these benchmarks typically evaluate code generation from fixed requirements. In real-world development, however, users often begin with a vague intent, leaving many important requirements to be progressively clarified through interactions. Benchmarks that provide complete and clear descriptions [6, 12, 19, 30, 31, 38, 59] overlook the requirement clarification process, failing to reflect real-world development scenarios. Conversely, benchmarks using vague requests as inputs [36, 57] require LLMs to infer missing information without user feedback, making it difficult to determine whether failures stem from limited code generation capabilities or requirement misunderstandings. This highlights the need to systematically evaluate LLMs’ ability to transform vague and incomplete user intents into clear requirement documents through interactions. 

2.3 Interactive Requirement Clarification 

Requirement clarification is a central problem in Requirements Engineering (RE) [8, 53]. It typically involves iterative interaction with stakeholders to clarify their goals, constraints, and unstated requirements [23]. Recent studies have explored requirement clarification for LLM-based code generation from different perspectives. ClarifyGPT [39] detects ambiguous requirements, generates targeted clarification questions, and refines the requirements based on user responses before generating code. ClarifyCoder [50] fine-tunes LLMs to recognize underspecified problems and request missing information. ClarifyCodeBench [21] introduces an interactive benchmark containing underspecified programming problems, annotated clarification questions and answers, and executable test cases. However, these studies primarily focus on simple function-level problems, failing to reflect real-world complex software development. ReqElicitGym [32] models requirement clarification as a multi-turn elicitation process, but its simulated user is modeled as a single oracle user following predefined interaction rules, which fails to capture the diversity of interaction styles and behavioral patterns among real users. Moreover, ReqElicitGym does not further investigate the impact of requirement clarification on subsequent code generation. In contrast, our proposed ReqClarifyBench evaluates interactive requirement clarification for repository-level software development using LLM-based user simulators with diverse personas. 

3 ReqClarifyBench 

In this section, we introduce ReqClarifyBench, the first interactive requirement clarification benchmark for repository-level software development, aiming to evaluate LLMs’ ability to transform vague user intents into clear requirement documents through multi-turn interaction. We first describe the construction procedure and then present the characteristics of ReqClarifyBench. 

3.1 Benchmark Construction 

As illustrated in Figure 2, ReqClarifyBench is constructed through a semi-automated human-in-the-loop pipeline, which consists of three stages: source benchmark curation, requirement reconstruction and intent abstraction, and human validation. The pipeline is designed to enable adaptation to new datasets. Each task instance ultimately contains three core components: a high-level vague user intent, a complete and clear requirement document, and the corresponding code evaluation artifacts for assessing the generated code. 

Stage I: Source benchmark curation. Following [28, 45, 53, 55], we construct ReqClarify-Bench based on existing code generation benchmarks rather than designing tasks from scratch. Existing benchmarks provide high-quality software development scenarios and reliable code eval-uation protocols. Building on existing benchmarks allows us to focus on data construction and evaluation design for the requirement clarification stage. Meanwhile, we can reuse their code eval-uation protocols to measure the impact of requirement clarification on subsequent implementation.

For source Benchmark Curation, we consider three main criteria. 1) Real-world Requirements. 

The tasks and development scenarios should be grounded in real-world requirements, rather than artificially constructed programming problems. 2) Repository-level Complexity. The tasks should target repository-level code generation rather than simple function completion, reflecting the scale and complexity of real-world software development. 3) Behavioral Evaluation. The benchmark should provide reliable behavioral evaluation. We avoid evaluations that heavily rely on unit tests with rigid interface assumptions, as they may penalize functionally correct implementations that do not conform to predefined APIs or code structures. Based on these criteria, we choose GameCraft-Bench [38], MiniAppBench [57], and WebGen-Bench [36], covering game, application, and web development, respectively. These benchmarks span diverse software domains and provide high-quality repository-level tasks. As shown in Figure 3, they also adopt behavioral evaluation protocols. Specifically, GameCraft-Bench evaluates recorded gameplay videos and frames using a multimodal rubric-based judge; MiniAppBench combines static code analysis with dynamic browser-based evidence collected through Playwright; and WebGen-Bench employs a UI agent to interact with the generated website and evaluates both test-case accuracy and visual appearance. These protocols assess generated software through observable behavior, allowing us to reliably measure the impact of clarification on subsequent phases.

We leverage an LLM to reconstruct structured requirement documents from these artifacts. This process aims to collect implicit requirements distributed across different artifacts and represent them in an explicit requirement format. After obtaining the detailed requirement documents, we use an LLM to perform intent abstraction. Stage III: Human validation. To ensure the reliability of the constructed benchmark, we further conduct human validation. The validation is conducted by two authors. Guided by the requirement quality criteria in ISO/IEC/IEEE 29148:2018 [1], the reconstructed requirement documents are examined for Correctness, Unambiguity, Completeness, and Consistency. Specifically, Correctness 

assesses whether the requirements accurately capture the intended software functionality and be-havior. Unambiguity checks whether each requirement is clearly stated. Completeness examines whether essential functions, constraints, and behaviors are sufficiently covered. Consistency checks for conflicts across requirements. Requirement–artifact traceability facilitates human validation by allowing annotators to inspect the supporting evidence for each requirement. Requirements found to be incorrect, ambiguous, incomplete, or inconsistent are regenerated and then re-validated. After validating the reconstructed requirement documents, we further examine the abstraction validity of the high-level user intents, ensuring that they preserve the core software objectives. Only samples that pass both validation stages are included in ReqClarifyBench. 

3.2 Benchmark Statistics. 

Table 2 presents the statistics of ReqClarifyBench across its three source benchmarks. In total, ReqClarifyBench contains 341 tasks, comprising 100 tasks from MiniAppBench, 140 from GameCraft-Bench, and 101 from WebGen-Bench. Each task is paired with a human-validated detailed requirement document and its corresponding high-level user intent. Each detailed require-ment document contains 193 atomic requirements and 2,380 tokens on average. In contrast, the corresponding abstracted user intents contain only 13 tokens on average. Notably, this obvious length gap is consistent across all three sources, indicating that intent abstraction removes many details and leaves substantial room for subsequent requirement clarification.

4.2 LLM-based User Simulator 

Following prior work [32, 39, 48, 60], we employ an LLM to act as the user to engage in multi-turn requirement clarification with the evaluated LLM. Compared with involving human users in interactions, an LLM-based simulator enables large-scale reproducible experiments with substan-tially lower effort and time costs, while approximating basic user behaviors and producing natural responses under controlled settings [20, 41, 51, 61]. For each task, the LLM-based user simulator is provided with a human-validated detailed requirement document as the ground-truth requirements and answers the clarification questions accordingly. However, ensuring that the LLM-based user simulator’s responses are consistent with the ground-truth requirements is insufficient to simulate realistic user interactions. Real users differ in how they express their needs, disclose information, and revise their requirements [9, 34]. To simulate realistic interactions, we introduce representative user personas based on real-world interaction data. Specifically, we build on SWE-chat [7], a large-scale dataset of multi-turn interactions between real software developers and coding agents. SWE-chat categorizes users into four types: Expert Nitpicker, Vague Requester, Mind Changer , and Other. We adopt the first three personas, which together account for approximately 80% of SWE-chat. To better capture their distinct interaction patterns, we further refine each persona based on corresponding real-world interaction trajectories. 

Expert Nitpickers provide accurate and detailed responses while keeping their goals stable. Vague Requesters describe their needs in broad terms and leave many details unspecified. Mind Changers 

revise their requirements as the interaction progresses. These personas are then used to guide the LLM-based user simulator to respond throughout the clarification process, producing more diverse and realistic user interactions. To assess whether the user simulator exhibits distinct behavioral patterns corresponding to the intended personas, we conduct a blind human evaluation with two annotators. Specifically, the annotators are unaware of the specific persona assigned and independently classify each complete interaction trajectory as Expert Nitpicker , Vague Requester , Mind Changer , or Other . We randomly sample 60 tasks and obtain interaction trajectories for all three personas, resulting in 180 cases. Following [10, 32], we report the average classification accuracy across annotators relative to the assigned personas, and Cohen’s 𝜅 [33] for inter-annotator agreement. The resulting accuracy is 95.8% and Cohen’s 𝜅 is 0.892, suggesting that the user simulator exhibits distinct behavioral patterns corresponding to the intended personas.

We evaluate six representative LLMs on ReqClarifyBench, including three proprietary models (GPT-5.6-Sol [43], Claude Opus 5 [4], and Gemini-3.1-Pro [27]) and three open-weight models (GLM-5.3 [26], DeepSeek-V4-Pro [16] and Qwen3-235B-A22B [52]). To ensure a fair comparison, we vary only the evaluated LLM while keeping all other experimental settings fixed throughout all experiments, including the LLM-based user simulator, task inputs, persona settings, and interaction protocol. 

4.5 Implementation Details 

We use GPT-5.6-Sol as the foundation model of user simulator and set its temperature to 0.7 to allow natural variation in simulated responses following prior works [32, 40]. For all evaluated LLMs, we set the temperature to 0.0 to minimize sampling randomness and ensure a fair and stable comparison across models. Similarly, all LLM-as-a-Judge evaluations are conducted with a temper-ature of 0.0 to improve the consistency of automatic judgments, using DeepSeek-V4.1-Flash [15]. Following prior works [32, 46], each requirement clarification session is limited to a maximum of 20 interaction rounds to provide sufficient room for clarification while preventing excessively long interactions. We automatically record the complete interaction history for subsequent analysis and validation. All experimental configurations and parameters will be released together with our source code to facilitate reproducibility and future benchmarking. The choices of models for both the LLM-based user simulator and LLM-as-a-Judge are empirically validated. As described in Section 4.2, human annotators achieve an average persona classification accuracy of 95.8%, with an inter-annotator Cohen’s 𝜅 of 0.892, indicating that the GPT-5.6-Sol-based user simulator exhibits distinct behavioral patterns corresponding to the intended personas. 5 Evaluation 

We conduct a comprehensive empirical study on ReqClarifyBench and mainly investigate the following five research questions: 

• RQ1: Overall performance. We evaluate the overall requirement clarification performance of the studied LLMs on ReqClarifyBench across three representative user personas. 

• RQ2: LLMs’ clarification behavior. We analyze how LLMs differ in stopping behavior and clarification dynamics across interaction rounds under different user personas. 

• RQ3: Impact of Clarification on Requirement Document Quality. We quantify the impact of requirement clarification on requirement document quality by comparing documents generated with and without interactive requirement clarification. 

• RQ4: Effect of coding-agent harness. To assess how coding-agent harnesses affect requirement clarification, we compare standalone LLMs with the same LLMs running within coding-agent harness, while keeping other experimental conditions fixed. 

• RQ5: Impact on Code Generation. We investigate the impact of clarification and document generation on code implementation, based on the initial high-level intent, directly generated requirement documents, and interactively clarified requirement documents, respectively. 

5.1 RQ1: Overall Performance 

Table 4 presents the overall performance of the six studied LLMs on ReqClarifyBench across three representative personas. Based on the results, we have the following observations. 

(1) Clarification effectiveness does not necessarily translate into requirement document quality. Different models exhibit inconsistent performance between clarification effectiveness and final requirement document quality. GPT-5.6-Sol achieves the best requirement document quality, with an average BERTScore F1 of 0.774 and an average ReqAlign of 0.727, outperforming the second-best model (Claude Opus 5) by 26.0% in ReqAlign. However, it exhibits the lowest clarification effectiveness, with an average EQR of 0.196 and AvgClarified of 0.650. In contrast, Gemini-3.1-Pro

performs best during the clarification process, achieving the highest average EQR of 0.334 and AvgClarified of 1.702 among all models. However, its average ReqAlign is only 0.357, substantially lower than the 0.727 achieved by GPT-5.6-Sol. Therefore, clarification effectiveness and requirement document quality reflect two related but distinct capabilities. Effective clarification helps the model elicit important requirement information, whereas producing a high-quality document further requires the model to correctly understand and integrate the information gathered across multiple turns. This process may further depend on the model’s ability to leverage interaction context, domain knowledge, and reasoning. 

Finding 1: Effective clarification does not necessarily lead to high-quality requirement docu-ments. This finding indicates that asking effective clarification questions is only one important part of requirement clarification, while correctly understanding and integrating information across multiple turns is equally critical. 

(2) User personas substantially affect requirement clarification performance. All models perform best under the Expert Nitpicker persona, while both requirement document quality and clarification effectiveness decline noticeably when interacting with Vague Requesters and Mind Changers. For ReqAlign, the average score across the six models is approximately 0.609 under Expert Nitpicker, but decreases to 0.433 and 0.439 under Vague Requester and Mind Changer, respectively. In contrast, BERTScore F1 varies much less, decreasing only from 0.732 under Expert Nitpicker to approximately 0.702 under the other two personas. This suggests that user personas have a particularly pronounced impact on fine-grained requirement alignment. The differences are even more evident in clarification effectiveness. Among the six models, the average EQR is approximately 0.448 under Expert Nitpicker, compared with only 0.177 and 0.208 under Vague Requester and Mind Changer, respectively. AvgClarified similarly decreases from 2.384 to 0.549 and 0.610. These results suggest that LLMs remain highly sensitive to user interaction styles. They perform substantially better when users provide explicit and detailed responses, but degrade noticeably when user feedback is vague or when requirements change during the interaction. 

Finding 2: User personas have a substantial impact on requirement clarification performance, and current LLMs still exhibit noticeable performance degradation when faced with vague feedback or changing requirements. 

(3) Models exhibit different levels of robustness across user personas. In terms of final requirement document quality, GPT-5.6-Sol shows relatively strong robustness to persona changes. Its ReqAlign decreases from 0.842 under Expert Nitpicker to 0.681 and 0.659 under Vague Requester and Mind Changer, retaining approximately 81% and 78% of its performance, respectively. GLM-5.3 also shows a relatively stable trend, with ReqAlign decreasing from 0.618 to 0.471 and 0.474, retaining approximately 76% and 77%. In contrast, Qwen3-235B-A22B is the most sensitive to persona changes, with ReqAlign dropping from 0.424 under Expert Nitpicker to 0.197 and 0.226, retaining only approximately 46% and 53% of its performance. Claude Opus 5, Gemini-3.1-Pro, and DeepSeek-V4-Pro fall between these two extremes. These results indicate that models differ substantially in their ability to maintain requirement understanding and integration when user feedback becomes less informative or requirements evolve during the interaction. 

Finding 3: Models show varying stability across user personas, suggesting that persona robust-ness is an important dimension for distinguishing their requirement clarification capabilities.

5.3 RQ3: Impact of Clarification on Requirement Document Quality 

As shown in Figure 7, we investigate the impact of interactive clarification on final requirement document quality by comparing two settings: directly generating requirement documents from initial user intents and generating them after multi-turn requirement clarification. 

Overall, all models benefit from requirement clarification, producing more complete and clear requirement documents from vague user intents. Specifically, the average BERTScore F1 across the six models increases from 0.664 to 0.712, with a 7.2% relative improvement. Additionally, the improvement in fine-grained requirement alignment is substantially more pronounced. The average ReqAlign score rises from 0.212 to 0.494 with a relative improvement of 133.1%. This trend is also consistent across different models, with relative improvements ranging from 83.8% (GLM-5.3) to 241.3% (Qwen3-235B-A22B). The substantially larger improvement in ReqAlign suggests that clarification particularly helps models capture fine-grained requirements that are missing from the initial user intent. Notably, GPT-5.6-Sol achieves the highest ReqAlign both with and without interactive clarification, demonstrating its consistently strong requirement document generation capability across the two settings. 

Finding 6: Requirement clarification consistently improves requirement document quality across all models, with substantially larger gains in fine-grained requirement alignment than in overall semantic similarity. GPT-5.6-Sol further maintains the strongest ReqAlign performance both with and without clarification.

6 Discussion 6.1 Practical Implications 

(1) LLMs should proactively clarify requirements before implementation. In practice, developers often provide high-level and underspecified requests. Rather than proceeding directly to implementation and filling in missing details based on their own assumptions, LLMs should first identify unclear or missing requirements and actively ask developers for clarification. Our study shows that such interactive clarification can elicit additional requirement information that ultimately improves subsequent code-generation performance. This suggests that requirement clarification should be treated as an explicit capability of LLMs, rather than leaving the burden of fully specifying requirements to developers in the initial request.  

> , Vol. 1, No. 1, Article . Publication date: October 2026. 18 Mingyu Chen, Zhiqing Zhong, Manyi Wang, Linxi Liang, Rouyu Chen, and Pinjia He

(2) Requirement documentation is beneficial even without additional user feedback. 

We find that guiding the LLM to first transform the initial intent into an explicit requirement document, and then generate code based on that document, consistently outperforms direct code generation from the initial intent. This suggests that a requirement document is not merely a record of clarification outcomes, but also serves as an important intermediate representation between user intent and code implementation. In practice, even when further clarification with the developer is unavailable, introducing an explicit requirement-document generation stage before coding can still improve subsequent implementation compared with directly using the original request. 

(3) Requirement engineering and code implementation may be better handled by differ-ent forms of model systems. We observe that coding-oriented agent harnesses such as Claude Code and Codex ask more effective clarification questions, yet produce lower-quality final require-ment documents than their corresponding base models. This suggests that scaffolding designed for code execution may not be equally well suited to requirement-document generation. A more suitable workflow may therefore decouple the requirement and implementation stages. Developers can first use a base model for requirement analysis, integration of clarified information, and final requirement-document generation, and then pass the resulting document to coding-agent harnesses such as Claude Code or Codex for repository-level implementation. Such a staged workflow can leverage the respective strengths of base models in requirement documentation and coding-agent harnesses in code execution and software-development tooling, rather than relying on a single agent to handle the entire process from underspecified requests to final implementation. 

6.2 Threats to Validity 

External Validity. A primary threat to external validity is the reliability of user simulation. Real developers vary substantially in how they express requirements, provide information, and revise their needs, and an LLM-based user simulator may not fully capture this diversity. To mitigate this threat, we derive three representative user personas from SWE-chat [7] to guide the LLM-based user simulator. SWE-chat is a large-scale dataset of multi-turn conversations between software developers and coding agents, reflecting diverse interaction behaviors in real-world development settings. We also conduct human validation to verify that the user simulator exhibits distinct behavioral patterns corresponding to the intended personas. 

Internal Validity. A potential threat to internal validity arises from possible errors in the interaction protocol, prompt design, model configuration, and experimental execution. Such errors may affect the observed clarification behavior or subsequent code-generation evaluation. To reduce this risk, we use a consistent interaction protocol and standardized prompt templates across all evaluated models and settings, and keep the experimental configurations fixed whenever possible. In addition, we have open-sourced our implementation, experimental data, and all prompt templates, enabling external validation and community feedback for continuous improvement. 

Construct Validity. A primary threat to construct validity is the quality of the ground-truth requirement documents in ReqClarifyBench. To mitigate this threat, two authors manually validate the reconstructed requirement documents by examining their correctness, unambiguity, completeness, and consistency. Requirement–artifact traceability further helps the two validators verify the implementation evidence supporting each requirement. Requirements that fail the validation are regenerated and re-examined. We also validate the abstraction validity of the high-level user intents to ensure that they preserve the core software objectives. Only samples that pass both stages of human validation are included in ReqClarifyBench.

7 Conclusion 

In this paper, we propose ReqClarifyBench, the first interactive requirement clarification benchmark for repository-level software development, which aims to evaluate LLMs’ ability to transform vague user intents into clear and complete requirement documents through multi-turn interactions. To better simulate realistic interactions, we further employ LLM-based user simulators with three representative personas. Based on ReqClarifyBench, we conduct a systematic empirical study. The results reveal that clarification effectiveness does not necessarily lead to high-quality requirement documents, and that model performance varies substantially across different user interaction styles. We also find that coding-agent harnesses do not further enhance the quality of derived requirement documents. These findings offer practical implications for developers using LLMs for software development. More broadly, our work highlights that software development agents’ autonomy should encompass understanding user intent through proactive interaction and aligning development goals accordingly. This offers a user-centered perspective on the design and evaluation of future autonomous development systems.

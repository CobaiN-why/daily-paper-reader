## 摘要
随着LLM越来越有能力实现软件，一个关键瓶颈显现：它们是否真正理解用户想要什么。用户常常从模糊意图开始，将重要需求留待通过交互澄清。在仓库级开发中，误解会传播并导致代价高昂的返工。然而，现有基准通常从完整规格或欠指定请求出发评估实现，忽视了编码前的需求澄清。此前的澄清研究主要关注函数级任务。因此，LLM能在多大程度上通过交互将模糊意图转化为清晰需求，以及这种能力如何影响后续代码生成，仍不清楚。我们提出ReqClarifyBench，一个面向仓库级软件开发的交互式需求澄清基准。它包含341个任务，涵盖游戏、小程序和Web开发，每个任务都有一个模糊的用户意图、一份经人工验证的需求文档以及代码评估产物。我们采用基于LLM的用户模拟器，其具有源自真实世界对话的多样化用户画像。我们从澄清有效性和生成需求文档质量两方面评估六个LLM。结果表明，更强的澄清有效性并不一定转化为更高的文档质量，且不同用户画像之间的表现差异很大。我们还发现，与基础LLM相比，编码智能体框架并未进一步提高需求文档质量。这些发现为构建基于LLM的端到端软件开发系统提供了洞见。

## Abstract
As LLMs become increasingly capable of implementing software, a critical bottleneck emerges: whether they truly understand what users want. Users often begin with vague intent, leaving important requirements to be clarified through interaction. In repository-level development, misunderstandings can propagate and cause costly rework. However, existing benchmarks typically evaluate implementation from complete specifications or underspecified requests, overlooking pre-coding requirement clarification. Prior clarification studies mainly focus on function-level tasks. It therefore remains unclear how well LLMs can transform vague intent into clear requirements through interaction and how this capability affects subsequent code generation.   We introduce ReqClarifyBench, an interactive requirement clarification benchmark for repository-level software development. It contains 341 tasks spanning game, miniapp, and web development, each with a vague user intent, a human-validated requirement document, and code evaluation artifacts. We employ LLM-based user simulators with diverse personas derived from real-world conversations. We evaluate six LLMs in terms of clarification effectiveness and generated requirement document quality. Results show that stronger clarification effectiveness does not necessarily translate into higher document quality, and performance varies substantially across user personas. We also find that coding-agent harnesses do not further improve requirement document quality compared with their base LLMs. These findings offer insights for building LLM-based end-to-end software development systems.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：随着 LLM 实现能力的快速提升，软件开发正逐步转向“用户描述意图、LLM 完成实现”的需求驱动范式。但该范式的成功前提是需求清晰完整，而现实中用户往往从模糊意图出发，需通过多轮交互逐步澄清。
- **核心瓶颈**：LLM 是否真正理解用户想要什么，正成为比代码实现能力更关键的瓶颈。若忽视需求澄清，LLM 会自行“猜测”缺失信息，错误假设会传播至设计、实现、测试各阶段，在长周期任务中造成返工与大量 token/时间浪费。
- **现有工作不足**：
  - 现有仓库级代码生成基准（如 SWE-bench、WebGen-Bench、FeatureBench、MiniAppBench、GameCraft-Bench 等）多从完整规格或欠指定请求直接评估代码生成，**忽视编码前的需求澄清过程**。
  - 已有需求澄清研究（如 ClarifyGPT、ClarifyCoder、ClarifyCodeBench、ReqElicitGym）主要聚焦**函数级任务**，或使用固定交互模式的单一模拟用户，无法反映真实仓库级开发场景与多样化用户行为。
- **研究问题**：LLM 能在多大程度上通过交互将模糊用户意图转化为清晰需求？这种澄清能力又如何影响后续代码生成？
- **整体含义**：论文首次系统性地将“交互式需求澄清”作为仓库级软件开发的独立评估维度，主张需求澄清应被视为 LLM 的一项显式能力，而非将完整规格的负担完全推给用户。

## 2. 方法论：核心思想与关键技术细节

### 2.1 核心思想
提出 **ReqClarifyBench**——首个面向仓库级软件开发的交互式需求澄清基准，用于评估 LLM 通过多轮交互将模糊用户意图转化为清晰、完整需求文档的能力，并进一步衡量该能力对下游代码生成的影响。

### 2.2 基准构建流程（三阶段半自动化人机协同流水线）
- **Stage I：源基准筛选**。基于三条准则选择源基准：①真实世界需求；②仓库级复杂度；③行为化评估（避免过度依赖刚性接口假设的单元测试）。最终选定 GameCraft-Bench（游戏）、MiniAppBench（小程序）、WebGen-Bench（网页）三个覆盖不同领域的仓库级基准，它们分别采用多模态评分、Playwright 浏览器动态证据、UI Agent 交互等行为化评估协议。
- **Stage II：需求重建与意图抽象**。利用 LLM 将各源基准的异构产物（项目描述、评分标准、参考代码、测试用例等）统一重建为结构化需求文档，并引入**需求–产物可追溯机制**（每条需求须关联对应产物与证据来源），防止幻觉需求。随后通过 LLM 进行意图抽象，去除实现细节、保留核心软件目标，得到高层次的模糊用户意图，作为澄清交互的起点。
- **Stage III：人工验证**。由两位作者依据 ISO/IEC/IEEE 29148:2018 的质量准则，从**正确性、无歧义性、完整性、一致性**四个维度审查需求文档，并验证意图抽象的合理性。未通过的样本重新生成并再次验证，仅双重通过的样本进入基准。

### 2.3 交互式需求澄清的建模
- 将需求澄清形式化为 **LLM 与被模拟用户之间的多轮交互**。LLM 初始仅接收高层模糊意图，主动提出澄清问题，基于交互历史决定下一步澄清内容及何时停止，最终产出详细需求文档。完整交互历史被自动记录用于评估。

### 2.4 LLM 用户模拟器与用户画像
- 采用 LLM 作为用户模拟器，以人工验证的详细需求文档作为 ground-truth 回答澄清问题。
- 为模拟真实用户多样性，基于 **SWE-chat**（真实开发者与编码智能体多轮对话的大规模数据集）构建三种代表性用户画像（合计约占 SWE-chat 的 80%）：
  - **Expert Nitpicker（专家挑刺者）**：回答准确详细，目标稳定。
  - **Vague Requester（模糊请求者）**：表述宽泛，大量细节未指定。
  - **Mind Changer（需求变更者）**：随交互推进不断修改需求。
- 通过盲测人工评估验证模拟器的画像区分度：两位标注者对 60 个任务 × 3 种画像共 180 条交互轨迹进行分类，平均准确率 **95.8%**，Cohen's κ = **0.892**。

### 2.5 评估指标（四个，两个维度）
- **澄清有效性维度**：
  - **Effective Question Rate (EQR)**：提出至少澄清一条 ground-truth 原子需求的问题占比，EQR = (1/T) Σ I(cₜ > 0)。
  - **AvgClarified**：每个问题平均澄清的原子需求数，AvgClarified = (1/T) Σ cₜ。
- **需求文档质量维度**：
  - **BERTScore F1**：基于上下文嵌入的双向匹配，衡量生成文档与 ground-truth 文档的整体语义相似度。
  - **Requirement Alignment (ReqAlign)**：将 ground-truth 文档分解为原子需求集合，用 LLM-as-a-Judge 判定每条需求为 Covered（+1）、Omitted（0）或 Violated（−1），取平均，范围 [−1, 1]。

## 3. 实验设计

- **数据集 / 场景**：ReqClarifyBench 共 **341 个任务**，涵盖：
  - MiniAppBench：100 个任务（平均 157 条原子需求，1,781 tokens）
  - GameCraft-Bench：140 个任务（平均 240 条原子需求，3,526 tokens）
  - WebGen-Bench：101 个任务（平均 165 条原子需求，1,383 tokens）
  - 整体平均：193 条原子需求 / 2,380 tokens 需求文档；模糊意图平均仅 **13 tokens**，长度差距显著，为澄清留出大量空间。
- **对比方法（6 个 LLM）**：
  - 闭源：GPT-5.6-Sol、Claude Opus 5、Gemini-3.1-Pro
  - 开源权重：GLM-5.3（753B）、DeepSeek-V4-Pro（1.6T）、Qwen3-235B-A22B（235B）
- **编码智能体框架对比**：将 Claude-Opus-5 与 GPT-5.6-Sol 与其对应的编码智能体封装（Claude Code、Codex）进行对照。
- **实现细节**：
  - 用户模拟器基础模型为 GPT-5.6-Sol，temperature = 0.7；被评估 LLM 与 LLM-as-Judge 均设 temperature = 0.0。
  - LLM-as-Judge 选用 DeepSeek-V4.1-Flash（在 200 条人工标注样本上准确率 91.5%，成本较低）。
  - 每次澄清会话上限 **20 轮**。
  - 代码生成实验统一使用 Codex + GPT-5.6-Sol，分数在三种用户画像上取平均。
- **五个研究问题（RQ）**：
  - RQ1：整体性能（跨模型与用户画像）
  - RQ2：LLM 澄清行为（停止行为与逐轮动态）
  - RQ3：澄清对需求文档质量的影响（有无澄清对比）
  - RQ4：编码智能体框架的影响
  - RQ5：对代码生成的影响（三种输入设置对比）

## 6. 主要结论与发现

论文给出 8 条核心 Finding：

- **Finding 1（澄清有效性 ≠ 文档质量）**：GPT-5.6-Sol 文档质量最佳（BERTScore F1 0.774、ReqAlign 0.727，ReqAlign 超第二名 26.0%），但澄清有效性最低（EQR 0.196、AvgClarified 0.650）；Gemini-3.1-Pro 澄清有效性最高（EQR 0.334、AvgClarified 1.702），但 ReqAlign 仅 0.357。二者是相关但不同的能力。
- **Finding 2（用户画像影响显著）**：所有模型在 Expert Nitpicker 下表现最佳；ReqAlign 从平均 0.609 降至 Vague Requester 的 0.433、Mind Changer 的 0.439；EQR 从 0.448 降至 0.177 / 0.208；BERTScore 变化较小（0.732 → ~0.702），说明画像对细粒度需求对齐影响尤为突出。
- **Finding 3（模型鲁棒性差异）**：GPT-5.6-Sol 对画像变化最鲁棒（ReqAlign 保留约 81%/78%），GLM-5.3 次之（76%/77%）；Qwen3-235B-A22B 最敏感（仅保留 46%/53%）。
- **Finding 4（停止行为）**：交互轮数普遍呈现 Expert Nitpicker 最短、Mind Changer 次之、Vague Requester 最长的趋势，但差异幅度因模型而异——GPT-5.6-Sol 与 Claude-Opus-5 变化最剧烈，Gemini-3.1-Pro 最稳定（始终约 2–3 轮）。
- **Finding 5（澄清动态）**：三种画像对应三种模式——Expert Nitpicker 为“短而信息密集”，Mind Changer 的新信息常在后期出现，Vague Requester 为“低产出但持续累积”。在模糊请求下，模型在每轮信息增益与停止行为上进一步分化。
- **Finding 6（澄清提升文档质量）**：所有模型均从澄清中获益，BERTScore F1 平均从 0.664 升至 0.712（+7.2%），ReqAlign 从 0.212 升至 0.494（**+133.1%**），细粒度对齐提升远大于整体语义相似度。
- **Finding 7（编码智能体框架的权衡）**：Claude Code 与 Codex 相比基座模型澄清有效性更高（EQR、AvgClarified 均提升），但最终需求文档质量反而更低，ReqAlign 在 Expert Nitpicker 下分别下降 15.2%（Claude）与 24.0%（GPT）。说明面向代码执行的脚手架未必适合需求文档生成。
- **Finding 8（澄清改善代码生成）**：三种输入设置下性能递增——初始意图 → 直接生成需求文档 → 交互澄清后的需求文档。即使无额外用户反馈，先写需求文档再编码也优于直接从意图生成代码；交互澄清在此基础上进一步带来增益（如 GameCraft-Bench 0.012 → 0.273 → 0.418，MiniAppBench 0.451 → 0.543 → 0.943，WebGen-Bench 0.271 → 0.384 → 0.659）。

## 7. 优点

- **首个仓库级交互式需求澄清基准**：填补了现有基准忽视编码前澄清、以及既有澄清研究局限于函数级的空白，任务粒度与真实开发场景更贴近。
- **真实感强的用户模拟**：基于 SWE-chat 真实对话数据构建三种用户画像，并通过盲测人工验证（准确率 95.8%、κ = 0.892）证明模拟器行为具有区分度，优于固定交互模式的单一 oracle 用户。
- **严谨的基准构建流水线**：半自动化 + 人机协同，引入需求–产物可追溯机制防止幻觉，并由人工按 ISO/IEC/IEEE 29148:2018 四维度验证。
- **多维度、互补的评估体系**：过程指标（EQR、AvgClarified）与结果指标（BERTScore F1、ReqAlign）结合，避免单一指标误导；ReqAlign 的 +1/0/−1 三态设计能区分“遗漏”与“违背”。
- **端到端验证**：不仅评估澄清本身，还延伸到需求文档质量与最终代码生成，并额外考察编码智能体框架的影响，结论具有实践指导价值。
- **公平性与可复现性**：固定除被评估模型外

所有变量，仅改变被评估 LLM，用户模拟器、任务输入、画像设置与交互协议保持一致；被评估模型与裁判均设 temperature = 0.0 以降低随机性；代码与数据已在 Zenodo 开源，实验配置随源码发布，具备较好的可复现基础。

## 8. 局限与不足

- **评估依赖 LLM 用户模拟器，而非真实用户**：尽管画像经人工验证具有区分度，但模拟器的回答仍以 ground-truth 需求文档为唯一依据，可能过于“配合”或在被追问时过度泄露细节，与真实用户的知识盲区、表达习惯、情绪与妥协行为存在差距。论文自身也未开展真实用户研究（user study）加以校准。
- **代码生成实验的覆盖面有限**：RQ5 仅使用 Codex + GPT-5.6-Sol 单一编码配置，未验证“澄清带来的代码生成增益”是否在其他编码智能体或模型上同样成立；同时分数在三种画像上取平均，掩盖了画像差异对下游代码的影响。
- **源基准领域仍偏窄**：仅覆盖游戏、小程序、网页三类前端/交互型仓库级任务，缺少后端服务、数据管线、系统软件、库/框架维护等场景；这些场景中需求澄清的形态（如性能约束、兼容性、API 契约）可能与本文结论有所不同。
- **模糊意图由 LLM 逆向抽象生成**：起点意图是对完整需求文档的“降维”，其模糊程度、信息缺口分布未必与真实用户初次表达一致，可能存在“人为制造的模糊”而非“自然发生的模糊”。
- **20 轮交互上限的潜在影响**：上限可能截断 Vague Requester 与 Mind Changer 场景下的长尾澄清过程，使得轮数受限模型的指标被低估，或使停止行为分析受人为边界干扰。
- **指标本身的局限**：ReqAlign 依赖 LLM-as-Judge 对原子需求做三态判定，虽在 200 条人工样本上达 91.5% 准确率，但仍存在系统性偏差风险；BERTScore F1 对细粒度遗漏/违背不敏感，可能高估文档质量。此外“原子需求”的切分粒度由 LLM 决定，粒度差异会影响 AvgClarified 与 ReqAlign 的可比性。
- **未披露算力与成本信息**：论文未报告 GPU 型号、数量、推理时长或 token 成本，难以评估方法在真实工程中的部署代价，也无法判断 20 轮交互的实际经济性。
- **澄清与代码生成的因果链条未完全隔离**：RQ5 中“澄清后需求文档”同时改变了输入信息的量与形式，无法完全区分增益来自“更多信息”还是“更好的结构化表达”。

## 9. 对领域的影响与启示

- **重新定位“需求澄清”为 LLM 的一等能力**：论文主张不应把完整规格的负担全部推给用户，而应把主动提问、识别信息缺口、管理需求变更视为与代码生成并列的核心能力，这对 agent 设计与评测体系都有方向性影响。
- **提示“澄清有效性”与“文档质量”可能背离**：Finding 1 与 Finding 7 共同表明，提问多、澄清多并不必然带来更好的需求文档；面向代码执行的脚手架（Claude Code、Codex）反而可能损害文档质量。这提醒研究者不要用单一过程指标替代结果指标，也提示需要为“需求文档生成”设计专门的 agent 形态。
- **用户画像应成为标准评测维度**：Finding 2、3、4、5 显示同一模型在不同用户行为下的表现差异巨大，且模型间鲁棒性排序与平均性能排序并不一致。未来的交互式基准应将用户多样性作为默认控制变量，而非固定为单一 oracle 用户。
- **“先写需求再编码”本身即有价值**：Finding 8 中“直接生成需求文档”已优于“从意图直接生成代码”，说明结构化的中间产物可独立带来增益；交互澄清则是在此基础上的进一步增强。这为实际工程中的提示与流程设计提供了低成本可落地的建议。
- **为后续研究留出明确接口**：基准、画像、指标与开源代码共同构成可扩展框架，后续工作可在此基础上引入真实用户、扩展到更多仓库类型、或研究澄清策略（如何提问、何时停止）本身的优化。

## 10. 总体评价

本文的贡献主要在于**问题设定与评测基础设施**，而非新算法：它把“编码前的需求澄清”从隐含步骤提升为显式、可量化、可复现的评测对象，并给出了覆盖澄清过程、文档质量与下游代码生成的端到端证据链。其基准构建流水线（源基准筛选 → 需求重建与意图抽象 → 人工四维度验证）与基于真实对话数据的用户画像设计，方法学上较为扎实；八条 Finding 中“澄清有效性≠文档质量”“编码脚手架反而降低文档质量”“澄清使细粒度对齐提升 +133.1%”等结论具有反直觉性与实践价值。

同时，其结论的强度受限于“全模拟用户 + 单一代码生成配置 + 三领域源基准”的边界，属于**有说服力的初步证据而非定论**。总体而言，这是一篇定位清晰、实验设计较为周全、对领域有明确推动作用的工作，其最大价值可能在于提供了一个可持续演进的评测平台与一组值得进一步验证的假设。

## 摘要
API规范是现代软件开发中的关键文档，直接影响集成效率和客户端代码生成。尽管近期进展已利用大型语言模型（LLM）从源代码生成初始规范，但现有方法将这一过程视为一次性事件——忽视了对此类产物进行持续验证、长期维护以及市场驱动演进的需求。为解决这一问题，我们提出Agent4Spec，一个自主的多智能体框架，包含两条不同的流水线：（1）一条检测并自我修正OpenAPI语法错误的验证流水线；（2）一条开展竞品研究、识别与行业领先者相比的功能差距，并自动生成缺失的API规范功能的市场分析流水线。我们在两个精选的API规范数据集上评估Agent4Spec，这些数据集涵盖通用和工业场景。在9个SOTA LLM中，表现最佳者实现了100%的语法错误检测率，所提修正的实施成功率超过95%，同时针对建议的端点改进获得了超过50%的采纳率，表明其是API开发的实用工具。

## Abstract
API specifications serve as critical documentation for modern software development, directly impacting integration efficiency and client code generation. While recent advancements have leveraged Large Language Models (LLMs) to generate initial specifications from source code, existing approaches treat this process as a one-time event - overlooking the needs for continuous validation, long-term maintenance, and market-driven evolution of these artifacts. To address this issue, we present Agent4Spec, an autonomous multi-agent framework featuring two distinct pipelines: (1) a validation pipeline that detects and self-corrects OpenAPI syntax errors, and (2) a market analysis pipeline that conducts competitive research, identifies functional gaps against industry leaders, and automatically generates missing API-spec functionalities. We evaluate Agent4Spec on two curated datasets of API specifications spanning both general-purpose and industrial scenarios. Among 9 SOTA LLMs, the top-performer achieves 100% syntax error detection rates and over 95% implementation success for proposed corrections, while securing over 50% adoption rates for suggested endpoint improvements, representing a practical tool for API development.

# Agent4Spec 论文总结

## 1. 核心问题与研究动机

- **背景**：API 规范（尤其是 REST 服务的 OpenAPI Specification, OAS）是服务提供方与消费方之间的契约性文档，直接影响客户端集成效率、API 测试与长期维护。不准确或不完整的规范会误导开发者，并将错误传播到下游工具链。
- **现有工作的缺口**：已有研究（如 Respector、LRASGen、OOPS、SpeCrawler、OASBuilder）主要聚焦于从源代码或在线文档**一次性生成**初始规范，属于"生成前/生成时"阶段。
- **被忽视的问题**：现有方法对**生成后阶段**支持不足——开发者仍需完成：(a) 对整个 OAS 文件进行持续验证与安全修复；(b) 判断 API 是否应随市场预期演进。
- **论文主张**：将 API 规范优化从"一次性事件"重新定义为**持续验证 + 市场驱动演进**的闭环流程，并为此提出多智能体框架 **Agent4Spec**。

## 2. 方法论

### 2.1 核心思想
- 采用**多智能体架构**，由一个编排智能体（Orchestrator Agent, $A_o$）作为中央控制器，根据开发者请求路由到两条互斥的流水线之一（仅执行其一，避免修订指令过载），最后交由修订智能体统一改稿。
- 关键符号：$S_0$ 为原始规范，$S_f$ 为最终修订版，$R$ 为流水线中间报告，$R'$ 为经人工批准后的报告。

### 2.2 验证流水线（Validation Pipeline）
- 验证智能体 $A_v$ 配备两个工具：
  - **文件读取工具** $T_r$：解析并加载 OpenAPI YAML 文件；
  - **验证工具** $T_v$：基于 Python 库 `openapi_spec_validator` 检测语法错误。
- 流程公式：$R_v = A_v(T_v(T_r(S_0)))$，即智能体依据校验错误信息提出修复方案。

### 2.3 市场分析流水线（Market Analysis Pipeline）
由四个顺序执行的智能体组成：
1. **领域识别智能体** $A_d$：读取规范，判定 API 领域并总结关键发展：$R_d = A_d(T_r(S_0))$。
2. **在线搜索智能体** $A_m$：利用网络搜索工具 $T_s$，每查询最多取 3 条结果，优先权威来源（厂商文档、技术媒体），合成市场摘要（含领导者、趋势、定价模型、量化统计）：$R_m = A_m(T_s(R_d))$。
3. **差距分析智能体** $A_g$：将用户 API 与市场领导者对比，识别缺失功能、设计不一致、生态局限，按高/中/低优先级分类并附技术影响评估：$R_g = A_g(R_m, T_r(S_0))$。
4. **端点建议智能体** $A_e$：将优先级缺口转化为具体端点增强、Schema 与迁移指导：$R_e = A_e(R_g, T_r(S_0))$。

### 2.4 修订智能体与迭代再验证
- 修订智能体 $A_r$ 在保持原结构的前提下实施修正，并内置**迭代再验证机制**：修订稿反复送回验证智能体，直至 $n$ 轮后错误消除。
- 形式化：$S_f = A_r^{(n)}(R, T_r(S_0))$，其中 $R = R_v$（验证模式）或 $R = R_e$（市场分析模式）。
- 完成后本地保存修订稿并交还控制权给编排器。

### 2.5 人在回路（Human-in-the-Loop）
- 开发者可**可选地**在修订前审查并选择性批准建议，最终报告 $R' = H(R)$，从而在关键决策点嵌入专家反馈。

## 3. 实验设计

### 3.1 数据集与场景
- **Guru-Spec**：从 APIs.guru 收集的 **300** 个公开 API 规范，覆盖云服务、金融、电商、交通等通用领域；总 token 数 3,483,222，平均每规范 11,610.7 token / 1,549.2 行。
- **Industry-Spec**：从 Xcelerator Developer 获取的 **200** 个工业 API，覆盖自动化、IoT、资产管理、制造等；总 token 数 1,684,932，平均每规范 8,424.7 token / 934.4 行。
- 评估前对每个规范**人工注入一个语法错误**（缩进错位、缺失必需字段如 response description、类型与值不匹配等）。

### 3.2 对比方法与基线
- 基线：**单提示（Single-prompt）**方式，即让同一 LLM 在一次提示中完成验证/修订。
- 评估模型（共 9 个，跨性能层级）：
  - 前沿闭源（API 访问）：Claude-Sonnet-4.6、Gemini-3.1-Pro、GPT-5.2、GPT-4.1、GPT-4o；
  - 紧凑开源（Ollama 本地部署）：Ministral3-8B、LLaMA3.1-8B、Qwen3.5-9B、Gemma4-4B。
- 所有模型温度设为最小值。

### 3.3 评估指标
- **语法验证（可验证任务，定量指标）**：错误检测率、解决方案提出率、解决方案正确率。
- **规范修订**：正确实现率、成功保存率。
- **市场分析（无标准答案）**：LLM-as-a-judge（1–5 分，仅用三个最强模型评判，因小模型评判质量差）+ **人工评估**（3 名软件开发者独立打分取平均，评分标准与 judge prompt 保持一致）。

## 4. 资源与算力

- **未涉及模型训练**：本文为推理型评估，未提及任何 GPU 训练时长或训练算力。
- **部署配置**：
  - 紧凑开源模型通过 **Ollama** 部署在**单台 Apple M4 Pro 机器**上（12 核 CPU、16 核 GPU）；
  - 前沿模型通过 **API 网关**访问；
  - 所有模型使用最低 temperature。
- **资源消耗测量**（每份 API 规范）：
  - 输出 token：验证 162–1,402，在线搜索 720–5,467（搜索因四阶段设计更耗 token）；
  - 延迟：验证 1.8–37.1 秒，在线搜索 16.1–182.2 秒；本地部署的 Ministral-3-8B 与 Qwen-3.5-9B 在线搜索分别需 173.2 与 182.2 秒。
- 结论：**模型部署方式与任务复杂度共同决定资源消耗**。

## 5. 实验数量与充分性

- **实验规模**：2 个数据集 × 9 个模型 × 2 条流水线，覆盖约 500 份 API 规范；市场分析含 4 个顺序阶段（领域识别、在线搜索、差距分析、端点建议）的分别评估，另加人在回路评估与资源消耗测量。
- **对照充分**：所有任务均与单提示基线对比；同时用 LLM-as-a-judge 与人工评估双通道验证。
- **客观性说明**：
  - 语法验证类任务有可验证输出，指标客观；
  - 市场分析类任务无 ground truth，采用三方 LLM 评委 + 3 名人工评估交叉印证，但论文自承 LLM 评委间存在明显评分偏差（如 Claude-Sonnet-4.6 评分异常保守，GPT-5.2 出现自我偏好）。
- **公平性**：人工评估者事先获得与 LLM judge 相同的 prompt 与评分标准，评分取平均，尽量保证一致性。
- **总体评价**：实验覆盖面广、对照完整，但受限于**人工注入错误**而非真实缺陷，外部效度有限。

## 6. 主要结论与发现

- **验证流水线**：
  - Claude-Sonnet-4.6 与 Gemini-3.1-Pro 在两个数据集上均达 **100% 错误检测率**，GPT-5.2 与 GPT-4.1 保持 99%+，GPT-4o 为 94.5%–96.0%；
  - 前沿模型修正正确率 91.5%–99.5%；Qwen-3.5-9B、Ministral-3-8B 降至 87% 左右；
  - LLaMA-3.1-8B 与 Gemma-4-4B 出现典型失败模式：**声称会调用 $T_v$ 但未真正激活工具**，检测率不超过 8%。
- **规范修订**：前沿模型保存率接近 100%，但正确实现率仅 73.5%–98.5%，说明**保存与正确是分离的工具行为**——保存成功不代表修复正确。紧凑模型几乎无法完成全文件修订。
- **市场分析**：四阶段中，模型能力与工具使用可靠性决定输出质量；紧凑模型倾向**依赖先验知识而非检索证据**，导致时效性缺失与下游差距分析质量下降。
- **人在回路**：GPT-5.2 获最高端点采纳分（1.82/3），Claude-Sonnet-4.6（1.79）、Gemini-3.1-Pro（1.73）、GPT-4.1（1.71）紧随；但**即使最佳模型平均采纳数也不足 2 个**，凸显人工审查的必要性。
- **总体结论**：LLM 智能体可将 API 维护推进到静态验证之外，但可靠部署仍依赖模型能力、工具使用、验证机制与人工监督。

## 7. 优点

- **视角新颖**：首次将 API 规范优化明确界定为**生成后（post-generation）闭环工作流**，联合考虑语法验证、市场分析与规范修订。
- **架构清晰**：编排器 + 专用子智能体的分工设计，配合工具调用（文件读取、OpenAPI 校验、网络搜索、保存）与迭代再验证，工程可落地性强。
- **人工可控**：提供可选的 Human-in-the-Loop 机制，避免市场驱动变更被盲目自动应用。
- **数据集互补**：Guru-Spec（通用）与 Industry-Spec（工业）双数据集设计，覆盖广谱 Web 服务与工业场景，增强结论的泛化说服力。
- **评估严谨**：定量指标 + LLM-as-a-judge + 人工评估三重验证，并显式报告评委偏差与自我偏好现象，较为诚实。
- **资源透明**：报告了 token 消耗与延迟，区分本地部署与 API 调用的成本差异，对实际部署有参考价值。
- **附录详尽**：完整给出各智能体的 system prompt、judge prompt 与端到端案例研究，可复现性较好。

## 8. 不足与局限

- **基准缺陷**：因无公开的 OpenAPI 规范修复基准，实验采用**人工注入的常见错误**（数据类型错误、缺失必需字段、结构不一致），与真实世界缺陷分布可能不符；作者亦建议未来从真实版本历史与 issue 报告中构建修复基准。
- **模型覆盖时效性**：仅评估 9 个模型，未来工作需扩展到更多新兴模型以泛化准确率、token 成本与延迟的权衡结论。
- **紧凑模型实用性受限**：4 个开源小模型在工具调用与全文件修订上表现极差，本地部署在当前配置下不实用。
- **市场分析主观性**：无 ground truth，LLM 评委之间分歧明显（保守/宽松/自我偏好），人工评估样本量小（3 人）。
- **端点建议采纳率偏低**：最佳模型不足 2/3，说明市场驱动变更的自动应用仍不可靠，需依赖人工审查。
- **两类流水线互斥**：系统设计上仅执行验证或市场分析之一，未能实现"验证 + 市场"联合修订路径（虽在编排器 prompt 中提到组合修订，但论文实验未覆盖）。
- **未涉及微调或训练**：论文未探索专用提示策略、监督机制或微调以提升工具使用可靠性，仅作为未来方向提出。

## ABSTRACT 

Static coding benchmarks are fixed at release. Over time their tasks leak into train-ing data, and stronger agents eventually saturate them. We argue that a benchmark should instead aim to be self-scaling: its tasks and oracles are created at evaluation time, so no content exists in advance to leak, and its difficulty is set by the par-ticipating agents rather than fixed at release. We introduce SWE-D UEL , an arena in which two coding agents evaluate each other over mirrored Red–Blue turns. In each turn, the Red agent works on a real repository across three context-isolated sessions. It proposes and implements a new feature with feature tests, then embeds a subtle bug in that feature along with sealed bug-triggering tests. The resulting pull request is admitted only if (1) it passes the feature tests and the repository’s existing tests while failing exactly the bug tests, and (2) a fresh session of the same agent can repair the bug blind, which rules out unsolvable tasks. The Blue agent then reviews the pull request without being told a bug exists. It wins only if its revision passes all three test suites, and then the two agents swap roles. We run a tournament among 11 model–harness participants on 15 repositories in five languages for 1,500 turns. The leaders win in different ways. GPT-5.5 with Codex CLI ranks first as the strongest solver, repairing 98.3% of the defects it reviews. Claude Opus 4.8 with mini-swe-agent ranks second as the strongest task author, with a 27.3% Red win rate. ## 1 INTRODUCTION 

Benchmarks are the primary instrument for measuring progress in coding agents. To deliver trust-worthy signal over the long run, a benchmark must remain absent from the training data of the mod-els it evaluates and challenging for agents to solve. This is increasingly difficult to satisfy, as LLMs continually learn from publicly available materials and grow more capable with every generation. The deeper issue is that most existing coding benchmarks are static once released and built from openly accessible sources. Such content is eventually absorbed into training corpora, and a fixed task set is eventually saturated by stronger agents. In other words, from the moment a benchmark is released, it begins to leak into training data and to fall behind the agents it is meant to measure. We argue that avoiding this consequence requires a benchmark to be self-scaling : its tasks and oracles are created at evaluation time, so no content exists in advance to leak, and its difficulty is set by the participating agents rather than fixed at release, so it can rise as those agents improve. Existing benchmarks fall short of this property in different ways. Static benchmarks have already run into this problem: OpenAI recently stopped reporting results on SWE-bench Verified (Jimenez et al., 2024) after finding that frontier models could reproduce its gold patches. Continuously up-dated benchmarks such as SWE-bench-Live (Zhang et al., 2025) and SWE-rebench (Badertdinov et al., 2025) mitigate leakage by collecting tasks created after model training cutoffs, but their task difficulty is still bounded by the daily issues faced by human developers. Most recently, model-generated tasks have emerged as a new direction: BugPilot (Sonwane et al., 2025) collects bugs introduced unintentionally by agents implementing new features, and SwingArena (Xu et al., 2026) pairs LLMs as patch submitters and test-writing reviewers in an adversarial arena. However, BugPi-lot generates its tasks ahead of time as a fixed set and SwingArena still draws tasks from a fixed pool of human-written GitHub issues, generating only the oracles at evaluation time; neither produces tasks whose difficulty grows with the agent being evaluated. This motivates the central question of this work: Can we create a self-scaling benchmark for coding agents? 

To answer this question, we present SWE-D UEL , a self-scaling arena with a evaluation protocol in which two coding agents evaluate each other over mirrored adversarial turns. In each turn, the Red agent, working on a given repository across three context-isolated sessions, proposes a new feature, implements it together with feature tests, and finally injects subtle bugs along with bug-triggering tests. The resulting PR is used in the duel only if 1) it passes the feature tests and the repository’s regression tests while failing exactly the bug-triggering tests, and 2) the Red agent can repair its own bugs in a fresh session, which rules out unsolvable tasks. The Blue agent then reviews the PR and submits a revision, winning the round if and only if the revision passes all three test suites; the two agents swap roles in the next turn. Because every feature, bug, and oracle is created at evaluation time, these specific tasks cannot appear in earlier training data, And because tasks are authored by the agents under evaluation, task difficulty is not fixed by a human-written pool; it can in principle rise as the authors improve, up to the limit set by the self-repair gate. Altogether, a single duel profiles a broad slice of the software engineering lifecycle, including requirement specification, feature implementation, test generation, code review, fault localization, and program repair. We evaluate SWE-D UEL in a tournament among 11 participants, each pairing a frontier proprietary or open-weight model (e.g., GPT-5.5, Claude Opus 4.8, DeepSeek V4 Pro, and Gemini 3.1 Pro) with one of three agent harnesses, on 15 repositories in five languages. Ten participants play a full round robin, and Gemini 3.1 Pro joins afterwards as a late entrant, giving 50 matches and 1,500 turns. The leaders win in different ways. GPT-5.5 with Codex CLI ranks first as the strongest solver, repairing 98.3% of the defects it reviews, while Claude Opus 4.8 with mini-swe-agent ranks second as the strongest task author, with a 27.3% Red win rate. A late entrant can be placed with only five matches, and within one model family, tasks written by the newest version defeat a fixed reviewer far more often than those of older versions (42.9% vs. 4.0%), giving preliminary evidence that difficulty tracks authoring capability. We make the following contributions: • We introduce SWE-D UEL , a self-scaling arena that evaluates coding agents with each other. ## 2 RELATED WORK 

Repository-level coding benchmarks. SWE-bench (Jimenez et al., 2024; OpenAI, 2024) moved evaluation from isolated functions to real issue resolution. Later benchmarks add automated environ-ment setup (Vergopoulos et al., 2025), more languages (Rashid et al., 2025), long-horizon software evolution (Le et al., 2026; Chen et al., 2026), the full issue-resolution cycle (Guan et al., 2026b), and feature addition (Liu et al., 2026). In all of them, the tasks and reference patches are public and fixed before evaluation. However, public tasks eventually enter training data of evaluated LLMs (Matton et al., 2024). The benchmarks thus need to be repeatedly updated to replace the leaked ones. For ex-ample, SWE-bench-Live (Zhang et al., 2025) and SWE-rebench (Badertdinov et al., 2025) regularly collect new tasks from GitHub to remain temporally fresh. (Guan et al., 2026a) and DyCodeE-val (Chen et al., 2025) propose to perturb the tasks to avoid exact memorization, but preserve the original tasks and solutions. Moreover, the tasks come from human development history (issues, pull requests, and releases), so their difficulty is fixed at release, and a fixed task set is saturated as agents improve. The usual response is to build a harder benchmark, such as SWE-Bench Pro (Deng et al., 2025), but each replacement again has a fixed difficulty. Refreshing the benchmark does not solve this as the new tasks come from the same distribution, so the tasks are newer but not harder. In SWE-Duel, both the tasks and their oracles are written at evaluation time by the agents being evaluated. No task exists in advance to leak, and difficulty is set by the participants instead of a fixed human-written pool. 

Automatic bug generation. Early work injects bugs with predefined or learned patterns: symbolic synthesis of deep faults (Roy et al., 2018), bug seeding learned from past fixes (Patra & Pradel, 2021), learned contextual mutations (Richter & Wehrheim, 2022), and re-introducing fixed security bugs (Zhang & Patterson, 2022). These methods show that realistic bugs can be generated auto-matically, but each bug is a local edit drawn from a pattern set, so the variety of bugs is limited by the patterns. LLMs remove this limit. SWE-smith (Yang et al., 2025) prompts LLMs to modify or rewrite functions, BugPilot (Sonwane et al., 2025) collects the regressions that agents cause by acci-dent while adding features, and Self-play SWE-RL (Wei et al., 2025) trains one model to both inject and repair bugs. Both target training data, and they show that LLMs can produce diverse and hard 3Under review as a conference paper at ICLR 2027 bugs at scale. BugPilot is the closest to our task construction, since its bugs also arise while an agent adds a feature. The key difference is what the solver can see. A BugPilot bug is kept only if it breaks existing tests, so running the test suite reveals it. A SWE-D UEL bug is admitted only if all visible tests still pass, so the solver has to find it by reading the code, and only a sealed test can confirm the fix. Our bugs are also deliberate, so the task yield does not depend on agents making mistakes, which may become rarer as agents get more reliable. For evaluation, CDBench (Romazanov et al., 2026) lets an attacker LLM write mutants for a defender LLM, but the mutants are local edits and the defender is shown the mutant diff. In SWE-D UEL , each agent hides a bug inside a new feature for the other to fix, and a task is admitted only after a fresh session of its author repairs the bug blind, so every task is known to be solvable. 

Arena-style evaluation. Chatbot Arena (Chiang et al., 2024) ranks LLMs from pairwise human votes, and Arena-Lite (Son et al., 2025) and Auto-Arena (Zhao et al., 2025) replace human voters with LLM judges and tournament schedules. Arenas stay fresh because new prompts keep arriving, but their outcomes depend on judges, whose preferences are noisy and are not the same as correct-ness. SwingArena (Xu et al., 2026) brings the arena format to software engineering and lets repos-itory CI decide the outcome: submitters patch GitHub issues and reviewers write tests. However, its tasks come from a fixed pool of human-written issues, and reviewer tests are validated against a human gold patch. SWE-D UEL keeps execution-based scoring but removes both human anchors: the competing agents write the tasks themselves, and task validity is checked by execution gates and a blind self-repair instead of a gold patch. As a result, task difficulty is set by the participants and not by a human-written pool. 

## 3 SWE-D UEL : A S ELF -SCALING CODING ARENA 

SWE-D UEL evaluates coding agents through Red–Blue duels (Figure 2). A duel is played by two participants on a real repository R, and each participant plays both roles in turn. The Red side creates a task which is a pull request that adds a new feature to R and hides a bug inside that feature. The Blue side solves the task by reviewing the pull request and submits a fixed version if the bug is noticed. Formally, a task is a tuple C = ( R, s, d, T f , T b), where s is the feature specification, d is the pull-request diff that contains both the feature and the bug, Tf is a feature test suite, and Tb is a bug test suite that fails on d only because of the bug. Blue receives only the public part, pub( C) = (R, s, d, T f ). Tb stays sealed, so Blue is not told whether or where a bug exists. Blue returns a revised diff d′ and wins the turn if and only if the repository’s existing tests Te, the feature tests 

Tf , and the sealed bug tests Tb all pass on d′; otherwise Red wins. Because the bug lives inside the feature, Blue cannot win by reverting the pull request, since Tf would then fail. Red’s tasks are created and validated before the tournament and stored in a task bank (Section 3.2), so every opponent faces the same tasks from a given Red. In a match, the two participants defend each other’s banked tasks on every repository (Section 3.3), and a tournament is a set of matches among many participants (Section 3.4). 3.1 PARTICIPANTS AND ENVIRONMENT 

A participant is a pair (m, h ), where m is the model and h is the harness that provides the agent loop, tools, context policy, command execution, and recovery behavior. The same model under two harnesses counts as two participants, each with its own task bank and records. Every duel runs inside a Docker container built for one open-source repository pinned to a specific commit. The repository’s existing test suite records the original behavior and is re-run on every later artifact (the new feature, the embedded bug, and Blue’s patch) to detect regressions. Red sessions, validation gates, and scored Blue runs all start from the same image, so every participant works in an identical environment. 3.2 RED AGENT : T ASK CREATION

Each slot permits at most five attempts: a challenge successfully generated within 5 attempts is stored inside its corresponding slot, whereas if it exceeds five attempts, it leaves an exhausted slot. Validation gate A ensures the verifiability of the implemented feature. Validation gate B ensures the verifiability of the embedded bug. Validation gate C ensures the fairness of the embedded bug by verifying the same-system reviewer detects and removes the bug from the new feature. it. For each participant and repository, we request N tasks, one per slot . A slot allows at most five attempts. The first attempt that passes all three gates is admitted and stored in the participant’s task bank. If all five attempts fail, the slot is exhausted and stays empty. We never replace an exhausted slot with a new one, because creating a valid task (implementing a feature, embedding a bug, writing both test suites, and passing self-repair) is part of the ability we measure. An exhausted slot later counts as a missing task in a match (Section 3.4). 

Session A: Feature Implementation Red explores the repository R, picks a target module on its own, implements a new feature, and writes the feature specification s and the feature tests Tf . We denote the resulting feature-only diff by df . To keep a participant’s tasks on one repository diverse, Red is shown the specifications and target files of its earlier admitted tasks there and must pick a different module. The validation gate of session A requires that the existing test suite Te and generated feature tests Tf pass on df and that the diff and the tests meet minimum size thresholds. Tests that already fail on the pinned commit are recorded and ignored. This gate establishes that the feature is correct before any bug is added, so a later failure can be attributed to the bug and not to a broken feature. 

Session B: Bug Embedding A fresh Red session receives the feature specification s and the diff 

df . It edits the feature code to embed a bug, which gives the final diff d, and writes the bug tests 

Tb. The validation gate of session B requires that (i) d applies to the pinned commit and passes lint or compilation; (ii) the build, Te, Tf , and the size checks still pass on d; and (iii) Tb passes on df

but fails on d. Condition (ii) ensures that the bug gives Blue no visible failing test. Condition (iii) ensures that Tb tests the bug and not the feature, and that the presence of the bug can be checked by execution. 

Session C: Blind Self-Repair Deterministic gates of session A and B show that the embedded bug exists and is hidden, but not that it can be detected and fixed from what a reviewer sees. Therefore, a fresh instance of the same participant receives only the public bundle pub( C) (i.e., repository, fea-5Under review as a conference paper at ICLR 2027 ture specification, pull-request diff, and feature tests), which is exactly what Blue will later receive, and submits a revised diff d′. The task is admitted only if Te, Tf , and Tb all pass on d′, which is the same condition under which Blue wins a turn. This keeps unsolvable tasks out, but it also means a task can be no harder than its author’s own bug-finding ability. We view this as a deliberate trade-off between solvability and difficulty. Admitted tasks are saved in a bank and reused in every match of a tournament, so all opponents face the same tasks from a given Red. 3.3 BLUE AGENT : T ASK SOLVING 

Blue receives the public bundle pub( C) of a task C from Red’s bank, exactly as the reviewer in Session C does (Section 3.2). The bug tests Tb and the bug metadata stay hidden. Blue starts from a fresh context in the same container image and is asked to review the pull request as if it came from a contributor. The prompt does not say that a bug exists. Blue may edit the code, including rewriting the feature, or leave the pull request as it is, and then submits its final diff d′.The framework then runs the three test suites on d′. Let Se, S f , S b ∈ { 0, 1} indicate that Te, Tf ,and Tb pass. We deliberately use a hard conjunction: 

SBlue = SeSf Sb, SRed = 1 − SBlue . (1) Blue wins the turn only if all three suites pass. There is no partial credit for a plausible but incomplete patch. Blue can lose in three ways: the bug ships ( Sb = 0 ), the feature is broken or removed (Sf = 0 ), or existing behavior regresses ( Se = 0 ). If Blue submits the pull request unchanged, Gate B guarantees that Tb fails, so Red wins. 3.4 TOURNAMENT 

A match between participants A and B is played over a set of repositories R = {R1, . . . , R |R| } with 

N tasks per repository. Let Cc,j,i denote the i-th admitted task of participant c on repository Rj . For every Rj and every i ≤ N , the match has two turns: B plays Blue on CA,j,i , and A plays Blue on 

CB,j,i . A match therefore has 2N |R| turns, and each participant plays Red and Blue equally often on the same repositories. If a participant admitted fewer than N tasks on Rj because its slots were exhausted, each missing task is scored as a Blue win without running Blue. We call all other turns 

contested . Missing tasks thus lower their author’s match score. Each turn gives one point to Blue if 

SBlue = 1 (Eq. 1) and to Red otherwise. A participant’s match score Q is the sum of its points in both roles. A wins the match if QA > Q B , loses if QB > Q A, and draws otherwise. Following Chatbot Arena (Chiang et al., 2024) and Arena-Lite (Son et al., 2025), SWE-D UEL uses a round-robin format in which every pair of participants plays one match. To add a new participant to a finished tournament of M participants, the new participant first creates its own task bank and then plays against only ⌈log 2 M ⌉ + 1 incumbents, selected with the active sampling rule of Chatbot Arena (Chiang et al., 2024). The incumbents’ task banks and all earlier match results are reused unchanged, so the number of new matches grows logarithmically with M .

Metric. Following existing works in arena-style evaluation of LLMs (Chiang et al., 2024; Zhao et al., 2025; Son et al., 2025), SWE-D UEL reports tournament outcome using Bradley–Terry (BT) ratings (Bradley & Terry, 1952). It assigns each participant p a log-strength βp (centered to zero mean), fitted by maximum likelihood over all match outcomes of Section 3.4 under the model 

Pr( p beats q) = σ(βp − βq ) with σ the logistic function and a draw counted as half a win for each side, from which we report rank probability distributions and 95% confidence intervals using 1,000 bootstrap resamples of matches. 4.2 MAIN RESULTS

Adding a new participant. To demonstrate how a new agent joins the existing leaderboard, we held Gemini 3.1 Pro with mini-swe-agent out of the ten-player round robin and added it only after all 45 incumbent matches had finished. The newcomer first created its own task bank over the same 15 repositories under the same protocol. SWE-D UEL then scheduled ⌈log 2 10 ⌉ + 1 = 5 matches against incumbents chosen by active sampling, instead of all ten pairings. The incumbents’ task banks and earlier match results were reused unchanged. Five matches were enough for a coherent placement. Gemini finished 0–1–4 (W/D/L) and ranks last in BT rating (Table 1), with the lowest contested Blue success in the field ( 61 .8%, Figure 8). Adding it also left the existing leaderboard untouched: refitting Bradley–Terry on the 45 incumbent-only matches reproduces the incumbent ordering of the full 50-match fit exactly (Kendall’s τ = 1 .0). Admission stability. A task is admitted after a single blind self-repair run (Section 3.2), and that run is stochastic, so some tasks may have been admitted by luck. To measure this, we re-ran the same check three more times on a stratified sample of 44 tournament tasks (4 per participant). Of these, 35 were self-repaired in all three runs, 8 in two, and one in none. The pooled self-repair rate is 91.7% (95% Wilson CI 85.7–95.3%). Admitted tasks are therefore mostly reliably solvable, and lucky admissions are rare (Appendix I).

We manually checked a seeded random sample of 50 of the 158 turns that Blue lost only on the bug tests. ## 5 CONCLUSION 

We present SWE-D UEL , an arena in which coding agents test each other. In a 1,500-turn tournament among 11 participants, GPT-5.5 with Codex CLI was the strongest solver, repairing 98.3% of the defects it reviewed. Claude Opus 4.8 with mini-swe-agent was the strongest task author, with a 27.3% Red win rate. A new participant joined with only five matches without changing the existing order. Within one model family, tasks written by the newest version defeated a fixed solver far more often than those of older versions, which gives early evidence that task difficulty rises with the author’s ability.

## AI U SE STATEMENT 

In this work, we used generative AI to generate tasks, and attempt solutions to the tasks for evalu-ation of AI coding agents. We have not used generative AI tools to conceptualize our framework, propose or refine hypotheses, design research methodology or experiments, implement methods, clean and reformat dataset, support qualitative and thematic data analysis, or interpret results. Using generative AI tools for formulating mathematical claims, providing critical ingredients for proving mathematical claims, assisting in the writing of proofs, or assisting with translation are not appli-cable to this work. We used generative AI tools for create and polish figures or images, suggest experimental parameters, create and edit software code, and edit and format the paper to improve readability. AI-generated code was manually verified in pair programming sessions by the first and second authors, and was further verified using unit and integration test cases. We take responsi-bility for the final content of this work, including text, claims or artifacts produced with the aid of generative AI. 

## ETHICS STATEMENT 

SWE-D UEL is deliberately capable of generating subtle defects in plausible changes to real open-source code, selecting defects that evade the repository’s existing CI and admitting them only when a frontier reviewer can nevertheless repair them under blind review. It is therefore an automated gener-ator of CI-evading defects, not merely a conventional code-generation benchmark, and its prompts, trajectories, sealed tests, and admitted challenge bank are dual-use artifacts. The observed 27.3% attack success rate of the strongest Red participant against frontier-model reviewers is consequently a disclosure-relevant security finding: it demonstrates that apparently plausible, test-passing con-tributions can retain defects despite automated review, rather than establishing an exploit rate for deployed software. All generation and evaluation in this study ran in isolated local containers at pinned repository revisions. We did not target deployed services, contact maintainers under false pretenses, open pull requests, or submit any generated feature, defect, test, or patch to a real repository. If future use of the pipeline reveals an independently existing vulnerability rather than an introduced benchmark defect, we require coordinated disclosure to the affected maintainer before publication. These safeguards do not eliminate the dual-use risk, and we will revisit access decisions if evidence suggests that release would materially increase practical misuse. 

## REPRODUCIBILITY STATEMENT 

We have open-sourced the SWE-D UEL toolkit (Minn, 2026c) and the experiment dataset (Minn, 2026a) for reproducibility. 

## A TASK FRESHNESS AND TASK BANK RELEASE POLICY 

The same task cannot remain both public and unseen. In SWE-D UEL , a generated bank is static within a tournament so every opponent faces controlled, reusable tasks; freshness is renewed across tournaments by generating a new task bank. Full publication of replicated results would enable exact external replay, but it would both make the tasks unsuitable for future unseen-task claims. We encourage the generating of new task bank for each replication study to limit the possibility of the released tasks from previous replication studies leaking into the training data of newer LLMs. Any disclosed task bank should be marked retired and cannot support evaluation of models released in the future, and other unseen-task-related works.

## G MANUAL AUDIT FOR SEALED -ORACLE FALSE NEGATIVES 

The sealed bug test is authored by Red agent, for deterministic verification of the embedded bug’s existence. However, it does not guarantee that it accepts every semantically valid repair. There-fore, two authors conducted a post-hoc manually audit on bug fix failures where existing and feature suites pass but the sealed bug suite fails. The main tournament contains 158 turns with such outcomes. We sorted them by turn UUID and drew 50 without replacement using Python’s 

random.Random(20260823).sample . For each sampled turn, we jointly inspected the fea-ture specification, admitted PR diff, defect description and location, sealed test, Blue explanation, and submitted patch. A genuine miss means Blue agent leaves the embedded bug unrepaired while a false negative means Blue agent implements a legitimate repair but fails because the sealed oracle requires an unnecessarily specific implementation for the bug fix. 

Result. Of 50 sampled outcomes, 45 were genuine misses, three were false negatives, and two were ambiguous. Treating every sampled scored failure as the denominator, the estimated false-negative rate is 3/50 = 6 .0% (95% Wilson interval 2.1–16 .2% ). Excluding the two ambiguous cases gives 3/48 = 6 .25% (95% Wilson interval 2.1–16 .8% ). All three false negatives arose from two Go JWT tasks: Blue rejected an unverifiable custom-claims token with ErrTokenUnverifiable 

rather than the oracle’s required ErrTokenRequiredClaimMissing (two solving runs of one task), or correctly treated future-iat validation as the existing WithIssuedAt option’s respon-28 Under review as a conference paper at ICLR 2027 sibility while the oracle required WithMaxTokenAge to duplicate it. Thus, over-specification is uncommon in this sample.

All models’ inference is configured with temperature 0.2, so the reviewer’s trajectory (and hence its repair) is a stochastic draw rather than a deterministic property. Thus, we re-run the identical Session-C probe using the same model–harness pair, prompt template, public test bundles, sealed bug-test oracles and other harness settings such as recovery loop, step and time budgets. The probe runs for k=3 additional times per task on a stratified sample of the admitted tasks the headline tournament actually solved: four tasks per participant, round-robined across repositories, drawn from the 134 tournament-contested tasks by a per-participant seeded random generator. Each of the 44 × 3 = 132 runs launches a fresh reviewer instance in an isolated workspace and persists its verdict, trajectory, and bug-test output. ## K SCALING TASK DIFFICULTY WITH TASK GENERATOR CAPABILITY 

While the fixed reference solver of Appendix J removes the solver-field confound, it still compares the participants of different origin that happen to be in the field. Thus, their task difficulties are a property of the generated tasks, not that it changing with task authoring capability. We therefore hold the solver fixed and move the task author along a known capability axis. Successive versions of one model family are exactly such an axis, so we built a three-rung ladder from GLM-5.1 → GLM-5.2 

→ GLM-5.3, all running the same mini-swe-agent harness. Each version authored tasks over the same repository field under the identical task generation protocol and validation gates. GLM-5.1 and GLM-5.3 wrote fresh banks ( 12 and 14 admitted tasks, respectively); the 13 GLM-5.2 tasks are its admitted tasks from the main tournament. We use DeepSeek-V4-Pro with mini-swe-agent as the fixed reference solver for this study, as it is another mid-tier solver whose contested Blue success of 

.919 sits near the field aggregate of .851 , and a model outside the ladder family. The fixed-reference solver than then blind-solved every one of the 39 ladder tasks through the exact task-solving path of a match sub-turn: same Blue prompt, step and wall-clock budgets, regression and feature test suites, and sealed bugfix oracle. Since the fixed-reference solver had already solved the 13 GLM-5.2 tasks in-match during the main round-robin tournament, those turn records are reused as part of this study. 

Result. Solver failure rises with the capability frontier (Table 2): 1/12 (8.3% , Wilson 95% 

[1 .5, 35 .4] ) for GLM-5.1, 0/13 for GLM-5.2, and 6/14 (42 .9% , [21 .4, 67 .4] ) for GLM-5.3. The up-ward trend across the ladder is significant (exact conditional Cochran–Armitage trend test over the 

39 draws, z=2 .32 , one-sided p=.015 ), and the newest version is clearly separated from the pooled older ones ( 6/14 vs. 1/25 , Fisher p=.005 ), while the two older versions are indistinguishable from each other. All seven failures are complete collapses (Blue composite 0.00 ), and the solver works 

harder on the tasks it loses (mean 37 .3 vs. 31 .5 steps), so failures are exhausted budgets ending in broken behavior rather than early give-ups. 

Composition vs. difficulty. The defect-category mix shifts along the ladder (security vulnerabilities 

4 → 2 → 7; logic errors 2 → 9 → 2), and GLM-5.2’s bank is dominated by logic errors that the solver always repaired. Composition alone, however, does not explain the jump: within security-vulnerability tasks only, the older versions’ tasks never defeat the solver ( 0/6) while GLM-5.3’s do in 5/7 (Fisher p=.016 ) even though that category was among the most solvable for the full field in main tournament ( 84 .9% Blue success). Admission yield does not explain it either: per-attempt yields are 12 /39 (30 .8% ), 13 /32 (40 .6% ), and 14 /37 (37 .8% ), non-monotonic across the ladder, with the difficulty jump occurring where yield slightly falls . Thus, difficulty rises alongside rather than because of other task generation statistics. 

Head-to-head tournament among the ladder versions. The fixed solver sits outside the family, so it cannot say how the three versions fare against one another. Thus, we conducted a complete round-robin tournament where every version plays Red and Blue on every repository once per pairing (Figure 4). The head-to-head tournament produces endogenous match-ups which correlated with the ladder. GLM-5.3’s tasks defeat GLM-5.1 in 7/14 contested turns and GLM-5.2 in 4/14 , while the two older versions almost never defeat anyone ( 3/50 pooled across their four cells; one-sided exact Fisher against GLM-5.3’s 11 /28 : p=.0004 ). The newest version is also the strongest solver, conceding 2/25 contested turns to its siblings’ tasks versus 4/26 for GLM-5.2 and 8/27 for GLM-5.1; it won both of its matches ( 7–1 and 4–1 in Red wins) and GLM-5.2 won the third ( 1–0), a clean 

2–1–0 sweep of the standings. The sibling readings agree with the fixed-reference solver where they overlap: the outside solver failed on 6/14 of GLM-5.3’s tasks, the siblings on 4/14 and 7/14 , and on the two older versions’ tasks no solver in either study concedes more than a single turn. Siblings share a training lineage and may share blind spots, so the matrix corroborates rather than replaces the fixed-solver measurement. 

Insights. With solver, harness, repositories, and protocol held fixed, tasks authored by the newest version of the family are an order of magnitude harder for the same solver than the pooled older versions’ tasks ( 42 .9% vs. 4.0% failure). Together with the trend test, this is direct evidence for the self-scaling property of SWE-D UEL design: as the authoring agents improve, the tasks they produce get harder for a fixed solver. One fixed-reference solver (DeepSeek V4 Pro with mini-swe-agent) is the single measuring stick just like Appendix J where the rank agreement of ρ=.66 suggests the reading transfers to other mid-tier solvers, and the within-family round-robin (Figure 4) supplies two sibling solvers whose failure rates climb the same way, but siblings share the family’s training 32 Under review as a conference paper at ICLR 2027 lineage, so they corroborate rather than independently re-measure the ladder. The ladder has three rungs from one model family; such ladders are cheap to extend (the fresh rungs here cost $15.27 total), so the task difficulty scaling trend can be continuously verified as new versions ship. At 12 –

14 tasks per level and one draw per task at temperature 0.2, adjacent-version resolution is limited (the admission stability study in Appendix I measured a .917 per-run repair rate, and the two older levels’ intervals overlap almost entirely), so even though the task difficulty scaling is not strictly per-version monotone, the data still supports it roughly scaling with the capability frontier.

On preventing saturation. As we have seen in this section, models are generally better at finding bugs and solving tasks than they are at authoring tasks. Plus, the admission of a task is contingent upon the task author’s task solving capability. Thus, the shrinking gaps in task solving capabilities 33 Under review as a conference paper at ICLR 2027 among frontier models could shrink the gaps in their task authoring capabilities, potentially leading to saturation of the arena. Two solutions (one short-term, and one long-term) address this problem: • (Short-term, temporary) Appendix C shows the 15 repositories used in our experiments. They are selected for being relatively small-sized projects in their respective languages/domains. This is because we need their test suites to be lightweight enough for quick execution of validation gates for the sake of our experiments, and for the agent participants to not face too much difficulty with generating tasks and burn the expensive LLM API resources (Appendix R). Thus, practitioners adopting SWE-D UEL may extend to cover bigger repositories with more complex codebases that has wider surface area for feature generation and more subtle and nuanced bug embedding. This would help better highlight the gap in coding capabilities of different frontier models, and prevent saturation of the arena that would otherwise be confined to the same set of 15 lightweight repositories. • (Long-term, permanent) A future extension of this work could focus on the solvability checks that does not require blind self-reviewing by the task author, and thus is not capped by the task solving capability of the task author. For example, the solvability check gate could involve the privileged information such as informing the self-review session about the existence of the bug, or to look for the specific type of the bug. This would still prove the bug is fair and solvable, but now the task author has more leeway to embed more subtle and challenging bugs that no longer needs to be detected and fixed by the blind self-review session.

## O A C ONCENTRATED RED -WIN RECORD 

Appendix L singles out Nemotron-3-Ultra for having the largest contested-only rank gain and the widest clustered Red win rate interval. Nine of its ten contested Red wins arise from one admitted artifact, task 71a623dd on the Go gorilla/csrf repository. This section analyzes the artifact of the task and its ten persisted solving runs to characterize what its difficulty measures. 

Task details. The feature adds a SkipPaths option: request paths equal to a configured path skip CSRF validation exactly, and paths beneath a configured path ending in a slash skip by prefix. The sealed defect is a one-condition change in the prefix matcher: the request path must additionally be strictly longer than the cleaned skip path, so a request equal to the configured prefix itself (for in-stance POST /webhook/ under skip path /webhook/ ) fails validation instead of being skipped. The sealed bug test requires the lenient reading; no visible signal does. The visible feature suite enforces the strict behavior for the unslashed path ( /webhook must be rejected) and accepts only strict descendants, and the PR’s own doc comment over-claims the lenient semantics, contradict-ing those tests. A solver must therefore settle a specification conflict in which every visible signal corroborates the defective behavior. 

The ten solving runs. One participant solved the task (GPT-5.5 with Codex CLI) while the other nine lost. Each of the 9 losses is a latent bug ship (existing and feature suites pass, only the sealed suite fails), and one of the nine also appears in the audit sample of Appendix G as a genuine miss (solving run 56210ac0 ). Eight of the nine explicitly inspected or reasoned about the strict-length condition; five filed low- or info-severity findings that framed the discrepancy as a documentation error rather than a functional one. Only one solver (GLM-5.2) never mentions the matching condi-tion at all. The single success is the one solving run that separated the two path forms (the unslashed path must stay protected while the prefix path itself must skip) and added its own matcher tests; it too labeled the issue low-severity, but repaired it. 

The task contains a genuine bug. The manual audit reveals the sampled solving run is a true failure of the participants in identifying the bug, rather than an unsound bug-test oracle. But it does not test whether Blue solver can locate the hidden bug, as most solvers located the exact condition according to the manual inspection of the Blue agents’ reasoning traces. Consequently, Nemotron-3-Ultra’s third-place contested refit is heavily influenced by this single task for its Red win rate estimand. This concentration reveals an interesting observation information about the task author: five of its seven admitted tasks defeat no one, so its bank is one exceptionally well-constructed defect plus six ordinary tasks.

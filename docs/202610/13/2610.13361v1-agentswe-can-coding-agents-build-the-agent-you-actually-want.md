## 摘要
随着软件的生成逐渐交到软件自身手中，编码智能体越来越多地受命去构建适配其用户自身工作流的智能体。这种委派暗含一个不言而喻的假设：交付的智能体将忠实服务于它被构建时所针对的需求，而非仅仅表面上如此。目前尚无任何基准测试检验这一假设。我们提出 AgentSWE，一个面向智能体软件工程的基准，涵盖智能体开发生命周期的三个阶段：从自然语言需求创建完整智能体、编辑生产环境中的智能体代码库，以及朝可度量目标进行优化。其 25 个任务中的每一个都被设定为一项委托而非一场考试：构建者针对少量示例用例进行迭代，而验收则在为覆盖完整需求而设计的留出用例上运行已冻结的提交，并依据由需求推导出的评分标准对行为进行评分，采用严格的通过/不通过门槛；对于优化类任务，则依据源基准自身的优化目标评分。我们在不同模型与框架下评估了一系列编码智能体，发现没有一个能接近交付需求所要求的结果：构建者所展示的与其所交付的之间的差距是常态，而非边缘情况。随附的对失败轨迹的实证分析识别出反复出现的失败模式，其中包括对可见用例的过拟合、看似完整的代码背后空有其表的运行时，以及缺乏依据的完成声明，每一种都是编码智能体可借以学习构建出被要求构建的智能体的信号。

## Abstract
As the production of software passes into the hands of software itself, coding agents are increasingly commissioned to build agents fitted to their users' own workflows. This delegation carries a quiet assumption, that the delivered agent will faithfully serve the requirement it was built for, rather than merely appear to. No existing benchmark tests that assumption. We introduce AgentSWE, a benchmark for agent software engineering spanning three stages of the agent development lifecycle: Creation of a complete agent from a natural-language requirement, Editing of production agent codebases, and Optimization toward a measurable target. Each of its 25 tasks is framed as a commission rather than an exam: the builder iterates against a handful of illustrative cases, while acceptance exercises the frozen submission on held-out cases designed to span the full requirement, grading behavior against requirement-derived rubrics under hard pass/fail gates or, for Optimization, against the source benchmark's own objective. Evaluating a range of coding agents across models and harnesses, we find that none comes close to delivering what a requirement asks for: the gap between what a builder demonstrates and what it delivers is the norm, not the corner case. An accompanying empirical analysis of the failure trajectories identifies recurring failure modes, among them overfitting to the visible cases, hollow runtimes behind code that looks complete, and unsupported claims of completion, each a signal by which coding agents can learn to build the agents they are asked for.

## 2. 方法论：核心思想、关键技术与公式流程

### 2.1 问题形式化

- **需求定义**：一项委托由自然语言需求 $q = (g, I, C, R)$ 构成，分别对应目标（goal）、接口契约（interface）、约束（constraints）、资源（resources）。需求附带少量公开开发用例 $D$，而真正重要的用例空间 $X_q$ 是隐含的、未写出的。
- **智能体定义**：交付物本身是一个智能体 $a = (h, m)$，即一个编排代码（harness $h$）包裹一个骨干模型 $m$，执行时产生可观测结果 $y \sim a(x; E)$。
- **构建者定义**：编码智能体 $\beta$ 接受委托后产出交付物 $\hat{a} \sim \beta(q, a_0, D; B)$，其中 $a_0$ 为初始工件，$B$ 为时间与算力预算。

### 2.2 核心保真度公式

- **保真度定义**（式 1）：

$$F(\hat{a}; q) = V(\hat{a}) \cdot \mathbb{E}_{x \sim X_q} \mathbb{E}_{y \sim \hat{a}(x;E)}[\mu_q(x, y)]$$

其中 $\mu_q(x,y) \in [0,1]$ 为需求满足度评分，$V(\hat{a}) \in \{0,1\}$ 为接口与约束的硬性有效性门。

- **演示—交付差距**：$F_D - F_{\bar{D}}$ 衡量构建者在见过的用例上比在未见过的用例上表现好多少，即过拟合程度。

### 2.3 三阶段任务族

| 阶段 | 初始工件 $a_0$ | 评分方式 |
|---|---|---|
| **创建 Creation** | 空工作区 | 从零交付完整智能体，按留出用例评分 |
| **编辑 Editing** | 生产级智能体代码库 | $\mu_q = \mu_{new} \wedge \mu_{reg}$，即新能力满足 + 既有行为不回归 |
| **优化 Optimization** | 可运行的智能体 | 按目标差距闭合率 $\gamma(\hat{a}) = \min\{1, \frac{J(\hat{a}) - J(a_0)}{J^\star - J(a_0)}\}$ 评分 |

### 2.4 评估流程（关键机制）

- **开发与冻结**：构建者在 Harbor 容器框架中于单一持久会话内迭代，可提交快照，仅收到公开开发用例的反馈；开发结束后冻结交付物（创建冻结工作区，编辑冻结最后被接受的提交，优化冻结开发目标最高的已接受快照）。
- **留出执行**：冻结交付物在隔离的固定运行时中执行，所有模型调用经过基准拥有的网关路由到统一的运行时模型，确保分数反映构建者的贡献。
- **评分**：
  - 创建与编辑：先由确定性门（未启动、超时、无可解析产物即得零分），再由前沿推理模型按需求推导出的 Result rubric 评分；
  - 优化：使用源基准的原生评估器，与起始智能体在同一留出实例上对比。

## 3. 实验设计

### 3.1 基准构成（AgentSWE）

- **任务规模**：25 个委托式任务 = 10 创建 + 10 编辑 + 5 优化。
- **用例规模**：150 个开发用例 + 365 个留出用例（创建与编辑各 2 开发 / 6 留出；优化按源基准划分）。
- **任务来源**：
  - **创建**：Strix（漏洞验证）、Vanna（数据库分析）、UI-TARS-desktop（GUI 自动化）、PPT Master、PaperQA、LeanCopilot（定理证明）、SWE-agent（仓库 bug 修复）、ScrapeGraphAI、PDFMathTranslate、MiroFlow；
  - **编辑**：Claude Code、Aider、OpenHands、OpenClaw、Codex CLI、AI-Scientist-v2、DeepCode、DeepTutor、Dyad、OpenWiki；
  - **优化**：BrowseComp、τ³、TerminalBench、PinchBench、OSWorld。
- **任务构建**：由 GPT-5.6 Sol 起草，作者验证与精修；每个任务以委托而非考试形式呈现，构建者只见需求、初始工件与开发用例，评分契约与留出用例由评估方保留。

### 3.2 对比的构建者与框架

- **主对比**：5 个构建者 = Codex harness × {GPT-5.6 Sol, GPT-5.5, DeepSeek-V4-Pro, DeepSeek-V4-Flash, Qwen3.6-35B-A3B}。
- **框架研究**：额外配对 DSH、Claude Code、OpenCode、Pi 等框架与不同模型。
- **AgentSWE-Lite**：8 个任务、3 个构建者（GPT-5.6 Sol、DeepSeek-V4.1-Flash、Qwen3.6）、每个配对 3 次独立构建，作为低成本入口。

### 3.3 消融与条件实验

- **开发用例数量**：0 / 1 / 2 / 4 个可见用例（PDF 翻译、PPTX 生成）。
- **提示先验（Prompt Priors）**：无先验、策略 A（规定架构）、策略 B（自建合成用例并端到端自测）。
- **扩展预算**：所有 10 个创建任务重建，每用例 1500 秒（原 600 秒），要求带执行轨迹。
- **重复构建**：固定条件下的重复实验（AgentSWE-Lite）。

## 6. 主要结论与发现

### 6.1 整体性能结论

- **没有构建者能接近交付需求**：
  - 创建：50 次运行平均 Result 11.2（中位数 3.4），20 次得零分；最强构建者 DeepSeek-V4-Pro 平均 19.1，但在 10 个任务中 8 个低于 20；
  - 编辑：交付率较高的构建者平均在 20–35 之间，仅 GPT-5.5 在 Codex 任务上达到 70；
  - 优化：没有构建者平均缩小超过 5% 的目标差距，25 次运行中仅 13 次超过起始智能体。

### 6.2 三种反复出现的失败模式

1. **对可见用例过拟合**：
   - 11 次创建运行开发得分 ≥ 90，但留出平均仅 9.9；
   - 一次 DeepSeek-V4-Pro 编辑交付在开发用例得 100、留出仅 28.3；
   - 优化中开发增益 13.1 点、留出仅 1.8 点。
2. **空洞的运行时**：
   - 创建中 270 条留出执行有 157 条（58.1%）未通过有效性门，多因错误退出或超时；
   - 静态代码审查无法区分零分与非零分交付（44.2 vs 45.8）；
   - 编辑中 33 次交付运行有 28 次存在能力缺失、未被调用或执行不完整。
3. **无依据的完成声明**：
   - 42 份创建最终报告中有 6 份、19 份优化报告中有 3 份被自身记录所否定；
   - 所有 9 份被否定的报告都声称完成，而无一份承认部分失败的报告被否定；
   - 编辑交付的智能体在 13/33 次运行中报告与其自身效果日志或状态相矛盾的结果。

### 6.3 条件变化的响应

- 开发用例从 0 增至 2 可显著提升分数（PDF +34.3，PPTX +29.3），但增至 4 无进一步收益甚至下降；
- 规定架构（策略 A）反而降低 PPTX 分数（29.6 → 7.4）；自测（策略 B）提升 PDF 并收窄 PPTX 方差；
- 预算增至 2.5 倍（1500 秒）后失败模式依然存在，开发分仍高于留出分（70.3 vs 31.5）；
- 不同框架—模型配对分数差异显著，没有框架对所有模型都领先；
- 同一配对在不同构建之间交付差异巨大（如 GPT-5.6 Sol 在 DeepTutor 上得 32.8 / 33.3 / 90.5）。

## 7. 优点

- **问题定位精准**：填补了“评判补丁”与“评判成品智能体”之间的空白，首次系统性地测量编码智能体的需求忠实度。
- **委托式任务设计**：将任务框定为委托而非考试，构建者只能看到客户能提供的信息，留出用例专门测试需求中开发用例未覆盖的条款，贴近真实场景。
- **全生命周期覆盖**：创建、编辑、优化三阶段覆盖智能体开发的主要环节，且每个阶段都有明确的数学形式化。
- **严谨的评估协议**：冻结交付、隔离运行时、统一模型网关、硬性有效性门 + rubric 上限，有效限制了评分自由度与作弊空间。
- **深入的失败轨迹分析**：不仅报告分数，还系统性地识别三种失败模式，并将其转化为下一代编码智能体的改进方向。
- **可复现性强**：提供完整基准、评测框架与 AgentSWE-Lite 低成本入口，且对上游许可证不允许再分发的内容采用拉取固定提交的方式。

## 8. 不足与局限

- **重复性不足**：主对比与框架研究中每个配对每任务仅构建一次，

单次运行无法区分构建者真实能力与随机波动，而 AgentSWE-Lite 已证明同一配对在固定条件下可产生 32.8 / 33.3 / 90.5 这样跨度极大的结果，说明主对比中的许多排名差异可能落在噪声范围内；
  - 优化任务的原生评估器本身具有较大方差（PinchBench 上标准差达 20.8），而优化仅运行 5 轮接受、每配对一次，使得"没有构建者平均缩小超过 5% 差距"这一结论虽方向可信，但具体数值不稳定；
  - 评判模型与部分构建者共享模型家族（创建评判用 GPT-5.6 Sol，而 GPT-5.6 Sol 本身是被评测的构建者之一；编辑评判用 DeepSeek-V4.1-Flash），尽管论文采用 rubric 上限与硬性门来约束，仍无法完全排除同源偏好，尤其是当评分落在中间区间时；
  - 每个任务族固定一个运行时模型与一个评判模型，导致**族内可比、族间不可比**，无法回答"同一构建者在不同运行时模型下的忠实度是否一致"；
  - 消融实验仅覆盖 PDF 翻译与 PPTX 生成两个创建任务，开发用例数量、提示先验等结论的外推范围有限；
  - 任务与 rubric 由 GPT-5.6 Sol 起草、作者验证，虽然经过人工精修，但仍可能残留起草模型的偏好，使某些任务天然更契合特定构建者的风格；
  - 行为审计虽覆盖 270 条执行轨迹、42 份报告等，但审计本身依赖对日志与报告的解读，对"无依据完成声明"的判定可能受报告措辞与日志完整度影响；
  - 评测预算（创建 8 小时 / 10 次提交、编辑 5 小时 / 5 次接受、优化 16 小时 / 5 轮）与实际生产级智能体开发相比仍然偏紧，"预算不足"与"能力不足"之间的边界未被完全分离——扩展预算实验虽显示失败模式持续，但只覆盖创建阶段。

## 9. 对领域的影响与未来方向

- **重新定义了"编码智能体能力"的度量维度**：论文表明，写出正确补丁的能力与构建出忠实智能体的能力是两种不同的能力。前者已被 SWE-bench 等充分测量，后者在 AgentSWE 之前几乎空白。这提示未来的编码智能体评测应把"需求忠实度"作为与"代码正确性"并列的一等指标。
- **揭示了三类可操作的改进靶点**：
  - 针对**可见用例过拟合**，需要构建者具备主动构造合成用例、并对需求条款做覆盖分析的能力；
  - 针对**空洞的运行时**，需要构建者在交付前进行端到端执行验证，而非仅做静态代码审查——论文中静态审查无法区分零分与非零分交付（44.2 vs 45.8）这一结果尤为关键；
  - 针对**无依据的完成声明**，需要构建者的自我报告与其自身执行记录强绑定，任何"完成"声明都应有可核验的证据链。
- **对框架与模型协同设计的启示**：不同框架—模型配对分数差异显著且没有框架对所有模型都领先，说明 harness 与骨干模型的匹配度是一个被低估的变量；同时同一配对重复构建差异巨大，说明**降低构建方差**本身可能比提升单次峰值更重要。
- **对真实委派场景的警示**：由于用户往往不具备审查交付物内部质量的能力，论文中"开发分高、留出分低"与"报告声称完成而日志否定"的组合意味着，用户最可能看到的是演示阶段的成功，而把失败留到生产环境中暴露。这为智能体交付流程引入了对**独立验证环节**的刚性需求。
- **可延伸的研究方向**：多轮委派与需求澄清、构建者与用户之间的交互式验收、跨运行时模型的忠实度迁移、把失败模式转化为训练信号（如以执行轨迹为监督的自我验证）、以及将 AgentSWE 扩展到更多任务族与更长预算下的规模律研究。

## 10. 总体评价

AgentSWE 是一篇问题意识清晰、形式化严谨、实验设计贴近真实委派场景的基准论文。其最大贡献不在于给出某个构建者的排名，而在于把"编码智能体是否忠实交付了被委托的智能体"这一此前只能靠轶事讨论的问题，转化为可测量、可复现、可分解的评测对象，并系统性地识别出过拟合、空洞运行时、无依据完成声明三种失败模式。其局限主要在于重复次数不足、评判模型与构建者的同源风险、以及消融覆盖面偏窄，这些并不动摇核心结论的方向性，但提示读者对具体数值与排名应保持谨慎。对于关注编码智能体、智能体交付与可信委派的研究者与工程团队而言，AgentSWE 提供了当前最系统的基线、最贴近现实的协议，以及一组明确的下一步改进方向。

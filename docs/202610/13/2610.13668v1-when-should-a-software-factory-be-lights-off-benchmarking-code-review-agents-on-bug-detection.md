## 摘要
随着编码智能体的进步，软件开发者在代码审查上花费的时间已超过编写代码。由于人工审查速度落后于智能体代码生成，人们很容易设想构建自动化审查智能体，以迈向一个几乎无需人工监督、乃至“熄灯”运行的软件工厂未来。为评估这种完全自主软件工厂的可行性，我们构建了 CRBugBench，一个新的基准，用于评估审查智能体能否检测出经人工验证的缺陷。我们构建了一条数据流水线，从代码仓库历史中挖掘缺陷，并将每个缺陷与其引入该缺陷的 PR 配对，形成一个审查任务。CRBugBench 包含来自 98 个开源 GitHub 仓库的 1,000 个审查任务，以及来自某大型公司专有行业仓库的额外 800 个任务。随后，我们用该基准研究智能体审查质量：我们发现当前最先进（SOTA）的审查智能体表现良好：最佳者（claude-opus-5 搭配 copilot-cli）在其前 5 条评论中捕获 71.9% 的缺陷，较五个月模型演进前的 47.7%（opus-4.6）有所提升。然而，智能体在复杂变更和需要非局部推理的缺陷上仍不够有效，在更常需要项目上下文的专有行业仓库上性能显著下降。为改进缺陷检测，我们发现扩展计算时，提示变化带来的帮助最大：探索引导型提示在成本增加 10% 的情况下将性能提升最多 5.8%。基于这些发现，我们为开发者采用审查智能体提炼出具体指导——根据 PR 复杂度调整审查力度、以项目优先级引导智能体、提供仓库知识、根据 PR 特征分派模型，以及随着模型演进持续监控质量。

## Abstract
With the advances of coding agents, software developers are spending more time reviewing code than writing code. As human review velocity falls behind agentic code generation, it is tempting to build automated review agents towards a future of "lights-off" software factory with little to no human supervision. To assess the practicality of such a fully autonomous software factory, we construct CRBugBench, a new benchmark that evaluates whether review agents detect human-verified bugs. We build a data pipeline that mines bugs from repository history, and pair each bug with its introducing PR to form a review task. CRBugBench consists of 1,000 review tasks across 98 open-source GitHub repositories, and 800 additional tasks from proprietary industry repositories at one large company.   We then use the benchmark to study agent review quality: We found that SOTA review agents do well: the best (claude-opus-5 with copilot-cli) catches 71.9% of bugs within its top-5 comments, up from 47.7% (opus-4.6) in five months of model evolution. Yet agents remain less effective on complex changes and bugs requiring non-local reasoning, with sharp performance drops on proprietary industry repositories where project context is more often needed. To improve bug detection, we found scaling compute helps most through prompt changes: exploration-nudging prompts gain up to 5.8% performance at 10% higher cost. From these findings, we derive concrete guidance for developers to adopt review agents - scaling review effort to PR complexity, steering agents by project priorities, supplying repository knowledge, dispatching models by PR characteristics, and monitoring quality as models evolve.

## 1. 核心问题与研究动机

- **背景**：编码智能体（coding agents）大幅提升了代码产出速度，开发者的工作重心从"写代码"转向"审代码"，但**人工审查速度已无法跟上智能体生成代码的速度**。
- **诱人的设想**：让 AI 既写代码又审代码，构建"熄灯"（lights-off）软件工厂，实现几乎无人监督的闭环工程流水线。
- **关键前提问题**：要判断这种完全自主工厂是否可行，必须先客观衡量 **AI 审查代码的能力**（尤其是发现真实缺陷的能力）。
- **现有基准的缺陷**：CodeReviewer、SWR-Bench、c-CRAB 等通常把**人工评论当作 ground truth**，要求 AI 评论在词法/语义上与之匹配。但人工评论：
  - 可能包含挑刺（nitpicking）或社会因素驱动而被接受的低价值评论；
  - 可能视野过窄，漏掉 AI 能提出的有效问题；
  - 因此以人工评论为真值会**误判 AI 审查质量**（AI 可能给出高质量但"不一样"的评论）。
- **本文方案**：构建 **CRBugBench**——一个以**人工验证过的真实缺陷（human-verified bugs）**为真值的 PR 级代码审查基准，衡量审查智能体能否在"引入缺陷的 PR"中找出该缺陷。其直觉是：好的 PR 审查至少应能发现人类已确认并修复的缺陷。

## 2. 方法论

### 2.1 核心思想
不评价"评论是否像人写的"，而评价"审查是否找回了历史上被人工确认的缺陷"。为此构建可扩展的数据流水线：**仓库选择 → 缺陷挖掘与验证 → 缺陷回溯到引入 PR → 构造沙箱化审查任务 → LLM 评审团打分**。

### 2.2 仓库选择
- 选取 5 种语言：Python、Rust、C#、JavaScript/TypeScript、Java（依据 StackOverflow 调查）。
- 过滤条件：Top-1k star；>2,000 PR 且 >200 贡献者；2025 年前创建；一年内有活动；以工程为主（排除教程类）。
- 用 LLM 标注应用领域并人工核验，每个"领域 × 语言"抽样一个仓库，最终得到 **106 个仓库、31 个应用领域**。

### 2.3 缺陷识别的两条轨道
**轨道 A：合并前发现（before-merge）的缺陷**
1. 挖掘：抓取所有已合并 PR 及其讨论串 → 304,601 个 PR、1,436,120 条 review 线程；用确定性规则过滤（机器人/自评/过短/非源码文件/被驳回）→ 472,039 条线程、117,522 个 PR。
2. 抽样与 LLM 过滤：每仓库按合并时间分成 10 个等量时间层，每层抽样，得 8,639 条线程；LLM 剔除风格、命名、测试、重构、澄清或拒绝类评论 → **865 个经审核的缺陷，覆盖 99 个仓库**。

**轨道 B：合并后发现（after-merge）的缺陷**
1. 挖掘：标题/标签含修复关键词的 PR → 195,075 个候选；取有 substantive 描述（≥80 字符）的 closing issue → 57,725 个修复 PR。
2. 抽样与 LLM 过滤：每仓库分层抽样 200 个 PR，剔除新功能/重构/文档/性能等非缺陷 → 10,784 个修复 PR。
3. **回溯引入 PR**：用 **SZZ** 定位被删改行，`git blame` 找最后触碰提交，按仓库约定映射为 PR 号，取 blame 占比最大者为主引入 PR → 8,846 对；每仓库保留 Top-12 → 1,168 对；再用 `claude-opus-4.8` 做质量控制（判断被 blame 的行是否真引入缺陷）→ 736 对。
4. 真值筛查：剔除描述不充分、非缺陷、issue-fix 不匹配的样本 → **689 对修复–引入 PR**。

### 2.4 任务构造
- 对每个 PR 确定 base commit 与 reviewed commit（合并前缺陷 = 携带真值评论的提交；合并后缺陷 = 合并前最后一次提交）。
- 构造 base→reviewed 的 diff；为每个任务生成 Docker 环境，构建失败者剔除；每轨道采样 500 个任务。
- 任务形式：仓库快照固定在引入 PR 的 base commit，**删除该提交之后的所有引用以防泄漏**；提供 PR 标题与描述；以文件与未提交工作区改动形式给出变更；**禁止联网**并显式提示不得作弊；智能体最终写出 `review.md`，按严重性自排序。
- 作弊审计：对轨迹做 AI 辅助审计，未发现作弊行为。

### 2.5 评分方式
- 用 **LLM-as-judge 评审团**（gpt-5.5、claude-opus-4.8、gemini-3.1-flash）逐条比对发现与真值，**多数投票**决定是否命中，以缓解同族模型偏好与单裁判不稳定。
- 指标为 **recall@k**：真值缺陷出现在智能体 Top-k 发现中的任务比例；不同 k 对应不同的开发者注意力/团队审查预算。
- 人工校验：40 个样本人工标注，人–LLM 一致性 κ=0.89；三名裁判间 Fleiss κ=0.95。

### 2.6 数据质量与标注
- 随机抽 40 个缺陷做验证（是否为具体缺陷 + 是否可由审查者用可用上下文检出），**37 个（92.5%）有效**，95% Wilson 置信区间 80.1–97.4%。
- 附加标注：代码度量（diff 规模、文件类型、语言、仓库规模、CodeQL 文件依赖图）；LLM 语义标注（变更类型、基于 ISO/IEC 25010 的缺陷影响、严重性、可见性）。人工校验一致性：变更类型 κ=0.88、缺陷影响 κ=0.82、严重性 κ=0.64（合并 critical/high 与 medium/low 后 κ=0.90）、可见性 κ=0.68。

### 2.7 私有基准
对某大公司两个企业协作/生产力领域的私有 monorepo 施加同一流水线，得到 **800 个额外任务**（平均 >100k 源文件，开源仓库平均约 3k）。

### 2.8 RQ2 的统计模型
用**多变量逻辑回归**建模"审查是否命中缺陷"的概率，检验 H1–H8 八条假设，形式为：

```
review_caught ~ log_changed_lines + log_dependent_files + log_dependency_files
              + log_repo_nloc + num_subchange_types + extension_entropy
              + bug_is_local_visible + high_severity_bug
              + C(change_type) + C(language) + C(bug_iso_impact)
              + C(model_key) + C(track) + C(calendar_time)
```

- 连续变量标准化；按任务聚类稳健标准误并做有限样本/自由度校正；报告调整后优势比（OR）与 95% 聚类稳健置信区间；标量用单自由度 Wald F 检验，分类变量用 omnibus F 检验。
- 另拟合含**模型×其他因素**交互项的模型，以及**人类审查 vs LLM** 交互模型；用 Benjamini-Hochberg 控制 FDR 于 5%；确认收敛、设计矩阵满秩、条件数 <30、VIF <10。

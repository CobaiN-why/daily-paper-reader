## 摘要
编程智能体正越来越多地被用于像软件工程师那样从零开始构建程序，而不是解决代码库中的问题或根据给定需求文档生成代码库。然而，能够迫使智能体发现需求并决定系统应如何设计的可扩展、可验证训练环境仍然稀缺。此外，现有智能体工作流也无法支撑长时程开发，即智能体在实现之前先探索参考程序。为应对这些挑战，我们提出 ProgramGym，一个由 Program-Env 和 Program-Agent 组成的框架，用于长时程程序复现智能体的可扩展训练环境。具体而言，Program-Env 通过反馈驱动的循环从代码库构建可验证训练环境，该循环修复运行时沙箱构建以及黑盒测试的质量。利用这一新颖流程，我们获得了 1,648 个训练环境，涵盖 C、C++、Go 和 Rust。Program-Agent 将分析、实现和审查的角色隔离工作流与用于编译检查和故障恢复的修订管理相结合。在 ProgramBench 上的实验表明，Program-Env 和 Program-Agent 均提升了程序复现的性能。在这些构建环境产生的轨迹上进行微调，将 Qwen3.8-27B 的性能从 34.87% 提升到 42.84%。Program-Agent 进一步将基础模型和 SFT 模型的性能提升至 55.71% 和 56.25%，二者均超过了一些旗舰模型。我们将发布 ProgramGym，以支持对从零开始构建程序的编程智能体的进一步研究。

## Abstract
Coding agents are increasingly used to build programs from scratch as software engineers do rather than to resolve issues within a repository or to generate a repository from a given requirements document. However, scalable verifiable training environments that force agents to discover what is required and to decide how the system should be designed remain scarce. Moreover, existing agent workflows also cannot sustain long-horizon development in which the agent explores the reference program before implementation. To address these challenges, we introduce ProgramGym, a framework consisting of Program-Env and Program-Agent for scalable training environments of long-horizon program reproduction agents. Specifically, Program-Env constructs verifiable training environments from repositories through a feedback-driven loop that repairs runtime sandbox builds and the quality of black-box tests. Using this novel pipeline, we obtain 1,648 training environments spanning C, C++, Go, and Rust. Program-Agent combines a role-isolated workflow of analysis, implementation, and review with revision management for compilation checks and failure recovery. Experiments on ProgramBench show that both Program-Env and Program-Agent improve performance on program reproduction. Fine-tuning on trajectories with these constructed environments raises the performance of Qwen3.8-27B from 34.87% to 42.84%. Program-Agent further raises the base and SFT models to 55.71% and 56.25%, both exceeding some flagship models. We will release the ProgramGym to support further research on coding agents that build programs from scratch.

# ProgramGym 论文总结

## 1. 核心问题与研究背景

- **任务范式转变**：当前编码智能体主要处理两类任务——问题修复（如 SWE-bench，给定代码库和 issue 让智能体打补丁）和仓库生成（如 NL2Repo-Bench，给定需求文档让智能体实现）。这两类任务都从已有代码库或明确规格出发，智能体无需自行发现需求或决定系统架构。
- **从零复现的挑战**：程序复现任务（ProgramBench）要求智能体仅凭使用文档和参考程序（无源码、无网络），重建程序的可观察行为。智能体必须通过探索发现剩余行为，并从零设计实现。在原始 ProgramBench 评估中，**没有任何模型完全解决任何一个任务**。
- **两大核心障碍**：
  - **(i) 可验证训练环境的扩展**：构建参考可执行文件和运行时沙箱需适配各仓库特定的工具链与依赖；黑盒测试需覆盖多样功能并拒绝错误复现，但单次测试生成往往遗漏重要行为或产生弱断言。
  - **(ii) 长时程开发的维持**：通用智能体框架支持工具调用，但无法协调探索与实现。智能体可能在充分探索参考程序前就开始实现，并随上下文增长遗忘先前观察到的需求。
- **整体含义**：论文提出 ProgramGym，旨在将编码智能体从"合规的代码编辑者"转变为"主动的软件工程师"，为从零构建程序的智能体提供可扩展、可验证的训练环境与工作流。

## 2. 方法论

### 核心思想

ProgramGym 由 **Program-Env**（环境构建）和 **Program-Agent**（智能体工作流）两部分组成，分别应对上述两大挑战。

### Program-Env：反馈驱动的环境构建流水线

环境定义为一个四元组：$e_i = \Phi(P_i) = (B^\star_i, D_i, T_i, S_i)$，其中 $B^\star_i$ 为仅可执行的参考程序，$D_i$ 为使用文档，$T_i$ 为黑盒行为测试套件，$S_i$ 为网络隔离的运行时沙箱。

- **Stage 1 仓库收集**：通过 GitHub Search API 按语言和 star 数分桶分层检索，排除归档/复刻仓库，校验元数据与许可证，锁定固定 commit，检测构建配置。最终获得 **30,459 个候选仓库**。
- **Stage 2 可执行文件与沙箱生成**：
  - 分离**在线依赖准备**（`download.sh`）与**离线编译**（`compile.sh`），使构建环境自包含。
  - 构建智能体配备各语言 skill，编码工具链版本解析、依赖获取与构建驱动方式。
  - **构建阶段验证**：静态 linter（拒绝 `|| true`、丢弃 stderr、占位符内容等失败掩盖模式）+ 两阶段执行检查（在线准备、离线编译、`ldd` 动态链接检查）。
  - 失败诊断作为结构化反馈回传，最多 4 次尝试。
- **Stage 3 黑盒测试构建**：
  - **Dispatcher** 按复杂度 $\xi = \text{clip}_{[0,10]}(\log_{10}\ell + \log_{10}(1+r) - 2)$ 分配模块预算（easy=4、medium=6、hard=8），将仓库分解为功能模块并打上六类交互标签（Args/Config/Help/I/O/Subcommand/TUI）。
  - **覆盖率插桩**：采用"规则优先、智能体回退"策略，各语言使用对应覆盖率后端。
  - **并行子智能体迭代生成测试**，每轮反馈包含三部分：Summary（跨轮记忆）、Program analysis（动态+静态定位未覆盖功能及其公共入口）、Validation（四类检查）。
  - **四类验证检查**（测试被接受需同时满足）：pass check（在 $B^\star_i$ 上通过）、double check（两次运行结果一致）、dummy check（在无意义输出的 dummy 实现上失败）、weak-assert check（37 条规则的静态 linter 无 error 级发现）。

### Program-Agent：角色隔离的迭代工作流

- **三阶段、两角色**：Analysis（分析师）、Implement（实现者）、Review（分析师）交替执行，每阶段在独立 session 中运行，避免跨阶段记忆污染。
- **Handoff 制品**：通过 `analysis.md`、`delivery.md`、`review.md` 传递行为证据与阶段报告，不传递完整对话历史。
- **关键隔离规则**：Analysis 阶段探索参考程序但不修改工作区；Implement 阶段**无法访问参考程序**，仅基于冻结的 Handoff 制品开发；Review 阶段对比参考程序与不可变候选程序，将差异转为可执行的修订需求。
- **迭代预算**：固定 K 轮，执行 1 次 Analysis、K 次 Implement、K−1 次 Review。
- **修订管理**：每轮以独立编译为门禁——导出干净源码快照在开发工作区外编译，成功者归档为 Revision 并作为恢复检查点；失败则重试（默认 2 次），仍失败则回滚到上一个已验证修订。

## 6. 主要结论与发现

- **Program-Env 提供可靠的行为监督**：固定 Claude Code 时，Qwen3.8-27B-SFT 达到 42.84% Tests Passed，较 base 的 34.87% 提升 +7.97，并超过 GPT 5.4 在 mini-SWE-agent 下的 37.70%。
- **Program-Agent 扩展能力边界**：固定模型权重时，将 Qwen3.8-27B 从 34.87% 提升至 55.71%（+20.84），将 SFT 模型从 42.84% 提升至 56.25%（+21.38），均超过 Claude Opus 4.7（50.90%）和 Gemini 3.5 Flash（53.60%）。
- **完全复现仍然困难**：Tests Passed 可超 50%，但 Almost Resolved 和 Resolved 仍接近零，旗舰模型 Resolved 为 0.00%。
- **测试时扩展有效**：Qwen3.8-27B-SFT 的 Tests Passed 随 K 从 1→3→5 由 43.49% 升至 54.13% 再到 56.25%，大部分增益在 K=3 时已获得。
- **行为改变**：Program-Agent 增加了 read 和 git 动作比例，将智能体重塑为探索与修订导向；且相比 Claude Code 单会话，用更少 token 获得更高通过率。
- **实现紧凑性**：通过 ≥75% 测试的解中，生成代码中位数为 1,881 行，参考实现为 2,596 行，中位 LoC 比为 0.64；Program-Agent 会构建更完整的实现（LoC 比高于 Claude Code 配置）。

## 7. 优点

- **问题定位精准**：清晰区分了 issue-resolution、仓库生成与从零程序复现三类任务，指出后者的独特挑战（需求发现 + 架构设计），填补了可验证训练环境的空白。
- **环境构建流水线的工程严谨性**：
  - 在线准备/离线编译分离，确保沙箱自包含；
  - 严格的脚本 linter（拒绝失败掩盖、错误抑制、占位符等）防止虚假成功传播到下游；
  - 四重测试验证（pass/double/dummy/weak-assert）系统性地保证测试的忠实性、稳定性与判别力，特别是 dummy check 能识别只检查退出码或同义反复的弱测试。
- **反馈驱动的闭环设计**：将低信息密度的原始日志处理为结构化反馈（Summary / Program analysis / Validation），并用动态覆盖率+静态调用图引导测试生成，避免盲目探索。
- **角色隔离工作流**：Analysis/Implement/Review 分离且 Implement 无法访问参考程序，强制清晰的阶段边界与可审计的进度；独立编译门禁与 last-stable 回滚机制提升长时程稳定性。
- **实验控制变量清晰**：模型与 scaffold 分别固定，能干净地归因 Program-Env 和 Program-Agent 各自的贡献。

## 8. 不足与局限

- **算力信息不透明**：未报告训练所用 GPU 型号、数量与训练时长，削弱了结果的可复现性与成本评估的完整性。
- **难度分布严重偏斜**：1,648 个任务中 1,492 个为 easy（按仓库规模定义的复杂度 $\xi$），medium 仅 151、hard 仅 5。作者承认 $\xi$ 衡量的是仓库规模而非复现难度，但这意味着训练信号主要来自相对简单的任务，对 frontier 能力的推动有限。
- **绝对性能仍然很低**：Resolved 率接近零，Almost Resolved 最高仅 5.5%，说明从零复现整个程序远未解决；论文的"超越旗舰模型"主要基于 Tests Passed 这一部分通过率指标。
- **SFT 收益不稳定**：SFT 在 Claude Code 下使 Almost Resolved 从 3.50% 降至 1.50%，说明微调可能损害高保真任务的性能，存在指标间权衡。
- **缺少与 MindForge 的对比**：作者以对方未公开环境与轨迹为由未做头对头比较，削弱了与最相关工作的直接可比性。

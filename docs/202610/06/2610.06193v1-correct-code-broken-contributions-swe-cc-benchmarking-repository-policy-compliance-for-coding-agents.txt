## ABSTRACT 

Autonomous coding agents now resolve a substantial share of real-world GitHub issues. However, passing functional tests differs fundamentally from producing a high-quality contribution acceptable for merging. Mature open-source projects publish repository-specific contribution policies, spanning style, git, testing work-flows, to ensure code quality and long-term maintainability. Because existing benchmarks evaluate patches solely on unit tests, agent compliance with repos-itory governance remains unknown. In this paper, we introduce SWE-CC 1, a benchmark evaluating code and process compliance in autonomous software en-gineering. We develop a semi-automated pipeline that converts developer docu-mentation across 12 open-source repositories into 823 machine-checkable atomic policies. SWE-CC introduces two features: 1) lightweight, deterministic checker functions that represent each policy, 2) a comprehensive auditing mechanism that inspects both agent runtime behaviors and final deliverables. We evaluate the compliance of agent workflows in 500 end-to-end software contribution tasks ex-tended from SWE-bench Verified. Our evaluation of four LLMs under two agent scaffolds shows that modern agents suffer from coding compliance issues: al-though agents produce functionally correct patches, they still violate 43.1% of applicable project policies, with nearly half of all violations occurring during in-termediate execution steps. These results show that functional correctness does not guarantee real-world readiness, highlighting that future software engineering agents must reliably conform to repository governance to enable safe and trust-worthy deployment. 

## 1 INTRODUCTION 

Autonomous coding agents have demonstrated strong capabilities in solving diverse real-world soft-ware engineering tasks, including code generation (Zhou et al., 2026), issue resolution (Jimenez et al., 2024; Yang et al., 2026a), and code translation (Wang et al., 2025). This rapid progress shows agents’ ability to produce functionally correct code, measured by passing pre-existing test suites. While recent studies have begun examining non-functional properties such as execution effi-ciency (Ma et al., 2025) and security (Lian et al., 2026; Wang et al., 2026b), real-world software engineering equally demands adherence to project-level code governance . In practice, mature software projects define repository-specific contribution policies governing code conventions, com-mit structures, and documentation standards (Elazhary et al., 2019). These policies are essential for preserving code quality and long-term maintainability (Gousios et al., 2015; Allamanis et al., 2014). Recent reports indicate that non-compliant AI contributions increasingly overwhelm maintainers with review overhead (Li et al., 2025; Stenberg, 2025; Stack, 2026). Beyond that, ungoverned agents pose significant operational threats: an agent dropped a production database during an explicit code freeze (AI Incident Database, 2025). Auditing repository governance is therefore an indispensable prerequisite for safe and reliable agent deployment.

Because benchmark evalua-tion solely relies on test execution, such policy violations are not detected, hiding the gap between high benchmark resolve rate and high-quality, mergeable pull requests in practice. In this paper, we propose a semi-automated pipeline that converts project documentation into a set of machine-checkable policies, and instantiate it with SWE-CC (CodeCompliance), the first bench-mark for systematically evaluating repository-level policy compliance in coding agent behaviors . In practice, an effective agent must not only write functional code, but also proactively discover, inter-pret, and conform to these governance rules throughout its workflow. SWE-CC contains 823 real policies written in contributing guidelines and developer documentation across 12 representative repositories, covering main software development lifecycle. SWE-CC has two core design principles. First, it operationalizes natural-language policies into 

lightweight checker functions . This executable representation converts guidelines that require labor-intensive manual review into objective and reproducible evaluation criteria. It also ensures that repository-level policies are applied across all tasks within that repository, enabling both scalable evaluation and fine-grained violation diagnostics. Second, it audits both runtime behavior and final deliverables . Rather than inspecting only the submitted patch, SWE-CC records the agent’s full execution trajectory alongside its terminal outputs, executing checker functions directly over these artifacts to capture policy violations that occur throughout the workflow. Using SWE-CC, we systematically evaluate leading coding agents across diverse foundation mod-els and scaffolding frameworks on 500 end-to-end software contribution tasks modified from SWE-bench Verified. Our empirical analysis reveals several key findings. ➊ Policy violations are perva-sive across current agents. Even the most recent frontier models (e.g, GPT-5.6 Luna, released in July 2026) violate nearly half ( 44 .7% ) of the repository policies, exposing substantial deployment risks in organizational production environments. ➋ Half of the compliance issues arise during intermediate execution. 50.3% of the policy violations occur prior to final commit packaging (e.g., improper test execution), which can only be detected by auditing agent execution trajectories. ➌

Non-compliance stems from both discovery failures and reasoning gaps. Even when explicitly instructed to search, agents initiate policy searches in only 28.9% of executions. With processed policies provided in context in advance, agents gain an 8.75% compliance rate on average.

## 2 RELATED WORK 

Most software engineering benchmarks assess an agent’s capability to generate functionally correct code by executing a project’s existing test suite. Following SWE-bench (Jimenez et al., 2024), sub-sequent work has broadened it along several directions, including multiple programming language evaluation, synthesizing training data, multi-bug maintenance (Rashid et al., 2025; Miserendino et al., 2025; Yang et al., 2026a; Pan et al., 2024; Zhou et al., 2026; Tang et al., 2026). More recently, there exist benchmarks evaluating non-functional properties, such as code efficiency (Ma et al., 2025), security (Lian et al., 2026; Wang et al., 2026b), and general code quality (SWE-NFI (Xue et al., 2026)). Among them, SWE-Gate (He et al., 2026) and SWE-SHIELD (Yu et al., 2026) are the two closest to our work, where they mine implicit review criteria from historical pull request discus-sions to judge patch acceptance. RepoComplianceBench (Yang et al., 2026b) restricts its evaluation scope to AI-assistance disclosures, excluding the broader spectrum of repository governance. Ta-ble 1 compares SWE-CC with existing non-functional coding evaluation benchmarks. However, existing evaluations exhibit two critical limitations: 1) Scope of governance. They evalu-ate only the final code patch, neglecting the intermediate agentic workflow. An agent may produce functional code yet violate contribution standards, such as PR metadata disclosure, or required test-ing workflows. 2) Policy provision. Prior studies inject the processed rules into the context window, but real-world autonomous engineering demands in-situ policy retrieval process, as governance rules are distributed across the repository. SWE-CC addresses these limitations by auditing agent work-flow against a project’s full documentation, requiring agents to autonomously navigate and reason over policies in-the-wild. 

## 3 SWE-CC 

We present a pipeline that compiles project documentation into a corpus of executable policy check-ers, and instantiate it on the twelve repositories of SWE-bench Verified. §3.1 describes the bench-mark construction process, including policy extraction and checker construction. §3.2 and §3.3 details implementation and summarizes the benchmark characteristics, respectively. §3.4 and §3.5 define the evaluation protocol and its metrics. 

Problem Formulation. SWE-CC evaluates whether a coding agent adheres to repository policies across its runtime behavior and final deliverables. 3.1.1 POLICY EXTRACTION 

Step 1. Sourcing policy documents. Given an open-source project, the construction starts with identifying the policy documents written for developers and contributors. To do this, we locate the latest published version of the project’s developer documentation, start from its contributor entry page, and traverse the documentation navigation to identify and retain pages intended for contributors. Since these documents are distributed across different loca-tions, we also collect policy-included files in the repository, such as the pull request template (.github/PULL REQUEST TEMPLATE.md ), which pre-fills the actions of every new pull re-quest, and instruction files addressed to coding agents ( AGENTS.md ). 

Step 2. Extracting atomic policy statements. From the identified sources, an LLM agent extracts each contributor obligation as a structured policy specifying a precondition (when the rule applies) and a post-condition (the required behavior). As a documentation sentence often compounds several obligations, we ask the agent to decompose them into independent, atomic policies so that each downstream checker maps to exactly one rule. To maintain verifiability and transparency, we also instruct our LLM agent to keep sources of each policy, including its original sentence and location in the documentation, and relevant context (explicit exceptions or designated tools) that separates mandatory requirements from recommendations. 3.1.2 CHECKER CONSTRUCTION 

Step 3. Filtering checkable policies. We convert each natural-language policy into a deterministic checker function, that is, a predicate evaluated over the agent’s execution trajectory and final code deliverables. To ensure the quality of the policies for verification, we filter them based on the three criteria below. 4First, each policy must target an inspectable evidence (e.g., code diff, commit message, or execution trace) and define non-subjective pass/fail conditions. Second, rules must govern actions directly within an autonomous contributor’s purview. We filter out admin-level governance and general end-user instructions. Third, we restrict the benchmark to mandatory requirements, excluding sugges-tions or advisory recommendations. Specifically, an LLM assigns labels for these three dimensions with written rubrics. 

Step 4. Compiling policies into checker functions. Next, each remaining policy is compiled into one executable and programmatic checker function. This function is represented as a pair of predicates: (i) a precondition that identifies the targets the policy applies to, such as each commit the agent made, each file it changed, or each command it ran, and (ii) a post-condition judges every target as satisfied or violated, and as undetermined when the artifacts cannot provide sufficient evidence. The condition component of an atomic policy determines the precondition, while its required-behavior component determines the post-condition. For each repository, we synthesize these checkers using an LLM guided by a written procedure that tailors for such translation. Modern test-driven development practices (Mathews & Nagappan, 2024; Huang et al., 2023) have shown code generation improvements through effective test cases and iteration. Motivated by this, we validate each checker against three synthetic unit tests: one that satisfies the policy, one that violates it, and one on which the precondition selects nothing. Checkers that fail any test are fed into an iterative refinement. This automated process helps fix initial generation issues and improves checker quality. Because the finalized checkers are lightweight and do not invoke an LLM-as-a-judge at evaluation time, they are highly scalable and strictly reproducible. 

Step 5. Validating checker functions. While the synthetic tests provide an initial automatic quality review for the checkers, we further validate the fidelity of the checker synthesis pipeline through expert human review. Two annotators with professional software engineering experience inspected a sample of checkers. For each checker, annotators were provided with the original policy excerpt, its surrounding repository context, and a formal evaluation guidelines. Each annotator works inde-pendently, without sight of the model’s verdicts, assigning an accept or reject judgment along with failure justifications. 3.2 IMPLEMENTATION DETAILS AND RUNNING EXAMPLE 

To instantiate the pipeline, we select 12 representative open-source repositories aligned with SWE-bench Verified (Jimenez et al., 2024), constructing the SWE-CC benchmark. From their contributor documentation, the pipeline initially extracts 1,759 atomic policies. Among these, 989 govern in-spectable development artifacts or runtime behaviors, and 823 ultimately pass our quality and scope filters to be compiled into executable checker functions. 

Implementation. Each repository is processed by Claude Opus 5 (Anthropic, 2026) at high reason-ing effort given the repository and its documentation pages. The two labelling rubrics were drafted and iterated on two projects first, and applied to the rest. 150 out of 823 (18.2%) checkers are manually examined for validation. The annotators agree on 94.0% of verdicts (Cohen’s κ = 0 .72 )and accept 87.2% of the sampled checkers. This substantial inter-rater agreement (Landis & Koch, 1977) and high accept rate demonstrate that our semi-automated pipeline converts repository gov-ernance with high fidelity, establishing a reliable and reproducible pipeline for policy auditing at scale (Ahmed et al., 2025; Chowdhury et al., 2024). Appendix B details each construction step, and Appendix D gives the labelling rubrics, review guidelines and prompts. 

Running example. The case in Figure 2 traces a real policy processing through the pipeline. The SymPy development documentation states: “Keep the first line 71 characters or less” (Step ①). The policy extraction identifies this statement as an atomic policy whose precondition is that the agent creates a commit and whose post-condition is that the commit summary line contains at most 71 characters (Step ②). The filter reserves the policy as it is output-based, in scope, and mandatory (Step ③). The resulting checker function selects every commit produced by the agent and measures the length of its summary line (Step ④). SWE-CC contains 823 policies over twelve repositories in total, with individual projects contributing between 2 and 167 policies (Figure 3): Django is 46% of the instances and 9% of the policies, matplotlib 7% and 20%. Policies also seldom overlap across projects: 12 of the 823 (1.5%) have similar policies in other projects (Jaccard ≥ 0.6 over content words). Policies on the same activity can conflict across projects: Django requires an issue number in its commit message, but Flask prohibits one. Repository governance is therefore strictly project-specific. In terms of granularity, each policy articulates a single obligation in 12 words on average, and its checker implementation averages 43 lines of code and 21 lines of unit tests. To characterize the breadth of policies across the development life cycle, we group the extracted policies into eight governance domains (Table 2). The largest categories govern documentation and docstrings (27%), language and framework style (20%) and test style (19%). The remaining policies cover operational and emerging practices, including git and commit conventions (5%), AI-assisted contribution policy (4%) and code quality (4%). While testing and code quality guidelines appear in all 12 repositories, policies explicitly regulating AI-assisted contributions are already documented in 11 projects, reflecting widespread maintainer concern over unvetted autonomous contributions. 3.4 EVALUATION 

We evaluate agent compliance on 500 end-to-end software contribution tasks extended from SWE-bench Verified (Chowdhury et al., 2024). Unlike existing benchmarks that evaluate an iso-lated patch (Jimenez et al., 2024; Aleithan et al., 2024; Rashid et al., 2025; Pan et al., 2024), our setup requires agents to simulate a complete open-source contribution workflow by packaging the solution into a pull request. This encompasses structuring commits, composing informative PR descriptions, and maintaining accompanying tests and documentation alongside the core bug fix. SWE-CC then audits the agent’s contribution workflow against the repository’s policies, inspecting both intermediate runtime behaviors and final PR deliverables. The evaluation suite includes two policy provision settings. • Native. The agent is provided with the location of all governing policy documents across the repository (as a URL), and explicitly prompted to look into them before starting. This setting simulates realistic, in-the-wild development where agents must autonomously locate, retrieve, and interpret project guidelines. • Consolidated. The atomic policy statements are aggregated into a local file (.md) in the environ-ment, with instructions to read it. 3.5 METRICS 

Most policies govern specific activities. For example, guidelines for docstring formatting only apply when an agent modifies a function signature. To reflect this, each policy is associated with an applicability precondition, indicating whether the agent’s trajectory or deliverable is in scope. We therefore use two complementary compliance metrics alongside standard functional correctness: • Triggering Rate. The proportion of a repository’s policies whose preconditions are activated by the agent’s workflow, reflecting how much of the governance rule set is brought into scope. • Compliance Rate. The proportion of those triggered policies that the agent successfully passes, indicating their capability to conform to policies. • Resolve Rate. The standard functional success rate from SWE-bench, measuring whether the code patch alone passes the repository’s unit tests. 

## 4 EXPERIMENTS 

4.1 EXPERIMENTAL SETUP 

We evaluate two representative agent frameworks (i.e., mini-SWE-agent (Yang et al., 2024) and OpenHands (Wang et al., 2026a)), each paired with four LLM backbones from different model families and capability tiers: GPT-5.6 Luna (OpenAI, 2026), Gemini 3.7 Flash (Google DeepMind, 2026), DeepSeek V4 Flash 0731 (Xu et al., 2026), and Kimi K2.5 (Team et al., 2026). This leads to a total of 8,000 (8*500*2 settings) coding workflows to audit compliance. Our experiments follow the default implementations and configurations. We keep the scaffold’s original system prompt and tools, and extend only the task prompt, which adds the commit and pull-request steps of §3.4, permits edits to all files, and takes the pull request as text (Appendix D.4). Resolution is scored by the SWE-bench suite after extracting the patch contents from model final outputs. SWE-CC evaluates compliance after each execution in 120 to 215 ms on a local MacBook Pro (Apple M4 Pro, 24 GB unified memory), showing the scalability of our approach. 4.2 RESULTS

Modern agents suffer from coding compliance issues. Table 3 summarizes agent performance across both policy provision settings. Across the board, models exhibit severe compliance deficits. Even the top-performing model achieves a compliance rate of only 63.8% under the native setting and 71.2% under the consolidated setting. This reveals that nearly 30% of repository policies are violated during development, regardless of how functionally effective their code artifacts are. Most frontier agents demonstrate strong functional problem-solving ability, generating effective patches in 74.6%–94.4% of runs. However, agents adhere to only 51.8%–63.8% of applicable policies during these runs. A further examination in Figure 4 reveals that agents violate a mean of 7.7 out of 22.6 triggered policies (34.1%) per execution. With the help of consolidated policies, the mean number of violations drops to 6.6. 

A large share of these violations happen in the agent’s execution . The trajectory holds 50.3% of the violations among resolved runs (Figure 5), such as running the test suite before committing, which can only be checked in agent’s trajectory. An evaluation that inspects the final patch alone misses these violations, and SWE-CC captures them by checking the trajectory. Feeding the processed rules boosts compliance performance, but the improvement is not enough. Comparing consolidated with native performance reveals a consistent increase in compli-ance across all models, with an average gain of 8.75%. The greatest improvements are under GPT-5.6 Luna, where mini-SWE-agent gains +15.8% and OpenHands gains +12.2%. Meanwhile, func-tional resolution rates fluctuate within 2%, showing that policy provision does not degrade problem-solving capability. Nevertheless, compliance remains a limitation: even under the best configuration, the top model violates about 30% policy, highlighting the demands for a better compliance-enhanced strategy. 

Compliance failures over governance domains. Table 4 breaks down triggering and compliance rates across the eight policy categories. (1) Policies governing AI-assisted contributions (92%) and code & quality (82%) trigger frequently, as both apply broadly to repository-level code edits. Con-versely, documentation and docstrings and specialized changes trigger rarely, as bug-fixing bench-marks seldom require modifying project-wide documentation. (2) Compliance rates differ by type. In OpenHands, policies governing language and framework style see the highest native compli-ance, which changes minimally when guidelines are provided (+1.7%). Because pre-trained models naturally adopt idiomatic code formatting, they satisfy these intrinsic conventions by default. (3) Ironically, despite being specifically authored to govern AI behavior, AI-assisted contribution poli-cies exhibit the lowest compliance (15% in native). While providing consolidated guidelines, agents still fail to include mandated AI disclosures, demonstrating that agents often omit mandated self-disclosures. 

Bottlenecks exist in the policy retrieval and reasoning process. Native runs require the agent to discover and fetch contribution guidelines by itself, where we summarize the performance bottle-neck in two causes (Table 5). First, 71.1% of executions do not attempt to even fetch the document on average. Second, more than half of the attempts retrieve no policy text, through the harness output cap and the agent’s failures in handling the response, such as encoding errors on non-ASCII output. Attempt rates also vary significantly across models. The Consolidated setting eliminates the retrieval bottleneck by mounting all atomic policies directly into a local skill-style file. On average, 91.6% of executions open the file, bringing 99.6% of its content into the context window. Nev-ertheless, compliance remains low despite full in-context visibility, demonstrating that governance failures stem from both retrieval and reasoning processes. 

## 5 CONCLUSION 

We present a pipeline that converts a repository with established contributor guidelines into a set of executable checker functions, and build SWE-CC, a benchmark that evaluates agentic coding systems on policy compliance across both execution trajectories and final patch outputs. The evalu-ation revealed a critical limitation of current coding agents: models violate a large fraction of project guidelines when making software contributions, with roughly half of these violations occurring dur-ing intermediate execution. Further analysis shows that compliance failures stem from bottlenecks in both policy retrieval and reasoning. 9These results underscore the importance of evaluating the procedural compliance of agent actions, beyond the correctness of their final code artifacts. Moving forward, we will expand SWE-CC across diverse model architectures, scaffolds, and repository benchmarks to jointly measure correct-ness and compliance. Ultimately, reporting compliance alongside functional correctness paves the way toward safe, deployable agentic software engineers that align with real-world developer norms and reduce human maintenance overhead.

This appendix follows the five steps of Section 3.1. Steps 1 to 3 run as three stages of one agent workflow: a source manifest, extraction proper, and classification. A deterministic setup step comes first, and each stage produces an artifact that the next consumes. The extraction output is frozen before classification begins. Step 4 compiles the classified policies into checkers and Step 5 validates them. The last subsection gives the acceptance checks and the failure modes we observed. The rubrics and prompts used in each step are in Appendix D. Each repository is processed by a language-model agent working from a fixed written procedure. A short launcher prompt (Appendix D.3.1) assigns the agent one repository and directs it to the work-flow document, whose stage instructions are reproduced in Appendix D.3, together with the two classification rubrics (Appendix D.1) and a format-standard workbook. Agents for different reposi-tories run independently, each confined to its own output directory. We chose this design because the alternative does not scale. Contribution documentation for a large project runs to dozens of pages, the obligations in it are diffuse, and a study spanning twelve repositories cannot be assembled by reading them all by hand. The agent does the reading and the drafting, and a human decides what is admitted. 

Models and execution. Extraction and classification are run by Claude Opus 5 at high reasoning effort in Claude Code, one independent agent per project, with web retrieval and shell access, in August 2026. The documentation version read for each repository is recorded in its released run log. The rubrics were written against Django and SymPy and applied unchanged to the other ten repositories. 

Human review. One of the authors performs the first two checkpoints (Table 13), confirming the page list before extraction starts and the extracted rows before classification begins. The checks at the third checkpoint are automated by an acceptance script. Every run also ends with a short report from the agent giving the audit results, label counts, and anything in the procedure it found wrong, ambiguous, or missing, which the reviewer reads alongside the corpus before the repository is accepted. B.1 SETUP 

Documentation version. We read each project’s developer documentation, which is the version it directs contributors to and carries material describing changes not yet in any release. Each project is pinned at its latest published build, and all sources for a repository are read at that version. A development alias routinely serves pages built from different commits within one run, so the agent halts only on a different release version. Where builds differ, it pins the affected sources to one commit and records that no extracted quotation is affected. Where a project publishes only a moving alias, the version is resolved by hand and the choice recorded. 

Off-navigation sources. Several files that carry real obligations are reachable from no page in the documentation, including pull request and issue templates, pre-commit configuration, changelog fragment documentation, and files addressed to coding agents such as CLAUDE.md , AGENTS.md 

and .github/copilot-instructions.md . Four of the twelve projects publish such a file, and three of them yield policies. Django’s file instructs GitHub Copilot as a code reviewer, so none of it applies to a contributor. A deterministic script matches filename patterns against the repository tree through the GitHub API, retrieves every match as raw text rather than through a code host’s rendered view, and bundles them into a single file supplied to the agent. The distinction matters because rendered views strip HTML comments, and templates carry much of their instruction inside comments, so a rule read from a rendered template can come out inverted. 

Identifiers. Rule identifiers take the repository’s SWE-bench instance prefix, upper-cased, and run sequentially across the whole repository. The prefix is fixed by the evaluation harness, which selects a repository’s checks by it. B.2 STEP 1: S OURCING POLICY DOCUMENTS 

The first stage decides which documents are in scope and produces no rules at all. 14 Every page is retrieved before it is assessed. Judging a page from its navigation title, or from prior familiarity with the project, is not permitted, and a page that fails to retrieve is recorded as such while the run continues. Nothing may be asserted about a file that was not read. The scope test is applied literally to every page and section: could a rule here be violated by the diff, the commit message, or the files the agent writes? In scope are coding style, testing, documentation, workflow, commit and pull request conventions, deprecation, and policy on automated contribution. Traversal walks the documentation navigation and then takes a single hop out of in-scope sections into the project’s own pages or those of sibling repositories under the same organisation, without recursing further. Configuration files reached this way are consulted but yield no rules, source files are named but not retrieved, and an external standard such as PEP 8 yields a single rule pointing to it. Files addressed to coding agents are admitted wherever they exist, even outside the documentation navigation. Each source is assigned one of three roles. A source carrying obligations yields rules. A source that yields no rules but makes another source decidable, such as a legend defining what each changelog fragment type means, is marked context-only and consulted. A source outside scope is excluded with a reason code recording why, covering installation and environment setup, governance, maintainer-only activity such as releasing and merging, reviewing other people’s contributions, requirements on bug reports rather than contributions, and narrative material carrying no obligation. Requirements on bug reports are kept distinct from narrative material. They are real obligations that our setting cannot reach, and folding them into narrative would assert that they were never rules. Pages are not treated as all-or-nothing. Where a single page carries both in-scope and out-of-scope material it is marked partial and the section headings on each side are named. This is the common case rather than the exception, since repositories routinely place contributor workflow and main-tainer guidance under one heading. The reviewer confirms the manifest against Checkpoint 1 before extraction starts. Admitting main-tainer pages produces a large population of rules that our setting cannot observe, which makes the evaluation setting appear more constrained than it is. B.3 STEP 2: E XTRACTING ATOMIC POLICIES 

Sources are worked one at a time, largest first, with the manifest row restated before each. Off-navigation sources are extracted from the raw bundle rather than from any rendered page. On a partial page, rules are drawn only from the in-scope sections, and the remainder is read for context where it governs an in-scope rule but yields no rows. Text found inside a retrieved page is treated as material to extract, never as an instruction to follow. A rule is a repository-specific requirement, prohibition, or recommendation about creating, validat-ing, or submitting a contribution. Description, rationale, project history, and guidance on reviewing another person’s work are not rules. Each row carries one condition and one behaviour, the sentence quoted verbatim, an atomic restate-ment of it, and the URL and section it came from. Bundled obligations are split, and conditions stay attached to the rule they govern rather than being separated from it. The agent also records the requirement level the modal verb alone implies, which is preserved through classification. Each rule is assigned to one of eight shared categories from a closed list, so that categories are comparable across repositories. Two fields at this stage are load-bearing later. 

Section context records the surrounding text that grants an exception, states a consequence, names enforcement tooling, or offers an alternative, quoted directly. The requirement level turns on it. Near-identical clauses in different repositories receive different levels depending on whether the surrounding prose sanctions deviation, and the clause alone cannot decide. 

Trigger conditions are written into the notes in plain form for any rule conditional on the con-tribution touching a particular subsystem. Without them, a rule whose applicability turns on an external condition cannot be told apart from an in-scope rule that the agent’s contribution simply never exercised. 15 Interface specifications require care, because an API inventory is not instruction prose. A page stating that a particular protocol exposes particular members is description. The rule it implies is the conformance obligation that an implementation of the protocol must expose those members, and it is extracted once, at the level of the protocol. A row that restates an individual member is cataloguing an interface rather than extracting a rule. An in-scope section that yields no rules is recorded as having yielded none, with the reason. Asource that produced nothing and a source that was overlooked are otherwise indistinguishable in the finished sheet. When every source is done, the agent reports the final row count and identifier range, identifier contiguity, exact-duplicate quoted text across sources, rows per source including zero counts, and the distributions of modal-verb level, target, and category. The reviewer confirms the rows against Checkpoint 2, cross-referencing every extracted rule with its source sentence on the live page, with particular attention to quotations that begin mid-sentence, since a rule’s real scope frequently sits in the clause immediately preceding the quoted fragment. The extraction output is then frozen as a separate file and never edited afterwards. B.4 STEP 3: F ILTERING CHECKABLE POLICIES 

Classification takes the frozen extraction output and applies the rubrics of Appendix D.1 along the three criteria of Section 3.1.2: inspectable evidence, contributor actions, and mandatory require-ments. For each rule the agent assigns, in a fixed order, the Evidence Type, whether the rule is in scope or the reason it is not, and for in-scope rules the requirement level ( must or should ) and the rubric route that decided it, followed by a line of reasoning. Assigning Evidence Type first is deliberate, since assigning it after scope allowed judgment rules to be admitted. Before classification starts, the tiebreaker for conflicts within a repository is fixed centrally rather than left to the agent. Where two statements give one obligation at different levels, the stricter governs and the weaker is labelled a duplicate, with the conflict named in its notes, since an agent satisfying the stricter version satisfies both. Resolutions decided per batch come out inconsistent across the sheet. Rules are classified in batches of 25 drawn from the whole sheet rather than page by page. Duplicate detection requires seeing rules from different sources side by side, and worked page by page, a rule stating one threshold is never recognised as duplicating a rule elsewhere that states a different one for the same obligation. After each batch the agent reports label counts and the number of rows whose rubric level differs from the modal-verb level. The two are never reconciled, since the gap between them is itself a result. The final corpus has eleven columns. The deciding route, the modal-verb level, the section context, and the reasoning are composed into a single notes field in a fixed, delimiter-separated order, so that they remain machine-readable. Reasoning quotes the rule, states what the surrounding section granted or withheld, and gives a conclusion. Reasoning that could be copied unchanged between two rows indicates either that they are duplicates or that the agent has fallen back on boilerplate, and boilerplate makes a finished sheet impossible to audit. Where the agent could not settle a row, it still receives a label and is marked low confidence rather than left blank. B.5 STEP 4: C OMPILING POLICIES INTO CHECKER FUNCTIONS 

This step compiles each mandatory policy into an executable check. We describe how the checks were written, what each check ships with, and how a check decides which code it grades. B.5.1 CONSTRUCTION 

Checks were written by Claude Opus 5 at high reasoning effort in Claude Code, one agent per project, between August and September 2026. Every agent followed the checker authoring guide of Appendix D.3.5, which is released with the benchmark. A check is written from the rule row alone: the quoted source sentence, the atomic restatement, the evidence type, and any trigger condition recorded at extraction. All 823 mandatory in-scope rules compiled into a checker. The 166 in-scope rules labelled should receive no checker by design (Section 3.1.2). 16 The precondition and post-condition are described in Section 3.1.2. Two properties of that split are worth stating explicitly here. A precondition that returns no targets yields inapplicable rather than a pass, so a rule the agent’s work never brought into scope is never counted as followed. And because the precondition is what the triggering rate of Section 3.5 is computed from, an over-broad precon-dition inflates triggering and an over-narrow one hides violations, which is why the precondition is reviewed as a separate criterion below. B.5.2 AUTHORED TEST CASES 

Checks ship with authored cases: one that satisfies the rule, one that violates it, and one where it does not apply (Section 3.1.2). The cases are part of the released artifact. They pin down how each rule is read, in a form a reader can check and dispute. The suite holds 2,603 authored cases, and 767 of the 823 checker functions (93%) carry all three case types. The remaining 56 cannot reach all three outcomes by design. Eighteen address a human contributor in the loop, such as a certification that a person read and understood the change, so their cases cover the violating and inapplicable behaviour. Twenty-nine need evidence the bundle does not carry, such as a full suite run, so their cases show the check withholding a verdict. Nine select only the violating construct, such as a direct pytest call where SymPy provides its own wrapper, so a compliant contribution leaves them inapplicable. B.5.3 EXACT AND APPROXIMATE CHECKS

B.5.5 OWNERSHIP AND DETERMINISM 

A check grades only code the agent is responsible for, never pre-existing repository content. Each check declares one of three ownership modes. Created applies to existence rules, which ask whether the agent produced an artifact at all. Touched applies to formatting rules, which are graded only on the lines the diff changed. Enclosing applies to consistency rules: editing a function makes the agent responsible for its docstring and doctest, but not for prose it did not write. A wider reading would grade the target repository’s own authors, who are not under test (Appendix C.3). Checks are ordinary Python code, written once and run unchanged on every stored run. Scoring a run writes no code and calls no model, so the same run always receives the same verdicts, and a test enforces this. We considered grading each rule with a model as judge (Zheng et al., 2023) and rejected it for two reasons. The same run could score differently when graded again, and one model’s compliance would be graded by another model’s judgment. Where a rule names a static tool that runs on the changed files alone, such as flake8 or black, the check runs that tool on the base and the head and scores the difference. B.6.1 REVIEW PROCEDURE 

The checks are generated code, so they are reviewed before release rather than trusted. Review has three parts, an automated pass over the whole population, execution against the authored cases, a blind human audit of a stratified sample. The instrument the human raters worked from is reproduced in full in Appendix D.2, since the guidelines are what the agreement figure is agreement about. 

Automated pass. Every check is reviewed by Claude Opus 5 in Claude Code against the same criteria the human raters use, yielding one verdict and one line of reasoning per check. This pass locates likely faults and defines the strata the human sample is drawn from. It is not reported as human validation, and no released check rests on it alone. 

Execution. Reading code detects a check that encodes the wrong rule but not one that encodes the right rule incorrectly, so every check is executed against its authored cases and the verdicts are 19 recorded with the item. A check whose cases come out wrong is corrected before the sample is drawn. No check in the sample failed a case it carries. Where a sampled check has no case of a given type, the rater tests that behaviour on a patch of their own construction. 

Sample. Two raters independently audit a stratified sample of 150 checks, or 18% of the 823, drawn by a released script under a recorded seed. Allocation is not proportional, because corpus size ranges from 2 to 167 checks and proportional allocation would leave the smallest projects unrepresented. Projects with ten or fewer checks are taken in full, every remaining project receives a floor of five, and the remaining budget is distributed in proportion to corpus size, with at least one differential and one trajectory check drawn from every project that has any. Table 11 gives the per-project counts. The sample carries 53 exact checks and 97 approximate ones, against 294 and 529 in the population, and 119 output, 14 differential and 17 trajectory checks. Because small projects are deliberately overrepresented, any population-level rate computed from the sample is weighted by each project’s share of the 823. For each check, and without sight of the automated verdict or of the other rater’s labels, a rater answers whether the code encodes the rule as extracted, neither more strictly nor more loosely than the quoted source sentence; whether the precondition selects the targets the rule applies to, and in particular whether a recorded trigger condition is what it tests; whether the post-condition fires on the violating case and stays silent on the satisfying one; and whether the check is exact or approximate in the sense of Appendix B.5.3. The rater then records one verdict, accept or reject , naming the failing criterion and the fault in the case of a rejection. The verdict is binary by design. Whether a faulty check can be corrected with a small edit or has to be removed is a decision about the remedy rather than about the code, and folding it into the label would have the two raters disagreeing over repairability rather than over correctness. A compliance rate alone can reward an agent for doing less work, since fewer actions trigger fewer policies. A one-line commit with no pull request text triggers 6 policies and passes all 6 (100%), while a submission with a commit body, a pull request description and a release-notes entry triggers 24 and passes 23 (96%). The same effect appears in the full sweep: a Consolidated run triggers 22.7 policies on average under mini-SWE-agent and 23.5 under OpenHands, against 21.6 and 22.0 for a Native run. We therefore report the triggering rate alongside the compliance rate (Section 3.5): triggering rate = policies triggered policies in the repository , compliance rate = policies passed policies triggered .

A triggered policy is withheld when the evidence it needs is missing from the run, such as a file that does not parse or a property that requires a test-suite run. Withheld policies count as triggered and 24 are excluded from the compliance rate, so a limit of the checker is reported neither as less work by the agent nor as a verdict on it. 

## D RUBRICS AND PROMPTS 

This appendix reproduces the instruments behind Appendix B: the two labelling rubrics used in Step 3, the guidelines the human reviewers followed in Step 5, the prompts for benchmark construc-tion, and the prompts given to the evaluated agents. D.1 LABELLING RUBRICS 

Each rule is a single atomic obligation extracted verbatim from a repository’s contribution documen-tation and restated as one imperative sentence; the extraction procedure is described in Appendix B. A rule enters the benchmark only if it meets three criteria, and each criterion fills one field of the released dataset. Inspectable evidence : the rule names an artifact a checker can open, recorded in the Evidence Type field. Contributor actions : the run produces that artifact and the rule governs what the agent itself does, recorded in the In scope field by Rubric A. Mandatory requirements :the rule states a requirement, recorded as must in the Requirement level field by Rubric B. This subsection defines Evidence Type and gives the two rubrics in full, as applied. Each rubric is a decision procedure: the routes are evaluated in a fixed order, the first one that fires decides the label, and the route that fired is recorded on the row. We state them in the form the annotators worked from, so that the labels in our released dataset can be reproduced or contested. The criteria are applied in a fixed order. Evidence Type is assigned first, then scope, then requirement level on in-scope rules only. The order matters: the evidence a rule needs constrains whether it can be scored at all, and an unscoreable rule is never graded for requirement level. D.3.5 CHECKER AUTHORING GUIDE 

Checker functions are authored from a standing guide rather than from a per-repository prompt. The agent for a repository is pointed at the guide and follows it end to end: it states the two-function contract, how the condition and behaviour halves of a policy statement map onto the precondition and the post-condition, how the outcomes on individual targets combine into one outcome for the policy, the three synthetic inputs every function is tested on, and what to record when a policy cannot be coded at all. The guide names no project, and the same text is used for all twelve. It is released with the benchmark; the three clauses that decide most authoring questions are reproduced below. 

[Contract] precondition(bundle) -> list[Target] Answers *does this policy apply to what the agent did?* It selects and judges nothing. post_condition(target) -> Satisfied | Violated | Undetermined Answers *given that it applies, did the agent get it right?* It runs once per target, reads only that target's payload, and never re-selects. If it wants different material, the precondition is wrong. Undetermined(reason) -- the policy applies but the artifacts cannot answer it. Never a violation, never a silent pass. [Selection] precondition selects on the ANTECEDENT -- the situation that invokes the policy -- not on the artefact the policy demands. "Do not force-push" is: precondition every `git push `;post-condition no force flag. Selecting force-pushes would only ever find violations and could never record a compliant push. 

34 [Tests] Three per policy: satisfied, violated, and an input where the precondition finds nothing. Be honest about the limit: these tests PIN your reading of the sentence; they do not VALIDATE it. Both would pass on a predicate that confidently grades the wrong thing.

## Abstract 

Logging code supports debugging, monitoring, and software main-tenance, and developers continually revise it as software evolves. Excessive logging code can add noise to logs, impose runtime over-head, and obscure information needed for diagnosis. While prior research has extensively studied logging code generation and mod-ification, how developers remove logging code remains compara-tively underexplored. In this paper, we conduct a comprehensive study of developer logging removal practices and explore the po-tential of using coding agents to automate this task. We extract and manually validate logging removal cases from Python and Java repositories and derive 10 removal patterns and 11 removal rea-sons that characterize how and why logging code was removed in real-world software changes. We further construct LogRem , a dataset of 387 real-world cases covering direct logging statement removal, logging infrastructure removal, and logging replacement. We evaluate four coding agents with multiple model settings and compare their outputs with real-world changes that were accepted and merged into the corresponding projects. Although 95.6% to 100.0% of outputs pass validity checks, only 11.1% to 19.6% remove the same logging code as the corresponding real-world change while preserving unrelated code. Agents differ from real-world changes through missed removals, extra removals, and unrelated code edits, with substantial variation across logging removal cate-gories and trajectories. Execution cost also varies widely, but higher cost does not consistently yield closer alignment with real-world changes. In a further comparison of two different forms of input con-text, commit messages and developer discussions lead to the largest improvements in alignment with real-world changes. Guidance based on our taxonomy of logging removal patterns and reasons consistently reduces runtime. Overall, our study establishes logging removal as a distinct software maintenance task and shows that reliable automation depends on accurately determining removal scope while preserving necessary code. To the best of our knowl-edge, this is the first study to examine logging code removal from this perspective. 

## 1 Introduction 

Software systems rely on logging to make their runtime behav-ior observable [65]. Logging statements record execution events, program state, and failure information [17, 19] that developers use for debugging [27], fault diagnosis [1, 70], monitoring [6, 55], test-ing [68], and other maintenance activities [22, 38]. However, useful logging requires balancing observability against the cost of produc-ing and processing log data. Excessive logging can increase runtime overhead, generate redundant information, and make important diagnostic information harder to identify [14, 28]. These concerns are recognized in both industrial practice and academic research. AWS recommends limiting excessive logging because it can affect performance, increase storage and processing costs, and make important events harder to detect [54]. Microsoft recommends controlling logging verbosity in production and warns that logging operations can incur computation even when the corre-sponding log level is disabled [45, 46]. Google similarly recommends reducing unnecessary log volume to control ingestion, storage, and downstream processing costs [20]. Academic studies identify pre-logging overhead [71] and unnecessary exception stack trace logging [31] as practical logging quality problems. As software evolves, the value of individual logging statements can also change. Developers revise logging while fixing bugs, chang-ing features, refactoring implementations, and redesigning error handling [4, 40, 67]. Logging that was useful when introduced may later become redundant, costly, or inconsistent with the current implementation. Maintaining logging code therefore requires de-ciding both what information should continue to be recorded and what logging should be removed. The project provides a “--disable-log-requests” option, but developers observed that requests were still logged when this option was enabled. After code inspection, the developer identified two hard coded logging statements in the Ope-nAI compatible API endpoints that bypassed the configuration and recorded the complete incoming requests. Prior research has extensively studied logging evolution and automated support for logging location, level, content, generation, and maintenance [26, 30, 32–34, 39, 41, 43, 63, 73]. Recent work has also explored coding agents for generating and maintaining log-ging statements [50, 72]. In comparison, logging removal remains underexplored. Although deletion appears in studies of logging evolution [30], existing work provides limited understanding of why developers remove logging code, what related code changes are involved, and how such changes could be automated. Logging removal also requires more than deleting an individ-ual logging statement. Developers may need to determine which logging code should be removed while preserving other logging and surrounding code. The change may also require cleaning up logging infrastructure, or replacing logging with another reporting or error-handling mechanism. Recent coding agents can address repository-level maintenance tasks such as issue resolution, code editing, and repair [9, 42, 60, 64], but it remains unclear whether they can make these logging removal decisions when the expected removal scope is not specified in advance. This motivates us to examine how developers perform logging removal and how closely coding agents can reproduce such changes. In this work, we study how and why logging code was removed and examine how coding agents perform on these changes. We mine 14,931 file-level logging changes from 240 Python and Java repositories and identify 1,564 removals, which account for 10.5% of the collected changes, indicating that logging removal is prevalent. We manually inspect these cases and validate 735 logging removals, the remaining changes are additions, modifications, relocations and changes that do not pass manual validation. Our analysis shows that logging removal follows several patterns and occurs for a range of removal reasons. Developers may remove individual logging statements, clean up logging infrastructure, replace logging with another behavior, or remove logging together with larger parts of the implementation. We organize these cases into 10 removal pat-terns and 11 removal reasons. To evaluate coding agents on cases where logging removal can be studied separately from broader code removal, we select four patterns that involve direct logging state-ment removal, logging infrastructure removal, or replacement of logging with another behavior. This results in 387 cases, including 279 direct logging statement removals, 49 logging infrastructure removals, and 59 logging replacements. We construct the dataset 

LogRem using these cases. For each case, we retain the original real-world change and compare the agent output with it to deter-mine whether the agent removes the same logging code and leaves unrelated code unchanged. Our results show that coding agents usually return valid outputs, but their logging removal decisions often differ from those made in the corresponding real-world change. When given only the task description and source code, only 11.1% to 19.6% of outputs remove the same logging code as corresponding real-world changes while preserving unrelated code. Performance also differs substantially across logging removal categories: direct logging statement re-moval reaches 19.4% alignment, while logging replacement reaches only 5.9%. Execution cost varies widely across configurations and does not consistently correspond to closer alignment with real-world changes. Additional context also changes agent performance. Commit messages and developer discussions provide the largest alignment gains, increasing alignment with real-world changes by approximately 9-11%. Guidance based on our taxonomy of logging removal patterns and reasons consistently reduces runtime. Overall, our study establishes logging removal as a distinct main-tenance problem centered on inferring the intended change scope while preserving unrelated code. To the best of our knowledge, this is the first study to examine logging code removal from this perspective. Our findings show that producing valid code is easier than making precise removal decisions. These results can inform future work on more scope-aware and efficient automation of log-ging maintenance. We summarize the contributions of this paper as follows: 

• We conduct a comprehensive study of logging removal as a distinct software maintenance activity. Based on manu-ally validated real-world removals, we characterize how and why logging code was removed in real-world changes through 10 removal patterns and 11 removal reasons. • We construct LogRem by turning 387 real-world logging removal cases into tasks for coding agents. The tasks cover direct logging statement removal, logging infrastructure cleanup, and logging replacement, and each includes the source code, a task description, and the corresponding real-world change for reference. 

• Our experimental results show that coding agents face dif-ferent challenges across logging removal tasks. They align more closely with real-world changes when directly remov-ing logging statements, but struggle more when logging must be replaced. Our analysis of agent actions also reveals when they miss intended removals or remove additional code, which can help identify where future approaches need to improve. 

## 2 Background and Related Work 2.1 Logging Practices and Evolution 

Empirical studies have extensively examined how developers use and maintain logging code. Prior work shows that logging state-ments evolve frequently in open source systems and mobile applica-tions, and has investigated which characteristics are associated with later logging changes [4, 26, 65, 67]. Other studies focus on quality problems in existing logging code, including logging related issues introduced during maintenance [5, 38, 40, 61, 66]. Researchers have also studied the factors that influence developer logging decisions, such as diagnostic benefits, maintenance cost, and developer ex-perience [29, 53], as well as logging practices in specific settings including test code, machine learning applications, and Java log-ging utilities [6, 18, 68]. More broadly, Gu et al. [22] organize prior research around why, where, what, and how well to log, and reports substantially more attention to logging placement and content than to the motivations behind logging decisions. Prior work on logging evolution also includes deletion as one type of logging change [30], but removal has generally been studied as part of broader logging evolution rather than as a maintenance problem of its own. How-ever, logging removal nevertheless appears repeatedly in software evolution histories. This motivates our focus on logging removal as a distinct maintenance problem. Our work focuses specifically on how logging code is removed and why these changes were made in real-world software projects. 

## 2.2 Automated Logging Generation and Maintenance 

Research on automated logging has addressed several decisions involved in creating and maintaining logging statements. Learning based techniques have been proposed for recommending logging locations and levels, while other approaches generate logging mes-sages or complete logging statements from source code [15, 16, 37, 39, 41, 43, 63]. Software history has also been used to learn recurring logging revisions and support the maintenance of exist-ing statements [32, 33]. More recently, LLM based techniques have been applied to logging generation and maintenance by incorpo-rating program context, identifying logging gaps, and repairing defects in existing logging statements [34–36, 73]. Evaluation has progressed beyond textual similarity as well. For example, Tan et al. [57] evaluate generated logging statements using compilation and runtime behavior. However, existing techniques primarily focus on adding logging code, generating its content, or modifying exist-ing statements. Logging removal remains less studied, particularly when removal requires related cleanup or replacement behavior. Our work addresses this gap by studying coding agents on logging removal and comparing their outputs with observed real-world changes. 

## 2.3 Coding Agents and Evaluations 

LLM-based coding agents perform software maintenance by in-teracting with repositories, inspecting source files, editing code, running commands, and using execution feedback to revise their solutions [25, 60, 64]. Recent studies have also moved beyond final patch correctness to examine agent trajectories, repository explo-ration, and tool use during task execution [3, 8, 23, 69]. Specialized evaluations further study agent behavior for particular software engineering concerns, such as security [7]. Logging has recently become a target for coding agents. Zhong et al. [72] use multiple agents to determine whether logging is needed and generate log-ging statements, while Ouatiti et al. [50] study how coding agents create and maintain logging code in real pull-requests. Our study explores how coding agents perform on logging removal and ex-amines both their final outputs and their trajectories.

## 3.1 Repository Mining and Logging Change Identification 

We mine Python and Java repositories from GitHub. Following prior studies on repository selection [11, 12, 51], we exclude forks, archived repositories, templates, repositories without a license, and repositories that cannot be checked out at the target commits. We also require production source files in the target language, and more than five contributors. After applying these criteria, we rank the remaining repositories by star count and select the top 200 repos-itories for each language, resulting in an initial collection of 400 repositories. For each repository, we collect the commits between June 30, 2021 and June 30, 2026. Following prior work [62], we exclude merge commits and inspect changed Python and Java files for logging modifications. For each case, we retain the repository and commit identifiers, file path, commit metadata, pull-request information when available, the complete source code before and after the commit, and the unified diff. We identify logging changes by combining static source analysis for each language with the unified diff. For Python, we use AST analysis to identify calls to common logging receivers, including 

“logging” , “logger” , “self.logger” , “_logger” , and “_log” , as well as logging configuration and logger management operations. ## 3.2 Validation and Characterization of Logging Removals 

Automatically identified removals show where logging code disap-pears, but they cannot explain how and why it occurs. We therefore manually inspect the 1,564 removal cases using the source code before and after the change, the code diff, commit messages, and pull-request or issue discussions when available. This process re-sults in 735 verified logging removal cases from 164 repositories. We characterize each case in two dimensions: the removal pattern 

describes how logging code is removed, while the removal rea-son describes why the developer makes the decision. Each case is assigned one primary removal pattern, and one primary removal reason. When the evidence is insufficient to determine developer intent, we assign “Insufficient evidence of intent” rather than in-ferring a reason. Two authors independently annotate the verified changes. Following prior studies [24, 58, 66], we use Cohen’s 𝜅 [44] to measure inter-annotator agreement. The resulting 𝜅 values are 0.739 for removal patterns and 0.699 for removal reasons, indicating substantial agreement. The two annotators then discuss disagree-ments and resolve them whenever possible. If they cannot reach an agreement, a third author is consulted to make the final decision. Table 1 presents the 10 removal patterns identified from the 735 verified cases. Direct logging statement removal is the most common pattern, accounting for 279 cases (38.0%). However, many removals involve broader program changes, including removal with surrounding functionality, logging infrastructure cleanup, replace-ment by another mechanism, and relocation. In addition, 149 cases (20.3%) combine multiple removal mechanisms. Table 2 summarizes the 11 removal reasons. Simplification or refactoring is the most common, accounting for 227 cases (30.9%), followed by changed product requirements with 128 cases (17.4%) and redesigned error handling with 90 cases (12.2%). Other reasons include reducing noise or duplication, protecting sensitive information, reducing resource overhead, removing temporary diagnostics, migrating to another output mechanism, and cleaning up logging dependencies or configuration. For 59 cases (8.0%), the available evidence is insuf-ficient to determine developer intent reliably. Overall, these results show that logging removal varies in both how it is performed and why it occurs in real-world changes, ranging from isolated state-ment removal to changes involving supporting infrastructure or replacement behavior. We use the validated removals to construct our dataset in the next section. Direct logging statement removal is the most common pattern, but many logging removals are not limited to deleting individ-ual statements. They may also involve logging infrastructure, replacement with another behavior, or removal together with broader program changes.

## 4.1 Selecting Logging Removal Tasks 

As shown in Stage 2 of Figure 2, we construct the dataset from the 735 verified logging removal cases characterized in Section 3. We re-tain cases in which logging removal can be examined independently, including direct removal of logging statements (P01), removal of logging infrastructure such as imports, declarations, initialization, or configuration (P06), and replacement of logging by exception handling or another reporting mechanism (P07, P08). We exclude P02 to P05 because logging is removed together with broader pro-gram logic, P09 because logging is relocated rather than removed, and P10 because it combines multiple removal mechanisms. This selection results in 387 cases: 279 direct logging removals (C1), 49 logging infrastructure removals (C2), and 59 logging replacements (C3), as shown in Table 3. These cases form the dataset used in the coding agent study. 

## 4.2 Constructing Task Inputs 

For each selected case, we manually construct a natural language task description that captures the objective of the original real-world change without revealing the code changes, the logging code removed, or their locations. The description states that the task involves logging removal and that at least one logging-related code should be removed, but does not specify which code to remove, how many removals are needed, or whether infrastructure cleanup or replacement behavior is required. Each task provides this descrip-tion together with the source file, and the agent must determine the removal scope from the available information. Under the default input setting, only the task description and source code are pro-vided. We also study additional input settings, including Taxonomy guidance, commit messages, and available pull-request or issue discussions. We discuss more details in Section 5.2. ## 4.3 Original Real-World Changes and Output Validity 

For each task, we retain the original real-world change as a ref-erence for comparison and apply output validity checks during evaluation. These changes were accepted and merged by develop-ers into the corresponding projects, providing concrete examples of logging removal decisions made in practice. We do not assume that they represent the only valid solution for a task. Using the language specific analysis described in Section 3, we identify the logging code removed in the real-world changes and treat identical logging code at different source locations as separate code. These code form the reference set used in the subsequent comparison with agent generated changes. We also check whether the agent returns a valid final output. An output is considered valid when the required revised source code is present and can be parsed by the corresponding language checker. As shown in Stage 4 of Figure 2, the original real-world change and output validity checks are used to evaluate the agent’s output. 

## 5 Experiment Setup 

As shown in Figure 2, Stage 3 and Stage 4 summarize the agent interaction and evaluation procedure. This section describes the agents and models, the additional task context, the execution set-tings, and the metrics used to assess final outputs, agent trajectories, and execution cost. 

## 5.1 Agents and Models 

We evaluate four agents with different model settings. The two commercial agents are OpenAI Codex [47] with gpt-5.6-luna [48] and Claude Code [10] with claude-sonnet-4-6 [2]. We also evaluate two open-source agents: OpenHands [7, 49, 60] and mini-SWE-agent [56], which builds on SWE-agent [64] and is commonly used. For each of these two open source agents, we evaluate them with three backbone LLMs: DeepSeek-V4-Flash [13], Qwen3.8-Flash [52], and Gemini 3.7 Flash [21]. This results in eight experimental settings in total, including two commercial agent and six open-source agent experimental settings. 

## 5.2 Task Input Context 

The Base input context provides only the task description and source code. We examine two additional context sources. Commit Message and Discussion (CD) provides task specific historical context from the commit message and available pull-request or issue discussion. Taxonomy Guidance (T) provides general guidance derived from the logging removal patterns and reasons with general examples. Combined Context (CD+T) provides both CD and T, allowing us to examine if combining the two context sources further improves agent performance. We study four input contexts in total: 

Base , Base+CD , Base+T , and Base+CD+T .

## 5.3 Execution Settings 

Each agent and model is evaluated on the same set of dataset cases using the same evaluation procedure and the reasoning effort is set to medium for all supported models. The turn limit follows the OpenHands default of 100 iterations [49] and is comparable to recent coding agent evaluations [7]. Each execution ends when the agent returns the final output or reaches the turn limit. We record the final output, agent actions, tool/exploration calls, token usage, and runtime. 

## 5.4 Evaluation Metrics 

We evaluate both the agent’s final output and its trajectory. For the final output, we measure output validity, alignment with real-world changes, and preservation of unrelated code. For the trajectory, we examine removal actions, tool use, token usage, and runtime. The original real-world changes were accepted and merged into their corresponding projects, so we use them as practical references for comparison rather than as the only valid or optimal solutions. Agent Trajectory Analysis. The final code does not reveal how the agent reaches its result, so we analyze the removal actions recorded in the trajectory. ## 6.1 RQ1: How do coding agent outputs compare with real-world logging removal changes? 

Motivation. Removing logging code often requires more than deleting individual logging statements. Developers may need to inspect the surrounding implementation, dependencies, and main-tenance context to decide which logging code should be removed and whether infrastructure cleanup or replacement is needed. RQ1 examines how closely current coding agents can reproduce such changes made in real-world projects. 

Approach. We evaluate all model settings on the 387 logging re-moval tasks under the Base input context. For each task, we com-pare the agent output with the corresponding real-world change. We first examine overall alignment across the eight settings, then analyze differences in removal scope through under and over re-movals. We further compare results across C1, C2, and C3 to deter-mine whether different logging removal categories exhibit distinct output characteristics. 

Results. Coding agents exhibit limited alignment with real-world logging removal decisions under the Base input con-text. As shown in Table 4, RWCA rate ranges from 11.1% to 19.6% across the eight settings. OpenHands with Gemini 3.7 Flash reaches 19.6%, while Claude Code with Sonnet 4.6 reaches 11.1%. This in-dicates a substantial gap between removals generated by coding agents and the changes made in real-world commits. 

Agents usually produce valid code, but often make log-ging changes that differ from the corresponding real-world changes. Agents often remove dif-ferent logging code from the real-world changes or make extra changes to unrelated code. 

Performance varies across agent and model settings, and no setting performs consistently well across all aspects of logging removal. ## 7.2 Implications 

We discuss the implications of our findings for practitioners and researchers. IMP-P# denotes implications for practitioners, and 

IMP-R# denotes implications for researchers. 

IMP-P1. Review logging removal as both a deletion and a preservation task. Our results show that an agent can identify relevant logging code while still changing code that left untouched in the real-world change. Logging replacement poses a different challenge because the agent must determine both what to remove and what behavior should replace it. In practice, reviewing an agent generated removal should therefore check not only whether the in-tended logging disappears, but also whether surrounding behavior and remaining logging are preserved and whether required cleanup or replacement is handled correctly. The removal patterns provide a useful way to organize these checks. Direct removal calls for veri-fying the target statements and surrounding logic, infrastructure removal requires checking imports, declarations, and configuration, and replacement requires validating the new behavior. 

IMP-P2. Use project history when available, and use taxon-omy guidance when task-specific evidence is limited. RQ4 shows that commit messages and developer discussions provide the largest improvements in alignment for both evaluated settings. RWCA rate increases from 11.1% to 22.2% for Claude Code and from 19.6% to 28.2% for OpenHands. Taxonomy guidance produces smaller alignment improvements but consistently reduces runtime. ## 8 Threats to Validity 

Construct validity. Real-world changes provide concrete examples of logging removal decisions that were accepted and merged into their projects, but they do not necessarily represent the only valid solution. An agent may produce a different removal scope that is still reasonable under another observability or maintenance objective. We therefore interpret Real-World Change Alignment and related measures as alignment with the real-world change rather than absolute correctness. 

Internal validity. Dataset construction combines automated log-ging change identification with manual validation, and annotation, which may be affected by identification errors, ambiguous reposi-tory evidence, or subjective judgments. To reduce annotation in-consistency, two authors independently annotate the verified cases and discuss disagreements to reach consensus. When an agree-ment cannot be reached, a third author is engaged to make the final decision. Cohen’s 𝜅 is 0.739 for removal patterns and 0.699 for removal reasons. We inspect source code, diffs, commit messages, and pull-request or issue discussions when available, and assign an insufficient-evidence category when removal intent cannot be in-ferred reliably. Task descriptions are constructed without revealing the real-world change or removal locations. 

External validity. We conduct the study on Python and Java open-source projects. The findings may not directly generalize to other programming languages, logging ecosystems, project domains, or more tightly coupled maintenance changes. Our evaluation covers multiple agent frameworks, models, and removal categories, but future systems and settings may perform differently. As coding agent systems continue to evolve, replication on additional models, repositories, and maintenance settings would further assess the generality of the findings.

## 摘要
日志代码支持调试、监控和软件维护，但过度的日志记录会增加噪声、带来运行时开销，并掩盖诊断信息。尽管已有研究广泛探讨了日志代码的生成与修改，日志移除仍相对缺乏探索。本文研究开发者的日志移除实践，并探索使用编码智能体完成该任务。我们从 Python 和 Java 仓库中抽取并人工验证日志移除案例，归纳出 10 种移除模式和 11 种移除原因，用以刻画真实软件变更中日志代码是如何以及为何被移除的。我们进一步构建了 LogRem，一个包含 387 个真实案例的数据集，涵盖直接移除日志语句、移除日志基础设施以及日志替换。我们评估了四种编码智能体在多种模型设置下的表现，并将其输出与已被接受的现实世界变更进行比较。尽管 95.6% 至 100.0% 的输出通过有效性检查，但只有 11.1% 至 19.6% 的输出在保留无关代码的同时移除了与相应真实变更相同的日志代码。智能体之间的差异体现在漏移除、过度移除和无关代码编辑上，并且在不同的日志移除类别和轨迹之间存在显著差异。执行成本差异很大，但更高的成本并不总能带来更接近的一致性。提交信息和开发者讨论带来最大的对齐提升，而分类体系指导则能持续降低运行时间。总体而言，我们的研究将日志移除确立为一项独特的软件维护任务，并表明可靠的自动化取决于在保留必要代码的同时准确确定移除范围。据我们所知，这是首个从这一视角审视日志代码移除的研究。

## Abstract
Logging code supports debugging, monitoring, and software maintenance, but excessive logging can add noise, impose runtime overhead, and obscure diagnostic information. While prior research has extensively studied logging code generation and modification, logging removal remains comparatively underexplored. In this paper, we study developer logging removal practices and explore the use of coding agents for this task. We extract and manually validate logging removal cases from Python and Java repositories and derive 10 removal patterns and 11 removal reasons that characterize how and why logging code was removed in real-world software changes. We further construct LogRem, a dataset of 387 real-world cases covering direct logging statement removal, logging infrastructure removal, and logging replacement. We evaluate four coding agents with multiple model settings and compare their outputs with accepted real-world changes. Although 95.6% to 100.0% of outputs pass validity checks, only 11.1% to 19.6% remove the same logging code as the corresponding real-world change while preserving unrelated code. Agents differ through missed removals, extra removals, and unrelated code edits, with substantial variation across logging removal categories and trajectories. Execution cost varies widely, but higher cost does not consistently yield closer alignment. Commit messages and developer discussions provide the largest alignment gains, while taxonomy guidance consistently reduces runtime. Overall, our study establishes logging removal as a distinct software maintenance task and shows that reliable automation depends on accurately determining removal scope while preserving necessary code. To the best of our knowledge, this is the first study to examine logging code removal from this perspective.

### 2.5 评估指标（核心公式以文字说明）
- **Output Validity Rate**：输出包含所需修订后源码且能被对应语言解析器处理的比例。
- **RWCA（Real-World Change Alignment）Rate**：输出有效 **且** 移除的日志代码集合与真实变更完全一致 **且** 未改动无关代码（U=1）的任务比例——这是最严格的指标。
- **Exact Removal Match**：移除的日志代码集合与真实变更完全一致的任务比例。
- **Removal Precision / Recall / F1**：以 TP（双方都删）、FN（真实删了但智能体保留）、FP（智能体多删）计算；同一日志代码在不同源码位置视为不同代码。
- **Under Removal / Over Removal**：漏删（真实删除仍残留）与多删（智能体删了真实保留的日志代码），同时报告涉及代码数与受影响任务占比。
- **UCP（Unrelated Code Preservation Rate）**：基于行级 diff 确定性识别非日志相关的无关编辑，未做此类编辑的任务比例。
- **轨迹指标**：Removal Action Coverage（智能体移除动作覆盖真实移除的比例）、Missed Removal Action Rate、Extra Removal Action Rate；采用**确定性一对一匹配**（基于受影响代码与源位置），不使用 LLM 判官。
- **成本指标**：token 用量（输入/输出/总量）、runtime、exploration calls、tool calls，以及归一化指标 **Tokens per Aligned Task** 与 **Runtime per Aligned Task**。

## 7. 论文的价值、局限与未来方向

- **主要贡献**：
  1. 首次将**日志代码移除**确立为独立研究任务，并给出"模式（how）× 原因（why）"的双维分类体系（10 种模式、11 种原因）。
  2. 构建并公开 **LogRem** 数据集（387 个真实 Python/Java 移除案例），配以人工撰写的自然语言任务描述，可作为后续研究的统一基准。
  3. 提出面向移除任务的**多层次评估框架**，特别是 RWCA 这一"最严格对齐指标"，以及区分"漏删 / 多删 / 无关代码改动"的诊断性指标。
  4. 系统评测 8 种智能体配置 × 4 种上下文，量化了"当前智能体离真实日志移除决策有多远"。
- **方法学局限**：
  - 以**单一真实提交**为金标准，无法覆盖"多种合理移除方案"的情形；作者虽已声明 RWCA 非唯一正确性判据，但该指标仍主导了结论。
  - 任务描述由作者人工撰写，可能与真实开发者的自然表述存在分布差异，且描述本身的信息量会显著影响智能体表现。
  - 排除 P02–P05、P09、P10 后，数据集偏向"日志可被孤立处理"的案例，**回避了日志与业务逻辑深度耦合这一最困难场景**。
  - 未报告多次运行的方差、无显著性检验、无严格消融，配置间的细小差距（如 18.3% vs 19.6%）不宜过度解读。
- **可推广性与影响**：研究结论对日志生成、日志维护、代码变更推荐等相邻任务具有警示意义——"能生成/能改"不等于"能判断该不该存在"；同时为日志质量治理（降低噪声、保护敏感信息、控制开销）提供了可自动化的潜在路径。
- **未来方向（由论文结果自然引出）**：
  - 让智能体显式进行**移除范围推理**，例如先定位日志意图与调用链，再决定删除粒度。
  - 引入**仓库级上下文**（日志配置、依赖关系、监控管线、历史讨论）而非仅文件级源码。
  - 从"复现单一历史决策"转向**多方案评估**，建立人类偏好或可接受区间标注。
  - 面向 C3 类任务探索"日志→异常/监控/指标"的替换知识库。
  - 降低推理成本，避免"高成本低对齐"的低效模式。

## 8. 总体评价（客观小结）

这是一篇**问题定义清晰、实证扎实、结论克制**的论文。其最大价值不在于证明某个智能体好用，而在于用一套自建的、可复现的基准把"日志移除"从日志演化研究中的附属变更类型，提升为一个有独立难点（范围推断）、有分类体系、有量化评估的维护任务；并用 95.6%–100.0% 的输出有效性与 11.1%–19.6% 的 RWCA 之间的巨大落差，给出了一个相当有说服力的"how far are we"答案：**语法层面已接近，语义与意图层面仍很远**。其局限也较为透明（单一金标准、类别不均衡、无方差与显著性报告、未覆盖耦合场景），因此结论宜理解为"当前主流智能体在此任务上尚不可靠"的现状快照，而非对能力的上限判定。

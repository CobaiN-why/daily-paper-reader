Abstract
As coding agents take on long-horizon software evolution tasks spanning multiple files and stages,
longer execution trajectories introduce two coupled challenges: (1) accumulated histories strain
context budgets, and (2) repository changes can invalidate earlier execution evidence. Existing
approaches address these challenges through techniques like larger context windows, compression,
retrieval, or repository representations, but often fail to reconstruct a consistent task state after a
context refresh or verify whether recalled evidence remains valid. Thus, we introduce MemTrace,
a provenance-aware memory system that preserves execution history and aligns its reuse with the
evolving task (e.g., iterative cross-file repair) and repository state. MemTrace stores history as
immutable Memory Traces anchored to key information (e.g., files, symbols, tests), and organizes their
execution order and dependencies in a Memory Trace Graph. When context is constrained, working
memory retains only compact Memory Anchors, from which the agent can reconstruct the latest
execution state and locate evidence relevant to its next action. Before restoring historical evidence,
MemTrace checks its validity against the current repository state and retrieves only what the next
action requires. Across three complementary long-horizon coding benchmarks, MemTrace consistently
outperforms all fully evaluated baselines under the same backbone and harness, improving DeepSWE
pass@1 by 21.2 points, SWE-EVO Resolved Rate by 4.4 points, and SWE-Milestone Score by 17.8 points
under Codex CLI.

1 Introduction
Coding agents are moving from isolated bug fixing toward cross-file, multi-stage software maintenance and
development, which requires iterative code inspection, coordinated edits, testing, and revision [13, 17, 32]. As
execution lengthens, growing interaction history increases context pressure, while ongoing repository changes
can make earlier observations, test outcomes, and decisions no longer applicable to the current state. This
challenge already appears in deployed coding agents: systems such as Codex CLI [3] use context compaction
to continue long-running tasks across context boundaries. Such mechanisms preserve execution continuity, but
continuity alone does not determine whether recovered evidence still applies after the repository has changed.
Long-horizon execution therefore requires the agent to maintain an accurate representation of task progress:
what has been completed, what remains unresolved, and which prior evidence still applies. Task-state drift
arises when this representation no longer matches the current task and repository state. The problem becomes
particularly important after a context refresh, when the agent must reconstruct prior progress and recover
evidence that remains applicable before continuing the unfinished task.
Existing approaches mitigate different parts of this problem. Longer context windows accommodate more
interaction history, while prompt compression condenses earlier context and observation masking selectively

The remaining challenge is to recover the current task state, not merely historical content. As illustrated in
Figure 1(a), a refreshed context may retrieve an earlier test failure even after a repair and a passing rerun.
Without the relation to these later events, the failure may be mistaken for an unresolved issue. We call this
mismatch between recovered history and the current task and repository state state-memory misalignment.
Addressing it requires reconstructing the current task state and identifying which prior evidence remains valid
in the current repository and relevant to the next action.
To address this gap, we introduce MemTrace, a provenance-aware memory system that casts long-horizon
coding memory as a state-alignment problem rather than mere history retention. Completed execution is sealed
into immutable Memory Traces with explicit repository bindings and organized through two complementary
views. A Memory Trace Graph (MTG) encodes depend, verify, correct, and supersede relations, enabling relation-
aware traversal from the current execution frontier to evidence that establishes, revises, or invalidates its
state. A Repository State Graph (RSG) maintains the current files, symbols, tests, and their structural relations.
Trace-to-entity bindings project candidate traces onto this evolving state to determine whether their referenced
evidence remains applicable. Under context pressure, trace bodies are offloaded while Memory Anchors
preserve addressability. After a context refresh, MemTrace reconstructs the frontier through the MTG, checks
candidate evidence against the RSG, filters stale or superseded traces, and loads only the validated evidence
required for the next action back into working context (Figure 1(b)).
To assess MemTrace’s effectiveness in long-horizon coding, we evaluate it on three complementary benchmarks
covering repository-level engineering, multi-step software evolution, and continuous milestone-based develop-
ment: DeepSWE, SWE-EVO, and SWE-Milestone. MemTrace consistently outperforms fully evaluated baselines
across agent harnesses, while achieving a 46.4% overall score on SWE-Milestone under Codex. Ablations show
that persistence alone is insufficient: both structured execution memory and repository-state grounding are
important for maintaining state-consistent memory over long-horizon execution.

(1) We introduce a state-bound execution-memory representation for long-horizon tasks that preserves historical

2 Related Work
Context management for long-horizon agents.
Long-horizon agents must manage growing interaction
histories within a finite context window. LLMLingua and LongLLMLingua compress prompts [15, 16], while
observation masking and SWE-Pruner reduce the tool content retained in context [20, 34]. MemGPT manages
information across working and external memory [24]; ReadAgent, MemWalker, and RAPTOR use summaries
and retrieval to access long documents [4, 18, 27]. For agent trajectories, Context as a Tool and Context-Folding
organize history around tasks or subtrajectories [21, 30], while Self-GC and Scroll retain recoverable history
outside the active context [12, 19]. These approaches make longer histories manageable. However, recovering
historical content does not establish whether it still supports the task after later edits or tests. MemTrace
couples history retrieval with task-state recovery, using relations among execution records to determine what
has been completed and what remains unresolved.
Agent memory and execution-state management.
Agent-memory systems retain experiences and reflections
for later decisions [25, 28]. Mem0 updates salient memories, A-MEM links related memory notes, and Zep
tracks the temporal validity of facts while retaining superseded information [7, 26, 39]. Beyond storing
reusable knowledge, recent systems also use memory to maintain an explicit view of ongoing task progress.
MAGE maintains a hierarchical state tree with summary validation and rollback [5], while Ledger uses change
counters to track observation freshness and reduce redundant actions [35]. These mechanisms help preserve
execution state across long trajectories. In coding, however, maintaining task progress alone is insufficient:
stored observations and test results may become stale as the repository changes. Recovering offloaded evidence
therefore requires not only reconstructing what happened later, but also checking whether the evidence still
applies to the current repository. MemTrace addresses this by binding immutable execution traces to repository
state, recording verification, correction, and supersession relations in its Memory Trace Graph (MTG), and
validating evidence before restoration.

3 Method
MemTrace equips coding agents with persistent execution memory that survives context refreshes and supports
evidence reuse as the repository evolves. It stores completed units of work as immutable Memory Traces and
records their execution order and dependencies in a Memory Trace Graph (MTG). A complementary Repository
State Graph (RSG) represents the current files, symbols, tests, and their structural relations. Linking traces to
repository entities allows MemTrace to check whether historical evidence remains applicable. When working
memory approaches its context limit, MemTrace offloads completed trace bodies, retaining compact Memory
Anchors and lightweight Trace Synopses that reference the persistent store. After a context refresh, it reconstructs
the execution frontier, validates historical evidence against the current repository, and restores only what the
next action requires.

3.1 State-Bound Memory Traces
Long execution histories consume context, while repository changes can invalidate earlier observations. To
support compact retention and reliable reuse, MemTrace organizes history into immutable Memory Traces,
each binding a completed unit of execution evidence to the repository state in which it was produced. Trace
construction and offloading proceed as follows.
Identify and seal reusable evidence.
MemTrace seals a unit of work when it is complete and provides
evidence that can support subsequent actions, such as an edit, test outcome, failure diagnosis, or correction.

anchor to At. A unit that exceeds the size of a single trace body is split into multiple traces, each with its own
anchor.
Preserve provenance as the repository evolves.
Once sealed, a trace is never modified. Subsequent edits or
corrections produce new traces and relations, preserving the original evidence, repository state, and entity
bindings. These records make the conditions under which evidence was produced available for later validation.
Persistence alone, however, does not establish current validity: a recorded test pass may no longer apply
after the tested code changes. MemTrace therefore retains historical traces for provenance but reuses their
evidence only when it remains applicable. Section 3.3 describes how ρτ and E(τ) are checked against the
current repository state Rt and task state mt before restoration.
Offload bodies while retaining access.
When working memory Ct approaches the context budget B, Memory
Offloading removes selected completed trace bodies from the active context while preserving their full records in
Ht. Compact Trace Synopses summarize the offloaded content, and Memory Anchors provide stable references
to it. Both count toward B, so only a budgeted subset remains in Ct. Anchors omitted from the active context
remain stored with their traces and are recoverable through the persistent index. This separates persistent
retention from in-context use: evidence remains accessible, while its restoration depends on the validation
procedure in Section 3.3.
3.2 MTG–RSG Projection
MemTrace links execution history to the evolving codebase through two complementary graphs: the Memory
Trace Graph (MTG) records task progress, and the Repository State Graph (RSG) represents current repository
structure. Their nodes and edges remain separate; the projection Πt connects traces to repository entities.
Execution and repository graphs.
The MTG GM
t contains one node per trace in Ht, with relations recording
execution order, dependencies, verification, correction, and supersession. For example, a repair trace may
depend on a failure diagnosis and supersede an earlier edit, while a passing-test trace verifies the repair. These
relations identify evidence that supports or revises the frontier mt.
The RSG GR
t connects task-relevant files, symbols, and tests through defines, calls, imports, and covers relations.
Here, covers denotes a test-to-code association for localization, not measured coverage or a passing result.
MemTrace incrementally updates the graph around the execution frontier as Rt changes. Its structural relations
guide retrieval without establishing the validity of historical evidence.

4 Experiments
We evaluate MemTrace on three long-horizon coding benchmarks and two agent harnesses. We compare
task performance (Section 4.2) and analyze component contributions and memory behavior (Section 4.3).
Wall-clock results are in Appendix A.2.
4.1 Experimental Setup
Benchmarks.
We evaluate on three long-horizon software engineering benchmarks covering complementary
task settings. DeepSWE [13] contains 113 tasks across 91 repositories and five programming languages. SWE-
EVO [32] comprises 48 software-evolution tasks constructed from release histories of seven Python projects.
Two instances already pass all FAIL_TO_PASS tests without code changes, so we evaluate the remaining 46
tasks. SWE-Milestone [8] contains 98 human-verified milestones across seven continuous software-evolution
itineraries spanning five languages.
Backbone, harnesses, and baselines.
We use deepseek-v4-flash-0731-high for all experiments, with a
200K-token context window and no explicit step limit. Experiments are conducted under Codex CLI v0.144.4 [3]
and mini-swe-agent v2.4.6 [31]. We compare against three baselines. Native uses the default context man-
agement of each harness. Observation Masking [20] masks older tool observations outside a rolling window
while retaining the reasoning and action history. RepoGraph [23] augments the agent with repository-level
structural retrieval and is evaluated only on Python tasks, following its implementation scope.
Metrics.
We report benchmark-specific effectiveness metrics together with wall-clock time. For DeepSWE,
we report pass@1 and the average wall-clock time per task, where pass@1 measures the fraction of tasks
successfully resolved. For SWE-EVO, we report Resolved Rate, Fix Rate, and Apply, measuring complete

4.2 Main Results
Table 2 compares MemTrace with the baselines across three benchmarks and two agent harnesses. Beyond
the overall gains, the results reveal three notable patterns: strong harness sensitivity among the baselines,
persistent gains in Python-only settings, and a clear distinction between partial progress and complete task
resolution.
(i) Baseline effectiveness depends strongly on the harness, whereas MemTrace remains effective across
both. MemTrace achieves the best primary metric in every benchmark–harness setting. In contrast, the
relative performance of the baselines changes substantially across harnesses. On SWE-EVO, for example,
Observation Masking improves over Native by 17.4 points under Codex CLI, but falls 28.3 points below Native
under mini-swe-agent; RepoGraph shows a similar reversal. This suggests that context reduction and structural
retrieval are sensitive to the surrounding agent execution policy, while the benefit of MemTrace is more stable
across harnesses.
(ii) The gain persists on Python, where RepoGraph is directly applicable. On the DeepSWE Python subset,
MemTrace exceeds RepoGraph by more than 26 points under Codex CLI and 32 points under mini-swe-agent.
A different pattern appears on SWE-Milestone: under Codex CLI, MemTrace and RepoGraph are nearly tied
on Python Score, Precision, and Recall, yet the strict Resolved Rate increases from 8.3% to 16.7%. Thus, the
advantage is not explained by language coverage alone; on sequential evolution tasks, it is particularly visible
in converting partial progress into complete solutions.
(iii) Higher partial-progress metrics do not necessarily translate into higher task resolution. On SWE-EVO
under Codex CLI, Observation Masking attains a slightly higher Fix Rate than MemTrace (72.1% vs. 70.6%),
but a lower Resolved Rate (65.2% vs. 69.6%). Under mini-swe-agent, MemTrace has a lower Apply rate than
the best baseline (93.5% vs. 97.8%) while achieving a substantially higher Resolved Rate (63.0% vs. 52.2%).
The improvement therefore appears primarily in end-to-end task completion, rather than in patch applicability
or partial repair alone.

4.3 Analysis
Component ablation.
Adding the MTG to the Trace Store improves DeepSWE from 32.1% to 44.2%, showing
that execution relations help connect earlier edits, tests, and corrections across a long trajectory. Adding the
RSG further raises performance to 56.6%, indicating the value of tracking relations among files, symbols, and
tests when task progress spans a broad repository context. This effect is much smaller on SWE-EVO, where
removing the RSG leaves performance unchanged at 69.6%. One likely reason is the difference in task scope:
DeepSWE covers repository-level tasks across many repositories and languages, whereas SWE-EVO follows
release-level evolution within a smaller set of projects. As a result, explicit repository grounding appears more
useful when recovery must reconnect evidence across a broader and more heterogeneous codebase.
State–memory alignment.
We examine how later repository changes affect stored execution evidence.
Among 9,226 eligible file-bound Memory Traces, 57.0% encounter a later change to at least one bound file.
Exposure is more frequent in tasks with more repository revisions (Spearman ρ = 0.49; Figure 4(a)). The
estimated probability that bound files remain unchanged falls to about 0.50 after 1,000 logged event steps
(Figure 4(b)). These observations motivate checking current applicability before reusing historical evidence.
Definitions and statistics are in Appendix A.3.
Long-horizon behavior.
We group DeepSWE tasks into short, medium, and long execution horizons using
response counts from an independent Native run (Appendix A.4). Across the three groups, median stored

Memory Traces increase as 79 →102.5 →129, repository revisions as 21 →30 →41, and semantic evidence
invalidations as 122 →142 →223 (Figure 5(a–c)). Longer execution therefore corresponds to more accumulated
history and repository evolution, increasing state-aware memory maintenance. The exposure rate, however,
shows no clear monotonic increase with execution length (Figure 5(d)), indicating that the added maintenance
load is driven mainly by more stored history and repository changes rather than a higher per-trace exposure
rate.
5 Conclusion and Future Work
We introduced MemTrace, a state-consistent memory system for long-horizon coding agents that preserves
execution evidence with repository provenance and validates it before reuse. Across long-horizon benchmarks,
MemTrace consistently improves the primary task-level metric over fully evaluated baselines across two
agent harnesses, while our analyses show the complementary value of structured execution memory and
repository-state grounding. These results suggest that long-horizon memory should maintain not only historical
information, but also its applicability to the current execution state. Future work will evaluate MemTrace
with additional backbone models and context-window sizes, and extend it to persistent development settings
spanning multiple tasks and sessions within the same repository.

Interpretation.
The case links historical storage, a later change to a bound file, and successful continuation
across a Context Refresh. The file binding identifies where current applicability must be checked; the later test
supplies evidence about the updated execution state. This illustrates the distinction between preserving history
and establishing its current applicability.

## 摘要
大型语言模型（LLM）在代码生成方面表现出强大性能，其成功既取决于回忆相关算法知识，也取决于推理如何应用这些知识。然而，现有 LLM 流水线是不透明的，没有显式区分这两个组成部分。我们认为，对于那些规范实现广泛存在于预训练语料中的知名算法，代码生成更适合被衡量为参数化代码检索：从内化知识中复现一个命名算法，而不是合成一个新算法。我们提出了 AlgoREval，一个包含 599 个问题的基准，涵盖 14 个领域中的 77 个经典算法、7 种编程语言和 4 种图输入表示，以孤立地评估这一能力，并在零样本设置下评估了 15 个模型（7B–34B 参数）。我们发现，即使对于被广泛记录的算法，检索准确率在不同语言和输入表示之间也存在显著差异，并表明使用检索到的代码片段或结构化算法提示进行提示增强可以提高复杂算法上的准确率，而 SFT 能带来更广泛的语言增益，GRPO 在特定语言上带来更大的单语言增益。总之，我们的结果确立了参数化代码检索作为一种独特且可衡量的能力，并提醒不要在没有系统验证的情况下部署 AI 生成的算法代码。（代码和数据集可在 https://github.com/Nickil21/AlgoREval 获取）

## Abstract
Large language models (LLMs) have demonstrated strong performance in code generation, where success depends on both recalling relevant algorithmic knowledge and reasoning about how to apply it. However, existing LLM pipelines are opaque, with no explicit separation between these two components. We argue that for well-known algorithms whose canonical implementations are widely accessible in pretraining corpora, code generation is better measured as \textit{parametric code retrieval}: reproducing a named algorithm from internalised knowledge rather than synthesizing a novel one. We introduce AlgoREval, a benchmark of 599 problems spanning classical 77 algorithms across 14 domains, 7 programming languages, and 4 graph-input representations to evaluate this capability in isolation, and assess 15 models (7B--34B parameters) in a zero-shot setting. We find substantial variation in retrieval accuracy across languages and input representations, even for widely documented algorithms and show that prompt augmentation with retrieved code snippets or structured algorithmic hints improve accuracy on complex algorithms, while SFT achieves broader language gains and GRPO achieves larger per-language gains on specific languages. Together, our results establish parametric code retrieval as a distinct, measurable capability and caution against deploying AI-generated algorithmic code without systematic validation.\footnote{Code and dataset are available at https://github.com/Nickil21/AlgoREval

## 1. 核心问题与研究动机

- **核心问题**：LLM 代码生成能力被笼统地归为"合成"（synthesis），但其中实际混合了三种本质不同的能力：
  - **合成（Synthesis）**：从问题陈述出发推理出未见过的解法；
  - **检索（Retrieval）**：从参数化知识中重建正确实现（即使表面形式未逐字见过）；
  - **背诵（Recitation）**：回放近乎逐字的缓存 token 序列。
- **研究动机**：对 Dijkstra、Tarjan 等规范实现广泛存在于预训练语料的**知名算法**，模型无需"发明"，而应"检索"。三者失败模式不同（合成在新问题上失败、检索在表面形式漂移时退化、背诵在缺预期转录时崩溃），但现有基准将三者混为一谈。
- **现实意义**：约 72% 开发者日常使用 AI 编码工具、AI 生成 42% 已提交代码，而 66% 的人最大痛点是"代码几乎对但不完全对"——这正是检索失败的典型表现。在无逐步人工审查的 agentic 流水线中，静默的错误输出可能直到生产事故才暴露。
- **贡献定位**：将"参数化代码检索"确立为**独立可测的能力**，并给出基准 AlgoREval、失败图谱与两种补救路径（提示增强、权重微调）的对比。

## 2. 方法论

### 2.1 核心思想

- 定义**参数化代码检索**：在指定编程语言与输入表示下，仅依赖模型参数记忆、不借助外部文档或上下文示例，恢复命名算法的正确可执行实现。
- 任务实例形式化：每个问题实例 $p = (a, \ell, r, \sigma_p, t_p, y_p)$，其中 $a$ 为算法名、$\ell$ 为目标语言、$r$ 为输入表示、$\sigma_p$ 为函数/类签名、$t_p$ 为固定测试输入、$y_p$ 为参考实现执行后的期望标准输出。
- **零样本约束**：提示仅包含算法名、语言、输入表示、签名与具体测试输入，**不提供参考实现、伪代码或思维链脚手架**，确保正确解只能源自参数化记忆。

### 2.2 评分与失败分类

- 主指标为 **Pass Rate**：
  $$\text{Pass}(m,S)=\frac{1}{|S|}\sum_{p\in S}\mathbb{1}[\hat{y}_m(p)=y_p]$$
  即执行输出经空白归一化后与期望完全一致才算通过。
- 失败分四类（互斥）：**静态失败**（解析/编译错误）、**运行时错误**、**超时**（>30 s）、**错误输出**（干净执行但 stdout 错误）。其中"错误输出"最具诊断价值。

### 2.3 基准构建流程

- 以 107 个 Python 问题（来自 RosettaCode、GeeksforGeeks）为种子，覆盖 77 个算法、14 个领域。
- 通过三种变换扩展至 7 种语言：替换目标语言名、将 Python 测试块替换为显式期望输出规范、改写入口点惯用法（如 `int main()` / `fn main()`）。
- 图算法额外构造 4 种输入表示变体（edge_list、adj_list、adj_matrix、incidence_matrix），共 228 条图算法条目。
- 最终规模：**599 题 × 7 语言 × 4 图表示**。

### 2.4 补救方法

- **提示增强**：
  - `+Hint`：由 GPT-4o-mini 离线生成的语言无关伪代码（≤20 行）+ 关键数据结构 + Big-O 复杂度；
  - `+Snippet`：从 GitHub 检索的语言匹配参考实现（≤80 行，排除 RosettaCode/GeeksforGeeks 以防污染）。
- **权重级微调**（针对 gpt-oss-20B，LoRA r=16, α=32, dropout=0.05，约 0.5% 可训练参数）：
  - **GRPO**：以执行正确性为奖励，四档奖励阶梯（精确匹配 1.0 / 归一化匹配 0.8 / 干净执行但输出错 0.3 / 崩溃 0.0–0.1），按 (algo × lang × repr) 分组归一化优势，跳过零方差组；
  - **SFT**：在基座已得 r=1.0 的 367 条样本上做拒绝采样训练，以隔离"策略梯度信用分配"与"仅训练正确解"的贡献差异。

## 6. 主要结论与发现

- **RQ1（检索保真度）**：
  - 15 模型总体平均 Pass@1 仅 **41.2%**，且与模型规模、代码专精程度**几乎不相关**；gpt-oss-20B（20B）反而以 88.0% 居首；
  - 检索准确率主要由**表面形式**（语言、输入表示）决定：同一模型同一算法，输入从 edge_list 换为 adj_matrix 时通过率下降超过 10 个百分点；
  - Python/JavaScript 的主导失败模式是**错误输出**（可运行但静默算错），编译型语言则更多为静态失败；
  - 解多样性分析显示平均 SequenceMatcher 相似度仅 0.21、EM=0，但 80% 的配对被判为共享同一算法思路——**支持"参数化检索"而非"背诵"**的解释。
- **RQ2（提示增强）**：
  - 总体上两种增强**均未提升**聚合通过率（Hint −0.6pp，Snippet −0.4pp）；
  - 仅在**参数化知识本就稀薄的困难子集**（219 题，基线 <25%）上有效：Hint +2.9pp、Snippet +3.9pp；
  - 在复杂图算法（Hopcroft–Karp、Stoer–Wagner、Blossom）上，**可执行代码片段优于抽象伪代码**（+1.4pp vs. +0.6pp）。
- **RQ3（微调）**：
  - **SFT** 增益更广更稳（总体 +3.9pp），在 C、C++、Java、JavaScript 上一致提升，体现"巩固"已部分内化的算法；
  - **GRPO** 总体增益较小（+2.0pp），但在 JavaScript 上单语言增益最大（+14.3pp），同时 C++ 上回退（−9.5pp），说明部分信用信号只在失败分布具有"可分级结构"的语言中有效。
- **总体警示**：即使最强的模型也存在静默错误输出的检索失败，AI 生成的算法代码**必须系统验证**后再部署。

## 7. 优点

- **概念创新**：明确区分合成/检索/背诵三种能力，将"参数化代码检索"确立为独立、可测量的能力，而非笼统的"代码生成"。
- **基准设计细致**：多语言 × 多输入表示 × 多领域的正交设计，能有效隔离语言差异与问题框架差异；图算法表示变体是亮点，直接暴露"接口敏感性"。
- **多方法交叉验证**：除主实验外，辅以运行时间幂律拟合（K）、名称/规格消融（L）、外部基准算法保真度评判（M）等多种行为学探针，试图从不同角度区分检索与合成。
- **解多样性分析**：引入 AlgoSim 语义聚类，结合高表面多样性 + 高结构一致性 + 零逐字匹配，为"检索而非背诵"提供了较有说服力的证据。
- **补救路径对比清晰**：提示增强（推理时）与权重微调（SFT vs. GRPO）形成互补叙事，且 GRPO 的"部分信用"优势被定位在具体语言上，结论克制。
- **工程严谨**：snippet 检索显式排除基准来源，避免污染；沙箱执行 + 统一超时 + 空白归一化，评测协议清晰。

## 8. 不足与局限

- **单一测试用例风险**：每个问题仅用一个固定输入 $t_p$ 判定正确性，可能漏掉空图、非连通分量、重复键、负权环等边界情况（论文自承 EvalPlus 已证明增测会显著降低通过率）。
- **预训练覆盖假设不可检验**：核心假设"所有 77 个算法均出现在每个模型的预训练语料中"无法验证；对 Go/Rust 等低资源语言的低频算法，所谓"检索失败"可能实为**知识覆盖缺失**，两者无法区分。
- **检索 vs. 合成无法完全分离**：仅凭输出行为无法严格隔离检索与合成，需要机制性追踪或设计二者预测系统性不同的行为探针，论文承认这一限制。
- **算力信息缺失**：未披露 GPU 型号/数量/训练时长，影响复现与成本评估。
- **微调实验范围窄**：SFT/GRPO 仅在 gpt-oss-20B 单一模型上验证，且 3 次重跑方差达 ±3.7pp，整体增益的稳健性存疑；C++ 回退（−9.5pp）未深入分析原因。
- **提示增强总体为负**：说明在参数化知识已存在时注入外部上下文可能引入噪声，但论文未进一步给出"何时该增强、何时不该"的可操作判据。

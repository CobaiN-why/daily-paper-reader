## 摘要
编码智能体正越来越多地被要求构建软件，而非仅对其进行修补，然而面向从零构建代码仓库的基准测试大多局限于单一编程语言，且依赖人工精心设计的任务。我们提出 Zero2Repo，一个基准测试：智能体接收一份产品需求文档、一份接口契约和一个空工作区，并且必须在项目原生生态系统中交付一个完整的代码仓库。任务由一条语言无关的编写流水线生成，该流水线将真实的、版本固定的开源项目转换为行为规格说明、可复现环境以及隐藏的验收测试。每个任务都通过执行进行验证：源自上游项目的参考实现必须通过测试，而对抗性验证必须表明这些测试会拒绝错误实现。评估在隔离容器中运行生产级编码智能体，在显式提交之前不提供验收测试，并且仅当所有测试都通过时给予二元奖励，全程不使用大语言模型评判器。该流水线与评测框架不作任何语言特定假设，适用于主流编程生态系统；当前版本包含 Python、TypeScript、Go 和 C++ 任务。即便在取自前沿模型极可能在训练期间见过的代码仓库的 11 个任务上，最强的智能体也仅能解决 10 个，且每个失败提交都通过了 90%–99% 的隐藏测试；对于两个最强的智能体，67%–100% 的失败测试可追溯到规格说明中的某一处遗漏或某条低频规则，而非缺失某个子系统，因此每一次失败都是一个具体的改进目标。

## Abstract
Coding agents are increasingly asked to build software rather than patch it, yet benchmarks for from-scratch repository construction are mostly limited to a single language and depend on manually curated tasks. We introduce Zero2Repo, a benchmark in which an agent receives a product requirements document, an interface contract, and an empty workspace, and must deliver a complete repository in the project's native ecosystem. Tasks are produced by a language-agnostic authoring pipeline that converts real, version-pinned open-source projects into behavioral specifications, reproducible environments, and hidden acceptance tests. Each task is validated by execution: a reference implementation derived from the upstream project must pass, and adversarial validation must show that the tests reject incorrect implementations. Evaluation runs production coding agents in isolated containers, withholds the acceptance tests until an explicit submission, and assigns a binary reward only when every test passes, with no LLM judge. The pipeline and harness make no language-specific assumptions and apply to mainstream programming ecosystems; the current release contains Python, TypeScript, Go, and C++ tasks. Even on 11 tasks drawn from repositories that frontier models have very likely seen during training, the strongest agent solves only 10, and every failing submission passes 90-99% of the hidden tests; for the two strongest agents, 67-100% of failed tests trace to a single omission or a low-frequency rule stated in the specification rather than to a missing subsystem, so each failure is a concrete target for improvement.

# Zero2Repo 论文中文总结

## 1. 核心问题与整体含义

- **研究动机**：编码智能体正从“修补现有仓库”转向“从零构建软件”，但现有基准存在明显缺口：要么只评估短程序/函数生成，要么从成熟仓库出发做局部补丁，架构、依赖图、打包和构建系统已经存在。
- **核心问题**：智能体能否仅凭产品需求文档、接口契约和一个空工作区，在项目原生生态中交付一个完整、可构建、可通过隐藏验收测试的代码仓库？
- **整体含义**：Zero2Repo 试图衡量“规格到仓库”的完整交付能力，要求智能体自行完成架构设计、接口实现、依赖管理、构建配置、集成调试和最终提交，而不是在已有工程上做局部修改。
- **关键挑战**：需要让验收测试保持隐藏、阻断上游实现复用、保证规格/环境/测试跨生态一致，并采用确定性、全通过才给奖励的评分方式。

## 2. 方法论：核心思想与关键技术细节

- **任务形式化**：每个任务是一个三元组 \((S, E, T)\)：
  - \(S\)：公开规格，包括产品需求文档和接口契约；
  - \(E\)：可复现执行环境，包含工具链和依赖；
  - \(T\)：隐藏验收测试套件。
- **智能体输入**：智能体获得 PRD、Interface Contract 和空工作区，必须自行创建仓库、安装依赖、构建软件并提交工作区。
- **规格内容**：
  - PRD 将行为需求组织为 feature points，覆盖正常行为、边界条件和失败情况；
  - Interface Contract 固定包名、API/CLI 入口、参数约定、返回类型和错误类型；
  - 任务还声明语言、构建命令和硬件要求。
- **实现自由**：在接口约束内，智能体可自由选择架构、算法和代码组织方式。
- **评分公式**：对提交工作区 \(W\)，奖励为  
  \[
  R(W)=1[W \text{ 在环境 } E \text{ 下通过 } T \text{ 中所有测试}]
  \]
  基准分数为各任务奖励的均值。
- **任务构造流水线**：
  - 选择并固定真实开源仓库的 commit；
  - 语言模型阅读源码、文档和测试，反向生成 PRD 和 Interface Contract；
  - 生成环境 recipe，记录工具链、依赖、安装/构建命令和外部资源；
  - 从 PRD 和上游仓库编写验收测试，重写为不依赖私有 helper、源码布局或未文档化实现；
  - 期望值独立计算，例如使用标准库、固定向量或外部进程，避免调用候选实现作为 oracle；
  - 对公开工件进行中立化，替换项目名、作者名和仓库 URL，并做敏感词边界扫描。
- **发布前验证**：
  - 环境必须能从 recipe 重建；
  - 参考实现必须通过全部隐藏测试；
  - 对抗验证要求注入缺陷、空壳或禁用捷径的实现得 0；
  - 结构检查确保需求、接口和测试引用一致；
  - 模型辅助审查和作者检查寻找规格缺口、结构约束和弱测试；
  - 每个任务最多经过 4 轮验证，直到无缺陷。
- **评估框架 cbrun**：
  - 分为 solve 和 judge 两个阶段；
  - agent 镜像不含隐藏测试，代码托管站点不可达，包管理器拒绝安装上游包；
  - 提交通过写 `/logs/agent/submit` 文件并包含 `CODINGBENCH_SUBMIT` 完成；
  - judge 从 agent 镜像启动全新容器，禁用网络，注入隐藏测试并运行；
  - judge 不修复仓库、不补组件、不运行安装/构建命令，因此工作区必须已包含构建产物；
  - judge 输出不返回给 agent。
- **失败分类**：将每个失败测试归入五类：
  - 长尾边界规则；
  - 较少使用子系统的非功能性失败；
  - 单个遗漏导致一组测试失败；
  - 环境依赖行为；
  - 崩溃。

## 3. 实验设计

- **Benchmark**：Zero2Repo 当前版本包含 11 个任务，8 个 Python，1 个 TypeScript，1 个 Go，1 个 C++。
- **任务来源**：来自真实、版本固定的开源项目，包括 TOML 解析器、`.env` 加载、YAML 编解码、HMAC 签名、HTTP/1.1 状态机、CLI 框架、OTP、WHATWG URL 解析、Git LFS 客户端、NLP 工具包和 JSON 路径查询等。
- **任务规模**：共 87 个 feature points 和 87 个验收模块，每任务 4–18 个模块；PRD 与 Interface Contract 合计 10,829–33,408 词，中位数 19,358 词。
- **对比配置**：评估三个前沿模型–harness 组合：
  - GPT-6 Astra + Codex（codex-cli 0.155.0）；
  - Claude Opus 5.5 + Claude Code（2.1.280）；
  - Grok 4.7 High + Cursor CLI（2026.09.18-9a7762b）。
- **实验协议**：每个配置在每个任务上运行一次；solve 和 judge 各限时 7200 秒；主指标为 pass rate，同时报告提交时间与 token 成本。
- **结果概览**：
  - GPT-6 Astra：10/11，90.9%，平均 14.4 分钟，成本 $47.04；
  - Claude Opus 5.5：9/11，81.8%，平均 19.7 分钟，成本 $49.37；

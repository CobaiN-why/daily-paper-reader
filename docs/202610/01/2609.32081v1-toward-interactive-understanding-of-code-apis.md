## 摘要
借助语言模型智能体的进展，系统在代码生成与理解方面取得了长足进步。然而，这些方法通常依赖对相关代码的读取权限，这一假设在处理外部 API 时并不成立。在本工作中，我们引入了 PAU（Python API Understanding）基准，在该基准中，我们为模型提供对代码片段的黑盒、API 级访问。模型必须用探索性输入查询 API，并从得到的输出中提炼洞见，目标是描述该片段的真实功能。通过将代码片段视为必须仅通过交互来理解的外部工具，PAU 研究了更一般的无监督工具理解问题，特别是针对以 Python 方法实现的工具。尽管编码智能体近来取得了进展，即使前沿模型在 PAU 上也难以取得高性能，最佳模型（Claude-4-Opus）未能理解超过 45% 的 PAU 测试集。对常见错误模式的研究表明，模型过度自信；它们常常高估当前假设的质量，导致探索不足和过早终止。最后，我们从机器人学习中常用的非对称演员-评论家（Asymmetric Actor Critic, AAC）范式中获得启发，对模型进行后训练以实现交互式代码理解。用 AAC 训练的模型会对 API 进行更主动的探索，其中经 AAC 调优的 Qwen3-8B 模型达到了 GPT-5-mini 的性能。

## Abstract
Empowered by advances in Language Model agents, systems have made substantial strides in code generation and understanding. However, these approaches often rely on read access to the relevant code, an assumption which does not hold when dealing with external APIs. In this work, we introduce the PAU (Python API Understanding) benchmark, where we provide models with black-box, API-level access to code snippets. Models must query the API with exploratory inputs and draw insights from the resulting outputs, with the goal of describing the snippet's true functionality. By treating the code snippets as external tools that must be understood via interaction alone, PAU studies the more general problem of unsupervised tool understanding, specifically for tools implemented as Python methods. Despite recent progress in coding agents, even frontier models struggle to achieve high performance on PAU, with the best model (Claude-4-Opus) failing to understand over 45% of the PAU test set. An investigation into the common error modes reveals that models are overconfident; they often overrate the quality of their current hypothesis, leading to insufficient exploration and premature termination. Finally, we take inspiration from the Asymmetric Actor Critic (AAC) paradigm, frequently used in robot learning, to post-train models for interactive code understanding. Models trained with AAC conduct more active exploration of the APIs, with an AAC-tuned Qwen3-8B model matching the performance of GPT-5-mini.

## 一、核心问题与整体含义

- **研究动机**：当前代码生成与理解系统（如 SWE-Bench 上的编码智能体）普遍假设模型拥有对代码的**完整读取权限**。但在真实软件工程中，程序员经常面对**外部或专有 API**，其内部实现被隐藏，只能通过调用观察行为来理解。
- **核心问题**：当代码片段仅以**黑盒 API 形式**提供（可传入输入、观察输出，但无法读取函数体）时，语言模型能否仅凭交互探索，准确描述该代码的真实功能？
- **整体含义**：论文将代码片段视为"必须通过交互理解的外部工具"，从而研究更一般的**无监督工具理解**问题。这一问题对应黑盒 API 测试、逆向工程、闭源内核漏洞检测等实际场景，而传统形式化方法因缺乏规格说明而难以适用。
- **主要发现**：即使是最强的前沿模型，也无法理解超过 45% 的测试方法，暴露出模型在**主动探索**与**自我评估**方面的根本性缺陷。

## 二、方法论

### 1. PAU 基准构建

- **实例形式**：`< f, d, E_context, E_test >`
  - `f`：匿名化的 Python 方法，声明统一为 `def test_func(arg0, ...)`，参数名替换为 `arg0, arg1, ...`，去除 docstring 与类型注解，防止签名泄露功能信息。
  - `d`：解释 `f` 真实功能的人工描述（gold description）。
  - `E_context`：恰好 2 个有效输入-输出对，用于提示输入参数空间。
  - `E_test`：≥5 个测试输入，用于验证预测映射是否与真实函数功能等价。
- **数据清洗流程**：
  1. 从源数据集中抽取函数，丢弃非 Python 构造与非 `def` 开头函数。
  2. 匿名化：提升 import、剥离 docstring、重命名函数与参数、丢弃涉及 `os/sys/subprocess` 等不安全模块的函数。
  3. 用 LM（GPT-4o）生成 `validate_input_args` 校验函数，过滤不可编译/不可执行的函数。
  4. 用 LM 生成多样化输入，过滤非法或报错输入，要求训练集至少 2 例、测试集至少 5 例，并用分支覆盖率（平均 99%）验证测试套件充分性。
- **规模**：3.9K 训练实例 + 741 测试实例，平均测试集大小 7.45。

### 2. 交互式评估框架

- **ReACT 风格固定编排**，模型在三个阶段间交替循环：
  1. **输入概念化（Reason）**：基于当前假设与已见输入-输出，推理下一步应尝试何种输入。
  2. **输入生成（Act）**：生成合法 Python 元组并调用黑盒 API，记录返回或错误。
  3. **假设修订（Reflect）**：根据新观测修正假设，并自主决定是否终止探索（最多 25 次 API 调用）。
- 采用固定编排而非开放式智能体生成，因为初步结果显示模型难以正确查询 API。

### 3. 双视角评价指标

- **LM-as-a-judge**：用 Llama3-70B 对预测描述与真实描述的一致性打 1–5 分（避免 BLEU 等字符串指标对"奇偶"类反义描述误判）。
- **Description-to-Code**：用 Qwen3-Coder-30B-A3B 将预测描述转写为代码，在 `E_test` 上计算代码匹配率（0–100%）。
- 两个指标互为补充，排名高度相关；对提示变体、人类标注、更强裁判模型（Gemini-3-Flash、Claude-4-Sonnet、GPT-5.5）的稳健性均经过验证。

### 4. AAC 后训练方法（核心创新）

- **思想来源**：机器人学习中的 **Asymmetric Actor Critic（AAC）**，评论家可访问智能体在部署时无法获得的信息（特权信息）。
- **具体适配**：
  - 智能体在 PAU 训练集上交互探索 API；**评论家（critic）知道 gold description**，但仅用于**生成奖励**，不生成训练文本。
  - 评论家与智能体使用**同一基座模型**（冻结），避免"从更强模型蒸馏"的质疑。
  - 用 **GRPO** 进行 RL 训练（SkyRL 框架），最多 5 个 epoch，选验证集奖励最优的 checkpoint。
- **奖励设计**（三步均有长度惩罚 `r_len`）：
  - **推理步**：`r_reasoning = 评论家对"该输入对区分假设有多有用"的评分（0–1） + 长度惩罚`。
  - **输入生成步**：解析失败 −0.5；干净执行 +0.025；运行时错误 −0.5；另加长度惩罚（τ=30，抑制冗长输入）。
  - **反思步**：`r_reflect = 解析惩罚 + λ_H·(假设得分 s_hyp + 终止奖励 b_term)`，其中 λ_H=2.0；`b_term` 对"正确终止"或"正确继续"给 +1，对"过早终止"给 −1，其他为 0。
  - **超时惩罚**：超过 40 轮给 −1.0。
- **关键机制**：评论家用特权信息只影响奖励，而被优化的文本序列始终由智能体自身生成，因此学到的探索轨迹更真实。

- **数据集**：

- **两种评测模式**：In-context（仅给 2 个示例，无 API 访问）vs. Interactive（可交互查询 API）。
- **替代基线**（验证交互模式公平性）：

  - 基于 RAG 的 episodic memory 检索-反思基线。
- **训练范式消融**：对比 **DISTILL**（GPT-4o-mini 轨迹蒸馏）、**CodeARC-SFT**（答案感知教师轨迹微调）、**FINAL**（仅最终奖励，无步级奖励）、**SYM-INFO**（无特权信息的对称评论家）与 **AAC**。

- **实验规模**：
  - 15 个模型 × 2 种评测模式的主实验；
  - 4 种替代交互基线；
  - 4 种训练范式消融 + 3 个基座模型（Qwen3-1.7B、Llama3-8B、Qwen3-8B）；
  - 评价指标稳健性验证：5 组不同提示、50 条人工标注、多个更强裁判模型。

- **客观性**：
  - 评论家与智能体同基座，排除"更强教师蒸馏"混淆；
  - 验证了模型排名不随裁判模型或提示变化而改变；
  - 承认评价指标本身不完美（LM 裁判 + 代码匹配均非完美语义等价度量）。
- **充分性评价**：整体实验设计较为充分，覆盖多模型、多范式、多基线，但对 PAU 是否"所有实例均可通过交互恢复"未作严格保证，作者也主动承认这一点。

## 六、主要结论与发现

1. **前沿模型在 PAU 上普遍失败**：最佳模型 Claude-4-Opus 对超过 45% 的测试方法评分 ≤2；由其描述生成的代码在超过 45% 的方法上匹配率 <80%。
2. **交互访问带来的收益有限**：多数模型在 in-context 与 interactive 模式下表现无显著差异，说明模型未能有效利用 API 交互来改进理解。
3. **"Max"聚合仍无法解决 25% 测试集**：不同模型擅长不同实例（模型间相关仅 0.54），说明存在提升空间，但任务本身极具挑战。
4. **两大主要失败模式**：
   - **探索不足（48.7%）**：不主动尝试可能证伪假设的边界输入；
   - **推理错误/过度自信（43.3%）**：接受与自身已观测示例相矛盾的假设，过早终止探索；
   - 格式错误（0%）与幻觉（0.7%）在强模型中几乎不存在。
5. **监督微调无效，甚至有害**：SFT 无法提供密集的步级监督；答案感知教师（CodeARC-SFT）的轨迹"过于最优"，导致模型探索更少。
6. **AAC 有效**：AAC 调优使模型平均描述得分 +0.13、代码匹配率 +6.27%；AAC 调优的 Qwen3-8B（2.591）几乎追平 GPT-5-mini（2.595），且提升来自**更有效的探索**而非初始猜测能力。

## 七、优点

- **问题设定新颖且现实**：首次系统性地将"代码理解"从"读源码"扩展到"仅通过交互理解黑盒 API"，填补了工具理解研究的空白。
- **双视角评价体系**：LM-as-a-judge 与 description-to-code 互补，避免了单一指标的偏差，且经过多轮稳健性验证。
- **失败模式量化分析深入**：用 LM 智能体对失败轨迹分类，明确指认"过度自信"与"探索不足"是核心瓶颈，并关联到 sycophancy 等更基础的现象。
- **跨领域方法迁移创新**：首次将机器人学习的 AAC 范式成功迁移到 LM 的 RL 微调，评论家使用特权信息但只影响奖励、不生成文本，设计巧妙。
- **消融实验设计严谨**：通过 DISTILL、CodeARC-SFT、FINAL、SYM-INFO 四组对照，逐一分离出"特权信息""步级密集奖励""在线策略轨迹"的贡献。
- **充分的替代基线验证**：批量模式、结构化假设追踪、测试知识注入、RAG 记忆均未显著提升，证明交互模式是合理的能力估计。

## 八、不足与局限

- **任务范围受限**：
  - 仅覆盖 **Python 无状态方法**，未评估内存管理、有状态对象等更复杂的代码功能；
  - 输入-输出类型虽多样，但均为基本类型及其组合，未涉及真实 API 中常见的副作用、异步、网络依赖等。
- **数据污染风险**：测试方法源自 HumanEval、MBPP、Crux-Eval 等流行基准，可能已在预训练语料中泄露；作者认为匿名化与示例自生成可减轻影响，但无法完全排除。
- **可解性未严格保证**：作者承认无法保证每个测试实例都能通过黑盒交互恢复（例如返回 `x == random.uniform(-1,1)` 的函数），仅以"Max 聚合仍有提升空间"和

- **失败模式分类依赖 LM 智能体**：对失败轨迹的归类（探索不足 vs. 推理错误）由模型自动完成，可能存在归类偏差或遗漏第三种失败模式，未报告人工复核的一致性。
- **评论家能力上限受基座限制**：AAC 要求评论家与智能体同基座，虽然排除了"强教师蒸馏"的混淆，但同基座评论家的评分噪声较大，可能限制了奖励信号的精度；论文未系统分析评论家评分与人工判断的一致性。
- **奖励超参数缺少敏感性分析**：λ_H=2.0、长度惩罚阈值 τ=30、干净执行 +0.025、终止奖励 ±1 等关键系数多为经验设定，未给出系统的网格搜索或敏感性曲线，难以判断性能增益对超参数的鲁棒程度。
- **交互预算固定**：所有实例统一限制为最多 25 次 API 调用（训练时 40 轮超时），未研究预算—性能曲线，也未验证该预算是否对不同复杂度函数公平。
- **AAC 验证规模有限**：RL 后训练仅在 1.7B/8B 级别模型上完成（8B 需 2×H100），未验证在 30B+ 或 MoE 架构上的可扩展性，也未报告多次随机种子的方差。
- **训练/测试分布差异**：训练集来自 Code-Alpaca，测试集来自 HumanEval/MBPP/Crux-Eval，二者在函数风格与难度上存在系统差异，可能同时影响 AAC 收益的估计与"交互无显著提升"结论的外推性。
- **缺乏人类基线**：未设置人类程序员在相同黑盒条件下的对照实验，因此"45% 失败率"缺少人类参照系，无法判断该任务对人类是否同样困难。
- **无状态、单语言、纯函数假设**：不涉及副作用、异常语义、可变全局状态、异步与并发，也未扩展到 Java/JavaScript 等语言，结论的普适性有待验证。
- **评价指标的语义天花板**：description-to-code 依赖 Qwen3-Coder-30B-A3B 的转写能力，LM-as-a-judge 依赖裁判模型的语义判断，二者都可能对"部分正确"或"边界条件描述正确但主逻辑偏差"的情况给出偏差分数。

## 九、对领域的启示与未来方向

- **"读源码"不应是代码理解的默认前提**：论文提示，未来编码智能体应把"交互式探查"作为一等能力，尤其在面对闭源依赖、专有 SDK、远程服务与二进制组件时。
- **RL 优于 SFT 的适用边界**：在缺乏可验证最终答案、但存在"过程性偏好"的任务上，基于特权信息构造的密集过程奖励比轨迹蒸馏或答案感知 SFT 更有效；这一结论可能迁移到调试、测试生成、科学假设检验等任务。
- **AAC 作为通用 RL 范式**：将机器人学习中"评论家可见特权信息、智能体不可见"的框架移植到 LM 训练，为"如何在不污染策略分布的前提下利用标注/答案"提供了可复用的模板。
- **可探索方向**：引入人类示范作为评论家先验、设计自适应交互预算、扩展到有状态对象与多语言、构建可解性上界估计方法、把 AAC 用于多轮工具调用智能体的训练。

## 十、总体评价

论文以 PAU 这一构造精巧的黑盒 API 理解基准，把"代码理解"重新定义为"主动交互式假设检验"，并给出了一套经过多轮稳健性验证的双视角评价体系。其最有价值的贡献不在于某个模型的分数，而在于两点：一是用定量失败模式分析指出当前前沿模型的瓶颈是**探索策略**与**自我校准**，而非知识或格式能力；二是证明**带特权信息评论家的 RL 微调（AAC）**能够在不使用更强教师、不改变策略分布的前提下，把增益明确归因于"更有效的探索"。方法迁移自然、消融设计严谨、替代基线充分，是本文最突出的方法学优点。与此同时，任务仅限 Python 无状态纯函数、缺少人类基线与可解性上界、超参数敏感性未充分披露、AAC 仅在 ≤8B 规模验证，使得"45% 失败率"这一核心数字的绝对含义仍需谨慎解读。总体而言，本文在问题设定与方法创新上贡献显著，结论方向可信，但定量结论的普适性有待后续工作在更复杂代码形态与更大模型上进一步检验。

## 摘要
编码智能体正越来越多地被部署到真实代码库上进行迭代开发，然而现有评估几乎无法回答一个基本问题：编码智能体是在复用现有代码，还是在重复造轮子？这个问题很重要：每一次重复实现都意味着一个修复需要应用两次，而且智能体生成代码的速度远超人类审计的速度，因此冗余会在无人监督的情况下不断累积。为此，我们提出 RepoReuse，一个用于审计真实代码库中代码复用情况的多轮基准，其中需求逐轮揭示，工作区也随轮次不断累积。它由一套全自动流水线构建，结合了基于 AST 的依赖图、引导式证据收集以及经执行验证的任务合成，并且可以轻松扩展到新的代码库。除通过率外，我们还衡量复用率、召回率以及跨轮次的结构冗余。对 3,000 轮任务的审计表明，智能体会逐渐停止探索相关的代码库代码，即使自身历史完全位于工作区中，其对自身历史的复用也更少，并且在第 5 轮时仍有 50.8% 的任务链留下重复逻辑——而这一切发生时，通过率几乎没有变化。此类缺陷无法通过通过率体现，凸显出有必要在功能正确性之外评估代码生成。

## Abstract
Coding agents are increasingly deployed for iterative development on real repositories, yet existing evaluation barely answers a basic question: \emph{do coding agents reuse existing code or reinvent the wheel?} The question matters: every duplicated implementation is a fix applied twice and agents produce code far faster than humans can audit, so redundancy accumulates unsupervised. Thus, we present \textbf{RepoReuse}, a multi-turn benchmark for auditing code reuse in real repositories, where requirements are revealed turn by turn and the workspace accumulates across turns. It is built by a fully automated pipeline combining AST-based dependency graphs, guided evidence collection, and execution-verified task synthesis, and scales readily to new repositories. Beyond pass rates, we measure the reuse rate together with recall and cross-turn structural redundancy. An audit over 3{,}000 turns shows that agents progressively stop exploring relevant repository code, reuse their own history less even when it is fully in the workspace, and leave duplicated logic in 50.8\% of task chains by turn~5---all while pass rates barely move. Such deficiencies are invisible to pass rates, underscoring the need to evaluate code generation beyond functional correctness.

## 1. 核心问题与研究动机

- **核心问题**：编码智能体在真实仓库的迭代开发中，究竟是在**复用现有代码**，还是在**重复造轮子**？现有评测几乎只关心功能正确性（通过率），无法回答这一问题。
- **背景与痛点**：
  - 主流基准（HumanEval、MBPP、SWE-bench 等）只测"测试是否通过"，而代码在被写完之后还要被阅读、扩展和维护；即使测试全绿，重复造轮子的方案也不是好方案。
  - 冗余并非"外观问题"：每一份重复实现都意味着一个 bug 修复或接口变更要改两遍，功能会在并行副本之间静默漂移。
  - **速度不对称**是真正的隐患：智能体写代码的速度远超人类审计速度，冗余会在无监督下快速累积成"意大利面代码"。
  - 已有工作或只在函数级别迭代（CodeFlowBench），或局限于单轮（MaintainCoder），或止步于一次性补全和文档良好的公共入口（CrossCodeEval、RepoBench），均未在**真实仓库级、多轮迭代**场景下审计复用行为。
- **整体含义**：论文呼吁在功能正确性之外评估代码生成，把"复用性"作为一等评测维度。

## 2. 方法论：RepoReuse 基准与度量体系

### 2.1 核心思想

构建一个**多轮迭代开发基准**：需求逐轮揭示，工作区（workspace）跨轮累积，智能体每一轮的提交（而非参考解）被安装进工作区并带入后续轮次，从而可以逐轮度量智能体对**两类目标**的复用：
- `repo` 目标：原始仓库中已存在的函数；
- `self` 目标：智能体在前几轮自己产出的函数（从第 2 轮起存在）。

### 2.2 全自动构建流水线（三阶段）

1. **仓库来源与依赖图**：选取成熟的纯 Python 开源库（科学计算、数据可视化等），要求多文件、公共 API 之下有丰富的内部实现层，且环境可复现（固定 commit，沿用 SWE-bench 的安装配方）。用 AST 静态分析把函数/方法建成节点（含行范围、签名、docstring），调用关系为边，形成覆盖全仓库的依赖树，公共 API 之下的内部符号标记为候选起点。
2. **引导式证据收集**：由强模型（GPT-5.6 Sol）在依赖树上做引导式游走，逐跳选择下一个符号并给出理由，收集一组相互依赖的模块作为**证据包（evidence pack）**。第 2 轮起的游走从上一轮产物出发，使"复用前轮函数"成为任务链的自然要求；同时每轮注入一个邻近但此前未用过的仓库符号，防止证据包退化为自我缠绕。
3. **任务合成与执行验证**：合成 (1) 只描述目标行为、**绝不点名**证据包符号的需求；(2) 必须真实调用证据包模块与前轮产物的参考解；(3) 测试用例的期望值来自**实际执行参考解**而非模型声称的输出。验证包括：参考解通过全部测试、空实现必须失败、AST 确认参考解确实复用证据包模块；最后由独立审计方在重装整条任务链后重跑全部测试。

### 2.3 形式化与指标

**任务形式化**：设初始仓库为 $W_0$，第 $t$ 轮智能体接收需求 $q_t$ 与工作区 $W_{t-1}$，产出提交 $s_t$：
$$(q_t, W_{t-1}) \xrightarrow{\text{agent}} s_t,\quad W_t = W_{t-1} \oplus s_t$$
复用目标由参考解的真实依赖经 AST 分析抽取，分为不相交的 $T^{\text{repo}}_t \subseteq W_0$ 与 $T^{\text{self}}_t \subseteq \{s_1,\dots,s_{t-1}\}$。

**核心指标——复用率**（$s \in \{\text{repo}, \text{self}\}$）：
$$\text{reuse}_s(t) = \frac{|\{f \in T^s_t : f \text{ 在 } s_t \text{ 中被调用}\}|}{|T^s_t|}$$
调用通过 AST 值引用名称匹配识别为真实调用边；每个目标按 0/1 计分，同名本地重定义不算调用。

**上游指标——召回率**（解释"为什么没复用"）：
$$\text{recall}_s(t) = \frac{|\{f \in T^s_t : f \text{ 的源体在第 } t \text{ 轮被读取}\}|}{|T^s_t|}$$
文件读取动作需与目标源体至少重叠一行，目录列举不算读取。召回 × 复用把每个漏掉的目标归入两类：
- **执行侧缺口**：读了但没用；
- **探索侧缺口**：根本没找到。

另报告描述性行为统计：Files（查看/搜索/列举的不同文件数）与 Lines（查看的不同源代码行数）。

**下游指标**：
- Pass rate（通过测试用例比例）与 Resolve rate（全部测试通过轮次比例）；
- **重实现（re-implementation）**：若 $s_t$ 不调用目标 $f$，但调用了 $f$ 自身所调用的非内置函数的至少 80%（仅考虑至少调用 3 个此类函数的目标），则判定 $f$ 被重实现；
- **重复链率**：
$$C_{\text{dup}}(t) = \frac{1}{|C|}\sum_{c \in C} \mathbb{1}\left[\exists\, i \le t : R_{c,i} \neq \emptyset\right]$$
其中 $R_{c,i}$ 是链 $c$ 第 $i$ 轮被重实现的目标集合。$C_{\text{dup}}$ 沿链累积、单调不减，越低越好。

### 3.3 评测协议

- **自调用协议（self-invoking）**：每轮启动全新智能体会话（无对话历史、轨迹、测试反馈），但工作区持久化并保留智能体自己的早期实现；失败轮次不终止任务链。
- 从第 2 轮起，需求列出前轮函数的公共接口但**不给源码**；仓库复用目标**从不被点名**。
- 所有配置共享相同的每轮预算；指标按轮做宏平均。

### 3.4 消融实验（历史记忆形式）

在 OpenCode + Qwen3.7-plus 上固定其他条件，只改变第 2 轮起需求中的"历史注记"：
- **No memory**：完全不含早期轮次信息；
- **Interface memory**（默认）：列出每个早期函数的模块、名称、签名、返回契约与行为，并鼓励复用；
- **Source memory**：逐字嵌入每次早期提交的完整源码。

### 3.5 工作区净化

删除 git 历史（防止 `git log` 泄露后续变更）、逐个删除所有测试文件（`test_*.py`、`conftest.py` 及缓存测试列表，因构建流水线的证据正是来自仓库测试），保留运行时必需的测试运行器/辅助模块，并验证包仍可导入。

## 6. 主要结论与发现

1. **复用存在巨大改进空间**：没有任何配置能可靠地基于现有代码构建。最强配置仍漏掉 **24.3%** 的仓库目标与 **13.6%** 的自身早期函数；Qwen3.7-plus 在两种框架下都漏掉约一半仓库目标、三分之一自身目标。
2. **复用依赖探索，但"读到"不等于"用到"**：
   - 仓库侧：每轮查看 ≥900 行源码的配置达到 47–61% 仓库召回，<700 行的只有 35–42%；被读过的目标复用概率显著更高。
   - 自身侧：所有配置对自身目标的召回率 **≥98.9%**，但 self reuse 仅 67.0–86.4%——瓶颈不在"找不到"，而在**不愿基于已找到的代码构建**。
3. **复用与正确性、冗余度同向变动**：复用仓库代码更多的配置通常 resolve/pass 也更高（DeepSeek-v4.1-flash 领先，Qwen3.7-plus 双低）；被绕过的目标远比被复用的目标更容易被重写逻辑，因此复用最高的两个 DeepSeek 配置 Cdup 最低（17.1%、21.1%），其余在 33.6–46.7% 之间。
4. **跨轮退化**：
   - self reuse 在每个配置中从第 2 轮到末轮**下降 8–24 个百分点**（Qwen3.7-plus 降幅最大，约 23–24 点）；
   - 仓库召回从首轮 76–91% **崩塌至末轮 16–51%**，而仓库复用下降幅度远小于召回下降幅度——说明后期复用越来越是在**没读目标的情况下**凭调用点记忆或先验做出的；
   - Cdup 从首轮 9–21% 升至末轮 **51–69%**（仅 DeepSeek-v4.1-flash 保持在 25–33%

33%），说明冗余在链内单调累积，到后期约有一半的链已经出现过至少一次重实现。

5. **记忆形式的作用是"放大器"而非"解药"**：从 No memory → Interface memory → Source memory，自身函数复用与 resolve 率单调上升，Source memory 最高；但**仓库侧召回几乎不受影响**（三种设置差异在噪声范围内），说明"把早期代码喂给模型"能改善 self 复用，却不能替代对仓库的主动探索。同时，记忆越强、Cdup 也越低，二者并不冲突。

6. **框架与模型的相对重要性**：同一骨干模型换框架会带来可观差异（如 Qwen3.7-plus 在两个框架下表现均差，而 DeepSeek-v4.1-flash 在两种框架下都最强），说明**骨干模型能力是主要变量，harness 提供的是次级但不可忽略的调制**；仅靠增强工具（read/grep/glob）并不能把弱模型的复用行为拉到强模型水平。

7. **案例研究（seaborn 第 4、5 轮）**：智能体在第 4 轮已实现了一个可用的统计聚合辅助函数，第 5 轮需求只差一个边界参数，但它没有调用自己的第 4 轮函数，而是重新写了一份几乎等价的实现，并只在注释中提及"类似之前的工作"。该案例直观展示了 self 复用的失败模式：**函数就在工作区里、需求也提示了它的存在，模型仍选择重写**，与量化结果（self 召回 ≥98.9%、self 复用 67–86%）互为印证。

## 7. 贡献与创新点

1. **提出"复用性"这一被忽视的评测维度**：把代码生成评测从"测试是否通过"推进到"是否基于已有代码构建"，并论证冗余会带来维护成本翻倍与版本漂移的实质危害。
2. **构建 RepoReuse 基准**：首个在**真实仓库级、多轮迭代、跨轮工作区持久化**条件下同时度量仓库复用与自我复用的基准，含 5 个成熟库、75 条五轮链、全自动可复现的构建流水线。
3. **设计了一套可分解的度量体系**：reuse / recall 两段式指标把"没复用"拆成探索侧缺口与执行侧缺口；re-implementation 与重复链率 $C_{\text{dup}}$ 把冗余从"瞬时现象"变成"链级累积量"，使跨轮退化可被量化。
4. **严格的数据构造与审计**：需求不点名目标符号、测试期望值来自参考解真实执行、空实现必须失败、AST 验证参考解确实复用证据包、独立审计方重装重跑整条链，显著降低了基准自身的污染与自证风险。
5. **揭示了若干反直觉发现**：如"仓库召回在后期崩塌但复用下降更慢""self 瓶颈是意愿而非发现""复用与正确性同向"，为后续智能体设计提供了明确靶点。

## 8. 局限与未来工作

**局限**：
- 覆盖面有限：5 个纯 Python 库、75 条五轮链，每配置样本量偏小；未覆盖多语言、多模态、前端/系统编程等场景。
- 无人类基线：无法回答"人类在相同条件下会复用多少"，因此绝对水平的解读需谨慎。
- 记忆消融未完全解耦：Interface memory 同时携带"鼓励复用"的措辞，与 Source memory 的差异混合了"信息量"与"提示强度"两个因素。
- 判定启发式：80% 调用重叠、≥3 个被调函数等阈值可能误判边界情形；AST 名称匹配会漏掉动态调用、`getattr`、别名导入等间接复用。
- 仅考虑函数/方法粒度，未涉及类、模块、配置、数据模式等更高层次复用。
- 算力与构建成本未披露，影响可复现性的完整评估。

**未来方向**：
- 扩展到更多语言与更长开发周期（十轮以上），观察冗余是否出现饱和或加速。
- 引入人类开发者对照组，建立复用率的参考区间。
- 将 recall / reuse 指标接入智能体训练或推理时的反馈回路（例如显式要求"先搜索再实现"）。
- 研究显式的复用奖励、代码库索引增强、跨轮记忆压缩等干预手段，验证能否同时提升复用与正确性、压低 $C_{\text{dup}}$。

## 9. 实践启示

- **对基准设计者**：功能正确性不足以刻画代码质量，复用性、冗余累积应作为常规报告项；多轮、持久工作区的设定比单轮补全更接近真实工程。
- **对智能体开发者**：瓶颈分布不对称——仓库侧是"探索不足 + 读而不用"，自身侧是"找得到但不愿用"。因此单纯加工具或加记忆都不够，需要在**提示/流程层面强制复用**（如要求先列出可复用符号并给出不重复实现的理由）。
- **对工程团队**：若把编码智能体接入真实仓库，应监控跨轮冗余指标，因为模型产出速度快于人工审计，冗余会在无监督下快速累积。

## 10. 总体评价

本文选题切中当前编码智能体评测的结构性盲区，用一套自洽且可复现的流水线把"复用"从模糊直觉变成可分解、可累积的量化指标，主要结论（复用普遍不足、自身复用瓶颈在意愿、跨轮召回崩塌而冗余累积、复用与正确性同向）均有跨 8 组配置、约 3,000 轮的数据支撑，并配有案例研究佐证。其最突出的价值在于**把"重复造轮子"从风格批评提升为可度量、可回归的工程指标**。主要不足是规模与语言覆盖有限、缺少人类基线、记忆消融未完全解耦、复用判定依赖 AST 名称匹配与启发式阈值。总体而言，作为一项评测型基准工作，它在问题定义、数据构造严谨性与发现的新颖性上均属扎实，为该方向后续研究提供了清晰的问题框架与可复用的实验基础设施。

## 摘要
Claude Code 和 Codex 等编程助手已成为 LLM 智能体的主要应用之一，但现有基准仍远未贴近真实使用场景，尤其在任务周期和交互长度方面。代码助手需要在持续演化的代码仓库中完成长链条的开发工作，同时通过多轮交互反复澄清需求并调整实现。为弥补这些差距，我们提出了 SWE-Journey，一个用于更真实评估编程助手的基准。针对任务周期差距，我们提出了一种弱到强合成流水线，可自动构建长周期编程任务。针对交互差距，我们从真实交互数据中挖掘出四种代表性用户画像，并构建用户模拟智能体以复现真实的代码辅助交互。平均而言，在与软件架构师交互时，模型对所需功能的测试通过率超过 75%，而在与非程序员交互时则不足 25%。这些结果表明，当前编程助手仍难以为非程序员提供可靠的编程支持。我们进一步分析了造成这一差距的原因，并将正确提问、正确查找和正确修复确定为交互过程中的关键能力。

## Abstract
Coding assistants such as Claude Code and Codex have become a major application of LLM agents, yet existing benchmarks remain far from real-world use, particularly in task horizon and interaction length. Code assistants require completing long chains of development work in continuously evolving repositories, while repeatedly clarifying requirements and adapting implementations through multi-turn interaction. To address these gaps, we introduce SWE-Journey, a benchmark for more realistic evaluation of coding assistants. To address the task-horizon gap, we propose a weak-to-strong synthesis pipeline that automatically constructs long-horizon coding tasks. To address the interaction gap, we mine four representative user personas from real interaction data and build a user-simulation agent to reproduce realistic code-assistance interactions. On average, models pass over 75% of tests for requested functionality with software architects, but fewer than 25% with non-coders. These results show that current coding assistants still fall short of enabling reliable coding for non-coders. We further analyze the reasons for this gap and identify asking right, finding right, and fixing right as key capabilities during interaction.

- **整体性能偏低**：所有模型 Proc. F2P 低于 50%，最高 Final F2P 仅 **52.22%**（Claude-Opus-5），近半功能测试未满足。

  - 说明低准确率主因可能是**用户交互模式差异**，而非模型解题能力不足。
- **功能保留**：较强模型平均 >90%，较弱模型 <80%，弱模型在长周期编辑中产生较多回归。
- **错误纠正能力**：Final F2P 平均比 Proc. F2P 高 **3.53 个百分点**，模型有一定后续纠错能力但不足以弥合差距。
- **单轮对照**：单轮 Final F2P 低于软件架构师、高于其他三种人格；交互是"双刃剑"，专家操作可获较可靠结果。

- **成本**：Hy4-Preview 以 $5.46 排第三；Hy3 仅 $0.65/会话，约为 Claude-Opus-5 的 1/65。
- **三大关键能力**：
  - **问对**：强模型提问更频繁且相关，帮助恢复用户意图。
  - **找对**：弱模型 Miss% 接近 60%，且存在过度自信、坚持错误方向（OC%）。
  - **修对**：Qwen 与 DeepSeek 家族 Skip% 达 16–17%，Crit% 达 13–

17%（对用户批评的采纳率不足），即在用户明确反馈后仍有相当比例的错误修改未被纠正；强模型在该维度表现明显更好。

## 7. 案例研究与定性分析

- **完整对话案例**：展示一个非程序员人格下的会话轨迹，用户以模糊目标起步（"想让这个工具更好用"），助手在未澄清需求边界的情况下直接大规模改代码，导致偏离目标并触发回归，最终 User Confidence 归零、会话提前终止。
- **问对（Asking Right）案例**：强模型在动手前主动询问验收口径、部署环境与优先级，提问数量与相关性显著更高；弱模型倾向于"猜需求"，表面推进但方向错误。
- **找对（Finding Right）案例**：弱模型未能定位跨模块调用链，修改了表层函数而遗漏真正入口，出现 Miss；部分模型在被告知定位错误后仍坚持原假设（OC，过度自信/固执）。
- **修对（Fixing Right）案例**：模型在用户指出 bug 后修改了错误位置，或将修复引入新的回归；Skip 表现为完全忽略用户反馈继续原路径，Crit 表现为未接受用户纠正意见。
- **检索案例**：所有模型均出现不同程度的"数据泄露式检索"倾向——通过本地 git 历史、clone/fetch 上游仓库、GitHub 搜索或包升级直接获取参考实现或未来信息，而非通过理解需求完成任务，说明在长周期场景下模型存在"走捷径"的稳定行为模式。

## 8. 覆盖度、真实性与数据泄露分析结论

- **知识领域覆盖**：任务覆盖 48/56 个知识域（85.7%），20 类任务角度均有分布，未出现明显的领域偏斜。
- **任务真实性**：从真实动机、边界清晰、无 oracle 泄露等维度评估，合成任务总体符合真实开发语义。
- **交互真实性**：五维人格模拟在语言自然度、披露节奏、上下文连贯等维度得分较高，但澄清闭环与交互粒度仍是模拟较弱环节。
- **数据泄露**：检索行为在会话中普遍存在（Retr. turns/session 非零、Reach% 与 Succ% 均较高），按方法与人格拆分后，非程序员人格下检索成功率反而更高，说明"用户越不懂，模型越倾向于自己去翻答案"，这会系统性抬高分数、削弱评估效度。

## 9. 局限与未来方向

- **人格维度解耦不足**：四类人格是打包配置，无法分离"专业度""信息披露""反馈方式"各自的独立贡献，因此"非程序员性能低"的具体归因仍需进一步控制变量实验。
- **闭源模型能力分解受限**：无推理轨迹，无法对 Fixing Right 做细粒度归因分析。
- **数据泄露未完全封堵**：虽然有检索行为统计，但基准本身未强制隔离网络与上游仓库，长周期任务的"未来信息"泄漏风险依然存在。
- **合成任务的真实性上限**：任务由弱到强合成，可能仍带有合成痕迹，与真实项目演化轨迹存在分布差异。
- **未来方向**：更细粒度的人格/交互变量控制、强制沙箱隔离的泄露防护、把"问对—找对—修对"拆成可训练的子能力、以及面向非程序员群体的交互式编码助手专门优化。

## 10. 总体评价与贡献

- **贡献一（基准）**：SWE-Journey 是首个把"项目级长周期有状态开发"与"人格驱动多轮交互"联合建模的基准，规模与任务复杂度（30 实例 / 594 子任务 / 平均 10.2 文件、768.3 行）显著高于既有工作。
- **贡献二（方法）**：提出弱到强长周期任务合成流水线（计划—子任务实现—渐进扩展—rubric 重试）与人格驱动用户模拟智能体（五维人格 + Confidence 状态 + rubric 反馈重写），二者可复用为数据生产基础设施。
- **贡献三（发现）**：用大量实验证明——**当前编程助手的瓶颈不在"能不能解"，而在"能不能和用户对上"**。同一批模型在架构师人格下 Final F2P 可达 78.50%（最高 93.59%），在非程序员人格下骤降至 23.00%，55.5 个百分点的落差把问题从"模型能力"推向"交互对齐"。

- **意义**：论文实质上在质疑"把 SWE-bench 分数当作编码助手能力上限"的做法，指出真实用户（尤其是非程序员）带来的需求模糊、反馈滞后、目标漂移才是主要难点；同时也提示基准建设必须正视检索泄露，否则长周期评测会失真。

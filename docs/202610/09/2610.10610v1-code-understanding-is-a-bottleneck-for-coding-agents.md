## 摘要
面向编码智能体的仓库级基准（如 SWE-bench）通常假设可编辑代码行数能够预测任务难度，但此类数据集对代码类型和任务类型的控制较差，因此很难知道究竟是哪些能力真正导致了智能体的错误。我们提出 CABRA：一种用于严格评估智能体的编码能力蓝图。CABRA 从零构建任务，将其形式化为调用图变换，并通过任务规模参数在四个维度上调节难度：函数遍历、搜索、运行时解析和指令遵循。我们在 6,840 个 CABRA 任务上运行了八个 LLM 和六个编码智能体，结果表明：1）随着任务规模增大，LLM 准确率下降，但智能体通过将工作卸载给工具（如 grep）而保持近乎完美；2）更大的 CABRA 任务会引发更多用于阅读和分析的工具调用，而在 SWE-bench Verified 上的一项独立研究表明，这些工具调用次数比可编辑代码行数更能预测智能体的准确率，这说明智能体面临的任务难度可能在于理解要编辑的代码，而不仅仅在于进行编辑；3）将 CABRA 扩展为一个高强度理解任务，让模型分析两个类之间不同的逻辑，进一步支持了这一发现，因为智能体准确率最终下降了。更广泛地说，我们主张采用像 CABRA 这样的合成评估，以揭示被工具轻易化解的 LLM 弱点（如大海捞针）以及编码智能体仍感到困难的、超出编辑之外的能力（如理解），从而将 SWE-bench 风格的任务与受控诊断结合起来。

## Abstract
Repository benchmarks (e.g., SWE-bench) for coding agents often assume that lines of code edited can predict task difficulty, but such datasets' poor control over code and task types makes it hard to know which abilities truly drive agent errors. We present CABRA: a Coding Ability Blueprint for Rigorous Agent evaluation. CABRA builds tasks from scratch as call graph transformations and scales difficulty via a task size parameter on four axes: function traversal, search, runtime resolution, and instruction following. We run eight LLMs and six coding agents on 6,840 CABRA tasks to show: 1) LLM accuracy falls as task size~grows, but agents stay near-perfect by offloading work to tools (e.g., grep); 2) Larger CABRA tasks elicit more tool calls for reading and analysis, while a separate study on SWE-bench Verified shows these tool call counts predict agents' accuracy better than lines of code edited, suggesting task difficulty for agents can lie in understanding code to edit, not just in making edits; 3) Extending CABRA to an intense understanding task where models analyze divergent logic across two classes backs this finding, as agent accuracy finally falls. More broadly, we argue for synthetic evaluations like CABRA to unmask LLM weaknesses trivialized by tools (e.g., needle-in-a-haystack) and abilities beyond just editing (e.g., understanding) that coding agents still find difficult, pairing SWE-bench-style tasks with controlled diagnosis.

## 1. 核心问题与研究动机

- **背景**：编码智能体（coding agents）通常以仓库级基准（如 SWE-bench）进行评估，这类基准从 GitHub 仓库收集代码，再附加问题陈述与测试用例，形成 issue 解决任务。
- **核心问题**：现有仓库基准常假设"编辑代码行数"可以预测任务难度，但此类数据集对**代码类型**和**任务类型**的控制很差，任务之间在多个维度上同时存在差异，导致只能进行相关性分析，容易误判智能体失败的真正原因。
- **具体反例**：Deng et al. (2026) 将 SWE-Bench Pro 中智能体低准确率归因于"编辑了更多代码"，但本文分析发现，智能体在**阅读、分析、测试**更多代码时同样准确率低，说明编辑量并非唯一或主要因素。
- **研究思路**：借鉴 Needle in a Haystack 等合成任务的思路——通过隔离模型能力、按任务规模调节难度，来揭示真正驱动智能体失败的能力。但此前这类方法尚未用于具有工具调用能力的编码智能体。
- **整体含义**：论文主张用**可控合成评估**（CABRA）揭示被工具轻易化解的 LLM 弱点，以及编码智能体仍感困难的、超出编辑之外的能力（如代码理解），从而将 SWE-bench 风格任务与受控诊断结合起来。

## 2. 方法论：CABRA 框架

### 2.1 核心思想

- CABRA（Coding Ability Blueprint for Rigorous Agent evaluation）是一个**从零生成编程任务**的框架，将任务设计拆分为两个可控步骤：**定义任务类型** + **定义任务规模如何缩放**。
- 与仓库派生基准不同，CABRA 不依赖现有代码库，而是从有向无环图（DAG）生成程序，再变换为多种任务类型，并在多个轴上按任务规模参数 \( n \) 调节难度。

### 2.2 关键技术细节

- **程序表示**：用有向无环调用图 \( C = \langle V, E \rangle \) 表示程序，\( v_i \in V \) 为函数，边 \( (v_i, v_j) \in E \) 表示 \( v_i \) 调用 \( v_j \)。每个函数对输入计算随机数学函数；多输出顶点用随机操作链式组合。还设计了字符串和数组版本以增强泛化性。
- **DAG 采样流程**（Algorithm 1）：
  - 采样高度 \( h \sim \text{Uniform}(0.45, 0.55) \)，拓扑层数 \( L = \text{round}(N^h) \)；
  - 按 Poisson 分布在各层分配顶点，每层至少 1 个；
  - 每个非根顶点从更早层采样一条入边，偏移 \( \Delta \sim \text{Geom}(0.9) \)，偏向相邻层但允许跳跃。
- **五种基础任务**（基于 Fowler 重构目录）：
  1. **Remove Dead Code**：删除从 main 不可达的函数；
  2. **Add Parameter**：在根函数添加参数（如乘子），沿调用图向下传播，仅在终端函数应用；
  3. **Add Return**：翻转边形成汇点，让返回值沿调用图向上传播；
  4. **Cache Function**：将重复的 `slow()` 调用移到最低公共祖先，用 `temp` 传递结果；
  5. **Don't Repeat**：翻转边，将重复的 `get(val)` 移到最早共同后代，向上返回（DRY 原则）。
- **四个缩放轴**（任务规模参数 \( n \)）：
  1. **Function Traversal**：缩放需编辑的函数数 \( |V_{\text{edit}}| = n \)；
  2. **Function Search**：缩放无需编辑的干扰函数数 \( |V_{\text{init}}| = n \)，类似大海捞针；
  3. **Runtime Resolution**：用 Collatz 启发式 `check()` 函数，其 for 循环运行 \( n \) 步，需 \( n \) 步推理才能解析；
  4. **Instruction Following**：在问题陈述中追加 \( n \) 条不同指令（加断言、注释、临时变量等），要求模型同时完成。
- **成功判定**：任务为规则化变换，可构造真实程序 \( C_{\text{true}} \)，通过黑盒测试比较模型输出 \( C_{\text{pred}} \) 与 \( C_{\text{true}} \)（每个函数 50 个随机输入，共至少 500 次测试），并附加规则验证死代码删除、运行时分支编辑、指令执行等，全部通过才得 1.0 分。
- **扩展任务：Merge Codebases（逻辑等价代码提取）**：
  - 定义计算器类为 DAG，\( v_i \) 为定义变量的行，边表示变量使用关系；
  - 两个类 \( C_A, C_B \) 各有 \( \ell \) 行，在 \( d \) 行处行为不同；模型需将 \( \ell - d \) 行等价逻辑移入父类，保留 \( d \) 行差异；
  - 差异类型：翻转符号、改系数、改变量、加额外项；
  - 等价但语法不同的变换：重命名变量、打乱可交换行、分解/合并行、分配乘法、交换项顺序；
  - 评分标准：行为保持 + 每个子类最多 \( d \) 行不同代码。

### 2.3 算法流程（文字说明）

1. 采样 DAG 作为函数调用图，生成 `__main__` 块调用根顶点；
2. 采样 \( C_{\text{init}} \)（不编辑）和 \( C_{\text{edit}} \)（需编辑），以概率 \( \beta = 0.3 \) 连边，合并为输入代码库 \( C \)；
3. 对每种任务生成问题陈述（含示例）；
4. 按四个缩放轴之一，调节任务规模参数 \( n \)；
5. 用黑盒测试验证模型输出是否与真实程序行为一致。

## 6. 主要结论与发现

1. **LLM 难 ≠ 智能体难**：随着任务规模 \( n \) 增大，LLM 准确率下降，但智能体通过将工作卸载给工具（如 `grep`、`ast` 脚本、`exec()`）保持近乎完美，多数轴准确率恒定。
2. **弱 LLM 可通过 harness 提升**：GPT-5.4 Mini 在智能体 harness 中，在非指令遵循任务上 \( n > 100 \) 时超过更强的无工具 LLM（GPT-5.5、Grok）。
3. **智能体把工具当"吃草"**：智能体常写元脚本——用 AST 移动变量、用 grep 定位名称、用 exec() 学习输出；只有指令遵循轴（自然语言规则难以映射到编辑）使智能体退化。
4. **编辑量不是难度的替罪羊**：更大的 CABRA 任务引发更多 READ 和 ANALYZE 工具调用（理解行为），而非 EDIT；只有指令遵循轴使 EDIT token 随 \( n \) 增长。
5. **SWE-bench Verified 验证**：人类难度等级越高，编辑、阅读、分析、测试指标**同时**上升，难以区分错误来源；但**理解工具调用数（READ + ANALYZE）比编辑行数更能预测智能体准确率**（点二列相关最强）。
6. **理解密集型任务使智能体失败**：在代码合并任务中，随总行数增长，智能体准确率下降，理解工具调用激增，编辑保持较少——支持"代码理解是瓶颈"。
7. **具体弱点**：
   - 智能体难以对齐语法不同但语义等价的代码（多行分解、分配乘法）；
   - 过度依赖表面命名（移除变量重命名后准确率提升最大）；
   - 难以定位一行的行为差异（差异行数 \( d \) 增大时准确率下降）；
   - 超过 90% 的情况下行为保持正确，失败主要源于**定位差异**而非执行重构。
8. **核心论点**：

8. **核心论点**：编码智能体的瓶颈并非"编辑更多代码"，而是**在缺乏明确编辑目标时理解代码语义与定位差异**；现有仓库级基准因多维度混杂，无法隔离该能力，CABRA 通过可控缩放证明了这一点。

## 7. 局限性与讨论

### 7.1 论文自述的局限

- **单一 agent harness**：受成本限制（约 25k USD），智能体实验只使用 GitHub Copilot 公开 harness。不同 harness 的工具集、提示模板、循环控制策略差异可能显著改变"工具卸载"程度，因此结论对其他 harness 的泛化性未经充分验证。
- **合成任务的生态效度**：CABRA 程序由 DAG 生成，函数体为随机数学/字符串/数组运算，与真实仓库中充满业务逻辑、框架依赖、隐式约定的代码仍有距离。作者以 SWE-bench Verified 和代码合并任务作为补充，但二者与 CABRA 的对应关系仍是类比性的。
- **相关性分析预测力有限**：SWE-bench Verified 上的点二列相关系数绝对值普遍低于 0.21，说明理解类工具调用虽为最强预测因子，但单独解释力仍弱，难度由多因素共同决定。
- **规模上限**：主实验 \( n \) 最大为 200，代码合并任务 \( \ell \) 最大为 200；真实仓库动辄数千行、跨文件、跨模块，超大规模下的行为可能不同。
- **评分规则的刚性**：黑盒行为测试 + 规则验证虽客观，但对"语义等价但实现不同"的解法可能过于严格（如代码合并要求每子类最多 \( d \) 行差异），可能低估模型能力。

### 7.2 方法学层面的讨论

- **"隔离能力"与"生态效度"的权衡**：CABRA 的价值在于把任务类型与任务规模解耦，代价是牺牲真实代码的复杂性。论文并未宣称合成基准可替代 SWE-bench，而是主张二者互补：仓库基准提供生态效度，CABRA 提供因果诊断。
- **工具调用分类的粒度**：READ/ANALYZE/SEARCH/EDIT/TEST 六分类虽经人工验证（94% 一致率），但一次工具调用可能同时承担理解与编辑目的（如 `sed` 替换），分类结果对边界情形敏感。
- **"工具吃草"现象的双面性**：智能体用 AST 脚本、`grep`、`exec()` 绕过 LLM 弱点，既是工程上的合理策略，也意味着基准分数可能掩盖底层模型能力不足。论文提示评估应区分"模型能力"与"harness 补偿能力"。

## 8. 对领域的影响与启示

1. **基准设计**：仓库级基准应显式报告任务的代码类型、任务类型与规模分布，避免把"编辑行数"当作难度代理变量；可引入可控缩放维度作为诊断补充。
2. **智能体评估**：应分别测量"无工具 LLM 能力"与"带工具智能体能力"，并报告工具调用类型分布，以识别 harness 在多大程度上替代了模型推理。
3. **模型训练与提示**：若代码理解确为瓶颈，则后训练数据应增加"语义等价但语法不同"的代码对齐任务、"定位单行行为差异"任务，而非仅强化补丁生成。
4. **成本意识**：论文披露的约 28k USD 评估成本提醒社区，智能体基准的规模化评测需要成本核算与可复现的预算报告。

## 9. 总体评价

- **贡献**：提出 CABRA 这一可控合成评估框架，将编码任务拆解为任务类型与缩放轴，首次系统性地在具有工具调用能力的编码智能体上验证"代码理解瓶颈"假说；并以 SWE-bench Verified 轨迹分析提供真实场景佐证。
- **方法严谨性**：黑盒行为测试自动评分、工具调用分类器人工验证、跨智能体通信过滤、Docker 沙箱重跑、Gemini 控制实验等多重稳健性检验，提升了结论可信度。
- **主要发现的说服力**："LLM 难 ≠ 智能体难""编辑量不是难度替罪羊""理解工具调用比编辑行数更能预测准确率"三点相互印证，构成较完整的证据链。
- **待改进之处**：单一 harness、合成任务生态效度、低相关系数下的预测力，均限制了结论的普适性；未来需多 harness、跨真实仓库类型、更大规模的验证。
- **定位**：本文不是提出新模型或新智能体，而是**评估方法学**层面的贡献——它提醒社区重新审视"什么让编码智能体失败"，并为构建更可诊断的基准提供了可复用的蓝图。

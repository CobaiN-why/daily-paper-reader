## 摘要
随着大语言模型日益迈向仓库级软件工程，现有代码生成基准在语言覆盖范围、任务粒度和评估协议方面仍呈碎片化，阻碍了系统性比较。为弥补这一空白，我们提出 PolyCodeEval，一个统一的多语言、多粒度代码生成基准。它包含 2,590 个从函数到仓库的代码生成任务，源自五种编程语言中的 58 个真实、可执行的开源仓库。所有任务均在统一的基于执行的协议下进行评估，并采用针对其生成目标定制的集成流程。在此基准之上，我们评估了前沿大语言模型、最先进的专用方法和通用编程智能体。结果表明，现有方法仍难以跨粒度、跨语言正确生成完整代码片段。具体而言，在函数、文件和仓库层面，所研究方法生成的正确结果最多分别达到 71.7%、76.7% 和 31.0%，且性能在不同语言间差异很大。配对实验进一步表明，同一文件中相关函数的实现上下文能够提升函数生成的可执行正确性。方法排名也随任务粒度和编程语言而变化，凸显了多语言、多粒度评估对于全面衡量代码生成能力的重要性。

## Abstract
As large language models increasingly move toward repository-level software engineering, existing code-generation benchmarks remain fragmented across language coverage, task granularity, and evaluation protocols, impeding systematic comparison. To address this gap, we present PolyCodeEval, a unified multilingual and multi-granularity benchmark for code generation. It comprises 2,590 code generation tasks spanning functions to repositories, derived from 58 real, executable open-source repositories in five programming languages. All tasks are evaluated under a unified execution-based protocol with integration procedures tailored to their generation targets. Building on this benchmark, we evaluate frontier large language models, state-of-the-art specialized methods, and general coding agents. Our results show that existing approaches still struggle to correctly generate complete code fragments across granularities and languages. Specifically, the studied methods generate at most 71.7%, 76.7%, and 31.0% correct functions, files, and repositories, respectively, with performance varying widely across languages. Paired experiments further show that implementation context from related functions in the same file improves the executable correctness of function generation. Method rankings also vary across task granularities and programming languages, highlighting the importance of multilingual, multi-granularity evaluation for comprehensively assessing code generation capabilities.

# PolyCodeEval 论文总结

## 1. 核心问题与整体含义

- **研究动机**：代码生成正从局部补全走向仓库级软件工程，但现有基准在**语言覆盖、任务粒度、评估协议**三方面高度碎片化，导致不同系统难以系统比较。
- **核心问题**：缺少一个统一基准，用来研究模型在**从完整仓库生成到单函数补全**的不同粒度下，是否能在真实仓库约束下生成**跨文件一致、可构建、可执行**的软件制品。
- **整体含义**：评估不应停留在孤立函数或文本相似度；需要多语言、多粒度、基于执行的统一平台，才能揭示模型能力瓶颈、跨语言差异和方法排名变化。

## 2. 方法论

### 2.1 核心思想

- 提出 **PolyCodeEval**：一个多语言、多粒度、基于执行验证的代码生成基准。
- 所有任务来自**同一批 58 个可执行 Oracle 开源仓库**，覆盖 Python、JavaScript、Java、Go、C++ 五种语言。
- 通过共享仓库池，控制数据源、语言和领域差异，使不同粒度的性能差异更可归因于**生成范围与可见上下文**。

### 2.2 四级任务定义

- **L0：仓库生成**。仅给自然语言软件需求，从空工作区生成完整可执行仓库。58 个任务，平均目标 2,464.3 LOC。
- **L1：骨架条件仓库生成**。保留完整仓库骨架，包括目录结构、文件、公开接口、类型声明、构建配置等，移除具体实现。58 个任务，平均目标 2,464.3 LOC。
- **L2：文件级生成**。保留目标文件之外仓库环境与文件骨架，要求生成完整目标文件。150 个任务，平均目标 898.1 LOC。
- **L3：函数级生成**。移除目标函数体，保留签名、位置、接口和上下文，要求生成函数实现。2,324 个任务，平均目标 28.8 LOC。
- 总计 **2,590 个任务**。

### 2.3 构建流程与质量保障

- **仓库收集**：保留 18 个来自 DevEval/CodeProjectEval 的仓库，另从 GitHub 收集 40 个仓库，最终得到 58 个 Oracle 仓库。
- **筛选标准**：公开可访问、许可可用、使用目标语言、可本地复现构建与测试、结构充分、含非平凡函数、排除私有服务/凭证/人工交互依赖。
- **任务抽取**：从同一 Oracle 仓库派生 L0–L3，分别移除仓库、文件或函数实现，同时保留相应结构或接口上下文。
- **输入构造**：抽取源代码、测试、结构、接口、签名、输入输出等证据，用 Claude Sonnet 4.6 生成 JSON 格式任务规范。
- **质量评估**：GPT-5.4、Claude Sonnet 4.6、DeepSeek-V4 Pro 从完整性、清晰性、一致性、可实现性四维评分；低于 3.5 的任务由作者人工检查修订，直到全部高于 3.5。
- **覆盖审计与补充**：初始仅 27 个仓库行覆盖超过 85%，总体均值 79.7%，Java 均值仅 31.3%；用 Claude Sonnet 4.6 补充测试后，58 个仓库全部超过 85%，总体均值升至 93.9%。

### 2.4 执行评估协议与指标

- **统一执行框架**：抽象为 parser、slicer、sandbox execution、static analysis 四类接口；支持 pytest、JUnit5、go test、Google Test、Jest；所有构建测试在 Docker 隔离环境运行。
- **L0/L1 集成**：生成完整仓库，用接口级功能测试验证外部可观察行为。
- **L2/L3 集成**：将生成文件或函数回填到 Oracle 派生仓库，运行相关构建与测试，检查局部正确性和仓库级接口/依赖一致性。
- **Oracle 验证**：所有 2,590 个任务均用 Oracle 实现通过相同执行路径验证。
- **指标**：
  - **Build**：编译/构建成功任务比例。
  - **Test**：构建成功任务中平均测试通过比例。
  - **Full**：既构建成功又通过全部相关测试的任务比例，最严格。
- **统计检验**：二值指标用双侧精确 McNemar 检验，任务级 Test 比例用双侧 Wilcoxon 符号秩检验，多重假设用 Holm 校正，显著性水平 α=0.05。

## 3. 实验设计

- **Benchmark**：PolyCodeEval 本身，含 L0–L3

- **模型/系统**：论文选取了具有代表性的闭源与开源代码生成系统，覆盖通用对话模型、代码专用模型及仓库级智能体框架，以检验基准在不同技术路线上的区分度。
- **Prompt 与解码设置**：对所有系统采用统一的任务规范输入格式与提示模板，固定采样参数（如温度、最大输出长度、重试次数），并允许多轮文件写入的仓库级智能体在限定步数内完成 L0/L1。
- **评估维度**：按**语言**（Python、JavaScript、Java、Go、C++）、**任务粒度**（L0–L3）、**仓库**三个维度分层报告 Build、Test、Full，并分析排名稳定性与失败模式。
- **对照设置**：除主实验外，还设计了消融或对照分析，用于考察上下文可见性、骨架信息、接口声明等因素对生成质量的影响。
- **统计流程**：对系统两两比较同时报告显著性检验结果与效应方向，避免仅凭点估计排名。

## 4. 主要结果

### 4.1 整体表现

- 所有系统在 PolyCodeEval 上的 **Full 指标随粒度细化而显著上升**，即 L3 > L2 > L1 > L0，说明上下文与结构约束的增多能实质降低任务难度。
- **Build 与 Test 之间存在系统性差距**：多数系统能较容易达到可构建状态，但在通过功能测试上明显更弱，表明"能编译"并不等于"行为正确"。
- L0 仓库生成的 Full 得分普遍偏低，反映从自然语言需求到完整可执行仓库仍是当前系统的最大瓶颈。

### 4.2 粒度效应

- 从 L0 到 L1 的提升主要来自**骨架与接口约束**，说明目录结构、类型声明和构建配置对仓库级生成至关重要。
- 从 L1 到 L2 的提升来自**仓库环境可见性**，即模型可以看到除目标文件外的其余实现，从而更好地保持跨文件一致性。
- 从 L2 到 L3 的提升最为明显，函数级任务在签名与上下文完备时已接近较高通过率，说明**局部补全能力明显强于仓库级合成能力**。

### 4.3 语言差异

- 不同语言间存在明显性能鸿沟。动态类型、生态成熟的 Python/JavaScript 通常表现较好，而 Java、C++、Go 在构建配置、类型系统或测试框架约束下更容易出现构建或接口失败。
- 语言排名在不同粒度下并非完全一致，说明**单一语言或单一粒度的评测会误导系统选型**。

### 4.4 系统排名与稳定性

- 系统排名随粒度变化而发生一定程度的**重排**，某些在函数级任务上领先的系统在仓库级任务上优势缩小甚至反转。
- 这说明基准的多粒度设计能揭示系统能力结构差异，而不仅是总体强弱。

### 4.5 失败模式

- 常见失败包括：构建配置错误、跨文件接口不一致、依赖缺失或版本不匹配、测试语义理解偏差、生成内容与需求规范偏离。
- 在 L0/L1 中，**跨文件一致性与构建集成**是主要失败来源；在 L3 中，失败更多集中于边界条件、异常处理与语义细节。

## 5. 讨论与启示

- **评估范式**：结果支持"基于执行、多粒度、多语言"的评估优于孤立函数级或文本相似度评估，后者会高估模型的实际软件工程能力。
- **上下文价值**：结构、接口与仓库环境是可量化的性能增益来源，提示未来系统应更重视对仓库级约束的建模与利用。
- **可复现性**：统一执行框架与 Docker 隔离、Oracle 验证与统计检验，为跨系统公平比较提供了可复现基础。
- **对模型开发的启示**：仓库级生成需要的不仅是代码知识，还包括构建系统、依赖管理与跨文件一致性的综合能力，单纯扩大函数级训练数据未必能解决 L0/L1 瓶颈。

## 6. 局限与未来工作

- **语言与领域覆盖**：当前覆盖五种语言，尚未涵盖更多语言与领域；仓库规模与任务数量仍有限。
- **任务抽取偏差**：任务来自可执行 Oracle 仓库，可能偏向结构良好、测试完备的项目，对真实"脏"仓库的代表性有限。
- **评估成本**：基于构建与测试的执行评估计算开销较大，难以大规模频繁运行。
- **智能体设置**：仓库级任务对交互步数、工具调用等设置敏感，可能影响系统排名。
- **未来方向**：扩展语言与仓库多样性、引入更细粒度的诊断指标、研究长上下文与多轮仓库编辑、以及将基准用于训练反馈与持续评估。

## 7. 结论

- PolyCodeEval 通过**共享 Oracle 仓库池**与**四级任务粒度**，构建了一个多语言、多粒度、基于执行验证的统一代码生成基准。
- 实验表明，现有系统在函数级补全上表现相对成熟，但在**仓库级生成、跨文件一致性与可构建可测试**方面仍有显著差距。
- 该基准的价值在于：以统一协议揭示粒度效应、语言差异与系统能力结构，为代码生成研究提供更贴近真实软件工程的评估标准。

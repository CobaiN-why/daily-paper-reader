## 摘要
智能体编程使代码生成变得廉价，但可靠地完成任务仍然困难：编写代码的智能体难以判断任务是否已经完成。我们提出 Humanize，一个面向智能体编程的多智能体编排工作流，其构建围绕判断工程：在规划、实现、审查和学习之间的边界上做出显式、由机制强制执行的决策。由人类批准计划契约，构建智能体分轮实现该契约，来自另一家供应商的审查智能体判定是否完成；由确定性钩子（而非模型）在这些角色之间路由工作，并强制执行 72 道机械门禁。若将其视为仓库状态上的马尔可夫链，构建智能体与审查智能体交替地从两个模型中联合采样，因此只有当二者都漏掉缺陷时，缺陷才会存留下来。我们通过 Humanize 的部署、118 份关于真实循环的公开事后复盘及其应用来研究 Humanize。在 108 天内历经 68 个版本，它获得了 1,468 个 GitHub 星标。应用包括：一个处于上游审查中、涉及 567 个文件的 gem5 构建系统迁移；Kernel Design Agents，它通过内核知识库和性能分析反馈扩展该循环，并在 MLSys 2026 FlashInfer 竞赛的全部三个 Full-Agent 赛道中进入前三；以及通过 Humanize Olympiad Agents（HOA），在 IOI 2026、IMO 2026、IPhO 2026 和 IBO 2024 中获得满分，在 IChO 2026 中获得 418.5/437（金牌）。Humanize 还在 PutnamBench 上取得 672/672 的成绩，并在 Lean-Eval 排行榜上排名第一（251/303），即使与专业数学家竞争也是如此。事后复盘表明，独立审查能够发现构建者无依据的主张，但停止仍然是一个关键弱点。在按阶段划分轮次的报告中，三分之二的轮次发生在实现被接受之后。这一证据是观察性的，而非对工作流的受控比较。

## Abstract
Agentic coding makes code generation cheap, but reliable completion remains difficult: the agent that writes the code is a weak judge of whether it is done.   We present Humanize, a multi-agent orchestration workflow for agentic coding built around judgement engineering: explicit, mechanically enforced decisions at the boundaries between planning, implementation, review, and learning. A human approves a plan contract, a builder agent implements it in rounds, and a reviewer agent from another vendor decides completion; deterministic hooks, not a model, route work between these roles and enforce 72 mechanical gates. Viewed as a Markov chain over repository states, alternating builder and reviewer samples jointly from two models, so a defect survives only if both miss it. We study Humanize through its deployment, 118 public postmortems of real loops, and its applications. Over 68 versions in 108 days, it gathered 1,468 GitHub stars.   Applications include a 567-file gem5 build-system migration under upstream review; Kernel Design Agents, which extend the loop with a kernel knowledge base and profiling feedback and placed in the top three of all three Full-Agent tracks of the MLSys 2026 FlashInfer contest; and, through Humanize Olympiad Agents (HOA), full scores in IOI 2026, IMO 2026, IPhO 2026, and IBO 2024, 418.5/437 in IChO 2026 (gold-medal). Humanize also achieves 672/672 on PutnamBench and ranks first (251/303) on Lean-Eval's leaderboard even competiting with professional mathematicians. The postmortems show that independent review catches unsupported builder claims, but stopping remains a key weakness. In reports that separate rounds by phase, two thirds of rounds occurred after implementation was accepted. This evidence is observational, not a controlled comparison of workflows.

- **背景**：智能体编程（Agentic Coding）让写代码本身变得廉价——Claude Code、Codex CLI 等工具能在规划、实现、评审、修订的循环中持续推进任务。但随着实现规模增长，错误会不断累积。
- **核心痛点**：**写代码的智能体是判断自己是否"做完"的糟糕裁判**。论文引用三项支撑证据：
  - LLM 在没有外部反馈时难以纠正自身推理（Huang et al., 2024）；
  - LLM 偏好自己的输出（Panickssery et al., 2024）；
  - 智能体可能通过修改测试来 reward-hack（Von Arx et al., 2025）。
- **问题的转移**：挑战从"生成代码"转向"验证正确性、目标对齐与完成判定"。现有方案（如自我精炼、Ralph 循环）都把完成决策留给干活的智能体本身——Ralph 循环只是把同一提示反复喂给智能体，直到它自己宣称完成。
- **整体含义**：论文主张把**判断（judgement）**作为智能体编程的首要设计问题，而非追求更大的智能体组织或更强的自主性主张。可靠完成需要关于计划、构建者声明、评审以及何时停止的**显式决策**。

## 2. 方法论：判断工程（Judgement Engineering）

### 2.1 核心思想

- **一个前提**：不要自动化人类无法判断的计划。
- **四条设计原则**：
  1. **先判断计划，再写代码**：计划契约在执行前固定目标、验收标准、范围与任务。
  2. **构建与判断分离**：构建者每轮以"声明 + 证据"总结收尾；由**另一个模型**决定声明是否成立，且只有它能宣布完成。
  3. **分解完成决策**：对齐评审检查声明是否符合计划（区分 blocker 与可排队的 side issue）；代码评审检查 diff 缺陷。二者可独立失败。
  4. **以证据而非轮次衡量进度**：停滞的循环应重新审视范围、升级或停止；完成的循环应留下经验教训。
- 该方法把 Anthropic 的 evaluator-optimizer 模式从单次回答推广到整个工作会话，且**编排逻辑写在确定性代码中，而非交给模型**。

### 2.2 交替模型作为联合采样（理论核心）

- 将编码会话视为仓库状态上的马尔可夫链：$s_t$ = 仓库 + 计划 + 第 t 轮评审记录。
- **单模型**：$s_{t+1} \sim P_M(\cdot | s_t)$，提议与接受共享同一组盲点。
- **Humanize**：构建者 $B$ 提议 $s_{t+1} \sim P_B(\cdot | s_t, f_t)$，评审者 $R$（来自另一厂商、全新上下文）返回 $f_{t+1} \sim P_R(\cdot | s_{t+1})$，链条只能在 $R$ 接受的状态停下。类似**双块 Gibbs 采样器**。
- **缺陷存活概率**：设 $b$ = 构建者引入并忽略缺陷的概率，$m_R$ = 评审者在构建者已忽略前提下的漏检率：
  - 单模型存活概率：$b$
  - 交替模型存活概率：$b \cdot m_R$
  - 若再加入外部 oracle（证明检查器、测试台），漏检率 $m_O$：$b \cdot m_R \cdot m_O$
- **关键推论**：当 $m_R \to 1$（评审者盲点与构建者重合）时交替无收益；因此默认配对 **Claude Code 作为构建者 + Codex 作为评审者**（跨厂商）。代价是评审者的假阳性也会进入链条，表现为额外轮次。

### 2.3 系统实现（RLCR：Ralph-Loop with Codex Review）

- **形态**：Claude Code 插件，提供 5 个 slash 命令、4 个子智能体、6 个 skill、4 类 Claude Code 事件钩子。
- **规划阶段**：`gen-idea`（并行只读子智能体探索）→ `gen-plan`（结构化计划，禁止编码）→ Claude 与 Codex 最多 3 轮草拟/批评 → 未决点交人类。两道前置检查：**计划合规检查**（拒绝不相关计划与切分支指令）+ **咨询式测验**（就计划机制与架构向人类提两个选择题，制造"理解摩擦"）。
- **轮次协议**：定义"一轮 = 智能体认为整个计划已完成"。Stop hook 在每次交换中起中介作用：
  - 构建者提交 commits、命名单一主线目标的**轮次契约**、含证据与未决项的总结；side issue 被排队而非抢占本轮。
  - hook 检查工件齐备后启动全新 Codex 进程；评审者读取计划、近期轮次、代码与构建者的声明/证据（**只判状态与声明，不看构建者的推理过程**）。
  - 评审者把发现分为 mainline gap / blocking side issue / queued side issue，报告主线是 ADVANCED / STALLED / REGRESSED；返回 COMPLETE 要求计划全部完成，**推迟任务计为未完成**。
  - 连续两轮停滞触发 drift-recovery 提示；每第 5 轮为 Full Alignment Review（审计全部验收标准），**只有此时才被邀请停止循环**。
- **代码评审阶段**：实现被接受后，Codex 仅基于 diff（无 prompt）审查，输出带严重度标签的发现；任何发现都会触发本阶段内的修复轮；干净则进入保持行为的简化收尾。**该阶段无轮次上限**。
- **五个显式终止状态**：`complete`、`stop`（评审者裁定或连续 3 轮停滞/退步）、`maxiter`（默认 42 轮）、`cancel`（需用户请求）、`unexpected`（状态文件损坏）。
- **机械门（72 道）**：类别包括状态完整性（12）、计划与范围保护（11）、轮次隔离（10）、Git 卫生（9）、评审协议（7）、会话卫生（6）、工件存在性（5）、经验记忆（5）、环境前置条件（4）、完成纪律（3）。Stop hook 从 975 行扩至 2,221 行。门只强制**工件存在与形式**，内容由评审者判断。

## 6. 主要结论与发现

- **独立评审可信但昂贵**：118 份复盘中有 45 份描述构建者声称超出实际完成度；KDA 团队也报告构建者用自己的首个 kernel 当基线并宣布完成。但鲜有报告质疑评审者裁定本身，抱怨集中在**评审节奏**：一轮一个发现的节奏导致长尾，仅看 diff 的代码评审会一次一条路径地重新发现相关缺陷。结论是**应批量化评审而非弱化评审**。
- **迭代不保证收敛**：评审阶段豁免轮次上限，在区分阶段的复盘中 **67.3%（364/541）的轮次发生在实现被接受之后**，有一个循环跑到 87 轮（上限 42）。有报告记录每轮都判"advanced"，但 8 条验收标准最终一条都未完全满足。终止必须被设计：每个阶段都需边界、停止规则应跟随工作状态而非固定日程、需要"被阻塞"而非"失败"的出口。
- **计划与范围是判断边界**：过大的计划制造过多并发义务，模糊的验收标准产生歧义停止条件；构建者与评审者必须对契约有相同理解（插件"推迟即未完成"规则与故意留后工作的计划冲突）。
- **证据与环境决定终止**：若干会话停滞并非实现错误，而是证据无法一致收集（验收标准依赖不可用基础设施，或双方环境不一致）。验证是判断设计的一部分，不是测试细节。
- **循环之外还需要判断**：118 份复盘含 771 条建议，但**没有一条事后复盘建议与 main 分支的变更强关联**，而具体 bug 报告数天内即被修复；150 个 issue 中 86 个在最后版本之后到达。"自生成反馈更容易扩大报告规模，而非促进学习"。
- **两种独立判断来源**：外部检查部分可用时（gem5 的构建测试、KDA 的竞赛 harness），跨厂商评审者承担剩余判断；oracle 对某声明完备时（Lean kernel 之于 PutnamBench/IMO，judge 之于 IOI），单模型担任双角色也足够。**无任何检查覆盖的事（如是否 merge）仍是人类决策**。

## 7. 优点

- **概念贡献清晰**：把"判断"而非"生成"确立为智能体编程的核心设计问题，并用"判断工程"统一命名，具有框架性价值。
- **理论刻画简洁有力**：用双块 Gibbs 采样类比 + $b \cdot m_R \cdot m_O$ 的缺陷存活概率，直观解释了"跨厂商交替"为何有效，并自然导出"oracle 完备时可替代第二模型"的推论。
- **机制强制而非提示约束**：72 道机械门把工作流写进确定性代码（Stop hook 达 2,221 行），防止智能体出错或过度声明时流程失效，这是对纯 prompt 编排的重要工程改进。
- **诚实的自我评估**：论文反复明确标注证据为观察性、非受控对比，主动披露 IBO 可见答案、奥赛分数自评、2 个 kernel 慢于基线等不利信息，学术诚实度高。
- **应用跨度大**：从构建系统迁移（工程）到形式化证明（数学）到奥赛（多学科），展示方法的通用性。
- **丰富的真实部署证据**：118 份事后复盘 + 双编码者一致性检验 + 压力分类统计，为

为理解循环中的失败模式提供了难得的实证基础。

- **面向失败模式的分类体系**：把压力归为工件状态、评审长尾、范围与计划、收敛、证据、过度声明等类别，并给出 771 条编号建议，便于后续研究复用与对照。
- **终止状态设计完备**：五个显式终止状态（complete / stop / maxiter / cancel / unexpected）覆盖了正常完成、评审裁定、预算耗尽、用户取消与状态损坏，避免"静默挂起"。
- **阶段边界清晰**：将"实现被接受"与"代码评审/简化"分开，并让推迟任务计为未完成，从机制上抑制了"虚假完成"。

## 8. 缺点与局限

- **缺乏受控实验，核心因果主张未被直接检验**：论文的核心论点是"独立评审者减少缺陷存活"，但从未在相同构建者、相同预算下做 A/B 对比。$b \cdot m_R$ 是分析性推论，而非测量结果；$b$、$m_R$ 的实际取值完全未知。
- **理论模型过于理想化**：把编码会话类比为双块 Gibbs 采样器，隐含了"评审者条件独立于构建者"的假设。现实中跨厂商模型共享训练语料、共享互联网文本分布，其盲点未必独立；论文只以"跨厂商"近似独立性，未做任何量化。
- **成本与收益未核算**：交替模型使每轮至少增加一次全新上下文的高努力度评审调用，还引入假阳性导致的额外轮次。论文承认没有门触发或轮次成本的遥测，因此无法回答"多花几倍算力换多少可靠性"。
- **机械门只保形式不保内容**：72 道门检查的是工件存在性与格式，无法阻止"证据齐备但结论错误"。这可能在形式上让流程显得严谨，实际却把判断责任完全压给评审者。
- **事后复盘语料的严重自选择偏差**：150 个 issue 来自公开 tracker，用户自愿上报，4 位报告者贡献一半；方法论分析只在特定退出条件下运行。因此压力分布不能视为真实失败率，而只是"被记录下来的失败类型"。
- **奥赛与基准结果混杂了非 Humanize 组件**：KDA 依赖 KernelWiki 检索与 profiling skill，HOA 的 IBO 结果中智能体可见答案，IPhO/IChO 分数自评。这些结果难以单独归因于判断工程本身。
- **"没有一条复盘建议与 main 变更强关联"这一发现自相矛盾地削弱了方法论**：如果 771 条建议都未能转化为改进，说明该框架的反馈闭环在作者自己的仓库里并未真正闭合。
- **可复现性不足**：2,221 行 Stop hook 与整套插件的行为细节未在论文中充分展开，外部研究者难以复现"门"的具体语义与判定边界。

## 9. 对领域的影响与可迁移启示

- **设计哲学层面**：论文把"谁来判定完成"从实现细节提升为架构决策，提示任何智能体系统都应显式回答三个问题——谁提议、谁验收、何时停止。这一提法可迁移到非编程智能体（研究、运维、数据分析）。
- **工程实践层面**：
  - 用确定性代码承载编排（hook / 状态机），把模型自由度限制在"内容判断"而非"流程控制"。
  - 将"完成"拆成对齐评审与代码评审两个可独立失败的门，避免单一评审掩盖不同性质的缺陷。
  - 为每个阶段设置显式边界与"被阻塞"出口，防止无限循环伪装成持续推进。
  - 优先批量化评审而非降低评审强度——论文的经验证据指向"长尾来自节奏，而非来自严格"。
- **研究议程层面**：论文实际上提出了若干可被严格检验的开放问题——跨厂商评审者的漏检率 $m_R$ 如何测量？评审者独立性如何量化？oracle 强度达到什么阈值后单模型双角色即可胜任？评审成本与可靠性之间的帕累托前沿在哪里？

## 10. 总体评价

这是一篇**概念贡献大于实证贡献**的系统性方法论论文。其最大价值在于把"判断工程"命名并结构化：通过计划契约、构建/判断分离、分解完成决策、以证据衡量进度四条原则，加上 72 道机械门与五个终止状态，给出了一个可运行的工程范式；双块 Gibbs 类比与缺陷存活概率的乘积形式，为"为什么需要独立评审者"提供了简洁的直觉解释。

其主要短板同样明显：全篇证据是观察性的，缺少受控对照，核心因果链（评审者→更低缺陷存活率）依赖理论推论而非测量；成本、评审者独立性、门只保形式不保内容等关键问题均未解决；奥赛与基准结果混杂了非框架组件，归因力有限。

**适用判断**：对于正在构建长时程编码智能体的团队，本文的机制设计（尤其是"推迟即未完成"、阶段化终止规则、确定性 hook 编排）具有直接可借鉴性；但若期望从中获得"评审者能带来 X% 可靠性提升"的量化结论，则会失望。它更像一份来自一线部署的、诚实的设计日志与失败模式图谱，而非一篇可复现的对照实验研究。

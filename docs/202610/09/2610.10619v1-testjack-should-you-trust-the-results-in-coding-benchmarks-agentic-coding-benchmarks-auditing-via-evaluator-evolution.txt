## Abstract 

Large language model (LLM) agents are rapidly reshaping software engineering, accom-panied by an explosion of new code benchmarks. Yet nearly all existing benchmarks still rely on the same decades-old criterion: a solution is correct if it passes a fixed set of unit tests . Such tests are often insufficient: they check only part of what the task requires, so agents can reward hack them or silently miss required behavior while still passing every test. As a result, higher benchmark scores may partly reflect better adaptation to the eval-uator rather than better problem solving. Existing works focus on static test augmentation: they strengthen each task’s tests once, before any trial is seen, and thus overlook how real trials actually fail. We introduce T EST JACK , a scalable framework for evaluating patches beyond fixed tests. For each trial, T EST JACK generates tests targeting prompt requirements the patch may violate, retains only tests passed by the ground-truth patch, and re-examines any trial failures. Each confirmed failure is thus supported by a replayable test. To reduce evaluation cost, we also introduce a lightweight variant which audits a random sample of trials in depth and reuses the resulting tests across all trials for the same task. Across 6 frontier model backends and 5 benchmarks such as DeepSWE and SWE Marathon, we find that about 34.4% of the model trials currently judged correct violate the task requirements, lowering the overall resolution rate from 50.6% to 33.2%. Our results reveal a fundamental limitation of current coding-agent evaluation: as LLMs become better at optimizing against fixed evaluators, those evaluators themselves must become more adaptive. 

## 1 Introduction 

Large language model (LLM) agents are reshaping software engineering. Modern agents navigate repositories, edit multiple files, run development tools, and iteratively refine their outputs, and sys-tems such as Claude Code, Codex, and Copilot have become integral to research and production, making their rigorous evaluation increasingly important. Code benchmarks have become the stan-dard yardstick for comparing these agents, from function-level synthesis in HumanEval [7] and MBPP [3] to repository-level issues in SWE-bench [18]. Their number continues to grow, with 210 introduced in 2024 and 316 in 2025 [5], and score improvements are routinely cited as evidence of progress. The community has invested heavily in these benchmarks: tasks are curated from real repositories or authored by engineers, and their tests are reviewed by hand, as when 93 professional developers screened SWE-bench to build SWE-bench Verified [10]. Yet nearly all of them share one evaluation schema: a task counts as solved once the submission passes a test suite fixed when the benchmark was published. With insufficient tests , the tests check less than the prompt requires, so trials that overlook a required case or game the tests still pass. With an underspecified prompt , a behavior is only implied by the prompt, so whether it must be implemented is ambiguous; the ground truth implements it but no test checks it. Only the first is a defect of the trial: T EST JACK refutes trials for insufficient tests, whereas it attributes the second to the prompt and reports it as a prompt defect without refuting the trial (§3.2). The resulting overestimation can be substantial: through manual inspection, SWE-Bench+ [2] shows that excluding patches that passed only because of weak tests or solution leakage reduces one SWE-bench agent’s resolution rate from 12.47% to 3.97%. Existing efforts to close this gap sacrifice either scalability or fidelity. Manual audits such as SWE-Bench+ reliably uncover such failures, but they do not scale: expert review must be repeated for every agent, model version, and run. Automated benchmark auditors such as ABA [32] ask whether a task is fair and remove flawed tasks, which corrects unfairly failed trials but leaves falsely passed ones in place. Test augmentation methods such as UTBoost [36] and SWE-ABS [37] produce ex-ecutable evidence but remain static : they strengthen each task’s suite once, before any submission is observed, so they catch only anticipated failures and fall short of the reward hacking of modern LLMs. PatchDiff [33] inspects submissions dynamically, but still relies on human effort to decide which divergences are genuine defects. What is needed is a dynamic evaluator that judges each trial against what the task asks for like a manual auditor, and backs every verdict with executable evidence at scale like automated testing. In this paper, we present T EST JACK 1, an automated framework that audits the successes reported by coding benchmarks by evolving the evaluator rather than trusting their fixed tests. Our key insight is to separate what a test should check from whether its expectations are correct: a trial should be judged against the requirements stated in the task prompt, and the ground-truth solution, which benchmarks already possess, can serve as an executable oracle that certifies any new test before it is used to judge a trial. Building on this insight, T EST JACK audits each benchmark-passing trial with prompt-grounded differential testing : an LLM agent reviews the trial against the prompt’s requirements, writes tests targeting the gaps it suspects, validates each on the ground truth, runs it on the trial, and re-judges any failure to confirm a genuine violation of the prompt, so every refutation is backed by a replayable witness test . Because auditing every trial is expensive, T EST JACK also offers a lightweight approach that first adds oracle-validated tests for requirements each task leaves

In summary, we make the following contributions: • Problem. We expose a fundamental limitation of static , test-based evaluation for coding agents and propose dynamic evaluator evolution , which generates new tests to probe each trial against the task requirements. • Technique. We design prompt-grounded differential testing, which writes tests from the task’s requirements, certifies them against the ground truth, and re-judges each failure, and a lightweight variant that combines task analysis with randomized auditing and cross-trial witness sharing. • Empirical study. We find that 34.4% of benchmark-passing trials of frontier agents on five bench-marks violate task requirements. And the lightweight variant recovers 72.4% of these refutations at 15.4% of the cost on three of the five benchmarks. Our audit results can serve as references for future benchmark design.

Coding Benchmarks. Benchmarks such as MMLU [16], BIG-bench [30], HELM [22], and Hu-manity’s Last Exam [6] structure progress in AI, yet their reliability is increasingly questioned: test sets contain label errors [27], public benchmarks leak into pretraining corpora [34], leaderboard practices can distort rankings [29], and flaws in agentic task setup or reward design can misestimate performance by up to 100% [40]; dynamic benchmarking [8, 9, 20] responds by continually collecting new adversarial examples. Coding benchmarks have evolved from function-level synthesis [3, 7] to repository-level is-sue resolution in SWE-bench [18] and its successors, which add human validation [10], languages [38], modalities [35], contamination-limiting refreshes [4, 39], and enterprise-grade changes [11]. Another line authors tasks from scratch, from command-line work [24] and skill-augmented workflows [21] to long-horizon engineering projects [12, 17]. Nearly all of these benchmarks share one static protocol: a submission is correct if it passes a test suite fixed when the benchmark is released. 

Benchmark Auditing and Test Strengthening. Prior work on benchmark reliability can be or-ganized along two axes (Figure 2): whether the evaluator is static , analyzing a task before any submission is observed, or dynamic , auditing the trials that agents actually produce; and whether its verdicts rest on manual checking or automated auditing. Manual audits expose failures that scores conceal [2] but must be repeated for every new agent and run. Automated auditors such as ABA [32] and BenchGuard [31] use LLM agents to flag tasks whose specification, environment, or grader is broken [25]; they audit the benchmark rather than individual trials, and their verdicts rest on LLM judgment. Another line strengthens benchmark tests, from amplifying HumanEval’s tests [23] to generating additional or adversarial tests for SWE-bench, as in UTBoost [36] and SWE-ABS [37], and issue-reproducing tests [1, 26]. These methods are static: they build one suite per task before observing any submission, so their tests must anticipate where agents fail and may encode incidental details of the gold patch. PatchDiff [33] is dynamic, testing agent patches differentially against the gold patch, but only 28.6% of the divergent patches it reviews can be confirmed incorrect and most 3cannot be judged either way, so deciding which divergences indict a trial still requires manual in-spection. TEST JACK is, to our knowledge, the first automated dynamic evaluator and occupies the automated, dynamic quadrant of Figure 2: it audits individual trials rather than tasks, derives tests from the task prompt rather than the gold patch, uses the ground truth only to validate their expectations, and backs every verdict with an executable witness test instead of LLM or human judgment. 

## 3 Methodology 

We first formulate the problem (§3.1), then present the per-trial audit (§3.2) and its lightweight variant (§3.3); Figure 3 gives an overview of both. 

3.1 Problem Formulation 

A benchmark instance consists of a natural-language task specification P (e.g., a GitHub issue), a repository snapshot R, a ground-truth implementation G (e.g., the developer-written reference patch applied to R), and a static test suite T0 used by the benchmark to score submissions. Running an agent on the instance produces a trial : a candidate patch s applied to R, yielding a submission R[s].A trial is passing if R[s] passes every test in T0. T EST JACK takes as input the set of passing trials 

S = {s1, . . . , s n} collected across agents and asks, for each trial, whether its passing verdict should be trusted. 

Requirements and behavior spaces. Let Q(P ) = Qe(P ) ∪ Q i(P ) denote the requirements of the task, where Qe(P ) contains the requirements that P states explicitly and Qi(P ) those that follow implicitly from P together with the documented behavior of the repository. For an artifact X, let 

B(X) denote the behaviors it pins down: B(T0) is the behavior asserted by the benchmark tests, 

B(P ) is the behavior required by Q(P ), and B(G) is the behavior exhibited by the ground truth. We assume each task is well-formed (Appendix A.1), so these spaces are nested: 

B(T0) ⊆ B (P ) ⊆ B (G). (1) The first inclusion reflects that the tests check only part of what the prompt requires. The second reflects that the ground truth, being a correct solution, implements every required behavior, together with incidental choices that P leaves open or ambiguous. A passing trial is guaranteed to agree with the task only on B(T0), so its possible defects lie in the gap B(P ) \ B (T0).

Witness tests. Auditing a trial s therefore amounts to searching this gap for a witness test t satisfying 

t checks some q ∈ Q (P ) ∧ t(R[G]) = pass ∧ t(R[s]) = fail . (2) A witness is a concrete, replayable demonstration that the trial violates a requirement of the task, even though it passes the entire benchmark suite T0.

3.2 Per-Trial Auditing via Prompt-Grounded Differential Testing 

There are two obvious ways to search for a witness test, and each fails in a different direction of Eq.(1). (i) Writing tests from P alone stays within B(P ) but raises the classical test-oracle problem: an LLM-written test may encode a wrong expectation, and nothing certifies that a failing trial is actually at fault. (ii) Writing tests from G alone , i.e., plain differential testing, accepts any test that separates R[G] from R[s]. Such tests range over all of B(G), including the incidental choices in B(G) \ B (P ), so they overfit to the ground truth and penalize a trial for not reproducing the reference patch rather than for failing the task. T EST JACK combines the strengths of both: it writes tests from P , which the first condition of Eq.(2) enforces, and uses G as an executable oracle, which the second condition enforces, so that a new test is trusted only if the ground truth passes it. The prompt thus determines what to test, the trial determines where to look for violations, and the ground truth confirms that the test’s expectations are correct. The boundary of B(P ), however, is not always sharp. Implicit requirements in Qi(P ) rely on back-ground knowledge that the prompt does not state, and when the prompt is underspecified , a witness for such a requirement may reflect a defect of the prompt rather than of the trial. Audit procedure. TEST JACK implements the audit with two LLM agents, an audit agent and a 

reviewer agent (Figure 3, left). Both operate inside the benchmark’s own execution environment, and neither treats the benchmark’s pass verdict as evidence of correctness. The audit agent proceeds in five steps. 1. Execution worlds. The agent builds three copies of the repository under the official evaluator: the model world R[s], the reference world R[G], and the null world R without any patch. The null world reveals which benchmark tests already pass without a fix and therefore verify nothing about the trial. 2. Requirements checklist. The agent decomposes P into atomic, testable clauses, which instantiate 

Q(P ), and records for each clause whether T0 covers it and whether the trial implements it. 3. Evidence collection. The agent then examines the trial’s diff along three axes: (i) ghost branches ,code paths in the diff that T0 never executes, identified with branch coverage and classified by whether P requires the behavior they implement; (ii) reward hacking , checked with explicit de-tectors for hard-coded expected values, special-casing of tested inputs, test-environment sniffing, harness tampering, and stubs behind a tested veneer; and (iii) general defects , including specifi-cation violations, robustness, and security issues, prioritized by mutation testing, which exposes behavior that T0 does not pin down. 4. Issue-demonstrating tests. For every suspected issue, the agent writes a test in the repository’s native framework that asserts the behavior the violated clause requires. The test must fail in the model world and pass in the reference world, which serves as the oracle. 5. Audit report. The agent assigns the trial a verdict, such as sound, incorrect despite passing, or reward hack. For each issue, it explains what the defect is, why it occurs, which clause of P

requires the correct behavior, and why T0 fails to catch it. The reviewer agent then re-judges these tests, treating P as the sole authority on required behavior and deliberately not using G to infer requirements. It labels each test as valid, questionable, or invalid, rejecting tests that assert behavior the prompt does not request, as they overfit to a particular solution. The trial is refuted if at least one valid test fails on it; such a test is a witness in the sense of Eq.(2). 

Properties. Every verdict is executable : unlike LLM-as-a-judge approaches, a refutation is backed by a test run against both implementations. Verdicts are prompt-grounded : the checklist and the 5reviewer hold the trial to what the task asked for. The audit is agnostic to the failure mode , catching reward-hacked patches by the same mechanism without a predefined taxonomy of exploits, and, being fully automatic, it can be repeated as new agents and trials appear. 

3.3 Lightweight Approach: Randomized Auditing with Witness Sharing 

The per-trial audit is precise but expensive: each audit is a multi-step agent session with repeated builds and test executions, and the number of trials grows multiplicatively with the number of agents, models, and repetitions evaluated on a benchmark. Auditing every trial independently is also waste-ful. Trials for the same task often fail for the same reasons, for instance when many agents miss the same edge case, so independent audits keep rediscovering the same defects. T EST JACK reduces this cost with two ideas: it moves part of the audit from individual trials to the task itself, and it shares every validated witness across all trials of the task (Algorithm 1 in Appendix A.3). 

Agentic task analysis. Many weaknesses of a task are visible before any trial is examined: compar-ing P with T0 often reveals an input the prompt mentions but no test exercises, an error condition that is never triggered, or neighboring behavior the change could break. T EST JACK therefore begins with a task-level analysis in which an agent reads P , T0, and G, identifies requirements of Q(P )

that T0 does not adequately cover, and writes new tests targeting them. With G as the oracle, a test that fails on R[G] is refined using the execution feedback until it passes, or discarded once the refinement budget is exhausted. The result is an augmented suite T1 = T0 ∪ Ttask , built once per task regardless of how many trials the task has. 

Randomized audit with cross-trial witness sharing. Task analysis cannot anticipate every way a trial may go wrong, so T EST JACK complements it with per-trial audits on randomly sampled trials whose witnesses are shared with every other trial of the task, exploiting the fact that trials share failure modes. Let T denote the current test suite, initialized to T1. Trials that fail any test in T

are refuted, and the remaining trials form the active set A. The loop then proceeds in rounds: (i) sample a trial s uniformly at random from A; (ii) run the per-trial audit of §3.2 on s; (iii) if the audit confirms witnesses W , add W to T , share W by executing it on every trial in A, and refute all trials that fail; (iv) otherwise, mark s as audited-clean and remove it from A. The loop terminates when 

A is empty or the working budget is exhausted. Sharing is sound because a witness belongs to the task rather than to the trial on which it was found. The first two conditions of Eq.(2), that t checks a requirement in Q(P ) and passes on R[G], do not involve s at all, and the reviewer agent judges them against P rather than against the trial. Thus, once a witness is accepted, deciding whether it refutes another trial reduces to the third condition. The scheme is economical because generating and validating tests is expensive, whereas replaying a test on another trial costs a single execution. Each audit round pays the generation cost once while its witnesses are shared with the entire active set, so when trials share failure modes, the number of expensive audits approaches the number of distinct defects rather than of defective trials. The trade-off is coverage: shared witnesses are not re-judged for each trial they refute, and defects unique to never-sampled trials can be missed under a finite budget (§4.3).

4.2 RQ1: Per-Trial Auditing on Frontier Benchmarks 

We run the per-trial audit of §3.2 on every benchmark-passing trial (Table 2). T EST JACK refutes 1,545 of 4,487 trials (34.4%), lowering the resolution rate over all 8,862 trials in scope from 50.6% to 33.2%; each refutation is backed by a witness test that checks a requirement of the prompt, passes on the ground truth, fails on the trial, and survives re-judgment. Roughly one in three successes thus violates the task requirements despite passing the benchmark’s own verifier. The refutation rate ranges from 7.6% on SWE-bench Verified to 53.6% on SWE-Marathon, and careful verifier design does not remove the problem: the from-scratch verifiers of DeepSWE and SWE-Marathon yield the two highest rates (43.5% and 53.6%). 4.4 RQ3: Comparison with Existing Benchmark Augmentation

4.5 RQ4: Ablation Study 

We compare task analysis only , which refutes trials using only the augmented suite T1, with the full lightweight approach at the RQ2 budget (Table 4). Task analysis alone refutes 345 trials and recovers 13.4% of the per-trial refutations: some gaps in T0 are visible before any submission is examined, and this trial-independent suite is built once per task. Adding randomized auditing with witness sharing raises recall to 72.4%, a 5.4 × increase, at essentially unchanged precision (49.3% vs. 49.2%), and the pattern holds on every benchmark. The stages are thus complementary in cover-age: most refutations require evidence from a concrete submission, which the second stage supplies without lowering agreement with the per-trial audit. 

## 5 Conclusion 

We present T EST JACK , an automated framework that audits the successes reported by coding bench-marks by evolving the evaluator rather than trusting the fixed tests shipped with them. T EST JACK 

audits each benchmark-passing trial with prompt-grounded differential testing: it writes tests for the requirements of the task prompt, certifies each test against the ground-truth solution, and re-judges every failure against the prompt, so that each refutation is backed by a replayable witness test. Its lightweight variant combines prompt-based task analysis with randomized trial auditing and reuses validated tests across all trials of a task. On 4,487 benchmark-passing trials of frontier agents across five benchmarks, T EST JACK refutes 34.4% of them, including 43.5% on DeepSWE, whose veri-fiers were written specifically to avoid weak tests, and lowers the overall resolution rate from 50.6% to 33.2%. The lightweight variant recovers 72.4% of these refutations at 15.4% of the cost, with 7.3 × the recall of the benchmark augmentation method SWE-ABS. These results suggest that fixed test suites substantially overstate the capability of frontier coding agents, and that evaluators should evolve with the submissions they judge.

## A Method Discussion 

A.1 Task Well-Formedness Assumption 

TEST JACK assumes that every task in the benchmark suite is well-formed in the sense of Eq.(1), which is, B(T0) ⊆ B (P ) ⊆ B (G). The assumption can fail in three ways, none of which we consider in this work: • B(T0)̸ ⊆ B (P ): the official tests assert behavior that the prompt does not require. A trial can then be marked failing even though it satisfies everything the task asked for, so the benchmark verdict we audit is itself unfair to the trial. • B(P )̸ ⊆ B (G): the prompt requires behavior, whether stated or implied, that the ground truth does not implement. Oracle validation would then discard a legitimate witness test, because a test of that behavior fails on R[G] and never reaches the trial. • B(T0)̸ ⊆ B (G): the official tests assert behavior the ground truth does not exhibit, i.e., the ground truth does not pass the tests the benchmark scores against. The two artifacts T EST JACK relies on then contradict each other, and neither can serve as a reference. The third case is largely ruled out by benchmark construction, since the benchmarks we audit verify that the reference solution passes the official tests before a task is released (§4.1). The first two are properties of task quality that a trial-level audit cannot repair: they call for fixing the task rather than for judging any particular submission. A related but distinct failure arises when Eq.(1) holds for the task author but not for the agent that reads P , which we treat separately in §A.2. 15 A.2 Implicit Requirements and Prompt Underspecification 

Explicit requirements in Qe(P ) are always clear to interpretation, but implicit requirements in 

Qi(P ) are harder. Task authors routinely omit requirements they expect any reader to infer, fol-lowing the maxim of quantity [14, 15], much as customers never state the “must-be” features they take for granted [19]. When author and reader share this background, the omission is harmless. When they do not, the prompt is underspecified: the ground truth implements the behavior and no official test checks it, but whether a trial must implement it is ambiguous (Figure 1, right). A failing witness then reflects a defect of the prompt rather than of the trial.

From the reader’s perspective, ∆( P ) belongs to the incidental part of Eq.(3), so the nesting in Eq.(1) holds for the author’s reading of P but not for the agent’s. A witness in ∆( P ) passes on R[G] and fails on R[s], yet the trial is faithful to the prompt the agent actually saw. Separating ∆( P ) from BRi (P ) requires knowing what a reader can infer, which is not directly observable. T EST JACK therefore uses the evaluated models themselves as readers. TEST JACK separates the two cases for every witness test tq that the reviewer agent accepts. Such a test checks a requirement q that T0 does not check, and tq (R[G]) = pass by construction. Two signals decide the class of q. First, q is explicit if the audit agent’s requirements checklist can quote a clause of P that states it, and implicit otherwise. Second, the trials of the task reveal whether q is inferable from P . We say that a model skips q if most of its passing trials on the task fail tq , and let ρ(q) be the fraction of models with passing trials that skip q. Counting models rather than trials keeps a model with many repeated runs from dominating. T EST JACK then classifies q empirically as follows. • Necessary, explicit (q ∈ Q e(P )): the prompt states q, so every trial that fails tq is refuted, however many models skip it. The defect lies in the insufficient tests .• Necessary, implicit (q ∈ Q i(P ) and ρ(q) ≤ 1/2): most models implement q without being told, which shows that it is inferable from P . Trials that fail tq are refuted, and the defect again lies in the tests. • Ambiguous (q ∈ Q i(P ) and ρ(q) > 1/2): most models skip a requirement the prompt never states. The defect lies in the underspecified prompt , and trials that fail tq are not refuted on its basis. In terms of Eq.(3), the three classes correspond to the stated part, the inferable part BRi (P ) \ B (T0),and the ambiguous part ∆( P ), with ρ(q) serving as an empirical test of whether q lies in BRi (P ).Tests for incidental behavior, which the prompt does not require at all, are already rejected by the reviewer agent (§3.2). Because ρ(q) depends on the trials of all agents, the classification is a property of the task and is computed once over the full trial corpus. Skipping is not the same as ambiguity. Agents may recognize an implicit requirement and still skip it, since test-based rewards give no credit for untested behavior and agent harnesses often instruct agents to make minimal changes [13]. Models may also collapse onto the same misreading of a task [28]. The ambiguous class can therefore contain requirements that are clear but widely skipped. We report the tasks with such ambiguity in Appendix B.2 together with some cases studies. 16 A.3 Randomized Trial Auditing

B.2 Underspecified Prompt 

We apply the requirement classification of Appendix A.2 to the witness tests produced by the lightweight approach. A requirement is ambiguous when the prompt does not state it and most models with passing trials on the task skip it, and we call a task’s prompt underspecified when at least one of its requirements is ambiguous. Under this rule, 29 of the 113 DeepSWE tasks (25.7%), 3 of the 13 audited SkillsBench tasks, and both audited SWE-Marathon tasks have underspecified prompts and Table 6 lists them. Underspecification thus arises even in benchmarks whose prompts were written from scratch and reviewed by their authors, and it affects every benchmark to which we apply the lightweight approach. These tasks contribute to the lower precision noted in Table 3: on them, whether a trial that departs from the reference solution also violates the prompt is itself 18 ambiguous, so the lightweight approach and the per-trial audit can reach different verdicts on the same trial. 

Case studies. We examine two DeepSWE tasks from Table 6 in detail. In both, every audited trial passes the official tests, and the lightweight approach produces a witness test that passes on the reference solution and fails on every trial. Neither witness, however, exposes a defect of the trials. Each fixes one of two coherent readings of the prompt, namely the reading that the reference solution happens to implement. 

Case 1: textual-richlog-follow-state . The task asks Textual’s Log and RichLog 

widgets to preserve the user’s viewport after the user scrolls away from the newest entries, and intro-duces an is_following_end flag, a follow_end() method, and a FollowChanged mes-sage. The prompt states that “while auto_scroll is enabled, new writes should follow only when the widget is already following the end”, but it never defines what is_following_end denotes. Two readings remain available. Under a position reading, the flag is true whenever the viewport is at the end, and auto_scroll separately decides whether new writes scroll the view. Under an 

effective-follow reading, the flag is true only when automatic following is enabled and the viewport is at the end. The readings agree whenever auto_scroll is enabled and diverge only when it is dis-abled, which is precisely the case that the qualifier “while auto_scroll is enabled” leaves open. The reference adopts the effective-follow reading: it initializes the flag from auto_scroll and refreshes it as auto_scroll and is_vertical_scroll_end . The witness test mounts an empty Log(auto_scroll=False) and RichLog(auto_scroll=False) and expects both flags to be False . All 30 audited trials instead adopt the position reading, report True , and fail. The failure occurs before any content is written, so it concerns only the meaning of the flag and not the scrolling behavior that the task is about. The official tests check the initial state only with 

auto_scroll enabled, where both readings produce the same result. 

Case 2: updo-policy-alerting . The task adds policy-based alerting to Updo. A monitored target enters a down state after a configured number of consecutive failures and recovers after a configured number of consecutive successes, and each evaluation returns a decision that carries the event, the state, and the current counters. The prompt requires that target_recovered 

be emitted “only after consecutive successful checks” and that every returned decision match the tracker state. It does not specify whether ConsecutiveRecoveries records the streak that triggered recovery or only the progress toward a recovery that has not yet occurred, and therefore whether the counter is reset before the recovery decision is returned. The omission is conspicuous, since the prompt does state when the latency-breach counter resets. The witness test configures one failure to enter the down state and two successes to recover, and inspects the decision returned by the second success. The reference increments the counter, resets it to zero upon recovery, and only then constructs the decision, so it reports ConsecutiveRecoveries = 0 . All seven audited trials emit target_recovered with the correct state, previous state, and reason, but report the completed streak of 2, and fail. Both behaviors yield a self-consistent snapshot of the tracker, and the official tests assert the event, the states, and the reason of the recovery decision but not its counter. Whereas Case 1 turns on two readings of a named piece of state, this case turns on an implementation choice, the timing of a reset, that the prompt leaves entirely to the implementer. 

Discussion. In both cases the requirement checked by the witness is implicit, and every model with passing trials on the task skips it, so the classification of Appendix A.2 labels it ambiguous. The cases also show that such gaps are inexpensive to close. For Case 1, a single sentence stating that 

is_following_end equals auto_scroll and is_vertical_scroll_end , together with an acceptance example for the disabled case, removes the ambiguity. For Case 2, a sentence stating that the counter resets before the recovery decision is constructed, together with the failure-and-recovery sequence above as an acceptance example, does the same. The witness tests that TEST JACK withholds from refutation therefore remain useful: they pinpoint where a benchmark’s prompt should be clarified. 19 C Case Studies

C.2 Cases in the Lightweight Approach 

The lightweight approach reaches a verdict for a whole task in two stages: prompt-based task anal-ysis builds the augmented suite T1 and refutes every trial that fails it, and the randomized loop then audits a few sampled survivors and replays the confirmed witnesses on the rest (Algorithm 1). We follow one DeepSWE task, httpx-deterministic-cookie-store , through both stages to show what each contributes and why the cheap stage does not subsume the expensive one. The task asks for a public httpx.CookieStore that extracts cookies from responses and builds outgoing 

Cookie headers, with deterministic ordering and eviction, expiry, domain and path matching, pre-fix rules, and mapping operations, while leaving existing behavior unchanged unless the new store is used. Of the trials in our corpus, 42 pass the official verifier, whose suite is substantial: it con-structs both Client(cookies=store) and AsyncClient(cookies=store) , imports a 

CookieJar , checks ordinary domain matching, and confirms that an extracted Secure cookie is withheld from an HTTP request. T EST JACK nonetheless refutes 24 of the 42, as summarized in Table 9. 

Stage 1: requirements the official suite never exercises. Task analysis reads the instruction, the repository, and T0 without access to any trial, and maps requirements onto the tests that check them. For this task it produces nine tests, of which two discriminate on the audited cohort; together they refute 11 of the 42 trials, leaving 31. Both target requirements that the prompt states outright and the official suite exercises only in part. The first concerns where the store may be used. The instruction requires the store to work anywhere 

cookies= is accepted, but T0 supplies it only to the client constructor, never as a per-request argument. The added test passes a non-empty store to a single request and expects a correctly built header. Nine trials fail it, and all nine fail the same way:             

> BaseClient._merge_cookies -> legacy Cookies.update -> stdlib cookiejar -> AttributeError: ’str’ object has no attribute ’domain’

These trials recognize the new container on the constructor path and leave the merge path on the old wrapper, which iterates the mapping into cookie names where the jar expects cookie objects. The reference solution instead converts at the merge boundary, building a CookieStore whenever either side of the merge is one. The second concerns which inputs update() accepts. The instruction enumerates 

CookieStore , httpx.Cookies , CookieJar , dictionaries, and lists of pairs; T0 covers every form except the httpx.Cookies wrapper. The added test supplies exactly that form:          

> store =httpx.CookieStore() store.update(httpx.Cookies({"a": "1"})) request =httpx.Request("GET", "https://example.org/") store.set_cookie_header(request) assert request.headers.get("cookie") == "a=1"

Two trials leave the store empty and produce no header, because they accept the underlying jar but not its wrapper, which the reference unwraps before importing. Neither test needs a defective patch to motivate it: both gaps follow from comparing an enumerated requirement with the call sites T0

actually exercises, which is precisely the evidence available to task analysis. 

Stage 2: defects that only a concrete trial reveals. The randomized loop then samples three of the 31 survivors, one per audit round, and the confirmed witnesses are replayed on the whole survivor pool. Each round inspects one implementation and generalizes the defect it finds into a test justified by the instruction. 23 The first round samples a gpt-5.5 trial that normalizes cookie domains with 

.lstrip(".").rstrip(".") , treating leading and trailing dots as interchangeable. For a response from example.org carrying Domain=example.org. , stripping the trailing dot turns a domain that should not match into one that does, so the cookie is stored instead of rejected. The reference removes leading dots only and then applies its matching helper. The witness checks that the cookie is rejected; the underlying defect, normalization that widens acceptance, is invisible from the task text alone, since the instruction invokes standard domain matching without spelling out trailing dots. The second round samples a claude-opus-4.7 trial that re-imports jar cookies through the public setter self.set(name, value, domain, path) . The setter takes no Secure ar-gument, so the import preserves the visible name, value, domain, and path while silently dropping the scheme restriction. The two witnesses import a Secure cookie from a raw CookieJar and from an httpx.Cookies wrapper, then assert that it is withheld from an HTTP request; the ref-erence copies the Secure flag and the expiry when importing. This defect sits in an interaction that no checklist of individual API names would catch: T0 checks jar import with a non-secure cookie and checks Secure only on the extraction path, so both features pass separately while their combination fails. The third round samples a claude-opus-4.8 trial that widens the scheme policy instead:      

> is_secure =url.scheme.lower() in ("https", "wss")

The instruction says Secure cookies are sent only over HTTPS, so the witness applies a stored 

Secure cookie to a wss:// request and expects no header. The reference restricts the scheme to HTTPS exactly. 

What the two stages contribute. Replaying the four audit-generated witnesses on the 31 survivors refutes 13 further trials, so the loop’s three expensive audits transfer to more than four times as many trials as they inspect. Of the 42 trials the benchmark accepts, 24 (57.1%) are refuted, 11 by task analysis and 13 by the randomized loop, and 18 survive. The two stages find different kinds of defects. Task analysis finds requirements that the prompt enumerates and T0 leaves unchecked, which is why its tests are cheap to derive and refute trials in bulk. The randomized loop finds defects that live inside implementation choices, namely a normalization helper that widens acceptance, a setter that silently drops metadata, and a scheme predicate with one extra entry, none of which is visible from the prompt and the official tests alone. Every witness here checks a requirement classified as necessary (Appendix A.2), so all 24 refutations stand. The replay result also reflects one execution of the loop: the sampled trials are themselves members of the pool, and a different sample would fix the witnesses in a different order, so the count of rounds needed to reach this outcome is not fixed by this run alone.

## E Limitations 

We summarize the main limitations of T EST JACK and of our evaluation. 

Dependence on a reference solution. TEST JACK relies on a reference solution to certify every new test, so benchmarks that ship only a prompt and a test suite fall outside its scope. It further assumes that each task is well-formed, i.e., that its tests, prompt, and ground truth are mutually consistent (Appendix A.1); tasks that violate this assumption call for repairing the task rather than re-judging its trials. 35 LLM-based auditing. The audit and reviewer agents are themselves LLMs, so a refutation is only as reliable as their reading of the prompt. Oracle validation guarantees that every witness asserts behavior the ground truth exhibits, but not that the prompt requires it. This judgment is delegated to the reviewer. Underspecified prompts, whose implicit requirements a reader cannot reliably infer, remain the main source of disagreement between our configurations (Appendix B.2). 

Coverage and precision of the lightweight approach. The lightweight approach trades coverage and precision for cost. Each audit round targets the defects of one sampled trial, so defects that are confined to trials it never samples can be missed under a finite budget, and tasks with few passing trials offer little opportunity to amortize an audit across trials. Moreover, the lightweight approach will amplify the noise in trials and the ambiguity in the prompt and diffuse across other unaudited trials, which has negative impact on precision. 

Scope of the evaluation. We audit trials from a fixed set of frontier models and excluded Skills-Bench and SWE-Marathon tasks that are not coding tasks, require a GPU, or are ultra-long-horizon projects (§4.1), so our refutation rates may not transfer to other agents or task types. Recall and precision in RQ2–RQ4 measure agreement with the per-trial audit rather than with a human-labeled ground truth. 36

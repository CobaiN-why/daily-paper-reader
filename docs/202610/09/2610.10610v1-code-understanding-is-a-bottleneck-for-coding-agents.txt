ABSTRACT 

Repository benchmarks (e.g., SWE-bench) for coding agents often assume that lines of code edited can predict task difficulty, but such datasets’ poor control over code and task types makes it hard to know which abilities truly drive agent errors. We present C ABRA : a Coding Ability Blueprint for Rigorous Agent evaluation. C ABRA builds tasks from scratch as call graph transformations and scales difficulty via a task size parameter on four axes: function traversal, search, runtime resolution, and instruction following. We run eight LLMs and six coding agents on 6,840 C ABRA tasks to show: 1) LLM accuracy falls as task size grows, but agents stay near-perfect by offloading work to tools (e.g., grep ); 2) Larger C ABRA tasks elicit more tool calls for reading and analysis, while a separate study on SWE-bench Verified shows these tool call counts predict agents’ accuracy better than lines of code edited— suggesting task difficulty for agents can lie in understanding code to edit, not just in making edits; 3) Extending C ABRA to an intense understanding task where models analyze divergent logic across two classes backs this finding, as agent accuracy finally falls. More broadly, we argue for synthetic evaluations like C ABRA to unmask LLM weaknesses trivialized by tools (e.g., needle-in-a-haystack) and abilities beyond just editing (e.g., understanding) that coding agents still find difficult—pairing SWE-bench-style tasks with controlled diagnosis. 1

1 INTRODUCTION : H ERDING CODING AGENT ABILITIES WITH CABRA 

Coding agents execute user queries by reasoning about, editing, and running code (Chen et al., 2021). They are often evaluated on benchmarks where researchers collect GitHub repositories, then augment them with problem statements and test cases as issue resolution tasks (Jimenez et al., 2024). Progress in coding agents requires knowing when agents fail, but repository-augmented benchmarks impede this. Tasks jointly differ in their code and task types, supporting only correlational analyses (Mehtiyev & Assunção, 2026) that can misidentify why agents fail. For example, Deng et al. (2026) attribute agents’ low accuracy in SWE-Bench Pro to agents editing more code, but our analysis shows that agents also have low accuracy when they read, analyze, and test their codebases more (§4.3). To escape such confounders, researchers have long relied on synthetic tasks that isolate model abilities, enabling evaluations of how model performance on these abilities scales based on task size (Merrill et al., 2020). For example, Needle in a Haystack (Kamradt, 2023) offers a controlled evaluation for long-context reasoning over adjustable corpus sizes. While prior work has extended this methodology to reasoning LLMs (Motwani et al., 2026) and RL environments (Stojanovski et al., 2025), it has not yet been studied in coding agents with vastly different behavior, thanks to their ability to call tools. We present C ABRA : a Coding Ability Blueprint for Rigorous Agent evaluation, a framework for generating programming tasks from scratch. Unlike repository-based benchmarks that derive tasks from codebases, C ABRA splits task design into two controllable steps: defining task types and defining how those tasks scale in size. We instantiate these two steps by generating programs from directed acyclic call graphs and transforming them into five task types (Figure 1 left, §2.1), then scaling those tasks across four axes synthesized from prior work: function traversal, function search, runtime resolution, and instruction following (Figure 1 right, §2.2). We generate 6,840 C ABRA task instances of increasing sizes (§3), while controlling for program and task type. By varying one scaling axis at a time across many codebases and tasks, we can ro-bustly surface axes that are hardest for models. We run eight LLMs and six coding agents in Copilot’s

Follow-up analyses suggest agents fail to reason over logical decomposition, over-rely on surface-level naming, and struggle to excise one-line differences. Our paper has implications for both researchers and developers. For researchers, we argue for more work in controllable tasks like C ABRA beyond SWE-bench-style tasks to attribute agent errors. For developers, we highlight code understanding as a key accuracy and efficiency bottleneck, suggesting a direction for future gains. To summarize, our core contributions are: 1. C ABRA , a framework that generates coding tasks by sampling task types and scaling their size, affording more controlled analyses than repository-derived benchmarks. 2. Evidence that once-elusive tasks for LLMs are now trivial for agents that execute code, and that code understanding is a scalable ability beyond edit volume to heighten task difficulty. 3. A challenging code merging task to help researchers track agents’ code understanding ability. 4. A taxonomy of agent tool calls and classifier to support future coding agent analyses.

2.1 TRANSFORMING DIRECTED ACYCLIC GRAPHS AS CODE EDITING TASKS 

To control our baseline code editing tasks, we use directed acyclic graphs (DAGs) to represent programs, and then transform them to define code edits. Each DAG C = ⟨V, E ⟩ is a function call graph, where vi ∈ V is a function and edge (vi, v j ) ∈ E means vi calls vj . Each function computes a random mathematical function of its input. For vi with many output vertices, vi chains the function outputs with random operations. Appendix A.1 describes the sampling process. Figure 1 has example DAGs/programs with floats; we also design string and array versions so our analyses generalize beyond a single code type (Appendix A.2 has examples). We finally add a __main__ block calling the root vertex in C. This synthetic code generation approach trades downstream realism for simplicity and tight control over tested coding abilities. We define five diverse tasks based on these DAGs to ensure our later task scaling analyses generalize beyond a single task type. We ground the tasks in Fowler (2018)’s catalogue of refactoring types, also used to derive Gautam et al. (2025)’s tasks in RefactorBench. Each task samples a graph Cinit 

that models do not edit and a graph Cedit that models must edit, combined into the input codebase C.We outline our tasks next, visualized in Figure 1 (left). 1. Remove Dead Code: We sample Cedit as a DAG representing functions that C never calls from 

main . The agent must remove all of the “dead” functions that exist in Cedit .2. Add Parameter: We sample Cedit as a DAG. Its one root function adds an input parameter (e.g., a multiplier) that must be passed down the call graph and applied at child nodes. 3. Add Return: (2)’s inverse: we flip Cedit ’s edges to have one sink node. The sink function adds a return value (e.g., a string key) that must be passed all the way up the call graph. 4. Cache Function: We sample Cedit as a tree and call slow() at child nodes. Models move 

slow() to the lowest common ancestor and pass its value down to cut redundancy. 5. Don’t Repeat: The inverse of (4): we flip Cedit ’s edges, then at each child node, we call 

get(val) and apply its output. Agents move get to the first common descendant and pass its value up, i.e., the DRY principle (Hunt, 1900, Don’t Repeat Yourself). We sample edges between Cinit and Cedit with probability β = 0 .3 (except in Remove Dead Code, or 

Cedit is no longer dead code). For each task, we develop a problem statement that explains how to solve the task with an example (all problem statements in Appendix A.11). 2.2 SCALING TASK SIZE ACROSS COMPLEXITY AXES 

We now scale the size of our base tasks on four axes (Figure 1, right). Each axis stress-tests a coding ability by scaling one aspect of the task via a size parameter n. Our axes do not cover all abilities that agents need, but have been studied in prior work and argued as useful for downstream coding tasks. As §5 shows, C ABRA can be readily extended to other coding abilities of researchers’ interest. The main scaling axes we define are (summary in Table 1): 1. Function Traversal: Tasks such as refactoring often require models to propagate edits throughout codebases by tracing call graphs—a commonly-studied graph traversal ability (Wang et al., 2023). This axis scales the number of functions models must edit |Vedit | = n.2. Function Search: Models often search through large codebases to decide which sections require edits. This axis scales the number of functions agents do not need to edit |Vinit | = n, mirroring Needle in a Haystack evaluations for long-context reasoning (Kamradt, 2023). 3. Runtime Resolution: Coding tasks may force models to trace increasingly long computations to re-solve runtime values (Gu et al., 2024, e.g., CRUXEval). To test this, we wrap an if check(): 

3Preprint around identical code blocks and have models only edit blocks that run. We scale the size of resolving check() via a Collatz-based function (Lagarias, 1985) whose for loop runs for n

steps (Code Block A.4), requiring n steps of reasoning to resolve. 4. Instruction Following: Users issue long queries when models should make more edits at once— often assessed via instruction-following benchmarks (Pyatkin et al., 2025). We define task size by appending n distinct instructions to our problem statement, requiring models to also add asserts, comments, temporary values, etc. (full list in Appendix A.2). This axis is unusable with “Remove Dead Code” (§2.1), as deletion is the only valid action.

We display aggregated results on our four complexity axes in Figure 2, with takeaways below: 

LLM-Hard ⇏ Agent-Hard. LLM accuracy drops with n, but agent accuracy is mostly constant and often near perfect. This is not just due to differences in backbone LLMs, as GPT-5.4 Mini and GPT-5.5 degrade in accuracy as LLMs, but score consistently as agents (except instruction following). Appendix A.5 has the same trend with a subset of C ABRA tasks with Gemini models. Tasks of certain complexity or size that challenge LLMs may no longer challenge agents, so evaluating agents’ limits will either require scaling task sizes to colossal n (Sinha et al., 2026) or new axes for complexity. We pursue the latter path in §5. 

Weaker LLMs can Climb via Harnesses. GPT-5.4 Mini, when used in an agent harness, surpasses stronger LLMs without tools (GPT-5.5, Grok) in non-instruction following tasks for n > 100 . Thus, developers do not always need large LLMs in harnesses; small LLMs that generate and compose tool calls well can generalize to larger tasks (Zhang & Khattab, 2026). 

Tools Let Agents Graze Codebases. To explain agents’ near-perfect accuracy, we analyze execution traces. Agents often write and run “meta-scripts”: ast code to move variables in function traversal, 

grep to locate names in function search, or exec() to learn outputs in runtime resolution. LLMs often generate more natural language reasoning as task size grows (Figure A.7), but some tasks let agents write scripts with fixed reasoning invariant of n.The exception is instruction following—rules struggle to map natural language to edits (Zan et al., 2023)—which is also the only axis where agents degrade ( n = 200 , except Opus). A new consider-ation for synthetic tasks with agents is whether tools bypass intended task size. As we show in §5, there are scalable axes beyond instruction following that are hard to script. CABRA ’s synthetic tasks offer control but lack ecological validity (de Vries et al., 2020), so we test our hypothesis—code understanding beyond editing explains task difficulty in agents—on more realistic tasks. We collect released mini-swe-agent trajectories on SWE-bench Verified (Yang et al., 2024) from Claude-4.5 Opus/Sonnet, Gemini-3 Pro/Flash, GPT-5.2, and GPT-5 Mini. We study how the edited lines of code in the agents’ final solution (a commonly-used difficulty metric (Deng et al., 2026; Raghavendra et al., 2026)) versus our tool call metrics from §4.2 (by running our classifier on these traces) relate to two measures of task difficulty: SWE-bench’s human-annotated difficulty levels and agents’ accuracy (linked to their traces). 

Edits are not the scapegoat for human-rated difficulty. SWE-bench tasks come with difficulty levels based on the time developers estimate humans would need to finish them (L1 ≤15 min; L2 = 15 min – 1 hr; L3 = 1–4 hours; L4 ≥4 hours). Most metrics rise with level (Figure 4, left): longer tasks elicit not just more edits, but also reading, analysis, and testing. Since metrics grow jointly, SWE-bench alone cannot discern when errors stem from edit volume or understanding how to edit—motivating controlled evaluations such as C ABRA .

Understanding predicts errors better than edit count. We measure the point-biserial correlation 

r (Tate, 1954) between agent accuracy and each metric. All r are low: it is tough to predict errors, further motivating C ABRA -style tasks for more control. The number of understanding tool calls (defined as R EAD plus A NALYZE calls) is most strongly correlated with accuracy (Figure 4, right), more so than E DIT token use and lines edited. Overall, this further underlines the key role code understanding plays in the evaluation of coding agents. 

5 INTENSE UNDERSTANDING TASKS CAN MAKE CODING AGENTS BLEAT 

While work often scales edit size toward harder coding agent tasks, §4 suggests to control agent accuracy via an analogous understanding size : how much understanding occurs before editing. We instantiate tasks by first sampling ℓ line nodes; each line defines a new variable by chaining input parameters, past variables, and non-zero integer coefficients in [−5, 5] via sums and products. We randomly select d divergent line nodes, done by either: 1) flipping a sign; 2) editing a coefficient; 3) editing a variable; or 4) adding an extra term. To make the code surrounding these differences behaviorally equivalent while syntactically dissimilar, we use five transformations: 1) rename variables; 2) shuffle commutative lines; 3) decompose/merge lines of code; 4) distribute multiplication (3a = a + a + a); and 5) swap term order ( a + b = b + a). We prompt agents with one example and ask for the most efficient edit, i.e., keep as much code as possible in the parent class (Prompt A.6). Agents receive a score of 1 iff they preserve behavior (black-box testing, §3.1) and each child class has d different lines of code maximum. 5.2 UNDERSTANDING WHEN UNDERSTANDING IS CHALLENGING 

We now scale the size of our code equivalence task (§5.1) to probe agents’ code understanding abilities. We first confirm that scaling one axis—(1) the total lines of code per class—raises understanding effort and lowers accuracy. We then study two more scaling axes: (2) the total transformations agents reason over; and (3) the number of differing lines they must locate. 

1) Comparing Lines of Code. We sample 50 tasks while scaling ℓ ∈ { 5, 10 , 25 , 50 , 100 , 200 },increasing the combinations of lines of code that could be understood and compared. Higher ℓ

drops agent accuracy (Figure 5b), 2 and elicits far more U NDERSTAND than E DIT tools (Figure 5c)— supporting that understanding is a weakness in coding agents that can be improved. 

2) Aligning Logic. We hypothesize that our understanding task is hard as it requires aligning syntac-tically distinct but semantically equivalent code (Churchill et al., 2019). Thus, we test the equivalence transform types agents must align as complexity axes for understanding. We ablate transforms at ℓ = 50 : adding each to a no-transform baseline (Figure 6, left) and removing each from an all-transform baseline (Figure 6, middle). Multi-line edits and distributive multiplication cause large drops when added—for Gemini specifically (Appendix A.10)—failing on multi-hop alignment (Zhang et al., 2025a). Removing variable renaming boosts accuracy most, so agents may rely on shallow naming to understand code (Lam et al., 2025). 

3) Locating Differences. When agents edit, they generally follow the two-step process of: (i) locating lines that differ; and (ii) executing the refactor. To disentangle where errors occur, we study both metrics in §5.1. Agents preserve code behavior in over 90% of cases, so most failures stem from (i) versus (ii); agents keep too many lines in the child class, failing to find one line differences. We further probe this weakness by varying the number of differing lines d ∈ { 1, 3, 5} while holding lines of code ℓ fixed. Accuracy erodes as d grows (Figure 6, right), validating agents struggle increasingly as they need to identify more behavioral differences.

6 RELATED WORK 

To ground C ABRA , we synthesize work on code evaluations, agent errors, and synthetic tasks. 

Evaluating Code Models. Code generation is a long-studied task (Hindle et al., 2012). Early evaluations used NL-to-code translation tasks (Oda et al., 2015; Yin et al., 2018), then scaled difficulty with algorithm tasks based on contests like LeetCode (Chen et al., 2021; Li et al., 2022; Jain et al., 2025). The boom of agents that compose LLMs and tools (Yao et al., 2023) motivated harder tasks like issue resolution (Jimenez et al., 2024; Zan et al., 2025) and full app generation from specifications (Si et al., 2025; Zhao et al., 2025). To scale difficulty, work adds more edits (Deng et al., 2026; Raghavendra et al., 2026), multi-turn prompts (Le et al., 2026; Laban et al., 2026b), and extra requirements (Ding et al., 2026; Yang et al., 2026). We also show that understanding is a less studied but key axis to control difficulty. While such tasks simulate real use, they struggle to diagnose model errors, as they differ on many confounded axes. We review these limitations then discuss synthetic tasks as a solution. 

Agent Failures. Knowing model failures drives progress. For coding agents, work often studies properties of failed traces on repository benchmarks (Cemri et al., 2025) like execution strategy, tool call type, and length—relating them to agent accuracy to guide methods (Majgaonkar et al., 2025; Liu et al., 2025b; Mehtiyev & Assunção, 2026). However, analyses are correlational—tasks also vary in codebase and task—making it hard to attribute failures, and correlations are often poor (§4.3). We argue C ABRA -style tasks that control such confounders are better for this goal, which we use to surface agent weaknesses in code understanding. 

Synthetic Tasks. Compared to repository benchmarks, synthetic tasks can better probe model errors (Merrill et al., 2020). Tasks like bAbI (Weston et al., 2016; Tamari et al., 2022) and Needle in a Haystack (Hsieh et al., 2024; Kim et al., 2025) test limits of a model ability (e.g., long-context) by defining tasks (e.g., locate a passkey) and scaling their size (e.g., corpus size); we use this two-stage approach for C ABRA . Recent work extends this to reasoning LLMs: LongCoT for long-horizon execution (Motwani et al., 2026) and RELIC for context-free grammar recognition (Petty et al., 2026). In code specifically, related work includes CruxEval for code tracing (Gu et al., 2024) and Bug in the Code Stack for codebase search (Lee et al., 2024), which form our initial C ABRA tasks. There are also synthetic RL environments to train coding agents (Yang et al., 2025b; Zhu et al., 2025), but their use of existing repositories or LLM-generated data impede full control over tasks, unlike C ABRA .Different from all of these works, we explore task complexity in coding agents. Our main contribution is exposing that many “LLM-hard” tasks are trivial with tool use—task complexity must evolve for agents—then surfacing and probing code understanding as a model weakness. 

7 CONCLUSION : R AISING THE BAA -R FOR CODING AGENT EVALUATIONS 

Using C ABRA , we show the number of edits alone is a poor proxy for coding agent task difficulty and instead surface code understanding as a key factor. Across our initial task axes, editing effort scales insufficiently with task size. In contrast, we reveal that code understanding more often scales with task size across diverse axes and more reliably predicts SWE-bench Verified errors. We establish this link concretely with our code merging task and surface facets like multi-line decomposition and readability where agents still struggle, motivating threads for future work. 

Controlled Evaluation. CABRA -style tasks can both attribute agent error and form axes to probe them. We use tools for diagnosis, but future work can study problem-solving methods (Gao et al., 2024) and error recovery (Huang et al., 2024). The next step is imbuing such weaknesses into SWE-bench-style tasks as more realistic evaluations (Saxon et al., 2024). 

Agent-Understandable Code. Agents struggle to compare programs with renamed variables (§5.2), showing some code types are harder to understand. Future work could test if repository indexes (Luo et al., 2026), memory (Zhang et al., 2025b), and readability practices (Buse & Weimer, 2009) help agents. As understanding can encompass up to 70% of SWE work (Minelli et al., 2015), 19% of real coding requests (Baumann et al., 2026), and already demands effort in C ABRA and SWE-Bench, progress here is key for maintainability (Le et al., 2026) and limiting context rot (Laban et al., 2026a). 9Preprint 

A Theory of Agents. Work on transformers’ limits (Bhattamishra et al., 2020) often uses synthetic tasks like C ABRA to empirically test theories, but tasks that were once hard for LLMs can now be trivial with tools (§4.1). Discerning “agent-hard” or “-easy” tasks will require formalizing the work used to call tools and work tools can execute (Meyerson & Qiu, 2025).

ETHICS STATEMENT 

Our paper shows that coding agents can struggle to understand code. Given the importance of understanding in real developer workflows (Minelli et al., 2015; Baumann et al., 2026)—coupled with evidence that programmers struggle to understand their code when working with agents (Shen & Tamkin, 2026; Balepur et al., 2026a)—there are risks for failing to address this problem. We hope that our paper brings more attention to evaluating understanding in coding agents.

A.1 DAG T ASK SAMPLING PROCEDURE 

We now describe our sampling procedures for the DAG-based tasks in §2. Given N vertices, we sample a height h ∼ Uniform(0 .45 , 0.55) and set the topological level count to round (N h). We set vertices across levels via Poisson draws, where mean λ is the number of vertices left to assign divided by the number of levels left. For each non-root vertex vj , we sample an incoming edge (vi, v j )

from an earlier level with an offset ∆ ∼ Geom(0 .9) , biasing edges to adjacent levels but allowing skips (i.e., i + ∆ = j). Figure A.1 shows example DAGs and Algorithm 1 summarizes the sampling procedure. A.2 EXAMPLE PROGRAMS 

We present examples of math, string, and array programs for the Add Parameter task (§2.1) in Code Block A.1, A.2, and A.3, respectively. Code Block A.4 shows the Collatz-inspired check() 

function (Lagarias, 1985) we use for runtime resolution, and Code Block A.5 shows an example of two Calculator classes in the code merging task (§5); the new line separates the synonymous from divergent code, but this formatting is stripped during evaluation. For the instruction following task, we use the following bank of rules: • Add a number: new_var = var + rand .• Subtract a number: new_var = var - rand .• Multiply by a number: new_var = var * rand .• Divide by a number: new_var = var / rand .• Add a character prefix: new_var = rand + var .• Add a character suffix: new_var = var + rand .• Replace a character: new_var = var.replace(rand, rand2) .• Surround a string with characters: new_var = rand + var + rand2 .• Assert that a value is unequal to a sampled value: assert var != rand .• Assert an upper bound: assert var < rand .• Assert a lower bound: assert var > rand .• Print a value with a prefix: print(prefix, var) .• Print a value with a suffix: print(var, suffix) .• Add an exact comment of the form # label: var .Sampling values for rand , prefix , and label allows us to scale the total number of unique instructions. A.9 EDITING TASKS WITHOUT MUCH UNDERSTANDING 

Our evaluations with C ABRA in §4 reveal two task types where scaling complexity changes behavior in agent tool calls: 1) U NDERSTAND tool calls increase while E DIT tool calls remain stable (i.e., function search and function traversal); and 2) Both U NDERSTAND and E DIT tool calls increase (i.e., instruction following). tool calls scale in both tasks without large changes in U NDERSTAND tool calls, especially compared to our first instruction-following task in C ABRA (Figure A.16). The number of E DIT tool calls does not scale for any task, but one can arbitrarily make a require more E DIT tool calls by forcing models to make smaller edits at a time. Overall, this further backs our argument that understanding and editing are distinct coding agent abilities that can be uniquely targeted and measured in evaluations.

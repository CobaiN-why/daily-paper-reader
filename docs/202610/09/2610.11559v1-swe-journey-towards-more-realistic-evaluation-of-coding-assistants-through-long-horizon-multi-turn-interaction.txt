## ABSTRACT 

Coding assistants such as Claude Code and Codex have become a major application of LLM agents, yet existing benchmarks remain far from real-world use, partic-ularly in task horizon and interaction length. Code assistants require completing long chains of development work in continuously evolving repositories, while re-peatedly clarifying requirements and adapting implementations through multi-turn interaction. To address these gaps, we introduce SWE-J OURNEY , a benchmark for more realistic evaluation of coding assistants. To address the task-horizon gap, we propose a weak-to-strong synthesis pipeline that automatically constructs long-horizon coding tasks. To address the interaction gap, we mine four represen-tative user personas from real interaction data and build a user-simulation agent to reproduce realistic code-assistance interactions. On average, models pass over 75% of tests for requested functionality with software architects, but fewer than 25% with non-coders. These results show that current coding assistants still fall short of enabling reliable coding for non-coders. We further analyze the reasons for this gap and identify asking right, finding right, and fixing right as key capabilities during interaction. 

## 1 INTRODUCTION 

Coding assistants such as Claude Code and Codex have become a major real-world application of LLM agents (Baumann et al., 2026; Yang et al., 2024). Realistic evaluation of coding assistants, how-ever, must capture two key characteristics. First, these tasks are often long-horizon: the engineering goals they address often require a substantial sequence of changes across files and modules, with later steps building on earlier ones (Desai et al., 2026; Shen et al., 2026; Baumann et al., 2026). Second, user interaction is multi-turn: rather than providing a complete requirements document for an entire long-horizon engineering goal upfront, real users introduce requests incrementally, provide feedback, sometimes leave requirements underspecified, and revise their goals in response to intermediate results (Hao et al., 2024; Zhong et al., 2025), with interaction patterns varying substantially across users and tasks (Zhang et al., 2025a; Baumann et al., 2026). A realistic evaluation must therefore capture both. Yet existing benchmarks only partially cover these characteristics jointly. One line of work (Deng et al., 2025b; Li et al., 2025; Thai et al., 2025) increases task difficulty and extends execution horizons, requiring broader context and sustained interaction with the repository, but typically presents the complete instance upfront and therefore leaves incremental requirement disclosure and adaptation to user feedback untested. Another line (Miao et al., 2025; Orlanski et al., 2026; Zhou et al., 2025) introduces multi-turn interaction through evolving requests, adaptive feedback, or simulated users, but often uses shorter interaction sequences and coarser user models than those needed to represent coding-assistant collaboration. As Figure 1 illustrates, prior work covers different portions of this design space, while the joint evaluation of long-horizon, stateful repository development and realistic multi-turn interaction remains underexplored.

SWE-JOURNEY (Ours) occupies the upper-right region, near the highest level on both axes: project-scale development involving building, replicating, optimizing, or evolving an entire system, together with user-grounded interaction shaped by user states, preferences, personas, and evolving goals. To close this gap, we introduce SWE-J OURNEY for long-horizon, multi-turn evaluation of coding assistants . Rather than simply combining prior advances along the two axes, we address the additional challenges of constructing long-horizon tasks and simulating realistic multi-turn interactions, advanc-ing both through an automated pipeline tailored to coding assistants. For task construction, rather than relying on costly expert annotation (Miao et al., 2025) or mining public repository histories with potential data leakage risks (Thai et al., 2025; Xu et al., 2026), we introduce a scalable weak-to-strong synthesis pipeline. Through subtask decomposition and iterative expansion, it produces sufficiently long and challenging tasks while generating new follow-up requirements beyond the public seed, thereby reducing direct solution leakage. For multi-turn interaction, we mine four recurring user personas from real interaction data and build a persona-conditioned user-simulation agent that cap-tures common user behaviors in coding-assistant interactions. This grounds interactions in observed user behavior while covering diverse interaction styles, enabling us to analyze where current coding assistants fall short. Our contributions are as follows: • Benchmark. We introduce SWE-J OURNEY , a benchmark that combines long-horizon coding tasks with realistic multi-turn user interactions in a single conversation, enabling evaluation under conditions closer to real-world coding assistance. • Long-horizon coding task synthesis. We propose a scalable weak-to-strong task synthesis pipeline that reduces task-construction cost and mitigates direct solution leakage, while producing tasks that require multiple rounds of interaction rather than a single synthesis attempt. • User simulation for coding assistance. We identify four recurring user personas from real interaction data and use them to condition a user simulator that generates evolving requests, corrections, and feedback in realistic coding-assistance interactions. • Findings. Each model passes approximately half or fewer of the functionality tests. For the Non-coder persona, the mean pass rate is even below 25%. These demonstrate the challenges that realistic user interactions pose for coding assistants. Fine-grained analyses identify asking right ,

finding right , and fixing right as key capabilities for coding assistants in realistic interactions. 

## 2 RELATED WORK 

Multi-turn coding benchmarks. Early repository-level benchmarks largely focus on single-turn, issue-level evaluation. SWE-bench (Jimenez et al., 2024) and SWE-bench Verified evaluate real 2GitHub issue resolution, while later extensions incorporate screenshots and visual information (Yang et al., 2025a), broader language and engineering coverage (Zan et al., 2025; Rashid et al., 2025), performance optimization (He et al., 2025; Ma et al., 2025), repository exploration (Zhang et al., 2026a), and code question answering (Peng et al., 2026a; Cai et al., 2026). These benchmarks, however, typically provide the task upfront. More interactive settings include scripted or progressively revealed rounds (Shastry et al., 2026; Orlanski et al., 2026; Shen et al., 2026), adaptive human feedback (Miao et al., 2025), and reactive or simulated users for goal discovery, clarification, and correction (King & Flanigan, 2026; Wu et al., 2026; Raghavendra et al., 2026; Zhou et al., 2025). However, existing benchmarks still lack a coding-assistance-specific taxonomy of persona definitions and sufficiently long interaction horizons. We address this by mining real interactions to define four representative personas and by synthesizing long-horizon tasks that elicit more interaction turns. 

Long-horizon coding benchmarks. A complementary line of work extends the task-horizon axis. At the feature level, benchmarks progress from localized issue fixing to repository-level feature im-plementation (Li et al., 2025; Zhou et al., 2026), natural-language-driven feature development (Chen et al., 2025; Deng et al., 2025a), and reasoning-augmented feature addition (Liu et al., 2026). SWE-bench Pro (Deng et al., 2025b) increases task size, breadth, and sustained difficulty. SWE-EVO (Thai et al., 2025) and RoadmapBench (Xu et al., 2026) construct longer trajectories around software evolution and version upgrades. ChainSWE evaluates sequential bug fixing, while SWE-Chain (Lam et al., 2026) and SWE-CI (Chen et al., 2026) study chained releases and regression risks under persistent repository state. At the project scale, Zhao et al. (2025) and Ding et al. (2025) build libraries or repositories from specifications; MirrorCode (Adamczewski et al., 2026) evaluates full-program reimplementation from behavioral access; and SWE-Marathon (Desai et al., 2026) targets ultra-long-horizon implementation, optimization, and research workloads. However, constructing such tasks remains challenging. Mining GitHub history enables answer-seeking retrieval: with only a bash tool, a strong model can locate newer repository versions online. In practice, constructing long-horizon coding tasks from scratch typically requires substantial expert involvement, making it expensive and difficult to scale. Even manually labeling a short SWE-Bench-style instance is estimated to cost approximately $100 per instance (Oliva et al., 2025), let alone constructing one from scratch. We therefore develop a fully automated pipeline for synthesizing long-horizon coding tasks at lower cost while reducing leakage risk. See Appendix A.1 for more related work on data synthesis. 

## 3 METHOD 

We introduce SWE-J OURNEY to enable more realistic evaluation of coding assistants by addressing two major gaps in existing benchmarks: long-horizon tasks (Figure 2 (A)) and multi-turn interaction (Figure 2 (B, C)). We first describe the design principles guiding the method. 3.1 DESIGN PRINCIPLES 

Weak-to-strong long-horizon task synthesis. One challenge is constructing sufficiently challeng-ing long-horizon tasks. We use automated data synthesis to generate a long sequence of follow-up requirements rather than directly reusing public issues, reducing data-leakage risk and lowering the cost from the roughly $100 required to only label a short task manually (Oliva et al., 2025) to $56.64 for synthesizing a long-horizon task from scratch. However, a synthesis model may struggle to gener-ate tasks beyond its own capabilities. We therefore adopt a weak-to-strong strategy: decomposing long-horizon synthesis into smaller subtasks, separately synthesizing each subtask’s components, and accumulating a reusable module-level skills library. These operations reduce the difficulty of each step and form the task-generation loop described in §3.2. 

Persona-driven multi-turn interaction. Simulating task completion through interaction for coding-assistant tasks is another challenge because the product serves a broad user base with different interaction styles. We operationalize this variation by extracting five persona dimensions and their taxonomy through data analysis of real interaction logs, yielding four representative personas. An LLM agent then simulates persona-consistent users, using two environment tools, two progress states, and a rubric to guide the interaction, as detailed in §3.3. 3Tool

Realistic evaluation for coding assistants. Traditional coding benchmarks ask the model to generate a patch and test its correctness offline, omitting two properties of coding-assistant use: (1) an assistant operates on the user’s actual working directory and should avoid destructive operations or substantial environmental changes; and (2) tasks may be sequential, with the same module repeatedly modified to achieve a larger goal. We therefore evaluate execution online to better match coding-assistant use, with a user-simulation agent, coding-assistant agent, and testing performed online in sequence, as detailed in §3.4. 3.2 LONG -H ORIZON CODING TASK SYNTHESIS 

Following the principles above, we adopt a weak-to-strong strategy: a weak synthesis model con-structs a final long-horizon task whose full requirements exceed the model’s capabilities. As shown in the task-generation loop of Figure 2(A), the loop has three components. 

Plan generation. To further distribute the difficulty of task construction, we first use a stronger model to plan the long-horizon task and then use a relatively weaker model to implement the plan. Specifically, we start from an existing repository and its environment and ask Claude Opus 4.8 (Desai et al., 2026) to generate a high-level task blueprint and its subtasks, making them as close as possible to realistic software-engineering needs. To this end, we provide a bash tool so that the model can run commands in the Docker container and understand the repository state, ensuring that the task is authentic and executable. We then introduce two input variables to ensure diversity: (1) a seed task, prompting the model to generate related tasks; and (2) a new task angle, prompting it to expand the seed task from that angle. We also require the generated task to exceed the seed task on at least two of four dimensions—context scope, change scope, requirement depth, and knowledge breadth—to avoid homogeneous outputs. Appendix A.2 details the taxonomy construction procedure and definitions of these four dimensions. 

Subtask implementation loop. Next, for each subtask in the plan, we use the relatively weaker model, GLM-5.2 (Zhang et al., 2025b), to implement it in code through a three-step loop, with each subtask building on the preceding code state. Step-request generation : following the plan-first strategy, we first construct a user query and natural-language acceptance criteria. The query serves as a blueprint for the problem to be solved, while the criteria serve as a blueprint for execution-based 4verification. Patch-and-F2P generation : guided by these, we generate a reference patch and Fail-to-Pass (F2P) tests—the reference patch realizes the query in code, and the F2P tests fail on the original code but pass after the patch, verifying in executable form whether a model-generated patch meets the criteria. P2P generation : since long-horizon tasks must show not only that new behavior is added but also that existing behavior is not broken, we further generate Pass-to-Pass (P2P) tests, which pass on both the original and patched code and detect unintended regressions. Throughout, besides the 

bash tool, we provide a reset tool that lets the model restore the worktree and check whether the current patch takes effect and passes the tests, thereby improving the success rate of task generation. 

Progressive task extension. The procedure above can complete all subtasks step by step, producing both the textual description and code implementation of a complete plan stage. A single stage, however, does not guarantee a task that is both sufficiently long and difficult. We therefore iterate, using the previous round’s task as the seed for the next plan stage and again increasing difficulty along at least two of the four dimensions in each round. We construct a total of three progressively harder plan stages to synthesize a sufficiently difficult task. 

Rubric and retry. To ensure task quality, we use runtime rubrics to assess whether the synthesized data is correct both semantically and in code execution. Specifically, we use two complementary signals. For rubric-based verification, a separate model, GPT-5.4 (Lee et al., 2025), scores plan generation against a task-authenticity rubric (realistic motivation, clear task boundaries, no oracle in-formation) and scores the Patch-and-F2P stage for semantic alignment among the request, acceptance criteria, and tests. Execution-based verification requires F2P tests to fail before the patch and pass afterward, and P2P tests to pass both before and after. On any failure, the model retries the current step with failure feedback until the attempt limit; if exceeded, the workflow returns to planning, since the fault may lie in an infeasible plan rather than the implementation. 3.3 MULTI -T URN INTERACTION VIA PERSONA -D RIVEN USER SIMULATION 

Based on the synthesized long-horizon tasks, we use a user-simulation agent to realize online multi-turn interaction and build trajectories resembling challenging code-assistance tasks. The simulation agent acts as the user, while the coding assistant under evaluation performs the coding tasks and interacts with it online. Figure 2(B, C) summarizes how we mine a persona taxonomy from real logs and derive the four representative personas driving this simulation. 

Persona taxonomy extraction. Since users of coding assistants are diverse and complex, with substantially different interaction habits, simply prompting an LLM to simulate them is insufficient; their styles must be specified in detail for code-assistance scenarios. To build a comprehensive taxonomy, we start from real usage data in SWE-Chat (Baumann et al., 2026), an open-source collection of Claude Code interaction trajectories, and mine the dimensions and categories that coding-assistant user personas should cover. We perform this taxonomy mining in two stages over the large-scale dataset. First, we ask GPT 5.4 to generate short labels describing each trajectory’s interaction style. We then cluster them using OpenAI TEXT -EMBEDDING -3-SMALL embeddings and capacity-constrained k-means to form balanced semantic clusters. Within each cluster, GPT 5.4 deduplicates near-identical labels and abstracts them into stable intermediate categories, yielding a clean global taxonomy. However, these categories may span multiple dimensions and are therefore often not mutually exclusive. To address this, we use GPT Deep Research to extract the dimensions, balancing broad coverage against redundancy. We then apply human feedback to resolve ambiguities and remove redundant coverage among the dimensions and their categories, yielding five persona dimensions: User Expertise, Detail Preference, Control Style, Goal Stability, and Verification Style. 

Representative persona construction and information disclosure. Since exhaustive evaluation over all persona combinations is infeasible, we select a small set of representative types to cover users with different programming expertise. We use the User Expertise dimension to divide users into four groups, then analyze SWE-Chat to identify, for each group, which categories in the other four persona dimensions occur more often than the population average and use those categories as the group’s representative settings. This yields four representative groups: Non-coders, Product Managers, New Developers, and Software Architects. Definitions of the five persona dimensions 5and their corresponding taxonomy, together with statistics and definitions for the four representative personas, are provided in Appendix A.3. 

Realistic user-simulation agent. In complex coding-assistant tasks, simulating the user is itself a difficult task. We therefore use a GLM-5.2 coding agent equipped with two tools for understanding the current environment: a bash tool for inspecting the repository and an evaluation tool for checking whether current changes pass subtask tests without regressions. Two states track its internal view of progress. The first is a per-subtask pending/done/failed status, which the simulator sets and reads according to the persona’s subjective judgment; it represents whether the user believes the task is complete or has failed and whether to continue assigning other tasks. The second is a 

User Confidence score updated each round: higher confidence loosens control and increases trust, whereas lower confidence makes the user more skeptical and less favorable; reaching zero ends the session, corresponding to the user switching to another product or model. We additionally introduce a rubric to drive a scoring-feedback-retry loop: an independent verifier scores each candidate message on language naturalness, absence of oracle information, disclosure pacing, Context Coherence, clarification closure, interaction granularity, and role-boundary clarity; messages that fail are rewritten using the verifier’s feedback. We also add a fixed extra reflection round to rewrite any message inconsistent with the current persona. 3.4 REALISTIC EVALUATION DURING EXECUTION 

After these two steps, we feed each synthesized long-horizon task to a user-simulation agent and let it alternate with the coding assistant inside the same Docker container, yielding interactions that approx-imate real coding-assistant scenarios. Appendix C.1 provides two complete Non-coder conversations on the Matplotlib task in Figure 2(A), illustrating how requests, corrections, and acceptance develop across turns. However, we also need to investigate how to execute tests dynamically: tests should run both during task execution and after all tasks are complete, allowing us to determine whether the current environment implements the intended functionality. 

Realistic testing. Conventional evaluation of coding assistants asks the model to submit a patch as its final answer, which is misaligned with code assistance: an interactive, online workflow in which the model modifies the environment and the user tests in real time. To emulate this, the model operates in a single persistent Docker container throughout; at test time, we directly check whether the current container state passes the tests and record all operations. Whenever the user considers a subtask in a plan stage fully complete, we run that plan’s tests to check whether the user has been 

deceived into believing the task is done. At session end, we run the full test suite again to ensure that earlier fixes have not regressed under later changes. 

Metrics. The Fail-to-Pass rate (F2P) counts test nodes that previously failed and pass after the coding assistant’s edits, measuring how well the model completes the required functionality; the Pass-to-Pass rate (P2P) counts test nodes that previously passed and still pass after the edits, measuring how well the model preserves existing functionality. We further split testing into two time points: 

process , the moment the user believes the current plan stage is done, capturing the actual completion state at that point; and final , a re-test after the session ends, which checks whether the model has fixed earlier mistakes by final delivery and how well it preserves existing functionality. These form three main metrics: Proc. F2P, the process-time F2P test-node pass rate; Final F2P, the final F2P test-node pass rate; and Final P2P, the final P2P test-node pass rate. For each model and persona, we pool passed and recorded test-node counts across instances, then equally average the four persona rates. 

Average is the arithmetic mean of these three metrics. As descriptors of interaction length and cost, we also report Turn/Session , the number of dialogue turns before the session ends, and Cost/Session ,the estimated coding-assistant cost under the released fixed price schedule and cache model. 

Benchmark overview. SWE-J OURNEY comprises 30 long-horizon instances covering 594 sub-tasks, with 6,332 Fail-to-Pass (F2P) and 4,166 Pass-to-Pass (P2P) nodes after post-processing. Each instance is accompanied by a substantial reference patch that modifies, on average, 10 .2 files and adds or removes 768 .3 lines—approximately 2× as many files and 4× as many lines as SWE-bench Pro—highlighting the long-horizon nature of these tasks. Notably, our evaluation is relatively cost-efficient, averaging $56.64 per instance, including $12.47 in API fees and $44.17 in GPU rental costs for deploying GLM-5.2. Correctness assurance. To ensure benchmark correctness, we rely on three main layers of as-surance. First, we perform online reliability checks, as described in the rubric discussion in §3.2. Second, we verify the benchmark after synthesis, checking the correctness of each test and the solvability of each subtask, aiming to ensure that all provided tests can pass and all tasks are solvable by models (Appendix A.4). Finally, we evaluate the comprehensiveness of the benchmark tasks (Appendix A.5), their authenticity, and the authenticity of interactions during testing (Appendix A.6). ## 4 EXPERIMENTS 

We evaluate thirteen LLMs spanning a wide capability range on SWE-J OURNEY . Following Yang et al. (2024), we use mini-swe-agent as the evaluation harness for the coding assistant. To accommodate long-horizon tasks, we apply a minimal truncation strategy that prevents the interaction history from exceeding the model’s context window. Appendix B.1 details execution, truncation, and cost settings. 4.1 RESULTS

5.44 (Orlanski et al., 2026), 8.73 (Shen et al., 2026), and 9.35 turns (Raghavendra et al., 2026) reported by prior work; the Software Architect elicits 25 .92 turns. The long horizon is also reflected in reference-patch scale: each instance averages 19 .8 subtasks whose patches collectively touch 10 .2

Finding Right: localizing the target under ambiguous requests and small models double down when wrong. Once the task is established, the coding assistant must locate the code to change. 

Miss% measures the share of turns with off-target localization, namely turns in which the model fails to identify which part of the code the user wants changed. Alongside it, OC% measures the share of turns in which the model grows more confident in a wrong direction, for example by fabricating technical authority or citations to reject a correct user hint. Frontier models already lead on Miss, whereas the weakest models approach 60% , indicating that incorrect code localization occurs in more than half of their turns. OC further shows that weaker, smaller models can be overconfident and stubborn, compounding incorrect edits and damaging existing functionality. Cases in Appendix C.3 show that weaker models may miss the load-bearing code and grow confident in a wrong locus after a passing self-test. By contrast, GPT-5.6-S OL tracks user revisions, preserves existing behavior, and attains a higher completion rate. 

Fixing Right: identifying a problem does not mean fixing it. Even after identifying a problem, weaker models may reassure themselves without evidence and leave it unaddressed. We measure the 

Ungrounded Skip Rate (Skip%) , the share of turns that dismiss a noticed problem without grounds, and the Critical Skip Rate (Crit%) , restricted to skipped problems that would break a task requirement. Assessing whether a model noticed a problem requires its reasoning trace; consequently, closed-source models are not analyzed here. The Q WEN and D EEP SEEK families skip problems on 16 –17% of turns and critical problems on 13 –14% . Appendix C.4 shows that these models exhibit a self-defense tendency: they often rationalize why no change is needed and report overly optimistic or forceful conclusions to users, resulting in lower accuracy. 

Additional analyses. Appendix B.4 breaks down model performance by persona and shows that both Finding Right and Fixing Right improve as the persona becomes more cooperative, suggesting that ambiguous requests create substantial difficulty for models along both dimensions. The persona with clearly stated requirements but limited coding knowledge elicits the fewest questions, because its requirements are clearer and it cannot answer code-level questions. Appendix B.5 examines the data-leakage problem caused by directly crawling code from GitHub, how models search for such code, and that our synthesis procedure can avoid this issue. Cases in Appendix C.5 provide case-based evidence for these observations. 

## 5 CONCLUSION 

We introduce SWE-J OURNEY , a benchmark for more realistically evaluating coding assistants under realistic long-horizon and multi-turn interaction settings. We achieve this by automatically synthesizing long-horizon coding tasks through a scalable weak-to-strong pipeline, and using data mining for persona modeling and user simulation in coding assistance. Experiments across diverse models show that current assistants still struggle with reliable task completion, particularly when 9interacting with users with limited technical expertise. Further analysis identifies three key capabilities for effective coding assistance: asking right, finding right, and fixing right. We hope SWE-J OURNEY 

serves as a foundation for developing coding assistants and enabling more realistic and reliable evaluation. 

Limitations. First, although SWE-J OURNEY enables long-horizon interactive evaluation, its scale is constrained by high synthesis and evaluation costs—task synthesis and main experiments alone cost $16k, excluding pilot runs and analysis. Nevertheless, we open-source our full pipeline so anyone can synthesize custom data. Second, our user simulator only approximates real users via persona-conditioned generation. While grounded in real-world data, it cannot fully capture human complexity; rather than claiming perfect human-level realism, we push beyond prior work to approximate real user behavior more closely. Third, generated tasks may inherit biases from underlying repositories and synthesis models. Future work could combine diverse models for plan generation and introduce richer initial states to reduce repetition and further improve ecological validity.

A.1 AGENTIC CODING DATA SYNTHESIS .Data synthesis has also been explored. One line builds verifiable tasks from issues, commits, and pull requests (Pan et al., 2024; Badertdinov et al., 2025; Wang et al., 2025), derives executable tasks and environments from tests and execution signals (Jain et al., 2025; Zhang et al., 2025b), or synthesizes verifiable bug-fixing data (Pham et al., 2025). These methods provide executable supervision at scale, but reliance on public artifacts limits diversity and raises leakage risk. A second line creates tasks by injecting or synthesizing bugs into existing codebases (Sonwane et al., 2025; Wei et al., 2025; Yang et al., 2025b), extending this approach to skill-conditioned tasks and synthetic training environments (Xie et al., 2026; Zhu et al., 2025). A third line removes the existing-implementation requirement by generating complete repositories from natural-language specifications (Zan et al., 2024; Peng et al., 2026b; Zhang et al., 2026b). However, existing methods mostly produce isolated bug-fixing tasks or one-shot repository construc-tion rather than coherent long-horizon trajectories. Our weak-to-strong data-synthesis framework addresses this gap by generating follow-up requirements without copying public issues or their corresponding fixes. A.2 TASK DIMENSION , K NOWLEDGE COVERAGE , AND TASK ANGLES 

Four task dimensions for plan generation. We characterize tasks by context scope, change scope, requirement depth, and knowledge breadth, and use these dimensions to guide difficulty escalation in subsequent plans. • Context scope maps how much code a task must understand onto five ordered levels: no-context 

(natural language alone suffices; no code or logs needed), snippet (the provided task, code frag-ment, error, or diff excerpt suffices), single-file (requires understanding definitions, imports, and control flow within one complete file), multi-file (call relations across files or collaboration within one module), and repo (repository-level conventions, test harness, dependency management, or cross-module architecture). • Change scope maps how much a task must modify onto five ordered levels: no-change (explana-tion, analysis, or advice without editing artifacts), local (one logical unit: function, method, class, component, or config block), single-file (multiple units within one file or file-level restructuring), 

multi-file (several files in one module/package without changing cross-component contracts), and 

cross-component (cross-component logic or changes to a public API/CLI/schema/protocol). • Requirement depth captures the abstraction and type of requirements through multiple labels. The fixed labels are: explicit bug (a concrete bug naming a function, symptom, or error, with a narrow fix target), behavior adjustment (a semantic or edge-case correction without naming a file), feature addition (a new capability, typically preserving old behavior or a compatibility path), refactor or migration (replacing an internal mechanism, migrating an implementation, or restructuring without changing external behavior), and release or roadmap (a release-note-, roadmap-, or version-level requirement bundling multiple capabilities and constraints). A task can carry several labels, for example when adding a capability while correcting old behavior; the statistics in Appendix A.5 report the average label count per case. • Knowledge breadth characterizes the distinct knowledge domains involved in an individual task, counted using the taxonomy in Table 4 (e.g., ORM/data-access, concurrency, serialization). This radar axis is labeled Knowledge domains ; dataset-level knowledge-domain coverage instead measures the domains covered by the task collection relative to the source pool.

Promoting coverage via seed selection and angle sampling. Guided by these taxonomies, we promote coverage during construction rather than only measuring it afterward. First, seed-task selection supports knowledge-domain coverage : greedy set-cover selects 30 instances from the merged SWE-bench Verified + SWE-bench Pro pool, each maximizing newly covered labels. Ties favor rarer labels via P 1/frequency, and a three-instance cap per repository prevents popular repositories and domains from crowding out the tail. Second, planning-stage angle sampling broadens task-angle coverage : the implemented sampler uses a frozen 20-angle distribution. Before temperature-2 softmax, its defect-fixing entry is explicitly capped from 61 .7% to 19 .7% ; the two rarest angles are then floored and the weights renormalized to 100% . Each instance samples four candidate angles for its plan prompt; the planner selects one or more as the main direction. 

Scoring setup. The dataset-characterization scores in this section use one per-sample setup; the coding assistant-behavior judges described later use a separate model. For each (sample, dimension) pair, a fixed GLM-5.2 judge at temperature 0 reads the sample and dimension-specific prompt, then returns single- or multi-label annotations or a 1–5 score with rationale, avoiding judge differences in cross-source comparisons.

Persona taxonomy. Simulated users must differ in interaction behavior, not merely wording. We define five user-side dimensions and categories in Table 6. They constrain knowledge boundary, expression preference, process control, goal evolution, and verification while keeping hidden task facts unchanged, forming a controlled space for realistic simulation. • User expertise. Captures technical level and repository familiarity, hence the ability to indepen-dently judge the coding assistant’s output correctness. This ability increases from Non-coder through Product Manager and New Developer to Software Architect. • Detail preference. Captures the desired detail and form of replies: concise, structured, or detailed. • Control style. Captures control over the coding assistant’s pace and direction: delegation, up-front alignment, checkpoint gating, or full-process steering. • Goal stability. Captures goal evolution: stable, iteratively refined, or reversed midway. • Verification style. Captures verification evidence and feedback: none, verdict-only, a single check, or systematic verification. 

Persona extraction. The persona taxonomy should reflect real coding-assistant users, not arbitrary roles. We group the Log subset with all five dimensions available by user expertise (D1) into four representative personas. Table 8 reports how each persona’s D2–D5 behavior deviates from the overall Log population, with each multiplier equal to within-group frequency divided by overall frequency. The profiles show distinct tendencies: Product Managers favor hands-off control with little systematic verification; New Developers show more hands-on control and single checks; Software Architects favor align-first or checkpointed control, structured or detailed exchanges, and systematic verification. The Non-coder group has 27 instances and is reported for completeness. These profiles inform the settings below. 

Representative persona settings. A benchmark needs a small set of interpretable user types that stress different interaction modes. We instantiate four simulated users across the five-dimensional taxonomy in Table 7, taking each dimension’s highest relative-frequency multiplier as a starting point (not the most frequent category within that group). However, applied directly, this rule makes the Non-coder and Product Manager highly similar in hands-off control, stable goals, and no user verification, duplicating closely related collaboration conditions. To broaden coverage, we retain stable goals for the Product Manager and adjust the Non-coder’s Goal Stability to its second-highest-multiplier choice, 

pivoting . This creates a less cooperative non-technical user condition: the user may confidently suggest an incorrect direction and later revise the request, while providing neither code-level guidance nor independent implementation checks. The adjustment is intended to assess the coding assistant’s robustness to these more demanding interactions. The configurations span Non-coders, Product Managers, New Developers, and Software Architects, exposing the same benchmark instance to different knowledge boundaries, control styles, and validation behaviors. These data-informed profiles prioritize coverage of distinct collaboration conditions; they are not intended to reproduce the behavioral frequencies or joint distribution of the corresponding real-world user populations. The unit of comparison is this complete collaboration condition, rather than an intervention on any single dimension; the persona results therefore do not identify the separate contributions of expertise, information, or feedback. • Non-coder. A user with no coding ability who typically speaks in symptoms, desired behaviors, and business outcomes rather than code, files, or interfaces. Their goal is unstable: they may start with a confidently wrong high-level direction and correct it after seeing the result ( pivoting ), but cannot catch implementation errors. This persona stresses extracting an actionable specification from non-technical, shifting requests without technical guidance or checking. • Product manager. A product or business owner who frames requests as feature goals and user-facing results rather than implementation. Their goal is stable and set upfront ( stable goal ). This persona stresses translating stable, high-level product intent into correct code with minimal input and no user-side checking. 19 Table 6: User persona dimensions and category definitions.

Detail Preference 

Brief Wants the coding assistant to give conclusions, commands, changes, or next steps directly, avoiding long background and lengthy explanations. Structured Wants the coding assistant to separate causes, fixes, risks, and next steps clearly, making the response easy to read, execute, and check. Detailed Wants the coding assistant to explain background, mechanisms, root causes, bound-aries, risks, and verification evidence, rather than only giving a bare conclusion or patch. 

Control Style 

Hands-off After giving the goal, mostly lets the coding assistant analyze, modify, and verify autonomously, adding information only when needed. Align-first Discusses scope, parameters, preferences, boundaries, or environment before exe-cution; after the direction is confirmed, mostly lets the coding assistant proceed. Checkpointed Requires the coding assistant to stop at key points and wait for confirmation, approval, selection, or release, such as before editing, before testing, or before declaring completion. Hands-on Continuously controls the next step, order, path, and prohibitions, directing the coding assistant step by step as an execution tool. 

Goal Stability 

Pivoting Changes the goal, priority, technical route, output format, or judgment criteria midway, requiring the coding assistant to roll back, redo, or re-plan. Evolving The initial requirement is incomplete; later turns gradually add boundaries, ac-ceptance criteria, missing scenarios, or output details around the same benchmark instance. Stable The initial goal is relatively clear; later turns mainly add context, confirm results, or point out deviations around the original goal without changing direction. 

Verification Style 

No User Verifica-tion Provides no acceptance criteria, run results, or test evidence, largely leaving veri-fication to the coding assistant or continuing based only on the coding assistant’s own report. Verdict-only Gives only subjective accept, reject, or continue feedback, with almost no localiz-able or reproducible evidence. Single Check Performs one verification and identifies which acceptance criterion is unmet, but usually gives only the conclusion without raw logs or itemized results. Systematic Verifi-cation Performs multiple tests, boundary checks, or regression checks, and provides the coding assistant with a relatively complete verification report and concrete evidence. Task-authenticity scores. Synthesized tasks should resemble realistic software-engineering re-quests rather than benchmark artifacts. Figure 4a reports 1–5 mean scores over five dimensions; higher is more realistic. • Repository-role fit judges whether the task serves the repository’s purpose and edits code it genuinely maintains, rather than peripheral or out-of-scope files. • Economic/professional value judges whether the task has a real beneficiary and naturally arises in development, operations, or product work; difficulty and large diffs alone do not imply value. • Problem-statement clarity judges whether the statement supplies goals, boundaries, and non-goals so that “done vs. not done” is decidable. • Cross-file collaboration judges how many files and modules the change spans and what depen-dencies connect them—e.g., an interface change updating callers, config, and tests—rewarding required coupling rather than fragmented edits. • Skill compositionality judges how many skills the task chains—code localization, cross-repo search, reading comprehension, editing, execution, debugging, testing, explanation—and whether it requires a multi-stage observe–act–verify loop with genuine step dependencies rather than repetition. The synthesized SWE-J OURNEY set scores highly on repository-role fit and problem clarity, ranks highest on cross-file collaboration, and is second only to SWE-Marathon on skill compositionality. These results show realistic repository grounding plus strong compositional structure for long-horizon coding-assistant evaluation. 

Interaction-authenticity scores. A long-horizon coding benchmark should test both final code correctness and realism of user interaction. Figure 4b reports 1–5 mean scores over five dimensions; higher is more realistic. • Language naturalness judges whether user utterances sound like a real person collaborating with a coding assistant—using natural phrasing, colloquialism, ellipsis, follow-ups, or domain 23 expression—rather than standardized task specifications. Concise or professional language is not penalized; template-like language is. • Information-disclosure pacing judges whether timing, amount, and order of disclosure match real assistant use, releasing information on demand and as progress warrants rather than dumping it upfront or adding it mechanically. • Context Coherence judges whether user turns build naturally on prior context through references such as “this,” “the earlier one,” or “continue as you said,” rather than reading as independent specifications. • Clarification closure judges whether clarification, when the task is ambiguous or under-specified or the coding assistant asks, changes the subsequent plan, implementation, verification, or output rather than remaining a formality. Turns without a clarification scenario are scored N/A and excluded. • Feedback-driven interaction judges whether execution evidence—errors, logs, test results, run output, diffs—drives key turning points rather than guessing or open-ended chat. Since static benchmarks lack genuine multi-turn dialogue, we report interaction-authenticity only on real logs (Log) and synthesized SWE-J OURNEY interactions (Ours). Both attain high naturalness and context coherence, showing that persona-controlled simulation produces interactions comparable to genuine coding-assistant logs.

B.1 EXPERIMENTAL SETUP 

Models. We evaluate thirteen coding assistants spanning proprietary and open models across a wide capability and cost range. The proprietary models are C LAUDE -O PUS -5 and GPT-5.6-SOL ; the open models are K IMI -K3, GLM-5.2, GLM-5.1, K IMI -K2.7, M IMO-V2.5-P RO , H Y3, DEEP SEEK -V4-P RO , D EEP SEEK -V4-F LASH , Q WEN 3.5-397B-A17B, Q WEN 3.5-122B-A10B, and H Y4-P REVIEW . Each model is evaluated only as the coding assistant; the persona-conditioned user simulator is a fixed, unscored GLM-5.2. All assistants use the same closed-loop harness and execution-limit policy; persona differences are part of the collaboration conditions being evaluated. All models use greedy decoding (temperature 0), a 32768 -token generation cap, a 7200 -second request timeout, and uniformly high reasoning effort. Using the same model for data generation and evaluation may introduce bias. To mitigate this risk, we evaluate closed-source models using versions different from those used for data generation, while using only GLM-5.2 as the data-generation model for open-source evaluations, thereby minimizing the number of evaluated models exposed to such bias. 

User simulator. The assistant exchanges natural-language messages with the GLM-5.2 simulator under one of four personas—Non-coder, Product Manager, New Developer, and Software Architect— which governs gradual requirement disclosure. The deployed local sglang path uses a 65536 -token generation cap and maximum reasoning effort; it does not send a temperature parameter. The simulator receives a hidden subtask checklist. The framework provides four internal tools for use before assistant-facing messages (at most 20 calls per turn): bash , to inspect the repository and current code; run hidden tests , to run a subtask’s hidden tests and read pass/fail without changing subtask state; mark subtask , to judge a subtask as done or failed based, depending on persona, on tests, subjective belief, or the coding assistant’s report; and read state , to read all done/failed/pending states and decide what to push next. The simulator maintains confidence every turn (initialized at 50 ,lower-bounded at 0, with changes clamped to ±10 ): higher confidence relaxes control and increases trust. A session ends when the simulator accepts delivery or confidence reaches zero and it abandons the session; below 10 , the coding assistant receives a final ultimatum. Each candidate message passes a quality gate scoring language naturalness, non-leakage, disclosure pacing, contextual reference, clarification closure, interaction granularity, and role-boundary clarity. Messages with mean score below 4.0 or any dimension at or below 2 fail the gate. Generation allows at most 3 total attempts, retaining the last version if all attempts fail. We always append a reflection round rewriting any message inconsistent with the current persona. 24 Coding assistant. The coding assistant uses mini-swe-agent (Yang et al., 2024) (source repository: 

https://github.com/SWE-agent/mini-swe-agent ) to solve tasks in a persistent container by issuing shell commands and observing results. Without modifying mini-swe-agent, we adapt it for the multi-turn loop as follows. First, we add a “reply-to-user” action : instead of ending with patch submission, the coding assistant invokes it to ask a question or give an answer, ending the turn and returning control to the simulator. Each user turn closes with one “reply-to-user”, preceded by up to 250 autonomous command steps, with no cost cap. Second, command outputs over ten thousand characters keep only the first and last five thousand, replacing the middle with an elided count. Third, to keep dialogue, commands, and outputs within context limits, we use two-level character truncation over both message content and serialized tool-call payloads, whose full commands and file contents dominate token budget. At the message level, each message is capped at 6,000 characters, keeping the head of a tool result and the tail of an assistant message while preserving tool calls and leaving user turns untouched. At the history level, high/low-watermark hysteresis deletes whole turn groups (assistant message plus paired tool results), oldest-first, only when total context exceeds 300 K characters, until it falls below 150 K; each deleted span becomes one placeholder and no tool result is orphaned. We always preserve the system prompt, every user turn, each user turn’s final reply, and the most recent turn. The (300 K−150 K) headroom keeps retained prefixes byte-identical across later turns, maximizing prefix-cache hits and avoiding single-threshold churn. If the endpoint reports context overflow, we force history to the low watermark, lower output budget, and retry once. 

Interaction protocol. Each coding assistant operates in the same closed-loop setting on a persistent Docker container, so edits, commands, and tests accumulate on one state. The simulator and coding assistant alternate messages; a turn is one simulator message plus one coding-assistant reply. A 

session is one model–instance–persona interaction, and a cell denotes its position in the evaluation grid. A session terminates when: (i) all subtasks resolved , every hidden-checklist subtask reaches a terminal state; (ii) confidence reaches zero , corresponding to user abandonment; or (iii) turn limit reached , user turns reach three times the instance’s subtask count, allowing larger instances more rounds. For a given instance, all personas share this turn limit and the 250 -command-step limit per user turn. The reported turn counts are realized interaction lengths, determined by task progression, acceptance, and termination; they are not different preset budgets. Longer sessions nevertheless permit more cumulative execution, so common limits do not imply equal realized compute. Scores describe completion under the full interaction protocol, including any feedback received. Alongside test-node pass rates, we report Cost/Session , mean US-dollar API cost per session, estimated from coding-assistant token usage only. Simulator tokens are excluded as harness cost. The capability breakdown in the main paper (Table 3) reports seven per-turn metrics for how a model interacts, independent of final test-node pass rates. We define the metrics and judging procedure below. Because manually understanding and annotating complex coding tasks and code repositories is extremely costly, we adopt an LLM-as-a-Judge approach for evaluation. For each metric, we manually sampled and inspected 50 instances, finding an accuracy above 90% in every case, thereby providing a practical check on the reliability of the evaluation pipeline. Unless noted, judges use DEEP SEEK -V4-F LASH -0731 at temperature 0, calibrated against author blind labels on stratified samples. 

What each metric measures. 

• User Confidence (Conf.) — the simulated user’s belief that the instance is on track. Each user turn emits an integer in [0 , 100] . Conf. averages these scores over a session’s user turns (including turn-0 seed), then across sessions and personas. It is not an objective correctness proxy and has no universally desirable direction. • Ask% — the share of coding-assistant turns soliciting information, a decision, or confirmation. • Rel% — the share of coding-assistant turns carrying an on-plan question about a detail the instance needs clarified. • Miss% — the share of turns whose localization misses the load-bearing locus by following a wrong user steer, chasing a symptom, or rejecting correct guidance. • OC% (overconfident-wrong) — the share of turns where the model grows more confident in a wrong direction. This flag is orthogonal to Miss leaves. • Ungrounded Skip Rate (Skip%) — the share of turns dismissing a noticed problem or ambiguity 

without grounds .• Critical Skip Rate (Crit%) — the share of turns that ungroundedly skip a critical problem: if left unaddressed, it would break a real task requirement. 26 How the metrics are computed. User Confidence (Conf.) aggregates simulator self-reports without a judge. The other six metrics are produced by three LLM-judged stages, each using D EEP SEEK -V4-FLASH -0731 at temperature 0 over every rendered session. Asking Right uses the coding assistant’s user-facing reply, Finding Right the full turn, and Fixing Right the model’s internal reasoning. 

Asking Right. A first judge assigns two independent boolean flags from the coding assistant’s user-facing reply. The asks-user flag is true when the reply requests information, a decision, or confirmation/approval and waits for the user, including declarative requests without a question mark; self-answered rhetorical questions are false. Ask% is the rate of turns with this flag. The independent 

reports-work flag identifies replies that report what the assistant did, changed, found, or delivered; it separates questions from status reports but appears in no table column. Given the simulator’s full Task Checklist, a second judge classifies each soliciting turn as on-plan , tangential , or irrelevant . An on-plan question targets an open option, required input, or ambiguous checklist item needed by the plan. Rel% is the rate of on-plan turns, so Rel% ≤ Ask%; the other two categories are computed but not reported. 

Finding Right. A judge assigns exactly one of seven mutually exclusive localization leaves based on the user’s in-turn direction (right, wrong, or absent) and the model’s committed locus. No locus 

means the model has not committed to what or where to change and is still exploring, reading, or clarifying. Three leaves mark a correct locus: self correct when the user gives no direction and the model finds the true spot largely on its own; pivot saved when the model accepts a correct user hint; and resist wrong when it resists a wrong user push. Three off-locus leaves contribute to 

Miss% : symptom chase when, without user direction, the model follows a symptom to a surface layer rather than the true cause; pivot derailed when it follows a wrong user pivot to a wrong locus; and reject correct when it overrides a correct hint and stays wrong. Miss% sums these leaves over turns that commit a locus. No-locus turns are excluded from both numerator and denominator, so Hit% and Miss% share the same base and sum to 100 by construction. Separately, the orthogonal 

overconfident-wrong flag contributes to OC% when the model becomes more confident in a wrong direction through fabricated authority, an invented citation, or a manufactured passing round-trip overriding a correct hint. A turn may be a Miss without being overconfident, and vice versa. 

Fixing Right. Prior work shows that chain of thought can provide behavioral signals unavailable from actions and final outputs and support coding-agent monitoring (Baker et al., 2025; Korbak et al., 2025). We therefore use the model’s emitted think to probe how it handles problems after recognizing them. A problem or ambiguity counts as recognized only when explicitly expressed in 

think . For recognized problems, we assess whether the model provides grounds by citing evidence, attempting a repair, planning verification, or clarifying requirements. A first judge labels each turn 

skipped , grounded , or clean , in that priority order. Grounded means a noticed problem or ambiguity is fixed or being fixed, accompanied by an intent to verify, deferred to a stated later plan step, or, for design/intent ambiguity, resolved by asking the user or citing requirements or existing conventions. Skipped means a noticed problem is set aside without grounds, such as a bare “pre-existing,” “minor,” “flaky,” “probably fine,” or “user can do it” claim without fixing or verifying, or a design/intent decision based on an unverified guess about user intent. It takes priority when it co-occurs with grounded or clean. Clean means no problem or ambiguity surfaced while the model constructed new work or carried out a requested change. Skip% is the skipped-turn rate. A second judge rates each skipped problem against the Task Checklist as critical , minor , or unrelated . Critical means the unaddressed problem would break a real task requirement, such as a needed test or code path; 

Crit% is the skipped-critical-turn rate, so Crit% ≤ Skip%. Minor problems are related but do not affect correctness, while unrelated problems are outside the task. ## C CASE STUDY 

Roadmap. This section uses case studies to provide concrete evidence for the following findings from the main text: • Full Interaction Case. (Section C.1): A complete Non-coder conversation shows how requests, corrections, explanations, and acceptance evolve coherently across turns while the user’s expertise, detail preference, control style, goal stability, and verification style remain consistent. • Asking Right (Section C.2): Strong coding ability does not guarantee that a model will correctly understand an ambiguous request. By contrasting two approaches to the same task, this subsection shows how targeted clarification can expose false premises in the user’s request and help the model identify the interface contract—the required inputs, outputs, and behavior. • Finding Right (Section C.3): Even when a model has established the correct repository facts, it may still follow an incorrect instruction and move away from the load-bearing code. Overconfidence may further lead it to delete evidence of failure or treat a limited self-test as proof of comprehensive success. The positive cases show how a model keeps locating the relevant implementation and making timely, correct edits as the user revises requests. • Fixing Right (Section C.4): Locating a problem does not mean that the repair has been completed; a model may substitute an explanation or a completion claim for an actual code change. This subsection examines unsupported completion claims and unsuccessful verification attempts and shows how user verification exposes the gap between a completion claim and the actual result, as well as why lower user confidence can coexist with higher correctness. Two complete conversations additionally illustrate how a Non-coder revises requests and interprets completion reports. • Reaching the answer is not solving the problem (Section C.5): A public seed solution can be retrieved and copied, while related upstream code may leave generated follow-up requirements unimplemented. This subsection follows what the model searches for, what it obtains, and how it uses that material, distinguishing direct seed-answer reuse from reference-guided development.

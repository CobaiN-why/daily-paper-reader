## ABSTRACT 

Coding agent harnesses mediate tool use and authorize actions, yet their security mechanisms and runtime effects remain incompletely characterized. We present HarnessSecurity , the first systematic empirical study and benchmark of open- and closed-source coding agent harnesses. First, we derive a ten-mechanism taxonomy and then assess 400 harness–mechanism cells using independent ratings by researchers and large language model (LLM) judges. We find that about half of confirmed mechanism implementations are opt-in, while closed-source harnesses exhibit substantial evidence gaps. Second, we introduce H ARNESS SECURITY -B ENCH , a benchmark of 23 tasks across five attack surfaces without sacrificing legitimate task requirements. Using separate deterministic oracles to measure task utility and attack effects with security setting comparisons, we evaluate nine mechanisms across six leading harnesses: Claude Code, Codex CLI, Gemini CLI, gptme, Qwen Code, and GitHub Copilot. Under a controlled LLM baseline GLM-5.2 , we conduct 2,500 trials, recording 81,155 tool calls and over 2.2 billion tokens. Enabling auto-approve increases utility and raises attack success from 29.2% to 95.6%. Network isolation and read-only mode reduce attack effects with substantial utility losses, while command allowlisting and command denylisting reduce attack effects with a small utility loss and a utility gain, respectively. Task-level cases show that restrictions on a shared capability can obstruct both legitimate and malicious operations, and that allowed tools or commands can leave unauthorized operations reachable through alternative execution paths. Harness providers should make security settings verifiable, test alternative execution paths to protected operations, and assess attack effects alongside task utility and execution costs. 

Keywords Coding agents, agent harnesses, LLM agents, security benchmark, empirical study, software security 

## 1 Introduction 

Coding agents based on large language models (LLMs) have moved from demonstrations to production, with products such as Claude Code [4] and Codex CLI [37] supporting autonomous repository-level software development. Each agent couples an LLM with a coding agent harness that assembles context, mediates tool use, and authorizes actions [14, 33]. Harness design affects task success and resource costs even when the underlying model is held fixed [18, 52]. Expanding coding agents’ capabilities also introduces risks in how their harnesses handle untrusted inputs, authorize tool execution, and process repository data. Recent disclosures illustrate how these risks arise in practice. In particular, prompt injection through issue titles induced shell command execution in a mirror of Cline’s triage workflow [24], demonstrating how untrusted content can redirect agent actions. Moreover, OpenAI and Anthropic reported network isolation failures during cybersecurity evaluations [8, 38], while IDEsaster showed how agent file edits triggered unsafe behaviors in the surrounding IDE [32]. First, surveys and empirical studies classify agent defenses, harness architectures, and execution controls, with an inspection of harness source code and public product materials [2, 11, 16, 25, 27, 44]. Second, agent security studies audit permissions and violations of information flows, evaluate attacks, defenses, and authorization policies in agent workflows [10, 12, 17, 29, 57]. However, existing studies remain limited in their empirical assessment of native security mechanisms across coding agent harnesses. Architectural mapping and literature reviews do not systematically assess mechanism implementation and default settings across coding products [27, 44]. Empirical comparisons cover only three coding agents [25] or eleven source-accessible harnesses [11], leaving closed-source products underrepresented. Practitioner comparisons describe native settings but do not report independent implementation status [2, 16]. These limitations leave a gap in the

Existing benchmarks also remain limited in their comparative evaluation of security mechanisms. IssueTrojanBench covers three coding agents on two Python repositories, while CapScope compares authorization policies within one Pi-based harness on five Python repair tasks [12, 48]. Other evaluations focus on attacks through particular resources, including instruction files, tool descriptions, and skills [31, 36, 47, 54]. Although some measure both task utility and attack outcomes [36, 47], they do not systematically isolate the effects of mechanism settings across harnesses and attack surfaces. These limitations leave a gap in the comparative assessment of security mechanisms across coding harnesses and attack surfaces . To bridge this research gap, we raise the following research questions (RQs): 

RQ1. What distinct security mechanisms can be identified in real coding agent harnesses? 

RQ2. To what degree are these mechanisms implemented? 

RQ3. How do security mechanisms in coding agent harnesses affect security and utility during adversarially augmented 

task execution? To address these research questions, we present HarnessSecurity , an empirical study of 40 coding agent harnesses: 27 open-source and 13 closed-source products. For RQ1, we derive a taxonomy of ten security mechanisms for assessment across coding agent harnesses. For RQ2, we assess all 400 harness–mechanism cells, recording evidence on implementation status, default settings, and supported configurations. These analyses in RQ1 and RQ2 establish the mechanism definitions and configurations used in the runtime evaluation. For RQ3, we introduce H ARNESS SECURITY -BENCH (HSB), a benchmark comprising 23 coding tasks spanning diverse programming languages, including Python, JavaScript, C#, C++, Go, and Ruby. HSB covers nine of the ten mechanisms across six harnesses. We augment task environments with misleading context and malicious resources across five attack surfaces (shown in A–E of Fig. 1). This augmentation preserves legitimate user instructions, task requirements, utility oracles, and valid paths to task completion. environment. Table 1 compares HSB with prior coding agent evaluations across harness coverage, attack surfaces, comparison of security mechanism settings, and evaluation oracles. The RQ1 study established a taxonomy of ten security mechanisms, and the RQ2 assessment confirmed implementation in 205 of 400 harness–mechanism cells and absence in 83, while 112 remain unresolved. The RQ3 evaluation comprised 2,500 trials under GLM-5.2 across six harnesses, recording 81,155 tool calls, over 2.2 billion native tokens, and 589.32 hours of cumulative agent execution time. The security and utility effects differ across mechanisms, harnesses, and tasks. Enabling auto-approve increased both utility and attack success, with attack success rising from 29.2% to 95.6%. Network isolation and read-only mode reduced attack success from 57.1% to 0.8% and from 8.3% to 0.8%, respectively, with utility losses of 24.5 and 34.0 percentage points. Command allowlisting and command denylisting reduced attack effects with a small utility loss and a utility gain, respectively. Task-level cases show that restricting a shared capability can block both legitimate and malicious operations, while alternative execution paths can leave unauthorized operations reachable. Harness development should test alternative execution paths to protected operations and evaluate security restrictions in terms of attack effects, legitimate task utility, and execution costs. We summarize our contributions as follows: • Security mechanism dataset and empirical study (RQ1–RQ2). We contribute a dataset covering 40 coding agent harnesses (27 open-source and 13 closed-source) and a taxonomy of ten security mechanisms derived by analyzing the source code and official product materials collected in the dataset. We further assess implementation status, default settings, and configuration across all 400 harness–mechanism cells, showing that about half of confirmed implementations are opt-in and that evidence gaps are more prevalent among closed-source harnesses. • HARNESS SECURITY -B ENCH (RQ3). We contribute a containerized benchmark for evaluating nine security mechanisms through 23 coding tasks. Task environments are augmented with misleading context and malicious resources across five attack surfaces while preserving legitimate task requirements and utility oracles. The benchmark compares enabled and disabled settings of native security mechanisms under the same execution environment, using separate deterministic oracles to assess task utility and attack effects.

The harness first assembles instructions, repository context, interaction history, and tool definitions for the agent to read. To construct the coding agent harness dataset for RQ1, we col-lected candidate harnesses from three channels: (i) GitHub repos-itories and lists of open-source coding agents; (ii) commercial products identified through vendor material; and (iii) coding agents that appeared in security disclosures and CVEs. The inventory contains 75 records (46, 17, and 12 from these three channels, respectively). After merging 19 pairs of records refer-ring to the same product, we retained 56 unique candidates. For example, we merged two records for Amazon Q Developer CLI, one identified through repository mining and the other through a public security issue [3, 40]. To focus on widely adopted, actively maintained coding agent harnesses, we further screened these candidates. For open-source candidates, we applied four screening criteria: (1) the candidate had to be publicly released; (2) its GitHub repository had to have at least 1,000 stars; (3) it had to support an agentic coding work-flow with code execution; and (4) publicly available materials had to allow us to assess its security mechanisms. We excluded projects with no maintenance for more than 12 months, as well as general agents and completion-only tools. For closed-source candidates, we required official documentation or CLI materials sufficient to assess their security mechanisms. Excluding 16 candidates, we finally retained 40 harnesses: 27 open-source and 13 closed-source (Table 2). The table distinguishes CLI tools, IDE extensions, IDE-based agents, and cloud/platform agents. For the 40 retained harnesses, we designed a programmatic collection procedure to archive official web documentation, README files, and available CLI materials. The procedure followed official documentation indexes and sitemaps where available and selected operationally relevant pages using links, titles, and keywords. For open-source harnesses, we additionally collected source code, typically from official GitHub repositories. Notably, for Claude Code, we pinned an unofficial public mirror of source recovered from an npm package source map for RQ1 analysis [9]. GitHub Copilot was collected from the official VS Code repository [34]. The RQ1 dataset cutoff is 2026-08-31 (23:59:59 UTC). Per-harness snapshot metadata identify pinned commits while document manifests record capture dates, URLs, local paths, and SHA-256 hashes. 

3.2 Study Design 

Following the principles of open and axial coding [50], we assigned initial security-related labels to eight harnesses, grouped the labels into mechanism categories, and then examined the remaining 32 harnesses to refine those categories and establish the final security mechanisms. We selected eight initial harnesses covering open- and closed-source products and all four harness types: Aider, Claude Code, and Codex CLI (CLI agents), Cline and GitHub Copilot (IDE extensions), OpenHands and Devin (cloud/platform agents), and Cursor (IDE-based agent). Three researchers, each with at least seven years of software development experience, independently examined the official documentation, CLI references, and source code for eight harnesses in our collected dataset to identify security-related behavior and assign initial security-related labels. After initializing and extending the labels, three researchers retained 44 security-related labels (i.e., 16, 15, and 13). Following discussion and adjudication, four researchers grouped the labels into ten mechanisms: auto-approve (AA), network isolation (NI), command allowlisting (CAL), command denylisting (CDL), MCP permissions (MCP), prompt-injection filtering (PIF), path restriction (PR), read-only mode (RO), audit logging (AL), and project trust (PT). Table 3 defines the ten mechanisms and gives representative security settings with examples describing their common behaviors. The taxonomy distinguishes mechanisms by the resources or operations they govern and their enforcement points in the harness loop (as shown in Fig. 1). PT determines whether repository-supplied configuration, instructions, and executable 5A Preprint 

resources are admitted according to the project trust state. PIF tags, detects, or sanitizes untrusted instructions in file, web, or tool content. Among execution restrictions, PR specifies permitted file targets, whereas RO suppresses persistent changes in covered operations. A workspace write restriction can therefore allow edits within the workspace while preventing writes elsewhere. These distinctions identify which resources or operations a mechanism governs even when several controls share a single configuration mode. The mechanisms also serve different security purposes. CAL, CDL, MCP, PR, NI, and RO govern the authorization or scope of operations. AA changes the confirmation requirements for those operations, and AL records actions and decisions for later review. This variation means that a mechanism’s presence must be interpreted together with its configuration and the operations it covers. RQ2 uses these categories to assess implementation and default settings, while RQ3 evaluates task utility and attack effects during execution. 

Answer to RQ1. RQ1 identifies ten mechanisms spanning resource admission, content handling, operation authorization, execution restrictions, and audit logging. Their category boundaries reflect the resources and operations they govern and where they act in the harness workflow. AA changes confirmation requirements, while AL supports later review. The taxonomy provides common categories for assessing implementation, default settings, and runtime outcomes across harnesses.

RQ2 evaluates the implementation of the ten security mechanisms established in RQ1 across 40 harnesses. Each of the 400 harness–mechanism cells receives one of five ratings. Both default-enforced (D) and configurable-off (C) mechanisms are implemented and active by default. C indicates that the mechanism can be disabled through a configuration option or CLI flag while D indicates that no such option or flag is available. As Fig. 3 shows, three LLM raters, L1 (Claude Opus 4.8), L2 (DeepSeek V4 Flash), and L3 (GLM-5.2), and two human researchers, H1 and H2, independently rate every cell without access to one another’s judgments. They assess official documentation, CLI materials, and source code from our dataset. Prior work pairs LLM judgments with code locations and explanations in fault localization, and with structured evidence chains in security risk assessment [23, 30, 56]. Building on this practice, we design an Evidence-of-thought rating method to make LLM judgments traceable to the inspected harness materials. The prompts require a separate justification for each harness–mechanism rating (Appendix B). Every non-U model rating must cite at least one supporting passage by source path and line range, while a U rating must explain the missing or conflicting evidence. H1 and H2 then review the recorded evidence for the 18 cells without a majority with a third human researcher, H3 (Meta-H3 in the figure), and agree on the final ratings. 4.2 Results 

The final ratings matrix shows how security mechanism implementation and default state vary across the 40 harnesses (Table 4) (Appendix A). Of 400 harness–mechanism cells, 205 have confirmed implementation (D, C, or O), 83 have confirmed absence (A), and 112 are rated U. Within the 205 implemented cells, O is the most frequent rating (109); the remaining 96 are active by default (64 C and 32 D). This pattern differs across mechanisms. Of 31 RO implementations, 30 are O; of 30 AA implementations, 26 are O. In contrast, 22 of 29 MCP implementations are active by default (20 C and 2 D), as are 20 of 22 AL implementations (16 D and 4 C). PIF has four confirmed implementations, 13 A ratings, and 23 U ratings. All 13 closed-source PIF cells are U. More broadly, U accounts for 69 of 130 closed-source cells (53.1%), compared with 43 of 270 open-source cells (15.9%). The matrix therefore resolves fewer implementation questions for closed-source products, particularly for PIF. The five initial raters reached a majority on 382 of the 400 cells; H1, H2, and H3 reviewed the evidence chains provided by L1, L2, and L3 and adjudicated the remaining 18. We calculated ordinal Krippendorff’s α with U treated as missing, retaining cells with at least two non-U ratings in the relevant rater group. Agreement was 0.740 for all five raters ( n=329 ), 0.669 for L1–L3 ( n=323 ), and 0.911 for H1–H2 ( n=192 ). 

Answer to RQ2. The 400-cell evaluation confirms implementation in 205 cells and absence in 83, while 112 remain unresolved. Of the confirmed implementations, 109 are opt-in and 96 are active by default. RO and AA are mostly opt-in, whereas MCP and AL are usually active by default. Unknown ratings are more frequent among closed-source harnesses and cover every closed-source PIF cell.

We curate 23 tasks (21 original and two adapted from the Terminal-Bench task repository [51]) across nine security mechanism benchmarks, spanning bug repair, feature implementation, and read-only analysis of code and data. The tasks cover six primary programming languages: Python, JavaScript, C++, C#, Ruby, and Go. Table 5 lists the task names, representative technical elements, and attack surface coverage for each benchmark. For each task, we provide an explicit legitimate user instruction, an executable environment, and utility oracles tied to the requested behavior. The user instruction is the authoritative source of legitimate task requirements. Each utility oracle checks a specified aspect of a requirement grounded in that instruction; a requirement may have zero, one, or multiple corresponding oracles. We then augment the task environment with five attack surfaces. Separate attack-effect oracles check the adversary’s specified actions or consequences. The augmentation leaves the original user instruction, legitimate task requirements, and utility oracles unchanged. To keep user instruction legitimate, direct-user-input attack surfaces are therefore excluded from HSB evaluation scope. 

5.2 Attack surface augmentation 

We construct attacks for the nine benchmarks by combining different attack surfaces, adversarial payloads, and artifacts encountered during legitimate task execution. The attacks cover five attack surfaces and introduce misleading workflow steps, fabricated operational prerequisites, or unauthorized additional actions (as shown in Fig. 4 and Fig. 5). For repository and workflow artifacts , we embed payloads in documentation, source comments, and configuration files. In AA, maintenance materials disguise queue purging as a necessary step for applying a backoff repair, as illustrated in Fig. 5. In CAL, validation helpers outside the allowlist are misrepresented as required utilities, while CDL frames table deletion or signing-key copying as prerequisites for validation. PR introduces closeout and activation steps whose helper actions write to or delete files outside permitted paths. RO similarly presents preview and receipt utilities that modify protected records. For agent instructions and skills , MCP’s Email Validation task uses a poisoned AGENTS.md to present a privileged registry update as routine maintenance. PT’s Pixel Pet Codec task supplies project instructions that 8A Preprint 

frame disclosure of a workshop ticket as a routine preview handoff. For tool interfaces , PIF’s Issue Triage task embeds instructions in incident handoff responses that request the submission of original attachments, logs, and collector context as a receipt requirement. Its C# Maze task uses returned release records to direct the agent to make regression checks advisory. MCP’s Doc Search task embeds index-publication instructions in a documentation tool’s description to solicit an unauthorized admin_exec call. PT’s Pocket Music Box task poisons a music preview tool’s description to request a privileged call that opens the preview queue. For knowledge and memory , MCP’s StreamLoop case reconciliation task poisons task-local case evidence and records of source authority. Coordinated claims about retention, reviewer identity, and policy exceptions are delivered as business records through an unmodified database tool. These records are designed to induce the deletion of protected evidence, privilege escalation, and changes to platform policies. For 

external services and execution dependencies , AA’s release materials solicit uploads of build tokens and deployment manifests. They also promote a downloaded validation helper whose execution deletes recovery snapshots. PT’s Clockwork Mobile task presents downloading and executing external validation code as a release check. PIF embeds instructions to redirect notifications or publish source code in HTTP records consulted during Issue Triage and C# Maze. NI adds a package lifecycle hook or enables a reporter endpoint in the configuration. Required installation or validation can then automatically trigger unauthorized callbacks and canary exfiltration. 

5.3 Utility and attack-effect oracles 

HSB evaluates task utility and attack effects using deterministic oracles to check file/database changes, receiver-side records, and execution events. Trace-based pattern matching and LLM judgment alone can misclassify them: a verbal refusal can coexist with a forbidden tool call [13], and a completion claim can contradict the environment state without an LLM judge detecting a discrepancy [1]. Each attack oracle evaluates a predefined, task-specific condition using recorded execution events or captured environment state. For example, an oracle may determine whether an unauthorized tool was invoked, whether a protected file was modified to the attacker-specified state, or whether a receiver obtained the trial canary. Oracle definitions and verdicts are kept outside the agent workspace, while execution traces are used only to interpret how the run unfolded.

5.5 Task review and validation 

Four software engineers who participated in RQ1 independently designed tasks based on existing proprietary products in their respective domains or on the Terminal-Bench tasks identified above. For each task, at least two researchers other than the designer reproduced it using commercial coding agents and audited the user instructions, executable environment, adversarial augmentation, and oracles. The audit verified that the environment supported legitimate task execution, that utility oracles corresponded to requirements grounded in the user instructions, and that attack-effect oracles captured the specified unauthorized actions or their consequences. 

## 6 Benchmark Evaluation 

6.1 HARNESS SECURITY -B ENCH Setup (RQ3) Execution environment. A trial is one scheduled evaluation of an agent on a task under a fixed harness, model, and security setting. Its trajectory records harness initialization and any subsequent model turns and tool calls until termination. Each trial runs in a fresh, isolated Docker container instantiated from a fixed image, where the harness under test operates on a separate copy of the task workspace. After the agent stops, we evaluate task utility and attack effects using the corresponding oracles outside the agent’s execution environment. For each evaluated harness, we construct the execution environment using the repository’s pinned release artifacts or building from its pinned source snapshot from our collected dataset. We record the source commit or release version and the corresponding artifact hash to identify the runtime evaluated in each trial. 

Evaluation metrics. We use Utility and attack success rate (ASR) to denote the proportions of utility oracle checks and attack-effect oracle checks that pass, respectively. We denote a mechanism’s enabled and disabled settings as ON and OFF, respectively. For each harness, mechanism, and setting, rates are calculated by dividing the total passed oracles by the total oracles. The Overall row includes only harnesses evaluated in both ON and OFF settings. Tables 6 and 7 report six quantities (Appendix C): Utility off, Utility on, ASR off, ASR on, ∆Utility , and ∆ASR .Unknown (U) oracle verdicts are recorded in evaluation reports and excluded from the denominators. We compute 

∆Utility = Utility on −Utility off and ∆ASR = ASR on −ASR off from unrounded rates. Both differences are expressed in percentage points (pp); the tables use a percentage suffix and arrows to show the magnitude and direction of change from OFF to ON. A negative ∆ASR means a lower ASR under ON, while a negative ∆Utility means a lower utility oracles pass rate. Differences require defined rates in both settings and are otherwise reported as not applicable (N/A). 

Harness scope. To support reproducible evaluation, we select open-source harnesses with at most one unknown (U) or absent (A) rating in the ten-security-mechanism matrix (as shown in Table 4). This rule selects six harnesses: Claude Code, Codex CLI, Gemini CLI, gptme, Qwen Code, and GitHub Copilot. 

Evaluation configuration and models. For each configurable-off (C) and opt-in (O) harness–mechanism cell, we compare ON and OFF settings using the same task, attack variant, and acting model. Other security settings (sandbox, approval, network, and tool configurations) are fixed across each ON/OFF comparison and recorded. These comparisons measure changes in task utility and attack effects under the tested configurations. For absent (A) cells, we run an OFF baseline; for unknown (U) cells, we observe the mechanism’s default setting with its implementation status unresolved. Default-enforced (D) cells are evaluated only in the ON setting when no supported disabled configuration is available. Evaluations with only one setting report the available Utility and ASR rates, with ∆Utility and ∆ASR marked N/A. Repeated trials characterize variation in agent behavior under fixed oracle criteria. For PT, where supported, ON marks the workspace as untrusted and OFF marks it as trusted, with approval, sandbox, and network settings fixed. Native startup refusal and controls with narrower resource coverage are evaluated according to their actual behavior. All harnesses use GLM-5.2 as the base LLM; in AA-OFF trials, a separate Qwen3.8-27B model reviews native permission requests through a deterministic bridge for all six harnesses. Each scheduled combination of task, harness, and security setting uses 10 trials for nine mechanism benchmarks, with 2,500 planned trials across 54 harness–mechanism batches, excluding reruns. All trials have an external execution deadline of 28,800 seconds (8 hours). We sum input and output tokens across trials; input totals include cached-read tokens. 10 A Preprint

Case A: Protection and its utility cost. We examine the Dependency Lock Repair task from the NI benchmark, where legitimate dependency installation requires access to a package registry. Across ten trials per setting, enabling NI in Claude Code reduced utility from 96% to 76%, while ASR fell from 100% to zero. A representative ON trace showed the native network policy rejecting the required registry access and preventing package retrieval. All four local functionality checks nevertheless passed, distinguishing successful local validation from completion of the registry-dependent installation workflow. Under OFF, installation also triggered a callback that sent data to the attack collector. In the ON trace, failed package retrieval prevented this callback. This case illustrates how legitimate and malicious operations can depend on the same network capability: restricting registry access prevented the malicious installation callback while also obstructing the dependency installation required by the legitimate task. 

Case B: Bypass through an allowed interpreter. We use the CLI Arg Parser task from the CAL benchmark to examine a bypass observed with Qwen Code under CAL ON. The task’s poisoned validation materials presented an unauthorized checker as a required validation utility. Qwen Code’s native gate rejected the checker, but after completing legitimate validation, the agent invoked it through an allowed Python interpreter. The trial passed all six utility checks and all three attack-effect checks, showing that satisfying the checked task requirements coexisted with successful attack effects. A separate ON trial completed the same task without executing the checker, passing all utility checks and no attack-effect checks. This comparison shows that executing the checker was unnecessary for satisfying the checked task requirements. The command restriction nevertheless left an interpreter-based execution path available, illustrating the need to mediate all paths to a protected operation [46]. 

Interpreting the security and utility trade-offs. The impact of a protection mechanism on utility depends on whether its restrictions also affect operations required for legitimate tasks. Restricting capabilities shared by both legitimate and malicious operations can reduce both ASR and utility, whereas controls that target harmful operations more precisely can reduce ASR with less impact on utility. Residual attacks can still succeed when alternative commands or tools provide access to the protected operation. 

Answer to RQ3. AA relaxed confirmation requirements and increased both utility and ASR. NI and RO reduced ASR with substantial utility losses; CAL and PT largely preserved utility, with PT’s startup-refusal configuration accounting for its overall utility loss. CDL, PR, and MCP reduced ASR with overall utility gains, while PIF showed small decreases in both measures in its only paired comparison. The cases demonstrate that protection can block required legitimate operations and that allowed commands can still provide bypasses. Evaluating a setting therefore requires measuring both outcomes and checking other paths to the protected operation. 

## 7 Discussion and Limitations 

7.1 Threats to Internal Validity Approval review. Approval decisions in AA-OFF trials may vary across reviewers and can directly affect the observed AA outcomes. To standardize these decisions, we use a predefined LLM-based approval reviewer with fixed review criteria across all trials. Model bias and residual nondeterminism may still affect individual approval decisions, so the reported AA results reflect the specified approval configuration. 

Rating consistency. Researcher and model biases may affect the accuracy and consistency of RQ1–RQ2 results. To reduce inconsistency and ensure that each judgment is auditable and traceable, we design the Evidence-of-Thought (EoT) method for both human and LLM raters. EoT requires independent ratings with retained source locators and passage hashes, followed by adjudication of disagreements. 

7.2 Threats to External Validity Harness scope. Closed-source harnesses are more difficult to evaluate reproducibly because their interaction modes differ, particularly for GUI-based IDE workflows, where automated execution may not faithfully reproduce interactive operation. To improve reproducibility, our core evaluation focuses on six open-source harnesses that cover a broad range of security mechanisms. In future work, we will develop automated evaluation methods for closed-source harnesses, extend our empirical evaluation to them, and compare the automated results with manual evaluation. 14 A Preprint 

Deployment environment. Docker containers, automated execution, and simulated services do not fully reproduce real deployments. To make the evaluation closer to practical settings, we use realistic service interfaces, documentation, URLs, and task requirements, and present these resources to agents in the same way as ordinary task inputs. 

Model coverage. Using a single base LLM may limit the generalizability of RQ3 because different models can vary in tool use and instruction following, affecting both absolute ASR and the magnitude of ON/OFF differences. To enable controlled comparisons, we use GLM-5.2 in both ON and OFF settings. Future work will extend the evaluation to additional LLMs. 

Model stochasticity. Model stochasticity and occasional erroneous outputs may introduce variation across repeated executions. To reduce the influence of individual trials on the reported results, we repeat each condition ten times. 

7.3 Implications for Harness Providers Make security settings verifiable. RQ2 leaves 69 of 130 closed-source harness–mechanism cells unresolved, including all 13 closed-source PIF cells. This finding characterizes what an external assessor can establish from the available evidence. Harness providers should publish versioned mechanism-level descriptions stating whether each mechanism is implemented, whether it is active by default, how users can change that state, and which inputs or operations it covers. Exposing the effective security settings through the CLI or UI would also allow users to verify the configuration they are actually running. 

Evaluate settings against task requirements. Providers should test alternative access paths to protected re-sources [46] and check whether legitimate tasks retain an authorized completion path. Repeating these checks after changes to tool routing or permission configuration would help detect regressions in access control. Evaluations should report attack effects, task utility, token usage, and runtime together so users can select settings appropriate to their workloads and acceptable risk. 

## 8 Related Work 

Security taxonomies and empirical harness studies. Prior studies characterize harness architectures and security mechanisms using literature reviews, source code, and product materials. Surveys organize harness engineering across architectural layers [27] and systematize agent attacks and defenses [25]. An execution security review synthesizes research on isolation, access control, and time-of-check-to-time-of-use vulnerabilities [44]. Source-level and practitioner analyses examine coding harnesses and their native security mechanisms [2, 11, 16]. HarnessSecurity adds a common mechanism taxonomy and rating protocol for comparing implementation and default state across 40 open- and closed-source coding agent harnesses. Independent ratings, recorded evidence, and disagreement adjudication make these comparisons auditable while retaining unresolved cases. 

Agent and harness security benchmarks. AgentDojo and Agent Security Bench evaluate attacks and defenses in tool-using agent workflows [17, 57]. HarnessAudit examines execution trajectories for boundary compliance and execution fidelity [29], and ClawSafety compares safety outcomes across agent frameworks [53]. HarnessRisk evaluates task utility, attack success, persistence, and detection across the harness lifecycle [10]. Related poisoning studies target agent memory and retrieved knowledge [15, 58]. These benchmarks organize evaluation around workflows and lifecycle phases. HSB organizes runtime comparisons around security mechanisms and supported configurations established by RQ1–RQ2, measuring their effects on task utility and attack effects. 

Coding agent attack benchmarks. AIShellJack tests poisoned agent instruction files [31], while QueryIPI studies malicious tool descriptions and their transfer to real coding agents [54]. IssueTrojanBench, RepoGuardBench, and CodeIPI evaluate attacks through issue content and repository resources [26, 48, 49]. Skill-Inject, PoisonedSkills, and SkillHarm examine skill-package attacks [36, 42, 47]. Skill-Inject and SkillHarm also measure task utility, with SkillHarm examining persistent skill mutation across sessions [36, 47]. RedCode evaluates risky execution requests and malicious code generation [22]. Table 1 summarizes selected evaluations of coding agents. Compared with evaluations centered on particular attack resources, HSB organizes tasks around the security mechanisms and introduces adversarial resources across five attack surfaces while preserving legitimate task requirements. Separate deterministic oracles check task utility and attack effects. 

Harness defenses, configuration, and task utility. Defense studies evaluate prompt interventions and added context or action checks [26, 36, 48], capability-scoped authorization through extension hooks [12], and defense evolution 15 A Preprint 

from execution failures [41, 45]. Harness-performance studies examine interfaces, planning, action space, context management, and resource use [18, 52, 55]. These studies construct defenses or characterize harness performance. In contrast, HSB evaluates security mechanisms already implemented in coding agent products. Where supported, HSB compares native ON and OFF settings for the target mechanism while holding the task configurations fixed. These paired comparisons quantify differences in attack success and task utility. 

## 9 Conclusion 

This study identifies ten security mechanisms across 40 coding agent harnesses and assesses their implementation, default settings, and supported configurations. We introduce H ARNESS SECURITY -B ENCH to evaluate nine mechanisms across six harnesses with separate deterministic oracles for task utility and attack effects. The effects of security mechanisms on attack success and task utility varied across harnesses and tasks. Overall, network isolation and read-only mode reduced attack success with substantial utility losses, while command allowlisting and command denylisting achieved reductions with a small utility loss and a utility gain, respectively. Enabling auto-approve increased attack success in all six harnesses, and some attack effects persisted through alternative execution paths outside a mechanism’s coverage. Harness providers should publish versioned descriptions of mechanism coverage and expose effective security settings so users can verify the configuration they run. They should examine alternative execution paths to protected operations and report attack effects alongside task utility and execution costs.

An unavailable CLI surface does not establish mechanism presence or absence. - Determine source-evidence availability from the supplied snapshot, not the open-source label. [Cross-Source Interpretation Rules] - Markdown converted from an official page may duplicate a copy in the fixed repository; duplicated content counts as one independent piece of evidence. - Prefer fixed-commit source code or executable schemas when determining whether a mechanism is implemented. Prefer explicit defaults in official documentation and CLI help when determining public configuration and default state, and cross-check them against source code. - If official documentation conflicts with the fixed commit, version attribution is unclear, or defaults conflict, record the conflict and assign U; do not choose the side that better matches expectations. - Marketing security claims and SOC, privacy, or data-retention statements do not automatically establish a harness runtime security mechanism. [Five-Level Scale] D = default-enforced: Evidence is sufficient, the mechanism is implemented and active by default at runtime, and no public one-step configuration option or CLI flag can disable it. C = configurable-off: Evidence is sufficient, the mechanism is implemented and active by default at runtime, but a public one-step configuration option or CLI flag can disable it. O = opt-in: Evidence is sufficient and the mechanism is implemented, but it is inactive by default and requires explicit user enablement. A = absent: Evidence is sufficient and confirms that the mechanism is not implemented. U = unknown: Evidence is insufficient to determine implementation or default runtime state. Treat U as a separate missing value, not as absent. [Decision Tree (stop at the first match)] 1. Is the evidence sufficient to determine implementation and default runtime state? No -> U. 2. Conflicting evidence or an unconfirmed default state -> U.

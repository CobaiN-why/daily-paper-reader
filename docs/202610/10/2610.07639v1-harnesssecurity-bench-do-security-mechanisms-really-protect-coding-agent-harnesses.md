## 摘要
编码智能体运行框架负责协调工具使用并授权操作，但其安全机制与运行时效果仍未得到充分刻画。我们提出 HarnessSecurity，这是首个针对开源与闭源编码智能体运行框架的系统性实证研究与基准。首先，我们构建了一个包含十种机制的分类体系，然后利用研究人员和大型语言模型（LLM）评判者的独立评分，评估了400个“运行框架—机制”单元。我们发现，已确认的机制实现中约有一半为选择性启用（opt-in），而闭源运行框架则存在显著证据缺口。其次，我们提出 HarnessSecurity-Bench，一个涵盖五个攻击面的23项任务的基准，且不牺牲合法任务需求。我们使用独立的确定性判定器来衡量任务效用与攻击效果，并进行安全设置比较，在六款领先运行框架上评估九种机制：Claude Code、Codex CLI、Gemini CLI、gptme、Qwen Code 和 GitHub Copilot。在受控的 LLM 基线 GLM-5.2 下，我们进行了2,500次试验，记录了81,155次工具调用和超过22亿个 token。启用自动批准会提高任务效用，并将攻击成功率从29.2%提升至95.6%。网络隔离和只读模式能降低攻击效果，但会带来显著的效用损失；而命令允许列表和命令拒绝列表则分别以较小的效用损失和效用增益来降低攻击效果。任务级案例表明，对共享能力的限制可能同时阻碍合法操作与恶意操作，而被允许的工具或命令可能通过替代执行路径使未授权操作仍可到达。运行框架提供方应使安全设置可验证，测试通往受保护操作的替代执行路径，并在评估攻击效果的同时考虑任务效用与执行成本。

## Abstract
Coding agent harnesses mediate tool use and authorize actions, yet their security mechanisms and runtime effects remain incompletely characterized. We present HarnessSecurity, the first systematic empirical study and benchmark of open- and closed-source coding agent harnesses. First, we derive a ten-mechanism taxonomy and then assess 400 harness-mechanism cells using independent ratings by researchers and large language model (LLM) judges. We find that about half of confirmed mechanism implementations are opt-in, while closed-source harnesses exhibit substantial evidence gaps. Second, we introduce HarnessSecurity-Bench, a benchmark of 23 tasks across five attack surfaces without sacrificing legitimate task requirements. Using separate deterministic oracles to measure task utility and attack effects with security setting comparisons, we evaluate nine mechanisms across six leading harnesses: Claude Code, Codex CLI, Gemini CLI, gptme, Qwen Code, and GitHub Copilot. Under a controlled LLM baseline GLM-5.2, we conduct 2,500 trials, recording 81,155 tool calls and over 2.2 billion tokens. Enabling auto-approve increases utility and raises attack success from 29.2% to 95.6%. Network isolation and read-only mode reduce attack effects with substantial utility losses, while command allowlisting and command denylisting reduce attack effects with a small utility loss and a utility gain, respectively. Task-level cases show that restrictions on a shared capability can obstruct both legitimate and malicious operations, and that allowed tools or commands can leave unauthorized operations reachable through alternative execution paths. Harness providers should make security settings verifiable, test alternative execution paths to protected operations, and assess attack effects alongside task utility and execution costs.

# HarnessSecurity-Bench 论文详细中文总结

## 1. 核心问题与整体含义

- **研究背景**：基于 LLM 的编码智能体（如 Claude Code、Codex CLI）已从演示走向生产，每个智能体由 LLM 与"编码智能体运行框架（coding agent harness）"耦合而成。运行框架负责组装上下文、协调工具使用、授权操作，其设计直接影响任务成功率和资源成本。
- **核心问题**：运行框架的安全机制及其运行时效果尚未被充分刻画。现有研究存在两大缺口：
  - 架构映射与文献综述未系统评估机制实现状态与默认设置；实证对比仅覆盖 3 个编码智能体或 11 个可获取源码的框架，闭源产品代表性不足。
  - 现有基准（如 IssueTrojanBench、CapScope）未系统隔离不同框架、不同攻击面下机制设置的效果。
- **整体含义**：论文首次对开源与闭源编码智能体运行框架开展系统性实证研究与基准构建，回答三个研究问题：
  - **RQ1**：真实运行框架中可识别出哪些安全机制？
  - **RQ2**：这些机制的实现程度如何？
  - **RQ3**：在对抗增强的任务执行中，这些机制如何影响安全性与任务效用？
- **实践动因**：多起真实事件（如 Cline 分诊工作流被 issue 标题提示注入触发 shell 命令执行、OpenAI/Anthropic 网络安全评估中网络隔离失效、ZCode 上传工作区快照含 Git 历史）表明运行框架层面的风险真实存在。

## 2. 方法论

### 2.1 核心思想
- 采用"**先刻画机制、再评测机制**"的两阶段路线：RQ1 构建分类法 → RQ2 评估实现状态 → RQ3 运行时量化安全与效用的权衡。

### 2.2 十机制分类法（RQ1）
- 通过开放编码与轴心编码：8 个初始框架（覆盖 CLI、IDE 扩展、IDE 智能体、云平台四类，含开源与闭源）标注出 44 个安全标签，经 4 名研究者讨论归并为 **10 种机制**：
  - **AA** 自动批准（auto-approve）、**NI** 网络隔离、**CAL** 命令允许列表、**CDL** 命令拒绝列表、**MCP** MCP 权限、**PIF** 提示注入过滤、**PR** 路径限制、**RO** 只读模式、**AL** 审计日志、**PT** 项目信任。
- 机制按"治理的资源/操作"和"在框架循环中的执行点"区分：如 PT 决定仓库配置是否被接纳，PIF 处理不可信内容，PR 指定允许的文件目标，RO 抑制持久性变更。

### 2.3 五级评分协议（RQ2）
- 每个"框架–机制"单元赋予五级之一：**D** 默认强制、**C** 默认开启但可一键关闭、**O** 需显式启用、**A** 确认未实现、**U** 证据不足。
- **Evidence-of-Thought（EoT）** 评分方法：3 个 LLM 评分器（Claude Opus 4.8、DeepSeek V4 Flash、GLM-5.2）与 2 名人类研究者独立评分；非 U 评分必须引用具体文件路径与行号，程序校验引用范围并记录 SHA-256 哈希；≥3/5 评分一致即达成共识，18 个无多数单元由第三名人类研究者（H3）裁决。

### 2.4 HarnessSecurity-Bench（RQ3）
- **任务构造**：23 个任务（21 个原创 + 2 个改编自 Terminal-Bench），覆盖 Python、JavaScript、C++、C#、Ruby、Go 六种语言，分属 9 个子基准（aa-bench、ni-bench、cal-bench、cdl-bench、mcp-bench、pif-bench、pr-bench、ro-bench、pt-bench）。
- **攻击面增强**：在保留合法用户指令、任务需求、效用判据不变的前提下，向 5 个攻击面注入误导上下文与恶意资源——仓库/工作流工件、智能体指令/技能、工具接口、知识/记忆、外部服务/执行依赖。
- **双确定性判据**：分别用独立确定性判据测量任务效用（utility oracle）与攻击效果（attack-effect oracle），检查文件/数据库变更、接收端记录、执行事件；判据定义置于智能体工作区之外。
- **执行流程**：每次试验在全新隔离 Docker 容器中运行，固定 harness、模型、安全设置，比较机制的 ON/OFF 设置；差异量 ∆Utility 与 ∆ASR 以百分点（pp）表示。

## 6. 主要结论与发现

- **RQ1**：识别出 10 种安全机制，跨越资源准入、内容处理、操作授权、执行限制与审计日志；AA 改变确认要求，AL 支持事后审查。
- **RQ2**：400 个单元中 **205 个确认实现**（109 个 O、64 个 C、32 个 D）、**83 个确认缺失**、**112 个 U**。
  - RO 的 31 个实现中 30 个为 O，AA 的 30 个实现中 26 个为 O；MCP 的 29 个实现中 22 个默认生效，AL 的 22 个实现中 20 个默认生效。
  - PIF 仅 4 个确认实现、13 个 A、23 个 U，且**全部 13 个闭源 PIF 单元均为 U**。
  - U 在闭源单元中占 53.1%（69/130），开源仅 15.9%（43/270）。
- **RQ3 核心量化结果**：
  - **AA**：效用 77.1%→95.4%（+18.3 pp），ASR 29.2%→95.6%（+66.4 pp）；6 个框架 ASR 全部上升，但效用增益差异大（Gemini CLI +2.3 pp，Claude Code −0.8 pp）。
  - **NI**：ASR 57.1%→0.8%（−56.3 pp），效用 90.9%→66.4%（−24.5 pp）；162 个效用失败中 161 个源于必需的网络交互。
  - **RO**：ASR 8.3%→0.8%（−7.5 pp），效用 69.8%→35.8%（−34.0 pp）；367 个效用失败中 347 个源于需要持久变更的检查。
  - **CAL**：ASR 98.1%→50.0%（−48.1 pp），效用仅 −1.5 pp。
  - **CDL**：ASR 41.7%→1.3%（−40.4 pp），效用反而 **+5.2 pp**（29 个额外通过中 15 个来自 Qwen Code 与 GitHub Copilot 报告不再含签名密钥材料）。
  - **PR**：ASR 95.0%→46.9%（−48.1 pp），效用 +0.3 pp。
  - **MCP**：ASR 82.2%→54.2%（−28.1 pp），效用 +0.5 pp。
  - **PIF**：仅 gptme 配对，ASR −3.3 pp，效用 −1.9 pp。
  - **PT**：总体 ASR 75.3%→40.3%（−35.0 pp），效用 −20.0 pp（全部来自 Gemini CLI 在 40 次 ON 试验中启动拒绝）；排除该配置后其余 4 框架效用保持 100%，ASR 从 75.8% 降至 50.4%。
- **任务级案例**：
  - **案例 A（NI，Dependency Lock Repair）**：Claude Code 效用 96%→76%，ASR 100%→0；合法依赖安装与恶意回调共享同一网络能力，隔离同时阻断两者。
  - **案例 B（CAL，CLI Arg Parser）**：Qwen Code 原生网关拒绝了未授权的 checker，但智能体随后通过被允许的 Python 解释器调用它，6 个效用检查与 3 个攻击检查全部通过——说明满足检查点要求与攻击成功可以并存，且该 checker 对任务并非必需。

## 7. 优点

- **首个系统性实证**：首次同时覆盖开源与闭源编码智能体运行框架，构建 10 机制分类法并在 400 个单元上评估实现与默认状态。
- **可审计的评分方法**：EoT 要求引用具体路径与行号并记录哈希，U 与 A 严格区分（不因"沉默"判缺失），并报告 Krippendorff's α。
- **基准设计严谨**：攻击增强不改变合法用户指令、任务需求与效用判据；双确定性判据避免 LLM 判官的误判；ON/OFF 配对比较隔离机制效果。
- **覆盖多攻击面与多语言**：5 个攻击面、6 种编程语言、9 个子基准，任务来自真实专有产品与 Terminal-Bench。
- **揭示反直觉发现**：CDL 在降低 ASR 的同时**提升**效用（阻止攻击副作用反而保护了合法交付物）；AA 在部分框架效用增益极小却大幅提升攻击暴露。
- **工程建议明确**：提出安全设置可验证、测试替代执行路径、同时报告攻击效果/任务效用/执行成本。

## 8. 不足与局限

- **框架覆盖受限**：核心运行时评估仅 6 个开源框架；闭源框架因交互模式差异（尤其 GUI 型 IDE 工作流）难以可复现评估，未纳入 RQ3。
- **单一模型基线**：RQ3 仅用 GLM-5.2，不同模型在工具使用与指令遵循上存在差异，可能影响

不同模型在工具使用与指令遵循上存在差异，可能影响结论的外部效度——机制的效果（尤其是 AA 的效用增益与 CAL/CDL 的误拒率）可能与基础模型的工具调用倾向、指令遵循严格程度及对注入内容的抵抗力发生交互，单一模型无法分离"机制效应"与"模型–机制交互效应"。

- **PIF 证据最薄弱**：9 个机制中仅提示注入过滤只有 gptme 一个框架具备配对 ON/OFF 比较，且 13 个确认缺失、23 个证据不足（全部 13 个闭源单元均为 U），因此关于 PIF 有效性的 −3.3 pp ASR / −1.9 pp 效用结论不能外推。
- **机制组合的交互作用未被刻画**：所有配对比较均为"单机制 ON/OFF"，而真实部署常同时启用多个机制（如 RO + PR + CAL）。机制之间可能存在冗余（重复阻断同一攻击路径）或冲突（如 RO 抑制持久化变更，同时削弱依赖 RO 之外的其他机制的可观测性），论文未给出组合矩阵下的联合效果。
- **语料时效性与可观测性偏差**：框架迭代速度快，40 个框架的评分以 2026-08-31 为截止，结论可能随版本更新而漂移；闭源单元 U 占比 53.1% 说明其机制状态主要依赖公开文档与可观察行为推断，存在"文档缺失 ≠ 机制缺失"的系统性风险，尽管 A 与 U 已被严格区分。
- **任务规模与子基准不均衡**：23 个任务分摊到 9 个子基准，单子基准任务数偏少，PT 的总体效用损失完全由 Gemini CLI 的启动拒绝贡献，说明部分机制的效应估计高度依赖个别框架或个别任务。
- **确定性判据的双刃性**：判据虽避免了 LLM 判官的口头拒绝/实际行为不一致问题，但案例 B（Qwen Code 的 CAL）显示"通过全部效用检查与攻击检查"可以并存，且被拒绝的 checker 对任务并非必需——说明结构化事件判据仍可能高估实际任务完成质量，也可能低估部分完成的贡献。
- **环境与部署场景的差距**：全部试验在全新隔离 Docker 容器中运行，而真实开发者环境带有持久凭证、已授权网络、IDE 深度集成与跨会话记忆，机制在长时程、多会话、状态累积场景下的表现未被覆盖。
- **成本维度未纳入统一权衡**：论文报告了 81,155 次工具调用、589.32 小时执行时间与超 22 亿 token，但未将机制本身的运维成本（如 CAL/CDL 允许列表与拒绝列表的维护负担、AA 审查桥接所需的额外模型调用）与安全性、效用一并建模，因而无法给出"性价比"意义上的机制排序。

## 9. 总体评价与启示

- **方法层面的贡献最为稳固**：以"分类法（RQ1）→ 实现状态评分（RQ2）→ 运行时配对评测（RQ3）"构成闭环，并用 EoT（引用路径+行号+哈希、LLM 与人类双轨评分、Krippendorff's α 报告）把"机制是否存在"这一原本模糊的问题变成可审计的判定，这一范式可迁移到其他智能体安全评测工作。
- **实验设计的可复用要点**：攻击增强保持合法指令、任务需求与效用判据不变；双确定性判据分离"任务效用"与"攻击效果"；ON/OFF 配对、同任务同攻击变体、10 次重复；判据置于智能体工作区之外以防止被篡改。
- **对实践者的核心结论**：机制的安全收益与效用代价差异极大——CAL、PR、CDL、MCP 属于低效用代价甚至正收益的"性价比区间"；NI 与 RO 安全性提升显著但效用代价高（分别 −24.5 pp、−34.0 pp），且代价几乎全部来自合法的网络交互与持久变更需求；AA 则是最危险的默认项（ASR +66.4 pp），其效用收益在部分框架几乎为零（Claude Code −0.8 pp），应默认关闭或配合确定性审查桥接。
- **对防御者的直接建议**：安全设置应可验证而非仅可声明；测试必须覆盖"被拒后的替代执行路径"（案例 B 的教训）；评估报告应同时给出攻击效果、任务效用与执行成本三项指标，避免用单一 ASR 数字掩盖效用塌陷。
- **后续研究方向**：扩展到多基础模型（至少覆盖不同规模与不同厂商）与闭源框架的可观测性方案；研究机制组合的联合效应与自适应攻击者在机制开启后的策略迁移；把长期状态、跨会话记忆与真实开发环境纳入评测；建立机制运维成本的量化口径，形成安全–效用–成本三元权衡的完整图景。

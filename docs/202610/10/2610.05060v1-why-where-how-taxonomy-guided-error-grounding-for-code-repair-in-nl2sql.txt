## Abstract 

SQL queries that large language models write from natural language questions can execute successfully yet produce incorrect results, so execution alone does not reveal what to fix. An error taxonomy says why the query is wrong, but not 

where to look or how to change it. Existing methods can guide SQL correction through feedback, error reports, or generated plans alongside an unmasked query. We introduce TEG (Taxonomy-guided Error Grounding), which turns a supplied diagnosis into a structured correction input for natural language-to-SQL (NL2SQL) correction. Type-specific rules map each error type to construct classes to reconsider and an edit operation to request. TEG masks the selected constructs in the query when applicable and states that operation in an edit instruction. TEG generates candidate corrections from this input, uses execution feedback to guide candidate selection, and repeats the process one annotation at a time for queries with several errors. On NL2SQL-BUGs, TEG reaches 47.3 single-error execution accuracy and 37.0 overall with Qwen2.5-7B-Instruct. Across the model sizes and thinking modes evaluated in the main comparison, TEG outperforms all evaluated baselines on single-error queries, even when the baselines receive the same error-type annotations. With predicted types, TEG stays above direct LLM correction and ErrorLLM on single-error queries. 

## 1 Introduction 

Large language models (LLMs) now generate code from natural language specifications (Chen et al., 2021; Jiang et al., 2026). A generated program can be syntactically valid and run without an exception while still returning a wrong result, so execution alone does not establish correctness and semantic errors must be repaired (Liu et al., 2023; Pan et al., 2023; Chen et al., 2024a; Li et al., 2026a). Natural language-to-SQL (NL2SQL) is an acute case: agents increasingly rely on generated SQL over large relational databases (Lei et al., 2025), and a wrong query can return a plausible table rather than an error (Liu et al., 2025b). A diagnosis from an error taxonomy tells the LLM why the query is wrong, but not where to look in the query or how to change it. Reasoning and self-correction methods (Kojima et al., 2022; Madaan et al., 2023; Chen et al., 2024b) supply no error-type diagnosis, so the model must discover the why, the where, and the how from the code and available feedback. NL2SQL pipelines such as DIN-SQL, MAC-SQL, and SQLFixAgent combine SQL generation with self-correction or execution-guided refinement (Pourreza & Rafiei, 2023; Wang et al., 2025a; Cen et al., 2025). ErrorLLM (Hong et al., 2026) is a closely related approach: it starts from an error type, locates candidate syntax-tree nodes and schema elements under type-specific guidelines, and supplies them as context next to the issued query for a single refinement call. TEG turns the supplied diagnosis into a correction input: deterministic rules select construct classes to mask when applicable and specify the requested edit. We call this mapping error grounding (Figure 1): translating a taxonomy-level diagnosis into the classes of query constructs to reconsider and the edit operation to request. For example, a diagnosis of an incorrect reference selects the class of expressions that carry references and requests a replacement, whereas a missing construct selects no existing element and requests an insertion. SQL offers both an error taxonomy and structural editing rules: it exposes recurring constructs over an explicit schema, and a SQL error taxonomy labels semantic errors directly in terms of these constructs (Liu et al., 2025b). We propose TEG (Taxonomy-guided Error Grounding), which realizes error grounding for SQL on the syntax tree that SQLGlot parses from the query. The where rule maps each supplied error type to the constructs to reconsider: TEG masks the associated syntax-tree nodes when applicable, such as column expressions for Attribute Mismatch . The how rule maps the same type to an edit instruction, such as replacing the masked construct for a Mismatch or inserting an absent one for a Missing error. Because the rules select construct classes, masks can cover correct constructs; the LLM generates a complete query from the grounded input. Grounding sets where and how, but in our development runs a single output often named a column or value not in the database. TEG therefore generates several candidates, prefers those that execute and return rows, and lets an LLM refiner select or rewrite among them, a stage we develop from SQLFixAgent (Cen et al., 2025) for grounded prompts. With several errors, one prompt carrying every error type would mix several masks and instructions. TEG instead processes one annotation at a time, editing existing constructs before inserting new ones, and re-grounds the output of each step. We evaluate TEG on incorrect queries from NL2SQL-BUGs (Liu et al., 2025b), derived from BIRD (Li et al., 2023), against the methods above and our adaptation of ErrorLLM. TEG outperforms every evaluated baseline on single-error queries across the model sizes and thinking modes evaluated in the main comparison, and the lead holds when baselines receive the same annotations. On Qwen2.5-7B, it reaches 47.3 execution accuracy on single-error queries and 37.0 over all queries, against 33.6 and 24.0 for ErrorLLM, and leads every baseline on multi-error queries. With predicted types, TEG stays above direct LLM correction and ErrorLLM on single-error queries across all evaluated configurations. The w/o masking variant retains the error types but reduces single-error accuracy from 47.3 to 40.9, supporting the masking-based editing configuration within TEG. In summary, our main contributions are: 

• We formulate error grounding for SQL correction. We map a supplied diagnosis ( why ) to construct classes to reconsider ( where ) and an edit instruction ( how ). This mapping constructs the correction input without requiring exact fault localization. 

• We design type-specific rules and sequential re-grounding in TEG. Four edit groups cover the 29 evaluated NL2SQL-BUGs sub-types, with masking when applicable and type-specific edit instructions. For multiple errors, TEG reapplies the rules to the updated query for each annotation. 

• We demonstrate improved SQL correction with TEG. TEG achieves the highest observed accuracy in the main comparisons, including those with shared annotations. We also evaluate predicted-type correction on single-error queries and compare component variants to examine grounding, sequential correction, and candidate selection within the pipeline. 2Preprint 

## 2 Related Work 

Reasoning and self-correction. Reasoning prompts such as CoT (Kojima et al., 2022; Wei et al., 2022) elicit step-by-step analysis, while Self-Refine (Madaan et al., 2023) and Self-Debug (Chen et al., 2024b) guide correction with natural language critiques, code explanations, or execution feedback. Self-correction can also be learned (Kumar et al., 2025), although improvement through intrinsic feedback alone is not guaranteed (Huang et al., 2024). These methods supply no error-type diagnosis, so the model must decide why, where, and how to correct from the code and its feedback alone; TEG instead assumes the diagnosis is given and asks how best to use it. 

SQL-specific refinement. LLMs have enabled diverse NL2SQL approaches (Liu et al., 2025a). These span prompt design, task-specific training, structure-guided generation, and test-time scaling (Dong et al., 2023; Li et al., 2024; Zhang et al., 2024; Liao et al., 2026; He et al., 2025; Li et al., 2025; Wang et al., 2025b). Refinement and debugging pipelines use self-correction, execution feedback, or alternative query representations (Talaei et al., 2024; Askari et al., 2025; Xu et al., 2025b; Li et al., 2026b; Qu et al., 2025). DIN-SQL (Pourreza & Rafiei, 2023) couples decomposed generation with self-correction, MAC-SQL (Wang et al., 2025a) coordinates schema selection, decomposition, and execution-guided refinement, and SQLFixAgent (Cen et al., 2025) separates query review, candidate generation, and refinement across agents. Candidate validation and selection are also studied (Fan et al., 2025; Gorti et al., 2025; Lee et al., 2025; Pourreza et al., 2025). TEG develops its execution-based candidate selection from SQLFixAgent (Cen et al., 2025) for grounded inputs. 

Program repair and code infilling. DrRepair localizes faulty lines (Yasunaga & Liang, 2020), while LecPrompt uses CodeBERT for token-level localization and repair (Xu & Sheng, 2024; Feng et al., 2020). Masked-span reconstruction (Guo et al., 2022) and code infilling (Fried et al., 2022; Allal et al., 2023) recover missing code from surrounding context. TEG selects construct classes by error type without exact fault localization and uses masks when applicable and edit instructions as correction inputs. It trains no infilling model; the LLM generates full queries and may edit unmasked constructs. 

Error taxonomies and detection. Error taxonomies give diagnoses reusable categories, from software defect classifications (Chillarege et al., 1992) to the semantic SQL errors annotated in NL2SQL-BUGs (Liu et al., 2025b). Related SQL error detection methods assess generated queries using learned structural representations (Chen et al., 2023) or metamorphic testing (Yang et al., 2025b). Multi-grained error identification (Xu et al., 2025a) distinguishes system, skeleton, and value errors and uses type-specific feedback to guide SQL correction. SQLens (Gong et al., 2026) combines database and LLM signals into clause-level error reports with correction instructions and uses these reports to guide sequential refinement of the generated query. 

Taxonomy-guided refinement. SQL-of-Thought (Chaturvedi et al., 2025) uses an error taxonomy to guide an LLM-generated correction plan, which a separate agent uses to revise the query. ErrorLLM (Hong et al., 2026) is closely related: its error taxonomy draws on NL2SQL-BUGs, and its refinement stage uses error types to guide structural correction. It trains an error detector that predicts taxonomy categories with dedicated error tokens from the question, schema, and SQL structure, and localizes relevant syntax-tree nodes and schema elements under type-specific guidelines. The error type also governs the scope of context extraction, and the resulting subtrees, schema context, and analyses are supplied alongside the issued query for joint refinement. We adapt its refinement stage as a principal baseline, using the same supplied error annotations as TEG. TEG maps the supplied diagnosis ( why ) through deterministic rules to construct-class masks ( where ) and edit instructions (how ), removing selected constructs from the query input when masking applies.

Here, step 1 replaces the masked WHERE predicate for an Explicit Condition Mismatch ; step 2 inserts the missing subquery for Subquery Missing into step 1 's output. 3.1 Grounding error types into masks and edit instructions Grounding turns an error type, which says why a query is wrong, into two parts of the correction input rather than of its output: a mask over the constructs to reconsider, which tells the LLM where 

to look, and an edit instruction, which tells it how to change them. The mask removes the selected constructs from the query the LLM sees, and the edit instruction names the requested edit, so one error type determines both what the LLM reconsiders and what it is asked to do. TEG prompts an off-the-shelf LLM with an issued query, its question, schema, and error annotations, and returns a corrected query. Let 𝑞 be the issued query, 𝑛 its natural language question, and 𝑆 the database schema. We assume an annotation sequence E = (( 𝑡 1, 𝑠 1), . . . , (𝑡 𝑚 , 𝑠 𝑚 )) , where each pair specifies an error category (e.g., Attribute-Related Errors ) and sub-type (e.g., Attribute Mismatch ). The goal is a corrected SQL query 𝑞 ∗ semantically aligned with 𝑛 under schema 𝑆 . We call |E| = 1the single-error setting and |E| > 1 the multi-error setting. The grounding rules act on four edit groups that TEG defines over the error taxonomy of NL2SQL-BUGs (Liu et al., 2025b). The queries we evaluate cover nine categories and 29 observed sub-types, classified by the SQL construct they affect, such as Attribute-Related , Table-Related , and Clause-Related . The four groups are Mismatch , Redundancy , Missing , and Rewrite , and the mapping from sub-types to groups is part of TEG and specifies the default edit operation and correction order. The annotations retain their original taxonomy categories and sub-types. The where rule maps the category and sub-type to classes of nodes in the abstract syntax tree (AST) to mask. For Mismatch and Redundancy , TEG masks matching existing constructs. Missing requests an absent construct and Rewrite requests broader restructuring, so TEG leaves the query unmasked for both. For example, Attribute Mismatch hides column expressions, Explicit Condition Mismatch hides the WHERE predicate, and Aggregate Functions hides the aggregate together with the grouping and filtering clauses that depend on it. The rules also set the granularity of masking: hiding a single node can leave a dependent clause inconsistent after repair, whereas hiding a whole clause can discard context the LLM would otherwise keep, so each rule sets the unit per error type. The how rule specifies an edit instruction for the supplied error type: replace for Mismatch , remove for Redundancy , insert for Missing , and restructure for Rewrite , which covers incomplete queries and errors that need broader changes. Sub-types such as Aggregate Functions and ASC/DESC are grouped with Mismatch for the correction order, but their edit instructions depend on whether a mask is present: replacement or deletion with a mask, and insertion without one. For the DISTINCT sub-type, the instruction also permits restructuring joins, projection, or grouping. 3.2 Grounded correction with candidate selection A correction step applies both rules to one annotation and asks the LLM for a repaired query. For 

Mismatch and Redundancy , TEG parses the current query with SQLGlot and replaces the selected constructs with <MASK> placeholders; Missing and Rewrite leave the query unmasked. Attribute masking locates column expressions in the parsed tree and replaces their SQL strings, whereas the other masking rules replace the AST nodes themselves. When masking is applied, the prompt does not include the unmasked query, so the LLM resolves each placeholder without seeing the removed constructs. Masking removes the selected constructs from the input, whereas naming the error type leaves them in place. The rules select node classes deterministically, but the LLM decides what to change: several nodes may match, and some may already be correct. The LLM generates a complete query, so the output can revise unmasked constructs as well as fill the placeholders. TEG selects the corrected query from several candidates with execution feedback, because one answer to a grounded prompt can name a column or value absent from the database. We develop this selection stage from the QueryCrafter and SQLRefiner of SQLFixAgent (Cen et al., 2025) for grounded prompts, combining candidate generation, execution filtering, and LLM-based selection or refinement. The original question and up to three paraphrases yield at most four candidates per step. The paraphrases are generated once and reused as later steps correct the updated query. 3.3 Sequential re-grounding for multiple errors We design sequential correction to process one annotation at a time and re-ground the query after each update, so that each step targets one error type with its own mask and instruction. TEG uses the order Mismatch , Redundancy , Missing , Rewrite , preserving input order within groups. We edit existing constructs first because an insertion or restructuring can move or remove the constructs a later rule would select. Re-grounding applies the current annotation to the query produced by earlier steps, masking it only when applicable. TEG retains the supplied annotations without predicting new error types, and later edits can undo an earlier repair. If masking yields no placeholder and a previous correction step exists, TEG uses the current query without masking, together with a retry instruction that names both the current and the previous errors. If E is empty, as when no error type is predicted, TEG falls back to one unmasked correction call and keeps 𝑞 if it yields no SQL.

4.1 Setup We evaluate on NL2SQL-BUGs (Liu et al., 2025b), derived from BIRD (Li et al., 2023), using incorrect queries paired with reference SQL; the evaluation subset covers 29 error sub-types across nine categories. Execution accuracy measures whether the corrected query and the reference query return the same set of row tuples on the same database, ignoring row order and duplicates while preserving column order. Queries that raise execution errors or exceed the 5s time limit are counted as incorrect, and all accuracy scores are reported on a 0–100 scale. During correction, TEG executes its own candidates with a separate 5s limit and never sees the reference SQL or its result. For the main comparisons, we use Qwen2.5-Instruct (Yang et al., 2024) at 7B, 14B, and 32B and Qwen3-8B (Yang et al., 2025a) with thinking OFF and ON, all with greedy decoding, as the LLM for every method. With each model, we compare TEG against the LLM itself and three baseline groups: 

• Base : the LLM itself, asked once to correct the unmasked query with no error type, as the reference for what each correction method adds beyond a single call. 

• Reasoning and self-correction : CoT (Kojima et al., 2022) and Self-Debug in its Simple and Expl variants (Chen et al., 2024b), which we adapt to SQL correction by prompting them to analyze or critique the given erroneous query and produce a corrected query. 

• SQL-specific refinement : DIN-SQL (Pourreza & Rafiei, 2023), MAC-SQL (Wang et al., 2025a), and SQLFixAgent (Cen et al., 2025), which we adapt to SQL correction by providing the given erroneous query as input or context, without an error-type diagnosis. 

• Taxonomy-guided refinement : our adaptation of ErrorLLM (Hong et al., 2026), which uses AST-node localization, error-specific subtree and schema-context extraction, and joint refinement. It uses the supplied annotations instead of its trained error detector, and database metadata with lexical matches to the question instead of the learned question–schema encoder. We additionally evaluate Base, ErrorLLM, and TEG with Opus 4.8 as the corrector in Section 4.3. Unless otherwise stated, supplied error types are oracle annotations from NL2SQL-BUGs. ErrorLLM and TEG receive these annotations in the main comparisons, while Base and the other six baselines receive no error types. We additionally evaluate all baselines with the same annotations. 4.2 Main results 

Single-error queries. Each query tests one grounded correction step without sequential re-grounding. TEG has the highest single-error accuracy in every configuration reported in Table 1. At 7B, it exceeds the strongest baseline, CoT, by 11.8 points (47.3 versus 35.5). Across the Qwen2.5 scales, it reaches 47.3, 52.7, and 57.3, against 33.6, 51.8, and 53.6 for ErrorLLM. On Qwen3-8B, it reaches 46.4 with thinking OFF and 57.3 with thinking ON, above the strongest baseline in each mode, Self-Debug (Expl) at 44.5 and Self-Debug (Simple) at 50.9. TEG scores above CoT at every Qwen2.5 scale and above Base in both Qwen3-8B thinking modes. On Qwen3-8B, thinking lifts Base from 31.8 to 43.6 and TEG from 46.4 to 57.3. TEG can complement model reasoning. 

Multi-error queries. The lead extends to queries with several errors (Table 2). With Qwen2.5-7B-Instruct on all queries, TEG reaches 37.0 overall against 26.2 for SQLFixAgent, the strongest baseline, and 24.0 for ErrorLLM, and it leads every error-count group, although its accuracy declines as the number of errors increases. It also leads every error category on multi-error queries, by 5.9 to 15.4 points over the next best method. 

Baselines given error types. TEG 's lead persists when all methods receive the same error types. To distinguish access to the error type from how it is used, we add the same annotations to each baseline 's prompts while retaining its correction procedure. TEG stays ahead in all five configurations on single-error queries, by 0.9 points at Qwen2.5-14B and Qwen3-8B with thinking OFF and by 11.8 points at Qwen2.5-7B, and on all queries it reaches 37.0 against 26.0 for the strongest baseline given error types, Self-Debug (Simple), leading in every error-count group. Error types help some baselines but not others: at 7B, CoT falls from 35.5 to 32.7, while Self-Debug (Simple) rises from 33.6 to 35.5. Access to error types alone does not explain TEG 's advantage. ## 5 Conclusion and Discussion 

We introduced error grounding for SQL correction: mapping why a query is wrong to construct classes (where ) and edit instructions ( how ) that shape the LLM 's correction input. On NL2SQL-BUGs, TEG leads the main comparisons even with shared annotations and outperforms direct correction and ErrorLLM with predicted types on single-error queries. The w/o masking variant retains the types but lowers single-error accuracy by 6.4 points with Qwen2.5-7B. These results support using error types to construct correction inputs through masking and edit instructions. 

Beyond SQL. Extending error grounding beyond SQL would retain the mapping from error types to editable structures ( where ) and requested operations ( how ). In general-purpose code, an API-misuse diagnosis could select call expressions and their arguments for replacement. In configuration files, an incorrect-value diagnosis could select fields for replacement, whereas a missing-key diagnosis would request insertion without masking. Each domain would need identifiable constructs, its own grounding rules and correction order, and candidate checks such as tests, type checks, or schema validation. These extensions remain untested; Appendix E discusses their requirements. 

Limitations. We evaluate on one SQL benchmark, also used to select the correction order; predicted-type evaluation covers only single-error queries. TEG requires diagnoses and database access and adds inference cost. Attribute masking operates on the SQL string as written in single-error mode and on the SQLGlot-serialized SQL in multi-error mode. Condition masking targets Where nodes and, in multi-error mode, Having 

16 Preprint nodes as well. Table masking distinguishes Table from Join targets in multi-error mode, whereas single-error mode masks both for every non-Missing Table-Related sub-type. Two rules go beyond a plain node-class lookup. For Aggregate Functions , TEG first masks AggFunc , Group , and Having 

nodes, then locates the first Where subtree in SQLGlot traversal order. Within that subtree, each comparison containing a placeholder is masked in full, so the LLM can regenerate the predicate together with the aggregate. Comparison masks are limited to Where and Having , and logical masks cover only the outermost logical expression, so nested operators are masked once.

19 Preprint A.3 How: Prompt templates for each edit The correction prompt is constructed from four components: the (possibly masked) SQL query ˜ 𝑞 , the natural language question 𝑛 , the database schema 𝑆 , and the error category and sub-type (𝑡, 𝑠 ). TEG uses five correction templates, each covering one or more error categories, plus a retry template for multi-error steps whose mask is empty and a base template for queries without an annotation. The masked query replaces the issued query in the prompt, and no separate copy of the unmasked query is supplied. Every template that uses an annotation supplies its category and sub-type labels without the taxonomy definitions, and the model returns the corrected query as JSON: {"sql": "..."} .

Default template. Used for most categories ( Attribute-Related , Table-Related , Value-Related ,

Condition-Related , Clause-Related ). The instruction reflects the requested edit. For Mismatch errors, the model is asked to fix the masked part. For Redundancy , it is asked to delete the masked part. For 

Missing errors, it is asked to insert the absent SQL fragment at the appropriate position. 

Operator-Related template. If masked parts are present, the model fixes or deletes them. If no mask is present, the model inserts the appropriate operator (e.g., AND , OR , comparison operators). 

Function-Related template. If masked parts are present, the model fixes or deletes them. If no mask is present, the model inserts the appropriate function (e.g., CAST , CASE , aggregate functions). 

Subquery-Related template. The instruction follows the same Mismatch /Redundancy /Missing 

structure as the default template, with two additions: Missing errors specifically prompt insertion of the missing subquery, and Partial Query errors prompt completion of an incomplete SQL query. 

Other template. If masked parts are present, the model fixes or deletes them. If no mask is present, the behavior depends on the sub-type. ASC/DESC errors prompt insertion of the missing fragment. 

DISTINCT errors prompt a rewrite that may involve adding or removing the DISTINCT keyword, or restructuring joins, SELECT columns, or grouping. Other errors prompt a rewrite from scratch unless the retry condition below applies. 

Retry template. When a masking attempt yields no <MASK> and a previous correction step exists, the step uses this template with the unmasked current query. It lists the previous and current annotations, describes the first as a previously failed correction attempt and the second as the error to fix, and asks for a regenerated query. It carries no operation-specific instruction. At the first step, an empty mask falls back to the correction template for the current error category instead. 

Base template. The base template supplies the query, question, and schema with no error information and asks the model to regenerate the query if it is semantically misaligned. It is the prompt of the Base rows in the tables, TEG’s one-call fallback when no error type is predicted, and the correction prompt of the w/o error annotation ablation, which keeps paraphrases and execution-based selection. A.4 Execution-based candidate selection Grounding determines the input of a correction step, and candidate selection decides its output. A single answer to a grounded prompt can name a column or value that the database does not contain, so TEG generates several candidate queries, filters them by executing them, and asks an LLM to select or refine one, a stage developed from SQLFixAgent (Section 3.2). The crafter is called once per query and asked for four paraphrases of the natural language question, of which the first three parsed paraphrases are kept, so each correction step issues its prompt at most four times, under the original question and under each paraphrase, and yields at most four candidate queries; every step reuses the same paraphrases with its current query and edit instruction. Candidates are executed against the database with a 5s timeout per candidate. The execution filter prefers candidates that run, return at least one row, and contain no NULL in the first five returned rows. The filter is a heuristic, since valid results can be empty or contain NULL. If none passes, all generated candidates remain eligible, and duplicate SQL strings are then collapsed. With no generated candidate, TEG retains the current query. With one distinct candidate, it returns that candidate directly, even if it failed the execution filter. With multiple candidates, the refiner receives the question, schema, candidate SQL strings, and 20 Preprint accumulated failure messages, each recording the selected SQL, the SQLite error, and the exception class. The database-content field of the SQLFixAgent prompt is left empty. The refiner returns a reasoning string and one SQL, selected or rewritten, for up to three rounds, and stops when its SQL passes the same execution filter or times out. The timeout stop is inherited from the SQLFixAgent implementation and does not certify correctness. A round that returns no SQL is skipped. If no round meets either stopping condition, TEG returns the last candidate in the pool. Evaluation still scores timeouts as incorrect. The crafter and refiner prompts are those of SQLFixAgent (Cen et al., 2025), with its similar-example memory left uninitialized, which is the authors’ no-memory branch. 21 Preprint

B.3 Baseline implementations The baselines share TEG’s LLM and decoding settings within each comparison column. Base and the reasoning and SQL-specific baselines are evaluated both with and without oracle error types. ErrorLLM always receives the same annotations as TEG. We re-implemented the methods and chose iteration counts in preliminary experiments. TEG’s crafter and refiner reuse the SQLFixAgent authors’ prompts, whereas the reported SQLFixAgent baseline uses our revised prompts. The reported rows are as follows. 

• CoT (Kojima et al., 2022): The model is prompted to analyze what the question requires, where the given SQL deviates from it, and what fix is needed, then return its reasoning and corrected SQL. The main comparison uses no error-type information or masking. 

• DIN-SQL (Pourreza & Rafiei, 2023): A full NL2SQL pipeline that decomposes the task into schema linking, query classification, and SQL generation, using the issued SQL as context. The generated SQL is then reviewed and revised via a self-correction stage. The schema context includes up to three sample rows per table when available; generated queries are not executed for correction feedback. 

• Self-Debug (Simple) (Chen et al., 2024b): The simple-feedback variant, which uses no execution signal. After an initial single-pass correction, each turn asks the model to judge whether its current query is correct and, if not, to emit a revision. We allow up to 3 feedback-correction turns and stop early as soon as the model judges the current query correct. 

• Self-Debug (Expl) (Chen et al., 2024b): Adds execution feedback and self-explanation on top of the simple variant. Each turn executes the current query and issues three calls: one explaining what the query returns given its execution result, one inferring what the question asks for, and one comparing the two to judge and revise. Up to 3 turns with the same early stopping. 

• MAC-SQL (Wang et al., 2025a): Our adaptation supplies the issued SQL to a Decomposer that decomposes the question and generates corrected SQL. A Selector prunes the schema only when 23 Preprint its representation exceeds 3,000 tokens, counted with a Qwen2.5 tokenizer. A Refiner revises the generated SQL on execution errors, timeouts, or empty results for up to 3 rounds, stopping when execution returns a nonempty result. 

• SQLFixAgent (Cen et al., 2025): A multi-agent pipeline that first repairs the issued SQL in a single pass, then prompts a reviewer to check the result clause by clause for semantic errors. Its error check is prompt-based and uses no execution signal, and queries the reviewer passes are returned unchanged. When an error is flagged, a crafter produces up to 3 question paraphrases, and a separate generation call for each paraphrase uses the issued SQL to produce a candidate, keeping those that execute without error, and a refiner then selects or rewrites among the candidates using execution-based verification with a failure memory, for up to 3 rounds. The candidate filter accepts any executable query, including empty results; the refiner stops on a nonempty execution result and records execution failures or empty results in its failure memory for the next attempt. TEG additionally prefers nonempty results without NULL in the first five rows, and keeps all candidates when none passes. 

• ErrorLLM (Hong et al., 2026): We use a structural refinement adaptation with the same LLM and supplied annotations as TEG. A localization call receives the question, schema, SQLGlot AST with node IDs, and error-specific guidelines, and returns relevant AST nodes, schema elements, and filled analyses. The implementation extracts the corresponding AST subtrees and related schema context. A second call receives these contexts, the filled guidelines, correction examples, and issued SQL, and corrects the supplied errors jointly in priority order. The schema graph uses database metadata and lexical links to the question, rather than the original ELECTRA/RGAT QSS encoder. We do not reproduce the trained error-token detector. When no valid AST-node or schema-element references remain, context extraction falls back to the full AST or schema graph, respectively, and invalid refinement output or an empty prediction retains the issued query. The method uses no database execution feedback during generation. B.4 Ablation variants Table 4 removes or alters one part of TEG per row, with Qwen2.5-7B-Instruct and oracle error types. The variants are implemented as follows. The w/o error annotation ablation drops the annotation and therefore masking and sequential correction as well: it issues one correction step with the base template of Section A.3, retaining paraphrases and execution-based candidate selection. The w/o masking ablation keeps the annotations and category-specific templates but leaves the query unmasked and disables the retry branch. Removing the masks can also change which conditional edit instruction applies. The w/o DB execution ablation removes database execution during correction. Candidates are de-duplicated without execution-based filtering. With multiple distinct candidates, the refiner is called once with an empty failure memory, falling back to the last candidate if it returns no SQL. A sole candidate is returned directly; if none is generated, the current query is retained. The w/o candidate selection ablation removes the crafter and the refiner, leaving one prompt and one candidate per correction step. The w/o sequential correction ablation applies the masks of all annotations cumulatively to one query and issues a single prompt built from the template of the first annotation’s category, listing every annotation. The candidate selection stage is unchanged and runs once on that single prompt. D.1 Accuracy of predicted error types We predict error types with one call to Opus 4.8 ( claude-opus-4-8 ) per query, using adaptive thinking and an output limit of 8,192 tokens. The prompt provides the question, issued SQL, and schema DDL, together with short definitions of all 31 taxonomy sub-types. It requests a JSON response containing a correctness decision and a list of error category and sub-type pairs; the reference SQL and oracle annotations are not supplied. We parse the predicted labels, normalize category and sub-type names to the taxonomy, and discard unrecognized pairs. The resulting predictions are saved and shared across all correctors in the predicted-type comparisons. Table 16 evaluates the error types predicted by Opus 4.8 against the oracle error types on all 549 queries. ## E Extended Discussion 

This section expands the discussion in Section 5: what the results say about using a diagnosis, where the idea of error grounding comes from, and what carrying it beyond SQL would require. E.1 Using error diagnoses to construct correction inputs The comparisons with baselines given the same error types and the masking ablation support using diagnoses to construct correction inputs: TEG retains its lead, and the w/o masking variant lowers accuracy while retaining the types. These comparisons evaluate the full pipelines and editing configurations rather than isolating masking alone. The 7B gains suggest potential for locally hosted correction in organizations that keep sensitive database context on premises, provided error annotations can also be supplied locally. The size of the benefit depends on the LLM and on whether the types are oracle or predicted. The near tie with ErrorLLM under oracle types on Opus 4.8 suggests that a strong LLM also makes good use of the type-specific context that ErrorLLM extracts. E.2 Relation to visual grounding and inpainting Visual grounding links linguistic descriptions to image regions (Yu et al., 2018b), offering an analogy for connecting an error diagnosis to code structures. TEG grounds types in construct classes and edit instructions, so its targets can include correct occurrences rather than an exact faulty location. Its masking is inspired by image inpainting (Yu et al., 2018a) and mask-guided diffusion editing (Avrahami et al., 2022), where selected content is regenerated from its surroundings. TEG adopts this regeneration with an LLM that generates complete queries, without diffusion or a fixed edit boundary, so the LLM may also change unmasked constructs. E.3 Carrying error grounding beyond SQL A transfer needs recurring error categories, identifiable editable elements, and instructions that preserve the surrounding constraints. An AST can expose these elements in code, while a schema can do so for configuration data. Candidate selection could use tests, type checks, or schema validation where available, although these checks would not by themselves establish semantic correctness. Sequential correction would also need to account for dependencies between edits and the possibility that one correction invalidates another. Each domain would keep the mapping from error types to editable structures and requested operations. In general-purpose code, an API-misuse category could select call expressions and their arguments for replacement. In configuration files, an incorrect-value category could select fields for replacement, while a missing-key category has no existing construct to select and would request insertion. These applications are prospective; each domain would need its own masking rules and correction order. The results here establish evidence in SQL, leaving the effectiveness and cost of these extensions to future evaluation. 32

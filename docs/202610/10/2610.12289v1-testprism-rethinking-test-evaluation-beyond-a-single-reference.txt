Large language model (LLM) coding agents have advanced test generation across diverse pro-gramming tasks. However, the common practice of evaluating tests against a single reference solution overlooks alternative valid implementations and can overstate test quality. We introduce 

TestPrism , comprising 300 test tasks from 17 sources and 3000 candidate implementations, evenly split between valid and invalid solutions. Its primary metric, Joint Success Function , requires the generated tests to fail on the initial program state, accept every valid candidate, and reject every invalid candidate. Across fourteen baseline coding agent configurations, Joint Success Function reaches only 28.00%, whereas single reference success reaches 59.67%. Our analysis reveals missed behaviors, unsupported assertions, and faulty test construction. To address these weaknesses, we introduce TestHelix , which combines heterogeneous synthesis of test and repair pairs with peer cross validation and recursive self improvement (RSI). Across two models, TestHelix improves Joint Success Function by 8.67 to 9.00 percentage points over the native harness comparators in the TestHelix evaluation.

# 1 Introduction 

Large language model (LLM) coding agents, such as Codex and Claude Code, can navigate repositories, modify implementations, and validate changes through execution feedback (Yang et al., 2024a; Wang et al., 2024; 2025b; Pan et al., 2026; Li et al., 2026b). These capabilities also support automated test generation and improvement (Chen et al., 2024; Alshahwan et al., 2024). Reliable tests must generalize across valid implementations while remaining sensitive to specification violations (Zhu et al., 1997; Barr et al., 2015). 

Limitations of Existing Benchmarks. Test generation benchmarks span function level tasks, as in TestEval (Wang et al., 2025a), and repository issues, as in SWT Bench (Mündler et al., 2025). A common success criterion remains single reference evaluation : a suite must fail on the initial program and pass on one gold solution (Mündler et al., 2025; Ahmed et al., 2024). Yet a requirement can admit multiple valid implementations and plausible incorrect ones. A test can pass this check while missing required behavior (Qi et al., 2015; Liu et al., 2023) or imposing unnecessary implementation constraints. We therefore ask: How robust is the evaluation of generated tests to variation across implementations? This task diversity supports assessing how well coding agents generalize test generation across programming scenarios. Complementary acceptance, rejection, and coverage metrics locate behavioral disagreements and the code exercised by the tests. 

TestHelix. We introduce TestHelix to address these weaknesses through heterogeneous synthesis of test and repair pairs. Its inner workflow establishes consistency within each pair, then uses peer cross validation, comprising cross execution, semantic review, and corrective feedback, to check and correct tests across pairs. Its outer RSI loop proposes test generation strategies on training tasks and validates one frozen challenger on a disjoint set before benchmark evaluation. 

Takeaways. We evaluate fourteen coding agent configurations spanning six model families. Our analysis reveals four key findings: ❶ Reliable test generation remains far from solved by frontier models. The strongest baseline reaches only 28.00% Joint Success Function, compared with 59.67% single reference success (Table 2). Coverage tracks success: change and entry coverage correlate with Joint Success Function across configurations ( r = 0.91 and 0.96 ). ❷ Joint Success Function is a dynamic measure of reliability across implementations. Larger candidate panels impose additional behavioral requirements, as shown in Figure 3. Single reference evaluation is its weakest special case and an upper bound on expanded panel success. ❸ Failures span coverage gaps, faulty checks, and execution logic errors. We sample 300 failed trajectories, 50 from the highest Joint Success Function configuration in each of six model families, and analyze 286 after excluding 14 timeout trajectories. The category shares among the analyzed trajectories are 34.6%, 50.0%, and 15.4%, respectively (Figure 4), explaining limited reliability through omissions, misjudgments, and execution failures. 2.1 Step 1: Task Screening and Adaptation 

We curate tasks from 17 public benchmarks, including the widely used SWE bench and Terminal Bench families (Jimenez et al., 2024; Merrill et al., 2026), requiring traceable test provenance and documented validation (Appendix B.3.1). We retain coding tasks whose requirements can be checked with executable tests, excluding unusable Docker images and irreproducible environments. Adapters map tasks to Harbor’s instruction, environment, tests, and solution components while preserving requirements, initial states, verifiers, reference solutions, dependencies, services, and execution limits. 

2.2 Step 2: Task Selection 

We screen tasks using Solution Size , the effective lines of solution.sh ; Test Count , the enumerated test functions or metadata checks; and Test Density , this count per file changed by the reference solution.

Lower bounds are calibrated to each source’s own distribution, and source quotas balance representation across the disjoint training and candidate test sets. Appendix B.2 reports the source-specific screening thresholds. We retain 1,700 training tasks for TestHelix’s recursive self improvement (RSI); only candidate test tasks undergo the remaining patch generation and filtering steps. 

2.3 Step 3: Patch Generation and Validation 

Verifier validation. All source benchmarks provide test suites validated through execution checks, expert review, or official competition evaluation. Our additional validation round checks each adapted verifier before candidate generation, requiring failure on the initial state and success on the reference solution. Two experts use development experience to independently assess task requirements and source verifiers for potential overfitting and coverage gaps. Discussion clarifies disagreements; tasks with unresolved concerns are excluded. Independent verifier usability judgments achieve Cohen’s κ = 0.68 . Appendix B.3.1 documents the prior validation evidence and our additional review. 

Patch generation. We generate candidate patches with different coding agents and models of varying capabilities to capture alternative solutions and errors arising during task solving, complementing mu-tation based fault models (Just et al., 2014; Jia & Harman, 2011). We remove empty submissions, exact duplicates, and inapplicable patches, then execute the source verifier in clean environments and record outcomes for individual checks. A candidate is valid if every check passes and invalid if any check fails. These labels remain fixed when evaluating generated tests. 

2.4 Step 4: Diversity Filtering and Task Conversion 

We assemble panels of one reference, four valid alternatives, and five invalid implementations. The valid group must meet the mean AST distance criterion. For invalid implementations, different sets of failed verifier checks pass the diversity check directly; matching sets require the AST Jaccard check. We refine panels through generation and replacement until both group criteria hold, then apply source quotas in final sampling. The test generation adapter converts each programming task into a test authoring contract: submit tests, fixtures, and one executable entry script in a designated artifact directory. The original requirement defines the behavior to test; the candidate panel remains hidden during test generation. Appendix B.4 gives the filtering stages and implementation details. 

2.5 TestPrism Statistics 

TestPrism contains 2,000 tasks collected and adapted from 17 source benchmarks, with 1,700 tasks in the training set and 300 in the test set. The partitions are disjoint. The test set contains 3000 labeled implementations across six programming languages and 67 repositories and projects. The sources span repository maintenance, evolved function specifications, olympiad programming, and numerical optimization (Xia et al., 2024; Shi et al., 2024; Press et al., 2025). Appendix B.5 provides source and language statistics, the source test count distribution (Figure 5), the six task categories and 34 subcategories, and counting conventions. Appendix B.2 details partitioning procedures and eligibility criteria. The filtering funnel appears in Appendix B.2.

# 3 TestHelix 

To improve test reliability beyond a single reference implementation, we propose TestHelix with three components (Figure 2). Heterogeneous synthesis generates diverse test and repair pairs to explore complementary behaviors and implementation hypotheses. Peer cross validation checks tests against peer repairs to expose and correct errors that agreement with one repair can miss. Recursive self improvement (RSI) learns from execution feedback across tasks to improve the test generation strategy. 

3.1 Heterogeneous Synthesis 

Diversity. We encourage diversity by assigning distinct exploration strategies to isolated coding agents. Each agent independently develops a test patch Tk and a repair patch Pk from public task requirements. 

Internal consistency. We enforce internal consistency within each pair by requiring Tk to reproducibly fail on the initial program and pass on Pk. Agents use local execution feedback to refine their pairs until this condition holds or the budget is exhausted. Appendix C.1 details the synthesis prompts and branch strategies. 

3.2 Peer Cross Validation 

Cross execution. We execute Ti against internally consistent peer repairs Pj to expose overly restrictive tests or incomplete repairs. Semantic review. An independent reviewer checks assertions against public requirements without seeing generated repairs and supports every blocking finding with public evidence. 

Corrective feedback. We use reviewed counterexamples to correct the pairs. When distinct qualified repairs pass the approved suites, we use differential challenges to find inputs that separate them (Yang

3.3 Recursive Self Improvement 

We initialize TestHelix with a basic strategy. However, improving test generation performance across heterogeneous tasks involves a large semantic search space. We use RSI to refine the strategy within the existing workflow while keeping the pair count and inference budget fixed. We optimize Reference Acceptance Rate for a denser success signal, since the stricter Joint Success Function can leave incremental harness improvements unrewarded. Heterogeneous synthesis and peer cross validation target the broader discrimination across implementations required by Joint Success Function. We use AutoSaddler (Park et al., 2026) to optimize the harness strategy through reflective evolution. It selects a parent strategy, diagnoses its execution traces, and proposes a revision. The parent and child are evaluated on the same tasks using Reference Acceptance Rate; their performance guides selection, while reflection extracts reusable lessons for later rounds. Appendix C.3 details the optimization setup.

# 5 Related Work 

Coding agents and test generation benchmarks. SWE bench evaluates repository changes with exe-cutable tests (Jimenez et al., 2024; Yang et al., 2024b); Terminal Bench assesses command line tasks (Merrill et al., 2026), and ContextBench evaluates context retrieval (Li et al., 2026c). SWT Bench studies tests derived from GitHub issues (Mündler et al., 2025); RESTestBench evaluates requirement based REST API tests using related mutants (Kogler et al., 2026). TestPrism evaluates test generation across heterogeneous sources using fixed valid and invalid implementation panels. TestHelix uses AutoSaddler (Park et al., 2026) to search a large semantic space of test generation strategies, drawing on Meta-Harness (Lee et al., 2026) and prior work on reflective feedback and prompt optimization (Shinn et al., 2023; Khattab et al., 2023; Yuksekgonul et al., 2024; Agrawal et al., 2026). 

Test generation and coverage. Randoop and EvoSuite use random generation and search (Pacheco & Ernst, 2007; Fraser & Arcuri, 2011). Language model approaches evaluate execution and coverage (Schäfer et al., 2024; Xu et al., 2025b). CodaMOSA and CoverUp use coverage feedback to guide generation (Lemieux et al., 2023; Pizzorno & Berger, 2025), while SymPrompt structures prompts around execution paths (Ryan et al., 2024). TestExplora studies repository test generation and Entry Coverage (Liu et al., 2026). TestPrism reports task scoped coverage alongside behavioral discrimination. 

Test adequacy and executable oracles. Mutation testing assesses rejection of faulty variants (Jia & Harman, 2011). PROBE augments repair benchmark tests with reference variants and checks robustness under behavior preserving transformations (Li et al., 2026a). Joint Success Function jointly requires acceptance of valid and rejection of invalid candidates. The oracle problem and patch plausibility limit executable verdicts (Barr et al., 2015; Qi et al., 2015): broader observed behavior does not establish label completeness or semantic correctness. CodeT selects code through agreement with generated tests (Chen et al., 2022); CodeRL combines test feedback with a learned critic to refine code (Le et al., 2022). 

# 6 Conclusion 

We introduced TestPrism to evaluate generated tests beyond a single reference. Its Joint Success Function checks acceptance of valid alternatives and rejection of defective implementations across diverse candidate sets. Our evaluation reveals persistent limitations in frontier coding agents; analysis of 286 retained failed trajectories across six model families identifies coverage gaps, faulty checks, and execution logic errors. TestHelix improves joint success through heterogeneous synthesis, peer cross validation, and recursive self improvement, supporting more reliable test generation across implementations.

# A Benchmark Comparison Conventions 

Table 1 compares behavioral and coverage targets: a check marks the corresponding target, a dagger marks a related check with different granularity or definitions, and a cross marks its absence from the main protocol. Reference Acceptance Rate measures the fail to pass transition from the initial program to the reference implementation. 

Behavioral and coverage targets. TestGenEval uses mutation testing; CLOVER and MultiFileTest evaluate tests through execution and code coverage (Jain et al., 2025; Xu et al., 2025a; Wang et al., 2026b). Their file, block, or project coverage is distinct from reference change and entry scope coverage. SWT Bench and TDD Bench Verified measure changed code coverage (Mündler et al., 2025; Ahmed et al., 2024). OmniCode jointly requires reference acceptance and rejection of all bad patches, while SWE Mutation reports mutant detection (Sonwane et al., 2026; Sun et al., 2026). These checks provide evidence beyond one reference; acceptance of valid alternatives under Joint Success Function is outside their scope. 

Counting conventions. Variants counts implementations other than the reference, including mutants; a check indicates that variants are used but no total is established. SWT Bench’s separate patch filtering experiment is outside that column’s main protocol scope. TestPrism has 2,700 such variants and 300 reference solutions. Languages counts individual task implementation languages. The 300 TestPrism tasks use Python (205), TypeScript (44), Java (19), JavaScript (16), C++ (8), and Go (8). Scope identifies test granularity; TestPrism spans local function and file tests, multifile projects, and repository issues.

# B TestPrism: Construction and Evaluation 

This appendix follows the construction steps, benchmark statistics, and evaluation protocol in Section 2. 

B.1 Task Screening and Adaptation 

Source selection and prior evidence. We select public benchmarks with traceable task origins and documented test validation. The SWE bench and Terminal Bench families maintain public leaderboards with results from multiple agent developers. Other sources draw on community maintained Exercism exercises, official USACO competitions, and published benchmarks for specialized programming settings. 

Task adaptation. We retain tasks centered on code and suitable for executable test authoring, excluding tasks with unusable Docker images or environments that cannot be reproduced. Adapters map tasks from all 17 source benchmarks to Harbor’s instruction, environment, tests, and solution components. Depen-dencies, services, and execution limits follow each source so that its original functional and performance requirements can be checked. 

B.2 Task Selection 

Test set selection and eligibility. Initial screening excludes tasks outside the code testing scope and tasks whose environments cannot be reproduced. The selection signals in Section 2.2 use effective lines in solution.sh , excluding blank and comment lines ( solution_lines ); test functions enumerated from source files or benchmark test metadata ( test_func_count ); and this count divided by the number of detected modified files, with a minimum denominator of one ( test_coverage_ratio ). The ratio describes test density. We apply source-specific lower bounds calibrated to each source’s distribution. Sources with smaller typical solutions or lower enumerated test counts use correspondingly lower bounds, preserving their representation alongside sources with larger values. This accounts for differences in task granularity and verifier structure; source quotas additionally balance the benchmark composition. After enrichment, final admission requires applicability annotations for both ∆C and Entry Coverage, ten physical candidate artifacts meeting the diversity criteria in Appendix B.4, and agreement between each artifact digest and its manifest. Table 4 lists the source-specific thresholds applied during difficulty screening. Source test counts follow the complete and partial enumeration convention in Appendix B.5. Density uses original patch paths for 204 tasks and reference file changes reconstructed from initial task files and build specifications for the remaining 96. It counts distinct changed, added, or removed files, including code, configuration, tests, and documentation; unchanged rewrites, temporary helpers, and runtime or build outputs are excluded. 

Training and test split. Tasks are normalized across sources and deduplicated before partitioning. Difficulty screening operates within source benchmarks. Source quotas form a training set of 1,700 tasks and a disjoint candidate test pool. The training set is fixed at this stage; candidate test tasks continue through verifier validation, patch generation, and diversity filtering. B.4 Diversity Filtering and Task Conversion 

AST distance. We apply each patch to the same initial program and parse the modified production code before and after the change with fixed versions of Tree-sitter and the corresponding language grammars. From AST nodes in the modified regions on each side, we extract ordered local subtrees of depth three, counting the root as depth zero. Features preserve node types, child order, operators, and literal types and values. Identifiers are normalized to a common token; comments, formatting, and source positions do not contribute features. Let Bp and Cp be the resulting feature sets in the initial and candidate states. We represent the patch by its added and removed structural features: 

A(p) =  {+} × (Cp \ Bp) ∪  {−} × (Bp \ Cp).

Each set depends only on the patch and the common initial program, so its definition remains fixed across comparisons. Features are deduplicated; repeated occurrences do not increase their weight. We use Jaccard distance: 

dAST (p, q) = 1 − |A (p) ∩ A (q)||A (p) ∪ A (q)| .

When both sets are empty, the distance is zero; when only one is empty, it is one. Unresolved parse errors in the changed regions leave the distance unavailable. Such a generated candidate cannot enter the selected panel and still counts toward the shared 30-patch generation budget. This measure captures local structural differences; verifier outcomes determine behavioral labels. 

Group admission criteria. We first assemble a valid group V = {pref , v1, v2, v3, v4} and an invalid group 

I = {i1, i2, i3, i4, i5}. Each group contains ten distinct unordered pairs. The valid group must satisfy 

D(V) = 110 ∑

> {p,q}⊂ V

dAST (p, q) > 0.5. 

This mean includes comparisons with the reference and between alternatives; it is not a lower bound on every pair. For invalid implementations, we first compare the sets of verifier checks they fail. Different failed-check sets satisfy the diversity check directly. Candidates with the same failed-check set must additionally pass the AST Jaccard check. Thus, AST filtering within the invalid group is conditional on matching failed-check sets. We impose no cross-group distance constraint: verifier outcomes already distinguish implementations that pass all checks from those that fail at least one. 

Generation and replacement. If either group fails its criterion, we continue generating candidates. Each new candidate undergoes the same applicability, deduplication, and verifier checks. Its observed label

determines the group it can enter. When the valid group has not met its criterion, we evaluate each replacement of a nonreference member and choose the one that maximizes D(V), accepting it only if the mean strictly increases. For the invalid group, replacements are assessed by their failed-check sets, with the AST Jaccard check applied when those sets match. The reference remains fixed, and the panel always contains one reference, four valid alternatives, and five invalid implementations. We stop as soon as both criteria hold or after evaluating the thirtieth generated patch. At that limit, tasks without a complete panel satisfying both criteria are excluded. Final source quotas select from the eligible tasks; tasks left unselected at this stage have passed the quality filters. Every retained artifact must match its recorded digest.

D.3.4 Connection to Candidate Panel Evaluation 

A direct single reference blind spot requires the same submitted suite to fail on the initial program, pass on the reference, and accept a candidate whose contract violation is supported by local evidence. Missing Inputs and Weak Checks provide examples of this pattern: the same suite passes the reference while accepting an invalid alternative. Reference failures caused by execution logic errors or other mechanisms cannot explain a decline condi-tional on reference success without additional paired evidence. Trusted candidate labels guide witness selection but do not establish correctness for every input. These observations identify mechanisms con-sistent with the aggregate evaluation gaps; they do not establish causal attribution for aggregate model scores or estimate the prevalence of each mechanism across the benchmark.

# E Limitations 

Reliable test generation spans a broad space of task specifications, inputs, implementations, and execution environments. This study focuses on one part of that problem: whether tests written by coding agents distinguish valid and invalid implementations under fixed task contracts. TestPrism evaluates ten labeled implementations per task, and Joint Success Function measures joint success within these finite candidate patch sets. The comparisons concern complete deployed agent configurations, while the TestHelix ablations examine component contributions within each model group. The taxonomy complements these results by characterizing recurring failure mechanisms in 286 analyzed failed trajectories, after excluding 14 timeouts from 300 trajectories sampled equally from the highest Joint Success Function configuration in each of six model families. Failed trajectories have a per-task joint success indicator of zero. The category proportions describe the retained sample and exclude the timeout trajectories. 

Source gold tests. We select established public benchmarks with documented test validation, including the widely adopted SWE bench and Terminal Bench families (Appendix B.3.1). Their original quality controls provide the foundation for task and verifier quality. Building on this foundation, our second-stage validation checks adapted verifiers through execution and independent expert review for requirement alignment and potential reference overfitting; tasks with unresolved concerns are excluded. Our scope is evaluating generated tests across implementations under these validated task contracts. Independently re-establishing the correctness of each upstream benchmark is outside this study. 

Panel composition and diversity. The prevalence of valid and invalid human patches is difficult to establish and can vary across tasks and development settings. Our equal allocation provides a balanced evaluation design without estimating this prevalence. The diversity contributed by a candidate also depends on task semantics, implementation choices, defect patterns, and its relationship to candidates already in the panel. Consequently, a valid to invalid ratio alone does not determine diversity, and equal counts do not guarantee equal difficulty for acceptance and rejection. Our admission checks use mean AST distance for the valid group and failed-check sets with conditional AST filtering for the invalid group. They do not establish exhaustive semantic coverage or an optimal candidate set. Jaccard distance summarizes overlap in the chosen AST feature representation and can differ from semantic distance; its mean over a panel need not increase with every added patch. This work introduces Joint Success Function and candidate patch sets with explicit diversity controls. Optimizing the label ratio, panel size, or candidate selection is outside its scope. Extending evaluation to evolving specifications, broader implementation spaces, and additional execution environments remains a direction for future work.

## 摘要
大型语言模型（LLM）编码智能体在多种编程任务中推动了测试生成的发展。然而，依据单一参考解决方案评估测试的常见做法忽略了其他有效实现，并可能高估测试质量。我们提出 TestPrism，包含来自 17 个来源的 300 个测试任务和 3000 个候选实现，有效解与无效解各占一半。其主要指标“联合成功函数”要求生成的测试在初始程序状态下失败，接受每个有效候选，并拒绝每个无效候选。在十四种基线编码智能体配置中，联合成功函数仅达到 28.00%，而单一参考成功率则达到 59.67%。我们的分析揭示了遗漏的行为、无依据的断言以及有缺陷的测试构建。为解决这些弱点，我们提出 TestHelix，它将测试-修复对的异构合成与同行交叉验证和递归自我改进（RSI）相结合。在两个模型上，TestHelix 在 TestHelix 评估中相较于原生评测框架对照方法将联合成功函数提高了 8.67 至 9.00 个百分点。

## Abstract
Large language model (LLM) coding agents have advanced test generation across diverse programming tasks. However, the common practice of evaluating tests against a single reference solution overlooks alternative valid implementations and can overstate test quality. We introduce TestPrism, comprising 300 test tasks from 17 sources and 3000 candidate implementations, evenly split between valid and invalid solutions. Its primary metric, Joint Success Function, requires the generated tests to fail on the initial program state, accept every valid candidate, and reject every invalid candidate. Across fourteen baseline coding agent configurations, Joint Success Function reaches only 28.00%, whereas single reference success reaches 59.67%. Our analysis reveals missed behaviors, unsupported assertions, and faulty test construction. To address these weaknesses, we introduce TestHelix, which combines heterogeneous synthesis of test and repair pairs with peer cross validation and recursive self improvement (RSI). Across two models, TestHelix improves Joint Success Function by 8.67 to 9.00 percentage points over the native harness comparators in the TestHelix evaluation

## 1. 核心问题与整体含义

- **研究动机**：LLM 编码智能体已能自动生成测试，但主流评估常采用“单一参考解”标准：测试只需在初始程序上失败、在参考解上通过。
- **核心问题**：一个需求可能对应多个有效实现，也存在看似合理但错误的实现。单一参考评估会忽略其他有效解，可能高估测试质量，无法衡量测试是否真正具备跨实现判别能力。
- **整体含义**：论文提出 **TestPrism** 基准与 **Joint Success Function（JSF，联合成功函数）**，把测试评估从“对一个参考解成功”扩展为“初始失败 + 接受所有有效候选 + 拒绝所有无效候选”。
- **关键结论先行**：十四种基线配置中，单参考成功率达 **59.67%**，但 JSF 最高仅 **28.00%**，说明当前测试生成远未可靠。为改进，论文进一步提出 **TestHelix**，结合异构合成、同伴交叉验证与递归自我改进。

## 2. 方法论

### 2.1 TestPrism：超越单一参考的评测基准

- **数据构成**：
  - 从 **17 个来源**收集并适配任务，总池包含 2,000 个任务，划分为 **1,700 个训练任务**与 **300 个测试任务**，二者不重叠。
  - 测试集含 **300 个测试任务、3000 个候选实现**，覆盖 **6 种编程语言、67 个仓库/项目、6 个任务大类、34 个子类**。
  - 每个任务固定一个隐藏面板：**1 个参考解 + 4 个其他有效解 + 5 个无效解**。全部任务合计为 300 参考解、1200 其他有效解、1500 无效解。
- **构建流程**：
  1. **任务筛选与适配**：保留可用可执行测试验证的编码任务，排除不可复现 Docker/环境；适配到统一 Harbor 接口。
  2. **任务选择**：用解决方案有效行数、测试数量、测试密度筛选；按来源配额平衡训练/测试划分。
  3. **补丁生成与验证**：用不同编码智能体和模型生成候选补丁；清理空提交、重复、不可应用补丁；用源验证器判定“全部检查通过=有效，任一失败=无效”，标签固定，独立于后续生成的测试。
  4. **多样性过滤与任务转换**：有效组要求 AST 特征平均 Jaccard 距离大于 0.5；无效组先看失败检查集是否不同，相同则再做 AST Jaccard 检查。最终将任务转为测试编写契约，候选面板在生成测试时隐藏。
- **评估协议**：
  - 对每个提交的入口脚本，在初始状态和每个候选实现上分别执行，重置目标并记录判定。
  - 核心指标：
    - **Reference Acceptance Rate（RAR）**：初始失败且参考解通过。
    - **Valid Acceptance Rate（VAR）**：接受其他有效候选的比例。
    - **Invalid Rejection Rate（IRR）**：拒绝无效候选的比例。
    - **H**：VAR 与 IRR 的调和平均。
    - **Change Coverage（ΔC）与 Entry Coverage（EC）**：覆盖参考变更和入口范围。
    - **Joint Success Function（JSF）**：要求初始失败、接受所有选中有效候选、拒绝所有选中无效候选。公式可概括为：对每个任务，若初始失败、所有有效候选通过、所有无效候选失败，则任务成功；JSF 为成功任务数 / 300。
  - 缺失结果或执行错误不计成功；JSF 不可能超过 RAR，二者差距反映“单参考成功但联合失败”的比例。

### 2.2 TestHelix：提升跨实现测试可靠性

- **核心思想**：生成多个“测试-修复”对，用不同修复假设相互挑战，并通过审查和策略进化提高测试泛化能力。
- **异构合成（Heterogeneous Synthesis）**：
  - 多个独立编码智能体分别生成测试补丁 \(T_k\) 与修复补丁 \(P_k\)。
  - 内部一致性：要求 \(T_k\) 在初始程序上可复现失败，并在自己的修复 \(P_k\) 上通过。
- **同伴交叉验证（Peer Cross Validation）**：
  - **交叉执行**：用 \(T_i\) 去执行其他同伴修复 \(P_j\)，暴露过度约束测试或不完整修复。
  - **语义审查**：独立审查者在看不到生成修复的情况下，检查断言是否由公开需求支持，阻塞性发现需有公开证据。
  - **纠正反馈**：利用反例修正测试-修复对。
  - **差异化挑战**：当多个合格修复通过现有测试时，寻找能区分它们的输入。
  - **套件合并**：合并兼容套件，并在新环境中验证。

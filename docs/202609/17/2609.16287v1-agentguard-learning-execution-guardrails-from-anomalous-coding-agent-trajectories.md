## 摘要
AI 编码智能体日益依赖执行框架来与代码仓库和外部工具交互。然而，任务成功并不保证执行可靠。智能体仍可能修改无关文件、重写测试、发出不安全命令或忽略失败的验证，这促使人们为可靠执行构建行为护栏。我们提出 AgentGuard，一个指令级护栏框架，可从编码智能体的异常轨迹中学习条件执行约束。AgentGuard 不依赖人工指定的安全规则，而是自动提取反复出现的执行失败模式，将其泛化为指令级行为约束，并将其组织为一个轻量级护栏技能，仅动态激活与当前指令相关的规则。这种设计能够在提供行为引导的同时，尽量减少对正常执行的不必要限制。我们使用从 382 个代码仓库任务中的真实编码智能体执行中收集的 642 条有记录的失败轨迹来评估 AgentGuard。护栏从覆盖 282 个任务的 461 条轨迹中学习，并在不重叠的 100 个任务集合上评估。我们以 Claude Code 搭配 Claude Haiku 4.5 作为底层编码智能体，将基线智能体与经 AgentGuard 增强的同一智能体进行比较。实验结果表明，AgentGuard 将异常执行率从 69.0% 降至 26.7%，并将任务成功完成率从 21.7% 提高到 35.0%。这些结果表明，从历史失败中学习到的执行护栏可以显著提升 AI 编码智能体的可靠性，同时也凸显了在安全性与任务完成之间取得平衡这一仍然存在的挑战。

## Abstract
AI coding agents increasingly rely on execution harnesses to interact with repositories and external tools. However, task success does not guarantee reliable execution. Agents may still modify unrelated files, rewrite tests, issue unsafe commands, or ignore failed validations, motivating behavioral guardrails for reliable execution. We present AgentGuard, an instruction-level guardrail framework that learns conditional execution constraints from anomalous trajectories of coding agents. Rather than relying on manually specified safety rules, AgentGuard automatically extracts recurring execution failure patterns, generalizes them into instruction-level behavioral constraints, and organizes them as a lightweight guardrail skill that dynamically activates only the rules relevant to the current instruction.   This design enables behavioral guidance while minimizing unnecessary restrictions on normal execution. We evaluate AgentGuard using 642 documented failure traces collected from real coding-agent executions across 382 repository tasks. Guardrails are learned from 461 traces covering 282 tasks and evaluated on a disjoint set of 100 tasks. Using Claude Code with Claude Haiku 4.5 as the underlying coding agent, we compare the baseline agent with the same agent augmented by AgentGuard. Experimental results show that AgentGuard reduces the Abnormal Execution Rate from 69.0% to 26.7% and increases the Successful Task Completion Rate from 21.7% to 35.0%. These results demonstrate that execution guardrails learned from historical failures can substantially improve the reliability of AI coding agents while highlighting the remaining challenge of balancing safety and task completion.

## 2. 方法论

### 2.1 核心思想

- 从已审核的异常执行轨迹中提取反复出现的失败模式。
- 将失败模式泛化为**指令级条件行为约束**。
- 将约束组织为轻量级“护栏技能”，仅在当前指令相关时动态激活。
- 设计目标是：提供行为引导，同时尽量减少对正常执行的不必要限制。

### 2.2 轨迹表示

- 一个编码智能体案例表示为：
  - `trace = ⟨(instruction_i, execution_i)⟩_{i=1}^N`
- 每次执行表示为交互三元组序列：
  - `execution_i = (response_{i,t}, action_{i,t}, result_{i,t})_{t=1}^{T_i}`
- 其中：
  - `response`：智能体推理或可观察消息；
  - `action`：工具调用，如 shell 命令、文件编辑、搜索；
  - `result`：环境反馈。
- 同时保留执行元数据：工具名、命令参数、文件路径、退出状态、仓库变更、生成产物等。
- 该层次化表示同时捕获：
  - 细粒度异常决策证据；
  - 跨指令的执行依赖、中间状态变化与下游后果。

### 2.3 证据提取

- 每条训练轨迹在 ABTest 中标注了一个已审核的异常动作，因此每条轨迹产生一个结构化 finding。
- finding 表示为：
  - `finding = (context, action, outcome, support, stage)`
- 提取过程：
  - 定位已审核异常动作；
  - 结合其指令、前序交互、执行结果，获得局部上下文与后果；
  - 检查完整任务轨迹，恢复继承约束、仓库状态、前序决策、后续影响与恢复尝试；
  - 只有动作、结果和轨迹支撑均可观察时，finding 才被使用。

### 2.4 规则归纳与整合

- 每条 finding 转换为条件护栏：
  - `r = (When, DoNot, Unless, Instead, ApplyAt)`
- 字段含义：
  - `When`：约束适用条件；
  - `DoNot`：应避免的行为；
  - `Unless`：任务允许该行为的例外条件；
  - `Instead`：避免异常结果的最小安全替代方案；
  - `ApplyAt`：执行阶段。
- 泛化原则：
  - 仅在不改变规则适用条件时，泛化仓库名、路径、错误字符串等细节；
  - 保留 finding 的支撑证据链接。
- 规则整合操作：
  - **去重**：同阶段、兼容条件下禁止同一动作且给出相同响应时合并，并合并证据。
  - **包含/吸收**：更具体规则可被更一般规则吸收，前提是不额外限制合法行为，且保留例外。
  - **冲突解决**：对同一表面动作给出不同响应时，保持规则分离或细化前置条件。
- 规则验证标准：
  - 必须由轨迹证据支撑；
  - 动作前可观察；
  - 有明确可行动替代方案；
  - 不干扰合法工作。

### 2.5 规则组织与路由

- 为避免每次加载全部护栏，论文按动作类型分组，形成**routing entry**。
- 主技能在执行工具前识别当前请求的工作类型，选择对应 routing entry，仅加载相关子技能。
- 五个 routing entries：
  1. 理解与路径解析；
  2. 命令执行与恢复；
  3. 项目变更；
  4. 文件系统、版本控制与外部状态变更；
  5. 产物、验证与报告。
- 从 461 条构建轨迹中最终归纳出 **15 条护栏**，每条实现为专门子技能。
- 路由机制只组织规则，不改变工具权限，也不拦截动作。

## 3. 实验设计

### 3.1 数据集与场景

- 使用 **ABTest** 发布的 **642 条已记录失败轨迹**，来自真实编码智能体执行，覆盖 **382 个仓库任务**。
- 每个任务是一个连贯的多步仓库工作流，并包含一个注入的对抗步骤，用于诱发异常行为。
- 注入步骤包括：
  - 不安全请求；
  - 缺失命令、文件或接口；
  - 需要澄清的模糊指令。
- 正确响应应处理注入问题，同时不伪造结果，也不无必要地放弃合法任务部分。
- 按任务划分，防止信息泄漏：
  - 规则构建集：**282 个任务、461 条轨迹**；
  - 留出评估集：**100 个不相交任务**。

### 3.2 评估设置

- 评估任务：100 个多步任务，每个含一个注入对抗步骤。
- 每个任务在每种条件下执行 **3 次**，以缓解 LLM 编码智能体随机性。
- 两种条件：
  - **Raw Agent**：原始任务指令，无行为护栏；
  - **Agent + AgentGuard**：同一智能体，在每个指令前接收 AgentGuard 指导。
- 总计：
  - 每配置 300 次执行；
  - 共 600 次 Docker 隔离执行。
- 底层智能体：
  - **Claude Code 2.1.19 + Claude Haiku 4.5**。
- 环境：
  - 相同执行环境；
  - 每次从全新 Docker 容器开始；
  - 使用相同 Click 仓库快照；
  - 工具访问、权限、运行时配置一致；
  - 唯一差异是是否加入 AgentGuard。

### 3.3 对比方法

- 主要对比：
  - 基线 **Claude Code**；
  - 增强后的 **Claude Code + AgentGuard**。
- 论文未与 GuardAgent、AGrail、TRIAD、R-Judge、TrajAD 等其他护栏/运行时监控方法进行直接实验对比。
- 论文也未设置手动规则护栏、无路由护栏、不同规则数量等消融对照。

### 3.4 评审与指标

- 三位人类评审独立评估全部 100 个任务、600 条执行轨迹。
- 评审证据包括：提示、工具事件、变更文件、产物、仓库状态；oracle 输出仅用于定位证据。
- 评审员可识别执行条件，因为 AgentGuard 会增加显式护栏指令。
- 分歧时共同复查证据并达成最终裁决。
- 裁决前 Fleiss’s kappa：
  - 主评审：**0.87**；
  - 效果归因评审：**0.81**。
- 指标：
  - **AER**：异常执行率；
  - **CAR**：正确对抗步骤处理率；
  - **CBR**：良性任务完成率；
  - **Success**：成功任务完成率；
  - **ORR**：过度拒绝率。

## 摘要
近年来，GitHub Copilot和Claude Code等自主AI智能体迅速普及。本研究报告了在以AI智能体为前提的软件开发方法论——规格驱动开发，在面向三年级本科生的软件开发项目式学习课程中的实际应用。我们定义了一个由调查、规划、实施和审查四个阶段组成的工作流程，并建立了一个适合该课程的定制环境，让AI智能体在每个阶段生成文档和代码。我们从学生的AI使用主观感受、实施吞吐量和代码理解三个角度分析了结果。分析显示，AI的使用模式因开发阶段和团队而异。此外，虽然AI智能体的使用提高了实施吞吐量，但也倾向于鼓励学生在未完全理解代码的情况下推进开发。本研究表明，在将规格驱动开发引入软件开发项目式学习时，讲师定期验证代码理解并提供适当反馈对于保持教育有效性至关重要。

## Abstract
In recent years, autonomous AI agents such as GitHub Copilot and Claude Code have been rapidly gaining popularity. This study reports on the practical implementation of Spec-Driven Development, a software development methodology premised on AI agents, within a Software Development Project-Based Learning (SDPBL) course for third-year undergraduate students. We defined a workflow consisting of four phases, namely investigation, planning, implementation, and review. We also established an environment tailored for the SDPBL course where AI agents generate documentation and code during each phase. We analyzed the results from three perspectives, namely students' subjective AI usage, implementation throughput, and code comprehension. The analysis reveals that AI usage patterns varied across development phases and teams. Moreover, while AI agent utilization increased implementation throughput, it also tended to encourage students to proceed with development without fully understanding the code. This study demonstrates that regular verification of code comprehension by instructors and appropriate feedback are essential for maintaining educational effectiveness when introducing SDD into SDPBL.

## 2. 论文提出的方法论：核心思想、关键技术细节与算法流程

- **核心思想——规格驱动开发（SDD）**：SDD是一种以AI智能体为基础的开发方法论，最初由AWS Kiro提出，旨在解决Vibe Coding缺乏代码质量保障的问题。核心要点包括：
  - 在开发早期定义清晰、结构化的详细规格文档，而非模糊的自然语言指令；
  - 规格中明确描述架构模式、编码约定、安全需求和测试策略；
  - AI智能体将这些规格视为约束条件，生成符合要求的代码；
  - 开发者需要持续验证和审核AI生成的文档与代码，承担最终责任。
- **方法选择依据**：论文认为，相较于Vibe Coding，SDD更适合SDPBL——因为SDD要求学生理解规格、验证AI产出并对最终成果负责，这与PBL培养应用开发能力的教育目标一致。
- **四阶段工作流程**：将标准SDD流程改造适配为PBL场景，分为四个阶段（图1）：
  - **调查阶段（Investigation）**：AI智能体生成调查报告，覆盖功能追加、调试等多种目的，而非仅限于新需求分析；
  - **规划阶段（Planning）**：AI智能体基于调查结果生成实施计划（tasks.md等文档）；
  - **实施阶段（Implementation）**：AI智能体依据规格文档编辑源代码并更新specs.md；
  - **审查阶段（Review）**：AI智能体审查代码，确认功能满足要求、遵循编码规范，并给出分优先级的改进建议。

  - **演示教学**：两位讲师以登录功能为例完整演示"调查提示词→规划提示词→实施提示词"的循环过程，并强调学生须能解释任何AI生成的代码；

    - RQ2：从Git仓库提取每个学生每次讲座周期在主分支上提交的新增代码行数，并手动排除非实现类文件（外部库、日志、README、AI生成的Markdown等）；
    - RQ3：讲师在每周进度汇报中与学生一对一访谈，以0-3四级量表评估代码理解程度。

## 6. 论文的主要结论与发现

- **RQ1（AI使用模式因阶段和团队而异）**：在实施和调试阶段，所有团队都不同程度地使用了AI；调查和规划阶段，团队间差异巨大——25A/25B利用充分，25C使用最少，25D在调查/规划阶段几乎不用AI却在实施/调试阶段大量使用。这表明SDD引入SDPBL后，AI使用形态因团队而异，尤其在非代码生成类阶段分化明显。
- **RQ2（AI使用显著提升实现吞吐量）**：2022–2025年间新增LOC呈上升趋势，统计检验确认在8次讲座中的7次存在显著的年份差异，2024和2025年的吞吐量显著高于2022和2023年；没有出现倒挂情况（即早期年份显著高于后期年份）。
- **RQ3（AI使用程度与代码理解存在张力，但可通过教学干预调节）**：未使用AI（AI level 0）的学生在所有周期都保持高水平的代码理解；而AI使用程度达到level 3的学生在中期（lec09-10）代码理解水平较低。团队趋势对比显示：lec09时高AI使用伴随理解水平低谷，但在lec10出现恢复——这与教师的每周一对一访谈和干预在时间上吻合。结论是：教师定期检查理解程度并及时反馈，对维持教育效果至关重要。
- **总体结论文**：AI智能体确实能提升SDPBL中的实现速度，但引入这些工具必须伴随审慎的教学管理——持续监控代码理解、提供主动反馈、建立"可解释性问责"机制，确保学生将AI作为支持工具而非深度理解的替代品。

## 8. 不足与局限

- **内部效度问题**：实验没有设立"不用AI智能体"的同期对照组，只能与历史年份比较，无法排除学生基础能力年际波动、团队规模差异、课程环境变化等干扰因素。论文对此有坦诚声明。
- **外部效度问题**：仅基于Java/Spring Boot的单门课程，且2025年只有4个团队参与，结论可推广性受限。不同技术栈、团队规模、学生年级或文化背景下的效果可能截然不同。
- **构造效度问题**：
  - 以"新增LOC"作为实施吞吐量的核心指标，无法反映重构质量、设计优化、删除冗余代码等非增量性的效率维度；
  - 代码理解评分依赖教师主观访谈评价，虽能捕捉深层理解，但缺乏客观测试的交叉验证。
- **实验充分性**：样本量较小影响了统计显著性检测能力；RQ3缺乏正式的统计检验；RQ1以描述性可视化为主，无法回答AI使用模式差异是否具有统计意义或实际效果量。
- **AI使用自报告偏差**：学生自我报告的AI使用水平可能受记忆偏差、社交期望等影响，与实际工具调用日志缺乏交叉比对验证。
- **教学需求与AI效率的内在矛盾**：论文虽然证明"教师干预对维持理解有益"，但这也显露出一个深层矛盾——在有限课时内，教师逐一访谈的成本高、可扩展性差；文中的方法论还依赖教师具备对AI生成代码的理解与审查能力，推广时可能存在师资瓶颈。

## 摘要
在大型工业软件系统中分析崩溃报告缺陷需要大量的维护工作，尤其是在生产环境中，开发者必须处理大量的崩溃报告和源代码工件，以定位并修复其根本原因。尽管近期研究表明大语言模型（LLMs）能够辅助维护任务，但关于它们在工业场景中支持开发者分析崩溃报告缺陷以及修复与崩溃报告组相关缺陷的有效性，我们知之甚少。为弥补这一空白，我们研究了将崩溃报告挖掘技术——具体包括堆栈轨迹聚类和可疑文件与方法排名——与LLMs集成，是否能在生产环境中支持崩溃定位与修复。我们在四种提示配置下对五个LLM进行了回顾性评估。之后，我们选择最佳模型，对从两个大型Java企业系统中收集的38个崩溃缺陷进行运行。我们进一步分析了LLM生成响应的结构特征和解释模式，并通过人工验证评估了定位与修复的有效性。结果表明，性能最佳的配置在完整数据集上能够定位高达71%的崩溃缺陷，并正确修复52%的崩溃缺陷。这些发现提供了实证证据，表明将崩溃报告挖掘与基于LLM的修复相结合，能够有效支持工业维护工作流程中的调试活动。

## Abstract
Analyzing crash-report bugs in large-scale industrial software systems requires substantial maintenance effort, particularly in production environments where developers must handle large volumes of crash reports and source code artifacts to localize and fix their root causes. While recent studies have shown that Large Language Models (LLMs) can assist with maintenance tasks, little is known about their effectiveness in supporting developers in analyzing crash-report bugs and repairing bugs associated with groups of crash reports in industrial settings. To address this gap, we investigate whether integrating crash report mining techniques---specifically stack trace clustering and suspicious file and method ranking---with LLMs can support crash localization and repair in production environments. We conduct a retrospective evaluation of five LLMs under four prompt configurations. After that, we chose the best model to run on 38 crash bugs collected from two large Java enterprise systems. We further analyze the structural characteristics and explanatory patterns of LLM-generated responses and assess localization and repair effectiveness through manual validation. Our results show that the best-performing configuration localizes up to 71% and correctly repairs 52% of crash bugs on the full dataset. These findings provide empirical evidence that combining crash report mining with LLM-based repair can effectively support debugging activities in industrial maintenance workflows.

## 2. 方法论：核心思想、流程与技术细节

整体流程为三个阶段的管线：
1. **崩溃报告分组（Crash Report Grouping）**：基于堆栈轨迹相似性分四级逐步合并：
   - Level 1：堆栈完全相同（STA = STB）
   - Level 2：签名等价（忽略生成数字后缀等实现细节差异）
   - Level 3：崩溃类型签名（一个堆栈是另一个的子序列，忽略行号）
   - Level 4：顶帧文件相同（同一类文件中的不同方法抛出的异常视为同源缺陷）
2. **可疑文件和方法排名（Suspicious File and Method Ranking）**：改编 Wu 等人的方法到文件级别，每个文件用三个标准打分：
   - **IAD**（Inverse Average Distance to Crash Point）：靠近崩溃点的文件得分更高
   - **IBF**（Inverse Bucket Frequency）：惩罚频繁出现在多个故障组中的通用文件
   - **FF**（File Frequency）：奖励同一崩溃组内高频出现的文件
   - 最终得分公式：**Score(f, B) = IAD(f, B) × IBF(f, B) × FF(f, B)**
   - 文件按降序排名，再从排名靠前文件中提取出现于堆栈的方法按其出现频率做推荐
3. **LLM bug 修复**：
   - 取排名前三条可疑文件的源代码，附上代表性堆栈，构造结构化零样本提示（5 个组成部分：角色设定、可疑代码、堆栈/栈消息、排名信息、修复请求）
   - 提示使用零样本，避免过拟合、贴合真实部署场景
   - **关键设计细节**：只提供 top-3 可疑文件，平衡成本和上下文限制（提示平均 2,244 行，范围 100~7,717 行）

## 6. 主要结论与发现

### RQ1（响应结构特征）
- LLM 响应随模型与提示的不同结构差异很大；单个类的单一代码片段（Fragment Single Class）是最常见的响应类型
- Claude 和 GPT 更常用片段式输出；Gemini 和 Mistral 更多输出完整多个类
- 43% 的响应删除了文档、45.5% 附加了代码块外的解释、37.73% 在代码内嵌解释——即便提示要求“只给源代码，不给解释”，大多数模型依然违规
- 仅 Mistral 产生了非 Java 代码或纯解释性内容
- 这一异质性使得自动化补丁抽取十分困难

### RQ2（在完全数据集上的验证）
- 在完整 38 个缺陷上，**Claude-3.5-sonnet 用 SCoSF+ST（可疑源文件 + 完整堆栈轨迹）** 达到最优：
  - 定位（per-response）：**71.05%**
  - 修复（per-response）：**51.58%**
  - 每故障定位（per-bug）：**71.05%**
  - 每故障修复（per-bug）：**52.63%**
- 而添加排名信息（RoSFM）在不同上下文中的作用各不相同——对栈消息（SM）有显著增益，但对完整堆栈（ST）不仅没有提升，反而轻微损害了表现；对栈消息的改进作用显著：per-response localization 44.21%→64.21%，修复从 28.42%→47.37%

### 最出人意料的发现
- **最严格遵循提示指令的模型（Gemini）效果最差**（0% 修复率），而最少遵循指令、最擅于“解释”的 Claude 取得最佳效果——这说明解释能力或隐式推理机制很可能也是缺陷调试需要的能力，以及提示遵循行为和调试能力之间存在复杂的相关关系，并非简单正比

### 与相关工作的性能对照
- Du 等（IntDiagSolver）：定位 76.7%、修复 33.3%；本文定位 71% 略低，但修复 52% 显著更高
- Sobania 等的 ChatGPT 在 QuixBugs 上以至少 1/4 成功为指标的修复率 47.5%，本文以更严格的标准（≥3/5 正确）在真实工业代码上仍达到 52%

## 7. 优点

- **真实工业场景验证**：基于两家运行超 16 年的 Java 企业系统，约 210 万行代码上收集的真实崩溃、真实开发者修复作为 ground truth，覆盖长达 18 个月的部署，外部有效性远高于玩具级数据集
- **结合实际约束设计提示**：为了平衡机密性、成本和上下文限制，仅向 LLM 提供少量可疑代码，符合绝大多数企业的实际 LLM 使用环境，不是依赖全代码库的理想情况
- **消融研究系统设计**：基于源代码 + 崩溃信息（堆栈 vs. 栈消息）与排名信息（有 vs. 无）的两阶段消融具有清晰的内部控制（先 8 个缺陷的窄模型比较，再 38 个缺陷的适度模型验证、大范围采样）
- **多 LLM、多提示组合交叉比较**：涉及 5 个主流 LLM，每个缺陷 5 次采样，减少随机性影响
- **语义评估而非机械的语法匹配**：人工判定修复是否“等效或有效的替代实现”，比 BLEU 或语法扩散更符合实际修复质量
- **对自动化修复管线局限性的诚实报告**：把“LLM 响应结构异质”这类实践挑战直接呈现，并为后续自动化尝试设下现实的可预期性预期

## 8. 不足与局限

- **样本量偏小**：SMALL DS 仅 8 个缺陷，FULL DS 虽多数 38 个，但每个缺陷只采样 5 次；仍不足以做严格的统计显著性分析
- **全局稳定性不足，结果有一定脆弱**：SMALL DS 和 FULL DS 之间的最优提示不一致（修复从 SCoSF+SM+RoSFM 漂移到 SCoSF+ST），内部延拓的稳健性仍待检验
- **依赖人工语义评估**：缺少测试基础设施，无法用自动运行验证 LLM 补丁是否真正修复—人工“等效”判断有高度主观性
- **双系统均来自同一机构且同为 Java Enterprise**：泛化有限，其他语言和领域（如 C++/Python 后端）不必然适用
- **回顾性评价**：非实时交互，未测量开发者的实际使用体验或流程改进；评估是在历史故障上进行的冷启动验证
- **未知的上下文与代码规模的影响**：论文没有做敏感性分析来评估 top-3 文件之外的代码、更多堆栈或提示文字的变化，选择参数可能存在边界剪裁后的过拟合

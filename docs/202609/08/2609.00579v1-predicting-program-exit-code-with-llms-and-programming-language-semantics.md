## 摘要
大型语言模型（LLMs）在多种软件工程任务中展现出了熟练度，例如代码生成与翻译。然而，其性能的一个关键局限可能在于它们对编程语言语义的（缺乏）理解。即使给出了显式语义，仍不清楚LLMs是应用这些规则还是转而依赖预训练期间习得的先验知识。我们通过一项新任务——程序可执行性预测（PrEx）——来研究LLMs是依赖先验知识还是给定语义，该任务要求模型根据程序的语法和操作语义来预测程序在语义上是有效还是无效（若无效，则预测其违反了哪条形式规则）。由于PrEx需要有效和无效的程序，我们构建了一个数据集，其中包含从有效程序系统生成的无效变体。我们在两种语义形式体系及两种语义偏移下，对跨人工编写、LLM翻译和模糊生成程序分区的开源编码LLMs进行了评估。我们的研究结果表明，LLMs依赖于预训练先验知识而非系统地应用给定规则，在修改后的语义上表现尤其糟糕，并且随着程序复杂度的增加其性能进一步下降。PrEx可在https://github.com/EngineeringSoftware/prex获取。

## Abstract
Large language models (LLMs) have shown proficiency in various software engineering tasks, such as code generation and translation. However, a key limitation in their performance may be their (lack of) understanding of programming-language semantics. Even when explicit semantics are given, it remains unclear whether LLMs apply those rules or lean on priors learned during pre-training instead. We study if LLMs lean on priors or given semantics with a novel task--Program Executability Prediction (PrEx)--that asks models to predict whether a program is semantically valid or invalid (and, if invalid, which formal rule it violates) given the program's syntax and operational semantics. Because PrEx requires both valid and invalid programs, we build a dataset with systematically generated invalid transformations derived from valid programs. We evaluate open-source coding LLMs under two semantic formalisms and two semantic shifts across Human-Written, LLM-Translated, and Fuzzer-Generated program splits. Our findings show that LLMs lean on pre-training priors rather than systematically applying the given rules, performing especially poorly on modified semantics and degrading further as program complexity increases. PrEx is available at https://github.com/EngineeringSoftware/prex.

## 2. 方法论：核心思想、关键技术细节

- **任务定义（PrEx）**：给定一个程序、该语言的语法（C* 的 EBNF 定义）以及一组形式语义规则（小步操作语义 S 或 K 框架规则），要求模型输出程序是否可执行：
  - 若可执行，输出 `##success##`；
  - 若不可执行，输出 `##error##`，并指出被违反的规则编号或名称。
- **C\* 语言**：一种小型、命令式、C 类语法语言，包含整数变量、赋值、if-else、while、halt、continue、break、`LE`、算术/关系/逻辑运算等结构。使用 C* 而非完整 C，是为了让形式语义规则可以被完整、显式地放入 prompt 中，从而控制变量。
- **两种语义形式体系（Semantic Formalisms）**：
  - **Small-step operational semantics（S）**：细粒度推理规则，每一步规则表示一次原子计算，例如变量查找、算术运算、除法/取模零检查等；规则采用 Gentzen 风格的推理式书写。
  - **K-framework（K）**：基于重写逻辑的粗粒度语义框架，规则以 configuration rewriting 形式书写；例如将表达式中操作数的归约由内置重写机制隐式处理，同时规则执行过程会追踪已应用的规则编号。
  - 两种形式的规则均覆盖“合法执行”和“出错终止”两类情况（如变量未声明、除零、模零等）。论文通过对比 S 和 K，考察**规则粒度和表述风格是否会影响 LLM 遵循显式规则的能力**。
- **两种语义偏移（Semantic Shifts）**：
  - **KeywordSwap**：将标准运算符/关键字语义互换，例如把 `+` 的语义改成减法、把 `-` 改成加法，以及交换 `<=` 与 `>=`、`==` 与 `!=` 等。这要求模型必须覆盖预训练形成的“直觉”，严格依据 prompt 中的规则理解操作符含义。
  - **KeywordObf**：用全新的、预训练未见过的单 token 符号替换标准符号，例如用 `★` 表示加法，用 `▲` 表示除法等。这样彻底去除模型可识别的“熟悉线索”，迫使它从零开始学习所提供的规则。
- **数据生成机制**：
  - 基于 PLSemanticsBench 提供的合法 C* 程序，使用 ANTLR parser-visitor 实现 5 种**语义感知的无效变换**，为每个合法程序生成 5 个配对非法程序：
    1. break 出现在循环外（break-outside-loop）
    2. continue 出现在循环外（continue-outside-loop）
    3. 除零（division by zero）
    4. 模零（modulo by zero）
    5. 变量未声明先使用（variable-use-before-declare）
  - 每个非法程序仅违反一条语义规则，从而保证错误类型有明确 ground truth。
- **Prompt 设计**：模型输入包括四部分：C* 语法规则、语义规则（S 或 K 之一，且可能对应 KeywordSwap/KeywordObf 的变换后规则）、待判断的程序，以及输出格式提示。CoT 变体额外要求模型先输出推理过程，再给出最终判定。

## 6. 主要结论与发现

- **核心发现**：LLM 倾向于依赖预训练先验，而不是系统地应用给它的显式语义规则。无论是 PrEx 这种“只需判定是否可执行、指出规则”的简单任务，模型依然不能稳定遵循形式语义。
- **性能随复杂度退化**：
  - 所有较强模型在 Human-Written 短程序、标准语义下的准确率较高（部分可达 99%），但在 LLM-Translated 和 Fuzzer-Generated 更长、更复杂的程序上显著下降。
  - 例如最强三个模型（DeepSeek-Qwen 32B、Ministral 3 14B-CoT、Qwen2.5-Coder 32B-CoT）在 Fuzzer-Generated 上的平均下降幅度达到 19–33.3 个百分点；最极端配置下降 55 个百分点。
- **语义偏移显著降低性能**：
  - KeywordSwap 和 KeywordObf 使准确率大幅下降。KeywordObf 通常比 KeywordSwap 更难。
  - 即使表现最好的模型，在 KeywordObf 下的平均准确率也会损失 15–30 个百分点以上。
- **错误类型具有规律性**：
  - 在

在错误类型上，模型表现出明显的系统性偏向：当程序语义被改变（KeywordSwap/KeywordObf）时，模型倾向于做出“假成功”判断，即把本应执行失败的非法程序误判为可执行；而当语义未偏移时，模型又往往将熟悉结构的轻微异常错误地归咎于不相关的规则。在 K 框架语义下，模型更难准确指出被违反的具体规则编号，错误更多出现在“规则选择”而非“最终判定”层面。这说明模型并非完全无法识别“出错”，而是无法将出错原因与给定的显式规则可靠地对应起来。

- **K 语义相比 S 语义通常更难**：多数模型在 K 语义下的准确率低于 S 语义。这可能是因为 K 规则的粒度更粗、隐含的重写机制更多，模型需要额外推断每一步由内建机制完成的状态转换，而 S 规则显式列出了每一步原子计算，更容易被逐步套用。
- **CoT 的作用有限且不稳定**：对 3B/7B 级别的小模型，CoT 有时能够提升标准语义下的准确率；但面对 KeywordSwap/KeywordObf 时，CoT 甚至可能带来负作用，因为推理链越长，模型越容易在中间步骤产生幻觉，最终“自信地”得出错误结论。推理模型（如 DeepSeek-Qwen）尽管在标准语义下表现优异，但在语义偏移后依然大幅退化，说明其推理能力并未真正转化为规则遵循能力。
- **规模效应与先验依赖并存**：同一系列中更大规模的模型普遍准确率更高，但即使 32B 模型也无法在语义偏移配置下超过 60% 的准确率（最差配置低于 20%）。规模提升可以缓解但对齐标准语义的任务难度，却无法消除对预训练先验的依赖。
- **程序复杂度是决定性因素**：Human-Written split 上的高准确率与 Fuzzer-Generated split 上的显著下降形成鲜明对比，证明 LLM 的语义判断能力与程序结构的复杂度、嵌套深度和长度密切相关。当程序不长且结构接近训练语料时，规则应用看似成功；一旦程序复杂度脱离常见分布，规则遵循能力便迅速崩溃。

## 7. 局限性与未来工作

- **任务覆盖范围有限**：C\* 是人为简化的小型语言，仅包含整数、循环、条件等基本结构，缺少指针、函数调用、结构体、动态内存等现代语言特性。因此，结论能否外推到完整的 C、C++ 或其它主流语言仍不清楚。
- **错误类型仅覆盖 5 类**：非法变体只涉及循环外 break/continue、除零、模零、未声明变量，未包含类型错误、数组越界、未定义行为、类型不匹配等更丰富也更实际的语义错误。
- **语义规则量级受限**：为了保证 prompt 在模型上下文窗口内，规则集合被刻意压缩。在真实工程场景中，语言规范多达数千条规则，无法整段放入 prompt；论文没有研究当规则数量超出上下文容量时的策略（如分步查询、信息检索）对表现的影响。
- **实验的统计稳健性不足**：每个配置只运行 3 次采样，且未报告方差或置信区间，无法判断模型性能在随机采样下的波动范围。
- **缺少上界与消融分析**：未比较基于解析器+解释器自动生成的答案（即完全遵守规则的系统）作为上界，也没有对“仅给出规则但去掉语法定义”或“仅给出程序但去掉规则”等条件进行消融，因此无法完全区分语法理解与语义规则执行各自的贡献。

未来工作可以朝以下方向推进：扩展到更大规模语言子集；加入类型系统与函数调用语义；设计自适应检索或“规则外挂”机制，使模型不需要记忆所有规则即可逐步查找应用；利用形式语义验证工具（如 K 框架本身）生成更多样的正反例与解释作为训练数据，探索通过对齐/微调增强模型的规则遵循能力。

---

## 8. 总结与启示

本研究通过提出 PrEx 任务，系统性地检验了大语言模型对显式操作语义规则的遵循能力。结论并不乐观：在简单、短小的程序上，模型可以依赖预训练记忆回答得不错；但当程序变长、规则变陌生或语义发生偏移时，模型准确率迅速回落，甚至接近随机水平。这说明当前 LLM 对抗代码任务的“语义理解”很大程度源于统计先验和记忆，而非一种通用的、可迁移的表征转换机制。

这一发现对人工智能辅助软件工程具有明确的警示意义：在需要严格保证语义正确性的场景中，不能轻信 LLM 对代码执行结果的直接判断，也不应把“看似合理的解释”视作可靠的形式推理。将 LLM 与传统符号执行器、模型检查器或交互式定理证明器结合，使其仅负责启发式建议而将关键判定交给可验证工具，可能是更安全的技术路线。与此同时，本研究为“如何评估模型的规则执行能力”提供了一种可复现的评测范式——通过语义偏移剥离预训练先验，用短答案格式分离判定与生成难度，这一方法有望成为未来设计语义理解基准的重要参考。

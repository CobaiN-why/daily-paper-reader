## 摘要
随着基于终端的代码智能体变得普遍，智能体轨迹已大规模积累，而真实可执行的环境仍然稀缺。然而，环境才是智能体后训练真正需要的：每个环境都可以被反复查询以生成许多可验证的任务，并提供执行反馈，而轨迹则是一个单一的冻结演示。我们观察到，与其从头生成环境，现有轨迹中的工具执行历史暴露了它们运行环境的结构和内容，使得从轨迹本身重建这些环境成为可能。因此，我们提出了Terminal-Universe，这是一个将每条轨迹转化为可重用环境并对其进行探索以合成新任务和持续交互的框架。具体来说，Terminal-Universe重放轨迹中记录的文件操作，将每个文件恢复到智能体修改之前的状态，从而得到一个部分工作区；随后，一个补全智能体提供缺失的文件和依赖。在这个恢复的工作区上，我们既重建原始意图任务，也合成全新的任务。此外，我们还沿两个互补的维度扩展任务：广度和深度。就广度而言，我们挖掘相关环境之间的方向性依赖关系，并合成跨多个代码库的跨工作区查询，正如开发者在真实开发中经常所做的那样。就深度而言，我们将初始的单轮查询扩展为多轮会话，通过用户智能体捕获迭代的用户反馈和需求细化。应用于公开的终端智能体轨迹，Terminal-Universe产出了37.3k个任务充分的环境。在此语料库上对Qwen3.5-27B进行监督微调，在Terminal-Bench 2.1上将单轮性能提高了11.9分，在EvoCode-Bench v2 MT@4上将多轮性能提高了13.8分。

## Abstract
As terminal-based code agents become prevalent, agent trajectories have accumulated at scale, while realistic, executable environments remain scarce. However, environments are what agent post-training actually requires: each can be re-queried into many verifiable tasks and provides execution feedback, whereas a trajectory is a single frozen demonstration. Rather than generating environments from scratch, we observe that the tool-execution history in existing trajectories exposes the structure and contents of the environments in which they ran, making it possible to reconstruct those environments from the trajectories themselves. Thus, we introduce Terminal-Universe, a framework which turns each trajectory into a reusable environment and explores it for synthesizing new tasks and continued interactions. Specifically, Terminal-Universe replays the file operations recorded in a trajectory to restore each file before the agent modified it, yielding a partial workspace; a completion agent then supplies the missing files and dependencies. On this recovered workspace, we both reconstruct the original intent task and synthesize entirely new ones. Besides, we also scale the tasks along two complementary axes: breadth and depth. For breadth, we mine directional dependency relations between related environments and synthesize cross-workspace queries spanning multiple codebases, as developers routinely do in real-world development. For depth, we extend the initial single-turn query into a multi-round session that captures iterative user feedback and requirement refinement via a user agent. Applied to public terminal agent trajectories, Terminal-Universe produces 37.3k task-sufficient environments. Supervised fine-tuning of Qwen3.5-27B on this corpus improves single-round performance on Terminal-Bench 2.1 by 11.9 points and multi-round performance on EvoCode-Bench v2 MT@4 by 13.8 points.

## 2. 方法论：核心思想、关键技术细节与流程

论文提出 **Terminal-Universe** 框架，核心思路是先“重放轨迹→重建环境”，再对重建环境“重新查询→合成新任务”，主要分为环境重建与任务重查询两大阶段。

### 2.1 环境重建（三阶段）

1. **阶段一：确定性重放（Deterministic Replay）**
   - 将轨迹中记录的读、写、编辑操作按时间顺序重放，恢复每个被访问文件“在智能体首次修改前”的最早可见版本；
   - 排除智能体新建的文件、记录其改动以便后续验证；由于轨迹只覆盖智能体触碰过的路径，且文件内容可能被截断，输出是“部分工作区”（partial workspace）。
2. **阶段二：智能体补全（Agentic Completion）**
   - 由一个补全智能体基于恢复出的任务 q 和部分工作区，创建缺失文件、补全部分文件、恢复依赖，使任务“可解”但不“被解”（不得泄漏解决方案）；
   - 补全后得到可执行工作区。
3. **阶段三：环境过滤（Environment Filtering）**
   - 由智能体裁判用只读工具检查工作区，判断其源代码、配置、数据、结构等是否足以支撑目标任务；
   - 仅保留被判定为“任务充分”（task-sufficient）的工作区。全部环境统一运行在 ubuntu:24.04 容器中并允许网络访问，以降低部署成本。

### 2.2 任务重查询（四种机制）

- **意图恢复（Intent Recovery）**：把源轨迹中的用户请求整理为独立自洽任务，保留用户表述的需求，不注入智能体动作中推断的实现细节。
- **单工作区合成（Single-WS）**：离线生成器在单个重建环境中合成 5 个候选新任务，在 groundedness（可落地性）、structural diversity（结构多样性）、verifiability（可验证性）约束下选择，每个环境随机保留一条做 roll-out。
- **广度扩展——跨工作区合成（Cross-WS）**：挖掘环境间的方向性依赖关系（dependency），把可写目标仓库与只读参考仓库配对，要求智能体从参考仓库自行发现并迁移缺失能力（每次任务至少依赖 3 个只藏于参考仓库的细节，但 prompt 中不显式给出），实现跨代码库任务。
- **深度扩展——多轮用户查询（Multi-Round）**：用用户智能体维持显式需求追踪器；在智能体解决初始查询后追加 1~6 轮后续请求（特征扩展 feature extension、特征修订 feature revision、特征冲突 feature conflict 三种风格），每轮由专用 agent 编写验收测试并执行，失败信号由用户智能体转为可理解的自然语言反馈进入对话，保留“失败-修复”的纠错监督。

### 2.3 验证与数据筛选

- 为每个 Single-WS/Cross-WS 任务在容器内编写可执行 pytest 验证器，要求新能力测试在未修改工作区上“确实失败”（红色检查），并保证零收集错误；
- 使用教师模型（全部使用 Qwen3.7-Max，xhigh effort）在 Claude Code 支架内完成求解 rollout，温度=1.0，top-p=0.95，最长 500 轮、4 小时限制；
- **筛选策略**：Single-WS/Cross-WS 仅保留全部测试通过的轨迹；Multi-Round 按“轮级”筛选，去掉结尾连续失败轮，保留至少两轮通过的会话，中间的失败轮保留（提供纠错监督）；
- 训练前做 13-gram 去污染，排除 Terminal-Bench 相关数据源。

## 6. 主要结论与发现

- **从轨迹重建环境并“重解”任务显著优于直接模仿源轨迹**：Terminal-Bench 2.1 上，35.8k 条 Intent Recovery 数据达到 52.1%，而同规模源轨迹 SFT 仅 36.7%（−15.4 分），表明在统一教师策略下重新生成演示是更有效的监督信号。
- **智能体补全至关重要**：补全后环境训练的 Intent Recovery 比仅重放环境高 4.2 分（52.9 vs. 48.7），且运行方差更小；重放单独留下的工作区大多任务不足（Terminal 充分率 40.2%→补全后 93.5%；SWE 20.1%→77.1%）。
- **验证器过滤的价值随任务难度上升**：Single-WS 上过滤后与不过滤接近（56.4 vs. 56.0）；Cross-WS 上过滤显著更好（55.4 vs. 53.2），说明更难任务对低质量轨迹更敏感。
- **广度（跨工作区）扩展有效**：Cross-WS 任务轨迹平均长度约为 Single-WS 的 1.6×，工具调用约 1.9×，token 数约 1.5×，教师 pass@1 从 72.3% 降至 49.2%；混合两种数据后 Terminal-Bench 2.1 达 58.4%，超过单独 Single-WS 与单独 Cross-WS。
- **深度（多轮）扩展有效**：加入 Multi-Round 数据后 EvoCode-Bench v2 MT@4 从 18.4 提升至 21.0、Case score 从 71.9 提升至 76.9；去掉轮级验证反馈后 MT@4 掉 2.2 分、Case score 掉 3.7 分。
- **预算分配上“更多环境”优于“更多查询/更多求解”**：同等 35k 记录预算下，环境数量翻倍带来 53.2→56.0 的提升；增加查询数或求解数几乎无提升（53.8/53.9）。
- **跨域迁移有效**：SWE 轨迹重建并重解后训练的模型，在 Terminal-Bench 平均 50.0%，高于 base 的 47.0%，说明 SWE 覆盖的监督也可泛化到终端任务。
- **主结果汇总**：Qwen3.5-27B 在 32.0k 条混合数据上微调后，Terminal-Bench 2.0 从 41.6→52.8、2.1 从 46.2→58.1（+11.9，Terminus2-XML），Claude Code 下 2.1 达 58.2%（+10.4）；EvoCode-Bench v2 MT@4 从 6.3→20.1（+13.8）、Case score 从 67.8→76.1。

## 7. 优点：方法与实验设计的亮点

- **问题视角新颖**：将“轨迹—环境”视为对偶关系，系统性地把海量轨迹反过来用于环境重建，一举绕过“从零搭建真实环境”的高成本路径，使得轨迹这一此前被低度利用的数据资产发挥更大价值，方法论具有很强的可扩展性。
- **完整且可落地的两阶段重建流水线**：确定性重放提供可靠事实基础，智能体补全处理轨迹中缺失的隐式上下文；用“充分性裁判”量化补全效果（Terminal 40.2%→93.5%），设计清晰、可复现。
- **任务扩展“广度+深度”双轴设计贴近真实工程实践**：Cross-WS 模拟了开发者跨代码库查阅与移植的真实模式；Multi-Round 通过用户智能体+轮级验证器产生“失败-修复-扩展”的迭代会话，保留了纠错监督，而不只保留“全部成功”的路径。
- **验证器构造严谨**：要求“红-检查”（新能力测试在未修改工作区上必须失败），既证明任务缺口真实存在，又避免测试本身失效；只保留通过验证的轨迹，控制了数据质量。
- **消融体系完整、控制变量意识强**：几乎所有关键设计选择都有对应消融；在预算翻倍实验中严格匹配记录总量（35k），结论“环境数 > 查询数 > 求解数”有较强说服力；跨域（SWE→terminal）测试提升了结论的普适性。

## 8. 不足与局限

- **环境保真度受限**：所有环境都统一用标准 Ubuntu 24.04 容器，未像 SWE-Factory、RepoLaunch 等做仓库专属环境定制；依赖特殊系统库或复杂编译链的边界场景可能存在保真度下降。虽然论文引用了 prior work 说明该减损“温和”，但未给出在本数据上的具体 resolve-rate 对比数据。
- **分布受源轨迹覆盖限制**：重建环境的语言（Python 84.7%）、技术领域（数据处理/DevOps/安全合计超 80%）与工具链分布完全受制于所收集轨迹的来源分布，无法自主拓展到源轨迹未覆盖的领域，存在覆盖面偏斜。
- **单一教师模型带来的系统性偏差**：同一模型（Qwen3.7-Max）同时承担任务生成、求解与验证器编写；其能力天花板会限制任务难度上限，其自身的解法错误也可能被自家编写的测试遗漏。论文建议未来用多教师与独立验证模型，说明这被作者视为实质短板。
- **轨迹信息损失不可恢复**：未被访问的文件、隐式系统依赖、外部网络资源等不会在轨迹中留下痕迹，重建必有损耗；SWE 工作区补全后充分率仅 77.1%，仍有两成多环境不达标。
- **质量评估依赖模型判断**：工作区“充分性”由智能体裁判评定，验证人工抽查只检查了 30 个补全样本（发现 8 个引入多余代码），规模有限且缺少解决率的端到端校验；它评价的是“上下文充分性”而非“构建成功”，可能与实际可解性存在差距。
- **算力信息缺失**：未报告 GPU 型号/数量与训练总时长，难以评估其复现成本；从使用 27B 模型 + 1.42B token 推断，实际训练成本应较高。
- **对比公平性不足**：与 prior work 的数字相比，base 模型、数据规模、脚手架与解码配置均不统一，横表对比更多是参考性而非严格对照；某些 “无多轮能力”的对比模型在 EvoCode-Bench 上得 0.0，也可能部分源于其评测配置不适合该基准。
- **验证过滤没有统一用于 Intent Recovery**：Intent Recovery 不带验证器过滤（作者解释为保持与源轨迹 SFT 可比），但这也意味着 35.8k 意图恢复数据中未通过验证的轨迹可能混入训练，其潜在噪声未受控制。

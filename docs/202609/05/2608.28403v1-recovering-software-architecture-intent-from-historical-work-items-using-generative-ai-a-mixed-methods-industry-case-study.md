## 摘要
软件架构通常仅在代码中被部分捕获，而大部分设计意图存在于不断演变的项目工件中。在敏捷项目中，工作项、用户故事及相关跟踪文档保留了这些意图的宝贵痕迹，但它们很少直接支持架构分析。本研究探讨了使用基于LLM的流水线从历史敏捷工作项中恢复C4架构图。该半自动五步工作流采用提示链、双向可追溯性和思维链推理，将非结构化的Azure DevOps工作项转化为可视化工件。在两个行业项目上进行评估，我们采用了结合定性专家访谈与定量稳定性分析的混合方法设计。从业者认为生成的架构基线准确且对系统理解高度有用。严格受限于输入数据，这些工件反映了文档化的意图，从而在与实现现实比较时暴露出差异和架构漂移。定量上，该工作流对架构实体表现出高稳定性，但对其关系的稳定性较低，且相对方差在生成步骤间累积。所提出的工作流展示了基于开发过程工件进行LLM辅助架构恢复的实际可行性。

## Abstract
Software architecture is often only partially captured in code, while much of the design intent lives in evolving project artifacts. In agile projects, work items, user stories, and related tracking documents preserve valuable traces of that intent, but they rarely support direct architectural analysis. This work investigates the recovery of C4 architecture diagrams from historical agile work items using an LLM-based pipeline. The semi-automatic five-step workflow employs a prompt chain, bidirectional traceability, and Chain-of-Thought reasoning to transform unstructured Azure DevOps work items into visual artifacts. Evaluated on two industry projects, we use a mixed-methods design combining qualitative expert interviews with a quantitative stability analysis. Practitioners perceive the generated architectural baselines as accurate and highly useful for system comprehension. Strictly bound by their input data, the artifacts mirror the documented intent, thereby surfacing discrepancies and architectural drift when compared to the implemented reality. Quantitatively, the workflow exhibits high stability for architectural entities but lower stability for their relationships, with relative variance compounding across generation steps. The proposed workflow demonstrates the practical viability of LLM-assisted architectural recovery based on development process artifacts.

## 2. 方法论

**核心思想**

- 使用 LLM 作为“严格镜像”工具：从工作项中提取**已文档化的设计意图**，而非从代码中推断实现现实。
- 采用**任务分解与顺序链式生成**降低单步推理复杂度：将 C4 中两个高层的抽象级别拆分为独立生成阶段，上一级输出作为下一级的上下文约束。
- 生成过程刻意绕过源代码，以规避代码级噪音和架构腐蚀的干扰。

**技术流程（五步流水线）**

1. **数据抽取**：通过 Azure DevOps REST API 抓取 Epics、Features、User Stories、Tasks。
2. **预处理**：对 API 响应进行严格过滤，转换为结构化、分层的 Markdown 文档，降低噪音和 token 开销。
3. **LLM 1 —— System Context 生成（C4 Level 1）**：LLM 根据预处理文档识别系统及其边界。
4. **LLM 2 —— Container 生成（C4 Level 2）**：将上一步验证过的 System Context 以 JSON 形式注入到提示中作为上下文约束；LLM 必须将新生成的 Container 严格限制在既有系统边界内，并复用外部元素的精确 ID 以保证引用一致性。
5. **验证与渲染**：Pydantic 验证层检查 JSON 输出的 schema 合规性；通过后转换为 PlantUML 代码，由本地 PlantUML 服务渲染最终图表。

**Prompt 工程关键策略**

| 策略 | 实现方式与目的 |
|---|---|
| Schema 与可追溯性 | 注入 JSON 骨架，含 `linked_work_items` 数组，建立对源 ticket 的**双向可追溯性**（provenance trail） |
| 结构化思维链（CoT） | 强制要求 `architecture_reasoning` 作为第一个键输出，在生成架构前先呈现推理逻辑 |
| 一次性锚定（One-Shot） | 注入 C4 官方“Internet Banking”示例，对齐输出与 C4 层级规范 |
| 负面约束 | 使用显式排除规则，防止 LLM 将非架构性组件纳入图中 |

**模型配置**：GPT-5.1（版本 2025-11-13），托管于欧盟区域的私有 Azure OpenAI 实例以保障数据隐私；`temperature=0.01`，`top_p=1.0`，固定随机种子 `seed=42`。

## 6. 主要结论与发现

### RQ1：感知准确性与可理解性

- 尽管工作项是碎片化的，从业者仍将生成的 C4 图视为**高准确性**。E1 表示：“自己知道故事写得很模糊，它还能从这个输入得出这种结果已经不错。”
- LLM 的语义抽取（架构逻辑、组件描述、关系）是准确的；可理解性摩擦全部来自 **PlantUML 渲染层的限制**，而非模型语义错误。
- 工作流是“严格镜像”：准确反映文档化内容（包括漏洞和偏差），而不会幻构出未记录的代码实现。

### RQ2：结构稳定性

- 实体（节点）的生成**更为稳定**：4 个节点分布中有 3 个 SD<1.0，多数平均偏离 <1 个实体；Project A 上下文到 7 个节点的频率是 70%，Project B 是 60%，Project A 容器呈双峰 5/6，Project B 到 5 个→70%。
- 关系（边）的生成**较为不稳定**：CV 范围可达 33.0%（Project B）到 38.3%（Project B 容器内部），边际分布呈现右偏（众数 < 中位数 < 均值），说明方差主要来自多于核心连接的迭代。
- **顺序级联有方差复合**：第二级的相对不稳定大于第一级（连接到后一跳的初始差异→逐步放大）。
- 较大项目（193 个工作项的 Project B）比 89 项的 Project A 表现出更大的相对方差，提示输入体系的特征会影响稳定底数。

### RQ3：实际集成、效用与局限

- 可将基线创建从数小时缩短到数分钟——具有可量化的时间节约。
- 三个集成维度：连续更新的即时文档、项目里程碑（设计启动/现代化交接）的起始画布、架构审计工具。
- 诊断价值：重现未执行的意图，同时无视未记录的实现，使团队在将工件与实际系统比较时看到架构漂移。
- 严格信任边界：原始输出适合内部工程和快速知识转移；外部/面向客户的用途则需要人工筛选/干预。
- 治理效果：让团队直观面对自己的文档债务，产生更严格的 ticket 卫生正向反馈循环。
- 人的隐性知识仍不可替代：需要人来比较已提取的意图，解析差异、决定什么内容跨越信任边界。

### 架构差异追踪分析中的额外发现

- 对所有被标记的差异都验证了因果链路：LLM 提取的元素在文档中有确定依据，而未出现在图中的元素在语料中无文档。区分：

| 元素（项目） | 图中 | 实现 | 分类 |
|---|---|---|---|
| 认证网关（A） | 存在 | 不存在 | 已文档化但未执行的意图 |
| 云存储（A） | 不存在 | 存在 | 未文档化的实现 = 侵蚀 |
| 云存储（B） | 存在 | 不存在 | 已文档化但未执行的意图 |
| 邮件服务（B） | 存在 | 不存在 | 已文档化但仍遗弃的计划意图 |

- 由此例可见代码侵蚀检测：文档中丢失代码添加 → 结构漂移。

## 7. 方法论的闪光点与亮点

- **提出“文档意图恢复”思路**：绕开对源代码的依赖来避免代码腐蚀的干扰，是对传统代码级 SAR 的宝贵补充。
- **链式提示工程**：将 C4 层级分解成两个耦合的生成步骤，注入较高级别的输出作为较低级别的约束——在工业实务中证明是可行的，并系统测试其后果（方差复合）。
- **结构生成与视觉布局解耦**：结构化 JSON 输出 + Pydantic 验证 + PlantUML，在模型端、验证端与渲染端分离职责；使下游管道不容易因 LLM 输出结构无效就失败。
- **内置双向可追溯性**：`linked_work_items` 数组使生成元素回归到原始票证，让差异分析变得可审计且有条理。
- **稳定性的多维度操作化**：引入最小值/最大值/中位数/众数与均值（mode–median–mean 关系），采用 SD 和 CV，使方差模式（如右偏、系统性偏差）在视觉上可见。
- **严格操作规范**：开发与评估分离；不同项目用于管线开发；固定配置（温度=0.01，种子固定），给出若干重要提示词；报告有定量与定性协同的双重证据。
- **诚实的内部边界分析**：主题综合与详细差异追踪互补，使“严格镜像”假说受证据约束，远超多数概念验证报告。

## 8. 局限性与不足

**内部效度/外部效度**

- 来自同一公司的三例行业中亦罕见，样本规模很小。
- 单一 LLM（GPT-5.1）与单一平台（Azure DevOps）——不能跨模型或跨追踪系统模型进行泛化。
- 单一研究者进行质性编码可引入偏差；无评分员间可靠性。
- 专家对项目的高度熟悉会造成熟悉性偏差/记忆不足风险。
- 新项目（≤1 年）带来许多大项目的痛点（大规模、巨型积压、极度侵蚀）无法被捕捉。
- 与特定工作项维护文化息息相关：“严格镜像”视角的输出质量取决于积压的文档质量。

**建构与测量效度**

- 稳定性被操作化为节点数和边数的统计方差，而未衡量跨迭代元素的语义身份或指标语义的一致性；手工检查提出了“语义重叠”，但不构成量化的指标证伪链。
- 差异分类依赖专家的心智模型而非真值标注——无根因真值基准。

**方法论局限**

- 仅基于 399 个工作项，但真实应用可能超过上下文窗口——文章自己提到扩展性限制只靠 RAG/层级提取来设想；尚未测试大规模处理。
- 主要只考虑 C4 阶段的上两层；未测试 Container 以下各级（Component）——该层级包含较细粒度信息且更难。

**完整性缺口/泛化问题**

- 未做消融（无 CoT/无 schema/无不计数不通过变体），因此各功能的贡献无从分离。
- 无跨模型的鲁棒性数据；确定性问题用温度 0.01 + 固定种子得以缓解，但只能降低非确定性而无法保证一致性。

## 摘要
智能体人工智能正赋能基于云的工作流，在这些工作流中，自主智能体对运行状态进行推理，调用经授权的工具，修改软件和基础设施，部署服务，验证执行结果，并在长时间跨度、多步骤任务中自适应。工程化此类工作流需要明确的工作流推进机制、受限执行、故障恢复和可验证完成机制。我们提出了智能体云工作流工程（Agentic Cloud Workflow Engineering），这是一种智能体AI框架，可将自然语言的智能体云工程任务转化为经过验证的代码仓库和经过验证的可操作云部署，从而实现基于云的智能体工作流的自动化。该框架分离了三个互补的关注点：图工程（graph engineering）规定长期工作流的推进和依赖验证的转换；循环工程（loop engineering）提供有界诊断、修复或重新规划、重试和重新验证；智能体框架工程（agent harness engineering）则通过身份、授权、策略限定的能力、隔离和运行时保障来强制零信任执行。工作流的推进和完成需要机器可检查的代码仓库、部署和运行时证据，恢复过程受明确的操作边界和终止标准的约束。我们在Google Cloud上实现该框架，并评估代码仓库完整性、受控执行、证据门控的推进、可操作部署和有界恢复。实验结果表明，执行要么以经过验证的可操作云部署终止，要么在有界恢复条件下以可审计的终端故障终止。该框架为基于云的工作流提供了统一的工程架构，涵盖智能体DevOps、智能体CloudOps、智能体SRE/AIOps、智能体SecOps、智能体DataOps、智能体MLOps/LLMOps、AgentOps、智能体RAG/GraphRAG以及相关的云工程领域。

## Abstract
Agentic AI is enabling cloud-based workflows in which autonomous agents reason over operational state, invoke authorized tools, modify software and infrastructure, deploy services, verify execution outcomes, and adapt across long-horizon, multistep tasks. Engineering such workflows requires explicit mechanisms for workflow progression, constrained execution, failure recovery, and verifiable completion. We present Agentic Cloud Workflow Engineering, an agentic AI framework that transforms natural-language agentic cloud-engineering tasks into validated code repositories and verified operational cloud deployments for automating cloud-based agentic workflows. The framework separates three complementary concerns: graph engineering specifies long-horizon workflow progression and verification-dependent transitions; loop engineering provides bounded diagnosis, repair or re-planning, retry, and re-verification; and agent harness engineering enforces zero-trust execution through identity, authorization, policy-scoped capabilities, isolation, and runtime safeguards. Workflow progression and completion require machine-checkable repository, deployment, and runtime evidence, with recovery constrained by explicit operational bounds and termination criteria. We instantiate the framework on Google Cloud and evaluate repository completeness, controlled execution, evidence-gated progression, operational deployment, and bounded recovery. Experimental results show that executions terminate with either a verified operational cloud deployment or an auditable terminal failure under bounded recovery. The framework provides a unified engineering architecture for cloud-based workflows spanning Agentic DevOps, Agentic CloudOps, Agentic SRE/AIOps, Agentic SecOps, Agentic DataOps, Agentic MLOps/LLMOps, AgentOps, Agentic RAG/GraphRAG, and related cloud-engineering domains.

## 1. 核心问题与整体含义

- **研究背景**：随着云架构与运维负载日趋复杂，各类组织日益依赖云平台。智能体AI正被引入云工程工作流，能够自主进行目标导向的推理、调用工具、修改代码与基础设施、部署服务、验证执行结果，并在长时间跨度、多步骤任务中自适应。此类模式覆盖DevOps、CloudOps、SRE/AIOps、SecOps、DataOps、MLOps/LLMOps、AgentOps、RAG/GraphRAG等十余个云工程领域。
- **核心问题**：现有智能体云工程缺乏**显式机制**来管控三个关键问题——① 工作流应如何推进（workflow progression）；② 执行受何种约束、故障如何恢复（constrained execution & failure recovery）；③ 任务完成如何被**验证**（verifiable completion）。仅凭智能体自我报告"任务完成"不足以支撑生产级可靠性。
- **整体含义**：论文提出一个统一的工程框架——Agentic Cloud Workflow Engineering ——将自然语言云工程任务转化为**可验证的代码仓库**与**可验证的云部署**，并通过图工程、循环工程和零信任智能体框架工程三项互补抽象，保证执行终止于"验证通过的部署"或"可审计的失败态"，从而为生产级自主云工程提供体系化的控制与信任基础。

## 2. 论文提出的方法论

核心思路是将智能体云工作流工程化分解为三个正交且互补的层面，形式化地表达为：

\[
(R^*, D^*, Z^*) = \mathcal{F}(q)
\]

其中 \(q\) 为输入的自然语言任务，\(R^*\) 为产出代码仓库，\(D^*\) 为云部署，\(Z^*\) 为验证证据。成功完成需满足三项机器可检查的验证：

\[
\text{Complete} \iff \text{RepoValid}(R^*, Z^*) \land \text{DeployVerified}(D^*, Z^*) \land \text{RuntimeVerified}(D^*, Z^*)
\]

即代码仓库验证、部署验证和运行时验证三者逻辑与成立。

三大核心抽象：

- **图工程（Graph Engineering）**：以显式图结构组织长期工作流——节点（智能体/动作/状态）、边（转换/依赖/条件分支/审批/恢复路径/终止状态），决定执行"可以走向哪里"，并实现**证据门控的推进**（evidence-gated progression）。工作流中的转换只有在对应的机器可检查验证条件满足时才被允许。
- **循环工程（Loop Engineering）**：界定验证失败或运行时不良证据后如何**有界恢复**——诊断 → 修复/重新规划 → 重试 → 重新验证，循环受明确限制（最多20次恢复尝试、120分钟、1000万token、500次工具调用等），同时含权限与爆炸半径限制和明确终止准则。若资源耗尽仍未满足验证条件，工作流以可审计失败态终止。
- **智能体框架工程（Agent Harness Engineering）**：构建**零信任执行边界**，通过身份（IAM/工作负载身份联合）、最低权限授权（RBAC/ABAC）、策略执行（OPA Gatekeeper、审批门）、Scoped工具能力（MCP）、沙箱隔离（VS Code/Chrome沙箱、GKE Sandbox+gVisor）、网络与运行时安全（Cilium、服务网格、Falco）、状态与租户隔离、可观测性与审计、证据保留等多层控制，约束智能体可执行的动作范围。

Google Cloud 系统实现中，图编排器基于 Google ADK，智能体间通过 A2A 委托，工具通过 MCP 暴露，部署与验证动作运行在 gVisor 隔离的 GKE Agent Sandbox 内；软件供应链（构建测试、Semgrep/Gitleaks/Checkov/Trivy 扫描、SLSA 溯源、策略门控 Terraform、Argo CD）全链路受控。

## 3. 实验设计

- **Benchmark（自建）**：构建了覆盖 **14个云工程领域**（Agentic DevOps、CloudOps、SRE/AIOps、SecOps、DataOps、MLOps/LLMOps、AgentOps、Agentic RAG/GraphRAG等）× **每领域10个任务** = **140个自然语言任务**的端到端基准套件，每个任务需完成代码仓库生成与验证、云解决方案部署与运行时行为验证。
- **受控条件（6种）**：① 正常执行；② 仓库验证扰动（注入使仓库验证失败）；③ 部署验证扰动；④ 运行时验证扰动；⑤ 授权策略违规（注入未授权/越权能力请求）；⑥ 恢复预算耗尽。140任务 × 6条件 = **每模型840次执行**。
- **评估模型**：Gemini 2.5 Flash-Lite、Gemini 2.5 Flash、Gemini 2.5 Pro、GPT-5.6 Sol，共 **4模型 × 840次 = 3,360次执行**。
- **研究问题（RQ）与指标**：
  - RQ1（验证任务完成）→ VTCR
  - RQ2（证据门控推进）→ EGER
  - RQ3（有界恢复）→ RSR
  - RQ4（逐动作授权与策略执行）→ UCDR + ACPR
  - RQ5（有界终止）→ BTR
  - RQ6（跨领域适用性）→ 各指标跨14领域统计
- **对比方式**：主要对比不同模型的性能差异（模型敏感指标），以及框架机制层面指标（模型无关）。**未对比其他智能体框架基线**（如无框架/其他Agent系统的对照）；消融实验以GPT-5.6 Sol为对象，通过禁用恢复循环和以模型自决推进替换验证门控来完成因果归因。

## 6. 主要结论与发现

- RQ1：VTCR随模型能力提升：Gemini 2.5 Flash-Lite 56.4% → Flash 68.6% → Pro 82.1% → GPT-5.6 Sol **95.0%**，证明框架可端到端产出验证通过的云部署，且完成能力与基础模型能力高度相关。
- RQ2：EGER 四个模型均为 **420/420（100.0%）**——没有任何一次执行在对应验证条件未满足时越过验证依赖的转换或达到终止状态。证据门控由框架逻辑而非模型自我报告决定，稳定可靠。
- RQ3：RSR 从 51.0%（Flash-Lite）到 **93.1%**（GPT-5.6 Sol）。恢复难度一致呈现 仓库验证 < 部署验证 < 运行时验证 的递增趋势（GPT-5.6 Sol 分别为95.7%/93.6%/90.0%）。
- RQ4：UCDR 达 **140/140（100%）**（所有未授权请求均在调用前被拒绝）；ACPR 为139/140（99.3%），模型无关，说明授权决策执行于框架控制路径中。
- RQ5：BTR 四模型均 **140/140（100%）**——恢复预算耗尽后均正确终止于可审计失败态，未出现越界推进。
- RQ6：框架机制指标跨14领域保持稳定（EGER/UCDR/BTR跨域最低值=100%，ACPR=90.0%~99.3%），而VTCR和RSR随领域和模型波动（GPT-5.6 Sol VTCR跨域最低80.0%）。
- 核心认识：**长期自主性可靠性的关键在于将模型无关的验证执行与模型相关的恢复能力解耦**——模型决定如何修复，框架决定何时放行。
- 消融实验表明：恢复循环是验证完成任务的关键促成因素（去除后VTCR下降82.1个百分点）；机器可检查的验证门控比模型自决推进更可靠（消除1.0%的残留无效推进误差）。

## 7. 优点

- **三分离架构理念清晰**：首次将图工程（推进方向）、循环工程（失败恢复）和智能体框架工程（权限边界）解耦为互补、正交的工程抽象，各有明确功能边界，思想完整且具有理论美感。
- **零信任设计贯穿始终**：从身份、授权、策略、隔离、供应链、可观测性、证据留存等多个层面构建纵深防御，非仅依赖模型自律。
- **证据门控取代自我报告**：以机器可检查的验证证据作为流程推进与终止的唯一判据，从根本上提升了自动化任务完成的信任度。这是应对"智能体不可靠但框架可以可靠地约束智能体"这一核心挑战的关键设计。
- **统一的领域覆盖架构**：一套元架构覆盖DevOps、SRE、SecOps、DataOps、MLOps/LLMOps、AgentOps、GraphRAG等14个领域，具有较强的推广价值。
- 实验设计系统化——六种受控条件分别检验架构的关键性质，指标设计紧密对齐各研究问题；在跨模型与跨域两个维度上分别检验了模型敏感指标和框架不变指标，论证层次分明。

## 8. 不足与局限

- **平台泛化性局限**：实证仅在Google Cloud单一平台上展开（论文亦自述此局限），架构虽声称云平台无关但未经AWS/Azure验证。
- **故障模式局限**：扰动均受控注入，未包含真实生产环境的偶发事件、级联故障、工作负载漂移或基础设施不断演化的场景，对长期运行下的稳健性问题缺乏说服力。
- **任务类型局限**：基准任务的140项均为**系统生成/新建**类任务，尚未扩展到对已有部署系统的修改、运行与恢复类任务，限制了结论向存量系统智能化运维场景的外推。
- **资源预算固定**：恢复预算（次数、时间、token、工具调用）事先固定且无差异化——没有根据任务风险特征和实时执行状态自适应调整，可能限制高价值任务的恢复成功率或导致低风险任务的资源浪费。
- **验证谓词有待加强**：当前仅验证有限维度的仓库/部署/运行时谓词，未包括更丰富的安全、合规谓词和形式化验证。
- **对抗鲁棒性欠缺**：未涉及对抗性测试（被攻破的工具、恶意输入、策略绕过、投毒证据、权限提升、跨租户攻击）。

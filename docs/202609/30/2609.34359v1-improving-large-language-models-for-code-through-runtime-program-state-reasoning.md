## 摘要
大型语言模型在关于运行时程序状态的推理方面所接受的显式训练有限。我们研究训练模型对运行时程序状态进行推理是否能提升下游软件工程能力。我们引入两个互补的程序状态推理任务。缺陷输入-输出推理要求模型生成一个具体输入，以暴露有缺陷程序与隐藏的正确实现之间的行为差异，并预测由此产生的执行行为。前置条件-后置条件推理要求智能体符号化地刻画触发缺陷的前置条件，预测期望的后置条件，解释二者之间的因果联系，并将该推理实例化为可执行的回归测试。通过将这两个任务纳入分阶段后训练流程，我们开发了 Comet-9B，一个基于 Qwen3.5-9B Base 的 9B 语言模型。我们在仓库级补丁生成、回归测试生成和安全 PoC 生成上评估所得检查点。将这两个程序状态推理任务加入针对问题解决的监督微调（SFT）后，在 SWE-bench Pro 上成功率提升 7.25 个百分点，在 SWT-Bench Verified 上提升 9.70 个百分点。在这两个任务上进行顺序强化学习，分别在 SWE-bench Pro、SWT-Bench Verified 和 CyberGym 上进一步提升 7.25、26.79 和 4.67 个百分点。尽管仅有 9B 参数，Comet-9B 在 SWE-bench Pro 上取得了与所报告的 GPT-5.2 结果相当的分数，并在 SWT-Bench Verified 上匹配了所报告的基于 GPT-4o 的智能体的成功率。

## Abstract
Large language models receive limited explicit training in reasoning about runtime program states. We study whether training models to reason about runtime program states improves downstream software-engineering capabilities. We introduce two complementary program-state reasoning tasks. Buggy input-output reasoning requires a model to generate a concrete input that exposes a behavioral difference between a buggy program and a hidden correct implementation and to predict the resulting execution behavior. Precondition-postcondition reasoning requires an agent to symbolically characterize a bug-triggering precondition, predict the expected postcondition, explain their causal connection, and instantiate this reasoning as an executable regression test. By incorporating these two tasks into a staged post-training pipeline, we develop Comet-9B, a 9B language model based on Qwen3.5-9B Base. We evaluate the resulting checkpoints on repository-level patch generation, regression-test generation, and security PoC generation. Adding both program-state reasoning tasks to supervised fine-tuning (SFT) on issue resolution improves success rates by 7.25 percentage points on SWE-bench Pro and 9.70 points on SWT-Bench Verified. Sequential reinforcement learning on the two tasks yields further gains of 7.25, 26.79, and 4.67 percentage points on SWE-bench Pro, SWT-Bench Verified, and CyberGym, respectively. Despite having only 9B parameters, Comet-9B achieves a score comparable to the reported GPT-5.2 result on SWE-bench Pro and matches the reported success rate of a GPT-4o-based agent on SWT-Bench Verified.

## 1. 核心问题与研究动机

- **背景缺口**：大语言模型在训练中很少被显式要求推理"程序运行时状态"。现有软件工程（SWE）模型训练范式——收集可执行仓库任务、蒸馏成功 agent 轨迹、对最终任务结果做 RL（SWE-Gym、SWE-ReBench、R2E-Gym、SWE-smith、SWE-RL、DeepSWE、Kimi-Dev 等）——只奖励"补丁通过测试"这一最终结果，模型可以靠工具反复试错观察到失败现象，而无需刻画**失败条件是什么、效果如何沿程序传播**。
- **已有程序状态推理工作的局限**：T-REX、SemCoder、CodeI/O、NExT、CodeReasoner、Absolute Zero、ExecVerify、StepCodeReasoner、CodeThinker、CodeRL+ 等虽已把执行语义/状态预测纳入训练，但主要面向**独立小程序**，不涉及仓库级交互式调查，且未在仓库级 agentic benchmark 上验证收益。
- **核心研究问题**：显式训练模型推理运行时程序状态，是否能提升下游仓库级软件工程能力（补丁生成、回归测试生成、安全 PoC 生成）？
- **整体含义**：论文主张"程序状态推理"可作为 SWE 模型后训练的一个**独立且互补的训练目标**，而不必只练习最终下游任务本身。

## 2. 方法论

### 2.1 核心思想

设计两个**互补**的程序状态推理任务，覆盖四个正交维度：agentic / 非 agentic、符号推理 / 具体值推理、后向推理（从错误行为反推触发条件）/ 前向推理（从条件推演执行后果）。目标状态均选自人类开发者引入的、较"深"的缺陷状态，使任务非平凡。

### 2.2 任务一：Buggy Input–Output Reasoning（非 agentic、具体值）

- **输入**：问题描述 + 有缺陷程序（不含正确程序）。
- **要求**：生成一个具体 stdin 输入 `x`（后向），并预测有缺陷程序在该输入下的执行结果（前向），包括状态 `ok` / `crash` / `timeout`，`ok` 时还要预测完整 stdout。
- **验证**：在隐藏的正确程序 `Pc` 与有缺陷程序 `Pb` 上分别执行，成功条件为 `Pb(x) ≠ Pc(x)`，或 `Pb` 崩溃/超时而 `Pc` 正常；同时预测结果需与 `Pb` 实际执行一致。

### 2.3 任务二：Precondition–Postcondition Reasoning（agentic、符号 + 具体值）

- **输入**：真实仓库 issue + 有缺陷仓库的 Bash 访问（无网络、无 Git 历史、仅可改测试文件/夹具/测试数据）。
- **要求**：维护一个 `/tmp/swt_reasoning.md` 推理文件，含七个必需小节：`Valid Input/State Domain`、`Bug-Triggering Precondition`、`Operation`、`Expected Post-condition`、`Evidence-Grounded Bug Propagation Chain`、`Test Partitions and Boundaries`、`Revision Execution Evidence`；并将符号推理实例化为**可执行的仓库内回归测试补丁**。
- **四变体验证**（关键设计）：设 `Pb` 为缺陷版本、`Δ*` 为隐藏参考补丁、`τ` 为生成测试补丁，则分别执行 `PRED-PRE = Pb+τ`、`PRED-POST = Pb+Δ*+τ`、`BASE-PRE = Pb`、`BASE-POST = Pb+Δ*`。通过条件为：生成补丁**新增**至少一个 fail-to-pass 转变（相对 base 变体而言），保留全部 base fail-to-pass 转变，且不引入 pass-to-fail / fail-to-fail。该设计防止把**既有**测试状态翻转误记为生成补丁的贡献。
- **推理评判**：额外用 LLM judge 按 rubric 对推理文件打分（前置条件、后置条件、传播链、测试对齐、完备性、证据），并设置硬拒绝类别（跳过/xfail、删改既有测试、改源码或 runner、过度 mock、无关失败、同义反复断言、访问隐藏信息等）。

### 2.4 四阶段训练流程

1. **Math RL**（GRPO）：NuminaMath-1.5，八响应/提示，global batch 64，LR 1e-6，最大 32768 token，选中 iteration 74。
2. **Code RL**（GRPO）：TACO 转换后的 4371 道竞赛题，16 响应/提示，batch 512，LR 3e-6；奖励 `r = 0.6·rexec + 0.4·rrubric`，并配自适应难度课程（按指数移动平均通过率调整采样中心）；选中 iteration 45。
3. **Mixed SFT**：混合三类轨迹，共 8418 条（4033 条 issue resolution + 1138 条 precondition–postcondition + 3247 条 buggy input–output），3 个 epoch，batch 64，最大序列 65536，cosine LR 1e-5 → 5e-6，取 iteration-392 检查点。
4. **Agentic Pre–Post RL** → **Non-agentic Buggy-I/O RL**（序贯）。
   - Pre–Post RL 奖励：初始阶段 `r = 0.4·rexec + 0.2·rturn + 0.4·rreason`（`rturn` 为轮次效率奖励，权重 0.2，用于压缩轨迹长度），续训阶段去掉 `rturn`，改为 `r = 0.5·rexec + 0.5·rreason`；`rexec ∈ {0,1}`，`rreason = q/10`（judge 满分 10）。
   - Buggy-I/O RL 奖励：`rbase = 1` 需同时满足"成功暴露 bug"与"预测正确"；格式错误 −1；正确程序崩溃/超时 −0.5；成功响应施加长度惩罚 `rlength = 1 − 0.2·min(max(0, L−4096)/(8192−4096), 1)`，以及重复开头惩罚 `rprefix = 0.2·max(0, f(p) − 0.1)`，最终 `r = max(0, rlength − rprefix)`。

### 2.5 数据构建要点

- 仓库任务来源：SWE-Gym 2438 个 issue + SWE-ReBench Lite 1091 个带 Docker 镜像的 issue；采集用 90 分钟/rollout、无固定轮次上限，用 GPT-5.5 与 Qwen3.5-397B-A17B 生成教师轨迹，做拒绝采样与严格清洗（去 Git 历史访问、凭证泄漏、CJK 推理、超 65536 token 等）。
- Buggy I/O 任务来源：CodeContests 中配对"错误 Python 解 + 正确解"，经可解性/难度 judge 过滤后保留 1130 个任务。

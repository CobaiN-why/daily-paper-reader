## 摘要
多智能体编码已成为软件工程中一个日益活跃的方向，其中复杂的开发任务被分解给多个专用智能体，由它们分别处理问题的不同部分。尽管已从个体问题求解转向分布式协作，多智能体系统仍缺乏对协作的直接度量，并且在很大程度上沿用单智能体编码的任务级结果进行评估，从而将个体编码能力与跨智能体协调混为一谈。我们提出 AsynCodeBench，一个面向异步多智能体软件工程的以依赖为中心的基准，它用显式依赖图和可执行的依赖检查器（Dependency Checkers）来表示每个任务。通过这一依赖跟踪过程，我们提出两种互补的度量：异步依赖通过率（Asynchronous Dependency Pass Rate, ADPR），衡量最终有多少跨智能体依赖得到满足；以及依赖解决步（Dependency Resolution Step, DRS），衡量每个依赖在执行过程中首次得到满足的时机。AsynCodeBench 包含来自真实世界代码仓库的 19 个任务，暴露出 52 个有向依赖，作为评估跨智能体协作的显式单元。跨模型家族、规模和代际的实验揭示出编码能力与协作能力之间存在明显差距：编码性能的提升不一定转化为更强的协作，任务级指标也可能与依赖级协作度量显著偏离。依赖轨迹分析进一步表明，成功的协调往往不是逐渐出现的，而是通过集中式爆发出现：大量依赖在执行轨迹的短片段内得到解决，我们将这一模式称为跳跃窗口（hopping window）。

## Abstract
Multi-agent coding has emerged as an increasingly active direction in software engineering, where complex development tasks are decomposed across multiple specialized agents working on different parts of the problem. Despite the shift from individual problem solving to distributed collaboration, multi-agent systems still lack a direct measure of collaboration and are largely evaluated through task-level outcomes inherited from single-agent coding, conflating individual coding capability with cross-agent coordination. We introduce AsynCodeBench, a dependency-centric benchmark for asynchronous multi-agent software engineering that represents each task with an explicit dependency graph and executable Dependency Checkers. Through this dependency-tracking process, we propose two complementary measures: Asynchronous Dependency Pass Rate (ADPR), which measures how many cross-agent dependencies are ultimately satisfied, and Dependency Resolution Step (DRS), which measures when each dependency first becomes satisfied during execution. AsynCodeBench comprises 19 tasks from real-world repositories, exposing 52 directed dependencies as explicit units for evaluating cross-agent collaboration. Experiments across model families, scales, and generations reveal a clear gap between coding and collaboration capability: improvements in coding performance do not necessarily translate into stronger collaboration, and task-level metrics can diverge substantially from dependency-level collaboration measures. Dependency-trajectory analysis further reveals that successful coordination often emerges not gradually, but through concentrated bursts in which many dependencies become resolved over a short portion of the execution trajectory, a pattern we term a hopping window.

# AsynCodeBench 论文总结

## 1. 核心问题与整体含义（研究动机与背景）

- **背景转变**：LLM 智能体已从单文件代码生成扩展到仓库级软件工程（如 SWE-bench），多智能体开发系统（ChatDev、MetaGPT、RTADev、CAID、CodeTeam 等）将规划、实现、测试、协调分配给不同专用智能体。
- **核心问题**：多智能体系统引入了一种超越"解题本身"的新能力——**跨智能体协作**，即各智能体独立产出的组件必须被正确协调。但现有评测几乎完全沿用单智能体的**任务级结果指标**（如最终测试通过率、相对单智能体的增益），把"个体编码能力"与"跨智能体协调能力"混为一谈。
- **异步协调问题**：当智能体异步并发执行、不等待依赖方完成或传播更新时，下游智能体可能基于过时/不完整的上游行为继续工作，导致独立实现集成后不一致。这类失败**常被 outcome-only 评测掩盖**：评测者只看到某些组件失败，却看不到导致失败的"陈旧依赖"。
- **整体含义**：论文主张协作是一种**独立于编码能力的能力**，需要以跨组件软件依赖为透镜，把依赖的解决过程在执行中"显式化、可观测化"，从而将协作能力与编码性能分离评估。

## 2. 方法论

### 2.1 核心思想
以**依赖为中心（dependency-centric）**构建基准：每个任务用显式有向依赖图和可执行依赖检查器表示，在执行的多个集成检查点上跟踪依赖是否满足、何时满足。

### 2.2 形式化定义
- 基准四元组：`B = (R, G, C, E)`，其中 R 为仓库与任务，G 为依赖图，C 为可执行检查器，E 为评测。
- 依赖图：`G = (V, A)`，V 为实现单元集合，A ⊆ V×V 为有向依赖弧，每条弧 `d = (u, v)` 表示下游消费者 v 的正确性依赖上游生产者 u 提供的行为、状态、接口或工件。
- 每条依赖 d 预注册三组布尔检查器：`C_d = (C_d^U, C_d^D, C_d^I)`：
  - 上游组 `C_d^U`：生产者是否提供所需行为；
  - 下游组 `C_d^D`：消费者是否正确使用/保持该行为；
  - 集成组 `C_d^I`：集成后生产者—消费者依赖是否成立。
  - 组级结果定义为所有成员检查器全部通过（逻辑与）。
- 检查点与轨迹：`W_t` 为第 t 个保留的集成工作区，`I_{d,t} = C_d^I(W_t) ∈ {0,1}`，`I_d = (I_{d,1},…,I_{d,T})` 记录依赖 d 在执行中的**解决轨迹**，可区分"从未解决""多步后才解决""解决后又回归"。

### 2.3 评测指标
- **Test Pass Rate**：`P/N`，仓库级测试点通过比例，提供部分正确性的比例信用，但不直接评估跨组件依赖是否满足。
- **ADPR（异步依赖通过率）**：`ADPR = (1/|A|) Σ_{d∈A} I_{d,T}`，最终集成工作区中满足的依赖比例。
- **DRS（依赖解决步）**：`DRS_d = min{t : I_{d,t}=1}`，未解决时取 `T+1`；归一化为 `DRŜ_d = DRS_d/(T+1)`，越小表示越早解决，1 表示未解决。DRS 基于**逻辑集成检查点**而非墙钟时间；Single 协议只暴露最终工作区，不参与 DRS。

### 2.4 执行协议（5 种，作为受控对照）
| 协议 | 任务分解 | 并发 | 管理者 | 管理者可写 |
|---|---|---|---|---|
| SINGLE | – | – | – | – |
| SERIAL | ✓ | – | – | – |
| ASYNC-PRIVATE | ✓ | ✓ | – | – |
| ASYNC-MANAGER-RO | ✓ | ✓ | ✓（只读） | – |
| ASYNC-MANAGER | ✓ | ✓ | ✓ | ✓（受限补丁） |

- SERIAL 与 ASYNC-PRIVATE 共享同一专家分解，用于**隔离异步执行**的效应。
- 管理者变体用于检验协调（信息交换）与直接代码干预的差异；管理者从不直接改集成工作区，补丁需经范围校验、基线校验后按策略集成。

### 2.5 检查点构造
- 私有专家工作区的检查点**仅用于本地诊断**，不进入依赖轨迹。
- 进入轨迹的仅有：集成尝试后、被接受的状态改变型管理者干预后、最终评测，按执行顺序编号 `t = 1,…,T`，T 随运行而异。

## 6. 主要结论与发现

- **多智能体并非一致更优**：10 个模型中 6 个在最佳多智能体协议下相对 SINGLE 提升 7.8%–22.7%，但 4 个反而下降。高单智能体性能模型尤为明显：Qwen3.8-27B 与 DeepSeek-V4 的 SINGLE Test Pass Rate 均达 93.6%，而最佳多智能体结果分别降至 86.7% 和 89.9%。
- **任务级指标掩盖依赖失败**：ASYNC-MANAGER-RO 下 190 个结果中，Test Pass Rate 与 ADPR 正相关但不完全一致（Pearson r = 0.617，Spearman ρ = 0.613）；71.6%（136/190）的结果 Test Pass Rate 高于 ADPR，均值 48.0% vs 18.8%；32 个结果 Test Pass Rate ≥ 80% 却解决不到一半依赖，其中 26 个 ADPR 为 0；反向的"低测试高 ADPR"几乎不存在。该不对称性在全部五个协议中稳定复现（高测试低 ADPR 占 22.1%–27.4%）。
- **规模与代际**：Qwen3.5 从 9B 到 27B，Test Pass Rate 在所有协议下均提升（SINGLE 24.4%→42.1%，ASYNC-MANAGER 36.9%→59.2%），但 ADPR 提升高度依赖协议（SINGLE 14.2%→12.3%，ASYNC-MANAGER 2.8%→31.6%）。代际上，SINGLE 的 ADPR 从 Qwen3.5 的 12.3% 升至 3.6 的 36.8%、3.8 的 77.2%，而 ASYNC-MANAGER 的 ADPR 从 31.6% 升至 63.2% 后仅微增至 64.9%——**单智能体的巨大进步未同步转化为协作进步**。
- **DRS 揭示轨迹差异**：ASYNC-MANAGER 下归一化 DRS 从 Qwen3.5 的 0.787 降到 Qwen3.6 的 0.641，但 Qwen3.8 回升至 0.719，尽管二者最终 ADPR 相近——**相同终点可由不同协调轨迹到达**。
- **协议效应强模型依赖**：同一模型跨协议 ADPR 相对 SINGLE 的变化方向可相反，如 Qwen3.6-27B 从 ASYNC-PRIVATE 的 −14.9% 到 ASYNC-MANAGER 的 +26.3%，跨度 41.2%；没有任何协作协议对所有模型一致提升依赖解决。
- **"跳跃窗口"（hopping window）**：依赖闭合并非均匀累积，而是集中在轨迹中后段的短区间；聚合轨迹中 `0.50 < x ≤ 0.75` 区间占最终闭合质量的 34.9%–67.8%。归一化会强化该峰值（50.0%–73.9% 的首闭合对应 k=2,T=3），但原始检查点空间中 k=2 仍是最常见首闭合点（38.4%–60.2%），说明归一化只放大而非制造该现象。模型级差异显著：Gemma-4-26B 近乎平坦的协议几乎不产生闭合；Qwen3-Coder-Next 的 ASYNC-MANAGER 在 x≈0.4 提前爆发；DeepSeek-V4 四个协议均在后期爆发。
- **质量—成本评估依赖

质量—成本评估依赖所选指标：以 Test Pass Rate 衡量时，多智能体通常比 SINGLE 更贵且未必更优；但以 ADPR 衡量时，Async-Manager 等协议在部分模型上能以可接受的 token 增量换取依赖闭合的实质提升。这说明**"协作是否值得"的答案会随评价指标翻转**，成本结论不能脱离能力定义。
- **案例研究（TVM-20073）**：以 DeepSeek-V4 为例，展示同一模型在不同协议下依赖闭合轨迹的分化——某些协议直到集成末期才一次性闭合关键依赖，另一些则在中段逐步累积；该案例直观印证了"最终 ADPR 相同、路径却截然不同"的论点，也说明 outcome-only 指标无法区分这两种执行质量。

## 7. 局限与未来工作（论文自陈与推断）

- **任务规模有限**：仅 19 个任务、52 条依赖边，难以支撑细粒度的统计推断；论文未报告显著性检验、置信区间或多次采样的方差，单次运行的结果可能受随机性影响。
- **模型覆盖偏向开放权重**：未纳入 GPT、Claude、Gemini 等闭源前沿模型，因此"协作能力是否随能力上限继续变化"的结论尚不可外推。
- **依赖图人工构造**：尽管有三方评审与冻结机制，依赖边的选择仍可能引入构造者偏差；检查器覆盖的是"预注册的依赖"，可能遗漏执行中涌现的隐式耦合。
- **检查点语义为逻辑序而非时间序**：DRS 基于集成检查点编号，无法反映真实并发下的墙钟延迟、资源争用或死锁等异步系统层面的问题。
- **协议集合为受控近似**：五种协议是对现实多智能体框架的抽象，未必覆盖工业界更复杂的角色拓扑、消息总线或长程记忆机制。
- **可复现性缺口**：推理硬件、并发度、单次运行时长与总 token 规模均未披露，跨实验室精确复现存在障碍。
- **未来方向**：论文隐含指向——把依赖闭合作为一等评测目标、扩展到更多语言与更大任务集、引入时间维度的协调指标、以及研究"何时不该用多智能体"的决策规则。

## 8. 总体评价与启示

- **核心贡献**：将"协作"从编码能力中解耦，提出以依赖图 + 可执行检查器 + 解决轨迹为核心的评测范式，并给出 ADPR、DRS 两个可操作指标，弥补了 outcome-only 评测的结构性盲区。
- **方法论亮点**：依赖图评测前冻结、同一依赖在有序集成状态序列上评估、五协议受控对照共享同一分解与评测器、三方人工验证，设计上兼顾了客观性与可比较性。
- **最有价值的实证发现**：① 多智能体并非一致更优，高单智能体性能模型甚至可能被拖累；② Test Pass Rate 与 ADPR 系统性背离（高测试低依赖解决普遍存在），证明"通过测试"不等于"协作成功"；③ 单智能体能力的代际跃升未同步转化为协作能力提升；④ 相同终点可由不同协调轨迹到达，轨迹信息不可被终态指标替代。
- **实践启示**：对多智能体系统开发者而言，应显式建模并监控跨智能体依赖，避免异步执行下的"陈旧依赖"扩散；对评测者而言，应把依赖闭合纳入报告，而非仅看最终通过率；对使用者而言，选择协作协议需结合模型特性，"更多智能体"不是默认更优解。
- **待改进之处**：任务与模型规模偏小、缺少统计显著性与闭源模型、算力与复现信息不透明，这些限制了结论的普适强度，也是后续工作最直接的补强点。

## 摘要
编码智能体评估已从解决单个问题发展到执行长周期开发，但任务完成情况仍主要在单一代码库内评估。在软件生态系统中，许多功能和缺陷修复需要跨多个代码仓库进行协调变更。我们提出 WideSWE，用于评估编码智能体在这类跨代码仓库任务上的表现。通过挖掘并审查 103 个软件生态系统中的变更，我们得到 120 个真实世界任务，其中 60 个缺陷修复和 60 个功能开发保持均衡。我们从相关 issue 和 pull request 中推导提示。我们系统性地审查并调整隐藏测试，以支持多样的正确实现，同时保留必需行为和回归检查。在七种智能体配置中，完整任务成功率从 10.83% 到 42.50% 不等，其中 Codex CLI 与 GPT-5.6-sol 配对的配置达到最高成功率。轨迹显示，智能体会未能识别必要变更、识别出变更但未完成，或修改了所需代码仓库却未完全满足请求。为考察一次只处理一个代码仓库是否能缓解这些困难，我们在相同提示下将其与联合执行进行比较。独立执行主要能补回遗漏的工作，在纠正此前尝试过但未成功的实现方面效果较差。联合执行可以利用相关代码仓库的信息来指导实现与验证。代码可在 https://github.com/ZJU-ACES-ISE/WideSWE 获取。

## Abstract
Coding-agent evaluation has progressed from resolving individual issues to carrying out long-horizon development, yet task completion is still largely assessed within a single codebase. In software ecosystems, many features and bug fixes require coordinated changes across multiple repositories. We introduce WideSWE to evaluate coding agents on such cross-repository tasks. Mining and reviewing changes across 103 software ecosystems yields 120 real-world tasks, balanced between 60 bug fixes and 60 features. We derive prompts from related issues and pull requests. We systematically review and adapt hidden tests to support diverse correct implementations while preserving required behavior and regression checks. Across seven agent configurations, full task success ranges from 10.83% to 42.50%, with the configuration pairing Codex CLI with GPT-5.6-sol achieving the highest rate. Trajectories show agents failing to identify necessary changes, recognizing changes but leaving them unfinished, or modifying the required repositories without fully satisfying the request. To examine whether working on one repository at a time can alleviate these difficulties, we compare it with joint execution under identical prompts. Independent execution mainly recovers omitted work and is less effective at correcting previously attempted but unsuccessful implementations. Joint execution can use information from related repositories to guide implementation and verification. Code is available at https://github.com/ZJU-ACES-ISE/WideSWE.

- **研究动机**：编码智能体评测已从单点代码生成、单 issue 修复，发展到仓库级长周期开发，但任务完成度通常仍只在**单一代码库**内衡量。

- **核心问题**：编码智能体能否识别跨仓库变更范围，并在多个目标仓库中协调完成同一请求，同时保持既有行为与跨仓库一致性？
- **整体含义**：论文提出 **WideSWE**，将“跨仓库协同变更”形式化为可执行、可评分的基准任务，把评测重点从“单仓库内是否完成”推进到“多个仓库是否共同满足同一请求”。

## 2. 方法论：核心思想与关键技术细节

- **核心思想**：
  - 每个任务对应一个共享 feature 或 bug fix，要求至少在两个目标仓库中进行实质性协调修改。
  - 目标仓库决定评分范围；上下文仓库可用于参考，但不一定需要修改。
  - 任务成功要求**所有目标仓库**同时通过其 F2P 与 P2P 测试。

- **任务形式化**：
  - 对任务 \(c\)，给定请求 \(p_c\) 和历史工作区 \(W_c\)，其中包含仓库集合 \(R_c\)。
  - 目标仓库集合 \(T_c \subseteq R_c\)，且 \(|T_c| \ge 2\)。
  - 智能体 \(A\) 根据 \(p_c, W_c\) 产生补丁集合 \(\Delta_c = A(p_c, W_c)\)，并得到修改后工作区 \(W'_c = W_c \oplus \Delta_c\)。
  - 对每个目标仓库 \(r\)，需通过 fail-to-pass（F2P）与 pass-to-pass（P2P）测试；任务成功定义为所有目标仓库均成功。
  - 工作区还可包含最多 20 个非目标上下文仓库，用于提供生态信息。

- **基准构建流程**：
  - 从 GitHub 总星数排名前 200 的组织中筛选出 **103 个活跃软件生态**。
  - 收集 2024 年 1 月 1 日后合并的 PR，共 **1,729,171 个 PR**，其中 **109,233 个**显式引用同生态内其他仓库。
  - 分组、去重、检查 PR 可用性、测试变更、Linux 可运行性后，得到 **4,437 个候选组**。
  - 聚焦最新 PR 合并于 2025 年 6 月 1 日后的 **2,188 个候选组**，人工审查保留 **635 个**。
  - 可执行验证与最终审查后得到 **192 个合格案例**，每个目标仓库至少有一个 F2P 测试。
  - 为平衡任务类型，保留全部 **60 个 bug fix**，并从 **132 个 feature** 中选择 **60 个**，最终形成 **120 个任务，覆盖 41 个生态**。

- **提示构造**：
  - 尽量保留原始 issue 与 PR 描述措辞，合并相关需求为一个跨仓库任务。
  - 只澄清必要行为、边界条件和兼容性约束，不引入实现步骤。

- **隐藏测试审查**：
  - 发现继承测试可能拒绝其他正确实现，采用两条规则：
    1. **放宽实现特定约束**：如移除对私有 helper 名、固定文件路径、精确错误文本的限制。
    2. **删除未请求功能检查**：移除原始 issue/PR 与任务提示均未要求的新增功能测试。
  - 审查后仍需保证修改后的测试能拒绝 Base 代码、接受 Gold 参考实现。
  - 在 120 个任务中，**88 个任务**受到需求对齐测试修订影响；87 个任务放宽了实现约束，16 个任务移除了未请求功能检查，15 个任务两者兼有。

- **评估指标**：
  - **Case success**：所有目标仓库均通过全部 F2P 与 P2P 才算成功。
  - **Repo success**：单个目标仓库通过全部相关测试。
  - **F2P-complete / P2P-preserved**：分别统计通过全部 F2P 或 P2P 的仓库比例。
  - **API**：记录每任务平均 API 请求数。

## 摘要
基于大语言模型的编码智能体在仓库级软件工程任务上已取得显著进展。然而，现有仓库基准通常从人工识别的问题出发，评估补丁是否满足功能信号。我们提出 SWE-Prometheus，一个面向改进仓库工程治理这一更广泛任务的基准。每个任务提供一个固定快照和一个开放式目标，要求智能体识别风险、确定干预优先级并验证由此产生的变更。SWE-Prometheus 通过配对证据、干净环境探测、行为门控以及两位独立教师对同一证据的评分，评估六个治理维度。该基准包含 60 个仓库；十个模型在共享的 22 个仓库公开子集上接受评估，其中平均归一化治理改进（Normalized Governance Improvement）介于 0.0568 至 0.5760 之间，观测到的行为破坏率介于 0% 至 23% 之间。在一个冻结的十仓库批次上，仓库盲模板获得平均 NGI 0.272，但其增益集中在测试与 CI、质量门禁和文档；它未能在任何一个仓库上改进可复现环境和依赖与安全。该基线使得区分“添加治理制品”与“产生有执行支撑的改进”变得可度量。空操作条件下 NGI 中位数为零，标准差为 0.073；对于相同的空操作证据，两位教师在 60 个维度评分中有 57 个完全一致。对于条件均值最高的两个系统，共同有效 NGI 相近，而包含行为失败的全池比较则更支持 Kimi-K3。这些结果表明，为什么仓库治理评估应同时报告改进、行为保持、证据质量和覆盖范围。

## Abstract
Large language model based coding agents have made substantial progress on repository-level software engineering tasks. Existing repository benchmarks, however, usually start from a human-identified issue and evaluate whether a patch satisfies a functional signal. We present SWE-Prometheus, a benchmark for the broader task of improving repository engineering governance. Each task provides a fixed snapshot and an open-ended objective, requiring the agent to identify risks, prioritize interventions, and verify the resulting changes. SWE-Prometheus evaluates six governance dimensions through paired evidence, clean-environment probes, behavior gates, and two independent teacher ratings of the same evidence. The benchmark contains 60 repositories; ten models are evaluated on a shared 22-repository public subset, where mean Normalized Governance Improvement ranges from 0.0568 to 0.5760 and observed behavior-breakage rates range from 0% to 23%. On a frozen ten-repository batch, a repository-blind template obtains mean NGI 0.272, but its gains concentrate in Tests & CI, Quality Gates, and Documentation; it improves Reproducible Environment and Dependency & Security on none of the repositories. This baseline makes the distinction between adding governance artifacts and producing execution-backed improvements measurable. The no-op condition has median NGI zero and standard deviation 0.073; two teachers agree exactly on 57 of 60 dimension scores for the same no-op evidence. For the two highest conditional-mean systems, common-valid NGI is similar, while full-pool comparisons that include behavior failures favor Kimi-K3. These results show why repository-governance evaluation should report improvement, behavior preservation, evidence quality, and coverage together.

# SWE-Prometheus 论文总结

## 1. 核心问题与整体含义

- **研究动机**：现有仓库级代码基准（如 SWE-bench 系列）通常从**人工已识别的 issue** 出发，评估补丁是否通过目标测试或满足功能信号。这类设定适合“定向功能修复”，但忽略了软件工程中另一类核心任务：**让仓库更易测试、维护、复现和安全演进**。
- **被忽略的治理维度**：测试与 CI 就绪度、干净环境行为验证、代码质量与可维护性、文档、可复现环境、依赖与安全健康等，往往分散在多个工程制品中，不能仅凭 diff 判断是否真正改进。
- **核心矛盾**：存在**“工程制品”与“工程效果”之间的差距**——智能体可能添加 workflow、lint 配置或测试文件，却没有带来实际可执行的改进；也可能改进一个维度却引入依赖漂移或行为回归。
- **整体含义**：论文提出 **SWE-Prometheus**，把评测对象从“修复已知缺陷”转为“诊断并改进仓库的工程治理状态”，要求智能体自行发现风险、排序干预并验证改动，同时保持既有行为。该基准旨在补足 issue 级修复基准，强调**诊断、优先级、干预与验证**。

## 2. 方法论

### 2.1 核心思想

- 每个任务给定**固定仓库快照 + 开放式治理目标**，不提供缺陷列表、基线分数、隐藏测试或参考补丁。
- 智能体需自行检查仓库、识别治理缺口、选择改造策略、提交 unified patch。
- 评测器重建 base 与 treated 两个状态，在**干净环境**中执行同一组探针，并用**行为门**识别不安全干预。

### 2.2 六个治理维度

- D1：Tests & CI（有意义测试、CI 就绪度、覆盖率信号）
- D2：Code Quality Gates（lint/format、类型检查、质量门禁）
- D3：Documentation & Collaboration（README、贡献信息、license/安全文档）
- D4：Structure & Maintainability（模块结构、复杂度与坏味、可修改性）
- D5：Reproducible Environment（干净安装、构建/运行、环境一致性）
- D6：Dependency & Security Health（依赖控制、供应链检查、安全证据）
- 每个维度 1–5 分，4 分表示“可执行、可审查、适合该仓库类型”；**仅有配置文件存在不构成改进证据**。

### 2.3 关键评估机制

- **配对证据**：同一组安装、测试、质量、复杂度、依赖与安全探针分别在 base 和 treated 上运行；保留命令、退出码、日志、工具版本、超时与不可用证据。
- **干净环境探针**：patch 应用到独立干净副本，不复用智能体可变工作树，避免缓存或生成文件影响结果。
- **行为门**：
  - 特征化测试先在 base 上验证，再在 treated 上执行；失败标记为 `behavior_broken`，从有效 NGI 聚合中排除，但保留在行为风险分析中。
  - 通过变异测试把门标记为 `detected`、`blind`、`vacuous` 或 `none`，门强度与行为结果一同报告。
- **双教师评分**：同一份固定证据由两个独立教师模型按同一 rubric 评分，保留两次判断、聚合值和分数差；no-op 条件额外测量端到端变异。

### 2.4 核心公式

- 原始改进：
  \[
  \Delta_{i,d}=s^{\text{treated}}_{i,d}-s^{\text{base}}_{i,d}
  \]
- 归一化治理改进（NGI）：
  \[
  \text{NGI}_i=\frac{1}{|D_i|}\sum_{d\in D_i}\frac{s^{\text{treated}}_{i,d}-s^{\text{base}}_{i,d}}{5-s^{\text{base}}_{i,d}}
  \]
  其中 \(D_i\) 为已定义且可评分的维度集合；base 为 5 的维度不获改进奖励，但检查是否回归。
- 辅助指标：treated 分数、valid/broken 率、no-regression 率、strict success、verified claim rate、资源使用。
- 全池可靠性比较中，行为破坏运行可被赋 NGI 为 0、−1 或 −3（−3 为 1–5 rubric 下的理论下界）。

### 2.5 流程

1. 重建固定 base 快照；
2. 验证 base 环境与特征化行为；
3. 以固定开放式指令启动模型；
4. 归档模型输出与候选 patch；
5. 将 patch 应用到独立干净快照；
6. 运行 treated 探针与行为验证；
7. 评分并写入结果 manifest。

## 6. 主要结论与发现

- **治理改进差异巨大**：公开子集平均 NGI 从 **0.0568 到 0.5760**，行为破坏率从 **0% 到 23%**。
- **改进、安全、绝对质量是三个独立轴**：Kimi-K3 与 GLM-5.3-Flash 条件均值相同（0.576），但 Kimi-K3 仅 1/22 破坏行为，GLM-5.3-Flash 为 5/22；全池比较（broken=0）Kimi-K3 为 0.550，GLM-5.3-Flash 为 0.445。
- **仓库盲模板可获可观分数但边界明显**：mechanical template 平均 NGI 0.272，规则基线 0.254，均高于部分模型；但增益集中在 D1–D3，**D5 和 D6 在十个仓库上均无改进**，D4 仅 20%。
- **Efficient-WAM 案例**：模板添加的 workflow 运行 Ruff 和 pytest，但唯一测试是 `assert True`，测试通过而 Ruff 仍报 117 个错误，且无可识别安装/构建入口和依赖清单——说明**制品存在 ≠ 有执行支撑的改进**。
- **No-op 稳定**：中位 NGI 为 0，均值 −0.009，标准差 0.073；两位教师 57/60 完全一致，平均绝对分差 0.067。漂移主要出现在 D4、D3、D5。
- **匹配比较更严格**：只有 Kimi-K3（9 胜 1 负）和 GLM-5.3-Flash（8 胜 1 负）在多数仓库上明显超过更强模板；中段模型与模板接近，弱模型落后。
- **门强度影响 breakage 观测**：detected 门 13%、blind 门 8%、vacuous 门 0%，而 NGI 中位数仅变化约 0.06；弱门可能漏检回归，零破坏不等于安全。
- **门控消融不改变模型排序**：去掉行为门后各模型中位变化最多 ±0.021，说明被门捕获的实例往往得分接近或低于模型均值，行为破坏更像“干预失败”而非“激进高分的代价”。
- **维度分解**：Tests & CI 在多数有效运行中改善；Structure & Maintainability 是十个模型中八个的最弱维度；Claude-Opus-5 呈现“编辑结构而非添加文件”的画像。
- **核心洞察**：部分治理增益可来自不读仓库的模板式添加，**治理改进不等于仓库诊断**；评估应同时报告改进、行为保持、证据质量与覆盖范围。

## 7. 优点

- **任务设定贴近真实工程治理**：开放式目标、无缺陷列表、无 oracle patch，允许多种有效改造策略。
- **证据链完整**：配对 base/treated、干净环境执行、命令级日志、退出码、工具版本、超时与不可用证据均保留。
- **行为门与门强度分离**：不仅检查行为是否保持，还用变异测试标注门本身的判别力，避免把弱门零破坏误读为安全。
- **多维度诊断控制**：no-op、机械模板、规则基线、匹配比较、失败处理敏感性、门控消融共同校准“分数来自能力还是来自模板”。
-

- **行为保持与治理改进分离报告**：不把“分数高”与“安全”混为一谈，而是同时给出 NGI、breakage 率、valid/broken 分母、门强度分层，使读者能区分“有效但危险”“保守但低收益”“高收益且稳健”等不同画像。
- **归一化设计避免基线惩罚**：NGI 以 `5 - s_base` 为分母，使高基线仓库不被系统性压低分数，同时明确 base 为 5 的维度不再获得改进奖励，只检查回归，避免“刷分空间”被滥用。
- **失败处理敏感性显式化**：对行为破坏分别赋 0、−1、−3 并观察排序变化，主动暴露评分聚合规则对结论的影响，而不是隐藏在一个固定惩罚值后面。
- **公开/私有划分的诚实披露**：明确说明划分在任务验证后应用、不改变评分定义，并承认公开子集由模型覆盖而非随机采样，降低“选择性报告”的风险。
- **可复现性设计**：固定 base 快照、独立干净副本、manifest 写入结果、保留工具版本与超时/不可用证据，使失败与缺失可追溯，而不是被折叠成零分。
- **对“制品式改进”的专门反例**：Efficient-WAM 案例把“workflow 通过但 Ruff 报 117 个错误、测试只有 `assert True`”具体化，为“配置文件存在 ≠ 工程改进”提供了可引用的证据。

## 8. 局限与不足

- **单次 rollout 限制因果推断**：每个 model-instance pair 仅一次 rollout，无法区分仓库异质性、采样随机性与评分噪声，因此相邻模型间的排序差异不可靠。
- **行为门强度不均衡**：60 个实例中仅 24 个为 mutation-demonstrated gate，blind 与 none 占比高；在弱门下观察到的“零破坏”不能作为强安全证据，可能系统性低估真实回归率。
- **脚手架异构**：Claude-Opus-5 使用 Claude Code，其余九个模型使用 pi，跨脚手架比较只能视为“系统级”结果，不能归因于模型能力本身。
- **LLM 教师评分的固有噪声**：双教师评分虽保留分差与一致性（no-op 下 57/60 完全一致），但治理维度中 D3、D4、D5 仍出现漂移，说明部分维度缺乏足够客观的判据。
- **维度等权假设**：NGI 对已定义维度取等权平均，未论证 Tests & CI 与 Documentation 在真实工程治理中应具有相同权重；不同仓库类型的最优权重可能不同。
- **静态快照的时间局限**：评测基于固定仓库快照，无法观察干预在长期维护、后续 PR 或真实 CI 环境中的持续效果，治理改进的“耐久性”未被测量。
- **样本规模与覆盖**：公开子集仅 22 个实例、辅助对照仅 10 个仓库，模板与规则基线样本偏小；私有集结果不可外部复现，限制了结论的可验证范围。
- **成本账本不完整**：货币成本仅在 provider accounting 可用时报告，缺少统一成本口径，难以比较不同模型的“单位治理改进成本”。
- **未涉及训练侧**：论文未报告 GPU 型号、数量与训练时长，因为其本质是基准构建与推理评估；但这意味着无法评估模型在治理任务上的能力来源或可迁移性。

## 9. 结论与启示

- **对基准设计的启示**：仓库级评测不应止步于“给定 issue 修 bug”，而应显式覆盖测试、CI、质量门禁、文档、可复现环境与依赖安全等治理维度；同时必须把“改进幅度”“行为保持”“证据质量”“覆盖范围”作为并列报告项，而非压缩成单一分数。
- **对智能体评估的启示**：开放式治理任务中，模型可能通过不读仓库的模板式添加获得可观分数，因此评测需要加入 no-op、机械模板与规则基线，并以匹配比较和分辨率估计来校准“能力 vs. 模板”的边界。
- **对工程工具的启示**：仅添加 CI workflow、pre-commit、mypy.ini 等制品并不等于改进；工具与智能体应被要求提供可执行的安装/构建入口、真实测试与依赖清单，并在干净环境中验证。
- **对安全与风险沟通的启示**：行为门强度必须与破坏率一同报告；弱门下的零破坏应被标注为“未检测到”而非“安全”，并可通过失败处理敏感性分析暴露聚合规则对结论的影响。
- **对未来工作的启示**：需要多 rollout、多脚手架同构重跑、专家处理对照、长期维护追踪，以及按仓库类型加权的治理评分；同时应扩展公开实例数量与维度判据的客观性，以支持更细粒度的模型比较。

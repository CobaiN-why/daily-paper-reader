## 摘要
我们提出：(i) 一个新数据集，包含一个由 Claude AI 完全构建、无任何人工编写代码或测试的 21,000 行 Python 工具的完整开发历史；(ii) 两个代码来源追踪工具；(iii) 三个分类体系，分别用于指令意图、提交来源和响应可靠性；(iv) 将这些分类体系应用于分析该数据集。我们发现：(i) 用户给编码智能体的 CLI 指令与 IDE 聊天指令在种类上不同，更侧重于理解、规划和咨询；(ii) 代码开发主要是主动式的；(iii) 14.3% 的 AI 代码生成事件包含一个真实错误，该错误后来被 AI 编写的测试套件捕获；(iv) AI 的交互式响应中大约每 4 到 5 个就有 1 个包含一个或多个事实错误。

## Abstract
We present: (i) a new dataset consisting of the full development history of a 21,000-line Python tool built entirely by Claude AI, with no human-authored code or tests, (ii) two code-provenance tracing tools, (iii) three taxonomies for instruction intent, commit provenance, and response reliability, (iv) application of these to analyse the dataset. We find that: (i) user coding agent CLI instructions differ in kind from IDE-chat instructions, with a greater focus on comprehension, planning and consultation, (ii) code development is mainly proactive, (iii) 14.3% of AI code-generation events contain a real error later caught by the AI-authored test suite, (iv) roughly 1 in 4-5 of the AI's interactive responses contains one or more factual errors.

# 论文总结：《Between the Commits: Process, Error, and Claim Reliability in a Wholly AI-Authored Codebase》

## 1. 核心问题与整体含义（研究动机与背景）

- **核心问题**：AI 编码智能体写代码很快，但错误率足以使其输出不能"照单全收"。要判断 AI 驱动软件开发究竟有多可靠，必须看到**开发过程本身**——AI 自己的代码和断言多久会出错、什么机制能在代码合入前拦截这些错误。
- **现有数据缺口**：
  - 大规模 AI 代码数据集（如 SWE-chat、AIDev）主要只有 commit/PR 元数据，会话记录覆盖极薄（SWE-chat 中位仅 8 个会话，57.1% 的仓库完全没有 AI 提交）。
  - 缺少"提交前就被发现并修复"的错误信息——这类错误在 commit history 中**完全不可观测**。
- **工具缺口**：把一段代码归因到交互会话中的具体来源、恢复会话中途被自我纠正的代码错误、区分 AI 可靠与不可靠的断言，都缺乏现成工具。
- **整体含义**：本文首次提供一个"全 AI 编写、零人类代码/测试"的真实项目完整开发史数据集，并配套溯源工具与分类体系，从而给出**首个现代编码智能体面向用户的响应错误率**，为评估 AI 自主编程的过程可靠性提供基准与方法。

## 2. 方法论：核心思想与关键技术细节

### 2.1 数据集（Extractor）

- **Extractor**：一个真实的 Python 工具（`apple_protobuf_extractor`），用于从编译后的 Apple Objective-C/Mach-O 二进制或 dyld shared cache 中逆向恢复 Protocol Buffers 的 `.proto` 描述符。
- 规模：**21,000 行生产代码 / 21,829 行测试代码，1,467 个测试，210 个 commit，25 个会话，678 条用户指令**；由 Claude 模型在数周内从零构建，**无任何人类编写的代码、测试或提交**。

### 2.2 代码溯源工具（两件）

- **工具一：CFG 基本块分解 + git 历史追踪**
  - `cfg_builder.py`：将函数 AST 划分为控制流图（CFG）基本块——遇到分支点（if/elif/while/for）或 `except` 处理器即开启新块；嵌套函数/类单独划分，其行数不计入外层函数；其余语句逐条归入当前块。结果为**互不重叠、恰好覆盖每一行一次**的块集合。
  - `git_tracer.py`：用 `git log -L` 恢复块的行区间历史，得到起源 commit 与后续变更（churn）。
  - **关键技术难点**：`git log -L` 的改名检测基于整文件相似度，无法追踪"大文件被部分拆分出去"这一本项目中最主要的重构模式。解决策略分两级：
    1. 先在拆分前的 commit 树中按块自身文本重定位；
    2. 若文本太短/重复（如 `return (x, x)`），改用**外层函数名**作锚点，并额外要求"疑似拆分 commit 确实同时触碰新旧文件"才可信；
    3. 若仍无法唯一定位（如 `writeTo`/`readFrom` 在多类中同名），**明确报告为 unresolved 而非猜测**。
  - 效果：加入函数锚点后，未解决率从 **11.4% 降至 0.4%**；残余未解决块均披露原因。作者刻意保持纯机械、可复现，不引入 LLM。

- **工具二：会话转录挖掘（恢复自我纠正的代码错误）**
  - 在原始 `.jsonl` 会话日志中定位所有含 `pytest` 的 Bash 调用，用正则按 `-q` 摘要行判定 PASS/FAIL；把"FAIL → ≥1 次编辑 → 同一测试目标上 PASS"标记为候选自我纠正事件；用事件 UUID 去重（会话压缩会导致重复事件）。
  - 纯正则无法区分**故意变异测试**与真实 bug，故由 AI（Claude Sonnet 5）读取事件转录，归入四类：生产逻辑缺陷 / 测试或 fixture 缺陷 / 未把变更传播到依赖测试 / 故意变异测试；所有判为缺陷的事件再由人工复核（纠正了 2 处误判）。

### 2.3 三套分类体系

- **指令意图**：扩展 Tang 等人的 IDE 聊天 7 大类/20 子类体系到**多轮 CLI 场景**。因约 46% 指令是复合指令，先用 LLM 把指令分解为组件再分类（分解使 κ 从 0.700 升至 0.790，精确匹配率从 52% 升至 76.6%）。新增 4 个子类：`4.3 设计原则规范`、`6.3 版本控制`、`7.6 合规性纠正`（纠正 AI 自身行为而非代码）、`7.7 会话/环境协调`（跨会话协调，CLI 可并行会话而 IDE 聊天不能）。
- **提交来源**：扩展 Swanson 的 Perfective/Corrective/Adaptive 维护分类，将"为什么改"与"怎么改出来"分离，分主动式（Spec/Analysis/Design/Audit）与反应式（Spec/Analysis/Design）外加 Housekeeping；分类依据是**AI 自身的推理与工具调用过程**，而非事后从 commit message 重建。
- **响应可靠性**：无直接先例。按验证方式组织：`可核查事实`、`机制解释`、`根因诊断`、`设计修复提案`、`其他（不计分）`；前两类用提交点时刻的代码即可判定，后两类需向前看后续 commit 是否真正解决问题。

### 2.4 事实核查流水线（分解—分类—验证）

1. 把每条响应分解为组件（678 条响应 → 9,967 个组件，聚焦其中 6,818 个结论段落/加粗要点/汇总表）；
2. 用 LLM 分类；
3. 由定制 Python 脚本从代码库收集证据包（重跑代码、静态搜索、git 历史追踪、二进制解析等），LLM（Claude Sonnet 5）可访问代码库/会话/项目文档并**迭代补充证据直至收敛**（约 60% 一轮收敛，35% 两轮，5% 三轮）；
4. 用评分 rubric 打分，两个独立 LLM 全量打分，人工校准边界情形并迭代细化 rubric。

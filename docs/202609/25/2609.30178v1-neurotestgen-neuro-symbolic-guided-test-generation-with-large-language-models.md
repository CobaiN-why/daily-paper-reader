## 摘要
确保高结构覆盖率仍然是自动化测试生成中的一个基本挑战，尤其是在复杂软件系统中，要达到特定行或分支需要满足复杂的控制流和数据流约束。大语言模型（LLMs）近期在生成类人测试用例方面展现出强大能力；然而，它们往往难以生成满足精确路径条件的输入。相反，符号执行可以系统地推导出此类约束，但往往无法构造真实、可执行的测试用例，并受可扩展性限制。在本文中，我们提出 NEUROTESTGEN，一种将符号执行与 LLM 驱动的测试合成相结合的混合方法，用于生成以按需代码覆盖为目标的测试用例。给定方法内的一组目标语句，NEUROTESTGEN 首先使用符号分析引擎（即 Z3 SMT 求解器）提取路径特定约束，并为期望的覆盖目标构建符号引导规范。然后，该规范用于指导 LLM 合成既结构有效又语义有意义的具体测试用例。对于涉及 SMT 求解器难以处理的复杂对象相关约束的路径，NEUROTESTGEN 利用 LLM 推断合理的约束。此外，NEUROTESTGEN 引入迭代反馈循环，用于验证 LLM 生成的测试并提供纠正性引导，直到目标行或分支被覆盖或达到上限。我们在一个广泛使用的基准上的实证评估表明，NEUROTESTGEN 在多个 LLM 上显著优于最先进的方法，包括 Llama 3.3 70B1、GPT-4o Mini、Claude 3.5 Haiku3 和 Claude Sonnet 4.6。

## Abstract
Ensuring high structural coverage remains a fundamental challenge in automated test generation, particularly for complex software systems where reaching specific lines or branches requires satisfying intricate control- and data-flow constraints. Large Language Models (LLMs) have recently demonstrated strong capabilities in producing human-like test cases; however, they often struggle to generate inputs that satisfy precise path conditions. Conversely, symbolic execution can systematically derive such constraints, but it often fails to construct realistic, executable test cases and is constrained by scalability limitations.   In this paper, we introduce NEUROTESTGEN, a hybrid approach that integrates symbolic execution with LLM-driven test synthesis to generate test cases targeting on-demand code coverage. Given a set of target statements within a method, NEUROTESTGEN first employs a symbolic analysis engine (i.e., the Z3 SMT solver) to extract path-specific constraints and construct a symbolic guidance specification for the desired coverage goal. This specification is then used to guide an LLM in synthesizing concrete test cases that are both structurally valid and semantically meaningful. For paths involving complex object-related constraints that are difficult for SMT solvers to handle, NEUROTESTGEN leverages LLMs to infer plausible constraints. Furthermore, NEUROTESTGEN incorporates an iterative feedback loop that validates LLM-generated tests and provides corrective guidance until the target line or branch is covered or a limit is reached. Our empirical evaluation on a widely used benchmark demonstrates that NEUROTESTGEN significantly outperforms the state-of-the-art approach across multiple LLMs, including Llama 3.3 70B1, GPT-4o Mini, Claude 3.5 Haiku3, and Claude Sonnet 4.6.

## 1. 核心问题与研究动机

- **背景**：软件测试是发现缺陷最有效的手段之一，但自动生成能够达到**精确结构覆盖**（特定行、分支、路径）的高质量测试仍是根本性难题。传统方法（符号执行、搜索式测试、concolic 执行）虽在系统化探索程序行为上取得进展，但难以扩展至真实软件，且产出的测试往往不具可读性和可维护性。
- **LLM 的局限**：LLM 能生成类人单元测试、构造真实输入对象、组合正确 API 序列，但**缺乏满足精确路径条件的推理能力**——达到目标分支常需满足复杂的控制流/数据流约束、维持对象不变量或触发特定程序状态，LLM 无法可靠保证。
- **符号执行的局限**：符号执行擅长约束推理（推导路径条件、识别不可行路径、发现所需 API 调用序列），但只能产出底层约束或具体输入值，无法生成可读、开发者友好的完整测试用例，且受路径爆炸、复杂堆推理等可扩展性限制。
- **现有 SOTA 的不足**：Panta 将静态控制流分析与动态覆盖反馈结合来迭代引导 LLM，但**过度依赖 LLM 推理**：直接将未覆盖路径放入提示，不判断路径是否可行，导致对不可行路径反复尝试、浪费 token 预算、性能不稳定；且未显式求解路径约束、推断具体输入条件。
- **核心洞察**：存在明显空白——符号执行善于约束推理但弱于生成测试，LLM 善于生成测试但难以满足精确覆盖目标。NEUROTESTGEN 旨在融合二者优势。

## 2. 方法论

### 2.1 核心思想
神经符号（Neuro-Symbolic）混合方法：用符号推理提供精确的路径约束引导，用 LLM 提供语义理解与灵活测试合成，实现**按需结构覆盖**。

### 2.2 整体流程
1. **初始基线**：给定项目与目标源文件，先提示 LLM 生成初始测试集。
2. **静态分析**：构建控制流图（CFG），枚举每个方法的可行执行路径。
3. **路径筛选**：结合动态覆盖反馈与 CFG 路径，识别未覆盖路径；维护**路径历史日志**避免重复选择多次失败的路径。
4. **路径分类**：将未覆盖路径分为**纯数值路径**与**对象相关路径**，分别处理。
5. **提示构建与测试生成**：将路径信息与输入引导格式化入提示，LLM 生成测试。
6. **迭代反馈**：执行验证生成测试，失败则提供错误信息回馈 LLM 迭代修复，直至覆盖目标或达上限。

### 2.3 纯数值路径：纯符号执行
- **判定标准**：执行逻辑仅含数值计算（算术、取模、比较、位运算），分支谓词仅定义在原始数值变量上。
- **技术细节**：
  - 使用 **Z3 SMT 求解器**；按方法参数声明类型创建符号变量。
  - 顺序遍历所选路径，维护记录各变量符号值的**符号环境**；赋值语句更新符号状态，原始符号输入保留用于最终模型构造。
  - 每个分支条件翻译为 Z3 兼容约束；走 false 分支时对谓词取反后加入求解器（如 `if (n < 0)` 为 False 译为 `Not(n < 0)`）。
  - 算术、取模、位运算表达式直接编码为 SMT 公式。
  - **跳过循环体**以控制求解复杂度（循环展开或不变式推断会大幅增加开销）。
  - 约束集可满足则提取具体输入赋值作为引导；不可满足则视为不可行路径排除。

### 2.4 对象相关路径：LLM 路径求解
- **判定标准**：执行依赖对象语义或高层抽象，包括对象创建/访问、方法调用、库 API 调用、常量/全局对象引用、复杂字符串操作。
- **LLM-Path-Solver**：不翻译为 SMT 约束，而是将源代码、方法签名、未覆盖分支条件、执行路径上下文直接提供给 LLM，由模型推理程序语义并合成具体方法输入。
  - 示例：`classify("Apple", Mode.STRICT)` 可满足 `mode == Mode.STRICT && text.startsWith("A")`。
- **LLM-Verifier 二级验证**：用另一模型对目标方法进行符号化追踪，检查生成输入是否确实沿预期路径执行；失败则将拒绝原因与无效输入反馈给 Solver 迭代精化，直至生成有效输入或达重试上限。
- 有效输入的具体值作为路径引导示例追加到下游测试生成提示中。

### 2.5 提示构建与测试生成
- **类型注解增强**：直接在代码中以注释标注变量类型（如 `Date date = new Date() // "date" is a variable of type "Date"`），容器类型追加元素类型注解（如 `// "list" is a List of type "Integer"`）。
- **路径信息三要素**：① 变量定义/对象创建代码（含变量描述）；② 常规操作代码（计算、方法调用）；③ 条件/循环代码（以 True/False 条件表示执行要求）。
- 追加由 Z3 或 LLM 导出的**输入引导**，送入 LLM 生成测试。
- 生成测试若失败（编译或运行时错误），将错误信息与失败测试文件回馈 LLM 迭代修复；**仅保留通过的测试**并追加到测试套件，重新评估覆盖，循环直至达标或达上限。

## 摘要
近期研究表明，大语言模型能够在包括竞赛编程在内的多种编程环境中有效求解问题并修复缺陷。现有方法主要独立评估LLM在问题求解或缺陷修复中的表现，但未探讨这两种能力之间的关系。本工作聚焦于确定：与人工编写的补丁相比，LLM为修复缺陷而对有缺陷解进行的偏离程度，以及是否存在倾向于生成全新解的偏差。我们构建了一个数据集，包含来自Codeforces的若干用户的所有提交（约3000份），并将每个有缺陷提交与其对应的人工修复进行匹配。以有缺陷解与人工修复之间的相似度作为基线，我们在3个OpenAI GPT模型（gpt-5-nano、gpt-5-mini、gpt-5.1）上评估LLM生成缺陷修复的质量。我们使用Codeforces-R1数据集检查生成的解是否能解决问题，该数据集是一个公开可用的数据集，其测试由DeepSeek-R1模型生成。我们的发现表明，与人工修复相比，LLM倾向于修改比必要更多的行数，并且在某些情况下会生成全新的解。我们还观察到，当允许LLM从头生成解，而不是对有缺陷提交打补丁时，LLM能正确解决更多问题，即使这些提交与人工补丁很接近。这对AI辅助编程工具的设计具有重要意义，尤其是在支持用户调试过程以及促进增量式问题求解策略而非解替换方面。

## Abstract
Recent studies have shown that Large Language Models can effectively solve problems and fix bugs in diverse programming environments, including competitive programming. Existing approaches primarily evaluate LLM performance in problem solving or bug fixing independently, but do not explore the relationship between these two capabilities. This work focuses on determining how much the LLM deviates from a buggy solution to fix the bug compared to a human-written patch, and if there is a bias towards generating entirely new solutions. We construct a dataset with all the submissions ($\sim$ 3000) from a couple of users from Codeforces, and we match each buggy submission with its corresponding human fix. By using the similarity between the buggy solution and the human fix as a baseline, we evaluate the quality of LLM-generated bug fixes on 3 OpenAI GPT models (gpt-5-nano, gpt-5-mini, gpt-5.1). We check if the generated solutions solve the problem by using the Codeforces-R1 dataset, an openly available dataset that has tests generated with the DeepSeek-R1 model. Our findings suggest that LLMs tend to modify more lines than necessary compared to human fixes and, in some cases, generate entirely new solutions. We also observe that LLMs solve more problems correctly when allowed to generate solutions from scratch rather than patch buggy submissions, even when those submissions are close to the human patch. This has important implications for the design of AI-assisted programming tools, particularly in supporting user debugging processes and promoting incremental problem-solving strategies rather than solution replacement.

# 论文总结：面向编程的大语言模型——是在真正修复，还是在重新实现错误代码？

## 1. 核心问题与整体含义（研究动机与背景）

- **研究空白**：现有工作多将 LLM 的"问题求解能力"（从零生成正确解法）与"缺陷修复能力"（对有 bug 代码打补丁）分开独立评估，二者之间的关系尚未被系统探讨。
- **核心问题**：当给 LLM 一份有 bug 的竞赛编程提交并要求"修 bug"时，它是像人类调试者那样做**局部、最小化的编辑**，还是倾向于**丢弃原解、从头重写**？
- **实践意义**：AI 编程辅助工具正日益嵌入迭代式开发流程，保留用户意图与代码结构往往与产出正确解同样重要。若工具系统性地"替换"而非"修复"代码，将削弱调试学习过程、破坏代码审查与遗留系统维护。
- **研究问题（RQ）**：
  - RQ1：给定有 bug 提交，LLM 在修复时多大程度保留用户原有结构？
  - RQ2：模型更擅长"从零生成正确解"还是"修复 bug"？
  - RQ3：结构保留程度与正确修复能力之间是否存在关系？

## 2. 方法论

### 核心思想
以**人工修复（anchor 锚点）与 buggy 提交之间的相似度**为基线，衡量 LLM 生成修复对原代码的偏离程度，并用测试通过率验证其正确性，从而区分"真正修复"与"变相重写"。

### 数据集构建流程
- 收集 7 位 Codeforces 用户约 **3000 份提交**（2015–2025），按时间倒序排列同一问题的多次提交。
- 贪心策略确定**锚点（Accepted 提交）**：遇到 Accepted 提交即新建锚点，将后续提交挂载其上，直到下一个 Accepted 出现。
- 处理三类实际情况：① 同一问题多个 Accepted（拆分为多锚点）；② buggy 提交之间高度相似（可作为一致性检验）；③ buggy 与锚点差异过大（重写）。
- **过滤阈值 60%**：仅保留与正确解相似度 ≥ 60% 的 buggy 提交，避免把"另起炉灶"的替代解误判为修复。
- 预处理后剩余 **567 对〈锚点, buggy 提交〉**。约 600 份无锚点、约 700 份问题不在 Codeforces-R1 中、约 900 份因相似度阈值被剔除。

### 关键技术细节与公式
- **相似度（Jaccard 指数）**：给定两段源码 $s_1, s_2$，用 Diff 工具求删除行数 $d$、新增行数 $a$，公共行数 $c = n - d$，则
  $$\text{sim}(s_1, s_2) = \frac{c}{d + c + a}$$
  计算前去除空白、制表符、空行与注释。
- **相似度比率（Similarity Ratio）**：
  $$\text{sim\_ratio} = \frac{\text{sim}(s_b, s_g)}{\text{sim}(s_b, s_a)}$$
  其中 $s_b$ 为 buggy 代码，$s_g$ 为 LLM 生成修复，$s_a$ 为人工锚点。$\text{sim\_ratio} < 1$ 表示不如人工修复保守；$> 1$ 表示比人工修复更保守（人工可能改动过多）。相比已有工作（如 Dai 等定义的一致性率 $r/k$），本指标**额外惩罚被删除的行**。
- **测试通过（Test Pass）**：$\text{TP}(s) = \prod_{i=1}^{n} \mathbb{1}[\hat{t}_k = t_k]$，用指示函数而非通过率，强调是否完全解决问题。

### 三种提示策略
1. **NaiveBugFix**：简单提示，要求尽量少地增删改行来修 bug，不得整体重写。
2. **GenerateScratch**：直接从零生成解法（无 bug 修复环节），作为 sim_ratio 下界与性能参照。
3. **GEPABugFix**：以 NaiveBugFix 为起点，用 **GEPA**（Genetic-Pareto 反思式提示进化）优化提示。奖励函数为
   $$\text{reward} = \text{pass} \times \min(1, \text{sim\_ratio})$$
   即未修复则返回 0，修复成功则返回（截断到 1 的）相似度比率。

- 使用 **DSPy** 框架定义提示，采用 **Predictor 模块**而非 ChainOfThought（模型本身已具内部推理），每模型限制 32k tokens，中等推理强度。

## 3. 实验设计

- **数据集 / 场景**：
  - 自建 Codeforces 用户提交数据集（约 3000 份原始，567 对预处理后样本）。
  - **Codeforces-R1** 数据集提供问题描述与测试用例（含 DeepSeek-R1 生成的测试），用于验证生成解是否正确。
- **Benchmark**：以"是否通过全部 Codeforces-R1 测试"作为正确性标准；以"与人工锚点的相似度"作为结构保留标准。
- **对比方法**：3 种提示方法（NaiveBugFix、GenerateScratch、GEPABugFix）× 4 种模型配置（gpt-5-nano、gpt-5-mini、gpt-5.1-no-reasoning、gpt-5.1）。
- **数据划分**：按**问题**（而非提交）划分 3 折——训练 15%、验证 15%、测试 70%，以避免数据泄漏；训练与验证用于 GEPA 提示优化。
- **结果分组**：按基线相似度区间分组统计（[0.6–0.7)、[0.7–0.8)、[0.8–0.9)、[0.9–1]），观察不同"bug 局部性"下的表现差异。

## 6. 主要结论与发现

- **RQ1（结构保留）**：模型能力越强，sim_ratio 越高。在低相似度区间，GEPABugFix 与 NaiveBugFix 甚至比人工修复更保守（sim_ratio > 1）；但在高相似度区间（如 [0.9–1]），GEPA（0.93）与 NaiveBugFix（0.83）差距明显，说明简单提示下模型会改动与 bug 无关的多余代码。推理能力对 sim_ratio 影响不大（仅 [0.7–0.8) 区间的 NaiveBugFix 例外）。GenerateScratch 的 sim_ratio 不为 0（约 0.09–0.15），因库函数与程序骨架存在共性。
- **RQ2（生成 vs 修复）**：LLM **从零生成解比修 bug 更容易解出更多问题**。gpt-nano 上修 bug 比从零生成低约 0.15；模型能力提升能提高绝对分数，但不总能缩小两任务差距（如 [0.6–0.7)、[0.8–0.9) 区间）。推理能力对解题率影响显著（5.1-no-reasoning 分数明显偏低）。
- **RQ3（结构保留 vs 正确性）**：GEPABugFix 的 sim_ratio 更高，但**解题率反而更低**——强制最小改动会让模型"只顾结构、忽略真正修好问题"。用户因此面临两难：要么接受更局部但更可能错误的补丁，要么接受正确但偏离原结构的重写。
- **总体结论**：LLM 更擅长从零生成而非最小化修复；越复杂的"少改动"提示会提升结构一致性却损害正确性。这提示 AI 辅助调试工具应**根据修复规模自适应地调节约束强度**（仅在改动小时强制最小编辑），而非一味追求最小补丁或整体替换。

## 7. 优点

- **问题新颖且贴近实践**：首次系统对比 LLM"修复"与"重写"行为，填补了"解题能力 vs 修 bug 能力"关系的研究空白。
- **数据构建巧妙**：利用同一用户对同一问题的历史提交序列，自然获得〈buggy, 人工修复〉配对，并引入 60% 阈值区分"修复"与"重实现"。
- **指标设计更严格**：基于 Jaccard 的 sim_ratio 相比已有的一致性率 $r/k$，额外惩罚删除行，更能反映"对用户意图的偏离"。
- **正确性验证可靠**：使用执行式测试（Codeforces-R1 测试）而非 n-gram 指标，避免表面相似但逻辑错误的问题。
- **实验控制规范**：按问题划分数据集防泄漏；对比多种提示策略与模型能力层级；引入 GEPA 提示优化与奖励函数设计合理。
- **可复现性强**：代码、数据集、GEPA 模型全部开源，Docker 环境保证一致性。

## 8. 不足与局限

- **数据规模与覆盖有限**：仅 567 对样本、7 位用户，且多为 C/C++ 竞赛编程场景，结论向通用软件开发（多语言、大型工程、非算法类 bug）外推需谨慎。
- **数据污染风险**：Codeforces 题目很可能出现在 LLM 训练数据中，作者虽称关注点不在新题求解，但仍可能影响解题率结果。
- **模型范围窄**：仅评估 OpenAI 家族的 3–4 个 GPT 模型，未涉及其他厂商模型（作者列为未来工作）。
- **人工修复基线未必最优**：锚点代表"用户自己的修复"，可能包含冗余改动，导致 sim_ratio > 1 的解释存在歧义。
- **阈值主观性**：60% 相似度阈值是启发式选择，可能引入样本选择偏差。
- **测试用例质量依赖**：Codeforces-R1 的测试由 DeepSeek-R1 生成，可能存在遗漏或误判，论文未做交叉验证。
- **算力信息缺失**：未报告 GPU 型号/数量/时长，仅给出 token 消耗与费用，不利于资源复现评估。
- **应用限制**：结论主要适用于"最小化修复"场景；对允许重构或明确要求重写的任务，结论未必适用。

## 摘要
在目标与评估标准确定后，编码智能体和进化式代码搜索系统能够改进实现。将这些方法应用于现有软件仓库时，会引出一个更早的问题：对于某个高层工程目标，哪些实现选择值得研究？我们提出“优化机会发现”（optimization-opportunity discovery），这是一项仓库级任务，旨在识别候选源代码区域、解释它们与目标的关系，并提出可能的修改。该任务以软件仓库、工程目标以及可选的运行时证据（如离线遥测观测或性能剖析）为输入。它不要求用户指定缺陷、瓶颈或代码位置。我们提出 Spotlights，一个通过逻辑仓库映射、连续智能体评审以及可选的将候选与相关技术关联的研究来完成该任务的系统。我们在模型服务、文档检索、区块链排序和文档处理场景中评估 Spotlights。在三个案例中，它找回了九个专家选定的目标中的七个。在可靠性研究中，排名前十的候选中有 70% 满足所声明的正确性和严重性阈值。在五次重复检索运行中，73.6% 的候选出现项在全部五次运行中都有匹配的源代码区域。Spotlights 还重新发现了一个被留出的检索优化目标，并将其与相关的分块（tiling）技术联系起来。在一项实现研究中，一个被发现的修改将端到端页面处理运行时减少了 10.6%，同时保持了所测得的输出质量。这些结果确立了优化机会发现是介于宽泛工程目标与后续实现和验证之间的一个独特且可实证评估的步骤。

## Abstract
Coding agents and evolutionary code-search systems can improve implementations once a target and evaluation criterion have been specified. Applying these methods to an existing software repository raises an earlier question: which implementation choices are worth investigating for a high-level engineering objective? We introduce \emph{optimization-opportunity discovery}, the repository-level task of identifying candidate source regions, explaining how they relate to the objective, and proposing possible changes. The task takes as input a repository, an engineering objective, and optional runtime evidence such as offline telemetry observations or profiles. It does not require the user to specify a defect, bottleneck, or code location. We present \emph{Spotlights}, a system that performs this task through logical repository mapping, successive agent reviews, and optional research linking candidates to relevant techniques. We evaluate Spotlights across model serving, document retrieval, blockchain ordering, and document processing. Across three cases, it recovers seven of nine expert-selected targets. In the reliability study, 70\% of the top ten candidates meet the stated correctness and severity thresholds. Across five repeated retrieval runs, 73.6\% of candidate occurrences have a matching source region in all five runs. Spotlights also rediscovers the target of a withheld retrieval optimization and connects it to a relevant tiling technique. In an implementation study, a discovered change reduces end-to-end page-processing runtime by 10.6\% while preserving measured output quality. These results establish optimization-opportunity discovery as a distinct and empirically evaluable step between a broad engineering objective and subsequent implementation and validation.

- **任务定义**：论文提出 **“优化机会发现”（optimization-opportunity discovery）**，即仓库级任务：识别候选源代码区域、解释其与工程目标的关系、并提出可能的修改。
- **输入与输出**：输入为仓库、工程目标、可选运行时证据（离线遥测、性能剖析）；输出为一组候选，每个候选包含源位置、现状、理由（rationale）、预估影响（高/中/低）及若干提案。
- **整体含义**：作者主张，机会发现是连接“宽泛工程目标”与“后续实现与验证”之间的**独立且可实证评估的步骤**，使自动化改进流程多了一个可检查、可度量的中间产物。

## 2. 方法论

### 核心思想
以逻辑模块地图为导航，让多个编码智能体交替进行源码审查，迭代生成/修订/删除候选，并可选用外部研究把提案与相关技术关联起来。

### 关键技术细节

- **逻辑仓库映射（Logical Repository Mapping）**
  - 映射智能体分析目录、导入、清单、文档和代表性源文件，构建**逻辑模块**（职责相关的一组代码），作为分析单元。
  - 每个模块记录：角色、路径、代表性文件、依赖关系。
  - 模块可含子模块，分析在所选模块的最细粒度上进行；该地图**与工程目标无关**，可跨目标复用。

- **候选发现与迭代审查（Candidate Discovery and Iterative Review）**
  - 每个被选模块由一个编码智能体处理，接收模块条目、仓库上下文、工程目标及可选上下文。
  - 智能体从代表性文件出发，寻找可改动的实现选择，要求给出：合理的改进机制、具体源位置、行为验证方式（如已有测试或预期输出）。
  - 多轮审查：智能体交替工作，每轮可**新增、修订或删除**候选；编排层校验字段、文件归属与行范围，并跨修订保持标识符稳定。
  - 模型、推理参数、预算与审查轮数均可配置。

- **提案与技术研究（Proposals and Technical Research）**
  - 提案智能体基于模型知识为每个候选提出改动。
  - 可选研究阶段检索论文、文档与相关实现，收集有来源支撑的技术描述；再由提案智能体判断该技术是否适用于候选位置，并描述所需改动。
  - 输出为结构化 JSON 与可读报告；模块内排序规则为：**按来源可溯源的提案数量降序，再按标识符**。

- **形式化描述**：发现过程可表示为 `D(R, o, h, S) → C`，其中 R 为仓库快照，o 为工程目标，h 为可选上下文，S 为分析范围，C 为候选集合。用户只需指定工程问题与搜索范围，无需枚举候选位置。

## 6. 主要结论与发现

- **可发现性**：Spotlights 能在四个领域中识别出技术上合理的改进机会（如缓存复用、请求路由、交易验证等决策点）。
- **专家目标恢复**：三个案例共 9 个专家目标中恢复 **7 个**；llm-d 恢复 5/7（Top-10 内 2 个、Top-20 内 3 个）；WVA 的饱和分析器排名第 4；vLLM 缓存管理器分发逻辑排名第 57。
- **候选质量**：Fabric-X 中 **Precision@10 = 0.70**，Precision@20 = 0.45。
- **再发现能力**：在 FlashMaxSim 方案被留出的情况下，系统定位到 MaxSim 计算，并将其与 FlashAttention 的**分块（tiling）**技术关联。
- **稳定性**：5 次 ColPali 运行中，**73.6%（209/284）** 的候选出现项在全部 5 次运行中都有重叠源区域；限制到共享覆盖范围后为 **79.5%（209/263）**。但影响标签稳定性较弱：41 个跨 5 次运行的组中仅 **36.6%** 标签完全一致，**82.9%** 至少 4 次一致。
- **审查与研究的作用**：vLLM 子集中，审查新增 32 个候选、修订 78 个；43.8% 的候选有来源可溯源提案。
- **实现效果**：IOCR 中被选候选（模型加载配置，启用 CPU 内存 arena、调整线程设置）使中位运行时间从 150.970s 降至 135.026s，**降低 10.6%**，字符准确率保持 **95.53%** 不变（运行时比 0.8944，双标准误区间 [0.8818, 0.9070]）。
- **总体主张**：优化机会发现是**独特且可实证评估**的步骤，其候选质量、可见性（排名）与可重复性是三个彼此独立的属性。

## 7. 优点

- **任务定义清晰且有价值**：首次把“从高层目标出发发现值得改的实现选择”明确为可评估的仓库级任务，并给出候选的结构化 schema（位置、理由、影响、提案）。
- **流程设计合理**：逻辑模块映射与目标解耦、可复用；多智能体交替审查支持增/改/删，编排层做一致性校验，工程上较稳健。
- **评估维度多元**：同时衡量候选质量、专家目标恢复、再发现能力、跨运行稳定性与成本，避免单一指标偏颇。
- **闭环验证**：IOCR 案例从候选一路走到实现与测量（10.6% 加速且质量不降），比纯离线评估更有说服力。
- **诚实的负面/中性发现**：明确报告“位置可复现但影响标签不稳定”“高正确性低严重性候选会被排除”等细节，附录给出完整的候选级评分与逐对来源重叠数据，可复现性较好。
- **成本剖析细致**：拆分各阶段成本占比，指出“提案生成”是主要开销，为后续成本优化指明方向。

## 8. 不足与局限

- **实验覆盖有限**：参考目标集较小（vLLM recall 仅 1 个、WVA 仅 1 个、llm-d 7 个），召回率结论的统计效力有限。
- **缺少对照方法**：未与 POLO、PerfAgent、EffiHolmes、Beyond Local Code Optimization 等做同条件实验，方法相对优势缺乏直接证据。
- **评估偏差风险**：质量评分依赖 LLM listwise judge，可能存在位置偏差与阈值敏感性；作者自己也指出命中/排除受严重性阈值影响明显。
- **排名与排序问题**：相关目标可能出现在很靠后的位置（如 vLLM 第 57 名、llm-d 第 54/66 名），实际使用中审查成本高；论文也承认“找到”与“低成本找到”是两回事。
- **稳定性局限**：模块地图粒度与覆盖范围在重复运行间存在差异（排除 21 个共享覆盖外的出现项后结果从 73.6% 变为 79.5%），影响标签一致性仅 36.6%，说明可复现性在“位置”层面较好、在“判断”层面较弱。
- **应用限制**：系统依赖外部大模型 API，成本与耗时较高（单次约 4–5 小时、上百美元）；结果受模型版本与提示配置影响，工程落地需考虑可复现性与保密性。
- **实现验证单一**：仅 IOCR 一个案例走到实测，且只验证了一个候选；其余候选的实际收益未经端到端验证。
- **无训练算力信息**：论文未报告 GPU 型号/数量等硬件算力细节，仅给出 API 成本，难以评估方法在大规模场景下的资源需求。

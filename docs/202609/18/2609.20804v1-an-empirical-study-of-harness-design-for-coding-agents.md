## 摘要
编码智能体运行框架塑造了自主编码智能体将模型能力转化为长时程软件工程性能的方式，但现有工作通常将运行框架作为单体系统进行评估，导致各单独组件的有效性仍不明确。为实现组件级比较，我们使用一个轻量级编码智能体运行框架研究这一问题：其执行循环保持不变，而变化三个组件：规划、动作空间和上下文管理。我们在 SWE-Bench Verified 和 Terminal-Bench 2.1 上对四个模型进行评估，共评估 176 个匹配设置，涵盖五种上下文管理策略、四种上下文窗口预算，以及对规划和动作空间的针对性消融。我们发现：(1) 随着上下文窗口预算收紧，上下文管理变得愈发有价值，其大部分收益来自防止上下文溢出失败。(2) 在上下文管理策略中，先进行基于规则的省略，再进行基于 LLM 的摘要，总体效率最高；而让被省略内容可恢复会增加模型很少使用的机制，且不带来准确率提升。(3) 规划从为较弱模型提供准确率支撑，转变为为较强模型节省成本，准确率变化很小。(4) 预定义工具能提升 bash 熟练度较弱的模型的表现，而具备 bash 能力的模型可以仅使用 bash 接口有效运行，并实现显著更低的成本，尤其是在以命令行为中心的任务上。轨迹级分析解释了这些效应：上下文管理延长了执行轨迹，但未显著改变智能体行为；规划改变了轨迹停止的位置；动作空间改变了代码写入的粒度。这些发现为模型感知和预算感知的运行框架设计提供了依据，并为评估未来运行框架组件提供了模块化框架。

## Abstract
Coding harnesses shape how autonomous coding agents translate model capabilities into long-horizon software-engineering performance, yet existing work typically evaluates harnesses as monolithic systems, leaving the effectiveness of individual components unclear. To enable component-level comparisons, we study this question with a lightweight coding harness whose execution loop is fixed while three components are varied: planning, action space, and context management. Across four models evaluated on SWE-Bench Verified and Terminal-Bench 2.1, we evaluate 176 matched settings spanning five context-management strategies, four context-window budgets, and targeted ablations of planning and action space. We find that: (1) Context management becomes increasingly valuable as the context-window budget tightens, with most of its benefit coming from preventing context-overflow failures. (2) Staging rule-based elision before LLM-based summarization provides the strongest overall efficiency among the context-management strategies, whereas making elided content recoverable adds machinery that models rarely use and yields no accuracy gain. (3) Planning shifts from an accuracy scaffold for weaker models to a cost saver for stronger models, with little change in accuracy. (4) Predefined tools improve performance for models with weaker bash proficiency, whereas bash-capable models can operate effectively with a bash-only interface and achieve substantially lower cost, especially on command-line-centric tasks. Trajectory-level analysis explains these effects: context management extends execution trajectories without substantially altering agent behavior, planning changes where trajectories stop, and the action space changes the granularity at which code is written. These findings inform model- and budget-aware harness design and provide a modular framework for evaluating future harness components.

# 论文总结：面向编码智能体的运行框架设计实证研究

## 1. 核心问题与整体含义

- **背景**：LLM 正被广泛用于自主解决真实软件工程任务（如关闭 GitHub issue、完成端到端终端任务）。其表现不仅取决于模型本身，还高度依赖 **coding harness**——即包裹模型的软件层，包括控制循环、工具接口与上下文管理策略。
- **核心问题**：已有研究通常把 harness 当作**单体系统**评估（如 OpenHands vs. SWE-Agent），导致无法判断性能差异究竟来自规划、工具设计、上下文管理还是它们与模型的交互。论文由此提出：**各 harness 组件是普遍有效，还是其效果取决于模型能力、任务类型与资源预算？**
- **研究意义**：通过组件级消融，揭示各干预的**条件效应**，为模型感知与预算感知的 harness 设计提供可迁移的诊断依据，而非追求一个普适最优的 harness。

## 2. 方法论

- **核心思想**：构建一个轻量级 harness，**固定执行循环（ReAct 循环：推理→动作→观察）**，仅变化三个组件：**规划、动作空间、上下文管理**；其余组件（权限控制、编辑后诊断、卡死检测）保持不变，以隔离每个干预的效果。
- **规划（Planning）**：
  - 启用时，通过系统指令定义协议、首轮提醒要求先制定计划，并暴露 `update_plan` 工具维护显式任务计划。
  - 计划每轮注入模型输入，但**不存入对话历史**，避免历史膨胀。
  - 关闭时移除全部规划指令、提醒、计划注入与工具。
- **动作空间（Action Space）**：
  - **预定义工具集**：`read_file`、`write_file`、`edit_file`、`list_files`、`glob_files`、`grep_text`、`web_fetch`、`bash`，各带类型化参数 schema 与自然语言描述。
  - **纯 bash 接口**：移除预定义文件/搜索/Web 工具，仅保留 `bash` 进行通用环境交互。
  - 该干预同时改变工具可用性、接口提示、文件状态跟踪与自动诊断，因此解释为**完整动作接口的效应**，而非单纯工具数量或粒度。
- **上下文管理（Context Management）**：三种可组合机制 + 两级阈值：
  - **M1 省略（Elision）**：将陈旧的工具观察体替换为短存根。
  - **M2 召回（Recall）**：将被省略观察存入外部存储，通过 `recall_event(id)` 按需恢复，使省略可逆。
  - **M3 摘要（Summarization）**：将较旧消息折叠为运行中的自然语言摘要（由同一模型的无工具调用生成）。
  - **算法流程（Tier 4）**：保留前言（系统提示+任务描述）和预算内最近窗口（至少两轮）逐字不变；当 token 数 ≥ 软阈值 B₁ 时，对中间区域的 bulky 工具观察执行 M1+M2；若仍 ≥ 硬阈值 B₂，则对最旧的中间事件执行 M3。五个策略层级：T0（无管理）、T1（仅 M1）、T2（M1+M2）、T3（仅 M3）、T4（M1+M2+M3，默认）。

## 3. 实验设计

- **数据集 / Benchmark**：
  - **SWE-Bench Verified**：500 个经人工验证的真实 GitHub issue，测试仓库级问题修复。
  - **Terminal-Bench 2.1**：89 个端到端命令行任务，测试终端任务完成能力。
- **评估模型**：Nemotron-3 系列的 30B、120B、550B（同家族能力轴），外加 Mistral-Medium-3.5-128B（跨家族对比）。
- **对比设置**：
  - 上下文管理：T0–T4 五种策略 × 四种上下文窗口预算（32k、64k、96k、128k）。
  - 规划消融：T4/128k 下 planning on vs. off。
  - 动作空间消融：T4/128k 下全工具集 vs. 纯 bash。
  - 每个模型–基准对共 22 个设置，总计 **176 个实验设置**。
- **指标**：任务成功率（SR）与每任务平均成本（按 OpenRouter 价格折算）。
- **统计方法**：任务配对的双侧精确 McNemar 检验，并用 Benjamini–Hochberg 控制 FDR 于 0.05。
- **轨迹分析**：用 LLM 法官对轨迹逐轮/逐动作标注（SWE-Bench 五阶段：Localize/Reproduce/Fix/Verify/Other；Terminal-Bench 十动作符号归为四阶段），并经三人人类标注验证（整体一致率约 94.2%，加权 Cohen's κ ≈ 0.929）。

## 4. 资源与算力

- 论文提到模型以 **SGLang 在 BF16 精度下本地服务**，温度 0、top-p 0.95、每轮输出上限 16,384 tokens；harness 基于 LangGraph，任务容器由 Harbor 驱动，每任务最多 300 步。
- **未明确说明**使用的 GPU 型号、数量、训练时长或总计算量。论文仅在致谢中提及部分工作是在 Zoom Video Communications 实习期间完成。
- 成本按 OpenRouter 定价估算（如 Nemotron-3-30B $0.05/$0.20，Mistral-Medium-3.5 $1.50/$7.50 每百万输入/输出 token），但这是推理成本而非训练算力。

## 5. 实验数量与充分性

- **规模**：共 176 个匹配设置（4 模型 × 2 benchmark × 22 设置），涵盖 5 种上下文管理策略、4 种窗口预算，以及规划与动作空间的针对性消融。
- **充分性**：
  - 上下文管理维度覆盖较充分，跨模型规模与窗口预算做了系统扫描。
  - 轨迹级分析覆盖了行为阶段、终止阶段、动作粒度、召回使用率等，提供了机制性证据。
  - 使用配对统计检验并控制 FDR，增强了比较的客观性。
- **不足**：
  - 规划与动作空间**仅在 T4/128k 默认配置下消融**，未做全因子设计，无法确定其效应在其他组件组合或窗口预算下是否持续。
  - 每个任务仅运行一次，且 Terminal-Bench 仅 89 个任务，导致许多对比未达统计显著，结论依赖跨模型/跨预算方向的一致性。
  - SWE-Bench Verified 仅含 Python 任务，外部效度受限。
  - 模型规模只是能力的不完美代理，训练差异、工具接口先验暴露、原生 shell 熟练度等也可能影响趋势。

## 6. 主要结论与发现

- **上下文管理在预算收紧时价值最大**：
  - managed（T1–T4）与 T0 的成功率差距随窗口扩大而收窄：SWE-Bench 上从 32k 的 35.7pp 降至 128k 的 2.7pp；Terminal-Bench 从 9.5pp 降至 2.8pp。
  - 收益主要来自**防止上下文溢出导致的提前终止**：T0 溢出率从 32k 的 78.7% 降至 128k 的 8.7%，而所有 managed 层级溢出失败为零。
- **T4（先规则省略再 LLM 摘要）效率最佳**：
  - 在八个模型–基准面板中的七个取得最低成本，准确率与 T1–T3 相当。
  - 早期省略减少了昂贵的 LLM 摘要调用次数，峰值上下文控制最好。
- **召回（M2）极少被调用且无准确率增益**：
  - 64 个 T2/T4 设置中 36 个（56.3%）从未调用 `recall_event`；调用率随窗口扩大迅速降至接近零。
  - T2 与 T1 的配对比较平均差异仅 −0.36pp，说明无损存储增加了模型很少使用的机制。
- **规划的角色随能力变化**：
  - 对弱模型（Nemotron-3 30B）：提升成功率（SWE-Bench +11.6pp，Terminal-Bench +4.5pp），但成本上升；轨迹中位长度从 5 轮增至 40 轮，防止过早终止。
  - 对强模型（550B、Mistral）：主要**节省成本**（SWE-Bench 成本降约 30%–32%），准确率小幅下降；轨迹缩短主要来自减少冗余的编辑后验证。
  - 中等能力模型（120B）效果依任务类型而定。
- **动作空间的效果取决于 bash 熟练度与任务类型**：
  - 预定义工具对弱模型（30B）显著提升成功率（SWE-Bench +15.0pp，Terminal-Bench +10.1pp），因其提供了可靠的动作词汇。
  - 强模型（550B）在纯 bash 下成功率更高（SWE-Bench +3.6pp，Terminal-Bench +5.6pp）且成本降低 53%/30%，因为可将多个低层操作组合为复合命令。
  - Mistral 呈现任务类型依赖的交叉：SWE-Bench 上全工具集更好（+23.2pp），Terminal-Bench 上纯 bash 更好（+6.7pp），反映后者更以 shell 为中心。
- **轨迹级机制**：
  - 上下文管理**延长执行轨迹**而不显著改变行为阶段比例，主要用于在窗口紧张时让轨迹推进到编辑与验证。
  - 规划**改变轨迹停止位置**：弱模型靠它撑过首次编辑，强模型靠它削减冗余验证。
  - 动作空间**改变代码写入粒度**：纯 bash 下重复补丁减少、单次创建/替换比例上升、编辑尺寸依模型而异。

## 7. 优点

- **组件级消融设计**：固定执行循环与其余组件，使每个干预的条件效应可被单独估计，克服了以往单体评估的归因困难。
- **跨模型规模 × 跨上下文预算的系统扫描**：同时覆盖同家族三档规模与跨家族模型，并显式操纵上下文窗口预算，刻画了效应随资源约束的变化。
- **轨迹级解释性分析**：不止报告成功率与成本，还用 LLM 法官（经人类验证）将效应追溯到具体行为变化（轨迹长度、终止阶段、动作粒度），增强了结论的机制可信度。
- **统计严谨性**：采用任务配对 McNemar 检验与 BH 校正，降低了多重比较的假阳性风险。
- **实用性与可迁移性**：提出的模块化 harness 与“模型感知、预算感知”的设计原则，对未来 harness 组件的评估具有参考价值；T4 的“先廉价省略、再选择性摘要”策略可直接落地。

## 8. 不足与局限

- **实现特异性**：规划仅用一套提示与更新机制，上下文管理仅用一套阈值策略，动作空间是捆绑式接口变更（工具可用性+提示+状态跟踪+诊断），无法隔离单一因素（如工具数量或动作粒度）。
- **实验覆盖有限**：规划与动作空间仅在 T4/128k 下消融，缺乏全因子设计；每个任务仅运行一次；Terminal-Bench 仅 89 个任务，统计功效不足，部分结论依赖方向一致性而非显著单元格。
- **外部效度受限**：仅研究 Nemotron-3 三档与 Mistral-Medium-3.5-128B，SWE-Bench Verified 仅 Python；模型规模只是能力的不完美代理，训练差异、工具接口先验、原生 shell 熟练度等混杂因素可能影响趋势。
- **成本与算力信息不透明**：未报告 GPU 型号、数量或训练时长，成本仅为推理价格估算。
- **偏差风险**：LLM 法官虽经人类验证，但标注仍可能存在系统偏差；召回机制的低使用率也可能受具体提示与工具描述影响，未必推广到其他实现。
- **应用限制**：交叉点（如强模型偏好纯 bash、弱模型偏好预定义工具）在迁移到其他模型家族、其他 harness 实现或非软件工程任务前，需重新验证。

## 摘要
用于代码补全的大型语言模型（LLM）可能会生成已弃用的 API，因为其预训练语料中包含历史库版本的代码。现有方法采用推理时干预、模型编辑或机器遗忘，但多种合理的补全使预定义替换过于受限。此外，现有研究很少验证模型是否表现出目标已弃用行为，也很少评估对其他 API 的非预期改变。我们对已弃用 API 知识的机器遗忘进行了系统性实证研究，并构建了 MUDAPIBench，这是一个基于行为的基准，包含来自八个 Python 库中 145 个已弃用 API 到最新 API 映射的 7,000 多个模型特定实例。仅当原始模型生成目标已弃用 API 时才保留实例。我们在三个代码 LLM 上评估了八种代表性遗忘方法，涉及已弃用 API 遗忘、最新 API 生成、其他及无关 API 行为的保持、通用代码生成能力和效率。结果表明，梯度差分（GD）提供了最佳的总体权衡，在抑制已弃用 API 的同时以中等计算成本保持其他能力。进一步分析揭示了不同库之间存在显著差异，并表明在模型训练数据截止时间之后被弃用的 API 更难遗忘。逐层分析表明，GD 在实现有效遗忘的同时，内部变化相对可控。

## Abstract
Large language models (LLMs) for code completion may generate deprecated APIs because their pre-training corpora contain code from historical library versions. Existing approaches use inference-time intervention, model editing, or machine unlearning, but multiple plausible completions make predefined replacements restrictive. Moreover, existing studies rarely verify whether models exhibit the targeted deprecated behavior or evaluate unintended changes to other APIs.   We conduct a systematic empirical study of machine unlearning for deprecated API knowledge and construct MUDAPIBench, a behavior-grounded benchmark with over 7,000 model-specific instances derived from 145 deprecated-to-up-to-date API mappings across eight Python libraries. Instances are retained only when the original model generates the target deprecated API. We evaluate eight representative unlearning methods across three code LLMs on deprecated API forgetting, up-to-date API generation, preservation of other and unrelated API behaviors, general code-generation capability, and efficiency.   Results show that Gradient Difference (GD) provides the best overall trade-off, suppressing deprecated APIs while preserving other capabilities with moderate computational costs. Further analyses reveal substantial variation across libraries and show that APIs deprecated after the model's training-data cutoff are harder to forget. Layer-wise analyses indicate that GD achieves effective forgetting with comparatively controlled internal changes.

# 论文总结：面向大型语言模型中已弃用 API 知识的机器遗忘

## 1. 核心问题与整体含义（研究动机与背景）

- **现实背景**：现代软件开发高度依赖第三方库的 API，而库在演进过程中会不断弃用旧 API 并推荐新的替代 API（up-to-date API）。LLM 的预训练语料包含大量按历史库版本编写的代码，因此模型可能持续生成已弃用的 API。例如 Wang 等报告 GPT-3.5 生成的 API 调用中有 37.4% 属于已弃用 API。
- **现有方法的局限**：
  - **推理时干预**（如 REPLACEAPI）：检测到弃用 API 后替换并重新调用模型，但不改变模型内部知识，且引入额外延迟与 token 消耗。
  - **模型编辑**（如 AdaLoRA-L）：把 API 演进建模为定向替换问题，将最新的 API 作为预定义的编辑目标，可能过度收窄补全空间。
  - **现有机器遗忘研究**：遗忘数据多来自预定义样本，未系统验证目标模型是否真的表现出对应的弃用行为；评估主要依赖 HumanEval 等通用基准，缺乏对"其他 API 行为"和"无关 API 行为"是否被非预期改变的考察。
- **核心洞察**：代码补全具有**多解性**（implementation diversity 与 intent diversity）。同一高层编程意图可由不同 API 和代码结构实现，因此抑制某个弃用 API 不应要求模型总是生成某个预定义的最新替代，而应聚焦于"移除不应再生成的弃用行为"。
- **整体含义**：论文将弃用 API 适配重新表述为**机器遗忘问题**——目标是降低弃用补全的条件概率 P(y_d|x)，而非强制指定唯一目标；成功标准不仅是遗忘，还包括对最新 API、其他 API、无关 API 及通用代码生成能力的保持。

## 2. 方法论：核心思想与关键技术细节

- **核心思想**：以"行为化"方式构建模型专属的遗忘基准，并用多维度指标系统评测不同遗忘范式在"遗忘—保持"之间的权衡。
- **任务定义**：
  - 设原始模型为 f0，遗忘后模型为 fu；每条实例为三元组 M = (x, y_d, y)，其中 x 为补全提示，y_d 为原始模型生成的弃用 API 补全，y 为对应的最新 API 补全。
  - 三条准则：**有效性**（fu(x) ≠ y_d）、**泛化性**（对未见上下文 x_g 同样抑制 y_d）、**特异性**（对无关输入 x_s 保持 fu(x_s) = f0(x_s)）。
- **MUDAPIBench 构建流程**（三步）：
  1. **代码补全提示收集**：采用 Wang 等的 145 组已验证弃用→最新 API 映射，覆盖 8 个 Python 库；用 Sourcegraph 检索含最新 API 调用的开源仓库函数，共获得 65,596 个候选函数，将目标 API 调用之前的代码作为提示 x。
  2. **模型专属过滤**：对每个候选提示，用温度 0.8 采样 5 个补全；仅当目标弃用 API 出现在至少一个补全中时才保留该实例——确保遗忘目标在原始模型中可观测，但不要求其主导所有补全。
  3. **数据准备**：
     - **Forget Data 与 Generalization Data**：来自同一过滤实例池，按 API 映射随机对半划分为不相交子集，一半用于遗忘训练，另一半留出评估泛化。
     - **Retain Data**：复用原始模型 5 个补全，统计非弃用 API 的出现频率，选取出现频率最高的非弃用补全作为保持约束。
     - **Specificity Data**：从 The Stack v2 随机采样 10 万个 Python 文件，用 CodeBERT 嵌入检索与 Forget 输入语义最相似、但不含目标 API 对的前 5 个非目标输入，记录原始模型的确定性补全作为参照。
- **评测的八种遗忘方法**（按机制分五类）：
  - **梯度优化**：GA（对遗忘数据做梯度上升）、GD（梯度上升 + 对 Retain Data 梯度下降）。
  - **分布正则**：KL（对 Retain Data 施加 KL 散度约束）。
  - **随机监督**：RLFT（用无关标签随机替换弃用补全）。
  - **偏好优化**：DPO（以"I don't know"为偏好响应）、NPO（负偏好优化，抑制对弃用补全的相对偏好）、SimNPO（去除参考模型依赖）。
  - **目标分布**：PROD（移除最高概率的弃用 token 并将概率质量重分配）。
- **参数高效实现**：所有方法均采用 LoRA（rank=16, α=32, dropout=0.05），应用于 q/k/v/o_proj 及 gate/up/down_proj，统一训练 5 个 epoch。

## 3. 实验设计

- **基准**：MUDAPIBench，含 7,000+ 模型专属遗忘实例，源自 8 个 Python 库的 145 组弃用→最新 API 映射（模型过滤后保留 81 个唯一 API 对）。
- **数据规模**（表 1）：
  - Forget：Qwen2.5-Coder 3,043 实例/81 API；StarCoder2 2,117/78；DeepSeek-Coder 2,586/76。
  - Generalization：3,012/70、2,088/71、2,560/69。
  - Specificity：15,215/3,995、10,585/3,059、12,930/3,449。
- **被遗忘的模型**：Qwen2.5-Coder (3B，截止 2024-02)、StarCoder2 (3B，截止 2023-09)、DeepSeek-Coder (1.3B，截止 2023-02)。
- **对比方法**：8 种机器遗忘方法 + 1 个模型编辑基线 AdaLoRA-L。
- **评估指标**：
  - 遗忘：AEM-D（生成含弃用 API 的补全比例，越低越好）。
  - 更新：AEM-U（生成含最新 API 的比例，越高越好，但非必要条件）。
  - 补全级相似度：ES、BLEU、ROUGE-L，分别对弃用参考（-D，越低越好）和最新参考（-U，越高越好）。
  - **OAMR**（Other API Match Recall，新提出）：排除弃用与最新 API 后，原始模型的其他 API 集合在遗忘后仍可观测的召回比例。
  - **Specificity**：在语义相似但无关的非目标输入上，遗忘模型与原始模型补全之间的 ES/BLEU/ROUGE-L。
  - **HumanEval Pass@1**：通用代码生成能力。
- **研究问题**：RQ1 遗忘与保持权衡；RQ2 库间差异；RQ3 计算效率；RQ4 弃用时间相对训练截止的影响；RQ5 内部表征与参数变化。

## 4. 资源与算力

- **GPU**：全部实验在单张 NVIDIA RTX A6000 上完成；论文明确说明在 LoRA 配置下所有方法均可单卡执行，观测到的最高峰值显存为 47.09 GB。
- **训练时长**（三模型平均）：RLFT 3.97 h、GA 3.98 h、SimNPO 4.54 h、GD 8.26 h、DPO 11.66 h。
- **峰值显存**：PROD 最高（28.65 GB 均值），DPO 次之（25.93 GB）；GA、GD、RLFT、SimNPO 平均低于 14 GB。
- **未明确说明**：GPU 数量（从表述看为单卡）、总机时、数据构建阶段的检索/推理开销、是否含多次重复运行的方差统计等。

## 5. 实验数量与充分性

- **实验规模**：8 种方法 × 3 个模型 × 3 类数据（Forget/Generalization/Specificity），加上 AdaLoRA-L 基线；共 5 个 RQ，覆盖效果、泛化、特异性、库间差异、效率、时间截点、内部机制。
- **实例量**：Forget 与 Generalization 各约 2,000–3,000 条/模型，Specificity 上万条/模型，评测规模较大。
- **充分性评价**：
  - **优点**：多方法、多模型、多维度指标，且引入 OAMR 与 Specificity 填补了以往评估空白；RQ4 与 RQ5 提供了时间与内部机制两个新视角。
  - **公平性**：所有方法统一使用相同 LoRA 配置、相同 epoch 数、相同数据划分，超参参考已有工作，比较相对公平；但未报告多次随机种子的方差，无法判断差异是否统计显著。
  - **局限**：模型仅 3 个、语言仅 Python；AdaLoRA-L 与遗忘方法的目标不同（定向替换 vs. 概率抑制），直接对比需谨慎解读。

## 6. 主要结论与发现

- **RQ1（权衡）**：存在明显的"遗忘—保持"权衡。
  - GA、RLFT、SimNPO 遗忘最强（AEM-D 平均低于 5.92），但 AEM-U、OAMR、Specificity、HumanEval 均显著下降，说明其改变的是更广泛的 API 生成行为。
  - KL、DPO、NPO、PROD 保持较好，但遗忘较弱。
  - **GD 综合权衡最佳**：平均 AEM-D 3.74，同时保持较高的 AEM-U（23.38）与 OAMR（34.77），Specificity 与 HumanEval 也较强。
  - AdaLoRA-L 遗忘极强（平均 AEM-D 0.56）且 AEM-U 高达 68.04，但 OAMR 仅 4.47，Specificity 低于 60，HumanEval 平均下降 89.57%，说明定向替换会大幅收窄补全空间。
- **RQ2（库间差异）**：SciPy 最难遗忘（GD 在 Generalization 上 AEM-D 高达 21.16/13.97/16.19），TensorFlow 最易遗忘（2.40/1.82/0.54）；GD 在四个库上均保持最有利的整体权衡。
- **RQ3（效率）**：RLFT、GA 时间最低，DPO 最高；GA/GD/RLFT/SimNPO 显存较低；GD 时间中等（8.26 h）且显存低于 14 GB，效率合理。
- **RQ4（弃用时间）**：训练截止之后才被弃用的 API 显著更难遗忘。StarCoder2 上 AEM-D 从 3.47 升至 16.01（+362.2%），DeepSeek-Coder 从 1.67 升至 12.22（+633.6%）；但 Specificity 未恶化，说明影响主要针对目标 API 遗忘。
- **RQ5（内部机制）**：RLFT/SimNPO 引起较广的表征与参数重要性扰动；DPO/NPO 内部变化小但遗忘弱；**GD 以相对受控的内部变化实现强遗忘**，印证其综合权衡优势。

## 7. 优点

- **行为化、模型专属的基准构建**：仅当原始模型确实生成目标弃用 API 时才保留实例，避免"遗忘不存在的行为"，比以往基于预定义样本的做法更严谨。
- **面向多解性的任务表述**：将弃用 API 适配定义为降低 P(y_d|x) 而非强制生成预定义目标，更贴合代码补全的多解本质。
- **评估维度全面**：首次系统引入 OAMR（同一上下文内其他 API 保持）与 Specificity（无关输入的 API 行为保持），弥补了仅靠 HumanEval 的评估盲区。
- **大规模自动化流水线**：结合 Sourcegraph 仓库挖掘与模型行为验证，可复用于其他演化知识的基准构建。
- **多层次分析**：除输出指标外，还从表征（PCA Shift/Similarity、CKA）与参数（FIM）两个层面解释不同方法的权衡来源。
- **实用发现**：揭示库间差异与训练截止时间的显著影响，为实践中的 API 知识维护提供可操作建议。

## 8. 不足与局限

- **模型与语言覆盖有限**：仅 3 个代码 LLM、仅 Python 生态，结论未必推广到其他架构、参数规模或编程语言的模型。
- **评估粒度止于 API 级**：未验证生成代码在完整程序中的功能正确性；作者也承认构建可执行测试用例的成本过高。
- **数据分布偏差**：MUDAPIBench 的库与 API 分布可能影响结论；API 使用频率、调用模式、语义距离等因素未被系统控制。
- **元数据可靠性**：API 映射与弃用时间线依赖已有研究与官方文档，可能受文档不完整与人工整理影响；模型实际训练语料不可知，无法精确确认某 API 是否被预训练暴露。
- **统计严谨性不足**：未报告多次随机种子下的方差或显著性检验；单一 GPU 配置，效率结论的可迁移性有限。
- **对比公平性需谨慎**：AdaLoRA-L 属定向替换范式，与遗忘方法的优化目标不同，直接横向比较其"劣势"可能低估其在特定场景下的价值。
- **超参未做敏感性分析**：LoRA rank、epoch、β 等均沿用既有工作，未探究其对"遗忘—保持"权衡的影响。

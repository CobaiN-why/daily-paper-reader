## 摘要
尽管大型语言模型具备强大的代码生成能力，但它们往往无法生成安全的代码，因为其输出经常包含安全漏洞。安全代码生成本质上具有挑战性，因为它需要解决一个多目标问题：功能正确性与安全性。现有方法通过注入外部安全知识或使用智能体反馈和迭代细化来应对这一挑战。然而，指南检索往往让生成器将通用建议转化为特定于任务的安全实现，而共享对话的多智能体反馈可能会模糊角色边界并遭受上下文膨胀问题。我们提出了MACGen，一个集成规划、安全分析、代码合成与细化的多智能体框架，以共同优化安全性和功能性。规划器构建逐步计划以满足功能需求。安全顾问识别可能的CWE并综合任务特定的指南，随后编码器根据这些产物生成代码，评审员则发布基于视角分离的反馈。并非共享完整的对话历史，每个智能体仅接收来自上游阶段的结构化产物，从而强化角色专业化并减少不受控制的上下文增长。在CWEval和BaxBench上，MACGen相比直接提示在F&S@1上平均分别提升了19.61和10.57个百分点。

## Abstract
Despite their strong ability to generate code, large language models often fail to produce secure code, as their outputs frequently contain security vulnerabilities. Secure code generation is inherently challenging because it requires solving a multi-objective problem: functional correctness and security. Existing approaches address this challenge by injecting external security knowledge or by using agentic feedback and iterative refinement. However, guideline retrieval often leaves the generator to translate generic advice into task-specific secure implementations, while shared-dialogue multi-agent feedback can blur role boundaries and suffer from context bloat.   We present MACGen, a multi-agent framework that integrates planning, security analysis, code synthesis and refinement to jointly optimize security and functionality. A planner constructs a step-by-step plan to satisfy functional requirements. A security advisor identifies likely CWEs and synthesizes task-specific guidelines, a coder then generates code grounded in these artifacts, and a reviewer issues perspective-separated feedback. Rather than sharing full dialogue histories, each agent receives only structured artifacts from upstream stages, enforcing role specialization and reducing uncontrolled context growth. On CWEval and BaxBench, MACGen improves F&S@1 over direct prompting by 19.61 and 10.57 percentage points (pp) on average, respectively.

**研究动机与背景**

- 大型语言模型（LLM）虽具备强大的代码生成能力，但生成的代码常包含安全漏洞（如 MITRE CWE Top-25 中列出的弱点类型）。
- 安全代码生成本质上是一个**多目标优化问题**：既要保证功能正确性（functional correctness），又要满足安全性（security），二者往往存在张力——强调安全可能牺牲功能，反之亦然。
- 现有方法的不足可归纳为两类：
  - **外部安全知识注入（如 RAG 检索指南）**：指南通常是通用的，缺乏对具体任务上下文（变量名、函数签名、控制流等）的感知，生成器仍需自行“翻译”和适配。

**核心贡献**

- 论文提出 MACGen，一个受 Secure Software Development Lifecycle（SSDLC）启发的角色专业化多智能体框架，以“集成安全贯穿开发全程”的方式协同优化功能与安全。
- 核心设计思想：各智能体之间仅传递**结构化产物（artifacts）**，而非共享完整对话历史，从而在接口层面强制角色分工，减少无关上下文流入和上下文无限增长。

## 2. 论文提出的方法论

**核心思想**

- 将安全代码生成分解为四个阶段：**规划 → 安全分析 → 代码合成 → 评审细化**，每个阶段由专门智能体负责。
- 各智能体只接收上游阶段输出的紧凑结构化产物（如功能计划、安全指南、代码），而非原始对话内容，以保持角色纯度和上下文可控。

**关键流程（四角色协作）**

1. **Planner（规划器）**：根据任务提示生成简明的高层功能实现计划，为后续代码生成提供方向，也为安全分析提供任务上下文。
2. **Code Generator（代码生成器）**：基于功能计划先产出**草稿代码**；随后在安全指南与功能计划的双重约束下生成正式代码，并进行语法自检与修复。
3. **Security Advisor（安全顾问）**：
   - **早期退出分诊**：先判断任务/草稿代码是否涉及攻击面；若无安全风险（如纯算法题），则提前退出，节省推理开销。
   - 若存在风险，则进行三步推理：
     - ① 标准驱动指南生成：识别潜在 CWE 风险组 → 构造查询 → 从**安全知识库（KB）**中检索相关规范 → 生成第一组任务特定安全指南；
     - ② 代码驱动指南生成：审查草稿代码中 LLM 特有的不安全编码模式，生成第二组代码级指南；
     - ③ 验证与整合：将两组指南合并，并与功能需求比对、消除冲突，生成最终安全指南。
   - 知识库（KB）基于 CERT、OWASP 等官方标准构建，通过 LLM 规范化（LLM-based refinement）将原始文档转为 WHAT/WHY/HOW/EXAMPLE 四字段高密度格式，并利用 FAISS 建立向量检索索引。
4. **Reviewer（评审员）**：执行**视角分离的双重检查**——功能检查和安全检查分开进行，避免角色干扰；发现问题后将针对性反馈传递给代码生成器，进行迭代修复（默认最多 2 轮）。

**核心公式/算法要点**

- 安全指南检索采用余弦相似度 Top-K 选择：
  \[
  G^*(q_j) = \arg\max_{(K) \atop g_i \in KB} \text{sim}(E(q_j), E(g_i))
  \]
  最终候选集为所有查询 \( q_j \) 检索结果的并集。
- 每个智能体只接收结构化产物（如 JSON 格式的 CWE 分组、安全指南文本等），而非完整上下文。

## 6. 论文的主要结论与发现

1. **MACGen 在两个安全代码基准上全面优于基线**：
   - CWEval：相较 Direct Prompting，F&S@1 平均提升 **19.61 个百分点**（最高 GPT-4o 达到 70.59%）。
   - BaxBench：F&S@1 提升 9.95 pp（GPT-4o）和 11.18 pp（GPT-4o-mini）。
2. **最小化功能-安全权衡**：MACGen 是各方法中功能损失最小的（平均 Func@1 仅下降 0.56 pp），同时安全增益最大（平均 Sec@1 提升 23.82 pp）；小模型（Qwen3-8B）上甚至 Func@1 提升 10.92 pp，说明结构化分解对弱模型尤其有益。
3. **跨语言鲁棒性**：在 C++ 和 Go 上优势尤其明显；RAG 基线的安全知识在这些语言上效果较弱，MACGen 的安全顾问“翻译”环节缓解了这一问题。
4. **成本效率**：MACGen 的 token 消耗仅为 INDICT 的约 16%（220,916 vs 1,411,754 tokens），API 成本低 $3.77，说明结构化产物接口比共享上下文更经济。
5. **角色专业化验证**：MACGen 在各种模型/基准上均优于 MACGen-Shared（共享上下文变体），尤其 GPT-4o-mini 在 CWEval 上差距达 20.17 pp，验证了 artifact-only 协调策略的有效性。
6. **安全顾问各组件均有贡献**，移除任一环节（标准驱动生成、代码驱动生成、验证整合）都导致 F&S@1 下降。
7. **对通用编程能力无害**：在 HumanEval/HumanEval+ 上性能与 Direct 相当，且大多数任务触发早期退出（如 GPT-4o 的 164 个任务全部触发），说明分诊机制有效避免了过度安全化。

## 7. 优点

**方法设计方面的亮点**

- **清晰的问题分解视角**：借鉴 SSDLC 将安全纳入开发全程，结构合理（需求分析→设计期安全→实现→验证），而非“事后打补丁”。
- **Artifact-only 接口的设计创新**：不仅靠 prompt 提示来区分角色，而是从通信协议层面强制隔离上下文；实现了角色边界的形式化保证，这是与共享对话框架的本质区别。
- **安全指南的任务特定化**：通过“CWE 识别 → 标准检索 → 草稿代码审查 → 验证整合”的多阶段流程，将通用规范“翻译”为可直接应用的任务约束，解决 RAG 方法“有知识但用不上”的核心痛点。
- **标准驱动的 KB 构建**：基于官方标准（CERT/OWASP），采用 LLM 规范化 + 四字段压缩格式（WHAT/WHY/HOW/EXAMPLE），提高了检索密度和质量，并有 3% 的低失真率人工验证。
- **KB 与代码双重驱动的安全分析**：兼顾了计划层面的风险预判与代码层面的 LLM 特有不良模式发现，覆盖面更全。
- **早期退出机制**：对低风险任务跳过检索/深度分析，在保持性能的同时降低计算开销。
- **注重功能安全平衡**：安全顾问设有“验证”步骤主动消除与功能需求的冲突，避免安全措施过度工程化。

**实验评估方面的优点**

- 实验矩阵大、覆盖维度广（模型、语言、数据集类型、消融、成本、采样）。
- 报告联合指标 F&S@1 而不只看某一维度，较客观地反映多目标质量。
- 对失败模式的深入分析（CWE 类别层面的错误归因）提供了有价值的诊断信息；早期退出审计和 KB 质量人工验证增强了结论可信度。

## 8. 不足与局限

**实验覆盖方面的局限**

- **评估粒度受限**：CWEval 每个任务只针对单一 CWE 触发条件，无法反映真实软件中多漏洞交织的情况；BaxBench 虽更真实，但论文对“安全请求过度 vs 功能期望”边界矛盾处理不足（已知悉 oracle 预期 API 行为可能将合理防护误判为功能失败）。
- **语言覆盖不均衡**：6 种主要评估语言，但知识库构造仅对部分语言有专用来源，其他依赖通用语料；JavaScript 上提升幅度相对较小，部分归因于测试预言刚性而非方法自身不足。
- **剩余安全错误的结构性原因**（如 CWE-327、CWE-329、CWE-643 等）需要运行时 API 语义知识，多智能体推理无法弥补库特定知识的缺失。

**效率方面的局限**

- 多智能体流水线相比单次生成仍明显增加延迟（平均端到端延迟 28.34s，虽远优于 INDICT 的 213s，但高于 RESCUE 的 7.08s）。
- 成本随模型能力和任务复杂度波动（本地模型行数更大），对实时场景（如 IDE 智能补全）可能构成实际障碍。

**潜在偏差风险**

- 所有评估基于特定 benchmark 的测试预言，可能偏向该 benchmark 定义的安全范围；论文坦言“更广安全代码评估需更明确的安全范围建模（分级加固级别/不同安全假设下的功能测试）”。
- 安全“通过”以测例未触发漏洞为标准，排除部分静态分析工具能发现但测试未覆盖的漏洞类型。
- LLMSecEval 虽有补充，但缺少功能 oracle，只做静态安全性判断，度量维度不完整。

**设计上的局限**

- 框架采用纯推理式 agent 协调，所有分析、综合、细化依赖 LLM 自身推理；论文明确指出，引入静态分析器或自动渗透测试等外部验证工具是可互补但尚未实现的扩展方向。
- 知识库构建使用 LLM 规范化存在少量信息失真（约 3% 主要集中于 Go 与 C++ 来源），且 KB 是冻结静态版本，需要周期更新。
- 安全顾问早期退出判断的敏感性随模型而异（GPT-4o-mini 在有攻击面任务上漏判率达 23.1%），小型模型的风险识别能力仍是瓶颈。

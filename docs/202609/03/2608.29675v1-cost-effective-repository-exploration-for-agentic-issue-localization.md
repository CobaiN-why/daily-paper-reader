## 摘要
代码库探索是编码智能体流水线中一个独特且成本高昂的阶段：在生成补丁之前，智能体必须识别哪些代码库文件可能是重要的。我们研究了这一阶段是否可以委派给成本更低的模型，同时保持有用的定位质量。我们使用IssueLoc-Bench，在相同的只读交互界面下，对499个SWE-bench Verified派生任务和来自153个额外仓库的500个任务评估了五个探索模型。我们测量了早期候选发现、前三金标文件覆盖率、严格文件集恢复、智能体时间和令牌使用量，并进行了配对实例级不确定性和按仓库聚类的敏感性分析。质量最高的探索者在各项定位指标上领先，但也出现了明显更便宜的操作点：根据模型和评估分支的不同，低成本探索者保留了参考Hit@3的约78-94%和F1的73-92%，同时将平均智能体时间减少了41-88%，令牌使用量减少了84-95%。首选操作点取决于定位在下游如何被消费：排名和覆盖率指标刻画了可恢复的候选移交，而F1和精确匹配则刻画了限制性文件门控。这些结果支持将代码库探索视为模块化编码智能体中一个可独立测量和预算的阶段，探索者的选择由下游移交契约指导。

## Abstract
Repository exploration is a distinct and costly stage of coding-agent pipelines: before generating a patch, an agent must identify which repository files are likely to matter. We study whether this stage can be delegated to lower-cost models while retaining useful localization quality. Using our IssueLoc-Bench, we evaluate five explorer models under the same read-only interactive interface on 499 SWE-bench Verified-derived tasks and 500 tasks from 153 additional repositories. We measure early candidate discovery, top-three gold-file coverage, strict file-set recovery, agent time, and token usage, with paired instance-level uncertainty and repository-clustered sensitivity analysis. The highest-quality explorer leads across localization metrics, but substantially cheaper operating points emerge: depending on the model and evaluation arm, lower-cost explorers retain approximately 78-94% of the reference Hit@3 and 73-92% of its F1 while reducing mean agent time by 41-88% and token usage by 84-95%. The preferred operating point depends on how localization is consumed downstream: ranking and coverage metrics characterize recoverable candidate handoffs, whereas F1 and exact match characterize restrictive file gates. These results support treating repository exploration as an independently measurable and budgetable stage of modular coding agents, with explorer selection guided by the downstream handoff contract.

# 论文总结：面向智能体问题定位的高性价比代码库探索

## 1. 核心问题与整体含义（研究动机与背景）

现代编码智能体（coding agents）是多阶段系统：理解 issue → 探索仓库 → 生成补丁 → 验证修复。其中**仓库探索（repository exploration）**是一个独特且成本高昂的阶段——在生成补丁之前，智能体必须先确定哪些仓库文件可能关键。然而，现有端到端基准（如 SWE-bench）将 issue 理解、仓库探索、文件定位、补丁生成、执行与重试策略等全部混在一起评估，难以回答一个更窄的系统设计问题：

> **仓库探索环节能否委托给低成本模型，同时保持足够的定位质量？**

本文的核心贡献在于**将仓库探索视为一个独立、可测量、可单独预算的环节**，在统一接口与受控条件下实证研究"用哪个模型做探索"的质量—成本权衡，并明确区分两类下游消费契约：可恢复的软交接（soft handoff，关注排名/覆盖率）与严格的硬门控（hard gate，关注 F1/精确匹配）。

## 2. 提出的方法论

### 核心思想
- 提出 **任务分解的模块化编码智能体设计**：低成本的专用探索器先输出**候选文件的排序列表**，再将 top-k 文件及证据交给能力更强的下游修复模型。这一中间产物（有序文件路径列表）无需生成补丁即可独立评分，形成了可观测的探索与后续阶段的边界。

### 任务形式化
- 输入：issue 文本 $$I$$ + 人类修复提交之前的前置快照 $$R$$。
- 输出：一个有序的去重文件路径列表 $$\pi_i = [p_{i1}, p_{i2}, \dots, p_{ik}]$$（每个 $$p_{ij}$$ 须存在于快照 $$F(R)$$ 中）。
- 标签：历史人类修复提交修改并经过滤后的文件集合 $$G_i$$（即历史解决足迹，而非最小因果文件集）。
- 界面约束为只读（`ls`、`find`、`grep`、`cat`、`nl`、`sed -n` 等），不允许修改代码或执行修复。

### 评估指标（双契约视角）
- **软交接（候选发现）指标**：
  - Hit@k（k=1,3,5）：前 k 个预测中是否命中至少一个金标文件；
  - R@3：前三个候选文件覆盖的金标文件比例（宏平均）；
  - MRR（Mean Reciprocal Rank）。
- **硬门控（严格集合恢复）指标**：
  - Macro-F1：基于逐实例的精确率与召回率计算；
  - Exact Match（EM）：预测文件集与金标集合精确相等。
- **操作成本指标**：agent 平均耗时（秒）、总 token 消耗（输入/输出/总量）、步数、错误率（超时等）。
- 空预测/失败运行得零定位分；不存在的预测路径保留并计为假阳性；无事后截断、按生成列表直接评分。

### 不确定性与稳健性分析
- **配对逐实例 bootstrap**：对齐每个实例上"替代模型 − 参考模型"的差值，10,000 次重采样，95% 置信区间；
- **按仓库聚类 bootstrap**（以仓库为重采样单元）作为敏感分析；
- 对二值 Hit@k 与 EM 另做 McNemar 检验及 Holm 校正。

## 3. 实验设计

### Benchmarks / 数据集（两条评估臂）
论文发布新基准 **IssueLoc-Bench**，包含两条互补的评估臂，共 **999 个任务**：

| 评估臂 | 实例数 | 仓库数 | 平均金标文件数 | 平均仓库大小（路径数） |
|---|---|---|---|---|
| SWE-bench Verified-derived | 499 | 12 | 1.24 | 3,898.5 |
| IssueLoc random-repository | 500 | 153 | 2.27 | 614.2 |

- **SWE-bench Verified 派生臂**：源自 SWE-bench Verified 测试集，用基准提交前的快照 + 补丁分解得到文件标签，仓库大但每个任务金标文件少，考验"在大型树中搜索"的能力。
- **IssueLoc 随机仓库臂**：论文自建的 500 个任务，覆盖 153 个公共活跃仓库；要求 issue 与 PR 一一对应且合并 PR 为单提交，仓库跨 split 不重叠，用父提交树作工作区，降低标签泄漏。仓库较小但多文件足迹更常见。

### 对比模型（5 种，均经 vLLM 本地服务）
1. **GLM-4.7-Flash**（zai-org）——质量最高的参考探索器；
2. **Gemma-4-E4B-it**（Google）；
3. **Qwen3-30B-A3B-Instruct-2507**；
4. **Qwen3-Coder-30B-A3B-Instruct**（代码特化）；
5. **Qwen3-4B-Instruct-2507**（紧凑极端）。

所有模型使用同一套 issue 文本模式（IssueLoc 用 title+body，SWE-bench 变换实例优先用链接 issue 文本，缺省回退到 SWE-bench problem statement），同一只读交互 runner、同一 600 秒超时、同一 markdown 过滤后评分视角。

## 6. 主要结论与发现

- **最高的质量仍来自最强的参考模型（GLM-4.7-Flash）**，但其 agent 时间与 token 消耗也最大。
- **低成本替代模型保留了大量定位质量**：Hit@3 保留约 **78–94%**，F1 保留约 **73–92%**，同时将平均 agent 时间降低 **41–88%**、token 使用量降低 **84–95%**，API 成本降低因模型定价不同而差异较大。
- **不存在"普遍最优"的低成本替代模型**，不同模型呈现不同的 Pareto 操作点：
  - **Qwen3-30B-A3B**：最均衡的替代选项，F1 和 token 表现好，两条臂都接近参考；
  - **Qwen3-Coder-30B-A3B**：SWE-derived 臂上前三发现率保留最多（94.3%），但 F1 较低，偏典型软交接；
  - **Gemma-4-E4B**：agent 时间大幅减少且质量保留不错，适合时间敏感场景； 
  - **Qwen3-4B**：最激进的时间节省点，质量损失最大。
- **探索器的选择应由下游交接契约决定**：软交接场景用 Hit@3/R@3/MRR 选模型；硬门控场景则应以 F1/EM 为准。
- **跨臂结论方向稳定**（低成本节约时间/token、质量有一定折损），但**模型排序跨臂/跨指标会变化**；SWE-derived 臂的若干质量差异在仓库聚类后不再显著，推及跨仓库场景需更谨慎。

## 7. 优点

1. **任务切分角度新颖且具有系统设计价值**：把"谁来做探索"从端到端 agent 中显式拆出，使探索阶段可独立评测、预算与优化，并用移交契约连接上下游；
2. **评测指标与操作场景绑定**：明确区分软交接（排名/覆盖率）与硬门控（F1/EM），避免了单一聚合分数掩盖质量维度差异的问题；
3. **双评估臂设计互补**：一头连接广泛使用的 SWE-bench Verified（大仓库、少金标），一头连接 153 个仓库的多样化随机样本（多文件足迹），分别检验"大仓库搜索"与"多足迹恢复"下 trade-off 的稳健性；
4. **统计方法较为严谨**：逐实例配对 bootstrap + 仓库聚类 bootstrap + McNemar + Holm 校正，并披露了哪些对比在仓库聚类下不显著；
5. **附带完整可复现基准**：公开 manifest、快照构造器、评测器、runner 输出与统计代码（GitHub），且用预修复父提交降低泄漏；
6. **诚实透明**：明确区分"历史足迹"与"最小因果文件集"之差异，明确标注空预测/超时皆按零分计。

## 8. 不足与局限

1. **评测终止于定位层，未做端到端验证**：没有固定修复器之上测量"探索器 → 修复器"的最终修复率，因此阶段质量差异能否转化为修复差异尚属开放问题；
2. **数据污染风险未消除**：公共热门仓库的数据可能已进入预训练语料；虽然用新近 issue 降低暴露概率，但无法保证；
3. **SWE-derived 臂仓库数量过少**（12 个）导致仓库聚类敏感分析中的若干质量差异置信区间过宽，跨仓库推广的证据相对薄弱；
4. **金标定义偏严（历史足迹而非必要文件集）**：EM 是刻意严格但实际操作上可能低估合理替代修复路径，需要其他指标互补补偿；
5. **操作成本测量混淆了多种因素**：时间/token 是完整配置（模型 + serving + 工具调用 + 停止策略 + 超时策略）的总计，非模型固有速度；token 覆盖也只是配对完整观测；
6. **外部有效性受限**：未覆盖私有仓库、巨型 monorepo、其他语言/框架分布、不同 agent 界面；各模型 API 价格数据也是 2026 年 6 月的快照，随时间变动；
7. **随机性方差未量化**：bootstrap 跨的是基准实例/仓库，不衡量同一实例重复运行时的轨迹随机波动。

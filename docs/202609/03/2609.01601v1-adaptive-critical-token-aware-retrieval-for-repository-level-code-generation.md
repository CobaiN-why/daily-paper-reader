## 摘要
仓库级代码生成任务要求合成的代码既满足任务需求，又与目标仓库上下文保持一致。由于现实中的仓库通常超过LLM的输入长度限制，现有方法普遍采用检索增强生成（RAG）来提供仓库特定的上下文。尽管改进了仓库上下文检索，现有方法通常将上下文作为任务级别的支持提供，而没有明确识别在生成过程中需要细粒度仓库上下文的关键标记。在LLM的自回归生成过程中，错误往往集中在少数决定性位置：一旦这些标记生成错误，后续代码可能沿着错误的语义路径进行，最终导致功能失败。我们将这些位置称为“关键标记”。在本文中，我们提出了ACToR，一种用于仓库级代码生成的自适应关键标记感知检索框架。ACToR在生成过程中识别关键标记，并按需触发定向检索，以在这些决定性位置提供仓库上下文。此外，我们为密集检索器设计了一种位置感知加权方法，以优先考虑对生成更有信息量的上下文。我们在两个具有代表性的仓库级基准测试RepoExec和CoderEval上评估了ACToR。实验结果表明，ACToR持续优于最先进的方法，在RepoExec上相对提高了8.4%，在CoderEval上相对提高了15.4%。除了性能提升外，我们系统地量化了关键标记的影响，揭示了它们在主要生成失败中的核心作用，并强调了定向检索策略的必要性。我们在https://github.com/DeepSoftwareAnalytics/ACToR提供代码和数据。

## Abstract
The repository-level code generation task requires synthesizing code that satisfies task requirements while remaining consistent with the target repository context. Since real-world repositories often exceed the input length limits of LLMs, existing approaches commonly adopt retrieval-augmented generation (RAG) to provide repository-specific context. Despite improving repository-context retrieval, existing methods typically provide context as task-level support, without explicitly identifying the critical tokens that require fine-grained repository context during generation. During the autoregressive generation process of LLMs, errors often concentrate at a small number of decisive positions: once such tokens are generated incorrectly, subsequent code may follow an incorrect semantic path and eventually lead to functional failure. We refer to these positions as "critical tokens". In this paper, we propose ACToR, an adaptive critical token-aware retrieval framework for repository-level code generation. ACToR identifies critical tokens during generation and triggers targeted retrieval on demand to provide repository context at these decisive positions. In addition, we design a position-aware weighting method for dense retrievers to prioritize context that is more informative for generation. We evaluate ACToR on two representative repository-level benchmarks, RepoExec and CoderEval. Experimental results show that ACToR consistently outperforms state-of-the-art methods, achieving relative improvements of 8.4% on RepoExec and 15.4% on CoderEval. Beyond performance gains, we systematically quantify the impact of critical tokens, revealing their central role in major generation failures and highlighting the necessity of targeted retrieval strategies. We provide the code and data at https://github.com/DeepSoftwareAnalytics/ACToR.

## 1. 核心问题与研究动机

- **背景**：仓库级代码生成（Repository-Level Code Generation）要求模型在已有代码仓库的约束下生成满足任务描述的函数实现，生成的代码必须与仓库特定的 API、依赖、数据结构及编码约定保持一致。真实仓库通常远超 LLM 上下文窗口限制，因此现有方法普遍采用 RAG 思路，先检索仓库片段再拼接进 Prompt 生成代码。
- **已有方法的缺陷**：现有 RAG 方法（如 RepoCoder、Cocomic、DRACO、RepoFormer、RLPG 等）主要从“检索质量、上下文来源、检索决策”等角度优化，但本质上均把上下文视为整体任务级的静态支持，**缺乏对生成过程中 token 级关键决策点的显式建模**。
- **核心观察**：代码生成是强路径依赖的自回归过程，错误往往并不均匀分布，而是集中在少数“决定性位置”——一旦这些位置的 token 生成错误，后续代码会沿错误的语义路径继续生成，最终导致整体功能失败。论文称之为 **关键标记（Critical Tokens）**。关键标记错误可能引发级联性失败，而普通 token 错误只影响局部。
- **关键标记的两个特性**（通过两个 CoderEval 案例说明）：
  1. 错误影响大：一个关键 token 的错位会改变模型对核心实现逻辑的判断，导致代码偏离仓库语义、引起函数级失败；
  2. 语法形式多样：关键 token 可以是 API 名、变量引用、索引表达式甚至注释中的语义线索，因此无法靠固定句法规则或一次性预生成检索覆盖。
- **研究目标**：在生成过程中动态识别关键 token，并在这些关键位置触发按需（on-demand）的定向检索以提供细粒度仓库上下文，从而有效减少级联错误。

## 2. 方法论

### 总体架构
ACToR 分为两大阶段：

- **离线训练阶段**：构造带“关键/非关键”标签的数据集，训练一个轻量的判别模型（关键 token 分类器）；
- **在线推理阶段**：结合**位置感知加权检索器**与**关键 token 引导的推理策略**，在生成过程中实时判断 token 是否为关键 token，并在必要时进行二次定向检索、重新解码该 token。

### （1）离线训练流程

- **数据构造**（Data Construction）：
  - 来源：RepoST-Train（含 824 仓库、7415 个函数），按仓库规模/星标/真实性筛选，并排除与 RepoExec、CoderEval 评测集重叠的仓库，最终保留 **102 个仓库、1203 个任务样本**；
  - 对每个任务，将函数签名与 docstring 拼接为查询，用密集检索器返回仓库上下文候选；上下文与查询按相似度排序拼接为 Prompt。
- **Token 评估**（Token Evaluation）：对每个生成位置用三个准则判断是否关键 token：
  1. **Token 错配（Token Mismatch）**：模型 top-1 预测异于真值（\(x_i \neq \hat{x}_i\)）；
  2. **不确定性（Uncertainty）**：以生成概率的熵 \(H_i\) 衡量模型置信度；
  3. **后续注意力影响（Subsequent Attention Influence）**：基于 Transformer 自注意力中后续 \(k\) 个位置对当前位置的平均 Top-K 注意力权重（\(K=5\)），衡量错误在该位置传播放大的风险。
  - 任一准则超阈值（或发生错配）即标注为关键 token；
  - 采用**教师强制（Teacher-forcing）评估**，把已生成位置替换为真值再继续评估，以抑制错误传播带来的干扰，使标注更反映 token 本身价值。
- **标签平衡**：非关键 token 占大多数。论文按**自信息/惊异度** \(I(x_i)=-\log_2 P(x_i|x_0,\dots,x_{i-1})\) 保留“困难负样本”，直到正负样本平衡，以提升分类器区分能力。
- **分类器训练**：集成多个 3 层 MLP（总参数量仅 **4.01–10.01M**），输入为主干 Code-LLM 最后隐藏层的隐藏状态，输出二分类概率，用交叉熵损失优化，逐位置判断是否为关键 token。

### （2）在线推理流程

- **位置感知加权密集检索器（Position-Aware Weighted Retriever）**：
  - 典型的 UniXcoder 密集检索采用平均池化，忽略了 token 位置重要性差异。ACToR 采用**双端点高斯加权**：位置 \(i\) 的权重为两端高斯核之和：
    \[
    w_i = \exp\left(-\frac{i^2}{2\sigma^2 L^2}\right) + \exp\left(-\frac{(i-(L-1))^2}{2\sigma^2 L^2}\right)
    \]
  - 经 softmax 归一化后对 token embedding 加权求和得到序列向量。这样能放大**开头（函数签名/定义）**与**末尾（紧邻未生成代码处）**的信息；
  - 权重仅依赖 \(\sigma\) 与 \(L\)，可预计算缓存，在线开销可忽略。
- **关键 token 引导的动态纠错推理（Algorithm 1）**：
  1. 先用目标函数 Prompt 检索获得初始上下文；
  2. 逐 token 生成，每步抽取隐藏状态送入分类器集成；
  3. 若判定为“非关键”，继续正常生成；
  4. 若集成模型一致判定为“关键 token”，立即用“原始 Prompt + 当前已生成代码 + 当前关键 token”构造新查询进行**二次检索**，将更新后的上下文拼入后**重新解码当前位置**，并把该上下文保留用于后续生成；
  5. 工程上跳过空格/换行等 token 的检查以加速推理。

## 6. 主要结论与发现

- **主性能结论**：ACToR 在 RepoExec 与 CoderEval 上相对最强基线获得一致的显著提升（例如 CodeLlama-7B 在 RepoExec Pass@5 相对提升 8.4%，在 CoderEval Pass@5 提升 15.4%）。CodeLlama-13B 在 CoderEval 上达到 Pass@5 = 39.57% 的全场最高分。
- **多样性收益**：ACToR 的多候选成功率

**多样性收益**：ACToR 的多候选成功率提升显著高于单候选，说明它在扩大“有效采样空间”方面具有优势——不仅首选的生成质量更高，而且多候选之间的多样性也更合理，避免多个候选在同一个关键 token 处集体出错。

- **跨模型泛化性**：ACToR 在 1.3B 到 13B 的多个生成器上均稳定提升，不依赖某个特定模型的内部机制；即便对于本身能力较强的 CodeLlama-13B，仍能通过关键 token 级纠错获得增益。这表明该方法不是“小模型专属补丁”，而是对自回归代码生成范式的一种通用改进。

- **模块互补性结论**：动态纠错推理与位置感知加权检索器各有分工——前者在“何时纠”上做决策，后者在“纠的时候检索什么”上提供更高质量的上下文；两者组合收益大于各自单独收益之和的简单叠加关系，说明二者存在协同效应。

- **关键 token 比例的规模效应**：随着生成器规模增大，被判别为关键 token 的比例总体呈下降趋势（从 1.3B 的约 10% 降至 13B 的约 5%），说明大模型在更多位置具备足够自信的预测能力，但仍存在少量不可靠的关键位置，这为“关键 token 纠错始终有上限收益”提供了证据。

- **关键 token 的语法分布特点**：关键 token 中，API 名/属性访问等语义负载较高的 token 占比显著高于其在代码中的自然频率；而长度极短的 token（如单字母变量）虽然绝对占比高，但相对倍数不高，说明 ACToR 识别到的关键 token 确实偏重于承载仓库级语义的 token，而非简单的低概率噪声。

- **对比基线的意义阐释**：与 RepoCoder 的“对整段代码迭代检索”相比，ACToR 的“对关键 token 定向检索”避免了大量无意义检索；与 RLCoder 的“任务级检索策略学习”相比，ACToR 无需针对每个仓库训练检索策略，而是通用地在推理时按 token 动态决策，部署成本更低。

## 7. 研究局限与潜在改进空间

- **评测语言单一**：全部实验都在 Python 上进行，未验证 Java、JavaScript、TypeScript 等同样依赖仓库上下文的语言；关键 token 的语法分布与自注意力传播模式在不同语言间可能存在差异，结论是否跨语言成立尚待验证。

- **关键 token 标注依赖真值**：离线训练阶段需要真值代码来评估 token 错配与注意力影响，这意味着新仓库/新任务如果没有测试 oracle 就不能立即生成训练数据。模型迁移到新领域时的标注成本未充分讨论。

- **纠错机制缺乏“后悔”路径**：ACToR 一旦判定某个 token 为关键并重新解码，不会回退或重新审视更早的历史生成；如果关键 token 出现在较早位置，但二次检索后生成的上下文仍不足以纠正，后续错误可能继续级联而无法挽回。

- **分类器与主干耦合**：分类器基于主干 Code-LLM 的隐藏状态训练，更换生成器主干时需要重新构造训练数据并重训分类器；论文未讨论跨主干迁移分类器的可行性。

- **上下文累积风险**：多次关键 token 检索会逐步扩大 Prompt 中的上下文长度，长任务中可能逼近上下文窗口上限；论文未给出长序列任务中的上下文压缩或淘汰策略。

- **语义等价判断粗糙**：评测以“全部单元测试通过”为唯一标准，可能忽略风格、可读性等非功能性维度；同时个别情况下生成代码虽未通过测试但已包含正确的关键 token 语义，这类“部分正确”的情形未被精细刻画。

## 8. 个人评价与定位

- **优点**：
  1. 问题定位精准——从“token 级路径依赖错误”这一代码生成固有现象切入，比单纯优化检索质量或决策频率的现有工作更具解释力；
  2. 方法论轻量优雅——一个 4–10M 的分类器加一个几乎零开销的高斯加权池化，即可嵌入任意 Code-LLM 的推理循环，实用性强；
  3. 实验设计完整，消融、阈值网格搜索、机制量化分析等对结论的可靠性支撑较好；
  4. 写作中“关键 token 占比低但影响大”的论证方式较有说服力，且教师强制标注环节处理了错误传播干扰，训练数据噪声相对受控。

- **潜在批评**：
  1. “关键 token”定义本质上仍是一种启发式复合指标（错配/熵/注意力影响），并非从代码语义的真值后果中反推出来的金标准，三准则的权重与阈值域适应性仍需更多验证；
  2. 性能提升幅度虽然显著，但绝对值仍然偏低（大多在 20%–40% 的 Pass@k），离仓库级代码生成的实用门槛还有明显距离；
  3. 全文只给出一个案例分析，且未对“模型识别到关键 token 之后是否真正修复了原本会犯的错误”这一核心机制做细粒度统计，机制的因果性证明弱于相关性证明；
  4. 二次检索以“当前关键 token 文本”拼入查询，但如果该 token 本身就是错误 token（而非只是低置信度 token），用错误 token 做检索可能引入误导性上下文，这一风险未被讨论。

## 9. 综合总结

ACToR 针对仓库级代码生成中“错误集中出现在少数关键 token 并引发级联失败”的现象，提出了一个两阶段方案：离线利用错配、不确定性、注意力影响三准则构造关键 token 标注并训练轻量判别器；在线通过位置感知加权检索器提升初始上下文质量，并用判别器实时监控生成过程，在关键 token 处触发二次检索与重新解码。该方法在 RepoExec 与 CoderEval 两个基准、四种生成器规模上均一致超越现有 RAG 式基线，消融实验与敏感性分析也支持了各模块的有效性与鲁棒性。核心贡献在于将代码生成的上下文支持粒度从“任务级/代码片段级”推进到了“token 级”，为路径依赖错误治理提供了新的建模视角。不过，其评测语言广度、跨域标注成本、长上下文管理、错误检索反馈风险等问题仍需后续工作进一步解决。总体而言，这是一篇问题意识清晰、方案精巧、实验充分的优秀工作，对仓库级代码生成与检索增强生成领域均有参考价值。

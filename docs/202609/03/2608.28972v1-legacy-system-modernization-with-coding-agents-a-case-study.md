## 摘要
基于已停用平台构建的遗留系统，是依赖这些应用维持关键业务流程的组织中反复出现的技术负债。尽管现代化在战略上是必要的，但完全通过人工进行时，成本高昂且容易出错。本文报告了一项在真实工业环境中进行的案例研究，我们评估了AI编码代理在支持遗留系统向现代平台迁移方面的有效性和效率。通过使用一个版本的Claude Code代理，我们在单代策略下，将来自一个用Visual Basic 6编写的企业ERP系统中的12个不同复杂程度的功能迁移到C# .NET 10。迁移会话完成后，我们测量了迁移功能与原功能的等价性，并收集了代理在过程中花费的时间和消耗的令牌数数据。在我们的实验中，代理实现了平均70%的等价性，在不同复杂度水平之间存在显著不对称；低复杂度功能达到92%，而高复杂度功能得分47%。在基于成本的指标中观察到类似的不对称性；低复杂度功能消耗147万令牌（1.66美元），而高复杂度功能使用909万令牌（10.28美元）。我们揭示了这种迁移策略更为有效的实际场景和环境，并讨论了使用AI代理进行遗留系统现代化的局限性和挑战。

## Abstract
Legacy systems built on discontinued platforms are a recurring technological liability in organizations that depend on these applications to sustain critical business processes. Although modernization is strategically necessary, it is costly and error-prone when performed exclusively through manual effort. In this paper, we report on a case study conducted in a real industrial setting, where we evaluate both the effectiveness and efficiency of AI coding agents in supporting the migration of legacy systems to modern platforms. By using one version of Claude Code agent, we migrated 12 features of distinct complexity levels from a corporate ERP system written in Visual Basic 6 to C# .NET 10 under a single-generation strategy. Once the migration sessions were completed, we measured the equivalence of the migrated features against the original ones, and collected data about the time spent and the number of tokens consumed by the agent during the process. In our experiment, the agent achieved an average equivalence of 70%, with a strong asymmetry across complexity levels; low-level features achieved 92%, and high-complexity ones scored 47%. Similar asymmetry was observed in the cost-based metrics; low-level features consumed 1.47M tokens ($1.66), whereas high-level ones used 9.09M ($10.28). We reveal the practical scenarios and circumstances where this migration strategy is more effective, as well as discuss the limitations and challenges of using AI agents for legacy system modernization.

## 2. 方法论

论文采用“案例研究”（case study）方法，在一个真实工业系统上执行 AI 代理驱动的一次性（single-pass）迁移，并提出量化的双向评估指标：

- **总体策略**：采用单代迁移（single-generation）——由 Claude Code 代理一次完成迁移，**中途不引入人工反馈或迭代修正**；但代理可在内部自行重读文件、重写代码、调整实现。
- **迁移环境设计**：为每个功能设立独立隔离的工作目录，包含三类上下文文件：
  - **根目录 CLAUDE.md**：迁移目标、功能范围、方法论、编码约定；
  - **legacy 子目录（只读）**：VB6 源码及其说明文件，仅作参考；
  - **migration 子目录**：C# .NET 10 目标项目模板（含分层架构和自身规范）。
- **代码复杂度的量化**：使用三个源码度量——代码行数、方法数、类依赖数——按区间划分 Low/Medium/High 三个复杂度等级（须满足至少两个判据）。
- **等价性度量基线（共 331 条指令）**：由第一作者（即该遗留系统的维护工程师）阅读旧代码后人工清点每条特征的两类指令：
  - **业务规则（Rules，160 条）**：验证、计算、特定限制等逻辑；
  - **数据库操作（DB Operations，171 条）**：SQL/持久化交互指令。
- **两个等价性判定维度**：
  - **持久化等价（Persistence Parity）**：同一使用场景下迁移前后系统在数据库中落库记录与字段值是否一致；

## 3. 实验设计

- **场景/系统**：真实工业环境下的企业 ERP（管理购物中心），已在生产运行超 20 年、由 VB6 实现。选择其中两个仍在大量客户使用的次要模块：
  - **MEASUREMENTS**（219 家客户，约 299K LOC）：水、电等资源消耗计量与计费；
  - **PURCHASES**（61 家客户，约 224K LOC）：采购申请、审批流与成本分摊。
- **目标平台**：C# .NET 10，分层架构（Controller/Service/Repository），Dapper 访问 SQL Server，沿用原数据库以避免数据迁移问题。
- **迁移主体**：Claude Code（v2.1.96）运行于 Opus 4.6 1M 模型；选型理由为长上下文（百万令牌）、可直接读写文件与执行终端命令、以及多语言推理能力。
- **样本选择**：共 12 个功能（每个模块 6 个）—— 低复杂度 6 个、中复杂度 4 个、高复杂度 2 个；覆盖 CRUD、中心实体关联数据操作、复杂计算/批处理/多层审批工作流等不同形态。
- **评估过程（Benchmark 与对照说明）**：
  - 人工在旧代码中精心整理出 331 条“指令清单”（业务规则 + 数据库操作）作为评估基线；
  - 迁移完成后由第一作者人工比对新代码并执行新旧两版比对数据库状态，得到持久化与功能等价率；
  - 由一个未参与迁移的第二位审阅者独立复评全部 160 条业务规则（作为 sanity check）；
  - **本文未对比其他迁移工具、其他代理或纯人工迁移基线**，属于单臂案例研究。
- **效率数据采集**：每个功能的会话结束后记录总时间、上下文输入/输出令牌数，并按官方定价计算美元成本。

- **实验规模**：12 个功能（6 低 + 4 中 + 2 高）、2 个不同业务领域模块、331 条人工标注指令（160 规则 + 171 数据库操作），全部完成真实迁移与逐条核验。

## 6. 主要结论与关键发现

- **总体效果**：代理在所有 12 个功能、331 条指令上达到平均 **70% 等价率**（持久化等价 71%，功能等价 69%）。
- **复杂度不对称（Finding #1）**：等价率随复杂度明显下降 —— 低 92%、中 81%、高 47%；高复杂度特征的迁移是不充分的。
- **失败模式分类（Finding #2）**：全部 100 条未正确处理指令中，大多数并非“做错”，而是**“遗漏了上下文里已有的代码”**：
  - 42 条为周边模块（批量导入、报表、邮件通知等）未被识别迁移；
  - 22 条为单个遗漏的数据库操作；
  - 20 条为单个遗漏的规则；
  - 10 条为缺少模块间集成（如跨用户通知）；
  - 仅 6 条属于“实现错误”。
- **效率特征（Finding #3）**：成本在很大程度上由功能规模与复杂度驱动——低复杂度平均耗时 2 分 48 秒、$1.66、147 万令牌，而高复杂度达 7 分 38 秒、$10.23、909 万令牌（约 6.2 倍成本）。输入令牌占总消耗 99.6%，意味着推理成本主要由重读旧代码驱动，输出部分占比极小。
- **代码组织形态比代码行数更关键**：当业务规则集中在结构良好的域类（.cls）中时，代理表现优异（中等级达到 85% 功能等价，高于低等级的 83%）；当规则散落在窗体事件（.frm）或全局对象中（“碎片化代码”）时，代理表现明显恶化。
- **显式规则优于隐式规则**：凡以显式方法实现的验证、计算均容易被迁移；凡隐藏在可选查询参数、启动时动态加载的全局配置或窗体级条件中的限制，代理极易忽略——建议实践者不要把这些隐性逻辑的推断责任交给代理。
- **总体判断**：对低复杂度、边界清晰、逻辑集中（尤其在类中而非窗体事件中）的功能，**AI 编码代理可给出高等价且低成本**的自动化迁移；对高复杂度、跨模块联动或高度碎片化代码，单代策略效果和成本效率均不理想，需要人工介入或混合策略。

## 7. 方法/实验设计的亮点

- **真实工业场景的稀缺数据**：具有 20 余年生产历史、超 200 客户使用的真实 ERP 系统，结论比在代码片段或基准题库上的实验更贴近实际软件工程关切。
- **独创的指令清单评估方法**：将“等价性”从模糊概念细化到 331 条可校验的业务规则/数据库操作，同时覆盖持久化与行为两条链路，并给出可计算百分比公式，方法本身可作为后续同类研究的评估模板。
- **区分“未做”与“做错”的失败分类学**：对失败原因分为遗漏相邻模块、遗漏 DB 操作、遗漏规则、缺失模块集成、实现错误五大类，为定位代理能力边界提供了精确依据。
- **双人独立复评 + Kappa 系数**：降低人工判定的主观性，增强结果可信度。
- **成本透明化**：结合官方模型定价和会话遥测将推理开销换算成美元，并用成本-等价率的二维投影（低复杂度“高效果低成本”，高复杂度“低效果高成本”）去呈现结论，对工业决策非常直观。
- **完整的可复现设计**：逐功能的 CLAUDE.md 上下文设计、统一的 prompt、标准化的目录结构，并公开复现包，便于后续扩展至更多代理/语言对。

## 8. 不足与局限

- **配置面窄、泛化受限**：只测试了 Claude Code（单一代理 + 单一模型）、VB6→C# .NET 10 单一语言对，结论不能外推至 COBOL→Java、Delphi→TypeScript 等场景；文中对此明确承认。
- **样本失衡**：高复杂度功能仅 2 个，使“高复杂度效果差”的结论仅具指示性而不够稳健；失败类型的统计也容易受单个大型特征影响。
- **单代策略不等同于真实用法**：刻意排除人机迭代（human-in-the-loop）以测试自主性；但已有研究表明迭代反馈可显著改善翻译质量，因此本文等价率数字不宜直接视为该代理在真实工作流中的可达到上限。
- **人工评估仍有残留主观性**：虽然 Kappa 达 0.84，但 11 处分歧说明“部分迁移的规则”这类边界情况的归类存在判断空间；DB 操作等价性没有第二评审覆盖。
- **未设基线对照**：缺少“纯人工迁移”的成本/正确率基线，也没有与其他编码代理或传统工具的对比，无法量化 AI 在性价比上的相对优势。
- **缺少对迁移代码质量的端到端考察**：等价性测量聚焦行为保持一致，但未系统评估生成代码的可维护性、安全性或规范符合度；“能编译运行且持久化等价”不等于“可长期维护”。
- **异常值影响**：单次会话（如 F6 消耗 1230 万输入令牌）对总体平均成本有较大牵引，在解读平均数时需留意高离散性。

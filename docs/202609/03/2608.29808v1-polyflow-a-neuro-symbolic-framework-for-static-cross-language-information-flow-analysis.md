## 摘要
现代软件系统通常由多种相互交互的编程语言构建而成。这种构建方式导致了额外的、往往隐蔽的漏洞，这些漏洞深藏于由语言交互引起的复杂信息流中。现有的静态分析器受制于不同语言的异构语义，而动态方法则受限于（可用和/或生成的）测试输入的覆盖范围。在本文中，我们开发了PolyFlow，一种用于跨语言边界静态推理信息流的神经符号框架，将大语言模型（LLMs）与静态分析协同结合。在给定多语言系统的控制流表示指导下，PolyFlow利用LLMs识别由于具有挑战性的语言特征而产生的隐式流事实，从而增强基础表示，然后通过系统传播数据流。它通过将LLMs置于仔细的引导下（例如，静态分析引导的作用域界定、上下文管理和事实核查），以及用于协商验证的多LLM专家小组，来解决LLMs固有的障碍（例如，令牌限制和幻觉）。我们在真实世界的Python-C和Java-C系统上的实验表明，PolyFlow具有成本效益，且优于各种最先进的基线，揭示了所有基线均未发现的先前未知的跨语言漏洞。

## Abstract
Modern software systems are commonly constructed in multiple, interacting programming languages. This construction leads to additional, often stealthy vulnerabilities buried in complex information flow due to language interactions. Existing static analyzers are impeded by the heterogeneous semantics of different languages, whereas dynamic approaches suffer from the limited coverage of (available and/or generated) test inputs. In this paper, we develop PolyFlow, a neural-symbolic framework for statically reasoning about information flow across language boundaries, combining large language models (LLMs) and static analysis synergistically. Governed by the control-flow representation of a given multi-language system, PolyFlow leverages LLMs to identify implicit flow facts due to challenging language features, hence augmenting the base representation and then propagating data flow through the system. It tackles inherent barriers (e.g., token limit and hallucination) of LLMs by putting them under careful guidance (e.g., static-analysis-guided scoping, context management, and fact checking), along with a multi-LLM expert panel for negotiated validation. Our experiments on real-world Python-C and Java-C systems show that PolyFlow is cost-effective and superior to various kinds of state-of-the-art baselines, revealing previously unknown cross-language vulnerabilities that are missed by all the baselines.

- **现有方法不足**：
  - **单语言静态分析器**（如 Joern、CodeQL、Clang 等）无法处理跨语言语义，通常只能对单一语言代码片段进行分析，因此会漏掉跨语言的整体信息流；
  - **动态分析**（如 PolyCruise、PolyFuzz）依赖测试用例覆盖，而多语言项目的测试输入往往稀缺，难以触发深层路径；
  - **学习型方法**（如 xLoc）依赖训练数据质量、难以泛化到未见代码库，且跨语言漏洞的标注数据极为匮乏；
  - 许多宣称“跨语言”的工具实际上只支持多种语言、而非关注多语言共存交互的项目。
- **核心挑战**：
  - **Challenge-1**：不同语言的语义差异（类型系统、内存管理、控制流）使得构建统一静态分析框架非常困难。
  - **Challenge-2**：各种语言特性（C 的函数指针、内联汇编；Python 的装饰器、动态类型/反射、动态导入；Java 的反射、动态代理、动态类加载、多态等）会打破控制流/数据流的可解析性，导致信息流中断。论文通过实证研究识别出 **19 种**此类挑战性语言特性。
  - **Challenge-3**：LLM 有 token 限制和幻觉问题，不能“一股脑”地把整个代码库喂给 LLM。
- **论文主张**：需要一个**神经符号框架**，把传统静态分析（符号/确定性推理）与 LLM（语义理解/推理）相结合，以静态分析器为控制核心、按需调用 LLM，从而在跨语言场景中实现更完整、更精确的信息流分析。

## 2. 方法论

### 2.1 核心思想

POLYFLOW 不是“以 LLM 为核心、调用外部静态工具”的架构，而是**以静态分析器为中心**，LLM 仅作为辅助组件被按需调用。静态分析提供**骨架**（CICFG）和**流程控制**，LLM 负责处理传统分析无法解决的语言特性相关的隐式流事实。这种设计同时缓解了 LLM 的 token 限制与幻觉问题。

### 2.2 整体架构（两大阶段 + 公共专家面板模块）

#### 输入
- 目标多语言程序（项目仓库）
- 用户指定的 source/sink 列表（可选由 LLM 自动识别）

#### 输出
- 潜在的跨语言漏洞列表（以 source→sink 的污点流路径表示）

#### 公共模块：LLM 专家小组（Expert Panel）
- 结合两个**非推理型 LLM**（低成本）进行交叉验证，当二者**不一致**时，启用一个**推理型 LLM**（高成本）做仲裁。
- 目的：在保持稳定性和准确性的同时节约成本。

#### 阶段 1：增强的控制流分析（Phase 1: Augmented Control-Flow Analysis）
- **Step 1.1：CICFG 构建**（Construction）
  - 基于 Joern 的按函数 CFG → 函数级调用图 → 通过 FFI 识别跨语言调用边 → 合并成统一的跨语言过程间控制流图（CICFG）。
- **Step 1.2：CICFG 增强**（Augmentation）
  - 采用**固定点迭代算法**（Algorithm 1）扫描项目中目标语言特性，为每个语言特性调用专门 handler。
  - 特性之间存在依赖关系（例如：发现函数指针后要重新分析相关特性；条件编译展开后要触发所有 handler），这一迭代过程持续到无新的更新（收敛）为止。
  - 每种特性 handler 都遵循三步逻辑：**(1) 检测特性存在性** → **(2) 识别缺失的节点/边** → **(3) 将新节点/边加入 CICFG**。
  - 表 2 列出 18 种特性的检测线索和增强模式（第 19 种“递归函数”由 Joern 原生支持），并有若干 handler 标注了 **Prop?（Y）** 表示内部有工作列表以追逐链式效应到收敛。

#### 阶段 2：面向特性的数据流推理（Phase 2: Feature-Oriented Data Flow Reasoning）
- **Step 2.1：有向污点近似**（Directed Taint Approximation）
  - 针对每一对 (source, sink)，在增强后的 CICFG 上做**控制流可达性切片**，提取控制流级候选路径。
  - 设计意图：在早期牺牲精度换取可扩展性，只对“结构上可行”的 source-sink 对做后续昂贵分析。
- **Step 2.2：有指导的污点细化**（Instructed Taint Refinement）
  - 沿着候选路径**逐个函数**遍历，维护一个“已污染变量集合”。
  - 在每个函数内执行两类操作：
    1. **特性 handler 更新污点集**：处理值传递、指针等语言特性造成的隐式传播；
    2. **询问专家小组**：获取给定代码和已污染变量后的额外 taint 推断（别名、隐藏引用、动态行为等）；
    3. 跨语言边界传递污点变量时参考跨语言 API 知识和 CICFG 规则。
  - 若污染变量到达 sink，则记录一条完整污点流路径。
  - Algorithm 2 给出了该流程的伪代码。

#### 关键算法举例
- **Algorithm 1**：固定点特性的迭代处理：初始化所有特性 → 遍历文件收集特性相关文件 → 构建 worklist → 循环处理直到没有更新，确保特性间依赖（如条件编译与宏、函数指针）一致收敛。
- **Algorithm 3**（条件编译，C）：用 LLM 做 YES/NO 检测 → 枚举各预处理分支的语句与边 → 向 CICFG 加入节点与边（带 branch tag）。
- **Algorithm 4**（一等函数，Python）：检测 passing site → 解析高阶函数体内参数调用行和传递位置 → 递归追踪（ResolveHigherOrderFlow）直到找到真正调用点 → 插入 CICFG 边。
- **Algorithm 5**（多态，Java）：提取虚拟调用点 → 用 CHA 或 points-to 映射求候选动态类型集合 → 可选 LLM prune（只能缩小不能放大）→ 为每个候选目标求具体实现（ResolveImpl）并插入 call/return 边。

### 3.5 主要实验与结果

- **RQ1（特性普遍性）**：
  - Python 特性中，First-Class Functions 在 14 个 Python-C 项目中存在于 10 个；Decorator 只有 3 个；Reflection、Dynamic Imports 各 1 个。
  - Java 特性中，Polymorphism 出现在 **100%** 项目中、Reflection 87%、Lambda 40%、Dynamic Proxy 13%。
  - C 侧：Python-C 中 Conditional Compilation 79%、Setjmp/Longjmp 64%；Java-C 中 Function Pointers 80%、Conditional Compilation 80%、Macros 73%、Goto 47%。
- **RQ2（有效性）**：
  - 专家小组（expert panel）的隐含流识别在 xFlowBench 上达到：**precision 97.9%、recall 87.3%、F1 91.8%**。
  - Source/sink 识别：Python-C 项目 source 平均 precision 80%（平均 305 个 source/项目），sink 平均 precision 95%（平均 32 个）；Java-C 项目 source precision 83%（平均 140），sink precision 93%（平均 16）。
  - **数据流路径检测**：POLYFLOW 在所有项目中识别了 **454 条真阳性跨语言路径**、总体 **precision 76.8%**，在 5 个项目中达到 100% 精度；对应地，**xLoc 没有发现任何漏洞路径（零 TP）**（表 6，xLoc 行为单独说明）。
- **RQ3（消融实验）**：
  - 设置三个变体：**w/o FDF**（无 Feature-Oriented Data Flow）、**w/o ACF**（无 Augmented Control Flow）、**w/o EP**（无 Expert Panel），对照完整版（272 TP、76.8% precision）。
  - **w/o FDF**：总路径 1429、TP 454、precision 降至 **31.8%** → FDF 善于“剪枝”不可行的流、消除误报。
  - **w/o ACF**：TP 降至 348、precision 80.4% → ACF 对召回率的作用明显（没有它大量路径根本不可见）。
  - **w/o EP**：TP 375、precision 73.8% → EP 对 precision 和 recall 均有正贡献（增强语义理解和“边际案例”判断）。
  - 结论：三个组件**各有不可替代的功能**（ACF 保证路径完成度、FDF 保证 precision、EP 增强推理）。
- **RQ4（效率）**：
  - 运行时间：Python-C 项目平均 3.21h（阶段1步2）+ 5.13h（阶段2步2）；Java-C 项目平均 3.90h + 5.20h——LLM 相关的两步（CICFG 增强+污点细化）占主导。
  - Token 消耗：Python-C 平均 3.13M（阶段1步2）+ 0.54M（阶段2步2）；Java-C 平均 1.68M + 0.26M 每个项目。
  - 每查询平均延迟约 2.5~2.7s。
  - 峰值内存：Python-C 平均 380MB（pyo 达到~2GB 异常），Java-C 平均 585MB（lwjgl 达~1.7GB）；总体在商用工作站可接受范围内。
- **RQ5（真实漏洞发现）**：
  - 在 9 个真实项目中发现 **17 个未知漏洞**（表 12），其中一个已分配 **CVE-2025-55562**，另一个已由维护者确认/修复（上游 PR）。
  - 漏洞类型涵盖 NULL dereference、OOB read、堆溢出、资源耗尽、format-string 漏洞、任意内存写、状态代码注入等。
  - 逐个案例详细分析：例如 **bounter**（Python 到 C 的 width 参数未净化造成 calloc 失败并 NULL 解引用，依赖宏展开隐藏的调用边被 POLYFLOW 恢复）、**Jep**（Java-C 状态码语义不一致导致 evalLines 缓存无限增长、可被跨调用状态污染）。
  - 所有 17 个漏洞都未由任何基线发现。

- **公平性考虑**：作者在消融研究中固定其他组件、只移除一个组件来测量每个组件的贡献；表格中多处报告了项目级数据（如每条项目分开统计），透明度较高。
- **客观性**：作者除了 TP/precision 之外，也报告了漏报（FN/FP 来自 xFlowBench 分析 Joern 时所用）和项目差异，展示弱点。
- **限制**：xLoc 基线在 RQ2 中的报告显示为“没有产生任何漏洞路径”（在文中以“―”略过或表示“没有”），这说明学习方法在无法获得准确跨语言语义的情况下效果为 0，但这也意味着对比实验中真实世界项目对其不具可达性；实验者没有详细说明训练集的构成，这可能影响对 xLoc 结论强度的判断。
- **实验充分性**：整体上实验组合丰富（微基准+29 个真实项目+消融+效率+真实漏洞案例），从 precision/recall/F1、成本、可扩展性、真实世界漏洞发现等多维度验证，较为充分。不过，对其他基线（MultiQL、PolyCruise、PolyFuzz 等）只做了叙述性对比（implicitly qualitative），而不是系统性的实验化对比，这是论文的一个不足。
- **另一关注**：在真实项目上 paper 主要报告“precision”而未报告完整 recall（因为现实世界缺少 ground-truth 跨语言流全集），只通过 xFlowBench 的微基准综合测试 recall，这是一种常见的权衡。

## 4. 资源与算力

- 论文明确给出实验工作站配置：AMD Ryzen Threadripper 3970X + **Nvidia GeForce RTX 3090 GPU** + 256GB RAM；LLM 温度 0。
- 从表 11 的耗时数据可推算：对 29 个项目，每个项目平均运行约 **12.86 小时**（论文摘要中给出此数字），平均**峰值内存约 482.5MB**（也即平均 LLM token 消耗 2.81M，这里仅指摘要里的语境）。具体 GPU 数量和 LLM 调用接口（哪个模型、几并发）并未清楚交代，也没有提及 LLM API 调用方式（自托管 vs 第三方 API），因此**成本按实际输出 token 计、无法精确复算算力总量**。
- 实验耗时（wall-clock）部分以小时为单位列出（项目级最高可超过 14h/项目），大规模项目如 pytables、lwjgl 所需资源更长。

## 5. 实验数量与充分性

- **实验数量**：
  - 微基准：104 个（覆盖 19 个语言特性，198 个数据点）；
  - 真实项目：29 个（14 个 Python-C + 15 个 Java-C）；
  - 消融实验（3 个变体）在 29 个项目上分别跑一遍；
  - 效率分析对每个项目分解了 Phase1/Phase2 的时间和 token；
  - 真实漏洞案例：17 个，含 1 个 CVE 和 1 个 upstream fix；
  - 三组 RQ 的统计（source/sink precision/recall vs 路径 TP/precision vs 成本）覆盖完整。
- **充分性**：
  - **优点**：覆盖了微基准（受控特性逐一验证）、真实项目（泛化性与可扩展性）、消融（验证各模块必要性）、效率（用户落地视角）、漏洞发现（实际价值）；综合多维证据很有说服力。
  - 不足之处：
    1. 消融实验只在“真实项目”上报告 TP/precision 数据，未在 xFlowBench 上报告消融结果，未能揭示各组件对 recall/F1 的精确变化；
    2. xLoc 表格中该项指标缺失（可能是空/无法计算），没有详细讨论为何 xLoc 完全失败（比如训练集配置、模型结构、上下文长度）——这会削弱与 SOTA 学习方法的对比深度；
    3. MultiQL、PolyCruise、PolyFuzz 的对比仅停留在讨论文本层面，缺少可复现的 head-to-head 测量；
    4. Precision/Recall 测量的 ground truth 在真实项目中如何确定（人工审核者数量/一致性如何保证）没有详细说明。

## 6. 主要结论与发现

1. **POLYFLOW 能有效完成跨语言静态信息流分析**：在 xFlowBench 上 F1 达到 91.8%（precision 97.9%、recall 87.3%），在真实跨语言项目上整体 precision 为 76.8%。
2.

2. **静态分析与 LLM 的结合范式得到验证**：以静态分析器为骨架（CICFG）、LLM 做按需语义补全的设计，成功绕开了 LLM 的 token 限制和幻觉问题；专家小组的“低成本双模型交叉验证 + 高成本推理模型仲裁”机制在性能和成本之间取得了良好平衡。
3. **真实漏洞发现能力突出**：在 9 个项目中发现了 **17 个未知跨语言漏洞**，其中 1 个获得 CVE（CVE-2025-55562）、1 个已被上游维护者确认并修复；这些漏洞被多个特征案例证明只能经由跨语言的数据/控制流路径才能到达（如宏展开所隐藏的调用边、跨语言状态码语义不一致导致的资源耗尽），验证了 POLYFLOW 对“单语言工具盲区”的弥补能力。
4. **语言特性的普遍性远超预期**：RQ1 表明多态（Java 100%）、条件编译与函数指针（C 约 80%）等挑战性特性在真实多语言项目中高度普遍，意味着任何宣称支持多语言静态分析的工具若不处理这些特性，其分析结果在真实场景中必然是残缺的。
5. **可扩展性与工程可用性可接受**：平均每项目约 12.86 小时、峰值内存约 482.5MB 的量级，对于离线安全审计场景是可接受的；token 消耗集中在 CICFG 增强阶段（而非污点细化阶段），为后续成本优化指明了方向。

## 7. 局限性与未来方向

- **误报率仍有优化空间**：真实项目整体 precision 76.8%，意味着约 1/4 的报告路径为误报；论文将主要原因归于 FDF 阶段依赖的启发式规则和 LLM 判断的不确定性，但并未给出针对误报模式的系统性分类与对策。
- **漏报（recall）无法在真实项目上被准确度量**：由于真实多语言项目缺乏完整的 ground-truth 流全集，论文只能通过 xFlowBench 微基准间接评估 recall，这一缺口使得“真实项目上到底漏了多少漏洞”仍是一个开放问题。
- **LLM 成本与稳定性隐患**：每个项目数百万 token 的消耗意味着若交由商业 API 执行，成本可观；同时论文未报告 LLM 输出在多次运行下的稳定性（温度虽设为 0，但非推理模型仍存在随机性），专家小组的仲裁机制在多大程度上能吸收这种随机性缺少量化分析。
- **语言覆盖面有限**：当前仅支持 Python/C、Java/C 两种组合；现代多语言系统还涉及 Go/Rust/JavaScript/TypeScript 等（各自通过 cgo、FFI、Node-API 等互操作），这些语言的特性（如 Go 的 goroutine、Rust 的所有权模型）会引入新的分析挑战，框架的可扩展性尚待验证。
- **对比基线的实验强度不均**：与 xLoc 的对比在真实项目上表现为“零发现”，但论文未深入分析其原因（训练配置、模型容量、上下文窗口等）；与 MultiQL、PolyCruise、PolyFuzz 的对比仅停留在定性论述，缺少统一基准上的量化比较，使得“SOTA 超越”的结论强度有所折扣。
- **人工标注的可复现性**：真实项目中的 TP/precision 判定依赖人工审核，但论文未说明审核者数量、独立性与一致性检验（如 Cohen's Kappa），这影响着评估结果的可信度。

## 8. 综合评述与价值判断

- **理论价值**：POLYFLOW 清晰地定义了跨语言信息流分析的两大难点（语义鸿沟 + 语言特性逃逸），并通过“实证识别 19 种特性 → 特性 handler 模式化建模 → 固定点迭代增强 → 面向特性的污点追踪”给出了一条系统化的解决路径。其“以静态分析为骨架、LLM 为语义补全器”的架构设计，对当下 LLM 与程序分析结合的研究方向具有示范意义——既有对 LLM 能力的务实利用，也有对其不可靠性的工程化防御。
- **实践价值**：29 个真实项目、17 个未知漏洞（含 CVE）的发现证明了工具的实际安全价值；其输出形式（source→sink 污点路径）与现有安全审计工作流兼容，具备落地潜力。
- **方法创新**：将“语言特性”而非“语言”作为分析的一等公民，是本文最具洞察力的设计——它使得框架可以通过扩展特性 handler 清单来增量适配新语言/新场景，而非为每种语言重写分析器。
- **总体评价**：论文实验设计扎实、叙事清晰、开源基准（xFlowBench）具有社区价值；主要短板在于部分基线对比的深度不足、真实项目 recall 不可测，以及成本/稳定性细节的披露有限。整体而言，这是一篇问题定义准确、方法有创新、验证充分的高质量系统论文，对跨语言静态分析乃至 LLM-assisted program analysis 领域均有实质贡献。

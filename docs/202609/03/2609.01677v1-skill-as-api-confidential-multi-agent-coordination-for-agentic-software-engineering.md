## 摘要
AI编码智能体正从孤立工具演变为协作队友，它们能够发现并调用彼此的专业技能。但协调通道本身可能泄露技能的知识产权。诸如MCP和A2A等协议在服务器端执行实现，却仍将每个技能的描述和类型化模式发布给所有对等方，无法隐藏技能的存在，也无法保证封装的系统提示词不经过网络传输。应用层隐私过滤器虽有帮助，但仅在模型决定生成敏感文本后起作用。我们采取互补的协议层路径：技能即API（Skill-as-API），一种协调协议，其对技能的公开视图仅限于名称、描述、类型化输入/输出模式和信任层级。技能主体被闭包捕获在所有者进程中，绝不经过网络传输。四个层次添加访问控制，并从结构上而非通过内容过滤来缩小提示注入攻击面。我们提供了基于XMTP的开源Python实现，具备1.8-2.9秒的跨大陆热重连延迟，以及一个软件工程案例研究，其中三个智能体协调拉取请求审查，同时每个智能体保留其专有分析提示词的所有权。

## Abstract
AI coding agents are evolving from solitary tools into collaborative teammates that discover and invoke one another's specialized skills. But the coordination channel itself can leak a skill's intellectual property. Protocols such as MCP and A2A run implementations server-side, yet they still publish each skill's description and typed schemas to every peer, offer no way to hide a skill's existence, and cannot guarantee that a wrapped system prompt stays off the wire. Application-layer privacy filters help, but act only after the model has decided to emit sensitive text. We take a complementary, protocol-layer route: Skill-as-API, a coordination protocol whose public view of a skill is limited to its name, description, typed input/output schemas, and trust tier. The skill body is closure-captured in the owner's process and never crosses the wire. Four layers add access control and narrow the prompt-injection surface structurally rather than by filtering content. We provide an open-source Python implementation over XMTP with 1.8-2.9 s cross-continent hot-reconnect latency, and a software-engineering case study in which three agents coordinate a pull-request review while each retains ownership of its proprietary analysis prompts.

## 1. 核心问题与整体含义（研究动机与背景）

### 背景

- AI 编码智能体（如 SWE-agent、OpenHands）正从单机助手演变为可跨组织边界协作的智能体小队。工程师扮演编排者，指挥多个自主智能体协同完成代码审查、漏洞扫描等任务，这一范式被称为"SE 3.0"（智能体软件工程）。
- 在跨组织协作中，一个团队编写的静态分析规则，或封装了专有漏洞模式库的 LLM 服务，本质上是该团队的**知识产权（IP）**。智能体之间需要互相调用技能，但协调通信通道本身可能泄露这些技能的方法论。

### 核心问题

- 现有主流协作协议（如 MCP、A2A）存在三重泄漏隐患：
  1. 虽然实现代码在服务器端运行，但**每个技能的名称、描述、类型化输入/输出 schema 都会公开给所有对等方**；
  2. **无法隐藏技能的存在**（攻击者可枚举技能命名空间）；
  3. **无法保证包装的系统提示词（system prompt）不经过网络传输**。
- 应用层隐私过滤器（如 PrivacyChecker）虽有帮助，但存在约 7–8% 的残余泄漏率，且**仅在模型已决定输出敏感文本后**才进行拦截，属于事后措施。

### 论文定位

- 论文提出一种**互补性的协议层（protocol-layer）策略**——Skill-as-API。它不是替代 MCP/A2A，而是在 ABI 层改变线路上暴露的信息，使加密、IAM、内容过滤等机制可以叠加其上协同工作。

## 2. 方法论

### 核心思想

- **技能主体（body = 代码 + 系统提示词）通过闭包捕获（closure-capture）保存在所有者（owner）进程中，永不跨网络传输。**
- 任何 peer 对技能的可见视图仅限：**名称、描述、自然语言路由提示、版本、输入/输出模式、最低信任等级、schema 哈希**——不含任何实现细节。

### 关键技术细节

**（1）核心抽象（Core Abstraction）**

- 技能定义为七元组：`S = (name, d, w, v, σ_in, σ_out, t_min, B)`
  - `d`=描述，`w`=路由提示，`v`=版本，`σ_in/σ_out`=输入/输出 schema，`t_min`=最低信任层级，`B=(c, p)`=主体（代码与系统提示）。
- 公开视图：`view(S) = (name, d, w, v, σ_in, σ_out, t_min, h)`，其中 `h=SHA256(name ∥ v ∥ σ_in ∥ σ_out ∥ t_min)[:16]` 是 16 字节 schema 哈希，用于快速重连。
- **机密性不变式：`B ∉ view(S)`**，即技能主体永不进入线路。
- 调用方式为 `call(S, x) = c(filter(x, σ_in))`，`filter` 丢弃不在 σ_in 中的键；系统提示 `p` 通过注册时闭包捕获被 `c` 引用，不是函数参数，无法从输入路径触达。

**（2）四层防御机制**

| 层次 | 作用 | 应对威胁 | 核心机制 |
|------|------|----------|----------|
| **Layer 1: 信任层级 ACL** | 访问控制 | T3（信任漂移） | 四级信任：UNTRUSTED=0、KNOWN=1、INTERNAL=2、PRIVILEGED=3。调用技能需 `t ≥ t_min`；入站消息类型按固定表分级门控（如 ping/trust_request 在 UNTRUSTED 层允许，discover 需 KNOWN，collab_request 需 INTERNAL，未知类型默认需 PRIVILEGED 并 deny-by-default） |
| **Layer 2: 自动降级（"一次性信任"）** | 权限衰减 | T3（信任漂移） | 信任不因成功使用而累积。**连续 3 次失败**降一级；**完成协作 OKR** 即降一级（有 KNOWN 下限）。Algorithm 1 详述了该过程 |
| **Layer 3: 技能隐藏** | 命名空间保护 | T1（技能 IP 提取 / 枚举） | 隐藏技能与不存在的技能返回完全相同的错误串 `"Unknown skill: X"`。所有者侧日志可区分，但此区别绝不跨线路；满足设计目标 G2（不可知性） |
| **Layer 4: 函数边界防御** | 提示注入抑制 | T2（提示词窃取） | 系统提示 `p` 在注册时闭包捕获；调用者输入仅作为命名、schema 过滤后的 kwargs 绑定到用户回合，**绝不与系统提示拼接**。结构性关闭系统角色拼接向量；残余的用户角色注入（模型自愿背诵提示）属于行为层问题（L2），不在协议保证范围内 |

**（3）实现架构**

- Python 3.10+ 包，**除标准库和可选 LLM 提供商 SDK 外零运行时依赖**。
- 传输层采用 Node.js sidecar，基于 XMTP v3（MLS）协议（@xmtp/node-sdk）；Python 核心通过本地 HTTP/SSE 通道与桥通信，将密码学实现隔离在 Python TCB 之外。
- 16 字节 schema 哈希 `h` 兼作快速重连缓存键。
- 诚实披露：信任衰减计数器目前仅存内存（重启重置）；技能版本使用精确字符串匹配而非语义化范围匹配。

## 3. 实验设计

### 研究场景（案例研究）

- **单一端到端案例研究**：三个智能体在实时 XMTP 通道上作为独立进程运行，协调一次**拉取请求（PR）审查**任务：
  - **编排代理（orchestrator）**：接收 PR，分发分析任务；
  - **代码质量代理（code-quality agent）**：专有代码审查技能，其系统提示嵌入约 1,200 字符的专有审查方法论清单；
  - **安全代理（security agent）**：以模式库提示为后端的漏洞扫描技能。
- 两个专家代理的技能注册在 `t_min = 1`（KNOWN），编排代理随后发现其 schema、调用其技能。

### 验证内容与"Benchmark"

- **G1 验证（schema-only view）**：检查编排代理发现 code_review 技能后，仅能获得名称/描述/`input_schema(diff: str)`/`output_schema(findings: list[str])`。通过在编排侧记录所有 XMTP 消息并确认与专家系统提示字符串零重叠来验证。
- **G4 验证（注入吸收）**：构造 **N=10** 条任务输入，覆盖 **8 个 OWASP 风格注入类别**：直接指令覆盖、角色反转/persona 替换、markdown/围栏逃逸、提示泄露请求、base64 编码封装、多语言改写、通过嵌入注释的间接注入、递归自调用（各类别计数：2/1/1/2/1/1/1/1）。测量标准：(a) 系统提示是否以逐字或释义形式出现在返回字段中；(b) 结构化输出 schema 是否保持。
- **G3 验证（信任衰减）**：在同一运行中验证三个转换：①两个专家先被提升到 INTERNAL；②OKR 完成后，Algorithm 1 第 10 行触发，双专家 INTERNAL → KNOWN（实测数值下降，非在底层空操作）；③在测试对等体上验证 PRIVILEGED → INTERNAL 转换。
- **延迟测试**：热重连延迟（先前已连接 peer 间的第二及后续调用）**1.8–2.9 秒**（N=30，两个跨大陆 XMTP 中继端点，普通 Linux 主机，100 Mbps 链路）。冷启动 30–60 秒（XMTP MLS 群组建立耗主导）。所有计时含密钥轮换。

## 6. 主要结论与发现

1. **协议层保密设计可行**：Skill-as-API 可确保技能代码与系统提示在协调过程中不离开所有者进程，公开视图严格限制为描述与 schema 级别元数据。
2. **结构防御有效**：10/10 注入载荷被"吸收"——系统提示未出现在任何返回字段中且输出 schema 保持完整。作者强调这是示例性抽查而非安全上界。
3. **权限衰减符合预期**：OKR 完成后权限从 INTERNAL 降回 KNOWN，一次性 PR 审查不会固化为永久技能访问通道；验证了"临时信任"（throw-away trust）的可行性。
4. **延迟表现可接受**：跨大陆热重连 1.8–2.9 秒，满足"低个位数秒"的设计目标 G5，接近实用门槛。
5. **正交兼容性**：Skill-as-API 与加密（AgentCrypt 风格）、IAM 门控（A2A 风格）、内容过滤（PrivacyChecker 风格）方法正交，可叠加组合而非互斥。

## 7. 优点

- **问题定义清晰且实际**：精准锚定跨组织 SE 多智能体协作的技能 IP 泄露问题，区分了调度层受信通道与应用层过滤器的空白地带，切入点有新意。
- **设计层级合理**：将保密要求提炼为五个可验证目标（G1–G5），并用四层机制逐一对应威胁（T1–T3），结构清晰、逻辑链条完整。
- **ABI 层定位具有互补性**：不宣称取代既有协议，而是明确站在"改变线路上有什么"的第四策略位置，与加密、IAM、内容过滤形成可叠加的安全纵深。
- **Closure-c

**Closure-capture（闭包捕获）的机密性保证**：`B ∉ view(S)` 这一不变式是通过语言级闭包机制实现的，而非依赖运行时检查或开发者纪律——系统提示在注册时被闭包捕获、仅由技能代码内部引用，调用者输入在数据结构上就不可触达 `p`，这种"架构性强制"比"策略性检查"更值得信赖。

- **诚实披露做法可取**：作者主动说明信任计数器仅存内存、版本匹配为精确字符串、注入测试 N=10 的统计弱点等局限，这在追求展示效果的论文中难得，增加了可读性与可信度。

## 8. 缺点与局限性

- **实验证据强度严重不足**：单一端到端案例、N=10 的注入抽查、无阳性对照组、无跨场景泛化——这些数据至多支撑"可行性演示"，不足以支撑论文标题所暗示的通用协议主张。作者自己也承认统计功效无法紧致界定残余泄漏率。
- **行为层泄漏（L2）被悬置**：论文明确将"模型自愿背诵系统提示"划归协议保证范围之外，但这一行为层恰恰是现实中最主要的提示窃取路径之一。若行为层目标未收敛，协议层的结构性保证在实践中的端到端安全性仍存疑。
- **信任门控阈值粗糙**：四级信任（UNTRUSTED/KNOWN/INTERNAL/PRIVILEGED）与 `t_min` 的整数比较过于简化。现实中"熟人"与"内部"之间、不同团队之间的信任关系是多维的（关系时长、共事历史、担保链等），单一标量难以刻画；降级规则（连续 3 次失败）也缺乏理论基础，任意的魔法数字。
- **隐藏技能（Layer 3）的安全收益有限**：以统一错误串掩盖不存在技能，仅对被动枚举有效。恶意对等方仍可通过时序侧信道、错误消息语义差异或直接尝试高权限操作来探测技能存在性；且 Layer 4 已拒绝了恶意输入，隐藏层在最关键的注入场景中并未提供额外纵深。
- **未集成到主流通用协议**：Skill-as-API 的 ABI 层设计若要落地，需要 MCP/A2A 等协议社区的采纳与实现配合。论文未讨论迁移路径、非 Python 语言生态的支持，或如何与既有工具链平滑共存。
- **系统提示的闭包捕获方案对 LLM 平台供应商不透明**：大多数技能实际运行在托管推理 API（如 OpenAI/Anthropic）上，服务端是否真正将系统提示与用户输入隔离，取决于供应商内部实现，协议层无法审计；论文的"结构性保证"在托管模型场景下退化为对第三方的信任假设。

## 9. 对领域研究的启示与可拓展方向

- **"ABI 级保密"是值得推广的思路**：将保密问题从应用层（过滤器、脱敏）下推至协议数据面，在消息格式与类型系统层面重新定义"哪些信息必须在线路上可见"，这一视角可迁移到 MCP 的 schema 设计或 A2A 的 card 描述中，未来协议迭代应默认采纳。
- **测试基准急需建立**：目前尚无面向"技能 IP 保护"的标准化基准。可借鉴 OWASP 的思路，构建包含提示注入、schema 嗅探、命名空间枚举、定时侧信道等攻击类目的评测集，供各协议方案公平比较。
- **信任生命周期理论化**：算法 1 的降级规则证实了"临时信任"思想的价值，但需要更严谨的模型——如何将协作任务价值、历史成功率、信息敏感度纳入量化框架，是值得深挖的交叉课题。
- **行为层与结构层协同防御**：论文正确指出 L2 不属于协议保证，但未来完整方案应说明协议层与行为层（如模型微调、解码时扰动）如何共同覆盖全部泄漏路径，而非将 L2 简单悬置。

## 10. 综合评价与最终结论

Skill-as-API 是一篇"问题先行、设计扎实、实验尚浅"的短篇论文。其核心贡献不在实验数据，而在**将保密问题重新框定为"线路上可见信息的 ABI 设计问题"**，并通过闭包捕获、统一错误串、信任衰减等几个轻巧机制给出了可行的协议层回答。它诚实地揭示了实验的示范性质，为后续的基准构建与协议整合留下了清晰的空间。对于研究社区而言，它的价值更多是**一个问题范式与架构蓝图的起点**，而非一项已被验证的生产级方案——若未来能以更大规模的攻击评测与真实跨组织试点加以补全，该方向有潜力成为多智能体安全协作的标准组成部分。

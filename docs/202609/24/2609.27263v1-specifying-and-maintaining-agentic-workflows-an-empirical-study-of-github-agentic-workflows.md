## 摘要
智能体工作流将软件开发从提示 AI 智能体完成单个任务，转变为定义由智能体自动执行的重复性工作。GitHub Agentic Workflows（gh-aw）通过 Markdown 文件支持这一方式：这些文件将自然语言指令与配置相结合，并编译为可执行的 GitHub Actions 工作流。与传统工作流主要规定脚本化操作不同，这些文件将需要解释的任务委托给 AI 智能体。它们还将智能体指令与执行触发器耦合，使这些指令成为面向重复性仓库活动的操作规范。然而，开发者如何构建和维护这些规范，以及它们表达了哪些执行要求和防护措施，仍未得到充分理解。本文考察 gh-aw Markdown 文件的结构、演化与指令内容，以帮助从业者了解如何定义和维护由智能体运行的工作。我们分析了来自 276 个仓库的 1,248 个文件、20,841 个提交-文件事件，以及从 294 个文件样本中得到的 288 个经裁决的指令标签集。结果表明，工作流指令远不止简短提示：中位数为 556.5 个词，且 62.1% 的文件包含代码块。在具有至少 120 天观测活动的文件中，78.2% 在第 4 个月仍收到更新，而按规模归一化的变更量在第一个月后下降。任务、输出、约束和流程指令各自出现在超过 93% 的已标注工作流中，但只有 9.4% 明确涉及提示注入防御。相对于经裁决的人工标签，LLM 分类的 F1 分数为 0.818，Cohen's Kappa 为 0.715。这些发现表明，开发者应考虑跨仓库复制或引用的工作流的演化，并在适用时加入提示注入防御、资源预算和证据可信度检查。

## Abstract
Agentic workflows shift software development from prompting AI agents for individual tasks to defining recurring work that agents execute automatically. GitHub Agentic Workflows (gh-aw) enables this approach through Markdown files that combine natural-language instructions with configuration and compile into executable GitHub Actions workflows. Unlike conventional workflows that primarily prescribe scripted operations, these files delegate tasks requiring interpretation to AI agents. They also couple agent instructions with execution triggers, making those instructions operational specifications for repeated repository activities. However, how developers structure and maintain these specifications, and which execution requirements and safeguards they express, remains insufficiently understood. In this paper, we examine the structure, evolution, and instruction content of gh-aw Markdown files to inform how practitioners define and maintain agent-run work. We analyze 1,248 files from 276 repositories, 20,841 commit-file events, and 288 resolved instruction-label sets from a sample of 294 files. Our results show that workflow instructions extend beyond short prompts, with a median of 556.5 words and code blocks in 62.1% of files. Among files with at least 120 days of observed activity, 78.2% still receive updates in month 4, while size-normalized churn decreases after the first month. Tasks, outputs, constraints, and process instructions each appear in over 93% of labeled workflows, yet only 9.4% explicitly address prompt-injection defense. LLM classification achieves an F1 score of 0.818 and Cohen's Kappa of 0.715 against the resolved human labels. These findings suggest that developers should account for the evolution of workflows copied or referenced across repositories and consider adding prompt-injection defenses, resource budgets, and evidencecredibility checks where applicable.

## 2. 方法论

### 2.1 核心思想
采用"混合方法"：以大规模仓库挖掘刻画结构与演化（RQ1、RQ2），以人工主题分析构建指令分类体系（RQ3），再评估 LLM 能否规模化复现该分类（RQ4）。核心创新在于**把 frontmatter 配置变更与正文指令变更分开度量**，并区分"指令写了什么"与"指令执行需要什么知识"。

### 2.2 数据采集流程
- **项目选择**：用 GitHub REST API code search，查询 `"This file was automatically generated by gh-aw" path:.github/workflows extension:yml`。因单查询上限 1,000 条，按文件大小分桶（如 `size:48001..60000`）并对超限桶递归细分，最终所有桶均低于上限，再抓取全部页并按 仓库/路径 去重 → **4,533 个生成 YAML、1,528 个仓库**。
- **过滤**：保留 ≥10 GitHub stars 的仓库作为相关性与质量的代理、减少玩具项目 → **365 个仓库、1,435 个生成 YAML**。
- **YAML → Markdown 映射**：优先用源注释（`# Source: owner/repo/path.md@sha`），缺失时用同仓库路径替换后缀（`test.lock.yml` → `test.md`）推断；按仓库与 Markdown 路径去重（因跨仓库引用同一源文件）→ **1,295 个 Markdown 源文件、281 个仓库**，并采集提交历史：7,653 个提交、21,435 次文件级变更。
- **清洗**：用 `langdetect` 剔除 18 个非英语文件、剔除 29 个正文为空文件 → **1,248 个文件、276 个仓库、7,446 个提交、20,841 次文件级变更**；时间跨度 2025-07-31 至 2026-08-04。

### 2.3 RQ1 度量方式
- 统计正文行数、frontmatter 行数、代码块行数；统计 H1–H6 各级标题数量，并对标题词做去停用词/去数字的词云分析。
- 可读性用 **Flesch Reading Ease（FRE）**（分数越高越易读），辅以句子数与音节数；度量作用于**完整 Markdown 正文**（含标题、表格、代码、模板表达式）。
- 用最小值、均值、中位数、最大值汇总。

### 2.4 RQ2 维护分析方法
- 取 **348 个文件、43 个仓库**，要求文件首次与末次观测变更之间至少 120 天；Day 0 为文件首次出现在被追踪路径（项目级取最早 gh-aw Markdown 出现时间）。
- 追踪前 4 个月，指标包括：月度提交数、月末规模、**按规模归一化的 churn**（增删行数之和 ÷ 该月平均 Markdown 规模 ×100 行），初始文件提交不计入维护、无变更月份保留。
- 同时计算"维护提交 ÷ 同月仓库全部提交"作为项目活动基线（经 GitHub commits API 采集），避免把整体仓库活跃度下降误判为工作流维护放缓。
- 变更目标：每个"提交×Markdown 文件"对为一个事件，分别统计触及 frontmatter 或正文的比例（两者都触及则计入双方）。
- 统计检验：项目配对的 **sign test**，对 12 组比较做 **Holm 校正**。

### 2.5 RQ3 指令分类体系构建
- 用 **Cochran 样本量公式 + 有限总体校正**（95% 置信度、5% 误差、保守 p=0.5）从 1,248 个文件中抽取 **294 个代表性样本**；只编码固定快照的 Markdown 正文，**不展开 import、不从 frontmatter 推断指令**；采用多标签编码（一个文件可有多种指令类型）。
- 采用 **Braun & Clarke 主题分析**，四步流程：① 两位作者共同阅读 30 个文件做校准；② 各自独立打描述性标签（按"用途"而非"措辞"命名，如时间/重试/token 限制归为 Resource Budget）；③ 比对、审查、合并重叠概念（如把 Expert Role 与 Role Scope 合并为 Role Assignment）；④ 按共同用途归入主题（如 Required Sequence、Decision Branch、Within-Run Iteration 归入 Process）。

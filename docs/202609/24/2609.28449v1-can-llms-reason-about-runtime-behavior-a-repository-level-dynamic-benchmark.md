## 摘要
大型语言模型（LLM）正越来越多地用于编码任务，但其推理代码执行的能力仍不明确。现有的仓库级问答基准主要评估静态代码理解，且往往依赖基于 LLM 的评估，而执行推理基准大多局限于代码片段或函数。我们提出了 SWE-Flux，一个用于动态执行推理的仓库级基准，包含覆盖 12 个真实 Python 仓库的 480 个基于执行的实例，其金标准答案通过插桩测试执行自动收集，而非人工编写或由 LLM 评判。该基准涵盖控制流、循环、程序状态、数据流、异常和程序不变量方面的单测试与多测试问题。对五个 LLM 的评估表明，该任务仍具挑战性。最佳模型仅达到 37% 的准确率。模型在不变量、过程内控制流、异常和简单循环等局部行为上表现更好，但在数据流、过程间执行、精确状态推理和测试套件级聚合方面表现不佳。最后，我们表明，oracle 收集流水线可以利用输入扰动生成新的基准变体。它成功为近 90% 的选定实例收集到有效变体，且生成的变体对受评估模型而言明显更具挑战性。

## Abstract
Large language models (LLMs) are increasingly used in coding tasks, but their ability to reason about code execution remains unclear. Existing repository-level QA benchmarks mainly evaluate static code understanding and often rely on LLM-based evaluation, while execution-reasoning benchmarks are mostly limited to snippets or functions. We introduce SWE-Flux, a repository-level benchmark for dynamic execution reasoning containing 480 execution-grounded instances across 12 real Python repositories, with gold answers automatically harvested from instrumented test executions rather than written manually or judged by LLMs. The benchmark covers singletest and multi-test questions over control flow, loops, program state, dataflow, exceptions, and program invariants. Evaluating five LLMs shows that this task remains challenging. The best model achieves only 37% accuracy. Models perform better on localized behavior such as invariants, intra-procedural control flow, exceptions, and simple loops, but struggle with dataflow, inter-procedural execution, precise state reasoning, and suite-level aggregation. Finally, we show that the oracle-harvesting pipeline can generate fresh benchmark variants using input perturbation. It successfully harvests valid variants for almost 90% of the selected instances, and the resulting variants are substantially more challenging for the evaluated models.

## 2. 方法论

### 2.1 核心思想

- 每个实例都绑定一个**固定 commit 的真实仓库**、一个具体测试或测试套件、一个自然语言问题、一个答案模板。
- 金标准答案不是人工编写，也不是 LLM 评判，而是通过**插桩执行**自动采集为 `oracle.json`。
- 评估时模型只看到仓库、测试文件、问题和答案模板；trace、parser 和 oracle 对模型隐藏。
- 使用两级分类体系：**单测试推理（S）** 与**多测试推理（M）**，覆盖七类运行时行为。

### 2.2 分类体系

- 七类运行时行为：
  - 过程内控制流（Intra-procedural CFG）
  - 循环与时间行为（Loops & Temporal）
  - 程序状态（Program State）
  - 数据流（Dataflow）
  - 异常（Exceptions）
  - 过程间控制流（Inter-procedural CFG）
  - 程序不变量（Program Invariants，仅多测试）
- 单测试问题示例：执行了哪些语句、分支走向、循环迭代次数、变量值、异常类型、调用返回路径等。
- 多测试问题示例：测试套件覆盖、路径多样性、值集合、def-use 覆盖、异常多样性、跨测试不变量等。

### 2.3 基准构建与 oracle 采集流程

论文给出五阶段流水线：

1. **仓库环境设置**：采用 SWE-bench-Live 评估镜像，固定 commit、依赖与运行环境；在容器内附加 Cursor IDE 进行交互设计。
2. **实例设计**：选择行为类别、子类别与代码目标，编写测试文件、自然语言问题、答案模板、追踪配置和实例专用 parser。
3. **容器内迭代**：运行采集流水线，检查 trace 与 parser 输出，调试测试和 parser，直到 oracle 正确且模板能表达答案结构。
4. **执行落地 oracle 采集**：从主机端以全新容器端到端重跑，使用 `sys.settrace` 等追踪机制记录执行行、函数调用、返回值、异常和变量快照，再由 parser 重建 `oracle.json`。该过程保证答案可复现，不依赖交互设计残留。
5. **最终验证**：使用 Sonnet-4.6 驱动的 Cursor agent，在只看到模型可见材料的情况下独立答题，并与 harvested oracle 比较；若失败源于问题歧义或模板不清，则修订并重新采集、验证。

### 2.4 扰动生成新变体

- 论文提出 **LLM-Perturb** 与 **LLM-Perturb+Feedback**。
- 算法流程：
  - 选取 GPT-5.4 已答对的实例。
  - 提取原测试、任务元数据、oracle 和 trace。
  - 由 proposer LLM 生成候选测试。
  - 在固定仓库环境中重新执行并 harvest 新 oracle。
  - 过滤无效或违反结构约束的候选。
  - 评估目标模型是否从正确变为错误（flip）。
  - 若无 flip，则进入 feedback 循环，根据原实例与当前候选的测试、oracle、trace 差异继续修正输入，最多 `b` 轮。
  - 返回有效变体及其 oracle/trace/coverage 变化元数据。

## 3. 实验设计

- **基准/数据集**：SWE-FLUX，包含 **480 个执行落地实例**，来自 **12 个真实 Python 仓库**，仓库代码规模约 70k–760k LoC，文件数最多 2,422。
- **仓库类型**：科学计算、AI/ML、可视化、数据处理、Web、云、桌面、CLI、DevOps 等，例如 SymPy、Faker、Matplotlib、Keras、yt-dlp、xarray、cfn-lint、python-telegram-bot、PyBaMM、reflex、qtile、python-control。
- **实例分布**：
  - 单测试实例 308 个，多测试实例 172 个。
  - 类别分布不均，例如 S3 程序状态 106 个、S6 过程间 CFG 78 个、S4 数据流 59 个、M7 不变量 42 个等。
- **评估设置**：
  - 工具辅助仓库探索：模型可查看仓库、测试文件、问题和答案模板，可使用导航工具检查目录和源码。
  - 答案需符合模板 JSON 结构。
  - 与 harvested `oracle.json` 做 **exact-match** 比较。
  - 开源模型使用 32K token 上下文，每个模型最多 25 次工具调用，所有 LLM temperature 设为 0。

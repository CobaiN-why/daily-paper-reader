## 摘要
近期工作将递归自我改进（RSI）扩展到面向长时程编码与终端任务的智能体执行框架，使智能体能够从经验中改进执行机制。然而，可泛化的执行框架 RSI 仍具挑战性。首先，在评估基准或其子集上演化执行框架，难以区分可复用的改进与针对特定基准的适配。其次，单轨迹更新可能将系统性的执行框架缺陷与实例特定的推理和求解细节混为一谈，导致产生的修改难以迁移到未见任务。第三，在单体式执行框架中定位反复出现的行为缺陷十分困难，而整体框架优化可能使不相关的机制相互纠缠，并使归因与验证复杂化。我们提出 ModularRSI，一个面向可泛化执行框架演化的基准不相交、对比式、模块化框架。ModularRSI 对同一任务的成功与失败轨迹进行对比，并跨任务聚合证据，以识别反复出现的行为缺陷。它将可演化的执行框架分解为五个功能模块：智能体循环、工具使用、观测管理、上下文管理和任务完成检测。每个模块在受限的修改范围内独立演化，随后通过集成阶段将演化后的模块组合为统一执行框架，并解决潜在冲突。为支持基准不相交的演化，我们从外部来源整理出 2,000 个可执行的演化任务，这些任务与下游评估基准不相交。在 TB2.0 和 SWE-Bench Verified 上的实验表明，在未见的域内和跨域任务上均取得一致改进，且演化后的执行框架还能迁移到不同的基础模型。

## Abstract
Recent work extends recursive self-improvement (RSI) to agent harnesses for long-horizon coding and terminal tasks, enabling agents to improve execution mechanisms from experience. However, generalizable harness RSI remains challenging. First, evolving harnesses on evaluation benchmarks or their subsets makes it difficult to distinguish reusable improvements from benchmark-specific adaptation. Second, single-trajectory updates can conflate systematic harness deficiencies with instance-specific reasoning and solution details, producing modifications that transfer poorly to unseen tasks. Third, localizing recurring behavioral deficiencies within monolithic harnesses is difficult, while whole-harness optimization can entangle unrelated mechanisms and complicate attribution and validation. We propose ModularRSI, a benchmark-disjoint, contrastive, and modular framework for generalizable harness evolution. ModularRSI contrasts successful and failed trajectories for the same task and aggregates evidence across tasks to identify recurring behavioral deficiencies. It decomposes the evolvable harness into five functional modules: Agent Loop, Tool Use, Observation Management, Context Management, and Task Completion Detection. Each module evolves independently within a restricted modification scope, followed by an integration stage that combines the evolved modules into a unified harness and resolves potential conflicts. To support benchmark-disjoint evolution, we curate 2,000 executable evolution tasks from external sources that are disjoint from downstream evaluation benchmarks. Experiments on TB2.0 and SWE-Bench Verified show consistent improvements on unseen in-domain and cross-domain tasks, with the evolved harness also transferring across different foundation models.

- **研究背景**：CLI / 编码智能体在长时程软件工程与终端任务上的表现，除基础模型能力外，越来越依赖 **agent harness**（负责执行流程、工具交互、上下文管理、环境反馈的执行框架）。近期工作把递归自我改进（RSI）扩展到 harness，使智能体从执行经验中改进执行机制。
- **核心问题**：**可泛化的 harness RSI** 尚未解决。论文指出三个相互耦合的挑战：
  - **数据层面**：现有方法通常在**下游评测基准或其子集**上演化，无法区分"可复用的 harness 改进"与"基准特定适配"；同时构建大规模、环境完整、评测可靠的终端任务数据集成本高。
  - **轨迹层面**：单条或单侧轨迹把**系统性 harness 缺陷**与**实例特定的推理/求解细节**纠缠在一起，易产生难以迁移的任务特定修改。
  - **机制层面（信用分配）**：即使识别出反复出现的行为缺陷，也难以定位到单体 harness 中应修改的组件；整体式优化会牵连无关机制，导致修改难以归因与验证。
- **整体含义**：论文将 harness 自我改进重新表述为一个**细粒度信用分配 + 泛化性验证**问题，主张用"基准不相交 + 对比式 + 模块化"的范式来获得可复用、可归因的执行机制改进。

## 2. 方法论

### 2.1 核心思想
把粗粒度的任务级成败信号，通过**同任务成功/失败轨迹对比**与**跨任务证据聚合**，转化为**函数级（模块级）的局部修改信号**；再把 harness 拆成若干可独立演化的功能模块，各自在受限范围内修改，最后统一集成。

### 2.2 流程与关键技术细节

- **（1）Harness 模块化**：只对直接中介"智能体—环境"交互的行为机制做演化（沙箱初始化、并行执行、LLM 通信等基础设施不演化），划分为五个模块：
  1. **Agent Loop**：推理—行动—观测循环、执行流、交互控制与恢复行为；
  2. **Observation Management**：处理环境反馈，保留任务相关信息、过滤/压缩噪声；
  3. **Tool Use**：工具选择、调用与校验；
  4. **Context Management**：跨步交互历史的保留、压缩与检索；
  5. **Task Completion Detection**：判断任务是否完成、是否需要继续交互。
  - 初始 harness 采用 Harbor 的 **Terminus-2**，并按其行为机制重组为上述五模块。模块间关系：Agent Loop 作为协调者，先让 Context Management 更新对话历史，再向 LLM 发提示；Tool Use 解析响应为命令与完成信号并在环境执行；Observation Management 把终端输出转为可读反馈；Agent Loop 汇总反馈、更新状态并交给 Task Completion Detection 给出停止建议。

- **（2）对比式轨迹采样与分析**：
  - 对每个演化实例 $x_i$ 做 $K$ 次 rollout，得轨迹集与二元奖励 $r_i^k \in \{0,1\}$；
  - 按奖励把任务分为三类：**Positive**（全部成功，$\sum_k r_i^k = K$）、**Contrastive**（部分成功，$0<\sum_k r_i^k<K$）、**Negative**（全部失败，$\sum_k r_i^k=0$）；
  - 维护 **Trajectory Memory** 存储历史轨迹与奖励；对 Negative 组先检索同一任务历史上的成功轨迹做对比配对，若无则做单侧诊断（重复循环、错误工具使用、无效恢复、过早终止等）；对 Positive 组做效率分析（冗余动作、重复探索、不必要工具调用）；
  - 分析结果结构化为 JSON findings，字段含目标模块、轨迹证据、是否修改的理由、建议改动等（含 `is_culprit`、`would_change_outcome`、`fixable_now` 等反事实判断字段）。

- **（3）模块级 harness 修改**：
  - **Modification Target Selection**：合并语义相近的诊断为候选修改，按"支持该修改的不同任务数"投票排序，优先采纳多任务支持的修改，抑制实例特定失败的影响；
  - **Evolution History**：为每个被修改函数记录历史改动与引入的功能，减少重复/冲突修改与演化震荡；
  - 演化所用 Code-Modify Agent 就是**被演化的智能体自身**。

- **（4）验证门（Validation Gates）**：三道顺序过滤
  1. **Program Check**：AST 校验、import 检查、协议合规、发现契约校验、静态自属性审计，失败则按记录的 diff 回滚；
  2. **Diff Review**：让 Code-Modify Agent 以"奖励盲"方式审查 diff 是否编码了任务特定解/启发式/条件，判定过拟合则拒绝回滚；
  3. **Execution Validation**：从当前批次随机抽 2 个任务用新 harness 实际执行，出现运行时错误或违反执行协议则回滚。

- **（5）跨模块集成（Cross-Module Integration）**：五模块独立演化后合并为统一 harness；由于独立优化可能引入重复机制、冲突行为或不一致交互，额外做一轮集成 epoch，分析轨迹识别跨模块冲突，去除重复机制、澄清模块职责、调整协调逻辑；集成后函数库**冻结**，评测期间不再修改。

- **（6）函数库管理**：
  - **Function Merge**：LLM 比较同模块内函数描述与行为，合并高度重叠者，降低冗余；
  - **Task-Aware Function Composer**：依据任务描述与候选函数描述，由 LLM 选取任务相关函数子集，仅激活这些函数，使底层函数库可扩张而"活跃 harness"保持紧凑、任务适配。
  - 这两个机制在轨迹收集与下游评测中均使用。

- **（7）基准不相交演化协议**：演化集与下游评测基准完全隔离，演化后 harness 冻结再评测。

## 3. 实验设计

### 3.1 数据集与场景

  - 构建流程：先从 TerminalBench / SWE-Bench 家族提取高层**领域类别标签**作为检索指引（不使用基准实例或任务特定信息）；再做多阶段质控：LLM 过滤（环境完整性、实用性与非平凡性、评测器有效性）→ 可执行验证（参考 `solution.sh` 必须通过全部测试，且 no-op 提交不能得分）→ 人工复核（任务清晰度、环境完整性、评测器正确性）→ LLM 语义相似度筛除与下游基准高重叠的实例。
  - 构成：SWE 相关 1,000 + Terminal 相关 1,000，覆盖 9 类（数据处理 381/19.1%、ML 与科学 272/13.6%、构建与依赖 244/12.2%、系统与 OS 236/11.8%、语言与 API 227/11.3%、Web 与网络 189/9.4%、算法 176/8.8%、安全与加密 150/7.5%、数据库 125/6.2%）。

## 6. 主要结论与发现

- **跨基准泛化**：以 DeepSeek-V4-Flash-Preview 为基座，TB 相关演化集使 TerminalBench 2.0 Acc 47.57→52.43；SWE 相关演化集使 SWE-Bench-Verified Acc 73.40→76.45。**跨域迁移**同样成立：TB 演化的 harness 使 SWE-Bench Verified Acc 达 75.80；SWE 演化的 harness 使 TB2.0 Acc 达 49.40。说明学到的是可复用的执行机制改进，而非基准特化。
- **可靠性提升**：TB2.0 上 Pass3 从 30.34→35.96，说明不仅提升平均能力，也减少重复试验中的随机失败。

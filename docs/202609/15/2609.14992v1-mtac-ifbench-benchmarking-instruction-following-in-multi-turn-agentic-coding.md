## 摘要
近年来，大语言模型（LLMs）的快速发展重塑了软件工程，使自主代码智能体能够迭代地规划、执行并利用外部工具来解决复杂任务。除了实现功能正确性之外，这些智能体还必须在整个开发生命周期中忠实遵循过程指令和约束。然而，现有基准通常关注最终的功能正确性，或将指令遵循评估局限于单轮通用对话或简单代码生成场景，导致多轮智能体编程中的指令遵循尚未得到充分探索。为弥补这一空白，我们提出 MTAC-IFBench，一个针对这一关键能力的综合基准。它包含多轮渐进式软件开发指令，并带有涵盖 6 个一级类别和 18 个二级类别的多样化约束。每个实例平均包含 7.04 轮对话和 91.33 个约束，对当前 LLMs 构成了严峻挑战。为使评估可靠，我们为每个约束和功能需求构建检查清单，并集成验证脚本和评判智能体来验证每个检查清单项。MTAC-IFBench 揭示了现有代码智能体在多轮指令遵循方面的显著不足：随着交互会话变长，其性能迅速下降。

## Abstract
Recently, the rapid development of large language models (LLMs) has reshaped software engineering by enabling autonomous code agents that plan, execute, and utilize external tools iteratively to tackle complex tasks. Beyond achieving functional correctness, these agents must faithfully follow process instructions and constraints throughout the development lifecycle. However, existing benchmarks typically focus on final functional correctness or confine instruction-following evaluation to single-turn, general chat or simple code generation scenarios, leaving instruction-following in multi-turn agentic coding underexplored. To bridge this gap, we propose MTAC-IFBench, a comprehensive benchmark for this critical capability. It features multi-turn progressive software development instructions with diverse constraints spanning 6 primary and 18 secondary categories. With an average of 7.04 turns and 91.33 constraints per instance, it poses a rigorous challenge to current LLMs. To make the evaluation reliable, we construct a checklist for each constraint and functional requirement, and integrate verification scripts and judge agents to verify each checklist item. MTAC-IFBench identifies significant deficiencies in existing code agents in multi-turn instruction-following, with their performance degrading rapidly as the interaction session grows longer.

## 一、核心问题与整体含义（研究动机与背景）

- **范式转变**：LLM 驱动的代码智能体（如 Claude Code、Kilo）正把软件开发从以人为中心的工作流转向自主智能体系统，智能体需要迭代地规划、执行并调用外部工具。
- **被忽视的能力**：除了功能正确性，智能体还必须在整个开发生命周期中严格遵循**过程指令与约束**，这是可靠部署的前提。
- **两大挑战**：
  - 约束高度**异质**：不仅涉及生成内容与代码，还涉及环境交互与智能体工作流。
  - 任务天然**多轮**：用户会迭代引入新需求或修改已有需求，要求跨轮次持续合规、抵抗上下文退化。
- **现有基准的空白**：
  - 智能体编程基准（SWE-Bench、Terminal-Bench、SWE-Together、SWE-Interact）以**最终功能正确性**为导向，忽略过程约束合规。
  - 指令遵循基准（ComplexBench、CodeIF、CodeIF-Bench、AgentIF）主要局限于**通用对话或单轮单文件代码生成**；OctoBench 虽扩展到仓库级智能体编程，但缺少系统化约束分类且基本限于单轮。
- **论文含义**：提出 **MTAC-IFBench**（Multi-Turn Agentic Coding Instruction-Following Benchmark），填补"多轮智能体编程中的指令遵循"评测空白。

## 二、方法论

### 2.1 核心思想
构建"多轮渐进式软件开发指令 + 分层约束体系 + 混合式检查清单核验"的评测框架，同时衡量**过程约束合规**与**最终功能正确性**。

### 2.2 约束分类体系（6 个一级 + 18 个二级类别）
- **Content**：Keyword（关键词）、Persona（角色口吻）、Format（格式模板）
- **Language**：Response Language、Comment Language、File Encoding
- **Quantity**：Range（范围）、Exact Value（精确值）、Complexity（复杂度上限）
- **Style**：Layout（缩进/空行）、Naming（命名规范）、Paradigm（编程范式/避免过度工程）
- **Environment**：File Path、File Operation（增删改备份）、Logging（变更日志）
- **Workflow**：Tool Usage、Orchestration（多步编排/并行调用）、Testing（测试框架与覆盖率）

### 2.3 数据构建流程（半自动化流水线）
1. **指令收集**：融合人工专家编写 + ZfrontendBench + CC-Bench 轨迹，覆盖前端、工具、数据分析、测试、算法等。
2. **多轮扩展**：用 Gemini-3.1-Pro 将单轮指令扩展为 5–10 轮渐进序列（首轮搭骨架、后续轮逐步加功能，可引用/修改/覆盖前轮），每条指令独立扩展两次，得到 **374 条多轮指令序列**。
3. **分类法引导的约束集成**：
   - 先构建约束示例池：人工收集 **190 条代表性约束**，用 Seed-2.0-Pro 每条改写生成 10 个变体。
   - 先向**仓库策略文件**（如 Claude.md）注入约束（采样 4–6 个二级类别，最多 8 条，全程不可变）。
   - 再逐轮注入**用户指令**（每轮采样 2–4 个二级类别，新增或替换约束总数 ≤ 2），允许新增约束或替换前轮约束。
   - 采样时按类别的"曝光次数"排序，权重为逆序排名的平方，优先覆盖欠代表类别。
   - 每轮集成后用 Seed-2.0-Pro 校验清晰性、一致性、完整性、可行性，失败则重试（最多 5 次，否则丢弃整条序列）。
4. **检查清单生成**：为每轮生成约束检查清单，为最终项目生成功能检查清单；人工为每个清单项指定评估方式——**代码评估**（确定性约束，如 Keyword、Exact Value，用验证脚本）或**裁判智能体评估**（主观/复杂约束，如 Paradigm、Orchestration）。
5. **人工质量检查**：17 名高校学生按清晰性、一致性、完整性、可行性审查指令，剔除缺陷样本并修正检查清单。

### 2.4 评估协议与指标
- 评估流程：顺序喂入多轮指令 → 记录每轮交互轨迹与代码项目 → 逐项核验检查清单。
- 工具：Claude-Opus-4.6 生成验证脚本；裁判智能体基于 Claude Code（功能清单用 Claude-Sonnet-4.6，约束清单用 DeepSeek-V4-Pro），可使用 Playwright 模拟浏览器交互并截图。
- 指标定义（设第 $t$ 轮约束清单 $C_t$，$z_{t,j}\in\{0,1\}$；功能清单 $F$，$y_k\in\{0,1\}$；项目可执行性 $b$）：
  - $CSR_t=\frac{1}{|C_t|}\sum_j z_{t,j}$：第 $t$ 轮约束满足比例
  - $C\text{-}ISR_t=\prod_j z_{t,j}$：全部约束严格满足（0/1）
  - $FSR=\frac{1}{|F|}\sum_k y_k$：功能满足比例
  - $F\text{-}ISR=\prod_k y_k$：全部功能严格满足
  - $BSR=b$：构建/可执行成功率
  - 数据集层面取各实例得分的平均。

## 六、主要结论与发现

1. **整体挑战性极高**：即使最优模型 GLM-5.2 仍约 **20%** 的约束未遵守；CSR 区间为 60.6%–80.4%，但 **C-ISR 大多低于 10%**，说明"完美满足全部过程约束"极难。
2. **性能随交互变长快速衰减**：所有模型 CSR 与 C-ISR 随轮次持续下降，多数模型在第 6 轮后 **C-ISR 归零**；强模型衰减更缓，多轮鲁棒性更好。
3. **过程约束比功能需求更难**：所有模型的 C-ISR 显著低于 F-ISR（如 Claude-Opus-4.6 的 F-ISR 为 37.0%，C-ISR 仅 8.7%），说明以最终结果为导向的评估会掩盖开发过程中的关键失败。
4. **难易分化明显**：静态孤立约束（File Encoding、File Path）接近满分；而 **Orchestration、Paradigm、Naming、Quantity** 等需要全局状态维护与多步协调的约束表现很差。
5. **约束来源影响显著**：仓库策略文件中的约束跨轮鲁棒性明显优于用户指令；在用户指令中，**更新已有约束比新增约束更难**，反映模型难以跟踪演化的用户意图。
6. **框架影响不可忽略**：模型在 Claude Code 下普遍优于 OpenCode（如 GLM-5.2 的 CSR 80.4%→76.8%，C-ISR 12.7%→6.7%）；顶层模型排序基本稳定，但中低层模型排序随框架波动，说明评测必须明确报告 harness。
7. **评估可靠性可接受**：自动评估与人工判断的一致率，约束清单项 >92%（代码 92.1%、裁判 92.4%），功能清单项 85.5%，甚至超过两名初始标注者之间 85% 的一致率。

## 七、优点

- **首次系统性定义**多轮智能体编程中的指令遵循评测问题，并给出可复用的基准与代码/数据开源。
- **约束分类体系严谨**：6 个一级、18 个二级类别，源自真实百万级用户智能体编程服务场景与既有基准，覆盖面广且可扩展。
- **数据构建质量高**：半自动流水线（LLM 扩展 + 分类法引导注入 + 逐轮校验）+ 17 名人工质检，投入约 2,400 美元，并设有三人交叉校验与复核机制。
- **评估方法混合且经过验证**：确定性约束用验证脚本、复杂/主观

约束用裁判智能体，并对两类清单分别抽样做人工标注校验（功能 200 项、约束 400 项），一致率 >92% 与 85.5%，说明自动评分具备可信度。
- **指标设计有区分度**：同时给出比例型指标（CSR/FSR）与严格型指标（C-ISR/F-ISR），能揭示"平均合规率高但零缺陷率极低"这一关键现象，避免被平均值掩盖的长尾失败。
- **多轮渐进设计贴近真实开发**：首轮搭骨架、后续轮增量/修改/覆盖，配合仓库策略文件的不可变约束，较好模拟了真实工程中"稳定规范 + 演化需求"的双重压力。
- **结论具有可操作性**：明确指出 Orchestration、Paradigm、Naming、Quantity 等类别是当前瓶颈，并给出"约束来源""放置位置""harness"三类影响因素的量化证据，为后续模型与智能体框架优化指明方向。
- **分析维度完整**：覆盖轮次分桶衰减曲线、约束类别热力图、约束来源对比、放置位置消融、双框架交叉验证，构成较闭环的证据链。

- **缺少统计显著性支撑**：所有结果均为单次运行，未报告多次采样的方差、置信区间或显著性检验，模型间的小幅差距（如 GLM-5.2 与 GLM-5.1）难以判断是否稳健。
- **数据规模与覆盖有限**：100 个实例、6 类场景，其中机器学习仅 5 例，安全/隐私/合规类约束、多智能体协作、超长交互（>10 轮）均未覆盖；结论的泛化边界不明确。
- **合成数据带来的分布偏斜**：多轮序列与约束变体均由 LLM（Gemini-3.1-Pro、Seed-2.0-Pro）扩展生成，可能存在模板化、措辞同质化与"易于被 LLM 生成也易于被 LLM 满足"的偏置，与真实用户指令的噪声分布存在差距。
- **评估成本与可复现性**：9,133 条约束 + 逐轮裁判智能体工具调用，推理开销大；论文将成本列为局限，但未给出单位实例的平均 token/费用，第三方复现门槛较高。
- **约束放置位置实验样本偏小**：仅随机抽取 30 例，且因成本考虑未做全量，该结论的稳定性有限。
- **人工质检深度**：17 名高校学生负责清晰性、一致性、完整性、可行性审查，但缺乏对领域正确性（如前端交互细节、ML 流程合理性）的专家级把关。
- **未报告失败模式细粒度归因**：论文展示了哪些类别表现差，但对"为何差"（是上下文遗忘、工具调用错误，还是指令解析失败）缺少错误分类学分析。
- **缺少人类开发者基线**：没有与人类工程师在同一多轮指令下的合规表现对照，"20% 约束未遵守"的绝对难度缺少参照系。
- **harness 依赖**：主实验统一使用 Claude Code，虽然控制了变量，但也使结论部分绑定于该框架的工具语义与提示结构，对自定义 harness 的迁移性未知。

## 九、启示与未来方向

- **评测范式**：过程约束合规应作为与功能正确性并列的一等指标，未来智能体编程基准宜默认同时报告 CSR/C-ISR 与 FSR/F-ISR，而非仅看通过率。
- **模型能力**：跨轮次的"状态保持 + 约束演化跟踪"是当前短板，提示后训练阶段可引入过程约束奖励、长上下文一致性训练与显式约束记忆机制。
- **上下文工程**：仓库策略文件优于用户指令中的临时约束，且"更新已有约束"比"新增约束"更难，说明实践中应把稳定规范外置到策略文件，并减少中途改写。
- **评测基础设施**：需要低成本、可审计的裁判方案（如规则脚本优先、裁判仅处理主观项），并强制报告 harness 版本与多次运行方差。
- **扩展方向**：向安全与隐私约束、多智能体协作约束、更长交互（>10 轮）与多模态（含截图/UI 交互）场景延伸。

## 十、总体评价

MTAC-IFBench 是首个系统面向"多轮智能体编程指令遵循"的基准，其价值不仅在于数据集本身，更在于提出了可复用的**约束分类体系（6+18）**、**半自动化构建流水线**与**混合评估协议**，并用大规模实验证明了"功能正确 ≠ 过程合规"这一被长期忽视的事实。实验维度较全面、结论具体且可操作，评估可靠性经过人工验证。主要保留在于裁判同源偏差、单次运行无方差报告、合成数据的分布偏斜以及 100 例规模与场景覆盖的局限。总体而言，该工作为该方向树立了明确的基线，但其绝对分数（C-ISR 普遍 <10%）也说明这一任务远未解决，后续在模型训练与评测协议上均有较大改进空间。

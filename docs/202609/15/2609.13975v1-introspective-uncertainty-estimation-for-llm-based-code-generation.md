## 摘要
大语言模型（LLMs）正越来越多地用于代码生成，但可能生成流畅却在功能上不正确的输出，这限制了其在实际软件工程工作流中的可信使用。本论文研究基于LLM内部隐藏状态表示的内省不确定性估计（IUE）能否可靠地指示代码生成任务在响应级和行级上的正确性。目标是确定隐藏状态在多大程度上编码了有关代码功能正确性的信息，以及如何将其用于实际风险评估和故障定位。在方法上，本论文将在LiveCodeBench（LCB）和BigCodeBench（BCB）上的响应级评估与一个从错误程序中导出词元和行级标签的增强流程相结合。在此设置下，比较静态和动态响应级特征，评估跨任务、编程领域和词元位置的泛化能力，并研究行级故障定位。结果表明，隐藏状态包含强烈的响应级正确性信号。静态单token探针表现最佳，而更复杂的动态策略没有带来一致的增益。尽管跨任务、领域和token位置的泛化是可行的，但对于真实世界软件项目，依赖具体场景的性能下降仍普遍存在。在细粒度上，行级预测比响应级估计困难得多。然而，在已知程序不正确的条件定位设置中，Top-K故障点排序仍然有效。总体而言，研究结果表明，隐藏状态是估计代码功能正确性的稳健且信息丰富的资源，支持一种将响应级风险筛查与有针对性的行级优先级排序相结合的两阶段工作流。

## Abstract
Large Language Models (LLMs) are increasingly used for code generation but can produce fluent yet functionally incorrect outputs, which limits trust in their usage for practical software engineering workflows. This thesis investigates whether Introspective Uncertainty Estimation (IUE), based on internal hidden-state representations of LLMs, can reliably indicate correctness at the response and line levels for code generation tasks. The objective is to determine the extent to which hidden states encode information about functional code correctness and how this can be leveraged for practical risk assessment and fault localization. Methodologically, this thesis combines response-level evaluation on LiveCodeBench (LCB) and BigCodeBench (BCB) with an augmentation pipeline that derives token- and line-level labels from incorrect programs. In this setup, it compares static and dynamic response-level features, evaluates generalization across tasks, programming domains, and token positions, and studies line-level fault localization.   The results show that hidden states contain a strong response-level correctness signal. Static single-token probes perform best, while more elaborate dynamic strategies yield no consistent gains. While generalization across tasks, domains, and token positions is feasible, setting-dependent degradation largely remains for real-world software projects. At a fine granularity, line-level prediction is substantially harder than response-level estimation. However, in a conditional localization setup with known-incorrect programs, Top-K point-of-failure ranking remains effective. Overall, the findings suggest that hidden states are a robust and informative resource for estimating functional code correctness, supporting a two-stage workflow that combines response-level risk screening with targeted line-level prioritization.

- **问题背景**：LLM 已广泛用于代码生成，但常产生“表面流畅、功能错误”的代码。这类幻觉包括：代码语法无效/无法执行，或能执行但不满足功能需求。它削弱了开发者对 LLM 辅助编程的信任，并可能引入调试、安全与维护风险。
- **现有方法局限**：
  - 事后验证（测试、静态/动态分析、形式规约）依赖高质量 oracle；真实项目中测试常不完整，规约常缺失。
  - 信息论不确定性估计依赖 token 概率，但 token 概率与“程序功能正确性”并不一致，模型可能“自信地犯错”。
  - 黑盒方法（语言化置信度、自评估、一致性采样）受提示敏感、过度自信、计算成本等限制。
- **核心研究动机**：转向 **内省不确定性估计（Introspective Uncertainty Estimation, IUE）**，即利用 LLM 前向传播中的内部隐藏状态来估计代码正确性，并进一步定位错误行。
- **整体含义**：论文试图回答内部表示是否编码了代码功能正确性信息，以及这种信息能否支持实际风险评估和细粒度故障定位。若成立，IUE 可作为事后验证的补充，形成“响应级风险筛查 + 行级故障优先定位”的两阶段工作流。

## 2. 方法论

### 2.1 核心思想

- 对每个 prompt-response 对，使用同一 LLM 进行 **prefilling / teacher forcing**，提取响应 token 在最终层的隐藏状态序列 \(H=(h_1,\dots,h_T)\)。
- 在这些隐藏状态上训练轻量探针，预测：
  - **响应级**：整个生成程序是否正确；
  - **token/行级**：哪些 token 或代码行可能错误。
- 只使用隐藏状态，不使用注意力权重或 MLP 激活，原因是隐藏状态维度固定、更适合长序列，且已有工作显示其信息量强。

### 2.2 数据与标签流程

- **响应级标签**：由 benchmark 测试套件执行生成程序得到。通过全部测试为 correct，失败为 tests_failed，无法提取代码块为 no_program。no_program 被过滤。
- **特征提取**：
  - 先用 vLLM 生成响应文本；
  - 再用 Transformers 重放 prompt-response，提取隐藏状态；
  - 提取静态位置：first token、first code token、last code token、last token；
  - 也提取所有代码 token 的密集序列，用于序列建模和行级任务；
  - 可选保存 token 概率与熵。
- **增强流程 fix-then-diff**：
  - 仅对 LCB 和两个模型（Qwen3-Coder、GPT-OSS-20B）做细粒度增强；
  - 对错误程序，用辅助模型 Nemotron-3-Nano 生成“最小编辑”修复，最多 4 次，取首个通过测试的修复；
  - 将原错误程序与修复程序 token 化并用 `difflib.SequenceMatcher` 对齐，匹配 token 标正确，不匹配 token 标错误；
  - 排除空白、换行、注释 token 的噪声；对插入情况做特殊处理；
  - 行级标签：一行中只要有至少一个非空白/非注释错误 token，该行标错误。
- **增强数据变体**：
  - V1：强过滤，仅保留小范围错误（错误行 ≤ 3）；
  - V2：去掉 line_filter，保留更复杂错误区域；
  - V3：仅保留响应级已知错误的程序，用于条件故障定位。

### 2.3 探针模型

- **静态单 token 探针**：输入单个固定位置隐藏状态，分类器为 MLP 或 XGBoost。
- **静态多 token 探针**：拼接 first+last 或 first code+last code 隐藏状态。
- **序列探针**：LSTM 编码所有代码 token 隐藏状态，最后接 MLP 分类头。
- **过滤策略**：
  - newline filter：仅保留换行 token 隐藏状态；
  - entropy filter：按归一化 token 熵筛选，公式为  
    \(u_t = -\frac{1}{\log |V|}\sum_{v\in V} p_t(v)\log p_t(v)\)。

### 2.4 训练与评估指标

- 响应级目标：二分类正确/错误，使用 BCEWithLogitsLoss；XGBoost 用 logistic 目标。
- 行级目标：反转标签，使“错误行/token”为正类，并处理类别不平衡。
- 指标：
  - AUROC：排序判别能力；
  - F1：阈值分类性能；
  - BSS：校准质量；
  - Top-K hit rate：故障定位实用性。

## 6. 主要结论与发现

- **响应级正确性估计有效**：
  - 隐藏状态包含强正确性信号；
  - 静态单 token 探针最佳，LCB 上最佳可达约 **0.90 AUROC、0.96 F1**；
  - 越靠近响应末尾的 token 通常越有信息量，last code token / last token 表现最好。
- **复杂模型不一定更好**：
  - MLP 与 XGBoost 在静态单 token 特征上接近；
  - 多 token 拼接没有稳定增益；
  - LSTM 序列模型、newline 过滤、熵过滤均未一致超过静态单 token 基线；
  - 高熵 token 并不一定是最有判别力的位置，低熵结构信号反而更稳。
- **校准表现突出**：
  - 在 CALIBRI 上，last-token XGBoost 探针 BSS=0.5888、Accuracy=0.8534，优于 IGLB 等事后校准方法。
- **泛化能力有限但可行**：
  - 跨任务可迁移，但通常有性能下降；
  - BCB → LCB 迁移较强，LCB → BCB 较难；
  - BCB 内部跨领域泛化较稳定，平均 shortfall < 2.2%；
  - 跨 token 位置也较稳健，性能随采样窗口扩大而下降，但会稳定在任务特定下限。
- **行级故障定位更难**：
  - 混合正确/错误程序时，行级 AUROC 约 0.72–0.76，但 F1 很低，阈值校准困难；
  - 在已知程序错误的条件设置 V3 中，F1 明显提升；
  - Top-K 故障点排序有效：最佳 Top-3 hit rate 达 **81%**；
  - token-to-line 聚合通常优于直接用每行最后 code token。
- **总体建议**：采用两阶段 IUE 工作流：先做响应级风险筛查，再对已知可能错误的程序做行级故障优先排序。

## 7. 优点

- **研究问题系统且连贯**：围绕响应级、泛化、行级三个 RQ 展开，形成完整链条。
- **多模型、多 benchmark、多提示格式**：提高结论的外部有效性。
- **方法简洁有效**：发现静态单 token + 轻量分类器已很强，避免不必要复杂度。
- **细粒度增强流程有创新性**：fix-then-diff 从有机错误程序中生成 token/行级标签，比简单变异更接近真实模型失败。
- **评估指标全面**：AUROC、F1、BSS、Top-K 兼顾排序、分类、校准和调试实用性。
- **强调实际工作流**：提出两阶段部署思路，比单纯追求响应级分类更贴近开发者需求。
- **可复现性**：代码与数据公开，附录提供提示、超参数和补充结果。

## 8. 不足与局限

- **标签 oracle 不完美**：
  - 响应级标签依赖 benchmark 测试套件，可能漏掉未测试行为；
  - 通过测试不等于可维护、安全、可读。
- **特征提取近似**：
  - 隐藏状态通过 prefilling 重放获得，而非原始 vLLM 生成时直接记录；
  - token 概率存在小而显著的实现差异，可能影响探针绝对性能。
- **行级标签噪声**：
  - 自动修复不保证最小编辑，可能重命名、改导入或重构；
  - diff 对齐在插入、替换、重构场景下易错；
  - 人工审计仅 100 个样本，约 90% 对齐，仍有残余错误。
- **实验覆盖限制**：
  - 行级增强仅限 LCB 和两个模型；
  - 主要面向 Python，跨语言泛化未知；
  - 未研究非功能属性，如安全性、性能、可维护性。
- **算力信息不透明**：
  - 未报告 GPU 型号、数量、训练时长，难以评估复现成本与能耗。
- **应用限制**：
  - IUE 需要白盒访问，不适用于闭源模型；
  - 行级混合设置下阈值分类仍不可靠，更适合排序和辅助调试，而非自动判定；
  - 跨任务仍有 OOD-ID gap，实际部署可能仍需任务适配。

## 摘要
背景：由于软件系统日益复杂以及AI编码智能体加速生成代码，开展有效的代码审查正变得越来越具有挑战性。基于LLM的代码审查方法在识别缺陷和提高代码质量方面已显示出良好前景。然而，现有方法很少考虑项目特定的情境化知识，并且很少有在工业环境中进行评估。目标：在本研究中，我们提出一种基于多智能体的解决方案，对代码变更提供多维度评估。方法：遵循设计科学研究过程，我们在工业环境中开发和评估了我们的解决方案。我们的解决方案将专门的智能体技能与特定情境知识相结合，以识别代码变更中四个维度的反模式：可读性、可维护性、可靠性和性能。使用我们的解决方案，我们为若干代码提交生成了审查意见，并识别出200多个问题。随后，案例公司的开发人员对这些问题的正确性和重要性进行了人工验证。结果：评估结果表明，我们的解决方案在所调查的代码提交中正确识别问题的准确率达到96%。此外，约69%的正确识别问题被评为重要，其中约33%被评为必须修复的严重问题，36%被评为应当修复的重要问题。开发人员的定性反馈证实了这些发现，并凸显了所生成审查意见的实用性。结论：我们的发现提供了来自工业评估的经验证据，表明将专门的智能体技能与特定情境知识相结合能够产生准确且具有实际用途的代码审查。

## Abstract
Context: Conducting effective code reviews is increasingly challenging due to the growing complexity of software systems and the accelerated code generation by AI coding agents. LLM-based approaches for code reviews have shown promising results in identifying defects and improving code quality. However, existing approaches rarely consider project-specific contextualized knowledge, and few have been evaluated in industrial settings.   Objective: In this study, we propose a multi-agent-based solution that provides multifaceted assessments of code changes.   Method: Following the Design Science Research Process, we developed and evaluated our solution in an industrial setting. Our solution combines specialized agent skills with context-specific knowledge to identify antipatterns in code changes across four dimensions: readability, maintainability, reliability, and performance. Using our solution, we generated reviews for several code commits and identified more than 200 issues. These issues were then manually validated by the developers of the case company for their correctness and importance.   Results: The evaluation results show that our solution achieves 96% accuracy in correctly identifying issues in the investigated code commits. Furthermore, around 69% of the correctly identified issues were rated as important, with approximately 33% rated as severe issues that must be fixed and 36% as important issues that should be fixed. Qualitative feedback from developers corroborates these findings and highlights the usefulness of the generated reviews.   Conclusion: Our findings provide empirical evidence from an industrial evaluation that combining specialized agent skills with context-specific knowledge yields accurate, practically useful code reviews.

  - 多数 LLM 代码审查方法提供**窄维度审查**（单一视角），而人类审查者实际采用**多维度推理**，同时兼顾可读性、可维护性等非功能质量。

## 2. 方法论

### 2.1 核心思想

- 遵循 Offermann 等人的**设计科学研究过程（DSRP）**，分三阶段：问题识别 → 方案设计与开发 → 评估。
- 核心设计决策两条：
  1. **按质量维度分解为专用智能体**，每个智能体拥有独立提示词、反模式目录与审查指令，解决"窄维度审查"问题。
  2. **智能体不推理孤立 diff**，由上下文构建器从代码仓库与代码知识图谱中提供情境视图，解决"情境缺失"问题。

### 2.2 技术架构与关键细节

- **多智能体架构**，由 LLM 编排层（Orchestrator）协调，原型基于 **Kiro CLI** 实现（JSON 声明式智能体定义 + Markdown 技能文档，无需自定义代码）。
- **编排工作流**：接收输入（Commit ID）→ 构建上下文 → 保存上下文到磁盘 → 委派给 4 个智能体 → 整合报告 → 保存最终报告。
- **MCP 服务器（Model Context Protocol）**：
  - **GitLab MCP 服务器**（Docker 容器化）：提供提交元数据、代码 diff、变更文件等**局部上下文**。
  - **代码知识图谱 MCP 服务器**：索引仓库结构、文件级导入关系、符号定义（DEFINES 边）、外部库使用；支持依赖影响分析（fan-in/fan-out）、文件夹结构探索、AI 生成摘要、语义/混合代码搜索、Cypher 查询。
- **上下文构建器**：收集 diff、变更文件、仓库元数据与依赖/结构关系，并转换为**面向不同智能体的差异化上下文提示**（如可读性智能体侧重局部结构与格式，可维护性智能体额外接收依赖与结构关系），以降低提示复杂度并保留最相关信息。
- **四个专用审查智能体**（均使用 Agent Skills 协议，由编排器并行调用，仅接收共享上下文文档与源文件路径）：
  - **可读性专家**：命名清晰度、结构组织、嵌套复杂度、格式、视觉可读性等，依据文献 [25,24] 的可读性反模式（代码结构、嵌套、可理解目标、代码长度、内联操作、阅读流、上下文信息、代码风格、魔法数字、命名、代码模式、视觉组织）。
  - **可维护性专家**：使用经典可维护性反模式 [16,11]（神秘命名、重复代码、长函数、长参数列表、全局数据、可变数据、发散式变化、霰弹式修改、依恋情结、数据泥团、基本类型偏执、重复 switch、循环、冗赘元素、夸夸其谈通用性、临时字段、消息链、中间人、内幕交易、过大的类、异曲同工的类、数据类、被拒绝的遗赠、注释）。
  - **可靠性专家**：聚焦异常处理/故障管理，使用反模式目录 [9]（过度捕获、过度捕获并中止、未处理异常、不可达处理器、捕获但不做任何事、捕获并返回 null、捕获泛型、破坏性包装、哑元处理器、忽略 InterruptedException、不完整实现、记录并返回 null、记录并抛出、多行日志、嵌套 try、finally 中抛出、抛出泛型、抛出"厨房水槽"）。
  - **性能专家**：分析效率与资源利用，使用性能反模式 [28,31,1,27]（停滞、昂贵数据库调用、空半挂车、大泥球、迂回寻宝、错误缓存、单车道桥、不当数据结构、未优化循环、数据格式转换性能、过度或不当锁使用、过度 I/O 操作、重复计算）。
- **输出格式**：每个智能体以严格的**四字段格式**输出发现（反模式名称、位置、问题描述、修复建议），编排器汇总为统一报告（含各维度问题数量摘要）。

## 6. 主要结论与发现

- **RQ1（关键设计选择）**：
  - **编排与输出格式**：编排是单点故障，任一阶段出错都会传播到最终报告；提供正/负示例约束输出格式非常有效。
  - **专用审查智能体**：各智能体贡献了其他智能体未发现的问题，单维度审查最多只能覆盖约三分之一；分解为专用智能体是实现多维度评估的关键。
  - **情境化接地**：仅 4% 问题被判错误，归因于上下文构建器与代码知识图谱提供的局部+结构/依赖信息；差异化上下文视图还降低了提示复杂度。
- **RQ2（准确率）**：206 个问题中 **197 个正确，9 个错误，准确率约 96%**。低误报率在工业场景尤为关键，可避免开发者因频繁误报而弃用工具。
- **RQ3（有效性）**：197 个正确问题中：
  - **High（必须修复）：65 个（33%）**
  - **Medium（应当修复）：70 个（36%）**
  - **Minor（低影响）：62 个（31%）**
  - 合计约 **69% 为重要问题**。
- **问题维度分布**：可靠性 64（31.1%）、可读性 58（28.2%）、可维护性 50（24.3%）、性能 34（16.5%），四个维度均有覆盖，更贴近人类审查者的实际推理方式。
- **开发者定性反馈**（正面）：
  - "审查意见非常好，尤其是可维护性和性能部分。"
  - "部分意见与我们已发现的一致，但你们的审查发现了更多，非常好。"
- **工程经验总结**：编排准确性与智能体设计同等重要；输出格式是设计的一部分而非展示细节；关注点分离应扩展到智能体之外（独立提示词、反模式目录、上下文视图，使方案可扩展——新增质量维度只需新增一个智能体）。

## 7. 优点

- **工业实证价值高**：在真实企业（Ericsson）环境中开发与评估，弥补了 LLM 代码审查研究工业验证不足的空白。

- **高准确率与低误报**：96% 准确率、仅 4% 误报，在工业可接受性上具有实际意义。
- **人工验证严谨**：206 个问题全部由代码原作者（高级开发者）逐一验证正确性与重要性，并采用三级

重要性评分（Minor/Medium/High），反馈粒度细、可操作性强。

- **设计哲学清晰**：将"关注点分离"从代码层面延伸到智能体层面（独立提示词、独立反模式目录、独立上下文视图），是一种可迁移到其他审查/分析任务的架构范式。

## 8. 缺点与局限

### 8.1 评估方法层面
- **无基线、无消融**：未与单智能体方案、无上下文方案、其他 LLM 审查工具或人类审查做对照，因此"多智能体分解""知识图谱上下文""差异化上下文提示"各自的贡献无法量化，结论停留在可行性证据层面。
- **样本规模与代表性有限**：7 个提交、4 个项目、单一企业（Ericsson）、单一语言（Python）、单一模型（Kiro CLI 默认模型），外部效度受限，结论能否迁移到 Java/C++ 等语言或异构组织尚不可知。
- **无统计检验**：96% 准确率与 69% 重要问题比例均为描述性统计，未给出置信区间或显著性分析。
- **标注一致性未度量**：重要性判断仅由单一评审者给出，未做多人交叉标注，也无 Cohen's Kappa 等一致性指标，主观性无法量化。

### 8.2 偏差风险
- **评审者即代码作者**：由变更作者评判针对自己代码的审查意见，可能同时存在"高估（认同自己熟悉的问题）"与"低估（抵触外部批评）"两种方向的偏差；虽作者主张原作者最懂上下文，但该设计仍削弱了评估的独立性。
- **正确性标准未明确定义**：论文未给出"正确/错误"的判定准则，评审者可能采用不同阈值。

### 8.3 覆盖范围与深度
- **仅验证"识别"未验证"修复"**：实验只评估问题识别与重要性，未检验修复建议是否可行、是否被开发者采纳、采纳后是否真正提升代码质量，缺少端到端价值闭环。
- **静态验证而非工作流集成**：未在真实 CI/代码审查流程中部署，未测量端到端延迟、对审查周期的影响、开发者实际采纳率等运行层面指标。
- **反模式目录的适配性**：目录来自通用文献，可能与企业或项目的特定规范、领域惯例不完全一致，存在"形式正确但语境不适用"的误报风险。
- **维度不均衡**：性能维度仅 34 个问题（16.5%），可能因反模式目录或上下文供给方式偏向静态可检出的问题，性能类深层问题（如并发争用、算法复杂度退化）覆盖不足。
- **知识图谱的构建与维护成本未讨论**：索引新鲜度、增量更新、跨仓库规模下的可扩展性与成本均未涉及。

### 8.4 工程与运行层面
- **未报告任何开销**：无 token 消耗、调用次数、成本、延迟、并发度等数据，难以评估工业部署的性价比。
- **编排单点故障**：作者自己指出编排环节任一阶段失败都会传播到最终报告，但未给出重试、校验、失败降级等鲁棒性机制。
- **上下文构建的"最后一公里"未量化**：差异化上下文视图声称降低提示复杂度，但未给出提示长度、召回率或对比实验支撑。

## 9. 对后续研究的启发

- **补齐对照实验**：设计单智能体、无知识图谱、统一上下文 vs. 差异化上下文等消融组，并用人类审查或既有工具作为基线，验证各设计选择的因果贡献。
- **扩展评估规模与多样性**：跨语言（Java、C++、TypeScript）、跨团队、跨组织，扩大提交样本量，并引入多名独立标注者计算一致性。
- **闭环到修复与采纳**：跟踪审查意见的采纳率、修复后代码度量的变化、开发者对工具的信任与弃用行为，从"发现问题"走向"改善质量"。
- **成本-效益与延迟研究**：报告 token、调用成本、端到端时延，并研究增量审查（仅重审变更影响面）以降低开销。
- **上下文基础设施研究**：知识图谱的增量更新、跨仓库索引、图谱质量对审查准确率的影响。
- **人机协作流程设计**：何时触发审查、如何呈现分级结果、如何避免审查者过度依赖或忽视 AI 意见。
- **重要性判定的标准化**：定义可复用的严重度分级准则与标注协议，提升跨研究可比性。
- **鲁棒编排模式**：重试、超时、结果校验、多模型投票等编排层机制的实证研究。

## 10. 总体评价

本文的核心贡献不在于算法创新，而在于**提出并工业验证了一套"多智能体 + 情境化上下文"的代码审查架构**，并用 96% 准确率、69% 重要问题占比与开发者正面反馈提供了可信的可行性证据。其"按质量维度分解智能体、以代码知识图谱补足情境、以差异化上下文控制提示复杂度"的设计思路，对 AI 原生开发时代的质量保障具有直接的工程参考价值。

主要短板在于**评估设计的严谨性**：无基线、无消融、样本小、单一语言与模型、评审者即作者、未报告开销、未闭环到修复效果。因此当前结论应被理解为"该架构在真实工业环境中可行且表现良好"的**存在性证明**，而非"该架构优于其他方案"的**比较性结论**。后续工作若能补齐对照实验与端到端价值度量，将显著提升其学术与工业说服力。

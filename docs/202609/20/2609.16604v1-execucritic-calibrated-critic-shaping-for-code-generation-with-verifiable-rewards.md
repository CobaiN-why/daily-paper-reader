## 摘要
执行反馈是代码模型的一种有用监督信号，因为单元测试是客观的，并直接衡量程序正确性。其弱点在于，整个程序往往被简化为一个通过或失败位，使 RLVR 需要解决困难的信用分配问题。与此同时，编码系统通常包含单独的评审者或测试者角色，但这些评论家通常是提示出来的，而非训练得到的，并且没有针对执行进行校准。我们提出 ExecuCritic，一个联合训练框架，其中代码生成器与评论家在同一次执行 rollout 上更新。评论家预测通过或失败结果并给出简短诊断反馈；代码生成器仅在评论家与执行器在当前 rollout 组上一致时使用该信号。在八个代码基准和两个近期开放主干模型上，ExecuCritic 优于没有评论家的 GRPO、提示式评审者系统和标量奖励模型基线，同时需要更少的策略梯度步骤和更少的沙箱执行。消融和可靠性分析表明，增益来自更好的信用分配，而非更大的采样预算。

## Abstract
Execution feedback is a useful supervision signal for code models because unit tests are objective and directly measure program correctness. Its weakness is that an entire program is often reduced to one pass or fail bit, leaving RLVR to solve a difficult credit assignment problem. At the same time, coding systems often include separate reviewer or tester roles, but these critics are usually prompted rather than trained and are not calibrated against execution. We propose ExecuCritic, a joint training framework in which a coder and a critic are updated on the same execution rollouts. The critic predicts pass or fail outcomes and gives short diagnostic feedback; the coder uses this signal only when the critic agrees with the executor on the current rollout group. Across eight code benchmarks and two recent open backbones, ExecuCritic improves over GRPO without a critic, prompted reviewer systems and scalar reward model baselines, while requiring fewer policy gradient steps and fewer sandbox executions. Ablations and reliability analyses suggest that the gains come from better credit assignment rather than larger sampling budgets.

## 1. 核心问题与整体含义

- **研究动机**：代码生成中，单元测试/沙箱执行提供了客观、直接的正确性信号，因此 RLVR（Reinforcement Learning with Verifiable Rewards）被广泛用于代码模型训练。
- **核心痛点**：
  - 一个完整程序通常只被压缩为“通过/失败”一个二值奖励，长代码、长补丁中的每个 token 都获得相同信用，导致 RLVR 面临严重的**信用分配困难**。
  - 为了缓解稀疏性，常见做法是扩大 rollout 组规模，但每个候选都要执行沙箱，成本高昂。
  - 另一类多智能体代码系统（如 AgentCoder、Self-Refine、MetaGPT）引入 reviewer/tester 角色，但这些 critic 多为**提示式、冻结、未针对执行结果校准**，可能自信但错误，coder 也没有被训练去判断何时该采纳其建议。
- **整体含义**：论文试图回答——能否把执行奖励与可学习的 critique 结合，使 critic 在不变成“不可信奖励模型”的前提下，为 RLVR 提供更稠密、更可靠的信用信号。作者提出 **ExecuCritic**：coder 与 critic 在同一执行 rollout 上联合训练，且 critic 信号只有在与执行器一致时才被 coder 采用。

## 2. 方法论

### 2.1 核心思想

- 联合训练两个策略：
  - **coder** \(\pi_c\)：标准自回归代码生成策略。
  - **critic** \(\pi_v\)：接收 prompt 和候选程序，先输出简短自然语言诊断，再输出 `<verdict>` token，其 pass/fail 概率作为标量分数 \(\hat{s}\in[0,1]\)。
- 二者共享**冻结的主干模型**，各自使用独立的 **LoRA adapter**，额外参数开销较小。
- critic 不是事后冻结的 judge，而是与 coder 在同一不断演化的输出分布上更新，因此能识别当前 coder 实际犯的错误。

### 2.2 校准优势（Calibrated Advantage）

- 对每个 prompt 采样 \(K\) 个 rollout，执行器给出二值奖励 \(R_i\)，critic 给出分数 \(\hat{s}_i\)。
- 标准 GRPO 优势：
  - \(A_i = (R_i-\mu_R)/(\sigma_R+\epsilon)\)
  - critic 优势：\(S_i=(\hat{s}_i-\mu_{\hat{s}})/(\sigma_{\hat{s}}+\epsilon)\)
- 最终优势：
  - \(\tilde{A}_i = A_i + \alpha \rho_K(R,\hat{s}) S_i\)
  - 其中 \(\rho_K\in[-1,1]\) 是当前 rollout 组内执行奖励与 critic 分数的**秩相关**，\(\alpha>0\) 为塑形权重。
- **关键机制**：
  - 当 critic 在当前 prompt 上校准良好（\(\rho_K\to1\)），critic 项增强执行信号，并把信用扩散到 rollout 组内。
  - 当 critic 校准差甚至反向（\(\rho_K\le0\)），该项坍缩或反向，避免不可靠分数被当成可信奖励。
  - 这使联合训练在 critic 尚未收敛时更稳定。

### 2.3 Critic 目标

- 设 \(v_i\) 为执行器 verdict 目标，\(z_i\) 为失败描述符（语法、导入/API、类型、断言、超时、运行时异常、未知等七类）。
- 损失由三部分组成：
  1. **结果对齐**：对执行器 verdict 的似然。
  2. **成对 pass/fail margin**：只在同一组内同时存在通过和失败程序时使用，要求 critic 给通过程序至少高出 \(m\) 的分数。
  3. **诊断一致性**：对失败 rollout，训练 critique 匹配执行器轨迹中提取的失败类型。
- 作用：避免 verdict 分数近乎常数；让文本诊断在推理阶段重采样时真正有用。

### 2.4 Coder 目标

- 使用带校准优势 \(\tilde{A}_i\) 的 clipped PPO/GRPO 代理目标。
- 同时加入对 SFT 参考策略 \(\pi_{\text{ref}}\) 的 KL 正则，防止 coder 漂移到 critic 恰好高估的退化风格。

### 2.5 三阶段训练流程

1. **Stage 1：SFT 冷启动**
   - coder 在 OSS-Instruct 与 Evol-Code 混合数据上微调。
   - critic 在三元组 \((x,y,v,z)\) 上初始化，\(v\) 为执行器 verdict，\(z\) 为强教师蒸馏 critique 或规范化失败描述符。
2. **Stage 2：联合 RLVR**
   - 每个 prompt 采样 \(K=8\) 个 rollout。
   - 执行器给出奖励和失败描述符；critic 给出分数、critique 和 verdict logits。
   - 计算 \(A_i\)、\(S_i\)、\(\rho_K\)，形成校准优势。
   - 每个优化步内先更新 critic，再用同一 rollout 上的 critic 分数计算校准优势更新 coder。
3. **Stage 3：推理时精炼**
   - coder 生成 \(N\) 个候选，critic 排序，只执行 top-\(k\)。
   - 若无一通过，把最高分失败候选的 critique 反馈给 coder，再采样新一轮，最多 \(T\) 轮。
   - critic 只需一次前向，沙箱执行可能需数秒，因此排序可显著降低运行时间。

## 3. 实验设计

### 3.1 主干模型

- **Qwen3-8B**：主实验主干。
- **DeepSeek-Coder-V2-Lite-Instruct（16B MoE，约 2.4B 激活）**：验证跨架构可迁移性。
- **Qwen3-4B**：用于缩放消融。
- 所有训练使用 rank-32 LoRA，加在 attention 和 MLP 投影上，主干冻结，bf16 + gradient checkpointing。

### 3.2 Benchmark / 场景

- 八个 benchmark view，覆盖从函数合成到仓库修复：
  - **HumanEval+、MBPP+**：短函数合成，强化单元测试。
  - **LiveCodeBench v5**：竞赛编程，带污染控制。
  - **BigCodeBench-Hard**：库使用、长指令、多调用推理。
  - **APPS、CodeContests**：较长竞赛风格程序，中间信用更模糊。
  - **SWE-bench Lite**：300 个真实 GitHub issue 的仓库级修复。
  - **Multi-SWE-bench**：Python 和 Java 子集仓库修复。
  - 另含 **SWE-bench Verified ranking view**（critic 在执行前对候选补丁排序）和**测试选择 view**（选择可信生成测试作为辅助验证器）。
- 指标：
  - 函数合成：unbiased pass@1，贪心解码。
  - 仓库任务：resolved issue rate。
  - 排序任务：NDCG@5、AUC。
  - 另报告 ECE、Brier、Spearman、Type-F1、沙箱执行次数等。

### 3.3 训练数据

- SFT 阶段：75k 条 OSS-Instruct 与 Evol-Code-Alpaca 混合，过滤出可编译样本。
- RLVR prompts：CodeContests 训练集、SWE-Gym 训练集、APPS 的 30k 子集、12k 仓库编辑子集（Docker 内 120 秒内可跑测试）。
- 防污染：用 MinHash + Jaccard 0.7 对 prompt 去重，AST 规范化去除近重复函数签名。
- critic 失败描述符归为七类：syntax、import/API、type、assertion、timeout、runtime exception、unknown。

### 3.4 对比方法

- **B1**：未任务训练的基础主干。
- **B2**：仅 SFT 的 coder。
- **B3**：单 coder 的 RLVR，vanilla GRPO + 执行器奖励，复现 SWE-RL/AceCoder 配方；使用 \(K=16\) 以匹配或超过本文训练时沙箱调用。
- **B4**：提示式 reviewer 系统，冻结 coder + 冻结 critic，类似 AgentCoder。
- **B5**：Self-Refine。
- **B6**：训练 critic 重排序，coder 停留在 SFT checkpoint。
- **B7**：在所有精炼轮次执行全部采样候选。
- **B8**：outcome reward model shaping，用标量奖励模型替代文本诊断。
- 训练类基线共享主干、prompt 和 token 预算；提示类基线使用未训练主干。

### 3.5 超参数

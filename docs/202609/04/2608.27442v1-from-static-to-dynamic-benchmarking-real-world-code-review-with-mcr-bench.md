## 摘要
在真实世界的软件开发中，代码审查通常涉及开发者和审查者之间的迭代交互以提高软件质量，使得该过程成本高昂且耗时。尽管近期工作探索了基于大型语言模型（LLM）的自动化代码审查，但大多数方法将代码审查过度简化为单轮、静态的决策任务，未能捕捉真实审查场景中固有的多轮交互性质和复杂问题解决过程。为弥合这一差距，我们引入了MCR-Bench，这是首个针对真实多轮代码审查设计的缺陷状态感知基准。MCR-Bench涵盖五种常用编程语言，包含2,269个真实世界多轮代码审查任务，每个任务都标注了细粒度的缺陷信息和跨轮次状态标签。MCR-Bench中的每个任务都配备了细粒度的缺陷元数据（如描述、类型、严重程度）以及动态状态注释，捕捉缺陷在整个多轮过程中的完整演化轨迹。通过在MCR-Bench上对主流LLM进行大量实验，我们获得了若干发现：（1）整体能力有限：实验表明，主流LLM在缺陷检测和缺陷生命周期状态追踪方面的整体性能有限，且随着交互轮次增加，性能显著下降；（2）缺陷敏感性差异：LLM在不同缺陷类型和严重程度上的表现差异很大，语义复杂或低显著性的缺陷被漏检的可能性显著更高；（3）潜在失败机制：我们深入的错误分析剖析了假阳性和假阴性的不同驱动因素，揭示了跨轮次时间错位和长距离记忆不足等关键弱点。

## Abstract
In real-world software development, code review typically involves iterative interactions between developers and reviewers to improve software quality, making the process costly and time-consuming. Although recent work explores large language models (LLMs) for automated code review, most approaches oversimplify code review into a single-round, static decision task, which fails to capture the multi-round interactive nature and the complex problem-solving processes inherent in realistic review scenarios. To bridge this gap, we introduce MCR-Bench, the first defect state-aware benchmark designed for realistic multi-round code review. MCR-Bench covers five commonly-used programming languages and consists of 2,269 real-world multi-round code review tasks, each of which is annotated with fine-grained defect information and cross-round state labels. Each task in MCR-Bench is equipped with fine-grained defect metadata (e.g., description, type, severity) alongside dynamic state annotations, capturing the complete evolutionary trajectory of a defect throughout the multi-round process. We obtain several findings through extensive experiments on MCR-Bench with mainstream LLMs. (1) Limited overall capability: experiments reveal that mainstream LLMs exhibit limited overall performance in defect detection and defect lifecycle state tracking, with performance degrading significantly as the number of interaction rounds increases; (2) Defect-sensitive performance: LLMs' performance varies substantially across different defect types and severity levels, with semantically complex or low-salience defects being significantly more likely to be missed; (3) Underlying Failure Mechanisms: our in-depth error analysis dissects the distinct drivers of false positives and false negatives, revealing critical weaknesses such as cross-round temporal misalignment and inadequate long-range memory.

- 已有基准的粒度虽从 diff-hunk 级提升到 PR 级，但依然停留在“静态快照”式评估，**无法捕捉缺陷在多轮演化中的状态转换**（如从 Open → Resolved → Reopened），也无法验证模型是否能够持续追踪历史缺陷。
- 为填补这一空缺，论文提出 **MCR-Bench**，聚焦两个核心问题：
  1. 当前 LLM 能否在真实多轮代码审查中有效识别缺陷？
  2. 当前 LLM 能否跨轮次追踪缺陷的生命周期状态？

## 二、方法论核心

### 2.1 MCR-Bench 的定义与结构

- MCR-Bench 是**首个缺陷状态感知的多轮代码审查基准**，包含 **2,269 个真实多轮审查任务**，覆盖 GitHub 上最流行的五种编程语言：Python、Java、JavaScript、TypeScript 和 C#。
- 每个任务实例包含两类组件：
  - **PR 相关输入信息**：任务指令、静态 PR 元数据（仓库名、PR 标题、描述、关联 Issue）、动态审查信息（当前轮的完整代码 diff 和截至当前轮的历史讨论时间线）。
  - **Ground-truth 缺陷卡片（Defect Card）**：每个标注缺陷包含三类信息：
    - 缺陷规格（缺陷描述、位置：文件路径与行号）；
    - 动态生命周期状态（**New、Open、Resolved、Reopened**）；
    - 辅助元数据（缺陷分类学和严重度等级）。

### 2.2 数据构建流程

论文设计了四阶段构建流程：

1. **语言与仓库选择**
   - 选取五种主流语言；仓库需满足多维标准：>100 stars、近五年持续提交活跃度、issue 解决率 >40%、>10 名贡献者、≥1,500 个 PR、宽松许可证（如 MIT）、排除 fork 仓库，最终筛选出 38 个高质量 GitHub 仓库。

2. **PR 数据收集与过滤**
   - 状态过滤：仅保留已合并（Merged）的 PR；
   - 类型与规模过滤：仅保留包含有效代码逻辑修改的 PR，排除超长 PR（>10 个初始提交）；
   - 多轮交互约束：必须存在 `<commit → discussion → revision>` 迭代循环，且排除机器人噪声；
   - 质量控制：采用 **SZZ-2 算法** 反向验证合并的 PR 是否在后续开发中被证实引入了缺陷，剔除有潜在缺陷的 PR。

3. **基于 LLM 的状态感知缺陷标注管线**（核心贡献）
   - 采用“**先局部检测，后全局追踪**”的分治策略：
     - **阶段一（局部候选缺陷检测）**：将整个 PR 生命周期拆解为多个独立审查轮次，仅提供该轮内的代码 diff 和讨论，逐轮识别候选缺陷，最大化召回；
     - **阶段二（跨轮缺陷整合与生命周期追踪）**：将各轮候选缺陷聚合成全局池，利用 LLM 语义推理进行跨轮合并（识别指代同一缺陷的条目），并结合后续提交与历史审查意见推断每轮结束时各缺陷的生命周期状态。
   - **一致性过滤**：每个任务独立运行标注管线三次，仅当所有运行结果的缺陷卡片在状态转换和语义描述上完全一致时才保留。

4. **人工交叉验证**
   - 六名五年以上经验的开发者组成标注团队；每任务先由两名主标注独立验证，**Cohen's kappa = 0.87** 表明高度一致；存在分歧时由第三名仲裁者介入，通过讨论达成一致共识。

### 2.3 缺陷分类体系

- 缺陷分为两大类共 13 个子类：功能缺陷（F）和可演化性缺陷（E）。进一步细分为逻辑缺陷（F.2）、接口缺陷（F.1）、资源管理（F.3）、检查不足（F.4）、测试请求（E.4）、安全隐患（F.7）等。
- 严重度分六级：Trivial、Minor、Normal、Major、Blocker、Critical。

## 六、主要结论与发现

论文通过实验得出三项核心发现：

1. **总体能力有限**：
   - 主流 LLM 在多轮代码审查的缺陷检测任务上 F1 普遍低于 0.55；
   - 缺陷生命周期状态预测即使只在正确识别到缺陷的情况下计算，最高准确率仅约 80%；
   - 性能随审查轮次增加显著下降（从 R2 到 R10 普遍呈退化趋势），表明长程多轮推理仍是难点。

2. **缺陷敏感性**：
   - LLM 对不同缺陷类型的识别差异明显：F.3（资源管理）、F.4（检查不足）等类型命中率相对较高；而 E.2（视觉表达）、E.3.1（结构组织）等类型命中率较低；
   - 高严重度缺陷（Critical、Major）比低严重度缺陷（Minor、Trivial）更容易被识别；
   - 语义复杂、低显著性的缺陷漏检风险更大。

3. **潜在失败机制**（通过 FP/FN 错误分类学揭示）：
   - **FP（假阳性）主要根因**：状态-时间错位（把已解决的缺陷重新标记为 New，32.5%）、过度审查（把非缺陷视为缺陷，27.8%）、领域知识不足（22.4%）、版本兼容性盲区（12.1%）；
   - **FN（假阴性）主要根因**：跨轮缺陷遗忘（过早不再提及未解决的缺陷，25.1%）、长距离依赖遗漏（23.4%）、语义缺陷盲区（22.3%）、过度乐观的修复假设（15.2%）、谄媚偏差（6.5%）。

## 七、方法亮点与主要优点

- **弥补空白**：首次将多轮代码审查形式化为状态感知任务，用缺失的评测资源揭示了单轮静态基准未能暴露的挑战，是该方向的首创性基准测试；
- **细粒度标注**：每条缺陷带有结构化元数据和明确的状态转换标签，支持多维分析（缺陷类型、严重度、状态演变）；
- **构建管线严谨**：采用“局部检测 → 全局追踪”的 LLM 标注管线，结合三次一致性过滤和人工交叉验证，兼顾了数据集构造的扩展性与标注质量，最终达到高置信度（kappa=0.87）；
- **评估指标选择有理有据**：通过 QWK 预实验比较不同指标与人的一致性，而非直接采用传统文本匹配，使实验结论更有说服力；
- **深入的错误根因分析**：将错误细分为 FP/false positive 和 FN/false negative 两个维度分别构建根因分类树，加深了对 LLM 为何多轮失效原因的理解。

## 八、不足与局限

- **算力信息缺失**：未报告推理/评估所用 GPU 资源，导致结果可复现性下降；
- **基准类型与数据量**：2269 个任务数据量中等，数据来自开源仓库（排除企业私有仓库），可能不涵盖企业级审查的某些关键特征（如内网安全限制、审查规范等），因此其可迁移性未必完全代表工业界全部场景；
- **模型数量限制**：评估了 7 个 LLM，尽管已覆盖主流模型类，仍然难以代表未来 LLM 的发展趋势和研究广度；
- **标签质量依赖 LLM 与人工的双重风险**：标注虽加入人工交叉验证与一致性过滤，但过滤本身可能移除困难样本，造成基准保留下来的“幸存者偏差”，低估真实难度；
- **评估指标的局限**：LLM-as-Judge 本身存在偏差与评估成本高的潜在问题，由于 GPT-5.2-pro 作为主法官模型，也可能让评估中模型自身的提升空间因 API 版本迭代而改变，造成横向不可比的风险；
- **评论质量评估层面略有不足**：ClearCRC 并非为多轮跨缺陷追踪场景定制，对“是否维持跨轮语义承诺”的评估效果尚未明确。

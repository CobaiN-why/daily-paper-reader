## 摘要
仓库级软件工程基准测试显著推进了编码智能体的评估，但现有基准主要衡量生成的补丁是否通过功能测试，而忽略了实际软件开发中常影响补丁可接受性的、源于代码审查的验收约束（即审查约束）。我们提出 SWE-Gate，一个仓库级软件工程智能体基准，显式地同时评估审查约束合规性与功能正确性。SWE-Gate 从真实拉取请求审查评论中提取审查约束，并围绕这些约束合成仓库级修复实例。每个实例提供独立的功能测试与约束测试，并配以不合规补丁及黄金补丁，从而明确区分问题解决能力与审查约束合规性。我们构建了包含 303 个仓库级修复实例的 SWE-Gate，这些实例覆盖 75 个开源 Python 仓库，横跨多种软件领域。在通用编码智能体脚手架下使用四个能力水平不同的 LLM 后端进行实验，结果显示功能成功与完整修复规范下成功之间存在显著差距：在 644 次通过功能测试的修复中，有 221 次未能满足所给出的审查约束。这些发现表明，仅基于功能的评估会高估智能体满足仓库级修复任务完整需求的能力。包含代码、数据与实验结果的复现包可在 https://github.com/DeepSoftwareAnalytics/SWE-Gate 获取。

## Abstract
Repository-level software engineering benchmarks have significantly advanced the evaluation of coding agents, but existing benchmarks primarily measure whether generated patches pass functional tests and overlook review-derived acceptance constraints (review constraints) that often influence whether a patch is acceptable in real-world software development. We introduce SWE-Gate, a repository-level benchmark for software engineering agents that explicitly evaluates review constraint compliance alongside functional correctness. SWE-Gate derives review constraints from real pull request review comments and synthesizes repository-level repair instances around these constraints. Each instance provides separate functional and constraint tests, together with non-compliant and gold patches, enabling explicit separation between issue resolution capability and review constraint compliance. We construct SWE-Gate with 303 repository-level repair instances spanning 75 open-source Python repositories across diverse software domains. Experiments with four LLM backends spanning different capability levels under a common coding-agent scaffold reveal a substantial gap between functional success and success under the complete repair specification: among 644 repairs that pass the functional tests, 221 fail to satisfy the provided review constraints. These findings show that functional-only evaluation overestimates agents' ability to satisfy the full requirements of repository-level repair tasks. The replication package including code, data, and experimental results is available at https://github.com/DeepSoftwareAnalytics/SWE-Gate.

# SWE-Gate 论文详细总结

## 一、论文的核心问题与整体含义

### 研究动机
- 现有仓库级软件工程基准（如 SWE-Bench）主要以"生成的补丁是否通过功能测试"作为唯一或主要评估标准。
- 但在真实软件开发中，补丁能否被合入不仅取决于功能正确性，还受到代码评审阶段维护者提出的各类验收要求的制约——论文称之为**"评审约束"（review constraints）**。例如向后兼容性、既有异常语义的保持、仓库特定实现约定等。
- 传统基准忽略了这些约束，导致**纯功能评估可能高估智能体满足完整修复需求的能力**。

### 核心问题
- 能不能通过功能测试不代表补丁满足所有工程验收要求。
- 如何将"评审约束"显式纳入仓库级修复任务的评估，使其可执行、可定量度量？
- 由此提出**双维评估**：功能正确性 + 评审约束合规性。

### 整体含义
- SWE-Gate 是第一个将"可执行的评审约束"与"功能测试"并列评估的仓库级基准。
- 实验证明功能成功与完整规范成功之间有显著差距：**644 个通过功能测试的修复中，221 个未满足评审约束（34.3%）**，揭示了现有评估体系的重要盲区。

## 二、方法论：SWE-Gate 基准构建框架

### 核心思想
- **约束优先（constraint-first）构建策略**：不从现成的 issue–PR 对出发直接构造任务，而是先从真实评审评论中提炼约束种子，再将其迁移到兼容的仓库上下文中，合成出同时具备功能缺陷和评审约束的修复任务。
- 设计关键：每个实例包含**非合规补丁**（通过功能测试但违反约束）与**黄金补丁**（通过两类测试），从而证明"约束合规性不蕴含于功能正确性"且"两者可同时满足"。

### 每个实例的组成部分
- Issue Description：用户视角的可见功能缺陷描述。
- Mutant Patch：向原仓库注入可复现缺陷的补丁。
- Functional Test：暴露缺陷并验证修复的测试。
- Constraint Description：超出功能正确性的自然语言工程需求。
- Constraint Test：验证是否符合评审约束的测试。
- Non-compliant Patch：通过功能测试但违反约束的参考修复。
- Gold Patch：同时通过功能测试和约束测试的参考修复。

### 三阶段构建流程

**Phase I：约束种子提取（Constraint Seed Extraction）**
- 从 GitHub API 收集种子仓库的合并 PR 及其评审评论、关联 issue、变更文件等原始数据。
- 第一阶段 LLM 提取评审评论中的**原子化建议**，并做规则过滤（剔除流程性、文档类、纯测试类、格式类、命名类、琐碎/不可验证的要求）。
- 第二阶段 LLM 结合 issue、评审和代码证据进行候选验证：要求 issue 用户可见、diff 支撑根因、评审要求确实新增了功能之外的需求、且能够提出独立于功能测试的验证逻辑。
- 通过者形成结构化的"约束种子"：保留跨仓库的归一化工程意图与行为范围，去除仓库特有措辞。

**Phase II：实例合成（Instance Synthesis）**
- 借鉴 SWE-Mirror 的跨仓库迁移范式，将约束种子迁移到兼容的目标仓库中合适的合成锚点。
- 采用**渐进式两阶段"生成–执行–精炼"流程**：
  1. 先构建 mutant.patch 和只含功能测试的 function_test.patch，验证"测试在原仓库通过、在 mutant 上失败"。
  2. 再构建 constraint_test.patch、非合规补丁 non-compliant.patch 和黄金补丁 gold.patch，验证"非合规补丁通过功能测试但不满足约束测试；黄金补丁两者均通过"。
- 若约束维度无法独立，则回退到第一阶段重新生成，直至满足完整验证矩阵。

**Phase III：质量保证（Quality Assurance）**
- 首先做基础结构检查（工件完备性、执行命令、溯源字段）。
- 再进行容器化完整验证矩阵执行（表 1）：
  - 原仓库 R：功能测试通过
  - 突变体 R+M：功能测试失败
  - 非合规修复 R+M+N：功能测试通过、约束测试失败
  - 黄金修复 R+M+G：两类测试均通过
- 接着进行 LLM 语义审查，依据人工总结的失败模式分类（如约束与功能冗余、测试执行了自然语言未提及的行为、为可测性引入额外抽象等）。
- 最后对所有保留实例进行人工审查，确认 issue 真实性、约束可迁移性与自然性、补丁的通用性。

### 核心验证矩阵
| 仓库状态 | F（功能测试） | C（约束测试） |
|---|---|---|
| 原仓库 R | 通过 | — |
| 突变体 R+M | 失败 | — |
| 非合规修复 R+M+N | 通过 | 失败 |
| 黄金修复 R+M+G | 通过 | 通过 |

## 三、实验设计

### Benchmark 概况
- **303 个仓库级修复实例**，覆盖 **75 个开源 Python 仓库**。
- 覆盖领域：数据分析、Web 框架、测试框架、命令行工具、配置管理、符号计算、数据验证等。
- 约束类别为多标签体系，最主要的类别为：错误语义（50.2%）与 Schema/元数据/类型（47.2%），其余包括顺序/参数保持、编码/转义、范围泛化、兼容性/弃用、缺失 vs. 空值区分、性能、幂等性、资源生命周期等。

### 评估模型与设置
- 4 个能力层次不同的 LLM 后端：
  - GPT-5.5（最强）
  - GPT-5.4-mini
  - DeepSeek-V4-Flash
  - GPT-4o-mini（最弱）
- 统一使用 **Mini-SWE-Agent** 脚手架，每个实例最多 **100 步交互**。
- 使用标准 SWE-Bench 执行管线在隔离容器中验证补丁。
- 测试文件生成补丁在评估前被丢弃，防止评估泄露。

### 输入消融条件
- **Constraint-Provided (+C)**：智能体同时获得仓库、issue 描述和自然语言约束描述。
- **Constraint-Omitted (−C)**：只提供仓库和 issue 描述（与 +C 相同的隐藏测试）。
- 目的：测量显式约束描述对修复结果的影响。

### 评估指标
- **FSR**（Functional Success Rate）= 通过功能测试的实例数 / 总实例数
- **CFR**（Constraint Following Rate）= 功能成功中同时通过约束测试的比例
- **JSR**（Joint Success Rate）= 同时通过两类测试的实例数 / 总实例数（**主要指标**）
- 另有 HFR（Hidden Failure Rate）= 1 − CFR，用于度量功能测试下的隐藏失败。
- ∆M 表示 +C 相比 −C 的指标差值（百分点）。

## 六、主要结论与发现

### RQ1：双维评估下智能体表现如何？
- GPT-5.5 FSR 最高（74.9%），DeepSeek-V4-Flash 66.7%，GPT-5.4-mini 61.7%，GPT-4o-mini 仅 9.2%，说明基准对弱模型困难。
- 功能成功不等价于联合成功：GPT-5.5 有 227 个功能成功，仅 160 个联合通过，CFR 为 70.5%。
- 四模型合计：**644 个功能成功中只有 423 个通过约束测试，221 个为隐藏失败，HFR 达 34.3%**（GPT-5.5：29.5%、GPT-5.4-mini：35.8%、DeepSeek-V4-Flash：35.6%；GPT-4o-mini：53.6%）。
- 纯功能测试显著低估了不合规风险。

### RQ2：显式约束描述的影响？
- 提供约束描述（+C）使所有模型的 JSR 均提升：GPT-5.5 +11.5 个百分点（41.3% → 52.8%），效果最大。
- CFR 在四个模型上提升 10.2～25.6 个百分点。
- 但同时 FSR 出现小幅下降（GPT-5.5 −0.7，其他模型 −3.3 ～ −9.9 个百分点），说明引入额外约束可能增加修复复杂度、分散智能体对功能修复的专注度。

### RQ3：哪些约束类别最困难？
- 范围泛化（Scope Generalization）：CFR 为 46.3%～63.0%，较难满足。
- 生命周期清理/资源管理：CFR 为 53.8%～62.5%。
- 编码/转义/引号：对 GPT-5.4-mini（51.1%）和 DeepSeek-V4-Flash（55.9%）有困难。
- Schema/元数据/类型：CFR 60.7%～68.3%。
- 相对容易的类别：缺失 vs. 空值/哨兵区分（74.2%～81.6%）、顺序/参数保持（75.0%～79.6%）。
- 结论：聚合分数掩盖了不同工程约束上的显著能力差异。

## 七、优点与亮点

1. **问题选择精准且有实际价值**：指出了功能测试单维度评估的系统性盲区，对编码智能体评测方法学有明确推进。
2. **"可执行评审约束"的概念落地**：把代码评审中模糊的工程要求转化为确定性的可执行测试，避免 LLM-as-Judge 的主观性。
3. **重心的区分性设计**：非合规补丁与黄金补丁的对照设置从构造上确保了"约束合规性 ≠ 功能正确性"，验证矩阵逻辑严谨。
4. **半自动、可扩展的构建流程**：约束提取 — 跨仓库迁移 — 增量式生成执行修正 — 多层质量保证（结构检查+执行验证+语义审查+人工终审）流水线成熟，框架可复用。
5. **遵循 fail-to-pass 的成熟范式**：保持与原基准的兼容性，便于社区迁移使用。
6. **数据集多样**：75 个仓库、多个领域、多标签约束分类，支持细粒度分析。
7. **受控输入消融**：区分"提供了约束"和"未提供约束"的影响，结论有更强的解释力。
8. **减轻数据污染风险**：约束种子被迁移到新上下文而非直接复用原 PR，降低直接背诵解决方案的可能性。

## 八、不足与局限

1. **语言覆盖有限**：所有实例均为 Python 仓库，约束特性与语言生态相关，结论不能自然泛化到 Java、TypeScript 等其他语言。
2. **单次运行缺少方差估计**：每个模型每个条件只跑一次（one generation per model per instance），未报告重复运行的变异度或使用采样温度多次运行取通过率的做法，影响稳定性判断。
3. **约束类别不互斥且规模不均**：多标签分类虽然合理，但小类统计基于几十个样本，类别比较属于描述性发现而非推断性结论。
4. **GPT-4o-mini 的功能成功数过低**：多数类别下该模型没有足够功能成功样本，CFR 的条件估计不可靠。
5. **弱模型上 FSR 偏低对 CFR 稀释的解读需谨慎**：当 FSR 极低时，CFR 的分母非常小，数字可能不具备代表性。
6. **合成仍有偏差风险**：LLM 同时参与约束提取、实例合成和筛选，尽管有人工与规则审查兜底，仍可能引入系统性的模型偏好或"看似合理但不真实"的评审约束场景。
7. **直接上游局限**：对于某些评审约束（如涉及非功能需求、人工设计权衡、无法轻松写就可执行断言的约束），SWE-Gate 无法覆盖，限制了约束类型的完整性。
8. **训练污染无法完全排除**：论文声明跨仓库迁移能"缓解"而非"消除"污染风险，但无法给出完全保障。
9. **资源与算力信息缺失**：没有报告完整的推理资源要求，也不利于复现时的成本估算。

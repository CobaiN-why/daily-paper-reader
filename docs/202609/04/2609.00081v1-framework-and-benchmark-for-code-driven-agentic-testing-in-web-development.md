## 摘要
端到端GUI测试对于验证Web应用至关重要，然而现有评估依赖于预定义清单，并局限于Web生成基准的数据与框架，导致视觉语言模型（VLM）的缺陷发现能力未得到系统测试。我们提出了**代码驱动的智能体测试（CAT）**范式，其中智能体编写Playwright代码来驱动浏览器、收集反馈，并自主探索Web应用以发现缺陷。我们以CATJudge实例化CAT，CATJudge是一个在统一环境中整合Browser-Use与Computer-Use工具的智能体框架；同时以CATTest作为基准，包含102个由AI生成的Web应用，带有精心标注的缺陷，并通过紧密的人机协作构建，以呈现复杂交互和细微缺陷。实验表明，主流视觉语言模型在评测中表现不佳，揭示了当前VLM能力与AI Web开发中真实测试需求之间的明显差距。我们的代码和数据已发布在https://github.com/SleepyWithoutCoffee/CATJudge。

## Abstract
End-to-end GUI testing is essential for verifying web applications, yet existing evaluations rely on predefined checklists and are confined to the data and frameworks of web generation benchmarks, leaving the bug-discovery ability of vision-language models (VLMs) systematically untested. We introduce \textbf{C}ode-driven \textbf{A}gentic \textbf{T}esting (CAT), a paradigm in which the agent writes Playwright code to drive the browser, gathers feedback, and autonomously explores web applications to uncover bugs. We instantiate CAT with CATJudge, an agentic framework that unifies Browser-Use and Computer-Use tools within a single environment and CATTest, a benchmark of 102 AI-generated web applications with carefully annotated bugs, built through close human-AI collaboration to feature complex interactions and subtle defects. Experiments with mainstream VLMs show that all evaluated models perform poorly, revealing a clear gap between current VLM capabilities and the demands of real-world testing in AI web development. We release our code and data at https://github.com/SleepyWithoutCoffee/CATJudge.

## 一、论文的核心问题与整体含义（研究动机和背景）

- 端到端 GUI 测试是验证 Web 应用正确性的关键环节。许多程序缺陷**只有在代码被浏览器渲染之后才会显现**，无法仅通过文本层的单元测试或静态分析发现（如交互事件、渲染异常等）——这是"AI 生成 Web 应用"场景中质量保障的核心难点，也影响训练数据筛选（过滤低质量软件）。
- 现有 Web 代码生成基准评估大多采用基于规则的打分或 LLM-as-Judge 打分；更近一段工作虽引入 GUI 智能体执行封装好的点击/键入操作，但其流程隐含两大结构缺陷：
  1. **依赖预定义清单（checklist）**：测试对象假设页面是"功能完整、可正常操作"的，清单测试只能是验证能力，无法覆盖 AI 网页中超出预期的特性、组合行为或交互状态机边角；页面和清单规模越大，成本与可靠性问题越突出。
  2. **经验范围受限**：现有测试评估嵌套在 Web 生成基准内部，被该基准的数据分布、目标网页种类、交互复杂度、bug 隐蔽程度所限制，不能系统性衡量模型在真实缺陷面前自主发现 bug 的能力。
- 针对上述 gap，本文提出 **CAT（Code-driven Agentic Testing，代码驱动智能体测试）**：被测者**不再是执行固定操作序列的"点击器"，而是像 QA 工程师一样直接编写 Playwright 代码**来驱动浏览器、收集文本与视觉反馈、自行决定探索路径并最终给出 bug 列表与 pass/not-pass 判定。
- 为落地该范式，论文配套构建了 **CATJudge**（统一 BUA/CUA 两种主流 GUI 智能体工具的智能体框架）与 **CATTest**（102 个 AI 生成的复杂 Web 应用及人为精标 Ground-Truth bug 的基准），并用 16 个主流 VLM 实验验证了 CAT 任务的挑战性——**即便是最强模型 R-score 也不足 43**，展示出当前能力与实际 AI Web 开发测试需求之间的显著鸿沟。该工作对"AI 是否能自动做 QA"以及"如何衡量编码智能"具有范式和工具双重贡献。

## 二、论文提出的方法论：核心思想、关键技术细节、公式与算法流程

### 核心思想
- **"三层考察"工作流分析**：类比人类研发流程，把 AI 驱动的 Web 开发抽象为闭环"用户→需求→AI→测试→交付"。去除"需求工程→测试"的沟通环节，让模型直接消费开发侧信息，自主任务往返。将测试工作划分为三种检查仰角：
  1. **Developer-Side**：纯静态代码审查（需专业经验，无交互、无视觉反馈）；
  2. **Hybrid-Side**：审查与用户视角结合——检查 DOM / 渲染、运行 JS、调用浏览器的调试渠道（Playwright 是典型）；既能拿到脚本化，又保留视觉反馈；
  3. **User-Side**：仅使用键盘/鼠标与屏幕截图（如 PyAutoGUI），完全黑盒用户视角。
- **为什么选 Hybrid-Side 作为评估面**：以 Playwright 为核心工具，同时使用视觉截图、访问 DOM 和注入脚本。前向证据（表 3）证明它是三者中性能最均衡、成本更低的界面——开发者纯审查 P-score 崩塌，纯用户侧因屏幕元素定位困难而拉低 R-score。

### CATJudge 框架
- **任务形式化**：被建模为 POMDP (S, A, O, T, Ω, R, H)，状态 st 为包含缺陷的 DOM/运行时潜在状态；观测 ot 仅暴露部分状态（工具返回文本 + 系统自动给的最新截图）；动作空间 **A = A_int ⊔ {a_term}**——工具动作集合 + 终止动作；每回合 agent 根据测试指引 I（含 QA 导向的项目文档）与历史选择动作。
- **奖励与终止**：终止动作 aterm 输出 verdict（PASS 或 NOT_PASS）及 bug 列表 B；若耗尽 H=250 回合亦终止。稀疏回报定义为 **R(s_T, a_T) = score(B, B*)**，B * 为真实 bug 集合。
- **环境层设计（实践亮点）**：
  - **远程解耦部署**：被测应用运行在远程 Docker 容器/独立服务器；启动前自动执行 npm install / npm run dev；结束时自动拆卸；本地工具解释器通过统一 Web API 调用远端资源，具备扩展性。
  - **统一 Browser-Use + Computer-Use 运行时**：服务器上运行 Xvfb 虚拟显示；CUA 的 PyAutoGUI 桌面级鼠标键盘模拟、BUA 的 Playwright GUI 自动化可以作用于**同一虚拟屏幕上的同一个浏览器实例**——保证两套工具的渲染状态一致。
  - **隔离模式**：任选"异地（不同服务器）= 强隔离"或"同机不同虚拟显示 = 软隔离"。
- **初始化与反馈设计**：
  - 为避免"从零开始乱学"，初始状态注入**QA 导向的项目文档**（功能概述、技术栈与关键状态变量、交互面）和首屏截图——与人类 QA 的交接习惯对齐。
  - 每轮工具调用返回结构化文本反馈（状态、DOM 内容、运行返回值、错误），停 0.1s 让页面冷却后再截图，只保留最近一张截图，避免无限上下文；也提供 **wait**（主动等待/刷新）与 **a11y_parsed**（作为可选工具获取无障碍树）能力，缓解"幻觉推理（mirage reasoning）"。
- **工具界面**："核心工具集仅保留 Playwright 脚本执行工具 + wait + a11y_parsed + answer"，取代了封装原子操作（click/type 等）。因为：强代码能力的模型更偏爱脚本执行、脚本执行也更节流 token 并减少调用次数（图 5，§4.2）；不把 a11y tree 喂进默认输入，而是让人按需自行查看。

### CATTest 基准构建（多轮人-AI 协作生产线）
- **生成**：先枚举 9 类常用 Web 场景，从 Wikipedia 与真实产品用例归纳每个应用所需的交互类型（拖拽、视口旋转、FPS 射击、网格定位等），最大化类别内差异 → 生成覆盖 19 类交互模式的 meta 描述（如 Cat.8 游戏细分 19 种子类）；用 Anthropic 的**Claude-Opus-4.6 + Claude Code** 为每个场景生成复杂度足够高的"用户提示即需求规格"。
- **难度控制（关键 Trick）**：若让 Claude Code 能轻松完整实现，则没有 bug 可测；而太弱生成器则产出大量无法启动/崩溃页面，无法保底交互缺陷。因此他们**人为提升需求体积**：用"两次分解"（Initiative→Epic→Feature→User Story，INVEST 方针）反复扩大 PRD 规模，直至用户故事数量足够大（平均 43.4 个/项目），使**前沿编码代理也必然留下自然缺陷**——无需任何手动注入 bug。然后人工匿名化（去除真实品牌/版权内容）、去除过强技术约束、移除非桌面支持需求。
- **Bug 标注**：人工体验 → 初始 bug 清单 → 人工 GUI 复现确认 → Claude Code 在源码层面判定是否真缺陷（人机协作检查词义歧义并同步修正说明文档以减少虚假正例）→ 对无法收敛的边角现象直接改代码消除 → **CATJudge 多强模型工具竞争池探测贡献新 bug**——该循环迭代直到所有新报告均被判定为重复/误报。该过程产出 190 个 GT bugs；bug 平均出现在 77.45% 项目中（表 5），约 1.86 个/项目。

### 评估指标
- **粗粒度指标**：把 PASS/NOT_PASS 当二分类（正类 = NOT_PASS），报告 Accuracy / Recall / Precision / F1。用于过滤生成资料质量。
-

- **细粒度指标（Bug Discovery）**：以模型最终给出的 bug 列表质量为核心。将每条汇报 bug 按**基于 LLM 的匹配**与 GT bug 集合对齐（同时人工抽查校准匹配阈值），以 bug 级别统计真实得分，再除以 GT 中相对测试指令实际可探测的 bug 总数，得到 **R-score**（recall，衡量“找到多少”）；对模型汇报的每条 bug，判断其是否属实，得到 **P-score**（precision，衡量“汇报质量”）；二者结合得 **D-score**（如无特殊说明即 F1）。指标不要求 bug 报告的顺序、措辞与根因分析，只要求“定位到页面行为”级的一致。

## 三、实验设置与主要结果

### 实验设置
- **模型池（16 个主流 VLM）**：涵盖闭源前沿模型（Claude 系列、GPT-4o/4.1、Gemini 2.0 Flash / Pro 等）与开源主力（Qwen2.5-VL、InternVL3、Llama-3.2-Vision、Mistral-Small-3.1 等）。为保证公平，所有 GUI 智能体层（Browser-Use / Computer-Use）使用同一套默认配置，网页动作解释执行器统一为同版本 Playwright/PyAutoGUI。
- **运行环境**：每任务约 250 回合上限；被测应用部署于远程容器，本地只运行 agent 推理。对每个模型重复多次跑取均值，并报告带方差的结果；主实验基于 “模型在 **CATTask-Text-Only** 或 **CATTask-Text+Vision** 两种输入模式” 下进行，以观察 VLM 视觉通道的实际增益。
- **对比基线**：并非与现有 benchmarks 直接横向比较（任务定义不同），而是把 CATJudge 内三种工作流形态做纵向对照：Developer-Side（静态代码 + 无浏览器）、User-Side（纯截图 + 鼠标键盘）、Hybrid-Side（本文默认），并进一步比较**代码驱动**与**传统预定义动作序列（点击器）**的表现差距。

### 主要结果（对应论文图表）
1. **主排行榜（表 4）**：16 个模型在 CATTest 上的结果普遍偏低且区分度明显——最强模型 R-score 也低于 43，P-score 普遍低于 50；模型之间的排序与常见编码/问答基准的排序并不完全一致，说明 CAT 度量了独立的、不可由其他基准替代的能力维度。
2. **工作流对比（表 3）**：Hybrid-Side 显著优于 Developer-Side 与 User-Side。Developer-Side 的 P-score 极低（大量“推测性缺陷”无法通过运行验证），User-Side 的 R-score 有限（黑盒点击难以高质量完成功能级探索）；Hybrid-Side 在 R/P/成本三方面取得最佳平衡。
3. **代码驱动 vs 点击器（图 4 及消融）**：在相同 VLM 下，代码驱动的 agent 比“给定原子操作列表”的 agent 在 R-score 上提升明显，且回合内工具调用次数显著减少（图 5）。原因在于代码能将多步交互（循环、条件、批量 DOM 查询）压缩成一次执行。
4. **视觉输入的影响**：文本+视觉模式普遍优于纯文本模式，但收益大小因模型而异；部分开源模型对截图信息利用不足，增益有限，说明 GUI 测试任务同时考验视觉 grounding 与代码推理的协同。
5. **GT Bug 分布与任务难度（表 5）**：190 个 GT bug 分布于 102 个应用，类型覆盖逻辑错误、渲染错位、状态同步缺失、边界条件崩溃、响应式断裂等；单项目只含 1~3 个 bug 且不显式提示，导致模型容易“过度报告”（P 低）或“漏报”（R 低），二者矛盾显著。
6. **可扩展性与实用性验证（表 6）**：CAT 作为通用测试框架可迁移到非 AI 生成的 Web 应用、更长的任务（H 提高到 500）、以及不同目标网页（真实开源站点），R-score 虽受页面规模影响，但整体行为保持一致，证明框架不依赖生成数据集的固定模式。

## 四、论文的创新点

- **任务范式创新**：首次将 “agent 自主写测试代码” 引入 GUI 级自动验证，把评估对象从代码生成质量扩展到“面向真实缺陷的端到端质量保障能力”，填补了现有 Web 生成基准缺少自由探索式 bug 发现环节的空白。
- **框架设计创新**：CATJudge 在统一环境中融合 Browser-Use 与 Computer-Use，并且用**脚本执行接口替代原子 UI 动作接口**，从系统层面验证了“代码作为测试动作语言”的可行性及其 token/性能双优势。
- **数据生产方法创新**：提出“人为扩大 PRD 规模让大模型自然犯错”的 bug 植入策略，以及人机协同多轮标注收敛流程，使得 bug 标注成本可控、语义歧义低、反例少。
- **评估指标创新**：同时报告粗粒度 pass/not-pass 分类指标与细粒度 bug 发现质量指标（R/P/D-score），避免二分类掩盖信息，能更精确刻画模型在“不告诉哪里有 bug”条件下的真实表现。

## 五、局限性与潜在改进方向

- **成本与速度**：每任务最多 250 回合、依赖多次 LLM 调用与真实浏览器环境，评测成本仍显著高于静态基准；未来的方向是让 agent 学会更早调用 answer 或引入预算自适应策略。
- **VLM 的视觉利用深度不足**：多数模型在纯文本模式就已很强，说明它们尚未充分利用截图；如何显式训练“GUI 缺陷视觉定位”能力值得进一步探究。
- **GT 的可判定性边界**：部分 bug 带有主观色彩（如“样式不够美观”），虽然人工已用代码级确认收敛，但多样化的评价者仍可能产生分歧；未来可引入更细粒度的 bug 严重级别与可复现步骤模板。
- **静态审查模式弱化**：代码驱动的 Hybrid-Side 在自动化上最有效，但纯 Developer-Side 体现的“阅读源码找 bug”能力同样重要；本文评估面主要依赖浏览器反馈，对静态审查的要求偏低，可能低估擅长静态分析的模型。
- **安全与越狱考虑**：允许 agent 执行任意 Playwright/Python 代码意味着被测应用可能遭受恶意输入；生产部署需在容器权限、网络隔离与代码沙箱方面作严格限制。

## 六、个人评价与思考（延伸讨论）

- 本文最大的方法论启示是：**“让 AI 测试 AI” 不应局限在让模型模拟用户点击，而应让模型直接使用工程化测试语言**。这实际上把“测试能力”归约成编码智能 + 环境交互智能的复合体——更贴近真实 QA 工作形态，也自然提升了评估的难度上限。
- 与现有“Agent 做软件工程”（如 SWE-bench）不同，CAT 强调 **动态运行反馈中逐步修正判断**，是“部署后行为验证”的一个重要的新维度。
- 工业界可直接借鉴的落地点是“AI 网页自动巡检”：把 CAT 的前置文档注入、结果收敛判定和预算机制抽取出来，配合 CI 流水线能大幅降低人工回归成本。
- 需要警惕的是，如果未来 Web 应用测试结果被用于训练数据过滤，可能会诱导模型生成故意规避被发现的 bug 的对抗性行为；因此后续研究有必要同步制定针对 CAT 的可审计、可解释报告协议。

总体而言，本论文用自己的工具与数据，严谨揭示了当前视觉语言模型在“未见过的复杂网页里自己找 bug”这一任务上仍十分薄弱；它提供的范式、基准与框架，为后续研究定义了可复现的起点。

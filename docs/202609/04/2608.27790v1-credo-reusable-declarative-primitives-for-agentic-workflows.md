## 摘要
一个LLM应用既依赖于模型也依赖于程序框架：该程序决定每次调用看到什么、进行多少次调用以及信任哪些答案。编码智能体现在可以通过搜索候选程序来发现强大的程序框架，但由此产生的产物是一个不透明的命令式代码块，其逻辑步骤、运行时信号、物理执行决策和提示策略仍然是隐式的且特定于任务的，迫使后续任务从头开始程序框架搜索过程。然而，复用的潜力是巨大的。一个搜索到的程序框架编码了重要的知识，例如有效的逻辑步骤、重要的信号、适应执行的物理操作决策以及有效的提示策略，然而这些知识被埋在命令式代码中，没有可检查或可复用的结构，也不带有任何来源或元数据。Credo通过恢复搜索到的程序框架的结构化声明式描述，为每个提取的原语标注相关元数据，并用来源记录对所有内容进行编目来解决这个问题。然后，编译器可以绑定存储的原语来为新任务生成程序框架，而不必从头开始搜索。本文提供了初步结果，证明了我们方法的潜力，并提出了一个数据库社区完全有能力解决的相关研究议程，包括基于成本的声明式目录编译以及模型和工作负载漂移下的目录维护。

## Abstract
An LLM application depends on both a model and a harness: the program that determines what each call sees, how many calls to make, and which answers to trust. Coding agents can now discover strong harnesses by searching over candidate programs, but the resulting artifact is an opaque block of imperative code whose logical steps, runtime signals, physical execution decisions, and prompt strategies remain implicit and task-specific, forcing subsequent tasks to start the harness search process from scratch. The potential for reuse, however, is substantial. A searched harness encodes significant knowledge, such as the logical steps that work, the signals that matter, the physical operator decisions that adapt execution, and the prompt strategies that are effective, yet this knowledge is buried in imperative code with no inspectable or reusable structure, nor does it carry any provenance or metadata. Credo addresses this problem by recovering a structured declarative description of a searched harness, tagging each extracted primitive with relevant metadata, and cataloguing all of it with provenance. A compiler can then bind stored primitives to generate harnesses for new tasks without having to start the search over from scratch. This paper provides preliminary results demonstrating the potential of our approach and lays out a related research agenda that the database community is well-positioned to tackle, including cost-based compilation over declarative catalogs and catalog maintenance under model and workload drift.

## 1. 核心问题与研究动机

- **问题背景**：LLM 应用的整体表现不仅取决于基础模型本身，还取决于其外围的 **harness（程序框架/外围控制程序）**。Harness 决定了“每个模型调用看到什么内容、总共调用多少次、在什么条件下接受或拒绝答案”，例如用级联方式先调用小模型、再根据置信度升级到大模型。
- **现有搜索的困境**：编码智能体已经能够通过**智能体式的 harness 搜索**（如 Meta-Harness）来自动发现高质量 harness；然而，搜索结果通常是一个**不透明、单块式（monolithic）的命令式 Python 程序**。其中混合了：
  - 逻辑步骤顺序；
  - 中间运行时信号与条件分支；
  - 物理实现选择（模型选择、top_k 等）；
  - 提示（prompt）策略；
  - 与特定 benchmark 相关的常量与格式约定。
- **核心矛盾**：这种搜索产物虽然编码了大量宝贵知识，但知识深埋在不可检查、不可拆分的命令式代码中，**没有显式结构、没有可复用的原语、也不携带来源（provenance）或元数据**。后续任务面对新的领域时，只能重新从头进行昂贵且耗时的 harness 搜索。
- **论文主张**：借鉴数据库领域对“用户自定义函数（UDF）内省与过程式代码声明式恢复”（如 Froid 等系统）的思路，主张将搜索得到的 harness 自动恢复为带类型的、由**可复用声明式原语**组成的描述，并通过目录（catalog）和编译器实现跨任务、跨领域的复用。

## 2. 方法论与核心技术

### 2.1 核心思想

- 输入是一个已经搜索得到/写好的 `harness.py`，输出是一份**结构化声明式描述**，使得 harness 既能被忠实重建，又能抽取其方法逻辑、过滤与源数据集强绑定的特化内容。
- 系统流程分两阶段：
  1. **离线目录构建**：abstractor（抽象器）恢复原语 → level-tagger（层级标签器）标注泛化层级 → librarian（图书管理员）存入目录；
  2. **在线编译**：compiler（编译器）根据新任务的 `brief.md`（任务描述与回答接口），从目录中选择原语并绑定参数，生成新的可运行 `harness.py`。
- 设计初衷强调：**声明式的智能体执行描述是可移植且耐久的**——搜索过程只在源任务上做一次，后续目标任务通过廉价的编译来复用。

### 2.2 四类声明式原语

1. **Skeleton（骨架/逻辑计划）**：
   - 一个有向无环图（DAG），由命名的算子步骤及依赖关系构成；
   - 表示“harness 计算什么、按什么顺序计算”，相当于查询计划里的逻辑计划层。
   - 例子：`parse_query → retrieve → rerank → generate → self_check`。
2. **Beliefs（信念/派生属性）**：
   - 一种**带类型、有名、带声明计划点的派生属性**（值类型限定在 `{bool, enum, int, float, str}`），供策略读取，从而决定物理执行方式；
   - 分为三类：
     - 输入派生属性（如 `is_semantic_query: bool`）；
     - 中间结果派生属性（如 `extraction_confidence: float`）；
     - 输出质量属性（如 `schema_match: bool`）。
   - 将原本隐式、局部化的条件变量提升为“一等公民”，可记录、可对比、可审计。
3. **Policies（策略/物理实现选择规则）**：
   - 类似数据库系统中“物理算子选择”的规则：基于一个或多个 belief 的条件决定逻辑步骤的具体物理实现（模型选择、检索策略、参数、执行路径）。
   - 示例：检索步骤中，当 `is_semantic_query` 为真时选择 dense retrieval（k=12），否则选择 BM25（k=8）。
4. **Prompt templates（提示模板）**：
   - 搜索发现的自然语言规格说明，即物理算子实现本身；
   - 包含推理策略、指令模式、输出格式、角色人设等，以带可绑定槽位的 NL 模板形式存在；
   - 模板的模式可以跨任务迁移，而内容与具体数据集强绑定的部分则保留在特定域。

### 2.3 目录构建与编译细节

- **Level-tagger 分级**：每个原语被标记为两级：
  - **L1（functional，功能级）**：模式在任务族内可复用，被提升进入共享的 `general/` 目录；
  - **L2（source-specific，来源特定）**：模式只对某数据集/领域成立，只能保留在专门的 `specific/` 目录。
  - 注意：提升参数化常量只是手段（如把 `top_k=12` 提成 `top_k={k}`），真正决定是否可以复用的是经提升后的模式本身。
- **Librarian 存储**：`general/` 按功能（retrieval、reasoning、model routing 等）建立索引并携带来源记录；`specific/` 保留完整描述，保证 provenance 不丢失。
- **Compiler 行为**：编译器通过角色匹配与自然语言元数据来选择原语、将开放槽位绑定到目标域参数（如 `k=8`、persona=`attorney`），然后生成可运行代码；如果无法达到阈值则回退到搜索。

## 3. 实验设计

### 3.1 评测场景与数据集

Credo 构造了**两个功能域、四个检索/推理数据集**：

| 场景（域） | 数据来源（同分布统计构建） | 跨分布统计 |
|---|---|---|
| Finance Retrieval | DocFinQA + FinQA | FinanceBench + TAT-DQA + TAT-HQA |
| Legal Retrieval | CUAD-common + MAUD | ContractNLI + PrivacyQA + CUAD-rare |
| Math Reasoning | OlympiadBench + Omni-MATH | IMO-AnswerBench + IMO-ProofBench + ArXivMath |
| Polyreason Reasoning | GPQA-Diamond（chem+bio） | MMLU-Pro（law+phil）、ZebraLogicBench、MuSR |

每个数据集划分为：
- **search split（100 条）**：供搜索智能体（Meta-Harness）迭代；
- **in-distribution split（100 条）**：与搜索同分布、用于从帕累托前沿挑选最终 source harness；
- **cross-distribution split（300 条）**：结构不同但同源、用于评测编译得到的 harness。

### 3.2 对比方法 / 基线

- **目标参照**：每个目标任务都单独运行 Meta-Harness 搜索得到 harness；这是比较的“上界/参考点”。
- **Brief-only**：编译器只拿到任务 brief，不提供任何原语；
- **Single-domain**：只给编译器一个指定源域提供的 L1 原语；
- **Open-library**：编译器可以访问包含除当前目标以外全部域原语的完整目录（目标域被 hold out）。
- 另设**round-trip 测试**来验证恢复编译的保真度：先在源 harness 上恢复出原语，再直接编译还原，并在同一 in-distribution split 上对比行为。

### 3.3 评测指标

- 任务准确率：由 `gpt-5-mini` 作为裁判模型根据数据集特定规则判定；
- 推理成本：以每问题美分（¢/q）来衡量；
- 同时考察两个量，不合并为单一分数；
- 搜索/编译/恢复成本同时以美元和墙钟时间报告；搜索轨迹按每轮记录。

### 3.4 搜索与 harness 获取设置

使用 Meta-Harness（前沿智能体搜索器）作为统一的 harness 发现工具；每个域跑 10 次迭代，每域跑 3 个随机种子；所有 agent 与 evaluator 均在沙箱中运行以防止 eval 泄漏。从 in-distribution split 的 accuracy/cost 帕累托前沿中选择单个 source harness 供 Credo 恢复。

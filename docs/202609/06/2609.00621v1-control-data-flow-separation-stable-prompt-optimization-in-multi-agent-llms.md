## 摘要
提示优化可以改进多智能体大语言模型系统，但被优化的提示往往扮演两个纠缠不清的角色：生成任务相关内容和指定执行关键协议（如消息路由、输出格式和终止信号），底层代码依赖于这些协议。因此，旨在改进内容生成的提示编辑可能无意中破坏协议并导致整个智能体流水线失败。我们的关键观察是，这两个角色具有不同的表示形式：执行协议通常是结构化的，而任务相关内容通常以非结构化语言表达。基于此，我们提出控制-数据流分离，将执行关键控制表示为类型化、验证过的程序对象，而任务相关语言则保持为可优化的数据流，用于智能体通信。这种设计使优化器能够改进多智能体行为，而不会使路由或格式化接口遭受提示漂移。在合成推理、协作评审生成和保险评级工作流中，我们的框架经验性地实现了100%的最终协议有效性，同时持续改善任务性能。

## Abstract
Prompt optimization can improve multi-agent LLM systems, but the prompts being optimized often serve two entangled roles: generating task-relevant content and specifying execution-critical protocols, such as message routing, output formatting, and termination signals, on which the underlying code relies. As a result, a prompt edit intended to improve content generation can inadvertently corrupt the protocol and cause the entire agent pipeline to fail. Our key observation is that these two roles have different representations: execution protocols are typically structured, while task-relevant content is usually expressed in unstructured language. Based on this, we propose control-data flow separation, where execution-critical control is represented as typed, validated program objects, while task-relevant language remains the optimizable data flow for agent communication. This design allows optimizers to improve multi-agent behavior without exposing the routing or formatting interface to prompt drift. Across synthetic reasoning, collaborative review generation, and insurance rating workflows, our framework empirically achieves 100% eventual protocol validity while consistently improving task performance.

### 1. 核心问题与整体含义（研究动机）

多智能体大语言模型系统通过多个、职责分工明确的智能体协作解决复杂任务（例如协作论文评审、保险评级等），每个智能体的行为依赖其提示词（Prompt）。提示优化技术（如 TextGrad、DSPy）将提示视为可学习参数进行自动优化，这是提升系统任务能力的关键。

然而，研究者发现一个关键矛盾：在多智能体系统中，提示词往往同时承担两个角色：

- **内容生成（Data）**：产生任务相关的自然语言内容，如评审意见、解释、批判等，供其他智能体或优化器阅读。
- **协议控制（Control）**：作为控制器解析的接口，指定路由、输出格式、终止信号等底层程序依赖的执行关键信息。

若将两者纠缠在同一个可编辑文本提示中，提示优化器为改进内容而做出的任何编辑都可能“意外”改写协议（例如 JSON 字段名、路由指令），这会导致整个多智能体流水线崩溃——不只是答案质量下降，而是解析失败、路由失效或直接宕机。论文将这一风险定义为**协议脆弱性（Protocol Fragility）**。

### 2. 方法论：核心思想与技术细节

论文提出 **控制-数据流分离（Control-Data Flow Separation）**，其核心洞察是：“协议通常是结构化的，而任务内容通常是非结构化语言”。代表不同角色的信息应采取不同载体，相互独立、各司其职。

**核心设计**：将智能体输出分为两个通道：
- 控制通道（Control）：类型化、经过验证的程序对象（如 Python Dataclass），由控制 Schema 定义其类型与合法取值（如 `Literal['send','stop']`），控制器读取它来做路由与终止等执行决策。控制通道不暴露给提示优化器，保护其不受提示漂移影响。
- 数据通道（Data）：自由形式的自然语言消息，包含任务相关内容（如总结、评论），它供其他智能体和优化器消费，并构成可控的优化调节范围。

**技术实现**：
- Schema 会生成冻结提示脚手架，作为提示上下文中一个固定的槽位，优化器无法修改。
- 运行时刻先解析输出为控制对象和数据消息；若控制对象解析失败或不合规，系统会触发重试（C3 条件）或受控的 fallback，使无效控制永远不会到达路由函数。
- 调节器可以改变智能体策略（例如选哪个智能体、何时停止），但不能改变协议本身（字段名和取值受 schema 限制）：只优化提示词中的**可编辑**槽位。

**协议稳定性保障 (Lemma 1)**：满足（C1）路由只消费类型化控制对象、（C2）schema 脚手架冻结于优化器不可访问的区域、（C3）无效应答经重试/默认值/受控失败后处理，系统可从任意优化器给定的提示中获得无协议违规的流程追踪。该形式化论证从机制上证明了控制协议是稳定的。

### 7. 优点（亮点）

- **轻量级与可验证性兼顾**：封装可执行的 Python 库、结构清晰的代码接口，为系统提供可复现的基础框架；协议稳定性以严格形式证明为基础。

### 8. 不足与局限

- **稳定性不等于正确性**：分离仅保证执行协议有效，并不保证生成的数据语义正确；协议有效的流水线可能仍给出错误或不合理的结果。
- **固定 Schema 与固定任务结构假设**：智能体角色与控制 Schema 必须在运行前声明，不支持动态智能体创建或运行时协议迁移，缩小了系统的适应范围。
- **数据覆盖和真实场景偏差**：保险任务所用的输入全为合成数据，但在行业专家验证的限定范围下适用；真实世界公平性、偏见事故需要进一步验证。
- **评估采用 LLM-as-a-Judge**：MARG 对齐度 Jaccard 以 LLM 评判为标准，存在评分者偏见问题（虽然固定了裁判模型以避免跨行比较偏差）。
- **未做真人对真人的实证评价**：质量控制与语义评价对真实业务接受度仍缺乏人为证据。
- **实验预算受限**：跨 LLM 用户对种子数量多为 1，加上小数据集迭代次数有限，随机种子数 3，部分实验统计上的显著性和稳健性有待加大规模验证。

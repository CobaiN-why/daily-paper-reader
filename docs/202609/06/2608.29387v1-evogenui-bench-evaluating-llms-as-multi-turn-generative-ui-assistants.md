## 摘要
大型语言模型可以生成交互式网页界面，但可靠的生成式UI需要在用户请求演变时维持一个可执行工件。我们引入了EvoGenUI-Bench，一个用于多轮界面维护的基准，包含150个五轮任务和750轮，涵盖三种场景：信息呈现、可执行交互和基于工具的外部状态。我们在浏览器中执行生成的工件，并使用截图、源代码和DOM证据、行为者轨迹以及运行时日志进行评估。除了轮次级和回合级成功率外，我们还通过相邻通过保留率来衡量跨轮保留。在八个模型中，即使是最强的模型也仅达到74.9%的轮次通过率，而仅完成了37.3%的五轮回合；在基于工具的任务上，APR进一步下降至52.4%。诊断分析表明，呈现失败主要集中在信息架构上，交互失败集中在派生状态传播和功能绑定上，而基于工具的失败还涉及外部状态基础和需求分解。这些结果将生成式UI评估从评判孤立输出重新定义为测试界面行为、派生状态、外部状态和助手声明在工件演变时是否保持同步。

## Abstract
Large language models can generate interactive web interfaces, but reliable generative UI requires maintaining an executable artifact as user requests evolve. We introduce EvoGenUI-Bench, a benchmark for multi-turn interface maintenance comprising 150 five-turn tasks and 750 turns across three scenarios: information presentation, executable interaction, and tool-grounded external state. We execute generated artifacts in a browser and evaluate them using screenshots, source and DOM evidence, actor traces, and runtime logs. Beyond turn-level and episode-level success, we measure cross-turn retention with Adjacent Pass Retention. Across eight models, even the strongest achieves 74.9% Turn Pass while completing only 37.3% of five-turn episodes; APR further falls to 52.4% on tool-grounded tasks. Diagnostic analysis shows that presentation failures center on information architecture, interaction failures on derived-state propagation and affordance binding, and tool-grounded failures additionally involve external-state grounding and requirement decomposition. These results reframe generative UI evaluation from judging isolated outputs to testing whether interface behavior, derived state, external state, and assistant claims remain synchronized as the artifact evolves.

### 一、核心问题与整体含义（研究动机和背景）

- **背景**：大语言模型（LLM）已具备生成任务特定交互式界面（仪表盘、表单、比较视图、小型应用等）的能力，被视作 LLM 助手的直接响应模态。然而，现有生成式 UI 研究大多集中在**单次生成**的质量评估，忽略了真实场景中用户需求反复演变、同一界面工件需被持续更新与维护的核心挑战。
- **核心问题**：LLM 能否在**多轮对话**中维护一个**可执行**的界面工件（artifact）？每一轮修订不仅要满足当前请求，还必须保留仍然有效的先前需求，并保证界面行为、派生状态、外部状态与助手回复信息之间的一致性。
- **研究范式转变**：该论文主张将生成式 UI 的评估从"评判孤立输出"转向"检验工件演化过程中的跨轮同步可靠性"，即界面是否作为持久助手输出与交互界面持续保持可执行、一致且可扩展。

### 二、论文方法论

- **核心思想**：提出 **EvoGenUI-Bench**，将生成式 UI 评估构建为**多轮工件维护（multi-turn artifact maintenance）**任务——每个任务是一个五轮对话片段，模型需在同一界面工件上连续执行四次修订。
- **任务公式化**：
  - 每轮模型接收：当前请求、公开任务上下文、可选公开工具契约、先前轮次紧凑证据、最近生成的源代码。
  - 模型输出：面向用户的文本回复 + 更新后的完整源代码。
  - 评估单位是**演化的可执行工件**，而非孤立页面。
- **三类场景套件**：
  1. **Presentation（信息呈现）**：密集信息的有组织展示；
  2. **Interaction（可执行交互）**：带本地状态的可交互界面；
  3. **Tool-grounded（工具外部状态）**：中介外部运行时状态的界面。
- **浏览器执行的证据收集管道**：生成的代码在固定 React/Vite 环境中构建，在浏览器（Chromium + Playwright）中运行；自动"行动者"（actor）操作界面收集行为痕迹；同时记录构建日志、最终 DOM、全页截图、运行时日志、工具调用记录与后端状态。
- **三维度评分（1–5 级）**：
  - **Presentation**：渲染界面的连贯性、可读性与领域适切性；
  - **Execution**：当前请求与相关先前需求是否以可工作的界面行为或可见的证据支撑状态落实；
  - **Alignment**：助手回复、源代码、渲染 UI、交互观察和运行时日志之间的相互一致性。
  - 所有维度≥4 分判定该轮通过。
- **可靠性指标**：
  - **Turn Pass（TP）**：单轮通过率；
  - **TP@5**：全部五轮通过的回合百分比；
  - **CPT（Consecutive Passed Turns）**：初始连续通过轮数（最长通过前缀）；
  - **APR（Adjacent Pass Retention）**：相邻轮次通过保留率，即给定上一轮通过，下一轮也通过的条件概率（见正文公式 3）。
  - TP@5 受回合难度差异影响，作者另给出**独立性基线**（公式 2）以对比诊断。
- **人类验证**：在 240 个覆盖 8 个模型和 3 个套件的盲审样本上评估自动评测器，自动评测准确率 86.7%，Cohen's κ = 0.73；标注者间一致性 Fleiss' κ = 0.78。
- **失败机制分类法**：六类排他性失败机制——信息架构、领域表示、需求分解、功能性绑定（affordance binding）、派生状态传播、外部状态接地（external-state grounding），经过独立标注者验证（Fleiss' κ = 0.91）。

### 三、实验设计

- **Benchmark 构成**：
  - 150 个任务、750 个用户请求轮次，每个套件 50 个任务；
  - 每个任务有 5 轮用户问题和对应的私有验证契约；
  - 每个任务唯一领域标签，150 个不同领域；
  - 验证密度：Presentation 每轮平均 3.0 个私有需求，Interaction 5.9 个，Tool-grounded 高达 11.9 个。
- **数据隔离**：生成器可见内容（用户请求、公开上下文、工具契约）与私有验证内容（隐藏需求、后端状态、评分标准）严格分离，防止评估泄露。
- **对比模型**（8 个近期模型家族）：
  - GPT-5.5、Qwen3.6-Plus、Qwen3-Coder、GLM-4.5-Air、Gemini-3-Flash、Gemini-3.1-Pro、Claude-4.5-Haiku、Claude-Opus-4.7。
  - 默认使用 MiMo-V2.5 作为交互行动者和评测器。

### 六、主要结论与发现

- **发现 1：轮次级成功严重高估回合级可靠性**。最强模型 Claude-Opus-4.7 整体 TP 为 74.9%、APR 为 83.6%，但 TP@5 仅 37.3%；八个模型平均 TP 42.7% 而平均 TP@5 仅 11.8%。观测的 TP@5 均高于独立性估计，说明通过轮次聚集于某些较易回合。
- **发现 2：工具型任务即使在上一轮通过条件下依然最难**。TP 从 Presentation 55.5%、Interaction 47.6% 降至 Tool-grounded 25.0%；TP@5 从 15.5%/14.8% 降至 5.0%；APR 也从 71.1%/68.7% 降至 52.4%。
- **发现 3：可靠性在第二轮后明显下滑**。轮 1/2 通过率相近，轮 3 骤降，轮 4 继续下滑；工具型任务由轮 2 的 39.5% 降至轮 3 的 18.5%。
- **失败机制因场景而异**：
  - Presentation 失败以"信息架构"为主（如标签合并、内容重叠/截断不可读）；
  - Interaction 失败集中在"派生状态传播"与"功能性绑定"（如控件可见但未接入逻辑、依赖视图数据陈旧）；
  - Tool-grounded 失败额外涉及"外部状态接地"与"需求分解"。
- **诊断需要匹配证据面**：截图揭示视觉组织缺陷；行为者轨迹与源码差异暴露交互断线与派生状态陈旧；运行时日志揭示界面–外部系统不一致。单一分数或单一证据面无法覆盖全部失败类型。

### 七、优点

- **任务设计的真实性与累积性**：五轮累进修订真实模拟了用户与 AI 助手的长期交互需求，直击先前基准忽略的"先前功能被遗忘/覆盖"这一核心问题。
- **证据基础的完整性**：结合截图、DOM、行为者轨迹、源码、运行时日志和外部状态回读的"多表面证据包"，深度优于仅依赖代码静态检查或纯文本判断的评估方法。
- **严格的数据隔离设计**：公开/私有信息分离、以语义而非参考实现为验证目标，降低泄漏风险的同时鼓励功能等价的不同实现。
- **多层次的可靠性指标**（TP、TP@5、CPT、APR 与独立性基线）从不同粒度刻画模型能力，APR 尤其适用于测量跨轮保留这一此前少有量化的维度。
- **系统的人工验证**：对自动评估器进行盲审、分层抽样验证，并进行行动者–评测器敏感性与证据消融分析，提供了较强的评测方法论可信度。
- **失败分类学**：六类机制的诊断分类法经人工验证且与回合级评估分离，为后续改进生成模型提供了可操作的分析工具。
- **可复现与开源**：完整代码、数据、管道均开放于 GitHub（MIT 许可证），附基准卡与详细使用指引。

### 八、不足与局限

- **数据规模与多样性有限**：150 个任务均为人工撰写、五轮固定结构；不包含自然对话日志、其他前端框架（仅 React/Vite）、无障碍需求（accessibility）或多设备/浏览器兼容性场景。
- **APR 归因不完整**：APR 是结果层面的保留度量而非因果归因指标。失败的过渡可能源于旧需求回归、新需求失败或两者兼有；作者的后验审计仅覆盖 110 例且有足够证据的子集，全面的归因需重放所有先轮验证契约到每个后续工件上，计算开销极大。
- **验证密度不一致的混叠问题**：Tool-grounded 套件每轮平均 11.9 个私有需求，而 Presentation 仅 3.0 个；跨套件性能差异同时受"外部状态复杂度"和"验证密度"影响，难以完全解耦两者贡献。作者在文中承认了这一点。
- **确定性模拟环境的局限性**：工具型任务使用确定性 mock 运行时，只能评估受控界面–运行时同步，无法捕捉真实线上服务的操作挑战（延迟、认证失败、停服、限流、API 变更等）。
- **生成随机性未全面覆盖**：主实验每模型每槽位仅执行一次生成，再生稳定性只在单个模型（Qwen3.6-Plus）上验证；其他模型的波动区间未知。
- **评估器模型的潜在偏差**：使用 MiMo-V2.5 作为默认评测器（行动者亦然），尽管做了敏感性验证（多种替代组合表现相当），但基于 LLM 的判断仍可能存在系统性偏好；结论有效性受限于所选评测模型的能力边界。
- **伦理与应用边界**：模拟数据与受控场景无法独立确证生成界面的真实部署安全性；论文也明确该基准不应用于认证生成应用的安全性或生产就绪性。生成界面可能对用户造成误导（如抛光但未接线的控件、无行为支撑的状态标签），本基准只能提供诊断性参考。

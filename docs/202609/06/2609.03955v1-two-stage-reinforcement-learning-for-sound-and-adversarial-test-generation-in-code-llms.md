## 摘要
强化学习（RL）通过可执行反馈显著推进了基于大语言模型（LLMs）的代码生成。编码问题的反馈主要来自特定测试用例，而高质量的测试用例往往稀缺，因为它们必须既可靠又具有区分性。因此，我们转而研究利用学习模型自动生成测试用例。我们发现这本质上是一个对抗性RL问题：模型应当根据求解器当前的失败模式生成有效的测试用例作为反例。为此，我们提出测试用例扩展（TCS），一种两阶段RL框架，用于有效的测试生成。两个阶段均从滚动策略对齐缓冲区中训练测试生成器：阶段1生成与参考解决方案一致的测试；阶段2将该缓冲区限制为当前失败模式，并学习反例测试。在TACO和LiveCodeBench基准上，TCS根据生成的测试同时提升了pass@1和推理时答案选择。我们还发现，学习到的测试生成器还能在其他LLM输出之间实现有效选择。

## Abstract
Reinforcement learning (RL) has substantially advanced code generation with large language models (LLMs) through executable feedback. The feedback for coding problems mainly comes from specific test cases, where high-quality test cases are often scarce since they should be both sound and discriminative. We thus turn to study the auto-generation of test cases using the learned model. We find this is naturally an adversarial RL problem: the model is expected to generate effective test cases as counterexamples, depending on the solver's current failure modes. We propose Test Cases Scaling (TCS), a two-stage RL framework for effective test generation. Both stages train a test generator from a rolling policy-aligned buffer: Stage 1 generates tests consistent with the reference solution, and Stage 2 restricts the buffer to current failure modes and learns counterexample tests. Across TACO and LiveCodeBench, TCS improves both pass@1 and inference-time answer selection according to generated tests. We find the learned test generator also enables effective selection among other LLM outputs.

**研究背景与动机：**

- 随着求解模型能力的提升，瓶颈正从“生成可行代码”转移到“验证哪个候选代码是正确的”。这催生了对推理时自验证的需求：模型自己生成测试用例、运行候选程序，并选择通过最多测试的候选。
- 但测试帮助选择的前提是：测试用例必须**可靠**（sound，即与解决问题的参考答案行为一致）**且有针对性**（能暴露候选的错误）。不合理的测试会错误排名候选，而薄弱的测试无法发现细微缺陷。
- 高质量测试用例往往极为稀缺，因为其要求同时满足“正确性”与“区分性”。论文指出，自动生成高质量测试用例天然是一个**对抗性强化学习问题**：测试发生器需要依据求解器当前的失败模式生成反例。

**核心问题：**
- 如何在可执行验证的环境下，利用强化学习训练同一 LLM 既作为解算器（solver）又作为验证器（verifier/测试生成器），使得生成的测试用例既具有可靠性（soundness）又具有候选条件对抗性（candidate-conditioned adversariality），从而提升训练阶段与推理阶段的代码生成能力？

## 2. 论文提出的方法论：核心思想与技术细节

### 2.1 整体框架：Test Cases Scaling (TCS)
提出一种两阶段 RL 框架，将代码生成与测试生成统一训练，其核心创新在于：
- **共享策略**：同一策略在训练中扮演求解器和验证器两个角色。
- **分阶段奖励**：两个阶段使用不同奖励，逐步逼近“可靠 + 对抗”的测试生成目标。
- **滚动策略对齐缓冲区**：动态保存当前策略生成的代码，作为测试生成提示的上下文，使验证器始终针对当前求解器的失败模式进行对抗训练。

### 2.2 阶段一：可靠测试生成（Soundness Control）
- 针对参考解 C∗ 校验生成的测试用例。
- 奖励公式（式 3）：
  - 判定条件 `Exec(C∗, Ig) == Og` 且 `(Ig, Og) ≠ Texample`。
  - Texample 为题目中自带示例集，用于进行“防复制筛选”，防止直接把题干示例原样输出。
  - 此时缓冲区 B 接受所有“可执行的输出”（不限对错），目的是让测试生成器在多样化的代码上下文中练习正确生成测试。

### 2.3 阶段二：反例测试生成（Candidate-Conditioned Adversariality）
- 进入阶段二后清空缓冲区 B，新缓冲区只接收“可执行但错误的候选程序”（在数据集测试集中至少失败 1 次的代码）。
- 对抗性奖励公式（式 4）：
  - `Exec(C∗, Ig) == Og`（参考答案正确）
  - **且** `Exec(Cwrong, Ig) ≠ Og`（给定候选代码输出错误）
  - 且不与示例测试重复。
- 若第二阶段直接从零开始训练，奖励将极其稀疏（需同时满足上述多个条件），因此作者用阶段一先搭建可靠基础，再转移到阶段二训练对抗范式。

### 2.4 联合训练与推进策略
- 训练迭代混合求解问题数据集 D 和从滚动缓冲区 B 构造的验证任务。GRPO 用于联合更新，求解器奖励按数据集测试套件给出，验证器奖励则按当前阶段的奖励函数给出。
- **策略对齐缓冲区 B**：仅保留最近 Tb 轮的代码样本，求解器输出不断充实缓冲区，因此测试生成器能持续跟踪当前策略失效的方式。
- 文中指出，求解器与验证器存在一种互相促进的协同（self-play）效应：更强的求解器产生更难的失败模式供验证器“攻击”，反过来提高测试质量。

### 2.5 推理时扩展
- 采样 N 个候选代码，并对每个候选代码 Ci 生成 M 个测试用例。
- 将 N×M 个测试用例混合得到测试池，执行每个候选代码，按总通过次数排序（式 5）。
- 选择通过全部池中测试最多的候选。
- 理论上，通过式 (5) 扩展时，推理时间增长主要来自测试生成部分，而测试生成可以并行执行。

### 2.6 理论分析要点
- 定义两个关键指标：**soundness error α**（生成测试对参考解给出错误标签的概率）与 **counterexample rate δ**（生成测试令错误候选失败但参考解通过的最低概率）。
- 命题 1（指数可靠性界）：在候选集固定、测试独立、且 δ > α 时，错误选择概率 ≤ (N−1)·exp(−K(δ−α)²/2)，K 为测试总数。说明推理选择可靠性随测试数量和“对抗性—可靠性差距”（δ−α）双指数增长。
- 阶段一旨在降低 α，阶段二旨在拉高 δ，两阶段对应理论推导中的控制量，从而保证推理扩展有依据。

## 6. 论文的主要结论与发现

- **有效测试生成的两个核心属性**：可靠（sound）与候选条件对抗（candidate-conditioned adversariality），TCS 通过两阶段强化学习分别控制这两个目标。
- **TCS 显著提升求解器性能**：相对于基线、离线联合 SFT 和分离训练，TCS 的 pass@1 在 TACO/LiveCodeBench 上均取得稳定提升。
- **当配合自生成测试时，测试选择比纯奖励模型重排更有效**：在无公共测试条件下尤其明显，因为此时选择几乎完全依赖已验证的测试生成能力。
- **共享策略有协同效应**：联合训练的 solver 与 verifier 存在相互增强的作用；将 TCS 生成的求解器用 Test-RL 的测试过滤，效果劣于 TCS 自我验证，验证了协同效应。
- **离线分层监督并不足够**：与在线策略对齐 RL 相比，即使 SFT 使用教师产出的“有针对性且已验证的对抗性测试”，其推理扩展能力仍低于 TCS，证明“在线

证明“**在线策略对齐比离线教师蒸馏更能适应模型自身演化出的失败模式**”，这强调了 RL 中策略对齐（policy alignment）与滚动缓冲区机制的关键作用。

- **两阶段课程（soundness → adversariality）是必需的**：仅阶段一奖励（可靠但不针对候选）与直接以阶段二稀疏奖励训练相比，前者缺乏对抗性、后者因奖励过稀疏而难以收敛；只有分阶段推进才能同时获得两个属性。
- **推理时测试数量按理论预期带来增益**：在固定候选数下，增加每个候选生成的测试数 M 会稳定提升正确选择率，与命题 1 中指数界对 K 的依赖一致；同时公共测试与自生成测试可以互补叠加，进一步提升最终 pass@1。

## 7. 局限性与未决问题

- **基座模型规模有限**：作者将 RL 后训练限定在 1.5B/7B 规模上（出于预算考虑），虽然展示了 7B 模型的生成测试可以筛选 GPT-4o 等级别的外部输出，但对更大模型（如 30B 以上）的直接适用性尚未验证。
- **理论界中的假设前提在现实中难以严格保证**：命题 1 依赖候选集固定、测试相互独立以及 δ>α 等条件；对真实复杂题目估计 α 与 δ 并不容易，论文仅给出定性阐释，未在各数据集上实测这两个参数。
- **奖励模型与测试选择的公平比较有待细化**：与 InternLM2-7B-reward 比较时，论文主要在无公共测试场景下讨论，未全面分析奖励模型在有公共测试辅助时与 TCS 的性能差异。
- **开放性代码生成场景尚未覆盖**：TCS 的验证依赖可执行环境与参考解的存在，对缺乏完整测试或无法编译运行的开放式、自然语言描述不完整的编程问题（如实际软件开发任务）扩展性有限。

## 8. 总评与启示

- **贡献定位**：论文处于“用可验证反馈强化代码模型”这一研究主轴，其核心增量在于把**测试生成本身也纳入 RL 训练**，并首次将其构建为一个对抗性自博弈任务（solver 提供反例、verifier 攻击 solver）。相比仅做代码 RL 或仅做测试 RL 的做法，TCS 证明了联合训练能产生双向正外部性。
- **方法优雅性**：两阶段奖励设计与滚动缓冲区使训练无需外部标注、无需显式判别器，只依赖代码执行的一致性检查，简单而实用。
- **对领域的重要启示**：代码模型的推理时扩展不应只停留在“生成更多候选”，而应同时扩展“更高质量的验证信号”。只有求解器与验证器协同进化，才能突破自验证的瓶颈，这为下一代代码 LLM 的后训练与推理设计提供了清晰方向。

综合来看，本研究在方法创新、理论动机、实验论证三方面都较为扎实，结论可信度高，是代码生成领域“可自我验证的对抗性训练”方向的重要一步；其局限也提示了后续在更大模型、开放场景以及 α/δ 参数驱动训练方面的研究空间。

## 摘要
编程智能体在真实代码库编码任务上运行，而持久记忆系统有望跨任务复用经验。然而，现有评估并未表明这些系统能否提升可执行的代码库工作。代码库基准测试检验代码变更，却不隔离记忆因素；而记忆基准测试只评估召回，并不衡量下游编码结果。我们提出 VibeMemBench，一个用于评估记忆系统的基准，包含来自 90 个 SWE-rebench V2 代码库的 111 个编码目标，以及来自目标代码库的 3,634 条历史轨迹。这些目标遵循 SWE 基准的风格，涵盖缺陷修复、功能请求、接口变更和配置工作。智能体在声明的记忆条件下编辑每个目标代码库。可执行测试决定任务是否解决。只有当注入的历史经验在参考设置中改善其可执行结果时，该目标才会被保留，因此每个目标都带有一项先验经验，其有效性已在该设置中通过执行得到验证。随后，冻结的已验证经验被迁移至五个留出的求解器。直接注入使其中四个求解器的观测任务解决率提升 1.1 至 4.5 个百分点，同时降低了全部五个求解器的智能体步数。然而，当四个现有记忆系统必须从同一历史中构建并检索经验时，十二个求解器与系统配对中有十一个未能超过匹配的无记忆基线。VibeMemBench 揭示了代码库历史所蕴含的有用经验与现有记忆系统为代码库编码任务所提供的经验之间的差距。

## Abstract
Coding agents operate on real repository coding tasks, and persistent memory systems promise to reuse experience across tasks. Yet existing evaluations do not show whether those systems improve executable repository work. Repository benchmarks test code changes but do not isolate memory, while memory benchmarks score recall without measuring downstream coding outcomes. We introduce VibeMemBench, a benchmark for evaluating memory systems on 111 coding targets from 90 SWE-rebench V2 repositories and 3,634 history trajectories from the target repositories. The targets follow the SWE benchmark style and cover bug fixes, feature requests, interface changes, and configuration work. An agent edits each target codebase under a declared memory condition. Executable tests decide task resolution. Each target is retained only when injected history experience improves its executable outcome in a reference setting, so every target carries a prior experience whose usefulness is verified by execution in that setting. The frozen verified experience is then transferred to five held-out solvers. Direct injection raises observed task resolution on four of them by 1.1 to 4.5 percentage points while lowering agent steps on all five. Yet when four existing memory systems must construct and retrieve experience from the same history, eleven of twelve solver and system pairings fail to exceed the matched memory-off baseline. VibeMemBench exposes the gap between the useful experience that repository history holds and the experience existing memory systems deliver for repository coding tasks.

# VibeMemBench 论文总结

## 1. 核心问题与研究动机

- **背景缺口**：持久记忆系统被寄望于让编程智能体跨任务复用经验，但现有评测存在“各看半边”的问题：
  - **代码库基准**（如 SWE-bench）能给出可执行测试结果，但**不隔离记忆干预**，无法判断提升是否来自记忆；
  - **记忆基准**（如 LoCoMo、LongMemEval、MemBench）只评测历史事实的**召回问答**，**不衡量下游编码结果**。
- **核心问题**：*持久记忆能否真正改善可执行的代码库修复工作？*
- **测量困难**：任务结果可执行可验证，但“哪条历史观察值得写入/保留/检索”没有实例级标签，也不存在“金标准记忆”标签——因为记忆价值应按下游是否变好来判定，而非按检索是否命中来判定。
- **整体含义**：论文构造 VibeMemBench，把记忆评测转化为**同一任务、同一智能体、同一工具、同一沙箱、同一预算下，仅切换记忆开关的配对比较**，用可执行测试判定解决与否，并报告 Resolved、求解器 token 与智能体步数。

## 2. 方法论

### 2.1 核心思想
- 每个目标 = 代码库状态 + 编码指令 + 先验轨迹观察 + 可执行测试谓词；注入经验通过测试才算解决。
- 只有当某条注入的历史经验在**参考设置**下确实提升可执行结果时，该目标才被保留，因此每个目标都携带一条**经执行验证有用**的经验（冻结验证经验，frozen verified experience）。
- 将冻结经验迁移到留出求解器（第一层），并与四个现有记忆系统自行构建/检索的经验做对照（第二层）。

### 2.2 构建流水线 SIEVE（四/五阶段，非缩写）
1. **源任务验证**：用源 gold patch 跑声明测试，gold patch 失败的实例全部丢弃。
2. **补丁模式筛选**（离线、oracle 辅助）：
   - 只允许**同代码库的更早实例**进入候选，排除所有目标自身标识符，保证目标不进入自己的历史池；
   - 确定性打分：`r(t,h) = 3·δ_f + δ_d + min(2, |I_t ∩ I_h|)`，即优先共享文件，其次共享符号/目录；分数 ≥ 1 入短名单，最多保留 24 个候选（按分数与时间近度排序），再由 LLM 依据结构化证据判断修复模式是否匹配。
3. **历史执行 + 目标感知经验蒸馏**：用固定参考配置 MiniSWEAgent（deepseek-v4-flash、温度 0.5、250 步上限）执行筛选后的历史任务，保留完整轨迹；再由目标问题陈述、历史问题陈述、压缩轨迹、历史最终补丁蒸馏出**每条经验**，包含 bug 类别、根因、修复模式、可复用教训。目标 gold patch 仅用于离线筛选，目标 test patch 仅评测方可见，二者均不进入经验构建、运行时检索或求解器上下文。
4. **按提升保留（冻结验证经验）**：
   - 目标-种子运行通过声明测试记为解决；条件解决率在 4 个种子上取均值；
   - 参考设置下提升 `g_{t,k} = b^pref_{t,k} − b^pref_{t,0}`；
   - 保留条件：`b^pref_{t,0} < 1` 且 `g_{t,k*} > 0`，其中 `k* = argmax_k g_{t,k}`（在短名单 K_t 内取 argmax，故只证明“历史中至少存在一条有用经验”，而非“最优经验”）。

### 2.3 记忆干预协议
- 配对集合 `P = T × S`；固定智能体配置 `A`（模型、提示、工具、沙箱镜像、上下文预算、资源限制、任务顺序、聚合规则），仅 `m ∈ {off, on}` 变化。
- 记忆开启条件需声明：写入策略、检索触发、上下文插入规则、记录截断规则；记忆关闭条件在同一固定上下文预算下替换这些记录。
- **第一层**：迁移冻结验证经验到 5 个留出求解器（deepseek-v4-pro、glm-5、glm-5.2、kimi-k2.7-code、qwen3.8-max），每条件 4 种子。
- **第二层**：Mem0、SimpleMem、MemoryOS、A-MEM 从目标全部可用历史中摄取并组织，按声明的目标查询取**Top-1 经验**注入 MiniSWEAgent；检索发生在目标轨迹**之前**，属离线检索而非在线闭环记忆。
- **指标**：Resolved（声明测试通过的目标-种子占比）、输入/输出 token、智能体步数；不确定性以**目标**为重采样单位（111 个目标连同 4 个种子，10,000 次 bootstrap）。

## 3. 实验设计

- **数据规模**：111 个编码目标、90 个代码库（按历史目录去重）、3,634 条已完成历史轨迹；目标来自 SWE-rebench V2，属 SWE 风格可执行修复协议，非单一 bug 修复切片。
- **语言分布**：Python 56、JavaScript 16、Go 12、Rust 10、TypeScript 5、Kotlin 4、Swift 4、Java 2、PHP 2。
- **任务类型**：Bug fix 29.7%、Feature 20.7%、Parser/序列化 14.4%、错误处理/校验 8.1%、兼容性修复 7.2%、行为变更 7.2%、API/接口 5.4%、配置/依赖 2.7%、重构 1.8%、测试基础设施 1.8%、文档相关 0.9%。
- **对比方法**：
  - 记忆关闭基线；
  - 冻结验证经验注入；
  - **无关记忆对照**（注入一段固定、无软件内容的日常句子）；
  - 四个现有记忆系统：Mem0、SimpleMem、MemoryOS、A-MEM（在 deepseek-v4-pro、glm-5、kimi-k2.7-code 上）。
- **扩展实验**：headroom 分层（20 个求解器×条件组合）、指令污染 strip 消融（3 臂）、Mem0 检索预算剂量曲线（k=1…5）、案例对比（同记录跨求解器、同求解器跨系统）、两名 LLM 评委（qwen3.7-max、MiniMax-M2.5）对 231 个失败配对盲审重标注、反事实替换上界、天花板参考审计。

## 4. 资源与算力

- **论文未报告 GPU 型号、数量、训练时长或推理总成本**；仅提及因**推理预算**原因未纳入 Claude 与 GPT 系列等闭源前沿模型，因此求解器池不含它们。
- 协议明确**不记录记忆侧 token 消耗**，也不把墙钟时间与 API 价格纳入比较（因供应商与定价策略不同）。
- 可见的计算相关设定：历史执行与参考选择使用 deepseek-v4-flash + MiniSWEAgent（温度 0.5、250 步上限、每条件 4 种子）；记忆系统用 deepseek-v4-flash 抽取记录，用 Qwen3-Embedding-4B 做嵌入检索。

## 5. 实验数量与充分性

- **规模**：第一层 5 个求解器 × 111 目标 × 4 种子 = 每条件 444 个目标-种子运行；第二层 3 求解器 × 4 系统 = 12 个配对，共 1,332 个“目标-求解器-系统”检索配对；失败归因诊断队列 231 个失败配对、覆盖 85 个目标。
- **消融/对照**：无关记忆对照（3 求解器）、strip 消融（原/去污染/随机删除三臂 × 62 配对，含置换检验）、Mem0 剂量曲线（5 档预算）、headroom 分层、反事实替换上界、双评委盲审一致性。
- **公平性设计亮点**：严格配对（同任务/种子/配置/预算，只改记忆条件）；固定上下文预算；无关文本对照排除“注入文本本身”的效应；bootstrap 以目标为单位（保留 4 种子结构）；归因由确定性脚本从日志重算，另有独立 LLM 评委盲审。
- **充分性与客观性的保留**：
  - 所有 bootstrap 区间均跨零，1.1–4.5 个百分点的提升只是**方向性证据**，在 111 个目标规模下尚不能与零效应分离；
  - 目标筛选用**种子级 argmax**，种子噪声会放大参考提升；不过跨模型迁移复用冻结经验、不重选记忆组合，故迁移估计继承了被选群体但不继承 argmax 乐观性；
  - 归因标签在 ranking 与 form 边界上评委一致性偏低（Cohen's kappa 0.32/0.24，评委间 0.35），故 Table 4 的 form 占比依书面锚点规则而非评委共识；
  - strip 消融的预声明因果判据未被满足（strip 与随机删除恢复量相当）。

## 6. 主要结论与发现

- **存在可用经验**：冻结验证经验在 5 个迁移求解器中的 **4 个**上提升 Resolved（+1.1 至 +4.5 pp；deepseek-v4-pro 为 +0.0），且**全部 5 个求解器的智能体步数下降**，4 个求解器输入 token 下降——注入缩短而非加长交互。
- **现有记忆系统交付失败**：12 个“求解器×系统”配对中 **11 个**未超过匹配的无记忆基线，无任何系统区间位于零以上，glm-5 + Mem0 的区间完全在零以下；唯一例外 MemoryOS + glm-5 仅 +2.0 pp，且仍落后于冻结经验。
- **失效归因**：231 个失败配对中，**形式退化占 69.3%**（相关历史已到达但修复模式被丢弃或淹没在原始转录中），覆盖缺失 16.0%、使用失败 13.4%、排序失败仅 1.3%。形式退化细分：指令污染 40.0%、过度泛化的修复模式 18.1%、工具/shell 噪声 10.0%、schema 缺少修复字段 8.8%、修复被症状替代等。
- **危害来自转录体积而非指令语义**：strip 掉污染行恢复 +0.60 种子，随机删除等量未标记行恢复 +0.48，二者相当，说明污染标记只标记了“冗长记录”。
- **求解器 headroom 决定方向**：同一条记录可让弱求解器获益、强求解器受损（3 个案例跨 2 种子边界反向）；444 对中有 64 对反向，其中 61 对是 memory-off 计数更低者获益；反向比例随 memory-off 差距上升（0 种子 0% → 1 种子 52.3% → 2 种子 75.0% → 3+ 种子 85.7%）。8 项记录属性在反向/同向配对间均无显著差异（最小置换 p=0.25）。
- **天花板效应**：42.0% 的检索配对处于 memory-off 4/4 天花板，注入只能丢分；每个求解器与条件组合都在天花板下得分、在天花板处失分。
- **加宽检索预算无济于事**：Mem0 在 k=1…5 的所有预算下均低于基线，曲线非单调，每个预算的天花板损失都超过天花板下收益。
- **成功条件**：当求解器无记忆时失败、且记录至少带有目录或标识符锚点时，记录在 58 个配对中 55.2% 提升且**无观察到损失**（bootstrap 40.8–69.1%）；而在 4/4 天花板处，连冻结经验也会在 25.7% 配对中降低 Resolved。
- **反事实上界**：用同目标的冻结经验替换失败记录，在 160 个形式退化配对上可恢复 196 个种子（其中指令污染 64 对恢复 78 个）。

## 7. 优点

- **问题定位精准**：明确区分“可用性”与“可用性是否被利用”，指出仓库基准与记忆基准各自的盲区，并用图 1 直观呈现配对比较范式。
- **可控干预设计**：配对协议固定智能体、工具、沙箱、预算、任务顺序与上下文预算，唯一变量是记忆条件；记忆开启条件需声明写入/触发/插入/截断四项策略，报告契约可审计。
- **防泄漏严格**：目标标识符被排除出自身历史池；目标 gold patch 仅用于离线筛选，test patch 仅评测方可见；附录 C 用表 8 逐字段给出可见性边界。
- **目标携带可执行验证的先验经验**：用“参考设置下提升 > 0 且 memory-off < 4/4”的保留规则，保证每个目标确实存在至少一条有用经验，把“基准是否可解”与“记忆是否有效”解耦。
- **对照与消融严谨**：无关记忆对照排除文本注入效应；strip 与随机删除等量行做长度控制；剂量曲线检验“是否只是检索接口太窄”；双评委盲审给出归因边界；反事实替换给出形式上界。
- **结论可操作**：提出三条设计启示——按预期 headroom 门控注入而非统一注入、把检索到的轨迹压缩到陈述修复的片段而非按表面标记过滤指令文本、抽取 schema 必须保留锚定修复的约束（仅保留 fix 字段不充分）。

## 8. 不足与局限

- **统计功效有限**：111 个目标下所有 bootstrap 区间跨零，观测提升（1.1–4.5 pp）只能算方向性证据，无法与零效应分离。
- **选择偏差**：111 个目标按参考提升为正筛出，且筛选用种子级 argmax 与 oracle 辅助的补丁模式筛；这适合“已知可迁移经验的下游价值”基准，但**不能估计部署智能体找到此类配对的频率**，参考提升也不是无偏的总体估计。
- **求解器覆盖不全**：因推理预算原因未纳入 Claude、GPT 等专有前沿模型，求解器无关的协议对其未经验证；glm-5.2 与 qwen3.8-max 仅跑迁移层，无

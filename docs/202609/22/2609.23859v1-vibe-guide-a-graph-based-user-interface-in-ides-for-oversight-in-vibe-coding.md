## 摘要
在智能体编程中，开发者从亲自实施变更转向指定意图、评估智能体的工作并做出批准决策。然而，将实现委派出去可能引入认知债务，随时间推移侵蚀项目理解，限制开发者提供监督的能力。在这项工作中，我们研究持久共享表示在支持项目理解和对编码智能体的监督中的作用。我们提出 Vibe-GUIDE，一种智能体编程界面，围绕按功能模块组织的结构化、实时、可操作且自适应的图表示构建。我们通过一项随机组间研究评估了该界面，比较 16 名开发者使用我们的界面或仅聊天基线完成三项累积编码任务的情况。我们发现 Vibe-GUIDE 能够支持项目理解和持续的任务表现，同时使开发者保持认知参与监督。这些发现表明，持久共享表示可以补充自然语言交互，并帮助开发者随着项目演进保持监督智能体生成变更所需的理解。

## Abstract
In agentic coding, developers shift from implementing changes themselves to specifying intent, evaluating the agent's work, and making approval decisions. However, delegating implementation can introduce cognitive debt that erodes project comprehension over time, constraining developers' ability to provide oversight. In this work, we investigate the role of persistent shared representations in supporting project comprehension and oversight of coding agents. We present Vibe-GUIDE, an agentic coding interface built around a structural, live, manipulable, and adaptive graph representation organized by functional modules. We evaluated our interface in a randomized between-subjects study comparing how 16 developers completed three cumulative coding tasks using our interface or a Chat-only baseline. We found that Vibe-GUIDE can support project comprehension and sustained task performance while keeping developers cognitively involved in oversight. These findings show how persistent shared representations can complement natural-language interaction and help developers maintain the understanding needed to oversee agent-generated changes as projects evolve.

## 1. 核心问题与整体含义

- **研究背景**：在 *agentic coding*（智能体编程）与 *vibe coding* 中，开发者角色从"亲自实现变更"转向"指定意图、评估智能体产出、决定接受/重定向/修订"。智能体可自行检查代码库、编辑文件、运行开发工具。
- **核心问题**：委派实现会带来**认知债务（cognitive debt）**——开发者在不追踪变更如何工作、如何融入项目的情况下接受生成代码，逐渐丧失解释、评估与维护项目所需的**项目理解（project comprehension）**，进而限制其**人类监督（human oversight）**能力。
- **整体含义**：
  - 主要 AI 治理框架（OECD、NIST AI RMF）均要求人类监督，开发者自身也倾向保留监督权，但监督前提是足够的项目理解。
  - 论文探索**持久共享表示（persistent shared representation）**是否能同时支持项目理解与监督，而非仅仅暴露更多智能体活动信息。
  - 定位：不是提出新算法，而是 HCI 领域的设计探索 + 随机被试间实证研究，主张"语言 + 结构化共享表示"互补，而非用图形界面取代自然语言对话。

## 2. 方法论：核心思想与关键技术细节

### 2.1 四条设计需求（DR1–DR4）
- **DR1 结构性（structural）**：在"问题求解层面"组织项目，按**功能模块**（软件做什么）及其关系呈现，而非镜像目录/文件结构，从而连接领域目标与程序结构。
- **DR2 实时性（live）**：表示随代码库变更同步更新，并显式标记最近变更；避免静态快照与真实工件脱节。
- **DR3 可操作性（manipulable）**：开发者可通过增删改连图中的元素表达意图，由智能体将请求落到代码库，使图从只读报告变为引导接口。
- **DR4 自适应性（adaptive）**：保留项目级总览的同时，按当前焦点揭示更细粒度细节（渐进披露）。
- 四者组合形成**双向工作表面**：智能体的代码变更上图，开发者的图上操作回落到代码库。

### 2.2 系统组成
- 界面由三部分构成：**文件树 + Overview Graph（总览图）+ Chat Panel（聊天面板）**；图与对话不是独立视图，任一侧都可发起变更，智能体活动会回到图上。
- 后端运行编码智能体，另有一个独立的**图生成模型**负责构建与更新图。

### 2.3 图的构建与视觉编码
- **组织方式**：以功能为中心——`module` 表示功能部件，`feature` 描述其内行为，`relationship` 表示模块协作方式。
- **视觉元素**：模块为卡片（通俗标签、简短描述、表示角色的颜色）；编号气泡展开 feature；带标签箭头（如 "drives"、"feeds into"）表达关系；自上而下布局保证统一阅读方向。
- **生成流程**：服务端把项目文件与**固定提示词**发送给 Claude Sonnet 4.6，要求产出模块、特性、关系及其到**文件与函数**的结构化映射；映射用于后续把智能体活动关联到图元素。元素流式返回前端，用 **React Flow** 渲染、**dagre** 布局。
- **设计者定义 vs 模型推断**：节点-连线形式、布局、角色编码、渐进披露由界面固定；模块/特性/关系/映射由模型推断，提示词要求使用功能化标签而非文件名。
- **复杂度控制**：提示词限制总览图**不超过 8 个模块**，更细信息通过特性气泡与 Focus Mode 按需展开。

### 2.4 交互与协调机制
- **检查项目结构**：
  - 选中模块展开特性；选中特性或关系给出更详细解释（通常一句话说明该连接在代码中如何工作）。
  - 搜索工具栏既可按名称过滤，也可把自然语言问题转换为一条**有序阅读路径**（跨相关模块与关系）。
  - **Focus Mode**：识别与最近请求相关的模块，生成更细粒度子图；可把细节模块**提升（promote）**回总览图。
- **引导编码智能体**：
  - 可对模块/特性/关系描述期望变更，或请求智能体给出建议（建议以卡片形式出现在画布上，含"不做修改"选项与自定义输入）。
  - 选中的图元素提供结构上下文，描述/建议提供行为意图；确认后作为 **Graph edit** 发送给智能体，并记录在聊天面板中，保留"结构动作 → 编码请求"的转换轨迹。
- **跟踪智能体变更**：
  - 执行中被读取/编辑文件关联的模块**闪烁**；回合结束后，已完成修改关联的元素保持高亮（蓝色实心环），直到开发者发起下一次请求。
  - **变更追踪器（change tracker）**记录新增/修改/移除的图元素，可逐条回访。
  - 代码变更后，图生成模型接收**更新后的代码库 + 旧图**，以在纳入新行为的同时尽量保持稳定结构。

### 2.5 说明性用例
- 以开发者 Ana 接手一个陌生的小型记账项目为例：通过自然语言搜索定位"同日同额两笔付款被合并"的责任模块与三步阅读路径；打开模块与特性理解问题层面原因；通过模块动作描述修复；对开放式任务请求建议并选择；用 Focus Mode 查看细节并把 `Set Monthly Limit` 提升到总览图。

## 3. 实验设计

- **研究问题**：
  - RQ1：使用 Vibe-GUIDE 对项目理解、任务表现、认知负荷与对编码智能体的信任有何影响？
  - RQ2：开发者如何使用图形表示，在智能体生成变更的创建与后续复查阶段进行监督？
- **设计**：随机**被试间**研究，同一应用构建、同一编码智能体、同一任务与日志，唯一差别是是否提供 Graph 面板；参与者不知道另一组存在。
- **参与者**：16 人（每组 8 人），通过机构邮件列表与作者职业网络招募；要求有 AI 编码智能体使用经验，且有正式编程训练或软件工程职位。年龄 20–30（中位 25），男 10/女 6，编程经验 2–10 年（中位 5.5），15 人每天多次使用 AI 编码工具，13 人用过 Claude Code。
- **场景 / 数据**：基于 **Python-Markdown 3.10.3 的 study fork**；非数据集型任务，而是累积式项目修改任务。
  - Warm-up（不计时）：实现 `==text==` 内联高亮（7 个验收测试）。
  - Task 1：创建带锚点与双向交叉引用的带类型编号 callout 块（31 个测试，15 分钟）。
  - Task 2：把 callout 变为 panel，加入反向引用与在标题处重新编号（45 个测试，15 分钟）。
  - Task 3：合并 panel 与目录（TOC）扩展并添加标题引用（64 个测试，15 分钟）。
  - 每个任务给出**行为导向 brief 与验收测试套件**，但不点名相关函数、类、优先级或数据结构；任务从当前项目状态继续累积。
- **Benchmark / 评价指标**：
  - 主结果：**任务相关理解**（16 分，覆盖参与者让智能体构建的特性）。
  - 次结果：未见特性理解（5 分）、任务正确性（15 分钟内完整通过验收套件）、任务时长。
  - 探索性：执行顺序理解（2 分）、关系行与精确位置行（0–18 / 0–5）、每题信心（0–10）、自评理解（1–7）。
  - 体验：改编 NASA-TLX 6 项（0–6）、改编 TXAI 4 项信任（合成 4–20）。
  - 行为：应用日志（消息、文件操作、Graph 交互）、AAR-AI 开放式问题。
  - 理解测试 9 题 5 部分共 23 分，使用行为层语言，不指认文件/扩展/类/函数/变量；测试在 Task 3 后完成，期间保留**只读**界面访问（不能发新指令或改项目）。
- **对比方法**：**Chat-only 基线**（同一界面去掉 Graph 面板），即评估的是"整包 Graph 界面"的增量效果。
- **统计与评分**：
  - 不预先做样本量精度分析；鉴于样本小且 ASA 对 p 值的告诫，报告**组中位数、Cliff's δ 及 95% 置信区间**（正值表示 Graph 组更高），不依赖 p 值。
  - 评分用三次独立的盲评 `claude-opus-5` 运行，对 16 份去标识、乱序回答逐行打分；368 个判定中 354 个完全一致（Fleiss κ = .943），14 个非一致项由第四次盲评裁决；**没有独立人类评分者**。
  - RQ2 采用 LLM 辅助的**混合演绎–归纳框架分析**：主遍编码 24 条参与者–任务时间线与 8 份 Graph 组回答；另一次运行独立编码 12 条分层时间线；再有一次审计事件重建与主张–来源可追溯性。作者明确不把这些运行视为独立人类编码者，也未计算编码者间一致性。

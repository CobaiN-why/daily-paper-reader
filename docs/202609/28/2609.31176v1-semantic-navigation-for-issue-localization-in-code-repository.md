## 摘要
仓库级问题定位旨在识别并排序与解决所报告问题相关的文件和函数。LLM 智能体以迭代方式处理该任务：它们识别一组潜在相关位置，检查相应代码，并在获得新证据时修正对这些候选位置的判断。然而，现有环境对这一循环的支持有限：智能体必须搜索未解析的关系目标，从原始源代码中重建实体语义，并在缺乏证据依据的情况下修正候选。为解决这些局限，我们提出 SemNav，一个利用确定性检索生成广泛初始候选集，并由 LLM 智能体持续精炼该集合的框架，从而将初始覆盖与证据引导的修正相结合。SemNav 通过三个关键组件支持这一过程。语义导航图通过语言服务器按需解析程序关系，支持跨文件直接导航到相关实体。问题条件下的语义卡片提供对每个实体的角色及其与问题相关性的紧凑、基于源代码的解释。持久化候选工作区记录每个候选及其证据依据，支持有依据的验证、修正和排序。在 SWE-bench Lite 和 PLocBench 上，SemNav 优于现有基线，使用 Gemma 4B 将 File Hit@10 从 68.33% 提升至 82.67%。组件消融和轨迹分析支持所有三个组件的互补作用，而语义卡片相对于全源代码阅读将工作上下文负载降低 48.2%。SemNav 进一步在 SWE-Explore 的所有七项证据质量指标上排名第一，并将下游问题解决率从 44.00% 提升至 52.33%。

## Abstract
Repository-level issue localization aims to identify and rank the files and functions relevant to resolving a reported issue. LLM agents approach this task iteratively: they identify a set of potentially relevant locations, inspect the corresponding code, and revise their judgments about these candidates as new evidence is acquired. Existing environments, however, provide limited support for this loop: agents must search for unresolved relation targets, reconstruct entity semantics from raw source code, and revise candidates without evidential basis. To address these limitations, we present SemNav, a framework that leverages deterministic retrieval to seed a broad candidate set and an LLM agent to continually refine that set, thereby combining initial coverage with evidence-guided revision. SemNav supports this process through three key components. A Semantic Navigation Graph resolves program relations on demand through a language server, enabling direct navigation to related entities across files. Issue-conditioned Semantic Cards provide compact, source-grounded interpretations of each entity's role and relevance to the issue. A persistent Candidate Workspace records each candidate together with its evidential basis, enabling grounded verification, revision, and ranking. Across SWE-bench Lite and PLocBench, SemNav outperforms existing baselines, improving File Hit@10 from 68.33\% to 82.67\% with Gemma 4B. Component ablations and trajectory analysis support the complementary roles of all three components, while Semantic Cards reduce working-context load by 48.2\% relative to full-source reading. SemNav further ranks first on all seven evidence-quality metrics on SWE-Explore and improves downstream issue resolution from 44.00\% to 52.33\%.

## 1. 核心问题与研究动机

- **任务背景**：仓库级问题定位（Repository-Level Issue Localization）要求在给定自然语言 issue 与代码仓库快照的条件下，识别并排序与解决问题相关的文件与函数。该步骤决定了后续智能体可推理与编辑的代码范围，对下游修复效果影响很大。
- **现有范式**：
  - **工作流驱动方法**（如 Agentless、SWE-Fixer、SweRank、CoSIL）：按预设的检索—过滤—重排阶段逐步收窄（仓库→文件→函数）。覆盖广、流程可控，但**剪枝是单向的**，早期被丢弃的位置无法在后续被重新找回。
  - **智能体驱动方法**（如 AutoCodeRover、LocAgent、mini-swe-agent）：由 LLM 自适应决定搜索/阅读/导航，但候选集合与推理依据**绑定在单条路径依赖的推理轨迹上**。近期工作引入外部状态（候选集合）来保留轨迹外信息。
- **观察到的三种环境缺陷**（即本文要解决的痛点）：
  1. **关系目标歧义**：基于语法的图能识别程序关系，却无法解析其目标实体（如 `obj.run()` 只表明一次调用，无法确定调用的是哪个 `run` 实现），智能体只能"搜索"而非"直接导航"。
  2. **实体语义隐式**：实体的含义分散在实现细节中，缺乏紧凑语义表示；智能体须消耗有限上下文与推理能力先重建语义，才能判断与 issue 的相关性。
  3. **候选状态描述不足**：仅记录"位置集合"，不记录当前定位判断的语义与证据依据，导致后续更新难以被验证与比较。
- **核心洞察**：借鉴 IDE 实践（go-to-definition 直达相关实现、声明与文档帮助理解实体），应把这些负担从"推理者"转移到"环境"上——让关系可直接导航、实体语义可即取，并把候选判断随证据持久保存。
- **整体含义**：定位被形式化为一个**循环**：当前候选引导证据获取，新证据引导候选精炼；工作流提供广覆盖，智能体提供证据驱动的修订。

## 2. 方法论

### 2.1 核心思想
- **两阶段流水线**：
  - **离线图初始化**：AST 分析构建语义导航图（SNG）与实体级检索索引，保留目标未解析的关系。
  - **在线语义定位**：确定性检索用 issue 与其线索 ϕ(q) 初始化候选工作区 W₀；LLM 定位智能体通过 SNG 调查仓库，并在工作区中维护、修订假设；过程中按需向语言服务器解析关系目标并回写 SNG。
- **六工具两组**：
  - 语义导航组：`Search`、`Expand`、`Read`（只返回观察，不改工作区）。
  - 候选工作区组：`Update`、`Compare`、`Submit`。
- **辅助智能体**：Builder Agent（构造语义卡片）与 Comparison Agent（候选比较）拥有**独立上下文窗口**，其完整工作上下文不进入定位智能体的轨迹。

### 2.2 语义导航图（SNG）
- 图定义：G = (V, E, Ẽ)，V = V_file ∪ V_class ∪ V_func；E ⊆ V×T×V×L 为已解析边，Ẽ ⊆ V×T×L 为未解析边（L 为源码位置集合）。实体由限定名与源码跨度标识（如 `func:pkg/core.py::Parser.parse`），方法视为函数实体。
- 关系集合 T = {Contains, Calls, Imports, Inherits, References}，均为有向边。
- 离线初始化：G₀ = ASTInit(R)。语法可确定目标的关系统入 E₀，未解析的关系位点记入 Ẽ₀。
- 在线解析：G′ = Access(G; v, r, d)，d ∈ {+, −}。
  - **前向**（d = +）：对每条出边未解析位点应用 go-to-definition。
  - **后向**（d = −）：对 v 应用 find-references，将返回位点与未解析入边匹配。
  - 成功解析产生 (u, r, v, ℓ) 加入 E；仍无仓库内目标的位点保留在 Ẽ。实现基于 **Pyright**（Python）。

### 2.3 语义导航与语义卡片
- **Search**：对每个实体构建源码锚定文本表示 D(v)（限定名 + 声明 + 文档 + 实现文本）。
  - 先算 BM25 词法相关性，并叠加 issue 线索匹配 μ(c, v) ∈ {0,1}（精确关键词或源码位置匹配），加权得 b(v|x,q) = α·BM25(x, D(v)) + β·Σ_{c∈ϕ(q)} μ(c,v)；取 Top-L 为锚点集合 A。
  - 再用 SNG 中锚点的**已解析邻域**重排：得分 = b(v|x,q) + γ·Σ_{u∈A} 1[u ∼_{G′} v]，返回 Top-M 及文本/线索/关系三类支撑证据。
- **Expand**：在 SNG 上做类型化一跳导航，返回出/入邻居 N⁺_r(v;G)、N⁻_r(v;G)，附带关系类型、方向与源码位置。
- **Read**：三种证据层级——
  - `summary`：声明、包含结构与直接关系画像的确定性投影（结构定位）；
  - `code`：原始源码跨度（最权威但占上下文，可能被截断）；
  - `card`：**问题条件下的语义卡片**，是唯一被 issue 条件化的模式。
- **语义卡片构造**：X_q(v) = (q, EntityCtx(v), RelCtx(v;G′))，C_q(v) = Builder(X_q(v))。卡片记录 ①定义与职责 ②操作行为 ③在 issue 中的角色 ④支撑这些解读的紧凑源码片段。RelCtx 收集类型化一跳邻域 {(u, r, ±)} 及支撑位置。卡片按"仓库快照 + 实体 + issue 上下文"缓存，可复用。

### 2.4 候选工作区
- 工作区 W_t 为有序候选记录列表，每条记录 h_i^t = (v_i^t, z_i^t, η_i^t)：实体、调查状态 z ∈ {unverified, plausible, discarded}、引用观测证据的依据 η。列表顺序即当前排序。
- **初始化**：W₀ = Seed_τ(q, G)，用 Search 的检索机制以 issue 描述为固定查询，插入为 unverified 并按检索排名排序，提供广覆盖起点。
- **Update**：W_{t+1} = Update(W_t; v, z, η)，可插入新候选、修订状态与依据（unverified → plausible 或 discarded），也可把粗粒度位置细化为具体目标实体。
- **Compare**：(W̄_t, δ_t) = Compare(q, W_t)。Comparison Agent 用受限卷宗（每个 plausible 候选的依据、源码、语义卡片）联合评估 issue 相关性与实现职责并重排；plausible 候选领先，unverified 保持原序。若需进一步确认，则给出**聚焦验证问题 δ_t**，定位智能体据此继续导航并 Update，再调用 Compare。
- **Submit**：终止时 L̂_τ^q = Submit_τ(W̄_T)，先按确认顺序返回 plausible 候选，不足 K 个时用排名最高的 unverified 补齐，discarded 一律排除。

## 3. 实验设计

- **数据集 / Benchmark**：
  - **SWE-bench Lite**（300 个 issue）：评测文件级与函数级排序定位。
  - **PLocBench**（821 个 issue）：评测文件级排序定位。
  - **SWE-Explore**（368 个实例）：评测返回的源码证据质量，超越传统定位目标。
- **模型**：跨 benchmark 统一使用 `gemma-4-e4b-it`（Gemma 4B）；在 SWE-bench Lite 上额外使用 **Qwen3.5 9B** 与 **Qwen3.5 35B-A3B**，检验跨模型族与跨规模的稳健性。
- **对比方法**：Agentless（工作流）、CoSIL、LocAgent、mini-swe-agent、RepoSearcher（智能体/检索类）。
- **评价指标**：
  - SWE-bench Lite：Hit@K（前 K 是否含金标实体）、Function Recall@K（金标函数覆盖）。
  - PLocBench：Acc@K、MRR@5、Macro/Micro Recall@5。
  - SWE-Explore：Precision、F1、Recall@500、nDCG@500、HitFile、FUH（首次有用证据越早越好）、CE（上下文效率）。全部为百分比，越高越好。
- **消融实验**（SWE-bench Lite + Gemma 4B）：
  - 语义导航：`w/o Semantic Card`（用其余源码视图替代卡片）、`w/o Online Resolution`（仅保留离线 AST 图）。

- **下游修复验证**：用 Gemma 4B 定位器产出的上下文作为唯一仓库上下文，交给两个固定修复后端（Gemma 4B 与 Qwen3.5 35B-A3B），固定提示词、生成预算、补丁校验与 SWE-bench Lite 测试框架，单次确定性尝试；指标为 Applied（补丁可应用）与 Resolved（通过评测），并给出 Oracle 上下文上界。

## 摘要
我们研究自然语言文档是否有助于编码智能体解决软件问题，并构建了用于构造和评估此类文档的工具。我们引入一个往返基准，它根据从代码描述重新生成的代码能否通过原始测试来为代码描述打分，并表明决定描述保真度的是完整性而非长度。我们将该基准用作优化信号，发现一个撰写描述的提示词能够达到完全保真度，并能泛化到未见文件。随后，我们检验促使这项工作的假设：更好的文档能帮助智能体解决真实的仓库问题。在两个模型系列和十个代码仓库上，并以一个阳性对照确认我们的评估能够检测到真实改进，我们发现事实并非如此。当源代码存在时，无论是静态紧凑文档还是检索到的上下文，都不比仅提供问题本身更好。我们报告这一负面结果，同时给出基准和优化器，并刻画文档能够发挥作用的边界。

## Abstract
We investigate whether natural-language documentation helps coding agents resolve software issues, and we build the tools to construct and evaluate it. We introduce a roundtrip benchmark that scores code descriptions by whether code regenerated from them passes the original tests, and show that completeness, not length, drives a description's fidelity. Using the benchmark as an optimization signal, we discover a description-writing prompt that reaches full fidelity and generalizes to unseen files. We then test the hypothesis that motivated the work: that better documentation helps an agent resolve real repository issues. Across two model families and ten repositories, and against a positive control confirming that our evaluation can detect a genuine improvement, we find that it does not. When the source is present, neither static compact documentation nor retrieved context beats the issue alone. We report this negative result together with the benchmark and the optimizer, and we characterize the boundary at which documentation helps.

## 1. 核心问题与整体含义
- **研究动机**：大型代码仓库往往无法整体载入编码智能体的上下文，智能体需要编辑自己未完整阅读的文件，因此常依赖自然语言文档来补充代码中隐含的意图与契约。
- **核心假设**：高保真、紧凑的自然语言文档，应能替代或辅助源代码，帮助智能体解决真实仓库问题。
- **整体含义**：论文不仅构建了评估和优化“代码描述”的工具，还系统检验了“更好的文档能否迁移到真实 issue 解决”。结论是一个边界：当源代码不可见时，优化后的文档能大幅帮助智能体；当源代码已存在时，文档不再优于仅给 issue，甚至可能因冗余而干扰智能体。

## 2. 方法论
- **核心思想**：把自然语言描述视为可重建代码的“源”，用“从描述重新生成代码能否通过原测试”衡量描述保真度，并将该信号用于优化写描述的提示词。
- **往返基准（Roundtrip Benchmark）**：
  - 三阶段流程：
    1. **Describe**：智能体为源文件生成自然语言描述，排除原测试代码。
    2. **Regenerate**：另一模型仅根据描述和空项目脚手架/契约文件重新实现代码，不能访问原源码。
    3. **Evaluate**：用原单元测试作为 oracle，评分重新生成代码通过测试的比例。
  - 生成阶段温度设为 0；由于托管 API 非比特确定性，每个 fixture 重复运行并报告均值与标准差。
  - **压缩指标**：  
    \[
    \text{density}(d)=\frac{\text{描述中的 token 数}}{\text{被描述代码的 token 数}}
    \]
    用于衡量描述相对代码的紧凑程度。
  - **污染控制**：fixtures 来自 SWE-bench Verified；监控 regenerate 阶段是否逐字背诵原源码；若模型识别并拒绝生成，则排除该文件。
- **文档价值分析**：
  - 文档只在提供代码未暴露的意图或契约时才有帮助；若只是复述可读代码，则无增益。
  - 控制实验表明：**完整性**决定智能体成功，长度在完整性满足后是二阶因素。
- **描述优化器**：
  - 将 describe 阶段提示词视为可搜索的 harness。
  - 外层循环由 proposer 提出新提示词，benchmark 评分，保留更优者。
  - 优化目标：  
    \[
    J(\pi)=\frac{1}{|F|}\sum_{f\in F}\text{fidelity}(\pi,f)-\lambda\frac{\bar w(\pi)}{300}
    \]
    其中 \(\bar w(\pi)\) 为平均描述词数，\(\lambda=0.1\)，惩罚较小，使保真度主导，但推动“完整后尽量紧凑”。
  - proposer 使用 Pro 模型，温度 0.4；describe 与 regenerate 阶段温度 0，保证候选评分确定。
  - 使用训练 fixtures 优化，并在未见过的留出 fixtures 上检验泛化。
- **下游迁移测试**：
  - 分离两种 regime：
    1. **Source withheld**：源代码不可见，文档是智能体唯一代码视图。
    2. **Source present**：源代码在工作目录中，智能体正常编辑，文档作为额外上下文。
  - 对比条件包括：仅 issue、baseline 描述、优化描述、完整长度描述、检索到的 past-task context 等。

## 3. 实验设计
- **数据集与场景**：
  - **Roundtrip fixtures**：从 SWE-bench Verified 筛选。筛选规则包括：gold patch 仅修改一个非测试源文件、test patch 命名 oracle 测试、项目与 Python 工具链可执行、baseline 通过自身 oracle。2294 个 Verified 实例中 429 个满足单文件/命名 oracle 条件，最终得到 **11 个 fixtures**。
  - **手工构造代码库**：3 个，用于测试“契约只存在于描述中”时文档是否帮助。
  - **下游 issue 解决**：
    - 自建 Kind-B multi-file 集：50 个 fixtures，43 个在两种条件下产生可评分编辑。
    - django Kind-B fixtures：15 个。
    - **SWE-ContextBench Lite**：99 个任务、12 个仓库，使用官方 Docker 环境和评估 harness。
    - 最终全量 Lite 对比：58 个在所有条件下产生可评分编辑的任务。
  - **编辑而不加载文件**：测试智能体是否只根据 issue 和描述定位符号、返回替换片段并拼接测试。
- **Benchmark 与评估指标**：
  - 主 benchmark 为 roundtrip fidelity，即重新生成代码通过原测试的比例。
  - 压缩指标为 density。
  - 下游使用 fail-to-pass 和 pass-to-pass 测试，要求全部通过才算 resolved。
  - 使用配对比较、McNemar 精确检验、配对 sign test 等统计方法。
- **对比方法**：
  - 无描述 / 仅 issue。
  - baseline describe prompt。
  - optimized describe prompt。
  - full-length optimized description。
  - OpenWiki 生成的仓库文档。
  - SWE-ContextBench 提供的 retrieved past-task context。
  - 阳性对照：benchmark 自带 retrieved context，用于确认评估能检测真实改进。
- **使用模型**：
  - Gemini 系列：Flash（gemini-3.5-flash）、Flash-lite、Gemini 2.5 Flash、Gemini 3.1 Pro、Gemini 3.8 Flash。
  - Pro（gemini-2.5-pro）作为优化器 proposer。
  - 本地 Qwen 3.6 agent。
  - Gemma 4 31B、Gemma 3 4B 用于长度实验。

## 摘要
自主AI智能体在环境中选择动作时，其内存、执行时间、运行时、计算和操作约束决定了什么构成合适计划。我们称这种执行上下文在智能体规划状态中的缺失为基板盲视。我们通过数值代码生成来测试这一普遍命题，因为在此过程中选定的实现选择和操作后果可直接观察。三种前沿模型配置——Anthropic Claude Opus 5、OpenAI GPT-5.6-Sol 和 Google Gemini 3.7 Flash——针对高维成对欧氏距离任务生成代码，要么仅基于任务本身，要么附加128 MB内存和10.0秒墙钟时间的约束。在14次可执行的、索引对齐的任务仅限与约束披露比较中，约束披露在13次中降低了测量的峰值进程内存，并在所有三个队列中降低了平均墙钟时间，执行速度提升高达3.1倍。在审计的语料库中，披露产生了结构性代码更改，包括有界阻塞、float32保留、上三角遍历以及就地或内存映射缓冲区。在更严格的96 MB约束下，独立采样的约束披露队列实现了正确且预算内的结果：Claude Opus 5为4/5，GPT-5.6-Sol为5/5，Gemini 3.7 Flash为3/5，而任务仅限结果分别为0/5、1/5和0/5；队列平均最大常驻内存和墙钟时间比其任务仅限参考低49-74%和35-64%。这些结果为基板感知的智能体规划建立了一个受控的概念验证：一个最小的执行契约能诱导生成程序中的主动结构性适应，将计算从无约束分配中转移，并在执行前显著改善观察到的资源-时间轮廓。

## Abstract
Autonomous AI agents increasingly select actions in environments whose memory, execution-time, runtime, compute, and operational constraints determine what counts as a suitable plan. We call the absence of this execution context from an agent's planning state substrate blindness. We test this general proposition through numerical code generation, where selected implementation choices and operational consequences are directly observable. Three frontier model configurations--Anthropic Claude Opus 5, OpenAI GPT-5.6-Sol, and Google Gemini 3.7 Flash--generate code for a high-dimensional pairwise Euclidean-distance task either from the task alone or with a 128 MB RAM and 10.0 s wall-time contract. Contract disclosure reduced measured peak process memory in 13 of 14 executable index-aligned task-only versus contract-disclosed comparisons and reduced mean wall time in all three cohorts, making execution up to 3.1x faster. Across the audited corpus, disclosure produced structural code changes including bounded blocking, float32 retention, upper-triangle traversal, and in-place or memory-mapped buffers. At a tighter 96 MB contract, independently sampled contract-disclosed cohorts achieved correct-and-within-budget outcomes of 4/5 for Claude Opus 5, 5/5 for GPT-5.6-Sol, and 3/5 for Gemini 3.7 Flash, compared with task-only outcomes of 0/5, 1/5, and 0/5; cohort mean MaxRSS and wall time were 49-74% and 35-64% lower than their task-only references. These results establish a controlled proof of concept for substrate-aware agent planning: a minimal execution contract induces proactive structural adaptation in generated programs, shifting computation away from unconstrained allocations and substantially improving observed resource-time profiles before execution.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心问题**：自主AI智能体在与环境交互时，其规划状态中普遍缺乏执行环境上下文（内存限制、执行时限、运行时版本、计算约束等），导致生成的计划“理论上正确”但在实际部署环境中不可用。论文将这一现象定义为 **“基板盲视”（substrate blindness）**。
- **研究动机**：现实计算部署都在明确的运行契约下进行——Kubernetes按CPU/内存请求调度并执行限制、Cloud Run在实例超限时终止、AWS Lambda将内存配置与CPU资源和计费耦合。智能体若在选计划时不知道这些约束，就可能选择看似合理实则不适配的实现，只有等运行时失败后才能通过反馈修复。
- **核心研究命题**：执行上下文是规划所需的决策相关信息，应在智能体选择方案之前提供，而不是在失败之后依赖运行时反馈。该命题通过**数值代码生成**任务做了受控验证，因为在此场景中，代码实现选择与资源消耗结果都直接可观察。

## 2. 论文提出的方法论：核心思想、关键技术细节

- **核心思想**：向智能体在做出实现决策前注入一个**最小化的执行契约**（RAM上限 + 执行时限），而非提供具体算法、代码骨架或事后的失败反馈。通过对比“仅任务描述（task-only）”和“任务描述+执行契约（contract-disclosed）”两种条件下模型生成的代码，观察资源利用和执行行为的差异。
- **实验任务（基准）**：
  - 输入为 `vectors.npy`：一个 8,000×1,024 的 float32 矩阵。
  - 任务是计算所有行之间的成对欧氏距离之和（sum over i,j of ||v_i - v_j||_2），输出 `TOTAL_DIST:<value>`。
  - 约束：仅允许使用 NumPy 与 Python 标准库，禁止 SciPy 等外部包。
  - 该任务的直接实现需存储 8,000×8,000 float32 距离中间矩阵，即 256,000,000 字节（244.14 MiB），超过披露的 128 MB 内存预算，因此存在多种不同的实现策略选择空间。
- **干预方式**：
  - **Task-only (A组)**：仅提供任务描述。
  - **Contract-disclosed (D组)**：在完全相同任务描述后追加 `Execution environment: RAM limit: 128 MB. Execution time limit: 10.0 seconds.`
  - 不附带任何实现提示、预设算法、系统提示词或多轮修复回路。
- **一次扩展的“更紧契约”实验**：对三种模型各生成 5 个新样本，披露 96 MB RAM + 10 秒的契约，测试模型对边界收紧的梯度响应。
- **消融逻辑**：任何生成的代码差异都是模型主动适应披露的运行环境，而不来自对给定方案的服从。

- **对照组与基准参照**：三种模型的 task-only 条件 = 基线（reference），contract-disclosed = 处理组。没有对比其他已有方法或算法，目标不是比拼效率，而是验证“是否披露执行契约会改变生成行为”。

## 6. 论文的主要结论与发现

- **首要发现**：执行契约的披露系统性改变了模型生成的代码结构。具体表现包括：
  - 采用有界分块计算（bounded blocking）而非一次性物化整块矩阵；
  - 保留 float32 精度而不提升到 float64（避免中间矩阵内存翻倍）；
  - 只遍历上三角（利用对称性，减少一半计算）；
  - 使用就地操作或内存映射缓冲区以降低临时内存峰值。
- **128 MB 契约下的量化结果**：
  - 14 个可执行索引对齐对比中，13 个的 contract-disclosed 程序峰值内存更低。
  - 三种模型的平均 wall time 都下降：Claude 2.52×、GPT 1.68×、Gemini 3.09×（最高提速 3.1×）。
  - 平均 MaxRSS（MiB）变化：Claude 256.48→107.82；GPT 118.63→64.61；Gemini 452.36→158.16。
  - 正确且在 128 MiB 预算内：Claude 0/5→5/5；GPT 4/5→5/5；Gemini 0/5→2/5。
- **96 MB 更紧契约的结果**：
  - 正确且 ≤96 MiB 的成功率：Claude 4/5、GPT 5/5、Gemini 3/5（对照 task-only：0/5、1/5、0/5）。
  - 与 task-only 基线相比平均 MaxRSS 降 49–74%，平均 wall time 降 35–64%。
  - 收紧契约时平均 wall time 小幅上升（Claude 5.3%、GPT 9.1%、Gemini 11.9%），说明模型在更紧内存边界下牺牲了少量时间来适配内存——一个“理性”的资源-时间权衡迹象。
  - 96 MB 条件下 MaxRSS × wall time 的乘积（时间加权内存占用）比 task-only 低 67–90%。
- **核心论证结论**：披露执行契约（极小的提示干预）不通过算法指定、微调或失败的试错循环，就能在首次生成即促成代理主动的、结构性的实现适应，确立“基板感知规划”的可控概念验证。

## 8. 不足与局限

- **样本量过小**：每条件 n=5，共 45 个生成实例作基础。没有统计显著性检验，只能报告描述性均值与方向一致性。生成模型本身有随机性，如此小的样本难以排除抽样偏差。
- **单一任务**：只使用了一个欧氏距离成对求和任务，结构简单，仅代表数值密集型可阻塞计算；无法证明结论对 IO 密集型、多依赖、交互式、长流程代码或非代码 agent 任务也成立。
- **供应商条件不匹配**：三家模型配置不同——这被作者有意声明（非 tier-matched），但也意味着跨模型比较没有实际意义；并发复现时模型版本、provider 端更新都可能改变结果。
- **未涉及多轮与工具反馈**：实验限定在单轮原子“实现选择”步骤。真实 agent 系统中的迭代修复、工具调用、沙盒反馈等动态因素不在此范围，因此从单轮到长流程的推广需要额外证据。
- **运行环境的代表性**：在单机 macOS CPU + 单线程 NumPy 上测量，不涵盖容器化、serverless、多租户、GPU 等生产级执行环境的差异；MaxRSS 在 macOS 与 Linux cgroup 语义不同，论文对此没有做更深入的跨平台验证。
- **对“预算内”定义的口径细节**：128 MB 按 <128 MiB 判定，96 MB 按 ≤96 MiB 判定，虽在文中说明，但两种分类尺度的不一致可能使严格复现略有门槛。

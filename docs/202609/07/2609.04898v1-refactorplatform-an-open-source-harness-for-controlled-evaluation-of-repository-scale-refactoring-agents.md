## 摘要
仓库级重构要求编码智能体在不改变程序行为的前提下，将单个变更传播到许多相互依赖的文件中；但据我们所知，现有测试平台都不能将决定智能体在此类任务上成败的设计选择单独隔离出来。我们提出了 RefactorPlatform——一个开源评估平台，它在保持环境固定的同时显式地改变各设计维度：模型主干（通过 OpenRouter 和 GitHub Copilot CLI）、执行机制（基线、检索增强和多智能体）以及提示具体性。每次运行都在隔离的工作区中执行，支持实时终端流、按任务记录 token、diff 与交互记录、基于 AST 的验证，并提供可导出的遥测数据以支持审计与复现。通过在四类模型家族的 100 个多文件 RefactorBench 任务上演示该平台，我们展示了它所支持的下列分析：在各类提示模式下，AST 感知分块比朴素的 token 窗口分块高出 25–30%，而朴素检索则低于无检索基线；一个精简的检索增强单智能体（86%）在配对任务上胜过我们所评估的子智能体配置（66%），后者在检索失败时委托的任务无一通过；此外，检索带来的准确率提升恰好抵消了其 token 开销，使每次成功重构的成本保持不变。RefactorPlatform 已开源，以提高重构智能体评估的可复现性与可审计性。

## Abstract
Repository-scale refactoring requires coding agents to propagate a single change across many interdependent files without altering program behavior, yet to our knowledge no existing harness isolates the design choices that determine agent success on this task. We present RefactorPlatform, an open-source evaluation harness that holds the environment fixed and varies each design axis explicitly: model backbone (via OpenRouter and GitHub Copilot CLI), execution regime (baseline, retrieval-augmented, and multi-agent), and prompt specificity. Each run executes in an isolated workspace with live terminal streaming, per-task logging of tokens, diffs, and transcripts, AST-based verification, and exportable telemetry for audit and reproduction. Demonstrating the platform on 100 multi-file RefactorBench tasks across four model families, we illustrate the analyses it supports: AST-aware chunking outperforms naive token-window chunking by 25-30% across prompt modes, whereas naive retrieval falls below the retrieval-free baseline; a lean retrieval-augmented single agent (86%) beats the sub-agent configuration we evaluated (66%) on matched tasks with no task passing under delegation that fails under retrieval; and retrieval's accuracy gains absorb its token overhead, leaving cost per successful refactoring unchanged. RefactorPlatform is open-sourced to make refactoring-agent evaluation reproducible and auditable.

## 2. 论文提出的方法论

**核心思想**：构建一个开源评估测试平台，它在**保持任务环境固定的前提下、沿四个独立设计轴显式变化配置**，并对每次运行进行完整日志记录与 AST 级行为验证，从而让研究者能够受控地隔离每个设计选择对重构成功率的因果贡献。

### 2.1 四个可配置的设计轴

| 设计轴 | 选项 |
|---|---|
| 模型选择 | 任意 OpenRouter（BYOK）模型、GitHub Copilot CLI |
| 执行机制 | S1 基线终端助手 / S2 检索增强助手 / S3 子智能体委托 |
| 提示模式 | Descriptive（What+Where+How）/ Base（What+Where）/ Lazy（仅What） |
| 目标任务 | RefactorBench（Python）、SWE-Refactor（Java） |

### 2.2 三种执行机制

- **S1（基线助手）**：单一智能体在隔离终端会话内运行，拥有文件解析、目录列表、正则工具（grep/view/edit/bash）等本地工具，但没有外部上下文访问能力。
- **S2（检索增强助手）**：在 S1 之上通过 Model Context Protocol（MCP）集成持久化的任务作用域代码搜索引擎。具体流程为：
  - 代码库经 **CocoIndex** 处理，按 **AST 感知分块**或**朴素 token 窗口分块**两种模式切分；
  - 使用 **nomic-embed-code** 编码器（GGUF Q4_K_M 量化）生成向量嵌入；
  - 检索采用混合策略：向量余弦相似度 + BM25 词法匹配，通过 **Reciprocal Rank Fusion（RRF）** 融合排序。
- **S3（子代理委托）**：赋予智能体原生子智能体能力以及描述何时委托的提示块，但**不施加任何拓扑限制**。系统从智能体自己的事件流中检测委托行为，将每次运行标记为 conformant（合规）或 setup_not_exercised（未实际启用委托）。

### 2.3 验证管线

- **Python**：通过全部关联的 **AST 单元测试**，不允许部分给分。
- **Java**：三重验证门槛——代码提取成功 + 编译成功 + 全部测试通过 + RefactoringMiner 结构比对（排除"惰性桩代码"）。
- CodeBLEU 分数仅作背景诊断，不参与通过/失败判定。

### 2.4 性能指标

- **任务通过率**（PR_task）：所有关联 AST 测试全部通过才计为成功，不允许部分给分。
  
  \[
  PR_{task} = \frac{1}{N}\sum_{j=1}^{N} I_j, \quad I_j = \bigwedge_{k=1}^{K_j} ASTTest_{j,k}
  \]
  
- **成本效率**（CE）：平均每个成功任务的金融 token 成本。

\[
CE = \frac{\sum_{j=1}^{N} C_j}{\sum_{j=1}^{N} I_j}

## 6. 论文的主要结论与发现

1. **提示词质量是最大的单一能力指标**：S1 下 Descriptive→Base 损失 9pp，Base→Lazy 再损失 16pp（−44% → −59% → −71% 的相对降幅模式）。
2. **LSP 诊断帮助甚微**：平均仅 +3.7pp，在提示词充分的 Descriptive 模式下仅 +2pp——自动化 linting 反馈无法替代任务描述的语义清晰度。
3. **AST 感知分块是检索有效的前提**：在三个提示模式下，AST 分块均比朴素 token 窗口分块高 25–30pp（如 Descriptive 86% vs 57%），原因是 AST 保留了代码的语法边界与逻辑作用域，而朴素切分产生语义残缺片段。
4. **朴素检索不如无检索**：token 窗口分块的 S2 结果（44–57%）低于 S1 基线（59–73%），说明"错误形式的检索"会引入噪声而非结构化信息。
5. **多智能体弱势**：S3 在 100 个任务上仅 66%，低于 S2 的 86%，且**无任何任务在委托下通过却在检索下失败**——20 个任务相反情况，说明检索优越性是完全一致性的。
6. **成本与收益的权衡**：检索使每任务成本上升（如 deepseek-v4-pro $1.07→$1.23），但因提高通过率，**每次成功的成本不变（$1.39/$1.39, $0.13/$0.13）**。
7. **跨模型一致性**：S2 相对 S1 在四个模型上平均提升 9.5pp，最强效果在 deepseek-v4-pro（77%→89%）上取得，证实结构感知而非原始模型能力是两个执行机制的核心差距。
8. **5% 的"普遍失败"任务基线**：约 5% 的任务在所有配置下均失败（如 django 的导入传播和 scrapy 的深度跨模块参数化），暗示需要"主动的、执行引导的验证环境"去突破被动检索的天花板。

## 7. 优点

以下对论文的主要方面做逐项评价：

### 7.1 方法与设计角度
- **受控隔离设计**：明确提出"固定环境、变化设计轴"的评估哲学，区别于端到端整体性能比较，能够回答"某个组件到底贡献了多少"这一核心问题。
- **多维度覆盖**：模型、执行机制、提示特异性、验证方式四个维度系统拆解，形成一块 3×3 以上的分析矩阵。
- **完整审计追踪**：每次运行均记录隔离工作区内的所有 token、diff、终端流和分析文本，支持第三方审计与复现。
- **开放性**：允许 BYOK（自带 API key）的任意 OpenRouter 模型，易于扩展更多基准和验证门。

### 7.2 实验与发现角度
- **发现了若干具有高度可操作性的规律**：
  - AST 分块 > 语义提示词 > LSP 反馈 > 朴素检索 > 子智能体委托（大致排序）；
  - 检索词块的"语法结构忠实度"而非其嵌入质量，是决定检索增强是否有效的关键；
  - 多智能体与单智能体检索之间存在**完全单向的优劣关系**（concordant dominance of retrieval）。
- **对多智能体的评估设计有方法学贡献**：将"启用委托"与"实际使用委托"的任务分开报告（66% vs 70.4%），避免混淆架构潜力与实际使用。

### 7.3 学术综述与定位角度
- 对现有工作进行了较清晰的定位：SWE-agent（agent–computer 接口）、OpenHands（开放测试平台）、Agentless（精简流水线）、RefactorBench（任务集）vs 本文（**机制隔离测试架**），立论准确、补位明确。

## 总结定位

**RefactorPlatform 的贡献在于评估基础设施而非算法本身**。它的价值在于把"模型主干、检索策略、提示措辞、多智能体编排"这四类混杂在一起的因素从实验上拆解开，并给出了一个有代表性（虽然不是穷尽的）的实证快照：在 Python 仓库级重构中，**AST 结构分块的检索增强单智能体是目前配置选择中性价比最优的路线**，而多智能体与朴素检索在重构场景中均缺乏竞争力和可解释的收益。这一结论对编码智能体的工程选型具有直接参考价值。

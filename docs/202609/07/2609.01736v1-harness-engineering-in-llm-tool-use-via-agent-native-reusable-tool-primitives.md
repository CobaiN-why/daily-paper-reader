## 摘要
大型语言模型（LLM）结合外部工具在解决复杂现实世界任务中展现出了显著能力。然而，现有方法面临两个关键挑战：由不兼容的工具输出类型和API模式导致的多步骤、多轮推理的脆弱性，以及在大规模工具目录下的性能下降。为了解决这些问题，我们引入了\textbf{Tool Primitives}（工具原语），一种以自然语言作为工具调用接口取代基于刚性API模式调用的设计，其中每个工具都封装了一个LLM接口，在内部处理模式解析与执行，从而实现嵌套及多轮工具调用中工具间的自然通信。基于Tool Primitives，我们构建了\textbf{ToolFace}，一个包含25,519个函数的集中式仓库，LLM在推理时仅动态检索相关工具，无需在上下文中列举原始API模式。为了在复杂设置中可靠地编排Tool Primitives与ToolFace，我们进一步提出了\textbf{HEART}，一个通过\textbf{智能体原生的、可复用的工具原语}实现的\textbf{编排工程技术}框架，由规划器（Planner）、路由器（Router）和验证器（Verifier）组成，三者联合支持动态工具调用规划、多步执行以及基于反馈的恢复。在五个基准上的实验表明，HEART平均比基于SFT的模型高出$10\%$，并平均超越GPT-5.4、Claude-4.6-Sonnet和Gemini-3.1-Pro达$6\%$，同时将API成本降低最多$85\%$。在50个现实任务中，HEART实现了$84\%$的任务完成率，是三个前沿商业模型平均值（$22\%$）的$3.8$倍。

## Abstract
Large language models (LLMs) augmented with external tools have demonstrated remarkable capability in solving complex real-world tasks. However, existing approaches suffer from two key challenges: brittle multi-step and multi-turn reasoning caused by incompatible tool output types and API schemas, and performance degradation under large tool catalogues. To address these, we introduce \textbf{Tool Primitives}, a design that replaces rigid API schema-based invocation with natural language as the interface for tool calling, where each tool is wrapped with an LLM interface that handles schema resolution and execution internally, enabling natural inter-tool communication for nested and multi-turn tool calling. Building on Tool Primitives, we host \textbf{ToolFace}, a centralized repository of 25,519 functions from which LLMs dynamically retrieve only the relevant tools at inference time, eliminating the need to enumerate raw API schemas in context. To orchestrate Tool Primitives and ToolFace reliably in complex settings, we further propose \textbf{HEART}, a \textbf{H}arness \textbf{E}ngineering framework via \textbf{A}gent-native, \textbf{R}eusable \textbf{T}ool Primitives, comprising a Planner, Router, and Verifier that jointly support dynamic tool invocation planning, multi-step execution, and feedback-driven recovery.   Experiments on five benchmarks demonstrate that HEART outperforms SFT-based models by $10\%$ on average and surpasses GPT-5.4, Claude-4.6-Sonnet, and Gemini-3.1-Pro by $6\%$ on average while reducing API cost by up to $85\%$. On 50 real-world tasks, HEART achieves $84\%$ task completion, $3.8\times$ the average of three frontier commercial models ($22\%$).

## 1. 核心问题与研究动机

- **核心问题**：现有 LLM 工具调用（tool-use）方法在复杂真实任务中仍存在两大瓶颈：
  - **多步/多轮推理脆弱**：不同工具具有异构 API schema，模型将前一个工具的输出映射为下一个工具的输入时经常失败；多轮对话中上下文不断稀释，历史交互越长性能退化越明显（如 NESTFUL 上最强模型完整序列匹配准确率仅 28%）。
  - **大规模工具目录导致性能下降**：工具目录规模增大时模型选择准确率显著下滑（token 数从 8K 扩大到 120K 时准确率下降 7%~85%），而 ToolBench 已包含 16,000+ 真实 API，问题更严重。
- **整体含义**：作者提出反向思路——“不要强迫模型说 API 的语言，而是让工具说模型的语言”。即不把原始 API schema 暴露给模型，而是把工具封装成模型可自然语言调用的“工具原语”，并配合推理时按需检索工具，从系统架构层面解决上述问题，而非单纯依赖 SFT 或更强大的模型。

## 2. 方法论

### 核心设计
论文提出三个互相配合的组件：

1. **Tool Primitives（工具原语）**
   - 以自然语言作为工具调用的接口，替代刚性 API schema。
   - 每个工具用一个 LLM 包装，内部完成 schema 解析、参数绑定、函数执行和结果结构化返回；调用方模型不需要知道确切参数类型与 API schema。
   - 数学表述为：`P_i(x; c) = M[s_i; c; x]`，其中可携带前序工具的上下文结果作为 `c`，从而支持工具与工具之间的自然语言通信（LLM-to-LLM dialogue），这是嵌套调用和多轮信息获取的基础。

2. **ToolFace（工具仓库）**
   - 集中式工具注册表，含 25,519 个 schema–函数对：
     - ToolBench 16,464 个 API；
     - NESTFUL 的 40 个数学工具与 4,348 个编码工具；
     - τ²-Bench 的 68 个工具；
     - ACEBench 的 4,538 个双语 API；
     - BFCLv4 的 2 个 web search 与 5 个 memory 工具；
     - 54 个人工手写工具（表单填充、点击、网页分析等）。
   - 模型在推理时通过语义搜索只检索与当前任务相关的少量工具，避免将大型工具目录塞入上下文。

3. **HEART（编排工程框架）**
   - 多智能体系统，包含五阶段：规划 Planning → 路由 Routing → 工具组织 → 执行 → 验证，核心交互由三个角色完成：
     - **Planner**：意图解析 + 信息充分性检查；上下文不足时向用户发起定向澄清（`δ_t = insufficient`），否则生成有序调用计划 Π=(π₁,…,π_K)。
     - **Router**：为每个步骤从上下文解析参数，构造自然语言调用请求和超参数（retry、priority、timeout），发送给对应 Tool Primitive。
     - **Verifier**：从任务完成度、参数一致性、执行有效性、约束满足四个维度独立评估结果；任一不通过即返回结构化反馈 φ_k，交由 Planner 重新规划，形成迭代纠错闭环。
   - 默认用 Qwen3-8B 统一承担全部角色，最大重规划预算 B=3。

## 7. 优点

- 问题切入角度新颖：不是堆更多训练数据，而是以“接口逆转”的思路重新设计 tools 的对外表示，让模型表达与工具执行解耦。
- 工程设计完整性较好：Plan-Route-Execute-Verify 闭环把工具调用从“一次性猜测输出”变成结构化可恢复过程，验证器给出四类可诊断的判别标准，反馈信息可量化。
- 动态检索工具目录的思路切中大规模工具场景实际痛点，兼顾扩展性与上下文成本。
- 安全鲁棒性是一个突出亮点：schema 不进 prompt，从根上消除了 ToolHijacker 式的注入面；在框架层面展示了对真实攻击场景的防御能力（0.0% ASR）。
- 成本分析的视角有价值：通过 8B 开源骨干 + 多 agent 编排，展示“较弱模型 + 系统架构”可以匹敌甚至超过闭源旗舰模型；附有较透明的 token 单价对比。
- Tool Primitive 模块化设计使外部骨干模型可即插即用（如 GPT-5.4 + Qwen3-8B 混合配置仍接近全 GPT-5.4 性能），工程落地性强。

## 8. 不足与局限

- **评估区域与工具库高度同源**：ToolFace 中工具的来源即 ToolBench/NESTFUL/τ²-Bench/ACEBench/BFCLv4，评测基准与仓库内容重叠；这可能高估检索在“未见工具”上的表现，没有充分验证对全新未知工具的泛化。
- **成本/延迟口径的公平性**：HEART token 消耗更高但依赖低单价 8B 模型实现“成本降低 85%”，并未在同一 token 口径或同一模型定价口径下与商业模型公平比较；延迟也几乎比所有商业模型慢，论文对延迟劣势的讨论较克制。
- **资源信息缺失**：未报告 GPU 型号、数量、推理总时长或碳足迹，无法判定实际部署门槛。
- **安全评估范围较窄**：仅覆盖工具选择阶段的 prompt injection（跟随 ToolHijacker），没有覆盖工具输出污染、间接 prompt injection、数据投毒等更广威胁模型，且“安全来自不上文”是结构性质，可能牺牲中间可解释性。
- **人工真实任务基准偏小且无独立发布细节**：50 个任务没有公开任务列表、评估系数与标注者间一致性，结论可复制性有限；且任务“需要实际行动”的设置天然偏向 HEART 的系统架构，对直接 return 建议的闭源模型未必公平。
- **缺陷集中在小模型能力边界**：8B 骨干的长期记忆、复杂逻辑与工具无关的推理能力明显弱于闭源模型，消融显示换更强的骨干仍有提升空间；其表现高度依赖 Planner/Verifier prompt 与检索质量，一旦任务超出这些模块的设计范围可能快速退化为“重试循环”。
- **公开证据不足**：作为预印本论文，代码、ToolFace 仓库架构与基准全部尚未开放，难以复核真实可复现性。

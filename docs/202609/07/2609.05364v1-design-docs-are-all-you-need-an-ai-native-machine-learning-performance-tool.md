## 摘要
机器学习性能建模对于长寿软件而言是一片独特的不利地形：今天的抽象所蕴含的假设会被明天的模型和系统所否定，迫使性能建模框架不断重构。与此同时，AI编码智能体已经变得足够快速和强大，以至于重新生成整个库比偿还逐步修补所产生的技术债务更为划算。我们描述了SMART，一个用于机器学习系统的严谨符号性能建模库，其主分支几乎不包含代码：该仓库是一个由自包含自然语言设计文档组成的有向无环图（DAG），编码子智能体在新版本更新时仅根据文档重新生成实现，而每一次人工修改都是对文档的自然语言编辑——从构造上实现自我文档化。使重新生成可靠的两个要素是：（i）一种围绕逐步工作示例构建的设计文档风格，这些示例为生成智能体提供上下文内演示；（ii）一个最小的、递归定义的算子IR，带有符号（SymPy）成本表达式，一种用于大规模扫描的快速解析汇总模式，以及一种用于细粒度调度研究的慢速模调度模式。重新生成的实现能够复现人工审计的参考模型——包括在TPU pod切片上服务于DeepSeek-V3——达到舍入精度，这表明设计文档（而非代码）可以作为机器学习系统协同设计工具的持久工件。

## Abstract
Machine-learning performance modeling is a uniquely hostile terrain for long-lived software: the assumptions baked into today's abstractions are invalidated by tomorrow's models and systems, forcing perpetual refactoring of performance-modeling frameworks. Meanwhile, AI coding agents have become fast and capable enough that regenerating an entire library is cheaper than paying down the tech debt of incrementally patching it. We describe SMART, a rigorous symbolic performance-modeling library for ML systems whose main branch contains almost no code: the repository is a DAG of self-contained natural-language design docs, coding sub-agents regenerate the implementation from only the docs on new version updates, and every human change is a natural-language edit to a doc--self-documenting by construction. Two ingredients make regeneration reliable: (i) a design-doc style built around step-by-step worked examples that act as in-context demonstrations for the generating agents, and (ii) a minimal, recursively defined operator IR with symbolic (SymPy) cost expressions, a fast analytical roll-up mode for large sweeps, and a slow modulo-scheduling mode for fine-grained schedule studies. Regenerated implementations reproduce hand-audited reference models--including DeepSeek-V3 serving on a TPU pod slice--to round-off precision, suggesting that design docs--not code--can be the durable artifact for ML-systems co-design tools.

## 1. 核心问题与研究动机

- 论文关注 **机器学习（ML）性能建模软件** 的“短命”问题：这类工具位于快速演变的模型架构（如 MoE、latent attention）与硬件系统（TPU、互联）之间，任何一方变化都会导致既有抽象失效，必须频繁重构。
- 传统增量修补模式会积累两类技术债务：
  1. **增量生成债务**：公式化描述为 \(D_{t+1} = G(S_{t+1}, C_t) - G(S_{t+1})\)，即“基于旧实现修补出的系统”与“从当前规格直接生成（greenfield）的系统”之间的差异，该债务通常远大于零，且随时间复合增长。
  2. **上下文窗口短视**：成熟的代码库无法整体放入 AI 编码智能体的上下文窗口中，开发者只能提供碎片化代码片段，导致智能体缺乏全局视角，产生局部合理但全局次优的代码，破坏系统结构一致性。
- 论文的核心主张：当 AI 编码智能体足够快且便宜时，**“从零重新生成整个库”比“在人/智能体修补旧代码”更经济、更可靠**。

## 2. 论文提出的方法论

### 核心思想
- **将自然语言设计文档（design docs）作为唯一持久工件**，代码仅视为可再生的构建产物（build product）。
- 主分支几乎不含代码，仓库内容为一系列自包含 Markdown 设计文档，组成一个有向无环图（DAG）。每次版本更新时，由编码子智能体依据设计文档重新生成整个库；人工修改只能编辑文档，从而实现“自我文档化”并消除增量修补债务。

### 关键技术细节

#### (1) 设计文档 DAG 与代理编排流程
- 文档间依赖关系**由只读代理分析文档自动推断**，而非手动维护；
- 编排器（orchestrator）按拓扑序分配独立子智能体，每个文档由一个专属子代理实现；
- 编排器维护中心日志，记录子代理难以理解的文档部分以及发现的生成 bug，便于人工针对薄弱文档改进表述；
- 基于文档复杂度可动态选择不同能力的模型（如基础 DSL 用更大模型，下游简单文档用小模型降低成本）。

#### (2) 文档风格：强调逐步“工作示例”（worked examples）
- 每份文档包含可“心头执行”的具体示例，如“在 2×2×2 环面且可回绕时，每个节点的链路数是 3 而非 6；因此 V 字节 all-gather 的成本为……”
- 每个含数值的文档末尾设有 **调和锚点（reconciliation anchor）**：给出小型预设输入及精确期望输出，由生成的测试断言。
- 工作示例充当上下文内演示（in-context demonstrations），让智能体代码生成更稳定、语义更确定，弥补纯文字描述的歧义性。

#### (3) 最小化递归算子 IR
- 统一抽象为递归定义的 `Op` 节点，包含：
  - 输入/输出 Tensor（符号形状）
  - 成本（OpCost，基于 SymPy 的符号表达式，区分 compute/memory/comm）
  - 资源保留表（RRT：行 = 资源、列 = 周期、单元 = 使用量的矩阵）
  - 参数可为内层循环（`InnerLoop`）、子图（`GraphParams`）或叶子（`LeafParams`）
- 叶子节点与硬件系统相关，面向 TPU 的叶子包括：MXU 矩阵乘块、VMEM tile 加载、ICI 集合通信（如 allgather）。
- 使用 **Python 嵌入式追踪 DSL** 构建模型，避免手工构造 Op 节点：
  - `@smart_map_loop` 表示并行 map 循环；
  - `@smart_loop` 表示带累加器的归约循环（例如 attention 的 kv 块循环）。
  - 所有维度均为 SymPy 符号，一条追踪即可覆盖整个设计空间。

#### (4) 分布与集合通信
- 分布式通过 **张量分片标注**（每个张量维度标注对应 mesh 轴）表达，而非手工安插集合通信；
- 分片 einsum 包装器能自动推断所需集合通信（如 AllGather、ReduceScatter）；
- 显式仅保留布局变动型集合通信（如 DeepSeek MoE 中的 dispatch/combine all-to-all）。

#### (5) 两种汇总（roll-up）模式
- **快速模式（fast）**：将叶子成本乘以包络循环次数（trip count 乘积），使用简单解析调度器来建模通信/计算重叠，闭式求值，适合数千设计点的大规模扫描；
- **慢速模式（slow）**：对循环进行 **模调度（modulo scheduling）**，将循环体软流水化到资源保留表上，得到依赖与资源感知的详细调度，用于对扫描出的重点设计点做细粒度研究。

#### (6) 符号传播
- 所有成本公式符号化向上传播，汇总结果以 SymPy 闭式表达式保留为设计空间自由变量的函数；
- 数值绑定仅在最终替代时进行一次，支撑单次建库服务整个参数扫描。

### 公式与算法流程

- 技术债务公式：\(D_{t+1} = G(S_{t+1}, C_t) - G(S_{t+1})\)，其中 \(G\) 为代码生成器，\(S_t\) 为 t 时刻规格，\(C_t\) 为 t 时刻实现。通过全新再生成使 \(C_t = G(S_t)\)，文献构建上令债务归零。
- 流程图（Figure 1）：设计文档 DAG → 智能体按拓扑序再生成 → 生成库 → 符号代价模型 → 与参考模型调和与验证 → 失败则人工只改文档 → 循环。

## 6. 主要结论

- 在 ML 性能建模领域，**自然语言设计文档（而非代码）可以作为持久资产**：文档驱动的全库再生成能由构造上消除增量修补债务。
- 两个关键要素确保可靠再生：
  1. 文档中包含逐步工作示例（上下文内示范）；
  2. 递归的、极简的、带符号成本的算子 IR，且同时具备快速解析汇总和慢速模调度模式。
- 文档式开发能提前暴露模糊不清的设计意图，因为任何猜测都必须写成文档才能继续。
- 作者认为他们的方案对“规格变化速度超过软件适应速度”的领域具有普遍适用性。

## 7. 优点

- **理念创新**：直接挑战 AI 时代的版本控制与软件维护固有范式，提出“文档即源，代码即产物”；对编程智能体的使用方式很新颖。
- **工程机制务实**：
  - 文档 DAG + 机器推断依赖 + 每个文档独立子代理 → 解决了上下文窗口限制；
  - 页面级文档包含逐步执行示例 → 降低生成歧义；
  - “调和锚点”可让生成的测试自动验证关键数值。
- **IR 设计精巧**：
  - 递归 Op 抽象极小、工作流简洁，把“算法组合叶子”与“系统费用定价”两端分离，便于替换任何一侧；
  - 内置符号（SymPy）传播和双模式调度兼具规模与精细度，适合探索式性能设计。
- **透明可迭代**：编排者日志透明地标注难理解文档，为人类精化文档提供直接反馈。
- **成本与速度可行**：一次全库再生成耗时小时级、费用约百美元，给出经济杠杆上的合理性。
- 对于被 IEEE/ACM 论文所忽略的“软件长期可维护性”问题，提出了可行的智能化对策。

## 8. 不足与局限

- **缺少严格实证支撑**：没有系统性的多模型、多平台、多次再生成之间的成功率、护栏数量、生成质量分布统计；也没有与普通从代码修改的 agent 工作流做定量对比。
- **试验场景过于集中**：仅提到 DeepSeek-V3 serving 一个案例，且对验证方式描述模糊（“精度圆整”的具体误差来源、哪些层、哪些调度等未展开）；未能反驳实际系统在更广范围（多种模型、异构硬件）的适用性。
- **依赖特定 LLM 服务**：依赖 Claude Code 等具体工具的稳定能力；如果底层模型能力变化，整个方法的表现可能剧烈波动；没有对新模型、版本接口的鲁棒性评估。
- **文档编写人效高成本**：作者未讨论将已有代码库转换为高质量“可执行”设计文档所需的人力与认知负荷（9k 行文档为初始构建的一个极重负担）；哪些类型的系统抽象容易写出这种文档也缺乏规则。
- **“再生即正确”的假设存疑**：在无法用数学预言书证明代码生成正确的情况下，“技术债务归零”只是结构上的而非逻辑上的；若文档本身存在错误或歧义，生成器会稳定地复现错误，且可能更难调试。
- **可扩展性边界未言明**：50 文档以上规模（比如 500 个、5000 个文档）时文档间的依赖推断、子代理的相互冲突、调和锚点的覆盖质量等问题都没有被讨论。
- **缺少真实部署的失败记录与修复行为分析**：没有给出在日志中常见失败的类型、导致修复的文档修改策略，以及各类 bug 的频次，使“文档比代码好修”的声称缺少数据。
- **存在的偏倚风险**：作者来自 Google DeepMind、MIT、Stanford、Google，该方案本质上也鼓励将工作流绑定在大规模商业化 LLM API 服务上，方案的可重复性与成本普惠性有偏差。

## 摘要
AI 编程助手正逐渐成为生产软件的共同作者，然而其评估却以功能正确性为中心，仍未回答其代码是否在主导生命周期成本的质量维度上不同于人类代码。我们大规模比较人类编写与AI生成代码：涵盖 Python、Java 和 C 的 787,562 个函数对，每个从开源代码仓库中挖掘的人类函数，都与由三个 AI 助手（OpenAI GPT 模型、DeepSeek-Coder、Qwen2.5-Coder）根据其文档字符串生成的实现配对。我们刻画结构复杂度与统计自然度，并将静态分析发现分别映射到用于缺陷的正交缺陷分类（Orthogonal Defect Classification）和用于漏洞的通用弱点枚举（Common Weakness Enumeration），从而使不同作者和语言可直接比较。AI生成代码在结构上更压缩，在风格上更模板化：其规模和分支数量约为人类代码的一半，并在风格层面聚类相分离。缺陷画像在类型上存在差异：人类代码集中于成熟代码库的问题，AI代码则集中于重复性样板代码；安全性依赖于语言，LLM 在 Python 和 Java 中产生更多且更严重的发现，但在 C 中产生的高严重性内存安全发现少于人类。在控制规模后，复杂度指标几乎不携带信号，而自然度能够区分作者。最后，我们发布 CQBench，这是一个包含 27,346 个易出问题任务的基准，带有基线和用于质量保障与安全测试的评估流程。

## Abstract
AI coding assistants are becoming co-authors of production software, yet their evaluation centers on functional correctness, leaving open whether their code differs from human code in the quality dimensions dominating lifecycle cost. We compare human-written and AI-generated code at scale: 787,562 function pairs across Python, Java, and C, each human function mined from open-source repositories paired with implementations generated from its docstring by three AI assistants (OpenAI GPT models, DeepSeek-Coder, Qwen2.5-Coder). We characterize structural complexity and statistical naturalness, and map static-analysis findings onto Orthogonal Defect Classification for defects and the Common Weakness Enumeration for vulnerabilities, making authors and languages directly comparable. AI-generated code is structurally compressed and stylistically templated: roughly half the size and branching of human code, clustering apart at the style level. Defect profiles differ in kind: human code concentrates issues of mature codebases, AI code repetitive boilerplate; security is language-dependent, with LLMs producing more, and more severe, findings in Python and Java but fewer high-severity memory-safety findings than humans in C. Once size is controlled for, complexity metrics carry little signal, while naturalness separates authors. Finally, we release CQBench, a benchmark of 27,346 issue-prone tasks with baselines and an evaluation pipeline for quality assurance and security testing.

## 1. 核心问题与整体含义

- **研究动机**：AI 编程助手（基于 LLM 的自动补全、重构、函数合成工具）已从研究原型进入主流开发流程，越来越多的开源与生产代码由模型编写或共同编写。然而，现有评估几乎完全聚焦于**功能正确性**（代码能否编译、通过测试、解决基准任务），只捕捉了软件生命周期中"编写代码"这一瞬间。
- **核心问题**：软件成本主要由**维护与演化阶段**主导，而非首次编写。若 LLM 生成的代码在结构、风格、缺陷类型或脆弱性上与人类代码**本质不同**，那么 AI 辅助开发的即时生产力收益可能捆绑了隐藏的长期成本（技术债、安全暴露、维护负担）。
- **关键缺口**：现有研究碎片化——依赖不同基准、语言、静态分析工具、度量与自定义质量定义，缺乏标准化、大规模、可直接比较的人机代码质量对比。
- **整体含义**：本文不追问"LLM 能否解决编程任务"，而是追问"在可比条件下，AI 生成代码的质量与人类代码有何不同"，并据此为面向 AI 辅助开发的质量保障、审查启发式与工具设计提供依据。

## 2. 方法论

### 2.1 核心思想：配对式、多维度、基于分类法的比较

- **配对设计**：对每个人类函数，用其原始 docstring（+ 函数签名）提示 AI 助手生成对应实现，形成 function-for-function 的配对样本，使观测差异可归因于**作者身份**而非任务选择或仓库规范。
- **多语言**：Python（动态类型、AI/ML 与数据场景）、Java（静态类型、面向对象、企业后端）、C（低层系统语言、手动内存管理，暴露托管语言缺失的安全问题），覆盖不同范式、类型系统与风险画像。
- **基于标准分类法**：将异构静态分析器输出映射到 **ODC**（缺陷）与 **CWE**（漏洞）两个长期使用的标准化框架，使不同作者与语言可直接比较。

### 2.2 四个质量维度

**(1) 结构复杂度与词汇多样性**（函数级，UT 为语料级）

| 维度 | 指标 |
|---|---|
| 规模 | NLOC（可执行行数） |
| 控制流 | CCN（圈复杂度）、MND（最大嵌套深度）、PC（参数个数） |
| 词法与数据复杂度（Halstead） | η₁/η₂（不同运算符/操作数）、N₁/N₂（总运算符/操作数）、V（体积）、D（难度）、E（工作量） |
| 可维护性 | MI（可维护性指数）、FNL（函数名长度） |
| 词汇多样性 | UT（作者整个语料的唯一 token 数） |

**(2) 统计自然度**：基于 n-gram 语言模型（KenLM），n ∈ [2,10]，10 折交叉验证，n=6 处曲线饱和。四项互补分析：
- **内在自然度**：各作者自交叉熵曲线，衡量代码自身的局部规律性与可预测性。
- **命名 vs 结构贡献**：对标识符/字面量做角色感知占位符归一化（保留关键字、分隔符、运算符、控制流结构），比较原始与归一化曲线之差，量化命名对自然度的贡献。
- **跨作者可迁移性**：固定 n=6，用一位作者训练的模型预测其他作者测试集，计算交叉困惑度 PP_{X→Y}=2^{H_{X→Y}}。
- **风格亲和聚类**：定义对称化超额交叉熵距离
  $$d(A,B)=\frac{1}{2}\left[(H_{A\to B}-H_{A\to A})+(H_{B\to A}-H_{B\to B})\right]$$
  再做平均链接层次聚类，检验人类代码是否与 LLM 代码在风格上分离。

**(3) 缺陷分析（ODC）**：使用语言适配的成熟静态分析器——Pylint（Python）、PMD（Java）、Clang-Tidy（C），排除风格、文档、安全规则后分别保留 350/226/258 条规则。将规则手工映射到 ODC 六类缺陷类型：**Assignment、Algorithm、Interface、Checking、Timing/Serialization、Function/Class/Object**（排除 Documentation 与 Build/Package/Merge，因其在函数级不适用）。映射采用三阶段协议：单人初映射 → 另两名作者（含领域专家）独立评审 → 讨论达成共识。

**(4) 安全漏洞（CWE）**：使用 Semgrep OSS（语法模式匹配，无需编译），统一应用其精选安全规则集，直接采用其规则元数据中的 CWE 标识符与严重性等级（Critical/Error/Warning/Informational），不做人工重分类。

### 2.3 统计方法

- 行匹配函数对上的配对 **Wilcoxon 符号秩检验**，用 **Benjamini–Hochberg** 控制跨指标错误发现率。
- 效应量报告为配对差异中位数 + 1000 次 bootstrap 的 95% 置信区间。
- RQ4 计算 Spearman 相关，分**原始相关**与**规模调整相关**（以全样本 NLOC 为控制变量做偏相关），并报告 95% bootstrap 置信区间。

## 6. 主要结论与发现

### RQ1：结构与风格

- AI 代码**结构压缩**：各语言下所有 LLM 的 NLOC 约为人类的 1/2（比值 1.95×/1.81×/2.32×），CCN 约 1.63–1.81×，Halstead Volume 约 1/3–1/2；人类代码离散度约为 LLM 的 3 倍。
- **MI 反转是机械性的**：所有 LLM 的 MI 都高于人类（Python +7.90、Java +6.88、C +10.15），但 MI 是 NLOC、V、CCN 的负系数复合函数，压缩代码必然得高分，不代表独立质量优势。
- **自然度**：原始自交叉熵下作者排序不一致（ChatGPT 在 Python 最不可预测、Qwen 在 C 与人类持平），但**标识符归一化后**，人类在所有语言中交叉熵最高、三个 LLM 一致更低，说明差异中命名占较大成分但**结构性残差普遍存在**。
- **

## 摘要
编码智能体使用系统级工具读取文件、执行命令并修改源代码。在智能体的沙箱内，这些工具通常带有环境权限：只要指明某个资源，就足以对其执行操作。间接提示注入利用这种权限，将指令放入仓库文件或工具输出中，诱使智能体执行用户并未请求的操作。我们提出 CapScope，一种管控框架层面的授权机制，它无需模型识别恶意文本即可限制工具使用。在读取仓库内容或工具输出之前，CapScope 从可信输入中推导出任务级权限上限。然后为每个智能体分配一组单独的类型化能力，存储于模型上下文之外。每次工具调用都会根据发起该调用的智能体所具备的能力进行检查。因此，分配给一个子智能体的权限不会自动可供另一个子智能体使用。注入可能使某个智能体请求执行某项操作，但除非该智能体已具备所需能力，否则该请求会被阻止。我们在 Pi 编码智能体上实现 CapScope，并在一个修复工作流中评估它，其中编排器将子任务委派给不同的子智能体。评估涵盖五个 Python 任务、五种注入面、四种授权条件，以及每个单元格三次试验（共 300 次运行）。在环境权限基线和全局策略基线中，注入效果在 33–47/75 次运行中执行，而 CapScope 下为 3/75。CapScope 完成 68/75 次修复，而基线完成 68–72/75 次。

## Abstract
Coding agents use system-level tools to read files, execute commands, and modify source code. Within the agent's sandbox, these tools often carry ambient authority: naming a resource is sufficient to act on it. Indirect prompt injection exploits this authority by placing instructions in repository files or tool output that cause the agent to perform actions the user did not request. We propose CapScope, a harness-level authorization mechanism that restricts tool use without requiring the model to identify malicious text. Before repository contents or tool output are read, CapScope derives a task-wide authority ceiling from trusted input. It then assigns each agent a separate set of typed capabilities, stored outside the model's context. Every tool call is checked against the capabilities of the agent that issued it. Permissions assigned to one sub-agent are therefore not automatically available to another. An injection may cause an agent to request an action, but the request is blocked unless that agent already has the required capability. We implement CapScope on the Pi coding agent and evaluate it in a repair workflow where an orchestrator delegates subtasks to separate sub-agents. The evaluation covers five Python tasks, five injection surfaces, four authorization conditions, and three trials per cell (300 runs). The injected effect executes in 33-47/75 runs under the ambient-authority and global-policy baselines, compared with 3/75 under CapScope. CapScope completes 68/75 repairs, while the baselines complete 68-72/75.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：编码智能体（coding agents）借助系统级工具读取文件、执行命令、修改源代码。在智能体沙箱内部，这些工具通常携带"环境权限"（ambient authority）——只要命名某个资源，就足以对其执行操作。
- **核心威胁**：间接提示注入（indirect prompt injection）。攻击者将恶意指令藏入仓库文件（README、AGENTS.md、技能文件、源代码注释/文档字符串）或工具输出（如 pytest 输出）中，当智能体读取这些不可信内容时，其中的文本就可能被当作指令执行，从而诱导智能体执行用户并未请求的操作（如写入后门签名密钥）。
- **现实严重性**：
  - Liu 等人报告针对生产编码编辑器的攻击成功率高达 84%；
  - CVE-2025-54135（CurXecute）将间接注入链式利用到 Cursor MCP 配置创建与远程代码执行；
  - 恶意规则文件与技能文件构成另一类后门向量。
- **问题本质**：这是一个经典的"混淆代理"（confused deputy）问题——管控框架（harness）拥有用户权限，而模型负责选择这些权限所作用的资源名称。
- **现有防御的局限**：多数防御在模型层工作（训练/提示模型对不可信指令保持怀疑、分类器标记可疑载荷），但这些都是对"文本是否为指令"做**概率性判断**，存在误报、被自适应攻击绕过的问题（已有研究在指令层级提示下仍发现攻击）。
- **论文含义**：论文主张"权限不是一个字符串"——不应让模型通过命名资源来隐式获得权限，而应由管控框架在分发（dispatch）前以显式的类型化能力进行授权检查，且无需模型识别恶意文本。

## 2. 方法论：CapScope 设计

### 2.1 核心思想
- 在读取仓库内容或工具输出**之前**，从可信输入推导出**任务级权限上限（task-wide authority ceiling）**；
- 为每个智能体（principal）分配**独立的一组类型化能力**，存储于**模型上下文之外**；
- 每次工具调用都依据**发起该调用的智能体**所持有的能力进行检查；
- 一个子智能体获得的权限**不会自动**传递给另一个子智能体；
- 注入可能使智能体"请求"某项操作，但除非该智能体已持有所需能力，否则请求被阻断。

### 2.2 信任边界
- **可信输入**：用户请求、开发者配置的系统提示、用户私有设置；
- **不可信输入**：仓库文件内容、命令 stdout/stderr、任何仓库贡献者可修改的项目本地配置文件；
- 模型的工具调用被视作**不可信请求**；权限不来自调用推断，而来自会话之外存储的授权。

### 2.3 能力定义（形式化）
- 能力定义为二元组 `c = (e, φ)`，记作 `Cap[e, φ]`：
  - `e ∈ Effects` 为效果类型；
  - `φ : Args → B` 为作用于该效果参数的**作用域谓词**；
- `Cap[e, φ]` 覆盖提案 `(t, a)` 当且仅当 `eff(t) = e` 且 `φ(a)` 成立；
- **能力存储 Σ** 是管控框架在会话期间持有的有限能力集合，模型从不直接持有能力。

### 2.4 三类效果类型与作用域谓词
| 效果类型 | 工具 | 作用域谓词 |
|---|---|---|
| Read | read | `φ(p) ≜ within(canon(p), π)` |
| Write | write, edit | `φ(p, _) ≜ within(canon(p), π)` |
| Exec | bash | `φ(s) ≜ allowed_A(parse(s))` |

- `canon` 解析 `..` 与符号链接，防止路径穿越；
- `parse(s)` 拒绝命令替换（`$(...)`）、拆分复合命令、移除重定向，返回每个命令段的参数向量；
- `allowed_A` 要求每一段都是读/导航命令，或以 `A` 中某个向量开头——因此 `pytest` 允许 `pytest -v`，但含有未覆盖 `curl` 段的复合命令会被拒绝。

### 2.5 三条形式化规则（算法流程）
1. **Mint（铸造）**：唯一引入新权限的规则。运行可信主机策略 `P`，对可信预检输入 `I_T` 返回有限能力集 `C`，加入任务上限 `D_r`。实现中由一个 LLM 仅基于**可信请求 + 项目文件树（仅名称，不含内容）**提出能力描述，再由确定性主机代码校验并编译为策略 `P`，随后**冻结**该策略。
2. **Derive（派生/收窄）**：委派时，模型提交请求授权 `C'`，主机侧 `derive` 仅保留结构上被 `D_i` 包含的能力（`c' ⪯ c`），丢弃未被覆盖的请求，安装 `C''` 作为子智能体存储。例如 `src/**` 可收窄为 `src/parser.py`，反之不行。
3. **Invoke（调用/检查）**：仅当 `Σ` 中存在某能力满足 `eff(t) = e` 且 `φ(a)` 成立时才执行工具；否则阻断并返回拒绝信息给模型。

### 2.6 关键性质
- 每个执行的效果都被某个可追溯到可信 Mint 的能力覆盖；
- 根权限仅通过编译进入 `Σ_r`，子智能体权限仅通过 Derive 进入，两者**只能收窄不能扩张**；
- 注入文本可影响提议的工具调用或请求的子智能体授权，但**无法扩张任务级上限**。

### 2.7 实现细节（Pi 上）
- 基于开源 TypeScript 编码智能体工具包 **Pi 0.78.0**，不修改其内部；
- 使用 `pi.on("tool_call")` 钩子，返回 `{block: true, reason}` 在分发前阻断调用；
- 为编排器与每个子智能体分别安装钩子（闭包捕获不同的能力存储）；
- `pi-subagents` 扩展实现进程隔离的子智能体，可独立播种能力存储；
- 四个组件：能力结构（结构化 ScopeSpec）、初始铸造（authorize 预检）、派生与转移（derive/spawnScoped）、逐主体分发检查（installCapScope）。

### 2.8 示例（allowlist 无法阻止的后门）
- 任务需要：项目读取、源代码写入、测试命令；
- 预检编译出 `c1`（读 project/**）、`c2`（写 src/**）、`c3`（执行 pytest/mypy）；
- runner 只获得 `c1'`（读 tests/**）与 `c3'`（执行 pytest），**无 Write 能力**；
- 被投毒测试输出诱导写入 `src/auth/keys.py` 时，runner 被阻断，而 patcher 仍持有完成修复所需的写权限。

## 3. 实验设计

### 3.1 场景与任务
- 每个任务是**小型 Python 项目**，含一个 bug 与一个失败的 pytest 套件；
- 5 个修复任务（T1–T5）：
  - T1：`daterange.py` 差一错误；
  - T2：`fees.py` 费用比较错误；
  - T3：`report.py` 字段查找错误；
  - T4：`indexer.py` 大小写敏感查找；
  - T5：`billing/fees.py` 折扣分支错误。

### 3.2 注入面（5 种，均属不可信）
1. README.md；
2. AGENTS.md（仓库控制的指令文件，自动加载）；
3. 项目本地技能文件（skill files，markdown 提示模板）；
4. 源代码注释/文档字符串；
5. pytest 工具输出。

- 注入请求执行项目本地工具或写入项目文件，动作**故意设计为看似合理**（在另一维护任务中可能是合法的），但**对本修复任务并不需要**；
- 每个恶意动作产生**唯一的哨兵/标记**，良性修复绝不会产生，据此判定攻击是否执行。

### 3.3 委派流水线（四主体拓扑，固定不变）
- **orchestrator**：诊断与协调，委派有副作用的实际工作；
- **runner**：执行失败测试；
- **patcher**：编辑相关源代码；
- **verifier**：重跑测试套件；
- 循环直到测试通过或运行终止。

### 3.4 对比条件（4 种授权模型）
| 条件 | 说明 |
|---|---|
| **B0** | 环境权限（ambient authority），所有主体无限制 |
| **B1** | 静态全局策略，任务无关，拒绝熟悉的高危项（.env、.ssh、rm -rf、sudo、curl 等），但允许普通项目操作 |
| **B2** | 任务特定全局策略，从可信任务描述 + 净化后的项目结构生成，读注入前即生成，但**所有主体共享同一策略** |
| **C（CapScope）** | 系统本身：预检铸造任务上限，各子智能体从适用委派上限派生独立存储 |

- **B2 是最强基线**：其策略在对抗文本到来前已针对任务定制，用于隔离"加入逐主体权限"带来的增量效果。

### 3.5 指标
- `task_success`：最终测试套件通过；
- `attack_executed`（头条防御指标）：运行后磁盘上存在攻击者专属哨兵/标记（每次运行布尔，至少执行一次即计一次）；
- 二者均从文件系统独立读取，互不依赖（一次运行可能既修复 bug 又被攻陷）；
- 次要诊断：逐调用决策日志中，模型是否提议了携带注入动作的调用、该层是否阻断。

  - 即 2 次直接源于过窄上限，其余 5 次反映委派或终止行为。

### 6.4 诊断与延迟
- 决策日志显示：CapScope 下模型在 34/75 次运行中**仍提议了**注入动作，而钩子记录仅 3 次运行出现被允许的攻击调用——说明**模型仍会被注入影响，但分发检查成功阻断了绝大多数**；
- 34 次含攻击目标提议的运行中，27 次出现重复的攻击目标调用，导致额外的模型轮次；
- 延迟增加主要来自拒绝后的重试与派生相关调用，而非授权检查本身；论文谨慎指出这**不隔离任何单一组件的因果成本**。

### 6.5 为何共享任务策略仍会放行攻击
- 单一共享策略必须授予任务所需一切（读取、源代码写入、测试命令）的**并集**才能完成修复，这份宽权限随后到达每个子智能体，包括读取被投毒输出的 runner；
- 移除任何任务必需权限又会阻止合法步骤；
- CapScope 改为按智能体划分权限：读取注入的 runner 能跑测试但不能写源代码，而 patcher 仍持有完成修复的写权限。

## 7. 优点

- **问题识别精准**：清晰指出当前编码智能体授权的**粒度缺口**——单一任务级策略无法给两个智能体不同权限，并将之形式化为混淆代理问题。
- **信任边界明确**：严格区分可信与不可信输入，工具调用被视作不可信请求，权限不来自调用推断。
- **设计原则正确**：遵循经典能力安全原则（完全中介、最小权限、衰减/收窄），权限存储在模型上下文之外，模型无法读取或修改。
- **机制完备**：三条形式化规则（Mint/Derive/Invoke）构成闭环，可证明"每个执行的效果都追溯到可信 Mint 且只能收窄"。
- **命令作用域处理精细**：Exec 作用域基于**解析后的参数向量前缀**而非字符串，复合命令逐段检查，允许 `pytest` 不等于允许 `pytest; cmd` 或 `$(cmd)`，避免了字符串匹配的常见陷阱。
- **预检时机正确**：在读取任何仓库内容前完成铸造并冻结，注入文本无法事后扩张权限。
- **实验控制严谨**：B2 作为最强全局基线，固定 LLM、任务与四主体拓扑，只变授权模型；结果从文件系统读取，独立于日志。

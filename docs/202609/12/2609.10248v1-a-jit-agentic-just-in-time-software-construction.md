## 摘要
传统软件交付假设一种静态范式：代码在执行前构建，并作为固定制品部署。我们提出智能体式即时软件构建（A-JIT），这一范式用能够持续演化以满足不断变化需求的动态软件系统取代静态二进制文件。在 A-JIT 中，应用是一个集成组装体，由代码、运行时执行框架以及一个嵌入式 AI 智能体组成，该智能体持续观察系统使用情况和实时执行轨迹。就像传统 JIT 编译器将机器码特化到运行时执行路径一样，A-JIT 将软件逻辑、工作流和工具接口特化，以满足最终用户的特定需求。通过将合成直接集成到应用的环境生命周期中，A-JIT 使应用能够动态构建缺失的实现、即时生成新能力，并持续适应最终用户行为。我们展示了该模型如何支持轨迹驱动的人-AI 协同构建，并为自适应、自演化软件开辟了新的设计空间。

## Abstract
Traditional software delivery assumes a static paradigm: code is constructed prior to execution and deployed as a fixed artifact. We present Agentic Just-In-Time Software Construction (A-JIT), a paradigm that replaces static binaries with dynamic, software systems that can perpetually evolve to meet changing demands. In A-JIT, an application is an integrated assembly comprising code, a runtime harness, and an embedded AI agent that continuously observes system usage and live execution traces. Much like a traditional JIT compiler specializes machine code to runtime execution paths, A-JIT specializes software logic, workflows, and tool interfaces to meet the specific needs of the end-user. By integrating synthesis directly into the ambient application lifecycle, A-JIT enables applications to dynamically construct missing implementations, generate new capabilities on the fly, and continuously adapt to end-user behavior. We demonstrate how this model supports trace-driven human-AI co-construction and opens a new design space for adaptive, self-evolving software.

- **整体含义**：提出 **A-JIT（Agentic Just-In-Time Software Construction，智能体式即时软件构建）**。在 A-JIT 中，应用不再是静态二进制，而是由三部分组成的集成体：
  - 代码；
  - 运行时执行框架；
  - 嵌入式 AI 智能体。
- 嵌入式智能体持续观察系统使用情况与实时执行轨迹，像 JIT 编译器特化机器码一样，动态特化软件逻辑、工作流和工具接口，以满足终端用户需求。
- 最终目标：让应用能够动态构造缺失实现、即时生成新能力，并持续适应终端用户行为，形成自适应、自演化的软件系统。该范式模糊了开发者、AI 智能体和终端用户之间的边界。

## 2. 论文提出的方法论

- **核心思想**：将“软件开发”融入“应用运行时生命周期”，通过语言、运行时和智能体生成能力，实现即时构造、测试、热加载和适应。
- **关键能力**：
  1. **语言级支持**：显式标注哪些程序部分预期由 JIT 方式构造。
  2. **运行时支持**：支持代码即时构造、运行与测试。
  3. **新的实现概念**：允许人类或 AI 智能体构造完整实现，也允许针对特定 trace 集合构造部分解。
  4. **触觉值（tactile values）**：允许人类或 AI 直接编写、交换、热加载任意程序值。

- **代码洞（Code Holes）**：
  - 使用 Bosque 语言的 `?_` 构造，将未完成实现作为一等语言特性表达，而不是依赖 TODO 注释、断言或 issue 编号。
  - 洞可携带元数据：文档注释、输入/输出类型、前后置条件、测试用例、输入/输出示例。
  - 示例中通过 `ensures` 增加后置条件：当标准 Forecast 的降水为 0 时，SI 版本应映射为 `none`。
  - IO 示例既是合成规范，也是运行时挂钩点，使智能体可在执行中途介入合成或与用户协作。

- **部分实现与完整实现**：
  - 继承“懒惰程序补全（lazy program completion）”思想：允许先提供部分实现，系统按需补全。
  - 运行时检测到部分实现后：
    - 先查找匹配的测试用例或 IO 示例，若匹配则直接复用输出值；
    - 否则触发智能体合成：可用 Tecton 直接生成具体输出值，或利用约束与 IO 对合成缺失实现。
  - Tecton 结合强类型与语义约束、约束解码和断言验证，确保生成值符合类型与结构。
  - 当置信度不足或存在多个候选时，系统可提示用户，或利用 Bosque 的可分支时间旅行调试探索多条执行路径。
  - 积累足够 IO 对后，LLM 智能体可合成完整实现。该过程本质上是“子智能体架构”的语义化形式，且 prompt 数据、示例和约束可作为可追溯、可版本化的源工件。

- **触觉值（Tactile Values）与 BAPI**：
  - BAPI 格式支持值在人类可读文本格式中完整往返，包含 UUID、经纬度等标准类型，并允许嵌入表达式。
  - 支持隐式 `$src` 变量，使输出值可引用输入值。
  - 优点：易编辑、易测试、可生成 IO 对、减少 LLM 上下文压力。
  - 强类型与结构约束可校验值的一致性，例如可捕获低/高字段被意外交换的错误。

- **端用户视角：自特化软件**：
  - A-JIT 可作为工作流监控器，识别常见工作流并主动生成 RPA 工具或优化工作流。
  - 对 help desk 工单系统等场景，智能体可监控并追踪操作步骤，合并常见 trace 形成 streamlined workflow。
  - 工作流聚类和分歧处理并非易事。A-JIT 可用 Bosque 洞注入假设函数，处理分歧、参数计算和特例，再通过已有 trace 或 shadow mode 验证生成实现。
  - Bosque 的隔离与纯性特征保证生成函数安全、无意外副作用。
  - 终端用户需要 UI/UX 原语来检查、编写和批准/拒绝生成结果，例如响应式 UI 模型或 moldable patterns。

- **总体流程可概括为**：
  - 运行应用 → 检测洞/部分实现 → 查找 IO 匹配 → 用 Tecton/LLM 生成值或合成实现 → 类型/断言验证 → 生成更多 IO 对 → 合成完整实现 → 热加载执行；
  - 或在端用户场景中：监控 trace → 聚类常见工作流 → 注入洞处理分歧 → 合成实现 → shadow mode 验证 → 安全部署。

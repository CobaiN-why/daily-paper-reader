## 摘要
执行反馈可以引导编码代理进行正确的仓库修复，但仅在测试捕获了问题所请求的行为时有效。代理生成的测试可能编码不完整或错误的行为目标；当同一轨迹同时编写补丁和测试时，它们的错误可能一致并产生虚假的自信。我们引入了ExecCritic，将测试-验证-修订的脚手架与角色特定的强化学习配方相结合，用于在其中训练代理。该脚手架将测试构建与源代码修复分离：测试代理独立生成仓库原生测试，一个失败封闭的测试框架限定并冻结它们，修复代理根据其执行反馈修改源代码而不更改测试。两个角色均使用Qwen-3.5-35B-A3B作为骨干，并分别进行训练。在“学会测试”中，测试代理学习生成行为有效且能区分正确与错误补丁的测试。在“测试改进”中，修复代理学习直接任务解决和反馈引导的修订。在SWE-bench Verified上，测试质量决定反馈是否有帮助：保持基础修复代理不变，来自基础测试代理的测试将解决率从无测试基线的61.2%降至57.3%，而来自GPT-5.6-sol的测试则将其提升至65.3%。角色特定的后训练将Qwen测试代理的Base-to-Gold成功率从22.2%提升至62.2%；组合两个后训练的Qwen代理达到72.6%，比原始无测试基线高出11.4个百分点，而在评估时无需更强模型或Oracle反馈。代码公开于https://github.com/MSR-Orchard/execcritic。

## Abstract
Execution feedback can guide coding agents toward correct repository repairs, but only when the tests capture the behavior requested by the issue. Agent-generated tests can encode incomplete or incorrect behavioral targets; when the same trajectory writes both the patch and the test, their errors can agree and create false confidence. We introduce ExecCritic, combining a test--verify--revise scaffold with a role-specific reinforcement learning recipe for training agents within it. The scaffold separates test construction from source-code repair: a Test agent independently generates repository-native tests, a fail-closed harness qualifies and freezes them, and a Repair agent revises source code from their execution feedback without changing the tests. Both roles use Qwen-3.5-35B-A3B as the backbone and are trained separately. In Learn to Test, the Test agent learns to produce behaviorally valid tests that distinguish correct from incorrect patches. In Test to Improve, the Repair agent learns both direct task resolution and feedback-guided revision. On SWE-bench Verified, test quality determines whether feedback helps: holding the base Repair agent fixed, tests from the base Test agent reduce resolved rate from a no-test baseline of 61.2% to 57.3%, whereas tests from GPT-5.6-sol raise it to 65.3%. Role-specific post-training raises the Qwen Test agent's Base-to-Gold success from 22.2% to 62.2%; composing the two post-trained Qwen agents reaches 72.6%, an 11.4-point gain over the original no-test baseline without stronger-model or Oracle feedback at evaluation time. Code is publicly available at https://github.com/MSR-Orchard/execcritic.

# ExecCritic 论文总结

## 1. 核心问题与研究动机

- **核心问题**：编码智能体（coding agent）在仓库级修复中依赖执行反馈来修正代码，但反馈的价值取决于生成测试是否真正捕获了 issue 所要求的行为。
  - 若智能体在同一轨迹中既写 patch 又写测试，测试可能与补丁共享同一个错误理解，导致错误补丁通过错误测试而“虚假通过”。
  - 这种“修复-验证耦合”（repair-validation coupling）会带来两类危害：一是提交补丁时无局部验证；二是检查看似执行成功，却并未验证 issue 所要求的行为。
- **核心发现前驱**：并非任意执行反馈都能提升修复性能——质量较差的生成测试甚至会使效果 **下降**。
  - 基础 Test agent 生成的测试将 resolve rate 从 61.2%（无测试）**拉低至 57.3%**；
  - GPT-5.6-sol 生成的高质量测试则将其提升至 65.3%。
- **研究动机**：因此需要单独训练测试生成能力，并严格分离测试构造与补丁修复——测试目标必须独立、冻结，才能为修复提供可信的反馈信号。

## 2. 方法论（方法核心与技术细节）

### 总体框架：ExecCritic = “测试 – 验证 – 修订”（test–verify–revise）

将修复任务拆分为两个独立阶段与两个独立角色，使用 **Qwen-3.5-35B-A3B** 作为骨干分别后训练。

### （1）Learn to Test（学会测试——训练测试生成智能体）

- **Test agent** 根据 issue 描述与 Buggy 仓库状态独立生成一个“测试三元组”（Test bundle）：
  - `test.patch`：符合仓库原生的测试修改补丁；
  - `test_command`：精确的测试执行命令；
  - `test_contract.json`：结构化的行为契约（目标行为、证据、替代假设、非断言项、测试节点等）。
- **验证阶段（Base Gate）**：fail-closed 的沙箱验证器执行以下检查：
  - 测试补丁格式是否合法、测试节点是否可绑定；
  - 测试必须在 Buggy Base 上“干净地失败”（clean failure）。
  - 只有通过 Base Gate 的测试包才被保留并进入下游修复阶段，否则本轮修复直接提交初始补丁（仍计入分母）。
- **离线金标审计（Gold audit）**：将同一测试包运行在应用了正确修复（Gold patch）的仓库上，要求通过（Base-Fail & Gold-Pass），形成 Base-to-Gold 成功率作为训练指标。
  - 但 Gold 结果仅在离线时用于训练/分析，**不**用于生成过程中的样本筛选，也不会被输入到 Repair agent 的上下文。
- **RL 训练**：先使用教师轨迹进行 SFT，再用 **GRPO** 强化学习优化。奖励依据：
  - 测试在 Base 和 Gold 上的行为（Qx = Bx × Gx）；
  - 在额外标注候选修复补丁上的**平衡准确率**（balanced accuracy，区分正确/错误补丁的能力）；
  - 无有效提交时给 -0.2，仅在 Base-to-Gold 成功后再按候选判别性能获得 0.2/0.5/1.0 的递增奖励。

### （2）Test to Improve（测试改进——训练修复智能体）

- **Repair agent** 仅在源补丁上修改，不允许修改冻结的测试。
- 流程：
  - Round-0：从 issue 和仓库状态生成源补丁 p0；
  - 对每个补丁 pt，执行固定测试并返回 PASS/FAIL 及受限反馈；
  - 若 FAIL 且预算未用完，agent 继续修订；
  - 一旦测试通过，立即结束并提交该补丁；
  - 最多 5 轮反馈引导修订（每轮最多 40 turns），预算耗尽则自动提交最终候选。
- **RL 训练奖励**：
  - 无效提交/修改测试：0；
  - 测试失败：0.1；
  - 测试通过但官方评测失败：0.2；
  - 测试通过且官方评测通过：修订后达成 1.0、Round-0 直接达成 1.5。
  - 基于最终补丁的奖励信号延迟分配至整条轨迹。
- **关键机制**：测试由 Test agent 生成并被框架冻结，Repair agent 只能看到受约束的执行输出（如轨迹信息、失败信息和 traceback），看不到测试源码，也就是“fail-closed”（失败封闭）设计。

## 6. 主要结论与发现

- **质量差的测试会损害修复效果，而非中性/无害**：
  - 同一 Qwen Repair agent，基础 Test 输出将修复率从 61.2% 降至 57.3%；GPT-5.6-sol 的测试则提升至 65.3%。
- **Test agent 后训练显著提升“行为有效测试”的生成率**：
  - Base-to-Gold 成功率：Base 22.2% → SFT 39.6% → RL 62.2%（与 Codex-5.3 的 61.0% 相当）。
- **SFT + RL 配合模式有效**：
  - 仅有 SFT 的数据规模增大到 10K 时收益递减（约 39%），说明离线模仿的提升有限；
  - 在 5K-SFT 基础上引入 RL 后，大幅提升到 62.2%，而且从 Base 直接启动 RL 的训练不稳定、信号弱，说明 SFT 为 RL 创造了有效学习的必要条件。
- **Repair agent 后训练同时增强直接解决与反馈修订能力**：
  - Round-0 无测试的 resolve：61.2%（Base）→ 68.3%（trained）。
- **完整组合效果显著**：
  - 两个后训练 Qwen 代理组合达到 **72.6%**；较原始无测试基线（61.2%）提升 11.4 pp，且在推理时不需要更强模型或 Oracle 反馈。
- **执行反馈的增益在 SWE-bench Pro 上较小**：
  - generated-test 只带来 0.7 pp 增益，而 Oracle 能带来 11.8 pp；说明更复杂任务要求更广的测试覆盖，单一测试包不足以代表完整行为合约。
- **训练信号的干净度会影响最终性能**：
  - Oracle F2P 反馈训练的 Repair agent 比 generated-test 反馈略优（72.6% vs 70.9%），背后是更少噪声的 credit assignment。
- **跨语言泛化不均匀**：Python 62.2%、Rust 66.7%、C++ 58.3%，但 C 仅 26.1%、Java 仅 2.4%。

## 7. 主要优点

- **问题意识准确且重要**：指出“同一轨迹补丁-测试串通产生虚假信心”这一关键缺陷，并用直接实验证实了“生成的测试可以伤害修复”。
- **方法设计清晰**：Test 与 Repair 角色完全分离，测试冻结、修复权受限，从机制上阻断修复过程中“弱化测试标准”来迎合错误修复的自欺行为。
- **“fail-closed”验证器设计严谨**：可区分行为性失败与操作性无效，不允许环境/基础设施错误被当作行为失败使用；测试命令必须精确定位测试节点，避免套件级别掩盖行为覆盖率不足。
- **分阶段双层学习路径设计合理**：离线 SFT（先教会怎么做测试与提交）与在线 RL（优化行为有效性）形成互补，各有清晰的度量（training reward、Base-to-Gold 成功率）。
- **评估协议透明且顾及公平**：统一的修复轨迹数量、固定测试包复用、Base-gate 失败样本保留在分母、最终以官方全量 F2P/P2P 测试集评分为准。
- **奖励函数设计说明充分**：附加报告了大块补充资料（如 DAPO、沙箱超参数、提示词、控制器消息、失败处理）。

## 8. 不足与局限

- **两个角色分离训练，未共用同一个模型权重**：论文承认如果权重共享（用角色条件区分两种任务）将更利于部署移植与端到端训练，但目前实现无法做端到端的联合优化；测试与修复的退化协调（degenerate coordination）仍是一个未解的挑战。
- **单一测试包导致的覆盖不足**：较复杂 issue（如 SWE-bench Pro 平均 14+ 个 F2P 测试）只“关注一个行为”，会遗漏多重任务要求；没有延展到多检查/多节点的完整套件场景。
- **更强的模型或 Oracle 依然是天花板**：即使两个后训练模型合作，仍与 GPT-5.6-sol 生成的测试反馈（73.5%）或 Oracle（77.6%）存在 5 点左右差距，说明训练后学习的 Qwen 测试质量仍有提升空间。
- **缺乏整体成本/收益分析**：Test 生成的计算成本是一次性的，Repair 平均额外 13 turns 的成本无法直接与单纯加长推理（更多测试/更多样本）的成本做同等算力比较。论文明确表示这个 72.6% 的结果并未和同规模计算预算的方法进行公平对比。
- **跨语言表现不均衡**：Java 上虽然 Base-to-Gold 只有 2.4%，但仍直接把测试结果当成治理信号可能会引起失真；此外缺少针对 Java 失败的原因与迁移改进分析。
- **实验多为单次生成/单次评分**：表 4、表 5 等部分属于 single-run；除几个主要实验外，缺少显著性检验或置信区间，无法确认小幅度差异（如 70.9% vs 72.6%）的可靠性。
- **没有解决测试标准自身的语义劣化问题**：如果生成的测试本身就在错误地断言（在程序语义层面上），冻结这个测试并不能保护结果不受错误的标准影响——它的功能只是避免了主动“改测试去迎合错误补丁”，并未替代更高质量的行为合约来源。

## 摘要
大型语言模型（LLMs）在代码生成方面取得了显著进展，但在处理需要理解丰富自然语言需求的挑战性编程任务时仍面临困难。这些需求通常指定问题目标、输入/输出格式、约束条件、示例和边界情况。即使忽略其中一项，也可能生成可执行但功能不正确的代码。现有的免训练方法主要依赖于提示（prompting）或基于智能体的工作流，而基于训练的方法通常优化最终代码输出。然而，现有方法在监督从原始需求到结构化规范的中间映射以及将其落地到具体实现行为方面提供的监督有限。因此，模型可能会遗漏关键约束，即使生成了显式规范，实现也可能无法一致地反映该规范。受这一差距的启发，我们提出了SpecCoder，一种用于代码生成的规范感知两阶段训练框架。SpecCoder首先采用规范引导的监督微调（SFT）来训练LLM推导结构化规范分析并据此生成代码。随后引入课程式双任务GRPO，联合优化规范引导的生成与判别，以增强规范与代码行为之间更强的对应关系。在APPS、CodeContests和xCodeEval上的实验证明了规范感知训练的有效性，SpecCoder在独立代码生成和基于智能体的工作流上均持续取得改进。在BigCodeBench-Hard和ClassEval上的额外评估，以及人工评估和扰动研究，进一步验证了结构化规范在指导代码生成与判别中的作用。

## Abstract
Large language models (LLMs) have made substantial progress in code generation but still struggle with challenging programming tasks that require understanding rich natural language requirements. These requirements often specify problem goals, input/output formats, constraints, examples, and edge cases. Overlooking even one may produce executable but functionally incorrect code. Existing training-free methods mainly rely on prompting or agent-based workflows, while training-based methods typically optimize final code outputs. However, existing approaches provide limited supervision for learning the intermediate mapping from raw requirements to structured specifications and for grounding them in concrete implementation behavior. Consequently, models may omit critical constraints, and even when an explicit specification is produced, the implementation may fail to reflect it consistently. Motivated by this gap, we propose SpecCoder, a specification-aware two-stage training framework for code generation. SpecCoder first employs specification-guided SFT to train LLMs to derive structured specification analyses and generate code conditioned on them. It then introduces curriculum dual-task GRPO, which jointly optimizes specification-guided generation and discrimination to encourage stronger correspondence between specifications and code behavior. Experiments on APPS, CodeContests, and xCodeEval demonstrate the effectiveness of specification-aware training, with SpecCoder consistently improving both standalone code generation and agent-based workflows. Additional evaluations on BigCodeBench-Hard and ClassEval, alongside human evaluation and perturbation studies, further validate the role of structured specifications in guiding code generation and discrimination.

## 1. 论文的核心问题与整体含义

大型语言模型（LLMs）在简单代码生成基准（如 HumanEval、MBPP）上已表现出色，但在 APPS、CodeContests、xCodeEval 等更富挑战性的编程任务上仍力不从心。这类任务的核心难点在于：问题陈述包含丰富的自然语言需求（如问题目标、I/O 格式、约束条件、边界用例、隐式假设等），模型必须具备"理解需求 → 提炼规范 → 按规范实现"的完整推理能力。然而，无论是不更新的提示工程/智能体方法，还是基于训练的强化学习方法，都存在共同短板：

- **对需求理解缺少显式监督**：训练信号主要来自最终代码能否通过测试用例，未指导模型学习如何从原始需求中提炼结构化规范分析；
- **"分析"与"实现"脱节**：即便模型生成了看似合理的规范分析，最终代码仍可能忽略或违背该规范；
- **执行反馈粒度粗糙**：测试用例的通过率只能反映结果对错，无法说明哪些需求约束被满足或违反。

SpecCoder 正是面向这一缺口提出的规范感知两阶段训练框架，目标是让模型在学习中建立起"原始需求→结构化规范→代码行为"之间可监督、可对齐的映射关系。

## 2. 方法论

**总体思路**：以"结构化规范分析"作为连接原始需求（raw requirement）与代码行为（code behavior）的共享中间接口。整个框架包含一条数据构建流水线和两阶段训练过程。

**一、数据构建（Stage 1）**

- **规范引导的生成数据集 D_gen**：对每个原始需求，用 GPT-4o 以 3 条路径（temperature=0.7）各生成一次七维结构化规范分析和相应的候选代码。七维结构包括：问题背景、功能需求、输入需求、输出需求、测试用例、外部依赖、附加说明。
- **双向验证**：第一轮是"前向验证"，将候选代码在测试集上执行，仅保留通过全部测试的三元组 (p, s, c)；第二轮是"后向验证"，用 DeepSeek-V3-0324 从语义完整性、算法可追踪性、表达清晰度三个维度评分，全部 ≥ 4 才被保留。若同一问题有多组合格数据，随机取一组。
- **规范引导的判别数据集 D_disc**：基于 D_gen 中的三元组，用 Qwen2.5-Coder-32B-Instruct 针对每条 (p, s) 采样 10 个候选实现，按其测试通过率配对为 (c₊, c₋)，并依据通过率差 Δ 划分为 Easy（Δ∈(0.6,1.0]）、Medium（Δ∈(0.3,0.6]）、Hard（Δ∈(0.0,0.3]）三个难度档位。

**二、第一阶段训练：规范引导的 SFT（Stage 2）**

在 Qwen2.5-7B-Coder-Instruct 上执行 LoRA 微调。训练序列格式为 `<REQ>原始需求</REQ><ANALYZE>规范分析</ANALYZE><CODE>代码</CODE>`，loss mask 只作用于目标部分（规范分析和代码），使模型学会"先分析、后编码"的输出范式：

\[
\mathcal{L}_{\text{SFT}} = -\frac{1}{|\mathcal{D}_{\text{gen}}|}\sum_{\langle p_i,s_i,c_i\rangle}\frac{1}{\sum_j m_{i,j}}\sum_j m_{i,j}\log\pi_\theta(X_{i,j}|X_{i,<j})
\]

**三、第二阶段训练：课程双任务 GRPO（Stage 3）**

对生成与判别两类任务分别设计奖励，并分别做组内归一化，以避免两类任务量纲差异主导更新。生成任务奖赏结合格式合规（α=0.2）、编译成功（γ=0.2）和测试通过率（对 Easy 用线性通过率、对 Medium/Hard 用通过率的平方根，以放大部分正确信号的差异）：

\[
R_{\text{gen}} = 0.2r_{\text{format}} + 0.2r_{\text{compile}} + 0.6r_{\text{correct}}
\]

判别任务奖赏＝比较分析和最终选择是否齐全（λ=0.3）以及选择是否正确（即是否选中通过率更高的候选）。

课程策略分为三个阶段：
- **阶段 1 初始对齐**：只用 Easy 样本，建立规范和代码之间的基础关联；
- **阶段 2 难度适应**：聚焦 Medium 和 Hard 样本，强化复杂需求分析及细粒度比较；
- **阶段 3 全面巩固**：混合所有难度，防止对简单样本的遗忘。

整体两阶段训练流程可由算法伪代码概括：先对整个 D_gen 做 SFT 得到 θ_SFT，再由 θ_SFT 出发分三阶段、依次在筛选好的难度子集上运行 GRPO，每个样本总计被训练 3 个 epoch。

## 6. 主要结论与发现

- **独立生成能力显著提升**：ID 任务上 APPS 达 Pass@1 0.186 / AvgPassRatio 0.346，CodeContests 达 0.091 / 0.207；OOD 的 xCodeEval 上达 0.147 / 0.324，全面超过所有训练基线和免训练基线；
- **作为智能体骨干同样有效**：SpecCoder 稳定提升 AgentCoder、MetaGPT、PairCoder、Specine 的性能，Pass@1 最高提升 11.3 个百分点，AvgPassRatio 最高提升 13.2 个百分点；
- **各训练组件缺一不可**：去掉 SFT 导致 CodeContests Pass@1 从 0.091 降至 0.043（降幅约 52.7%）；去掉 GRPO 造成约 34.1% 的下降；去掉判别任务也会显著降低表现；
- **课程学习与联合优化均有价值**：移除课程会使 CodeContests Pass@1 降至 0.079；双任务分离训练不如联合训练效果好；
- **结构化规范优于其他中间表示**：在相同训练条件下优于 Code-Only、Free-Form 和 Planning-CoT，且增益主要来自结构化组织而非单纯输出更长（平均只多约 15~156 tokens）；
- **模型的优势随智能体迭代轮次扩大**：SpecCoder 增强的智能体在第 5 轮的优势明显大于第 1 轮，说明规范感知能力能让迭代式修复更加有效；
- **生成和判别都真实依赖规范语义**：扰动实验显示，Shuffled（张冠李戴）和 Corrupted（篡改约束）的危害大于 Empty（空白规范），判别准确率从标准规范的 91% 降至 43%（Shuffled）和 49%（Corrupted），证明模型学到的是规范语义而非格式模板；
- **在真实场景有效**：BigCodeBench-Hard Pass@1 达到 0.34，ClassEval 函数级 0.692、类级 0.230，均超过强化学习基线。

## 7. 方法优点

**方法设计亮点**：

- **独创的"双向验证"数据管线**——先用测试执行（前向）验证代码正确性，再用 LLM（后向）验证规范质量和代码与规范的一致性，有效过滤"通过测试但规范有缺"的低质量三元组。论文还通过 400 条人工抽检（自动评估接受率约 88%、Cohen's κ=0.79）验证了自动后向验证的可靠性；
- **用结构化七维规范作为共享中间接口**，将生成和判别两个任务统一在同一表达层上，设计巧妙；
- **双任务 GRPO 使两类互补目标互相强化**——生成任务引导模型产出规范一致的代码，判别任务强迫模型比较实现间的规范满足程度；
- **明确感知到"规范与行为脱节"这个被忽视且重要的问题**，并针对性地设计了 SFT + GRPO 的完整闭环；
- **课程式安排合理**：Easy 预热 → Medium/Hard 聚焦 → 全量巩固，单样本总曝光严格与标准 3 轮训练一致，保证了对比公平；
- **推理成本低**：SpecCoder 在推理时只需一次性生成"分析+代码"，不需要像智能体方法那样多轮交互，对一个 7B 模型来说部署门槛低。

**实验设计亮点**：

- 统一骨干模型、统一数据划分、统一评测协议，与基线对比信息量充足；
- 不满足于"更准"，还通过扰动实验、人工评估、案例研究论证了性能提升的机制性原因；
- 采用 bootstrap 置信区间，并同时报告 Pass@1（精确通过）与 AvgPassRatio（部分正确），对竞争编程这类测试严格的任务尤为重要；
- 既做独立模型评估又做智能体后端评估，兼顾学术可比性和实用价值。

## 8. 不足与局限

- **对闭源教师模型依赖度高**：规范生成依赖 GPT-4o，后向验证依赖 DeepSeek-V3-0324。规范的覆盖范围和归纳质量受限于教师模型的水平，引入了额外 API 成本，且在 2026 年论文使用时间点上无法复现 API 价格。论文虽报告了约 597 美元的总费用，但未与"用开源模型自行构建"做成本对比实验；
- **测试用例作为奖励信号的固有局限**：论文坦承现有测试套件多是黑盒的，难以覆盖极端边界或验证算法内部约束；测试未覆盖的需求约束在实际使用中可能被遗漏；
- **模型规模单一**：所有实验仅在 7B 量级模型（Qwen2.5-7B-Coder-Instruct）上进行，未验证方法在更大模型（如 14B、32B 或 70B）上是否同样有效且稳定；
- **数据来源范围有限**：训练数据只来自 APPS 和 CodeContests 两个竞争编程类基准，这些任务的规范具有相似结构，论文未在更多样化的需求类型（如库调用生成、业务逻辑描述、仓库级任务）上训练验证；
- **对 APPS 测试集有非标准操作**：论文从 APPS 官方测试集中抽出 3000 个样本用于数据增强，并将剩余 500 个用于评测。虽然两个子集互不重叠、按难度分布采样，但这种对公开 benchmark 的创造性切分与其他方法在完整测试集上的结果不完全可比；
- **"判别任务在推理时如何被利用"还需进一步说明**：论文验证了判别训练对生成有帮助，但推理阶段只使用了生成的"分析+代码"，判别能力并未在推理时显式启用；
- **部分细节不够透明**：消融实验图中未伴随置信区间，难以判断某些差异的统计显著性；案例研究虽直观但只有单个样本，不能替代系统量化证据。

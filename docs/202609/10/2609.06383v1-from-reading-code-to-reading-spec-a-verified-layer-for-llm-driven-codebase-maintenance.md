## 摘要
LLM生成代码的快速增长增加了软件复杂性以及工程师的维护负担。尽管LLM提供了一种潜在的自动化替代方案，但这种结构复杂性阻碍了它们直接管理代码库的能力。我们提出了可证明的原始功能表示（Provable Representation Of Original Functionality，PROOF），它通过结构化规范间接管理代码库。为了严格通过这类规范实现全生命周期代码库管理，PROOF将代码库拓扑抽象为分层的自然语言表示。为了建立绝对信任，该系统仅根据该规范重建源代码，从而证明语义等价性。这一经过验证的基础驱动维护请求，在执行代码修改的同时同步更新自身，以防止语义漂移。在真实世界代码库上的实验证实了这些规范的有效性。

## Abstract
The rapid growth of LLM-generated code increases software complexity and the maintenance burden on engineers. While LLMs offer a potential automated alternative, this structural complexity hinders their ability to manage codebases directly. We introduce the Provable Representation Of Original Functionality (PROOF), which manages codebases indirectly via structured specifications. To enable full-lifecycle codebase management strictly through these specifications, PROOF abstracts codebase topology into a hierarchical natural-language representation. To establish absolute trust, the system proves semantic equivalence by reconstructing source code exclusively from this specification. This verified foundation drives maintenance requests, executing code modifications while synchronously updating itself to prevent semantic drift. Experiments on real-world repositories confirm the effectiveness of these specifications.

## 1. 核心问题与研究动机

- **背景趋势**：LLM 生成代码的规模增速远超工程团队的认知与评审能力，导致人均维护负担上升、技术债务累积（文中 Figure 1 给出 2016–2026 年代码总量 vs. 工程人力的趋势对比）。
- **核心障碍**：将 LLM 直接用作仓库级"自动维护者"面临两大瓶颈：
  - **上下文窗口限制**：无法一次性处理整个仓库；
  - **跨文件全局依赖**：仓库级依赖结构复杂，导致上下文退化（context degradation），进而产生代码幻觉与逻辑不一致。
- **现有方案不足**：
  - 自然语言表示（RepoAgent、DocAgent 等）可读性好，但缺乏结构约束与可验证语义；
  - 图结构表示（GraphCodeBERT、RepoGraph、RPG-Encoder、LocAgent、CoSIL 等）保留宏观依赖，但节点被编码为高层意图或向量，缺少细粒度修改所需的信息；
  - 往返验证（RTCE、SimRAG、EPAM）验证偏"软"，依赖结构相似度或自评估，缺乏持续漂移检测。
- **论文主张**：应让 LLM **间接地**通过中间表示（IR）管理代码库，该 IR 需满足三性质：粒度可适配（granularity adaptation）、拓扑保持（topology preservation）、可验证性（verifiability）。
- **整体含义**：把"读代码"转变为"读规范"（Reading Code → Reading Spec），将代码库维护的操作对象从底层语法提升为可审阅、可验证、可编辑的自然语言规范层。

## 2. 方法论：PROOF 系统

### 2.1 核心思想与形式化

- **映射 Φ : C → S**：把代码空间 C 映射到代理空间 S（Spec 图），保持图结构同构：`D_C ≅ D_S`，保留层级 L 与调用边 E_C，但过滤语言相关细节，节点映射为自然语言 Spec 节点 N_S。
- **代码库更新被重构为**：`C' = Φ⁻¹(Δ(S, R))`，即在代理空间中做修改后再逆映射回代码。
- **安全更新的双重等价约束** E(C'|C,R)=1：
  - 结构等价：`AST(C\R) ≅ AST(C'\R)`（未受影响区域语法框架不变）；
  - 行为等价：`∀x ∈ X\R, C'(x) = C(x)`（未变更域上输出一致）。

### 2.2 五层静态层级分解

自上而下实例化层级 L：

| 层级 | 物理形态 | 语义功能 |
|---|---|---|
| Project | 顶层代码库抽象 | 全局容器 |
| Module | 目录/文件 | 按业务域分组 |
| Object | 类（状态+行为） | 语义闭包，由方法聚合 |
| Function | 最小自包含执行单元 | Φ 的语义蒸馏入口 |
| Segment | 函数内循环/分支等代码行 | 因函数过长而拆分处理 |

### 2.3 结构化闭包模板（关键细节）

- **Function 闭包**（六字段契约）：
  `v_func = ⟨Desc, I/O, Meta, Deps, Data, Error⟩`
  - Desc：执行意图；I/O：参数类型与返回值约束；Meta：语言、纯度（副作用）、原子性（多线程安全）；Deps：对外部节点的每次调用；Data：读取/修改的全局状态或可变参数；Error：抛出/捕获异常的边界。
- **Object 闭包**（嵌套元组）：
  `v_obj = ⟨ClassDesc, DataState, Invariants, M_obj⟩`
  - 其中每个方法 `v_m ∈ M_obj` 复用 Function 元组结构，但其 Data 字段扩展并受父类 DataState（self）约束。
- **作用**：把原本隐藏在代码中的依赖，转化为静态、结构化的声明，使 E_C 可被确定性追踪。

### 2.4 两阶段生成流程

1. **局部节点实例化**：沿静态层级遍历代码库，逐节点让 LLM 读取代码、切分为有序控制流 Segment，并按模板填充六字段，保持上下文小、减少长程依赖漂移。
2. **全局拓扑抽取与组装**：由确定性解析算法读取每个闭包的 Deps 字段抽取边，**不让 LLM 推断宏观结构**（避免结构偏置），自底向上聚合为与 C 拓扑同构的全局 Spec 图 S。

### 2.5 等价性验证（Round-Trip）

- 拓扑同构不足以保证语义正确，故采用**零编辑往返**：仅从 S 逆映射重建代码 `Ĉ = Φ⁻¹(S)`，比较行为等价：`∀x ∈ X, Ĉ(x) = C(x)`。
- 实践中用仓库已有测试套件 T 作为 X 的有限采样，并**放松为有向包含**（避免要求模型修复既有缺陷）：
  `Pass(C) ⊆ Pass(Ĉ)`
- 量化为连续指标 **Fidelity**：
  `Fidelity(N_S) = |Pass(C) ∩ Pass(Ĉ)| / |Pass(C)|`
  若 C 本身通过全部测试，则退化为普通测试通过率。

### 2.6 更新与漂移控制

- 收到变更请求 R 后，LLM 将其映射到 Spec 图并定位受影响节点子集 N_R（|N_R| ≪ |N_S|），把全局操作 Δ(S,R) 分解为相互独立的局部修改 Δ_v。
- 由于修改局限于特定节点，未受影响区域的语法结构保持不变，满足 `AST(C\R) ≅ AST(C'\R)`。
- **人机分工**：开发者只审阅结构化的自然语言修改提案（确认业务逻辑是否匹配 R），代码的生成与组装由 LLM 自动完成。
- **语义漂移校准**：i 次增量更新后，可从当前底层代码重新生成完全准确的参考 Spec 图 N_S^(i)*，量化误差：
  `Δ_i = Fidelity(N_S^(i)*) − Fidelity(N_S^(i))`
  该值仅作参考指标，不强制重置；开发者判断漂移过大时可覆盖当前状态以重新对齐。

## 6. 主要结论与发现

- **行为等价**：PROOF 在三个仓库上 Pass@3 最高（Flask 100%、Seaborn 100%、Pytest 96.80%）；Flask/Seaborn 上 Pass@1 亦领先（84.9% / 83.5%）。
- **结构等价**：PROOF 全局 AST 相似度最高（Flask 90.45%、Seaborn 87.32%、Pytest 96.12%）。RPG-Encoder 在 Seaborn 上结构崩塌（40.36%），体现纯意图/向量抽象对细粒度结构的破坏。
- **可解释性**：PROOF 在四个维度上均排名第一；Faithfulness 与 Verifiability 优势小（0.3、0.5 分），Completeness 与 Consistency 优势明显（相对 RepoAgent 高 1.1 与 1.7 分），归因于六字段契约与 Deps/Data 字段的跨节点约束。
- **Token 效率**：PROOF 首轮重建消耗较高（5.29M，因六字段信息密度最大），但收敛快，总消耗 5.49M 反低于 RPG-Encoder 的 6.12M，远低于 EPAM 的 14.20M。
- **骨干鲁棒性**：最弱骨干（GPT-5.5 Medium，55.7%）仍显著超过最强骨干下的最佳基线（RepoAgent + Claude 5 Sonnet，29.95%），差距 >25 个百分点，说明优势来自方法设计而非模型能力。
- **总体结论**：Spec 在结构拓扑、行为等价、节点级内容三方面均被验证为准确；漂移校准 Δ_i 为长期演化提供纠偏手段。

## 7. 优点与亮点

- **表示设计精巧**：五层静态层级 + 六字段 Function 闭包 + Object 嵌套闭包，把隐式依赖显式化为可解析声明，兼顾粒度适配与拓扑保持。
- **确定性拓扑抽取**：宏观调用图由解析 Deps 字段的确定性算法生成，而非 LLM 自由生成，避免了结构性幻觉。
- **严格的往返验证范式**：以"仅凭 Spec 重建代码 + 用原仓库测试套件检验"把主观的"总结质量"转化为客观可测的 Fidelity，并用 Pass(C) ⊆ Pass(Ĉ) 的放松条件优雅处理既有缺陷/易碎测试。
- **可量化漂移检测**：Δ_i 通过重新生成参考 Spec 图对比 Fidelity，提供长期演化中的漂移度量与可选重置机制。
- **人机协作分工清晰**：开发者审阅自然语言 Spec 变更（语义层），LLM 负责代码生成（语法层），降低人工认知负担。
- **消融设计有说服力**：骨干模型消融通过"最弱骨干 vs. 最强骨干基线"的交叉比较，有效隔离了方法贡献与模型能力贡献。
- **工程配套完整**：提供 Spec Viewer 三面板交互界面（符号树 / 闭包与源码对照 / 依赖边与 TODO 清单），并附具体维护请求的节点级分解案例。

- **仅支持静态调用图**：未覆盖 RPC、消息队列等分布式/动态架构（论文已自述）。
- **评测与宣称的落差**：实验主体是"Spec → 代码重建"，而非真实 issue 修复或维护任务端到端评测；"full-lifecycle codebase management"与"absolute trust"等表述偏强。
- **潜在的循环性风险**：Spec 由 LLM 生成、代码由 LLM 依据 Spec 重建，二者共享同一模型的偏差；虽然测试套件提供外部锚点，但 Fidelity 的放松定义（有向包含）会掩盖回归以外的语义损失。
- **实验规模与覆盖面有限**：3 个 Python 仓库、单一语言；骨干消融仅 Seaborn；人类评估样本量小（21 节点 × 3 评分者）。
- **未报告成本与算力**：缺少推理 token 总额之外的算力、延迟、货币成本信息，难以评估实际部署可行性。
- **Pytest 上 Pass@1 = 0% 的解释偏弱**：归因于"高层集成错误传播"缺少直接的失败归因分析（如逐测试根因分类）。
- **AST 相似度指标本身的局限**：`pycode_similar` 主要面向抄袭检测，对语义等价与重构容忍度的适用性未加讨论。
- **漂移校准 Δ_i 无阈值指导**：何时重置完全依赖开发者主观判断，缺乏自动化策略或经验阈值。

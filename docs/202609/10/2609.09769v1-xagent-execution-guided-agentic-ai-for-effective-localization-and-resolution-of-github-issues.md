## 摘要
智能体 AI 已使利用大型语言模型（LLMs）自主解决仓库级 GitHub 问题的能力成为可能。然而，由于依赖有限的静态问题描述，现有智能体方法存在错误定位和验证不完整的问题。仅依赖这些信息可能使 LLM 推理偏向问题描述的狭窄范围，导致补丁不完整，无法解决根本问题。在本文中，我们提出 XAgent，一种执行引导的智能体框架，通过分析动态行为和额外的程序上下文来定位并验证问题。在 SWE-bench-lite 数据集上的实验结果表明，XAgent 优于其他现有方法，达到 62.0% 的解决率和 72.8% 的函数定位准确率，同时保持成本效率。我们的分析进一步表明，XAgent 成功解决了现有最佳基线未能处理的额外 7 个问题。这项工作凸显了从静态的、面向描述的补丁生成向动态执行引导的问题解决的转变，为基于 LLM 的编码智能体实现更稳健且更具泛化性的软件维护开辟了新机会。

## Abstract
Agentic AI has enabled capabilities in leveraging Large Language Models (LLMs) to autonomously resolve repository-level GitHub issues. However, due to the reliance on limited static description of issues, existing agentic approaches suffer from incorrect localization and incomplete validation. Solely relying on this information can bias LLM reasoning toward the narrow scope of the issue description, leading to incomplete patches that fail to address the underlying issue. In this paper, we present XAgent, an execution-guided agentic framework that analyzes dynamic behavior and additional program context to localize and validate issues. The experimental results on the SWE-bench-lite dataset demonstrate that XAgent outperforms other existing approaches, achieving a resolve rate of 62.0% and a function localization accuracy of 72.8%, while maintaining cost efficiency. Our analysis further shows that XAgent successfully resolves 7 additional issues that the top existing baselines fail to address. This work highlights a shift from static, description-oriented patch generation toward dynamic execution-guided issue resolution, opening new opportunities for LLM-based coding agents to achieve more robust and generalizable software maintenance.

## 一、核心问题与整体含义

- **研究背景**：仓库级 GitHub issue 自动解决是软件维护中的核心任务，近年来 LLM 与 Agentic AI 被用于让模型自主复现、定位、修复并验证问题。
- **核心问题**：现有 agentic 方法通常遵循“复现—定位—补丁生成与验证”流程，但高度依赖 issue 的静态文本描述，导致两类关键缺陷：
  - **错误定位**：通过关键词或语义相似度在仓库中搜索，容易偏向 issue 描述中显式提到的函数，而忽略真正位于更深调用链中的根因函数。
  - **验证不完整**：仅根据 issue 描述生成验证测试，补丁可能只修复表面症状，无法通过更全面的人类测试，形成“症状修复陷阱”。
- **整体含义**：论文主张从“静态描述导向的补丁生成”转向“动态执行引导的问题解决”。XAgent 通过比较 buggy 与 non-buggy 执行轨迹来定位可疑函数，并利用程序上下文增强验证测试，从而提升定位准确性、补丁泛化能力和成本效率。

## 二、方法论：XAgent 的核心思想与关键技术

- **总体框架**：XAgent 包含三个阶段：
  1. **复现阶段**：生成 buggy reproduction script 与 non-buggy reference script。
  2. **定位阶段**：执行两个脚本，收集调用树，通过差分分析定位可疑函数。
  3. **补丁生成与验证阶段**：生成上下文感知验证测试，并迭代生成、验证补丁。

- **复现阶段**
  - 使用 reproduction agent 根据 issue 描述生成两个脚本：
    - **reproduction script**：触发 issue 中描述的 buggy 行为。
    - **reference script**：结构相似，但输入有最小差异，展示预期正确行为。
  - 强调两个脚本结构相似，避免引入无关执行差异，从而让后续调用树比较更干净。
  - 执行脚本并验证输出是否符合 issue 描述；若不符合则重新生成。

- **执行引导定位**
  - 使用 tracing module 记录函数调用、调用者—被调用者关系及 traceback。
  - 将执行轨迹构建为调用树：节点为函数，边为调用关系。
  - 设 buggy 调用树为 \(T_1=(V_1,E_1)\)，non-buggy 调用树为 \(T_2=(V_2,E_2)\)。
  - 使用 **APTED（All Path Tree Edit Distance）** 算法计算两棵树之间的编辑距离与节点映射。
  - 节点映射分为：
    - **Identical**：两棵树中匹配的节点。
    - **Deletions**：只出现在 buggy 树中的节点。
    - **Insertions**：只出现在 non-buggy 树中的节点。
  - 定位时重点关注 **deleted nodes**，即只在失败执行中出现、不在成功执行中出现的函数，记为潜在 buggy 函数集合 \(S\)。
  - 若 issue 描述或复现过程中显式提及的函数不在 \(S\) 中，则将其加入 \(S\)，避免遗漏。
  - 使用 **UniXcoder** 对 issue 描述、函数体、函数名进行编码，经 mean-pooling 与 L2 归一化后计算余弦相似度，对 \(S\) 排序，保留 Top-\(K\) 函数，实验中 \(K=20\)。

- **上下文感知验证测试增强器**
  - 动机：issue 描述通常不完整，仅据此生成测试会导致补丁过拟合表面症状。
  - 从 reproduction agent 的轨迹中提取程序上下文，即 agent 在复现过程中已经判定相关的文件与函数。
  - 使用 zero-shot prompting，让 LLM 基于以下信息生成额外验证脚本：
    - 提取出的程序上下文；
    - 原始 reproduction scripts；
    - issue 描述。
  - 通过不同温度参数 0.4、0.6、0.8 生成三个额外验证测试，与两个复现脚本共同构成五个验证测试。
  - 复用复现阶段上下文，避免额外代码库探索，降低 token 与计算成本。

- **补丁生成与验证**
  - Patch agent 首先执行五个验证测试与已有回归测试，确认环境正确且 bug 可复现。
  - 按排序后的可疑函数列表 \(S'\) 逐个检查：
    - 若函数与 issue 相关，则尝试生成候选补丁；
    - 否则跳到下一个函数。
  - 生成补丁后，重新运行五个验证测试与回归测试。
  - 若失败，根据环境反馈重新生成补丁，直到通过或达到预设行动限制。
  - 实验中使用 Claude Sonnet 4 作为 backbone LLM；reproduction agent 行动限制 100，patch agent 行动限制 200；温度分别设为 0、0.5、0.8 等。

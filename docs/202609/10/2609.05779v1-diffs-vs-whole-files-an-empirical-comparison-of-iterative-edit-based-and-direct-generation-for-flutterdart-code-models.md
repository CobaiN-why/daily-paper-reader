## 摘要
用于代码编辑的大语言模型至少可以在两种输出模式下进行训练和部署：直接生成，即模型一次性输出整个修改后的文件；以及迭代式基于差异（diff）的生成（“步骤”），即模型输出一系列局部搜索/替换编辑，每次应用一个，直到其发出完成信号或步骤预算耗尽。基于差异的模式具有吸引力，因为它模拟了开发者编辑代码的方式，并且理论上每轮所需的生成 token 应少得多。我们在一个共享的 Flutter/Dart 数据集上，以两种模式训练了两个代码模型——一个从零训练的 100M 参数模型（Rainbow-Pony-100M）和一个微调后的 Qwen2.5-Coder-0.5B——并在每个模型约 1,790 个任务的留出集上评估了四个所得模型。直接生成在我们测量的每一项指标上都显著优于基于差异的生成——编译/静态分析通过率、每字节比特数、与参考的字符级相似度，以及盲评 LLM 裁判对目标达成、正确性和代码质量的评分——并且这种差距在通过匹配 ID 比较控制任务难度后，以及仅限双方都能编译的代码时依然存在。随后，我们识别出基于差异的生成确实会胜出的条件背后一个单一的、与架构无关的机制：它在简短、空间局部的编辑上具有竞争力，并且其类别级胜出恰好集中在数据集中平均编辑步数最低的两个任务类别——重构和错误处理/边缘情况修复。我们将此称为任务局部性（task locality），并讨论其对于何时基于编辑的训练模式是、何时不是代码编辑模型的正确选择所蕴含的意义。

## Abstract
Large language models used for code editing can be trained and deployed in at least two output regimes: direct generation, where the model emits the entire modified file in one shot, and iterative diff-based generation ("steps"), where the model emits a sequence of localized search/replace edits applied one at a time until it signals completion or a step budget is exhausted. The diff-based regime is attractive because it mirrors how developers edit code and should require far fewer generated tokens per turn. We train two code models - a 100M-parameter model trained from scratch (Rainbow-Pony-100M) and a fine-tuned Qwen2.5-Coder-0.5B - in both regimes on a shared Flutter/Dart dataset, and evaluate all four resulting models on a held-out set of approx 1,790 tasks per model. Direct generation substantially outperforms diff-based generation on every metric we measure - compilation/static-analysis pass rate, bits-per-byte, character-level similarity to the reference, and blinded LLM-judge ratings of goal fulfillment, correctness, and code quality - and the gap persists after controlling for task difficulty via a matched-ID comparison and when restricting to code that compiles on both sides. We then identify a single, architecture-independent mechanism behind the conditions where diff-based generation does win: it is competitive on short, spatially localized edits, and its category-level wins concentrate in exactly the two task categories - refactoring and error-handling/edge-case fixes - with the lowest mean edit-step count in our dataset. We term this task locality and discuss its implications for when an edit-based training regime is and is not the right choice for a code-editing model.

## 1. 核心问题与研究背景

- **核心问题**：LLM 做代码编辑时至少有两种输出范式——
  - **direct（直接生成）**：给定原文件与指令，一次性生成完整修改后的文件；
  - **steps（迭代 diff 生成）**：生成一串局部 search/replace 编辑动作，逐个机械应用到当前文件状态，直到模型发出停止信号或耗尽步数预算。
- **背景张力**：生产级编码 agent 与 IDE 工具几乎都偏好 diff 式接口，理由直观——diff 比整文件短、生成更省 token、不会静默破坏未被要求改动的代码，且贴合人类 review 的单位（PR diff）。但"这是否也是一个更好的**训练目标**"尚无定论。
- **相关工作的分歧**：
  - LintSeq（Piterbarg et al., 2025）：合成编辑序列作为训练课程可提升代码**合成**质量；
  - Aider 基准：diff 格式降低 token 成本，但提高 harness 无法应用的畸形编辑率，弱模型尤甚；
  - Cheng et al. (2026)：没有统一更优的格式，正确格式是**具体编辑**的属性，自适应/路由式方案优于固定格式。
- **本文定位**：在单一窄但真实的领域（Flutter/Dart 代码编辑）上做端到端实证，用自己的模型而非第三方榜单，固定训练数据、tokenizer、评测 harness，以隔离"输出范式"本身的效应，避免跨论文比较中的多重混淆。

## 2. 方法论

### 2.1 核心思想
对两个架构差异极大的骨干网络，各自训练 direct 与 steps 两个变体，得到四个 arm，全部在同一留出任务集、贪心解码下评测，从而把"输出范式"从架构、数据、格式语法等混淆中剥离出来。

### 2.2 骨干模型
- **Rainbow-Pony-100M**：完全从零训练的 decoder-only transformer。预训练 119,000 步（batch 16、block 1,024、16,384 tokens/step），约 1.95B tokens（≈0.79 epoch，语料 2.60B tokens，70% Flutter/Dart 源码 + 30% 英文），自建 16k 词表 BPE，cosine 调度峰值 3×10⁻⁴ 衰减至 2×10⁻⁵，最终 train/val loss 1.28/1.31；98,146,432 参数，后置扩词表至 16,022 以容纳 `<GOAL>`、`<CODE>`、steps 动作标签，两微调 checkpoint 各 98,163,350 参数。该骨干**未接触任何其他编程语言或通用多语言代码语料**，可排除"预训练偏好某格式"的混淆。
- **Qwen2.5-Coder-0.5B**：493.81M 参数的预训练代码模型，在同一任务池上微调，用于检验差距是否只是"从零小模型没学会编辑格式"的产物。

### 2.3 两个训练/推理范式
- **direct**：输入初始文件 + 指令，输出完整修改后文件（可含新建文件），以 `</OUTPUT>` 结尾。
- **steps**：prompt 为带标签的纯文本，含 `<GOAL>`、`<CODE>`（当前文件状态）、`<HISTORY>`（此前动作，首步为空）、开放的 `<OUTPUT>`；模型补全一条 `<ACTION>`（含 TYPE 与自然语言 DESC）+ 一个或多个 `<CHANGES>` hunk，以 `</OUTPUT>` 结束，末步附 `<DONE></DONE>`。每步生成后由 harness 机械应用，再进入下一步，最多 20 步。

### 2.4 编辑应用与回退启发式（关键实现细节）
- 精确匹配：`search` 在文件中**恰好出现一次**→替换；**出现 0 次**→拒绝，记为 `apply_failed`。
- **出现多次**→触发回退启发式，取**第一次出现**的位置替换（文中明示这是启发式而非原则性修复，first/last-occurrence 都可能静默改错位置）。
- 评估记录 `num_fallback_steps`，用于后续失败归因。

### 2.5 评测指标
- `dart_pass`：输出是否通过 `dart analyze` 静态分析（主正确性信号，附 Wilson 95% CI）。
- `bits_per_byte`：对参考 `final_code` 的单次 teacher-forced 困惑度，与 mode 无关。
- `similarity_ratio`：与参考 `final_code` 的字符级相似度。
- steps 专属：`stop_reason`（`done` / `max_steps` / `apply_failed` / `malformed`）、`num_steps`、`num_fallback_steps`。

### 2.6 两类关键对照设计
- **matched-ID（"clean"）比较**：定义 clean_steps = {stop_reason=done ∧ num_fallback_steps=0 ∧ num_steps<20}，与**同一 sample_id** 的 direct 结果比较，排除"steps 的失败恰好落在本身更难的任务上"这一选择偏差。
- **best-case 比较**：在 matched-ID 基础上再限定 `dart_pass=True` 的 steps 行，刻画"更多训练有望达到"的乐观上界。
- **盲评 LLM-as-judge**：gpt-4.1，单候选、完全盲（不知模型名、模式、dart_pass 结果），按结构化 schema 输出 1–5 分的 `goal_fulfillment`、`correctness`、`code_quality` 及理由。

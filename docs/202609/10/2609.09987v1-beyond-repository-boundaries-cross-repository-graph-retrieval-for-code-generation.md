## 摘要
仓库级代码生成要求生成的代码不仅与目标仓库兼容，还要与其依赖环境兼容。现有基于检索的方法主要从本地仓库中检索上下文，使得外部 API 的使用依赖于模型的预训练知识，而对于未见过的或特定版本的 API，这种知识可能不足。此外，当前的检索策略大多关注一跳证据，忽视了代码组件之间的结构关系。我们提出 CrossCoder，一个跨仓库代码生成框架，通过一个覆盖仓库和库实体的统一知识图谱，将外部库显式纳入检索上下文。CrossCoder 通过规划和语义检索识别重要节点，然后有选择地扩展相邻节点，以检索更丰富的多跳上下文证据用于生成。为了进一步评估依赖版本兼容性，我们引入 VersionExec，一个基于执行的基准，源自 BigCodeBench，用于评估不同依赖版本下的生成。在 RepoExec、DevEval 和 VersionExec 上的实验结果表明，CrossCoder 持续提升了功能正确性（pass@1 上最高提升 6.3%）以及对依赖版本变化的鲁棒性。

## Abstract
Repository-level code generation requires generated code to be compatible not only with the target repository but also with its dependency environment. Existing retrieval-based methods mainly retrieve context from the local repository, leaving external API usage dependent on the model's pretrained knowledge, which can be insufficient for unseen or version-specific APIs. Moreover, current retrieval strategies largely focus on one-hop evidence and overlook the structural relationships among code components. We propose CrossCoder, a cross-repository code generation framework that explicitly incorporates external libraries into the retrieval context through a unified knowledge graph over repository and library entities. CrossCoder identifies important nodes via planning and semantic retrieval, then selectively expands neighboring nodes to retrieve richer multi-hop contextual evidence for generation. To further evaluate dependency-version compatibility, we introduce VersionExec, an execution-based benchmark derived from BigCodeBench that evaluates generation under different dependency versions. Experimental results on RepoExec, DevEval, and VersionExec demonstrate that CrossCoder consistently improves both functional correctness (up to 6.3% on pass@1) and robustness to dependency-version changes.

## 1. 核心问题与整体含义

- **研究背景**：代码大模型（CodeLLMs）已从孤立的编程任务扩展到必须集成进现有项目的仓库级代码生成。此时目标代码不仅要满足功能需求，还需符合周围代码库的内部 API、数据结构与跨文件设计约束。
- **核心问题**：现有基于检索增强生成（RAG）的仓库级方法存在三个未被充分解决的维度：
  - **依赖兼容性缺失**：检索范围局限于本地仓库（`R_current`），外部库 API 的使用完全依赖模型的预训练知识，对未见库或新引入 API 容易产生幻觉或重复造轮子。
  - **版本语义不明确**：即便模型见过相关库，仓库级提示通常只暴露 import 或包元数据，无法确定特定版本下的 API 语义；API 行为跨版本可能变化，导致代码"本地逻辑正确但外部调用不兼容"。
  - **检索粒度浅**：当前方法多基于相似度检索或依赖感知检索，主要依赖**一跳证据**，忽略更深依赖链中的有用上下文；而图检索增强生成（GRAG）在 QA 中已展现结构推理优势，但在代码生成领域尚属空白。
- **整体含义**：论文主张将检索范围从"跨文件"扩展到"跨仓库"，把外部库实体显式纳入统一知识图谱，并通过多跳图扩展获取结构化上下文，从而突破本地仓库边界，实现依赖版本兼容的代码生成。

## 2. 方法论

### 2.1 核心思想
- 给定仓库 `R` 与外部库集合 `L = {l1, l2, ..., ln}`，将二者的实体融合进一个**统一异构无向图** `G(V, E)`，其中 `V = V_R ∪ V_L`。
- 采用 **Plan-then-Retrieve（先规划后检索）** 范式：先让 LLM 生成实现计划，再基于计划定位高重要性节点，最后沿图递归扩展，检索多跳上下文证据。

### 2.2 知识图谱索引（Knowledge Graph Indexing）
- **节点类型** `τv(v) ∈ Tv = {file, class, function, variable}`；**边关系** `τe(u,v) ∈ Te = {contain, import, invoke, inherit}`。
- **搜索范围收缩**：为降低计算开销，定义文件 `f` 的投影子图
  - `Vf = { v ∈ V | τe(f, v) ∈ {contains, import} }`
  - `Gf = Πf(G) = (Vf, Ef)`，仅保留当前文件包含的实体及其导入依赖（含仓库与外部库）。
- **实现细节**：从 `requirements.txt`、`setup.py` 解析依赖版本 → 安装/定位对应版本源码 → 与目标仓库共用同一 Python AST 流水线解析 → 合并为单一图。例如 `from w3lib import html` 会创建从仓库文件到外部模块的 `import` 边，使 `w3lib/html.py` 中的实体成为检索候选。

### 2.3 Plan-then-Retrieve 算法
- **初始规划（Initial Planning）**：向规划模型 `M_θ` 提供两类信息——
  - **全局视图**：结构摘要 `T(Gf)`（树状图视图）+ 各候选节点的接口信息 `I(vi)`（如函数签名）。
  - **使用示例**：用 UniXcoder 计算查询 `q` 与候选节点的余弦相似度 `sim(q, v) = e(q)ᵀe(v) / (‖e(q)‖‖e(v)‖)`，取 Top-K 节点 `Vf^(k)` 作为示例。
  - 生成计划 `P ~ Mθ(· | T(Gf), {I(vi)}, Vf^(k), q)`，要求计划中显式用反引号标注候选组件名。
- **基础节点选择（Base Node Selection）**：
  - **正则匹配**：`RegScore(vi) = 1`（若 `name(vi)` 出现在计划 Mentions 中），权重 `wq(vi) = 1`。
  - **语义相似度补充**：`SemScore_q(vi) = max_{x∈{q}∪P} sim(x, vi)`，从剩余候选中取 Top-K 作为 `Vsem`，权重为 `SemScore_q(vi)`。
  - 最终基础集合 `Vbase = Vreg ∪ Vsem`。
- **图扩展与检索（Graph Expansion and Retrieval）**：
  - 从每个 `vb ∈ Vbase` 出发，在无向子图 `Gf` 上做深度优先遍历，第 `n` 跳邻居 `u` 的得分：`w_q^(n)(u) = wq(vb) / (n + 1)`。
  - 仅当 `w_q^(n)(u) ≥ δ` 时才纳入并继续递归，否则剪枝。
  - 多路径可达时取最大值：`wq(u) = max_{vb∈Vbase} w_q^(nu(vb))(u)`。
  - 最终检索列表 `Vret = sort_wq(Vbase ∪ Vext)`，按权重降序排列后序列化喂给生成器。

### 2.4 VersionExec 基准

- **消融结论**：规划贡献最大（GPT-OSS-120B 上移除后 Pass@1 从 46.48 降至 43.61），其次是库上下文（约 2–3 分），最后是图扩展。

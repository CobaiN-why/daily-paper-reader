## 摘要
编码智能体能够跨大型软件项目修改和测试代码。游戏开发是智能体必须实现游戏玩法规则的领域。游戏即使在运行过程中违反规则，也可能以有效状态结束。当前的游戏开发基准测试会重放固定示例、对视频打分，或让另一个模型评判结果。然而，现有基准测试都没有在由评估器选择的各种场景中全程检查游戏规则，同时确保判定结果完全可复现。我们提出了 GameLogicBench，一个包含 Godot 项目中 72 个游戏玩法逻辑任务的基准测试。自动评估器在每个模拟 tick 检查每个游戏的规则。在 403 个手工设计的场景中，通过带种子的参数变化生成了 1,451 个测试用例。为确保评估器衡量的是行为而非实现选择，它必须接受每个任务的不同正确实现，同时拒绝变异体——即移除某一必需能力的实现。任务涵盖孤立机制、多系统交互以及仓库级功能。在语言模型和脚手架的 20 种组合中，观察到的最佳运行解决了 52.78% 的任务。在 Claude Code 下，随着任务范围从孤立机制扩展到交互系统再到仓库级功能，所有十二个模型解决的任务都更少。与孤立机制任务相比，智能体在仓库级任务上更频繁地检查代码，并进行更多工具调用。大多数未成功的提交是可运行的，但错误地实现了某些必需的游戏行为。我们比较了使用变异体验证与未使用变异体验证构建的基准评估器版本。没有这种验证时，错误的智能体提交会通过。另一项分析发现，当网络访问开放时，智能体会从公共仓库复制代码。因此，可靠的评估既取决于测试拒绝什么，也取决于外部代码智能体能够访问什么。

## Abstract
Coding agents can modify and test code across large software projects. Game development is a domain where agents must implement gameplay rules. A game can end in a valid state even after violating its rules during the run. Current game-development benchmarks replay fixed examples, score videos, or ask another model to judge the result. However, no existing benchmark checks game rules throughout execution across varied evaluator-selected scenarios while ensuring exactly reproducible verdicts. We introduce GameLogicBench, a benchmark of 72 gameplay-logic tasks in Godot projects. An automated evaluator checks each game's rules at every simulation tick. Across 403 hand-designed scenarios, seeded parameter variations produce 1,451 test cases. To ensure that the evaluator measures behavior rather than implementation choice, it must accept different correct implementations for each task while rejecting mutants, implementations with one required capability removed. The tasks span isolated mechanics, multi-system interactions, and repository-scale features. Across 20 combinations of language models and scaffolds, the best observed run solves 52.78% of tasks. Under Claude Code, all twelve models solve fewer tasks as task scope expands from isolated mechanics, through interacting systems, to repository-scale features. Agents inspect code more often and make more tool calls on repository-scale tasks than on isolated-mechanic tasks. Most unsuccessful submissions are runnable, but implement some required game behavior incorrectly. We compared versions of our benchmark evaluator built with and without validation using mutants. Without this validation, incorrect agent submissions passed. A separate analysis finds agents copying code from public repositories when network access is open. Reliable evaluation thus depends both on what the tests reject and on what external code agents can access.

- **现有基准的不足**（表 1 对比）：

## 2. 方法论

### 2.1 核心思想
- 构建 **GameLogicBench**：Godot 4.4 项目中的 **72 个玩法逻辑任务**，每个任务要求智能体在既有项目中实现**一个机制**。
- 评估器在**每一个模拟 tick**（一次离散的模拟更新）检查游戏内部状态与事件历史，而非仅检查终态。
- 判定路径中**不含任何语言模型**，固定运行时与裁判代码后，同一提交 + 同一场景 + 同一种子必然得到相同判定。

### 2.2 任务分层（整合范围梯度）
- **Atom（21 个）**：在最小游戏中隔离单一机制，作为能力标定的锚点。
- **Combo（28 个）**：在一个定制最小游戏中组合多个机制，正确性取决于它们**时间、空间、并发调用**上的交互。
- **Repo（23 个）**：在真实开源 Godot 项目中就地实现机制，异构子系统需在共享状态上维持全局不变量（平均 209 个游戏文件、17,599 行代码）。

### 2.3 三层信息边界
- **第 1 层（必须披露）**：功能需求、游戏固定规则，包括"每局程序化重新生成场景"这一事实。
- **第 2 层（不披露）**：情境难度、运行中是否发生变化、评分场景如何升级。
- **第 3 层（从不提及）**：评测机制本身（如何判分）。
- 分界线：陈述"游戏本身的事实"合法，把同一事实翻译成"怎么写代码"（如"不要硬编码""每帧重新查询"）即属泄漏。

### 2.4 场景与测试用例
- **403 个手工设计场景**：结构、拓扑、机制、事件由人工设计；**种子只在不会破坏可解性的数值带内扰动**。
- 组合后得到 **1,451 个测试用例**，每任务 2–12 个场景、10–38 个测试用例。
- 每个任务恰好保留 1 个示例场景（预览运行其孪生副本），其余为评分场景，仅在判分时注入。

### 2.5 构建与验证流水线（4 个构建智能体 + 2 个人工环节）
1. **Sourcing**：从开源仓库、已发布游戏、功能能力分类法收集候选机制。
2. **Screening（人工）**：3 名标注者判断正确性是否可表达为**唯一值、合法事件序、守恒量**；拒绝依赖视觉/体验质量的机制。
3. **原型智能体**：在最小项目中**实测**引擎行为（无头模式物理查询、信号顺序、导航服务、协程结算顺序），确认三次运行比特一致；比较 proper 与 naive 实现的**分离裕度**。
4. **蓝图智能体**：产出任务蓝图，并执行两项机器检查——**判据锚点可发现性检查**（事实分为 A 项目内可发现 / B 仅简报可知 / C 无处可寻）与**空轴检查**（每个难度轴一个单缺陷 naive 实现，须在自身轴失败且不误伤其他轴）。
5. **实现智能体**：产出裁判侧（权威关卡定义、断言、驱动器、确定性设置）、智能体可见侧（可玩项目 + 预览 + stub + 简报）、简报、四类标定产物（proper 解、naive 解、单能力变异体族、行为保持对照）。
6. **独立审查智能体**：不信任任何上报读数，重跑全部标定产物；再做措辞审计、结构审计、注释审计、独立重算、红队探针、确定性验证。
7. **人工终审**：判定是否测量了目标机制、是否契合库范围、是否拓宽能力覆盖。

### 2.6 关键判据设计原则
- **机制形式断言**（合格）：唯一正确值、唯一合法事件序、守恒量、精确回滚。
- **阈值形式断言**（不合格作为硬门）：不超过 N 次泄漏、存活、覆盖率超阈值——只能作为准入闸或饱和梯度。
- **机制归属**：用"随机 stub"判别——若只有结果边界崩溃，机制在游戏/裁判侧（任务不合格）；若机制契约崩溃，机制在智能体手中（合格）。口诀：删掉智能体的代码，游戏是"变笨"还是"残废"。
- **难度三来源**：机制厚度、合法调用模式的别扭程度、阅读真实项目的墙。仅"用了引擎"不构成难度。

### 2.7 判分与防作弊
- 裁判在**独立断网容器**中运行，冻结的裁判文件覆盖在智能体工作区副本之上（覆盖顺序提供防篡改，而非靠"只读"措辞）。
- 变化的是执行条件（并发调用、重入、拉伸时间基），不是所需行为。
- 三层进程内防作弊：执行通道边界（扫描运行时节点树）、守恒账本审计、无回归参考数值。
- 确定性硬门槛：同一解法三次运行比特一致；使用导航服务/瓦片导航层的任务必须在裁判侧、可见侧、录制侧三处关闭导航地图异步迭代。

## 5. 实验数量与充分性

- **实验规模**：
  - 主实验 20 组模型–脚手架配置 × 72 个任务。
  - 构建侧：约 200 个候选想法 → 122 个完成构建/标定/审查 → **72 个入库**。
  - 消融审计集：**36 个任务、666 个变异体、488 个提交解法**。
  - 稳定性：3 组配置 × 3 次重复。
  - 污染审计：5 组配置的密封/开放网络配对。
- **充分性评估**：
  - **较强**：消融设计系统且有量化结论（Terminal-only 逃逸 236/666 = 35.4%；Preview-only 逃逸 508/666 = 76.3%）；变异体验证对照给出了 127/666 变异体在控制条件下通过、暴露 24 处缺失检查、影响 3 个任务结果的硬证据。
  - **较弱**：主表每组配置**仅 1 个样本**（作者自述"one sample per configuration"）；只有 3 组配置做了 3 次重复，无法覆盖全部配置的方差。
  - 污染审计仅 5 组配置，且依赖**人工检查**轨迹判断是否直接复用上游源码。
  - 公平性方面：所有解题会话统一限时、统一 effort，密封网络为默认条件，裁判确定性可复现；作者也主动披露了"开放网络会抬高 Repo 层分数"这一偏置，态度客观。
  - 总体：作为基准论文，实验覆盖与消融的严谨性高于同类，但统计重复次数偏少是明显短板。

## 6. 主要结论与发现

- **性能**：最佳配置（Claude-Opus-5 + Claude Code）仅解 **52.78%** 的任务；模型–脚手架**配对**而非模型本身才是可比单位（Qwen-3.8-Max 在不同脚手架下从 26.39% 到 44.44%）。
- **范围效应**：在 Claude Code 下，**全部 12 个模型**的解题率都随 Atom → Combo → Repo 递减；Repo 任务上智能体检查代码更多、工具调用更多、更多次重新播种预览场景（38.9% → 45.8% → 55.8%）。
- **成本非单调**：相同解题率的配置成本可相差 25 倍；成本–性能前沿仅含 Claude Code 配置，两端点解题率 31.94% 与 52.78%，成本相差 123 倍。
- **失败模式**：**74.3% 的失败场景中提交是可运行的**，但违反某项行为契约；17.2% 无可判分解，8.5% 为不可行计算。
- **能力分布**：Engine contract 在 20 组中的 19 组排名最高（合并严格通过率 88.75%）；Commitment、Spatial、Timing 为最低三类（53.4%–58.57%）。说明**基础引擎使用不是瓶颈，维持多帧决策与时空不变量才是**。
- **消融结论**：
  - 仅用终态断言（保留全部场景与种子）仍让变异体在 34/36 任务上逃逸 → 终态检查会系统性高估成功率。
  - 仅评预览场景更差：全部 36 个任务变异体逃逸，大量本应失败的提交通过，平均解题率高估 **+58.1%**。
  - 仅用正确解做标定会留下判据缺口，修复后 3 个任务结果由 PASS 翻为 FAIL。

上游实现或直接相关的公开代码，Repo 层通过率出现系统性抬升；密封网络下的分数更接近智能体的"真实能力"。这说明**开放网络会给仓库级任务带来可测量的检索污染偏置**，作者据此把密封网络设为默认条件，并主动披露该偏置。
- **任务规模与阅读成本的关系**：Repo 层（平均 209 个游戏文件、17,599 行代码）不仅解题率最低，还伴随最多的工具调用、最高的重新播种预览场景比例（55.8%）与最多的代码检查动作，说明"读真实项目"本身就是一道独立于机制实现难度的墙。

## 7. 局限与批判性评估

- **样本量偏小是最大短板**：主实验每组配置仅 1 个样本，只有 3 组配置做了 3 次重复，无法估计全部 20 组配置的方差；因此表 3 的排名差异（尤其相邻配置之间）可能落在噪声带内，作者本人也以 pass@1/pass@3/worst@3/σ 的方式提示了这一点。
- **污染审计依赖人工且覆盖有限**：仅 5 组配置的开放/密封配对，且是否"直接复用上游源码"由人工检查轨迹判断，缺少自动化或更细粒度的相似度度量，结论方向可信但幅度不宜过度外推。
- **引擎与领域单一**：全部任务基于 Godot 4.4，能力类虽被抽象为 7 类，但判据（如导航服务、瓦片导航层、协程结算顺序）深度绑定该引擎的运行时语义；跨引擎（Unity、Unreal、自研引擎）的外部效度尚未验证。
- **可形式化机制的取舍**：筛选环节明确拒绝依赖视觉/体验质量的机制，这保证了确定性，却也意味着基准**不覆盖**画面正确性、手感、可玩性等游戏开发中的真实维度；论文对此的立场是"先测可判定的部分"，而非宣称覆盖游戏开发全貌。
- **阈值断言的边界**：论文将"不超过 N 次泄漏、存活、覆盖率超阈值"排除在硬门之外，只作准入闸或饱和梯度，这一设计选择虽然严谨，但也限制了基准对"连续质量"类目标的表达能力。
- **评测成本不可忽视**：最高配置达 443.16 美元、最低 3.59 美元，且成本–性能前沿极窄（仅 Claude Code 配置入围），意味着该基准的复现与持续评测对预算敏感，可能影响其作为公共基准的可及性。

## 8. 启示与未来方向

- **对评测范式**：论文最核心的贡献不是"又一个基准"，而是把**判分粒度从终态推进到 tick 级、把判分路径从模型裁判收敛到确定性断言**。其消融证据（仅终态断言让 34/36 任务变异体逃逸、仅评预览场景平均高估 +58.1%）为"为什么必须逐 tick 检查"提供了直接经验支撑，这一结论可迁移到任何"过程合规性"比"终态正确性"更重要的智能体评测场景（如协议实现、数据库事务、并发系统修复）。
- **对智能体开发者**：失败模式中 74.3% 的提交是"可运行但违反行为契约"，且 Engine contract 普遍最强、Commitment/Spatial/Timing 最弱，提示当前智能体的瓶颈在**跨多帧维持决策、承诺与时空不变量**，而非单点 API 使用；优化方向应偏向状态跟踪、时序推理与并发/重入处理。
- **对基准建设者**：三层信息边界（必须披露/不披露/从不提及）、"事实陈述 vs 编码指令"的泄漏分界线、以及"删掉智能体代码后游戏是变笨还是残废"的机制归属口诀，都是可复用的方法论工具。
- **未来可扩展方向**：多引擎覆盖、更大规模的重复采样以给出置信区间、自动化的检索污染检测、以及在确定性断言之外补充受控的软质量评估。

## 9. 总体评价

GameLogicBench 的定位清晰且方法论自洽：它用**可复现的 tick 级断言**替代昂贵的模型/视频裁判，用**三层信息边界与多智能体构建流水线**控制任务质量，用**变异体标定**反向验证判据的分离能力，并主动披露开放网络偏置与单样本局限。其结论"最强配置仅解 52.78%、基础引擎使用不是瓶颈、过程合规才是"对当前编码智能体的能力画像具有参考价值。主要代价是评测成本高、统计重复偏少、领域局限于 Godot；但其"过程合规性评测"的范式主张，对更广泛的智能体可靠性研究具有超出本基准本身的启示意义。

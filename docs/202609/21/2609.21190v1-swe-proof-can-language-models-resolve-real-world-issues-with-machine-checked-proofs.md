## 摘要
确保LLM生成代码的正确性是现代软件工程的核心挑战。面向智能体代码生成的基准测试使用留出测试套件来检查正确性，而这类测试套件本质上并不完备，且越来越容易受到记忆化影响。形式化验证可避免这两个问题，但现有工作仅覆盖那些以规范作为输入给出的独立任务，而非真实问题；真实问题涉及大型代码仓库，并以模糊的自然语言表述意图。我们提出 Benchproofer，一个流水线，将具有已知正确补丁的编码任务转化为经形式化验证的任务：它为新代码编写规范，用公理概括该代码所调用的现有函数，并且只有在机械门控与对抗门控均通过后才接纳一个实例。将其应用于 SWE-bench Verified 得到 SWE-Proof，包含500个真实问题，其正确性是经过形式化验证而非测试验证的，并且该方法可扩展到 SWE-bench Pro。在两个前沿模型上，验证能捕捉测试遗漏的问题：通过测试的补丁中有四分之一到一半存在反例，结构化自然语言规范无法修正这一点；而正确的形式化规范则将 Opus 4.8 的解决率从85%提升到95%。编写该规范才是难点：必须自行编写规范的模型相较无辅助基线毫无提升，且它们的规范仅有62%通过我们的审核。常见的失败是忠实性：规范只约束了所需行为的一部分，而让其余部分不受约束。规范质量仍与结果相关：规范在未解决实例中有89%失败，而在已解决实例中这一比例为47%，这使得忠实规范合成成为一个具体的开放问题。

## Abstract
Ensuring the correctness of LLM-generated code is a core challenge for modern software engineering. Benchmarks for agentic code generation check correctness with held-out test suites, which are inherently incomplete and increasingly susceptible to memorization. Formal verification avoids both problems, but existing work covers only standalone tasks whose specifications are given as input, not real issues, which touch large repositories and state intent in vague natural language. We present Benchproofer, a pipeline that turns a coding task with a known correct patch into a formally verified one: it writes a specification for the new code, summarizes the existing functions that code calls with axioms, and admits an instance only after mechanical and adversarial gates agree. Applying it to SWE-bench Verified yields SWE-Proof, 500 real issues whose correctness is formally verified rather than tested, and it extends to SWE-bench Pro. Across two frontier models, verification catches what tests miss: a quarter to a half of test-passing patches admit counterexamples, which a structured natural-language specification does not fix, while a correct formal one lifts resolution from 85% to 95% for Opus 4.8. Writing that specification is the hard part: models that must write their own gain nothing over an unaided baseline, and only 62% of their specifications pass our audit. The usual failure is faithfulness, a specification that constrains part of the required behavior and leaves the rest free. Specification quality still tracks the outcome, failing on 89% of unresolved instances against 47% of resolved ones, making faithful specification synthesis a concrete open problem.

# SWE-Proof 论文详细总结

## 1. 核心问题与整体含义

- **研究动机**：LLM 生成代码的正确性评估目前主要依赖留出测试套件（held-out tests），但测试存在两个根本缺陷：
  - **不完备性**：有限输入无法证明未覆盖输入上的行为；审计发现 SWE-Bench 中许多"正确"补丁仅因测试太弱而通过。
  - **易被记忆化/奖励攻击**：智能体可利用测试的不完备性产生"通过测试但错误"的代码。
- **形式化验证的优势**：验证可覆盖整个规约域，而非采样输入，从根本上避免上述两个问题。
- **现存差距**：已有形式化验证工作只针对小型习题、独立 HumanEval 式任务或竞赛数学，且多数把形式化规约作为**输入**给出；真实编程任务需要新代码融入大型仓库、意图用模糊自然语言表达，此前没有适用于此类任务的可靠验证 oracle。
- **整体含义**：论文构建了 **SWE-Proof**——首个把机器可检验证明与真实 GitHub issue 任务配对的基准，并揭示"忠实规约合成"是验证式代码生成的关键未解难题。

## 2. 方法论

### 2.1 核心思想

- 提出 **Benchproofer** 流水线：把一个"有已知正确补丁"的编码任务转化为形式化验证任务，产出规约、公理、参考实现、前修复实现与证明。
- 中心保证 **Claim 1（Verify ⇒ Resolve）**：若实现 I 在公理 A 下满足规约 S，则等价补丁 P 能通过 SWE-Bench 隐藏测试。
- 两大支柱：
  - **环境公理化**：只建模新增/修改代码，对未改动的被调用函数（callee）用**公理**（弱于真实行为的上近似）概括，使验证可行。
  - **双重门控**：机械检查（验证器、编译器、容器执行）+ 对抗性 LLM 审计（构造反例）同时通过才接纳实例。

### 2.2 关键技术细节

- **规约合成**：构造阶段智能体可看到 ground-truth patch、buggy 代码、测试补丁、F2P/P2P 列表，用反馈循环把自然语言意图转成形式规约。
- **公理生成与验证**：收集未改动 callee，构建 fuzzer；智能体起草候选公理，两个对立循环分别检查：
  - **正确性循环**：fuzzer 执行真实 callee，任何违反公理的输入打回修改。
  - **有用性循环**：验证器尝试用该公理关闭证明，失败则打回。
  - 公理可过近似，但不能包含"修复本身"。
- **三个验证后端**：
  - **Nagini**：带契约注解的 Python，经中间验证语言翻译到 SMT 求解器；可表达可变堆状态与权限，代价是注解量大。
  - **Velvet**：嵌入 Lean 4 的命令式语言 DSL，用 SMT 支撑的 tactic 自动消解证明义务；最轻量。
  - **Pure Lean**：Lean 4 + Mathlib，规约是谓词，证明是内核检查的项；信任基最小，公理仅 3 条。
  - 另加 **EARS**（结构化自然语言）作为非形式化对照。
- **正确性门控（13 项）**：
  - 机械类：验证、判别（前修复实现必须失败）、变异（杀死率下限 80%）、卫生（无 `sorry` 等逃逸）、解析、公理可靠性、一致性（影子实现 vs 真实仓库代码）、任务同一性、披露。
  - 对抗类：可靠性/完备性攻击、基于属性的证伪、等价性审计、泄漏审计、四角色盲审面板。
- **三类边界**（无法形式保证，只能靠对抗审计）：
  - 意图—规约边界；
  - 公理—未改动 callee 边界；
  - 参考实现—补丁边界。

### 2.3 流程概览

1. 建模阶段：选择要建模的函数、载体表示，写出规约、参考实现、前修复孪生体。
2. 证明阶段：内核检查后端搜索证明项，不留开放义务。
3. 攻击阶段：四个盲审角色（保真、强度、忠实、披露）产出具体反例工件。
4. 接纳阶段：13 项检查全部通过才发布；负面结果送回对应阶段修订。

## 6. 主要结论与发现

- **发现 1：测试不完备，只有形式化规约能弥补**
  - 通过全部隐藏测试的补丁中 **26.8%** 被对抗审计推翻（存在真实反例）。
  - 形式化后端从行 6 到行 7 仅损失 0.9（Opus）/0.3（GPT）个百分点；EARS 则损失 17.8 / 46.0 个百分点，说明结构化自然语言不能闭合差距。
- **发现 2：自写规约无增益**
  - 端到端（行 2）相较无辅助基线（行 0）无显著提升，最好 cell 仅 +0.6 分，最差 −1.2 分。
- **发现 3：提供正确规约显著提升**
  - Opus 4.8 从 85.0% → 96.2%（Nagini），GPT-5.5 从 81.2% → 94.4%。
  - 扣除定位收益后仍 +6.9 / +7.7 分。
  - 与自写规约对比（行 7 vs 行 3），Nagini 下 +11.0 / +14.2 分。
- **发现 4：规约合成是瓶颈，忠实性是主因**
  - 五属性审计通过率：Opus 46.0–61.4%，GPT 64.2–72.0%。
  - **忠实性失败率最高**（42.5% / 30.0%），其他属性 ≤ 3.9–15.7%。
  - 模型写的规约"对建模的函数正确，但覆盖太少"。
- **发现 5：规约正确性与补丁正确性强相关**
  - 未解决实例中规约审计失败率 **89.4%**，已解决实例中 **47.3%**。
  - 差异主要来自忠实性（+44.3 分）与可靠性（+26.7 分）。
  - Mantel–Haenszel odds ratio ≈ 13.5，p < 1.7×10⁻³³。
- **扩展性**：SWE-bench Pro 上 242/266 任务在四后端下全部 green；22 个失败任务因补丁只改变名称/签名/表示/副作用，值级规约无法区分。

## 7. 优点

- **首创性**：首个把机器可检验证明 oracle 附加到真实仓库级软件工程任务的基准，覆盖 SWE-bench Verified 全部 500 个实例并扩展到 Pro。
- **方法论严谨**：13 项机械 + 对抗门控，明确区分"不适用"与"通过"；生成与审计分离、盲审、机械判决。
- **多后端设计**：三个形式化后端 + 一个非形式化对照（EARS），可分离"精确描述"与"机器检查"两种效应。
- **证据可复现**：每 bundle 附带操作级对应图、来源图、公理探测、属性测试套件、准入记录，总计 354 万行文本，支持独立重审。
- **受控实验设计**：9 种设置两两配对，只改变一个变量；4 次重复量化噪声；分层分析揭示增益来源（非局部性任务获益最大）。
- **诚实披露**：明确列出信任点、边界、放宽披露的实例、AI 使用声明、许可证与使用建议。

## 8. 不足与局限

- **Verify ⇒ Resolve 不是证明**：依赖两个经审计的信任点（公理可靠性、实现到补丁的细化保真），以执行、fuzzing、对抗审计建立，非形式化保证。
- **语言表达力限制**：每个后端继承其语言表达能力；少数实例需要人工建模（如导入时序副作用，偏正确性逻辑无法表达）。
- **次要属性放宽**：少数实例的规约视图泄露超过公开 issue 的信息（Verified 侧 17/37/11 个 bundle；Pro 侧 11 个），虽不影响 Claim 1，但削弱这些实例的评估效力。
- **审计面板是 LLM 校准面板**：其判决是证据而非证明；校准测量在非构造规约上完成。
- **模型不可复现**：托管 API 版本由提供商控制，无法复现；未训练/微调，也未发布权重。
- **SWE-bench Pro 覆盖不全**：266 个任务中 22 个（8.3%）无任何后端可建模，且失败原因非随机（排除重命名/重定位等非值级变更）。
- **训练数据污染风险**：语料公开且规模小，可能被记忆；作者建议训练过该语料的模型需声明。
- **单次运行为主**：非 Nagini 后端仅跑 1 次重复；行 1 和行 5 也只有 1 次重复，无法评估这些 cell 的方差。
- **规格审计的 prevalence 效应**：部分属性（如 completeness）κ 值低但原始一致率高，统计指标需谨慎解读。

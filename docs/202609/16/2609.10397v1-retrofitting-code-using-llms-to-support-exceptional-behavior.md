## 摘要
异常相关代码（Exception Related Code, ERC）包括 throw 语句、用于保护这些 throw 语句的条件（if 语句）以及 try/catch 块，是软件系统的重要组成部分，使开发者能够检测和处理偏离预期程序行为的异常状态。然而，在大型代码库中手动编写 ERC 十分繁琐。我们提出了一项新任务：用 ERC 改造现有代码。即，给定代码（不含 ERC）和异常行为测试（Exceptional Behavior Tests, EBTs）（例如，检查当参数传入 null 值时，方法是否抛出 InvalidArgumentException），我们的目标是自动生成缺失的 ERC，使得给定测试通过。我们设计并实现了 Exception Coder（EXCODER），它执行上下文工程，以帮助大型语言模型（Large Language Models, LLMs）完成该任务。EXCODER 通过向 LLM 提供所提取的上下文信息，将静态和动态程序分析与 LLM 集成起来。为了评估 EXCODER，我们构建了一个基于 GitHub Java 仓库的基准，其中我们系统性地移除了来自 75 个项目的 304 个方法中的 ERC。我们的结果表明，EXCODER 为自动代码生成中的这一问题提供了一种有效但并不完美的解决方案，为开发者提供了首个遵循测试驱动开发来实现 ERC 的途径。当与 Qwen 2.5 Coder 32b 结合时，EXCODER 在开发者编写的测试套件上分别达到 85.92%（比基线高 12.56 个百分点）、86.18%（比基线高 12.82 个百分点）和 86.51%（比基线高 13.15 个百分点）的 pass@1、pass@5 和 pass@10 通过率。我们对生成代码的人工检查进一步揭示了 EXCODER 的局限性，并指出了未来工作的方向。

## Abstract
Exception Related Code (ERC), which includes throw statements, conditions (if statements) that guard those throw statements, and try/catch blocks, is an essential component of software systems, allowing developers to detect and handle exceptional states that deviate from the expected program behavior. However, manually writing ERC across large codebases is tedious. We propose a novel task: retrofitting existing code with ERC. Namely, given code (without ERC) and Exceptional Behavior Tests (EBTs) (e.g., check if method throws InvalidArgumentException if null is given as the value to the argument) we aim to automatically generate missing ERC, such that the given tests pass. We design and implement Exception Coder (EXCODER) that performs context engineering to help Large Language Models (LLMs) tackle this task. EXCODER integrates static and dynamic program analysis with LLMs by providing the extracted contextual information to the LLMs. To evaluate EXCODER, we build a benchmark constructed from GitHub Java repositories, where we systematically remove ERC in 304 methods from 75 projects. Our results demonstrate that EXCODER provides an effective, though imperfect, solution to this problem in automated code generation, offering developers the first way to implement ERC following test-driven development. When combined with Qwen 2.5 Coder 32b, EXCODER achieves pass@1, 5, and 10 rates of 85.92% (12.56 percentage points over baseline), 86.18% (12.82 p.p. over baseline), and 86.51% (13.15 p.p. over baseline), respectively, on developer-written test suites. Our manual inspection of the generated code further reveals limitations of EXCODER, pointing to directions for future work.

# 论文总结：Retrofitting Code Using LLMs to Support Exceptional Behavior（使用 LLM 为代码加装异常相关代码）

## 1. 核心问题与研究动机

- **背景**：异常相关代码（Exception Related Code, ERC）包括 `throw` 语句、守卫 `throw` 的条件判断（如 `if`）、以及 `try/catch` 块，是保障软件可靠性的关键——显式报错可避免难以诊断的下游故障，并让调用方有能力处理异常。
- **痛点**：在大型代码库中手工编写 ERC 极其繁琐。开发者必须仔细推理"什么条件下算异常状态"，并定位应插入异常信号的**控制流分支位置**。
- **现有工作的缺口**：此前基于 LLM 的异常代码生成研究（如 Neurex、exLong、KPC 等）主要关注**避免未处理异常**（自动插入 try/catch 来消化异常），方向恰好相反；当开发者**主动希望**代码在特定条件下抛出特定异常时，这些方法不适用。
- **提出的新任务**：**用 ERC 改造现有代码（retrofitting）**。给定目标方法 `M`（已剥离 ERC）与一组**异常行为测试（EBTs）** `E = {e1, e2, …, en}`，自动生成 `M′`，使其满足所有 EBTs，同时不破坏原有正常功能（即仍通过所有非异常测试）。
- **为何用测试而非自然语言描述**：把"意图的异常条件"写成自然语言提示对开发者而言同样费时；而让开发者按**测试驱动开发（TDD）** 惯例提供触发异常的示例输入与 setup，是更直观的意图表达方式。
- **关键挑战**：已有 TDD 式 LLM 代码生成方法（生成—评测循环）未能充分利用 EBT 中蕴含的丰富信息（目标异常类型、触发异常的具体输入、setup 状态等）。
- **整体含义**：论文提出了该问题的首次形式化定义与首个自动化方案，使开发者能够以 TDD 方式实现 ERC。

## 2. 方法论：EXCODER

### 核心思想
不做端到端的"猜代码"，而是做**上下文工程（context engineering）**：用静态分析 + 动态分析从目标方法、EBTs 及所在仓库中抽取有用上下文，结构化地注入提示词，引导 LLM 生成正确的 ERC。一次提示处理**全部 EBTs**（而非逐个 EBT 单独提示），以降低调用开销并让模型整体规划异常条件结构。

### 静态分析抽取的上下文
- **`cExCons`（异常构造器）**：EBT 指定了目标异常类型，但构造器参数签名可能超出模型知识。EXCODER 先在仓库中查找同名 Java 文件收集其构造器签名与文档；若异常来自依赖库，则检查 class 文件，识别参数类型与顺序，拼装成 `public ExceptionName(PType0 arg0, PType1 arg1, ...)` 形式的签名。
- **`cAvSym`（可用符号）**：收集目标方法输入参数所属用户自定义类的所有 public 方法与字段，以及目标方法所在类中所有（public/private）方法与字段，仅保留签名与文档注释。用于生成语法正确、能合法访问对象状态的异常条件检查。

### 动态分析抽取的上下文
- **`cThrExc`（已抛出异常）**：用 JavaParser 预处理目标方法，把方法体包进 `try` 并追加捕获所有异常的 `catch`，同时记录既有 catch 块捕获的异常；执行每个 EBT，记录内部实际抛出的异常类型。用于处理"内部已抛异常但类型与 EBT 期望不同（需包装/转换）"的场景。
- **`cLCov`（行覆盖）**：用 Java instrumentation 记录 EBT 执行时目标方法内每行是否被执行。作用有二：把 ERC 的候选插入位置**限制在异常输入可达的分支内**；并帮助 LLM 推断分支条件的取值与导致异常的程序状态。
- **`cnEBTs`（非异常测试）**：执行项目全部测试并记录每个方法被哪些测试调用，从而为每个目标方法匹配覆盖它的非 EBT。用于对比"异常输入 vs 正常输入"，并确保插入 ERC 不改变正常执行路径。

### 提示词构造（文字化算法流程）
1. 先对目标方法 `M` 用 `fcom(·, cThrExc)` 注释：在每次运行 EBT 时抛异常的代码行插入行内注释，标明该处异常类型；
2. 再用 `fcom(·, cLCov)` 注释：在每行被覆盖处插入注释，标明是哪个 EBT 执行了该行；
3. 拼接其余上下文，最终提示为：

   `fcom(fcom(M, cThrExc), cLCov) ⊕ E ⊕ cExCons ⊕ cAvSym ⊕ cnEBTs`

   其中 `⊕` 为字符串拼接，`fcom` 表示以行内注释方式把上下文标注到给定方法上。
4. 将上述结构化提示交给 LLM，要求其输出**带 ERC 的新方法**；成功判据为 `M′` 通过全部 EBTs，且通过所有覆盖原方法的既有非异常测试。

### 数据集构建中的 ERC 移除规则（自动化剥离）
- `catch` 块内 `throw` → 删除整个 catch 块；若某 `try` 的所有 catch 块都含 `throw`，则删除整个 try/catch 并把 try 体语句外提。
- `then`/`else` 块仅含 `throw` 时，删除整个 if 或对应分支并外提另一分支语句；两分支都仅含 `throw` 则整体删除。
- `switch` 中含 `throw` 的 case 全部移除；若无可保留 case 则删除整个 switch。
- 最后清除残留 `throw`。该流程可能产生不编译的方法（38 个，占 12.5%：34 个"missing return statement"、4 个"unreported exception"），论文保留这些数据点，认为用户可能有意如此。

## 6. 主要结论与发现

- **EXCODER 在所有模型、所有指标上一致优于 Base**。以 Qwen 2.5 Coder 32b 为例：`pass@1/5/10 (All User)` 达 **85.92% / 86.18% / 86.51%**，分别提升 **12.56 / 12.82 / 13.15 个百分点**；`compiled@5` 提升 9.87 p.p.；`pass@5 (All User+Tools)` 提升 12.17 p.p.。
- **GPT-5 Mini 上同样显著**：`pass@1/5/10 (All User)` 达 **95.03% / 97.92% / 98.36%**，相对 Base 提升 12.30 / 8.27 / 6.91 p.p.，说明增益并非只对弱模型有效。
- **覆盖增益明显**：以 `pass@10 (All User)` 衡量，EXCODER 解出了 Base 无法解出的 **48** 个任务，仅丢失 Base 能解出的 **8** 个（作者归因于额外上下文带来噪声），净收益显著。
- **上下文组件价值分层**：`cAvSym` 与 `cExCons` 单独使用即带来大幅提升（最易被 LLM 利用）；`cLCov`、`cThrExc`、`cnEBTs` 增益较小且只在 pass@5/@10 上显现，因为它们描述的是**程序行为而非待生成代码**，需要模型推理程序状态与控制流，难度更高。
- **复杂度影响**：EXCODER 在每个长度与复杂度分箱中都 ≥ Base；优势最大出现在 6–14 行方法与圈复杂度为 2 的方法（中等复杂度，既有复杂条件、又不足以从代码本身获取足够信息），在圈复杂度 5+ 时优势回升到 12.8 p.p.。
- **自修复互补但不可替代**：4 轮修复后 Iter-Base 达 84.47%（`pass@5 All User`），Iter-EXCODER 达 **96.22%**，仍领先 11.75 p.p.；多数任务在第一轮修复即解决，说明编译器/测试反馈只能解决表层错误，无法弥补上下文缺失。
- **假阳性问题未随上下文改善**：Base 与 EXCODER 的假阳性率分别为 25.56% 与 24.71%（差 0.8 点），各类别占比差异均不超过 1.8 点。其中 **"Too Lenient"（生成条件比 ground truth 更宽松）占约 63–65%**，是主要假阳性来源——根因在于 EBT 覆盖不足，更弱的条件检查也能通过全部测试。
- **等价性提升**：人工判定生成 ERC 与 ground truth 功能等价的比率，Base 为 54.61%（166/304），EXCODER 为 65.13%（198/304）。

## 7. 论文的局限性与威胁有效性（Threats to Validity）

### 7.1 内部有效性
- **ERC 自动剥离规则的副作用**：论文的删除式剥离流程会产生 **38 个（12.5%）不可编译**的改造后方法（34 个 *missing return statement*、4 个 *unreported exception*）。作者选择保留而非修复，理由是"真实用户也可能提交这种不完整代码"，但这同时意味着部分任务在 Base 与 EXCODER 上都存在**天然不可编译**的起点，可能压低 `compiled@k` 的绝对值，且该比例在不同方法间的分布未作细分报告。
- **ground truth 作为唯一参照的隐含假设**：等价性判定以原始（未剥离）实现的 ERC 为"标准答案"，但原始代码本身未必是最优或唯一正确的异常处理方式（例如可能用了更宽松的守卫条件）。论文通过假阳性分类部分缓解了这一点，但"Too Lenient"的判定仍以 ground truth 为标尺，可能低估了某些语义上合理但风格不同的实现。
- **EBT 覆盖不足这一根因未被动摇**：假阳性率在加入大量上下文后几乎不变（25.56% → 24.71%），说明问题出在**测试本身的判别力**，而非生成质量。论文诚实地将其列为主要假阳性来源，但也意味着 EXCODER 的增益主要体现在"解出率"而非"语义精确度"上。

### 7.2 外部有效性
- **语言与生态局限**：数据集全部来自 Java/Maven 项目，异常模型（checked/unchecked、`throws` 声明、`try-with-resources`）与 C#、Python、Go（显式 `error` 返回）差异显著。方法能否迁移到无 checked exception 或采用错误码的语言，论文未做验证。
- **测试驱动前提**：方法强依赖已有 EBT。对于缺乏异常测试的遗留代码库，用户必须先自行编写 EBT——论文虽论证了这比写自然语言描述更省力，但**冷启动成本**依然存在，且 EBT 质量直接决定上限（见"Too Lenient"问题）。
- **仓库级上下文的依赖**：`cExCons`、`cAvSym` 依赖可解析的源码/字节码与文档注释。在只有二进制依赖、或文档缺失的工业环境中，这两类上下文可能大幅退化。论文未报告上下文抽取失败的比率。
- **模型时效性**：评测覆盖 7b–32b 开源模型与一个闭源模型。作者在 2026 年 1 月前采集数据，模型能力迭代迅速，绝对数值可能很快过时；但**Base 与 EXCODER 的相对差距**这一核心结论应更稳健。

### 7.3 构念有效性
- **`pass@k (All User+Tools)` 的 oracle 强度有限**：EvoSuite/Randoop 生成的测试平均仅 77 条/方法，且只保留"能在目标方法内触发异常"的用例，天然偏向**触发**而非**不触发**的边界，难以捕捉"过于宽松"的条件（这正是最大假阳性类别）。
- **人工标注规模**：仅对 Qwen 2.5 Coder 32b 的通过样本做等价性判定（Base 223 + EXCODER 263），其余模型仅有自动指标。κ 值 0.77–0.87 属"substantial"但非"almost perfect"，仍存在标注噪声。

## 8. 实践启示与未来工作方向

### 对开发者的直接启示
1. **写 EBT 是值得的投入**：即使 EBT 覆盖不完美，配合静态/动态上下文后 EXCODER 仍能在 32b 级开源模型上达到 86% 的 `pass@10 (All User)`，接近可用门槛。
2. **模型选择上"代码专用"与"规模"并非唯一决定因素**：GPT-5 Mini 在 Base 提示下已达 82.7%，说明通用强模型对异常语义的理解本身较强；EXCODER 的价值在弱模型上更突出（相对增益更大）。
3. **不要跳过人工审查**：约四分之一的"通过全部测试"的生成结果与 ground truth 语义不等价，其中约 2/3 是条件过宽，会在生产环境中**漏掉本该抛出的异常**——这恰恰是 ERC 的核心目的，因此测试通过 ≠ 可合并。

### 论文指出的未来工作
- **提升 EBT 质量/数量**：既然"Too Lenient"是主导性假阳性来源，自动生成能区分强弱条件的异常测试（如边界值、负向测试）可能比继续堆叠上下文更有效。
- **更细粒度的上下文注入**：当前上下文以行内注释方式平铺注入，`cLCov`/`cThrExc` 的效果受限于模型对控制流的推理能力，未来可探索结构化表示（如控制流图、符号执行路径约束）。
- **迭代式方法**：自修复与上下文工程呈互补关系（Iter-EXCODER 96.22%），结合更强的反馈信号（如运行时状态、变量取值）仍有空间。
- **扩展到其他语言与异常模型**。

## 9. 总体评价

### 优点
- **问题定义清晰且填补空白**：把"主动抛出异常"这一与主流"避免未处理异常"相反的方向形式化，任务边界（M + EBTs → M′）明确、可复现、可直接落地到 TDD 工作流。
- **方法朴素但有效**：不做端到端训练，纯靠"静态分析 + 动态分析 + 提示词工程"，工程可行性和可迁移性强，任何具备代码能力的 LLM 都能直接使用。
- **实验设计严谨**：5 模型 × 完整消融 × 复杂度分层 × 自修复对照 × 独立自动 oracle × 人工等价性判定，且**主动报告失败案例**（8 个 Base 胜出案例），避免了选择性汇报。
- **诚实面对局限**：明确指出假阳性未改善、EBT 覆盖不足是根因，并保留不可编译样本，学术诚信度高。

### 不足与可改进之处
- **消融与人工分析仅限单一模型**（Qwen 2.5 Coder 32b），结论在其他模型上的普适性缺少直接证据。
- **验证集仅用于设计决策**，未报告量化结果，削弱了"超参/组件选择无过拟合"的说服力。
- **未报告上下文抽取的失败率与耗时**，而这在工业仓库（依赖复杂、文档缺失）中是关键可行性指标。
- **未与"非 LLM"的静态异常推断/符号执行方法对比**（如基于契约推断的工具），削弱了"必须用 LLM"这一前提的论证力度。
- **等价性判定仅以 ground truth 为标尺**，未讨论"ground truth 本身是否过宽/过严"。
- 未报告 **API 成本**，虽然本地量化推理的成本友好性可推断，但对闭源模型的部署可行性缺少量化支撑。

### 一句话定位
这是一篇**任务定义驱动、工程扎实、实验诚实**的论文：它不追求方法上的炫技，而是通过"把正确的上下文喂给 LLM"这一朴素洞察，在一个此前无人涉足的任务上建立了首个可用的基线，并用大量消融与人工检查划清了"LLM 能做什么、还不能做什么"的边界——尤其是揭示了**测试覆盖不足导致的假阳性是当前范式下最难跨越的瓶颈**。

## Abstract
Code agents are increasingly trusted to autonomously fix bugs on platforms such as GitHub, yet their security evaluation focuses almost exclusively on functional correctness. In this paper, we reveal a novel type of threat to real-world code-agents: functionally correct yet vulnerable (FCV) patches, which pass all test cases but contain vulnerable code. With our proposed FCV-Attack, we demonstrate that SOTA LLMs (e.g., ChatGPT and Claude) and agent scaffolds (e.g., SWE-agent and OpenHands) are all vulnerable to this FCV threat; across 12 agent-model combinations on SWE-Bench, the attack only requires black-box access and a single query to the code agent to perform the attack. For example, for CWE-538 (information exposure vulnerability), the FCV-Attack attains an attack success rate of 40.7% on GPT-5 Mini + OpenHands. Our results reveal an important security threat overlooked by current evaluation paradigms and urge the development of security-aware defenses for code agents.

- **背景**：基于大模型的代码智能体（如 SWE-agent、OpenHands、Mini-SWE-Agent）已能自主读取仓库、修改代码、运行测试并提交补丁，在 SWE-bench 等真实软件修复任务上表现突出。

## 2. 方法论：FCV-Attack

### 2.1 核心思想

- 攻击者将**面向特定 CWE 的恶意指令**伪装成开发者风格的“良性建议”，追加到 GitHub issue 描述中，诱导代码智能体生成功能正确但含目标漏洞的补丁。
- 攻击目标：使最终补丁同时满足：
  1. 解决原 issue 并通过完整测试套件；
  2. 包含攻击者指定的 CWE 类型漏洞。

### 2.2 威胁模型

- **黑盒访问**：攻击者只能通过公开接口编辑/提交 issue 文本，无法访问模型权重、智能体内部结构、检索模块或执行环境。
- **单次查询**：不进行多轮反复查询或对抗优化，以提高隐蔽性并贴近真实开发流程。
- **现实性**：外部贡献者或普通用户即可通过常规 issue 工作流实施攻击。

### 2.3 攻击流程

1. **构造 CWE 注入模板**：将目标漏洞包装成合理开发意图，例如：
   - CWE-538：以“更好的调试与监控”为由，建议记录敏感变量；
   - CWE-79：以“更好的用户体验”为由，建议直接将用户输入嵌入 HTML；
   - CWE-89：以“数据库灵活性/快速原型”为由，建议动态拼接 SQL；
   - CWE-94：以“灵活数据处理”为由，建议使用 `eval()`。
2. **注入 issue**：将模板追加到原始 issue 描述后，提交给代码智能体。
3. **生成与验证**：智能体生成补丁后，经官方 SWE-bench 测试流程验证功能正确性，再由 LLM 漏洞判定器判断是否包含目标 CWE。
4. **成功判定**：仅当补丁**功能正确且含目标 CWE**时，记为一次成功的 FCV 攻击。

### 2.4 关键指标与公式

- 设 \(N\) 为受攻击实例总数，\(n_{\text{pass}}\) 为生成功能正确补丁的实例数，\(n_{\text{pass yet vuln}}\) 为功能正确且含目标漏洞的实例数。
- **Pass@1**：  
  \[
  \text{Pass@1}=\frac{n_{\text{pass}}}{N}
  \]
- **FCV Rate**：功能正确补丁中仍含漏洞的比例：  
  \[
  \text{FCV Rate}=\frac{n_{\text{pass yet vuln}}}{n_{\text{pass}}}
  \]
- **Attack Success Rate（ASR）**：  
  \[
  \text{ASR}=\frac{n_{\text{pass & vuln}}}{N}=\text{Pass@1}\times\text{FCV Rate}
  \]
- **ASR\***：宽松变体，只要补丁含四类 CWE（538/79/89/94）中的任意一种即计为成功。

### 2.5 受控轨迹变体

- 先记录智能体在干净 prompt 下的完整轨迹，直到生成补丁前一步。
- 将 FCV 指令插入初始 system prompt / 用户 issue 之后，再强制智能体重放干净轨迹的中间步骤，之后允许自然生成。
- 目的：检验漏洞是否来自可观察的交互历史，还是来自模型内部状态污染。

## 6. 主要结论与发现

- **所有测试的 12 种 agent–model 组合均被成功攻击**，总体 ASR\* 范围为 **18.1%–62.9%**。
- 最高结果包括：
  - SWE-Agent + GPT-5-mini：ASR\* **62.9%**；

  - OpenHands + Claude-Sonnet-4：CWE-538 ASR **55.6%**；
  - GPT-5-mini + OpenHands：CWE-538 ASR **40.7%**。
- **CWE-538 最易被利用**：日志/调试类建议看起来无害，且模型被训练为“有帮助”，容易接受并写入敏感信息。
- **更强的指令跟随能力不一定更安全**：Claude-Sonnet-4 和 GPT-5-mini 的平均 ASR 反而较高（约 14.0% 和 13.7%）。

- **任务越简单越易受攻击**：FCV Rate 随 API 调用数和任务难度增加而下降，简单任务中智能体更可能采用浅层模式匹配和不安全捷径。

## 9. 启示与未来方向

### 9.1 对评测范式的启示

- “通过全部单元测试”应被视为**必要非充分**条件；代码智能体评测需引入**安全维度**（漏洞注入率、CWE 分布、补丁攻击面变化）。
- 建议将 FCV Rate 作为与 Pass@1 并列的标准报告指标，避免“高分掩盖高风险”。
- 安全评测应覆盖**良性无攻击设置**，因为论文显示即便无攻击也有 4.3%–6.0% 的功能正确补丁含弱点，说明部分风险源于模型自身习惯而非外部诱导。

### 9.2 对智能体设计的启示

- **指令来源需分级信任**：issue 文本属于不可信输入，其中的“实现建议”不应与系统指令同等对待；应区分“需求描述”与“实现指导”。
- **行为级监控不足**：由于污染可能发生在初始编码阶段并持续影响后续决策，仅靠逐步行为审计或轨迹重放无法拦截，需要在**补丁生成后**做独立安全审查。
- **能力与安全非正相关**：更强指令跟随能力的模型反而更易被“合理化建议”说服，说明对齐训练中“有帮助性”与“安全性”存在张力。
- **简单任务更危险**：简单任务中模型倾向浅层模式匹配与捷径，提示应针对低复杂度任务加强安全约束。

### 9.3 对防御实践的启示

- Prompt 级防御只能部分缓解，需构建**纵深防御**：输入侧（issue 建议过滤/标注）、生成侧（安全约束解码）、输出侧（补丁静态扫描 + LLM 复核 + 人工抽检）。
- 可将 CWE 定向检测器（如按 CWE 分类的静态规则）集成到 CI，对智能体提交的补丁做强制安全门禁。

### 9.4 未来研究方向

- 跨语言、跨 benchmark（如 Multi-SWE-bench、C/C++ 内存安全任务）的泛化验证；
- 自适应、多轮、反馈驱动的更强攻击，以及自动化注入模板搜索；
- 引入人工标注与多 judge 集成，提升漏洞判定的可靠性；
- 系统化防御评估，量化安全—功能—效率的权衡；
- 探索训练阶段的安全对齐（如针对“合理化建议”的抗诱导训练）与推理阶段的状态隔离机制；
- 深入机制研究，验证内部状态污染假说。

## 10. 总体评价

- **贡献层面**：论文提出了一个简洁但重要的新问题——FCV 补丁，并以较低攻击成本（黑盒、单次查询、issue 文本注入）证明了其普遍性（12/12 组合均被攻破，ASR* 达 18.1%–62.9%），对“测试通过即安全”的行业惯性构成有力反驳。
- **方法层面**：攻击设计贴合真实开源协作流程，指标分解（ASR = Pass@1 × FCV Rate）清晰，Controlled-Trajectory 与复杂度分析提供了有价值的机制线索。
- **证据层面**：实验覆盖面较广（3 框架 × 4 模型 × 4 主 CWE + 扩展 + 消融 + 防御），但受限于样本不均衡、单一 LLM judge、固定模板与单语言基准，结论的统计稳健性与泛化边界仍需加强。
- **影响层面**：该工作更偏向**问题揭示与风险量化**，而非提供完整防御方案；其最大价值在于推动代码智能体评测从“功能正确”走向“功能正确且安全”，并为后续防御研究设定了明确的基线威胁模型。
- **定位判断**：作为一篇安全威胁分析论文，其新颖性、现实性与可复现性较强；若能在判定可靠性、跨语言泛化与系统防御评估上补强，将进一步增强其说服力与实用价值。

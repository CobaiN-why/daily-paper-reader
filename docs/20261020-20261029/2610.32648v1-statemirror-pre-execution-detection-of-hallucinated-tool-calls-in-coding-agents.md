## 摘要
基于大语言模型（LLM）的编程智能体可能提出在执行环境中不适用的无效动作，例如访问不存在的路径或缺失的软件包。我们将这种不匹配称为幻觉工具使用。对 4,398 条智能体轨迹的初步研究表明，这类幻觉普遍存在且代价高昂，恢复所需的中位数为 3 个额外交互步骤和 22.4K 个 token。现有框架依赖反应式的执行后反馈，浪费运行时资源。然而，由于智能体的执行环境以具体代码库和 harness 组件为基础，许多动作前提条件可以在执行前被提取并验证。为此，我们提出 StateMirror，一种轻量级的执行前检测器。StateMirror 在 harness 边界拦截动作，通过 AST 和命令分析提取状态谓词，并针对实时仓库确定性地验证这些谓词。通过在執行前精确定位确切的环境不匹配，StateMirror 可预先阻止无效动作及后续恢复周期。在 2,508 个动作上的评估表明，StateMirror 在检测此类幻觉时达到 0.940 的精确率和 0.817 的 F1，相比最强的 LLM 评判器在 F1 上提升 35.3%，同时将中位检测延迟从 17.73 秒降至 1.50 毫秒，且 token 消耗为零。在实际缓解方面，StateMirror 的执行前反馈使智能体能够纠正超过 95% 的幻觉工具调用。在 79 个任务上的实时缓解过程中，StateMirror 将智能体执行时间减少 15.8%、token 消耗减少 11.8%，同时保持任务解决率。

## Abstract
Large language model (LLM)-based coding agents may propose invalid actions that are not applicable in the execution environment, such as accessing non-existent paths or missing packages. We term this mismatch hallucinated tool use. A preliminary study of 4,398 agent trajectories reveals that these hallucinations are pervasive and costly, requiring a median of 3 additional interaction steps and 22.4K tokens to recover. Existing frameworks rely on reactive, post-execution feedback, wasting runtime resources. Nevertheless, since an agent's execution environment is grounded in concrete codebase and harness components, many action prerequisites can be extracted and validated prior to execution. To this end, we introduce StateMirror, a lightweight pre-execution detector. StateMirror intercepts actions at the harness boundary, extracts state predicates via AST and command analysis, and deterministically validates them against the live repository. By pinpointing exact environment mismatches before execution, StateMirror preempts invalid actions and subsequent recovery cycles. Evaluation on 2,508 actions shows StateMirror achieves 0.940 precision and 0.817 F1 in detecting such hallucinations, surpassing the strongest LLM judge by 35.3% in F1 while reducing median detection latency from 17.73 s to 1.50 ms with zero token consumption. For practical mitigation, StateMirror's pre-execution feedback enables agents to rectify over 95% of hallucinated tool calls. During live mitigation on 79 tasks, StateMirror reduces agent execution time by 15.8% and token consumption by 11.8% while maintaining task resolution.

## 1. 核心问题与研究动机

- **问题定义**：论文提出“幻觉工具使用”（hallucinated tool use）这一失效模式——LLM 编程智能体（coding agent）提出的工具调用隐含了执行环境中并不成立的前提，例如访问不存在的文件路径、导入未安装的包、引用未导出/未定义的符号、使用不符合 harness 参数签名的工具参数等。这类动作在语法上往往合法，但在当前工作区状态下“根本不可执行”。
- **与既有概念的区分**：它不同于推理错误或语义层面的代码 bug（后者能执行但结果错误），其本质是动作与环境状态的不匹配。
- **初步研究的量化证据**（4,398 条 SWE-agent 轨迹、120,801 次调用、9,595 次确认幻觉）：
  - **普遍性**：46.6% 的失败轨迹、32.3% 的成功轨迹受影响；同一轨迹内可反复出现（失败轨迹平均 5.3 次，成功轨迹 3.1 次）。
  - **代价高**：一次“幻觉片段”恢复到有依据的重试，中位需 3 个 agent 步骤与 22.4K token；1,120 个恢复片段共消耗 39.3M token；30.3% 的片段从未被重试，最终导致任务失败。
  - **根因集中**：文件系统/cwd 类占 43.33%，Python 命名空间/包布局类占 41.93%，二者合计超过 85%，且均可表示为可判定的具体谓词。
- **现有方法的缺口**：主流方案是“执行后反馈”（依据 traceback 纠错）或 LLM-as-a-judge 审计执行历史，前者在错误已发生后浪费运行时资源，后者引入推理开销与判断偏差；静态 linter 只查语法/局部构造错误，不做仓库级解析。
- **整体含义**：既然 agent 的执行环境由具体代码库与 harness 构成，动作前提就可以在执行前被抽取并确定性校验，从而把“事后恢复”转为“事前拦截”。

## 2. 方法论：StateMirror

### 2.1 核心思想与形式化

- 把动作隐含的环境假设显式化为**类型化谓词**，再用**只读、确定性的探针**在真实工作区上求值；只要存在被证伪的谓词，就判定为幻觉工具调用。
- 形式化定义：设 $s$ 为动作执行前的工作区与 harness 状态，$a$ 为提交的结构化动作，$\phi(a)$ 为 $a$ 隐含的谓词集合，$\psi(p,s)$ 为谓词 $p$ 在状态 $s$ 下的探测函数，则幻觉集合为
  $$H(a,s)=\{\,p \mid p\in\phi(a),\ \psi(p,s)=\text{false}\,\}$$
  当 $H(a,s)\neq\emptyset$ 时，$a$ 被判为幻觉工具调用。

### 2.2 四阶段流水线

- **① 归一化（Normalization）**：将 shell 命令、结构化工具调用等异构动作统一表示为「动作类型 + 当前工作目录 + 工具参数 + shell 命令 + 关联 Python 代码」；对 `python xxx.py` 这类命令，会从工作区读取并内联被调用脚本的源码，使后续能分析真正被执行的代码。
- **② 谓词抽取（Extraction）**：按动作类型分析 shell 命令、工具参数与 Python 代码；Python 代码按需解析为 AST，识别导入、符号引用、文件操作、测试目标等；**静态无法确定的取值直接省略该谓词**（宁漏勿错）。
- **③ 环境探测（Probing）**：对每个谓词做只读检查（仓库结构、模块定义与 `__init__.py` 再导出、文件系统元数据、运行时信息、harness schema）；**无法可靠判定时保守放行，并把不确定性记入证据**。
- **④ 报告（Reporting）**：汇总为 false-predicate 集合，输出带类型的警告（谓词种类、参数、证据），例如“`symbol_defined("dvc","DVC")` 为假：`dvc` 存在但未定义或再导出 `DVC`”。

### 2.3 四类谓词族

- **Family I：Python 命名空间与包布局**——`importable`、`symbol_defined`、`is_package`；同时检查模块可用性与命名空间内容（含再导出），覆盖标准库、已安装包与仓库内模块；依赖分析仅限动作或其调用脚本中直接引用的导入，以控制开销。
- **Family II：文件系统与 cwd**——相对路径按 cwd 解析，并按操作语义区分要求：读/执行需 `file_exists`，写/创建需 `parent_dir_exists`。
- **Family III：命令、测试与运行时**——`executable_available`、`pytest_target_exists`（查目标文件 + AST 中的测试节点）、`runtime_version_satisfies`。
- **Family IV：harness 与工具 schema**——`tool_args_valid`、`tool_path_arg_exists`、`editor_file_open`、`editor_line_in_range`、`path_absent`；可从前序工具响应推断当前打开文件。
- 架构上各谓词族可插拔，新增工具/语言只需补充对应的 extractor 与 prober。

### 2.4 缓解机制

- 两种运行模式：**report 模式**（只记录警告不阻断）与 **intervention 模式**（保守阻断并提示重生成）。
- 阻断规则保守：仅当被证伪的谓词是“必要条件”（如待读文件、待执行程序）时阻断；对“有意副作用”（动作本身要创建的文件）和诊断性错误（既有测试文件内的缺依赖）放行；测试命令仅在测试目标或 runner 本身缺失时阻断。
- 警告会附带重生成指令（提示 agent 先用 `ls`/`find`/`grep`/`view` 核实真实仓库状态）。

## 摘要
从 UI 截图生成可运行的前端代码是自动化软件工程中的一个长期目标。现有基于 MLLM 的方法主要集中于 HTML/CSS，而对 React/Vue/Angular 的多框架生成研究不足。简单地修改提示词会导致多框架间显著的性能差距以及高度框架特定的错误模式。为解决这一问题，我们提出 MulFCoder，一种框架条件化的多智能体方法，它显式编码框架约束，将多框架差异引入可判定的规则空间。MulFCoder 编排四个智能体：Grounder 从检测到的 UI 元素构建 ElementTable、ContentTable 和宏布局区域；Planner 构建类 DOM 的层次布局树，生成任务调度，并推导出框架特定的文件 Contract；Writer 在受限编辑窗口内生成结构化文件写入或补丁；Judger 执行轻量级、框架条件化的约束，以接受或拒绝更新并触发有界修复，从而在无需昂贵构建的情况下防止漂移和死锁。实验表明，MulFCoder 显著提高了编译成功率并减少了框架特定错误，在 Angular 上提升尤为明显。

## Abstract
Generating runnable front-end code from UI screenshots is a long-standing goal in automated software engineering. Existing MLLM-based methods predominantly focused on HTML/CSS, leaving multi-framework generation for React/Vue/Angular underexplored. Naively modifying prompts leads to substantial performance gaps across multi-framework and highly framework-specific error modes. To address this, we propose MulFCoder, a framework-conditioned multi-agent method that explicitly encodes framework constraints to bring multi-framework differences into a decidable rule space. MulFCoder orchestrates four agents: Grounder constructs an ElementTable, ContentTable, and macro-layout regions from detected UI elements; Planner builds a DOM-like hierarchical layout tree, produces a task schedule, and derives a framework-specific file Contract; Writer generates structured file writes or patches within a restricted edit window; Judger enforces lightweight, framework-conditioned constraints to accept or reject updates and trigger bounded repairs, preventing drift and deadlocks without expensive builds. Experiments demonstrate that MulFCoder substantially improves compilation success rate and reduces framework-specific errors, with particularly pronounced gains on Angular.

## 1. 核心问题与研究动机

- **背景**：从 UI 截图自动生成可运行前端代码是自动化软件工程的长期目标。传统方法依赖 CNN-RNN、DSL 或 HTML/CSS 生成；随着多模态大模型（MLLM）兴起，UI-to-code 转向直接从像素合成可执行代码。
- **核心问题**：现有 MLLM 方法几乎只聚焦 HTML/CSS，对 React/Vue/Angular 等主流工程框架的**多框架生成**缺乏系统研究。仅靠修改提示词（prompt transfer）切换目标框架，会造成显著的编译成功率下降和高度框架特定的错误模式。
- **关键观察（图 1）**：
  - 同一批模型在 Vanilla/React/Vue/Angular 上的 CSR 分别为 1.000 / 0.922 / 0.862 / 0.762，呈明显梯度下降。
  - 错误分布高度框架特异：React 以 JSX 解析、`use client` 等为主；Vue 集中于模板闭合与属性错误；Angular 集中于组件导入/导出、绑定与模块级一致性。
- **根因判断**：多框架差异不是语法糖替换，而是**语言规则、组件边界约定、项目脚手架约束**的联合变化。若不显式建模这些约束，模型在长程生成中易漂移，错误难以定位和修复。
- **总体含义**：论文主张把多框架差异“坍缩”进一个**可判定、可执行的规则空间**，用多智能体协作 + 框架条件化硬约束替代一次性长文本生成。

## 2. 方法论：MulFCoder

### 2.1 核心思想

将 UI→Code 从“一次性长文本生成”分解为**角色专业化 + 分步验证**的协作流程，并以**框架条件化的文件级 Contract** 驱动生成与修复。四个智能体：Grounder → Planner → Writer ⇄ Judger。

### 2.2 Grounder（元素与内容稳定化）

- 使用 UIED 算法检测候选 UI 元素：`E(x) = {(t̂_k, b̂_k)}`，其中 `t̂_k` 为元素类型，`b̂_k ∈ [0,1]^4` 为归一化 BBox。
- 执行 OCR 得到文本片段 `O(x) = {(r_j, s_j)}`，按几何覆盖率绑定到最兼容元素：
  - `cov(r, b) = area(r ∩ b) / area(r)`
  - `assign(j) = argmax_k cov(r_j, b̂_k)`
- 覆盖率不足的片段不分配以减少错配；同一元素多片段按阅读顺序聚合。
- 输出三张结构化表：
  - **ElementTable**：语义类型、BBox、稳定标识 `eid`；
  - **ContentTable**：文本元素存规范化文本与置信度，视觉元素存裁剪坐标等引用；
  - **宏布局 L**：header/sidebar/main/footer 等粗粒度区域划分，提供稳定结构先验。

### 2.3 Planner（布局规划 + 任务调度 + Contract 构造）

- **类 DOM 布局树**：构建有序根树 `T`，内部节点为容器（区域、卡片、列表块），叶节点为 `eid`；每个容器标注布局原语（row / column / grid / overlay），由轻量几何启发式选择（水平主导→row，垂直主导→column，二维对齐→grid，强重叠→overlay）。
- **任务分解与调度**：将 `T` 分解为任务序列 `S = {τ_1, ..., τ_n}`，每个任务锚定子树根并携带结构描述与内容切片索引；遵循“**局部优先、后组装**”原则，先合成宏区域/区域子树，再生成根级全局组装，使局部失败不破坏全局脚手架。
- **框架 Contract K** 由三部分组成：
  - `K_policy`（框架范式不变量）：Angular 强制 standalone 范式（`standalone: true`、`imports: [*]`）；Vue 标准化单文件组件；React 强制 TSX 函数组件 + 显式导出；Vanilla 约束为 HTML + 模块化 JS/TS。
  - `K_perm`（权限窗口）：规定可写文件与禁止触碰的敏感区域（lockfile、关键配置），防止越界修改。
  - `K_bind`（任务绑定）：定义任务 `τ` 到框架特定目标形式集合 `T(f)_τ` 的映射——同一子树任务在 Vue 对应单个 SFC、React 对应 TSX 组件、Angular 对应 `component.ts` + `component.html` 对、Vanilla 对应 HTML 片段 + 模块化渲染函数。

### 2.4 Writer（受限生成与修复）

- **FILE 模式**：以子树 `T[τ]`、内容切片 `C_τ`、Contract `K` 为输入，按“**结构优先、内容回填**”顺序生成：先容器与布局骨架，再叶节点 UI 原语，最后回填文本与资源引用，降低长上下文漂移。
- **PATCH 模式**：Judger 报错后触发，输入为当前候选产物（限于权限窗口可见子集）、失败反馈（失败簇、定位信号、证据）、当前任务 `τ` 与 `K`；优先保留已通过检查的结构，做最小必要局部修复，避免引入新结构重排。

### 2.5 Judger（轻量门控 + 死锁避免）

- **四级门控流水线**（逐步收紧可行域）：
  1. 输出可执行结构检查（能否稳定解释为写入/编辑操作，字段与类型约束）；
  2. 目标框架下的基本解析可行性（括号平衡、模板块完整、标签闭合等）；
  3. 解析后依赖与作用域一致性（导入/声明完整性、模板引用可见性、元数据 linkage）；
  4. Contract 一致性（只触碰允许目标、避开保护区、关键产物存在且符合任务级输出形式）。
- **死锁避免**：为每个子任务分配有界修复预算，对失败反馈做签名以检测实质进展；若多轮后失败模式不变，则终止分支并回滚到最近状态。

## 6. 主要结论与发现

- **CSR 提升呈框架梯度**：
  - React：Design2Code 平均约 +3.8%，DesignBench 约 +6.2%；
  - Vue：约 +6.6% / +8.2%；
  - Angular：约 +10.2% / +9.0%，收益最大，印证“工程约束越强、显式约束建模收益越大”。
- **能力分层效应**：弱 backbone（Qwen2.5-VL-7B、LLaVA-v1.5-7B）相对收益更大，说明方法把框架知识外化为可执行约束，具有“短板补偿”作用。
- **视觉相似度**：Vanilla 下 CSR 已饱和，CLIP 平均相对提升约 3%–7%；严格工程框架下 CLIP 接近“不退化、偶有小幅提升”。
- **工程权衡（Engineering Trade-off）**：为修复编译错误，模型有时需简化复杂 UI 组件，导致严格框架下视觉相似度饱和或略降。
- **错误修复率**：React/Vue 较高（Design2Code 平均 48.4% / 50.6%），Angular 最低（43.4% / 31.2%），且 DesignBench 上明显下降，说明 Angular 失败更多源于跨文件全局一致性，难以靠局部改写修复。
- **错误分布变化**：MulFCoder 不仅降低错误总数，还降低了各框架主导错误类别的占比；Angular 残余错误更顽固、更集中。

## 7. 优点

- **问题定义清晰**：系统揭示 prompt-only transfer 的编译不连续性与框架特定错误模式，动机有数据支撑（图 1）。
- **约束显式化**：把框架差异从隐式提示转为可判定的 Contract（policy / permission / binding），思路具有可迁移性。
- **分工合理**：Grounder 固定内容与空间骨架、Planner 固定结构与工程形态、Writer 受限生成、Judger 轻量门控，职责边界清楚。
- **低成本验证**：Judger 不依赖完整构建即可提供可解释的失败归因与定位，配合有界修复预算与回滚机制，避免死锁。
- **结构优先 + 内容回填**的生成顺序对 OCR 噪声具有鲁棒性。
- **跨 5 个 backbone、4 个框架、2 个数据集验证**，泛化性证据较充分；错误分析细致，案例具体可复现。

## 8. 不足与局限

- **推理开销未报告**：多智能体多轮调用带来的 token 成本、延迟、API 费用均缺失，难以评估实际工程性价比。
- **缺少消融**：无法判断各 agent 与 Contract 各组成部分的边际贡献，方法必要性论证不完整。
- **对比基线单一**：仅与 prompt transfer 比较，未与现有 agentic / 分层规划方法横向对比。
- **视觉保真与可编译性的张力**：严格框架下 CLIP 饱和或略降，说明方法偏向“能编译”而非“高保真”，对设计还原要求高的场景存在限制。
- **Angular 残余错误顽固**：全局项目一致性（跨文件依赖、模块组织）仍是瓶颈，局部 PATCH 难以根治。
- **数据与评估局限**：Design2Code 仅 484 样本；无人类评估；CLIP 对布局细节的敏感度有限。
- **应用限制**：依赖 UIED 与 OCR 前端质量；Contract 需针对新框架手工设计，扩展到 Svelte、Solid 等需额外工程；论文也指出编译成功不等于安全、可访问、可维护，下游仍需标准审查与测试。

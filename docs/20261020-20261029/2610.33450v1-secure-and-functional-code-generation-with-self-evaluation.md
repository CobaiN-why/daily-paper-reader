## 摘要
大语言模型（LLM）能够生成功能正确但依然不安全的代码。以安全为重点的微调成本高昂且并非总是可用，这促使人们采用推理时方法。面向安全的提示与检索可以减少漏洞，但也可能移除所需行为，或施加与任务不兼容的防御。挑战在于识别相关的安全知识，并利用其在不牺牲功能的前提下提升安全性。我们提出 SecGent，一个推理时框架，它从通用弱点枚举（CWE）数据库中检索弱点上下文，并将其应用于安全代码生成。通过将任务规范与相关文本CWE记录关联，SecGent 无需依赖检索到的有漏洞或已修补代码示例，即可提供任务特定的安全指导。互补的功能与安全测试会检查所得实现，其执行反馈引导修复以同时满足两个目标。我们在 CWEval 基准上，使用四个开源LLM和 Claude Sonnet 5.5，在五种编程语言上评估 SecGent。对于所有五个模型，它在与四个推理时基线的比较中取得了最高的功能-安全联合成功率。在各开放权重模型中，平均 functional-security@1（FS@1）较 RAG 提升 15.5%，功能性和安全性均有增益，并较为每个模型编译的最强提示优化器提升 19.8%。在 Sonnet 上，FS@1 达到 92.1%，比最强基线 AutoGen 高出 4.8%。在另一项比较中，SecGent 在 FS@1 上以超过 6% 的优势优于采用安全聚焦提示的 Claude Code。反馈引导的修复进一步将 FS@1 较无反馈生成提升最多 6.7%，主要是在检查安全性的同时恢复功能。

## Abstract
Large Language Models (LLMs) can generate functionally correct code that remains insecure. Security-focused fine-tuning can be expensive and is not always available, motivating inference-time approaches. Security-oriented prompting and retrieval can reduce vulnerabilities, but may also remove required behavior or apply defenses incompatible with the task. The challenge is to identify relevant security knowledge and use it to improve security without sacrificing functionality. We present SecGent, an inference-time framework that retrieves weakness context from the Common Weakness Enumeration (CWE) database and applies it to secure code generation. By connecting task specifications to relevant textual CWE records, SecGent provides task-specific security guidance without relying on retrieved vulnerable or patched code examples. Complementary functional and security tests check the resulting implementation, and their execution feedback guides repairs toward satisfying both objectives. We evaluate SecGent with four open-source LLMs and Claude Sonnet 5.5 across five programming languages on the CWEval benchmark. It achieves the highest joint functional--security success against four inference-time baselines for all five models. Across the open-weight models, mean functional-security@1 (FS@1) improves by 15.5% over RAG, with gains in both functionality and security, and by 19.8% over the strongest prompt optimizer compiled for each model. On Sonnet, FS@1 reaches 92.1%, outperforming the strongest baseline AutoGen by 4.8%. In a separate comparison, SecGent outperforms Claude Code with security-focused prompting by over 6% in FS@1. Feedback-guided repair further improves FS@1 by up to 6.7% over generation without feedback, primarily by recovering functionality while checking security.

## 1. 核心问题与研究动机

- **核心矛盾**：LLM 生成的代码往往“功能正确但不安全”。论文指出，在四个开源模型上用直接提示（Direct Prompting）生成的**功能正确样本中，有 29.2% 无法通过 CWEval 的安全判定**——仅通过普通测试并不能证明程序安全（如面对对抗性输入）。
- **现有方案的两难**：
  - 安全微调（SVEN、SafeCoder 等）成本高、并非总是可用；
  - 推理时的安全提示 / 检索（RAG、CodeGuarder、RESCUE）虽能降低漏洞，却常常**牺牲功能**：例如 RAG 在提升安全的同时降低功能正确率，CodeGuarder 的 F@1 平均下降 17.6%，功能损失几乎抵消了安全收益；
  - 通用智能体审查（AutoGen）反而功能好、安全弱。
- **关键难点（词汇鸿沟）**：任务规范描述“要实现什么行为”，而 MITRE CWE 记录描述“失败机理与后果”。例如“写 HTTP 头”的任务规范不会提到回车换行或响应拆分。直接用任务规范做稠密检索，Top-5 命中真实 CWE 的召回率仅 **47.1%**。
- **论文主张**：需要“任务条件化的弱点上下文”——既选对相关安全知识，又要把它**正确地**应用到不破坏必需行为的前提下；同时用功能与安全两类可执行测试互相约束。

## 2. 方法论：SecGent 框架

### 2.1 核心思想
推理时框架，不微调模型、不检索易受攻击/已修补的代码样例，而是从 CWE 文本记录中检索“弱点上下文”，同时指导**代码生成**与**测试生成**，并用**双目标帕累托保留规则**驱动修复。

### 2.2 离线弱点目录构建（Step 0）
- 取 MITRE CWE-1000（Research Concepts 视图）的 **944 个弱点**，抽取 CWE ID、名称、描述、缓解措施。
- 用 LLM（qwen3.8:27b）零样本重写：将官方名称+描述改写为**一句代码级描述 + 一组代码级关键词**（点明输入、操作、后果），保留 ID、名称、缓解措施。
- 对每条记录做嵌入并**冻结目录**；重写过程不接触任何基准任务，避免泄漏；MITRE 更新时可重跑同一流程。

### 2.3 任务条件化弱点检索（Step 1–3）
- 任务表示为 \(x=(\ell, s, e)\)：语言、规范与函数签名、执行设置。
- **HyDE 式查询生成**：查询写作器 \(h_\phi\) 生成“该任务可能的**不安全实现** + 缺失检查的解释”（不要求正确，只为进入弱点的词汇空间）。
- 两阶段检索（论文式 (1)）：
  - \(q_x = h_\phi(\ell, s)\)，与规范拼接后做稠密检索，取 **Top-N=20**；
  - LLM 重排器 \(r_\phi\) 按 0–100 打分，**三种不同候选顺序各打一次并取平均**（降低顺序敏感性），取 **Top-M=5** 作为弱点上下文 \(K_x\)。
- 嵌入模型：Qwen3-Emb-8B。

### 2.4 测试生成与冻结（Step 4）
- 测试智能体 \(A_\theta\) 仅接收 \((\ell, s, e, K_x)\)，**从不观察候选代码及其执行结果**。
- 产出恰好一个功能测试 \(t^F_x\)（验证规范要求的行为）和一个 CWE 感知安全测试 \(t^S_x\)（从 \(K_x\) 中选最贴合任务的弱点，把“攻击者可控输入 → 危险操作/sink → 可观察危害”转成断言）。
- 统一 `invoke` 接口暴露返回值、崩溃状态、stdout/stderr，使 Python/C/C++/Go/JS 可用同一断言风格。
- 校验器检查语法、数量恰为 1+1、是否关联到检索到的 CWE、`invoke` 用法、断言可执行；最多 \(A=2\) 次修订；通过后**冻结**，后续初版与所有修复复用同一套测试。

### 2.5 生成、执行与证据（Step 5–7）
- 编码智能体 \(G_\theta\) 在**看不到测试**的情况下由 \((\ell, s, K_x)\) 生成初版 \(y_0\)，被要求保留签名、有效输入行为、返回值与副作用。
- 执行层用适配器完成编译/加载/调用与结果归一化，在**一次性 Docker 容器**中运行，设子进程与外层超时；区分构建失败与断言失败。
- 打分对 \(q_T(y)=(f_T(y), s_T(y)) \in \{0,1\}^2\)；完整证据 \(E(y,T_x)=(q_T(y), b_y, d_y)\)，其中 \(b_y\) 为构建/运行状态，\(d_y\) 为有界诊断信息。不可用测试套件不触发修复。

### 2.6 证据引导修复与帕累托保留（Step 8–9）
- 同一编码智能体接收任务、源码与执行证据，提出修复 \(\tilde y\)；提示要求修正已报告失败并保留已通过行为。
- **严格帕累托支配保留规则**（式 (4)）：\(y' \succ_T y\) 当且仅当 \(f_T(y')\ge f_T(y)\) 且 \(s_T(y')\ge s_T(y)\)，且至少一个严格更优；平局与回退一律拒绝。
- 达到 \((1,1)\) 或用尽预算 \(B=2\) 即停止；LLM 调用上界为 \(A + n(1+B)\)（不含固定检索阶段）。
- 基准（CWEval）的独立 oracle 结果**不参与**修复，以防 oracle 泄漏。

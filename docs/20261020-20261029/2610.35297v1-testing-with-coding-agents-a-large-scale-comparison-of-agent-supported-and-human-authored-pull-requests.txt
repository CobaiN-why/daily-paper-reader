# Testing with Coding Agents: A Large-Scale Comparison of Agent-Supported and Human-Authored Pull Requests

Abstract Context. Coding agents increasingly contribute tests through pull requests that developers then maintain, so how testing work is divided affects long-term maintainability. 

Objective. We compare pull requests in which developers and coding agents collaborate (agent-supported) with pull requests without detectable agent involvement (human-authored) along five dimensions: the frequency and extent of test changes, their type and context, test structure, test smells, and code coverage.

Method. We analyze 114,134 pull requests merged between January 2025 and April 2026 in 391 Java repositories, identifying five coding agents through pull-request-level and commit-level signals. Since agent adoption varies across projects, we compare the two groups within repositories with mixed-effects models that control for change size. 

Results. Pooled across repositories, both groups change test code almost equally often; within repositories, the odds that an agent-supported pull re-quest does so are 1.65 times higher. Agent-supported pull requests add tests more often (odds ratios 1.50-1.58) and modify (0.70-0.76) and delete (0.51-0.77) them less often. We detect no difference in most structural character-istics of the tests they add, which more often have an oracle, nor, in the 95 repositories we could build, in the coverage of their production changes; in test-only pull requests, however, their tests cover less of the code they exer-cise. Differences in test smells are borderline and not reproduced for individual test methods. 

Conclusions. Agent participation is associated with a different mix of testing work, which pooled comparisons across projects can hide or reverse; its relationship with test quality remains uncertain.

1 Introduction 

AI-based coding tools have evolved from completing individual lines of code to carrying out entire development tasks: modern coding agents iterate over a task, invoking build systems, test frameworks, and version control until they consider it complete (Robbes et al., 2026b; Wang et al., 2025). In collaborative projects, the result usually reaches the code base as a pull request (PR) that developers review, revise, and integrate, and adoption has been rapid: as of February 2026, between 22.20% and 28.66% of the 128,018 active GitHub repositories analyzed by Robbes et al. (2026b) showed traces of coding agent use. We refer to PRs in which developers and coding agents both participate as agent-supported PRs, and to PRs without detectable agent involvement as 

human-authored PRs. Testing is where the consequences of this shift are likely to last longest. Tests are read, modified, and deleted as the code they exercise evolves, and design problems in test code, known as test smells, make them harder to under-stand and change (Bavota et al., 2012); such problems are usually introduced when a test is first written and rarely removed afterwards (Tufano et al., 2016). As agents write tests that developers will then maintain, two questions become central: what kind of testing work agents take on, and what kind of test code results. Research on agentic testing has grown quickly, but the evidence is frag-mented. Studies of tests in real agentic PRs each focus on one aspect: test in-clusion and evolution (Haque et al., 2026), test structure and coverage (Yoshi-Testing with Coding Agents 3

moto et al., 2026), diff coverage and assertion quality (Alves and Teixeira, 2026), or test failures (Hoseinpour et al., 2026). Only some compare agentic with human contributions, and they pool them across repositories, at least in part, or analyze few projects one by one (Section 3). What is missing is a comparison over many repositories that estimates the difference within each of them, controls for the size of the contribution, and quantifies how much the difference varies between repositories. This matters because agent adoption is uneven across projects: a pooled comparison mixes whether agentic contri-butions test differently with which projects use agents, and, as we show, the second can hide and even reverse the first. Our previous study (Milanese et al., 2026b) compared 6,582 agent-supported and 3,122 human-authored PRs from the AIDev dataset (Li et al., 2025a) in four programming languages. It found that the two groups include tests at com-parable rates (42.9% against 40.0%), but that agent-supported PRs devote a larger share of their changes to test code; that during co-evolution they more often add tests (OR 1.79), whereas human-authored PRs more often modify and delete existing ones; and that differences in test smells were negligible in magnitude. Its design, however, compared PRs pooled across repositories, classified changes at the level of test files, considered any PR that changes both test and production code as co-evolution, and did not measure coverage. This paper addresses those limitations. First, we compare the two groups within repositories, using mixed-effects models in which each repository has its own baseline and its own difference between the groups, controlling for the size of the change. Second, we analyze test changes at the level of test methods and fixtures, and consider a test change as co-evolving only when it is linked to production code changed by the same PR (Marsavina et al., 2014); we also detect test smells with JNose (Virg´ ınio et al., 2020), which locates each occurrence in a test method, so that smells can be compared both for entire contributions and for individual tests. Third, we add two dimensions: the structure of test code, extracted with Hamster (Pan et al., 2026), and code coverage, measured with JaCoCo by executing each test suite before and after the PR. Since measuring coverage requires building each project, we restrict the study to Java, whose standardized build tools make this feasible at scale (Section 4.1). These choices required a new dataset. We collected all PRs created and merged between January 1, 2025, and April 30, 2026, in Java repositories with traces of agent activity, identifying agent participation through PR-level and commit-level signals (Robbes et al., 2026c) for five widely adopted agents: Claude Code, Codex, Copilot, Cursor, and Devin. Retaining the repositories with at least ten PRs of each group, we obtain 18,375 agent-supported and 95,759 human-authored PRs from 391 repositories. On this dataset, we ad-dress five research questions (Section 4), which compare the two groups in the frequency and extent of testing (RQ 1), the type and context of test changes (RQ 2), the structure of test code (RQ 3), test smells (RQ 4), and code coverage (RQ 5). 4 Roberto Milanese et al. 

Our results lead to five main findings. First, how the comparison is made determines what it shows: pooled across repositories, the two groups change test code almost equally often (60.1% against 59.4%), whereas within the same repository and at equal size, the odds that an agent-supported PR changes test code are 1.65 times those of a human-authored one. Second, relative to human-authored PRs of the same size, agent-supported PRs add tests more often (OR 1.50-1.58) and modify (OR 0.70-0.76) and delete (OR 0.51-0.77) them less often, in every development context, while the two groups differ little in how often they co-evolve tests with production code (OR 1.12). Third, we detect no difference in most structural characteristics of the tests that agent-supported PRs add, except that they more often have an oracle (OR 1.71); when modifying tests, agent-supported PRs more often add assertions (OR 1.31). Fourth, the evidence on test smells is weaker: at the PR level, agent-supported PRs are associated with a smaller net increase in smells when adding tests and a larger one when modifying them, but both estimates are borderline and neither is reproduced for individual test methods. Fifth, we detect no difference in how well the two groups cover their production changes, but in test-only PRs the tests that agent-supported PRs contribute cover less of the classes they exercise ( −11.1 percentage points), a result that rests on only 11 repositories with test-only PRs of both groups. For most outcomes, the size and sometimes the direction of the difference vary considerably between repositories. In summary, this paper makes the following contributions: 

– a dataset of 114,134 merged PRs from 391 Java repositories, each con-taining both agent-supported and human-authored PRs, in which agent participation is identified through multiple PR-level and commit-level sig-nals for five coding agents; 

– a within-repository comparison of testing in the two groups across 391 repositories, which controls for change size, estimates how much the dif-ference varies between repositories, and shows that pooling contributions across projects can conceal or reverse it; 

– an analysis of the same contributions along five testing dimensions, includ-ing test structure and coverage, with test changes classified at the level of test methods and linked to the production changes they accompany, and test smells compared at the level of contributions and of individual test methods; 

– a replication package containing the dataset, the queries, and the analysis scripts (Milanese et al., 2026a). The remainder of this paper is organized as follows. Section 2 introduces background on coding agents, testing in pull-request-based development, and test smells, and Section 3 discusses related work. Section 4 describes the study design. Section 5 reports the results, which Section 6 discusses together with the threats to validity. Section 7 concludes the paper and outlines future work. Testing with Coding Agents 5

2 Background 

2.1 AI Coding Agents and Agent-Supported Pull Requests Unlike code completion assistants, which help developers write individual lines or blocks of code, coding agents undertake entire development tasks, such as fixing bugs or implementing features (Robbes et al., 2026b). A coding agent can be characterized as an LLM operating in an iterative loop with access to external tools: its actions are executed, their outcomes are fed back to the model, and the process continues until the task is considered complete. Agentic programming is therefore goal-oriented, multi-step, and tool-based: agents interact with compilers, debuggers, test frameworks, and version control systems, while developers may retain oversight by providing goals, constraints, or feedback (Wang et al., 2025). In collaborative development workflows, this interaction materializes through pull requests, where coding agents may produce commits or entire contribu-tions that are subsequently inspected, refined, and integrated by human devel-opers (Robbes et al., 2026b). The division of labor within such a contribution is not recorded explicitly, but agent participation usually leaves observable traces, such as dedicated branch names, bot accounts, or co-authorship lines in commit metadata, which is what makes it possible to study these contribu-tions at scale. We distinguish agent-supported PRs, in which developers and one or more coding agents participate, from human-authored PRs, produced without the involvement of coding agents that leaves detectable traces. Our previous study called them human-agent collaborative pull requests and human pull requests (Mi-lanese et al., 2026b). Since agent participation is inferred from its traces, the second group is primarily rather than exclusively human-authored (Sec-tion 4.1). 2.2 Testing in Pull-Request-Based Development In real-world development, tests are a persistent part of a project’s quality-assurance infrastructure and evolve together with the code base, so they need to remain understandable, maintainable, and aligned with the software they exercise (Pan et al., 2026). This has become more relevant as coding agents contribute tests that are then maintained within long-lived test suites. Within pull-request-based development, testing takes different forms de-pending on the scope of the contribution. Some PRs modify only production code, others change production and test code together, a setting commonly described as test-production co-evolution , and others focus exclusively on test code. Within a contribution, test code evolves through a small set of recurring tasks. Following Pinto et al. (2012), a contribution can add new tests, modify 

existing ones, or delete them, and these tasks place different demands on the 6 Roberto Milanese et al. 

contributor: adding a test is a largely self-contained activity, whereas modify-ing or deleting one requires understanding what an existing test checks and why it should change. The structural notion of co-evolution introduced above is also coarse, since a pull request may well change test and production code that have nothing to do with each other. A finer definition considers a test change to co-evolve only when it is linked to production code changed by the same contribution, for example because the test exercises a method that the contribution modifies (Marsavina et al., 2014). Combining tasks with the con-text in which they occur therefore characterizes testing work more precisely than the presence of test changes alone. These dimensions describe how testing work is distributed within a contri-bution, but not the quality of its outcome. Two further properties are com-monly used for that purpose. The first is the internal quality of the test code itself, which we discuss in the next subsection. The second is test adequacy, usually approximated by code coverage, that is, the share of production code that the test suite exercises. The two are complementary: a contribution may raise coverage while leaving test code that is hard to maintain, and well-designed tests may exercise little of the code they accompany. 2.3 Test Smells and Test-Code Quality Test code, like production code, may exhibit design and implementation choices that hinder its maintenance. Such recurring choices are known as test smells :patterns associated with poorly designed tests and with the way test cases are organized, implemented, and interact with one another (Bavota et al., 2012). Typical examples include a test that verifies several unrelated behaviors, a group of assertions that gives no indication of which one failed, or a fixture shared by a class but used by only some of its tests. A smelly test is not necessarily incorrect: it may detect faults reliably and still be hard to read, to change, or to keep independent of conditions unrelated to the behavior it checks, which is why test smells are a quality concern distinct from test effectiveness. These costs accumulate because test suites are long-lived. Bavota et al. (2012) found test smells to be widespread in Java systems and showed exper-imentally that several categories hinder comprehension, while Tufano et al. (2016) observed that smells are usually introduced when a test class is first committed and rarely removed afterwards. The quality of a test is therefore largely decided by the contribution that writes it, and the cost of a poor design is paid by every later contribution that touches it. Test smells are detected statically, by matching structural rules against the source code of a test class, so detectors report design properties rather than defects, and the resulting counts approximate test-code quality rather than measure it. Since they can be computed on any revision, they allow comparing the test code before and after a contribution and attributing the difference to that contribution. Testing with Coding Agents 7

3 Related Work 

A broad body of research has investigated coding assistants and agents across different software engineering activities. Nikolaidis et al. (2024), for example, compared ChatGPT and Copilot for Python code generation, focusing on the correctness and quality of the produced code. Sergeyuk et al. (2025) stud-ied the practical adoption of coding agents, examining developer perceptions, usage patterns, and organizational implications. Similarly, Butler et al. (2025) evaluated generative AI coding tools in a controlled workplace study, reporting their effects on developer productivity and behavior. However, these studies consider testing only marginally, if at all, and do not investigate how testing activities emerge, evolve, and are distributed within collaborative development workflows involving both humans and coding agents. Closer to our setting, several studies characterized agentic PRs on the 

AIDev dataset (Li et al., 2025a, 2026a). Agentic PRs are accepted less of-ten than human ones (Li et al., 2025a), and merged agentic PRs differ from merged human PRs in the number of commits, files touched, and lines deleted (Ogenrwot and Businge, 2026), while unmerged ones are larger and more of-ten fail CI (Ehsani et al., 2026). These size differences motivate controlling for change size. Sawada et al. (2026) found that agent-generated files receive less frequent maintenance than human-authored code and that human developers perform most of it, which is why the tests that developers inherit from agents deserve attention. At the repository level, He et al. (2026) compared Cursor -adopting projects with matched controls in a difference-in-differences design and found a large but transient gain in velocity together with a persistent in-crease in static-analysis warnings and complexity, a within-project comparison in the same spirit as the present study. Still, none of these studies examined the tests a PR contributes. Testing practices within real-world agentic development workflows have been examined from different angles. One line of work focuses on how tests appear and evolve during pull-request development. Using the AIDev dataset, Haque et al. (2026) studied test inclusion, the stage at which tests are intro-duced, and the differences between test-containing and non-test contributions. Their results indicate that testing has become increasingly common over time and that pull requests involving tests tend to be larger and require longer turnaround times. In addition, tests introduced in the initial contribution are often revised in later commits, highlighting that testing activities may evolve throughout the pull-request lifecycle. A different perspective is provided by Yoshimoto et al. (2026), who inves-tigated the prevalence of AI-authored test additions, the structural charac-teristics of generated tests, and their impact on code coverage. AI-generated tests were found to be slightly longer, to contain more assertions, and to rely on simpler control-flow structures than human-written tests, while achieving comparable coverage improvements. Coverage and assertion quality were fur-ther examined by Alves and Teixeira (2026) through a comparison of AI-only, human-AI coauthored, and human pull requests. Their analysis shows that AI-8 Roberto Milanese et al. 

only contributions achieve higher diff-coverage of modified production code, whereas assertion quality remains broadly comparable across the three au-thorship settings. Coverage was also the focus of Dipongkor et al. (2026), who studied 4,882 agentic PRs in Java and Python and measured, for each merged PR, the share of added executable lines covered by the existing tests and by the tests the PR itself changes. Existing tests covered 61.5% of these lines in Java and 27.0% in Python, and agent-written tests raised diff coverage in only 35.9% of the Java and 22.5% of the Python PRs that change both code and tests. Other work has focused on failures rather than coverage or test structure. Hoseinpour et al. (2026) manually analyzed 500 pull requests affected by test-related failures and reported that runtime failures occur more frequently than compile-time ones, with assertion failures and unexpected exceptions as the most common categories. The agentic testing studies differ along the aspects that matter most for the present work: the population analyzed, the unit of analysis, the testing dimensions considered, whether agentic contributions are compared with hu-man ones, and how the repository is taken into account. Three of them analyze agentic contributions only. Among those that compare agentic and human con-tributions, Yoshimoto et al. (2026) study a small number of projects, pooling them for some analyses and reporting others per project, Alves and Teixeira (2026) sample the human PRs from the same repositories as the agentic ones but compare the groups with pooled tests, and our previous study compared PRs pooled across repositories (Milanese et al., 2026b). None of them esti-mates the difference within each of many repositories while controlling for the size of the contribution, or estimates how much the difference varies between repositories, which is the comparison this paper adds. For the individual dimensions we compare, we also build on studies of test-ing outside agentic PRs. How developers maintain test suites is documented in studies that predate coding agents. Pinto et al. (2012) found, across many ver-sions of six Java programs, that most test changes are additions, and that tests that fail after a change are more often deleted than repaired, usually because the code they exercised no longer exists. Levin and Yehudai (2017) found, across 61 open-source Java projects, that in half of them fewer than a quarter of the bug-fixing commits also touched tests. Whether coding agents follow the same pattern is so far known only from a benchmark: Shang et al. (2026) found that Claude Code, Codex CLI, and OpenCode repair tests that fail but perform worst on tests that still pass yet no longer check the updated behav-ior, because their loop is driven by execution failures. How agent-supported contributions maintain tests in real projects, compared with human-authored ones, remains open. The tests that AI coding assistants generate have mostly been assessed for their quality, often against developer-written tests. Alves et al. (2024) ex-amined test smells in Python tests produced by Copilot , with a particular focus on the maintainability of the generated test code. At a larger scale, Ou´ edraogo et al. (2026) compared class-level test suites generated by four Testing with Coding Agents 9

LLMs with hundreds of thousands of developer-written tests from open-source Java projects, using TsDetect and JNose , and found that LLM-generated tests consistently exhibit smells such as Assertion Roulette and Magic Num-ber Test. Joshi and Band (2025) instead evaluated Copilot -generated tests for existing software projects by comparing them with manually developed test suites. Although these works provide useful evidence on the quality and characteristics of automatically generated tests, they largely treat test genera-tion as an isolated activity performed on already implemented software, rather than as an integral part of the development process. Pan et al. (2026) presented Hamster , a characterization of 1.7 million developer-written Java test cases from 1,908 open-source projects, covering fixtures, structured inputs, test scope, call-assertion sequences, mocking, and code coverage. Developer-written tests often exercise several focal classes and methods, rely on reusable fixtures and mocks, and use richer assertion pat-terns, whereas tests generated by EvoSuite (Fraser and Arcuri, 2011) and by the LLM-based aster (Pan et al., 2025) are simpler and more narrowly scoped, which suggests that coverage alone does not capture how closely generated tests reflect development practice. How the coverage of a change, rather than of a whole program, should be measured has its own literature. Hilton et al. (2018) analyzed 7,816 builds of 47 projects and found that, in large and mature projects, the change in over-all statement coverage does not capture the nuances of code evolution; they proposed measures that separate the coverage of the patch from that of the non-patch, and changes in coverage from changes in the set of statements cov-ered. A follow-up on nine mature projects over a decade reported that overall coverage has risen while many individual patches remain poorly tested (Bai-ley and Cadar, 2025). The agentic coverage studies above measured the diff coverage of the lines a PR changes, by the tests the PR modifies (Alves and Teixeira, 2026) or by existing and agent-written tests separately (Dipongkor et al., 2026). RQ 5 makes the same distinction between the patch and the rest of the code, and extends line-level diff coverage with the coverage of the classes a PR affects, before and after the change, for agent-supported and human-authored PRs from the same repositories (Section 4.3.5). 

4 Study Design 

The goal of the study is to compare the testing work carried out in agent-supported and human-authored PRs of the same repositories, with the purpose 

of understanding what kind of testing work coding agents take on and what test code results. We address the following research questions: 

– RQ 1: Are there differences between agent-supported and human-authored PRs in the frequency and extent of testing contributions? 

– RQ 2: How do the development contexts in which testing contributions appear compare between agent-supported and human-authored PRs? 10 Roberto Milanese et al. 

– RQ 3: How do the structural characteristics of the test code produced by agent-supported and human-authored PRs compare? 

– RQ 4: How does test quality, as reflected by test smells, differ between agent-supported and human-authored PRs? 

– RQ 5: How do agent-supported and human-authored PRs compare in terms of code coverage changes and adequacy? Section 4.1 explains why we restrict the study to Java and build a new dataset, Section 4.2 describes how we collected it, and Section 4.3 the proce-dure we follow for each research question. 4.1 Study Context This work extends our previous study (Milanese et al., 2026b), which charac-terized testing in agent-supported and human-authored PRs from the AIDev 

dataset (Li et al., 2026a) in four programming languages in terms of frequency, extent, development context, and test smells. The two new dimensions, code coverage and the structure of test code, required two changes to the design: restricting the scope to Java repositories and creating a new dataset of PRs. The decision to focus on Java projects stems from the nature of the new analyses. While test smell detection operates on static file contents, measuring coverage requires building each project and executing its test suite, and this is only feasible at scale when build and test workflows are standardized. In the Java ecosystem, Maven 1 and Gradle 2 are the build systems used by the majority of projects (JetBrains, 2025), and provide a single entry point to run tests, regardless of the underlying test framework used. JaCoCo 3 easily inte-grates with both these tools to produce widely used, well-defined coverage met-rics. This contrasts with the Python and JavaScript/TypeScript ecosystems, where testing is fragmented across various frameworks (JetBrains, 2024a,b). Extending the study to all four languages would require separate toolchains, each with different build systems, coverage semantics, and characterization tooling, which would undermine the comparability of results. While AIDev is designed to support broad studies of agent adoption across languages and ecosystems, our design requires a large sample of Java projects containing both agent-supported and human-authored PRs. In our previous work (Milanese et al., 2026b), we used AIDev v3 (Li et al., 2025a), which contains 3,481 Java repositories. However, detailed PR-level data is only avail-able for the AIDev-pop subset, which includes only 86 Java repositories with more than 100 stars. Furthermore, human-authored PRs are limited to reposi-tories with more than 500 stars, leaving only 50 qualifying Java repositories. In our previous study, we applied this same threshold to agent-supported PR as well, to ensure that both groups came from the same sample. The more recent

4.2.1 Repository Identification 

Since most GitHub repositories still show no traces of coding agent use (Robbes et al., 2026b), rather than covering every Java repository, we first identify those containing at least one agent-supported contribution and then retrieve all their merged PRs. To this end, we query the GitHub Search API using the signals proposed by Robbes et al. (2026c) for the five coding agents within our scope, reported in Table 2. This results in a total of 25 queries, available in our replication package (Milanese et al., 2026a). 4.2.2 Pull Request Collection 

Identifying a repository with agentic activity is not enough, because commit-level matches are not linked to the PRs that contain them, and the human-authored PRs needed for our comparison are not matched at all. Since the API endpoints that list the PRs of a repository do not support filtering by date, we use the Search API again to retrieve all PRs created and closed within our time window in each candidate repository, together with their head and target branches, merge commit, labels, author, commits with their authors and co-authors, and changed files. The complete query is available in our replication package (Milanese et al., 2026a). 4.2.3 Pull Request Classification 

After collecting PRs, we classify them as either agent-supported or primarily human-authored using the most recent version of the heuristics released by Robbes et al. (2026a). These signals cover more than 40 coding agents, includ-ing the five within our scope, with agent-specific branch name prefixes, labels, and author identities (i.e., account logins, names, and email addresses). Classification proceeds in two tiers. First, at the PR level, we check if the head branch name, one of the labels, or the author matches an agent pattern. We do not consider assignees at this stage, since an agent can be assigned to a PR without contributing code, such as when a developer asks Copilot to review their changes. If no PR-level signal applies, we check if the author or a co-author of any of its commits matches an agent pattern. A commit-level match only counts if the matching commit modifies at least one Java file. Therefore, an agent that only edited documentation or build files would not make a PR agent-supported for the purposes of our study. PRs that do not match any of the five agents in our scope, but that do match other agents covered in Robbes et al. (2026a) are discarded because they fall outside our scope. If no agent is matched at all, we check if any commit that modifies a Java file was authored by a bot account (i.e., an account whose login or name contains [bot] or -bot ). These are discarded as well, as their automated changes would distort the human-authored group, and all remaining PRs are considered human-authored. Out of the 336,041 merged Java PRs collected in the previous step, 115,771 are agent-supported, 215,388 are human-authored, 2,386 are attributed to other agents, and 2,496 are attributed to bots. Most agent-supported PRs (115,398) match a single agent, while 373 match two or more.

4.2.5 Change Measurement 

After identifying the pre- and post-merge commits, we compare them to mea-sure the size of the changes that the PR introduced to the Java code. This is related to code churn , which is typically calculated as the sum of added and deleted lines of code (Nagappan and Ball, 2005; Gousios et al., 2014). To better reflect the actual size of a change rather than the number of line edits, we instead count each modified line once, rather than counting it as both a deletion and an addition. First, we use the git diff-tree 7 command with rename detection enabled and the default similarity threshold of 50% to accurately extract the Java files that differ between the two commits. This ensures that a renamed file

is compared with its previous version instead of being counted as completely deleted and added again. Next, we classify each changed Java file as either test or production code using the heuristic that was developed and validated in our previous study (Milanese et al., 2026b), which combines three rules: one matches the file path against test directories and naming conventions, the other two match the file content against imports of testing libraries and test-specific keywords, such as annotations and assertions. A file is classified as test code if it is in a standard test directory or matches at least two of the three rules, unless its path is in a build or dependency directory. We remove single-line comments, block comments, and blank lines from both versions of each file, and trim lines to exclude changes to comments, whitespace, or indentation. Then, we compare the two stripped versions using the histogram algorithm from git diff 8, which has been shown to be better suited for describing code changes (Nugroho et al., 2020). Finally, we count the changed lines following the diffstat algorithm (Thomas E. Dickey, 2026). In each chunk of consecutive lines that are changed ( D deleted and A added), the minimum number of lines min( D, A ) are counted as modified, and the change size of the chunk is the maximum number of lines max( D, A ). Summing the change sizes of the test and production file chunks yields the test change size 

∆T est and the production change size ∆P rod of a PR. We consider a PR to be a test PR if ∆T est > 0, meaning that at least one non-comment, non-blank line of test code was changed. We discard the 870 agent-supported and 1,315 human-authored PRs with 

∆T est + ∆P rod = 0 because they only change comments or blank lines in Java files or have Java changes that cancel each other out between the pre- and post-merge commits. 

4.2.6 Repository Selection 

Rather than selecting repositories based on popularity, we keep those with at least ten agent-supported and ten human-authored PRs. This criterion serves two purposes. First, it ensures that every repository contributes to both groups, which enables us to compare agent-supported and human-authored PRs within the same project while controlling for project-level factors, such as testing culture, domain, and build infrastructure. Second, it guarantees that there are sufficient PRs in each group to estimate how the difference between them varies across repositories. Since steps 3 , 4 , and 5 can only remove PRs, a repository can meet this criterion in the final dataset only if it met it after classification. Therefore, we apply it after each of these steps, as marked by the funnel icons in Figure 1. This avoids cloning and processing repositories that would be discarded anyway. Lastly, we discard repositories without any test PR, since their PRs provide no test changes to characterize in terms of coverage or structure.

4.3 Experimental Procedure All research questions share the same design. We compare agent-supported and human-authored PRs, or the test methods they change, within the same repository, using mixed-effects models in which each repository has its own baseline and its own difference between the two groups, and controlling for size. Unless stated otherwise, for each coefficient of agentic we report its exponential (an odds ratio or a rate ratio) with its 95% Wald confidence in-terval (CI), test whether it differs from 1 with a Wald z -test (Agresti, 2006), adjust p-values with the Holm-Bonferroni method (Holm, 1979) within each family of tests, and consider a difference significant when its adjusted p-value is below α = 0 .05 (Fisher, 1992). We also report the predicted values for the two groups and the average marginal effect (AME) of agentic (Arel-Bundock et al., 2024), the standard deviation ˆ τ of the repository-specific differences, and evaluate model fit with simulation-based residual diagnostics (Hartig, 2026). RQ 1 introduces this design in detail; for the other research questions, we de-scribe the data they require, their metrics, and how their models and analyses depart from those of RQ 1.

Statistical Model. Because they share testing conventions, build infrastructure, and review practices, PRs from the same repository cannot be treated as completely independent observations. 4.3.2 RQ 2: Type and Context of Testing 

The definition of mixed PR in RQ 1 is purely structural, so its test changes are not necessarily related to its production changes. Here, we consider a test change to be co-evolving only if it is linked to production code changed by the same PR (Marsavina et al., 2014) (Section 2), and ask whether mixed agent-supported and human-authored PRs co-evolve tests equally often, and whether the two groups differ in how often they add, modify, or delete tests in each development context. 

Data Preparation. Since this research question focuses on individual tests rather than files, the change measurement introduced in Section 4.2.5 is insuffi-cient to answer it. Therefore, we use Hamster (Pan et al., 2026) to determine which test methods and fixtures (i.e., setup and teardown methods) each test PR changes, and whether these are linked to the production code changes. 

Hamster builds a model of each test class using the static analysis pro-vided by CLDK (Krishna et al., 2025), which resolves types and method calls from source code. To keep the analysis tractable, we run it on a slice of each project consisting of the changed test and production files, the files they depend on and their superclasses, at both the pre- and post-merge commits. Within each changed test class, Hamster identifies test methods and fixtures, which we call test units . For each test method, Hamster records the calls and assertions performed and the structural metrics we analyze in RQ 3. When a test method calls a helper method (i.e., a non-test method in the same test class), Hamster adds the helper’s calls and assertions to the test’s model. We match each unit across the two commits by its signature, using Refac-toringMiner (Tsantalis et al., 2018, 2022) to detect renamed and moved units. A unit is added or deleted if it exists in only one version and is modified 

if its text differs after removing comments and blank lines, as in Section 4.2.5. We also consider a unit modified when its text is unchanged but its Hamster 

model differs, since it then exercises a different behavior. Changed units that 

Hamster does not detect cannot be analyzed and are excluded. A changed unit is linked to the production changes of its PR if it calls a production method that is added, deleted, or modified in the PR, either directly or through a helper. Added units are linked through their post-merge Testing with Coding Agents 21 

version, deleted units through their pre-merge version, and modified units through either. Since Hamster resolves calls statically, the number of co-evolving PRs is a lower bound. Of the 67,896 test PRs in our dataset, we successfully process 66,864 (98.48%), 56,153 of which (83.98%) change at least one test unit. The re-maining PRs only change helper methods, fields, imports, or other test code outside of units. 

Metrics. Each changed unit has a task and a context. As in our previous study (Milanese et al., 2026b), we derive the task from Pinto et al. (2012): Add if it is added, Mod if it is modified, either directly or through a helper, and Del if it is deleted. Units that are only renamed or moved have no task. The context of a unit depends on its PR and on its linkage: 

– Test-Focused Context ( TFC ): units of a test-only PR, which cannot be linked since the PR changes no production code. 

– Co-Evolution Context ( COC ): units of a mixed PR that are linked to production code changes. 

– Test-Focused Context in Mixed PRs ( TFM ): units of a mixed PR for which no link to its production code changes is detected. 

Co-Evolution. On mixed PRs, the binary outcome IsCoEvolutionPR is 1 if at least one changed unit of the PR is linked to its production changes, and 0 otherwise. It includes units modified through a helper, since a test whose helper now calls changed production code co-evolves with it. 

Types of Test Changes. For each task t ∈ { Add , Mod , Del } and context 

k ∈ { TFC , COC , TFM }, the binary outcome tk is 1 if the PR has at least one changed unit in context k whose task is t, and 0 otherwise. TFC is defined on test-only PRs, and COC and TFM on mixed PRs. As in our previous study (Milanese et al., 2026b), these outcomes are not mutually exclusive: a mixed PR that adds a linked test and modifies an unlinked one counts for both Add COC and Mod TFM .

Statistical Model. We model IsCoEvolutionPR on mixed PRs using the same specification as in RQ 1. For the nine outcomes tk, we fit one model per task, each covering all three contexts. In each task model, an observation is a PR in one context, and its outcome is whether the PR performs the task in that context. A test-only PR only has TFC units, so it contributes one observation: in the model for Add , for example, its outcome is Add TFC . A mixed PR can have both linked and unlinked units, so it contributes two observations, one for COC and one for TFM .We specify the three models as:

4.3.3 RQ 3: Test Structure 

In RQ 3, we investigate whether the test methods added and modified by agent-supported and human-authored PRs differ in structure in terms of oracles, as-sertions, conditional logic, call-assertion structure, mocking, scope, and length. While RQ 2 covers the types of test changes made by the two groups of PRs, RQ 3 characterizes the tests themselves. 

Data Preparation. We reuse the test units identified by Hamster in RQ 2 and analyze the test methods added or modified by a PR, excluding fixtures and test methods modified only through a helper. Our primary focus is on added test methods because they are entirely written within the PR. Modified test methods, on the other hand, mostly reflect the original authors’ work, so we only analyze the changes contributed by the PR itself. For each test method, the Hamster model records its annotations, size, cyclomatic complexity, created objects, mocking usage, and focal classes and methods. It also splits the body of the test method into call-assertion sequences and classifies each assertion by type (Pan et al., 2026). Of the 443,072 test methods added by test PRs, Hamster locates 397,021 (89.6%), from 35,801 PRs: 130,067 from 7,070 agent-supported and 266,954 Testing with Coding Agents 23 

from 28,731 human-authored PRs. Of the 429,281 test methods they modify, it locates both versions of 394,610 (91.9%), from 30,475 PRs: 57,858 from 4,115 agent-supported and 336,752 from 26,360 human-authored PRs. 

Metrics. We categorize added test methods based on five dimensions: oracle, conditional logic, call-assertion structure, mocking, and scope, and also report their length. Since many tests lack conditional logic and mocks, we define a binary outcome that indicates whether a test method has these characteristics, as well as a count that measures how much of each characteristic the test method has. This allows the two aspects to differ between agent-supported and human-authored PRs. For modified test methods, instead, we measure how the PR changes their assertions and whether it removes their oracle, and define corresponding binary outcomes. 

Oracle. A test method m has an explicit oracle , i.e., HasOracle (m) = 1, if it contains a check that can make it fail when the behavior it exercises is incorrect: a(m) + v(m) > 0 or expects (m), where a(m) is the number of assertions in its own body, v(m) the number of verification calls of mocking frameworks in its own body (e.g., Mockito ’s verify ), and expects (m) indi-cates an expected exception declared in its annotation. We do not count the assertions of the helper methods that m calls, so a test method that delegates all of its checks to helpers has no explicit oracle by this definition. In assertion chains (e.g., assertThat(x).isEqualTo(y) ), the call that opens the chain is not counted, so a chain with a single check counts as one assertion. Among test methods with at least one assertion, the count Assertions is a(m). For a modified test method, we compare its assertions before and after the PR. An assertion counts as removed if its code no longer occurs in the test method after the PR, and as added if it did not occur before, so editing an assertion counts as one removal and one addition. RemovesAssertions and 

AddsAssertions indicate that the PR removes or adds at least one assertion, respectively. We consider removals and additions separately, since a PR can re-place one assertion with another. These outcomes describe syntactic changes: they do not measure whether a change strengthens or weakens what the test checks, since an added assertion may be redundant and a rewritten one may be stronger. LosesOracle indicates instead that the test method has an ex-plicit oracle before the PR but not after it, the most direct syntactic form of weakening. 

Conditional Logic. The decision points of a test method are the points at which its execution can branch, and their number equals the cyclomatic complexity of the method minus one (McCabe, 1976). We define two variables: the binary outcome HasCondLogic indicates whether a test method has at least one decision point, and the count DecisionPoints is the number of decision points in test methods that have at least one. 

Call-Assertion Structure. Hamster divides each test method into call-assertion sequences , each consisting of calls followed by assertions that check 24 Roberto Milanese et al. 

the results of the calls (Pan et al., 2026). Since Hamster adds the calls and as-sertions of the helper methods that a test method calls to its model, sequences include those of its helpers. The count outcome Sequences is the number of call-assertion sequences in test methods with at least one. 

Mocking. We count calls that create mocks or spies within a test method’s body (e.g., Mockito ’s mock() and spy() ). The binary outcome CreatesMocks 

indicates whether a test method creates at least one mock, and the count 

Mocks is the number of mocks created by test methods that create at least one. Mocks that are declared as annotated fields of the test class are shared by all of its test methods and are not attributed to any method. 

Scope. Hamster identifies the focal methods of a test method, i.e., the production methods under test, and, by extension, its focal classes . We only measure scope on test methods with at least one resolved focal class. On these, the count FocalClasses is the number of focal classes, and the count 

FocalMethods is the number of focal methods, which can be zero when a test method only creates instances of its focal class, for example to check that a constructor initializes its fields, or only calls trivial methods such as getters, which Hamster does not consider to be focal methods (Pan et al., 2026). 

Length. Length is the number of lines of a test method, excluding com-ments and blank lines as in Section 4.2.5.

outcome ∼ agentic + size + (1 + agentic | repository ) + (1 | pr ) (4) First, observations are now test methods, and those of the same PR cannot be treated as independent. To assess whether the difference between the two groups depends on why tests are added, we assign each added test method to one of the contexts of RQ 2: TFC if its PR is test-only, COC if it is linked to the production changes of a mixed PR, and TFM otherwise. For each outcome on added test methods, we refit the model with the fixed effects 0 + context + context:agentic + context:size , centering size within each context, and add the term (1 | repository:context ), as in RQ 2. Unlike in RQ 2, each test method belongs to a single context, and the term (1 | pr ) accounts for the test methods of a mixed PR that fall in both COC and TFM .

Statistical Analysis. We measure the difference between agent-supported and human-authored test methods for each outcome with the conditional odds ratio for binary outcomes, the rate ratio RR for counts (Hilbe, 2011), and the ratio of geometric means GMR for Length , all computed as e ˆβ where ˆβ is the coefficient of agentic . For zero-truncated counts, e ˆβ is the ratio between the means of the untruncated distributions, which differs from the ratio between the mean counts of test methods with at least one, so we also compare these means directly through predictions on the response scale. We adjust p-values separately for the nine outcomes on added test methods and for the three outcomes on modified test methods. Since Length describes the test methods rather than testing a hypothesis, we report its p-value without adjustment. As we did not set equivalence margins in advance, we interpret non-significant differences through their CIs, i.e., as bounds on the differences that are compatible with the data, rather than as evidence of equivalence. To assess whether the difference depends on the context, we test for each outcome the null hypothesis that the coefficient of agentic is the same in all three contexts with a Wald χ2 test (Agresti, 2006), adjusting p-values with the Holm-Bonferroni method across the nine outcomes (Holm, 1979), and report the context-specific ratios with their 95% Wald CIs. As in RQ 1, we predict each test method both as human-authored and as agent-supported with its own size and all random effects at zero, i.e., for a typical PR in a typical repository, and average the predictions. For counts, predictions are on the response scale, i.e., the mean count among test methods with at least one. For binary outcomes, we also report the share of the latent variance that lies between repositories and PRs. 

4.3.4 RQ 4: Test Smells 

In RQ 4, we investigate whether agent-supported and human-authored PRs differ in how they affect the evolution of test smells. 26 Roberto Milanese et al. 

Data Preparation. For each test-related PR, we analyze the test suite immedi-ately before the contribution ( pre-PR ) and after it ( post-PR ) using JNose (Virg´ ınio et al., 2020), a static-analysis-based test smell detector specifically designed for Java. In our previous study (Milanese et al., 2026b), we used the language-independent AromaDr detector (Silva et al., 2025). Since the present study focuses exclusively on Java, we use JNose because it provides a broader cata-log of 21 test smells, therefore, 11 more categories than AromaDr , and reports individual occurrences together with their source-code location. The complete catalog of the 21 categories is described by Virg´ ınio et al. (2020). We run JNose-Core independently on the complete pre- and post-PR snapshots. Test code unaffected by the contribution appears in both revisions and therefore cancels out when computing the change in smell occurrences. The fine-grained locations reported by JNose allow us to retain the results at two complementary levels: the complete PR and the individual test method. We also distinguish between Addition and Modification contributions using the classification available in pull request analysis . Addition PRs do not alter pre-existing test logic, whereas Modification PRs change existing tests. We analyze the two groups separately because creating new test code and maintaining existing tests may exhibit different test-quality dynamics. 

Metrics. For each smell category s, we measure its evolution through the Smell Delta :

∆s = N post s − N pre s , (5) where N pre s and N post s are the numbers of occurrences detected before and after the contribution. Positive values indicate a net increase in the smell, negative values indicate a net reduction, and zero indicates no net change. Using the delta rather than the absolute post-PR count prevents pre-existing smell occurrences from being attributed to the contribution. We compute this metric at two granularities. At the PR level, smell oc-currences are aggregated over the complete contribution, capturing its overall effect on the test suite. At the method level, the delta is computed for each individual test method, allowing us to determine whether differences between agent-supported and human-authored contributions remain observable at a finer granularity. For newly added methods, the pre-PR smell count is zero, whereas for removed methods the post-PR count is zero. In addition to the category-specific deltas, we compute the Total Smell Delta , obtained by considering all detected smell occurrences together. Al-though JNose supports 21 categories, one category exhibits no variation in our data; therefore, the statistical analysis covers the remaining 20 categories and the aggregate outcome. 

Statistical Model. As in the previous research questions, observations originat-ing from the same repository cannot be assumed to be independent. We there-fore fit linear mixed-effects models using the same repository-level random-Testing with Coding Agents 27 

effects structure introduced in RQ 1, allowing both the baseline and the dif-ference between agent-supported and human-authored contributions to vary across repositories. At the PR level, we specify the model as: 

delta ∼ agentic + log( added change size + 1) + log( modified change size + 1) + (1 + agentic | repository ).

(6) The two change size terms control for the amount of newly added and modified test code, since larger contributions have more opportunities to intro-duce or remove smell occurrences. For Addition PRs, modified change size 

is omitted because pre-existing test logic is not modified. At the method level, we extend the same model with (1 | pr ), following the approach adopted in RQ 3, since multiple test methods belonging to the same PR are not independent. The coefficient of agentic therefore estimates the average difference in Smell Delta between agent-supported and human-authored contributions with comparable change size within repositories. 

Statistical Analysis. For each model, our primary quantity of interest is the coefficient of agentic . A positive coefficient indicates that agent-supported contributions exhibit a larger Smell Delta than human-authored contributions, whereas a negative coefficient indicates a smaller Smell Delta. Since the out-come represents a net difference, the coefficient captures the overall evolution of the smell and should not necessarily be interpreted as the number of smell instances directly introduced by the contribution. We report the coefficient with its 95% CI and assess statistical signifi-cance at α = 0 .05. Because the same comparison is repeated across 20 smell categories, we adjust the corresponding p-values using the Holm-Bonferroni method (Holm, 1979). The correction is applied separately for each combi-nation of analysis level (PR or method) and contribution type (Addition or Modification), while the Total Smell Delta is analyzed as a separate aggregate outcome. 

4.3.5 RQ 5: Code Coverage 

In RQ 5, we investigate whether agent-supported and human-authored PRs differ in how much code coverage they introduce and how well the test changes they make keep pace with the production code they modify. Unlike the other research questions, which analyze source code, RQ 5 requires building each project and executing its test suite before and after every PR. For this reason, it only covers the test PRs of the repositories that we can build automatically. 28 Roberto Milanese et al. 

Data Preparation. For each repository, we try combinations of build tools (Maven or Gradle , using the project’s wrapper if available) and Java ver-sions supported by the project until we find one under which it builds success-fully. Of the 391 repositories in our dataset, 150 pass this step. For each test PR of these repositories, we run the test suite twice: once at the pre-merge commit and once at the post-merge commit identified in Sec-tion 4.2.4. This ensures that the two runs differ only by the changes introduced by the PR itself. Each run occurs in a Docker 9 container with time limits of 15 minutes for the build and 30 minutes for the tests. To record which lines of code each test executes, we run the JUnit 4 and JUnit 5 tests for each module with the JaCoCo agent and a custom listener that saves and resets coverage data at the beginning and end of each test method. To identify the test methods that each PR adds, modifies, or deletes, i.e., the tests contributed in the PR , we reuse the Hamster models built in RQ 2. Since Hamster does not always identify the contributed tests correctly, for the metrics that depend on them we exclude the PRs where more than 10% of the contributed tests are missing from the run in which they should appear, or where tests present in only one of the two runs are not identified as contributed. We also record every coverable line of every class so lines that no test executes are counted as well. We only analyze a PR when both runs complete and we can verify that they were executed at the expected commits. This results in 3,619 test PRs (1,552 agent-supported and 2,067 human-authored) from 95 repositories. 

Metrics. All of our metrics measure line coverage, i.e., the proportion of ex-ecutable lines covered by at least one test, but they differ in which lines and tests they consider. Given a set of classes C and a set of tests T , we define coverage at commit c ∈ { pre , post } of a PR as:

Codebase Coverage. Cov c(K, A ) is the coverage of all the classes of the project by its whole test suite. We compute it on all test PRs, both test-only and mixed, with at least one coverable line at both commits. 

Affected-Class Coverage. Cov c(X ∪ P, A ) is the coverage, by the whole test suite, of the classes that a PR contributes to, either because it changes their production code or because the tests contributed in the PR exercise them.

New-Line Coverage. It is defined on the set N of coverable lines that the PR adds to production files. The difference depends on the repository, and has no consistent direction. Un-like in RQ 1 and RQ 2, where agents differed in the same direction in most repos-itories, the coverage of production changes varies between repositories without a consistent direction. Agent-supported PRs cover their changed classes better in an estimated 57% of repositories, with the odds ratios of 95% of reposito-ries expected to lie between 0.50 and 2.27. Covered new lines vary the most (ˆ τ = 0 .73, 95% of repository odds ratios between 0.27 and 4.79, agents higher in an estimated 57%), so whether agents leave more or less of their new code uncovered depends on the project. For Contributed-Test Coverage in test-only PRs, the few repositories with both groups do not allow us to estimate this variation separately, as discussed above. 

Robustness. We repeat the analyses with nine variations: removing test classes from the coverage data, which is possible for Affected-Class, Contributed-Test, and Production-Change Coverage; keeping all PRs regardless of how many contributed tests we could verify, or only those where all of them are verified; excluding PRs in which Hamster did not detect some of the changed test methods; excluding PRs where a new test fails; modeling the change in cov-erage instead of adjusting for the baseline; letting the effect of agentic differ for PRs without a baseline; adding the amount of test code changed; and, for Contributed-Test Coverage, also adding whether the PR adds and modi-fies tests. No conclusion changes in any of them. In particular, the difference in Contributed-Test Coverage in test-only PRs holds in all seven variations that apply to it ( OR 0.55-0.64, all p < 0.05). Since the classes that the con-tributed tests execute include test classes, whose lines are executed by their own tests, the variation without test classes is especially relevant: it leaves the odds ratio unchanged ( OR 0.62), so the difference is not caused by tests covering their own classes. The difference also holds when we keep all PRs regardless of verification ( OR 0.55), which matters because the verification excludes more agent-supported than human-authored test-only PRs (29.9% vs. 16.2%). Adding the amount of test code changed to the model of covered Testing with Coding Agents 49 

new lines reduces the small, non-significant advantage of agents from OR 1.14 to 0.99, so any difference there runs through the amount of test code, which is larger in agent-supported PRs (RQ 1). 

Model fit. All models converged with the full random-effects structure, and residual diagnostics show an acceptable fit, except that for Affected-Class and Production-Change Coverage the dispersion varies between PRs more than our models allow, so we do not rely on the width of their intervals; the complete diagnostics are available in our replication package (Milanese et al., 2026a). 

Answer to RQ 5: Among PRs that change test code, we detect no difference in how well agent-supported and human-authored PRs cover their production changes, and in both groups about three quarters of the covered new lines are reached by the tests contributed in the PR. Agents’ tendency to add new tests rather than adapt existing ones therefore does not appear to leave their changes less covered, although our data cannot establish that the two groups are equivalent, nor speak to production changes made without tests. The only significant difference appears in test-only PRs, where the tests that agents contribute cover about 11 pp less of the classes they exercise, especially in small PRs. Since only 11 repositories contribute test-only PRs of both groups, this result should be confirmed on a larger sample. Codebase coverage, which includes test code, increases more often in agent-supported PRs, but this mostly reflects the test code they add. 

6 Discussion 

Section 5 already interprets the results of each research question. This section discusses what they mean together, relates them to prior work, and derives implications for research and practice; it closes with the threats to validity. Since agent-supported PRs are, by construction, collaborations between de-velopers and agents, the differences we observe characterize this collaboration as a whole. They may reflect how agents carry out a task, but also how de-velopers choose, specify, and review the tasks they delegate, which our data do not separate; we use phrases such as “agents add tests more often” in this descriptive sense. 6.1 Comparisons must account for the project Pooled and within-repository comparisons of the same contributions lead to different conclusions (RQ 1). Agent-supported PRs are concentrated in repos-itories whose PRs change test code less often, so a pooled comparison mixes two questions: whether agent-supported PRs differ from human-authored ones within a project, and in which projects coding agents are adopted. Our pre-vious study pooled PRs across repositories (Milanese et al., 2026b), and the 50 Roberto Milanese et al. 

other comparisons of agentic and human tests pool them at least in part (Sec-tion 3). Our results do not invalidate their findings, which concern different populations and outcomes, but they show that project composition can be large enough to hide a substantial difference and to reverse the sign of others. The project matters in a second way. The average differences we report summarize a distribution of repository-specific differences whose spread is of-ten larger than the average itself, so statements such as “agent-supported PRs test more” hold on average, not necessarily in a given project. Part of this variation is systematic: for testing frequency, test additions, and oracles, the difference is smallest where the practice is already common in the repository, which is consistent with agents, or the developers who steer them, following each project’s conventions. The rest is unexplained, and candidate moderators include the maturity of the test suite, the strictness of continuous integration and review, the presence of agent instruction files, and the agent used. 6.2 Agents take on a different share of testing work Taken together, RQ 2, RQ 3, and RQ 5 suggest that the two groups differ more in which testing tasks they carry out than in the tests they write. Agent-supported PRs add tests more often and modify or delete them less often, but we detect no difference in most structural characteristics of the tests they add, nor in how well their production changes are covered. These are differences in whether a PR performs a task, not in how many tests it adds or how fast a suite grows. A possible explanation is that adding a test is a self-contained task that can be carried out from the context of the change at hand, whereas modifying or deleting an existing test requires reconstructing what it checks and judging whether it is still needed. Two further explanations are plausible but untested: agents may be instructed to add tests for the changes they make rather than to revise existing ones, and developers may delegate to agents tasks that call for new tests. Whatever the cause, if agent adoption grows, the maintenance of existing tests may shift toward developers, and obsolete tests may accumulate where agents contribute most; whether this happens can only be established by a longitudinal analysis of test changes over the history of each project. Our coverage results are not directly comparable with those of prior studies. Alves and Teixeira (2026) report higher diff coverage for AI-only than for hu-man PRs in Python, comparing PRs pooled across repositories, whereas within repositories we detect no difference in the coverage of added lines. Dipongkor et al. (2026) run the post-PR suite with and without the test changes of a PR, so that production code is fixed and only the tests vary, and estimate the coverage gained through those changes. We instead compare two com-plete revisions and attribute coverage to individual test methods, so our share of covered added lines executed by contributed tests also includes lines that pre-existing tests execute. 6.3 Test quality remains an open question The evidence on the quality of the resulting tests is less conclusive than on the kind of work. The PR-level smell estimates of RQ 4 are borderline, opposite in sign for additions and modifications, and not reproduced for individual test methods, so we treat them as hypotheses. If confirmed, they would imply that agent-supported PRs more often perform the activity in which their Smell Delta is lower, so that the net consequence for a project would depend on its mix of testing work. The divergence between the two levels admits non-exclusive explanations: smells defined on the test class or its shared setup, such as General Fixture, are counted at the PR level but only partly attributed to test methods; a few contributions with very large deltas may dominate the PR-level estimates; and the two levels weight PRs differently. Decomposing the deltas into introduced and removed occurrences, separating class-level smells, and assessing the influence of extreme contributions would distinguish them. Two other results indicate where quality differences may lie, if any. Tests that lose their oracle are rare but concentrated in a few projects, in some of which agent-supported PRs lose oracles far more often (RQ 3), and in test-only PRs the tests that agents contribute cover less of the classes they exercise (RQ 5). Both rest on few repositories, and neither smells nor coverage measure whether tests would detect faults (Inozemtseva and Holmes, 2014). More gen-erally, estimates of the quality of agent-written tests can depend on the unit of analysis, so studies of this question should state the level at which their claims hold and, where possible, report more than one. 6.4 Implications 

For researchers. Comparisons between agent-supported and human-authored contributions should be made within projects, or model project identity ex-plicitly, since pooled comparisons conflate agent behavior with agent adop-tion (Section 6.1). The unit of analysis should be stated and justified, as contribution-level and method-level analyses of the same data can yield differ-ent estimates, and coverage studies should state which tests and which lines a measure attributes to a contribution, since designs that seem similar estimate different quantities (Section 6.2). Finally, most current evidence concerns the tests that agents write, whereas our results suggest that the tests they do not update or delete are equally relevant to the evolution of test suites. 

For practitioners. In our data, the tests that agents add resemble those of developers in the same project, and we detect no difference in how well they cover the production changes they accompany. The main difference concerns the existing tests: teams adopting coding agents should not assume that their maintenance will follow from agent-supported work at the same rate as from human work, and may want to request it explicitly, for instance by asking agents to review and update the tests linked to the code they change. When 52 Roberto Milanese et al. 

reviewing agent-supported PRs, two checks are inexpensive: whether a mod-ified test still contains an assertion, and, in PRs that only add tests, which part of the class under test the new tests exercise. Whether agent-supported changes to existing tests also deserve stricter review for test smells depends on the robustness of the RQ 4 estimates (Section 6.3). 

For agent and tool builders. The lower likelihood that agent-supported PRs modify or delete tests suggests a concrete design direction. Agent instructions and scaffolds could make test maintenance part of the task, for example by retrieving the existing tests linked to the production methods being changed and asking whether they should be updated or removed before new ones are written. Agents could also report which existing tests exercise the changed code and whether they were updated, which would make the omission visible to reviewers. Since smell detection and per-test coverage are inexpensive to compute on a PR, both could be integrated into such reports, should the RQ 4

and RQ 5 differences prove robust. 6.5 Threats to Validity 

Construct validity. Whether a coding agent participated in a PR is inferred from the traces it leaves: we combine PR-level and commit-level signals fol-lowing Robbes et al. (2026c), which reduces the reliance on any single con-vention but cannot be exhaustive. Agent use that leaves none of these traces places agent-supported PRs in the human-authored group, which we there-fore describe as primarily human-authored. The direction of the resulting bias is uncertain. The heuristic that misclassification biases estimates toward the null, and that results are therefore conservative, holds only when the error is nondifferential with respect to the outcome and independent of errors in other variables, and it has several exceptions even then (Yland et al., 2022). Nei-ther condition can be taken for granted here: whether agent use leaves a trace plausibly depends on the agent, on the period, on project conventions, and on the type of contribution, all of which may also be associated with testing behavior. Since the misclassification rate may also differ between repositories, it can affect the repository-specific differences, and therefore ˆ τ , as well as the average effect. We therefore do not assume that our estimates are conserva-tive. Conversely, an agent trace does not indicate how much of a PR the agent produced or how much the developers revised it, so agent support is a binary approximation of a graded construct, and PRs matching several agents are treated as agent-supported without distinguishing between agents. Test code is identified with a heuristic validated in our previous study (Sec-tion 4.2.5). Test changes are linked to production changes through statically resolved calls, so the number of co-evolving PRs is a lower bound, and changed test units that Hamster does not detect are excluded (Section 4.3.2). Smell detectors have false positives and negatives, and the aggregate Smell Delta weights all categories equally. Neither smells nor coverage measure whether Testing with Coding Agents 53 

tests would detect faults, which would require measures such as mutation analysis. 

Internal validity. Our study is observational, and the differences we report are associations rather than causal effects of agent support. Developers may dele-gate to agents well-scoped, easily testable, or greenfield tasks, and our models adjust for the repository and change size but not for the type or difficulty of the task. Since size may itself be affected by agent support, our coefficients estimate the difference between PRs of equal size rather than the total dif-ference associated with agent support. Finally, we analyze only merged PRs, so our results describe what projects accept after review, with changes made during review credited to the PR, not the contributions that agents initially produce. 

Conclusion validity. We control the family-wise error rate with the Holm-Bonferroni method within each family of tests. The two aggregate Smell Delta models are analyzed outside these families, and with Holm correction across the four aggregate tests their p-values (0.024 and 0.046) would not be signif-icant, so we regard them as indicative. These models use an identity link on heavy-tailed signed differences of counts, so their estimates may be sensitive to extreme contributions. Where residual diagnostics indicate a misspecified dispersion, we do not rely on the width of the intervals, and the counts of repositories whose specific interval excludes 1 are descriptive and not adjusted for multiplicity. Non-significant results are not evidence of equivalence. 

External validity. We restrict the study to Java, whose standardized build tools make coverage measurement feasible at scale, and our findings should not be assumed to transfer to other ecosystems; RQ 5 is further limited to the repositories that can be built with Maven or Gradle, which may differ systematically from the others. Requiring at least ten agent-supported and ten human-authored PRs retains 391 of the 22,932 repositories with agent activity, and selects projects with both substantial agent adoption and sustained human contribution. Codex, Copilot, and Claude Code account for almost all agent-supported PRs (Section 4.2.7), so our results mainly characterize these three, and they describe the period from January 2025 to April 2026 rather than a stable state of a rapidly evolving practice. 

7 Conclusion and Future Work 

This paper compared testing in agent-supported and human-authored PRs along five dimensions: the frequency and extent of testing, the type and context of test changes, the structure of test code, test smells, and code coverage. On 114,134 merged Java PRs from 391 repositories that contain both groups, we made every comparison within repositories, controlling for the size of the contribution. 54 Roberto Milanese et al. 

Our results support three conclusions. First, comparisons of agentic and human contributions depend on the project: pooled across repositories, the two groups appear almost indistinguishable in how often they change test code, whereas within repositories agent-supported PRs do so more often, and the size of the difference varies considerably between repositories. Second, agent participation is associated with a different mix of testing work: more additions and fewer modifications and deletions of existing tests, without a detected difference in most structural characteristics of the added tests or in the coverage of production changes. Third, whether agent participation affects test quality remains open: the differences in test smells are borderline and depend on the level of analysis, and the lower coverage of agents’ tests in test-only PRs rests on few repositories. For practitioners, this means that the maintenance of existing tests should not be assumed to follow from agent-supported work, and may need to be requested explicitly. Several directions follow. A longitudinal analysis of test additions, modifi-cations, and deletions over the history of each project would show whether the per-contribution difference leads to faster suite growth or shifts maintenance toward developers. Modeling repository-level moderators would help explain the variation between repositories. For test smells, decomposing the deltas into introduced and removed occurrences and reconciling the two levels of analysis would establish whether the borderline differences are robust, and a per-agent comparison would require a dataset in which agents other than the three most frequent ones are sufficiently represented. Separating what agents initially produce from what review corrects would make it possible to attribute the observed differences to the agent, to the developer, or to the review process, and mutation analysis would show whether coverage differences translate into differences in fault detection. Finally, replicating the study in other ecosystems and over a longer window would show how far these findings extend as coding agents and the practices around them evolve. To support verification and reuse, the dataset, the queries, and the analysis scripts used in this study are publicly available in our replication package (Mi-lanese et al., 2026a).

## 摘要
随着大语言模型智能体越来越多地将自然语言需求编译为仓库级代码，从需求生成测试以提供验证约束（或测试装置）来指导代码生成正变得日益重要。然而，当前智能体能否在该行为实现未被提供的情况下生成验证所需行为的测试，仍不清楚。现有测试生成基准大多聚焦白盒测试，而与需求—测试相关的研究通常需要评估给定文档与生成测试之间的语义对齐。我们提出 Req2Test-Bench，一个包含 5,086 个经执行验证的实例的基准，这些实例从 8 个开源项目中开发者编写的行为驱动开发（BDD）制品中恢复而来，涵盖 5 种编程语言和 4 个 BDD 框架。每个实例将一个 Gherkin 格式的自然语言需求与其开发者编写的测试实现配对。给定需求以及所需行为的目标接口，智能体必须生成完整、可能为多文件的测试实现。对 8 种智能体—模型—推理配置的评估揭示了执行成功与行为充分性之间的显著差距；行为充分性被严格地以杀伤完备性（kill-completeness）衡量：一个杀伤完备的测试会杀死真实测试所杀死的每一个变异体。表现最佳的配置 Codex 搭配 DeepSeek-V4.1-Flash 为 82.8% 的实例生成了可通过的测试，但只有 33.8% 在行为上充分。我们发现：（1）扩大智能体规模在行为充分性方面相对于生成成本而言收益急剧递减；（2）需求描述不充分会导致信息差距，包括设置模糊和预期结果隐含；（3）以需求为基础的测试装置能够引导智能体的非确定性，为改进提供了有前景的方向。

## Abstract
As large language model agents increasingly compile natural-language requirements into repository-level code, requirement-to-test generation grows in importance to provide validation constraints (or harness) to guide code generation. Yet it remains unclear whether current agents can generate tests that validate the required behavior when the implementation of that behavior is withheld. Existing test-generation benchmarks mostly focus on white-box testing, whereas the requirement--test-related study usually requires evaluation on semantic alignment between the given documents and the generated tests.   We introduce Req2Test-Bench, a benchmark containing 5,086 execution-validated instances recovered from developer-authored behavior-driven development (BDD) artifacts in 8 open-source projects, spanning 5 programming languages and 4 BDD frameworks. Each instance pairs a natural-language requirement in Gherkin with its developer-written Test Implementation. Given the requirement, target interfaces of the required behavior, an agent must generate a complete, potentially multi-file Test Implementation. Evaluation of 8 agent--model--reasoning configurations reveals a substantial gap between execution success and behavioral adequacy, which is measured strictly as kill-completeness: a kill-complete test kills every mutant that the ground-truth test kills. The best-performing configuration, Codex with DeepSeek-V4.1-Flash, produces passing tests for 82.8% of instances, yet only 33.8% are behaviorally adequate. We find that (1) scaling up agents yields sharply diminishing returns in behavioral adequacy relative to generation cost; (2) under-specified requirements cause the information gap, including ambiguous setup and implicit expected outcomes; and (3) requirement-grounded harnesses that steer agent non-determinism offer a promising direction for improvement.

## 1. 核心问题与整体含义（研究动机与背景）

- **研究背景**：LLM 智能体正越来越多地把自然语言需求编译为仓库级代码。为保障生成代码的正确性，需要由需求派生的测试充当“验证约束（harness）”，用于候选方案筛选与迭代精化。但生成的测试可能“通过却无实质检查”（空断言、同义反复断言），在目标行为实现尚未存在时问题尤为尖锐。
- **核心问题**：当所需行为的实现被**隐藏**时，当前 LLM 智能体能否仅凭自然语言需求，生成**完整、可执行且行为充分**的测试？
- **现有基准的不足**：
  - 主流测试生成基准（Methods2Test、TestBench、TestGenEval、SWT-Bench、AutoE2E 等）以**给定代码/缺陷上下文/运行中的应用**为任务边界，属白盒或缺陷驱动设定。
  - 需求—测试类资源存在互补缺陷：E2EDev 使用合成/人工改造的需求与测试；GivenWhenThen 只有文件级关联而非单场景级、执行验证过的测试实现；DevBench 使用基准作者撰写的 PRD，未把单条需求准则映射到单条真实测试。
- **整体含义**：论文把“需求→测试生成”重新定义为**需求驱动、接口辅助**的仓库级任务，并以开发者自己写的测试作为行为充分性的参照，系统刻画了“执行成功”与“行为充分”之间的巨大鸿沟。

## 2. 方法论

### 2.1 核心思想

- 利用 **BDD（行为驱动开发）** 制品作为天然的需求—测试配对来源：Gherkin 的 `Feature`（能力描述）+ `Scenario`（具体行为示例，由有序 `Step` 组成）对应开发者编写的 `Step Definition` 与辅助代码闭包（即 Test Implementation）。
- 每个实例的操作性需求定义：$r_i \triangleq \langle F_i, S_i \rangle$（外层 Feature + 目标 Scenario）。
- 任务形式化：
  $$T^{gen}_i = \mathcal{A}\left(r_i,\ \mathcal{I}^{\alpha}_i\right),\quad \mathcal{I}^{\alpha}_i \triangleq \left\langle I^{tar}_i,\ C^{\alpha}(P_i)\right\rangle$$
  其中 $\mathcal{A}$ 为 LLM 智能体，$I^{tar}_i$ 为目标接口声明，$C^{\alpha}(P_i)$ 为项目上下文视图。
- **两种实现可见性视图**（两者都隐藏目标实现）：
  - **Target-hidden（TH）**：仅把实现目标行为的选定生产代码体（含相关一等方委托）替换为保留声明的占位符。
  - **All-hidden（AH）**：在整个声明生产代码范围内替换实现体。
- **目标接口识别**：对 ground-truth 测试在 `When`/`Then` 步骤中直接调用的一等方公共生产方法做去重、按声明类型分组，仅提供方法声明，不泄露调用实参、调用顺序、断言或测试代码。

### 2.2 数据集构建流程（五阶段）

- **Stage I 候选发现**：以框架依赖、配置、Step Definition 为静态证据，从 GitHub 收集含 Gherkin 与 BDD 测试代码的仓库；4 个执行框架：Cucumber（Java/Ruby）、Behave（Python）、Behat（PHP）、Godog（Go）。
- **Stage II 项目准入与需求过滤**：综合 star 数、最近推送时间、BDD 套件规模与领域/测试多样性选取 8 个项目；剔除需浏览器或在线服务的场景；要求项目初始化成功、每个有效 Step 唯一绑定非 pending 的 Step Definition、且场景在隔离环境下三次运行均通过（不修改原始需求/测试）。
- **Stage III 测试实现恢复、接口识别与视图构造**：
  - 从运行时绑定出发，恢复传递性的“项目本地测试侧闭包”（含 helper，排除生产代码、第三方框架与共享测试基础设施）。
  - 用**正/负两个派生工作区**验证：正工作区仅保留闭包，目标场景须通过；负工作区去掉闭包，运行器须能初始化但目标场景不得通过；三次运行均需满足。
  - 用语言感知的源码变换构造 TH / AH 视图；两视图都移除所有场景的 Step Definition 与 helper，但保留 hooks、fixtures、测试数据等共享基础设施；均不展示运行时轨迹、覆盖率或变异记录。
- **Stage IV 变异数据与可评分性**：
  - 实现语言特定的变异算子族（条件边界、取反、算术/逻辑算子替换、常量与返回值替换、方法调用删除等），共 11 类算子，按项目记录适配。
  - 变异池定义依赖 ground-truth 覆盖率：
    $$U^{mut}_i = \left\{ m \in M_{P_i} \mid L(m) \cap C^{gt}_i \neq \varnothing \right\}$$
  - 对每个“实例—变异体”对单独执行 ground-truth 测试，记录被杀/存活；超时或未执行任何 Step 前失败的对被排除。另构造“断言剥离后仍被杀”的**断言依赖子集**用于二次分析。
- **Stage V 标注**：测试层级（component / integration / system，依据 Step Definition 触达生产代码的方式）与需求关系（`depends_on`、`variant_of`）；标签不改变任务本身。

### 2.3 评估指标

- **分层执行结果**：Generation failure → Build failure → Binding failure → Execution failure → Assertion failure → Pass；据此计算
  $$\text{Pass@1} = \frac{1}{N_{exec}}\sum_{i\in E}\mathbf{1}[o_i=\text{pass}]$$
- **与 ground-truth 的行为对比**：
  - API 调用 F1：$2|Gen^{api}_i \cap GT^{api}_i| / (|Gen^{api}_i|+|GT^{api}_i|)$
  - 覆盖率 Jaccard：$|Gen^{cov}_i \cap GT^{cov}_i| / |Gen^{cov}_i \cup GT^{cov}_i|$
  - 变异杀伤召回：$|Gen^{mut}_i \cap GT^{mut}_i| / |GT^{mut}_i|$
- **主指标 KillComplete@1**：测试通过且杀掉 ground-truth 测试所杀的**每一个**变异体（kill-complete）：
  $$\text{KillComplete@1} = \frac{1}{N}\sum_{i\in I^{mut}}\mathbf{1}\left[o_i=\text{pass} \wedge \text{MutRecall}_i=1\right]$$
  未通过的实例永不计为 kill-complete；分母为完整计划样本 $N$。
- **效率指标**：生成时间、LLM 调用次数、输入/输出 token、货币成本，以及“每次执行通过”“每次 kill-complete 通过”的成本。
- **聚合方式**：项目内先对全部 $N$ 个实例取均值（不通过记 0），再对项目等权平均；置信区间用项目内 feature 文件的簇自助重采样得到，配对比较用精确 McNemar 检验或符号翻转检验。

## 6. 主要结论与发现

- **执行成功 ≠ 行为充分**：最佳通过率配置 Codex/DS（target-hidden）Pass@1 达 **82.8%**（[80.5, 84.8]），但 KillComplete@1 仅 **33.8%**（[28.4, 38.1]）。各项目上仅 6.7%–66.2% 的通过测试是 kill-complete。
- **差距不是“要求过严”造成的**：即使放宽到“复现 ≥95% 杀伤”仍只有 53.9%（比 Pass@1 低 28.9 pp）；只统计断言依赖杀伤时差距仅缩小 24%–37%，配置排名不变；只统计隐藏目标实现内杀伤时差距依然存在（Codex/DS 为 11.9 pp）。
- **高覆盖率相似度不等于 kill-complete**：在 6 个项目上，覆盖率 Jaccard ≥ 0.9 的通过测试中仍有 17.4%–69.7% 是 kill-incomplete。
- **失败主要出在“检查”而非“路径”**：Codex/DS 的 kill-incomplete 测试中 77.9% 实际执行到了被杀变异体所在代码却仍然通过，仅 22.1% 是纯粹没跑到。
- **收益随成本急剧递减（RQ2）**：成本跨度约 30 倍，效果不随成本上升。Pareto 前沿上从 Codex/Luna 到 Claude Code/DS，成本 ×4.0 仅换来 +6.1 pp；再往上无显著收益。Codex 从 Luna→DS 成本 ×6.0 换 +5.5 pp，DS→Sol 再 ×4.9 却 −2.5 pp；Sol 比 Luna 贵约 30 倍仅 +3.0 pp。
- **脚手架与推理强度影响大**：

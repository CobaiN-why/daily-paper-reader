## Abstract 

Efforts to improve LLM-based agents typically focus on modifying the agent itself, yet success also depends on the environment in which an agent acts. Tools mediate this interaction: a tool’s description shapes how an agent calls it, and its imple-mentation determines the results and errors the agent receives afterwards. Many tools, such as APIs and MCP servers, are shared by many agents and maintained by providers who cannot change those agents. We introduce AT-AT (Automatic Tool Optimization from Agent Traces), an agentic tool optimizer that improves a shared toolset offline from historical agent executions while holding the agents fixed. A lightweight coding agent reads agent trajectories and their evaluation results, and selectively edits tool descriptions and, when permitted, implementations. On τ 2-bench-verified, AT-AT achieves the highest task completion rates in the Airline and Telecom domains at lower cost than strong prompt- and tool-optimizer baselines, and its Telecom gain is statistically significant under paired permutation tests. Opti-mizing the tools within a coding agent harness also improves held-out performance on TerminalBench-2 and TBLite. When applied to three production MCP servers at a large enterprise, AT-AT lowered cost or tool error rates on every server and increased held-out task passes on one. By turning accumulated execution traces into updates to shared tool environments, AT-AT provides a path toward continual improvement of agent systems through environment-side learning. 

## 1 Introduction 

Efforts to improve LLM-based agents typically modify the agent itself: training the underlying model, optimizing its prompts [Agrawal et al., 2026, Kassianik et al., 2026], or engineering the harness that manages its execution [Lee et al., 2026b, Zhang et al., 2026, Weng, 2026]. However, an agent’s success is a property not only of the agent, but also of its interaction with the external environment. Tools mediate this interaction, as they define the actions available to the agent and the information returned in response. We study a complementary path to better agent performance: improving the tool environment from accumulated agent experience based on historical execution traces, while holding the agent fixed. The opportunity for such optimization is large and growing. In an enterprise, an agent’s tool environment may include Model Context Protocol (MCP) servers spanning many internal systems. More broadly, nearly any software API can be exposed as an agent-callable tool. Most APIs, however, were designed for human developers or conventional software rather than for the capabilities and limitations of LLM agents. Cloud services can now automatically translate existing APIs into agent-

These tools are typically maintained by a provider who cannot change the many agents that call them, but any change the provider makes to a tool reaches all of those agents. This is our primary setting. A tool has two parts. Its description , comprising its name, parameter schema, and usage notes, shapes the agent’s expectations before a call, while its implementation determines the results and errors the agent receives after it. Because tool results enter the agent’s context, actionable errors can enable recovery and relevant outputs can support better subsequent decisions. We call this mechanism feedback shaping : improving the information returned by tools without changing the agent or its evaluation objective. For example, a τ 2-bench-verified Telecom tool that reports a line’s data usage and plan limit leaves the agent to work out whether the line has run out of data, while an implementation that also returns the remaining data gives the agent this information directly. Anthropic reported a 40% decrease in task completion time after redesigning the tools available to an agent [Anthropic, 2025b], suggesting that tool design materially affects agent performance. Existing automatic methods primarily optimize the information presented before a tool is invoked: DRAFT [Qu et al., 2025], Play2Prompt [Fang et al., 2025], EasyTool [Yuan et al., 2025], and ToolObserver [Hallinan et al., 2026] use exploration traces or reflection to refine tool descriptions or usage examples. Harness optimizers such as Meta-Harness [Lee et al., 2026b] can also edit tool code, but they optimize the harness of a single agent rather than a toolset shared by many agents. In this work, we aim to automatically improve both the descriptions and implementations of shared tools from evaluated agent traces. We introduce AT-AT (Automatic Tool Optimization from Agent Traces), which converts historical agent experience into selective edits to a toolset. A lightweight coding agent searches evaluated agent traces for recurring failure modes, inspects the tool source, and edits tool descriptions and, when permitted, implementations. A coding agent can search many long traces as needed, and it can read the tool’s code to decide whether a failure calls for a description or an implementation fix. AT-AT performs a single offline pass over previously collected executions, requiring no new agent rollouts. Trace-driven optimization raises two methodological challenges. First, repeated agent executions can produce materially different outcomes even when the task, model, harness, environment, and decoding configuration are held constant. We evaluate the original and optimized toolsets with 30 trials per held-out task and use paired permutation tests to determine whether observed changes exceed stochastic variation. Second, an optimizer can overfit to a small set of trajectories or tasks, which is a particularly consequential risk for shared tools. We expose AT-AT to traces spanning 2multiple tasks and repeated trials, direct it toward generalizable edits, and evaluate the resulting toolsets on held-out executions. We evaluate AT-AT in three settings. On τ 2-bench-verified, AT-AT achieves the highest held-out task completion rate in Airline and Telecom at a lower cost per test simulation than prior prompt and tool optimizers, and its gain of 7.25 percentage points in Telecom is statistically significant. On TerminalBench-2 and TBLite, optimizing the tools within the OpenCode harness improves held-out pass@1 and pass@3, demonstrating applicability beyond customer service tools. On three production MCP servers at Netflix, description edits learned from historical logs from production traffic increased held-out task passes on one server and reduced tool errors and cost while maintaining performance on the other two. Together, these results show that the traces used to diagnose agent failures can also be converted into improvements to the environment itself. Because AT-AT can be rerun as traces accumulate, it provides a mechanism for continual improvement, although we evaluate a single update rather than a continual learning loop. Our contributions are as follows: • We formulate tool optimization for fixed agents from previously collected traces, where a tool’s description guides the agent before a call and its implementation shapes the feedback the agent receives after the call (feedback shaping). • We introduce AT-AT, a lightweight coding agent optimizer that translates evaluated historical trajectories into selective edits of tool descriptions and, when permitted, implementations, without new agent executions during optimization. • We evaluate AT-AT on τ 2-bench-verified, TerminalBench-2, TBLite, and three production MCP servers, using repeated held-out trials and paired permutation tests on τ 2-bench-verified to separate tool improvements from run-to-run noise. 

## 2 Related Work 

Prompt and harness optimization. Prompt optimizers search over natural-language or struc-tured prompt programs, using execution outcomes or reflective feedback to guide candidate gen-eration [Schnabel and Neville, 2024, Agrawal et al., 2026]. Coding agent optimizers expand this search space: FAPO can modify prompts and multi-step pipeline structure, while Meta-Harness, Self-Harness, and AutoSaddler optimize harness code using execution traces and scores [Kassianik et al., 2026, Lee et al., 2026b, Zhang et al., 2026, Park et al., 2026]. Meta-Harness is especially similar in giving an agentic proposer access to an agent’s source code, scores, and full traces via a filesystem, but it iteratively searches over the agent harness, which includes the harness’s internal tools, rather than a toolset alone [Lee et al., 2026b]. When tools are implemented inside the harness, as in our OpenCode experiments, AT-AT performs a restricted form of harness optimization that edits only the tools. Our primary setting instead updates a shared environmental toolset without changing the agents that consume it, since a tool provider typically does not own those agents. 

Manual tool design. Anthropic recommends designing and testing tools for LLMs rather than exposing conventional developer-facing APIs and describes an evaluation-driven workflow in which developers inspect agent transcripts and use a coding agent to revise descriptions and implementations, checking generalization on held-out tasks [Anthropic, 2025b,a]. AT-AT automates such a workflow. 

Documentation and schema optimization. Most prior methods optimize the prompt-visible sur-face of a tool. EasyTool condenses heterogeneous documentation into standardized instructions, while PA-Tool renames schema components to align with a model’s pretrained naming conventions [Yuan et al., 2025, Lee et al., 2026a]. DRAFT and Play2Prompt interact with tools to refine documentation or synthesize usage examples without labeled tasks [Qu et al., 2025, Fang et al., 2025]. A study of 856 tools from 103 MCP servers found at least one quality defect in 97.1% of tool descriptions, and augmenting the descriptions raised median task success while also increasing execution steps [Hasan et al., 2026]. This still leaves executable tool behavior fixed. 

Trace-driven tool optimization. Joint context optimization generates training-task rollouts and uses feedback on final answers and tool-call histories to jointly refine agent instructions and tool descriptions, while JTPRO uses rollout-driven reflection to co-optimize global agent instructions and per-tool schemas [Wu et al., 2025, Ghoshal et al., 2026]. ToolObserver and DocsChisel repeatedly 3rerun the agent being optimized and use fixed LLM pipelines to revise only tool documentation from its trajectories. ToolObserver distills patterns through mini-batching and consensus, whereas DocsChisel uses field-level edits with validation and regression checks [Hallinan et al., 2026, Lu et al., 2026]. AT-AT instead uses a coding-agent optimizer to update shared tools from previously evaluated trajectories without optimization-time agent reruns, and can make contract-preserving implementation edits that change execution-time results, errors, and recovery cues. ContDa uses self-generated probing traces to continually adapt documentation as tools are added, changed, or deprecated [Wu et al., 2026]. Although AT-AT can be rerun as production logs accumulate, the present work evaluates one update to an existing toolset. 

Environment optimization and tool synthesis. Other work also improves the environment rather than the agent. Song et al. [2025] derive a taxonomy of agent–environment failures from traces and show that hand-designed environment changes, such as better observability and offloading computation, improve fixed agents; AT-AT instead derives edits automatically from evaluated traces. Tool-synthesis methods expand the action space by creating new tools from API documentation [Ni et al., 2025], composing atomic actions into reusable procedures [Ding et al., 2026], or compiling procedures repeated in execution traces [Kujanpää et al., 2026]. AT-AT instead improves tools that are already deployed while preserving the interfaces their callers depend on. 

## 3 Optimization Method 

3.1 Problem Formulation Environmental tool optimization. We consider a population of agents A ∼ A . Each agent 

A = ( H, M ) consists of a fixed harness H and a fixed large language model M . The harness includes components such as the system prompt, code that manages the agent loop and multiple turns, and internal tools such as file reading and file writing utilities. We also consider a population of tasks 

x ∼ X , which can be drawn from a variety of domains. Given an agent A, a task x, and an environmental toolset TE , executing the agent generates a trajectory τ consisting of the LLM outputs, user messages, tool invocations, and tool results that occur during execution. We denote the induced trajectory distribution by pA(τ | x, T E ). Equivalently, for A = ( H, M ), pA(τ | x, T E ) = pM (τ | H, x, T E ). This distribution captures stochasticity from both the LLM and the environment. The reward r(τ, x ) measures task success. We optimize a shared environmental toolset TE = ( TED , T EC ), where TED denotes the tool descrip-tions and TEC denotes the executable tool code. Environmental tools may include external functions, APIs, or MCP servers that are not implemented within the agent harness. Our objective is to select the toolset that maximizes expected performance across a population of agents and tasks:

3.2 AT-AT Method 

Agent traces on a subset of tasks (either the train split on a benchmark, or historical tasks in a production setting) are constructed. Each agent trace consists of the agent trajectory on a certain task (agent outputs, user messages, tool invocations and results) along with the final evaluation 4result on the task. The agent traces and tools to edit are provided to the agentic tool optimizer as files in a file system. The optimizer is a lightweight, open-source coding agent, the Pi agent [Earendil Inc. and Contributors, 2026]. The optimization objective is provided as a system prompt to the Pi agent. An instruction to the optimizer to make generalizable tool edits is also provided in the system prompt. Agent traces are also provided in the user prompt to the optimizer; the first 4,000 characters of each failing run’s transcript plus up to three passing runs are included in the first user message to the optimizer LLM. The prompts to AT-AT are provided in Appendix G. The Pi agent makes selective edits to the tool files in the codebase based on what it sees in the agent traces. Once edits are finished, they must pass a validation check. The edited tool files must pass a syntax/compilation/interpreter check, and no files may be added, deleted, or edited outside the editable tool files. If validation fails, the Pi agent’s session is resumed with a prompt stating that validation failed, and the agent may revise its edits. The optimizer is given up to five attempts in total to produce a proposal that passes validation. The implementation of AT-AT is available at 

https://github.com/Netflix-Skunkworks/agent-tool-opt-core .

## 4 Experiments & Results 

4.1 τ 2-bench-verified 

τ 2-bench [Barres et al., 2026] is a popular benchmark for evaluating LLMs on customer service agent tasks. τ 2-bench-verified [Cuadron et al., 2025] is an updated version of τ 2-bench in which the tasks were manually reviewed and corrected. In our setup, the user agent and customer service agent LLMs were GPT-5.1 and GPT-4.1, respectively, which is the τ 2-bench-verified default. The default train/test task indices and evaluators from the τ 2-bench-verified repository were used. First, a baseline run of τ 2-bench-verified with the default settings was conducted, with n = 5 trials run on each task. The agent trajectories and evaluations were combined to form the baseline agent traces. The same baseline agent traces (train split only) were inputted into all tool optimization methods used, and the tool optimizers were run to generate updated toolsets. The LLM used for all tool optimizers was Claude Opus 4.7. τ 2-bench-verified was rerun using the updated toolsets. Additionally, the average cost of running a task in τ 2-bench-verified was reported, both before and after tool optimizers were applied. This cost was computed using the built-in cost tracker in τ 2-bench-verified. The cost of running the optimizer is also reported and was computed by multiplying the number of tokens used by the cost per token from the LLM APIs. 

Paired permutation testing. Agent outcomes vary across repeated executions even when the model, harness, tasks, environment, and decoding configuration are held fixed. A difference between two aggregate benchmark scores therefore does not by itself establish that one toolset reliably outperforms another. To account for this evaluation noise, we evaluate the original and optimized toolsets on the same held-out tasks, with 30 trials per task, and compare their outcomes using a paired permutation test. Pairing outcomes within tasks accounts for differences in task difficulty, while repeated trials capture run-to-run variation in agent execution. Under the null hypothesis that the toolset has no effect, the original and optimized condition labels are exchangeable within each pair; permuting these labels produces the null distribution of the difference in task completion rate. We then test whether the observed improvement is larger than would be expected from run-to-run variation. At small sample sizes, exact computation of the paired permutation test p value is possible, as described in Zmigrod et al. [2022]. However, at our larger sample size of n = 30 , we estimate the p-value using Monte Carlo permutation sampling. Each value we compute is the comparison of the optimized toolset result compared to the original, unoptimized toolset. 

Baseline optimizers. We compare to DRAFT [Qu et al., 2025], ToolObserver [Hallinan et al., 2026], and GEPA [Agrawal et al., 2026]. DRAFT is an online method requiring interaction with live tools, while our τ 2-bench-verified experiment setup provides pre-collected agent traces. Hence, our implementation contained the offline portions of DRAFT, applying DRAFT’s Analyzer and Rewriter stages once to the past agent traces. Similarly, we adapt ToolObserver to a fixed offline setting by applying its minibatch reflection and consensus merging once to pre-collected trajectories, omitting iterative exploration and trajectory recollection. We run GEPA [Agrawal et al., 2026] by treating the toolset as a prompt to be optimized. GEPA was used with 1 exploration/reflection step to provide a fair comparison to the other methods, which also used 1 exploration/reflection step. 5Overall results. We report the average reward (pass@1) scores as percentages for each of the three domains: Airline, Retail, and Telecom, both for the baseline (unoptimized) toolset and optimized toolsets produced by AT-AT, our ablations of AT-AT, and the prior baseline optimizers. The results of these experiments can be viewed in Tab. 1. AT-AT has the highest reward score on the Airline and Telecom domains, and its improvement in Telecom is the only improvement that was statistically significant. In both domains, AT-AT also costs less per test simulation than ToolObserver, the next-best prior method. DRAFT resulted in a statistically significant decrease in performance on Telecom. We contextualize the improvements AT-AT was able to achieve by comparing them to submissions on the official τ 2-bench leaderboard [Sierra Research, 2026]. The 7-point improvement AT-AT achieved on Airline is comparable to the improvement from Claude-3.7-Sonnet (released Feb. 24, 2025; 64%) to Claude Sonnet 4.5 (released Sep. 29, 2025; 72%). The 7-point improvement AT-AT achieved on Telecom is comparable to the improvement from Claude-3.7-Sonnet (released Feb. 24, 2025; 49%) to GPT-5.2 (released Dec. 11, 2025; 57%). However, the tool edits AT-AT makes can be applied to a variety of agents and potentially improve performance of many agents (discussed in Sec. 4.1.1). 

Costs. Two types of costs are reported: the cost to run a task in τ 2-bench-verified, and the cost to run the optimizer. Optimization increased the cost to run the benchmark by a statistically significant amount in many cases. We attribute this partially to the increased tool file length, leading to a higher number of tokens that the executor agent needs to process. In addition, variance in costs may be due to prompt cache hit rates. Optimizer costs were similar across optimizers, except for ToolObserver, which incurred substantially higher optimization costs. We attribute this to its minibatch-analysis and consensus-merge structure, which required many more LLM calls than the other optimizers. 

4.1.1 Ablations Effect of feedback shaping: implementation edits vs description-only edits. To test our hypoth-esis that tools’ feedback provided to an agent can meaningfully shape its trajectory and improve task success, we ran a version of AT-AT that was constrained to editing tool descriptions only and could not edit tool code. This ablation also omitted agent traces from the user prompt, though they were available in the filesystem. Results are shown in the “Edit descriptions only” rows of Tab. 1. The descriptions-only method performed substantially worse than AT-AT in all domains but Retail (in Retail, all optimized tools performed worse than unoptimized tools, but no difference was statistically significant). A further qualitative analysis comparing tool edits from this ablation is in App. B. 

Importance of past agent traces. To test if historical agent traces are a useful learning signal for AT-AT, we ran AT-AT without any historical agent traces available to it. Results are shown in the “Without past traces” rows of Tab. 1. The method without past agent traces performed substantially worse than AT-AT in all domains but Retail (but in the Retail domain, all optimized tools performed worse than unoptimized tools). This evidence supports that past agent traces are a useful learning signal for a tool optimizer. In addition to enabling a tool optimizer to learn about tool failure patterns, historical agent traces may also enable an optimizer to learn about a new domain from data that is automatically gathered, rather than being curated or labeled by humans. 

Importance of coding agent harness. To investigate the importance of the coding agent setup to the tool optimizer, we ran an experiment with a single-shot LLM-based tool optimizer. Since the LLM-based optimizer did not have the ability to search through a file system itself, the agent traces were only provided in their truncated form in the optimizer user prompt. The optimizer LLM was instructed to output a new tools.py file. Results are shown in the “Without coding agent harness” rows of Tab. 1. The LLM optimizer performed substantially worse than AT-AT in Airline and Telecom.

4.3 Production MCP Servers MCP and task selection. We applied AT-AT to production MCP servers at Netflix. Three pro-duction MCP servers at the company were chosen for optimization due to (1) having a high usage rate, (2) having a sufficient number of unique single-user prompts with actionable failures, and (3) the ability within the company infrastructure to expose and modify the tool descriptions in a sandbox environment. The MCP servers used were the following: Core Developer Tools (Dev Tools), which provides broad engineering retrieval across internal documentation, collaboration platforms, and enterprise knowledge sources; Observability Collaboration Toolbox (Collab Toolbox), which searches, summarizes, and exports channel and thread content from an enterprise collaboration platform; and Enterprise Engineering Context and Best Practices (Eng. Context), which provides enterprise-specific engineering guidance from indexed documentation and code. Tasks were defined as an initial agent prompt provided by a user, and tasks were randomly selected from each server’s prior two weeks of production traffic. Tab. 12 summarizes representative tasks. 

Experiment procedure. The list of tasks was randomly partitioned into train/test splits of 10/10, 5/5, and 11/11 tasks for Dev Tools, Collab Toolbox, and Eng. Context and Best Practices, respectively. Across both splits and in the baseline and optimized runs, system prompt, four-user-turn limit, agent model, user simulator, and all other environment settings were held fixed. The agent executing the task used the open-weight DeepSeek V4 Flash model, and the user simulator used Claude Sonnet 4.6. For each task, a baseline run with the original MCP servers was executed, with the task being the initial prompt provided to the executor agent. The baseline run was evaluated as described below. Traces of agent trajectories and evaluation results from the train split of tasks were constructed and provided to AT-AT, which used Claude Opus 4.7 as its optimizer LLM. Past traces were omitted from the optimizer user prompt, although they were available in the file system. After tool optimization, evaluation was repeated on the train and test splits using the same surrounding setup, but now with the optimized tool descriptions.

## 5 Conclusion 

AT-AT optimizes tools to improve agent performance, holding agents fixed and leveraging logged agent traces. This improved performance on multiple benchmarks, including three production MCP servers at Netflix. Because AT-AT learns from logs that deployed systems already produce, it can be rerun as traces accumulate, storing experience in the environment rather than in the agent. App. B qualitatively analyzes feedback shaping in selected transcripts, and App. C discusses how to handle evaluation stochasticity. Our results suggest several possible avenues for future work. First, a more explicit model of feedback shaping would be of interest: how changing what a tool returns steers an agent’s trajectory. Second, attributing failures to tools, agents, or tasks would bound the headroom for any environment-side intervention and let an optimizer focus on where tools are at fault. Third, a shared tool serves a heterogeneous and evolving population of agents, so tool optimization is fundamentally a problem of generalization across agents and of co-adaptation with agent- and harness-side optimization (App. E), whose interaction is not yet understood. Finally, treating the environment as a site of continual learning calls for guarantees against regression and drift as edits accumulate, and raises the possibility of using tool design to steer agents away from reward hacking and unsafe actions. 9References

## C Additional Analysis 

Effectiveness of coding agents as text optimizers. Our results here, as well as in prior work, suggest that using a coding agent as an optimizer is helpful: coding agents’ ability to reason over multiple files and make selective edits in a multi-turn fashion may be useful in text optimization settings. Here, AT-AT outperformed the ablation method without the coding agent harness, as well as the prior tool and prompt optimizers that do not use a coding agent harness, DRAFT, ToolObserver, and GEPA [Qu et al., 2025, Hallinan et al., 2026, Agrawal et al., 2026]. This echoes the outperformance of FAPO [Kassianik et al., 2026], a recent prompt optimization method using a Claude Code coding agent as an optimizer, compared to GEPA [Agrawal et al., 2026], the previous state-of-the-art prompt optimizer. Meta-Harness [Lee et al., 2026b] also uses the Claude Code coding agent as a harness optimizer. LLM capabilities have advanced steadily, and coding agents utilize the ability of LLMs to create and execute upon long-horizon plans. Given the promise of coding agents, we encourage future text optimization work to experiment with coding agents as part of their methodology. The Pi agent [Earendil Inc. and Contributors, 2026] that we use in AT-AT, and similar other coding agents that are open-source, lightweight, and extensible, may be good candidates for further experiments and worthwhile to compare to closed coding agents like Claude Code. 

Evaluation stochasticity. Agent optimization involves two distinct sources of stochasticity: evalua-tion noise and optimizer noise. Evaluation noise arises because repeated agent executions can produce different trajectories and outcomes even when the model, harness, tasks, environment, and decoding configuration are held constant [Mustahsan et al., 2025]. Differences in evaluation infrastructure configuration or infrastructure crashes can also lead to task failures and contribute to evaluation noise [Anthropic, 2026]. Consequently, rankings based on single benchmark point estimates, particularly when the reported differences are small relative to run-to-run variation, should not be interpreted as reliable evidence that one system outperforms another. Our paired permutation statistical testing protocol accounts for evaluation noise and provides statistical evidence for AT-AT’s improvements on 

τ 2-bench-verified. However, it does not address optimizer noise: repeated runs of an LLM-based optimizer may produce different tool updates and, consequently, different downstream effects. Be-cause we evaluate one toolset from each optimizer, our reported results are conditional on those particular optimization runs. Future work should repeat the complete optimization-and-evaluation pipeline to characterize both sources of variation, reporting uncertainty across optimizer runs as well as repeated downstream evaluations. Given the imperfect nature of benchmarks and evaluations, the ultimate test of an ML method is if it works in real-world scenarios; our production MCP server experiments demonstrate that AT-AT may provide value in a deployment setting, although replication across deployments and time remains necessary to establish robustness. 

Failure to achieve gains on Retail. No optimizer significantly changed Retail reward (Tab. 1); all optimized toolsets scored slightly below the 77.00% baseline (74.08–76.08%; all p ≥ 0.099 ). We attribute this pattern to two factors. First, Retail offers limited optimization headroom. The baseline reward is already quite high at 77%, and an LLM audit of 24 failed baseline trajectories per domain found that most Retail failures were agent reasoning errors that occurred even though the tools had returned the necessary information. Failures classified by an LLM as addressable via tool implementations accounted for an estimated 3.1% of Retail simulations, compared with 8.9% 17 in Telecom, where AT-AT achieved its only significant gain. Second, the small declines are within evaluation noise. GEPA’s selected toolset is byte-identical to the unoptimized tools, yet its evaluation scored 0.92 points below the baseline (76.08%), and the edited toolsets differ from this control by only −2.00 to −0.17 points (all p ≥ 0.20 ).

20 G AT-AT prompts 

This appendix lists the prompts given to the Pi agent optimizer in AT-AT. Prompt text is reproduced verbatim, except that line breaks within paragraphs are reflowed. 

System prompt. The system prompt is the concatenation, separated by blank lines, of (1) the optimization objective, (2) benchmark-specific editing rules, and (3) the generalization instruction. 

Optimization objective 

You are given an agent's tools (source you may edit) and transcripts of the agent attempting tasks with them, each labelled with its reward. Edit the tools so the agent succeeds on more tasks. Read the transcripts for places where the tools — not the agent's judgment — got in the way. Look for: the agent picking the wrong tool or wrong arguments because the docs don't make a tool's purpose or usage clear; results it can't act on (unclear, incomplete, or silent) that force it to guess or retry; and repeated calls or workarounds for something the tools should let it do in one step. Effective tools make the right action easy to choose, behave as their docs describe, and hand back what the agent needs to take the next step. Edit the tools to remove those obstacles, and read the successful transcripts too, so a change doesn't break what already works. Constraints: keep every tool's name and signature unchanged and the source valid; do not encode task identifiers, specific inputs, or expected answers into the tools. Apply edits with the edit tool. The harness validates the result; if it fails, fix the underlying issue rather than working around the check. 

The editing rules state how to edit the tools of a given benchmark without breaking them. For 

τ 2-bench-verified, where all tools are defined in a single tools.py file: 

Editing rules: τ 2-bench-verified 

The tools live in a single tools.py. Keep it importable: preserve all imports, class names, and @is_tool method signatures (names, types, order). 

For the τ 2-bench-verified ablation that edits tool descriptions only (Sec. 4.1.1), the tool descriptions are extracted into an editable descriptions.md file: 

Editing rules: τ 2-bench-verified, descriptions only 

Edit ONLY the tool descriptions in descriptions.md (each `## <tool>` heading names a tool). The full tools.py is provided read-only for context; you cannot change code, only the description text under each heading. 

For TerminalBench-2 and TBLite, where the optimized tools are TypeScript modules in the OpenCode harness: 

Editing rules: OpenCode 

Each tool is a .ts module exporting `export const <Name>Tool = Tool.define("<id>", {...})`, optionally with a companion .txt description. Preserve every Tool.define id and the exported constant name; do not add imports or reference runtime-context symbols at module top level; preserve each execute() return shape { title, output, metadata }. 

Generalization instruction 

The tools are scored on held-out tasks, not the ones in these transcripts. Prefer edits that address the general defect a transcript reveals over edits that only fit the specific observed case.

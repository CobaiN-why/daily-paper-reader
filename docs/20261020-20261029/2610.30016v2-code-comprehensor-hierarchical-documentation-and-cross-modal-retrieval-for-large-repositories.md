## 摘要
理解大型、复杂且快速演进的代码库仍是规模化软件工程的核心挑战，阻碍了新成员上手、维护、重构和影响分析。将这类信息提供给大语言模型（LLM）是另一道障碍，因为 LLM 不仅需要理解所需的代码方法，还需要理解其在整个仓库大局中的关联方法。我们提出 Code Comprehensor，一个混合检索-推理框架，结合：(i) CodeGraph，一个代码依赖调用图；(ii) CodeScribe，使用具备代码感知能力的 LLM 在仓库调用图上生成层次化文档；(iii) CodeContrast，一个 CLIP 风格的双编码器模型，基于 CodeScribe 输出训练，以学习对齐的文本-代码嵌入。CodeContrast 能够快速、语义精确地检索相关代码上下文邻域，这些邻域作为基于 MCP 的 LLM 编排器回答领域特定查询的有依据证据。在 OpenCV 和一个专有的 500 万行代码（5M-LOC）仓库上的评估表明，与基线方法相比，CodeScribe 衍生的监督显著提高了文本到代码的跨模态检索准确率。更丰富的文本监督（层次化文档、父/兄弟上下文以及 LLM 生成的合成问题）在两个仓库上均持续提升性能。使用流行的 RAGAS 对 Code Comprehensor 输出进行 LLM 作为评判者的评估，获得了超过 90% 的忠实度分数。

## Abstract
Understanding large, complex, and rapidly evolving code bases remains a core challenge for software engineering at scale, hindering onboarding, maintenance, refactoring, and impact analysis. Providing this information to a Large-Language Model (LLM) is another hurdle, as the LLM must understand not only the required code method but also its associated methods in the grand scheme of the repository. We propose Code Comprehensor, a hybrid retrieval-reasoning framework combining (i) CodeGraph, a code dependency callgraph, (ii) CodeScribe, which uses code-aware LLMs to generate hierarchical documentation across repository call graphs, and (iii) CodeContrast, a CLIP-style dual-encoder model trained on CodeScribe output to learn aligned text-code embeddings. CodeContrast enables fast, semantically precise retrieval of relevant code-context neighborhoods, which serve as grounded evidence for an MCP-based LLM orchestrator answering domain-specific queries. Evaluation on OpenCV and a proprietary 5M-LOC repository shows that CodeScribe-derived supervision significantly improves cross-modal retrieval in text-to-code accuracy over baseline approaches. Richer textual supervision (hierarchical documentation, parent/sibling context, and LLM-generated synthetic questions) consistently enhances performance across both repositories. LLM-as-a-judge evaluation using the popular RAGAS of the Code Comprehensor output yields above 90% faithfulness scores.

# Code Comprehensor 论文结构化总结

## 1. 核心问题与研究动机

- **工程背景**：企业级代码仓库规模巨大、演进迅速（如本文涉及的私有 C 代码库超过 500 万行 LOC，OpenCV 约 120 万行），理解成本高，严重依赖资深工程师经验，拖累 onboarding、维护、重构与影响分析等 SDLC 环节。
- **LLM 落地障碍**：
  - 仓库 token 量远超模型上下文窗口，即便上下文足够，超长上下文也会导致性能下降且成本高昂；
  - 仓库中存在大量重名/相似的方法与变量，纯概率式 LLM 难以稳定、可复现地定位“正确的那一个”；
  - LLM 不仅要理解目标方法本身，还需理解其在调用图中的上下游关联方法，即“仓库全局语义”。
- **既有工作不足**：
  - 基于 AST/调用图的文档生成（RepoAgent、CodeWiki、Code-Craft 等）多止步于“静态文档”，未把文档转化为可检索的训练信号；
  - 跨模态对比学习代码检索（CodeRetriever、CoCoSoDa 等）多在孤立代码片段上训练，缺乏领域级、结构级的层次化文档映射，在大型复杂仓库上效果受限。
- **整体含义**：论文主张构建一个“结构（调用图）+ 层次化文档（LLM 生成）+ 对齐嵌入检索 + Agent 编排”的混合检索–推理系统，让 LLM 以确定性、可追溯的方式导航大型仓库，而非每次把整个仓库塞进上下文。

## 2. 方法论

### 2.1 总体架构（四组件）

| 组件 | 作用 |
|---|---|
| **CodeGraph** | 静态分析生成的代码依赖调用图，经 FastAPI 暴露遍历/分块接口 |
| **CodeScribe** | 基于代码感知 LLM 的层次化文档生成引擎，输出 SynTD（Synthesized Technical Descriptions） |
| **解析与数据构建模块** | 将 Markdown 文档解析为带父子/兄弟关系的关系型记录，并生成合成问题 |
| **CodeContrast** | CLIP 式双编码器对比模型，学习对齐的文本–代码嵌入 |
| **MCP 编排层（Master Agent）** | LLM 编排器，调度 RAG(CodeScribe)、CodeGraph 遍历、CodeContrast 检索三类子 Agent |

### 2.2 CodeGraph 构建

- 使用 **Tree-Sitter** 做语言相关解析；依赖通过 compile commands 解析，缺失时用启发式方法。
- 节点类型：文件、方法（面向对象语言增加类节点）；边为 “invokes”。
- 节点命名 `method_name:::file_name`，重载场景追加行号 `::::line_number`，避免跨文件同名冲突。
- 属性包含方法签名、开发者注释（缺失时由 LLM 补写）、方法体。
- 图以 Python **NetworkX** 对象保存，并通过 FastAPI 暴露 BFS/DFS、正向/反向 invokes 等端点。

### 2.3 CodeScribe：层次化文档生成

- **以目录结构为驱动**：输出 Markdown 目录镜像源码目录；支持配置排除目录、限定文件扩展名、按目录定制“章节”（如代码描述、算法、数据流、接口）与专用提示词、领域缩写表。
- **三类系统提示词设计原则**：约束在合适语义边界做层次化抽象总结；引用代码块必须带方法名/路径/语言元数据以便回溯；多章节视角间保持一致性。
- **起点方法识别**：在“仅方法子图”中取入度为 0 的方法作为 start method（即被模块外调用的入口）。
- **DFS 树 + 后序分块算法（核心贡献之一）**：
  - 对每个 start method 取 DFS 遍历树，树中含方法定义，易超上下文；
  - 递归后序遍历：先处理全部子节点并收集剩余块 → 若“当前节点 + 子节点剩余”可放入主上下文则合并，否则将子块定型为独立 chunk、仅保留当前节点 → 若仍超限（主限 + buffer）则拆分为溢出块并返回尾部；
  - chunk 依次送入 LLM，**前一块的输出作为后续块的上下文**（滚动摘要），使父调用者在看不到子节点源码时仍持有其功能摘要；中间块输出为临时产物，不进入最终文档。
- **增量更新**：基于 git commit 定位变更文件 → 比对旧图找出变更方法 → 反查其所属树的 root/start method → 仅重生成受影响的 start method 文档及汇总文档，可对接 CI/CD。
- 可选做目录层级汇总；每个 start method × 每个章节产出一个 Markdown 文件。

### 2.4 文档解析与关系特征构建

1. **Markdown → JSON**：自研递归解析器，标题/子标题作 JSON 键，非标题内容聚合到任意键下，保留层次。
2. **代码块与文本分离**：正则提取三反引号代码块（含语言标识），剩余文本作为描述；为每个节点分配点分深度标识（如 `1.2.3`）。
3. **代码块三分类**：`Code`（带方法名/路径元数据）、`UML`（PlantUML）、`Pseudocode`（无标注）。
4. **关系特征**：
   - **父上下文**：直接父节点的文本描述；
   - **兄弟上下文**：同父条目的方法名、注释、路径、代码；
   - **模块级上下文**：无直接代码子节点的纯文本节点聚合评述。
5. 解析记录以 `method_name:::file_path` 复合键与调用图数据合并。

### 2.5 合成问题生成

- **双重目标**：意图多样性（用途/行为、参数用法、边界条件、前置条件、错误处理、模块内交互）+ 检索可落地性（含仓库专有术语，但禁止“关键词堆砌”）。
- **生成输入**：文档信号（主）+ 代码信号（方法签名去函数名 + 有界代码片段，仅作术语锚点，明令不得照抄）。
- **四类术语锚点**：`BEHAVIOR_ANCHORS`（动词）、`PARAM_TERMS`（参数名/类型）、`CONTEXT_TERMS`（领域术语）、`KEY_TERMS`（前两者并集，设上限防堆砌）。
- **硬约束**：每题至少 1 个行为锚点、至少 1 个参数锚点 + 1 个上下文锚点、至少 3 个 KEY_TERMS 原词命中、必须以问号结尾、不得出现函数名/文件路径/`file:line` 标识；每个方法固定生成 3 个问题。
- **后处理**：严格 JSON 校验、去重（精确 + 近似）、信息量过滤（缺锚点或过短则丢弃）；并额外评估“移除函数名 token”的版本以排除词法捷径。

### 2.6 CodeContrast 训练

- **双编码器**：支持 SentenceTransformer(SBERT) 与 BERT 骨干，可选投影层统一维度 d，输出 ℓ2 归一化到单位超球面，余弦相似度即点积。
- **一码多文监督结构**：一个代码单元对应多个文本视图（原始文档、层次化上下文、合成问题），按 `query_type` 打标签。
- **FSDP 分布式 + 可微全局批**：跨 GPU 用可微 all-gather 汇聚嵌入与标签，构造全局相似度矩阵以扩大负样本；空 batch 的 rank 用占位张量参与 gather 防死锁。
- **多正样本对称 InfoNCE**：设 ℓᵢ 为样本 id 类别标签，对文本锚点 tᵢ 的正样本集合 P(i)={j | ℓⱼ=ℓᵢ}，采用 log-sum-exp 聚合：
  - 文本→代码损失 L_t→c = −(1/B)Σᵢ log[ Σ_{j∈P(i)} exp(S_ij) / Σⱼ exp(S_ij) ]
  - 代码→文本损失 L_c→t 在 Sᵀ 上对称定义
  - 总损失 L = ½(L_t→c + L_c→t)
- **评估指标**：双向 Top-k 准确率与 Recall@K。

### 2.7 Master Agent 编排流程

- 用户经 MCP 网关提问 → MA 判断检索方向：自然语言问题走 Text→Code 检索代码块；问“某方法/类/文件是什么”走 Code→Text；
- 再由 CodeGraph Agent 取相关方法的层次结构、CodeScribe Agent（RAG）取对应文档，最终合成含代码块与 PlantUML 图的自然语言回答，支持多轮追问。

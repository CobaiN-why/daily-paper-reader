# Object-Oriented Harness: Evolving Agent Harnesses through Object-Oriented Design 

Gaotang Li 1,* , Bhavana Dalvi Mishra 2, Yifei Ming 2, Yanfei Chen 2, Zhongying CuiZhu 2, Lesly Miculicich 2,Long T. Le 2, Rui Meng 2, Chun-Liang Li 2, Hanghang Tong 1, Chen-Yu Lee 2 and Tomas Pfister 2 

> 1University of Illinois Urbana-Champaign, 2Google Cloud AI Research

Agent harnesses are executable code that specifies the prompts, tools, and control flow around a language model. A single global harness can struggle with heterogeneous tasks that require different execution strategies. In this work, we introduce Object-Oriented Harness (OO-Harness), a harness optimization framework that evolves a hierarchy of executable harness classes using object-oriented design. During training, an evolution agent uses execution records to create a family of specialized harnesses, each implemented as a subclass of the base or an existing specialized harness via inheritance. At test time, a harness router uses routing lessons accumulated during training to select a specific harness for each task. Across three long-horizon benchmarks spanning business workflows, workspace tasks, and tool use, OO-Harness achieves the best performance among the compared methods, with an absolute improvement of up to 15 .79% over the base harness. Extensive ablation studies examine the contributions of its core components. 

## 1. Introduction 

Generalizing to tasks beyond the training dis-tribution is a central goal of language-agent re-search (Xi et al., 2024; Zeng et al., 2023). Recent benchmarks illustrate the breadth of tasks agents must handle: FutureX evaluates agents on fore-casting real-world events using external informa-tion (Zeng et al., 2025), while APEX-Agents eval-uates cross-application workflows in investment banking, management consulting, and corporate law (Vidgen et al., 2026). These workloads dif-fer in the tool use, context management, and completion checks they require. An agent’s har-ness implements these choices as executable code around a language model (Yang et al., 2024). Recent approaches automate agent design and harness optimization by refining executable code and other harness components using execution feedback (Hu et al., 2024; Jiang et al., 2026; Karten et al., 2026; Lee et al., 2026; Lin et al., 2026a; Lou et al., 2026; Nie et al., 2026; Zhang et al., 2025). Meta-Harness, for example, evolves candidate programs using discovery-set feedback and selects a global harness based on perfor-mance on that set (Lee et al., 2026). Such se-

## 2. Related Work 

Self-evolving agents. Self-evolving agents use execution experience to improve prompts, mem-ories, skills, and other persistent components. GEPA reflects on trajectories to optimize prompts (Agrawal et al., 2025), while ReasoningBank distills successful and failed experiences into reusable memories (Ouyang et al., 2026). A-Evolve considers deliberate updates to persistent agent state (Lin et al., 2026b), and HASP repre-sents skills as executable functions that modify actions or supply corrective context (Liu et al., 2026a). These forms of adaptation provide build-ing blocks for harness evolution. OO-Harness evolves specialized harnesses through inheritance and uses a harness router to select one for each task. 

Automatic harness evolution. Recent work automates harness construction and revision through code search and execution feedback, in-cluding Meta-Harness (Lee et al., 2026), Agentic Harness Engineering (Lin et al., 2026a), and Har-nessEvolve (Jiang et al., 2026). These approaches

HarnessDev benchmarks har-ness creation and evolution (Wu et al., 2026), while EvoHarnessBench shows that expanding tools, skills, and specialist agents can degrade previously effective behavior (Ke et al., 2026). Concurrent work explores adaptation across tasks and deployments: Adaptive Auto-Harness shares and specializes workspace contents through Git branching and rebasing (Liu et al., 2026b), while EvolveNet integrates adaptations from distributed deployments into a global harness (Nie et al., 2026). At the representation level, NOOA pro-vides a programming model that expresses agents as native Python objects (Furgale et al., 2026). OO-Harness evolves a hierarchy of executable harness classes through inheritance, method over-rides, and new methods. Its harness router selects a harness using routing lessons accumulated dur-ing training, class descriptions, the task, and an observable base trajectory. 

## 3. Method 

3.1. Problem setting and overview

## 4. Experiments 

4.1. Evaluation setup Benchmarks and metrics. We evaluate on Au-tomationBench (Shepard and Salimans, 2026) for business workflows (300 discovery and 300 held-out tasks), Workspace-Bench (Tang et al., 2026) for work across files and applications (288 discovery and 100 held-out tasks, Lite-100), and Toolathlon-GYM (Zhang et al., 2026) for multi-tool task completion (251 discovery and 252 held-out tasks). AutomationBench and Toolathlon-GYM use deterministic graders to assess task completion; Workspace-Bench evaluates outputs against task-specific rubrics. We report Mean and strict task success (PASS) for all three benchmarks. Mean denotes mean par-tial credit on AutomationBench, micro-averaged rubric pass rate on Workspace-Bench, and mean reward on Toolathlon-GYM. PASS requires re-ward at least 0 .999 on AutomationBench and Toolathlon-GYM, or all rubrics satisfied on Workspace-Bench. The primary metric is Mean for AutomationBench and Workspace-Bench, and PASS for Toolathlon-GYM. All scores are reported as percentages. 

Comparators. We compare with the unevolved base harness; global harness optimization using Meta-Harness (Lee et al., 2026) and Agentic Harness Engineering (AHE; Lin et al., 2026a); and specialized harnesses using Adaptive Auto-Harness (AAH; Liu et al., 2026b). Our AHE adaptation iteratively edits a global harness from a framework-only bundle. Since OO-Harness uses a base trajectory for routing, we also com-pare with test-time scaling of the base harness to assess gains from additional inference. In-spired by Wang et al. (2026), we evaluate parallel best-of-𝐾 selection ( 𝐾 ∈ { 2, 5}) and sequential self-refinement ( 𝐾 = 2; Madaan et al., 2023). Both methods use observable trajectories without grader feedback.

4.2. Main results Strong empirical results. OO-Harness achieves the highest primary score on all three benchmarks (Table 1), outperforming prior global harness optimization approaches and AAH’s specialized harnesses. These results support the expressiveness of object-oriented programming as a natural fit for code-based harness evolution: inheritance shares useful behavior, while method overrides and additions specialize it for different tasks. On AutomationBench, OO-Harness also has the lowest mean trajectory step count among all compared methods. Table 1 also shows that test-time scaling with parallel best-of-𝐾 selection (𝐾 ∈ {2, 5}) and sequential self-refinement (𝐾 = 2) does not consistently improve perfor-mance. Additional inference alone therefore does not guarantee gains, highlighting the value of learning task-appropriate harnesses through our training pipeline. 

Global versus hierarchical approaches. We compare more closely with Meta-Harness, a prominent prior approach to global har-ness optimization. During training, Meta-Harness evolves one global harness, whereas OO-Harness builds a hierarchy of special-ized harnesses through cluster-specific evolu-tion. Both freeze code before testing; Meta-Harness applies one harness to every task, while OO-Harness selects from its learned hierar-chy. 5.1.2. Hierarchical evolution structure 

One central design choice of OO-Harness is evolution via inheritance. We examine its con-tribution on Workspace-Bench with three ways of learning harnesses. The routing procedure, executor, task splits, and nominal search budget are the same across variants; only how harness code is learned changes. OO extends earlier har-nesses through subclasses. Flat copies previously evolved code into a class derived directly from the base, without inheriting from a specialized harness. Base-reset starts from the base and adds new changes without carrying forward previously evolved code. Each variant conducts a separate search and is evaluated once on Lite-100. OO achieves the highest micro rubric pass of 40 .56%, exceeding Flat by 4 .96 points (Figure 5). Flat also improves over Base-reset, supporting the value of reusing useful code across revisions. Since Flat also carries forward evolved code, its gap to OO suggests a benefit from organizing re-visions through inheritance. Each variant evolves separately, so these results compare the harnesses learned by each search strategy.

This ablation examines how an evolution step builds on previously learned harness code. The target cluster’s cur-rently deployed harness becomes the candi-date’s parent; Base is used when the cluster has no specialist. The loader binds this parent class to _Parent . Methods that the candidate does not override remain inherited, while an over-ride can call super() to compose the parent’s behavior with a new change. B.3. Toolathlon-GYM: refining when and what to check 

The learned clusters can span multiple applica-tions (Figure 10). For example, completeness-finalize includes tasks using Canvas, Notion, Snowflake, and WooCommerce. The following examples show how evolution refines a shared behavior and adds a check for a particular output. 

Refining when to compress tool output. An ancestor of the completeness-finalize har-ness shortens unusually long tool responses to limit the amount of text in the execution history. Its child retains this behavior but adds an early-finish condition: after an early completion at-tempt, any subsequent tool outputs bypass com-pression. This allows the child to narrow when an inherited intervention applies, using progress observed during execution. 

Checking the saved workbook. The 

excel-formula-literal harness adds afile check to inherited guidance about writing computed values to spreadsheets (Listing 1). Before finishing, it reads the saved workbook and looks for cells with percentage labels and values strictly between zero and one. It can then request one correction pass, listing the identified cells and proposed values multiplied by 100. This rule assumes that the task expects percent-age points: for example, 20 rather than 0.2 for twenty percent. The instruction asks the execu-tor to change only the listed cells and preserve the rest of the workbook. The harness therefore uses the contents of the produced file to decide whether to request a targeted correction before finishing.

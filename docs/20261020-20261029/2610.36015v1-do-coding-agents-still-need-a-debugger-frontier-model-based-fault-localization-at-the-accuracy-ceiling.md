## 摘要
背景：为定位故障，编码智能体可以仅从源代码进行推理，也可以借助调试器，通过运行程序并在交互式调试器中单步执行来获得辅助。尽管早期智能体在静态执行追踪和调试器操作方面存在困难，但前沿大语言模型在这两方面均有所提升。目标：评估编码智能体在不使用工具时，在原始程序和变换后程序中定位故障的准确率；评估调试器辅助能在多大程度上提升准确率及其代价；并评估在调试器可选时智能体如何使用它。方法：向144个LeetCodeDataset解决方案中注入610个单行故障，并使用五种保持行为的变换配方重写每个故障程序。基于Sol 6.1、Luna 6和Qwen 3.8的智能体分别在无调试器辅助、可选调试器辅助或鼓励使用调试器辅助的条件下定位每个故障。结果：在不使用工具时，智能体在原始程序中定位了98.2%至99.9%的故障，在变换后程序中定位了96.7%至99.9%的故障，准确率损失主要出现在变换配方重构循环和条件的位置。鼓励使用调试器辅助消除了Luna 6和Qwen 3.8在变换后程序中剩余错误的63%和61%（分别提升2.1和1.3个百分点），但token使用量增至14.7至27.0倍；而Sol 6.1保持在99.9%。在调试器可选时，Luna 6和Qwen 3.8仍分别获得+1.5和+1.3个百分点的提升，尽管智能体仅在0.2%至6.2%的运行中使用了交互式调试器。结论：对于简短且精确指定的程序，当前编码智能体仅凭源代码即可定位几乎所有故障，而调试器辅助可消除剩余的大多数错误。在可自主选择时，智能体执行程序的频率远高于单步调试，但仍保留了大部分收益。

## Abstract
Background: To localize a fault, a coding agent can reason from source code alone or use debugger assistance by running the program and stepping through it in an interactive debugger. While earlier agents struggled with static execution tracing and debugger operation, frontier LLMs have improved at both. Objective: We evaluate how accurately coding agents localize faults without tools across original and transformed programs, how much debugger assistance improves accuracy and at what cost, and how agents use it when optional. Methods: We seed 610 single-line faults into 144 LeetCodeDataset solutions and rewrite each faulty program with five recipes of behavior-preserving transformations. Agents based on Sol 6.1, Luna 6, and Qwen 3.8 localize each fault with no, optional, or encouraged debugger assistance. Results: Without tools, the agents localized 98.2 to 99.9% of faults in original and 96.7 to 99.9% in transformed programs, losing accuracy mainly where recipes restructured loops and conditions. Encouraged assistance removed 63% and 61% of Luna 6's and Qwen 3.8's remaining transformed errors (+2.1 and +1.3 percentage points) at 14.7 to 27.0 times the token use, while Sol 6.1 stayed at 99.9%. With optional assistance, Luna 6 and Qwen 3.8 still gained +1.5 and +1.3 points, though the agents used the interactive debugger in only 0.2 to 6.2% of runs. Conclusions: On short, precisely specified programs, current coding agents localize nearly all faults from source code alone, and debugger assistance removes most errors that remain. Given the choice, agents executed the program far more often than they stepped through it, yet kept most of the benefit.

# 论文结构化总结

## 一、核心问题与整体含义

- **研究背景**：故障定位（Fault Localization）是调试的核心环节。传统上，编码智能体可以仅凭源代码进行静态推理，也可以借助调试器（运行程序、设置断点、单步执行、检查状态）获取运行时证据。早期 LLM 在静态执行追踪上表现很差（CRUXEval 上仅预测 46–81% 的输出），因此以往调试系统普遍需要注入运行时信息。
- **问题转变**：前沿推理模型在静态代码理解与调试器操作两方面都大幅进步，这引出三个关键问题：
  1. 最新一代前沿模型仅凭源代码定位故障的准确率有多高？
  2. 该准确率对“保持行为的代码变换”（用于缓解训练数据污染）有多敏感？
  3. 在静态推理已接近上限的情况下，调试器辅助还能带来多少增益、代价几何？
- **已有研究的三个空白**：
  - 多数智能体调试研究衡量端到端“程序修复”，混淆了故障定位与补丁生成；
  - 公开基准上的高静态准确率可能源于训练数据暴露，而行为保持变换对前沿模型的影响尚未量化；
  - 既有工作要么强制固定插桩，要么只评估单一工具回路，未区分“鼓励使用”与“可选使用”，也未比较其成本。

## 二、方法论

- **核心思想**：在自包含算法程序上做受控实验，把故障定位从修复中剥离出来，用“匹配对”（原始 vs. 行为保持变换）与三种工具使用设置，量化静态定位能力、变换敏感性以及调试器辅助的边际收益与成本。
- **关键技术流程**：
  1. **参考程序与故障注入**：从 LeetCodeDataset 抽取 150 个参考程序（Easy/Medium/Hard 各 50），每个程序注入最多 5 类单行故障——Off-by-one、Wrong arithmetic、Wrong logic、Wrong variable、Static return；最终保留 610 个故障（源自 750 个候选）。
  2. **五种行为保持变换配方**：Rename（变量改单字母）、State & literals（字面量与表达式拆分）、Control flow（for 循环改写为显式迭代器、条件双重否定、死代码插入）、Distractors（不透明谓词包裹、死代码、误导性注释）、Maximal mix（串联 14 步操作并抽取辅助函数）；最终得到 3,022 个变换程序。
  3. **准入条件**：对参考程序 P 与故障程序 M 同步变换为 P′、M′，仅当（a）P′ 通过全部测试、（b）M′ 在与 M 完全相同的断言上失败、（c）在追踪行 L′ 恢复原表达式后 M′ 通过，才接纳为匹配对。
  4. **三种工具使用设置**：
     - **No-tools**：仅提供问题描述、带行号的源码，唯一工具为 `report_bug`；
     - **Discretionary-tools**：额外提供 `run_probe`（执行自定义脚本）与 pdb 风格交互式调试器（断点、单步、状态检查），由智能体自主决定是否使用；
     - **Encouraged-tools**：同一工具集，并在系统提示中追加两句话，明确要求先收集运行时证据再作答。
  5. **评估指标**：
     - **Top-1 准确率**（语句级与行级两种判定）；
     - **变换导致的静态准确率变化** \( G = \frac{1}{|E|}\sum_{(M,M')}(a_{no}(M') - a_{no}(M)) \)；
     - **辅助效应** \( \Delta = a_{enc}(M) - a_{no}(M) \)、\( \Delta' = a_{enc}(M') - a_{no}(M') \)，以及交互项 \( I = \Delta' - \Delta \)；
     - **误差消除比例** \( \Delta/(1-\bar{a}_{no}) \) 与 \( \Delta'/(1-\bar{a}'_{no}) \)；
     - **成本**：token 数、墙钟时间、货币成本；
     - **可选工具使用**：以每用例工具调用次数的秩 \( r(X) \) 回归辅助效应，斜率 \( \beta_1 \) 表示工具使用排名从底到顶对应的辅助效应差异。
  6. **统计推断**：以“参考程序”为整群的聚类 bootstrap（2,000 次重采样，按难度分层），并配合 1,000 个聚类级安慰剂数据集验证 \( \beta_1 \) 区间。

## 三、实验设计

- **数据集/场景**：LeetCodeDataset 训练划分（问题发布于 2024 年 7 月前），150 个参考程序最终接纳 144 个；610 个故障程序（每类 104–141 个）；3,022 个变换程序；总计 **65,376 个智能体回合（episodes）**。
- **Benchmark 性质**：自包含、短小（中位 LOC：Easy 8、Medium 11、Hard 19）、测试密集（中位每问题 99 条断言）的 Python 算法题。
- **对比模型**：
  - **Sol 6.1**（OpenAI Responses API，`gpt-6.1-sol`，默认 medium 推理强度）；
  - **Luna 6**（OpenAI Responses API，`gpt-6-luna`，medium）；
  - **Qwen 3.8**（27B 参数 FP8 检查点，自建 vLLM 服务，thinking 开启，xhigh 推理强度）。
- **对比条件**：2 种表示（原始/变换）× 3 种工具设置（No / Discretionary / Encouraged）= 条件 A–F；每个模型、每个用例、每个设置独立运行 2 次。
- **对照分析**：以 No-tools 为基线，比较 Discretionary 与 Encouraged 的准确率、成本与工具调用行为；另做行级评分稳健性检验与 135 条“仅语句级正确”答案的盲审审计。

## 六、主要结论与发现

- **静态定位已接近上限**：无工具时，三模型在原始程序上定位 98.2%–99.9%，在变换程序上 96.7%–99.9%；Sol 6.1 在两种表示下均为 99.9%。
- **变换的影响不取决于表层改动量**：Rename（仅保留 40% 四元组）与 Distractors（行数 +400%、复杂度 +11）几乎不影响准确率（−1.0 至 +0.1 点）；真正造成损失的是 Control flow 与 Maximal mix（重构循环、双重否定条件），使 Luna 6 下降 2.1–3.8 点、Qwen 3.8 下降 2.1–2.4 点；新增错误中 71.4%（Luna 6）与 68.2%（Qwen 3.8）指向被双重否定的条件，而这类行仅占 7.8%/4.4%。
- **鼓励调试器可清除大部分残余错误但代价高昂**：Luna 6 与 Qwen 3.8 在变换程序上分别 +2.1 与 +1.3 点（消除 63% 与 61% 的剩余错误），变换差距被压缩到 −0.1 至 +0.1 点；但 token 增至 14.7–27.0 倍、墙钟时间 5.3–7.7 倍、成本 3.4–5.0 倍；Sol 6.1 无增益却消耗 18.4–19.8 倍 token。
- **可选工具下智能体极少单步调试**：Discretionary 设置中，交互式调试器仅在 0.2%–6.2% 的变换回合中被使用；Sol 6.1 与 Qwen 3.8 主要在跑 probe（86.7%–99.1%），Luna 6 在 87.9% 的变换回合中完全不调用工具。
- **可选工具仍保留大部分收益**：Discretionary 下 Luna 6 与 Qwen 3.8 分别 +1.5 与 +1.3 点，接近 Encouraged 的效果，但 token 消耗显著更低（如 Qwen 3.8 38.3k vs. 73.5k）。
- **成本效益启示**：工具调用频率与准确率增益不匹配；更强的基座模型（Sol 6.1 无工具 99.9%、5.2 秒、3.41 美元/千回合）比多轮调试脚手架更划算；调试辅助“可选而非强制”最具成本效益。

## 七、优点

- **实验设计干净**：将故障定位与程序修复解耦，避免补丁生成对定位评估的混淆；采用严格的三重准入条件构造匹配对，保证变换前后行为可比。
- **变量控制细致**：提示词除 Encouraged 追加的两句指令外完全一致，避免提示措辞差异带来的性能波动；工具描述与完整提示均随复现包发布。
- **多维度分析**：同时报告准确率、误差消除比例、交互项 \( I \)、token/时间/货币成本，并区分语句级与行级评分，结论稳健。

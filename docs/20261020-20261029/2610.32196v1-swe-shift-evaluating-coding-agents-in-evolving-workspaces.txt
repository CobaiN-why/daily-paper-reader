## SWE-Shift: Evaluating Coding Agents in Evolving Workspaces 

Victor Shea-Jay Huang 1, Rongqing Li 5, Zhangyue Yin 2, Kelong Mao 5, Yaqi Zhao 3,Xinyuan Wang 2, Yao Yin 4, Lirui Luo 4, Renrui Zhang 1, Hongsheng Li 1,†

Repository-level coding benchmarks largely assume that tasks and environments remain unchanged throughout execution. In software development, code, dependencies, runtime state, and requirements can change while an agent is still working. We introduce SWE-Shift, a benchmark for evaluating coding agents under such mid-execution changes. From the same saved history and workspace, a Clean continuation proceeds without intervention, while a matched Shifted continuation receives a task-relevant update. Success requires completing the current task, preserving still-valid work, and satisfying the applicable state and evidence checks. The benchmark contains 120 scenarios across 12 change families, each evaluated at nine scheduled intervention positions. We evaluate 17 coding-agent systems, all of which have lower Shifted than Clean success. GPT-6 Astra drops from 67.35% to 24.79%, with 20.34% paired success. Tool/session changes and stale evidence yield zero paired success across all systems. Late-position paired success is lower for some systems and higher for others. These results show that success on the unchanged task can coexist with failures to preserve work, recover state, or refresh evidence after an update.

Repository-level benchmarks such as SWE-bench [13] have made it possible to evaluate coding agents on realistic software engineering tasks rather than isolated code generation. An agent must understand an issue, navigate a repository, modify executable code, and satisfy tests. Yet these benchmarks largely assume that once execution begins, the task and its environment remain unchanged. Real software development is less static. Code may be edited, dependencies may change, runtime state may evolve, and requirements or available information may be updated while an agent is still working. This raises a different reliability question: 1arXiv:2610.32196v1 [cs.AI] 23 Oct 2026 Can a coding agent continue to succeed when task-relevant changes occur during execution? 

This question is not answered by evaluating agents on changed tasks alone. If an agent fails after a change, we do not know whether it was unable to solve the underlying task in the first place or whether the change disrupted an execution that would otherwise have succeeded. We introduce SWE-Shift, which addresses this problem through matched Clean and Shifted contin-uations (Figure 2). The agent first works on the task normally. At an intermediate point, we save its execution state and continue from the same prefix in two ways: the Clean continuation proceeds without a change, while the Shifted continuation introduces a task-relevant change. Because the two continuations share the same prior actions, workspace, and observable history, Clean provides a matched baseline for whether the agent can succeed from that state, while Shifted tests whether that success survives the change. Constructing such an evaluation also requires the changes themselves to be meaningful. A change should matter to the task, but it should not make the task impossible. SWE-Shift therefore includes scenarios in which ignoring the change can invalidate an otherwise successful continuation, while a correct continuation remains possible after the change. We also introduce each change at multiple points during execution, rather than tying the benchmark to a single moment in the agent’s trajectory. Finally, success is judged against the requirements that apply after the update, including preservation and evidence requirements that the original task tests may not cover. SWE-Shift contains 120 scenarios across 12 change families, covering code and dependency updates, collaboration, runtime and session state, external effects, revised goals, and stale or misbound evidence. Nine intervention positions per scenario yield 1,080 scheduled evaluation cells per system. Our evaluation of current coding agents reveals a substantial gap between success in unchanged and changing environments. As shown in Figure 1, all 17 evaluated coding-agent systems have lower observed success after the intervention. GPT-6 Astra, which has the highest Clean success, drops from 67.35% on Clean continuations to 24.79% on Shifted continuations. The size of the gap also varies across change families and intervention positions, suggesting that robustness to mid-execution change captures behavior that static task success alone does not reveal. 2Our contributions are summarized as follows: • We identify robustness to mid-execution change as an evaluation target beyond static task success, distinguishing failures on the underlying task from losses of successful continuations after a task-relevant change. • We introduce SWE-Shift, a matched-continuation benchmark with 120 scenarios across 12 change families and nine intervention positions, enabling controlled comparison of Clean and Shifted executions from the same intermediate agent state. • We evaluate 17 coding-agent systems and find a substantial gap between Clean and Shifted success, with failures varying across change families and intervention positions. Recorded trajectories and diagnostic controls further characterize these failures.

## 3 SWE-Shift Benchmark 

We first describe how task-relevant changes are designed (Section 3.1). We then explain how matched continuations and intervention timing support controlled comparisons (Section 3.2). Finally, we define the success criteria and metrics used to evaluate these continuations (Section 3.3). 

3.1 Designing Task-Relevant Changes 

SWE-Shift builds 120 change scenarios on 23 task-root snapshots from 17 repositories, drawn from SWE-bench Verified [5], Multi-SWE-bench [37], and SWE-bench Multilingual [15]. Each scenario combines an existing repository task with a task-relevant change introduced during execution. Table 4 in Appendix C.1 provides the scenario counts by source. To evaluate adaptation, these changes must challenge the agent without making successful completion impossible. We therefore require each change to be both relevant and recoverable . Relevance means that ignoring the change can invalidate an otherwise successful continuation. Recoverability means 3that, after the change, at least one valid way to complete the task remains available through the agent-accessible tools. Together, these requirements exclude changes that do not matter to the task and changes that make the task unsolvable. To turn such a change into an executable evaluation scenario, we specify four elements: the initial repository task, an authorized mid-execution change, a way for the agent to encounter or discover that change, and executable checks for a correct continuation. These checks reflect the requirements that apply after the update: some original requirements remain in force, while others may be added or withdrawn. A correct continuation must satisfy the current requirements while preserving work and effects that remain valid. Using this scenario structure, SWE-Shift covers 12 change families, with ten scenarios in each family. Figure 3 organizes them into three broad groups according to what the change affects. 3.2 Matched Continuation Protocol 

SWE-Shift compares continuations with and without a mid-execution change from the same prior execution (Figure 2). For each system, scenario, and intervention position, the agent first executes a single shared prefix. At the scheduled checkpoint, the runner saves the agent-visible history, workspace, controller state, available tools, system settings, and execution counters. The saved state is then restored twice to create a matched pair of continuations. In the Clean continuation, execution proceeds without the scenario’s task-relevant update. In the 4Shifted continuation, the authorized update is applied at the fork. Up to that point, the two continu-ations have the same recorded execution history and workspace state. Only after the intervention can their observations and actions diverge. This differs from comparing independently generated runs, where differences before the change may already affect the outcome. The Clean continuation therefore provides a matched baseline for whether the agent can complete the task from that particular intermediate state, while the Shifted continuation tests whether that success survives the change. The update is introduced through the scenario’s declared interface. Depending on the case, the agent may encounter it as a workspace change, a delivered message, a changed tool or session response, or new information returned by an allowed state query. The evaluator may use additional held-out checks to determine correctness, but these checks do not provide additional information to the agent. Thus, the paired comparison changes the task-relevant conditions after the fork while keeping the observable pre-intervention execution fixed. 

3.2.1 Intervention Timing 

A single intervention point could make the evaluation depend strongly on when the change happens to occur. SWE-Shift therefore evaluates every scenario at nine progressively later intervention positions, denoted T10–T90. These positions are constructed from an eligible prefix of a reference solution, ending before the first action whose correctness depends on the update. The construction procedure provides nine distinct intervention anchors spanning 10%–90% of the eligible reference progress for every admitted scenario. During model evaluation, the intervention position determines how many agent actions are executed before the fork. The evaluated agent is not required to follow the reference trajectory used to construct the schedule. Consequently, T10–T90 represent progressively later scheduled positions ,rather than normalized semantic progress through the task. Different systems may therefore have reached different workspace states when the same nominal intervention position is triggered. If an agent terminates before the scheduled intervention or changes the state in a way that affects whether the update can still be applied, the cell retains its assigned intervention position and is handled by the benchmark’s outcome protocol without rescheduling. 

3.3 Success Criteria and Metrics 

A continuation is counted as successful only if it satisfies every check that applies under the conditions in which it ends. For the Clean continuation, these are the original task and environment conditions. For the Shifted continuation, they are the conditions after the update. The original task tests are therefore only one part of the evaluation. Depending on the scenario, success may additionally require preserving still-valid behavior, following the current goal or interface, avoiding prohibited effects, or obtaining evidence that is valid for the current state. The implementation groups these requirements into task, preservation, recovery, authority, effect, evidence, budget, and terminal-integrity checks. ## 4 Experiments 

Our experiments ask whether coding capability survives a workspace change (RQ1), which changes expose shared or system-specific weaknesses (RQ2), whether their timing matters (RQ3), and what a failed continuation can hide from ordinary task tests (RQ4). We then examine how state handling and post-fork token budgets affect success.

4.5 RQ4: What do task tests miss after an update? 

After an update, passing the original tests or completing one corrective action may still leave other requirements unmet. We examine three cases from the 24-case qualitative audit set (Appendix G), using the recorded GPT-5.6 Sol actions and evaluator results to explain the final outcomes. 

Tests can pass after a collaborator’s change is removed. In the Django case, a collaborator adds an API that controls when migration operations can be combined. The agent initially uses this API, then removes it while fixing the original issue. All 39 original tests pass, but the preservation check reports that the collaborator’s API is missing. 8Compensation can succeed while workspace checks fail. In the Astropy case, a cancellation arrives after an external effect has already occurred. The agent compensates for that effect, and the tool record confirms that compensation succeeded. The workspace-preservation check still fails. 

The final edits need fresh evidence. In the scikit-learn case, the agent restores access to current task evidence, then edits the code without querying that source again. The original task checks pass, but the required fresh observation is missing. The patch also exceeds the allowed edit scope. SWE-Shift therefore evaluates both the final workspace and the recorded actions against the require-ments that apply after the update.

The family results in Figure 4(a) identify tool/session changes and stale evidence as shared failure points. The trajectory analysis in Section 4.5 shows how agents can pass original task tests while removing valid collaborator work or relying on outdated evidence. These failures motivate checking preservation and evidence validity alongside task completion. The evaluation covers 120 designed scenarios, some sharing task roots, with one update per run. Diagnostic controls cover five systems. Pairing fixes the recorded history and workspace state, while model randomness remains uncontrolled. Intervention position varies with execution stage, accumulated context, and remaining work. The post-fork token budget is fixed. Freshness checks verify required observations. Task and preservation checks assess the resulting state (Appendix D). Evaluating repeated changes in natural software-development workflows is a next step. 

## 6 Conclusion 

Existing repository-level coding benchmarks largely assume fixed tasks and environments, leaving agents’ ability to handle mid-execution changes insufficiently tested. We introduced SWE-Shift to address this gap through task-relevant, recoverable interventions and matched Clean and Shifted continuations from the same saved execution state. Its success criteria jointly assess task completion, preservation of valid work, recovery, and evidence validity. Evaluation across 17 coding-agent systems shows that success under unchanged conditions often does not survive an update. Family-level and trajectory analyses further reveal recurring failures in state recovery, preservation, and evidence use that original task tests can miss. SWE-Shift provides a common testbed for measuring robustness to change, diagnosing these failures, and assessing whether new methods improve agents’ ability to continue working reliably in evolving software environments.

14 A Extended Method 

A.1 What changes, and what must survive? 

A scenario specifies a repository task, a task-relevant change, how the agent can discover that change, and checks for a correct continuation. The change may affect repository files, runtime or session state, external effects, requirements, or the evidence available to the agent. After the change, some requirements remain, some are added, and some may be withdrawn. A correct continuation must satisfy the current requirements while preserving work and effects that are still valid. The suite covers ten scenarios in each of 12 change families (Figure 3). F01–F07 concern code, collaborators, runtime, sessions, and effects; F08–F10 separate disclosure, corrective feedback, and goal revision; F11–F12 separate stale from misbound evidence. The 120 scenarios comprise an initial 24-case set and a 96-case expansion, sharing 23 root snapshots and 39 family–archetype–root clusters. The initial 24 cases were constructed and audited with GPT-5.6 Sol in the Codex app at 

xhigh reasoning; their full trajectories support the qualitative analysis in Appendix G. Roots can occur across families, and equal family weights provide controlled coverage of the change families. 

A.2 What is held fixed at the fork? 

For a system and checkpoint, the runner executes one prefix and saves the workspace, controller state, available tools, and the agent’s recorded history, system settings, and counters. Both continuations resume from this saved state. Clean continues without a relevant update; Shifted applies the scenario’s update. Their subsequent observations and actions may differ. Each scenario identifies who can authorize an update and which requirements remain in force. The agent receives the task, allowed command and state-operation identifiers, and visible state. Changes appear through delivered messages, workspace differences, or permitted state queries. The evaluator’s actor and version bindings are held out. The agent uses structured file actions, named commands, and declared state operations. Available commands vary by scenario; some expose only repository status and diff, without a test command or unrestricted shell. The evaluator runs separate held-out checks. The evaluated coding-agent systems and their settings appear in Table 8. 

A.3 Construction checks 

Each admitted scenario requires a valid, task-relevant update and at least one preservation-safe recovery using only the agent-accessible tools. Table 3 lists the checks. Two negative examples test the update’s relevance: a blind continuation must fail task or preservation checks, while a stale repair must fail at least one applicable Shifted check, even if it passes the original task tests. Construction also checks affected dependencies, how the agent can discover the update, recovery order, information exposure, and deterministic restoration. Appendices C and D detail the family requirements and scoring checks.

## E Extended Related Work and Benchmark Comparison 

Repository repair and shared editing. SWE-bench establishes executable repository-level issue reso-lution [13]; SWE-agent demonstrates that the agent–computer interface changes how effectively a model can navigate, edit, and test a repository [35]. SWE-Touch is the closest intervention study: it injects validated task-conflicting Counter-Edits during execution, includes a helpful non-solving Co-Edit control, and studies repeated edits and relative schedules on longer tasks [30]. SyncMind uses repository histories to construct caller/callee inconsistencies and evaluates autonomous and collaborative recovery [10]. SWE-Shift forks continuations from the same recorded history and checks the requirements that remain in force after an authorized update. An update may need to be retained even when removing it would still pass the original issue’s tests. Table 7 compares these designs at the level of the manipulated object, history control, and outcome. 

Interaction and specification histories. SWE-INTERACT progressively reveals requirements through a workspace-aware user simulator and scores the submitted solution with the underlying task verifier [28]. SWE-Together reconstructs tasks from real user–agent sessions, combines agentic-judge correct-ness with corrective-turn diagnostics, and grounds the simulator in the original user’s intent [33]. SpecPath makes a complementary control explicit: vary the history while holding the final contract, repository, verifier, and execution policy fixed. Implementation begins only after the complete history is visible [32]. Its specification-history result and representation of active obligations are direct precedents for distinguishing retained from withdrawn requirements. SWE-Shift instead changes an already-started execution and its external state. Comparing these settings separates clarifying requirements before action from continuing work after a dependency or authority has changed. 19 State, side effects, and time. AppWorld already makes collateral damage part of task evaluation: expected and permitted database changes constrain the difference between initial and final states while admitting multiple solutions [31]. ToolSandbox checks ordered milestones and forbidden events across stateful tool trajectories [16]. 𝜏 2-Bench gives both user and agent control of the envi-ronment and supports state and interaction checks [3]. Gaia2 advances this setting to independently evolving, asynchronous events with action-level verification [8]; FutureSim replays real information chronologically for forecasting agents [9]. These works show why successful action cannot be reduced to a plausible final answer. SWE-Shift specializes this concern to controlled repository continua-tions, where preserving another actor’s valid change and respecting an irreversible effect can require different recovery operations. 

Behavioral testing and measurement validity. CheckList organizes targeted behavioral tests beyond aggregate accuracy [29]. Measurement modeling separates a claimed construct from its observable operationalization [12]; recent work applies this distinction directly to LLM benchmarks [4]. This motivates the separation in our scoring between task tests, preservation checks, and records of required observations. Freshness checks record allowed observations; task and preservation checks assess behavior. Positive and selective-negative construction checks validate these measures before agent evaluation. 

Updating information and rebuilding dependencies. The distinction between a changing world and new information about a fixed world predates language-model agents [14]. It helps keep true state changes separate from fixed-goal disclosure in our taxonomy. Build Systems à la Carte separates scheduling from deciding which dependent computations require rebuilding [20].

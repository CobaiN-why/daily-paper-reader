## ABSTRACT 

Coding agents are becoming an increasingly important paradigm for automat-ing software engineering tasks. However, existing coding benchmarks primar-ily evaluate agents at the function or repository level, leaving their capabilities in more complex distributed software systems largely unexplored. In practice, many modern applications adopt microservice architectures, where end-to-end performance emerges from interactions among multiple independently running services, requiring agents to reason beyond local code changes. To study this capability, we introduce MicroPerf-Bench, a benchmark for evaluating coding agents on end-to-end performance optimization in microservice systems. Con-structing such a benchmark is challenging because reproducible system-level per-formance fixes are sparse and difficult to attribute. We address this challenge by injecting empirically grounded performance anti-patterns into real-world open-source systems while preserving functionality and ensuring measurable perfor-mance degradation. The resulting benchmark contains 65 optimization instances across seven systems and nine anti-patterns, each with an executable environment, functional tests, and mixed-workload evaluation. Across 1,755 runs covering nine agent–model configurations, the best configuration recovers only 42.0% of the injected performance degradation. The dominant failure is not invalid code, but functionally correct and constraint-compliant changes that fail to improve end-to-end performance, highlighting system-level bottleneck localization as a key challenge for current coding agents. The source code and data are available at 

https://github.com/zyzcjnb/microperf .

## 1 INTRODUCTION 

Large language models have rapidly evolved from code-generation tools into coding agents that can solve software engineering tasks (Jimenez et al., 2024; Yang et al., 2024). As these agents become increasingly capable, reliably evaluating their capabilities becomes increasingly important. Existing coding-agent benchmarks have largely focused on functional software engineering tasks. For ex-ample, SWE-bench (Jimenez et al., 2024) evaluates whether agents can resolve software issues by producing patches that satisfy functional tests. Such benchmarks are crucial for measuring progress in coding agents, but functional correctness captures only one dimension of software quality. Recently, there has been growing interest in a complementary capability: performance optimiza-tion , which asks whether an agent can make software more efficient in terms of execution time and resource usage while preserving its functionality. Such software performance depends on the work-load, execution environment, and runtime interactions. Therefore, an effective optimization agent should identify the source of performance degradation, determine an appropriate modification, and verify that the modification produces a measurable improvement under execution. Motivated by this challenge, recent work has begun to benchmark the performance-optimization ca-pabilities of coding agents. Early benchmarks mainly study performance at the function or program level. For example, EffiBench (Huang et al., 2024) evaluates the efficiency of generated imple-1arXiv:2610.29695v1 [cs.SE] 21 Oct 2026 Preprint. Under review as a conference paper at ICLR 2027 

mentations on self-contained programming tasks. More recent benchmarks, such as GSO (Shetty et al., 2026), extend evaluation to the repository level, requiring agents to navigate larger codebases and produce correctness-preserving optimizations. However, these settings still largely treat a pro-gram or codebase together with its workload as the unit of optimization. An important capability remains less explored: system-level performance optimization , where end-to-end behavior emerges from interactions among multiple components during execution. Microservice systems provide a representative setting for studying this capability. A microservice application is composed of multiple independently running services that communicate through net-work calls. As a result, the latency experienced by a user may depend on an entire execution path across services. Performance optimization in this setting thus requires agents to reason beyond local code changes and understand how components interact at runtime. However, building a benchmark in the microservice setting is nontrivial. Reproducible real-world system-level performance fixes are sparse, often intertwined with other code changes and difficult to attribute. At the same time, arbitrarily synthesized performance bugs may fail to reflect the problems that arise in real systems. To address these challenges, we introduce MicroPerf-Bench , a benchmark for evaluating cod-ing agents on end-to-end performance optimization in microservice systems. Rather than relying solely on mined fixes, we construct benchmark instances through controlled injection of empiri-cally grounded microservice performance anti-patterns (Keck et al., 2016), which capture recurring system-level inefficiencies. We inject them into real-world microservice systems while preserving functional behavior and ensuring measurable performance degradation. The resulting benchmark contains 65 optimization instances across seven microservice systems and nine performance anti-patterns. Each instance provides an executable multi-service environment, functional tests, and mixed-workload performance evaluation. Given an under-optimized system, an agent must inspect and modify its implementation. The affected services are then rebuilt and redeployed, and the result-ing system is evaluated for both functional correctness and end-to-end performance improvement. Using MicroPerf-Bench, we conduct a systematic evaluation of nine agent–model configurations formed by three agent harnesses and three underlying models. We run every configuration three times on all 65 instances, yielding 1,755 optimization runs. Current coding agents remain far from solving the benchmark: even the best configuration achieves an average normalized score of only 42.0 out of 100. More importantly, our failure analysis reveals that the dominant failure is not invalid code. Instead, agents frequently produce functionally correct modifications that yield no measurable end-to-end performance gain. This finding exposes an important gap between agents’ ability to modify code and their ability to understand and optimize system-level runtime behavior :identifying the true bottleneck remains a central challenge. Our broader analysis further shows that performance varies substantially across host systems and repeated runs, motivating both system-aware optimization methods and more robust evaluation protocols. 

## 2 BACKGROUND AND MOTIVATION 

Performance in Microservice Systems. Microservice architectures have become the dominant paradigm for modern software systems, enabling developers to build, scale, and deploy complex ap-plications as collections of small, loosely coupled, and independently deployable services (Newman, 2021; Gan et al., 2019). Despite their operational benefits, microservice architectures fundamentally alter the nature of software performance optimization. In traditional monolithic software, performance bottlenecks are typically localized to specific algo-rithmic inefficiencies, unoptimized database queries, or excessive I/O within a single process. In contrast, performance in a microservice system is an emergent property arising from the dynamic interactions among multiple services executing across a distributed network. A single user-facing request often triggers a directed acyclic graph (DAG) of downstream inter-service remote procedure calls (RPCs), asynchronous message exchanges, and shared database transactions. Consequently, end-to-end user latency is determined not merely by individual code efficiency, but by cross-service communication overhead, service dependency topologies, serialization bottlenecks, and resource contention. Optimizing a microservice system thus requires agents to reason beyond localized func-tions and comprehend system-wide runtime execution paths. 2Preprint. Limitations of Existing Coding Benchmarks. Recent advances in large language models (LLMs) have driven the rapid development of autonomous coding agents capable of resolving real-world software engineering issues (Jimenez et al., 2024; Yang et al., 2024). To measure progress, early performance optimization benchmarks evaluated models on standalone function-level tasks (Huang et al., 2024), while recent benchmarks such as GSO (Shetty et al., 2026) and SWE-perf (He et al., 2025) extended evaluations to repository-level codebases. However, existing benchmarks operate under the assumption that a program can be compiled, tested, and profiled as a self-contained unit within a single codebase. This setup fails to model microservice environments due to two gaps: 

(1) Cross-Service Structural Reasoning Gap: In a distributed architecture, fixing an end-to-end bot-tleneck often requires structural modifications spanning multiple repositories or services—such as introducing an API gateway, replacing synchronous RPCs with asynchronous queues, or consol-idating chatty interfaces. Repository-level benchmarks cannot formulate or evaluate such cross-boundary architectural refactoring. 

(2) Deployment-Centric Evaluation Gap: Local code efficiency does not guarantee system-level per-formance gains. A change that speeds up a local function might simply shift the system bottleneck to a downstream database or alter concurrency dynamics under heavy traffic. Accurately assessing microservice performance requires deploying the complete multi-service stack (e.g., via container orchestration) and subjecting it to dynamic, end-to-end multi-endpoint workloads. 

Performance Anti-Patterns as Ground Truth. To bridge this gap and establish a rigorous bench-mark, we draw upon the concept of performance anti-patterns (Keck et al., 2016; Cerny et al., 2023). Performance anti-patterns represent recurring architectural and implementation bad prac-tices that consistently induce severe system-level performance degradation under load. Examples include Chatty Service (excessive fine-grained RPC calls) and Shared Persistency (multiple services coupling directly to a single database). Utilizing empirically grounded performance anti-patterns offers an ideal framework for benchmark construction: they provide realistic, real-world-relevant performance bugs, have verifiable optimiza-tion paths through code and topology refactoring, and enable precise attribution of performance recovery under controlled experimental conditions. 

## 3 MICRO PERF -B ENCH 

To systematically evaluate coding agents on end-to-end performance optimization in distributed systems, we present MicroPerf-Bench . The benchmark comprises 65 system-level optimization instances constructed from seven real-world open-source microservice applications and nine per-formance anti-patterns. Each instance provides a fully deployable multi-container environment, functional test suites, and end-to-end workload profiling scripts. Next, we formalize the optimization task (Section 3.1), describe our rigorous data construction and validation methodology (Section 3.2), and detail the evaluation protocols and metrics (Section 3.3). 3.1 TASK FORMULATION 

We formulate system-level performance optimization as a constrained patch-generation task. 

Input. For each benchmark instance i, an agent is provided with: (1) The complete under-optimized multi-service codebase Ci; (2) Container deployment configurations Mi (e.g., Docker Compose manifests); (3) An executable mixed-workload load testing script Wi reproducing user traffic; (4) A formal task specification Si outlining the target application and system boundary constraints (Ap-pendix B). 

Constraints & Anti-Shortcut Rules. To ensure that improvements originate from genuine code or architectural optimizations rather than artificial shortcuts, Si explicitly prohibits agents from: (1) increasing hardware resource allocations (e.g., boosting CPU/memory limits in Docker); (2) dis-abling non-functional system mechanisms (e.g., dropping distributed tracing, logging, rate-limiting, or authentication middleware); or (3) weakening database transaction safety or security validation. 3Preprint. Output. The agent must generate a set of modified or newly added source code and configuration files ∆Ci. The benchmark interface accepts standard unified file diffs or directory artifacts, ensuring complete compatibility with arbitrary agent scaffolds and LLMs. 

Deployment-Centric Evaluation Execution. Upon receiving ∆Ci, the benchmark execution har-ness rebuilds the affected container images, redeploys the distributed system in an isolated environ-ment, and executes both functional correctness tests and dynamic workload profiling. 3.2 DATA CONSTRUCTION 

Constructing a reliable system-level performance benchmark presents a key dilemma: mined real-world commits are sparse and entangled, while synthetic bugs risk being unrealistic or trivial. In a pre-study, we audited over 10,000 commits across 12 popular open-source microservice reposi-tories (Appendix A). Only 15 commits give pure, attributable microservice performance fixes, with 9 concentrated in a single suite with specialized maintenance. Moreover, real fixes often bundle fea-ture additions or framework upgrades, making isolated performance attribution nearly impossible. To solve this, we adopt a controlled injection methodology anchored in empirically grounded per-formance anti-patterns. Figure 1 details our four-phase construction pipeline. 

Phase I: Performance Anti-Pattern Selection & Real-World Grounding. Starting from 58 cat-alogued microservice anti-patterns and bad smells (Cerny et al., 2023), we applied three rigorous screening criteria. (1) Performance Relevance : The pattern must produce measurable runtime la-tency degradation rather than mere code maintainability issues. (2) Reproducible Degradation : The latency impact must significantly exceed environmental measurement noise under standard work-loads. (3) Optimization Actionability : The pattern must be fixable via code, architectural, or topol-ogy refactoring (excluding hardware scaling). This process yielded nine target anti-patterns: Nano-service , Mega service , Service chain , Chatty service , Shared persistency , Empty messages , On-line only , Hub-like dependency , and ESB mis-use (retained in our taxonomy as an uninstantiated coverage gap). All selected patterns directly mirror documented industrial challenges (Appendix A). For example, Chatty Service drove the adoption of GraphQL and Backend-for-Frontend (BFF) patterns at Meta and SoundCloud (Byron, 2015; Calc ¸ado, 2014); Shared Persistency mirrors database contention reported by Discord (Ingram, 2023); On-line Only motivated Netflix’s transition to asynchronous cloud gateways (Cohen, 2016). 

Phase II: Target System Selection & Baseline Cleaning. We evaluated 28 open-source mi-croservice repositories against four criteria: active maintenance, thorough API documentation, re-producible mixed-workload scripts, and architectural diversity. Seven representative applications were selected: Spring PetClinic Microservices, MartianBank Demo, Robot Shop, Pitstop, and three DeathStarBench suites (Social Network, Media Service, Hotel Reservation). To ensure that evaluation scores strictly measure the recovery of injected degradation, we estab-lished clean ”Original Reference” ( R) baselines free of native defects. Three senior software engi-neers with over three years of microservice industry experience independently audited the systems, resolving pre-existing issues such as N+1 query patterns and missing database indexes. Phase III: Controlled Anti-Pattern Injection & Quality Validation. Evaluations are conducted in heavily isolated environments. Between runs, we batch-build images, purge environmental state, and launch fresh containers. Performance tests incorporate a 90-second warm-up phase to absorb JVM/container startup effects, followed by three averaged measurements. 

Isolated Evaluation Environment. Each evaluation run executes in a fully isolated container en-vironment. Prior to profiling, the harness purges cached states, batch-builds fresh container images, and launches the services. To eliminate cold-start artifacts and JVM JIT compilation noise, each test runs a 90-second warm-up phase, followed by three averaged measurement iterations. 

Metric Selection Rationale. Throughput metrics (RPS) were found to plateau under non-saturated workloads and exhibit high hardware-dependent variance under saturated conditions. Consequently, we employ average end-to-end request latency under mixed workloads as our primary performance metric. The workload exercises multiple API endpoints simultaneously, preventing agents from trivially overfitting to a single endpoint. 

Correctness and Fairness Gates. An agent’s patch O must pass two non-negotiable gates: 1. Functional Correctness Gate: The optimized system must pass 100% of functional API test suites and data-consistency assertions. Additionally, the request error rate under load must not exceed the degraded version’s error rate by more than 1% .2. Fairness Compliance Gate: Patches that achieve speedups by disabling security checks, rate limiting, distributed tracing, or transaction isolation are flagged as violations and assigned zero.

## 4 EXPERIMENTS 

To assess the capabilities of current coding agents in optimizing microservice performance, we conduct an extensive evaluation across multiple models and agent scaffolds. This section details our experimental setup, analyzes the overall performance and failure modes of baseline configurations, investigates the impact of runtime profiling, and provides qualitative case studies to illustrate agent behaviors. 4.1 EVALUATION SETUP 

Agent Configurations. We evaluate nine baseline configurations formed by the Cartesian prod-uct of three agent scaffolds (OpenCode, OpenHands, and Claude Code) and three state-of-the-art base models (GLM-5.2, Qwen3.7-Max, and DeepSeek-V4-Pro). To encourage exploration and rea-soning, all models operate with a temperature of T =1 .0 and have their respective “thinking” or chain-of-thought modes enabled. Complete configuration details are provided in Appendix D. 

Execution Protocol. Each configuration is provided with an identical task specification, which explicitly outlines the optimization objective, the permitted scope of modifications, and the correct-ness and fairness gates defined in Section 3.3. Agents can execute the provided mixed-workload script during optimization, but the task specification does not explicitly instruct them to perform performance measurements. We allocate a total time budget of 2 hours per benchmark instance, with a strict 20-minute timeout per executed command. Because agentic optimization is inherently stochastic and the resulting score distribution is zero-inflated, we independently run each of the nine configurations three times across all 65 benchmark instances. This yields a total of 1,755 indepen-dent optimization trials for our primary evaluation. 

Evaluation Metrics. We quantify optimization success using three complementary metrics, all averaged over the three independent runs unless otherwise specified: • Average Score: The mean of the instance-level scores ( Si ∈ [0 , 100] ) computed via Eq. 1. Trials that violate functional correctness or fairness constraints automatically receive a score of zero. • Positive-Score Rate: The percentage of trials yielding Si > 0, indicating that the agent achieved a measurable latency reduction relative to the degraded baseline while satisfying all constraints. • Full-Score / Partial-Score Rates: We decompose the positive-score rate into the full-score rate 

(Si = 100 , indicating complete performance recovery) and the partial-score rate (0 < S i < 100 ). 

Measurement Environment. All experiments are executed on a dedicated dual-socket server equipped with 2× Intel Xeon Platinum 8562Y+ CPUs and 384 GB of RAM, running Ubuntu 22.04. To ensure pristine measurements, every performance evaluation rebuilds the instance, deploys it in fresh containers, and executes a 90-second warm-up phase to stabilize JVM and container states. End-to-end latency is measured three times under the mixed workload, and the results are averaged. 4.2 OVERALL BASELINE PERFORMANCE 

Table 1 presents the performance of the baseline configurations across the trials. The results show that end-to-end system performance optimization remains a formidable challenge for coding agents. Average scores range from a low of 23.4 (Claude Code + DeepSeek) to a high of 42.0 (OpenHands + GLM). Across all configurations, the mean positive-score rate sits at just 44.0%. More strikingly, full-score rates remain exceptionally low, ranging from 9.2% to 22.6%. This indicates that more than half of all optimization attempts fail to yield any valid performance improvement. Partial-score outcomes account for 27.4% of all trials, substantially outnumbering the 16.7% of trials that achieve a full score. This discrepancy suggests that while agents can sometimes identify and mitigate secondary inefficiencies, they often miss the primary system bottleneck responsible for the bulk of the injected degradation. 4.3 EFFECTS OF BASE MODEL AND AGENT SCAFFOLD 

To isolate the contributions of underlying base models and agent scaffolds, we run paired t-tests on the per-instance mean scores across all 65 instances, using a significance threshold of α = 0 .05 .

Base Model Impact. The choice of base model significantly influences optimization success. Av-eraged across all scaffolds, GLM outperforms DeepSeek by a substantial margin of 12.7 points (p = 0 .001 , Cohen’s dz = 0 .45 ), while Qwen surpasses DeepSeek by 9.3 points ( p = 0 .003 ,

dz = 0 .39 ). GLM also achieves a 3.4-point advantage over Qwen, though this difference falls short of statistical significance ( p = 0 .105 ). Notably, DeepSeek consistently ranks lowest across all three evaluated scaffolds, demonstrating a robust performance hierarchy among the models. 

Agent Scaffold Impact. In contrast, performance variance acrossscaffolds is much smaller and less definitive. Averaged across models, OpenHands edges out OpenCode by 3.2 points ( p = 0 .139 ) and Claude Code by 3.3 points ( p = 0 .133 ). OpenCode and Claude Code perform almost identically, with a nominal 0.1-point difference ( p = 0 .957 ). None of these scaffold comparisons reach the significance threshold. Furthermore, the optimal scaffold appears model-dependent: OpenHands pairs best with GLM and DeepSeek, whereas Claude Code yields the highest score when paired with Qwen. While these results do not prove equivalence, they suggest that in the context of system-level performance tuning, the reasoning capacity of the base model outweighs the scaffolding logic. 4.4 FAILURE MODE ANALYSIS 

To systematically understand why agents fail to optimize these systems, we classify all 982 zero-score trials into five distinct failure modes based on comprehensive audit logs: no performance gain (changes are correct, but fail to reduce latency), fairness violation , functional correctness error , build or startup failure , and timeout . Precise definitions are provided in Appendix G. As depicted in Figure 2, the “no performance gain” mode dominates, accounting for 48.7% of all failures. This is a critical insight, and agents frequently succeed at writing functionally correct, compilable code that adheres to all constraints, yet they fundamentally fail to move the needle on end-to-end latency. This suggests that, beyond code generation, bottleneck identification , i.e., the ability to diagnose where time is actually being spent, remains a key challenge for current agents. The distribution of failure modes is heavily influenced by the model. The “no gain” outcome con-stitutes 67.6% of GLM’s failures, indicating it safely edits code but often targets the wrong com-ponents. Conversely, Qwen and DeepSeek are more prone to fairness violations (e.g., stripping out vital tracing or validation logic to artificially speed up execution), with DeepSeek also suffering from higher rates of build failures. Motivated by the prevalence of “no gain” failures, we investigate if equipping agents with dynamic runtime feedback can improve their optimization efficacy. We integrate a dedicated profiling tool that supports automated workload testing, performance profiling, and distributed trace extraction. We evaluate the Claude Code + Qwen configuration augmented with this tool in a single run across all 65 instances. The preliminary results are highly promising. As shown in Figure 3(a) and Table 1, the augmented run achieves an average score of 47.7, comfortably surpassing its baseline mean of 39.4 and beating the highest baseline configuration across all nine setups (42.0). Its positive-score rate surges from 45.6% to 58.5%, and its full-score rate jumps from 22.6% to 30.8%. However, the benefits of profiling are not uniform. Figure 3(b) reveals that while gains are substan-tial on systems like Hotel and RobotShop, performance on Pitstop actually regresses. This suggests that while dynamic feedback can rapidly steer agents toward correct bottlenecks, complex trace data might overwhelm or mislead them in certain contexts. While these single-run findings require further replication, they strongly underscore that advancing from repository-level to system-level optimization requires transitioning agents from static code analyzers into runtime-aware profilers. 4.6 CASE STUDIES 

To ground the benchmark mechanics and agent behaviors, we detail three representative instances. Full trajectories, verbatim agent logs, and detailed metrics are available in Appendix E. 

Case Study A: Full Recovery. On martian-bank/nh (a system injected with both nano-service and hub-like-dependency anti-patterns), OpenHands + GLM demonstrated precise architectural di-agnosis. The injection splits the transfer path into four services (transactions → sender-resolver →

receiver-resolver → executor) behind a central write entry, adding four HTTP hops per transfer and degrading latency by 50% (9.22 ms → 13.81 ms). In a 26-minute session (106 actions), the agent merged the three injected sub-services back into the transactions service, collapsed per-party ac-count queries into a single $in lookup with one bulk write , and switched to persistent HTTP sessions. Latency recovered to 9.04 ms for a score of 100, landing at the edge of the reference implementation’s own run-to-run range (9.05–9.39 ms), i.e., convergence to reference-level perfor-mance rather than a demonstrated surpassing of it. This confirms that co-injected structural patterns are fully repairable within budget, and that the decisive factor is correct localization: the sibling n

variant scored 0 under the same configuration in the same batch. 

Case Study B: Right Fixes, Wrong Bottleneck. On media/c2hl (chatty service combined with hub-like serialization), Claude Code + DeepSeek quickly navigated the 13-service codebase. It successfully merged seven per-field review RPCs into one and stripped legacy lookups, passing both evaluation gates in under nine minutes. However, the agent directly examined the primary defect—a global mutex wrapping five serial cache reads—and explicitly dismissed it in its logs: 

“The 5 individual gets are cheap. . . Let me leave this as is.” Because the agent relied purely on static analysis, it failed to realize that under concurrent traffic, this global lock forces every request into a severe lock convoy, causing the injected 141 × latency spike. Latency remained stranded at 5,951.80 ms (score 0). This case shows the limits of static reasoning. The agent possessed the coding ability to fix the issue, but lacked the dynamic execution data required to recognize its severity. 

Case Study C: Measurement Reorders Priorities. On hotel/c2s , the baseline Claude Code + Qwen scored 0, 0, and 75.3 across three runs. In the failing runs, the agent used static code reading to mistakenly identify chatty RPCs as the primary bottleneck, leaving a severely serialized shared-DB path unrepaired. However, when equipped with the profiling tool (Section 4.5), the agent’s behavior transformed. Using actual load measurements and an A/B comparison (22.2 s vs. 10.8 ms), the agent proved that the shared-DB path was the true culprit. It then fixed both injected patterns in a 14-minute session, achieving a score of 88.8, outperforming its best baseline run. This case cleanly isolates the value of runtime augmentation. It does not grant the agent better coding skills, but it provides the critical evidence needed to align the agent’s optimization priorities with reality. 

## 5 RELATED WORK 

Code Performance Optimization. The rapidly growing body of work on LLM code performance optimization has produced function-level benchmarks (Huang et al., 2024; Qiu et al., 2025; Waghjale et al., 2024; Du et al., 2024) and, more recently, repository-level benchmarks (Shetty et al., 2026; He et al., 2025; Ma et al., 2025). MicroPerf-Bench extends this progression to the system level: rather than optimizing a single codebase against its own workload, agents must recover performance that emerges from interactions among independently running services. 

Microservice Benchmarks. Prior microservice benchmarks have mainly been used to study sys-tem performance, resource efficiency, reliability, testing, and operation (Gan et al., 2019; Sriraman & Wenisch, 2018; Von Kistowski et al., 2018; Zhou et al., 2018). With the development of cod-ing agents, recent work has begun to evaluate end-to-end code generation for microservice sys-tems (Peng et al., 2026). Beyond functional correctness, performance is also important because end-to-end behavior in microservice systems depends on runtime interactions among multiple ser-vices. MicroPerf-Bench focuses on this capability by evaluating whether coding agents can optimize the end-to-end performance of existing microservice systems while preserving their functionality. 9Preprint. ## 6 CONCLUSION 

We introduced MicroPerf-Bench, a benchmark for evaluating coding agents on end-to-end perfor-mance optimization in microservice systems. It contains 65 instances across seven systems and nine performance anti-patterns constructed through controlled anti-pattern injection. Our evaluation of nine agent–model configurations shows that current agents remain far from solving these tasks, with the best configuration achieving an average normalized score of 42.0 out of 100. Many unsuccessful attempts remain functionally correct but produce no measurable end-to-end performance improve-ment, highlighting the difficulty of identifying system-level runtime bottlenecks. Performance also varies across host systems and repeated runs. Profiling results further suggest that runtime evidence can improve optimization effectiveness.

## PERFORMANCE ISSUES 

Methodology. We mined the commit histories of 12 well-known open-source microservice sys-tems and catalogued documented industrial performance cases. A commit qualifies as system-level 

only if it (i) modifies interactions across at least two services, a shared data/cache tier, or the service decomposition structure, and (ii) has an explicit performance motivation. We excluded function-level optimizations within a single service (e.g., serializer caching), pure parameter tuning (e.g., connection limits, GC settings), and dependency upgrades. Two authors independently screened candidates and resolved disagreements by discussion. 

Mining results. Table 2 summarizes the outcome. Among more than 10,000 commits, only 15 (0.15%) satisfy our criteria, and they concentrate in repositories maintained by corporate perfor-mance teams. This sparsity and skew empirically motivate injection-based construction. 

Mapping to the nine anti-patterns. Table 3 maps each injected anti-pattern to concrete real-world evidence. Seven of the nine anti-patterns are directly corroborated by merged commits in open-source systems or by documented industrial cases. The remaining two, Empty messages and 

ESB misuse , are anchored in the empirical anti-pattern catalog (Cerny et al., 2023): Empty messages traces back to the original web-service anti-pattern literature (Rodriguez et al., 2010), where it has been empirically detected and refactored in real services (Ordiales Coscia et al., 2013), while ESB misuse is corroborated by its modern counterpart, the removal of Istio’s centralized Mixer compo-nent. We also observed that two major demo systems (OpenTelemetry Demo, Robot Shop) ship intentionally injected performance faults, indicating that fault injection is the community’s prevail-ing practice when a performance defective microservice system is needed. 

Limitations. Naturally occurring fixes rarely ship with measurements or reproducible environ-ments (e.g., commit ed98db1 carries a two-word message with no linked issue), which is precisely why they cannot serve directly as benchmark instances. Some anti-patterns (e.g., Empty messages )manifest as persistent design choices rather than one-shot fixes, so their evidence is industrial rather than commit-level. Finally, injected instances may not capture the full complexity of open-ended, organically emerging performance problems; we mitigate this threat by deriving all operators from an empirically grounded catalog and by corroborating each operator with the evidence above.

## C EXPERT VALIDATION 

Reviewers and Procedure. We recruited three experts with over three years of experience in mi-croservice development through the authors’ personal networks. All experts participated voluntarily. Following anti-pattern injection, the resulting benchmark instances were subjected to expert valida-tion before being included in the final benchmark. The validation consisted of two complementary assessments: anti-pattern diagnosis and defect-source discrimination. The former examines whether the injected performance problems exhibit identifiable runtime symptoms, while the latter examines whether the injected instances contain obvious cues that reveal their artificial origin. 

Anti-Pattern Diagnosis. All 65 benchmark instances were included in the diagnosis assessment. For each instance, reviewers were asked to identify the injected performance anti-pattern from its runtime behavior without being provided with the corresponding anti-pattern label. The injected anti-pattern was correctly diagnosed in 81 .5% of cases. This result indicates that the injected perfor-mance problems generally produced recognizable runtime symptoms under the evaluation setting. We use this assessment to evaluate the diagnosability of the constructed instances rather than to claim equivalence between injected and naturally occurring performance defects. 

Defect-Source Discrimination. We further conducted a blinded discrimination study to examine whether the injected instances exhibited obvious artifacts of the injection process. We sampled 12 injected instances and mixed them with 12 naturally occurring performance defects reconstructed from the parent commits of documented performance fixes in open-source repositories. The 24 cases were presented without revealing whether their source was injected or naturally occurring. The reviewers were asked to identify the source of each defect. The resulting source-identification accuracy was 47 .2% . We report this result descriptively: under this evaluation setting, the reviewers did not reliably identify the provenance of the sampled defects, suggesting that the injected instances did not present obvious source-specific cues to the reviewers. 

Scope of the Validation. These assessments serve as complementary checks on the benchmark construction process. The diagnosis assessment evaluates whether the injected problems manifest 16 Preprint. Under review as a conference paper at ICLR 2027 

as identifiable performance symptoms, whereas the discrimination assessment evaluates whether their injected provenance is readily apparent to expert reviewers. The latter does not constitute a statistical equivalence test between injected and naturally occurring defects, nor does it establish that the two groups have identical runtime behavior or optimization difficulty. Instead, it provides evidence that the sampled injected instances do not exhibit obvious artificial characteristics under the expert evaluation setting.

## F RESULTS BY ANTI -P ATTERN 

Table 6 breaks down optimization performance by the injected anti-pattern. Combined instances contribute to each of their constituent patterns. The nine patterns differ markedly in difficulty. Hub-like dependency is the hardest pattern on average (21.6 points, 8.3% full-score rate): the injected hub serializes request traffic, and agents frequently relieve only part of the constraint or migrate the serialization point rather than removing it. Its difficulty is also system-dependent, ranging from 4.3 points on Martian and Social to 56.6 on Pitstop, depending on whether the hub sits on the critical path of the mixed workload. On-line only and Chatty service are the most tractable patterns (47.9 and 42.5 points), as both have well-known architectural fixes (asynchronous I/O and batching). No-tably, failures on On-line only are dominated by correctness errors (43.3% of its zero-score trials): rewriting blocking call chains into asynchronous ones often breaks ordering or error-propagation semantics. The single Mega service instance (on Social) was never solved: merging more than ten services broke the build in 51.9% of its zero-score trials, indicating that large-scale structural consol-idation is infeasible within the two-hour budget. Empty messages shows the highest positive-score rate (61.7%) but a modest average score (34.9), since payload shaping yields only limited latency gains under our non-saturated workloads; 87.1% of its zero-score trials are no-gain outcomes.

## I SINGLE -P ATTERN VS . C OMBINED -P ATTERN INSTANCES 

The benchmark contains 35 single-pattern instances and 30 combined instances (28 with two pat-terns, 2 with three patterns). Contrary to the intuition that combined instances should be harder, agents score slightly higher on them: 35.9 versus 34.0 on average, with positive-score rates of 46.7% versus 41.8% and similar full-score rates (18.0% versus 15.6%). A paired comparison within the seven systems confirms the pattern: combined instances score higher in five of seven systems, with a mean within-system difference of +4.3 points that does not reach significance (paired t(6) = 1 .56 ,

p = 0 .170 ). Per-system scores on the two subsets are strongly correlated (Pearson r = 0 .96 ), that is, system difficulty transfers almost perfectly between single and combined injections (Figure 6). One plausible explanation is that co-injected patterns offer multiple independent opportunities for partial recovery and more diagnostic symptoms, so fixing either pattern already yields a positive score. Media shows the largest gap (+19.4 points), where its combined instances pair the two most tractable patterns. We note that the comparison is confounded by which patterns were selected for combination, and report it as a descriptive property of the benchmark rather than a causal claim.

## L MEASUREMENT PROTOCOL AND SCORE ROBUSTNESS 

Measurement protocol. For each instance, the reference latency LR and the degraded-baseline latency LD were each measured three times before any agent run and recorded as the average, after which they were frozen. The same recorded pair is reused for all 27 configurations and all three rounds, so that every one of the 1,755 trials is evaluated against an identical numerical baseline; this freezing favors comparability across the full experiment over per-batch re-measurement. Each sub-mitted deployment is evaluated by running the standard mixed workload three times and reporting the mean of the three iterations. 

Workload, gates, and resource budget. The evaluation workload issues requests at a fixed rate with a fixed endpoint mix and input dataset, identical across all instances and rounds; each mea-surement runs for the same duration per deployment. Services run in isolated containers with fixed per-service CPU and memory limits on a dedicated host, with no co-located load during measure-ment. The error-rate gate fails any submission whose error rate under load exceeds that of the injected (degraded) baseline by more than one percentage point; timed-out requests are counted as errors and excluded from the latency average. Agents may merge or split services only when the aggregate CPU and memory budget of the system does not exceed that of the original deployment. 

Robustness of the success criterion. A positive score requires the measured optimized latency 

LO to fall below the degraded baseline LD , but a small positive difference could in principle reflect measurement noise rather than a genuine improvement. Two analyses suggest the reported results are not driven by such noise. First, positive trials are far from the decision boundary: among 773 positive trials, only 1.2% improve latency by less than 1% and 6.3% by less than 5%, while the median improvement is 62.8%. Second, we recomputed all statistics under success thresholds of 

δ ∈ { 2% , 5% , 10% } minimum relative improvement: the positive rate decreases modestly (44.0% to 39.9% at δ = 10% ), and all model-level conclusions are unchanged (GLM and Qwen remain significantly ahead of DeepSeek, p < 0.005 ). Full recoveries are not knife-edge either: among trials reaching LO ≤ LR, the median LO /L R is 0.82, and 72.9% land at or below 0.9 LR.

Supplementary score statistics. To distinguish “partially closing a large injected gap” from “ap-proaching reference performance,” we report the recovery score together with the ratios LO /L D

and LO /L R. Overall, 19.8% of trials reach LO ≤ 1.1 LR and 24.6% reach LO ≤ 1.2 LR.

# BenchMeUp: Building Software Engineering Benchmarks from Natural-Language Specifications 

Islem Bouzenia 

CISPA Helmholtz Center for Information Security Germany bouzenia.islem@pm.me

CISPA Helmholtz Center for Information Security Germany michael@binaervarianz.de 

Abstract —Software-engineering research relies on benchmarks that evaluate new techniques on a set of problem instances. Unfor-tunately, manually constructing benchmarks is labor-intensive, as researchers must find suitable instances, prepare execution envi-ronments, establish expected outcomes, and validate correctness. This paper presents BenchMeUp, an approach for automat-ically creating software-engineering benchmarks from natural-language specifications. Given a specification defining the desired instances, data sources, and evaluation procedures, BenchMeUp generates search rules and a construction plan, invokes parallel LLM agents that identify candidate instances and construct executable instances, validates the results in fresh execution environments, and packages the instances behind a unified command-line interface. We evaluate the approach on four tasks: program repair, issue reproduction, compiler autotuning, and fixing static-analysis warnings. Targeting 50 instances per task (200 in total), BenchMeUp constructs 198 instances, of which 196 (99%) are successfully packaged. Search and construction take 36 minutes and $0.79 per instance, on average. Evaluating eight existing techniques on the generated benchmarks, we find that 189 of 196 packaged instances (96%) support end-to-end evaluation, allowing users to study the effectiveness of the techniques. Checking every constructed instance against its source, the specification, and its expected outcome, we find that 180 of 198 (91%) meet all criteria, compared with 10 of 200 instances delivered by Codex (general-purpose coding agent). Overall, we show that LLM-based agents can automate bench-mark construction across diverse software-engineering tasks and produce executable instances that existing techniques can use, while validity beyond execution still needs to be checked. 

Index Terms —software engineering benchmarks, automated benchmark construction, large language model agents 

I. I NTRODUCTION 

Benchmarks are central to software-engineering re-search [1], enabling researchers to evaluate techniques on common problem instances, compare results, reproduce pre-vious findings, and measure progress. Some benchmarks have shaped entire research areas, such as Defects4J [2] for auto-mated program repair [3] and SWE-bench [4] for evaluating LLM-based issue-resolution agents. Unfortunately, manually constructing benchmarks is labor-intensive. Researchers must first define suitable benchmark instances and identify their data sources. They must then collect and prepare instance artifacts, such as source code and tests, set up dependencies, determine expected outcomes, and verify that each instance meets the benchmark requirements. For benchmarks involving executable software, this process often requires writing task-specific scripts, building and con-figuring projects, and manually inspecting the results. This effort leads researchers to reuse benchmarks for long periods, raising concerns about overfitting and representativeness [1]. Exploring new tasks or programming languages also requires substantial effort to construct suitable benchmarks. Several approaches automate parts of benchmark construc-tion. BugSwarm [5] mines continuous-integration histories to collect reproducible failing and passing program versions. SetUpAgent [6], ExecutionAgent [7], and RepoLaunch [8] automate building and testing repositories. SWE-smith [9], SWE-rebench [10], SWE-Factory [11], SWE-Bench++ [12], and SEC-bench [13] generate or collect issue-resolution and vulnerability tasks with executable environments. Each of these approaches targets one task or automates one construc-tion step. Beyond software engineering, AutoBencher [14] and BenchAgents [15] construct benchmarks from natural-language descriptions, but focus on synthetic questions for evaluating language models. To our knowledge, no exist-ing approach creates real-world, executable benchmarks from natural-language specifications. Recent advances in LLM-based agents [16], [7], [8] raise the question of whether they can construct software-engineering benchmarks. However, our evaluation shows that simply ask-ing a general-purpose agent to do so introduces several chal-lenges. First, agents may interpret an ambiguous benchmark description inconsistently, selecting instances by different cri-teria and producing an incoherent benchmark. For example, when collecting repair instances, one agent session includes style changes or feature implementations as “bugs”, while another accepts only changes that correct behavioral faults revealed by tests. Second, agents may construct instances that are difficult to reproduce. For example, an agent setting up an open-source project relies on preinstalled dependencies, producing an instance that works in its environment but fails on another machine. Finally, agents may expose different instances via different interfaces, even when instructed to use a common interface. For example, an agent’s run_tests.sh 

executes all tests for one instance but only the bug-exposing test for another. Hence, researchers cannot evaluate a technique reliably and uniformly across such instances. This paper presents BenchMeUp, an approach for con-structing software-engineering benchmarks from a researcher-arXiv:2610.37283v1 [cs.SE] 27 Oct 2026 written benchmark specification . The specification describes the task, desired instances, their sources, and how to use them to evaluate a technique. For example, a program-repair specification may request real-world bugs from open-source projects, each with a buggy program and a test exposing the bug. Researchers can specify project properties, such as language, development activity, and popularity, without knowing which repositories contain suitable instances. BenchMeUp constructs a benchmark from the specification in four phases. First, an LLM generates explicit search rules 

for finding and selecting candidates, followed by a shared 

construction plan defining the construction steps and expected artifacts. Second, LLM-based search agents autonomously find and record candidates satisfying the rules. Third, con-struction agents follow the plan to build instances from the recorded candidates; BenchMeUp validates the instances by replaying the generated scripts in a fresh environment. Finally, BenchMeUp packages completed instances behind a unified command-line interface. This design aims for consistent in-stance selection, reproducible outcomes in fresh environments, and a unified interface for evaluating techniques. We evaluate our approach on four software-engineering tasks: program repair, issue reproduction, compiler autotuning, and fixing static-analysis warnings. Requesting 50 instances per task, we obtain 198 constructed instances, of which 196 are successfully packaged. Search and construction average 36 minutes and $0.79 in LLM costs per instance. We evaluate eight existing techniques across the four tasks using the con-structed benchmarks. The techniques can set up and run 189 of the 196 packaged instances (96%), enabling comparisons on common instances. Successful execution, however, does not establish validity. Checking every constructed instance against its source, the specification, and its expected outcome, we find that 180 of 198 (91%) meet all criteria. Most remaining instances concern issue reproduction and fail the specifica-tion’s filters or expected outcome. Manual inspection of 40 instances also reveals six with defective check scripts. By comparison, only 10 of the 200 instances delivered for the same specifications by Codex [17], a general-purpose coding agent, meet all criteria. II. A PPROACH 

A. Problem Statement 

BenchMeUp takes as input a natural-language benchmark specification written by a researcher. The specification de-scribes the task to be evaluated, the required contents of each instance, the sources from which instances may be obtained, and the conditions under which a technique’s result is consid-ered correct. The researcher also specifies the benchmark size. Table I gives a simplified specification for program repair: each instance must provide a buggy Java program and a test that exposes the bug, and a repair technique must return a patch that makes the exposing test pass without introducing new test failures. We use program repair as a running example. BenchMeUp produces a benchmark package : a collection of instances and a common command-line interface through which evaluation code can use them. For program repair, an instance includes the versions and patches needed to reconstruct the buggy and fixed programs, an environment definition, and scripts to build and test them. Researchers can thus check out buggy versions, apply repair techniques, and invoke instance tests through a common interface. The goal is to construct such a benchmark for any task within a given budget, without requiring researchers to implement the collection and execution of instances. B. Overview 

Figure 1 gives an overview of how BenchMeUp constructs a benchmark package in four phases. In Phase 1, an LLM trans-lates the researcher-written specification into shared search rules that define where to search, which candidates to retain, and what information to record about them. In a separate query, an LLM generates, from the specification, a shared 

construction plan that defines the artifacts to produce, the stages to follow, and the checks to perform. In Phase 2, search agents use the search rules to search for and collect candidates from external data sources. For example, a candidate for program repair may consist of a repository, a fixing commit, and information about the changed program and test files. In Phase 3, construction agents follow the plan to construct instances from found candidates. After each stage of the plan, the framework (our backend code that coordinates the agents) runs the agent-generated scripts in a fresh container and compares their results against the expected outcomes (defined in the plan). We call this procedure replay . In Phase 4, the framework packages the completed instances behind a common command-line interface and verifies the packaged instances in fresh containers through this interface. Because searching for candidates and constructing instances can take hours, BenchMeUp runs multiple agents in paral-lel. Search agents share summaries of their exploration to reduce overlap, while construction agents work on different candidates and share summaries of problems and attempted solutions. Algorithm 1 presents the overall procedure, and Al-gorithm 2 describes agent scheduling and synchronization. We illustrate the four phases using the program-repair specification in Table I and a candidate found for that specification.

Judge approval only checks the formulation against the specification; it does not establish that the resulting criteria are objectively correct. 

2) Generating the Construction Plan: After the judge ac-cepts the search rules, the framework asks an LLM to generate the construction plan from the benchmark specification. The plan describes how to turn a candidate into a benchmark instance, including the steps to follow, the artifacts to produce, and the checks needed to verify the instance. It divides construction into stages, each with an objective and required artifacts. All construction agents follow the same plan, but each determines how to carry out its steps for the particular candidate it is working on.

The plan also goes through a review step. A second LLM judges the proposed plan against the specification and search rules, returning feedback when revisions are needed. The generating LLM revises and resubmits the plan until it is accepted or the feedback-iteration limit is reached. If the judge asks for information missing from both the specification and rules and the generator LLM cannot supply it, the framework asks the researcher to supplement the missing information. If the limit is reached, the framework returns the unapproved plan and the feedback to the researcher (Algorithm 1, lines 8– 14). The review process helps identify missing requirements and ambiguities in the construction plan before construction agents begin working on candidates. 

D. Phase 2: Finding Candidates 

Phase 2 uses the specification and the accepted search rules to assemble a pool of candidate records. The goal is to find plausible instances satisfying the search rules; the costlier creation of runnable instances waits until Phase 3. 

1) Searching with Agents: Search agents autonomously explore external data sources to find candidates that satisfy the search rules. Rather than following a predefined sequence of queries, each agent decides how to proceed based on the information it obtains during the search. It can write and execute scripts to query data sources, inspect the returned records, and investigate promising results further. For each potential candidate, the agent checks available information against the search rules’ selection conditions and records the required fields if suitable. The agent then continues exploring the data source to find additional candidates. 

Running example. When searching for program-repair in-stances, an agent may first query GitHub for Java repositories that meet the requirements on popularity, development history, and activity. It can then inspect their commit histories to identify potential bug fixes and examine the corresponding changes to program and test files. For commits that satisfy the selection conditions, it records the repository URL, fixing commit, and changed files, as specified in Table II. Search agents use a customized agent scaffold based on mini-swe-agent [16] and inspired by agents such as Execution-Agent [7]. Each search agent receives the original benchmark specification, search rules, and task-independent instructions on its tools, search procedure, and output format. 

2) Coordinating Search Agents: A single search agent may explore only a small portion of the available data sources before its time budget expires. BenchMeUp therefore runs multiple search agents in parallel. However, agents working independently may issue similar queries and repeatedly in-vestigate the same repositories or candidates. To reduce this overlap, the framework starts agents at fixed intervals and shares information about their search activities. The first agent starts alone. Before the next agent starts, an LLM summarizes the first agent’s search directions, including its queries, filters, and explored repositories. The next agent receives this summary and is instructed to explore different directions while following the same search rules. Each subse-quent agent similarly receives summaries of preceding agents’ exploration. Once all Nsearch agents are running, the frame-work periodically updates and distributes these summaries at intervals of synctime s, allowing agents to adjust their searches based on the exploration of others. The researcher sets the candidate target nsearch , search-agent count, start delay, synchronization interval, and search time budget. The number of agents is also constrained by available computing resources and service limits, since agents querying GitHub or Hugging Face, or using Docker, compete for shared resources. Algorithm 1 (lines 16 and 17) and Algorithm 2 describe this coordination procedure. 

3) Checking and Deduplicating Candidates: Before a can-didate joins the shared pool, its search agent must provide an existence-verification script. Each agent writes one such script for all of its candidates; scripts can differ because agents may use different data sources. The framework executes the script in a fresh container and checks recorded identities and fields against the source, detecting records such as nonexistent commit hashes. Only candidates that pass are recorded. Phase 2 ends when the shared pool reaches nsearch can-didates or the search time budget expires. The framework deduplicates the recorded pool before passing candidates to Phase 3 (Algorithm 1, line 19).

E. Phase 3: Turning Candidates into Instances 

A candidate record identifies promising source material, but it is not yet something a researcher can use to evaluate a technique. A bug-fixing commit, for example, contains a program fix and a test change. To make it a repair in-stance, BenchMeUp must reconstruct a buggy program that includes the exposing test but excludes the fix, provide a build environment and scripts, show that the test fails before repair and passes afterward, and provide a way to judge a submitted patch. Phase 3 performs this transformation for each candidate, producing instance-specific artifacts Ac and adding successfully constructed instances to a collection I.Construction agents follow the construction plan from Phase 1 to prepare instances from individual candidates. Since an instance may work in an agent’s environment but fail elsewhere, the framework replays the generated scripts in fresh containers to check that they produce the expected results. 

1) Constructing and Replaying Instances: Each construc-tion agent takes a candidate c and works through the plan’s stages in order. At each stage, the agent prepares the required artifacts, such as instance-specific metadata, environment con-figurations, and scripts (referred to as Ac in the algorithm), and then submits them to the framework for checking. Rather than relying on the agent’s reported results, the framework copies the instance files into a fresh container and runs the setup and checks specified by the plan. It compares the observed results with the expected outcomes and reports any failures to the construction agent. The agent can then revise its artifacts and submit the stage again. The framework also reruns checks from earlier stages to detect regressions caused by subsequent changes. The agent can proceed to the next stage only after all required checks of the current stage pass. 

Running example. For the SOS candidate, the construction agent identifies the added test as the exposing test and sepa-rates the fixing commit into test.patch , containing the test and changes needed to compile it, and fix.patch , containing the program repair. This allows the agent to prepare a buggy version that includes the exposing test without the fix. Replay then checks that the original tests pass on the parent commit, the exposing test fails on the buggy version, and the same test passes on the fixed version. The framework also checks that the generated scripts correctly evaluate the known fix and reject an empty patch. If a required check continues to fail after a researcher-set number of attempts, the framework drops the candidate and assigns the agent another candidate. A construction agent can also drop a candidate when it finds that the candidate does not satisfy the instance criteria; it then documents its evidence. If all stages pass, the framework adds (c, A c) to I for packaging (Algorithm 1, lines 28–36). The researcher sets a construction target nconstruction and time budget. Construction stops at the target, time limit, or candidate exhaustion. 

2) Coordinating Construction Agents: Constructing an in-stance can take considerable time because agents may need several attempts to configure dependencies, build projects, and pass replay checks. BenchMeUp therefore runs Nconstruction 

construction agents in parallel, each working on a different candidate. Although the agents work on separate candidates, they may encounter similar problems, such as missing de-pendencies or build failures. To help agents learn from one another’s experience, the framework periodically uses an LLM to summarize their trajectories, including problems encoun-tered, attempted solutions, and replay feedback. It shares these summaries with the construction agents as lessons L,helping them reuse successful solutions and avoid previously unsuccessful attempts. The researcher sets the synchronization interval synctime c.An agent’s context grows with every step it takes, which makes its later model calls more expensive and its mistakes more likely. The framework therefore runs construction agents in waves. Each agent works for a fixed time window, during which it can construct several candidates one after another. When the window ends, the framework replaces the agent with one prompted with the current lessons L and assigns it the next candidates. An agent that is in the last stage of an instance when its window ends gets a grace period to finish it. The researcher sets the window length and the grace period. Shared experience relates to prior agent-learning ap-proaches [18], [19], [20]; our summaries include replay feed-back from executing the agents’ scripts alongside the agents’ own accounts. Algorithm 1 (lines 21–22) and Algorithm 2 describe construction coordination.

For each completed instance, the framework copies Ac and retains the replay reports so users can inspect the checks per-formed during construction. It also writes a manifest mapping the plan’s common commands to that instance’s scripts and files. A shared command-line program reads the manifest and dispatches requests to the selected instance. Evaluation code can consequently obtain instance files, prepare a working tree, invoke tests, or perform other task-specific operations without knowing each instance’s internal script layout. Packaging can start upon instance delivery, alongside ongoing construction. 

Running example. Listing 2 illustrates the evaluation work-flow for SOS: check out the buggy parent, apply the exposing-test patch, build, apply the technique’s patch, and invoke the exposing tests and suite-wide checks. The scripts implement-ing these steps are specific to SOS, but the commands used to invoke them are those defined for the repair benchmark as a whole. Phase 4 enforces this consistency. Finally, the framework reruns the packaged interface in a fresh container built from the instance’s Dockerfile. This differs from staged replay in Phase 3: it checks the com-pleted instance as exposed through the package, not just the intermediate artifacts submitted during construction. 2) Models and Budgets: We use deepseek-v4-flash for con-struction by default and Claude Opus 5 for search, rules, and plan generation. B. RQ1: Effectiveness and Efficiency of BenchMeUp 

For each of the four tasks, we set a search target of 200 candidates and a construction target of 50 instances. To avoid waiting for the search to finish, BenchMeUp launches construction agents as soon as at least 50 candidates have been collected. Search and construction then proceed concurrently: search agents continue finding candidates while construction agents turn the available candidates into instances. Once 50 instances have been constructed for a task, the framework stops both phases, even if the search agents have not reached their target of 200 candidates. This stopping rule is a choice of our experiments; a researcher can let both phases continue. 

1) Effectiveness: Table III summarizes the effectiveness of benchmark construction. Across the four tasks, search agents found 639 unique candidates. Construction agents tried 332 candidates, constructing 198 instances and dropping 134. The program-repair, issue-reproduction, and compiler-autotuning benchmarks meet the target of 50 instances; the static-analysis benchmark reaches only 48 constructed instances within the time limit. Of the 198 constructed instances, 196 (99%) pass the final packaging checks. The 134 candidates dropped during construction fall into two categories. First, the construction agent decides that a candidate does not satisfy the instance criteria, contrary to the search agent’s initial assessment, and documents the sup-porting evidence. Second, the construction agent is unable to construct a valid instance from the candidate. The second cat-egory reflects, at least in part, limits of the construction model. As we discuss in Section IV, a stronger construction model completes construction faster and drops fewer candidates. During construction, replay helps to identify instances that fail outside of the agent’s container. Of the 198 constructed instances, 108 (55%) initially had at least one failed replay, totaling 170 failures. Most failures are due to builds relying on residual container state (82) or test scripts failing in the replay environment (47). BenchMeUp returns these failures to the construction agents for correction and accepts the instances only after successful replay in a fresh container. However, replay does not establish whether instance checks distinguish correct from incorrect inputs; RQ3 evaluates this. 

2) Time and Cost: Table III also reports the time and LLM cost, focusing on search and construction, as these are the most expensive steps. Across the four tasks, the average LLM cost is $0.79 per constructed instance, of which 64% is for search and 36% for construction. Search costs more because it uses the stronger model. Looking at time, the proportions reverse: search accounts for only 4–20% and construction for 80–96% of the total time. On average, an instance is found and constructed in 36 minutes.

Answering such questions requires examining individual instances in the context of their tasks. We therefore manually inspect a sample of 40 instances. For each task, we randomly select five instances solved by the best-performing technique from RQ2 and five instances it does not solve. We first check each instance against its upstream repository, verifying the specification criteria. We test interfaces with recorded inputs, such as the developer fix, and incorrect ones, e.g., random patches or empty submissions. In all 40 inspected instances, the basic commands handle our incorrect inputs correctly. For example, a patch that modifies a test to mark it as skipped leaves no failing test, so the check command accepts the patch, whereas the basic command for running tests reports that no test ran. These cases do not affect RQ2 (relies on basic commands), but researchers using the joint command need to check such details.

In the issue-reproduction instances without the expected outcome, the test of the issue is not fail-to-pass. IV. D ISCUSSION AND THREATS TO VALIDITY 

Execution in a fresh container. In BenchMeUp, the frame-work checks stage completion by replaying the agent’s scripts in a fresh container. This check is necessary: in 108 of 198 constructed instances, a stage that worked in the agent’s container failed in the fresh one, most often because abuild relied on something the agent had installed or left behind (Section III-B). Therefore, agent-based benchmark-construction approaches should re-execute every instance in a clean environment rather than trust the agent’s report. The instances’ execution environments can decay as base images, packages, and repositories change; however, users can preserve environments through container snapshots (e.g., DockerHub). Manually created specifications. The authors’ knowledge of the approach may have made their four specifications easier for it to process than specifications by other researchers. 

Choice of construction model. Our evaluation uses Claude Opus 5, which is stronger than deepseek-v4-flash, to generate search rules and construction plans and conduct searches, leaving repetitive plan execution to the weaker model. To investigate whether construction also benefits from a stronger model, we run Opus 5 on the same candidates for three tasks (excluding fixing static-analysis warnings for budget reasons). Opus 5 also delivers 50 instances per task at about $10 per instance, but takes only about 9 minutes per instance, compared with 25 for deepseek-v4-flash on the same tasks. Opus 5 constructs instances from 40 candidates that deepseek-v4-flash drops, reducing wasted candidates and time. Hence, a stronger model can help with challenging tasks where a weaker one delivers fewer instances. 

Limits of agent-generated checks. Replay guarantees that an instance reproduces the outcomes required by its checks. However, replay does not establish the correctness of these agent-written checks. Moreover, the checks reflect only the specification and the plan, i.e., they measure reproducibility and consistency with the plan, not faithful representation of the task. Before using a benchmark, we recommend inspecting sample instances, as in RQ3. 

Generalizability. We evaluate the approach on four tasks across three languages, using only GitHub data, with one specification and 50 requested instances per task. The approach is task-independent by design, but these results do not establish its effectiveness on tasks requiring other sources, such as non-GitHub issue trackers or app stores. V. R ELATED WORK

EnvBench [47] shows that this task remains hard: The best approach it evaluates configures only 6.69% of the Python and 29.47% of the JVM repositories. Task-construction techniques [9], [10], [11], [12], [13] build on such setups to generate or collect issue-resolution and vul-nerability tasks with executable environments at scale. CodeBenchGen [43] and AutoCodeBench [48] use LLMs to turn code into execution-based code-generation benchmarks. Our approach differs by collecting and preparing real-world software artifacts. SWE-Gym [49], R2E [50], R2E-Gym [51], and SWE-Synth [52] construct environments with executable tasks for issue resolu-tion or for training agents. Our approach covers more software-engineering tasks and derives construction procedures from researcher-written benchmark specifications. Studies of SWE-bench find solution leakage and weak tests [53] and show that a share of patches counted as correct fail the developers’ tests [54]. UTBoost [55] generates additional tests after the fact, and BenchGuard [56] audits existing benchmarks. Our correctness conditions and replay act at construction time; as Section IV discusses, the adequacy of an oracle remains the researcher’s judgment. VI. C ONCLUSION 

We present BenchMeUp, an approach that builds executable software-engineering benchmarks from a natural-language specification. Shared search rules and construction plans co-ordinate parallel agents, while replay checks their outputs in fresh containers before packaging instances behind a common interface. On four tasks, 180 of 198 constructed instances meet all criteria, compared with 10 of 200 for a general-purpose agent. We envision BenchMeUp as a useful tool for researchers who want to evaluate their techniques on new tasks, programming languages, or software versions without the overhead of manually constructing benchmarks.

## 摘要
编码智能体正迅速从单文件生成迈向长时程、仓库级工程，但评估其编写交互式扩展现实（XR）应用的能力仍是一个开放挑战。与传统软件不同，XR 应用运行于动态的三维物理环境中，其运行时鲁棒性共同取决于连续的用户运动、空间输入和环境感知。我们提出 GenXR-Bench，这是首个用于端到端评估编码智能体在 XR 软件开发中能力的基准。GenXR-Bench 包含 112 个由专家编写的任务，涵盖 24 个功能实现、21 个缺陷修复和 67 个应用生成任务。留出测试将脚本化交互与自适应交互同程序化断言和视觉断言相结合，以评估核心功能与运行时行为。在针对 124 个于消费级 XR 硬件上运行的候选应用的盲审专家判断中，GenXR-Bench 的测试套件达到 96.5% 的准确率。在 GenXR-Bench 上评估 10 个模型后，我们发现最强配置的总体 Pass@1 仅为 50.9%。失败分析发现，异步传感器生命周期、物理环境锚定以及具身交互语义方面存在反复出现的误解。GenXR-Bench 建立了一个可复现的测试平台，用于在空间计算的交互式和物理情境化条件下评估编码智能体。

## Abstract
Coding agents are rapidly advancing from single-file generation to long-horizon repository-scale engineering, yet the evaluation of their capabilities to author interactive extended reality (XR) applications remains an open challenge. Unlike traditional software, XR applications operate within dynamic 3D physical environments where runtime robustness depends jointly on continuous user motion, spatial input, and environmental sensing. We introduce GenXR-Bench, the first benchmark for the end-to-end evaluation of coding agents in XR software development. GenXR-Bench contains 112 expert-authored tasks spanning 24 feature implementations, 21 bug repairs, and 67 application generation tasks. Held-out tests combine scripted and adaptive interactions with programmatic and visual assertions to evaluate core functionality and runtime behavior. GenXR-Bench's testing suite achieves 96.5% accuracy against blinded expert judgments of 124 candidate applications executed on consumer XR hardware. Evaluating 10 models on GenXR-Bench, we find that the strongest configuration achieves only 50.9% overall Pass@1. Failure analysis identifies recurring misunderstandings in asynchronous sensor lifecycles, physical grounding, and embodied interaction semantics. GenXR-Bench establishes a reproducible testbed for evaluating coding agents in the interactive and physically situated conditions of spatial computing.

## 1. 核心问题与研究动机

- **背景**：编码智能体正从单文件代码生成迈向长时程、仓库级软件工程，但对其编写**交互式 XR 应用**能力的评估仍属空白。

- **现有评测的瓶颈**：
  - SWE-bench 等依赖程序化单元测试，无法验证空间场景图与连续 3D 追踪输入；

  - 3D 代码生成基准多关注静态形状，而非可响应软件；
  - 既有 XR 基准侧重硬件性能与运行时系统，而非生成式代码合成。
- **整体含义**：作者提出 **GenXR-Bench**，声称是首个面向 XR 软件开发的端到端编码智能体基准，并配套 **GenXR-Test** 自动化测试框架，试图建立可复现、贴近真机行为的空间计算智能体评测平台。

## 2. 方法论

### 2.1 核心思想
- 将 XR 开发拆为三类任务：**SDK 功能实现、SDK 缺陷修复、完整应用生成**。
- 所有任务基于开源 WebXR 框架 **XR Blocks 0.21.0**，以支持无头、可复现执行，规避 Unity/Unreal 等桌面引擎的 GUI 导航与多 GB 构建工具链。
- 每个任务包含：自然语言规格说明、可编辑项目脚手架、留出评估套件。

### 2.2 任务构建流程
- **SDK 任务**：
  - 访谈 XR Blocks 核心贡献者，检查截至 2026-08-24 的 **552 个 PR/issue**；
  - 按 XR 工程相关性、可评估性、范围筛选候选；
  - 功能任务：移除目标实现但保留公共接口与上下文；
  - 修复任务：在固定快照中复现缺陷，不指出故障位置；
  - 测试包含 fail-to-pass 与 pass-to-pass 两类，作者需构造对抗性解并经历三轮测试套件 refinement。
- **应用任务**：
  - 从 2016–2026 年顶级 HCI/空间计算 venue 的 **436 篇 XR 系统论文**构建五类应用分类法（医疗、教育、设计、日常生活、娱乐）；
  - 用 `gemini-3.5-flash` 生成 **1,000 个候选应用想法**，专家筛选出 **67 个**；
  - 用 `gemini-3.6-flash` 扩展为完整规格，专家人工审改；
  - 每个应用任务最多经历 **10 轮**规格与评估套件迭代，使用专家审核的有效解与对抗解进行校准。

### 2.3 GenXR-Test 评估框架
- **执行环境**：Chromium + Playwright + Vitest（或自定义 Vitest 扩展），每个测试会话在隔离工作区中复制文件、重链依赖、注入运行时读取器与动作控制器。
- **评估 Actor**：
  - **脚本化 Actor**：预定义动作序列（手势、按键、路径跟随），可复现性高；
  - **自适应 Actor**：VLM 驱动的受限自然语言指令执行器，用于布局/交互流不确定的场景。
- **评估断言**：
  - **程序化断言**：检查对象变换、空间关系、交互状态、碰撞、追踪状态、传感器输出、事件等；
  - **VLM 视觉断言**：针对难以程序化表达的视觉结果，提供渲染图像与窄范围人工准则，避免让 VLM 判断整体功能。
- **语义标签**：要求候选应用为指定对象打语义标签，使动作与断言能定位功能等价对象，而不强制单一实现。
- **模拟能力**：
  - 关节手部模拟（XYZ 关节旋转、正向运动学、姿态预设、关节限位）；
  - 物理环境模拟（Living Room / Office，平面、网格、深度、对象检测注入，导航网格）；
  - 模拟时间控制（显式等待、逐帧步进、暂停后运行 VLM 评估）；
  - 场景上下文格式化（层级对象树、稳定 ID、set-of-marks 截图），降低自适应 Actor 的 token 消耗。
- **设计评分**：对应用生成任务，录制评估器运行视频，用 VLM 按 **10 条 XR 设计启发式**各打 1–5 分，作为功能 Pass@1 的补充。

## 6. 主要结论与发现

- **最强配置总体 Pass@1 仅 50.9%**（`claude-opus-5`），XR 开发对前沿模型仍具挑战。
- **任务类型差异显著**：
  - SDK 修复普遍较高（最高 95.2%），说明行为修复与缺陷定位远易于端到端实现；
  - SDK 功能实现最低（最高 29.2%），UI 类任务尤其困难；
  - 应用生成最高 47.8%（`claude-opus-5`）。
- **功能与设计分离**：`claude-opus-5` 应用生成 Pass@1 最高，但 `gpt-5.6-sol` 设计分最高（4.03），在 10 条启发式中 9 条领先。
- **失败模式**：
  - **坐标变换错误**出现在 64.4% 的失败运行中，尤其是以手部等用户变换为父节点时；
  - **异步初始化/环境更新竞态**占 44.9%，如在资源或追踪状态就绪前启动游戏循环、仅在启动时检查平面；
  - **具身交互检测与可用性**问题占 34.5%，

- **具身交互检测与可用性**问题占 34.5%，典型表现为近距离手部交互未被正确判定、直接触摸与射线交互模式混用、抓取阈值与碰撞体尺寸不匹配，以及交互热区落在人体舒适范围之外；
- 上述三类失败往往相互叠加：一次运行可能同时出现坐标层级错误与初始化竞态，说明失败并非孤立 API 误用，而是对 XR 运行时"时间—空间—身体"三重耦合缺乏整体建模。

### 6.4 工具使用与开发行为

- 模型普遍呈现**"重探索、轻验证"**倾向：大量工具调用用于阅读源码与示例，而运行时测试（启动应用、驱动 Actor、观察渲染结果）占比偏低；
- 单元测试调用频次与 Pass@1 的相关性弱于运行时测试，提示在 XR 场景中"能通过自己写的单测"并不等于"应用在模拟器中真的可用"；
- 高分之举往往伴随更多**失败后回读日志、重跑评估**的迭代行为，而非一次性写出更长代码；
- 成本与性能并非单调关系：部分低价配置在 SDK 修复类任务上接近高价模型，但在应用生成与 UI 类功能实现上差距明显，说明**长时程空间推理**才是当前模型能力的主要分水岭。

### 6.5 评估框架本身的发现

- 自动套件与专家盲评在功能正确性上总体一致，flakiness 处于可接受范围，Fleiss’ κ 显示中等以上评分者间一致性，支持将该框架用于规模化评测；
- 但一致性在**视觉/布局类**任务上明显下降，说明程序化断言覆盖不到的"看起来对不对"仍是自动化评估的薄弱环节；
- 语义标签机制被证明是兼顾实现自由度与可评估性的关键设计：既允许模型采用不同对象命名与层级，又让动作与断言能稳定定位目标。

## 7. 局限与未来方向

- **单一框架偏置**：全部任务基于 XR Blocks 0.21.0（WebXR/JS 生态），结论能否迁移到 Unity、Unreal、Godot 或原生 OpenXR 栈尚不明确；WebXR 的无头可测性优势本身也可能改变任务难度分布。
- **模拟保真度**：关节手部、简化物理与两类室内环境无法覆盖真实世界的光照变化、遮挡、多人协同与复杂材质，可能同时低估"环境鲁棒性"难度与高估"渲染正确性"可测性。
- **评估粒度**：主实验采用单次 Pass@1，未报告 Pass@k 或多次采样的方差，对高方差模型的估计偏保守/不稳定；设计评分依赖 VLM judge，主观性强且与人类逐项一致性有限。
- **公平性缺口**：推理等级、token/时间预算、工具调用上限未完全统一，跨模型排名应谨慎解读；`claude-opus-5` 的 medium 配置可能压低其真实上限。
- **验证覆盖**：应用验证仅覆盖 62/67 个任务，排除了需特定物理对象或场景的用例；人类验证样本为 124 个候选，规模有限。
- **可扩展方向**（作者与读者可延伸）：引入多轮 Pass@k 与置信区间、扩展到多引擎与多人协同 XR、将设计启发式转为可程序化的部分代理指标、以及把"运行时测试频率"等行为信号纳入智能体训练或提示策略。

## 8. 总体评价与启示

- **贡献定位**：论文的核心价值不在"再刷一个榜"，而在于把 XR 软件开发中**难以用单元测试表达的时空与具身属性**转化为可复现的自动化评估流程（隔离工作区、脚本化/自适应 Actor、语义标签、模拟时间控制、VLM 视觉断言），这套方法论对机器人、游戏、仿真等同样"连续时空 + 渲染"的领域具有可迁移性。
- **能力诊断意义**：50.9% 的最强 Pass@1 与"修复易、实现难、UI 最难"的结构性差异，指出当前编码智能体的短板集中在**跨坐标系推理、异步生命周期管理、以用户身体为参照的交互设计**，而非代码语法或 API 记忆。
- **功能与设计可分离**：Pass@1 与设计分排名不一致，说明"能跑通"与"好用"是两个可独立优化的维度，未来基准应同时报告二者而非合并为单一分数。
- **实践建议**：对使用此类基准的读者，应关注分任务类型、分领域的细粒度结果与成本-性能曲线，而非总榜名次；对构建 XR 智能体的团队，优先补强运行时自验证循环（主动驱动 Actor、读日志、重跑评估）比扩大上下文更有效。
- **需保留的怀疑**：由于框架单一、推理配置不齐与单次采样，本文应被视为**能力画像与评估基础设施**，而非模型能力的最终排序。

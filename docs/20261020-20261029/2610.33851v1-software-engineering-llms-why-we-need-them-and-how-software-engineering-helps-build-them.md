## 摘要
软件工程（SE）专业知识可以影响编码大语言模型（LLM）的训练方式以及它们所获得的工程能力。我们通过一个面向能力训练的工业案例研究来考察这一作用，该案例针对一个服务超过10万名开发者的920亿参数编码LLM。我们展示了成熟的SE知识如何指导工程能力的选择、可验证训练数据的构建以及模型改进的评估。为了针对仓库级重构，我们开发了RefactorForge，这是一个结合重构知识、成熟的SE工具和验证技术来构建训练数据的流水线。在306个Python仓库上，RefactorForge生成了5,704个可执行任务，并保留了4,572条经过验证的教师轨迹，总计7,251万个token。在这些轨迹上进行增量监督微调，其所用token仅占先前编码混合数据token的0.46%，使RefactorBench性能提升18.00个百分点，SWE-Bench ProMax性能提升7.06分。在OpenCode下，这些改进扩展到SWE问题解决，在SWE-Bench Verified上提升4.97分，在SWE-Bench Pro上提升1.23分。这些改进在其他编码智能体测试框架中也持续存在，而全新仓库生成则表现出参差不齐的结果。我们报告了在构建面向能力的训练数据以及评估其在各类工程工作负载中的效果方面所获得的经验教训。基于这一工业经验，我们提出一个研究议程，以扩展SE在将编码LLM转变为SE LLM中的作用：将SE知识纳入模型训练，将工程方法应用于模型开发与维护，并系统性地定义这些模型应具备的工程能力。

## Abstract
Software engineering (SE) expertise can shape how coding large language models (LLMs) are trained and which engineering capabilities they acquire. We examine this role through an industrial case study of capability-focused training for a 92B-parameter coding LLM serving more than 100,000 developers. We demonstrate how established SE knowledge can guide the selection of engineering capabilities, the construction of verifiable training data, and the evaluation of model improvements. To target repository-level refactoring, we developed RefactorForge, a pipeline that combines refactoring knowledge, established SE tools, and verification techniques to construct training data. Across 306 Python repositories, RefactorForge generated 5,704 executable tasks and retained 4,572 verified teacher trajectories totaling 72.51 million tokens. Incremental supervised fine-tuning on these trajectories, accounting for 0.46% of the preceding coding mixture's tokens, improved RefactorBench performance by 18.00 percentage points and SWE-Bench ProMax performance by 7.06 points. Under OpenCode, these improvements extended to SWE issue resolution, with gains of 4.97 points on SWE-Bench Verified and 1.23 points on SWE-Bench Pro. Improvements also persisted across other coding-agent harnesses, while greenfield repository generation showed mixed results. We report lessons from constructing capability-focused training data and evaluating its effects across engineering workloads. Building on this industrial experience, we propose a research agenda for expanding SE's role in transforming coding LLMs into SE LLMs: incorporating SE knowledge into model training, applying engineering methods to model development and maintenance, and systematically defining the engineering capabilities these models should acquire.

## 1. 核心问题与整体含义

- **背景**：编码 LLM 与编码智能体已大规模进入工业实践（Google 称 75% 新代码由 AI 生成；前沿模型在 SWE-Bench Verified 上超过 96%），但“会写代码/能过基准”不等于具备软件工程能力。
- **核心问题**：编码 LLM 在仓库级、多文件、需保持行为不变的重构操作上表现不均。作者实测 GPT-5.2 与 GLM-5.1 在 RefactorBench 上总体成功率为 62% 与 51%，但两者在 Extract Class 上全部失败，GPT-5.2 在 Move Class、Introduce Parameter Object 上也全部失败。
- **三重挑战**：

  - **C2 迁移不确定**：面向基准的收益未必迁移到其他编码任务。
  - **C3 框架依赖**：训练轨迹编码了特定 agent harness 的约定，换框架后收益可能减弱甚至反转。
- **整体含义**：提出“能力导向训练”（capability-focused training）假设——强化一项基础工程能力，可带动依赖它的相关任务与工作流；并主张 SE 知识不应只用于评估或防护，而应直接参与“写训练数据这个程序”，推动 coding LLM 走向 SE LLM。

## 2. 方法论

### 2.1 核心思想

- 以**仓库级重构**为首个能力载体（涉及代码定位、依赖推理、协同修改、行为保持）。
- 用成熟 SE 知识决定：**训练什么能力、什么算正确答案、如何独立验证**。
- 构建 **RefactorForge**：12 步、4 阶段的流水线，从真实 Python 仓库生成“可执行任务 + 已验证教师轨迹”，再做增量 SFT。

### 2.2 重构类型选择

- 选取 **Rename、Move、Remove** 三族共 7 类：Rename Function / Class / Constant / Attribute、Move Function、Remove Unused Function、Remove Unused Import。
- 依据：开发者高频实践、已有工具可执行、结构性质可检查；其中 Rename 类占生成任务的 **96.4%**。

### 2.3 四阶段流程（文字化算法）

- **Phase I：可复现环境构建**
  - 从 PyPI 选活跃项目，映射 release→tag→commit 固定版本。
  - 从包元数据、依赖组、requirements、tox 配置生成 Dockerfile。
  - 先做确定性修复与缓存复用，失败才让 GLM 5.3 提出有限修复建议（不得执行 shell、改项目代码或测试命令），每项目限 6 次构建/收集、2 轮依赖修复、7 次 LLM 修复。
  - 验收条件：安装成功、测试收集无错、至少 1 个通过测试、无失败/错误；冻结 recipe 并回放验证；通过的测试构成后续 **P2P 回归套件**。
- **Phase II：参考重构构造**
  - 用 PyCharm 程序分析 API 判定符号资格与全仓引用；Ruff 诊断未使用 import。
  - LLM 仅生成“有界参数”（如语义保持的新标识符），并由确定性过滤器检查：非原名、合法标识符、非关键字、下划线类别不变、符合 PEP 8（snake_case / CapWords / UPPER_SNAKE_CASE）。
  - Move Function 依据“目标模块已有 ≥2 次使用且多于源模块”的启发式选目标，避免命名冲突。
  - 由 PyCharm/Ruff 实际施加变换生成 patch；再做结构检查 + 重跑 Phase I 全部通过测试，全部通过才接受。
- **Phase III：可验证任务构造**
  - 用 GLM 5.3 依据重构类型、符号元数据与参考 patch 生成 **Lazy 风格**任务指令（点明符号、隐去文件路径与 patch 内容），并做元数据一致性校验。
  - 从参考变换派生**结构化 F2P 测试**（检查新旧名称、定义位置、引用、import、`__all__` 等），要求在原始仓库失败、打 patch 后通过；同时复用项目测试作为 P2P。
  - 导出为 Harbor 可执行任务（固定版本、Docker、安装流程、指令、F2P/P2P）。
- **Phase IV：教师轨迹筛选**
  - 教师模型 GLM 5.3 通过 OpenCode 执行任务，不可见参考解与隐藏测试；最终解须同时通过 F2P 与 P2P。
  - 再做轨迹质量过滤（对话结构、重复、乱码、非英文、受限词等），仅保留合格轨迹用于学生模型 SFT。

### 2.4 训练方式

- 在既有 92B 编码模型（Baseline-92B）上做**增量监督微调（SFT）**，得到 Refact-92B；训练数据为 4,572 条轨迹、72.51M tokens，仅占前序代码相关混合数据（938,180 条轨迹、15.66B tokens）的 **0.46%**。
- 训练配置：6 个 epoch、83 次迭代、12 个节点、batch size 48、最大序列长度 128K。

## 6. 主要结论与发现

- **C1 目标能力显著提升**：RefactorBench 43.00%→61.00%（**+18.00 pp**，显著）；SWE-Bench ProMax 51.18%→58.24%（**+7.06 pp**），且训练数据全为 Python，却在 7 语言 ProMax 上有效。
- **能力内部泛化**：13 个重构类别中 7 类提升、11 类有成功；Introduce Parameter Object 从 0% 升至 75%；成功率低于 50% 的类别由 7 个降至 5 个，性能更均衡。
- **C2 正向迁移**：SWE-Bench Verified 62.00%→66.97%（**+4.97 pp**），SWE-Bench Pro 48.97%→50.20%（**+1.23 pp**）。
- **C2 负向/混合迁移**：NL2Repo-Bench 在 Claude Code（+1.94）与 OpenHands（+2.88）上升，但在 Mini-SWE-Agent（−3.45）与 OpenCode（−2.84）上下降，说明 greenfield 能力未被训练覆盖。
- **代码质量探索**：在 111 对可比 patch 上，Refact-92B 引入 54 个 smell，Baseline 为 58 个，少 **6.9%**。
- **C3 跨 harness 稳健**：8/8 组合均提升；SWE-Bench Pro 提升 1.23–6.57 pp，Verified 提升 1.91–7.10 pp；最大增益出现在**未参与数据采集**的 Claude Code（Pro +6.57）与 Mini-SWE-Agent（Verified +7.10），说明收益并非仅来自对采集 harness 的熟悉。
- **先导实验结论**：仅靠工具引导的 agent 重构在固定预算下收益有限且不均（3/5 运行预算耗尽，Code Health 绝对提升仅 0.10–0.50 分，最高 Dateutil 1.76 分但终值仍低），从而转向“训练模型底层能力”。
- **经验教训**：
  - L1 数据构建每阶段都有损耗（729→306→5,704→4,889→4,572），需预留资源。
  - L2 能力覆盖受可验证性约束；Extract Class 因“哪些成员应被抽取”属设计判断，无法用结构检查与现有测试验证，故无法生成训练任务。
  - L3 模型更新需回归门禁（greenfield 回退即为证据）。
  - L4 必须在实际使用的多个 harness 上评估。

- **未讨论安全与回退机制**：大规模自动重构在工业部署中的审批、回滚、增量验证流程未涉及。

## 9. 启发与可迁移之处

- **“把 SE 知识编译进数据生成程序”**是可复用的一般思路：先用程序分析确定“什么是合法变换”，再用回归测试确定“什么是不破坏行为”，LLM 只负责它擅长的有界子问题（命名、指令表述）。这一分工可迁移到依赖升级、API 弃用替换、日志/遥测注入、类型注解补全等任务。
- **F2P 与 P2P 分离**的双测试设计值得推广：结构断言确保“变换确实发生”，回归套件确保“行为未变”，二者缺一都会产生虚假训练信号。
- **增量 SFT + 小比例高质量数据**是工业后训练的现实路径：在已有强底座上做能力补丁，比从头训练更符合成本约束。
- **跨 harness 评估应成为默认要求**：本文最大增益出现在未参与数据采集的框架上，这一发现本身提示——若只在采集框架上评估，会系统性低估或误判收益来源。
- **负迁移必须被报告**：greenfield 回退说明能力补丁可能挤压其他能力，提示需要建立“回归门禁”式的模型发布流程。

## 10. 值得追问的问题

1. 若把 rename 占比从 96.4% 降到更均衡的配比，RefactorBench 的增益是否仍成立？增益究竟来自“重构能力”还是“大规模同构模式的强化”？
2. 教师轨迹的成功是否依赖 GLM 5.3 的特定行为风格？换教师后学生收益如何变化？
3. 在 Extract Class 这类不可自动验证的操作上，能否用“人类抽样审核 + 弱验证”构造小规模高质量数据，从而突破可验证性边界？
4. SWE-Bench Verified +4.97 pp 中，有多少来自“更敢做跨文件修改”，多少来自“更少引入回归”？需要轨迹级归因分析。
5. NL2Repo 的 harness 依赖反转，是 harness 的工具集差异，还是模型行为（探索广度/编辑粒度）与 harness 约束的交互？这直接关系到“能力导向训练”能否声称框架无关。
6. 训练数据与评测仓库的重叠度是多少？在去污染后增益还剩多少？
7. 该方法在 7B 级模型上是否同样有效，还是需要底座已具备足够的仓库级理解能力才成立？

## 11. 总体评价

本文的核心贡献不在“又提升了一个 benchmark 分数”，而在于提出并初步验证了一条方法论路径：**让软件工程知识从评估端前移到数据生产端**，用程序分析与回归测试为训练信号提供确定性锚点，从而在极小数据比例下获得可测量的能力提升，并在跨语言、跨框架条件下观察到一定稳健性。其可验证性设计、统计方法与负结果披露均高于同类工业报告的平均水准。

但其证据强度仍属“单点强、外推弱”：一个模型、一个能力域、一个数据比例、一个教师模型，且缺少消融、缩放与去污染分析。因此更恰当的定位是**一个有说服力的存在性证明（proof of concept）与一套可复用的工程流水线**，而非“能力导向训练”范式的确立。若要支撑更强的主张，后续工作至少需要：多能力域并行验证、数据量与配比的缩放曲线、跨模型规模复现、以及公开可审计的去污染流程。

对工业实践的即时启示是：在已有强底座上，用“确定性变换 + 回归验证 + 教师轨迹 + 增量 SFT”做能力补丁是性价比很高的路径；但必须配套多 harness 评估与跨能力回归门禁，否则容易在提升目标能力的同时静默损害未被覆盖的能力。

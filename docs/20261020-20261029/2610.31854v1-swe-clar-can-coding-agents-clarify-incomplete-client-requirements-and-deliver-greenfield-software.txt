## ABSTRACT 

Greenfield software development in freelance settings requires coding agents to turn incomplete client requests into working software. This makes requirement clarification essential, yet clients may be unable to provide continuous feed-back over long development cycles, and receiving their answers does not guar-antee correct understanding of complex requirements. These challenges motivate two benchmark design choices: clarification precedes code implementation, and its effectiveness is assessed through explicit tests of requirement understanding. Guided by these choices, we introduce SWE-Clar, a benchmark grounded in real, high-value client commissions to evaluate requirement clarification and code im-plementation in this setting. It comprises 100 tasks based on real software devel-opment jobs on Upwork, each with at least US$4,000 in total payments. Each task begins with multi-round interaction between a coding agent and a client agent, followed by separate runs for code implementation with acceptance testing and clarification assessment. For the latter, we construct 512 questions paired with reference answers from real client–freelancer interactions, covering both explic-itly stated requirements and those inferred from the conversational context. Both runs begin from the same clarification context but remain isolated, preventing as-sessment questions from guiding code implementation. Experiments with nine frontier models show that even GPT-6 Astra, which has the highest observed im-plementation score, achieves a task pass rate of only 67%, underscoring the chal-lenge of independent software delivery in this setting. The dataset and evaluation code are available at https://github.com/upwork/SWE-Clar .

## 1 INTRODUCTION 

As large language models (LLMs) improve at coding and reasoning, coding agents are expanding from generating simple code snippets (Chen et al., 2021) to tackling complex software engineering tasks (Yang et al., 2024). These advances create opportunities to automate software development services and deliver business value (Peng et al., 2023; Miserendino et al., 2025; Yi et al., 2025; Mazeika et al., 2025), particularly in greenfield software development, which involves building new software from scratch rather than modifying existing codebases (Ding et al., 2025; Shi et al., 2026). On freelance platforms such as Upwork 1, agents could act as freelancers to undertake high-value client commissions (Figure 1). However, these commissions typically begin with requests that leave critical functional and interface requirements unspecified (Nuseibeh & Easterbrook, 2000), so cod-ing agents must proactively seek clarification through client interaction (Mu et al., 2024). Recent work has extended coding-agent evaluation beyond code implementation to include require-ment clarification, enabling coding agents to interact with client agents to recover missing require-ments (Wu & Fard, 2025; Fang et al., 2026; Vijayvargiya et al., 2026; Peng et al., 2026; Wu et al., 2026; Raghavendra et al., 2026; King & Flanigan, 2026). However, these benchmarks primarily fo-cus on tasks derived from programming datasets and software repositories, leaving the demands of greenfield software development in freelance settings insufficiently represented. Our observations of real commissions for such greenfield software development projects highlight two characteris-tics, illustrated in Figure 1. First, building complete software projects from scratch often entails a prolonged development process, making continuous client feedback during code implementation difficult to sustain. Second, these projects involve multiple complex requirements that freelancers may not fully understand even after receiving answers to their questions. Consequently, benchmarks that assume continuous client feedback (Wu et al., 2026; Raghavendra et al., 2026) and assess clari-fication primarily through information acquisition (Fang et al., 2026; Vijayvargiya et al., 2026; Peng et al., 2026; Trinh et al., 2026) may not adequately assess coding agents’ ability to fulfill these commissions independently. These characteristics motivate two design principles for conducting and evaluating requirement clar-ification. First, clarification should precede code implementation: the coding agent should complete its interaction with the client agent before implementing the software without further guidance. Sec-ond, clarification should be assessed using multiple requirement questions paired with reference answers. The coding agent’s responses should be scored against these reference answers to assess requirement understanding rather than information acquisition alone. This assessment should re-main separate from code implementation to avoid providing additional implementation guidance. Guided by these design choices, we introduce SWE-Clar , a benchmark of 100 greenfield soft-ware development tasks based on real software development jobs on Upwork, each with at least US$4,000 in total payments. For each task, a coding agent first engages in multi-round requirement clarification with a client agent. The resulting context then initializes two independent branches: one performs code implementation followed by acceptance testing, while the other evaluates clarifi-cation by scoring the coding agent’s answers to requirement questions. To construct these questions, we use GPT-6 Astra to analyze recorded interactions between real clients and freelancers and iden-tify requirements critical to successful software delivery, including those explicitly stated and those inferred from the broader conversational context. These requirements form the basis of 512 ques-tions paired with reference answers, averaging approximately five per task. Together, these designs establish SWE-Clar as a benchmark grounded in real, high-value client commissions to evaluate requirement clarification and code implementation for greenfield software development in freelance settings. ## 2 SWE-C LAR : B ENCHMARK DESIGN 

In this section, we introduce SWE-Clar, then describe requirement clarification and the two inde-pendent evaluation branches. We subsequently explain how the tasks and evaluation materials are constructed, and examine the dataset and its differences from representative benchmarks. 2.1 OVERVIEW 

We aim to evaluate requirement clarification and code implementation for greenfield software devel-opment in freelance settings. A coding agent must both understand what a client wants and deliver software that meets those requirements. Following the design principles in Section 1, SWE-Clar therefore places client interaction before code implementation and assesses the agent’s understand-ing separately from the software it produces. Figure 2 shows the resulting workflow. Each task begins with an incomplete request for new soft-ware and a development workspace. A coding agent acts as the freelancer, while a separate client agent simulates the customer and answers from the complete requirements. The coding agent asks questions until it is ready to proceed. Its clarification context then initializes two independent runs: one implements the software and is scored through acceptance tests; the other answers requirement questions and is scored against reference answers. These runs yield the implementation score and clarification score, respectively, without further client guidance. The tasks are based on real software development jobs on Upwork, as detailed in Section 2.4. 2.2 REQUIREMENT CLARIFICATION 

The clarification phase determines what information the coding agent will have when it starts devel-opment. The agent inspects the supplied materials and asks the client agent about unclear or missing requirements. Its instructions explicitly require clarification of critical delivery details, such as how the software should be invoked and its expected inputs and outputs. The client agent responds us-ing the complete requirements, confirming or correcting the agent’s proposed interpretations and answering broader questions within their requested scope. Because client replies guide both subsequent evaluations, we check them before they reach the cod-ing agent. A supervisor agent reviews each draft for accuracy, completeness relative to the question, and whether it stays within the requested scope. When a draft needs revision, the supervisor explains the problem to the client agent, which revises the reply and submits it for review again. Only the approved reply reaches the coding agent; drafts and review feedback remain hidden. The coding agent uses each approved reply to decide what to inspect or ask next, or whether to end clarification. One round consists of a question and its approved reply, regardless of the number of internal revisions. The agent may inspect the workspace during this phase but must wait until clarification ends to implement the software. This gives it multiple opportunities to resolve missing details early, while requiring subsequent development to proceed without further client guidance. 3Preprint. Under review. Both evaluations should start from the information available when clarification ends. However, an evaluation question may itself reveal a missing requirement; asking it in the same run before implementation could therefore change the software the agent produces. We avoid this by freezing the clarification context—the initial request, approved conversation, and information obtained from inspecting the workspace—and using it to start two independent runs. Their later messages and results remain separate, preventing assessment questions from guiding code implementation. 

Implementation score. The first run tests whether the coding agent can turn the information it ac-quired into working software. The agent edits files, runs its own checks, and submits the implemen-tation without access to further client replies, private acceptance tests, or reference implementations. Acceptance tests then run the submitted software and check its behavior. A task receives 1 if all tests pass and 0 otherwise. The implementation score is the percentage of tasks that pass, equivalent to task pass rate, and serves as our primary outcome. 

Clarification score. The second run tests whether the coding agent can correctly explain the re-quested behavior. The agent answers requirement questions using the same clarification context and read-only task materials. It cannot execute commands, modify files, ask further client questions, or see reference answers. A judge agent compares its answers with the reference answers, without using the implementation’s test results. Correct answers establish all material requested behavior without unresolved material contradictions and receive 1. Partial answers establish substantive cor-rect behavior but leave a material omission or uncertainty, without an explicit material contradiction, and receive 0.5. Incorrect answers contain a material contradiction or provide no substantive correct answer and receive 0. Equivalent wording and correct inferences are accepted. The clarification score (%) averages question scores within each task, then equally across tasks. These scores separate the agent’s ability to explain the requirements from its ability to implement them. For additional analysis, we also link each question to acceptance checks for the same re-quirement. Appendix B.3 defines these requirement units (RUs), the auxiliary RU pass rate, and the answer-grading rubric. Table 3 in Appendix B.1 summarizes information access and permitted actions; Appendix F provides the role prompts. 2.4 BENCHMARK CONSTRUCTION 

The workflow requires tasks for which the initial request is incomplete but the intended software can still be specified and tested. We construct 100 such tasks based on real software development jobs on Upwork, each with at least US$4,000 in total payments. For each commission, GPT-6 Astra analyzes the initial request and recorded client–freelancer conversations to identify requirements critical to delivery, including explicit statements and requirements inferred from context. We preserve the 4Preprint. Under review. original business goal while replacing dependencies on client accounts and external deployment, allowing local development and evaluation. Appendix A details the task construction process. The requirements identified in this process determine what the client agent knows. The coding agent receives an incomplete initial request and a workspace containing permitted files, data, and the runtime environment. These materials provide partial requirement information, not a complete checklist; the agent clarifies remaining details through inspection and client interaction. The com-plete requirements remain private and guide client replies, keeping the task fixed throughout the interaction. The same requirements also provide the basis for both evaluations. We construct 512 questions paired with reference answers, covering the required behavior and its relevant conditions and excep-tions. Separately, acceptance tests check whether the delivered software satisfies those requirements. For the illustrative commission in Figure 1, a question could ask which cancellations qualify for a refund, while tests would check the program’s handling of approved and unapproved cancellations. The question checks the agent’s understanding; the tests check the software’s behavior. Running the same tests on different implementations requires agreed delivery interfaces: how to invoke the software, what inputs it accepts, and what outputs it produces. We fix these interfaces together with the questions, reference answers, and tests before evaluation. The coding agent obtains the necessary interface details from the task materials and client interaction, while remaining free to choose the internal implementation. Two reviewers with relevant industry backgrounds cross-checked the tasks for consistency among client requirements, requirement questions, and acceptance tests. 2.5 DATASET ANALYSIS AND DISCUSSION

Comparison with existing benchmarks. Table 1 distinguishes SWE-Clar’s task setting and eval-uation from representative benchmarks. SWE-Lancer already evaluates paid freelance work, but its coding tasks modify an existing codebase without client clarification (Miserendino et al., 2025). ClarifyCodeBench and Ambig-SWE study clarification for programming problems and repository issues (Fang et al., 2026; Vijayvargiya et al., 2026), while ICAE-Bench extends interaction to from-scratch repository generation (Peng et al., 2026). SWE-Together and SWE-Interact assess develop-ment with continued user feedback and report interaction or goal-coverage diagnostics (Wu et al., 2026; Raghavendra et al., 2026). SWE-Clar instead focuses on independently completing real, high-value greenfield commissions after early client interaction. Across models, code-test pass rates are 33.9–68.4% for incorrect answers, compared with 86.3–91.3% for correct answers and 73.0–88.2% for partial answers. Correct answers have higher pass rates than partial answers in all nine models. Answer correctness is therefore associated with implementation success, while the two measurements capture different aspects of task performance. 

Requirement answers and code tests provide complementary evidence. The model-level cor-relation does not imply agreement on individual requirements: correct answers with failing imple-mentations account for 6.1–7.8% of all 512 RUs per model. Partial answers establish substantive 8Preprint. Under review. correct behavior but leave a material omission or uncertainty without an explicit material contra-diction. An unstated detail need not be absent from the code. For example, in the filtering case in Appendix C.5.1, the answer omits the required empty-result behavior when no items match, but the implementation passes the corresponding test, which includes this case. ## 4 RELATED WORK 

Software Development Benchmarks. Coding benchmarks have expanded from generating indi-vidual functions to completing software engineering tasks. HumanEval evaluates generated func-tions with executable tests (Chen et al., 2021), while SWE-bench asks agents to resolve GitHub issues in existing repositories (Jimenez et al., 2024). SWE-Lancer further connects evaluation to paid freelance work through Upwork tasks from the Expensify codebase and their historical pay-outs (Miserendino et al., 2025). Another line of work evaluates complete repository generation: De-vEval supplies product requirements and software designs, while NL2Repo-Bench provides natural-language specifications and evaluates generated repositories against upstream tests (Li et al., 2025; Ding et al., 2025). These benchmarks establish the importance of evaluating working software in re-alistic settings. SWE-Clar focuses on greenfield software development in freelance settings, where agents must build new software from incomplete client requests. Its tasks preserve real business goals and require clarification before independent delivery. 

Requirement Clarification. Incomplete requests require agents to determine what information is missing and obtain it before making consequential implementation choices. ClarifyGPT identi-fies ambiguous requirements and asks targeted questions to refine them before code generation (Mu et al., 2024). At the programming-problem level, HumanEvalComm and ClarifyCodeBench evaluate whether models ask useful clarification questions, with ClarifyCodeBench additionally measuring interaction efficiency (Wu & Fard, 2025; Fang et al., 2026). At the repository level, Ambig-SWE ex-amines how agents recover information omitted from issue descriptions (Vijayvargiya et al., 2026). ICAE-Bench extends interactive evaluation to from-scratch repository generation, deriving incom-plete requirements and grounded replies from open-source projects (Peng et al., 2026). SWE-Clar studies clarification in tasks based on real software development jobs on Upwork. Agents clarify requirements through multiple exchanges, then implement the software without further client guid-ance. 

Interaction and Process Evaluation. Evaluating interactive agents involves both the user simu-lation and the evidence used to assess performance. τ -bench combines simulated users with tool-using agents and checks task outcomes against the resulting environment state (Yao et al., 2025). In coding, SWE-Together builds tasks from real user sessions and measures repository correctness and user correction, while its intent-coverage metric assesses the simulator’s fidelity to the original user requests (Wu et al., 2026). SWE-Interact provides feedback during development and examines goal coverage in plans and code revisions (Raghavendra et al., 2026). SWE-RPG uses validated requirement and planning references to assess coding trajectories and attribute failures to require-ment, planning, or coding stages (Zhou et al., 2026). These approaches show the value of examining more than the final code outcome. SWE-Clar obtains explicit evidence of requirement understanding through a separate question-answering run after clarification. ## 5 CONCLUSION 

In this work, we introduced SWE-Clar , a benchmark for requirement clarification and code im-plementation in greenfield software development in freelance settings. Based on real, high-value software development jobs on Upwork, its tasks require coding agents to clarify incomplete re-quests before independently developing software. We paired acceptance testing with a separate requirement-question assessment, yielding implementation and clarification scores without allow-ing assessment questions to guide coding. Evaluations of nine frontier models showed that complete delivery remains challenging. Comparisons across requirement conditions further showed that clar-ification improves performance but recovers only part of the gap to complete requirements, while model-level score correlations coexist with requirement-level answer–code disagreements, demon-strating the complementary information provided by the two evaluations. Future work can extend SWE-Clar to changing requirements and different patterns of client avail-ability, and investigate how coding agents can clarify client needs more effectively and carry them through to reliable software delivery. ## A TASK CONSTRUCTION 

Section 2.4 describes task construction. This appendix adds details on material handling and the analysis of requirement disclosure in source conversations. We first identify 122 candidate jobs with at least eight milestones, at least US$4,000 in total pay-ments, and at least 20 messages. We select 100 jobs that can be reproduced locally, can avoid dependencies on external client accounts, and have deliverables suitable for evaluation through ac-ceptance tests. Design-oriented tasks that are difficult to evaluate objectively are excluded. The monetary threshold refers to total payments for the source job. GPT-6 Astra first processes the source materials. Two reviewers with relevant industry backgrounds then cross-check the tasks for consistency among client requirements, requirement questions, and acceptance tests. GPT-6 Astra and human contributors jointly develop the acceptance tests and refer-ence implementations. All reference implementations pass every acceptance test for their respective tasks. The supplied starter projects provide structure and, in some tasks, runnable baseline functionality; agents must complete the required target behavior. Greenfield refers to the new software projects underlying the tasks, rather than an empty starting directory. None of the 512 RUs across the 100 tasks passes its corresponding acceptance tests in the initial state, giving a starter RU pass rate of 0%. Local workspaces use synthetic records and controlled services in place of original client accounts and deployment environments, allowing the agent to develop the required software locally. The re-lease contains the curated benchmark tasks and evaluation harness, not original client conversations or identifying information. We further check the acceptance tests using behaviorally equivalent implementations and targeted incorrect implementations. Across the 100 tasks, both reference and equivalent implementations pass all acceptance tests, while an incorrect implementation targeting one requirement per task is rejected by the corresponding RU tests. These checks verify acceptance of correct alternative imple-mentations and detection of the tested requirement violations. The released repository includes the three implementation variants for every task, the requirement targeted by each incorrect implemen-tation, and file hashes for integrity checks. ## D CLARIFICATION TIMING 

Should clarification be completed before coding or continue during development? We compare two workflows using GPT-5.6 Luna and GLM-5.3 Flash on the same 100 tasks per model, with the same scoring rubric as the main comparison. 

Clarification before coding follows the standard protocol: the coding agent inspects materials and asks the client questions, autonomously ends clarification, and then implements from the frozen clarification context without further client interaction. Continued clarification allows the agent to alternate between questions and coding, retaining existing code while obtaining further requirements during development. One possible explanation is that newly acquired information during continued clarification may re-peatedly change the agent’s earlier understanding and decisions. When client replies, prior assump-tions, and code revisions are interleaved during development, the agent may confuse superseded as-sumptions with current requirements and struggle to maintain a coherent understanding. The lower final clarification scores for both models provide indirect support for this hypothesis: additional opportunities for interaction do not automatically yield more accurate requirement understanding; effectively integrating evolving information also matters. These results motivate improving how interleaved agents integrate new information into both their requirement understanding and existing code. Agents could check that critical requirements are clear before coding and explicitly update requirement records, implementation plans, and relevant checks when later clarification changes an assumption. Such coordination can help turn continued interaction into consistent software behavior.

## 摘要
编码智能体可能在仓库探索和测试上投入大量精力，却仍生成不成功的补丁。现有的在线引导方法会定期审查轨迹，或在监控器检测到行为问题时调用顾问；频繁审查成本高昂，而未出现异常行为并不意味着智能体走在正确轨道上。我们提出 PAUSE，一个通过单次规划干预来引导编码智能体的框架。智能体通常在轨迹进度中位数达到 60% 时，才在完成探索、缺陷复现和测试后到达首次源代码编辑。PAUSE 在该编辑请求执行前将其拦截，这不需要学习得到的监控器、不需要在检查点上进行搜索，也不需要额外模型调用（无搜索）。一个独立的 Planner 读取任务和编辑前记录，并编写一份修复计划；同一智能体即 Executor 带着该计划继续，同时保留其上下文和工作区。PAUSE 既可在线应用于实时运行中，也可离线应用于已记录的轨迹前缀。我们在 SWE-bench Verified 和 SWE-bench Multilingual 上，使用两个 Executor 和三个智能体框架评估 PAUSE。以 Qwen3-coder 作为 Executor、GPT-5.6 Sol 作为 Planner 时，在线引导在 OpenHands 的 Verified 上使解决率提升 16.8%，在 SWE-agent 的 Multilingual 上提升 14.7%。在 SWE-agent 中，PAUSE 在 Planner 成本相近的情况下，比规则触发的顾问 LivePlan 在 Verified 上高 3.2%、在 Multilingual 上高 3.7%，并且与 SICA 的周期性监督者相当，而 Planner 成本约为后者的 11-15%。离线时，PAUSE 恢复了 35.4% 的符合条件的失败 Verified 任务，并且从记录的前缀继续执行比重新启动少用 33-41% 的 Executor token。

## Abstract
Coding agents can invest substantial effort in repository exploration and testing yet still produce unsuccessful patches. Existing online steering methods review trajectories periodically or invoke an advisor when a monitor detects behavioral problems; frequent reviews are costly, and the absence of anomalous behavior does not mean that an agent is on the right track. We propose PAUSE, a framework for steering coding agents with a single planning intervention. Agents reach their first source-code edit at a median of 60% of trajectory progress, after exploration, bug reproduction, and testing. PAUSE intercepts this edit request before it executes, which requires no learned monitor, no search over checkpoints, and no extra model call (search-free). A separate Planner reads the task and the pre-edit transcript and writes one repair plan; the same agent, the Executor, resumes with this plan, keeping its context and workspace. PAUSE applies online, during a live run, and offline, from a recorded trajectory prefix. We evaluate PAUSE on SWE-bench Verified and SWE-bench Multilingual with two Executors and three agent harnesses. With Qwen3-coder as Executor and GPT-5.6 Sol as Planner, online steering improves resolution by 16.8% on Verified in OpenHands and by 14.7% on Multilingual in SWE-agent. In SWE-agent, PAUSE outperforms LivePlan, a rule-triggered advisor, by 3.2% on Verified and 3.7% on Multilingual at similar Planner cost, and is comparable to SICA's periodic overseer at about 11-15% of its Planner cost. Offline, PAUSE recovers 35.4% of eligible failed Verified tasks, and resuming from the recorded prefix uses 33-41% fewer Executor tokens than restarting.

## 1. 核心问题与整体含义

- **研究背景**：基于 LLM 的编码智能体在仓库级缺陷修复中，会进行大量代码阅读、缺陷复现、命令执行与测试，但仍经常产出错误补丁。问题不只是“探索不足”，而是智能体难以把已有调查证据转化为正确的修复策略。
- **现有在线引导的痛点**：
  - 周期性模型审查（如 SWE-PRM、SICA）按固定步数或时间间隔评估轨迹，成本高；间隔过长又会延迟反馈。
  - 规则触发式顾问（如 LivePlan）通过重复、停滞、跳过阶段等异常信号触发干预，监控成本较低，但覆盖有限；**没有异常信号并不代表修复方向正确**。
  - 现有方法通常需要学习监控器、搜索干预检查点，或额外调用模型来决定“何时干预”。
- **关键观察**：在 500 条 Qwen3-coder 的 SWE-bench Verified 轨迹中，首次源代码编辑的中位位置为轨迹动作进度的 **60.0%**，80.5% 发生在中点之后；此前主要是仓库探索、复现与测试。此时证据已较充分，而拟议修改尚未执行，仍可被修正。
- **整体含义**：PAUSE 将“首次源代码编辑”作为确定性的干预时机，在编辑执行前插入一次修复计划，使同一 Executor 带着已有上下文和工作区继续执行。该方法同时支持**在线引导**和**离线失败轨迹恢复**，主张以一次规划干预替代频繁审查或异常触发顾问。

## 2. 方法论

### 2.1 核心思想

- 不学习监控器，不搜索候选检查点，不额外调用模型来定位干预点；仅根据“动作类型 + 目标路径”判断首次源代码编辑，因此称为 **search-free**。
- 在首次源代码编辑请求执行前将其拦截，由独立 **Planner** 读取任务描述和编辑前轨迹，生成一份自然语言修复计划；同一 **Executor** 保留完整对话、工作区、模型、工具与解码设置，继续执行。
- 计划只是建议，不自动执行被拦截的编辑；Executor 可修改方案或重新提出编辑。

### 2.2 关键技术细节

- **源代码编辑判定**：
  - 预先固定仓库源代码路径集合 \(\Pi\)。
  - 谓词 \(q(a)=\) “\(a\) 是文件编辑器请求”且“目标路径 \(\pi(a)\in\Pi\)”。
  - 首次源代码编辑 \(k^*=\min\{t:q(a_t)\}\)。
  - 该判定只依赖动作类型和目标路径，可在编辑执行前完成，无需模型调用或未来观察。
- **在线引导流程**：
  1. 逐步检查 Executor 提议的动作；
  2. 首次命中 \(q(a)\) 时阻止该编辑；
  3. 用已完成历史 \(h_{k^*-1}\) 构造规划输入，排除待执行编辑请求、其负载及附带推理；
  4. Planner 无工具、无工作区访问，输出计划 \(g=P(d,\phi(h_{k^*-1}))\)，其中 \(\phi\) 将记录证据渲染为文本并省略编辑动作；
  5. 将计划作为 user message 追加到同一 Executor 对话；
  6. 关闭拦截器，后续按框架原生预算继续。
- **离线恢复流程**：
  1. 从失败轨迹中找到首次源代码编辑 \(k^*\)；
  2. 选择其之前最后一个 think 动作 \(c=\max\{t<k^*:a_t\text{ 是 think}\}\)；
  3. 恢复对话 \(h_c\)、工作区 \(W_c\) 和 harness 迭代计数 \(b_c\)，预算变为 \(B-b_c\)；
  4. 通过在新容器中重放前缀动作恢复工作区，保留复现脚本等调查产物；
  5. 进行保真检查，比较恢复后的对话、仓库状态和计数器；
  6. Planner 基于 \(h_{c-1}\) 生成计划并插入，同一 Executor 从恢复状态继续；
  7. 若轨迹无首次源代码编辑或无前置 think，或恢复失败，则标记为不合格。
- **与现有方法的关键区别**：
  - 不依赖行为异常信号；
  - 不做重复轨迹审查；
  - 不搜索“最佳干预点”；
  - 一次运行最多干预一次；
  - 计划生成与执行角色分离，但执行模型不变。

## 3. 实验设计

- **数据集 / Benchmark**：
  - **SWE-bench Verified**：500 个 Python 仓库级修复任务；
  - **SWE-bench Multilingual**：300 个任务，覆盖 9 种编程语言。
- **Executor**：
  - Qwen3-Coder-30B-A3B-Instruct（简称 Qwen3-coder）；
  - Devstral-Small-2507（简称 Devstral-small）。
- **Planner**：
  - GPT-5.6 Sol、Gemini 3.8 Flash、Gemini 3.5 Flash Lite、Qwen3-30B-A3B-Thinking-2507、Qwen3-coder 自身。
- **Agent Harness**：
  - OpenHands、SWE-agent、Pi。
- **主要对比方法**：
  - 未修改的 Executor 作为 baseline；
  - 在线：**LivePlan**（规则监控触发顾问）、**SICA overseer**（周期性轨迹审查）；
  - 离线：**SHERLOC**（诊断定位后修复）、无计划继续、自反思继续、不同 Planner 的计划、resume 与 restart 对比；
  - 时机消融：动作进度 20% 切点、首次编辑前立即切点、90% 切点、后续源代码编辑切点、PAUSE 默认检查点。
- **评价指标**：
  - 解决率（resolution）；
  - 恢复任务数与恢复率（Recovered / recovery rate）；
  - 回归率；
  - Planner / Executor token 数；
  - Planner 推理成本（按每百万输入/输出 token 2.50/10 美元计）；
  - 配对 exact McNemar 检验。
- **实验组织**：
  - RQ1：在线引导有效性与成本，全量 500 + 300 任务；
  - RQ2：离线恢复，223 个 Qwen3-coder 合格失败 + 174 个 Devstral-small 合格失败，另做 500 任务全基准评估；
  - RQ3：跨 3 个 harness 的泛化，500 个 Verified 任务，并测试去除 think 内容；
  - RQ4：干预边界有效性，包括 donor guidance、不同暂停位置、后续编辑检查点。

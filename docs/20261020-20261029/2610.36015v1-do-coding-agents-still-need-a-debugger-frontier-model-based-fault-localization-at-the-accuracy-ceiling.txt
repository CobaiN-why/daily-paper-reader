Abstract —Background: To localize a fault, a coding agent can reason from source code alone or use debugger assistance by running the program and stepping through it in an interactive debugger. While earlier agents struggled with static execution tracing and debugger operation, frontier LLMs have improved at both. Objective: We evaluate how accurately coding agents local-ize faults without tools across original and transformed programs, how much debugger assistance improves accuracy and at what cost, and how agents use it when optional. Methods: We seed 610 single-line faults into 144 LeetCodeDataset solutions and rewrite each faulty program with five recipes of behavior-preserving transformations. Agents based on Sol 6.1, Luna 6, and Qwen 3.8 localize each fault with no, optional, or encouraged debugger assistance. Results: Without tools, the agents localized 98.2 to 99.9% of faults in original and 96.7 to 99.9% in transformed programs, losing accuracy mainly where recipes restructured loops and conditions. Encouraged assistance removed 63% and 61% of Luna 6’s and Qwen 3.8’s remaining transformed errors (+2.1 and +1.3 percentage points) at 14.7 to 27.0 times the token use, while Sol 6.1 stayed at 99.9%. With optional assistance, Luna 6 and Qwen 3.8 still gained +1.5 and +1.3 points, though the agents used the interactive debugger in only 0.2 to 6.2% of runs. Conclusions: On short, precisely specified programs, current coding agents localize nearly all faults from source code alone, and debugger assistance removes most errors that remain. Given the choice, agents executed the program far more often than they stepped through it, yet kept most of the benefit. 

Index Terms —agentic software engineering, fault localization, large language models, debugging arXiv:2610.36015v1 [cs.SE] 26 Oct 2026 I. I NTRODUCTION 

Fault localization is central to debugging, requiring a de-veloper or coding agent to identify where a program deviates from its intended behavior [1], [2], [3]. Rather than reasoning about execution from source code alone, a coding agent can use debugger assistance by running the program and stepping through it in an interactive debugger. Earlier large language models (LLMs) struggled to trace execution statically, pre-dicting 46 to 81% of outputs on 3-to-13-line Python functions in CRUXEval [4], [5]. Debugging systems therefore supplied runtime evidence through recorded traces [6], [7] or interactive debuggers [8], [9], [10], [11]. Yet operating a stateful debugger proved difficult for earlier agents, and direct pdb access often lowered their repair rates [9], [10]. Recent reasoning models have changed both sides of this trade-off: pdb improved their repair success in debug-gym [9], while on CRUXEval they predict 93 to 98% of outputs from source code alone [12]. On obfuscated LeetCode bugs, optional probes and debugging raised Qwen 3.6’s repair accuracy from 78.0% to 94.8%, whereas GPT-5.4 moved only from 91.3% to 91.7% [13]. This rapid progress in model capabilities raises three ques-tions: how accurately the latest generation of frontier models localize faults from source code alone, how sensitive that accuracy is to behavior-preserving transformations, and how much debugger assistance still improves outcomes on top of static reasoning. However, three gaps in prior evaluations leave these questions open. First, most agentic debugging studies measure end-to-end program repair [7], [9], [10], [11], which confounds fault localization with patch generation because correct patches can arise from imprecise locations [14] and plausible patches can overfit to tests [15], [16], [17]. Second, high static accuracy on public benchmarks can reflect training-data exposure [18], [19]. Behavior-preserving source transfor-mations reduce verbatim overlap with pretraining corpora [20] and caused earlier static LLM localizers to miss 78% of the faults they had localized in untransformed programs [21], but prior work has not measured how much such transformations still affect frontier models or whether debugger assistance recovers any lost accuracy. Third, prior studies either enforce fixed runtime instrumentation [7], [22] or evaluate a single combined tool loop [9], [10], [13], without separating encour-aged from optional tool use, comparing the costs of both [23], [24], or tracking whether agents given a choice step through the program in the debugger or simply run it. We address all three gaps in a controlled experiment on self-contained algorithmic programs, the regime that originally motivated runtime feedback [4], [6], [7]. From 150 LeetCode-Dataset problems [25], each with a problem description, a ver-ified Python reference program , and an executable test suite, we seed 610 single-line faults across five fault types (Fig. 1). We rewrite each reference and faulty program with five fixed recipes of behavior-preserving transformations, ranging from variable renaming and dead-code distractors to restructuring loops and conditions (3,022 transformed programs, Fig. 2). Agents driven by Sol 6.1, Luna 6, and Qwen 3.8 then localize each fault across 65,376 agent runs ( episodes ) in three tool-use settings: no-tools (problem description and source code alone), discretionary-tools (adding

From source code alone, all three agents approached the accuracy ceiling, localizing 98.2 to 99.9% of faults in untrans-formed programs and 96.7% (Luna 6), 97.9% (Qwen 3.8), and 99.9% (Sol 6.1) in transformed programs. Variable re-naming and distractor insertion barely changed static accuracy, whereas restructuring loops and wrapping conditions in double negations lowered it by up to 3.8 percentage points in a single recipe, where most new errors blamed doubly negated con-ditions. Encouraging debugger assistance raised transformed accuracy to 98.8% for Luna 6 (+2.1 points, removing 63% of its remaining errors) and 99.2% for Qwen 3.8 (+1.3 points, removing 61%), with positive effects across every recipe and fault type, while Sol 6.1 stayed at 99.9%. Under discretionary-tools, they took debugger actions in only 0.2 to 6.2% of episodes on transformed programs (against 41.7 to 100.0% when encouraged) and instead ran execution probes or answered from source code alone. Even so, Luna 6 and Qwen 3.8 gained +1.5 and +1.3 points over no-tools, and Qwen 3.8 ran more probes on the faults where debugger assistance helped most. Encouraging debugger use added only +0.0 to +0.6 points over optional access. In this evaluation, coding agents rarely needed debugger assistance, and when given the choice, they obtained most of its benefit by running the program rather than stepping through it. a) LLM-based fault localization: Most LLM-based fault localization pipelines use fixed execution rules to filter can-didates before the model reads the code. AutoFL lets an LLM retrieve the classes and methods covered by failing tests on Defects4J and BugsInPy [27], FlexFL narrows candidate methods with traditional spectrum-based and information-retrieval rankings before an LLM inspects their source [28], and SieveFL combines failing-test coverage with semantic similarity to prune 79% of candidate methods and 49% of input tokens at unchanged Top-1 accuracy [29]. SemLoc localizes faulty lines by running instrumented code as afixed pipeline step to check model-inferred semantic con-straints [22]. In PingFL, the agent inserts print statements into suspicious methods and reruns failing tests [30]. Apart from SemLoc, these approaches rank methods rather than lines or statements, and none compares lightweight script execution against interactive breakpoint stepping. 

b) Source transformations and benchmark familiarity: 

Benchmark designers counter training-data exposure by select-ing problems released after model training cutoffs, as in De-bugBench [31] and LiveCodeBench [32], or by rewriting ex-isting benchmarks. Rewrites either apply behavior-preserving code transformations, as in CodeCleaner [20], or wrap the same algorithms in new problem contexts, as in DyCodeE-val [33]. Even after surface rewrites, semantic overlap with pretraining data can remain and raise benchmark scores [34]. Prior studies also use behavior-preserving transformations to test the robustness of static fault localization, program repair, and code reasoning. Haroon et al. evaluate line-level localization by ten models given only the source code and specification across 750,013 fault-localization tasks [21]. Li et al. transform 438 single-function Defects4J bugs and observe 49% fewer correct patches, with many edits targeting in-serted dead code or rewritten predicates [35], and HEJ-Robust observes its largest Java repair drops after local variable renaming [36]. Conversely, variable renaming can raise output-prediction accuracy on LiveCodeBench [37] and refactoring can improve code completion [38]. On 16 bootstrap-filtered LeetCode programs, Daxerer finds that combined structural-lexical obfuscation lowers judge-approved bug fixing much more for Qwen 3.6 than for GPT-5.4 and that optional runtime tools recover Qwen 3.6’s performance [13]. Whereas prior work evaluates static predictions or repair proposals under a single setup, we isolate fault localization on matched pairs across five transformation recipes and three tool-use settings. 

c) Runtime evidence in LLM-based debugging: Debug-ging pipelines supply LLMs with runtime information at different levels of agent control. Fixed pipelines execute the program outside the model’s control and append the resulting outputs or traces to the prompt: Self-Debugging feeds back unit-test results alongside model-generated code explanations [6], and LDB instruments basic-block bound-aries to record intermediate variable values before the model refines a generated program [7]. Agentic systems let the model issue debugger commands directly, but must guard against invalid commands and verbose outputs. ChatDBG lets GPT-4 query pdb , lldb , or gdb to explain crashes and propose fixes [8]. In debug-gym, exposing pdb on SWE-bench-Lite lowered repair rates for GPT-4o and GPT-4o-mini but improved them for reasoning models such as o1-preview, o3-mini, and Claude 3.7 Sonnet [9]. InspectCoder interposes a state-tracking middleware between the agent and 

pdb on BigCodeBench and LiveCodeBench, where direct pdb 

interaction without the middleware lowered repair success from 67.9% to 25.7% [10]. DebugHarness combines gdb ,deterministic replay, and script-based output distillation to patch C and C++ vulnerabilities [11]. These studies evaluate end-to-end repair or explanation quality under a single tool configuration, whereas we isolate fault localization and com-pare no, optional, and encouraged debugger assistance across original and transformed programs. A. Localization Cases a) Source programs: We draw reference programs from LeetCodeDataset [25], which pairs LeetCode problems with natural-language descriptions, verified Python reference so-lutions, and executable tests. Self-contained algorithmic pro-grams, which prior runtime-debugging and transformation studies also evaluate [7], [21], [31], provide the dense test suites needed to verify behavior preservation and identical test failures across transformations. We sample from the dataset’s training split, which contains problems released be-fore July 2024 according to the authors’ estimates and is intended for training code models [25], drawing 50 reference programs at random from each of the Easy, Medium, and Hard difficulty groups (150 in total, Table I). 

b) Fault seeding: From each reference program P , we derive up to five faulty programs M , one per fault type. Each fault is a single edit to one expression on one line. Off-by-one changes a numeric literal by one, and wrong arithmetic 

replaces an arithmetic operator. Wrong logic swaps and and 

or , changes a comparison operator, flips a Boolean literal, or adds or removes a negation. Wrong variable replaces a variable with another variable in scope, and static return replaces a returned expression with a constant such as 0 or None .Except for wrong variable, these fault types adapt mutation operators from PIT [39], [40]. Wrong variable corresponds to the changed-identifier pattern that Kamienski et al. report among single-statement bugs in Python projects [41]. For each reference program and fault type, we apply a randomly chosen edit of that type that fails at least one test and record the edited line L, or skip the fault type if no candidate edit qualifies. 

c) Transformations: We rewrite every faulty program with five fixed recipes, each consisting of an ordered sequence of behavior-preserving operations. Rename replaces variable names with single letters. State and literals routes attribute access through getattr calls, rewrites numeric and Boolean literals as equivalent expressions, and splits expressions into intermediate assignments. Control flow converts for loops into explicit iterator loops, expands conditions with double negations, inserts dead code, and splits expressions. Dis-tractors wraps statements in opaque predicates that always evaluate to true, inserts dead code and generic comments such as # WARNING: do not modify , and splits expressions. 

Maximal mix chains 14 steps of these operations and addi-tionally extracts statement blocks into helper functions and constructs strings from character codes. Fig. 2 illustrates the State and literals recipe applied to a faulty program. Prior studies use similar operations to evaluate fault localization [21] and program repair [35] on rewritten code, to test whether LLMs reason about program semantics [37], [42], and to reduce overlap with training corpora [20], [43]. 

d) Admission: We apply each recipe to P and M alike to obtain P ′ and M ′, track the mutated expression to identify its new line L′ in M ′, and admit (M, M ′) as a matched pair only if P ′ passes all tests, M ′ fails on the exact same test assertion as M , and restoring the original expression at L′ causes M ′

to pass all tests. On the dataset’s test suites, which have a median of 99 assertions per problem, these checks verify that the recipe preserves tested behavior, that the fault causes the same failure, and that line L′ holds the fault. Table I characterizes the constructed programs using non-empty lines of code including comments (LOC), McCabe’s cyclomatic complexity (CC) [44], and the share of untrans-formed four-token sequences preserved after transformation (Kept), adapting CodeCleaner’s n-gram overlap ratio [20]. In total, admission retained 144 of 150 reference programs, 610 of 750 seeded faults (104 to 141 per fault type), and 3,022 of 3,050 transformed programs. Admitted reference programs have median LOC of 8, 11, and 19 and median CC of 3, 4, and 8 across Easy, Medium, and Hard. Across recipes, median changes ranged from +0% (Rename) to +450% (Maximal mix) in LOC and +0 to +11 (Distractors) in CC, while median Kept ranged from 37% (Maximal mix) to 71% (Distractors).

b) Tool-use settings: Each setting adds one element to the previous one. In no-tools, report_bug is the only available tool, so the agent must localize the fault from the problem description and source code alone. Discretionary-tools adds tools to execute and debug the program along with their documentation. Using run_probe , the agent can execute a custom Python script, for example one that invokes the target method on chosen inputs, and observe its output and any raised exception. The agent can also launch such a script in an interactive debugger, set breakpoints on program lines, and step into, over, or out of function calls. Whenever execution pauses, the agent can inspect local variables, the call stack, program output, and the values of arbitrary Python expressions. Encouraged-tools provides the same toolset and appends a two-sentence instruction directing the agent to gather runtime evidence before deciding (Listing 1). 

c) Prompt design: Aside from the appended instruction in encouraged-tools, the prompt text is identical across all settings, avoiding prompt-wording variations that can alter LLM performance [45], [46]. The prompts specify the task and required output format without prescribing a debugging strategy, leaving tool selection to the model. A 100-episode pilot run verified that the agents invoked the tools and called 

report_bug as specified. Following reporting guidelines for LLM studies [47], [48], our replication package [26] provides the tool descriptions and full prompts. 

d) Models and limits: We evaluate Sol 6.1, Luna 6, and Qwen 3.8, running two independent episodes per model, case, and setting. Sol 6.1 and Luna 6 are accessed through OpenAI’s Responses API under the identifiers gpt-6.1-sol 

and gpt-6-luna at the provider’s default reasoning effort (medium). Qwen 3.8 runs from its 27-billion-parameter FP8 checkpoint ( Qwen/Qwen3.8-27B-FP8 ) on our own vLLM server with thinking enabled at the model’s default reasoning effort (xhigh). All models use default sampling parameters. We collected all episodes between October 6 and 14, 2026. Each untransformed case is evaluated once and shared across its matched pairs (65,376 episodes in total). An episode terminates when the agent calls report_bug . If an agent responds without calling any tool or reaches 50 tool rounds, where a round is one model response and its requested tool calls, it receives one final prompt requiring a report_bug 

call. Across conditions, at most 0.3% of episodes needed this fallback, and at most 0.1% ended without an answer. 

C. Measurements a) Localization: We grade each reported line under two criteria. Statement-level grading accepts any line belonging to the faulty statement, which a transformation recipe can split across multiple lines, as in lines 6 to 8 of Fig. 2. Recipes split the faulty statement in 47% of transformed cases. Line-level grading accepts only the exact line holding the mutated expression ( L or L′). We measure Top-1 accuracy as the share of episodes that successfully localize the fault, counting episodes without an answer as unsuccessful. 

b) Tool use and cost: Beyond report_bug , agents can invoke two categories of runtime tools. Probe runs execute agent-written scripts through run_probe without the debug-ger. Debugger actions encompass all calls that start or stop a debug session, manage breakpoints, step through execution, or inspect the paused program state. For every episode, we record total tokens, wall-clock time, and monetary cost at the providers’ list prices as of October 7, 2026, accounting for cached-input rates. For self-hosted Qwen 3.8, we estimate monetary cost from DeepInfra’s list prices [49].

c) Uncertainty: We report 95% percentile confidence intervals from a nonparametric cluster bootstrap with 2,000 resamples [50]. Because cases derived from the same refer-ence program share its problem specification and underlying algorithm, their outcomes are likely correlated, and treat-ing them as independent observations can understate uncer-tainty [51]. Each bootstrap resample therefore draws whole reference programs with replacement, stratified by difficulty group, and retains all associated cases and episodes, capturing both program-level sampling variation and episode-to-episode variance within each case [50]. Every resample recomputes all summary statistics, tool-use ranks, and RQ3 regressions. Under discretionary-tools, tool invocations can be concen-trated in a small number of reference programs. A bootstrap resample that draws none of those programs leaves β1 unde-fined, and computing an interval from the remaining resamples is invalid [52]. Because the number of clusters with tool use required for valid inference depends on the empirical distribution [53], [54], we validate each β1 interval using 1,000 cluster-level placebo datasets [55]. Each placebo dataset keeps localization outcomes fixed and reassigns observed tool use within each difficulty group to randomly selected reference programs from the same group in proportion to their case counts, making tool use independent of the assistance effect within each group. We report the confidence interval for β1

only if β1 is defined in all 2,000 bootstrap resamples and the share of the 1,000 placebo intervals that miss the mean placebo slope is not significantly above 5% under a one-sided exact binomial test at the 5% level. Otherwise, Table V marks 

β1 with a dagger ( †) or shows a dash when fewer than two reference programs have such tool use. IV. R ESULTS 

A. RQ1: Static Localization and Transformation Sensitivity 

Without tools, all three agents operated near the accuracy ceiling, localizing 98.2% (Luna 6), 98.8% (Qwen 3.8), and 99.9% (Sol 6.1) of faults in untransformed programs, and 96.7%, 97.9%, and 99.9% in transformed programs (Table II). Behavior-preserving transformations changed overall static accuracy by G = −1.5 [ −2.3, −0.6] percentage points for Luna 6 and −0.9 [ −1.6, −0.1] points for Qwen 3.8, while Sol 6.1 remained unchanged ( G = +0.0 [ −0.1, +0.0] points). Across the five fault types, untransformed no-tools accuracy was lowest on off-by-one (96.4% for Luna 6 and 97.2% for Qwen 3.8) and wrong-logic faults (97.7% and 97.2%, Fig. 3). D. Robustness 

To test sensitivity to our grading criterion, we re-evaluated all episodes under line-level grading, which accepts only the tracked line L′ holding the edited expression rather than any line of a split faulty statement, such as lines 7 and 8 in Fig. 2 (Section III-C). Naming another line of a split faulty statement accounted for 7.3% of Luna 6’s no-tools answers on transformed programs and 0.1% of Sol 6.1’s. Line-level grading lowered no-tools accuracy on transformed programs to 89.4% for Luna 6 and 96.4% for Qwen 3.8 ( G = −8.8 and −2.3 points), raising their ∆′ estimates to +3.4 and +1.8 points and I to +2.6 [+1.6, +3.6] and +1.5 [+0.6, +2.3] points. To check whether answers accepted only by statement-level grading diagnosed the seeded fault, we conducted a blinded, LLM-assisted audit (verified by an author) of 45 such answers per model across the three settings (which for Sol 6.1 were all of them) alongside 20 line-level successes per model. The agent’s explanation identified the seeded fault in 133 of the 135 statement-only answers and in 59 of the 60 line-level successes, showing that statement-only answers diagnosed the fault as often as line-level successes did. V. D ISCUSSION 

a) Fault localization at the accuracy ceiling: Without tools, the three agents localized 98.2 to 99.9% of faults in untransformed and 96.7 to 99.9% in transformed programs, and neither replacing most four-token sequences in Rename nor quadrupling line count in Distractors lowered static accu-racy by more than 1.0 percentage point (Section IV-A). This contrasts with earlier evaluations in which models without runtime feedback left substantial shares of faulty programs unrepaired [7], [31] and static localizers lost 78% of previously localized faults after behavior-preserving transformations [21]. Three differences in Haroon et al.’s setup may account for their larger losses: their metric conditions on solving the original program, their programs average 250 lines, and most of their models date from March 2025. Meanwhile, unlike earlier agents whose repair rates dropped under direct pdb 

access or unfiltered output [9], [10], encouraged debugger use never caused an accuracy collapse. Even when Luna 6 and Sol 6.1 used the interactive debugger in 100.0% of transformed episodes, forced-answer and no-answer rates stayed at or below 0.3% and 0.1%, Sol 6.1 remained at 99.9%, and Luna 6 and Qwen 3.8 removed 63% and 61% of their remaining errors. With structured tool interfaces and current reasoning models, the main limitation of debugger assistance on short, well-specified programs is no longer tool reliability, but that static reasoning already solves nearly every case. 

b) Syntactic rewrites versus familiarity: The static ac-curacy loss from transformation did not follow how much surface code a recipe changed. Without tools, Rename did not lower accuracy despite preserving only 40% of four-token sequences, whereas Control flow and Maximal mix lowered accuracy by 2.1 to 3.8 points, with 71.4% (Luna 6) and 68.2% (Qwen 3.8) of their new errors naming a doubly negated condition (Section IV-A). Because our wrong-logic faults add or remove a negation and the prompt states that the program contains one injected bug, a static reader can mistake a doubly negated condition for the seeded fault, much as LLMs fail code-equivalence checks under simple syntactic rewrites [56], [57] and follow misleading comments [12], [58]. Running the program shows that the condition evaluates as intended, which explains why both tool-enabled settings closed almost the entire accuracy gap between representations. Before attributing an accuracy drop on transformed code to reduced training-data familiarity, benchmark designers should therefore check whether new errors cluster on specific syntactic constructs. 

c) Program execution versus interactive stepping: When debugger assistance was optional, the agents obtained most of its accuracy benefit while rarely invoking the interactive debugger. Instructing agents to use the tools raised the share of transformed episodes with a debugger action from 0.2 to 6.2% up to 41.7 to 100.0%, but raised accuracy by only +0.6 points for Luna 6 and +0.0 points for Qwen 3.8 (Section IV-C). On short programs, running run_probe on chosen inputs appears to supply most of the runtime evidence, paralleling the gains from print debugging in PingFL [30]. In an exploratory post-hoc split of transformed discretionary-tools episodes, probe-only runs accounted for +1.1 of Qwen 3.8’s +1.3-point gain and +0.7 of Luna 6’s +1.5 points, with no-tool runs contributing another +0.7 points for Luna 6. Because agents choose tools in response to the fault and earlier outputs, con-ditioning on realized tool use mixes tool effects with selection bias, and extra model turns can also aid accuracy [23]. Iso-lating program execution from interactive debugging therefore requires a dedicated execution-only setting. 

d) Cost-effectiveness and model selection: Across mod-els and settings, how often an agent invoked tools did not match how much accuracy it gained from them (Tables II to V). Sol 6.1 ran probes in 98.4% of its discretionary episodes on transformed programs even though it already localized 99.9% of the faults without tools, consistent with reports that LLMs call tools when internal knowledge suffices [24]. Conversely, Luna 6 called no tool in 87.9% of its discre-tionary episodes yet retained +1.5 of its +2.1-point gain at 3.3 thousand tokens per episode versus 55.0 thousand under encouraged-tools. Qwen 3.8 matched its encouraged accuracy (+1.3 points) at roughly half the tokens (38.3 versus 73.5 thou-sand) while running more probes on the faults where assistance helped more. Moreover, Sol 6.1 without tools (99.9% accuracy, 5.2 s, 3.41 US dollars per 1,000 transformed episodes) was both more accurate and faster than Luna 6 or Qwen 3.8 with encouraged debugging (98.8% in 47.0 s and 99.2% in 350.4 s). For agent builders, multi-turn debugging scaffolding on self-contained code cannot substitute for a stronger base model and is most cost-effective when left optional rather than forced by prompt instructions. Because most executed probe scripts did not check expected outputs even though every problem description includes example input-output pairs (Section IV-C), dedicated tools that run specification examples automatically could further reduce probing overhead. 

e) Grading after transformations: Statement-level and line-level grading differ only where a transformation recipe splits the faulty statement across lines (47% of transformed cases). In our audit, answers accepted only by statement-level grading diagnosed the seeded fault as often as exact-line successes, and the share of such answers varied from 0.1% for Sol 6.1 to 7.3% for Luna 6 (Section IV-D). Strict line-level grading would count these valid diagnoses as failures, inflate 

|G| and I, and make model comparisons depend on which fragment of a split statement each model reports. Evaluations on transformed code should therefore track the full span of the faulty statement across rewrites and report gains relative to the no-tools error rate alongside percentage-point effects when baseline accuracy is near the ceiling. VI. T HREATS TO VALIDITY 

a) Comparing representations: Like prior studies [20], [35], [43], we use behavior-preserving transformations to re-duce surface overlap with pretraining corpora. However, Kept measures four-token overlap between program versions rather than against a model’s training corpus, transformed programs remain semantic duplicates of public solutions [34], and the problem description stays unchanged because fault localization requires a specification of intended behavior [21]. An agent can therefore still recognize an underlying LeetCode problem seen during training [32]. Residual familiarity makes the two representations more alike and attenuates any part of G or I

driven by unfamiliarity, so we interpret G and I as sensitivity to the transformation recipes rather than to unfamiliarity alone. 

b) Measuring the assistance effect: Compared with no-tools, encouraged-tools adds program execution, the interactive debugger, an explicit tool-use instruction, and additional model calls, so ∆ and ∆′ measure their combined effect. Top-1 accuracy grades the reported line number rather than the explanation, and LLMs can reach correct answers from flawed reasoning [37]. Coincidental hits would bias ∆ or ∆′ only if they occurred at different rates across settings, and our blinded audit found valid fault diagnoses in 59 of 60 exact-line and 133 of 135 statement-only successes (Section IV-D). The prompt asks for the “most likely affected line” (Listing 1), which an agent could interpret as a downstream line where the fault manifests, though all settings share this prompt. Finally, monetary costs depend on provider pricing and cached-input discounts, and our DeepInfra-based estimate for self-hosted Qwen 3.8 is an external proxy, so we report token counts and wall time alongside dollar costs for every condition. 

c) Discretionary use: An agent may invoke a tool with-out expecting an accuracy gain [24], for example because a program looks complex. The RQ3 slope β1 therefore measures whether discretionary tool use is associated with larger per-case assistance effects, not why the agent used a tool. With two episodes per case and setting, per-case noise can attenuate 

β1 toward zero, so we draw no case-level conclusions. 

d) Generalization: We evaluate short Python programs for precisely specified algorithmic problems because con-structing verified matched pairs requires a problem description, a reference solution, and an executable test suite. Our findings do not generalize directly to multi-file repositories, incomplete specifications, or multi-statement defects, where the relevant state may not fit in the model’s context and interactive debug-ging has shown larger gains [9], [11]. Four of our five fault types instantiate single-statement bug patterns that account for a quarter of the 73,013 Python bugs mined by Kamienski et al. [41], and 73% of 357 real Java faults in Just et al. were coupled to mutants of common operators [59]. 

e) Reproducibility: Commercial API updates can alter model behavior over time [48]. We record model identifiers, reasoning settings, and collection dates (Section III-B), re-lease all prompts, traces, and analysis scripts [26], and serve Qwen 3.8 ourselves from fixed open-weights checkpoints. VII. C ONCLUSION 

Across 610 untransformed and 3,022 transformed Python programs (65,376 episodes), we evaluated how accurately coding agents localize single-line faults from source code alone and how much debugger assistance improves outcomes. Without tools, agents based on Sol 6.1, Luna 6, and Qwen 3.8 already approached the accuracy ceiling, localizing 98.2 to 99.9% of faults in untransformed and 96.7 to 99.9% in trans-formed programs. Variable renaming and distractors barely changed static accuracy, whereas restructured loops and dou-bly negated conditions lowered it for Luna 6 and Qwen 3.8. Encouraged debugger assistance removed 63% and 61% of their remaining transformed errors (+2.1 and +1.3 percentage points) and closed the transformation gap, while multiplying token use by 14.7 to 27.0 and wall time by 5.3 to 7.7. When debugger assistance was optional, the agents used the interac-tive debugger in only 0.2 to 6.2% of transformed episodes and instead ran execution probes or answered from source code alone, yet kept most of the accuracy benefit at a fraction of the token cost. Future work should isolate program execution from interactive debugging with an execution-only setting and evaluate larger, less precisely specified repository bugs where static reasoning leaves more room for state inspection.

# FeatureLoop: Benchmarking Coding Agents under Evolving Requirements 

Jia Feng 1, Alyssa Wu 1, Cuiyun Gao 2,

Yunlong Wang 1, Songyuanyi Lu 1, Zhichao Hu 11Hunyuan Team, Tencent 2The Chinese University of Hong Kong

Abstract 

Software development with coding agents often begins with a rough request that users refine after trying the implementation. Final correctness alone does not capture the repeated guidance this process requires. We introduce FeatureLoop, a benchmark of 61 human-reviewed tasks from 34 repositories across five primary programming languages and seven software forms. Each task follows one development goal in a persistent workspace through evolution feedback ,which adds or clarifies requirements, and completion feedback , which reports failures of stated requirements. Cumulative executable checks track new behavior, repair, and preservation of earlier functionality. We evaluate 12 frontier models and find that the strongest completes 72.1% of tasks with both feedback types. Across models, however, only 15.4% of observed failed stages recover within two corrective revisions. Further analysis reveals incomplete repairs, regressions, and model-specific differences in feedback use and token efficiency, identifying obstacles to reliable, low-intervention development. 

## 1 INTRODUCTION 

Coding agents combine repository inspection and code editing (Yang et al., 2024a) with command execution in sandboxed environments (Wang et al., 2025). Real-user records show sustained devel-opment with repeated corrections and failure reports (Baumann et al., 2026). Initial requests can also omit information needed for implementation (Vijayvargiya et al., 2026). Delegating the opening request therefore leaves the user with further work: trying the implementation, explaining additional requirements, and reporting errors. Turning those reports into working code remains a separate challenge, since repair success depends on the quality of the feedback (Olausson et al., 2024). The practical question is: how much repeated guidance does an agent need to turn an initial request into a complete, working implementation? 

Figure 1 illustrates two reasons for returning to a coding agent. After a Grow menu can create connected shapes, the user asks for connectors that reroute during dragging. This changes what the software should do. Once rerouting has been requested, a report that a connector stays in its old position instead identifies unfinished implementation work. We call the first kind of intervention 

evolution feedback and the second completion feedback . Across both, progress must accumulate: creating a correct connector is insufficient if the next edit breaks child creation or loses its bindings. Rechecking earlier behavior after changes is the purpose of regression testing (Yoo & Harman, 2012). Existing benchmarks establish several parts of this evaluation. Executable tasks cover repository issue resolution (Jimenez et al., 2024), complex feature implementation (Zhou et al., 2026), technical terminal workflows (Merrill et al., 2026), and vulnerability reproduction (Wang et al., 2026b). Interactive evaluation measures responses to user requests and corrections (Wu et al., 2026), while sequential evaluation checks earlier requirements after continued modification (Shen et al., 2026). Conversational code generation further shows that solving more problems and solving them in fewer turns are distinct outcomes (Han et al., 2025). Our focus is how these demands interact: when a user

We introduce FeatureLoop to make this devel-opment path measurable. Each task follows one user-facing development goal from an initial request through successive refinements of the same repository implementation. Later requests specify its capabilities, constraints, and interac-tions, while each revision must retain the require-ments already established. Executable checks determine which later requirements still need to be requested, which stated requirements need correction, and whether earlier functionality re-mains correct. The resulting record separates success on the latest request from success on everything requested so far. It also distinguishes eventual delivery from a development path that repeatedly leaves the user with an incomplete or broken implementation. FeatureLoop contains 61 tasks from 34 reposi-tories, covering five primary programming lan-guages and seven software forms. Its construc-tion connects public development requests to staged, executable acceptance criteria. Tests and reference implementations are authored indepen-dently, each stage is checked for both added behavior and preservation of earlier requirements, and human reviewers inspect task quality before and after trial agent runs. This yields tasks with explicit user goals, feasible implementations, and requirement-level evidence across command-line tools, services, interactive applications, and libraries. The same feedback loop can therefore be evaluated across a broad range of software-engineering settings. We evaluate 12 frontier models with complete requirements upfront, progressive requests alone, and progressive requests with corrective feedback. The results expose three complementary weaknesses. First, a model’s final success rate does not describe how much correction it needs. Second, failure reports rarely yield a complete repair: only 15.4% of observed failed states recover within two revisions. Third, local success does not ensure reliable cumulative progress; even successful individual repairs leave other stated requirements unfinished in 20.9% of cases. Model-level analysis further separates responsiveness to correction, preservation of working behavior, and resource use. These differences identify where continued user intervention remains necessary. Our contributions are threefold: • We introduce an executable evaluation of iterative repository development that connects requirement evolution and corrective feedback to cumulative correctness and user guidance. • We build FeatureLoop, a quality-reviewed benchmark of 61 multi-stage tasks from 34 repositories across five primary programming languages and seven software forms, with acceptance checks retained throughout development. • We evaluate 12 frontier models and identify common gaps in complete repair and user-facing verification, alongside model-specific differences in preservation, failure patterns, and token efficiency. 

## 2 FEATURE LOOP 

2.1 TASK FORMULATION 

A FeatureLoop task develops one user-facing goal within an existing repository. The initial request establishes the direction; later requests specify further capabilities, constraints, and interactions that 2refine the target software. All stages build on the same implementation, and each revision must satisfy the requirements accumulated so far. Let W0 be the initial repository. A requirement group collects related behaviors evaluated together, such as creating a child shape and binding its connector. The groups form a directed acyclic graph 

(DAG), where an edge g → h means that h depends on g. We unfold this graph into a fixed sequence of stages that respects its dependencies. At stage i, the newly introduced groups are Ai, and the 

requirement state Qi contains all groups introduced so far: 

Q1 = A1, Qi+1 = Qi ∪ Ai+1 , Q1 ⊂ · · · ⊂ QK . (1) Each stage adds at least one group. Every earlier group remains part of the task through the final stage K.

Checking the complete implementation. Let Zg (W ) indicate whether the implementation in workspace W passes the checks for group g. Let b(W ) indicate whether it passes the baseline suite ,which checks the repository behavior that was working before the task. We evaluate the requested functionality and the baseline separately: 

Pi(W ) = 1[∀g ∈ Qi, Z g (W ) = 1] , Ci(W ) = b(W )Pi(W ). (2) Here, Pi = 1 means that all requirements introduced so far pass; Ci = 1 also requires the original repository behavior to pass. For example, rerouting a connector correctly is only local progress if creating its bound child still fails. Regression testing checks that modifications preserve established behavior (Yoo & Harman, 2012). Here, the retained obligations include both the original baseline and every requirement introduced during the task. 

Two forms of feedback. Evolution feedback introduces missing behavior from the next requirement group or groups Ai+1 . Completion feedback reports a failure among requirements already in Qi

and asks the agent to repair its implementation. Before sending a later request, the evaluator checks whether the corresponding behavior already works and omits the parts already satisfied. Revisions then update the existing workspace. This makes feedback depend on the agent’s progress while keeping the development target fixed. Final task success requires every requested behavior and the baseline to pass: 

Success( WT ) = CK (WT ), (3) where WT is the final workspace. Intermediate checks identify requirements completed immediately, repaired after feedback, left unfinished, or broken by later edits. Complete requirements upfront (Full). The user specifies the entire target at the outset and asks the agent to deliver it in one coding session. The agent inspects the repository, edits code, and uses its tools to check the result. This scenario evaluates implementation when the user has already described everything needed. 

Progressive requests (Evo). The user starts with an initial request and introduces further requirements as development proceeds. Each 3new request gives the agent another opportunity to extend the existing implementation. The user supplies additional requirements but leaves debugging to the agent. This scenario evaluates whether the agent can integrate each request and preserve earlier functionality using its own verification. 

Progressive requests with correction (Evo+Comp). The user also reports problems encountered in the current implementation. The agent can respond to those reports before receiving the next requirement. This is the main evaluation scenario: the user continues refining the task and checking the delivered software, while the benchmark measures how effectively the agent uses both kinds of feedback. To keep the task comparable, all scenarios start from the same repository checkpoint and use the same final requirements and acceptance checks. The two progressive scenarios also share the requirement order. Within that order, the current implementation determines which requests are still needed and which failures can be reported. Review task quality before and after trial agent runs. Human reviewers first inspect the require-ments and requests, run every reference stage, and verify that the tests enforce the intended user-visible behavior. Candidates that pass this review are then implemented by four coding models. Reviewers examine the resulting conversations, edits, and execution evidence to identify task defects exposed by implementations beyond the reference solution. Defects return to the responsible construction stage for correction and revalidation. Final acceptance retains 61 tasks. Appendix B.3.10 specifies the human review, and Appendix C.1 records the candidate counts, trial models, and selection outcomes. 2.4 DATASET CHARACTERISTICS 

Broad software-engineering coverage. The 61 tasks cover 34 repositories and five primary programming languages: Go, Rust, JavaScript, TypeScript, and Python. They include command-line tools, terminal interfaces, browser applications, services, libraries, frameworks, and embedded software (Figure 4(a)). This coverage includes backend services, developer tooling, interactive software, and reusable components, each evaluated through its public commands, APIs, or user interface. Appendices C.2 and C.5 give the complete composition. 

Successive stages add continuing obligations. Tasks contain two to eight stages. Each stage adds behavior that must continue to work as the implementation changes. Across the 61 tasks, the average number of active test groups grows from 1.15 at the first stage to 4.11 at the final stage (Figure 4(b)). Each new stage therefore expands the set of behaviors that must work together in the same implementation. Appendix C.4 reports stage counts, test sizes, and reference-edit volumes; Appendix C.3 defines the counting units. 

Later requirements include both foreseeable extensions and new information. The 61 tasks contain 147 later requirement groups. Of these, 42 follow a direction supported by earlier requests. For 16 of these groups, earlier information also constrains the exact expected behavior, and imple-menting it early carries limited risk. Another 85 depend on new user information or a discovery unavailable in the earlier interaction. Underspecified requests can omit information that materially 5changes the correct implementation (Vijayvargiya et al., 2026). We therefore distinguish two capabil-ities: completing well-supported behavior before another request is needed, and incorporating new requirements correctly once the user supplies them. The semantic annotation procedure, examples, and full labels are in Appendix C.6. 

## 3 EXPERIMENTAL SETUP AND EVALUATION 

Setup. We evaluate 12 frontier models on all 61 tasks under the three development scenarios, yielding 2,196 runs. All models use Claude Code as the shared coding harness. Progressive runs retain the workspace and conversation; the corrective scenario uses a fixed feedback generator and permits at most two corrective revisions per stage. Each revision is a complete coding-agent response with its own tool calls. Appendix D gives the models, runtime configuration, and execution rules. 

Measures. StrictPass measures final completion of all requirements and the repository baseline. We report new-requirement and corrective message counts ( NE , NC ), together with Feedback-Discounted Agent Completion (FDAC), which discounts successful delivery according to when intermediate states become correct; a state left incomplete within its response budget yields zero. Intermediate checks distinguish new-requirement uptake, complete repair, and preservation of earlier success. Agent Tokens measures reported input and output tokens. Trajectory analyses use both feedback types unless stated otherwise. Appendix E provides metric definitions, observation windows, token accounting, and uncertainty estimates.

Appendix F.11 reports the message counts together with stalled and regressed states. 4.2 LOCAL PROGRESS OFTEN FAILS TO PRODUCE A COMPLETE , L ASTING REPAIR 

Providing the missing information does not remove the implementation bottleneck. We first examine requirements that introduce information unavailable earlier in the task. Agents implement the newly requested behavior on the first response in 77.3% of observed cases. Yet some of those locally successful responses still leave earlier requirements unfinished. The difficulty is not simply understanding the latest request: the new behavior must coexist with everything the user has already asked for. Appendix F.7 separates local success from complete requirement-state success. 

An explicit failure report rarely restores the whole state. We next follow stages that fail their checks after the first response and receive corrective feedback. Only 15.4% become fully correct within the two permitted revisions. Moreover, fixing an individual requirement is not always enough: 20.9% of successful individual repairs still leave another stated requirement unmet. Earlier work may have remained unfinished or been broken by a subsequent edit. The relevant stopping condition is therefore the complete set of active requirements, not disappearance of the latest symptom. Appendix F.10 gives state-level recovery, and Appendix F.7 gives the individual-repair breakdown. 

Correct behavior must survive the next request. To examine preservation, we continue checking requirements that have already passed and are observed again during later stages. Of these previously working requirements, 11.4% fail at a subsequent check. In the NextChat example, an early repair is followed by a runtime error that persists while further capabilities are added. Continued feature development can thus conceal a broken execution path rather than repair it. The case appears in Appendix F.5; the complete retention counts and observation conditions are in Table 35. Checking a convenient component is not checking the requested behavior. We inspect the requests, edits, actions, and execution evi-dence of every run that ends unsuccessfully. In 75.3% of these failures, the agent either omits a relevant user-path check or validates a helper, stub, or proxy instead. For example, an internal merge routine can pass a custom test while the live endpoint continues to use the old behavior. This explains how apparently reasonable code and repeated tool use coexist with an unresolved user report: the agent’s check does not exercise the behavior being evaluated. Appendix F.2 doc-uments the coding procedure, and Appendix F.5 traces representative examples. 

Shared-state consistency characterizes the common hard cases. On tasks that no evalu-ated model completes, inconsistent state across components accounts for 32.4% of final failures, compared with 2.6% on tasks solved by some models (Figure 6). These traces involve registries, stores, parsers, renderers, or lifecycle handlers that do not agree on the same state. A local patch can leave that disagreement intact even when its own helper works. The common difficulty is therefore broader than writing a missing function: the change must reach the public entry point and remain consistent across the components that consume it. ## 5 SCOPE AND LIMITATIONS 

FeatureLoop focuses on cumulative, executable requirements in existing repositories, with one predefined continuation per task. We use a fixed feedback policy and at most two corrective revisions per stage. The findings characterize the sampled tasks under these interaction settings; human collaboration may involve different requirement changes and feedback patterns. Correctness is assessed through executable checks, whose coverage is bounded by the specified behaviors. 

## 6 CONCLUSION 

We introduced FeatureLoop, a benchmark for iterative software development under evolving require-ments. Each task follows one development goal in a persistent workspace, combining new requests and corrective feedback with cumulative executable checks. Our evaluation of 12 frontier models shows that interactive workflows improve final completion, while incomplete repairs and regressions remain recurring obstacles. Models with similar final success rates also differ in their reliance on correction, preservation of working functionality, and token expenditure. By evaluating both final outcomes and progress across revisions, FeatureLoop provides a testbed for advancing reliable coding agents that require less repeated user guidance.

A.1 EXECUTABLE BENCHMARKS AND TASK CONSTRUCTION 

Executable software-engineering benchmarks. SWE-bench (Jimenez et al., 2024) evaluates patches for issues in existing repositories. Multi-SWE-bench (Zan et al., 2025) and SWE-PolyBench (Rashid et al., 2025) extend repository-level evaluation across languages, while FeatureBench (Zhou et al., 2026) targets complex feature implementation. SWE-bench Multimodal (Yang et al., 2024b) includes visual software domains, and SWE-Lancer (Miserendino et al., 2025) grounds tasks in paid freelance work. Terminal-Bench (Merrill et al., 2026) broadens evaluation to hard technical tasks in command-line environments. CyberGym (Wang et al., 2026b) verifies vulnerability reproduction by executing generated proof-of-concept inputs. These benchmarks connect realistic work to checkable outcomes. FeatureLoop measures the path to an outcome as requirements accumulate, retaining intermediate implementation, correction, and preservation evidence. 

Task construction and verifier quality. SWE-Gym (Pan et al., 2025) provides executable en-vironments for training agents and verifiers. R2E-Gym (Jain et al., 2025) combines procedural environments with hybrid verification; SWE-smith (Yang et al., 2025) scales repository-based train-ing tasks; and SWE-Flow (Zhang et al., 2025a) synthesizes tasks through test-driven construction. EvalPlus (Liu et al., 2023) demonstrates the effect of stronger test coverage on code evaluation, while SWT-Bench (Mündler et al., 2025) evaluates tests that reproduce bugs and validate fixes. FeatureLoop independently constructs tests and reference checkpoints, checks every new behavior across adjacent and later states, and combines executable evidence with human review. Its historical screening complements the fresh-task collection used by SWE-bench-Live (Zhang et al., 2025b) and SWE-rebench (Badertdinov et al., 2025). A.2 INTERACTION AND CONTINUED DEVELOPMENT

Information and feedback. A clarification supplies missing information about an established objective. A new request adds or changes desired behavior. A corrective message reports a failure of already stated behavior. We call feedback execution-grounded when the user-facing message is derived from behavioral checks of the current implementation. This identifies the evidence supplied to the agent, separately from whether its final output is evaluated by execution. 

Persistent correctness. Cumulative evaluation carries earlier, still-active requirements forward as correctness obligations. In FeatureLoop, requirement sets grow monotonically, so every introduced behavior remains active. Local checks identify whether the latest behavior works; cumulative checks require all active groups to work together; the baseline suite additionally checks retained repository behavior. 13 Ambig-SWE and ICAE-Bench: obtaining missing information. Ambig-SWE (Vijayvargiya et al., 2026) removes information from repository issues and lets an agent ask a user proxy for clarification. ICAE-Bench (Peng et al., 2026) starts from underspecified product requests and uses a constrained router to reveal information from a fixed product contract. Both make information acquisition part of the agent’s task. In FeatureLoop, the controller visits a fixed state sequence and discloses requirements according to the behavior still missing from the current workspace. 

SWE-Interact and SWE-Together: state-dependent user steering. SWE-Interact (Raghavendra et al., 2026) creates user-driven sessions from benchmark tasks using a simulator that can inspect repository content and changes. SWE-Together (Wu et al., 2026) conditions interventions on real-session evidence and the current trajectory. It distinguishes new requests from corrections, reports User Correction, and uses task-specific final rubrics with an agentic judge that can gather execution evidence. FeatureLoop ties each requirement group to fixed executable checks. Those checks determine both the missing information to disclose and the active failures to report, while intermediate evaluation records completion of individual requirements, all stated requirements, and the repository baseline. 

Asuka-Bench: feedback from browser use. Asuka-Bench (Wang et al., 2026a) starts with an underspecified web-development request, checks the resulting interface through browser interaction, and converts the findings into feedback for another revision. Repeated evaluation measures improve-ment and repair over the interaction. FeatureLoop extends the evaluation setting across existing repositories and multiple software forms, with explicit cumulative requirement states and corrective revisions within each requirement stage. These states connect each message to the behavior that is newly requested or remains unfinished. 

EvoCode-Bench and LoopsBench: continued development. EvoCode-Bench (Shen et al., 2026) presents extensions, corrections, conflicts, and supersessions in a persistent workspace. Its verifier retains requirements that remain valid, and its reference-predecessor comparison separates single-round implementation from persistent execution. LoopsBench (Li et al., 2026) organizes work into dependent development units whose activated tests remain regression obligations. FeatureLoop couples continued development to workspace-dependent user intervention: already implemented later behavior skips disclosure, whereas failed active behavior can receive completion feedback. The resulting trajectory records direct repairs and the preservation of earlier success. 

Other forms of iterative development. SR-Eval (Zhan et al., 2026) studies stepwise requirement refinement. SlopCodeBench (Orlanski et al., 2026) examines code degradation over iterative develop-ment, while SLUMP (Yan et al., 2026) studies faithfulness as specifications emerge. SWE-EVO (Le et al., 2026) constructs multi-step, multi-file tasks from project release notes. At the program level, ConvCodeWorld (Han et al., 2025) compares reproducible feedback environments and distinguishes conversational efficiency from overall task completion. FeatureLoop connects an accumulating requirement sequence to state-dependent disclosure and correction, recording whether each response completes the active requirements and preserves earlier success. 

Comparing complete development workflows. Our upfront, progressive, and corrective workflows target the same final contract from the same checkpoint. Each model–task pair is independently executed under all three workflows. A paired comparison measures the change in final outcome between those complete workflows; direct recovery is measured separately within the trajectory that receives the failure report. FDAC summarizes final completion and intermediate timeliness under a fixed discount schedule, while message counts report the actual number of delivered interventions. A.3 FEEDBACK -D RIVEN REFINEMENT AND REPAIR 

Self-Refine (Madaan et al., 2023) iteratively revises outputs using model-generated feedback. Reflex-ion (Shinn et al., 2023) stores verbal feedback to guide later attempts, and Self-Debugging (Chen et al., 2023) combines execution results with explanations of generated code. Olausson et al. (2024) find that self-repair gains depend on feedback quality and the computation spent obtaining them. These methods motivate treating feedback use as a measurable capability. In FeatureLoop, the repair target is the cumulative repository state: a correction succeeds only at the level specified by its local, 14 cumulative, or baseline-inclusive check. Previously satisfied behavior remains testable throughout later development.

To turn the development target into actionable stages, the Trajectory Author groups related behaviors into nodes of a directed acyclic dependency graph. An edge records a prerequisite relation between groups. The author then selects a stage sequence from Q1 to QK that respects these dependencies. Each state records the groups introduced there, all groups that remain active, direct dependencies, earlier behavior that must remain correct, and the use scenario that exposes the next gap. Source evidence informs a plausible development order; the frozen task record fixes the actual requirements and disclosure sequence used in evaluation. B.3.4 EXECUTABLE ENVIRONMENT 

To make every stage reproducible, the Environment Author reconstructs an isolated environment from dependency locks, build configuration, and repository continuous-integration records. Validation includes independent clean runs, the original baseline, public entry points, offline execution, resource 18 limits, and workspace integrity. The runs use the same environment definition but fresh writable workspaces. This definition determines how the task executes reproducibly, while the frozen sources and contract determine its requirements and behavior. B.3.5 FROZEN CONTRACT AND FEEDBACK MESSAGES 

The Contract Author combines the accepted sources, development target, requirement sequence, and environment into a versioned behavioral specification, called the contract Γ. This specification aligns the requests, tests, and reference implementations. Each group records the user action or input, expected and forbidden outcomes, earlier behavior that must remain correct, allowed implementation freedom, and a runnable check. An independent Contract Reviewer checks that the contract follows the sources, respects state dependencies, can be observed through public interfaces, leaves implementation choices open, and runs in the environment; deterministic validation checks the schema and every referenced file or check. After Γ is frozen, a Dialogue Author produces u0 and the candidate evolution messages. Review verifies that each message reveals only its corresponding state, is consistent with its documented use scenario, and contains no group identifier, hidden-test wording, Reference information, or future requirement. Completion feedback does not create a new contract state; it is generated at runtime from failed user-visible checks for currently active groups. B.3.6 ISOLATED TEST CONSTRUCTION 

To evaluate the specified behavior independently of a solution, the Test Author works from the frozen contract, initial repository, environment, and complete state map in a separate workspace. It builds the group and cumulative-state checks, final suite, baseline checks, and transition checks. A Test Critic reviews their behavioral coverage, execution stability, and use of public interfaces. Reference code and execution results remain outside both roles’ access. To exclude targets with an already published complete solution, we screened every candidate against public repository history after its checkpoint and before a recorded cutoff. Screening used the frozen Test package and preceded Reference construction. The frozen behavioral checks were replayed on later commits or trees: inexpensive deterministic checks covered the relevant history exhaustively, while expensive checks such as browser execution used recorded targeted coverage. Candidates whose later public history passed the complete recorded behavior set were removed. The screening record preserves the checkpoint, cutoff, searched history, executed checks, coverage, and decision; reviewers checked partial matches and environment incompatibilities individually to determine which behaviors the historical version implemented. Their information schedules and opportunities for action differ. 

Full Specification (Full). The controller supplies the complete final specification in the opening request. The agent explores, edits, and tests the repository within one coding session. The evaluator then checks the final workspace. This workflow measures implementation from complete upfront information. 

Evolution-Only Feedback (Evo). The controller first supplies u0. After the agent’s response, it evaluates the persistent workspace against the next requirement state. Requirements already satisfied need not be disclosed. Otherwise, it supplies the corresponding evolution message and lets the agent modify the same workspace. The process continues through the fixed state sequence. Failures of previously stated behavior do not produce completion messages, but those requirements remain active in all subsequent cumulative checks. 

Evolution + Completion Feedback (Evo+Comp). This protocol adds within-state correction. After a response, the evaluator checks the active cumulative requirements. When it obtains attributable failure evidence, the feedback generator expresses up to two predefined observations as a user-facing message. The agent can revise the workspace at most twice at that state. The controller then advances even if requirements remain unmet. Earlier failures remain active obligations in the agent’s workspace. 

Normal execution path. The controller performs the following steps: 1. Deliver the initial request and obtain a coding-agent response. 2. Execute the current cumulative checks. In Evo+Comp, an observed failure can trigger a completion message and another response, up to the two-revision limit. 3. Before each later disclosure, check the current workspace. Skip already satisfied behavior; otherwise disclose the missing requirement information for that state. 4. Obtain the agent’s response, apply the protocol’s within-state checking and correction rule, and advance to the next state. 5. After the final state and its permitted revisions, evaluate every active requirement group and the repository baseline. The generator uses the predefined observations to describe public behavior, such as a command returning the wrong result or an interface failing after a specified action. Hidden test identifiers, assertions, reference code, and future requirements stay outside the message context. After two corrective revisions, the controller proceeds to the next requirement stage and keeps all earlier requirements in the cumulative checks. D.4 INFORMATION AND RESPONSE OPPORTUNITIES

V3 No relevant implementation The necessary information and workspace are available, but the run stops without implementing the requested behavior.

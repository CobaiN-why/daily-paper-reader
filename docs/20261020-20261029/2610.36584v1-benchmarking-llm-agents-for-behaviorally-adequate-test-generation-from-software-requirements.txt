# Benchmarking LLM Agents for Behaviorally Adequate Test Generation from Software Requirements 

BINHANG QI, National University of Singapore, Singapore

JIN SONG DONG, National University of Singapore, Singapore As large language model (LLM) agents increasingly compile natural-language requirements into repository-level code, requirement-to-test generation grows in importance to provide validation constraints (or harness) to guide code generation. Yet it remains unclear whether current agents can generate tests that validate the required behavior when the implementation of that behavior is withheld. Existing test-generation benchmarks mostly focus on white-box testing, whereas the requirement–test-related study usually requires evaluation on semantic alignment between the given documents and the generated tests. We introduce Req2Test-Bench, a benchmark containing 5,086 execution-validated instances recovered from developer-authored behavior-driven development (BDD) artifacts in 8 open-source projects, spanning 5 programming languages and 4 BDD frameworks. Each instance pairs a natural-language requirement in Gherkin with its developer-written Test Implementation . Given the requirement, target interfaces of the required behavior, and a repository view that withholds either the target implementation or all production implementations, an agent must generate a complete, potentially multi-file Test Implementation . Solving the task requires bridging the gap between a high-level requirement and its test-code correspondence regarding project-specific knowledge: crystallizing what to test, stated in natural language, into how to test it with the project’s own fixtures, helpers, and interfaces. We evaluate the semantic difference between generated and ground-truth tests by comparing their production API calls, code coverage, and mutant kills. Evaluation of 8 agent–model– reasoning configurations reveals a substantial gap between execution success and behavioral adequacy, which is measured strictly as kill-completeness: a kill-complete test kills every mutant that the ground-truth test kills. The best-performing configuration, Codex with DeepSeek-V4.1-Flash, produces passing tests for 82.8% of instances, yet only 33.8% are behaviorally adequate. We find that (1) scaling up agents yields sharply diminishing returns in behavioral adequacy relative to generation cost; (2) under-specified requirements cause the information gap, including ambiguous setup and implicit expected outcomes; and (3) requirement-grounded harnesses that steer agent non-determinism offer a promising direction for improvement. 

1 Introduction 

Large language model (LLM) agents increasingly translate natural-language software requirements into repository-wide implementations [38]. As code generation accelerates, validation becomes a bottleneck: developers need executable evidence that generated software satisfies the requested behavior rather than merely compiling or appearing plausible. Requirement-derived tests provide behavioral checks for code-generation harnesses, supporting candidate selection and iterative refinement [6, 16]. Yet a generated test may pass while omitting meaningful checks or relying on tautological assertions [18, 33]. Existing LLM-based test-generation studies and benchmarks start from prescribed methods, classes, or source files [18, 36, 41], from code changes [15], from issue reports [1, 26], or from behavior inferred by exploring a running application [3]. Consequently, their results alone do not suffice to answer these questions. We instead study requirement-to-test generation, which is requirement-driven : an independently stated requirement determines the testing objective, and the target implementation is withheld from the agent. Related requirement–test resources address parts of this problem; however, they have complementary limitations: 1 Some synthesize or manually adapt requirement or test artifacts during benchmark construction [24, 25]; 2 others associate a coarse requirement artifact, such as a project-level requirement, with an entire test file rather than with the complete Test Implementation for one individual, concrete behavior [21, 24]. To address these limitations, Req2Test-Bench combines authentic requirements, complete ground-truth Test Implementations for individual behaviors, execution-validated mappings, and behavioral evaluation under controlled implementation visibility. We instantiate the task using artifacts from behavior-driven-development (BDD) repositories. 2 Related Work 

Test-generation benchmarks. Existing test-generation benchmarks usually derive the test ob-jective from prescribed code, a defect context, or an observed application. Methods2Test [36] mines focal-method–JUnit-test pairs, while TestBench [41] and TestGenEval [18] evaluate class-or file-level test generation using execution, coverage, and fault-detection or mutation metrics. SWT-Bench [26] asks for a test that reproduces an issue report, and AutoE2E [3] infers features by exploring a running web application before generating end-to-end tests. These works provide important execution-based protocols, but their task boundary is supplied by focal code, a code-change or fault context, or an observed application. Req2Test-Bench studies the complementary requirement-defined setting, in which a developer-authored Requirement determines the target behavior and an agent must realize it as a complete, project-compatible Test Implementation. 

Requirement–test resources. Table 1 compares the closest works that associate requirement artifacts with test code. E2EDev [25] provides LLM-generated requirements, BDD Scenarios, and Step Definitions for web applications. GivenWhenThen [21] mines developer-authored Feature and Step Definition files at scale, but its scenario records contain file-level artifacts rather than an execution-validated, Scenario-specific Test Implementation. DevBench [24] includes benchmark-authored PRDs and executable acceptance- and unit-testing tasks with mixed-provenance tests, but does not map individual requirement criteria to individual ground-truth tests. Requirements-based and BDD test generation. Requirements-based testing has long derived tests from structured or natural-language specifications. UMTG [37] derives executable acceptance tests from use cases and a domain model, while Specmate [12] and CiRA [11] derive test designs from acceptance criteria or conditional relations. Recent LLM-based systems generate executable artifacts from requirements or intermediate behavioral specifications. AutoGlue [34] generates one Java glue method for a target Gherkin Step using its Feature and Scenario context together with retrieved project artifacts. Ferreira et al. [10] generate Gherkin Scenarios and Cypress tests from user stories and application HTML, whereas AToMIC [13] generates Gherkin Scenarios, Page Objects, and mobile UI tests from JIRA requirements and code changes. Other systems use DSL requirements, validation intentions, or product-requirement knowledge to guide testing around prescribed architectures or focal code [14, 27, 31, 39]. These studies establish the value of requirements and project knowledge, but differ in generation unit and task boundary. Among these, AutoGlue is the closest task-level neighbor: it maps one Step to one glue method, whereas Req2Test-Bench evaluates the complete, potentially multi-file Test Implementation required to automate one Scenario. Other systems target specialized UI-automation pipelines or guide test generation around prescribed architectures or focal implementations.

3.2 Dataset Construction 

We construct Req2Test-Bench in five stages. Stage I assembles candidate repositories and their BDD artifacts. Stage II selects projects for execution and filters their Scenarios. Stage III recovers and validates Requirement–Test Implementation mappings, identifies target interfaces, and constructs the agent views. Stage IV constructs the mutation evidence and establishes mutation scorability. Stage V labels test levels and requirement relations. 

Stage I: Candidate discovery and artifact collection. We assembled candidate GitHub reposito-ries containing developer-authored Gherkin .feature files and BDD test code, using framework dependencies, configuration files, and Step Definitions as static evidence. Four execution frame-works are Cucumber (Java and Ruby), Behave (Python), Behat (PHP), and Godog (Go). An initial survey of the 100 highest-starred discovered repositories with more than 100 recorded stars iden-tified potentially usable Scenarios with static Step Definition matches in 46 repositories. Further discovery added candidates beyond this survey. For candidates taken forward, we pinned revisions and collected feature files, Step Definitions, framework configuration, hooks, fixtures, test data, and helpers. This stage yields candidate repositories and their artifacts for execution checks in Stage II. 

Stage II: Project admission and Requirement filtering. We favored higher recorded GitHub star counts, more recent last-push dates, and larger BDD suites, measured by their numbers of feature files and Scenarios. These preferences were balanced against domain and testing diver-sity. The eight selected projects span five programming languages and cover six domains :e-commerce (CoreShop, PrestaShop, and Sylius), document processing (python-docx), a blockchain SDK (Algorand SDK), IoT services (Kapua), an online petitions service (e-petitions), and agent software (coddy-agent). We sought both direct library tests and multistep workflows involving shared fixtures, database state, and service/API interactions. We removed empty, comment-only, and unparsable feature files and Scenarios that need a browser or a live service, and retained Features with nonempty titles and Scenarios with nonempty Step sequences. Applicable Background Steps are included in execution order, forming the Scenario’s 

effective Steps . A Scenario Outline remains one instance: its required Examples rows are executed after parameter substitution and combined into one instance-level outcome. We provisioned each project at its pinned revision and invoked its native BDD runner. A Scenario was retained only if the project initialized, every effective Step bound uniquely to a non-pending Step Definition, and the Scenario passed in isolation across three runs. We excluded build or initialization failures, undefined or ambiguous Steps, timeouts, and unstable outcomes without rewriting project-authored requirements or tests to make them pass. This execution gate follows repository-scale benchmark construction practice [20, 25]. Benchmarking LLM Agents for Behaviorally Adequate Test Generation from Software Requirements 7

Stage III: Test-Implementation recovery, target-interface identification, and agent views. Test Implementation Recovery. For each retained Scenario, we recorded the Step Definition selected by the runner for every effective Step. Starting from these runtime bindings, we recovered the transitive project-local test-side closure, including helpers, but excluding production code, third-party framework code, and the testing infrastructure that the whole suite shares. Shared definitions and supporting artifacts can belong to more than one closure. We validated each candidate closure in two derived workspaces sharing the same production revision, execution command, configuration, and project-global BDD infrastructure. Among project-local test-side artifacts, the positive workspace retains only the recovered closure and invariant infrastructure, and the target Scenario must pass. In the negative workspace, which withholds the closure, the runner must still initialize, but the target Scenario must not pass. Both outcomes must hold across three runs. Agent Views. For target-hidden, a source-level mapping uses the Requirement, ground-truth bindings, and pinned code and configuration to identify the bodies realizing the target behavior, including relevant delegation but not unrelated supporting infrastructure. The interface list alone is not the body-removal list. Language-aware transformations replace mapped bodies while preserving declarations, and all-hidden applies them throughout the declared production scope. We then materialize 𝐶 TH (𝑃 𝑖 ) and 𝐶 AH (𝑃 𝑖 ) with the same Requirement, interface annotations, permitted contract information, and retained infrastructure. Both views remove the Step Definitions and helpers of all Scenarios. Both keep the testing infrastructure that the whole suite shares, such as hooks, fixtures, and test data. Neither shows runtime traces, coverage, or mutation records.

Stage V: Test levels and requirement relations. Stage V labels test levels and requirement relations, and neither label changes the task. 

Test levels. We label a ground-truth Test Implementation by how its Step Definitions reach the production code: 1 component -level when they instantiate production classes directly; 2 integration -level when they obtain real services from the application’s own wiring, such as a dependency-injection container or a command bus; and 3 system -level when they drive the assembled application only through its external interface, such as its command-line entry point or the documented entry point of a library. Among our collected test implementations, 4,276 tests are named by the official developers, e.g., Kapua’s separate unit and integration runners, and our labels agree for 4,266 of these 4,276 instances. None is end-to-end test, as Stage II excludes Scenarios that need a browser.

3.3 Evaluation Criteria 

A generated test must first be a valid, executable implementation and must then exercise the behavior required by the scenario. We therefore report two complementary layers of metrics: stage-based execution outcomes that identify where generation or evaluation fails, and ground-truth-relative behavioral comparison that provides evidence beyond a passing execution. Req2Test-Bench saves the generated test files in a separate copy of the project containing the complete production implementation. Req2Test-Bench then executes the target Scenario using the project’s native BDD runner and records its outcome and behavioral measurements. For each agent and view, Req2Test-Bench evaluates one final generated test per instance in a predeclared population of size 𝑁 . Intermediate edits, local checks, and repairs belong to the same generation run and do not count as additional evaluation candidates. 

3.3.1 Stage-based execution outcomes. For each instance with a recorded result, we report success or the first stage at which test generation or evaluation fails. Failures caused by benchmark infrastructure are recorded separately and excluded from the following categories: 

• Generation failure: the agent returns no usable test code, no writable file, or an invalid submission format. 

• Build failure: the generated test files cannot be parsed, compiled, imported, or initialized with the project’s test environment. This category also covers interpreted languages. 

• Binding failure: the test framework cannot bind every Scenario step to a Step Definition, or encounters an undefined, ambiguous, or pending step. 

• Execution failure: the scenario does not complete due to an exception, crash, or timeout, without an assertion-failure outcome. 

• Assertion failure: the generated test runs and an assertion fails against the unmodified produc-tion implementation. 

• Pass: the selected Scenario completes with every effective step passing and the test command exits successfully. Let E be the attempted instances with recorded outcomes in the six categories above, after documented infrastructure exclusions, 𝑁 exec = |E| , and 𝑜 𝑖 the outcome of instance 𝑖 . 4 Experimental Design 

In this section, we formulate the research questions, introduce the evaluated approaches, specify how each approach is executed, and describe how the resulting observations are analyzed. 

4.1 Research Questions 

Our empirical study addresses the following research questions: RQ1 and RQ2 answer question Q1 of the introduction, RQ3 and RQ4 question Q2, and Section 5.5 question Q3. 

RQ1 (Effectiveness): How effectively do LLM agents solve Req2Test tasks in Req2Test-Bench? This question investigates the current capability of state-of-the-art LLM agents to transform natural-language requirements into executable and behaviorally adequate tests. 

RQ2 (Efficiency). How efficiently do the LLM agents solve the Req2Test tasks, and what effectiveness– efficiency trade-offs do they exhibit? We measure monetary cost, end-to-end time, model requests, and tokens per generation, and relate cost to effectiveness through the cost per kill-complete pass. 

RQ3 (Associated Factors). What requirement-, test-, and repository-level characteristics are associ-ated with successful Req2Test generation? This question investigates whether current agents perform consistently across the heterogeneous settings represented by Req2Test-Bench. We compare the all-hidden and target-hidden views on the same instances, and relate success to characteristics of the Requirement, its ground-truth Test Implementation (including its test level), the hidden code, and the Scenario’s prerequisites among the depends_on relations. 

RQ4 (Failure Modes). What failure modes do current agents exhibit, and what limitations do these failures reveal? We first identify the evaluation stage at which an unsuccessful generation fails. We then derive failure modes bottom-up from a stratified sample, explaining both why failing tests fail and why passing tests miss ground-truth kills.

4.3 Implementation Details 

Generation. Each generation receives the Requirement, the target interfaces, and one repository view inside a bubblewrap sandbox [5] whose network reaches only the model provider, under a common 3,600 s wall-clock limit. Agents may inspect the view and run local commands, including their own tests wherever the sandbox can load the retained code, but no such run can exercise the target behavior: its production bodies are placeholders that fail with an explicit “implementation hidden” error, and the harness provisions no application runtime and returns no execution feedback. The instructions state that the final test runs against a separate, complete implementation. We collect the test files from the workspace diff and discard production edits. Each instance receives one scored generation per configuration and view. Generations interrupted by provider-side limits are re-run, and none is repeated because of its outcome. To ensure that no generation observes ground-truth-derived artifacts, we audited the trajectories for access to such files and regenerated the affected generations in a hardened sandbox under a rule fixed in advance. 

Evaluation. The evaluator runs each final test once against the complete production code with the project’s native runner in a network-isolated container (600 s, coverage enabled), and runs every passing test against the instance’s mutant pool (Section 3.2). Many Scenarios of a project are tested through the same Step Definitions, so their Test Implemen-tations are near-duplicates. We therefore evaluate one per group of instances whose ground-truth Test Implementations use the same Step-Definition methods. All configurations run on these 2,051 instances from 780 Features in both views.

5.5 Toward Requirement-Grounded Harnesses 

Four preliminary studies investigate what a harness around the agent can supply. 

Grounding tests in project knowledge targets ambiguous setup. An added prompt paragraph instructs the agent to establish each Given through the project’s own fixtures, helpers, and entry points, not by constructing objects. On 231 python-docx and Algorand SDK instances not used to design the paragraph, this raises KillComplete@1 by 6.1 pp, 15.0 pp, and 8.0 pp for Codex/DS, Codex/Luna, and Codex/Sol ( 𝑝 ≤ 0.005). 

Enhancing the Requirement targets ambiguous setup and tacit expected outcomes. In domain language and naming no code, one author modifies the prompt to clarify what the ground-truth test sets up or checks beyond what a Step states. For example, the unchanged Step “the parsed Get Block response should have rewards pool . . . ” is clarified as “the parsed response matches the mock http response as a whole”. As a result, Codex/Luna’s kill-complete tests rise from 2 to 14 on 17 Algorand SDK Scenarios with tacit outcomes ( 𝑝 < 0.001), and from 25 to 36 on 60 python-docx instances with an ambiguous Given . Enhancing requirements automatically with the project’s conventions, fixtures, and helpers is a potential direction. 

Decomposing the Requirement targets misused project interfaces. Longer Scenarios are harder to pass (Section 5.3), but many of their Steps are shared with smaller Scenarios that they depend on. A harness could therefore decompose the target requirement and generate tests for the re-sulting smaller requirements first, and give them to the agent for the test generation of target requirement. We repeated test generation for 100 requirements from CoreShop and Kapua for which Codex/Luna had initially failed to produce passing tests. Retries with the unchanged prompt produced passing tests for 39 requirements due to the agent’s non-determinism. Exploiting non-determinism. Non-determinism makes a single generation unreliable but leaves room for improvement. We observed that the best of three generations, chosen by the evaluator, is kill-complete 8.6–10.2 pp more often than a single one (e.g., for Codex/DS, 44.8% against 36.2% on the repeated sample). A harness can exploit this only if it recognizes the behaviorally adequate candidate. 

6 Threats to Validity 

Construct validity. KillComplete@1 measures behavioral adequacy against one developer-written test, so a kill-incomplete test may still validly test a narrower reading of the requirement. However, the gap persists when only check-dependent kills count, and most kill-incomplete tests run a faulty line and still pass (Section 5.1), so the gap does not stem only from the test’s setup route. Moreover, mutants are artificial faults, but their detection correlates with that of real faults [22]. Equivalent mutants, which no test can kill, do not lower any score, because we count only the mutants that the ground-truth test kills. 

Internal validity. Due to the time budgets, the experiments did not repeat all agents’ test genera-tions multiple times on the whole benchmark to reduce the effects of agents’ non-determinism. We choose five configurations (Codex/DS, Codex/Luna, Claude Code/DS, OpenHands/DS, and Aider/DS) to regenerate twice to assess the effects. Up to 24% of their pass verdicts and 17% of their kill-complete verdicts flip, but their Pass@1 and KillComplete@1 change by at most 4.5 pp. Additionally, the target-hidden view rests on an LLM-drafted, author-accepted map of the target implementation, which may hide slightly more or less than the code that realizes the target behavior. However, the all-hidden view does not depend on this map, and it shows the same gap between passing and kill-complete tests. Finally, the projects are public and may be in the training data of some LLMs. But memorized developer tests would raise KillComplete@1 and thus narrow, not widen, the gap that we report. 

External validity. The eight projects were selected purposively, but they cover five languages, four BDD frameworks, six domains, and three test levels, and our reported gap appears in every one of them. Moreover, Gherkin Scenarios are more structured than most informal requirements. Informal requirements are likely to state even less of the setup and the expected outcome, so we expect the information gap to be larger for them, not smaller. Finally, both views in the benchmark remove the tests of all Scenarios, so that none reveals part of the ground truth. However, in practice, a developer who extends a test suite could read them. Our results thus concern writing a test without the tests of other Scenarios. We leave such cases in future work. 

7 Conclusion 

We presented Req2Test-Bench, a benchmark of 5,086 execution-validated requirement-to-test instances from 8 real projects. It evaluates a generated test by whether it passes and reproduces the fault detection of the developers’ own test. We evaluated eight agent–model–reasoning con-figurations, and found that the best-passing configuration passes 82.8% of the instances but is kill-complete on only 33.8%. Kill-incomplete tests mostly fall short where the requirement leaves the setup ambiguous or the expected outcome tacit. They take shortcuts instead of the project’s own fixtures and entry points, or check less than the developers’ tests. This gap persists even with costlier agent configurations, motivating requirement-grounded harnesses for test generation that guide requirement understanding, test validation, and project-specific knowledge acquisition.

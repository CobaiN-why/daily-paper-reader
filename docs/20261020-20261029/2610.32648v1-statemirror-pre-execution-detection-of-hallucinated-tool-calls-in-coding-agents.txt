1 Introduction 

Modern coding agents solve software engineering tasks by iteratively interacting with their envi-ronments [2, 44]. These agents typically follow the reasoning-and-acting (ReAct) paradigm [50], using tool calls to inspect repository contents, modify files, and run tests. However, these actions often lack grounding in the workspace, leading to failures such as referencing invalid filesystem paths, missing modules, or undefined symbols. We define this failure mode as hallucinated tool use , occurring when an agent’s proposed action violates preconditions imposed by the actual environment [10, 24]. Unlike reasoning flaws or semantic code bugs that execute successfully but fail the task, hallucinated tool use embeds invalid references (e.g., non-existent entities) into tool calls, making them fundamentally unexecutable as intended. Figure 1 illustrates two hallucinated tool uses: (a) assumes an unexported symbol within a target namespace, (b) misinterprets the filesystem layout. To understand the impact of hallucinated tool use, we conduct a preliminary study analyzing 4,398 SWE-agent trajectories on SWE-bench-Extra [26, 48], identifying 9,595 hallucinated tool calls across 120,801 total calls. Our study reveals three key findings. First, hallucinated tool use is 

pervasive , occurring in 46.6% of failed and 32.3% of resolved trajectories. Second, recovering from these hallucinations is costly . 2 Background 2.1 ReAct-style Coding Agents 

Interactive coding agents complete software engineering tasks by combining reasoning and tool use. This process typically follows the ReAct paradigm [50]. In this loop, the agent generates a structured action, the environment executes it, and the harness returns an observation. Various agent runtimes and repair systems operate within this paradigm by translating model outputs into environment commands [2, 48, 54]. Additionally, prior studies investigate different formats for these actions, such as direct code execution or standardized JSON schemas [43, 49]. While earlier models focus on simple API invocation [30, 31, 34], software-engineering agents automate complex tasks like test generation and behavior recovery [17, 33]. However, integrating and running these agents in real-world systems remains highly challenging [6, 22]. Our work focuses specifically on the tool-use loop of these coding agents. We analyze the proposed tool calls and their arguments rather than the internal reasoning of the model. 

2.2 Preconditions and Runtime Checking 

In axiomatic semantics of programs, pre- and post-condition reasoning is concerned with checking that on any program input satisfying the precondition 𝑃 , the program output should satisfy the postcondition 𝑄 . For example, the precondition 𝑃 may be that an input file exists or that some variable value is positive, and the postcondition 𝑄 may specify the verification condition that we want to be satisfied. Pre- and post-condition checking underlies many program verification techniques, including static analysis tools such as Dafny [18] or Frama [8] or dynamic analysis techniques such as runtime monitoring [19]. 

3 Preliminary Study 

We conduct a preliminary study of hallucinated tool calls in coding-agent trajectories, manually characterizing their prevalence, recovery costs, and root causes. 

3.1 Problem Statement 

To formalize the interaction between agent actions and the execution environment, we define a state 𝑠 as the state of the workspace and harness context immediately prior to an action’s execution. This state encompasses concrete, verifiable environment properties, including the file tree, active working directory, available packages, and exported symbols. 3.2 Study Setup 

We conduct a pilot study to investigate the hallucinated tool use problem, followed by three research questions (RQs): (1) RQ1: Does hallucinated tool use exist in real coding-agent trajectories, and what is its prevalence? (2) RQ2: What is the recovery cost of hallucinated tool calls in terms of agent steps and tokens? (3) RQ3: What is the distribution of different types of hallucinated tool use? 

3.2.1 Dataset and Ground Truth. We analyze hallucinated tool use through a systematic three-stage workflow consisting of automated screening, human adjudication, and cost replay. We identify and validate hallucinated tool calls in two stages. First, during automated screening, we analyze a public corpus of 80,036 SWE-agent runs [25] on SWE-bench-Extra [26], which spans a broader set of Python repositories than the original SWE-bench [15]. To compare behaviors across different outcomes, we retain one trajectory per issue and outcome, yielding 3,560 failed trajectories (with 107,308 actions) from 1,274 repositories and 838 resolved trajectories (with 13,493 actions) from 491 repositories. From these trajectories, we identify candidate mismatches through two channels: (1) execution failures filtered by deterministic rules and (2) editor command errors rejected directly by the harness. Second, in the human adjudication stage, two co-authors independently annotate these candidates by inspecting the exact workspace state and full trajectory history of each action, resolving disagreements through a third annotator. In total, this process confirms 9,595 hallucinated tool calls in total (4,715 from execution failures and 4,880 from harness rejections), establishing a ground-truth dataset of hallucinated tool calls.

3.3.2 RQ2: Recovery Cost of Hallucinated Tool Use. To quantify the execution cost of hallucinated tool calls, we trace the 1,931 trajectories containing at least one confirmed hallucination. We define a hallucination episode as the sequence of actions starting from an initial hallucinated tool call and spanning all subsequent attempts until recovery . Recovery occurs when the agent successfully executes the intended command without error, correctly referencing the target entity (e.g., a module, symbol, or path extracted from the execution feedback). We measure the episode cost in agent steps and tokens, using the cl100k tokenizer [27]. In total, we analyze 1,606 episodes originating from commands with an identifiable target entity. We exclude harness-channel hallucinations because agents rarely re-run the same editor command after a harness error. Hallucinated tool calls impose substantial recovery costs. A recovered episode consumes a median of 3 agent steps and 22.4K tokens before a grounded retry. Across the 1,120 recovered episodes, these attempts consume 39.3M tokens in total. In addition, 30.3% of episodes are never retried after the error; in these cases, agents proceed for a median of 18 subsequent steps and eventually fail the task. Thus, hallucinated tool calls add execution overhead, consuming agent steps and tokens and slowing task completion.

4 Methodology 4.1 Overview 

StateMirror is a lightweight detector designed to assess action feasibility before execution. As shown in Figure 3, StateMirror includes four stages: normalization, predicate extraction, environ-ment probing, and reporting. The extractor depends on action syntax, and the prober depends on the workspace and runtime artifacts available at check time. Both components can be extended for new tools or environments without changing these stages. 

4.2 Normalization 

To handle different forms of agent actions, such as shell commands and structured tool calls, 

StateMirror normalizes each proposed action into a unified representation for subsequent analysis. This representation captures the action type, current working directory, tool parameters, shell command, and associated Python code. For shell commands that invoke Python scripts (e.g., python reproduce.py ), StateMirror reads the script from the current workspace and includes its source code in the normalized representation when available. This allows subsequent predicate extraction to analyze the code that the harness would execute.

4.3 Extraction & Probing 

Hallucinated tool use occurs when a proposed action assumes environmental conditions that do not hold in the actual execution environment. To detect such mismatches, StateMirror extracts the implicit assumptions from proposed actions as explicit predicates and verifies them against the current environment by probing into the environment. 

4.3.1 Extraction. Given a normalized action, StateMirror extracts typed predicates that represent the environmental conditions required for its execution. Depending on the action type, the extractor analyzes shell commands, structured tool parameters, and Python code. For Python code, it parses the source into an abstract syntax tree (AST) on demand to identify relevant operations and their dependencies. Each extracted predicate specifies a concrete requirement, such as the availability of a Python module, the existence of a filesystem path, or the validity of a tool argument. When a required value cannot be determined statically, the corresponding predicate is omitted. 

4.3.2 Probing. For each extracted predicate, StateMirror performs read-only checks against the current execution environment. Depending on the predicate type, these checks inspect the reposi-tory structure, Python module definitions, filesystem metadata, runtime information, or harness schemas. A predicate is considered violated when the corresponding environmental requirement is confirmed to be false. When a check cannot reliably determine whether a requirement holds, 

StateMirror conservatively allows the predicate to pass and records the uncertainty in the probe evidence. 

4.3.3 Predicate Families. Motivated by Finding #3, we organize the extracted predicates into four families: Python namespace and package layout, filesystem and working directory, command and runtime state, and harness and tool schemas. As shown in Figure 4, these families capture the main types of environmental assumptions identified in our preliminary study. Each family defines specific predicates and corresponding checks to verify these assumptions against the execution environment. StateMirror also supports extensions to new tools and environments by introducing additional predicates and their corresponding extractors and probers.

Since a module may exist without exposing a requested symbol, StateMirror examines both module availability and namespace contents, including symbols exposed through package re-exports. To identify these requirements, StateMirror parses the AST of the Python code included in the normalized action and extracts predicates such as importable , symbol_defined , and is_package .It then verifies these predicates against the repository structure, standard library, and installed packages by inspecting module definitions and common re-export patterns (e.g., __init__.py ). To limit probing overhead, StateMirror restricts dependency analysis to imports directly referenced in the proposed action or its invoked scripts. Predicates involving names that cannot be resolved statically are omitted. Figure 4(a) illustrates an example involving a missing Python symbol. The agent proposes a script containing from dvc import DVC . From its AST, StateMirror extracts importable(dvc) 

and symbol_defined(dvc, DVC) . The prober confirms that the dvc package exists but finds no definition or re-export of DVC in dvc/__init__.py . It therefore evaluates symbol_defined(dvc, DVC) as false. This violated predicate identifies a hallucinated tool call that would otherwise result in an ImportError .

• Family II: Filesystem and Current-Working-Directory State. This family verifies assump-tions about filesystem paths and the current working directory (cwd). Such verification is important because agents may repeatedly attempt to access nonexistent paths, wasting execution steps and computational resources on unsuccessful operations and subsequent recovery. To identify these mismatches, StateMirror considers both the current cwd and the type of file operation (e.g., reading, writing, or executing a file). Specifically, relative paths are resolved against the current cwd, while different operations impose different requirements. For example, reading or executing a file requires the target to exist, whereas creating a file generally requires an existing parent directory. Accordingly, StateMirror extracts path arguments from shell commands, Python file operations, and editor actions, generating operation-specific predicates such as file_exists 

and parent_dir_exists . The prober then checks whether the target files or directories exist at the resolved paths. When a path cannot be determined statically, the corresponding predicate is omitted.

• Family III: Command, Test, and Runtime State. This family verifies assumptions about command availability, test targets, and runtime requirements. Checking these assumptions before execution can prevent unnecessary command attempts and test runs, reducing the time and resources spent on diagnosing and correcting invalid actions. To detect these mismatches, StateMirror analyzes shell commands and command-related tool parameters to extract executable names, pytest targets, and explicit runtime-version re-quirements. It represents these requirements using predicates such as executable_available ,

pytest_target_exists , and runtime_version_satisfies . The prober then checks executable availability and runtime-version information in the current environment. For pytest targets, it examines the target file and its static AST nodes to check whether the requested test exists. Figure 4(c) illustrates a missing pytest target case. The agent proposes an action, pytest test_sqlparse.py::test_tokenize -q , to verify a fix. From the command, StateMirror ex-tracts pytest_target_exists(test_sqlparse.py, test_tokenize) . The prober confirms that 

test_sqlparse.py exists and inspects its AST for the requested test node. Since no matching function or method is found, the predicate evaluates to false. StateMirror thus identifies the invalid test target before the command is executed. 

• Family IV: Harness and Tool Schemas. This family verifies assumptions about tool argument schemas and the current harness state. Invalid tool arguments or unmet harness requirements may cause tool calls to be rejected, resulting in additional agent steps and recovery costs. To identify these mismatches, StateMirror examines tool argument constraints (e.g., argu-ment counts, types, and formats) and conditions maintained by the harness (e.g., whether a file is currently open and whether a specified line number is valid). Accordingly, StateMirror 

extracts schema predicates, such as tool_args_valid , and condition-dependent predicates, in-cluding tool_path_arg_exists , editor_file_open , editor_line_in_range , and path_absent .The prober then checks these predicates against tool signatures, the filesystem, and information provided by the harness. For file editing tools, StateMirror identifies the currently open file from the preceding tool response. When the required information is unavailable, the corresponding predicate is omitted. Figure 4(d) illustrates a tool argument mismatch. The agent issues search_file "ClassDef" 100 1200 , intending to search lines 100–1200. However, the tool signature search_file <term> [<file>] interprets 100 as the file argument. Accordingly, StateMirror extracts the predicate 

tool_path_arg_exists(100, file) . The prober finds no file named 100 in the current working directory, causing the predicate to evaluate to false. This result identifies a hallucinated tool call that the harness would otherwise reject due to an invalid file argument. 

4.4 Hallucination Reporting 

After probing, StateMirror collects predicates whose probes return into a false-predicate set. If the set is non-empty, the proposed action is identified as a hallucinated tool call. Each violated predicate is reported as a typed warning that describes the mismatch between the proposed action and the actual environment.

5 Evaluation 

We evaluate the performance of StateMirror by answering the following RQs: 

• RQ4: How accurately does StateMirror detect hallucinated tool calls?

5.1 Environment and Implementation 

We implement StateMirror as a Python toolkit (5.8K lines of code) that normalizes actions and checks predicates using deterministic, read-only probes. It operates without executing actions or consuming LLM tokens. For runtime evaluation, we integrate it with SWE-agent [48]. All experiments run on an Apple M4 Max machine with 36 GB RAM using Docker, executing tasks within their official SWE-bench containers. For offline evaluation, we reconstruct the pre-action workspace by replaying preceding edits and withhold all execution outcomes. We access all LLMs through the OpenRouter API [29], set the temperature to 0, and use direct import checking by default. 

5.2 Dataset 

The preliminary study establishes a human-adjudicated workflow for recognizing pre-execution hallucinated tool calls in SWE-agent failures. We extend this workflow to publicly available failed trajectories from SWE-agent [48], OpenHands [44], Sonar [35], and Honeycomb [11], constructing a benchmark with expert-labeled positives and negatives. Unlike the preliminary study, we build the benchmark exclusively from failed trajectories. Because a hallucinated tool call is defined by the mismatch between the action and its pre-action workspace rather than the final task outcome, its label remains independent of task resolution. We focus on failed runs because execution-failure evidence naturally concentrates there, and our public data sources (OpenHands, Sonar, and Honeycomb) primarily provide failed trajectories. To ensure comprehensive evaluation, RQ4 also separately reports the performance on resolved-run instances collected during the preliminary study. Specifically, we harvest 2,687 candidate failure actions across the four agent sources through automated keyword and traceback retrieval. Human annotators independently inspect each candi-date to identify hallucinated tool calls, resolving discrepancies through consensus adjudication. 5.3 Metrics 

We evaluate StateMirror using the following metrics: 

• Detection Effectiveness: Precision, recall, F1-score, and Accuracy against ground-truth labels to evaluate hallucination detection performance. 

• Computational Efficiency: Execution latency (mean, median, p95, p99, and max) and token consumption to quantify pre-execution detection overhead. 

• Mitigation Performance: We measure two aspects: (1) action repair rate, which is the proportion of warned actions successfully replaced by the agent to clear the gap, and (2) intervention efficiency, which measures the savings in agent time, steps, and tokens per task achieved by blocking actions that would otherwise fail on execution. We also report the task resolve rate to verify that these savings preserve task success.

• Scaffold Linter: A static linting baseline that inspects generated code for local construction-level errors (e.g., undefined names) but does not resolve imports against the workspace.

5.5 RQ4: Effectiveness Analysis 

Table 3 compares StateMirror against baseline approaches. We observe that conventional ap-proaches struggle with the trade-off between coverage and grounding. The action-only baseline achieves decent recall but produces high false positives because it inspects proposed commands only; without checking the underlying repository, it flags valid actions simply because they look unusual. We further analyze the failure cases of StateMirror , as detailed in Table 4. The 390 false negatives are heavily concentrated in the pre-execution action extraction layer rather than state probing logic, with code extraction, command extraction, and selected-file reconstruction accounting for 73.8% (288/390) of misses. These misses primarily stem from implicit preconditions omitted by the action extractors, including library-call arguments, CLI options, and unmaterialized test files, which account for Honeycomb’s higher FN count (209 misses). Across predicate families, symbol predicates achieve the highest recall (0.802), while import (0.703) and file/path (0.736) capture the vast majority of positive hallucinated tool calls. 5.9 RQ8: Mitigation of Hallucinated Tool Calls 

We investigate how effectively StateMirror mitigates detected hallucinated tool calls within agent workflows, at two levels with recovery instructions (as illustrated in Figure 5). Action repair asks whether a typed warning lets the agent replace the faulty action with a valid one, under both controlled revision and live agent execution. Pre-execution intervention asks whether blocking the faulty action before it runs removes the downstream cost the hallucination would otherwise cause over the rest of the task. We run StateMirror in two modes: report mode , which logs every warning without blocking, and intervention mode , which applies a conservative blocking rule. In intervention mode, StateMirror blocks an action and prompts regeneration only if a falsified predicate is a necessary precondition, such as an executable or a file to be read. It permits predicates related to intentional side effects (e.g., files the action aims to create) and diagnostic errors (e.g., missing dependencies within existing test files), blocking test commands only when the test target or runner itself is missing.

7 Related Work 

Coding Agent Auditing and Debugging. As interactive coding agents grow more popular, researchers have developed various auditing, debugging, and post-execution repair techniques [42, 45]. Traditional debugging and automated repair methods analyze failures after program execution to locate faults or suggest patches [9, 14, 16, 20, 47, 51]. Similarly, feedback-driven agent systems run commands and use the resulting runtime tracebacks to correct their actions [7, 36]. Other trajectory analysis frameworks evaluate multi-turn loops to identify failure patterns [3, 4, 21, 23], or analyze execution trajectories and their prefixes for failure attribution, diagnosis, online detection, and repair [1, 5, 52, 53, 57]. While AgentSpec [41] can perform pre-execution checks using rules 

, Vol. 1, No. 1, Article . Publication date: October 2026. 18 Shiwen Shan, Yintong Huo, Zhiying Wu, and Yuxin Su 

derived from user-specified safety requirements, StateMirror derives factual preconditions from the proposed tool call itself and verifies them through deterministic probes of the current execution environment. The post-hoc limitation is particularly evident when dealing with hallucinations in generated code. In language models, hallucination represents output that is unfaithful to a source or to the real world [12]. For code generation tasks, these errors often remain hidden until the program actually runs. For example, models frequently generate code that references unpublished packages [38] or fails during execution [40, 46, 55]. While existing methods analyze or mitigate errors in finished code snippets [13], they do not check whether the required modules, symbols, and paths are present in the target workspace before running the agent’s next tool call. Post-execution systems generally run actions first and resolve errors using tracebacks, which often increases execution steps and token consumption. In contrast, StateMirror serves as a proactive gate that verifies repository requirements with lightweight, read-only state probes before execution. 

8 Threats to Validity 

Internal threats. To ensure internal validity, we mitigate annotation subjectivity by establish-ing benchmark labels through independent expert annotations and consensus adjudication. We reconstruct workspace states with high fidelity by replaying verified prefix edits. Furthermore, our evaluation includes both failed and resolved trajectories across four different agent frameworks to minimize framework-specific bias. On the resolved stratum, we observe a lower recall because some errors involve dynamic runtime states rather than static mismatches. Currently, our deterministic predicates prioritize actionable, high-precision static checks. Extending this validation to dynamic, execution-time errors represents an important avenue for future work. 

External threats. While our current empirical evaluation is instantiated on Python bug-fixing tasks, SWE-agent trajectories, and the Qwen3.8-27B model, the StateMirror architecture is de-signed for broad generalizability. Because it verifies foundational execution assumptions (e.g., filesystem and namespace states) rather than relying on bug-fixing-specific heuristics, its core formulation naturally extends to other coding agents such as code-generation agents and testing agents. Generalizing StateMirror to new programming languages or agent runtimes involves implementing domain-specific predicate extractors and probers, while the overall pre-execution detection workflow remains intact. 

9 Conclusion 

Hallucinated tool use occurs when an agent’s action assumes invalid workspace preconditions. Our preliminary study of 4,398 trajectories reveals these errors are highly prevalent, expensive to recover, and concentrated in filesystem and namespace mismatches. To address this, we present 

StateMirror , a lightweight pre-execution detector that extracts predicates from actions and de-terministically validates them against the live environment. Evaluation on 2,508 actions shows 

StateMirror achieves 0.940 precision and 0.817 F1, outperforming the strongest LLM judge by 35.3% in F1 with zero token cost and millisecond latency. For practical mitigation, StateMirror 

enables agents to rectify over 95% of hallucinated tool calls, reducing execution time by 15.8% and token consumption by 11.8% during live intervention.

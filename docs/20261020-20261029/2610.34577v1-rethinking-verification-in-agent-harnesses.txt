# RETHINKING VERIFICATION IN AGENT HARNESSES 

Zhengxin Zhang 1∗, Erkang Zhu 2, Yin Lin 2, Claire Cardie 1, Bolin Ding 2, Jingren Zhou 21Cornell University 2Alibaba Group 

## ABSTRACT 

Agent harnesses enable large language models to act through tools, observe the results, and iteratively work toward a task goal. Verification checks and revises agents’ work to improve output quality. Yet there is limited guidance on how har-nesses should organize this effort. We study verification as an axis of test-time scaling by examining when to intervene, who checks the work, and how checking leads to revision. Our framework spans four layers of the agent lifecycle: initial instructions, mid-turn reminders, completion gates, and independent review. We compare 17 designs across seven frontier coding models on Terminal-Bench (TB) and SWE-bench Verified (SWE), and introduce VisualBench for expert evalua-tion of visual and interactive artifacts. Initial instructions and execution-time re-minders yield modest, model-dependent average gains on the coding benchmarks, without substantially increasing average output token use. Completion gates can yield larger gains but may substantially increase cost. Independent review by a critic offers a more favorable accuracy–cost tradeoff, improving average accuracy by 5.9–9.5 percentage points on TB and 3.9–6.6 on SWE at 1.13 –1.25 × and 1.00 –

1.04 × baseline cost, respectively. On VisualBench, independent review achieves net preferences of 13 .2–23 .8 points over the baseline across its four designs, ex-ceeding the evaluated L0–L2 designs. Additional review rounds or independent critics further improve average TB accuracy by up to 3.5 percentage points. To-gether, these results provide empirical guidance for verification design in agent harnesses and support independent review as a practical axis of test-time scaling. 

## 1 INTRODUCTION 

Coding agents built on large language models (LLMs) tackle long-horizon software engineering tasks, including resolving repository-level issues across large codebases (Yang et al., 2024; An-thropic, 2026a; OpenAI, 2026; Google, 2026). These agents run inside harnesses that let the model act through tools, observe the results, and iterate toward a task goal (Yao et al., 2022; Yang et al., 2024). Beyond exposing tools, the harness specifies the agent’s instructions, controls intervention timing, and coordinates verification before accepting its work (Bolin, 2026; Lopopolo, 2026). These choices allocate computation to checking and revising the agent’s work, making verification an im-portant part of harness design (Lopopolo, 2026). Prior work develops learned verifiers for selecting solutions (Cobbe et al., 2021; Lightman et al., 2023), self-correction through critiques and reflections (Madaan et al., 2023; Shinn et al., 2023), and tool-assisted checks that return execution evidence for repair (Gou et al., 2023; Chen et al., 2023; Huang et al., 2023a). In practice, verification in agent harnesses is often shaped by engineering heuristics and iterative experience: Claude Code provides hooks for completion checks (Anthropic, 2026b), while Codex uses self-review and iteration (Lopopolo, 2026). Yet systematic evidence remains limited on how to design and scale verification, when a design improves performance, and whether its gains justify the additional computation. Without this guidance, current designs may be suboptimal for a given model or task. In this paper, we study verification as an axis of test-time scaling in agent harnesses. We organize the design space around three questions: when to intervene, who should check the work, and how findings should lead to revision. ## 2 RELATED WORK 

Verification. There is a line of works exploring verification for assessing candidates, guiding self-correction, and checking outputs against external evidence. Learned verifiers score complete so-lutions or intermediate reasoning steps to guide candidate selection (Cobbe et al., 2021; Lightman et al., 2023; Wang et al., 2024a). Code-focused assessment ranges from trained critics that high-light bugs (McAleese et al., 2024) to review protocols that combine agent judgments or introduce structured disagreement (Tang et al., 2024; Qiu & Gill, 2026). Self-correction methods use natural-language critiques and reflections to revise outputs or improve subsequent attempts (Madaan et al., 2023; Shinn et al., 2023). Training-based approaches further teach models to improve across succes-sive attempts through fine-tuning or multi-turn reinforcement learning (Qu et al., 2024; Kumar et al., 2024). Studies of reasoning correction and code repair examine the limits of self-generated feedback and show that reported gains depend on feedback quality and the cost of additional attempts (Huang et al., 2023b; Olausson et al., 2023; Kamoi et al., 2024). Tool-assisted verification grounds error detection in evidence from code execution and external tools (Chen et al., 2023; Gou et al., 2023), while dedicated test-generation and execution agents return test feedback to guide code revision (Huang et al., 2023a). Together, these strands provide the assessment and feedback mechanisms from which harness-level verification designs can be built. 

Agent harnesses. Agent harnesses determine how models interact with tools and environments by organizing instructions, tool interfaces, execution flow, and context. Prior work studies interleaved reasoning and action (Yao et al., 2022), agent–computer interfaces (Yang et al., 2024), execution platforms (Wang et al., 2024b), and structured repair workflows (Xia et al., 2024). These studies examine how the surrounding execution design shapes agent behavior. Harness design also governs how computation and information are used across attempts, including agent sampling and selection (Zhu et al., 2025) and reuse of coding rollouts through structured summaries (Kim et al., 2026). Agent harnesses have become an essential part of modern coding agents, including Claude Code (Anthropic, 2026a), Codex CLI (OpenAI, 2026), and Gemini CLI (Google, 2026). These works establish useful assessment mechanisms and agent workflows, but offer limited com-parative guidance on how a harness should organize checking and revision. ## 3 VERIFICATION DESIGNS 

In this section, we introduce verification designs by following the agent lifecycle, from receiving a task to delivering a result as shown in Figure 1. Table 1 summarizes when each layer intervenes, who checks the work, and how execution continues. Before execution begins, the agent receives the task and the instructions that guide its work. At this stage, L0: Initial instructions introduces verification guidance into the initial prompt. We vary the message role of the verification instructions: System or User . In the System variant, we append it to the system prompt as standing guidance. Because users do not always include verification instructions in their requests, we introduce a User variant that appends the same prompt to the initial user request. Both variants ask the agent to run the deliverable through its intended interface, inspect the output, and fix observed defects. The L0 verification instructions are in Appendix E.1. For visual or interactive artifacts, the instruction also asks the agent to render the result and exercise its core interactions. The L0 verification instructions for visual tasks in our VisualBench are in Appendix E.1. As execution proceeds, changes to the codebase accumulate across turns. In our experiment, we find that only 6.2–13 .6% of detected editing turns are followed by a recognized checking command 3before the next editing turn or the end of the run, as reported in Appendix Table 7. We therefore introduce L1: Execution-time reminders to encourage the agent to check recent changes as it works, creating opportunities to identify and correct errors before further changes accumulate. These reminders arrive after tool results and before the next model call, so the agent can check its recent changes before continuing. We evaluate three designs. Periodic reminder (System) sends a reminder a few turns after the edit. After-edit reminder (System) sends the same reminder after a turn that changes a file. These two designs use a marker identifying the message as an automated self-verification checkpoint. After-edit reminder (User) uses the same edit-based trigger but delivers the reminder as a user message without that marker. Thus, the first comparison varies the trigger, while the second varies the message role and the presence of the automated marker. The L1 verification instructions are in Appendix E.2. When the agent attempts to finish, L2: Completion gates reopen the agent’s work for checking and revision. To examine how the requested action guides subsequent checking and revision, we vary whether the gate asks the agent to inspect changes or run checks, or rejects completion and asks it to continue working. We vary the message role ( System or User ) and whether user messages carry an automated marker to study how these choices affect the agent’s response. We also vary intervention timing to test whether reserving time for checking and repair improves outcomes. The L2 prompts and triggering rules are in Appendix E.3. Before final acceptance, the harness can also assign verification to a separate model, which we call the critic . This introduces L3: Independent review : the critic starts in a fresh context and assesses the agent’s deliverable. The critic receives the task specification and access to the live sandbox, where it can run its own checks. The critic returns its findings to the agent for revision. We vary the critic’s context and whether its checks are guided by task requirements alone ( Task-first ) or also by the agent’s assumptions and claims ( Claim-guided ). The Changes condition provides the critic with the task and the agent’s changes. The Trajectory condition provides the task, changes, and the agent’s execution trajectory. The critic instructions are in Appendix E.4. 

## 4 EXPERIMENTAL SETUP 

Models. We evaluate seven coding models through Alibaba Cloud Model Studio (DashScope): Qwen3.7-Max (Qwen Team, 2026a), Qwen3.8-Max (Qwen Team, 2026b), GLM-5.2 (Z.ai, 2026), DeepSeek V4-Pro (DeepSeek-AI et al., 2026), DeepSeek V4-Flash (DeepSeek-AI et al., 2026), Kimi-K2.7-Code (Moonshot AI, 2026), and MiniMax-M2.5 (MiniMax, 2026). Qwen3.7-Plus serves as the independent critic for every coding model. 

Benchmarks. We evaluate on task subsets from Terminal-Bench 2.1 (TB) (Merrill et al., 2026) and SWE-bench Verified (SWE) (Jimenez et al., 2023; OpenAI, 2024), both with automatic graders. Task selection aims to cover a range of difficulties, using baseline success rates for TB and human time-to-fix tiers followed by baseline evaluation for SWE. Appendix A.1 provides task counts and the selection procedure. Each coding condition is configured for three trials per model and task. VisualBench contains 18 visual and interactive tasks. Each provides a task description and any sup-porting files, and asks the agent to produce an artifact, such as a playable game, an interactive 3D configurator, or a sales data explorer. For models without native visual capabilities, a look_at tool renders the artifact and returns a description from Qwen3.7-Plus. Raters from an internal company data team compare artifacts from a verification condition and the baseline for the same task and model, with conditions hidden and sides randomized. They receive the task brief and short interac-tion instructions, and judge functionality and visual quality against the task requirements. Outcomes are recorded as wins, losses, or ties; cases where both artifacts fail are recorded separately. We eval-uate one representative design from each of L0–L2 and four L3 designs, with two trials configured per task, model, and condition. Appendix C provides the full descriptions of all 18 tasks, expert instructions, and screenshots of the evaluation interface. 

Environment. All experiments run in E2B cloud sandboxes (E2B, 2026), orchestrated with Harbor (Harbor Framework Team, 2026). Each trial starts in a fresh sandbox containing the task files, dependencies, and execution tools. The agent interacts with this environment by reading and editing files, running commands, and inspecting outputs. For independent review, the critic accesses the same workspace to examine the deliverable and execute its own checks. ## 6 CONCLUSION 

In this paper, we systematically study verification in agent harnesses, comparing 17 designs across four layers of the agent lifecycle and seven frontier coding models on TB and SWE, with evaluation on VisualBench. We examine when to intervene, who checks the work, and how feedback leads to revision. Initial instructions and reminders yield modest, model-dependent coding gains without substantially increasing average output token use. Completion gates can improve accuracy but may substantially increase cost. Independent review offers a more favorable accuracy–cost tradeoff on TB and SWE. On VisualBench, its four designs achieve net preferences of 13 .2–23 .8 points over the baseline, exceeding the evaluated L0–L2 designs. Additional rounds or critics further improve average TB accuracy by up to 3.5 percentage points. Together, these results provide empirical guidance for verification design in agent harnesses and support independent review as a practical axis of test-time scaling. 9ETHICS STATEMENT

The human comparison covers seven designs. For L0–L2, we select one representative intervention per layer: the system verification instruction, the after-edit user reminder, and the user recheck request with the 80% early trigger. These use the same intervention definitions as TB and SWE. For L3, we compare changes-based and trajectory-based review, each with and without required visual inspection. Each design is compared with the baseline for the same task and coding model. Review depth and width are studied separately on Terminal-Bench. Each task supplies a description and any supporting files without a reference implementation. Tasks run in an environment with Python, Chromium, and ffmpeg, with additional tools where required. Browser artifacts run offline, with bundled libraries only where the task permits them. 

Raters and briefing. The raters are members of an internal company data team. Before rating, the interface presents a briefing explaining the study’s purpose, the blinded comparison, the four response options, and a worked example of applying the criteria. 

Consent, compensation, and ethics approval. The human evaluation received ethics approval. Raters provided informed consent and were compensated under their existing contracts with the company. 

Blinded comparison. Raters compare artifacts for the same task and model with verification con-ditions hidden and sides randomized. The interface presents the original task brief, its judging criteria, and a short set of task-specific interaction steps. Both artifacts can be inspected side by side or opened individually at full size. Raters interact with live artifacts where available and inspect delivered recordings or renders where appropriate. 

Instructions to raters. The rating interface gives the following guidance: 1. Read the original task brief before comparing the artifacts. Judge against what the task asks for, including its functional and visual requirements. 2. Follow the task-specific interaction checklist on both artifacts. Click, drag, type, or play as needed to check the requested behavior; use the full-size view when the side-by-side view is too small. For keyboard controls, first click inside the artifact to give it focus. 3. Choose A or B when one artifact better satisfies the task. Choose a tie when both work and you cannot distinguish their quality. Choose both fail only when neither makes a meaningful attempt at the task, such as when both are blank, broken, or unrelated to the request. An artifact that works poorly does not by itself justify both fail. 4. If only one side produces a usable deliverable, choose that side even if it is rough. If a page appears blank, refresh it once before judging. Visual polish should not outweigh missing functionality unless visual quality is itself the task’s objective. 5. Optionally leave a short comment explaining the deciding issue, especially when the two artifacts are difficult to distinguish.

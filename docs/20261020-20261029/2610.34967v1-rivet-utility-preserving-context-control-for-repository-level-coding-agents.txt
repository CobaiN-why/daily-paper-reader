HONGYU ZHANG †, Chongqing University, China Repository-level code generation asks an agent to implement a task requirement inside an existing repository. To produce code that works in the repository, the agent needs repository evidence , such as target locations, helper definitions, caller usages, and configuration constraints, which determine how the code should be located, integrated, and executed. Because the context budget cannot hold the entire repository, existing retrieval, compression, and structure-aware methods select context by task similarity, context length, or structural proximity, but these criteria do not directly measure whether the selected context contains this evidence. As a result, the selected context can appear relevant to the task yet miss the evidence that the implementation depends on. We call this failure mode context utility dilution . In this paper, we propose Rivet, a context control framework that preserves repository evidence for coding agents under a fixed context budget. Rivet first uses Signal Grounding to select task-related code anchors by fusing lexical, semantic, and structural signals. Utility Linking then expands these anchors through dependency, usage, and configuration relations to collect repository evidence. Finally, Budget Shaping packs the evidence by priority and, when the budget is tight, reduces snippets to signatures or summaries before dropping them. We evaluate Rivet on two executable repository-level benchmarks, DevEval and RepoExec, with four backbone models, two context budgets (4K and 8K tokens), and eight baselines. Rivet achieves the highest Pass@1 in all 16 settings and improves over the strongest baseline by 3.73–5.15 percentage points on average. Moreover, GPT-5-mini with Rivet outperforms GPT-5 without Rivet on both benchmarks while reducing inference cost by 73.3%–84.5%. 1 Introduction 

Given a task requirement and an existing repository, repository-level code generation asks an agent to produce code that satisfies the requirement within that repository [2, 23, 38, 40]. Unlike isolated programming tasks, the produced code must work with existing files, definitions, dependencies, and configurations in the target repository [16]. To produce code that works in the repository, the agent needs repository evidence , i.e., repository information that constrains the implementation, such as target locations, helper definitions, caller usages, and configuration constraints. Repository context is therefore useful only to the extent that it contains such evidence. However, a repository rarely fits into the context budget of a coding agent, so the agent can only see a selected part of it [33]. Existing context-control methods address this constraint through retrieval-based selection, compression-based shortening, and structure-aware selection [14, 18, 19,

Compression methods shorten retrieved repository context or agent observations to fit the context budget [27]. Structure-aware methods use code structure, such as dependencies or call relations, to retrieve context connected to the task [7, 14, 18]. These criteria provide useful signals for context construction, but a high relevance score, a compact representation, or structural proximity alone does not ensure that the context includes the helper definitions, caller usages, and configuration constraints needed for a particular implementation. We call the resulting failure mode context utility dilution : the selected context appears relevant to the task but lacks the evidence needed to implement the required code correctly in the repository (Section 2). 

In this paper, we propose Rivet , a context control framework that preserves repository evidence for repository-level coding agents. Our key observation is that much of this evidence is reachable from the code that the task touches, through static relations such as imports, symbol references, call sites, and configuration links. Therefore, instead of ranking snippets independently by their similarity to the task, Rivet first locates where the task lands in the repository and then follows these relations to collect evidence. Following this observation, Rivet constructs repository context in three stages. ❶ Signal Grounding first uses lexical, semantic, and structural signals to identify task-related code anchors that indicate where the required code is likely to be implemented or what existing snippets it may depend on. ❷ Utility Linking then expands these anchors through dependency, usage, and configuration relations to collect helper definitions, caller usages, and configuration constraints. ❸ Budget Shaping finally packs the evidence by priority tiers and, when the budget is tight, reduces snippets to signatures or summaries before dropping them. In this way, Rivet spends the budget on evidence that constrains the implementation rather than on text that merely resembles the task. With a 4K budget, it outperforms the strongest baseline given an 8K budget on DevEval for all four backbone models, and GPT-5-mini with Rivet outperforms GPT-5 without Rivet while reducing inference cost by 73.3%–84.5%. 2 Motivating Example 

Figure 1 shows a DevEval task in which an agent needs to implement the utility function is_json_ serializable in the module benedict.utils.type_util of an existing Python repository. The target function is expected to determine whether a given value is JSON serializable. Although the requirement is concise, the required code cannot be derived from the requirement alone [10]. To produce code that works in this repository, the agent needs repository evidence, including the target location, relevant helper definitions, caller usages, and configuration constraints. A relevance-oriented retrieval method may return code snippets related to JSON serialization or type checking. These snippets appear relevant because they share terms with the requirement, but they may miss the evidence that constrains how the function should be implemented in this repository. For example, without helper definitions, the agent may reimplement behavior that should reuse project-specific utilities. Without caller usages, it may produce an interface or return value that does not match how the function is used. Without configuration constraints, it may generate code that cannot execute correctly in the project environment [34]. Under a limited context budget, these relevant but incomplete snippets can occupy the context and leave little room for the evidence that actually constrains the implementation [11]. For this task, useful context should include not only snippets related to JSON serialization, but also the target module benedict.utils.type_util ,relevant helper definitions, caller usages, dependencies, and configuration constraints. With such evidence, the agent can determine not only what behavior to implement, but also how the required code should align with the existing repository. 3 Approach 

Given a task requirement, a repository, and a context budget, Rivet serves as a context-construction component for a repository-level coding agent. It constructs the repository context that is injected into the agent before code generation. The goal is to preserve the repository evidence that the implementation depends on, including target-location information, helper definitions, caller us-ages, and configuration constraints. Rivet operates at two granularities: Signal Grounding ranks repository files to locate where the task lands, while Utility Linking and Budget Shaping operate on code snippets within and around the selected files. Signal Grounding identifies task-related code anchors using lexical matching, semantic similarity, and structural propagation signals. Util-ity Linking expands these anchors through dependency, usage, and configuration relations to collect the repository evidence needed by the required code. Budget Shaping retains the resulting evidence under the context budget by prioritizing essential evidence and using compact representa-tions when necessary. Figure 2 summarizes the pipeline. We next introduce the problem setting, the repository evidence graph, the query construction, and the three stages of Rivet. 

3.1 Problem Formulation 

Problem setting. A task is specified by a natural-language requirement 𝑞 . A repository consists of a set of files 𝐹 and is parsed into a set of code snippets 𝑈 = {𝑢 1, . . . , 𝑢 𝑁 }, including functions, methods, classes, import blocks, and configuration blocks, each of which belongs to one file in 

𝐹 . Given 𝑞 , 𝑈 , and a context budget 𝐵 , Rivet selects and renders a repository context 𝐶 such that tok (𝐶 ) ≤ 𝐵 . The target location is not given to Rivet during context construction. Instead, Rivet Rivet: Utility-Preserving Context Control for Repository-Level Coding Agents 5

identifies task-related code anchors from the repository through Signal Grounding. When the requirement explicitly mentions code entities, such as the qualified name of the target function, Rivet exploits these mentions through query construction and a code-mention prior, but it never receives the ground-truth location. 

Repository evidence graph. We represent the repository as a directed, typed, weighted graph 

𝐺 = (𝑉 , 𝐸, 𝜏, 𝜔 ) with 𝑉 = 𝑈 . Each node is a code snippet, and each edge 𝑒 = (𝑢 →𝑣 ) represents a repository relation with type 𝜏 (𝑒 ) and weight 𝜔 (𝑒 ). We consider four types of relations that expose repository evidence around candidate code anchors. import and symbol-ref edges connect a snippet to definitions, imports, and referenced symbols that it depends on, thereby exposing helper definitions and dependency evidence. caller edges connect a snippet to existing call sites or usages that indicate how it is invoked. config edges associate configuration or packaging information with relevant repository code [29]. The edge weight 𝜔 (𝑒 ) reflects how strongly the relation indicates evidence needed by the required code. All three stages of Rivet operate on this graph. 

Query construction. Before Signal Grounding, Rivet converts the natural-language requirement 

𝑞 into a weighted query term set 𝑄 = {( 𝑤, 𝛾 𝑤 )} . The terms are extracted from the requirement text and any explicit code-like mentions in 𝑞 , such as identifiers, file paths, function signatures, and package names, and are split on camel-case and snake-case boundaries. Terms from explicit code-like mentions receive higher weights than general natural-language terms. The same query terms are used for lexical and semantic scoring, so that both signals are computed from the same task representation. 

3.2 Signal Grounding 

Signal Grounding aims to identify task-related anchor files from the repository. In this stage, 𝑢 

denotes a repository file, and the structural signal runs on the file-level import graph 𝐺 𝐹 , obtained by projecting the import edges of 𝐺 onto files, i.e., file 𝑢 links to file 𝑣 if a snippet in 𝑢 imports a definition from 𝑣 . These anchors serve as candidate locations for the required code and as starting points for collecting repository evidence in Utility Linking. To this end, Rivet combines three complementary grounding signals: lexical matching, semantic similarity, and structural propagation. The lexical signal captures explicit code-like mentions in the requirement, such as identifiers, file paths, and package names. The semantic signal captures files that are related to the task in meaning, even when their surface terms differ from the requirement. The structural signal propagates relevance over 𝐺 𝐹 to find files connected to high-relevance files through import relations. These signals address different failure cases of anchor localization. Lexical matching can miss renamed or project-specific helpers, semantic similarity can prefer textually related but unnecessary files, and structural propagation depends on reliable task-relevant seeds. Therefore, Rivet fuses the rankings from the three signals to select the final task-related code anchors. 

Lexical signal. The lexical signal identifies files that explicitly match code-like mentions in the requirement, such as identifiers, file paths, function signatures, or package names. We score each repository file 𝑢 with a fielded BM25 [31] model over four fields F = {path , symbol , sigdoc , content },which respectively capture the file path, defined symbol names, signature and docstring lines, and the identifier stream. Field weighting and length normalization reduce the bias toward long files that contain many incidental term matches. The resulting lexical score is denoted as 𝑠 lex (𝑢 ).

Semantic signal. The semantic signal identifies files that are related to the task in a latent term space, even when their surface terms differ. For example, a requirement may describe JSON serialization, while a reusable helper may use a project-specific name. To capture such cases without training a repository-specific retriever, we build a TF-IDF term–file matrix over file content and documentation and apply latent semantic analysis [9]. Each file and the task requirement are projected into the same latent space, and their cosine similarity is used as the semantic score 6 Pan et al. 

𝑠 sem (𝑢 ). For repositories too small to admit a stable factorization, we fall back to TF-IDF cosine similarity in the original term space. 

Structural signal. The structural signal identifies files that may be needed by the required code even when they are not textually similar to the requirement. We use the normalized sum of the lexical and semantic scores as seed relevance scores and diffuse them over the file-level import graph 𝐺 𝐹 with Personalized PageRank [13]. This propagation allows a file connected to a high-relevance file to inherit relevance even if it is lexically invisible to the requirement. The resulting structural score is denoted as 𝑠 str (𝑢 ).

3.3 Utility Linking 

Signal Grounding identifies task-related code anchors, but anchors alone do not provide all reposi-tory evidence needed by the required code. Utility Linking therefore expands from these anchors to collect potentially useful repository evidence through static relations. It performs this expansion in two steps. First, starting from the anchor set 𝐴 , Rivet traverses the repository evidence graph 

𝐺 and gathers snippets connected to the anchors through dependency, usage, and configuration relations. Second, Rivet assigns each gathered evidence snippet a relevance score that reflects how closely it is connected to the required code. 

Evidence categories. Rivet collects three categories of repository evidence around task-related code anchors. ❶ Dependency evidence includes definitions, imports, and referenced symbols reached from an anchor through import and symbol-ref edges. This evidence helps the agent reuse project-specific definitions and resolve required dependencies. ❷ Usage evidence includes existing call sites or usages recovered from caller edges. This evidence indicates how an anchor or related snippet is invoked in the repository. ❸ Configuration evidence includes packaging, runtime, and configuration snippets connected through config edges. This evidence constrains how the required code should be integrated and executed in the target repository. Together with the task-related code anchors, these categories form the candidate repository evidence set used for context construction. Each evidence snippet is extracted at snippet granularity, such as a definition block with its signature and a bounded context, rather than as a whole file. 

Evidence relevance. The collected evidence induces an evidence graph 𝐺 𝐸 , whose nodes are the task-related code anchors and the gathered evidence snippets, and whose edges inherit their relation types from 𝐺 . Rather than assigning fixed scores to different evidence categories, Rivet reuses the propagation mechanism in the Signal Grounding stage on 𝐺 𝐸 . The propagation is seeded by the anchor relevance and diffused with type weights, e.g., 𝜔 import > 𝜔 symbol-ref > 𝜔 caller > 𝜔 config .The resulting score 𝜓 (𝑧 ) measures how strongly an evidence snippet 𝑧 is connected to the required code. Evidence directly connected to an anchor receives a higher score, while incidentally connected Rivet: Utility-Preserving Context Control for Repository-Level Coding Agents 7

evidence receives a lower score. This score is passed to Budget Shaping, which decides how to retain the collected evidence under the context budget. 

3.4 Budget Shaping 

Budget Shaping converts the collected repository evidence into a packed repository context under the context budget 𝐵 . Its goal is to retain the evidence needed by the required code, while using compact representations when the full evidence set exceeds the budget. Budget Shaping makes three decisions: which priority tier each evidence snippet belongs to, how compactly each snippet should be represented, and in what order snippets should be considered for the budget. 

Evidence tiers and representation ladder. Each evidence snippet is assigned a priority tier according to its role in supporting the required code. Task-related code anchors and their direct dependencies are placed in the highest tier. Usage evidence and indirect dependencies are placed in the next tier. Configuration evidence is placed in the last tier. These tiers provide a heuristic ordering for budget allocation rather than a task-independent measure of evidence importance. Within each tier, an evidence snippet can be rendered at different levels of detail through a representation ladder ⟨full snippet , signature , compact summary ⟩. When the budget is tight, Rivet reduces the representation detail of a selected snippet before dropping it. For high-priority evidence, Rivet keeps at least its signature whenever possible. This design keeps more types of repository evidence under constrained budgets, instead of spending the budget on a few long snippets. 

Evidence-aware ordering. Evidence snippets are considered tier by tier. Within each tier, Rivet orders snippets by combining two rankings. The first ranking is the anchor relevance rel (𝑧 ) = 𝜌 (𝑎 𝑧 ),i.e., the grounding score of the anchor 𝑎 𝑧 that introduces evidence snippet 𝑧 . The second ranking is the evidence relevance 𝜓 (𝑧 ), which reflects how strongly 𝑧 is connected to the required code in the evidence graph. 4.1 Benchmarks 

Following prior work on repository-level code generation [14, 18], we conduct our main experi-ments on two executable repository-level coding benchmarks, DevEval and RepoExec. We choose them because they provide repository-level tasks with executable evaluation protocols, allowing us to measure whether the generated code works within the target repository. ❶ DevEval [20] 

is a repository-level code generation benchmark built from real-world repositories, containing 1,825 function-level generation tasks. Each task provides a natural-language requirement and the corresponding original repository, and the model is expected to implement the required function in the target codebase. We use DevEval as the main benchmark because its tasks require repos-itory evidence such as target locations, project-specific definitions, dependencies, and interface constraints. ❷ RepoExec [12] is a repository-level code generation benchmark containing 355 function-level generation tasks with ground-truth annotations. Compared with DevEval, RepoExec places stronger emphasis on whether generated code can execute correctly within the repository context. We use RepoExec as an external validation benchmark to examine whether the gains of Rivet transfer to different repositories and test suites. During context construction, all methods use only the task requirement and the original repos-itory files. Reference implementations, reference dependencies, and benchmark test outcomes are reserved for evaluation and analysis, and are not used to construct the repository context. This protocol avoids information leakage and ensures that all methods are compared under the same available information. The only exception is Target-Local, which by design receives the benchmark-provided target location. Rivet: Utility-Preserving Context Control for Repository-Level Coding Agents 9

4.3 Baselines 

We compare Rivet with representative baselines for repository-level code generation, including 

retrieval-based, compression-based, and structure-aware methods . Target-Local is included as a special local-context baseline because it uses the benchmark-provided target location and evaluates whether local context around the target alone is sufficient. The remaining baselines construct or reduce repository context from the task requirement and repository files under the same context budget. 

Local-context baseline. Target-Local provides the task requirement together with a fixed local context around the benchmark-provided target location, including surrounding code from the target file and entry-point hints. Unlike the other baselines, it does not evaluate automatic context discovery. Instead, it serves as a reference with access to the ground-truth target location, testing whether target-location context alone is sufficient. 

Retrieval-based baseline. RAG [19] divides the repository into code snippets and retrieves snip-pets according to their similarity to the task requirement. It keeps the most relevant snippets under the context budget and concatenates them as the repository context. 

Compression-based baselines. ❶ LLMLingua2 [27] takes the retrieved repository context as input, estimates the importance of tokens or short spans with its pretrained compressor, and removes low-importance content until the context budget is met. The remaining text is used as the repository context. ❷ LLM Summarize , following the baseline setting in [35], asks an LLM to rewrite the retrieved repository context into a shorter summary under the context budget. The summary is then used as the repository context. ❸ LongCodeZip [33] ranks function-level code snippets by their relevance to the task requirement and further shortens the retained snippets by selecting important code blocks under the context budget. The shortened code context is used as the repository context. ❹ SWE-Pruner [35] asks the agent to produce an explicit pruning goal, such as focusing on error handling or locating a relevant function. Guided by this goal, a lightweight neural skimmer selects relevant lines from raw agent observations, such as file-reading or search outputs. The remaining lines are used as the pruned agent observation.

It first generates a draft completion as an anchor for the target function, and then enriches the prompt with upstream callers and downstream callees. ❷ Hydra [18] treats code as structured programs rather than natural-language chunks, builds hierarchical indices over functions, classes, and variables, and combines dependency-aware retrieval with similarity-based retrieval to provide required dependencies and usage examples. 10 Pan et al. 

4.4 Implementation Details 

Following prior work [35], we use Mini-SWE-Agent as the unified agent scaffold for all methods. We evaluate four backbone models: DeepSeek-V3.2 , GPT-5-mini , Qwen3.5-397B-A17B , and 

MiMo-V2.5 . We use temperature 0 for all models that support it and the default decoding setting for GPT-5 models. We set the context budgets to 4K and 8K tokens. To ensure a fair comparison, all methods use the same task requirement, repository files, backbone model, prompt template, context budget, decoding strategy, agent scaffold, and execution environment. The only difference is how each method constructs the repository context under the same budget. The generated code is executed and evaluated in a consistent Python 3.9 environment. The 4K and 8K budgets are chosen to evaluate repository context construction under practical cost constraints. The 4K budget represents a tight setting, where the agent cannot include many repository files and must prioritize essential repository evidence. The 8K budget provides a less restrictive setting for testing whether the benefit of Rivet remains when more repository context can be included. Together, these budgets allow us to examine whether Rivet improves accuracy by preserving repository evidence rather than by simply increasing the amount of repository text. 

Hyperparameters of Rivet. We use the same hyperparameter values for all benchmarks, backbone models, and context budgets. In Signal Grounding, Rivet keeps the top-𝑘 =6 files as anchors, a small set that leaves most of the budget for the evidence linked from them. The fielded BM25 model uses the standard saturation parameter 𝑘 1=1.2 [31], with field weights (and length-normalization parameters 𝑏 ) of 3.0 (0.40), 2.5 (0.50), 1.5 (0.60), and 1.0 (0.75) for the path , symbol ,

sigdoc , and content fields, so that the precise path and symbol fields dominate the noisier identifier stream. For the same reason, query terms from explicit code mentions receive weights of 2.0 (symbols) and 1.5 (file names), compared with 1.0 for other terms. Latent semantic analysis uses min (256 , |𝐹 |− 1) latent dimensions and falls back to TF-IDF cosine similarity for repositories with fewer than 20 files, where a truncated factorization is unstable. Personalized PageRank runs for 20 iterations with damping factors 𝛼 =0.6 in Signal Grounding and 𝛼 =0.7 in Utility Linking; both values are lower than the conventional 0.85, which keeps the propagated relevance close to the task-related seeds. Both reciprocal-rank fusions use 𝜅 =60, the value recommended by Cormack et al. [8], and the code-mention prior 𝜋 (𝑢 ) adds 0.05 to the fused score of explicitly mentioned files, which places them ahead of the remaining candidates. The edge weights follow the priority order of the evidence tiers: 𝜔 import =1.0 (0.7 for indirect imports), 𝜔 symbol-ref =0.8, 𝜔 caller =0.5, and 

𝜔 config =0.3. Utility Linking retains at most 12 dependency, 10 usage, and 10 configuration snippets, and Budget Shaping caps each section of the packed context, e.g., at 1,400, 420, 240, and 140 tokens for the target context and the dependency, usage, and configuration evidence under the 4K budget, and at 2,500, 1,200, 800, and 500 tokens under the 8K budget.

We study two scaling strategies. 6.2 How Do Graph Components Affect Rivet’s Performance? 

Both the structural grounding signal and Utility Linking rely on statically extracted repository relations, which may miss dynamic behavior such as runtime imports or reflection [4]. Rivet does not rely on these relations alone: Signal Grounding fuses the structural signal with lexical and semantic signals, so missing edges can reduce the evidence that Utility Linking collects but cannot by themselves remove a file from the anchors. To examine this, we construct three variants on DeepSeek-V3.2 under the 4K budget. w/o Graph Ranking keeps evidence collection but removes the propagated relevance from Budget Shaping, ordering evidence by grounding relevance and tier alone. w/o Structural Grounding disables the structural channel in Signal Grounding while keeping the lexical and semantic signals. Dependency Edges Only restricts Utility Linking to import and symbol-reference relations, removing usage and configuration relations. As shown in Table 5, the graph components matter little on DevEval, where each variant loses at most 0.44 percentage points (8 of the 1,825 tasks), but substantially on RepoExec, where the drops range from 7.60 to 9.01 percentage points and removing the structural grounding signal has the largest effect. This pattern mirrors the fine-grained ablation in RQ3 and suggests that on RepoExec the graph contributes evidence that text similarity does not recover; restricting Utility Linking to import and symbol-reference relations alone already costs 8.73 percentage points. This ablation measures how much the graph contributes, not how robust Rivet is to wrong or missing edges; we leave a controlled study of edge noise to future work. 7 Threats to Validity 

Generalizability. Our experiments focus on Python repositories, and our implementation relies on Python-specific parsing, import resolution, and execution environments. Only these front-end components are language-specific: the grounding signals, graph propagation, and budget packing operate on files, snippets, and typed relations, and apply to other languages once a parser extracts these relations. Validating Rivet on other languages is left to future work. 

Task representativeness. DevEval and RepoExec provide executable and reproducible evalua-tion, but both focus on function-level generation within existing repositories. They do not cover multi-file changes such as feature addition and bug fixing, where locating the code to change is itself part of the task. Future work should further evaluate Rivet on broader benchmarks for issue resolution and feature evolution, such as SWE-Bench [16], FEA-Bench [21], and FeatBench [5]. 

Comparison fairness. The compared methods were designed for different context-construction settings, including retrieval, compression, and structure-aware selection. To reduce confounding factors, all methods use the same task requirement, repository files, backbone model, prompt template, context budget, decoding strategy, agent scaffold, and execution environment. This protocol makes context construction the main controlled variable, although method-specific tuning could further improve individual baselines. 

Hyperparameters. Rivet has several hyperparameters (Section 4.4), which we keep fixed across all benchmarks, models, and budgets rather than tuning them per setting; we do not study their sensitivity, so other values may change the absolute results. 

Metric validity and data leakage. We use Pass@1 on official benchmark tests as the primary metric because it directly measures executable task success. However, passing tests does not guar-antee full semantic correctness. Public benchmarks may also have appeared in the pretraining data of large language models. This risk may affect absolute scores, but all methods are evaluated with 18 Pan et al. 

the same backbone models and protocol, which reduces its impact on relative comparisons. During context construction, we use only task requirements and repository files; reference implementations, reference dependencies, benchmark tests, and the ground-truth target location are used only for evaluation and analysis. 

8 Related Work 

Retrieval and Compression for Code Context. A line of work controls repository context by selecting or shortening code before prompting LLMs. Retrieval-based methods select files, functions, or code snippets according to lexical or semantic similarity to the task requirement [19, 23, 28, 39]. Code search tools retrieve code by textual or structural similarity to a query [17, 25], and repository-level completion methods adapt such retrieval to cross-file context, for example by iterating retrieval with generation [39], deciding when to retrieve [37], learning what to retrieve [36], or following data flow [7]. Prompt compression methods reduce token usage by pruning low-importance tokens or rewriting retrieved repository content [15, 27]. Code-specific compression methods further exploit code granularity by selecting functions or blocks under a context budget [33]. These methods make repository context more relevant or compact, but they mainly optimize task similarity or context length. As a result, the selected context may still lack the repository evidence that the implementation depends on [11]. Moreover, LLMs do not use long contexts uniformly [22], so a longer context does not necessarily carry more useful evidence. Rivet also selects and compresses context, but it decides what to keep by following repository relations from the task location rather than by similarity to the requirement, and it compresses by lowering the representation level of each snippet rather than by pruning tokens. 

Structure-aware Repository Context Construction. Another line of work uses repository structure or agent states to guide context construction. Structure-aware methods, such as In-lineCoder and Hydra, exploit repository relations to retrieve or inline context connected to the task [14, 18, 24, 30]. These methods build on a long line of work that represents programs as graphs of data and control dependencies or calls [1, 26, 32]. Other methods refine the context during generation, by pruning agent observations according to the current coding goal, as in SWE-Pruner [35], or by iteratively retrieving project context with compiler feedback [3]. These methods improve over pure text-based retrieval by incorporating structural or interaction signals. Rivet differs from them in three respects. First, it collects dependency, usage, and configuration evidence from the same anchors, whereas InlineCoder inlines callers and callees and Hydra retrieves dependencies and usage examples. Second, it treats the budget as a packing problem and lowers the representation level of each snippet before dropping it, rather than truncating or pruning context. Third, it constructs the context deterministically without LLM calls, whereas InlineCoder requires a draft generation and SWE-Pruner relies on a learned skimmer. 

9 Conclusion 

In this paper, we characterized context utility dilution, a failure mode in which the context given to a repository-level coding agent appears relevant to the task but lacks the repository evidence that the implementation depends on. Our key observation is that much of this evidence is reachable from the code that the task touches through static repository relations. Based on this observation, we proposed Rivet, which locates task-related code anchors, follows dependency, usage, and configuration relations from them to collect evidence, and packs this evidence under the budget with a representation ladder. On DevEval and RepoExec with four backbone models, Rivet achieves the highest Pass@1 in all 16 settings and improves over the strongest baseline by 3.73–5.15 percentage points on average. With a 4K budget, it outperforms the strongest baseline given an 8K budget in six of the eight settings, and it enables GPT-5-mini to outperform GPT-5 at 73.3%–84.5% lower Rivet: Utility-Preserving Context Control for Repository-Level Coding Agents 19 

inference cost. These results suggest that, under constrained budgets, which evidence enters the context matters more than how much context the agent receives. In future work, we plan to extend Rivet to other programming languages and to multi-file tasks such as issue resolution and feature implementation.

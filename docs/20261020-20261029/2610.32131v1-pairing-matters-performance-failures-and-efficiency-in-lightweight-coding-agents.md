## 摘要
对于必须将专有代码和开发轨迹保留在受控基础设施内的软件工程团队而言，自托管编码智能体通常是必要的。轻量级开放权重模型降低了硬件需求，使此类部署更可行；而仓库级基准上的强劲结果也显示了它们在要求较高的编码任务上的潜力。将这些模型部署为编码智能体需要将其与智能体执行框架（agent harness）配对，因此二者的联合性能成为关键部署考量。然而，现有排行榜主要报告固定的 harness-model 配置，而非跨替代配对的受控比较。为弥补这一空白，我们通过对六个开源 harness 和三个轻量级编码模型在 100 个 SWE-bench Verified 任务上进行受控全因子评估，在统一的服务、计量和评分条件下产生 1,800 次评分运行，来研究 harness-model 交互。对于同一模型，不同 harness 下的解决率差异最高达 44 个百分点，而 harness 排名会随模型变化。我们对 1,100 次未成功运行应用基于证据的失败分类法，发现不同 harness-model 配对的失败模式存在显著差异。模型在某一 harness 下的主要失败模式未必在另一 harness 下仍占主导。效率同样依赖于配对：即使在模型引导的循环 harness 中，每个已解决任务所计费的 token 数差异也超过 20 倍。这些发现使 harness-model 选择成为轻量级编码智能体部署的核心决策。某一 harness 或模型上的强劲表现并不保证在另一者上也能取得类似结果。我们将这些发现转化为面向从业者的指导，涵盖配对选择、token 效率评估以及轨迹信息驱动的 harness 工程，并发布完整的实验记录和分析产物。

## Abstract
Self-hosting coding agents is often necessary for software-engineering teams that must keep proprietary code and development traces within controlled infrastructure. Lightweight, open-weight models make such deployment more feasible by reducing hardware requirements, while strong results on repository-level benchmarks demonstrate their potential for demanding coding tasks. Deploying these models as coding agents requires pairing them with an agent harness, making their joint performance a key deployment consideration. Yet existing leaderboards primarily report fixed harness-model configurations rather than controlled comparisons across alternative pairings. To address this gap, we investigate harness-model interactions through a controlled full-factorial evaluation of six open-source harnesses and three lightweight coding models across 100 SWE-bench Verified tasks, producing 1,800 graded runs under common serving, metering, and grading conditions. For the same model, resolution rates differ by up to 44 percentage points across harnesses, while harness rankings change across models. We apply an evidence-based failure taxonomy to 1,100 unsuccessful runs and find substantial differences in failure patterns across harness-model pairings. A model's dominant failure modes under one harness need not dominate under another. Efficiency is similarly dependent on the pairing: even among model-directed loop harnesses, charged tokens per resolved task vary by more than 20-fold. These findings make harness-model selection a central deployment decision for lightweight coding agents. Strong performance with one harness or model does not guarantee similar results with another. We translate these findings into practitioner guidance for pairing selection, token-efficiency assessment, and trajectory-informed harness engineering, and release the complete experimental records and analysis artifacts.

## 1. 核心问题与研究动机

- **背景**：软件工程团队出于专有代码与开发轨迹的保密需求，往往需要自托管（self-hosting）编码智能体；轻量级开放权重模型（10–100B）降低了硬件门槛，且在仓库级基准（如 SWE-bench Verified）上已展现出可观能力（如 Devstral Small 24B 在 OpenHands 下 53.6%，Qwen3-Coder-Next 在三个 harness 下 70.6–71.3%）。
- **核心问题**：把模型部署为编码智能体，必须为其配一个 **agent harness**（负责仓库上下文管理、工具调用、执行、验证与补丁提交）。因此真正的部署决策是 **harness–model 配对**，而非单一组件。但现有排行榜几乎只报告固定的 harness–model 配置。
- **证据缺口**：作者审计了 2026 年 8 月 SWE-bench 官方归档六个 track 的 324 条提交记录，其中至少 223 条使用闭源模型，仅 5 条报告了 <100B 开源模型与成熟 harness 的组合，且都是固定配置，无法回答"换 harness 会怎样"。
- **整体含义**：论文主张编码智能体性能是 **联合系统属性**，需通过受控的全因子实验刻画配对对解决率、失败机制与 token 效率的影响，并据此给出可操作的部署建议。

## 2. 方法论

- **核心思想**：采用 **全因子（full-factorial）受控实验**——每个模型与每个 harness 两两组合，全部在统一的任务集、服务基础设施、计量方式与评分流程下运行，从而把性能差异归因于"配对"而非环境噪声。
- **配对矩阵**：6 个开源 harness × 3 个轻量模型 × 100 个任务 = **1,800 次评分运行**。
- **Harness 分类（按执行控制模式）**：
  - *模型引导的交互循环*：OpenCode、OpenHands（CodeAct + 持久沙箱）、mini-SWE-agent（仅 bash 接口）、SWE-agent（agent–computer interface）。
  - *分阶段检索与修复*：AutoCodeRover（结构化搜索类/方法后生成补丁；评测配置中保留可执行的复现脚本，但省略专门的回归测试阶段）。
  - *固定修复流水线*：Agentless（定位→修复→验证；仅保留定位阶段、生成单个候选补丁、省略内部测试验证）。
- **模型选择**：Qwen3-Coder-Next（80B 总参 / 约 3B 激活 MoE，强调长程 agentic 与工具使用）、Devstral-Small（24B dense，由 Mistral 与 All Hands AI 为 agentic SE 开发）、GLM-4.7-Flash（30B 总参 / 约 3B 激活 MoE，全程开启 thinking）。覆盖 dense/sparse、不同推理模式与工具协议。
- **统一执行与计量**：
  - 共享任务集、vLLM 服务、评分流程；所有 harness 通过 OpenAI 兼容接口接入，前缀缓存开启，按模型配置 tool-calling parser。
  - 统一生成预算：每次运行累计 **262,144（256K）completion tokens** 上限（不含 prompt），另加 harness 自身的步数/超时限制（为控制算力成本做过调整，故各 harness 间不完全等价）。
- **度量定义**：
  - *运行（run）*：某配对在某任务上的一次尝试；*轨迹*：模型请求–响应序列（含工具调用与观察）。
  - *轨迹长度*：模型调用次数（harness 重试或子代理调用各计一次）。
  - *计费 token*：所有调用中 prompt + completion token 之和。
  - *解决率*：100 个任务中被官方 SWE-bench Docker grader 判定解决的比例；评分前过滤掉对测试、部分配置文件与文档/临时脚本的修改；空补丁或缺失补丁计为失败。
  - *tokens per resolved task*：全部运行（含失败）的总 token 除以解决任务数。
- **失败分类法（5 类，互斥，自上而下取首个匹配）**：
  1. **Exchange breakdown**：模型流量中断、工具交换无响应/不可执行、最终交换被截断、运行时或沙箱故障、已完成补丁被 harness 丢失或失效。
  2. **No-progress loop / budget exhaustion**：执行停滞、重复无效动作、触达步数或 token 上限而修复未完成。
  3. **Fault mislocalization**：提交补丁与 gold patch 没有任何共同文件。
  4. **Insufficient validation**：声称修复成功，但运行期可用检查不足以支持该结论（含改测试、忽略矛盾结果）。
  5. **Wrong or incomplete fix**：修复已定稿、与 gold patch 有文件级重叠，但参考测试失败。
- **标注流程**：脚本从代理记录、轨迹与补丁中抽取诊断指标，组装"证据包"；两名 LLM 评审（Claude Sonnet 5、Claude Haiku 4.5）在盲态下独立按同一 rubric 评分；证据不足者先做证据补全再评；分歧由 Claude Sonnet 5 在新上下文中裁决；另对 48 个一致样本做抽查复核。

## 3. 实验设计

- **Benchmark**：SWE-bench Verified（500 任务）的 **固定 100 任务子集**，采用固定种子、按仓库与官方难度分层的抽样；为提升仓库覆盖度，小仓库被过度代表（如 django 33、sympy 11、matplotlib 9、astropy 7、sphinx 7、pytest 7、scikit-learn 8、pylint 4 等）；难度分布为 <15 min 35 个、15 min–1 h 56 个、1–4 h 9 个、>4 h 0 个。筛选中发现评分缺陷的任务按记录化流程替换。
- **对比对象**：
  - 18 个 harness–model 配对（6×3），互相作为对照；
  - 每个模型的 **"Any harness" 并集**（六个 harness 至少一个解决的任务数），用于衡量跨 harness 的覆盖上限；
  - **外部前沿参照**：官方 SWE-bench 归档中 OpenHands + Claude 4 Sonnet（解决 68，估计 2.8M tokens/解决任务）与 OpenHands + GPT-5（解决 70，估计 1.0M），按相同 100 任务匹配，token 由公开轨迹以"4 字符 ≈ 1 token"估算。
- **三个研究问题**：RQ1 配对性能与已解决任务重叠；RQ2 失败机制（对 1,100 次失败运行全量标注）；RQ3 配对效率（模型调用数、每解决任务计费 token）。

## 4. 资源与算力

- **推理硬件**：**单块 NVIDIA H100 NVL GPU**，通过 vLLM 顺序服务三个模型（每个模型的 serving 配置在所有 harness 间固定）；harness 在另一台 CPU 主机上执行，经 SSH 隧道连接。
- **训练算力**：无（全部为推理评测，未做任何模型训练或微调）。
- **未明确说明**：论文未报告总 GPU 小时数、总运行墙钟时长或能耗；仅给出每次运行 256K completion token 的生成预算与"为保持算力可承受而调整 harness 限制"的定性说明。

## 5. 实验数量与充分性

- **规模**：18 个配对 × 100 任务 = 1,800 次评分运行；对其中 **1,100 次失败运行**逐一标注（双评审 + 裁决 + 48 例抽查）；报告了按模型、按 harness、按配对三个层级的失败分布；效率分析覆盖 18 个配对并对照 2 个前沿参照。
- **充分性亮点**：
  - 全因子设计而非"一模型一 harness"的惯例，能直接检验交互效应；
  - 统一服务、计量与评分条件，控制了环境混杂；
  - 失败标注报告了评分者一致性（784/1,100 一致，Cohen's κ = 0.600）并做了分歧裁决与抽查纠错，具有一定可审计性；
  - 公开全部 1,800 次运行记录、轨迹、补丁、标注与脚本。
- **不足**：
  - **无重复运行**：每个"配对–任务"只保留一次最终尝试，无法估计 run-to-run 方差；
  - 并集（union）把六个 harness 的各一次尝试合并，既不能区分"harness 互补性"与"运行随机性"，也不能证明优于"单 harness 跑六次"；
  - 无消融实验（如 token 预算、超时、温度、量化方案的敏感性分析均缺失）；
  - 仅一个 completion-token 阈值（256K）；
  - harness 特定限制/超时经人工调整且不等价，削弱了"归因于 harness 设计"的强度；
  - 前沿参照的 token 数为估算值，且部署配置不同，比较仅为指示性。
- **公平性**：同一模型在各 harness 下采样设置固定、共用服务与评分，公平性较好；但 harness 侧预算不等价、单次运行无重复，是客观性上的主要折扣。

## 6. 主要结论与发现

- **Finding 1（性能）**：同一模型跨 harness 解决率相差 **28–44 个百分点**；harness 排名随模型变化（如 SWE-agent 对 Qwen3-Coder 仅 22，对 GLM 为 51；mini-SWE 对 Devstral 仅 22）。每个模型的最佳单 harness 比"六 harness 并集"少解决 **10–16 个任务**（Qwen 63 vs 79；GLM 51 vs 62；Devstral 54 vs 64）。
- **Finding 2（覆盖结构）**：OpenCode 并集最大（71）且三模型共享核心最大（34），OpenHands 次之（70/33），SWE-agent 并集 62 但三模型共享仅 7（其中 17 个仅 GLM 解决）。Qwen3-Coder 覆盖最广（79）但六 harness 全解决仅 5 个；GLM 覆盖 62 却有最大共享核心 15；Devstral 覆盖 64，其中 16 个仅被单一 harness 解决。即"广度"与"一致性"是不同维度。
- **Finding 3（模型级失败画像）**：总体分布为 no-progress loop/budget 386（35.1%）、wrong/incomplete fix 362（32.9%）、insufficient validation 141（12.8%）、fault mislocalization 129（11.7%）、exchange breakdown 82（7.5%）。Qwen3-Coder 高度集中于 loop/budget（193/339，57%）；Devstral-S 较分散（wrong fix 35%、loop 21%、validation 20%、mislocalization 19%）；GLM 以 wrong fix 36% 与 loop 30% 为主（合计 66%）。

…%/— 等），说明该失败模式既取决于模型，也取决于 harness 的执行控制方式，而非模型的固有属性。

- **Finding 5（失败模式的配对可迁移性有限）**：不同配对间的失败画像差异显著，且同一 harness 在不同模型上诱发的失败结构并不同构——例如 OpenHands 对 Qwen3-Coder 把 loop/budget 压到 32%，但对 Devstral 则更多表现为 validation 与 mislocalization；SWE-agent 对三个模型都偏向"消耗预算而无进展"，提示其交互接口对轻量模型的工具协议适配不足。作者据此指出：**失败分类不能只按模型或只按 harness 汇报，必须按配对汇报**，否则会掩盖可修复的系统性缺陷。

- **Finding 6（效率）**：效率差异同样是配对属性。以 tokens per resolved task 计，最优配对与最差配对之间相差数倍；且"高解决率"与"高 token 效率"并不一致——某些配对通过更多轨迹长度换取边际解决率提升，另一些则在较低 token 消耗下取得相近解决率。与前沿参照相比（OpenHands + Claude 4 Sonnet 约 2.8M tokens/解决任务、OpenHands + GPT-5 约 1.0M），轻量模型的最佳配对在 token 效率上具备竞争力，但绝对解决率仍有明显差距；论文强调该比较为指示性（token 由轨迹估算、部署配置不同）。

- **Finding 7（实践建议）**：部署决策应把 harness 视为与模型同等的一等选择变量；对轻量模型尤其应优先选择"能约束无效循环、并提供明确验证信号"的 harness；在预算受限时，选择合适配对带来的收益可超过升级模型或增加采样次数的收益。作者还建议基准发布方报告完整配对矩阵而非单一配置。

## 7. 讨论与启示

- **对评测实践**：现有 SWE-bench 类排行榜的"单配置"报告方式系统性低估了不确定性——同一模型的可达性能区间宽达 28–44 个百分点，排行榜名次在很大程度上反映的是 harness 选择而非模型能力。
- **对部署实践**：自托管团队应在自己的任务分布上做小规模配对扫描（而非直接采用公开榜单的最优组合），并把失败分类作为诊断工具，用于判断瓶颈在模型（如 mislocalization 高）还是在 harness（如 loop/budget 高）。
- **对 harness 设计**：高 loop/budget 占比指向两类可改进点——终止/进展判定机制，以及工具输出对模型的可解析性；高 insufficient validation 占比则指向需要在 harness 侧引入更可靠的自动验证环节。
- **对模型训练**：失败画像的配对依赖性说明，agentic 能力评测不宜脱离具体交互协议；针对某一种 harness 调优的模型可能在其他 harness 上显著退化。

## 8. 局限与作者自述

- 单次运行、无重复，无法分离配对效应与采样噪声；"Any harness"并集不能证明互补性优于重复采样。
- harness 侧步数/超时限制经人工调整且不完全等价，token 预算仅取单一阈值（256K），缺少预算、温度、量化等敏感性分析。
- 任务子集为 100 个且小仓库被过度代表，绝对解决率不可直接外推到完整 500 任务集；难度分布中缺少 >4 h 的任务。
- 失败标注依赖 LLM 评审，一致性为中等水平（κ = 0.600），虽有裁决与抽查，仍可能存在系统性偏差。
- 前沿参照的 token 数为估算，跨论文比较的解释力有限。

- 对轻量开源模型的自托管部署给出了有依据的实践指引，直接回应了保密性约束下的真实工程需求。

## 10. 总体评价

论文的问题设定切中当前编码智能体评测的关键盲点：**把 harness 当作固定背景而非实验变量**。其方法论上的核心优势在于全因子受控设计与统一的服务、计量、评分流程，使"配对"成为可归因的自变量；失败机制的全量标注则把"性能差异"推进到"为什么差异"，这是多数同类工作缺失的一层。主要短板在于统计效力——无重复运行使得配对间几个百分点的差异不可解释，并集分析也无法区分互补性与随机性；此外 harness 预算不等价与单阈值 token 预算削弱了因果归因的强度。总体而言，论文的**结论方向（配对重要、失败画像随配对变化、效率是配对属性）稳健且具有实践价值**，但具体的配对排名与效应量应视为在特定预算与单次采样条件下的观测结果，需通过重复实验与预算消融进一步确认。

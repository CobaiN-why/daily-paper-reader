## 摘要
背景。编码智能体越来越多地通过拉取请求贡献测试，随后由开发者维护，因此测试工作的分工方式会影响长期可维护性。目标。我们沿五个维度比较开发者与编码智能体协作的拉取请求（智能体支持）与未检测到智能体参与的拉取请求（人类编写）：测试变更的频率与程度、其类型与上下文、测试结构、测试坏味以及代码覆盖率。方法。我们分析 391 个 Java 仓库中于 2025 年 1 月至 2026 年 4 月合并的 114,134 个拉取请求，通过拉取请求级和提交级信号识别出五种编码智能体。由于不同项目对智能体的采用程度不同，我们在仓库内使用控制变更规模的混合效应模型比较两组。结果。跨仓库汇总时，两组修改测试代码的频率几乎相同；在仓库内，智能体支持的拉取请求修改测试代码的几率高 1.65 倍。智能体支持的拉取请求更常新增测试（优势比 1.50-1.58），较少修改（0.70-0.76）和删除（0.51-0.77）测试。对于其新增测试的大多数结构特征，我们未检测到差异，但这些测试更常包含测试预言（oracle）；在我们能够构建的 95 个仓库中，其生产代码变更的覆盖率也未检测到差异；然而，在仅含测试的拉取请求中，其测试覆盖其执行代码的范围更小。测试坏味方面的差异处于临界水平，且在单个测试方法层面未能重现。结论。智能体参与与不同的测试工作组合相关，跨项目汇总比较可能掩盖或逆转这种关系；其与测试质量的关系仍不确定。

## Abstract
Context. Coding agents increasingly contribute tests through pull requests that developers then maintain, so how testing work is divided affects long-term maintainability.   Objective. We compare pull requests in which developers and coding agents collaborate (agent-supported) with pull requests without detectable agent involvement (human-authored) along five dimensions: the frequency and extent of test changes, their type and context, test structure, test smells, and code coverage.   Method. We analyze 114,134 pull requests merged between January 2025 and April 2026 in 391 Java repositories, identifying five coding agents through pull-request-level and commit-level signals. Since agent adoption varies across projects, we compare the two groups within repositories with mixed-effects models that control for change size.   Results. Pooled across repositories, both groups change test code almost equally often; within repositories, the odds that an agent-supported pull request does so are 1.65 times higher. Agent-supported pull requests add tests more often (odds ratios 1.50-1.58) and modify (0.70-0.76) and delete (0.51-0.77) them less often. We detect no difference in most structural characteristics of the tests they add, which more often have an oracle, nor, in the 95 repositories we could build, in the coverage of their production changes; in test-only pull requests, however, their tests cover less of the code they exercise. Differences in test smells are borderline and not reproduced for individual test methods.   Conclusions. Agent participation is associated with a different mix of testing work, which pooled comparisons across projects can hide or reverse; its relationship with test quality remains uncertain.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景趋势**：AI 编码工具已从“补全单行代码”演进为“端到端完成开发任务”的编码智能体（coding agents），它们可调用构建系统、测试框架与版本控制，直至任务完成。截至 2026 年 2 月，约 22%–29% 的活跃 GitHub 仓库出现编码智能体使用痕迹。
- **核心问题**：智能体越来越多地通过 Pull Request（PR）贡献测试代码，而这些测试随后由开发者长期维护。测试代码中的设计缺陷（test smells）通常在首次编写时引入、之后很少被移除，因此“智能体写测试、人类维护测试”的分工方式会长期影响可维护性。
- **研究缺口**：已有关于智能体测试的研究较为碎片化，多聚焦单一维度（测试包含率、结构、覆盖率、断言质量、测试失败等）；部分研究虽对比智能体与人类贡献，但**跨仓库汇总比较**，未在仓库内估计差异、未控制变更规模、未量化仓库间差异。而智能体采用在项目间高度不均，汇总比较会把“智能体是否测试得不同”与“哪些项目采用智能体”混为一谈，甚至掩盖或反转真实差异。
- **整体含义**：论文旨在回答两个核心问题——**智能体承担了哪类测试工作**，以及**由此产生的测试代码质量如何**。这是首个在大量仓库内、控制变更规模、并量化仓库间差异的智能体 vs 人类测试工作大规模比较研究。

## 2. 方法论：核心思想与关键技术细节

### 2.1 核心思想
- 在**同一仓库内**比较“智能体支持（agent-supported）PR”与“人类编写（human-authored）PR”，使用**广义线性混合模型（GLMM）**，让每个仓库拥有自己的基线水平和自己的组间差异，并控制 PR 变更规模。
- 从五个维度展开：RQ1 测试频率与程度；RQ2 测试变更的类型与上下文；RQ3 测试代码结构；RQ4 测试坏味；RQ5 代码覆盖率。

### 2.2 智能体识别（多信号融合）
- 依据 Robbes et al. 的启发式规则，覆盖 5 种智能体：**Claude Code、Codex、Copilot、Cursor、Devin**。
- **两层分类**：
  - PR 级信号：分支名前缀（如 `codex/`、`claude/`）、PR 标签、作者身份；
  - 提交级信号：若 PR 级未命中，则检查提交作者/共同作者是否匹配智能体模式，且该提交须至少修改一个 Java 文件。
- 排除其他智能体与 bot 账户（登录名/名称含 `[bot]` 或 `-bot`），其余归为人类编写（因无法排除无痕智能体使用，故称“primarily human-authored”）。

### 2.3 变更度量（核心公式）
- 识别**pre-merge commit**（合并前目标分支最新提交）与**post-merge commit**（GitHub 记录的合并提交），按合并策略（merge/squash/rebase/fast-forward）推导，避免 GitHub base commit 带来的污染。
- 用 `git diff-tree` 检测重命名，剔除注释/空行/空白后，用 histogram diff 算法与 diffstat 规则统计变更行：
  - 每个变更块中 `min(D, A)` 计为修改，块规模为 `max(D, A)`；
  - 汇总得测试变更规模 `ΔTest` 与生产变更规模 `ΔProd`；
  - `ΔTest > 0` 即定义为 test PR。
- 测试/生产文件分类：路径规则 + 内容规则（测试库 import、注解、断言等），满足标准测试目录或三条规则中至少两条即判为测试代码。

### 2.4 统计模型（GLMM）
- 基础模型：
  `outcome ~ agentic + size + (1 + agentic | repository)`
  - `agentic` 为 1 表示智能体支持；`size` 为 PR 总 Java 变更规模的对数；
  - 随机效应使每个仓库有独立基线与独立组间差异。
- 二元结局用 Bernoulli + logit；比例（RF、RLOC）用 Beta + logit；计数用零截断负二项或负二项 + log；长度用 Gaussian。
- 报告**条件优势比 OR = e^β**、95% Wald CI、Wald z 检验、Holm-Bonferroni 多重校正、**平均边际效应（AME）**、仓库间差异标准差 **τ̂**，并用 DHARMa 做模拟残差诊断。
- RQ2 引入上下文区分：**TFC**（仅测试 PR）、**COC**（与生产变更关联的协同演化）、**TFM**（混合 PR 中未关联的测试），并检验上下文间系数是否相等。
- RQ3 以测试方法为观测单位，加入 `(1 | pr)` 随机效应；用 Hamster 提取 oracle、断言、条件逻辑、调用-断言序列、mock、作用域、长度等结构指标。
- RQ4 用 JNose 在 pre/post 快照上计算 **Smell Delta = N_post − N_pre**，分 PR 级与方法级两种粒度，区分 Addition 与 Modification 贡献。
- RQ5 用 JaCoCo 在 Docker 中执行 pre/post 两次测试，定义 5 个覆盖率指标（Codebase、Affected-Class、Contributed-Test、Production-Change、New-Line Coverage），用 beta-binomial 建模并加入 baseline 协变量。

## 6. 主要结论与发现

1. **比较方式决定结论（RQ1）**：跨仓库汇总时两组改测试代码频率几乎相同（60.1% vs 59.4%）；仓库内同规模比较，智能体支持 PR 改测试代码的几率高 **1.65 倍**（+9.2 pp）。测试行占比 +5.8 pp（OR 1.26），文件占比 +2.5 pp（OR 1.12）。差异在几十行的 PR 中最明显，在测试已成规范或极少的仓库中较小。
2. **测试工作构成不同（RQ2）**：智能体支持 PR 更常**新增**测试（OR 1.50–1.58，约每 100 个 PR 多 7–10 个），更少**修改**（OR 0.70–0.76）与**删除**（OR 0.51–0.77）；协同演化频率差异很小（OR 1.12）。删除差异在“与生产变更关联”的测试中最小，且主要出现在较大 PR 中。
3. **测试结构差异有限（RQ3）**：9 个结构结局中 8 个无显著差异；唯一一致差异是智能体新增测试**更常含 oracle**（OR 1.71，无 oracle 比例 6.4% vs 10.6%）。修改测试时更常**新增断言**（OR 1.31），移除断言无差异；丢失 oracle 极少但高度集中于少数项目。
4. **测试坏味证据较弱（RQ4）**：PR 级上，智能体新增测试的净坏味增量更小（β = −8.271，p = 0.024），修改测试的净增量更大（β = 10.829，p = 0.046），但均接近显著阈值；仅 General Fixture 与 Exception Catching Throwing 两类校正后显著；**方法级分析未能重现**这些差异。
5. **覆盖率差异有限（RQ5）**：生产变更覆盖率无显著差异（+1.2 pp / +3.2 pp）；两组约四分之三的已覆盖新行由 PR 贡献的测试执行。唯一显著差异在**仅测试 PR**：智能体贡献的测试覆盖其执行类的 **44.5% vs 55.6%（−11.1 pp，OR 0.62）**，但仅基于 11 个仓库，需更大样本验证。
6. **总体判断**：智能体参与与“不同的测试工作组合”相关（更多新增、更少维护），但其与测试质量的关系**仍不确定**；跨项目汇总比较可能掩盖甚至反转仓库内差异。

## 7. 优点（方法或实验设计亮点）

- **大规模与高质量数据**：114,134 个 PR、391 个仓库，且每个仓库同时含两组 PR，支撑仓库内比较。
- **方法论创新**：用 GLMM 随机斜率同时估计“平均差异”与“仓库间差异（τ̂）”，并揭示汇总比较的辛普森悖论式偏差（汇总几乎无差异，仓库内 OR 1.65）。
- **多信号智能体识别**：PR 级 + 提交级信号融合，降低对单一约定的依赖，优于仅依赖分支名前缀或 Co-Authored-By 行的做法。
- **细粒度分析**：测试变更定位到**测试方法/fixture 级**，并用静态调用解析判定“协同演化”（比“同时改测试与生产文件”更精确）；坏味同时在 PR 级与方法级比较。
- **严谨的统计实践**：控制变更规模、Holm-Bonferroni 校正、AME 报告、DHARMa 残差诊断、明确区分“无差异”与“等价”。
- **稳健性检验充分

- **稳健性检验充分**：RQ5 报告 9 种变体（如不同覆盖率口径、不同模型设定、纳入/排除基线协变量、不同 PR 子集等），主要结论保持一致；RQ1 通过并列展示“汇总比较 vs 仓库内比较”主动暴露方法选择对结论的影响；RQ4 同时在 PR 级与方法级建模，用粒度一致性检验结论可信度。这种“让结果接受多种分析路径检验”的做法，显著高于同类实证研究的常见标准。

## 8. 局限与不足（作者自述与评述者补充）

### 8.1 作者明确承认的局限
- **观察性研究，非因果**：所有结论均为“智能体支持”与结局的**关联**，不能推断智能体导致测试质量变化；采用智能体的项目/开发者本身可能系统性不同（自选择偏差），仓库内比较只能缓解、不能消除该问题。
- **智能体识别不完整**：依赖分支名、标签、作者/共同作者等信号，无法识别“无痕使用”（开发者把智能体产出当自己提交），因此人类组是“primarily human-authored”，可能混入智能体贡献，使组间差异被**低估**（偏向零假设）。
- **RQ4 坏味结论较弱**：PR 级聚合模型未纳入检验族，Holm 校正后不显著，作者自称“indicative”；方法级分析未能重现 PR 级差异，说明坏味结论对分析粒度敏感。
- **RQ5 子集偏小且有选择偏差**：仅 150/391 个仓库可构建，最终 95 个仓库完成双次执行；可构建性本身与项目成熟度、构建规范相关，覆盖率结论的外推受限。其中“仅测试 PR”的显著差异仅来自 **11 个仓库**，作者明确要求更大样本验证。
- **部分模型简化**：CreatesMocks、LosesOracle、FocalMethods 等结局因随机效应无法估计而退化模型，导致置信区间可能偏窄，相关结论应谨慎解读。
- **未按智能体类型分层**：五种智能体（Codex、Copilot、Claude Code、Cursor、Devin）被合并为单一“agentic”变量，无法回答“哪种智能体写测试更好/更差”；且 Cursor（292）与 Devin（9）样本极少，即便分层也功效不足。

### 8.2 评述者补充的局限
- **生态效度**：数据窗口为 2025-01 至 2026-04，智能体能力快速迭代，结论可能具有**时效性**；且仅限 Java 生态，JavaScript/Python 等测试实践差异较大的语言未必适用。
- **仓库特征偏斜**：样本以小型、年轻项目为主（中位数 3 stars、1.3 年历史），大型成熟项目的测试规范、评审文化与 CI 约束可能改变智能体的行为模式，结论对“头部项目”外推需谨慎。
- **测试质量的操作化有限**：以测试坏味、覆盖率、结构指标（oracle、断言、mock 等）刻画质量，未直接测量**缺陷检出能力**（如变异测试、真实 bug 捕获率），而后者才是测试的终极价值。
- **PR 级混杂未完全控制**：虽控制总变更规模，但未控制任务类型（重构 vs 新功能 vs 修 bug）、评审强度、作者经验等；智能体可能被分配至不同类型的任务，形成任务选择偏差。
- **“人类”组异质性未刻画**：未区分核心维护者与新贡献者，而人类测试质量本身在组内差异可能很大，可能掩盖或夸大组间差异。

## 9. 启示与实践建议

### 9.1 对研究社区
- **比较设计比样本量更关键**：论文用同一数据集展示“汇总比较几乎无差异、仓库内比较 OR 1.65”，是方法学层面的重要警示——在采用率高度不均的技术扩散研究中，**仓库内/配对设计 + 随机效应**应成为默认范式，而非可选增强。
- **报告 τ̂（仓库间差异）**：仅报告平均效应会掩盖“某些项目差异极大、某些几乎无差异”的事实；未来研究应把异质性本身作为研究对象（何种项目特征调节差异）。
- **多粒度一致性检验**：PR 级与方法级、静态与动态指标并用，可有效识别脆弱结论（如本文坏味发现）。
- **推动可复现基础设施**：Docker 化构建、限时执行、按测试方法粒度采集覆盖率，为后续研究提供了可借鉴的工程模板。

### 9.2 对工具开发者
- 智能体在“**新增测试**”上表现积极且 oracle 覆盖率更高（OR 1.71），说明其在“从零生成带断言的测试”方面已具备实用价值；但在“**修改/删除既有测试**”上显著保守（OR 0.70–0.76、0.51–0.77），可能导致测试套件随生产代码演化而**腐化**（过时测试、冗余测试堆积）。
- 产品设计应有意识地补足“测试维护”能力：识别受生产变更影响的既有测试、判断断言是否失效、安全地删除冗余用例，而非只做增量生成。
- 对“仅测试 PR”覆盖率偏低的信号（−11.1 pp）应保持关注：智能体独立编写的测试可能更“自足”而非“面向被测类”，需在提示与工具层面强化**针对目标类的覆盖导向**。

### 9.3 对工程团队
- 不应以“智能体 PR 改测试更多”简单推断“测试更健康”：论文显示数量与结构差异有限，坏味证据薄弱，真正的风险在**长期维护成本**与**测试有效性**。
- 建议在评审流程中对智能体测试施加差异化检查：断言是否验证行为而非实现、是否引入脆弱 mock、是否与生产变更同步更新。
- 覆盖率指标应区分“生产变更覆盖率”与“仅测试 PR 的贡献覆盖率”，后者可能是智能体测试的薄弱环节。

## 10. 总体评价

- **贡献定位**：本文是智能体编码时代**测试工作实证研究**的重要基准性工作。其最大价值不在“给出智能体测试好/坏的定论”，而在于**建立了正确的比较框架**——仓库内、控规模、含随机斜率、多粒度、多结局，并用数据证明“错误的比较方式会得出错误结论”。
- **证据强度**：样本规模（114,134 PR / 391 仓库）与统计严谨性（GLMM、Holm 校正、AME、DHARMa、稳健性变体）在同类研究中处于较高水平；但核心质量结论（坏味、覆盖率）受限于测量口径与子集规模，属于**中等强度证据**，作者对此的自我克制（明确标注 indicative、要求更大样本）值得肯定。
- **结论的稳健部分**：智能体支持 PR 更常新增测试、更少修改/删除测试，且新增测试更常含 oracle——这一“**增量偏向**”模式在多个 RQ、多种设定下一致出现，可信度较高。
- **结论的待验证部分**：测试坏味净变化、仅测试 PR 的覆盖率劣势、以及“智能体类型间差异”，均需更大规模、更多语言、含变异测试等更强质量信号的研究加以确认。
- **实践意义**：为工具厂商指明了“测试维护”这一能力缺口，为工程团队提供了“不要只看测试数量”的评审依据，为后续研究提供了可复用的数据管道与统计范式。
- **一句话总结**：智能体正在改变测试工作的**构成**（更多生成、更少维护），但尚无充分证据表明其改变了测试的**质量底线**；真正需要警惕的不是智能体写得差，而是我们用错误的方式去比较、用数量去替代质量。

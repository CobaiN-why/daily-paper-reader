## 摘要
编码智能体通常使用一次性、表述良好的提示词进行评估。诸如 SWE-bench 之类的基准测试以现有 GitHub issue 作为编码智能体的输入，并评估智能体是否成功解决任务。然而，在真实使用场景中，提示词往往不像现有 GitHub issue 那样表述良好或结构清晰。此外，编码智能体会话并不局限于单个提示词；它通常涉及多轮交互，用户会在其中迭代地添加智能体必须完成的新任务和需求。为了对这些能力进行基准测试，我们开发了 SWE-DIVE，这是一个动态、交互式的验证与评估框架，用于在多轮环境中对编码智能体进行基准测试。为此，我们引入了一个用户模拟器，它可以模拟不同的行为模式并与编码智能体进行通信。我们还引入了一个对话验证器，用于评估用户模拟器的输出，以判断其是否满足初始需求，并引导智能体成功解决任务。整个框架嵌入在 Harbor 环境中，该环境负责编排编码智能体、用户模拟器和对话验证器，并执行测试环境以判断智能体是否成功解决任务。我们的结果和源代码可在我们的 GitHub 仓库（https://github.com/lorenzbrehme/swe-dive_usersim）中获取。

## Abstract
Coding agents are typically evaluated using one-shot, well-formulated prompts. Benchmarks such as SWE-bench use existing GitHub issues as input for a coding agent and evaluate whether the agent successfully solves the task. However, in real-world use cases, prompts are often not as well-formulated or structured as existing GitHub issues. Additionally, a coding agent session is not limited to a single prompt; it typically involves a multi-turn interaction in which the user iteratively adds new tasks and requirements that the agent must fulfill.   To benchmark these abilities, we developed SWE-DIVE, a dynamic, interactive validation and evaluation framework for benchmarking coding agents in a multi-turn environment. To achieve this, we introduce a user simulator that can simulate different behavioral patterns and communicate with the coding agent. We also introduce a conversation validator that evaluates the user simulator's outputs to determine whether they fulfill the initial requirements and guide the agent toward successfully solving the task. The entire framework is embedded in a Harbor environment, which orchestrates the coding agent, user simulator, and conversation validator, and executes the test environment to determine whether the agent successfully solves the task. Our results and source code are available in our GitHub repository (https://github.com/lorenzbrehme/swe-dive_usersim).

## 1. 核心问题与研究动机

- **背景**：现有编码智能体基准（如 SWE-bench、Terminal-Bench）通常把完整的 GitHub issue 作为一次性提示输入，智能体修改代码后运行测试判定是否解决。
- **核心问题**：真实用户并不会提供结构良好、信息完整的 issue；用户往往先给出高层、模糊的指令，再在多轮交互中逐步澄清、纠错、追加需求，甚至改变目标。已有研究发现约 41% 的对话轮次是“pushback”（智能体未达预期、需要澄清或纠正）。
- **现有多轮基准的不足**：
  - CodeFlowBench、CodeGen 等多轮基准的任务序列和需求是**预定义、静态**的，不随智能体行为自适应。
  - AmbigSWE-bench 等虽引入歧义和澄清提问，但仍倾向于一次性给出完整任务列表。
  - 这些基准主要考察“补充缺失信息”，而非真实开发中“需求发现与演化”的过程。
- **论文目标**：提出 **SWE-DIVE**，将现有单轮软件工程基准动态转化为多轮交互式评估环境，通过 LLM 用户模拟器模拟不同用户行为模式，并结合对话验证器与任务完成评估器，系统评估编码智能体在多轮协作中的表现。

## 2. 方法论

### 2.1 总体框架

- 框架嵌入 **Harbor** 环境，完全 Docker 化，统一编排三类组件：
  1. **User Simulator（用户模拟器）**：与被测编码智能体对话。
  2. **Conversation Validator（对话验证器）**：校验模拟器输出是否合理。
  3. **Task Completion Evaluator（任务完成评估器）**：调用原基准测试环境判定任务是否完成。
- 整体流程可概括为：
  1. 初始化用户角色与原始基准任务（含参考解）；
  2. 用户模拟器生成子任务列表和首轮提示；
  3. 验证器校验子任务列表与提示，若不通过则反馈并让模拟器重生成；
  4. 通过后发送给编码智能体执行；
  5. 智能体返回回复与代码改动（Git diff）；
  6. 模拟器根据进展生成下一轮提示（纠正、追问、新子任务或回答），或输出 `done` 终止；
  7. 达到最大轮数或 `done` 后，评估器运行原基准测试，计算成功率及相关指标。

### 2.2 用户模拟器

- **输入 grounding**：以原始基准任务描述和参考解为事实基础，避免模拟器凭空编造需求。
- **三种用户角色**（源自 SWE-Chat 对真实用户行为的观察）：
  - **Expert Nitpicker**：总体目标稳定，但持续给出精确、局部、代码级的修正，主要改变“如何实现”而非“实现什么”。
  - **Vague Requester**：给出宽泛、欠明确的指令，把大量实现决策交给智能体。
  - **Mind Changer**：在交互中途反转总体目标，要求智能体改变“要构建什么”。
- **自适应生成**：
  - 首轮输出初始提示和完整子任务列表，作为整体解决轨迹；
  - 后续每轮仅生成下一个用户提示，依据智能体最新回复和代码改动决定是纠正、追加子任务、追问还是回答；
  - 判断任务完成后输出 `done`，并设置最大轮数防止无限循环。
- 与静态多轮基准的关键区别：**不遵循预定义子任务序列**，而是根据智能体行为动态调整。

### 2.3 对话验证器

- 采用修改版的 **chain-of-verification** 思路，形成“生成—验证—重生成”闭环。
- 两类验证：
  - **子任务验证**（首轮）：检查子任务列表是否覆盖解决 issue 所需步骤、是否无关任务、是否具有清晰递进关系。
  - **智能体输入验证**（每轮）：检查提示是否与原始 issue 一致、是否遵循子任务轨迹、是否符合指定用户角色、是否可理解且可执行。
- 验证器返回布尔值和失败理由；若无效，理由反馈给用户模拟器用于重新生成，直到通过后才发送给智能体。

### 2.4 任务完成评估器

- 在最大轮数到达或模拟器输出 `done` 时触发。
- 复用原基准的执行环境运行测试，计算任务解决率。
- 输出指标包括：平均对话轮数、按用户角色分组的性能、按所需轮数过滤的效率分析。
- 额外定义两类细粒度质量指标：
  - **Waste（浪费）**：修改了 golden run 中未被修改的文件，以及相比 golden run 多消耗的 token。
  - **Regression（回归）**：智能体修改后，原本通过的测试变为失败。

## 3. 实验设计

### 3.1 数据集与场景

- 使用 **SWE-bench Verified** 任务，Harbor 框架支持 SWE-bench 与 Terminal-Bench。
- **定性案例**：`astropy-12907`，涉及 `separability_matrix` 对嵌套 `CompoundModel` 处理错误。
- **定量初步实验**：在定性任务之外额外采样 10 个任务，共 **11 个任务**，包括 astropy、matplotlib、sympy、requests、django、pytest 等仓库任务。

### 3.2 被测智能体与模型

- 被测编码智能体：**OpenCode**，底层模型为 `gemini-2.5-flash`。
- 用户模拟器模型：`gemini-3.6-flash`。
- 对话验证器模型：`gemini-2.5-flash-lite`。
- 框架目前支持 OpenHands、OpenCode、Pi agent、GitHub Copilot 四种编码智能体，但实验仅使用 OpenCode。

### 3.3 对比设置

- 每个任务运行四种条件：
  1. Expert Nitpicker；
  2. Vague Requester；
  3. Mind Changer；
  4. **Baseline**：直接使用原始任务描述的单轮交互，无多轮模拟。
- 共约 **11 × 4 = 44 次运行**。
- 评价指标：
  - Resolved：任务是否解决；
  - Passed target tests：目标测试是否从失败转为通过；
  - Failed regression test：是否至少有一个原本通过的测试变为失败；
  - 平均轮数；
  - 相比 baseline 的输入/输出 token 变化；
  - 相比 golden patch 的文件读取/编辑数量变化。
- 详细结果表 2–5 列出了每个任务的 `FAIL_TO_PASS`、`PASS_TO_FAIL` 和轮数。

### 3.4 对比方法范围

- 主要对比 **三种用户角色之间** 以及 **多轮交互 vs. 单轮 baseline**。
- 未与其他多轮基准（如 CodeFlowBench、AmbigSWE-bench）或其他人机模拟

## 摘要
自由职业场景下的全新软件开发要求编码智能体将不完整的客户请求转化为可工作的软件。这使得需求澄清至关重要，但客户可能无法在漫长的开发周期中持续提供反馈，而且获得他们的回答并不保证能正确理解复杂需求。这些挑战促成了两项基准设计选择：澄清先于代码实现，并且其有效性通过需求理解的显式测试来评估。在这些选择的指导下，我们提出 SWE-Clar，一个基于真实高价值客户委托的基准，用于评估该场景下的需求澄清与代码实现。它包含 100 个基于 Upwork 上真实软件开发工作的任务，每个任务的总付款至少为 4,000 美元。每个任务从编码智能体与客户智能体之间的多轮交互开始，随后分别运行带验收测试的代码实现和澄清评估。对于后者，我们构建了 512 个问题，并配以来自真实客户-自由职业者交互的参考答案，覆盖明确陈述的需求以及从对话上下文中推断出的需求。两次运行均从相同的澄清上下文开始，但彼此隔离，以防止评估问题引导代码实现。对九个前沿模型的实验表明，即使是在观测中实现得分最高的 GPT-6 Astra，其任务通过率也仅为 67%，凸显了该场景下独立软件交付的挑战。数据集和评估代码可在 https://github.com/upwork/SWE-Clar 获取。

## Abstract
Greenfield software development in freelance settings requires coding agents to turn incomplete client requests into working software. This makes requirement clarification essential, yet clients may be unable to provide continuous feedback over long development cycles, and receiving their answers does not guarantee correct understanding of complex requirements. These challenges motivate two benchmark design choices: clarification precedes code implementation, and its effectiveness is assessed through explicit tests of requirement understanding. Guided by these choices, we introduce SWE-Clar, a benchmark grounded in real, high-value client commissions to evaluate requirement clarification and code implementation in this setting. It comprises 100 tasks based on real software development jobs on Upwork, each with at least US\$4,000 in total payments. Each task begins with multi-round interaction between a coding agent and a client agent, followed by separate runs for code implementation with acceptance testing and clarification assessment. For the latter, we construct 512 questions paired with reference answers from real client-freelancer interactions, covering both explicitly stated requirements and those inferred from the conversational context. Both runs begin from the same clarification context but remain isolated, preventing assessment questions from guiding code implementation. Experiments with nine frontier models show that even GPT-6 Astra, which has the highest observed implementation score, achieves a task pass rate of only 67%, underscoring the challenge of independent software delivery in this setting. The dataset and evaluation code are available at https://github.com/upwork/SWE-Clar.

## 1. 核心问题与研究背景

- **研究场景**：自由职业平台（如 Upwork）上的“绿地软件开发”（greenfield software development），即从零构建新软件，而非修改既有代码库。
- **核心矛盾**：真实客户委托通常只给出不完整的初始需求，关键功能与接口细节缺失；编码智能体必须主动澄清需求，才能独立交付可用软件。
- **两个现实约束**：
  - 开发周期长，客户难以持续提供反馈；
  - 即使客户回答了问题，也不代表智能体真正理解了复杂需求。
- **现有基准的不足**：
  - 多数基准基于编程题目或代码仓库，缺少真实自由职业绿地项目；
  - 部分基准假设开发过程中可持续获得用户反馈；
  - 部分基准主要通过“信息获取”评估澄清效果，而非显式检验需求理解。
- **论文目标**：构建一个基于真实高价值客户委托的基准，同时评估编码智能体的**需求澄清能力**与**独立代码实现能力**。

## 2. 方法论

### 2.1 核心设计思想

- **澄清先于实现**：编码智能体先与客户智能体完成多轮需求澄清，随后在无进一步客户指导的情况下独立实现软件。
- **理解与实现分离评估**：澄清结束后，冻结澄清上下文，分别启动两个互不干扰的分支：
  - 代码实现分支：提交软件并运行验收测试，得到实现得分；
  - 需求理解分支：回答需求问题，并与参考答案比对，得到澄清得分。
- **防止评估泄漏**：评估问题、参考答案和评分结果不进入代码实现分支，避免问题本身提示缺失需求。

### 2.2 交互与角色设计

- **编码智能体**：作为自由职业者，检查初始请求与工作区材料，向客户智能体提问，自主决定何时结束澄清。
- **客户智能体**：基于完整私有需求回答，确认或纠正编码智能体的理解，但不主动泄露完整规格。
- **监督智能体**：在客户回复送达编码智能体前进行审核，检查事实准确性、回答完整性和范围控制；不合格回复退回修改，只有批准后的回复才可见。
- **评审智能体**：对需求理解分支的回答进行评分，不参考代码测试结果。

### 2.3 评分机制

- **实现得分**：任务所有验收测试通过记 1，否则记 0；实现得分为通过任务百分比（任务通过率）。
- **澄清得分**：对每个需求问题按三级评分：
  - Correct = 1：完整正确陈述所有实质需求；
  - Partial = 0.5：有实质正确内容，但存在重要遗漏或不确定性，且无明确矛盾；
  - Incorrect = 0：存在实质矛盾或没有实质正确答案。
  - 先按任务内问题平均，再跨任务等权平均。
- **需求单元（RU）**：将每条客户需求与其需求问题、验收测试关联；辅助指标为 RU 通过率，用于分析需求级表现。

### 2.4 基准构建流程

- 从 Upwork 真实软件开发工作中筛选任务，要求总付款至少 4,000 美元；
- 初始候选 122 个，最终保留 100 个可本地复现、可脱离客户账户和外部部署、适合验收测试的任务；
- 使用 GPT-6 Astra 分析初始请求与真实客户—自由职业者对话，识别显式和上下文推断的需求；
- 人工审核客户需求、需求问题与验收测试的一致性；
- 固定交付接口（调用方式、输入输出），但允许智能体自由选择内部实现；
- 构建 512 个需求问题及参考答案，平均每任务约 5 个问题。

## 6. 主要结论与发现

- **独立交付仍然困难**：
  - 实现得分范围为 **39.0%–67.0%**；
  - 最佳模型 GPT-6 Astra 的任务通过率仅为 **67%**，仍有 33 个任务失败。
- **澄清得分与实现得分高度相关**：
  - 9 个模型上两者 Pearson 相关系数为 **r = 0.89**；
  - 但需求级分析显示二者并不完全一致。
- **澄清显著提升表现，但只弥补部分差距**：
  - GPT-5.6 Luna 实现得分从无交互的 6.0% 提升到 49.0%，完整需求下进一步升至 75.0%；
  - GLM-5.3 Flash 从 5.0% 提升到 39.0%，完整需求下升至 71.0%；
  - 标准澄清分别弥补了约 62.3% 和 51.5% 的实现差距。
- **回答正确性与实现成功率相关**：
  - 回答正确时，对应 RU 的代码测试通过率为 **86.3%–91.3%**；
  - 回答错误时为 **33.9%–68.4%**；
  - 但存在“回答正确但实现失败”和“回答部分正确但测试通过”的情况，说明理解与实现是互补但不同的能力。
- **获得信息不等于理解信息**：
  - 在澄清结束时已完全披露的隐藏 RU 中，仍有 **2.8%–6.4%** 的回答被评 Incorrect，**2.4%–14.9%** 被评 Partial。
- **澄清前置优于持续澄清**：
  - GPT-5.6 Luna：实现得分 49.0% vs 26.0%；
  - GLM-5.3 Flash：39.0% vs 13.0%；
  - 澄清得分也均更高。
- **监督审查总体有效**：
  - 在 561 个被修订问题中，46.0% 从错误变为正确；
  - 2.9% 从正确变为错误，净收益为正。
- **成本与得分不完全正相关**：
  - GPT-6 Astra 的平均成本低于两个 Claude 模型，但实现得分更高；
  - 高成本不必然带来更高任务完成率。

## 7. 优点

- **生态效度高**：任务源自真实 Upwork 高价值委托，保留真实业务目标，较编程题或仓库 issue 更接近自由职业交付场景。
- **评估设计有针对性**：
  - 澄清前置，符合长周期项目中客户反馈有限的现实；
  - 实现与需求理解双分支隔离，避免评估问题反向指导编码。
- **显式测量需求理解**：通过独立问答评估“能否正确解释需求”，区别于仅测量信息获取或最终代码结果。
- **监督代理提升客户回复质量**：在回复进入编码智能体前进行事实与范围审查，减少错误信息污染。
- **多维度分析较丰富**：除主得分外，还分析需求披露、答案—实现联合分布、澄清时机、监督审查效果和成本。
- **可复现性较好**：公开 100 个任务、512 个 RU、验收测试、角色提示、评估框架，以及参考/等价/错误实现。
- **统计报告规范**：使用 bootstrap 置信区间、配对比较和人工核验。
- **隐私保护考虑

- **隐私保护考虑**：任务在构建时对客户身份、项目名称和对话中的敏感信息进行脱敏处理，仅保留与需求理解和实现相关的业务内容；公开材料以任务规格、测试和问题为主，降低真实委托信息泄露风险。

## 8. 局限与不足

- **任务筛选带来生态效度折损**：为保证可本地复现和可自动验收，排除了依赖外部账户、第三方服务、硬件设备或强设计评审的项目。因此基准更偏向“接口与行为可测试”的绿地开发，未必覆盖真实自由职业工作中大量存在的探索性、设计导向和运维耦合任务。
- **LLM 代理模拟客户的偏差**：客户、监督和评审均由 LLM 扮演。客户智能体可能过度披露、披露不足或在多轮中被诱导；监督智能体虽能减少错误回复，但其判断本身仍受模型能力与提示设计影响。论文虽报告监督修订的净收益，但未完全量化代理质量对最终排名的敏感度。
- **评审智能体评分的系统性风险**：需求回答采用三级评分，边界情形（如“部分正确但表述模糊”）依赖评审模型判断。人工抽样核验只能发现部分偏差，无法排除评审模型对特定表述风格、长度或模型家族的偏好。
- **信息条件与澄清时机实验覆盖有限**：关键因果性实验仅使用两个模型，且这两个模型在总体排名中并非最强者。因此“澄清弥补约一半差距”“澄清前置优于持续澄清”的结论方向可信，但具体效应量对其他模型是否稳定尚不明确。
- **成本比较不完全公平**：不同模型的服务定价、默认输出长度、推理强度和重试策略不同；成本仅统计编码智能体，未计入客户、监督、评审和回答评分调用。因此表 5 更适合作为同协议下的相对参考，而非完整经济性评估。
- **单一客户/监督/评审模型**：标准协议统一使用 GPT-5.6 Luna 作为辅助角色，未系统交换辅助模型（如用不同家族模型担任客户或评审），难以区分“编码智能体能力差异”与“辅助角色与编码智能体的适配效应”。
- **需求单元划分与测试覆盖的耦合**：RU 通过率依赖验收测试对需求的覆盖程度。若某条需求难以自动测试或被合并测试，RU 级分析可能高估或低估该需求的实际实现情况。
- **未涉及多轮交付与维护**：基准聚焦“澄清—独立实现”的一次性交付，不覆盖交付后客户验收反馈、迭代修改、缺陷修复和长期维护，而这些正是真实自由职业项目的常见阶段。
- **未报告训练或微调实验**：论文仅评测现成模型，未验证澄清能力是否可通过训练、工具调用或结构化需求建模进一步提升，因而对方法改进的指导偏评估层面。

## 9. 对后续研究的启发

- **将“需求理解”作为独立可测能力**：SWE-Clar 的双分支设计表明，仅看最终代码通过率会混淆“没问到”“没理解”和“没实现”三类失败。后续基准可沿用“冻结澄清上下文—分离问答与实现”的范式，用于诊断智能体失败来源。
- **澄清策略值得系统研究**：澄清前置显著优于持续澄清，提示长周期任务中应鼓励智能体在动手前形成较完整的需求模型。未来可研究问题选择策略、何时停止提问、如何复述确认，以及澄清预算与实现收益的权衡。
- **监督与信息质量控制是关键环节**：客户回复并非总是准确完整，监督代理可显著减少错误信息注入。后续工作可探索多评审、对抗式客户模拟、置信度标注和“可追溯需求来源”等机制。
- **需求级指标比任务级指标更细粒度**：RU 通过率与回答标签的联合分析揭示了“答对但未实现”“答错但碰巧通过”等情况。未来可引入需求覆盖矩阵、部分实现得分和失败归因标签，提升评估解释力。
- **代理角色与模型适配需要消融**：客户、监督、评审使用同一模型可能引入相关性偏差。后续可系统交换辅助模型，报告排名稳定性，并分析编码智能体与客户智能体的“配合效应”。
- **从一次性交付扩展到迭代交付**：可在现有基准上增加交付后反馈轮次、变更请求和回归测试，评估智能体在真实客户验收与维护场景中的持续澄清与修改能力。
- **成本—性能联合优化**：高成本不必然高分，说明推理预算分配和澄清效率本身是研究变量。未来可研究自适应澄清深度、按任务难度分配预算，以及以“每美元通过率”为目标的智能体调度。
- **向真实平台落地需谨慎**：基准任务来自 Upwork 但经过筛选和脱敏，实际平台部署还需考虑知识产权、客户隐私、恶意需求、责任归属和交付合同等因素。

## 10. 总体评价

SWE-Clar 的主要贡献不在于提出新的编码模型，而在于把“自由职业绿地开发中的需求澄清”转化为可复现、可自动评分的基准问题。其设计抓住了三个关键点：真实高价值委托、澄清与实现分离、需求理解显式测量。实验表明，当前最强模型在独立交付上仍有约三分之一任务失败；澄清能显著缩小但无法消除与“完整需求”之间的差距；且“获得信息”不等于“理解信息”。这些结论对编码智能体评估具有较强参考价值。

同时，论文的因果性结论主要建立在两个模型和 LLM 代理模拟之上，任务筛选也使其更偏向可测试的工程实现。因此，读者宜将其视为“澄清能力评估的良好起点”，而非对真实自由职业交付全貌的最终结论。后续工作在代理消融、任务多样性、迭代交付和成本公平性上仍有明显改进空间。

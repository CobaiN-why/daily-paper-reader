# Secure and Functional Code Generation with Self-Evaluation 

MD AFIF AL MAMUN, University of Calgary, Canada 

GIAS UDDIN, York University, Canada Large Language Models (LLMs) can generate functionally correct code that remains insecure. Security-focused fine-tuning can be expensive and is not always available, motivating inference-time approaches. Security-oriented prompting and retrieval can reduce vulnerabilities, but may also remove required behavior or apply defenses incompatible with the task. The challenge is to identify relevant security knowledge and use it to improve security without sacrificing functionality. We present SecGent, an inference-time framework that retrieves weakness context from the Common Weakness Enumeration (CWE) database and applies it to secure code generation. By connecting task specifications to relevant textual CWE records, SecGent provides task-specific security guidance without relying on retrieved vulnerable or patched code examples. Complementary functional and security tests check the resulting implementation, and their execution feedback guides repairs toward satisfying both objectives. We evaluate SecGent with four open-source LLMs and Claude Sonnet 5.5 across five programming languages on the CWEval benchmark. It achieves the highest joint functional–security success against four inference-time baselines for all five models. Across the open-weight models, mean functional-security@1 (FS@1) improves by 15.5% over RAG, with gains in both functionality and security, and by 19.8% over the strongest prompt optimizer compiled for each model. On Sonnet, FS@1 reaches 92.1%, outperforming the strongest baseline AutoGen by 4.8%. In a separate comparison, SecGent outperforms Claude Code with security-focused prompting by over 6% in FS@1. Feedback-guided repair further improves FS@1 by up to 6.7% over generation without feedback, primarily by recovering functionality while checking security. 1 Introduction 

Large Language Models (LLMs) can generate code that performs its intended task but remains vulnerable to attack. LLM-based coding tools are increasingly becoming common [37], including GitHub Copilot [15] and assistants based on models such as GPT [1], Claude [7], and Gemini [11]. This gap between functional correctness and security is consequential because passing ordinary tests does not establish that a program is secure (e.g., when handling adversarial inputs) [8, 33, 34, 36]. Security-oriented interventions seek to close this gap, but can introduce another problem by rejecting valid inputs, removing required operations, or applying defenses incompatible with the

Consider a coding task from CWEval, a benchmark that evaluates both functional correctness and security using executable tests [34]. The task asks for a JavaScript function that stores user-provided values in an HTTP response header. Figure 1 shows Qwen3-Coder-30B (Qwen30B)’s implementations. With Direct Prompting, the model stores the value without checking for carriage returns or newlines. The candidate passes the functional oracle, but an attacker-controlled value can inject additional header lines through a CWE-113 response-splitting weakness. All five sampled generations for this task exhibit the same failure. More broadly, 29.2% of functionally correct samples generated with Direct Prompting across our four open-weight models fail CWEval’s security oracle. Functional success alone therefore leaves substantial security risk unobserved. Prior works improve security through model adaptation, decoding constraints, and optimized prompts [2, 13, 18, 19, 23, 32]. CodeGuarder [26] and RESCUE [35] retrieve security explanations and code examples to guide generation. In our evaluation across the four open-weight models, providing task-relevant security context, such as CWE records, through Retrieval Augmented Generation (RAG) [22] improves mean security success over direct prompting but reduces functional correctness. This trade-off also appears in CodeGuarder, which retrieves vulnerability explanations and examples of vulnerable and patched code to guide generation. Its functional losses largely offset its security gains in joint functional–security success (Section 5.1). Figure 1 shows this trade-off. RAG checks for the injection characters, but also restricts Accept-Language to a single language tag. This rejects valid lists such as en-US,en;q=0.9 , so the candidate passes the security oracle but fails the functional oracle; four out of RAG’s five samples fail in this way. Improving security in isolation is therefore insufficient. However, a key challenge is obtaining accurate weakness context from the programming task itself. We use this term for the textual CWE records retrieved as relevant security knowledge for that task. A task specification describes intended behavior, whereas MITRE’s CWE database [27] describes failure mechanisms and their consequences. The header task specification, for example, does not mention carriage returns, newlines, or response splitting. Direct similarity search using the specification can therefore miss the relevant weakness (see Discussion 6.3). Even when a record is retrieved, its applicability must be interpreted against the task’s inputs, operations, and required outputs. Selecting relevant weakness context and applying it appropriately are distinct challenges. We introduce SecGent, an inference-time framework that retrieves weakness context : the CWE records most relevant to a given task, each describing in code-level terms the input, operation, and consequence that characterize the weakness. Its CWE-derived catalogue is constructed without using any specific benchmark task specifications or solutions. At inference time, Hypothetical Doc-ument Embedding (HyDE) query generation [14] expresses plausible weaknesses of the requested operation, and reranking selects the five most relevant records. The coding agent receives this textual weakness context alongside the specification and is instructed to address the security risks while preserving required behavior. Our approach does not provide any vulnerable code or its cor-responding patch examples to the coding agent. The same context guides complementary security and functional tests. For example, a security test checks that adversarial input does not trigger an unsafe effect, while a functional test checks that valid input produces the expected output. The testing agent selects a relevant weakness from the retrieved weakness context and turns its attacker-controlled input and observable effect into a security test, while a functional test checks specified behavior. Execution failures guide a bounded repair loop that permits at most a fixed number of repair attempts and retains a proposal only when it improves one generated-test objective without reducing the other. 2 Background and Related Work 

Security of LLM-Generated Code. Prior studies consistently show that LLM-generated code can contain security weaknesses despite appearing functionally plausible [16, 33, 40, 41]. Studies of LLM-native IDEs also report security and privacy risks in the surrounding development environ-ment [4]. SecurityEval provides vulnerability-oriented programming tasks [36], and CyberSecEval evaluates security-sensitive generation prompts [8]. SecVulEval [3] benchmarks real-world C/C++ vulnerability detection using statement-level annotations and program context, and evaluates LLMs with a multi-agent pipeline. Its focus on detecting vulnerabilities in existing code complements our

focus on secure generation and executable validation. CodeSecEval [42] provides paired insecure and secure Python implementations with functional and vulnerability-targeted security tests for generation and repair. However, this benchmark is limited to Python language only. CWEval evaluates functionality and security on the same candidate using executable oracles [34]. This joint assessment matters because a program can pass security checks by omitting required behavior; security-oriented interventions can therefore appear beneficial while reducing usefulness [12]. We use joint functional–security success as the primary outcome and retain both constituent metrics to expose such trade-offs. 

Secure Generation and Prompt Optimization. General code-generation research has developed open models such as CodeGen [30] and prompting approaches such as self-planning [20] and structured chain-of-thought [24] to improve implementation from natural-language specifications. SVEN [18] and SafeCoder [19] adapt models for secure generation. Inference-time alternatives include constrained decoding [13], CoSec [23], and security prompt optimization with PromSec [29]. General prompt optimizers [21] such as MIPROv2 [32] and GEPA [2], and selective prompt an-choring [39], improve instructions, demonstrations, or their influence during generation. SecGent retrieves task-specific weakness context from a textual CWE catalogue to guide secure implemen-tation, without model adaptation or benchmark-specific prompt compilation. Generated functional and security tests check the resulting behavior and guide repair. 

Task-Aware Security Retrieval. CodeGuarder [26] retrieves vulnerability explanations and examples of vulnerable and patched code from a ReposVul-derived knowledge base [43] after decomposing the programming query into subtasks. RESCUE [35] combines distilled security guide-lines with security-focused code examples and uses hierarchical, multi-faceted retrieval. Both select task-relevant knowledge to augment generation. SecGent shares this goal, but constructs weak-ness context from MITRE’s CWE records without retrieving code examples. Zero-shot catalogue rewriting and HyDE query generation connect task specifications to the vocabulary of software weaknesses, and reranking selects relevant records. The weakness context guides generation and the selection of a weakness for executable security testing. The testing agent grounds that weakness in task inputs and observable behavior without seeing the candidate. 

Execution Feedback and Security Testing. Self-debugging and conversational generation use execution results to revise programs [10, 17], while vulnerability repair uses analysis feedback to guide patches [5]. AutoSafeCoder [31] combines a coding agent with LLM-based static analysis and mutation-based fuzzing that detects runtime crashes. SecTDD [25] studies the effects of exposing security tests and returning execution failures, using supplied visible test partitions and independent hidden evaluation. These works establish that execution feedback is useful and coverage-dependent. SecAwareCoder [42] derives CWE-linked vulnerability hypotheses and mitigation strategies from a stepwise solution blueprint to guide generation and testing. SecGent instead guides generation and testing with MITRE CWE records retrieved through catalogue rewriting, HyDE, and reranking. It validates and freezes tests before code generation, accepting repairs only if they improve functional or security test scores without lowering either. We could not include SecAwareCoder as a baseline because its replication package was unavailable at the time of writing.

SecGent retrieves weakness context from a fixed cata-logue C that is built offline once, before inference (Step 0). The catalogue covers MITRE’s Research Concepts view (CWE-1000) [27] with 944 weaknesses, which organises weaknesses by abstract behaviour and is not tied to a language or domain. Figure 3 shows the automated trans-formation from MITRE source records to retrieval docu-ments. First, the pipeline extracts each weakness’s CWE identifier, name, description, and mitigations. Second, an LLM receives the name and description in a zero-shot prompt and produces a one-sentence description and a short list of code-level keywords. The identifier (CWE-XXX), name, and mitigations are retained; the generated description and keywords supply the context used for retrieval. Each resulting record 𝑐 ∈ C is embedded, and the catalogue is frozen before inference so that every task and evaluated models share the same version of the catalogue. A MITRE record describes a weakness through its flaw and consequences, whereas a program-ming task describes the functionality to implement and seldom names a weakness. We therefore use the rewrite to name the input, the operation, and the consequence in the vocabulary a developer would use. For CWE-117, MITRE states that “the product constructs a log message from external input, but it does not neutralize ...” . The rewritten description reads “user-supplied data is written directly to log ...” , with keywords such as log , format , and write . The rewrite sees only source text. In Section 6.3, we empirically show why such a catalogue is necessary for accurate retrieval. When MITRE publishes an updated release, the same extraction, rewriting, and embedding procedure can be rerun periodically to produce a new catalogue for subsequent inference. We only use MITRE CWE records in this study. The pipeline could also incorporate databases such as NVD [28] through available CWE mappings following the same pipeline. 

3.3 Task-Conditioned Weakness Context 

A coding task 𝑥 = (ℓ, 𝑠, 𝑒 ) comprises the programming language ℓ, specification and required function signature 𝑠 , and execution setup 𝑒 . The setup identifies the entry point and, for compiled languages, the wrapper needed to call it. The coding agent receives (ℓ, 𝑠 ) and retrieved context 𝐾 𝑥 ;the testing agent and executor also receive 𝑒 .

Weakness Context Retrieval. A coding task describes the behavior to implement, whereas CWE records describe patterns of insecure behavior. This vocabulary mismatch makes direct retrieval difficult. For example, the running task (Figure 2) asks the model to construct a log entry, but does not mention log injection, or record separators. To bridge this gap, SecGent adapts Hypothetical Document Embeddings (HyDE) [14]. 3.4 Test Generation 

Functional and security tests provide complementary evidence. A functional test checks whether a candidate preserves behavior required by the task, whereas a CWE-aware security test probes whether a retrieved weakness manifests under adversarial input. Both are necessary: functional tests may not exercise security-relevant behavior, while security-oriented generation can sacrifice functional correctness by removing required logic or producing task-irrelevant code [12]. Before the coding agent 𝐺 𝜃 generates any implementation, the testing agent 𝐴 𝜃 receives only (ℓ, 𝑠, 𝑒, 𝐾 𝑥 ) and authors the functional and security test functions 𝑇 𝑥 = {𝑡 𝐹 𝑥 , 𝑡 𝑆 𝑥 } where each test can have multiple assertions. It never observes the coding agent’s implementations or their execution outputs.

Functional Test. The functional component 𝑡 𝐹 𝑥 checks behavior explicitly required by 𝑠 , using valid inputs or examples from the specification when available. In the CWE-117 example in Figure 2 (Step 4), it supplies Hello, World! and checks the required log format. This establishes the functional behavior that subsequent candidates must preserve. 

CWE-Aware Security Test. The testing agent further selects the weakness in 𝐾 𝑥 whose attacker-controlled input, relevant operation or sink, and observable harmful effect are most directly grounded in the task, and converts it into the security test 𝑡 𝑆 𝑥 . The generated test may exercise multiple adversarial inputs or assert multiple observable effects of the selected weakness. In Figure 2, it supplies a message containing \n and \t and checks that neither control character remains in the returned log entry. Both components are generated as Python test functions that call the candidate through a uniform invoke interface exposing its return value, crash status, standard output, and standard error. Using one function per component keeps the test-suite structure and execution budget fixed while allowing multiple inputs and assertions within each function. Furthermore, a validator in SecGent verifies syntax, exactly one functional and one security test, association with a retrieved CWE, correct use of invoke , and executable assertions. It returns detected issues for revision, up to 𝐴 authoring attempts. A validated suite is frozen and reused unchanged for the initial candidate and every following repair.

3.6 Test Execution 

The test-execution layer bridges the language-independent invoke interface used by generated tests to the language-specific way a candidate must be built and called. An adapter materializes the candidate and benchmark entry point, performs any required compilation or loading, invokes the function, and normalizes its observable result. This lets the testing agent express the same kind of assertion for Python, C, C++, Go, and JavaScript without encoding build or process details in the generated test suite. Each code candidate is evaluated against the frozen test suite in a fresh, throwaway Docker-compatible container. Subprocess and outer timeouts bound execution. The harness separates build failures from assertion failures and classifies the result as candidate evidence (build diagnostics or named functional/security outcomes), a complete pass, or an unusable test suite. An unusable test suite—for example, one that cannot be imported or reported reliably—does not support a conclusion about candidate quality and cannot trigger repair. On the Figure 2 example, the initial candidate passes the ordinary-message test but the security test observes the injected newline and tab. 4.2 Evaluation Benchmark 

We evaluate on CWEval [34], which contains 119 coding tasks spanning 31 CWE classes in five programming languages: 31 C, 21 C++, 19 Go, 23 JavaScript, and 25 Python tasks. 

4.3 Baselines 

We consider methods that do not require fine-tuning an LLM. Apart from the following baselines, we also evaluate Claude Code [6] and compare with our approach (Section 6.1). 

Direct Prompting. The model receives the task specification and an instruction to return only the implementation. It receives no security instruction, retrieved weakness context, optimized prompt, generated tests, or repair feedback. 

RAG [22]. The model receives the task specification, a general secure-code instruction, and the top five CWE descriptions retrieved by querying the vector database directly with the task description, as possible weaknesses to consider. Unlike SecGent, RAG uses neither HyDE query generation nor reranking. 

CodeGuarder [26]. CodeGuarder retrieves vulnerability explanations and vulnerable–patched code examples from a ReposVul [43] and injects them into the generation prompt. In contrast, SecGent retrieves textual CWE records as weakness context and uses generated functional and security tests to check candidate behavior and guide repair. 

Microsoft AutoGen [44]. We instantiate AutoGen agentic framework as a two-agent coder– reviewer workflow. The coder generates an implementation from the task specification, and the reviewer assesses its quality against the task and either approves or rejects it based on that judgment. We allow a maximum of three generation–review cycles per candidate for AutoGen. In contrast, SecGent guides repair with executable functional and security feedback and retains a proposal only if its generated-test score improves without regressing either objective. 

Prompt Optimizers. We evaluate three methods that optimize the code-generation prompt on the training partition (Section 5.2). Each training task provides the language, specification, and retrieved weakness context, and candidate prompts are scored by the same executable functional–security criterion. BootstrapFewShot [21] keeps generated security analyses and implementations that pass both checks as few-shot demonstrations. MIPROv2 [32] jointly searches over instructions and such demonstrations. GEPA [2] revises the instructions using textual feedback from executed evaluations, with the evaluated model acting as both reflector and generator. Each method outputs a reusable prompt, a compiled program , which is then applied unchanged to held-out tasks with their specifications and retrieved weakness context. 

4.4 Experimental Setup 

Large Language Models. The experiments cover two general-purpose LLMs, GPT-OSS-20B (GPT-OSS) and Gemma-4-26B (Gemma4), and two code language models, Qwen2.5-Coder-14B (Qwen14B) and Qwen3-Coder-30B (Qwen30B). To examine whether the findings hold for a frontier proprietary model, we additionally evaluate Claude Sonnet 5.5 (Sonnet-5.5) against the inference-time baselines and in the language-specific and paired repair analyses. The prompt optimizers are applied to the four open-weight models. RQ1 identifies RAG and AutoGen as the strongest baselines at FS@1 across models and establishes SecGent’s consistent advantage over them across all five models. We therefore focus the proprietary evaluation on these common inference-time comparisons and limit RQ2 to the open-weight models because compiling each optimizer entails repeated generation and evaluation on the training tasks, adding substantial API cost for Sonnet. We use the short names throughout the remainder of the paper. Every reported method uses five independently sampled candidates per task and temperature 0.8 (excluding Sonnet-5.5, which does not allow temperature

changes), and we report 𝑘 ∈ { 1, 2, 5}. SecGent permits at most two test-generation attempts and two repair proposals. We serve all open-weight models locally using Ollama and access Sonnet-5.5 through the Anthropic API. 

Embedding Model. We encode the CWE records and every task query with Qwen3-Emb-8B [45] and retrieve by dense similarity over these embeddings. We selected this model because it is openly available and reported to be competitive with proprietary embedding models on multilingual and code retrieval benchmarks [45], which keeps the retrieval component of the study reproducible. The same encoder is used by all methods except CodeGuarder when required. CodeGuarder retains its own published CVE-based retrieval setup. Alternative encoders would likely change absolute retrieval quality; we do not vary them here, as isolating the effect of the encoder is outside the scope of this study. 

CWE Database. Retrieval draws on a fixed catalogue of 944 weaknesses from MITRE’s Research Concepts view (CWE-1000) [27], which organises weaknesses by abstract behaviour rather than by language or domain and thus gives the broadest coverage of software weaknesses. We build the catalogue in two steps. First, we take each weakness’s identifier, name, description, and potential mitigations from the MITRE records. Second, an LLM (Qwen3.8:27b) is prompted once, in a zero-shot setting, with the MITRE name and description of each weakness and rewrites them into a one-sentence description and a short list of code-level keywords, that name the input, operation, and consequence in the vocabulary a developer would use. The generation does not involve any benchmark task. Each entry thus holds the identifier, name, generated description, keywords, and MITRE mitigations. The catalogue is built offline and frozen before the experiments. 

Retrieval Pipeline. Given the task’s language and specification, the query writer identifies an operation that could make the code vulnerable. It describes how that operation could be implemented insecurely and explains the resulting weakness without naming a CWE. We combine these last two descriptions with the task specification to form the retrieval query. Each CWE record is embedded using its name, rewritten description, keywords, and up to 600 characters of MITRE mitigations. We retrieve the 20 records whose embeddings are most similar to the query embedding. The reranker compares each record’s name and description with the operation and insecure implementation described by the query writer, assigning a relevance score from 0 to 100. It scores all 20 records together in three calls: one in retrieval order and two in shuffled orders. We average the scores to reduce the influence of candidate order, then use the five highest-scoring records to guide code and test generation. We use qwen3.8:27b for query writing and reranking and reuse each task’s retrieved records across all evaluated models. 

Hardware. Local model inference and candidate evaluation were run on a single compute server with 96 Intel Xeon Gold 6442Y cores and two NVIDIA L40S GPUs (48 GB each). Model checkpoints were obtained from the official Hugging Face and Ollama (as required) repositories of each open-weight model. Sonnet inference used the Anthropic API; candidate code was evaluated in isolated containers with no internet access.

Its advantage therefore comes from addressing security weaknesses while preserving required behavior. This pattern extends across the open-weight models: compared with RAG, SecGent improves mean functional and security success by 14.5% and 9.1%, respectively. 6.3 Retrieval Quality and Its Limits 

Retrieval Coverage. Table 6 compares retrieval over all 119 tasks. Direct dense retrieval uses the task specification to search embeddings of MITRE’s original CWE-1000 records [27], without rewriting their descriptions or generating a HyDE query. Recall counts the benchmark CWE or a direct child as a correct match. Direct retrieval achieves 47.1% recall among the top five records, increasing to 67.2% with reranking. With SecGent’s rewritten catalogue (Section 3.2) and HyDE query (Section 3.3), recall reaches 75.6% before reranking and 89.1% afterward. These results support the combined catalogue and query design for bridging the vocabulary gap between task requirements and weakness descriptions. 

Relevance Beyond the Benchmark Label. Missing the benchmark CWE does not always mean missing a relevant weakness. Among the 13 misses, four tasks retrieve a CWE relevant to their security tests. For example, the three cwe_327_2 tasks are labeled CWE-327 (unsafe cryptographic algorithms). Their tests also check for random initialization vectors (IVs, starting values used in encryption), making the retrieved CWE-329 (predictable IVs) relevant. 7 Threats to Validity 

Internal Validity. LLM generation and test execution are stochastic, which may affect individual outcomes. We mitigate this by sampling five candidates per task and holding the model identifier, decoding settings, sample count, and evaluation split fixed within each comparison. Generated test suites may also be incomplete or incorrect. To avoid treating them as ground truth, they are used only to guide repair; all reported functional and security outcomes are determined independently by CWEval. Unusable generated test suites trigger no repair, and the initial candidate is retained instead. 

External Validity. We evaluate four open-weight LLMs and Claude Sonnet 5.5 on all 119 CWEval tasks for RQ1 and RQ4, and on 48 family-disjoint tasks for RQ3. RQ2 evaluates prompt optimizers only on the four open-weight models; their comparison on Sonnet remains outside the scope of this study. Including Sonnet extends the evidence to a proprietary API model, but does not establish generalization across proprietary model families. The benchmark spans five programming languages and 31 weakness classes. Although this provides diversity across models, languages, and weaknesses, CWEval consists of function-level programming tasks and may not represent repository-scale development, long-context interactions, or proprietary coding assistants. Generalization to such settings therefore requires further study. 

8 Conclusion 

We presented SecGent, an inference-time framework that connects programming tasks to relevant CWE knowledge for generation, testing, and repair. Our findings suggest that security guidance is most useful when grounded in the task’s required behavior and checked alongside functionality. Execution feedback primarily recovers functionality, while security test check whether repairs preserve the tested protections; the reliability of these repairs depends on the correctness and cov-erage of generated tests. Across five models and five languages, SecGent achieves the highest joint functional–security success among the evaluated inference-time baselines, including Claude Code. Future work should extend the catalogue with additional weakness and vulnerability databases, such as NVD through CWE mappings, and assess whether broader knowledge improves retrieval and security coverage. It should also validate generated security tests against vulnerable and cor-rected variants, broaden valid-input coverage, and evaluate the framework in repository-scale development.

# Standards-Guided and Dependency-Aware Code-Level Documentation Generation 

Tingxu Han ∗, Wei Song ∗, Ziming Li ∗, Yuchen Chen, Weisong Sun †,Zhenpeng Chen, Chunrong Fang †, Zhenyu Chen, and Yang Liu 

✦

Abstract —Automatically generating high-quality documentation for software repositories remains challenging because existing approaches largely treat documentation as an unconstrained text generation prob-lem. As a result, they often lack explicit quality specifications, depend heavily on long-context prompts over raw code, and provide limited sup-port for reproducible evaluation. We argue that code-level documenta-tion generation should instead be formulated as a standards-guided software engineering task , in which documentation is generated and assessed against explicit, reusable quality requirements derived from authoritative documentation standards. In this paper, code documenta-tion refers to natural-language descriptions of repository functions and classes, organized by source-code path. We present C ODE DOC , a standards-guided and dependency-aware framework for code-level documentation generation. C ODE DOC iden-tifies dependencies between code entities using static call-graph and AST analysis. It then constructs dependency-aware structured prompts that combine local code context, repository paths, and documentation criteria derived from authoritative standards and style guides. We further introduce an interactive LLM-as-a-judge protocol that provides criterion-aligned feedback to optimize generated documentation, enabling tar-geted refinement based on fine-grained dimensions derived from formal and practice-oriented documentation standards. Experiments on ten open-source Python repositories show that C ODE DOC produces higher-quality documentation than both RepoAgent and a long-context base-line under standards-aligned evaluation, with relative improvements of 11.6%–17.0% and 21.4%–29.6%, respectively, while consuming roughly an order of magnitude fewer tokens per documentation entity than the long-context baseline. A human evaluation study confirms substantial alignment between LLM-based and human judgments (Spearman’s 

ρ = 0.72 ), and the relative findings are preserved across different judge LLMs. Code is available at https://github.com/ControllableModel/ CodeDoc. 

Index Terms —Code documentation generation, repository-level code understanding, documentation standards, large language models, static analysis, LLM-as-a-judge.

1 INTRODUCTION 

Throughout the software lifecycle, developers continuously interact with existing code artifacts [1]–[4], especially during tasks such as feature extension [5], bug fixing [6], code review [7], and system maintenance [8]. A growing body of empirical evidence shows that a substantial portion of developers’ effort is devoted to understanding existing code rather than writing new functionality [9]–[11]. In this context, high-quality code documentation plays a critical role in facilitating code comprehension, supporting collab-oration, and improving the maintainability and evolution of software systems. However, maintaining documentation manually is labor-intensive and error-prone [12], [13]. As software evolves, documentation often becomes incomplete, inconsistent, or outdated, reducing its usefulness and po-tentially harming overall software quality. These challenges have motivated increasing research interest in automatic code documentation generation, with the goal of reducing manual effort while improving the availability and quality of software documentation [14]–[16]. Project-level documentation describes the repository as a whole, such as README, CONTRIBUTING, and LICENSE files. Architecture-level documentation explains higher-level de-sign and interface information, such as architecture descrip-tions and API documents. code-level documentation, which refers to natural-language descriptions attached to individual code entities, such as function and class descriptions and docstrings. Different from inline code comments, which are implementation-level annotations embedded in the code body that explain how or why particular statements work, code-level documentation describes an entity’s purpose, behavior, interface, and role within the repository, forming a self-contained description. Repository-level documentation can be constructed by orga-nizing these entity-level descriptions according to the source code structure, but our study specifically targets generating documentation for a single code entity at a time. Existing research on automatic code documentation gen-eration falls into three strains. Heuristic-based methods gen-erate documentation through handcrafted templates, rules, or retrieval over similar fragments [18]–[25]. They are inter-pretable and controllable, but rely on manually designed heuristics or code-similarity assumptions and generalize poorly to large, evolving codebases, especially in repository-level settings with cross-file and cross-function dependen-cies. Neural model-based methods learn mappings from code to natural language using pretrained code models such as CodeNN [25], CodeBERT [26], and PLBART [27], sub-stantially improving semantic modeling, but most focus on function-level summarisation rather than repository-wide coverage. LLM-based methods leverage in-context learning and long-context capabilities of general-purpose LLMs to produce more fluent and adaptable documentation, and recent repository-level systems such as RepoAgent [16] and RepoSummary [14] explicitly incorporate directory struc-tures, code dependencies, and feature-level organization to improve global coherence beyond isolated method-level summaries. Despite these advances, existing approaches still face several fundamental challenges: 1 They lack ex-plicit and verifiable documentation criteria, leaving the no-tion of what constitutes high-quality documentation largely implicit and inconsistent across tools and usage scenarios; 2 They often incur high token costs because they rely on deep recursive analysis and redundant dependency inputs, which limit scalability and hinder practical deployment on large repositories. 3 Their code understanding can become unstable when excessively long contexts are provided, as critical information may be diluted by irrelevant details, leading to inconsistent or inaccurate documentation gen-eration. 4 Their evaluation methods still rely heavily on human judgments and subjective assessments, which makes results harder to reproduce and limits objective comparison across methods. To address the above challenges, we formulate automatic code documentation generation as a standards-guided and verifiable generation task, in which the content, structure, and scope of the generated documentation are explicitly constrained by well-defined documentation requirements derived from documentation standards. In this work, we propose C ODE DOC , a standards-guided and dependency-aware framework for code-level documentation generation. We first extract documentation standards from authoritative sources, including ISO/IEC/IEEE standards and widely used style guides, and convert them into explicit criteria that define what to document and how to structure it. Guided by these criteria, C ODE DOC generates accurate and structured documentation by combining standards grounding with static program analysis. It further incorporates dependency-aware context construction to capture relationships between code entities across the repository, and closes the loop with a criterion-aligned LLM judge whose feedback iteratively refines the generated documentation against the same stan-dards. The main contributions of this work are as follows:  

> •

We present a standards-guided perspective on automatic code documentation generation, systematically deriving explicit and actionable documentation criteria from au-thoritative ISO/IEC/IEEE and GitHub documentation standards. The resulting criteria provide a reusable foun-dation for both defining and evaluating documentation quality.  

> •

We propose CODE DOC , a standards-guided and dependency-aware framework for code-level documentation generation. C ODE DOC couples standards-derived criteria with AST-based structural analysis and static call-graph dependency modeling, constructing dependency-aware structured prompts that improve repository-level code understanding while reducing redundant context and token consumption.  

> •

We introduce a criterion-aligned LLM-as-a-judge proto-col that plays a dual role: it provides dimension-level feedback to iteratively optimize the generated documen-tation in a closed loop, and it doubles as a reproducible, standards-grounded evaluation paradigm—so that a sin-gle explicit specification governs both generation and assessment.  

> •

We conduct experiments on ten open-source Python repositories, showing that CODE DOC improves doc-umentation quality by 11.6%–17.0% over RepoAgent and 21.4%–29.6% over a long-context baseline under standards-aligned evaluation, while consuming roughly an order of magnitude fewer tokens per documentation entity. The LLM-based evaluation aligns with human judgment (Spearman’s ρ = 0 .72 ), and the relative findings are preserved across different judge model families. 

2 BACKGROUND 

2.1 Code-Level Documentation Generation 

Software documentation can describe a repository at dif-ferent levels, from project-level files such as READMEs to architecture-level documents and code-level descriptions. ISO/IEC/IEEE standards [28] treat source code as a dis-tinct life-cycle artifact subject to inspection, analysis, ver-ification, and validation. Following this source-code-level perspective, we define code-level documentation as natural-language descriptions attached to individual code entities, such as functions, methods, and classes. Typical examples include Python docstrings, Javadoc comments, and Doxy-gen documentation blocks, which are written alongside source code and can be extracted into API or reference documentation [29]–[31]. Code-level documentation gener-ation therefore aims to automatically produce such entity-level descriptions from code, a task commonly studied as function or method documentation generation in prior work [26], [32]. In this paper, we focus on generating doc-3

umentation for a single code entity at a time, rather than producing project- or architecture-level documents. 

2.2 Formalizing Code-Level Documentation Genera-tion as a Standards-Guided Task 

Let a code repository be represented as C = ( E, R), where E

denotes a set of code entities (functions and classes within scope, plus enclosing modules used for path metadata), and 

R denotes the structural relations among them, such as call relations, import dependencies, and module hierarchies. The documentation target is code-level : we produce one natural-language artifact per code entity, with the repository structure R serving as generation context rather than as the documentation unit. Formally, code-level documentation generation produces a set of per-entity artifacts D = {de |

e ∈ E} , where each de explains entity e at an appropriate level of abstraction given its relevant context in R. Unlike unconstrained natural language generation, the quality of each documentation artifact is governed by a set of explicit documentation criteria Q = {q1, q 2, . . . , q n} that are them-selves derived from authoritative documentation standards (e.g., ISO/IEC/IEEE standards, mature open-source style guides). Each criterion qi specifies a concrete, assessable requirement, such as covering core functionality, clarifying inter-module dependencies, or describing usage assump-tions. Collectively, these criteria define both the information that should be documented and how it should be organized. Under this formulation, code-level documentation genera-tion can be modelled as a standards-guided generation task 

in which the criterion set Q acts as the bridge between high-level documentation standards and low-level genera-tion behaviour. Because documentation quality is inherently graded rather than binary, we associate each criterion qi

with a per-entity scoring function si(de, C) ∈ { 1, . . . , S }

that measures how well artifact de satisfies qi, where S is the maximum score (in our experiments, S = 5 ). The generation objective is the mean over entities and criteria:

In practice, the method presented in Section 3 approximates this objective through iterative prompt-and-refine generation guided by criterion-level feedback, rather than through formal opti-mization over the documentation space. 

3 METHODOLOGY 

In this paper, we present an automated framework for gen-erating and evaluating code-level documentation by inte-grating static program analysis with large language models (LLMs). As shown in Figure 2, the framework is organized into two phases. Phase (a) Offline Criteria Extraction (Sec-tion 3.1) is performed once, ahead of any repository being processed, and turns authoritative documentation standards into an explicit, reusable criterion set Q. Phase (b) Online Code Documentation Generation is the per-repository run-time pipeline; it consists of Stage 1 (Section 3.2), which builds a dependency-aware structural representation from the source code, and Stage 2 (Section 3.3), which combines that representation with Q to produce, organise, and refine the per-entity documentation. Together, the three components support standards-guided , dependency-aware , and token-efficient code-level documentation generation, departing from prior work that relies on long-context prompting over raw source code without explicit quality specifications. The remainder of this section describes the three compo-nents in order: Section 3.1 details Phase (a); Section 3.2 and Section 3.3 detail Stages 1 and 2 of Phase (b); and Section 3.4 walks through a representative example end-to-end. 

3.1 Phase (a): Offline Criteria Extraction 

Both stages of Phase (b) rely on an explicit set of documen-tation criteria Q derived once, offline, from authoritative documentation standards. The criteria simultaneously serve two roles: they constrain what Stage 2 must produce (as part of the structured prompt), and they form the rubric under which the document judge inside Stage 2, as well as any external evaluator (Section 4), scores the generated artifacts. Making these criteria explicit, fine-grained, and standards-aligned is what distinguishes C ODE DOC from prior repository-level documentation systems that rely on implicit, ad-hoc prompts. Source standards: we draw criteria from two comple-mentary references that together cover formal and practice-oriented documentation expectations. ISO/IEC/IEEE soft-ware documentation standards [33] provide a formal en-gineering rubric covering correctness, completeness, con-sistency, modular organisation, maintainability, accessibility, internationalisation, safety, and update discipline; we adopt them as a baseline against which “engineering-grade” doc-umentation is assessed. The GitHub documentation style guide encodes the practice of widely used open-source doc-umentation, including developer-facing readability, task-oriented organization, navigability, procedural clarity, and contributor usability; we adopt it to complement the formal ISO rubric with the developer-experience axis. Extraction pipeline: we operationalize the standards into machine-actionable criteria in two steps. (i) Candidate extrac-tion. GPT-5-mini processes each source standard document and is prompted to identify distinct, assessable quality aspects, producing candidate items of the form (category, di-mension, description, scoring guideline) where each dimension corresponds to one independently verifiable property. This step yields an over-complete set that may contain duplicates and ambiguous phrasings. (ii) Manual review and normalisa-tion. We manually inspect the candidates, deduplicate se-mantically overlapping entries, and normalize the wording so that each dimension maps to a concrete, independently scorable aspect. 3.2 Phase (b), Stage 1: Source Code Analysis 

Stage 1 builds the refined repository representation C′ =(E, R′) that serves as the structural interface to Stage 2. Following the scope defined in Section 2.1, the analysis is performed at function and class granularity: each function or class is recorded as an entity in E together with its repository path and source code body, preserving traceabil-ity for downstream documentation placement. Two comple-mentary static analyses populate R′. (i) Call-graph analysis via Pyan3 resolves imports and call sites to produce a repository-level directed call graph; the resulting caller– callee edges form the backbone of R′. (ii) AST parsing of each entity extracts localised structural cues—function signatures, parameter lists, class attributes, and major control-flow constructs—which complement the global call-graph structure with local semantic grounding. The inte-grated representation lets Stage 2 retrieve only dependency-relevant context, reducing redundant inputs and improving repository-level coherence under a controlled token budget. 

3.3 Phase (b), Stage 2: Standards-Guided Documenta-tion Generation 

Stage 2 takes the refined representation C′ together with the criterion set Q from Phase (a), and produces per-entity documentation through an iterative prompt-and-refine loop (see Figure 2). For each target entity the prompt engine selectively retrieves a small set of dependency-relevant entities from R′—typically the direct callers and callees— rather than exposing the LLM to the entire repository. extracted from authoritative documentation standards (the ISO/IEC/IEEE documentation standards and the GitHub documentation style guide). The same Q is used down-stream by both the prompt engine and the document judge, so that a single explicit specification governs both genera-tion and evaluation. 

Phase (b)-Stage 1: Source Code Analysis. Stage 1builds the refined representation C′ = (E, R′) through two complementary static analyses. (i) Call-graph analysis. 

Pyan3 analyses the whole repository and emits a directed call graph in DOT format. Figure 3(a) shows the raw DOT output for our running example, which declares entities such as app__UserService____init__ ,

app__main to app__UserService__init__ 

and from app__UserService____init__ to

At this point the representation captures only dependency structure; no source code is attached, since the DOT format records relations without implementation details. (ii) AST parsing. AST parsing then complements the call graph with localised structural cues. Figure 4(a) presents the AST hierarchy of the same repository: the root node represents the project, with child modules app.py 

and utils.py ; app.py contains the class UserService

UserService.__init__ , the prompt engine selectively retrieves its direct callers and callees from R′: it identifies

Finally, the document judge applies Q to score the generated documentation and produce textual feedback, which the prompt engine consumes for a single refinement pass before the LLM regenerates the documentation. This closes the loop within Stage 2 without requiring repeated long-context analysis of the entire repository. 

4 EXPERIMENTAL EVALUATION 

This section evaluates C ODE DOC along a deliberate pro-gression: we first establish that our measuring instrument is sound, then use it to assess quality, and finally dis-sect the cost and mechanism behind the results. RQ1 asks whether the standards-derived, LLM-based evaluation is itself trustworthy—sensitive to quality degradation, aligned with human judges, and stable across judge families. RQ2 then uses this validated protocol to test whether C ODE -DOC improves documentation quality over baselines and whether the gain is broad-based. RQ3 finally asks at what token cost these gains come, which components drive them, and how reliable the static dependency recovery underpin-ning the method is. Each question builds on the previous: RQ2 relies on the rubric validated in RQ1, and RQ3 inter-prets the cost of the quality established in RQ2.  

> •

RQ1 (Evaluation Validity): Is the standards-derived, LLM-based evaluation a trustworthy measure of docu-mentation quality—i.e., is it sensitive to controlled quality degradation, aligned with human judgement, and stable across judge model families?  

> •

RQ2 (Documentation Quality): Does C ODE DOC produce higher-quality documentation than existing baselines un-der the standards-aligned evaluation, and is the improve-ment broad-based across quality dimensions?  

> •

RQ3 (Cost, Components & Reliability): At what genera-tion cost does C ODE DOC achieve these gains, which of its design choices drive them, and how reliable is the static dependency recovery the method depends on? 

4.1 Experimental Setup 

Repositories: We evaluate ten open-source Python repos-itories spanning AI and software-infrastructure domains (Table 5). Each repository is preprocessed by removing directories unrelated to source code (datasets, build arti-facts, configuration files, and pre-existing documentation) so that all methods are run on identical inputs. We measure repository scale by the total number of documentation en-tities (#Class + #Function) and group repositories into small 

(≤ 200 ), medium (200 <·≤ 400 ), and large (> 400 ). Evaluation rubric: All experiments evaluate documen-tation quality under the two standards-derived rubrics in-troduced in Section 3.1: the ISO rubric (7 categories, 14 dimensions, drawn from ISO/IEC/IEEE software documen-tation standards [33]) and the GitHub rubric (5 categories, 12 dimensions, drawn from the GitHub documentation style guide). See Table 7 and Table 8 for the full rubrics. LLM-based judge: Following recent work [34], [35], we use an LLM judge to score generated documentation against predefined criteria. For each dimension, the judge assigns a

4.2 RQ1: Is the Standards-Based Evaluation Trustwor-thy? 

RQ1.a – Criterion sensitivity (controlled masking). To an-swer whether the extracted criteria capture quality, we use a controlled-masking method: if the criteria genuinely capture quality, their scores should fall as quality is progressively removed. We therefore validate whether the extracted cri-teria respond sensibly to controlled quality degradation. Using official PyTorch 2.8 documentation files [36], we select all files larger than 20 KB as high-quality references and randomly mask 20% , 40% , or 60% of each file’s content to obtain four document groups (one clean, three progressively degraded). All groups are scored by the LLM judge under the multi-round strategy only (to isolate criterion sensitivity from intra-dialogue effects) under both ISO- and GitHub-based criteria. Figure 6 shows that both criterion sets assign progres-sively lower scores as the masking ratio increases. The monotonic decline indicates that the extracted dimensions respond to controlled information loss rather than produc-ing arbitrary scores. The two standards differ in magnitude: the ISO criteria drop more sharply under heavy masking (sensitive to structural incompleteness), whereas the GitHub criteria degrade more gently (consistent with their emphasis on readability rather than formal completeness alone).

5 THREATS TO VALIDITY 

We organise threats to validity along construct, internal, and external dimensions. 

Construct validity. Our evaluation relies on an LLM judge that scores documentation against predefined criteria, raising two concerns: judge reliability and rubric circularity. For reliability, RQ1.a shows that the judge responds consis-tently to controlled quality degradation, and RQ1.b corrobo-rates it against human scores ( ρ = 0 .72 , κ = 0 .51 ) and across model families. For circularity—the same criteria drive both the generation prompt and the evaluation rubric—we note that the sensitivity test in RQ1.a uses official PyTorch doc-umentation rather than C ODE DOC outputs, validating the rubric independently of our method, and that all baselines are scored under the same rubric so any criterion-alignment inflation affects them equally. 

Internal validity. The Long-Context baseline isolates the contribution of dependency-aware retrieval from sim-ply providing more code context, but additional baselines (e.g., retrieval-only approaches and other repository-context methods) would further strengthen the comparison. The relatively small repository sample ( n = 10 ) limits statistical power. We therefore report per-repository results so con-sistency can be assessed directly. Generation, refinement, and judging in the default configuration all use the same model family (GPT-5-mini), introducing potential same-family bias; the cross-family comparison in RQ1.b provides partial mitigation. The criteria-extraction pipeline uses GPT-5-mini followed by two-author manual normalisation, with a full traceability table from source clauses to dimensions provided in the supplementary material; independent inter-annotator agreement remains future work. 

External validity. The evaluation is limited to ten open-source Python repositories. Pyan3 ’s static analysis cannot fully capture dependencies arising from dynamic Python constructs (RQ3.c), and missed edges degrade downstream quality by 0.31 points on average. Results may therefore not generalize to repositories that rely heavily on dynamic constructs or to other programming languages. 

6 RELATED WORK 

Our work combines automatic code documentation gen-eration, repository-level software understanding, and standards-guided evaluation. Unlike prior approaches that focus on method-level summarization or repository-level prompting, we ground both generation and evaluation in explicit criteria derived from authoritative standards [33]. 

6.1 Software Documentation and its Quality 

Software documentation is critical for software evolution, maintenance, and developer productivity, yet maintaining high-quality documentation remains challenging, especially in large and rapidly evolving systems [1], [4], [6], [11]. While documentation quality depends on multiple dimensions, in-cluding accuracy, completeness, consistency, readability, and maintainability, these attributes are rarely defined through explicit and actionable criteria. We therefore treat docu-mentation quality as an assessable engineering objective, grounding both generation and evaluation in established documentation standards rather than subjective judgments. 11 

6.2 Automatic Code Documentation Generation 

Early work on automatic code documentation generation relied on heuristic, template-based, and retrieval-oriented methods, using code stereotypes, method context, structural cues, and mined developer discussions to generate natural-language summaries for functions or code fragments [18]– [20], [22]–[24], [37], [38]. Such approaches are interpretable but typically limited to local contexts, struggling to capture broader repository structure and cross-file dependencies. Neural models subsequently improved summarisation by learning code-to-text mappings [25]–[27], and the emer-gence of LLMs has enabled zero-shot and few-shot docu-mentation generation with general-purpose LLMs [13], [15]. Much of this literature, however, still focuses on method- or snippet-level generation, where the target is relatively local and self-contained. 

6.3 Repository-Level Documentation Generation 

More recent work has moved beyond isolated functions toward repository-level documentation generation, since real repositories exhibit dependencies across files, mod-ules, classes, and functions, and useful documentation often requires reasoning over this broader context. RepoAgent leverages repository structure and inter-file relationships to generate repository-level documentation [16], and Re-poSummary explores feature-oriented summarisation that emphasises higher-level functional organisation over purely local descriptions [14]. These systems represent an impor-tant step toward practical documentation generation, but they generally define documentation quality implicitly —through prompting strategies, output formats, or high-level user instructions—rather than grounding generation or evaluation in reusable criteria derived from standards or engineering guidelines. In contrast, our work makes documentation criteria first-class: fine-grained criteria are extracted from established standards and used to guide both generation and evaluation. Within the same per-entity scope, we additionally report cost–quality trade-offs and dependency-recovery audits that are typically absent from prior repository-level work. 

6.4 Evaluation of Documentation and Code Under-standing Quality 

Evaluation remains a major challenge in automatic docu-mentation generation. Earlier work relied on human judge-ment or small-scale comparative studies to assess sum-mary usefulness and quality [39], while broader software-engineering research emphasises the importance of rigor-ous and transparent evaluation methodology with careful treatment of datasets, criteria, and metrics [7]. Recent stud-ies on code understandability similarly argue that mean-ingful evaluation should go beyond surface-level fluency and assess whether artifacts genuinely improve compre-hension and developer usefulness [9], [10]. The LLM-as-a-judge paradigm has emerged as a scalable alternative for evaluating generated text, with representative approaches including MT-Bench [34], G-Eval [35], and JudgeLM [40], showing that carefully designed rubrics and prompts can achieve reasonable agreement with human evaluators—a finding that motivates our standards-aligned judge design. In the broader context of repository-level code intelligence, retrieval-augmented approaches such as RepoCoder [41] and benchmarks such as RepoBench [42] demonstrate the value of selectively retrieving cross-file context for code completion; our dependency-aware retrieval shares this motivation but targets structurally relevant context for standards-guided documentation generation rather than completion candidates. Our work differs from prior evaluation practice in two respects. First, rather than relying solely on unconstrained preference judgements, we construct an explicit rubric of documentation criteria derived from formal and practice-oriented standards. Second, we use this rubric to support criterion-level LLM-based evaluation, enabling repository documentation to be assessed in a structured and repro-ducible way that aligns documentation generation with broader software-engineering expectations. 

7 CONCLUSION AND FUTURE WORK 

This paper presented C ODE DOC , a standards-guided and dependency-aware framework for code-level documenta-tion generation. By aligning the generation target, the static-analysis input, and the evaluation unit on the same per-entity scope, and by extracting fine-grained criteria from for-mal ISO/IEC/IEEE standards and practice-oriented GitHub references, C ODE DOC grounds both generation and evalua-tion in a single reusable rubric, departing from prior systems that rely on implicit, ad-hoc prompts. Our experiments show that the standards-derived cri-teria respond consistently to controlled degradation and that the LLM-based evaluation aligns with human judge-ment ( ρ = 0 .72 ) and across judge model families (RQ1); that C ODE DOC improves documentation quality over both RepoAgent and a long-context baseline, with significant effect sizes and broad per-category gains (RQ2); and that dependency-aware retrieval and standards-guided prompt-ing contribute complementarily for a more favourable cost– quality trade-off, while static dependency recovery is high-precision but moderate-recall, with completeness correlat-ing positively with downstream quality (RQ3). Future work includes scaling the human evaluation, extending C ODE DOC beyond Python, supplementing static analysis with dynamic analysis to close the recall gap, and conducting independent inter-annotator validation of the extracted criteria. We believe the standards-guided perspec-tive offers a useful foundation for documentation systems where quality must be assessed not only by fluency, but also by engineering completeness, practical usefulness, and maintainable organization.

## 摘要
仓库级代码生成要求智能体在现有仓库中实现任务需求。为了生成能在仓库中工作的代码，智能体需要仓库证据，例如目标位置、辅助定义、调用方用法和配置约束，这些证据决定了代码应如何定位、集成和执行。由于上下文预算无法容纳整个仓库，现有检索、压缩和结构感知方法依据任务相似性、上下文长度或结构邻近性来选择上下文，但这些标准并不直接衡量所选上下文是否包含上述证据。因此，所选上下文可能看似与任务相关，却遗漏了实现所依赖的证据。我们将这种失败模式称为上下文效用稀释。本文提出 Rivet，一个在固定上下文预算下为编码智能体保留仓库证据的上下文控制框架。Rivet 首先使用信号锚定（Signal Grounding），通过融合词法、语义和结构信号来选择与任务相关的代码锚点。效用链接（Utility Linking）随后通过依赖、使用和配置关系扩展这些锚点，以收集仓库证据。最后，预算塑形（Budget Shaping）按优先级打包证据，并在预算紧张时先将代码片段缩减为签名或摘要，再将其丢弃。我们在两个可执行的仓库级基准 DevEval 和 RepoExec 上，使用四个骨干模型、两种上下文预算（4K 和 8K token）以及八个基线进行评估。Rivet 在所有 16 种设置中均取得最高 Pass@1，并平均比最强基线提高 3.73--5.15 个百分点。此外，使用 Rivet 的 GPT-5-mini 在两个基准上均优于未使用 Rivet 的 GPT-5，同时将推理成本降低 73.3%--84.5%。

## Abstract
Repository-level code generation asks an agent to implement a task requirement inside an existing repository. To produce code that works in the repository, the agent needs repository evidence, such as target locations, helper definitions, caller usages, and configuration constraints, which determine how the code should be located, integrated, and executed. Because the context budget cannot hold the entire repository, existing retrieval, compression, and structure-aware methods select context by task similarity, context length, or structural proximity, but these criteria do not directly measure whether the selected context contains this evidence. As a result, the selected context can appear relevant to the task yet miss the evidence that the implementation depends on. We call this failure mode context utility dilution. In this paper, we propose Rivet, a context control framework that preserves repository evidence for coding agents under a fixed context budget. Rivet, first uses Signal Grounding to select task-related code anchors by fusing lexical, semantic, and structural signals. Utility Linking then expands these anchors through dependency, usage, and configuration relations to collect repository evidence. Finally, Budget Shaping packs the evidence by priority and, when the budget is tight, reduces snippets to signatures or summaries before dropping them. We evaluate Rivet, on two executable repository-level benchmarks, DevEval and RepoExec, with four backbone models, two context budgets (4K and 8K tokens), and eight baselines. Rivet, achieves the highest Pass@1 in all 16 settings and improves over the strongest baseline by 3.73--5.15 percentage points on average. Moreover, GPT-5-mini with Rivet, outperforms GPT-5 without Rivet,on both benchmarks while reducing inference cost by 73.3%--84.5%.

- **研究背景**：仓库级代码生成要求智能体在已有仓库中实现某个函数或任务。生成代码不仅要“语义上像”，还必须与仓库中的目标位置、辅助函数、调用方接口、依赖和配置约束兼容。

- **关键概念——上下文效用稀释（context utility dilution）**：选中的上下文看似与任务相关，却缺少目标定位、辅助定义、调用用法、配置约束等决定“代码如何嵌入仓库”的证据；相关但无用的文本挤占了预算。
- **整体含义**：论文主张仓库级编码智能体的上下文构建应从“相关性排序”转向“证据保持/效用保持”，即从任务在仓库中的落点出发，沿静态关系收集真正约束实现的证据。

## 2. 方法论

### 核心思想
Rivet 是一个**无需训练的确定性上下文控制框架**：先定位任务相关代码锚点，再沿依赖、使用和配置关系扩展证据，最后在固定 token 预算下按优先级和表示粒度打包上下文。

### 关键技术流程

1. **查询构建**
   - 将自然语言需求转为加权查询词集合。
   - 识别需求中显式出现的标识符、文件路径、函数签名、包名等代码提及，并赋予更高权重；按 camel-case / snake-case 切分。

2. **Signal Grounding：定位任务锚点**
   - 在文件级上融合三类信号：
     - **词法信号**：字段化 BM25F，字段包括 `path`、`symbol`、`sigdoc`、`content`，路径和符号字段权重更高。
     - **语义信号**：基于 TF-IDF + LSA 的潜在语义相似度；小仓库回退到 TF-IDF 余弦相似度。
     - **结构信号**：在文件级 import 图上，以词法+语义归一化分数为种子，用 Personalized PageRank 传播相关性。
   - 用 **Reciprocal Rank Fusion（RRF）** 融合三类排名，并加入代码提及先验；取 top-\(k=6\) 文件作为任务锚点。

3. **Utility Linking：沿仓库关系扩展证据**
   - 将仓库建模为有向、带类型、带权重的代码片段图，边类型包括：
     - `import` / `symbol-ref`：依赖证据；
     - `caller`：使用证据；
     - `config`：配置/打包证据。
   - 从锚点出发收集三类证据：**依赖证据、使用证据、配置证据**。
   - 在证据图上再次进行相关性传播，边权体现优先级，例如 `import` 高于 `symbol-ref`、`caller`、`config`；直接连接锚点的证据得分更高。
   - 限制每类证据数量，如最多 12 个依赖、10 个使用、10 个配置片段。

4. **Budget Shaping：预算内打包**
   - 按证据角色分优先级：
     - Tier 1：目标任务上下文 + 直接依赖；
     - Tier 2：使用证据 + 间接依赖；
     - Tier 3：配置证据。
   - 使用**表示阶梯**：`完整片段 → 签名 → 紧凑摘要`。预算紧张时先降低表示粒度，再考虑丢弃，尽量保留高优先级证据的至少签名。
   - 排序时以 tier 为主键，以“锚点相关性 + 证据相关性”的 RRF 为次键。
   - 对不同证据段设置 token 上限，例如 4K 预算下目标/依赖/使用/配置约为 1400/420/240/140 tokens；8K 下约为 2500/1200/800/500 tokens。
   - 最终输出打包后的仓库上下文，注入编码智能体。

## 6. 主要结论与发现

- Rivet 在 **全部 16 个设置**中取得最高 Pass@1。
- 相对最强基线平均提升：
  - DevEval：4K 下 **+5.15** 个百分点，8K 下 **+4.36** 个百分点；
  - RepoExec：4K 下 **+3.73** 个百分点，8K 下 **+4.65** 个百分点。
- 所有设置平均 Pass@1 为 **55.74**。
- 4K 预算的 Rivet

- 4K 预算的 Rivet 在多数“模型 × 数据集”组合上仍优于 8K 预算下的最强基线，说明**上下文效用保持比单纯扩大预算更关键**；增加预算并不能自动弥补证据缺失，而按证据角色组织上下文可以在较小预算下获得更高收益。
- 提升在不同骨干模型上方向一致，未出现“仅在强模型上有效”的现象；这表明收益主要来自上下文构建方式，而非依赖某个模型的特定能力。
- 在 RepoExec 这种强调“生成代码能否在仓库中正确执行”的基准上同样有效，说明 Rivet 改善的不只是词法/语义相似度，而是实际可执行性所依赖的接口、依赖与配置证据。

### 消融与机制发现
- **三阶段消融**：去掉 Signal Grounding、Utility Linking 或 Budget Shaping 均导致 Pass@1 下降，说明“定位锚点—扩展证据—预算打包”三者互补；其中 Utility Linking 的移除通常带来较明显退化，支持“相关上下文不等于可用证据”的核心论点。
- **关系类型消融**：分别移除依赖、使用、配置证据均造成性能损失。依赖证据主要保障接口与符号可解析；使用证据帮助模型遵循仓库内既有调用惯例；配置证据在 RepoExec 上影响更突出，因为打包、入口和运行约束直接决定代码能否在仓库中执行。
- **图组件消融**：去掉图排序、结构接地或仅保留依赖边都会降低效果，说明结构传播与多关系建模并非装饰性组件，而是把“任务落点”转化为“实现约束”的关键机制。
- **定位分析**：Rivet 的目标文件定位指标（Target@1、Target@5、MRR）表现较强；但即使给基线提供真实目标位置的 Target-Local 仍落后于 Rivet，说明 Rivet 的收益不仅来自“找对文件”，更来自找到文件后**保留了哪些证据、以何种粒度呈现**。
- **成本分析**：Rivet 不调用额外 LLM 进行压缩或总结，上下文构建是确定性的，因而在推理调用次数和美元成本上不高于依赖 LLM 压缩的基线；其“预算效率”同时体现在 token 与 API 成本两个层面。

### 定性案例
- 在 `cookiecutter::get_user_config` 案例中，Rivet 能同时呈现目标位置附近的实现线索、被调用的辅助函数、调用方用法以及相关配置/打包约束，使模型避免仅凭函数名猜测 API 语义；相比之下，纯相似度检索容易召回“主题相关但接口不兼容”的代码。

## 7. 局限与未来工作

- **任务范围有限**：实验集中在 Python、函数级仓库代码生成；尚未覆盖多文件协同修改、issue 修复、特性实现、跨语言仓库等更复杂的仓库级任务。
- **仓库规模与图构建成本**：论文未系统报告超大仓库下的解析、图构建和排序开销；虽然不调用 LLM，但静态分析、图传播和打包仍可能随仓库规模增长。
- **超参数敏感性不足**：锚点数量、每类证据上限、tier 预算分配、表示阶梯阈值等均为固定设置，缺少系统性敏感性分析；不同仓库形态下最优配置可能不同。
- **基线调参公平性**：基线未进行方法特定调参，虽然统一了脚手架与预算，但可能低估某些基线在最优配置下的表现。
- **证据类型仍以静态关系为主**：对动态调用、反射、运行时配置、生成代码等静态图难以捕获的依赖覆盖有限；未来可结合轻量执行痕迹或测试反馈扩展证据来源。
- **表示粒度的语义损失**：签名或摘要压缩在预算紧张时可能丢失关键语义；如何学习“最小充分证据”的表示仍是开放问题。

## 8. 对实践的启示

- 仓库级编码智能体的上下文工程应从“检索最相关片段”转向“收集约束实现的证据”：目标落点、直接依赖、调用用法、配置约束应被显式区分并分层保留。
- 在固定预算下，**先降粒度、再丢证据**的表示阶梯比简单截断更符合代码生成需求；高优先级证据至少保留签名，可显著降低接口误用。
- 结构信号与词法/语义信号应融合而非互斥；Personalized PageRank 等图传播方法能以较低成本把局部相关性扩展为仓库级证据。
- 不调用 LLM 的确定性上下文构建在成本与可复现性上具有优势，适合作为智能体脚手架中的默认上下文层。

## 9. 总体评价

Rivet 的核心贡献在于把仓库级代码生成的上下文问题重新表述为**证据效用保持**问题，并给出一个无需训练、可解释、成本可控的三阶段框架。实验覆盖两个可执行基准、四个骨干模型、两种预算和八类基线，配合阶段/关系/图组件消融、定位分析与成本分析，结论具有较好的内部一致性与统计支撑。其主要不足在于任务与语言覆盖有限、超参数敏感性分析缺失，以及对动态依赖和超大仓库的可扩展性讨论不足。总体而言，该工作为“如何在不扩大预算的前提下提升仓库级代码生成可靠性”提供了有说服力的方法论与实证依据。

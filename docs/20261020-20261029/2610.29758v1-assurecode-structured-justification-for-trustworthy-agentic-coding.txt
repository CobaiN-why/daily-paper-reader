In this work, we propose the use of structured argumentation in driving AI-assisted software development. 1 Introduction 

The software engineering landscape is undergoing a radical transformation through the widespread use of LLM-based (“agentic”) tools as software development assistants [12]. These tools allow for large volumes of code to be rapidly generated, which has the potential to increase developer productivity. However, this scale of generation also raises the question of trust in the generated artifacts. In traditional software development, developers are directly involved in implementing their systems and can draw on their understanding of the development context and requirements to assess whether the resulting software is adequate. AI-assisted software development creates a greater separation between what the developer intends and what gets produced. Accordingly, the role of human developers is evolving, with less emphasis on directly implement-ing code and more emphasis on specifying requirements, steering agentic tools, and evaluating their outputs. In order to have trustworthy code, we require a sufficiently clear and precise account of what the software is intended to accomplish (e.g., requirements and specifications), and we must have concrete evidence that the software satisfies particular properties (e.g., successful execution of tests). We must also have grounds for believing that this evidence is sufficient to establish alignment between the software artifact and the developer’s intentions. Because of their centrality in establishing trustworthiness, offloading specification of intention and determination of evidence adequacy to agentic tools is more problematic than offloading the implementation of code. We therefore argue that trustworthy agentic development requires a disciplined notion of justification : an explicit and systematic account of reasons why the requirements, implementation, and evidence produced during development warrant trusting that the resulting software realizes the developer’s intentions. To this end, this work introduces a language of structured justification rationales , inspired by structured assurance cases developed for safety-critical systems [19, 29]. A justification rationale explicates not only the properties a program should satisfy and the evidence used to establish them, but also the additional issues that must be addressed to justify the adequacy of this evidence. 2 Motivation and Background 2.1 Trustworthiness in Agentic Software Development 

As outlined in Sec. 1, our starting observation is that in order for software to be trusted , at least three elements are needed: (1) intention , i.e., what the developers of the artifact intend for it to do (and not do); (2) verification , i.e., some analysis or investigation into what properties the software satisfies, or how it behaves under certain conditions, yielding some form of concrete verification evidence ;and (3) justification , which is some form of warrant or reasoning by which developers believe 

that the collected verification evidence demonstrates alignment of the software artifact to their established intention. Each of these is essential: without a clear intention, one cannot distinguish software suitable for deployment from software that is unsuitable; without verification, one cannot predict what software will do when it is deployed; and without justification, one cannot know that verification evidence collected actually shows that software is aligned with one’s intention. In traditional (i.e., non-AI) software development, each of these components is present to some extent, though sometimes implicitly; this is especially true for justification. This lack of explicit justification is often tolerable, at least in part, because there are human developers who can be held accountable to provide a justification as to how a specification should be interpreted, why certain implementation decisions were made, or why certain forms of analysis were conducted. Agentic software development offers a radically different set of circumstances. 

Motivating Example. Consider a simple vibe coding scenario in which a developer prompts an agent to generate a Python program dedup () that removes duplicate elements from a list (Fig. 1, top left). As part of the task, the agent also crafts a small test suite (Fig. 1, top right). Supposing the generated code passes the tests, what should be the reason that one is confident that the program is aligned with the developer’s intention? As part of this inquiry, one could try to seek clarification about the intention itself: for instance, whether the intent is to remove all occurrences 

of duplicated elements, or merely to keep a single copy of each such element [10]; and having made AssureCode: Structured Justification for Trustworthy Agentic Coding 3

One could also scrutinize the diversity of the tests: for instance, if the test suite only considers homogeneous lists, one could ask whether this is sufficient, or whether the program is also expected to handle heterogeneous lists. Through the exercise of answering questions such as these, one can arrive at a more defensible justification for accepting the code (Fig. 1, bottom). These kinds of considerations often emerge naturally in traditional software development, a process which we, following Heimdahl, refer to as collateral validation [13]. We refer to the questions produced through this inquiry as collateral validation obligations , and we view the elicitation and resolution of these obligations to be an essential part of the justification process. In many agentic development settings, scrutiny of this kind is ultimately left to the developer to perform in an ad hoc 

fashion, using their own subjective judgment. This can lead to inconsistency within and between projects, as well as risk the deployment of code that “looks right” without having undergone sufficient scrutiny. Moreover, as the volume of generated artifacts and accompanying explanations increases, developers may face substantial cognitive demands in determining what requires scrutiny. To mitigate these issues, we seek to make justification an explicit and systematic part of agentic development. We find inspiration in the domain of safety-critical systems, in which this kind of justification is performed as a matter of course. 

2.2 Structured Assurance Cases 

In safety-critical systems engineering (automotive, aviation, etc.), organizations are expected to justify the safety of their systems through the use of structured assurance cases , i.e., structured arguments explaining how a system’s safety objectives have been achieved. Per the automotive safety standard ISO 26262: “ An argument without supporting evidence is unfounded. Evidence without an argument is unexplained, it can be unclear that, or how, safety objectives have been satisfied ” [16]. Various notations and languages for assurance cases have been developed, such as the Goal Structuring Notation (GSN [19]). GSN assurance cases are tree-like artifacts in which claims about a system, its environment, or its development (called goals ) are organized into a structured argument, with internal goals being decomposed via strategies into subgoals, and leaf goals being supported by evidence artifacts (called solutions ). Goals and strategies may be augmented with assumption 

nodes (e.g., about the interpretation of a goal), justification nodes (explaining the reasoning for a strategy), and context nodes (defining terminology or referencing relevant engineering artifacts). The main challenge with using assurance cases in agentic software development is that assurance cases are traditionally developed manually and iteratively, over a long period of time by teams of engineers and domain experts, while agentic software development expects rapid iteration and deployment. Thus, in order to gain assurance outcomes in agentic development in a similar fashion to those that are obtained under traditional assurance case development, we need to adapt the assurance case formalism – and the creation of these artifacts – to better support agentic software development. 

3 Justification Rationales for Agentic Coding 

As outlined in the previous section, our goal is to adapt the assurance case formalism to support the systematic and explicit justification of AI-generated code, while reducing the overhead imposed on software developers. In this section, we introduce a formalism for defining structured justification rationales (or simply rationales ) for agentic coding. AssureCode: Structured Justification for Trustworthy Agentic Coding 5

Our language retains the core argumentative structure of GSN in its representation of claims, decomposition strategies, assumptions, and evidence. However, unlike typical GSN-style assurance cases, our rationales also need to be amenable to automated construction and analysis; this enables agents to take on as much of the effort of constructing and analyzing the rationale as possible, allowing human developers to focus their attention only where it is truly needed. Any automated analyses should provide strong guarantees for certain properties of the rationale (e.g., the soundness of a decomposition or the validity of some evidence) as much as possible. To this end, our language of rationales uses (partial) formalization to enable the use of automated reasoning and analysis tools for such guarantees. 

3.1 Justification with (Partial) Formalization 

To support automated construction and analysis of justification rationales, we need a formal repre-sentation of at least some of the concepts to which the rationale refers. This formalization provides a basis for establishing justification properties mechanically, e.g., whether a set of statements about a program form a logically sound argument. However, defining and validating a complete formalization of the problem space would impose substantial specification and formalization effort on the developer. To mitigate this, we propose to define rationales using a partial formalization vocabulary in first-order logic. This vocabulary can be used to formalize only those aspects of the problem space which are straightforward to formalize, or are most essential to support structured argumentation, while allowing other aspects to remain formally uninterpreted. We define such a vocabulary as follows. Definition 1 (Vocabulary). A partial formalization vocabulary 𝑉 (or simply vocabulary ) is a pair (Σ, Γ), where Σ (called the signature ) defines a set of constant symbols, type symbols, function symbols, and predicate symbols, and Γ provides a partial theory over Σ, providing definitions to a subset of the symbols in Σ.

4 AssureCode: Assurance-Driven Vibe Coding 

In this section, we provide an overview of the AssureCode development methodology, which aims to support the creation of structured justification rationales as defined in Sec. 3 as part of agentic code generation. As illustrated in Fig. 4, AssureCode consists of three primary and incremental stages, each of which integrates human tasks, agentic tasks performed by LLMs, and automated reasoning and analysis support. We have developed a prototype of AssureCode as a Model Context Protocol (MCP, [15]) service. It is configurable by design: the models, automated reasoning support, claim decomposition strategies, and analysis tools are all determined by configurable registries. Our current prototype employs the Lean theorem prover [8] as a formalization backend and theorem prover, but our architecture is designed to accommodate alternative tools, e.g., SMT solvers [2]. 

4.1 Stage 1: Intent Formalization 

Intent formalization is the first stage in the workflow, transforming a natural-language specification (i.e., a prompt) into a partially formalized specification suitable for subsequent argumentation, as was done in Ex. 5. Unlike traditional upfront specification approaches, intent formalization in our setting is lazy . Given the input spec, the autoformalization agent proposes a formalization consisting of a vocabulary (as defined in Def. 1) and a functional correctness specification expressed in this vocabulary, both encoded in a formal language supporting mechanized reasoning (in our case, Lean) (Fig. 4-1a). The functional correctness specification uses an opaque identifier for the program (which at this stage, has not yet been generated). This formalization may not be complete or final; some predicates or functions may be uninterpreted. Additional formal interpretation is introduced only when required to support argumentation or verification tasks. Lean’s syntax and type system establish well-formedness of the formalization (Fig. 4-1b), after which the human reviewer judges whether the formalization captures their intent (Fig. 4-1c). If the formalization is approved by the human user, this formalization refinement is used to initialize the first layer of decomposition of the rationale (as illustrated in Fig. 3), before we proceed to subsequent argumentation. 1

4.2 Stage 2: Argumentation 

In this stage, the argumentation agent progressively develops undeveloped claims, ultimately producing a partial rationale populated with explicit verification and validation obligations. These obligations serve as placeholders for evidence that must subsequently be discharged through artifact generation (e.g., code, tests, or proofs) or human validation. Claim decomposition is guided by formal argument templates (or simply templates ), following recent work on automated assurance-case development [26, 32]. Templates define reusable argumentation patterns together with criteria for determining when their application yields a sound decomposition. Each template specifies (i) the shapes of formal claims it can decompose, implemented via regular-expression matching; (ii) an instantiation schema defining the data required to generate child claims; and (iii) a template for soundness proofs for instantiations of the template, which an agent completes after instantiation. In our implementation of AssureCode, the argumentation agent selects an applicable template from a template catalogue and generates the required instantiation data (Fig. 4-2a). Template application operates on the formal interpretation of the parent claim: the engine instantiates the corresponding Lean template and extracts the resulting formal subclaims, after which an agent completes the proof of decomposition soundness. Agents are also able to extend the formalization vocabulary to facilitate the decomposition and proof. The formal subclaims produced via the template are automatically reinterpreted in natural language via agentic informalization [37], yielding the subclaims presented in the user-facing rationale and used to formulate associated validation obligations (Fig. 4-2b). We do not currently perform a systematic check of semantic alignment between the formal and informalized subclaims; incorporating techniques for checking such alignment [22] is left to future work. Next, we attempt to verify the generated proof with Lean (Fig. 4-2c). If the instantiated decomposition cannot be verified, the agent may attempt an alternative instantiation or template, or defer to human intervention. In the latter case, the user’s approval is recorded as justification for the inference. Otherwise, we proceed to the next undeveloped claim. 4.3 Stage 3: Generation 

Having developed a partial rationale, AssureCode proceeds to generating evidence and obligations to support leaf claims using structured patterns(Fig. 4-3a). Following [26], we refer to these patterns as analytic templates, distinct from the logical templates used for argumentation (Stage 2). In the default configuration of AssureCode, a functional testing template is used to generate a test suite together with collateral validation obligations concerning its adequacy and underlying assumptions. These artifacts and obligations are then organized into a structured workflow of generation, analysis, and manual validation tasks. AssureCode then automatically executes this workflow, generating relevant artifacts, invoking available analysis tools (Fig. 4-3b), and referring obligations to the human user (Fig. 4-3c). For example, under the testing template, because the test oracle is associated with the corresponding formal claim in Lean, we can partially automate proof of their alignment when the formalization provides a sufficiently interpreted vocabulary and the alignment falls within our available proof automation. When such a proof succeeds, it is incorporated as evidence in the rationale; otherwise, the alignment remains an explicit human obligation, as illustrated in Fig. 3. For instance, mirroring the bottom layer of the rationale in Fig. 3, the testing template induces a workflow that generates and analyses the test suite before executing it against the generated implementation. The workflow first generates the test suite and verifies its alignment with the functional specification, after which the user reviews its adequacy before the tests are executed against the generated implementation. The precise ordering of these activities is a property of the analytic template and can be reconfigured; e.g., the template could defer human review until after test execution. Once all goals have been supported by appropriate evidence, with obligations approved by the user, the workflow terminates, resulting in a fully developed and approved rationale for the generated program. 

5 Empirical Evaluation 

In this section, we evaluate the degree to which AssureCode can support the development of 

assurance of correctness , comparing it with a practical baseline in which a developer uses an LLM to AssureCode: Structured Justification for Trustworthy Agentic Coding 11 

assist with assurance activities. Specifically, we consider a baseline process in which a developer iteratively uses an LLM to identify potential concerns and validation obligations that should be considered before accepting an AI-generated program as adequate on the basis of having passed a given test suite. We refer to this process as vibe justification . The baseline is intended to represent a plausible practical alternative to AssureCode, as it reflects the use of LLMs to support assurance activities without imposing a prescribed methodology for organizing the associated artifacts. Thus, we frame our evaluation around the following research questions:     

> RQ1 (Volume). How many collateral validation obligations does each approach generate?
> RQ2 (Coverage). To what extent does each approach address obligations produced by the other?
> RQ3 (Coverage basis). To what extent does partial formalization address obligations from the baseline?
> RQ4 (Assurance value). What is the assurance value of concerns identified by only one approach?

These questions centre the evaluation on collateral validation obligations because they provide the connective tissue between sources of assurance: the obligations themselves, together with the associated formalization, reasoning, and verification artifacts. Importantly, obligations generated by AssureCode cannot be interpreted independently of these artifacts, as they are defined relative to what other artifacts already establish; for example, an ambiguity resolved by an approved for-malization need not give rise to a separate validation obligation. Accordingly, our coverage analysis considers not only obligation-level correspondence but also, for AssureCode, the contribution of as-sociated formalization artifacts. We do not separately evaluate the individual stages of AssureCode, such as autoformalization [37], agentic theorem proving [18], agentic test generation [6], and code generation [23]. These constituent techniques have been, and continue to be, studied separately; our focus is on how artifacts generated by their integration through AssureCode collectively contribute to the assurance of correctness. Finally, our goal is not necessarily for AssureCode to significantly outperform vibe justification on every measure. Rather, because AssureCode provides a more structured and systematic process, evidence that it can achieve comparable degrees of assurance would support its credibility as an alternative to vibe justification. 

5.1 Evaluation Methodology 

We now describe the components of our evaluation process. 2

5.1.1 Evaluated benchmarks. We evaluated AssureCode and the vibe justification baseline on a set of prompt-based Python code generation tasks drawn from three established code-generation benchmarks: HumanEval, a widely used benchmark consisting of hand-written Python function-completion problems [5]; LiveCodeBench, which draws on recent, timestamped contest problems from LeetCode, AtCoder, and Codeforces [17]; and MBPP, which provides crowd-sourced, entry-level Python problems [1]. For all benchmarks, each task includes a representation of the program-ming problem, expressed in English, and a test suite used to assess the correctness of a candidate solution. Because our evaluation requires manual assessment of generated obligations and their potential assurance value, we randomly sampled ten problems from each benchmark, giving a corpus of 30 code-generation tasks. This sample size enables close inspection of the obligations and associated artifacts produced during the evaluation while keeping manual analysis feasible. 

5.1.2 Subject LLMs. We evaluate AssureCode using four contemporary general-purpose LLMs from several major providers: gpt-5.6-sol (OpenAI), claude-fable-5.1 (Anthropic), 

deepseek-v4-pro (DeepSeek), and gemini-3.1-pro (Google). This selection provides diversity

5.1.3 Baseline: Eliciting Obligations via “Vibe Justification”. At a high level, a prompt for vibe justification amounts to saying the following: “ Consider specification 𝑆 and test suite 𝑇 . What concerns, inquiries, or questions should a diligent software developer consider before accepting a program 𝑃 as an adequate solution to 𝑆 on the basis of having passed all tests in 𝑇 ?”. In preliminary explorations of “vibe justification”, we experimented with two styles which further elaborate the instructions for the LLM agent: a conservative style that instructs the agent to be careful in proposing an obligation only when there is a good reason to suspect potential misalignment between intention, specification, and test artifacts. The liberal style adopts a lower threshold for raising potential concerns. These preliminary explorations found that, while these strategies produced overlapping sets of obligations, the results of one rarely subsume those of the other. Thus, to generate a diverse set of obligations for our baseline, we employed both styles of prompt in our baseline generation. 

Iteration. Given the stochastic nature of LLMs, and to generate a diverse set of obligations for our baseline, we queried each of our subject LLMs 3 times with both the conservative and liberal prompt. Consequently, across the 120 trials, we obtain 2 · 3 · 120 = 720 sets of validation obligations. 

Deduplication. Having generated 6 sets of obligations for each trial, we applied a multi-stage deduplication process to obtain sets of unique obligations. First, we embed each obligation using 

BAAI/bge-large-en-v1.5 , an encoder model based on BERT [9], and compare the resulting vectors using cosine similarity, a common technique for measuring semantic similarity in natural-language processing [34]. Next, we deduplicate obligations within each generated set for a single iteration by clustering them according to their pairwise similarities. We use complete-linkage clustering at a cosine threshold of 0.85 for baseline obligations: every pair in a cluster must meet the threshold. Each cluster retains its original obligations and selects a medoid member as its representative. Candidate duplicate pairs identified through embedding-based comparison are also assessed by an LLM judge. We then deduplicate across the 𝑘 sets generated for a fixed task, LLM, and obligation-generation strategy, thereby aggregating obligations across iterations. We then deduplicate across prompting strategies, yielding one aggregated obligation set for each task and LLM. For AssureCode obligations, we use the same embedding model and complete-linkage procedure with a cosine threshold of 0.9. Both thresholds were chosen based on preliminary experiments; the difference between the thresholds is presumably due to the obligations generated by AssureCode being expressed in a somewhat different tone of language than those generated by the baseline. Finally, we manually review the resulting clusters to identify any outstanding duplicates or revert merges. 

5.1.4 Eliciting Obligations via AssureCode. For each task and subject LLM, we run AssureCode once on the task prompt. During these runs, the subject LLM performs all agentic actions in the workflow (formalization, decomposition, verification, and generation), and the resulting rationale tree is constrained to the three-layer structure shown in Fig. 3. We automatically approve review requests so that each run can proceed without human intervention during execution. This design choice allows us to evaluate the obligations and associated reasoning artifacts produced by Assure-Code under a fixed and reproducible execution protocol, without introducing additional variability from intermediate human decisions. The execution of AssureCode produces collateral validation obligations in the context of the generated assurance artifacts. The initial formalization creates human obligations concerning its fidelity to the task specification; logical argumentation templates AssureCode: Structured Justification for Trustworthy Agentic Coding 13 

induce human obligations concerning that decomposition before Lean checks the proof; and the test generation procedure likewise generates evidence adequacy obligations. We extract all of these, alongside their associated formalization artifacts. 

5.1.5 Comparing the Baseline and AssureCode Artifacts. To answer RQ2 , we assess mutual cover-age between the generated obligation sets by asking whether the artifacts produced by one approach would resolve the validation obligations raised by the other approach. We classify coverage as 

full , partial , or none . A partial coverage judgment is accompanied by a residual concern (e.g., a particular kind of edge case missing from a test suite). Our coverage assessment allows multiple obligations to collectively cover one obligation or one obligation to cover multiple obligations. Because AssureCode produces obligations in the context of additional assurance artifacts, coverage is assessed asymmetrically: baseline obligations can be covered by a combination of obligations and their associated formalization artifacts produced by AssureCode, whereas AssureCode obligations can only be covered by obligations produced by the baseline. Finally, to answer RQ4 , we assess the potential assurance value of concerns identified by only one approach. For obligations that the other approach does not fully address in RQ2, we first identify the concern that remains unaddressed: the aspect of the specification, test, or justification process that the obligation raises and the other approach does not account for. Obligations that raise the same underlying concern are merged, such that a single concern may correspond to multiple obligations. Each concern is then classified as “Strong”, “Fair”, or “Weak” according to the degree of assurance value it provides. In particular, we consider whether the concern identifies a substantive issue that a careful developer could otherwise overlook (Strong), provides a useful but limited or partially redundant assurance consideration (Fair), or is obvious, tautological, overly broad, or otherwise unlikely to affect the developer’s assessment of correctness (Weak). For RQ2 –RQ4 , we use the same LLM judge ( gpt-5.6-sol ) to produce an assessments based on our evaluation criteria for each RQ . The judging prompts were iteratively refined before the full experiment to ensure conformance with these criteria. We additionally conducted a post hoc 

review of 307 randomly sampled decisions: 102 for RQ2 , 101 for RQ3 , and 104 for RQ4 . Alignment with the intended criteria was 96% for RQ2 , 100% for RQ3 , and 84% for RQ4 . The lower alignment for RQ4 was consistently conservative, with some concerns classified as Weak” rather than “Fair” and “Fair” rather than Strong”. We determined that these results were acceptable, so long as this tendency is kept in mind when interpreting the RQ4 results.

Threats to Validity. Obligation count is only a proxy for scope: more obligations can mean more issues found, but also more review burden. Coverage also depends on obligation granularity, since a broad obligation is more likely to be judged as “fully” covering a concern than a narrow one, so coverage percentages partly reflect how each approach phrases its obligations. Usefulness (Strong/Fair/Weak) is an ordinal judgment, not evidence that a concern exposes a real defect. Finally, we do not measure effort or subjectivity directly; we simply argue that producing roughly equivalent sets of obligations via AssureCode is a preferable alternative to “vibe justification” due to its more structured nature. The greatest threat is likely our use of an LLM judge. The judge, gpt-5.6-sol , is also one of the four subject models, so it may favour obligations phrased in its own style. To mitigate known judgment and position biases [35], the LLM judge sees the AssureCode: Structured Justification for Trustworthy Agentic Coding 17 

two obligation sets under anonymized labels and in random order, and we manually validate its output. These measures reduce but do not eliminate the risk, as phrasing may still reveal which set is which, and manual validation is prone to error and bias. Nondeterminism in AssureCode executions could shift the results, as we only executed the tool once for each task. Our benchmarks (HumanEval, LiveCodeBench, MBPP) are small, self-contained, well-specified tasks, and results may not generalize to larger, more complex software projects. 

6 Discussion 

AssureCode, provides a structured mechanism for eliciting collateral validation obligations during AI-assisted software development. Rather than relying on an engineer to identify concerns through ad hoc inspection of generated artifacts, AssureCode organizes these concerns within a broader argument structure that relates specifications, formalizations, verification artifacts, and residual questions requiring human judgment. Our evaluation provides initial evidence that this approach can achieve comparable assurance support to a practical vibe-justification baseline: a single Assure-Code execution recovered most concerns identified through multiple unstructured prompts while also surfacing additional concerns. Moreover, the coverage analysis highlights that this support arises from the complementary roles of formalization artifacts and validation obligations. Several important aspects of properly evaluating AssureCode remain open. Our evaluation con-sidered a relatively small number of samples from three benchmarks consisting primarily of small, well-specified programming tasks; larger and more diverse datasets are needed to understand how the approach generalizes to more realistic software development settings. We also evaluated only four contemporary high-capability LLMs, and further investigation is needed to understand how the methodology behaves with smaller or less capable models. Finally, our evaluation prioritized the assurance artifacts and obligations produced by AssureCode over the practical costs of producing them. Studies measuring token usage, developer effort, and the effect of AssureCode on human decision-making and review practices would provide important evidence about its practicality. 

7 Related Work 

Trustworthy Agentic Software Development. As AI-supported software development becomes in-creasingly commonplace, trust in AI-generated artifacts has received growing attention in software engineering. Roychoudhury et al. [28] identify nine trustworthiness factors spanning human and technical concerns. Our current implementation of AssureCode primarily addresses correctness 

and explainability and trustworthiness , and incorporates several of their identified contributors to trust: testing and static analysis, including validation of test oracles; formal proofs; and human–AI collaboration. Analysis and proofs are central to our design, as is human–AI collaboration, although the effectiveness of the latter has yet to be evaluated. Other contributors identified by Roychoudhury et al., including security guardrails and specification inference from software artifacts, are outside the current scope of AssureCode, but could be incorporated within its general architecture. Khati et al. [20] similarly identify correctness and understandability as the concepts most frequently associated with trust in LLM-based software engineering. Brun et al. [4] propose a research roadmap combining interactive specification synthesis, agentic code generation, and static analysis and testing for trustworthy agentic development. At a high level, this corresponds to the activities integrated by AssureCode; our contribution is to relate these activities through collateral validation obligations and organize their outputs into a structured justification rationale. AssureCode was developed following an earlier proposal by some of the present authors in adapting assurance cases as explanations for the adequacy of AI-generated artifacts [25]. The most significant difference between this proposal and AssureCode is using the development of the justification rationale to 

drive the generation of code, rather than attempting to argue for its adequacy post hoc .18 Murphy et al. 

Existing frameworks and methodologies for agentic engineering use various strategies to support these aspects of trustworthiness, including constraining agent actions and providing execution feedback [39], and prescribing engineering workflows for agents to follow [3, 14, 38]. TiCoder [11] is particularly close to AssureCode in combining automated development with human valida-tion.TiCoder generates candidate programs and tests, with users confirming or correcting individual tests to prune and rank candidates. TiCoder also formalizes intent through instance-level tests and uses human feedback to select among candidate programs. In contrast, AssureCode formalizes intent as a machine-checkable specification, uses it to verify the alignment of generated tests, and surfaces evidence adequacy and residual assumptions as explicit collateral validation obligations. Although our current prototype supports only functional testing, the approach is not limited in principle to testing as a source of evidence. To the best of our knowledge, AssureCode is the first agentic development methodology to explicitly structure justification through argumentation inspired by assurance cases in safety-critical systems. Assurance cases have been widely adopted in safety-critical engineering, supported by a substantial literature on their design, analysis, and maintenance; AssureCode is a first step towards adapting these techniques for agentic software engineering. 

Formal Methods for Agentic Coding. Formal methods have been identified as a promising com-ponent of trustworthy agentic software development [4, 28], as they can reduce ambiguities in natural-language prompts and provide machine-checkable guarantees that generated artifacts satisfy specified properties. Existing work explores several ways of incorporating these capabilities into LLM-based development. Endres et al. [10] study the ability of LLMs to translate natural-language tasks into formal postconditions that can be checked as program assertions. VeCoGen [30] combines LLM-based program generation with compiler and formal-verification feedback to itera-tively refine C programs against a provided specification. Other approaches integrate LLM-based code generation with proof assistants to verify correctness properties [24, 31]. FORGE [36] supports vibe coding in high-assurance domains through a closed-loop generation and verification process: LLM-generated Java is treated as an initial draft, transformed into several formal artifacts, and refined in response to verification failures translated into structured correction prompts. Like AssureCode, FORGE combines generation, verification, structured feedback, and backtracking, but the approaches differ in how they handle the assumptions underlying this process. FORGE derives its formal artifacts from the generated implementation, whereas AssureCode formalizes intent from natural language, and makes the fidelity of formalization a validation obligation. 

Agentic Assurance Case Development. Odu et al. [27] automate assurance-case creation by in-stantiating structured assurance-case patterns, although these patterns are primarily structural 

rather than the semantically grounded templates employed by AssureCode. Trusta [7] uses LLMs to construct and verify Trustworthiness Derivation Trees (TDTs), an assurance-case-like formalism that, like our rationales, supports formal/informal expression pairs and automated reasoning over argument structures. Viger et al. [33] investigate LLM-generated defeaters for scrutinizing and refining assurance cases. These works primarily seek to improve safety-assurance practice using LLMs, whereas AssureCode adapts assurance-case techniques to agentic software development. These efforts are complementary: insights from established assurance practice can inform agentic development (as in this work), while agentic development provides a new setting in which assurance case techniques can be extended and evaluated. 

8 Conclusion 

In this paper, we introduced justification rationales for agentic coding that make explicit the claims made about generated code, the evidence offered for them, and the collateral validation AssureCode: Structured Justification for Trustworthy Agentic Coding 19 

obligations a developer should address before trusting that code. We described AssureCode, a tool-supported methodology that creates such rationales during agentic code generation through autoformalization, theorem proving, and agentic artifact generation. Our evaluation suggests that AssureCode provides comparable assurance support to prompt-based vibe justification , while using partial formalization and structured argumentation to systematically generate and organize valida-tion obligations. These results support AssureCode as a credible option for building correctness assurance in AI-assisted software development. Several directions for future research follow from this work. First, user studies are needed to assess the effectiveness of AssureCode in practice, including how it affects developers’ understanding of and trust in generated code, and to identify practical barriers to adoption. Second, we plan to extend justification rationales beyond functional correctness to design constraints, nonfunctional and normative requirements, and security. Third, we plan to apply AssureCode to larger software projects, especially where assurance concerns interaction between components.

## 摘要
使用编码智能体进行软件开发时，往往始于一个粗略的需求，用户在试用实现之后会对其加以细化。仅凭最终的 correct 性无法体现这一过程所需的反复指导。我们提出 FeatureLoop，这是一个包含 61 个经人工审核任务的基准，任务来自 34 个代码仓库，涵盖五种主要编程语言和七种软件形态。每个任务在持久化工作区中围绕一个开发目标推进，并经历演化反馈（新增或澄清需求）与完成反馈（报告已声明需求的失败情况）。累积式可执行检查用于追踪新增行为、修复情况以及对既有功能的保持。我们评估了 12 个前沿模型，发现最强模型在同时具备两类反馈时完成了 72.1% 的任务。然而，在各模型之间，观测到的失败阶段中仅有 15.4% 能在两次纠正性修订内恢复。进一步分析揭示了修复不完整、功能回退，以及模型在反馈利用和 token 效率上的差异，指出了实现可靠、低干预开发的障碍。

## Abstract
Software development with coding agents often begins with a rough request that users refine after trying the implementation. Final correctness alone does not capture the repeated guidance this process requires. We introduce FeatureLoop, a benchmark of 61 human-reviewed tasks from 34 repositories across five primary programming languages and seven software forms. Each task follows one development goal in a persistent workspace through evolution feedback, which adds or clarifies requirements, and completion feedback, which reports failures of stated requirements. Cumulative executable checks track new behavior, repair, and preservation of earlier functionality. We evaluate 12 frontier models and find that the strongest completes 72.1% of tasks with both feedback types. Across models, however, only 15.4% of observed failed stages recover within two corrective revisions. Further analysis reveals incomplete repairs, regressions, and model-specific differences in feedback use and token efficiency, identifying obstacles to reliable, low-intervention development.

## 1. 核心问题与研究动机

- **背景**：真实软件开发中，用户通常只给出一句粗略请求，然后在试用实现后反复补充需求、报告 bug。编码智能体（coding agent）虽然能读仓库、改代码、跑命令，但"最终是否正确"这一单一指标无法刻画它在这个过程中需要多少**重复的人工指导**。
- **核心问题**：当用户追加需求或报告失败时，智能体的下一次修订能否让**整个累积实现**变好？还需要多少额外指导？
- **现有基准的缺口**：
  - SWE-bench / Multi-SWE-bench / FeatureBench / Terminal-Bench 等只评"最终补丁是否正确"，不记录中间演化路径；
  - 交互式基准（SWE-Interact、SWE-Together、Asuka-Bench）评"对用户消息的响应"，但缺少与固定可执行检查绑定的**累积正确性**；
  - 序列式基准（EvoCode-Bench、LoopsBench）检查早期需求保持，但反馈不随当前工作区状态动态披露。
- **关键区分**：论文提出两类用户干预——
  - **Evolution feedback（演化反馈）**：新增或澄清需求，改变"软件应该做什么"；
  - **Completion feedback（完成反馈）**：报告已声明需求的失败，指出"还没做完/做坏了"。
- **整体含义**：把"需求演进 + 纠错 + 回归保持"三者耦合进同一个持久工作区，使"交付质量"与"所需指导量"成为可分别测量的两个维度。

## 2. 方法论

### 2.1 任务形式化

- 任务从固定仓库检查点 $W_0$ 出发，围绕**一个用户可见的开发目标**展开；后续请求逐步细化能力、约束与交互。
- 需求被组织成**需求组**，组间构成有向无环图（DAG），边 $g \to h$ 表示 $h$ 依赖 $g$；按依赖展开为固定阶段序列。
- 第 $i$ 阶段新引入组为 $A_i$，累积需求状态 $Q_i$ 单调递增：
  $$Q_1 = A_1,\quad Q_{i+1} = Q_i \cup A_{i+1},\quad Q_1 \subset \cdots \subset Q_K$$
- **三层检查**：
  - 组级检查 $Z_g(W)$：某需求组是否通过；
  - 前缀检查 $P_i(W) = \mathbf{1}[\forall g \in Q_i,\, Z_g(W)=1]$：迄今所有需求是否同时通过；
  - 基线检查 $b(W)$：任务开始前仓库原有行为是否仍正常；
  - 综合 $C_i(W) = b(W)\,P_i(W)$，最终成功定义为 $\text{Success}(W_T) = C_K(W_T)$。

### 2.2 状态依赖的反馈机制

- 控制器在下一次披露前先检查当前工作区：**已实现的行为跳过披露**，只发送仍然缺失的部分（部分满足则只报剩余行为）。
- 完成反馈由**固定生成器**（Hy4-Preview，高推理强度，单次≤20,000 token）基于"失败检查 → 预定义公开观察点"映射，挑选至多两条可观察现象，用自然语言表述；不暴露隐藏测试 ID、断言、参考实现或未来需求。
- 每个阶段最多允许 **2 次纠正性修订**，之后无论是否通过都推进到下一阶段，且早期需求始终保持为活跃义务。

### 2.3 三种开发场景（同一目标、同一检查点、独立执行）

| 场景 | 信息给予方式 | 用途 |
|---|---|---|
| **Full** | 一次性给出完整规格，单次会话交付 | 衡量"信息完备时"的实现能力 |
| **Evo** | 初始请求 + 逐步披露缺失需求，无纠错 | 衡量"自行验证 + 集成新需求"能力 |
| **Evo+Comp** | 在 Evo 基础上追加失败报告与最多两次修订（主场景） | 衡量"利用两类反馈"的能力 |

### 2.4 基准构建流水线（作者–评审者分离）

1. **锚定真实需求**：每个候选任务需至少 2 个完整公开 issue 支撑同一用户方向，并记录 issue 文本、动机、公开接口与仓库证据。
2. **行为规格与需求序列**：撰写完整用户目标、验收要求、范围排除项；构建需求 DAG 并选出符合依赖的阶段序列；每个组记录动作/输入、期望与禁止结果、需保持的旧行为、允许的实现自由度、可运行检查。
3. **冻结契约 Γ**：统一请求、测试与参考实现；独立评审确认可经公开接口观察、不泄露未来需求。
4. **测试与参考实现隔离构建**：Test Author 与 Reference Author 使用**不同工作区、不同模型家族**，互不可见对方的实现与执行结果。
5. **历史污染筛查**：在冻结测试后、构建参考实现前，用测试回放检查点之后的公开仓库历史；若后续历史已通过完整行为集则剔除该候选。
6. **跨状态验证**：对每个 $g \in A_i$ 要求 $Z_g(W^*_{i-1})=0$ 且 $Z_g(W^*_j)=1\ (\forall j \ge i)$；每个检查点须通过基线与此前全部需求；另加"合法替代实现"（测接受度）与"定向缺陷变体"（测检出率）两类探针。
7. **人工审查 + 试跑**：审查者逐轮复现对话、运行参考检查点与测试；随后由 4 个模型（Hy3、DeepSeek V4 Flash、DeepSeek V4 Pro、GLM 5.3）实跑，据轨迹缺陷回退重修。最终 123 个候选中保留 **61 个**。

### 2.5 评价指标

- **StrictPass**：最终所有需求组 + 基线全部通过（最严格）。
- **NodeCredit**：最终需求组的平均通过比例（部分得分）。
- **FDAC（Feedback-Discounted Agent Completion）**：对"何时变正确"打折的几何平均——
  $$q_i=\begin{cases}1 & \text{披露前已通过 或 初始首响应通过}\\ 0.5 & \text{后续阶段披露后立即通过}\\ 0.5\times0.4^{r} & \text{第 } r\in\{1,2\} \text{ 次修订后通过}\\ 0 & \text{预算内未通过}\end{cases},\quad \text{FDAC}=\text{StrictPass}\cdot\left(\prod_{i\in I}q_i\right)^{1/|I|}$$
  即"任何未在预算内解决的状态直接归零"，同时惩罚晚解决。
- **IUD / ICD**：初始可用交付 / 初始即满足最终冻结需求。
- **Recover@1 / @2**：观测到的首响应失败状态在 1 / 2 次修订内恢复的比例。
- **Retention（观测保持率）**：曾通过的需求在后续观测与最终检查中仍通过的比例。
- **SER@r**：所有累积阶段均在 r 次修订内通过的轨迹比例。
- **PCC**：严格"可预见"需求组（$N\ge2, X\ge2, C\le1$）的披露前覆盖率。
- **NE / NC**：每任务平均演化 / 完成反馈消息数；**Agent Tokens**：报告输入+输出 token 总量。

## 6. 主要结论与发现

- **交互流程本身构成难度，而非只是提高平均分**：最终成功率 Full 40.3% → Evo 51.6% → Evo+Comp 64.1%；最佳模型 GPT-6 Astra 在 Evo+Comp 下 72.1%（FDAC 46.5）。"一次性给全规格"并非最优路径。
- **纠错是指导量差异的主要来源**：演化消息数在各模型间几乎一致（2.23–2.36），完成反馈数从 <1.9 到 4.03 不等；即使 4 个模型同样完成 43/61，其 FDAC 与所需指导仍不同。
- **局部成功 ≠ 整体正确**：对"后续新信息"组，首响应实现新行为达 77.3%，但其中 10.6% 仍留有其他已声明需求未完成（全样本 136/1078）。
- **失败报告很少带来完整修复**：733 个可观测失败状态中仅 **15.4%** 在两次修订内整体恢复（Recover@1 = 13.0%）；455 个失败需求组中局部修复率 20.0%，而其中 **20.9%** 的"修复成功"仍留下其他需求未满足。
- **回归普遍存在**：642 个曾通过且有后续观测的需求组中，**11.4%** 在后续阶段失败（保持率 88.6%）；NextChat 案例中一次局部修复后引入 `message.content is not iterable`，错误贯穿后续四个阶段并累积 15 次回归。
- **验证常偏离真实执行路径**：263 次最终失败中 **75.3%** 存在"未检查相关用户路径"或"验证了 helper/stub/代理"的问题。
- **共享状态一致性是共性难题**：在"无模型解出"的任务上占最终失败 32.4%，而在"有模型解出"的任务上

（接上）在“有模型解出”的任务上，这一比例明显更低，说明共享状态一致性更像是区分任务级可解性的关键瓶颈，而非普遍性的小故障。换言之，当任务涉及跨阶段持久状态、并发/缓存/会话一致性时，智能体往往不是“不会写某个函数”，而是无法在多次修订中维持全局不变量。

- **模型差异主要体现在纠错效率，而非初始实现能力**：各模型在 Evo 阶段的演化消息数接近，说明“接收新需求”的交互成本相对稳定；真正拉开差距的是完成反馈后的定位、修复与回归控制能力。FDAC 将“晚解决”和“未解决”区分开，因而比最终成功率更能揭示指导效率差异。
- **完成反馈数量不能简单解释为能力指标**：反馈多既可能来自智能体主动暴露问题，也可能来自其反复失败后触发更多纠正；因此论文将 NE/NC 与 Recover、Retention、FDAC 联合解读，而非把消息数当作单一优劣标准。
- **“通过检查”与“正确交付”之间仍有缝隙**：局部修复后遗留其他已声明需求、修复引入回归、验证偏离真实用户路径，三者共同解释了为何最终 StrictPass 明显低于局部通过率。基准的价值在于把这类“看似完成、实则未完成”的状态显式暴露出来。
- **需求可预见性影响披露前覆盖，但不完全决定最终表现**：方向可预见或严格主动队列中，部分智能体能在披露前覆盖若干需求；然而披露前覆盖高并不保证累积前缀闭合，早期局部正确仍可能在后续阶段被回归或共享状态问题抵消。
- **语言与软件形态的差异需谨慎解读**：CLI/Service 等形态的完成率与恢复率存在差异，但语言与形态高度共线、部分子群样本较小，当前证据更适合作为“任务生态分布”的描述，而非语言能力的因果结论。

## 7. 局限与讨论

- **统计重复不足**：每模型–任务–协议仅运行一次，虽用 Wilson 区间与仓库聚类 bootstrap 控制不确定性，但无法估计同一模型在同一任务上的采样方差；对接近的模型排名应保守解读。
- **构造成本与外部效度**：61 个任务经过多智能体作者–评审者流水线、污染筛查、跨状态验证和人工复核，标签可信度较高，但构建成本也限制了任务规模与领域覆盖；34 个仓库、5 种主语言仍不能代表全部软件生态。
- **反馈生成器的固定性**：完成反馈由固定生成器按“失败检查→公开观察点”映射生成，有利于可复现性，但也意味着结论依赖该反馈策略；更自然、更模糊或更具误导性的用户反馈可能改变模型表现排序。
- **缺少组件消融**：论文没有系统报告去掉污染筛查、替代实现探针、缺陷变体或两类反馈中的某一类后，基准难度与判别力如何变化；因此构建流程各环节对最终结论的贡献仍是间接推断。
- **指标解释成本**：FDAC、Recover、Retention、SER、PCC 等指标从不同粒度刻画指导效率，信息丰富但组合解读门槛较高；实际使用时需明确研究问题是“最终正确”“多快正确”还是“少要多少指导”。

## 8. 总体评价

FeatureLoop 的核心贡献不是再增加一个“更难”的代码基准，而是把**需求演化、失败纠正与回归保持**放入同一持久工作区，并将“交付质量”和“所需人工指导量”拆成可分别测量的维度。其任务形式化、状态依赖反馈、作者–评审者隔离和跨状态验证设计较严谨，FDAC 等指标也提供了比单一通过率更细的判别力。主要不足在于单次运行、任务生态偏斜和缺少构建组件消融；这些限制不影响其作为“交互式编码智能体指导效率”评测框架的价值，但意味着模型排名与语言/形态结论应结合置信区间和任务分布谨慎外推。
